# 5장. 클래스

[파이썬 기초](README.md) 과정의 다섯 번째 장이다. 4장에서는 일을 함수로 나누었다. 그런데 실습 4-7의 도서 대출 프로그램을 떠올려 보면, `borrow(loans, ...)`, `return_book(loans, ...)`, `loan_lines(loans, ...)`처럼 **모든 함수에 같은 데이터(`loans`)를 계속 넘겨야** 했다. 데이터는 `main()`에, 그 데이터를 다루는 함수는 파일 여기저기에 흩어져 있었다. 이 장에서는 **데이터와 그 데이터를 다루는 함수를 한 덩어리로 묶는 방법**, 즉 클래스를 배운다.

- **클래스와 객체** — `class`로 나만의 자료형을 만들고, `__init__`으로 객체가 가질 데이터(속성)를 정하고, 객체에 붙여 쓰는 함수(메서드)를 만든다. 메서드의 첫 매개변수 `self`가 무엇인지 이해한다.
- **클래스 설계 기초** — 모든 객체가 함께 쓰는 값(클래스 속성)과 객체마다 따로 가지는 값(인스턴스 속성)을 구분한다. `print()`했을 때 보기 좋게 나오도록 `__str__`과 `__repr__`을 만든다. 바깥에서 함부로 바꾸면 안 되는 속성을 `_이름`과 `@property`로 보호한다.
- **상속** — 이미 있는 클래스를 바탕으로 기능을 더하거나 바꾼 새 클래스를 만든다(`super()`, 메서드 오버라이딩). `isinstance()`가 상속을 어떻게 다루는지 이해한다.
- **데이터 클래스** — 타입 힌트(`name: str`)를 읽고 쓰며, `@dataclass`로 "데이터 묶음"을 짧게 정의한다. 딕셔너리 대신 데이터 클래스를 쓰면 좋은 경우를 판단한다.

AI 엔지니어가 쓰는 라이브러리는 거의 모두 클래스로 되어 있다. LLM API를 쓸 때는 `client = OpenAI()`처럼 **클래스로 객체를 만들고**, `client.chat.completions.create(...)`처럼 **객체의 메서드를 호출**한다. 응답도 `response.choices[0].message.content`처럼 **객체의 속성을 따라가며** 꺼낸다. LLM이 돌려줄 데이터의 모양을 정할 때는 `class Answer(BaseModel):` 아래에 `title: str`, `score: int`처럼 **타입 힌트가 붙은 필드**를 늘어놓는다(이 장의 데이터 클래스와 같은 모양이다). 이 장을 마치면 그런 코드를 보고 "어떤 클래스로 어떤 객체를 만들었고, 무엇을 꺼내 쓰는지" 읽을 수 있고, 자신의 프로그램도 클래스로 정리할 수 있게 된다.

## 학습 목표

이 장을 마치면 다음을 할 수 있다.

- 클래스와 객체(인스턴스)의 관계를 설명하고, `int`, `list`, `date`처럼 이미 써 온 자료형도 클래스라는 것을 안다.
- `class`로 클래스를 정의하고, `__init__`에서 인스턴스 속성을 만들고, 객체를 만들어 속성과 메서드를 쓸 수 있다.
- `a.deposit(1000)`이 `Account.deposit(a, 1000)`과 같다는 것으로 `self`의 의미를 설명할 수 있다.
- 클래스 속성과 인스턴스 속성을 구분하고, 가변 객체를 클래스 속성으로 두면 생기는 문제를 피할 수 있다.
- `__str__`과 `__repr__`을 정의해 객체가 `print()`와 대화형 셸에서 보기 좋게 나오도록 만들 수 있다.
- `_이름` 관례와 `@property`로 바깥에서 바꾸면 안 되는 속성을 읽기 전용으로 공개할 수 있다.
- 부모 클래스를 상속한 자식 클래스를 만들고, 메서드를 오버라이딩하고, `super()`로 부모의 메서드를 호출할 수 있다.
- `isinstance()`가 상속 관계까지 고려해 판단한다는 것을 설명할 수 있다.
- 타입 힌트의 기본 형태를 읽고 쓰며, `@dataclass`로 데이터 클래스를 정의하고, 일반 클래스·딕셔너리와의 차이를 설명할 수 있다.
- VS Code 디버거로 메서드 안에 들어가 `self`가 가리키는 객체의 속성을 확인할 수 있다.

**대화형 셸에 붙여 넣는 클래스 코드**

이 장의 클래스는 4장의 함수보다 길어서, 앞에 `>>>`와 `...`를 붙여 보여 주면 복사해 쓰기 불편하다. 그래서 대화형 셸에서 정의할 클래스는 **프롬프트 없이 별도의 코드 블록으로** 보여 주고, 그 클래스를 쓰는 코드는 바로 뒤의 `>>>` 블록으로 보여 준다. 공부하는 방법은 다음과 같다.

1. 클래스 코드 블록을 그대로 복사해 셸의 `>>>` 프롬프트에 붙여 넣는다.
2. `>>>` 프롬프트가 다시 나올 때까지 Enter를 누른다(한두 번). 그러면 클래스 정의가 끝난다.
3. 이어지는 `>>>` 블록의 코드를 같은 셸에서 한 줄씩 입력해 결과를 확인한다.

붙여 넣을 클래스 코드에는 **메서드 사이에 빈 줄이 없다.** 셸에서는 빈 줄이 "정의 끝"이라는 뜻이라서, 붙여 넣은 코드를 한 줄씩 처리하는 셸(파이썬 3.12 이하)에서는 클래스 안의 빈 줄이 오류를 일으키기 때문이다. 클래스를 직접 타이핑할 때도 마찬가지로 클래스 안에는 빈 줄을 넣지 않는다(`class ...:` 줄 다음부터 프롬프트가 `...`로 바뀌는 것은 4장에서 본 것과 같다). 반면 스크립트 파일에서는 메서드 사이에 빈 줄 한 줄을 넣는 것이 관례다(Ruff 포매터가 맞춰 준다).

> **붙여 넣었는데 `IndentationError`가 나면**
> 파이썬 3.13부터의 대화형 셸은 `:`로 끝나는 줄 다음에 들여쓰기를 자동으로 넣어 준다. 터미널이 붙여 넣은 내용을 키보드로 한 글자씩 친 것처럼 보내면 이 자동 들여쓰기가 겹쳐서 `IndentationError: unexpected indent`가 날 수 있다. 이때는 셸에서 **F3** 키를 눌러 붙여넣기 모드(`(paste)` 표시)로 바꾼 뒤 붙여 넣고, F3을 다시 눌러 붙여넣기 모드를 끝낸 다음 Enter를 누른다. 셸 사용이 번거로우면 클래스와 사용하는 코드를 스크립트 파일에 함께 쓰고 실행해도 된다.

그 밖에 `>>>`가 없는 코드는 스크립트 파일에서 실행하는 코드다. 본문에서 첫 줄이 `class`나 `@dataclass`로 시작하는 블록은 셸에 붙여 넣는 클래스 코드이고, 첫 줄에 `# account.py` 같은 파일 이름이나 실습의 `# (가)` 같은 표시가 있으면 스크립트 파일 코드라고 구분하면 된다.

> **1단계를 마친 사람에게**
> AI가 만들어 준 코드에서 `class TodoItem:`, `def __init__(self, title):`, `self.items = []` 같은 줄을 보았을 것이다. 모든 메서드의 첫 매개변수가 `self`인데 호출할 때는 아무도 `self`를 넘기지 않는 것이 이상했을 수도 있고, `@dataclass`, `@property` 같은 `@` 줄이나 `name: str` 같은 표기가 무슨 뜻인지 몰라 그냥 넘어갔을 수도 있다. 이 장은 그 줄들을 하나씩 풀어 읽는 장이다. 3장의 "변수는 객체에 붙인 이름표"와 4장의 "함수도 객체"를 기억하고 있다면, 클래스도 결국 그 두 생각의 연장이라는 것을 알게 된다.

## 5.1 클래스와 객체

이 절에서는 클래스를 만들고, 그 클래스로 객체를 만들어 쓰는 방법을 배운다. 먼저 클래스가 **왜** 필요한지부터 보자.

### 5.1.1 왜 클래스가 필요한가

은행 계좌 두 개를 관리하는 프로그램을 3·4장에서 배운 것만으로 만들어 보자. 계좌 하나는 "예금주와 잔액"을 함께 가지므로 딕셔너리로 표현하고, 입금과 출금은 함수로 만든다.

```python
# account_dict.py
def deposit(account, amount):
    """account 계좌에 amount원을 입금한다."""
    account["balance"] += amount


def withdraw(account, amount):
    """account 계좌에서 amount원을 출금한다. 잔액이 모자라면 False를 돌려준다."""
    if amount > account["balance"]:
        return False
    account["balance"] -= amount
    return True


chulsoo = {"owner": "철수", "balance": 10000}
younghee = {"owner": "영희", "balance": 5000}

deposit(chulsoo, 3000)
withdraw(younghee, 2000)
print(chulsoo)
print(younghee)
```

```
{'owner': '철수', 'balance': 13000}
{'owner': '영희', 'balance': 3000}
```

잘 동작한다. 4.3.5에서 배운 대로 딕셔너리를 함수에 넘기면 함수 안에서 바꾼 내용이 호출한 쪽에 보인다. 그런데 프로그램이 커지면 문제가 드러난다.

1. **데이터와 기능이 따로 논다.** "계좌"라는 데이터는 딕셔너리로, "입금"과 "출금"이라는 기능은 함수로 흩어져 있다. 계좌로 무엇을 할 수 있는지 알려면 파일 전체에서 `account`를 받는 함수를 찾아봐야 한다.
2. **아무 딕셔너리나 넘길 수 있다.** `deposit({"name": "커피", "price": 2500}, 1000)`처럼 엉뚱한 딕셔너리를 넘겨도 파이썬은 막지 않는다. 실행해 봐야 `KeyError`가 난다.
3. **키 이름을 틀리기 쉽다.** `{"owner": "민수", "balence": 0}`처럼 키 이름에 오타를 내면, 그 계좌로 입금할 때가 되어서야 오류가 난다. VS Code도 딕셔너리 키는 자동 완성해 주지 못한다.
4. **데이터를 매번 넘겨야 한다.** 모든 함수 호출에 `chulsoo`, `younghee`를 첫 인자로 넘긴다. 실습 4-7에서 모든 함수에 `loans`를 넘겨야 했던 것과 같다.

**클래스**(class)는 이 문제를 해결한다. "계좌는 예금주와 잔액을 가지고, 입금과 출금을 할 수 있다"를 **한곳에 정의**해 두고, 그 정의로 계좌를 여러 개 만들어 쓴다. 클래스로 고친 코드를 먼저 보자. 아직 문법은 몰라도 된다. 아래쪽 사용하는 부분만 읽어 보자.

```python
# account_class.py
class Account:
    def __init__(self, owner, balance=0):
        self.owner = owner
        self.balance = balance

    def deposit(self, amount):
        self.balance += amount

    def withdraw(self, amount):
        if amount > self.balance:
            return False
        self.balance -= amount
        return True


chulsoo = Account("철수", 10000)
younghee = Account("영희", 5000)

chulsoo.deposit(3000)
younghee.withdraw(2000)
print(chulsoo.owner, chulsoo.balance)
print(younghee.owner, younghee.balance)
```

```
철수 13000
영희 3000
```

`deposit(chulsoo, 3000)`이 `chulsoo.deposit(3000)`이 되었다. `"hello".upper()`처럼 **값 뒤에 점을 찍고 기능을 부른다.** 계좌로 할 수 있는 일은 모두 `class Account:` 안에 모여 있고, 잔액은 `chulsoo["balance"]` 대신 `chulsoo.balance`로 읽는다. 이 절이 끝나면 위 코드의 모든 줄을 읽을 수 있게 된다.

### 5.1.2 클래스와 객체 — 우리는 이미 클래스를 써 왔다

클래스라는 말이 처음 나왔지만, 사실 우리는 2장부터 클래스를 써 왔다.

```python
>>> type(10)
<class 'int'>
>>> type("hello")
<class 'str'>
>>> type([1, 2])
<class 'list'>
```

2장에서 `type()`이 보여 주는 `<class 'int'>`를 "int라는 종류의 값"이라고 읽었다. 정확히는 "**`int`라는 클래스의 객체**"라는 뜻이다. 파이썬에서 자료형과 클래스는 같은 말이다.

- **클래스**: 어떤 종류의 값이 **어떤 데이터를 가지고 무엇을 할 수 있는지** 정의한 것. 설계도나 틀에 해당한다. `int`, `str`, `list`, `dict`가 클래스다.
- **객체**(object): 클래스로 만든 실제 값. `10`, `"hello"`, `[1, 2]`가 객체다. 어떤 클래스로 만든 객체인지 강조할 때는 **인스턴스**(instance)라고도 한다. "`10`은 `int`의 인스턴스다"처럼.

붕어빵 틀과 붕어빵을 떠올리면 쉽다. 틀(클래스)은 하나지만, 그 틀로 찍어 낸 붕어빵(객체)은 여러 개다. 붕어빵마다 속에 든 팥의 양은 다를 수 있지만 모양은 모두 틀을 따른다.

```
     클래스 str                      객체(인스턴스)
  ┌──────────────────┐         ┌───────────┐  ┌──────────┐
  │ 데이터: 글자들   │  ───▶  │  "hello"  │  │  "파이썬" │  ...
  │ 기능: upper,     │         └───────────┘  └──────────┘
  │  split, strip ...│        저마다 다른 글자를 가지지만
  └──────────────────┘        모두 upper(), split()을 쓸 수 있다
```

**클래스 이름을 호출하면 객체가 만들어진다**

2장에서 자료형을 변환할 때 쓴 `int("3")`, `str(10)`, 3장에서 빈 리스트를 만들 때 쓴 `list()`, 4장에서 날짜를 만들 때 쓴 `date(2026, 10, 31)`은 모두 **클래스 이름을 함수처럼 호출해 그 클래스의 객체를 만든** 것이다.

```python
>>> int("3")
3
>>> list()
[]
>>> from datetime import date
>>> d = date(2026, 10, 31)
>>> type(d)
<class 'datetime.date'>
```

`d`는 `datetime` 모듈에 있는 `date` 클래스의 객체다. 그리고 객체에 점을 찍어 그 객체가 가진 **데이터**와 **기능**을 꺼내 쓴다.

```python
>>> d.year
2026
>>> d.month
10
>>> d.weekday()
5
```

`d.year`처럼 괄호 없이 꺼내는 데이터를 **속성**(attribute), `d.weekday()`처럼 괄호를 붙여 호출하는 기능을 **메서드**(method)라고 한다. 메서드는 "객체에 붙어 있는 함수"다. 2장부터 써 온 `"hello".upper()`, `scores.append(90)`, `prices.items()`가 모두 메서드 호출이다.

이 장에서 배우는 것은 `int`나 `date` 같은 클래스를 **직접 만드는** 방법이다.

### 5.1.3 `class`로 클래스 정의하기

가장 간단한 클래스부터 만들어 보자. 다음 코드를 대화형 셸에 붙여 넣는다(실습 준비의 "대화형 셸에 붙여 넣는 클래스 코드" 참고).

```python
class Account:
    pass
```

- `class` 다음에 클래스 이름을 쓰고 콜론(`:`)을 붙인다. 클래스의 내용(**본문**)은 들여쓰기로 구분한다.
- `pass`는 "아무것도 하지 않는다"는 뜻의 문장이다. 본문을 비워 둘 수 없으므로 자리를 채우는 데 쓴다.
- 클래스 이름은 단어의 첫 글자를 대문자로 쓰는 **CamelCase**(카멜 표기법)로 짓는다. `Account`, `BankAccount`, `TodoItem`처럼. 변수와 함수는 `snake_case`, 클래스는 `CamelCase`라는 것이 PEP 8의 관례다(2.1.2). 이름만 보고도 "이건 클래스구나" 하고 알 수 있다. (`int`, `str`, `list`처럼 소문자로 된 내장 클래스는 예외다. 오래전에 정해진 이름이라 그대로 쓰고 있다.)

클래스 이름을 함수처럼 호출하면 객체가 만들어진다.

```python
>>> a = Account()
>>> b = Account()
>>> type(a)
<class '__main__.Account'>
>>> a
<__main__.Account object at 0x104f3e2a0>
```

`<class '__main__.Account'>`는 "지금 실행 중인 프로그램(`__main__`)에서 만든 `Account` 클래스"라는 뜻이다. `__main__`의 의미는 8장에서 자세히 배운다. 셸에 `a`를 입력하면 "`Account` 클래스의 객체가 메모리 어딘가에 있다"는 정보만 보인다. 보기 좋게 바꾸는 방법은 5.2에서 배운다. (뒤의 숫자는 실행할 때마다 다르다.)

`a`와 `b`는 같은 클래스로 만들었지만 **서로 다른 객체**다. 3장에서 배운 `is`로 확인할 수 있다.

```python
>>> a is b
False
>>> isinstance(a, Account)
True
```

**객체에 속성 붙이기**

객체에 점을 찍고 이름에 값을 할당하면 그 객체에 **속성**이 생긴다.

```python
>>> a.owner = "철수"
>>> a.balance = 10000
>>> a.owner
'철수'
>>> a.balance + 5000
15000
```

속성도 결국 이름표다. `a.owner = "철수"`는 "`a`가 가리키는 객체 **안에** `owner`라는 이름표를 만들어 `"철수"`에 붙인다"는 뜻이다. 변수는 프로그램에 붙어 있는 이름표이고, 속성은 객체에 붙어 있는 이름표라는 차이가 있을 뿐이다.

```
  a ──▶ ┌── Account 객체 ──┐
        │ owner   ──▶ "철수" │
        │ balance ──▶ 10000  │
        └───────────────────┘
```

그런데 `b`에는 아무 속성도 붙이지 않았다.

```python
>>> b.owner
Traceback (most recent call last):
  File "<python-input-9>", line 1, in <module>
    b.owner
AttributeError: 'Account' object has no attribute 'owner'
```

`AttributeError`는 "그런 속성이 없다"는 오류다. 객체를 만들 때마다 속성을 하나하나 붙이는 방법은 번거롭고, 빠뜨리기 쉽다. 그래서 **객체를 만들 때 속성이 자동으로 만들어지도록** 클래스에 적어 둔다. 그것이 다음에 배울 `__init__`이다.

### 5.1.4 `__init__` — 객체를 만들 때 실행되는 메서드

클래스 안에 `def`로 함수를 정의하면 그 함수는 **메서드**가 된다. 그중 `__init__`이라는 이름의 메서드는 특별해서, **객체가 만들어질 때 파이썬이 자동으로 호출**한다. 객체를 초기화(initialize)한다는 뜻이다.

```python
class Account:
    def __init__(self, owner, balance):
        self.owner = owner
        self.balance = balance
```

```python
>>> a = Account("철수", 10000)
>>> b = Account("영희", 5000)
>>> a.owner, a.balance
('철수', 10000)
>>> b.owner, b.balance
('영희', 5000)
```

(같은 이름 `Account`로 클래스를 다시 정의했다. 3장의 이름표 생각대로, `Account`라는 이름표가 새 클래스로 옮겨 붙은 것이다. 앞의 객체 `a`, `b`도 새 객체로 바뀌었다.)

`Account("철수", 10000)`을 실행하면 파이썬은 다음 일을 순서대로 한다.

```
Account("철수", 10000)
  1) 속성이 하나도 없는 Account 객체를 새로 만든다
  2) __init__(새 객체, "철수", 10000)을 호출한다
       → self는 새 객체, owner는 "철수", balance는 10000
       → self.owner = owner      : 새 객체에 owner 속성을 붙인다
       → self.balance = balance  : 새 객체에 balance 속성을 붙인다
  3) 속성이 붙은 새 객체를 돌려준다
```

핵심은 2)다. `__init__`의 **첫 번째 매개변수 `self`에는 방금 만든 객체가 자동으로 들어간다.** 우리가 넘긴 인자 `"철수"`, `10000`은 그다음 매개변수 `owner`, `balance`에 순서대로 들어간다. 그래서 `__init__` 안의 `self.owner = owner`는 "새 객체(`self`)의 `owner` 속성에, 인자로 받은 `owner`를 붙여라"라는 뜻이다.

`self.owner`와 `owner`는 **다른 이름**이라는 데 주의하자.

| 이름 | 무엇인가 | 언제까지 있나 |
|---|---|---|
| `owner` | `__init__`의 매개변수. 4.3의 지역 변수다 | `__init__`이 끝나면 사라진다 |
| `self.owner` | 객체에 붙은 속성 | 객체가 있는 동안 계속 있다 |

매개변수 이름과 속성 이름을 같게 짓는 것이 관례라서 헷갈리기 쉽다. "**매개변수로 받은 값을 객체에 옮겨 담는다**"고 읽으면 된다.

**`__init__`도 함수다**

`__init__`은 메서드이고, 메서드는 함수이므로 4장에서 배운 규칙이 그대로 적용된다. 인자 개수가 맞지 않으면 `TypeError`가 나고, 기본값도 쓸 수 있다.

```python
>>> Account("민수")
Traceback (most recent call last):
  File "<python-input-15>", line 1, in <module>
    Account("민수")
    ~~~~~~~^^^^^^^^
TypeError: Account.__init__() missing 1 required positional argument: 'balance'
```

오류 메시지가 `Account()`가 아니라 `Account.__init__()`을 말하고 있다. 객체를 만들 때 넘긴 인자는 `__init__`에 전달된다는 것을 확인할 수 있다. 새 계좌는 잔액 0원에서 시작하는 경우가 많으므로 `balance`에 기본값을 주자.

```python
class Account:
    def __init__(self, owner, balance=0):
        self.owner = owner
        self.balance = balance
```

```python
>>> c = Account("민수")
>>> c.balance
0
>>> d = Account(owner="지수", balance=3000)
>>> d.owner, d.balance
('지수', 3000)
```

키워드 인자(4.2.2)도 그대로 쓸 수 있다.

> **밑줄 두 개로 둘러싼 이름**
> `__init__`처럼 앞뒤에 밑줄 두 개가 붙은 이름은 파이썬이 **정해진 때에 자동으로 호출하는** 특별한 메서드다. 밑줄 두 개(double underscore)를 줄여 **던더**(dunder) 메서드라고 부르기도 한다. 4.5.4에서 `dir(list)`의 앞쪽에 잔뜩 나와 "지금은 건너뛴다"고 했던 이름들이 바로 이것이다. 이 장에서는 `__init__`, `__str__`, `__repr__`, `__eq__`를 만난다. 이름은 우리가 지어내는 것이 아니라 파이썬이 정해 둔 것이므로, `_init_`이나 `__intit__`처럼 철자를 틀리면 그냥 평범한 메서드가 되어 자동으로 호출되지 않는다.

### 5.1.5 인스턴스 속성

`__init__`에서 `self.이름 = 값`으로 만든 속성은 **객체마다 따로** 있다. 이것을 **인스턴스 속성**(instance attribute)이라고 한다.

```python
>>> a = Account("철수", 10000)
>>> b = Account("영희", 5000)
>>> a.balance = a.balance + 3000
>>> a.balance
13000
>>> b.balance
5000
```

`a`의 잔액을 바꿔도 `b`의 잔액은 그대로다. 붕어빵마다 팥의 양이 따로인 것과 같다.

```
  a ──▶ ┌── Account 객체 ──┐      b ──▶ ┌── Account 객체 ──┐
        │ owner   ──▶ "철수" │            │ owner   ──▶ "영희" │
        │ balance ──▶ 13000  │            │ balance ──▶ 5000   │
        └───────────────────┘            └───────────────────┘
```

**객체의 속성 한눈에 보기 — `vars()`**

객체에 어떤 속성이 붙어 있는지 보고 싶으면 `vars()`를 쓴다. 속성 이름과 값을 딕셔너리로 보여 준다.

```python
>>> vars(a)
{'owner': '철수', 'balance': 13000}
```

`dir(a)`도 쓸 수 있지만 밑줄 두 개짜리 이름까지 모두 나오므로, 인스턴스 속성만 보고 싶을 때는 `vars()`가 편하다.

**속성 이름을 틀리면**

```python
>>> a.balanse
Traceback (most recent call last):
  File "<python-input-23>", line 1, in <module>
    a.balanse
AttributeError: 'Account' object has no attribute 'balanse'. Did you mean: 'balance'?
```

1장에서 본 `NameError`처럼 비슷한 이름을 제안해 준다. 딕셔너리의 `KeyError`보다 친절하다. 그리고 VS Code는 `a.`을 입력하는 순간 `owner`, `balance` 같은 속성 이름을 **자동 완성 목록**으로 보여 주므로 처음부터 오타를 낼 일이 적다. 5.1.1에서 말한 딕셔너리의 세 번째 문제(키 이름 오타)가 여기서 해결된다.

다만 **할당할 때의 오타**는 오류가 나지 않는다는 점에 주의하자.

```python
>>> a.balanse = 0
>>> vars(a)
{'owner': '철수', 'balance': 13000, 'balanse': 0}
```

`a.balanse = 0`은 5.1.3에서 본 "객체에 속성 붙이기"이므로, 파이썬은 오타가 아니라 새 속성을 하나 더 만든다. 변수 이름을 틀리게 할당하면 새 변수가 생기는 것(2.1)과 같다. 그래서 속성은 **`__init__`에서만 만들고**, 바깥에서는 이미 있는 속성을 읽거나 메서드를 호출하는 습관을 들이자. 다음에 배울 메서드가 그 역할을 한다.

### 5.1.6 메서드 — 객체에 붙어 있는 함수

입금과 출금 기능을 메서드로 추가하자. `__init__`과 마찬가지로 클래스 안에 `def`로 정의하고, **첫 매개변수는 `self`**로 둔다.

```python
class Account:
    def __init__(self, owner, balance=0):
        self.owner = owner
        self.balance = balance
    def deposit(self, amount):
        """amount원을 입금한다."""
        self.balance += amount
    def withdraw(self, amount):
        """amount원을 출금한다. 잔액이 모자라면 출금하지 않고 False를 돌려준다."""
        if amount > self.balance:
            return False
        self.balance -= amount
        return True
    def show(self):
        """예금주와 잔액을 출력한다."""
        print(f"{self.owner}: {self.balance:,}원")
```

(셸에 붙여 넣는 코드이므로 메서드 사이에 빈 줄을 넣지 않았다. 실습 준비에서 말한 대로다.)

메서드는 **객체에 점을 찍고** 호출한다.

```python
>>> a = Account("철수", 10000)
>>> b = Account("영희")
>>> a.deposit(3000)
>>> a.show()
철수: 13,000원
>>> a.withdraw(20000)
False
>>> a.withdraw(5000)
True
>>> a.show()
철수: 8,000원
>>> b.deposit(1000)
>>> b.show()
영희: 1,000원
```

`a.deposit(3000)`은 `a`의 잔액을, `b.deposit(1000)`은 `b`의 잔액을 바꾼다. 같은 메서드인데 어떻게 "누구의" 잔액을 바꿀지 아는 걸까? 그 답이 `self`다.

메서드는 함수이므로 4장에서 배운 것을 모두 쓸 수 있다. 독스트링을 쓰면 `help(Account.withdraw)`나 VS Code 말풍선에 나온다. 결과를 돌려줄 때는 `return`을 쓰고, 돌려주지 않으면 `None`을 돌려준다(`a.deposit(3000)`의 결과가 셸에 아무것도 나오지 않은 이유다). `withdraw()`가 성공 여부를 `True`/`False`로 돌려주는 것도 4.1.5의 "결과를 돌려주는 함수"다. (출금에 실패했을 때 `False`를 돌려주는 대신 **오류를 일으키는** 더 좋은 방법은 6장 "예외"에서 배운다.)

지금의 `Account`는 **입금액과 출금액이 양의 정수라고 가정**한다. `deposit(-20000)`처럼 음수를 넘기면 입금인데 잔액이 줄고, `withdraw(-5000)`은 출금인데 잔액이 늘어난다. 문법을 익히는 동안에는 이 검사를 생략하고, 5.2.7에서 클래스를 다듬을 때 추가한다.

### 5.1.7 `self`의 의미

메서드 정의에는 매개변수가 두 개(`self`, `amount`)인데, 호출할 때는 인자를 하나(`3000`)만 넘겼다. 나머지 하나는 어디서 왔을까?

**`a.deposit(3000)`은 `Account.deposit(a, 3000)`과 같다.**

```python
>>> Account.deposit(a, 1000)
>>> a.show()
철수: 9,000원
```

`Account.deposit`은 클래스 안에 정의된 **평범한 함수**다. 4.4에서 배운 대로 함수도 객체이므로 `Account.deposit`처럼 점을 찍어 꺼낼 수 있다. 그 함수를 호출하면서 첫 인자로 `a`를 넘기면 `self`에 `a`가 들어가고, 함수 안의 `self.balance += amount`는 `a.balance += 1000`이 된다.

`a.deposit(1000)`은 이 호출을 짧게 쓰는 방법이다. 파이썬은 **점 앞의 객체를 첫 번째 인자로 자동으로 넘겨 준다.**

```
a.deposit(1000)
│    │
│    └─▶ a의 클래스(Account)에서 deposit 함수를 찾는다
└──────▶ 그 함수를 호출하면서 a를 첫 번째 인자(self)로 넘긴다
         → Account.deposit(a, 1000)
```

그래서 `self`는 **"이 메서드를 호출한 그 객체"**를 가리키는 이름이다. `a.deposit(...)`이면 `self`는 `a`이고, `b.deposit(...)`이면 `self`는 `b`다. 메서드 안의 `self.balance`는 "지금 이 메서드를 호출한 객체의 잔액"이다. 같은 메서드 하나로 `a`와 `b`의 잔액을 각각 바꿀 수 있는 이유가 이것이다.

**이제 풀리는 수수께끼들**

앞 장들에서 "5장에서 배운다"고 미뤄 둔 것들이 이것으로 설명된다.

```python
>>> "hello".upper()
'HELLO'
>>> str.upper("hello")
'HELLO'
```

`"hello".upper()`는 `str.upper("hello")`와 같다. `upper`는 `str` 클래스 안에 정의된 메서드이고, 점 앞의 `"hello"`가 `self`로 넘어간다. 4.4.3에서 `apply_to_all(str.upper, ...)`, 4.5.5에서 `sorted(words, key=str.lower)`처럼 메서드를 함수로 넘길 수 있었던 이유도 같다. `str.upper`는 "문자열 하나(`self`)를 받아 대문자로 바꾸는 함수"다.

4.5.4에서 `help(str.split)`이 보여 준 함수 정의 `split(self, /, sep=None, maxsplit=-1)`의 `self`도 이제 읽을 수 있다. "`split`은 문자열 하나(`self`)를 첫 인자로 받는 함수이고, `"a b".split()`처럼 쓰면 점 앞의 문자열이 `self`로 들어간다"는 뜻이다.

> **`self`는 이름일 뿐이다**
> `self`는 파이썬 문법이 아니라 관례적인 이름이다. 첫 매개변수 이름을 `me`나 `this`로 지어도 동작은 한다. 하지만 모든 파이썬 코드가 `self`를 쓰므로 반드시 `self`로 쓰자. 자바나 자바스크립트를 본 적이 있다면 그 언어의 `this`에 해당한다. 다른 점은, 파이썬은 `self`를 **메서드 정의에 직접 적어야** 하고 메서드 안에서 속성을 쓸 때도 **`self.`을 생략할 수 없다**는 것이다.

**흔한 실수 1: 정의에서 `self`를 빠뜨린다**

```python
class Counter:
    def __init__(self):
        self.count = 0
    def increase():
        self.count += 1
```

```python
>>> c = Counter()
>>> c.increase()
Traceback (most recent call last):
  File "<python-input-37>", line 1, in <module>
    c.increase()
    ~~~~~~~~~~^^
TypeError: Counter.increase() takes 0 positional arguments but 1 was given
```

우리는 인자를 하나도 넘기지 않았는데 "1개가 주어졌다(1 was given)"고 한다. 파이썬이 자동으로 넘긴 `c`가 그 1개다. 메서드를 호출했는데 **인자 개수가 하나 어긋난 `TypeError`**가 나면 정의에서 `self`를 빠뜨리지 않았는지 먼저 확인하자.

**흔한 실수 2: 메서드 안에서 `self.`를 빠뜨린다**

```python
class Counter:
    def __init__(self):
        self.count = 0
    def increase(self):
        count += 1
```

```python
>>> c = Counter()
>>> c.increase()
Traceback (most recent call last):
  File "<python-input-40>", line 1, in <module>
    c.increase()
    ~~~~~~~~~~^^
  File "<python-input-38>", line 5, in increase
    count += 1
    ^^^^^
UnboundLocalError: cannot access local variable 'count' where it is not associated with a value
```

4.3.3에서 본 오류다. `count += 1`은 함수 안에서 할당하는 이름이므로 **지역 변수** `count`를 뜻한다. 객체의 속성 `count`와는 아무 관계가 없다. 메서드 안에서 객체의 속성은 반드시 `self.count`처럼 `self.`을 붙여야 한다. 정리하면, **`self.`이 붙은 이름은 객체에 붙어 있으므로 메서드가 끝나도 남고, 메서드 안에서 `self.` 없이 할당하는 이름은 그 메서드의 지역 변수라서 메서드가 끝나면 사라진다.** 할당하지 않고 읽기만 하는 이름은 4.3에서처럼 지역 → 전역 → 내장 순으로 찾으므로, 메서드 안에서도 전역 상수나 `len()` 같은 내장 함수는 `self.` 없이 그대로 쓴다.

### 5.1.8 메서드에서 다른 메서드와 다른 객체 쓰기

**같은 객체의 다른 메서드 호출하기**

메서드 안에서 같은 객체의 다른 메서드를 호출할 때도 `self.`을 붙인다. 출금하고 입금하는 "이체" 메서드를 만들어 보자. 이체할 상대 계좌는 **다른 `Account` 객체**를 인자로 받는다.

```python
class Account:
    def __init__(self, owner, balance=0):
        self.owner = owner
        self.balance = balance
    def deposit(self, amount):
        self.balance += amount
    def withdraw(self, amount):
        if amount > self.balance:
            return False
        self.balance -= amount
        return True
    def transfer(self, other, amount):
        """other 계좌로 amount원을 이체한다. 성공하면 True를 돌려준다."""
        if not self.withdraw(amount):
            return False
        other.deposit(amount)
        return True
    def show(self):
        print(f"{self.owner}: {self.balance:,}원")
```

```python
>>> a = Account("철수", 10000)
>>> b = Account("영희", 5000)
>>> a.transfer(b, 3000)
True
>>> a.show()
철수: 7,000원
>>> b.show()
영희: 8,000원
>>> b.transfer(a, 100000)
False
```

`a.transfer(b, 3000)`에서 `self`는 `a`, `other`는 `b`다. `self.withdraw(amount)`는 `a`에서 출금하고, `other.deposit(amount)`는 `b`에 입금한다. 출금 규칙(잔액이 모자라면 실패)은 `withdraw()`에만 쓰여 있고 `transfer()`는 그것을 **다시 쓴다.** 4장에서 "고칠 곳을 한 군데로 모은다"고 한 함수의 장점이 메서드에서도 그대로다.

**객체를 리스트에 담기**

객체도 값이므로 리스트나 딕셔너리에 담을 수 있다. 3·4장에서 딕셔너리의 리스트로 하던 일을 객체의 리스트로 할 수 있다.

```python
>>> accounts = [Account("철수", 7000), Account("영희", 8000), Account("민수", 500)]
>>> for acc in accounts:
...     acc.deposit(1000)
...
>>> for acc in accounts:
...     acc.show()
...
철수: 8,000원
영희: 9,000원
민수: 1,500원
>>> richest = max(accounts, key=lambda acc: acc.balance)
>>> richest.owner
'영희'
```

`max()`의 `key`(4.5.5)에 람다를 넘겨 "잔액이 가장 큰 계좌"를 찾았다. 딕셔너리였다면 `lambda acc: acc["balance"]`라고 썼을 것을 `lambda acc: acc.balance`로 쓴다.

**객체를 함수에 넘기면**

객체를 함수나 메서드의 인자로 넘기면 3장의 이름표 규칙이 그대로 적용된다. 매개변수 이름표가 **같은 객체**에 붙으므로, 함수 안에서 객체의 속성을 바꾸면 호출한 쪽에서도 바뀐 것이 보인다(4.3.5). `transfer()` 안의 `other.deposit(amount)`가 바깥의 `b`를 바꿀 수 있었던 이유다. 직접 만든 클래스의 객체는 **가변 객체**다.

### 5.1.9 스크립트로 정리하고 디버거로 `self` 보기

지금까지 셸에서 만든 `Account`를 스크립트 파일로 정리하자. `ch05` 폴더에 `account.py`를 만든다.

```python

    """은행 계좌."""

    def __init__(self, owner, balance=0):

        if not self.withdraw(amount):
            return False
```

3. `F11`을 눌러 `transfer()` 안으로 들어간다. 변수 패널의 지역 변수에 `self`, `other`, `amount`가 보인다. `self`를 펼치면 `owner: '철수'`, `other`를 펼치면 `owner: '영희'`다. **`self`가 `chulsoo`와 같은 객체**라는 것을 눈으로 확인하자.

5. `Shift + F11`로 `transfer()`로 돌아온 뒤, `other.deposit(amount)` 줄에서 다시 `F11`로 들어간다. 이번에는 `deposit()`의 `self`가 **`'영희'` 계좌**다. 같은 메서드라도 누구의 메서드로 호출했느냐에 따라 `self`가 달라진다.

`self`가 헷갈릴 때마다 이렇게 디버거로 들어가 `self`를 펼쳐 보는 것이 가장 확실한 방법이다.

## 5.2 클래스 설계 기초

5.1에서 클래스를 만들고 쓰는 문법을 배웠다. 이 절에서는 클래스를 **잘** 만드는 데 필요한 기초를 다룬다. 모든 객체가 함께 쓰는 값은 어디에 두는지, 객체를 `print()`했을 때 어떻게 보이게 할지, 그리고 객체의 데이터를 바깥에서 함부로 바꾸지 못하게 하려면 어떻게 하는지다.

### 5.2.1 클래스 속성 — 모든 객체가 함께 쓰는 값

모든 계좌는 같은 은행의 계좌이고, 같은 이자율을 적용받는다고 하자. 이런 값을 `__init__`에서 `self.bank_name = "파이썬은행"`처럼 객체마다 만들 수도 있지만, 모든 객체가 똑같은 값을 하나씩 들고 있는 것은 낭비이고, 이자율이 바뀌면 모든 객체를 찾아 고쳐야 한다.

이런 값은 **클래스 본문에 직접** 쓴다. 메서드 밖, 클래스 안에서 할당한 이름은 **클래스 속성**(class attribute)이 된다.

```python
class Account:
    bank_name = "파이썬은행"
    interest_rate = 0.02
    def __init__(self, owner, balance=0):
        self.owner = owner
        self.balance = balance
    def add_interest(self):
        """잔액에 이자를 더한다."""
        self.balance += int(self.balance * self.interest_rate)
```

```python
>>> a = Account("철수", 10000)
>>> b = Account("영희", 50000)
>>> Account.bank_name
'파이썬은행'
>>> a.bank_name
'파이썬은행'
>>> b.interest_rate
0.02
```

클래스 속성은 `Account.bank_name`처럼 **클래스에 점을 찍어** 읽을 수도 있고, `a.bank_name`처럼 **객체에 점을 찍어** 읽을 수도 있다. 객체에는 `bank_name` 속성이 없는데 어떻게 읽힐까?

```python
>>> vars(a)
{'owner': '철수', 'balance': 10000}
```

`a`에는 정말 `bank_name`이 없다. 파이썬은 `a.bank_name`을 만나면 다음 순서로 이름을 찾는다.

```
a.bank_name
  1) 객체 a에 bank_name 속성이 있나?           → 없다
  2) a의 클래스(Account)에 bank_name이 있나?   → 있다! '파이썬은행'
```

4.3에서 이름을 "지역 → 전역 → 내장" 순으로 찾았던 것처럼, 속성은 **"객체 → 클래스" 순으로** 찾는다. 메서드도 같은 방법으로 찾는다. `a.deposit`도 객체에는 없고 클래스에 있는 함수를 찾아 쓰는 것이다(5.1.7).

```
  a ──▶ ┌─ Account 객체 ─┐          Account ──▶ ┌──── Account 클래스 ────┐
        │ owner   ─▶ "철수" │   못 찾으면          │ bank_name     ─▶ '파이썬은행' │
        │ balance ─▶ 10000  │  ────────────▶     │ interest_rate ─▶ 0.02       │
        └──────────────────┘                     │ __init__, add_interest  ... │
                                                 └────────────────────────────┘
```

**클래스 속성을 바꾸면 모든 객체에 보인다**

클래스 속성은 클래스에 **하나만** 있으므로, 클래스를 통해 바꾸면 모든 객체에서 바뀐 값이 보인다.

```python
>>> Account.interest_rate = 0.03
>>> a.interest_rate, b.interest_rate
(0.03, 0.03)
>>> a.add_interest()
>>> a.balance
10300
```

**객체를 통해 할당하면 클래스 속성이 아니라 인스턴스 속성이 생긴다**

그런데 객체에 점을 찍어 **할당**하면 이야기가 달라진다.

```python
>>> a.interest_rate = 0.1
>>> a.interest_rate, b.interest_rate, Account.interest_rate
(0.1, 0.03, 0.03)
>>> vars(a)
{'owner': '철수', 'balance': 10300, 'interest_rate': 0.1}
```

`a.interest_rate = 0.1`은 클래스 속성을 바꾸는 것이 아니라 **`a` 객체에 `interest_rate`라는 인스턴스 속성을 새로 만든다**(5.1.3의 "객체에 속성 붙이기"다). 이제 `a.interest_rate`를 읽으면 1)단계에서 `a`의 속성을 먼저 찾으므로 클래스 속성은 가려진다. 4.3.3에서 함수 안에서 할당하면 전역 변수가 아니라 지역 변수가 생겼던 것과 같은 원리다. **읽을 때는 객체 → 클래스 순으로 찾지만, 할당은 언제나 점 앞의 그 대상에 한다.**

```python
>>> del a.interest_rate
>>> a.interest_rate
0.03
```

`del`로 인스턴스 속성을 지우면 다시 클래스 속성이 보인다. 이런 혼란을 피하려면 클래스 속성은 **클래스 이름으로 바꾸는** 습관을 들이자.

**클래스 속성으로 객체 수 세기**

클래스 속성은 "지금까지 만든 계좌 수"처럼 **클래스 전체에 대한 정보**를 기록할 때도 쓴다. 이때도 메서드 안에서 `self.count`가 아니라 `Account.count`로 바꾸어야 한다.

```python
class Account:
    count = 0
    def __init__(self, owner, balance=0):
        self.owner = owner
        self.balance = balance
        Account.count += 1
```

```python
>>> a = Account("철수")
>>> b = Account("영희")
>>> c = Account("민수")
>>> Account.count
3
```

`Account.count += 1`을 `self.count += 1`로 쓰면 어떻게 될까? `self.count += 1`은 `self.count = self.count + 1`이다. 오른쪽의 `self.count`는 클래스 속성 `0`을 읽고, 왼쪽의 할당은 **객체에** `count = 1`이라는 인스턴스 속성을 만든다. 그래서 객체마다 `count`가 1이 되고 클래스의 `count`는 계속 0으로 남는다. 실습 5-2에서 직접 확인해 보자.

**상수는 클래스 속성으로**

4장 실습 4-7에서 `LOAN_DAYS = 14`, `LATE_FEE_PER_DAY = 100`을 파일 맨 위에 전역 상수로 두었다. 그 값이 **특정 클래스에만 관계있다면** 클래스 속성으로 옮기면 좋다. "이 값은 도서관의 규칙"이라는 것이 코드 모양으로 드러나고, 전역 이름이 줄어든다. 상수이므로 4장과 같이 대문자로 이름을 짓는다.

```python
class Library:
    LOAN_DAYS = 14
    LATE_FEE_PER_DAY = 100
    ...
```

메서드 안에서는 `self.LOAN_DAYS`나 `Library.LOAN_DAYS`로 읽는다. 실습 5-5에서 이렇게 한다.

| 구분 | 만드는 곳 | 누가 가지나 | 예 |
|---|---|---|---|
| 인스턴스 속성 | 메서드 안 `self.이름 = 값` (주로 `__init__`) | 객체마다 따로 | 예금주, 잔액 |
| 클래스 속성 | 클래스 본문 `이름 = 값` | 클래스에 하나, 모든 객체가 함께 읽음 | 은행 이름, 이자율, 상수, 만든 객체 수 |

### 5.2.2 가변 객체를 클래스 속성으로 두면

거래 기록을 남기도록 리스트를 하나 두자. 다음 코드에는 버그가 있다.

```python
class Account:
    history = []
    def __init__(self, owner):
        self.owner = owner
    def deposit(self, amount):
        self.history.append(("입금", amount))
```

```python
>>> a = Account("철수")
>>> b = Account("영희")
>>> a.deposit(1000)
>>> b.deposit(5000)
>>> a.history
[('입금', 1000), ('입금', 5000)]
>>> a.history is b.history
True
```

철수의 거래 기록에 영희의 입금이 섞였다. `history = []`는 클래스 본문에 있으므로 **클래스 속성**이고, 리스트는 클래스에 **딱 하나**만 만들어진다. `self.history.append(...)`는 할당이 아니라 **리스트를 고치는 것**이므로 인스턴스 속성이 새로 생기지 않는다. `self.history`는 객체 → 클래스 순으로 찾아 결국 클래스의 그 리스트 하나를 가리키고, 모든 객체가 그 리스트를 고친다.

4.2.5의 "가변 객체를 기본값으로 쓰면 생기는 문제"와 똑같은 모양의 버그다. 거기서는 기본값 리스트가 **정의할 때 한 번** 만들어져 모든 호출이 공유했고, 여기서는 클래스 속성 리스트가 **클래스를 정의할 때 한 번** 만들어져 모든 객체가 공유한다.

고치는 방법은 객체마다 따로 있어야 하는 리스트를 **`__init__`에서** 만드는 것이다. `__init__`은 객체를 만들 때마다 실행되므로 객체마다 새 리스트가 생긴다.

```python
class Account:
    def __init__(self, owner):
        self.owner = owner
        self.history = []
    def deposit(self, amount):
        self.history.append(("입금", amount))
```

```python
>>> a = Account("철수")
>>> b = Account("영희")
>>> a.deposit(1000)
>>> b.deposit(5000)
>>> a.history, b.history
([('입금', 1000)], [('입금', 5000)])
```

> **클래스 속성에는 바뀌지 않는 값만**
> 클래스 속성에는 문자열, 숫자, 튜플처럼 **불변 객체**나 상수만 두자. 객체마다 따로 쌓여야 하는 리스트, 딕셔너리, 집합은 반드시 `__init__`에서 `self.이름 = []`처럼 만든다. AI가 만들어 준 코드에서 클래스 바로 아래에 `items = []`가 있다면 이 버그가 아닌지 의심해 보자. (5.4의 데이터 클래스는 이 실수를 하면 **오류를 내서** 막아 준다.)

### 5.2.3 `__str__` — `print()`했을 때 보이는 모습

5.1의 `Account`는 잔액을 보여 주려고 `show()` 메서드를 만들었다. 그런데 객체를 그냥 `print()`하면 어떻게 될까?

```python
class Account:
    def __init__(self, owner, balance=0):
        self.owner = owner
        self.balance = balance
```

```python
>>> a = Account("철수", 10000)
>>> print(a)
<__main__.Account object at 0x104f3e2a0>
```

파이썬은 우리가 만든 객체를 어떻게 글자로 보여 줘야 할지 모른다. 그래서 "어느 클래스의 객체가 어디에 있다"는 정보만 보여 준다. `__str__` 메서드를 정의하면 이것을 바꿀 수 있다.

```python
class Account:
    def __init__(self, owner, balance=0):
        self.owner = owner
        self.balance = balance
    def __str__(self):
        return f"{self.owner}님의 계좌 (잔액 {self.balance:,}원)"
```

```python
>>> a = Account("철수", 10000)
>>> print(a)
철수님의 계좌 (잔액 10,000원)
>>> str(a)
'철수님의 계좌 (잔액 10,000원)'
>>> f"계좌 정보: {a}"
'계좌 정보: 철수님의 계좌 (잔액 10,000원)'
```

`__str__`은 `print(a)`, `str(a)`, f-string의 `{a}`처럼 **객체를 문자열로 바꿀 때 파이썬이 자동으로 호출**하는 던더 메서드다. 규칙은 하나다. **출력하지 말고 문자열을 돌려준다.** `__str__` 안에서 `print()`를 하고 `return`을 빠뜨리면 `TypeError: __str__ returned non-string (type NoneType)`이 난다. 4.1.5의 "계산하는 함수는 출력하지 말고 돌려준다"가 여기서도 적용된다.

`show()`처럼 직접 출력하는 메서드보다 `__str__`이 나은 이유는 4장에서 `print_grade()`를 `get_grade()`로 바꾼 이유와 같다. 문자열을 돌려받으면 출력할지, 파일에 쓸지, 다른 문자열과 합칠지를 **쓰는 쪽에서 정할 수 있다.**

### 5.2.4 `__repr__` — 개발자를 위한 모습

`__str__`을 정의했는데도 대화형 셸에 `a`만 입력하거나, 객체를 **리스트에 담아** 출력하면 여전히 알아보기 어렵다.

```python
>>> a
<__main__.Account object at 0x104f3e2a0>
>>> print([a, Account("영희")])
[<__main__.Account object at 0x104f3e2a0>, <__main__.Account object at 0x104f3e5d0>]
```

이때 쓰이는 것이 `__repr__`이다. 파이썬은 객체를 글자로 바꾸는 방법을 두 가지 가지고 있다.

| | `__str__` | `__repr__` |
|---|---|---|
| 누가 읽나 | 프로그램을 **쓰는 사람** | 프로그램을 **만드는 사람**(개발자) |
| 목표 | 읽기 좋게 | 무엇인지 **정확하고 분명하게** |
| 언제 쓰이나 | `print(x)`, `str(x)`, f-string `{x}` | 대화형 셸에 `x` 입력, `repr(x)`, **리스트·딕셔너리 안의 요소**, 디버거, f-string `{x!r}` |
| 없으면 | `__repr__`을 대신 쓴다 | `<... object at 0x...>` |

4.6.9에서 날짜를 셸에 입력하면 `datetime.date(2026, 10, 31)`로, `print()`하면 `2026-10-31`로 보였던 것이 바로 이 차이다. `date` 클래스가 두 메서드를 다르게 정의해 두었기 때문이다. 문자열도 마찬가지다.

```python
>>> s = "안녕"
>>> print(s)
안녕
>>> s
'안녕'
>>> print([s])
['안녕']
```

`print(s)`는 `__str__`을 써서 따옴표 없이, 셸과 리스트 안에서는 `__repr__`을 써서 따옴표를 붙여 보여 준다. 따옴표가 있어야 `"10"`(문자열)과 `10`(정수)을 구별할 수 있기 때문이다. 이것이 "정확하고 분명하게"의 의미다.

`__repr__`은 관례적으로 **그 객체를 만드는 코드와 같은 모양**으로 쓴다. `datetime.date(2026, 10, 31)`처럼, 셸에 그대로 붙여 넣으면 같은 객체가 만들어지는 모양이다.

```python
class Account:
    def __init__(self, owner, balance=0):
        self.owner = owner
        self.balance = balance
    def __str__(self):
        return f"{self.owner}님의 계좌 (잔액 {self.balance:,}원)"
    def __repr__(self):
        return f"Account({self.owner!r}, {self.balance!r})"
```

```python
>>> a = Account("철수", 10000)
>>> a
Account('철수', 10000)
>>> print(a)
철수님의 계좌 (잔액 10,000원)
>>> accounts = [a, Account("영희")]
>>> accounts
[Account('철수', 10000), Account('영희', 0)]
>>> print(accounts)
[Account('철수', 10000), Account('영희', 0)]
```

f-string의 `{self.owner!r}`에서 `!r`은 "이 값을 `repr()`로 바꿔 넣어라"는 뜻이다. 그래서 `'철수'`처럼 따옴표가 붙는다. `!r` 없이 `{self.owner}`로 쓰면 `Account(철수, 10000)`이 되어 셸에 붙여 넣을 수 없는 모양이 된다.

`print(accounts)`가 각 계좌를 `__str__`이 아니라 `__repr__`로 보여 준다는 점에 주의하자. 리스트를 문자열로 바꿀 때는 **요소마다 `repr()`**을 쓰기 때문이다. 리스트 안의 문자열에 따옴표가 붙는 것과 같은 이유다.

> **무엇을 정의할까**
> - **`__repr__`은 거의 언제나 정의한다.** 셸에서 확인할 때, 리스트에 담아 출력할 때, 디버거로 볼 때 모두 `__repr__`이 쓰인다. `__str__`이 없으면 `print()`도 `__repr__`을 쓴다.
> - **`__str__`은 사용자에게 보여 줄 모습이 따로 있을 때** 추가한다.
> - 5.4의 데이터 클래스는 쓸 만한 `__repr__`을 **자동으로** 만들어 준다.

### 5.2.5 캡슐화 관례 — `_이름`

지금의 `Account`에는 큰 구멍이 있다.

```python
>>> a = Account("철수", 10000)
>>> a.balance = 100000000
>>> a
Account('철수', 100000000)
```

입금하지 않았는데 잔액이 1억 원이 되었다. 출금하지 않고 잔액을 음수로 만들 수도 있다. `withdraw()`의 "잔액이 모자라면 출금하지 않는다"는 규칙이 아무 의미가 없어진다. (5.1.6에서 말한 음수 금액 문제는 메서드 안의 검사로 막을 수 있다. 5.2.7에서 한다. 하지만 속성에 직접 할당하는 것은 메서드를 거치지 않으므로 메서드 안의 검사로는 막을 수 없다.) 잔액은 **입금, 출금, 이체를 통해서만** 바뀌어야 하는데, 바깥 코드가 속성에 직접 할당하는 것을 막을 방법이 없다.

이처럼 객체의 데이터를 바깥에 그대로 드러내지 않고, 정해진 메서드를 통해서만 다루게 하는 것을 **캡슐화**(encapsulation)라고 한다. 알약의 캡슐이 속의 가루를 감싸 보호하는 것처럼, 객체가 자신의 데이터를 감싸 규칙에 맞게만 바뀌도록 지키는 것이다.

자바 같은 언어는 `private` 같은 키워드로 바깥에서 속성에 아예 접근하지 못하게 막는다. 파이썬에는 그런 강제 장치가 없다. 대신 **이름 앞에 밑줄 하나(`_`)를 붙이는 관례**를 쓴다.

```python
class Account:
    def __init__(self, owner, balance=0):
        self.owner = owner
        self._balance = balance
    def deposit(self, amount):
        self._balance += amount
    def get_balance(self):
        return self._balance
```

```python
>>> a = Account("철수", 10000)
>>> a.deposit(5000)
>>> a.get_balance()
15000
```

`_balance`처럼 밑줄로 시작하는 이름은 **"클래스 내부에서 쓰는 이름이니 바깥에서는 건드리지 말라"**는 표시다. 클래스 안의 메서드는 `self._balance`를 자유롭게 쓰지만, 클래스 밖의 코드는 `a._balance`를 읽거나 바꾸지 않고 `deposit()`, `get_balance()` 같은 메서드를 쓴다. VS Code의 자동 완성도 밑줄로 시작하는 이름을 목록 뒤쪽으로 보내거나 감춘다.

어디까지나 **약속**이므로 `a._balance = 0`이라고 쓰면 실행은 된다. 파이썬은 "모두 성인이니 약속을 지킬 것이다"라는 생각으로 막지 않는다. 다른 사람이 만든 클래스(라이브러리)의 `_`로 시작하는 속성이나 메서드를 쓰지 말아야 하는 이유는, 그것이 **언제든 바뀌거나 사라질 수 있는 내부 사정**이기 때문이다. 라이브러리 버전을 올렸더니 내 코드가 깨지는 일을 피하려면 밑줄 없는 공개된 이름만 쓰자.

> **밑줄 두 개(`__balance`)는?**
> 이름 앞에만 밑줄 두 개를 붙이면(`self.__balance`) 파이썬이 이름을 `_Account__balance`로 살짝 바꿔 저장한다(이름 장식, name mangling). 바깥에서 `a.__balance`로는 읽을 수 없게 되지만 이것도 완전히 막는 장치는 아니고, 상속할 때 헷갈리는 문제를 일으킨다. 특별한 이유가 없으면 **밑줄 하나**를 쓰자. 앞뒤에 모두 밑줄 두 개가 붙은 `__init__` 같은 던더 메서드와는 다른 것이다.

### 5.2.6 `@property` — 메서드를 속성처럼 읽기

`get_balance()`로 잔액을 읽을 수 있게 되었지만, 잔액을 읽을 때마다 괄호를 붙이는 것은 어색하다. 잔액은 "하는 일"이 아니라 계좌가 "가진 값"이기 때문이다. `a.balance`처럼 읽되, 할당은 막고 싶다. 이때 `@property`를 쓴다.

```python
class Account:
    def __init__(self, owner, balance=0):
        self.owner = owner
        self._balance = balance
    @property
    def balance(self):
        """현재 잔액."""
        return self._balance
    def deposit(self, amount):
        self._balance += amount
```

```python
>>> a = Account("철수", 10000)
>>> a.balance
10000
>>> a.deposit(5000)
>>> a.balance
15000
```

`balance`는 `def`로 만든 메서드인데, 호출할 때 **괄호를 붙이지 않는다.** 메서드 정의 바로 위의 `@property` 한 줄이 "이 메서드는 속성처럼 읽게 해 달라"는 뜻이기 때문이다. `a.balance`를 읽으면 파이썬이 `balance(a)`를 호출해 그 결과를 돌려준다.

그리고 할당하려고 하면 오류가 난다.

```python
>>> a.balance = 100000000
Traceback (most recent call last):
  File "<python-input-84>", line 1, in <module>
    a.balance = 100000000
    ^^^^^^^^^
AttributeError: property 'balance' of 'Account' object has no setter
```

"`balance` 프로퍼티에는 값을 넣는 방법(setter)이 없다"는 뜻이다. 이렇게 `_balance`를 감추고 `balance` 프로퍼티로 **읽기만** 공개하면, 잔액은 클래스 안의 메서드를 통해서만 바뀐다. 이것이 파이썬에서 캡슐화를 하는 가장 흔한 방법이다.

```
  바깥 코드                     Account 객체
  ─────────                    ─────────────
  a.balance        ──읽기──▶   @property balance ──▶ self._balance
  a.deposit(5000)  ──────────▶  deposit()  ──바꾸기──▶ self._balance
  a.balance = 0    ──✕──      (setter가 없어 AttributeError)
```

> **`@`로 시작하는 줄 — 데코레이터**
> `@property`처럼 함수 정의 바로 위에 `@이름`을 쓰는 문법을 **데코레이터**(decorator)라고 한다. "바로 아래 함수에 특별한 기능을 덧붙인다"는 뜻이다. 5.4에서 `@dataclass`를 클래스 위에 붙이는 것도 같은 문법이다. 웹 프레임워크에서는 `@app.get("/users")`처럼 "이 함수를 이 주소의 요청을 처리하는 함수로 등록한다"는 뜻으로 많이 쓴다. 이 과정에서는 이미 만들어진 데코레이터를 **붙여서 쓰는 것**만 다룬다. 데코레이터를 직접 만드는 방법은 파이썬 중급에서 배운다.

**계산해서 돌려주는 프로퍼티**

프로퍼티는 저장된 값을 그대로 돌려줄 필요가 없다. 다른 속성으로 **계산한 값**을 속성처럼 보여 줄 때도 많이 쓴다.

```python
class Rectangle:
    def __init__(self, width, height):
        self.width = width
        self.height = height
    @property
    def area(self):
        return self.width * self.height
```

```python
>>> r = Rectangle(3, 4)
>>> r.area
12
>>> r.width = 10
>>> r.area
40
```

넓이를 `__init__`에서 `self.area = width * height`로 미리 계산해 두면, 나중에 `width`를 바꿨을 때 넓이가 따라 바뀌지 않는다. 프로퍼티는 **읽을 때마다 계산**하므로 언제나 맞는 값을 돌려준다.

**바깥에 내준 리스트를 지키기**

거래 기록처럼 내부에 **리스트**를 가지고 있을 때는 한 가지 더 조심해야 한다. 프로퍼티가 내부 리스트를 그대로 돌려주면, 3장에서 배운 대로 바깥 코드가 **같은 리스트**를 고칠 수 있다.

```python
class Account:
    def __init__(self, owner):
        self.owner = owner
        self._history = []
    @property
    def history(self):
        return self._history
    def deposit(self, amount):
        self._history.append(("입금", amount))
```

```python
>>> a = Account("철수")
>>> a.deposit(1000)
>>> h = a.history
>>> h.append(("입금", 99999999))
>>> a.history
[('입금', 1000), ('입금', 99999999)]
```

`a.history = []` 같은 할당은 막았지만, 돌려받은 리스트를 `append()`로 고치는 것은 막지 못했다. `h`와 `a._history`가 같은 리스트이기 때문이다(3.2.2). 이럴 때는 **튜플로 바꿔서** 돌려준다. 튜플은 불변이므로 받은 쪽에서 고칠 수 없다(3.3.2).

```python
class Account:
    def __init__(self, owner):
        self.owner = owner
        self._history = []
    @property
    def history(self):
        """거래 기록. 바깥에서 고칠 수 없도록 튜플로 돌려준다."""
        return tuple(self._history)
    def deposit(self, amount):
        self._history.append(("입금", amount))
```

```python
>>> a = Account("철수")
>>> a.deposit(1000)
>>> h = a.history
>>> h
(('입금', 1000),)
>>> h.append(("입금", 99999999))
Traceback (most recent call last):
  File "<python-input-7>", line 1, in <module>
    h.append(("입금", 99999999))
    ^^^^^^^^
AttributeError: 'tuple' object has no attribute 'append'
```

`list(self._history)`나 `self._history.copy()`로 복사본을 돌려주는 방법도 있다. 이 경우 받은 쪽에서 고쳐도 원본은 그대로지만, 고쳐도 아무 효과가 없다는 사실이 코드에 드러나지 않는다. "읽기만 하라"는 뜻을 분명히 하려면 튜플이 낫다.

> **튜플이 지켜 주는 범위**
> 튜플로 돌려주면 받은 쪽에서 요소를 추가하거나, 지우거나, 다른 요소로 바꿔 끼울 수 없다. 하지만 **요소 객체의 안쪽까지** 지켜 주지는 않는다. 3.2.5에서 얕은 복사가 안쪽 리스트를 공유했던 것과 같은 이야기다. 거래 기록의 요소는 `("입금", 1000)` 같은 튜플(불변 객체)이라서 안전하지만, 요소가 리스트나 우리가 만든 객체라면 `h[0].append(...)`나 `h[0].amount = 0`처럼 요소 안쪽을 바꿀 수 있고, 그 변경은 클래스 안의 원본에도 그대로 보인다. 요소까지 지키려면 **요소도 불변 객체로** 만든다. 5.4.6의 `frozen=True` 데이터 클래스가 그 방법이다.

**프로퍼티로 할까, 메서드로 할까**

| 프로퍼티(`a.balance`) | 메서드(`a.deposit(1000)`) |
|---|---|
| 객체가 **가진 값**처럼 느껴진다 (명사: 잔액, 넓이, 평균) | 객체가 **하는 일**이다 (동사: 입금한다, 저장한다) |
| 인자가 필요 없다 | 인자가 필요할 수 있다 |
| 빠르게 계산된다 | 시간이 걸리거나, 객체의 상태를 바꾼다 |

애매하면 메서드로 만들자. 프로퍼티는 "읽기만 하는데 어딘가 바뀌는" 일이 없어야 한다.

> **값을 넣을 수 있는 프로퍼티(setter)**
> `@property`로 만든 프로퍼티에 `@balance.setter`를 붙인 메서드를 하나 더 만들면 `a.balance = 값`으로 할당할 때 그 메서드가 호출되게 할 수도 있다. 할당되는 값을 검사해 잘못된 값이면 오류를 일으키는 데 쓰는데, 오류를 일으키는 방법(`raise`)은 6장에서 배운다. 이 장에서는 프로퍼티를 **읽기 전용**으로만 쓰고, 값을 바꾸는 일은 메서드에 맡긴다.

### 5.2.7 정리 — 다듬은 `Account` 클래스

이 절에서 배운 것을 모두 적용해 `Account` 클래스를 다듬자. `ch05` 폴더에 `account2.py`를 만든다.

```python
# account2.py
class Account:
    """은행 계좌. 잔액은 입금, 출금, 이체로만 바뀐다."""

    bank_name = "파이썬은행"
    count = 0

    def __init__(self, owner, balance=0):
        self.owner = owner
        self._balance = balance
        self._history = []
        Account.count += 1

    @property
    def balance(self):
        """현재 잔액."""
        return self._balance

    @property
    def history(self):
        """거래 기록. (종류, 금액) 튜플을 담은 튜플로 돌려준다."""
        return tuple(self._history)

    def deposit(self, amount):
        """amount원을 입금한다. 금액이 0 이하이면 입금하지 않고 False를 돌려준다."""
        if amount <= 0:
            return False
        self._balance += amount
        self._history.append(("입금", amount))
        return True

    def withdraw(self, amount):
        """amount원을 출금한다. 금액이 0 이하이거나 잔액이 모자라면 False를 돌려준다."""
        if amount <= 0 or amount > self._balance:
            return False
        self._balance -= amount
        self._history.append(("출금", amount))
        return True

    def transfer(self, other, amount):
        """other 계좌로 amount원을 이체한다. 성공하면 True를 돌려준다."""
        if not self.withdraw(amount):
            return False
        other.deposit(amount)
        return True

    def __str__(self):
        return f"{self.owner}님의 {self.bank_name} 계좌 (잔액 {self._balance:,}원)"

    def __repr__(self):
        return f"Account({self.owner!r}, {self._balance!r})"


chulsoo = Account("철수", 10000)
younghee = Account("영희")
chulsoo.transfer(younghee, 3000)
younghee.withdraw(500)
print(chulsoo.deposit(-20000), chulsoo.withdraw(-5000))
print(chulsoo)
print(younghee)
print(younghee.history)
print([chulsoo, younghee])
print(f"개설된 계좌 수: {Account.count}")
```

```
False False
철수님의 파이썬은행 계좌 (잔액 7,000원)
영희님의 파이썬은행 계좌 (잔액 2,500원)
(('입금', 3000), ('출금', 500))
[Account('철수', 7000), Account('영희', 2500)]
개설된 계좌 수: 2
```

5.1의 `show()`는 지우고 `__str__`으로 바꾸었다. `deposit()`과 `withdraw()`는 금액이 0 이하이면 아무것도 바꾸지 않고 `False`를 돌려준다. 그래서 `deposit()`도 `withdraw()`처럼 성공 여부를 돌려주게 되었다. `transfer()`는 `withdraw()`의 검사를 그대로 거치므로 따로 검사하지 않아도 된다. (객체를 만들 때 넘긴 초기 잔액이 음수인 경우처럼 `False`를 돌려줄 수 없는 `__init__` 안의 검사는 6장에서 오류를 일으키는 방법을 배운 뒤에 한다.) `transfer()` 안의 `other.deposit(amount)`는 다른 객체의 `_balance`를 직접 고치지 않고 **그 객체의 공개 메서드를 호출**한다는 점도 눈여겨보자. 같은 클래스의 객체끼리라도 정해진 길로만 데이터를 바꾸는 것이 캡슐화다.

## 5.3 상속

은행이 일반 계좌 말고도 **마이너스 통장**(잔액이 0원 아래로 내려가도 정해진 한도까지는 출금할 수 있는 계좌)과 **적금 계좌**(이자가 붙는 계좌)를 만들기로 했다. 두 계좌 모두 예금주와 잔액이 있고, 입금과 이체를 할 수 있다는 점은 일반 계좌와 같다. 다른 점은 몇 군데뿐이다. 이럴 때 쓰는 것이 상속이다.

### 5.3.1 왜 상속이 필요한가

가장 쉬운 방법은 `Account` 클래스를 통째로 복사해 `MinusAccount`라는 이름으로 붙여 넣고, 출금 규칙만 고치는 것이다. 하지만 그러면 4.1.1에서 함수가 없을 때 겪었던 문제가 클래스 단위로 다시 생긴다. 입금할 때 거래 기록을 남기는 방식을 바꾸려면 `Account`, `MinusAccount`, `SavingsAccount`를 모두 찾아 고쳐야 한다.

**상속**(inheritance)은 이미 있는 클래스를 바탕으로 새 클래스를 만드는 방법이다. 새 클래스는 바탕이 된 클래스의 속성과 메서드를 **물려받고**, 필요한 것만 **더하거나 바꾼다.** 공통된 부분은 한 클래스에만 쓰여 있으므로 고칠 곳이 한 군데로 모인다.

### 5.3.2 부모 클래스와 자식 클래스

이 절에서 쓸 `Account`를 셸에 붙여 넣자. 5.2.7에서 다듬은 클래스를 조금 줄인 것이다. 상속에 집중하기 위해 거래 기록과 금액 검사는 뺐다(금액은 양수만 넘긴다).

```python
class Account:
    def __init__(self, owner, balance=0):
        self.owner = owner
        self._balance = balance
    @property
    def balance(self):
        return self._balance
    def deposit(self, amount):
        self._balance += amount
    def withdraw(self, amount):
        if amount > self._balance:
            return False
        self._balance -= amount
        return True
    def __repr__(self):
        return f"{type(self).__name__}({self.owner!r}, {self._balance!r})"
```

`__repr__`에서 클래스 이름을 `"Account"`라고 직접 쓰지 않고 `type(self).__name__`으로 꺼냈다. `type(객체)`는 그 객체의 클래스이고, 클래스의 `__name__` 속성에는 클래스 이름 문자열이 들어 있다. 이렇게 해 두면 잠시 뒤에 만들 자식 클래스의 객체는 `MinusAccount(...)`처럼 자기 클래스 이름으로 보인다.

상속하려면 클래스 이름 뒤 괄호 안에 **바탕이 될 클래스**를 쓴다.

```python
class SavingsAccount(Account):
    pass
```

```python
>>> s = SavingsAccount("영희", 10000)
>>> s.deposit(5000)
>>> s.balance
15000
>>> s
SavingsAccount('영희', 15000)
```

`SavingsAccount`의 본문에는 `pass`밖에 없는데도 `__init__`, `deposit()`, `balance`, `__repr__`이 모두 동작한다. `Account`에게서 물려받았기 때문이다.

- `Account`처럼 물려주는 클래스를 **부모 클래스**(parent class)라고 한다. 상위 클래스, 기반 클래스(base class), 슈퍼클래스(superclass)라고도 한다.
- `SavingsAccount`처럼 물려받는 클래스를 **자식 클래스**(child class)라고 한다. 하위 클래스, 파생 클래스, 서브클래스(subclass)라고도 한다.

물려받는 원리는 5.2.1에서 본 속성 찾기 순서가 한 단계 길어진 것이다.

```
s.deposit
  1) 객체 s에 deposit이 있나?                    → 없다
  2) s의 클래스 SavingsAccount에 deposit이 있나? → 없다
  3) 그 부모 클래스 Account에 deposit이 있나?    → 있다! 이것을 쓴다
```

**자식 클래스에 새 기능 더하기**

적금 계좌에는 이자를 붙이는 기능을 더하자. 자식 클래스 본문에 클래스 속성과 메서드를 추가하면 된다.

```python
class SavingsAccount(Account):
    interest_rate = 0.03
    def add_interest(self):
        """잔액에 이자를 더한다."""
        self.deposit(int(self._balance * self.interest_rate))
```

```python
>>> s = SavingsAccount("영희", 10000)
>>> s.add_interest()
>>> s.balance
10300
```

`add_interest()`는 `SavingsAccount`에만 있다. 부모의 `Account` 객체로는 쓸 수 없다.

```python
>>> a = Account("철수", 10000)
>>> a.add_interest()
Traceback (most recent call last):
  File "<python-input-8>", line 1, in <module>
    a.add_interest()
    ^^^^^^^^^^^^^^
AttributeError: 'Account' object has no attribute 'add_interest'
```

자식은 부모의 것을 물려받지만, 부모는 자식이 더한 것을 모른다.

`add_interest()` 안에서 `self._balance`를 읽었다. 밑줄로 시작하는 이름은 "바깥에서는 건드리지 말라"는 표시였는데(5.2.5), **자식 클래스는 바깥이 아니라 같은 집안으로 보는 것이 관례**다. 자식 클래스의 메서드에서는 부모가 만든 `_` 속성을 써도 된다. 다만 잔액을 바꿀 때는 `self._balance += ...`로 직접 바꾸지 않고 부모의 `deposit()`을 불렀다. 입금 규칙(예를 들어 거래 기록 남기기)이 나중에 `deposit()`에 추가되더라도 이자 입금에도 저절로 적용되게 하려는 것이다.

### 5.3.3 메서드 오버라이딩 — 물려받은 메서드 바꾸기

마이너스 통장은 잔액이 모자라도 한도 100만 원까지는 출금할 수 있다. 출금 규칙이 다르므로 `withdraw()`를 **자식 클래스에서 다시 정의**한다.

```python
class MinusAccount(Account):
    LIMIT = 1_000_000
    def withdraw(self, amount):
        """잔액이 0원 아래로 LIMIT원까지 내려가도록 출금할 수 있다."""
        if amount > self._balance + self.LIMIT:
            return False
        self._balance -= amount
        return True
```

```python
>>> m = MinusAccount("민수", 10000)
>>> m.withdraw(300000)
True
>>> m.balance
-290000
>>> m.withdraw(800000)
False
>>> m.deposit(50000)
>>> m
MinusAccount('민수', -240000)
```

(`1_000_000`은 `1000000`과 같은 정수다. 숫자 사이의 밑줄은 자릿수를 읽기 쉽게 하는 구분자로, 파이썬이 무시한다.)

이처럼 부모에게서 물려받은 메서드를 자식 클래스에서 **같은 이름으로 다시 정의해 바꾸는 것**을 **메서드 오버라이딩**(method overriding)이라고 한다. `m.withdraw(...)`를 호출하면 파이썬은 속성 찾기 순서대로 `MinusAccount`에서 먼저 `withdraw`를 찾으므로, 부모의 `withdraw`는 가려지고 자식의 것이 쓰인다. `deposit()`은 오버라이딩하지 않았으므로 여전히 부모의 것이 쓰인다.

```
m.withdraw(300000)                         m.deposit(50000)
  MinusAccount에 withdraw가 있다 → 이것!     MinusAccount에 deposit이 없다
  (Account의 withdraw는 가려진다)            Account에 있다 → 이것!
```

`__repr__`, `__str__` 같은 던더 메서드도 오버라이딩할 수 있다. 사실 5.2에서 `__str__`과 `__repr__`을 정의한 것도 오버라이딩이었다. 그 이유는 5.3.5에서 알게 된다.

### 5.3.4 `super()` — 부모의 메서드 부르기

**자식의 `__init__`에서 부모의 `__init__` 부르기**

마이너스 통장의 한도를 계좌마다 다르게 정하고 싶다. 그러려면 객체를 만들 때 한도를 받아 인스턴스 속성으로 저장해야 하므로 `__init__`을 오버라이딩해야 한다. 그런데 이렇게 쓰면 문제가 생긴다.

```python
class MinusAccount(Account):
    def __init__(self, owner, balance=0, limit=1_000_000):
        self.limit = limit
```

```python
>>> m = MinusAccount("민수", 10000, limit=500000)
>>> m.limit
500000
>>> m.balance
Traceback (most recent call last):
  File "<python-input-23>", line 1, in <module>
    m.balance
  File "<python-input-1>", line 7, in balance
    return self._balance
           ^^^^^^^^^^^^^
AttributeError: 'MinusAccount' object has no attribute '_balance'. Did you mean: 'balance'?
```

(파이썬이 비슷한 이름인 프로퍼티 `balance`를 제안했지만, 여기서 없는 것은 `_balance` 속성 자체다.) 자식이 `__init__`을 오버라이딩했으므로 부모의 `__init__`은 **호출되지 않았다.** 그래서 `owner`와 `_balance` 속성이 만들어지지 않았다. 부모의 `__init__`이 하던 일을 자식에서 그대로 베껴 쓸 수도 있지만, 그러면 상속한 의미가 없다. 대신 **`super()`로 부모의 `__init__`을 호출**한다.

```python
class MinusAccount(Account):
    def __init__(self, owner, balance=0, limit=1_000_000):
        super().__init__(owner, balance)
        self.limit = limit
    def withdraw(self, amount):
        if amount > self._balance + self.limit:
            return False
        self._balance -= amount
        return True
```

```python
>>> m = MinusAccount("민수", 10000, limit=500000)
>>> m.owner, m.balance, m.limit
('민수', 10000, 500000)
>>> m.withdraw(600000)
False
>>> m.withdraw(510000)
True
>>> m.balance
-500000
```

`super()`는 "부모 클래스 쪽에서 찾아라"라는 뜻이다. `super().__init__(owner, balance)`는 "부모(`Account`)의 `__init__`을 지금 이 객체(`self`)에 대해 호출하라"는 뜻이고, `self`는 자동으로 넘어가므로 쓰지 않는다. 부모의 `__init__`이 `owner`와 `_balance`를 만들고, 자식은 자기에게만 필요한 `limit`을 더 만든다.

**자식 클래스에서 `__init__`을 오버라이딩하면 거의 언제나 첫 줄에서 `super().__init__(...)`을 호출한다**고 기억하자. AI가 만들어 준 코드에서 `super().__init__()`을 자주 보았다면 이 때문이다.

**오버라이딩한 메서드에서 부모의 메서드 쓰기**

`super()`는 `__init__`이 아닌 메서드에도 쓴다. 적금 계좌에서 중도 출금할 때마다 수수료 500원을 함께 빼기로 했다고 하자. 출금 규칙 자체(잔액이 모자라면 실패)는 부모와 같고, **출금 금액에 수수료를 더하는 것**만 다르다.

```python
class SavingsAccount(Account):
    FEE = 500
    def withdraw(self, amount):
        """수수료 FEE원을 더해 출금한다."""
        return super().withdraw(amount + self.FEE)
```

```python
>>> s = SavingsAccount("영희", 10000)
>>> s.withdraw(3000)
True
>>> s.balance
6500
>>> s.withdraw(6500)
False
>>> s.balance
6500
```

자식의 `withdraw()`는 금액에 수수료를 더해 **부모의 `withdraw()`에게 일을 맡긴다.** 잔액 확인과 출금은 부모의 코드가 하고, 자식은 "다른 점"만 쓴다. 여기서 `super().withdraw(...)` 대신 `self.withdraw(...)`라고 쓰면 어떻게 될까? `self.withdraw`는 속성 찾기 순서대로 **자식 자신의** `withdraw`를 찾으므로, 자기가 자기를 끝없이 호출하게 된다(`RecursionError`). 부모의 메서드를 부를 때는 반드시 `super()`를 쓴다.

| 쓰는 모양 | 뜻 |
|---|---|
| 자식에 메서드를 정의하지 않음 | 부모의 메서드를 그대로 쓴다 |
| 자식에 같은 이름의 메서드를 정의 | 오버라이딩. 부모의 것은 가려진다 |
| 오버라이딩한 메서드 안에서 `super().메서드(...)` | 부모의 것을 불러 쓰고, 앞뒤에 자식만의 일을 더한다 |

### 5.3.5 `isinstance()`와 상속

4.5.3에서 `isinstance()`는 "자료형이 정확히 같은가"가 아니라 "**그 자료형의 한 종류인가**"를 묻는다고 했다. 상속을 배웠으니 정확한 뜻을 알 수 있다.

```python
>>> a = Account("철수")
>>> m = MinusAccount("민수")
>>> type(m)
<class '__main__.MinusAccount'>
>>> isinstance(m, MinusAccount)
True
>>> isinstance(m, Account)
True
>>> isinstance(a, MinusAccount)
False
>>> type(m) == Account
False
```

`m`은 `MinusAccount`의 객체이면서 **`Account`의 객체이기도 하다.** 마이너스 통장도 계좌의 한 종류이기 때문이다. 반대로 일반 계좌는 마이너스 통장이 아니다. `type()`은 정확한 클래스 하나만 알려 주므로 `type(m) == Account`는 `False`다. 그래서 자료형을 **검사할 때는** `type()`이 아니라 `isinstance()`를 쓴다고 했던 것이다(4.5.3). 클래스 사이의 관계는 `issubclass()`로 확인한다.

```python
>>> issubclass(MinusAccount, Account)
True
>>> issubclass(Account, MinusAccount)
False
```

**`bool`은 `int`의 자식 클래스다**

4.5.3에서 `isinstance(True, int)`가 `True`였던 이유가 이것이다.

```python
>>> issubclass(bool, int)
True
>>> True + True
2
```

`bool`은 `int`를 상속해 만든 클래스이므로 불리언도 정수의 한 종류다. `isinstance(x, int) and not isinstance(x, bool)`처럼 써야 불리언을 걸러낼 수 있었던 이유도 이제 설명된다.

**모든 클래스의 조상, `object`**

부모 클래스를 쓰지 않고 `class Account:`로 만든 클래스도 사실은 **`object`라는 클래스를 상속**한다. 파이썬의 모든 클래스는 거슬러 올라가면 `object`에 닿는다.

```python
>>> issubclass(Account, object)
True
>>> Account.__mro__
(<class '__main__.Account'>, <class 'object'>)
>>> MinusAccount.__mro__
(<class '__main__.MinusAccount'>, <class '__main__.Account'>, <class 'object'>)
>>> bool.__mro__
(<class 'bool'>, <class 'int'>, <class 'object'>)
```

`__mro__`는 메서드를 찾는 순서(Method Resolution Order)를 보여 준다. `m.withdraw`를 찾을 때 파이썬은 객체 → `MinusAccount` → `Account` → `object` 순서로 찾는다.

`object`에는 `__init__`, `__str__`, `__repr__`, `__eq__` 같은 기본 던더 메서드가 들어 있다. 5.1.3에서 아무것도 정의하지 않은 `Account`의 객체를 `print()`했을 때 `<__main__.Account object at 0x...>`가 나온 것은 `object`의 `__repr__`이 쓰였기 때문이다. 5.2에서 `__str__`과 `__repr__`을 정의한 것은 `object`에게서 물려받은 메서드를 **오버라이딩**한 것이었다.

**같은 메서드, 다른 동작**

상속의 가장 큰 쓸모는 **종류가 다른 객체를 같은 방법으로 다룰 수 있다**는 데 있다. 세 종류의 계좌를 리스트에 담고 모두에서 같은 금액을 출금해 보자.

```python
>>> accounts = [Account("철수", 5000), MinusAccount("민수", 5000), SavingsAccount("영희", 5000)]
>>> for acc in accounts:
...     result = acc.withdraw(5000)
...     print(acc, result)
...
Account('철수', 0) True
MinusAccount('민수', 0) True
SavingsAccount('영희', 5000) False
>>> for acc in accounts:
...     acc.withdraw(3000)
...
False
True
True
>>> accounts
[Account('철수', 0), MinusAccount('민수', -3000), SavingsAccount('영희', 1500)]
```

반복문 안의 코드는 계좌의 종류를 전혀 따지지 않고 `acc.withdraw(...)`를 부를 뿐인데, 객체마다 **자기 클래스의 `withdraw()`**가 실행된다. 이처럼 같은 이름의 메서드가 객체의 종류에 따라 다르게 동작하는 것을 **다형성**(polymorphism)이라고 한다. 새로운 계좌 종류가 생겨도 `Account`를 상속하고 필요한 메서드만 오버라이딩하면, 계좌 목록을 처리하는 코드는 한 줄도 고칠 필요가 없다.

첫 번째 반복에서 적금 계좌는 수수료 500원까지 5,500원이 필요해 출금에 실패했고, 두 번째 반복에서는 잔액이 0원이 된 일반 계좌가 실패하고 마이너스 통장은 0원 아래로 내려갔다. (두 번째 반복문에서 셸에 `False`, `True`, `True`가 출력된 것은 반복문 안에서 호출만 하고 결과를 버렸기 때문이다. 대화형 셸은 식의 결과가 `None`이 아니면 화면에 보여 준다. 스크립트 파일에서는 아무것도 출력되지 않는다.)

> **예외도 클래스다**
> 지금까지 본 `ValueError`, `TypeError`, `KeyError`, `AttributeError`도 모두 클래스이고, 상속 관계로 묶여 있다. 예를 들어 `KeyError`와 `IndexError`는 `LookupError`의 자식이고, 거의 모든 예외는 `Exception`의 자손이다. 6장에서 "`except LookupError:`로 잡으면 `KeyError`와 `IndexError`를 모두 잡을 수 있다", "`class InsufficientBalanceError(Exception):`으로 나만의 예외를 만든다" 같은 내용을 배우는데, 모두 이 절의 상속과 `isinstance()`의 원리로 동작한다.

### 5.3.6 상속은 언제 쓰나

상속은 강력하지만 아무 데나 쓰면 오히려 코드가 꼬인다. 상속을 쓸지 판단할 때는 다음 문장을 만들어 보자.

> **"자식은 부모의 한 종류다"** (is-a)

- "마이너스 통장은 계좌의 한 종류다" → 자연스럽다. 상속해도 좋다.
- "정사각형은 직사각형의 한 종류다" → 자연스럽다.
- "장바구니는 상품의 한 종류다" → 어색하다. 장바구니는 상품을 **가지고 있다**(has-a).
- "도서관은 책의 한 종류다" → 어색하다. 도서관은 책을 **가지고 있다.**

"가지고 있다"가 자연스러우면 상속하지 말고 **속성으로 가지게** 한다. 실습 5-2의 `Cart`가 상품 정보를 `_items` 속성으로 가진 것, 실습 5-5의 `Library`가 책 목록을 속성으로 가지는 것이 그런 예다. 객체가 다른 객체를 속성으로 가지는 것을 **구성**(composition)이라고 하며, 실무에서는 상속보다 훨씬 많이 쓴다.

> **실무에서 만나는 상속**
> 이 과정을 마치고 실제로 코드를 쓰다 보면, 상속은 **내가 부모 클래스를 설계하기보다 라이브러리가 준비한 부모 클래스를 물려받는** 경우가 대부분이다. 6장의 `class 내예외(Exception):`, LLM의 응답 모양을 정할 때 쓰는 Pydantic의 `class Answer(BaseModel):`, 테스트를 쓸 때의 `class TestCart(unittest.TestCase):` 같은 것이다. 이런 코드를 만나면 "부모가 준비해 둔 기능을 물려받고, 필요한 것만 더하거나 오버라이딩하는구나" 하고 읽으면 된다. 직접 상속 구조를 설계할 때는 **두세 단계를 넘지 않게** 얕게 유지하자.

### 실습 5-3. 상속

**1) 결과 예상하기**

```python
# (가)
class Animal:
    def __init__(self, name):
        self.name = name

    def speak(self):
        return "..."

    def introduce(self):
        return f"{self.name}: {self.speak()}"


class Dog(Animal):
    def speak(self):
        return "멍멍"


class Puppy(Dog):
    def speak(self):
        return super().speak() + "(작게)"


for a in [Animal("동물"), Dog("바둑이"), Puppy("초코")]:
    print(a.introduce())
```

```python
# (나)
class Parent:
    def __init__(self):
        self.x = 1


class Child(Parent):
    def __init__(self):
        self.y = 2


c = Child()
print(c.y)
print(c.x)
```

```python
# (다)
class A:
    pass


class B(A):
    pass


b = B()
print(isinstance(b, A), isinstance(b, B), isinstance(b, object))
print(type(b) == A, type(b) is B)
print(issubclass(A, B))
```

(가)에서 `introduce()`는 `Animal`에만 정의되어 있는데 `speak()`의 결과가 객체마다 다른 이유를 설명해 보자. (`introduce()` 안의 `self`가 무엇인지 생각해 보자.) (나)는 오류가 난다. 어디서 왜 나는지 설명하고 고쳐 보자.

**2) `payroll.py` — 급여 계산**

직원의 종류에 따라 월급을 다르게 계산한다.

- `Employee(name, base_pay)`: 정규직. `pay()`는 기본급 `base_pay`를 돌려준다. `__str__`은 `철수(정규직): 3,000,000원`처럼 이름, 종류, 월급을 보여 준다. 종류를 돌려주는 `kind()` 메서드를 두고 `__str__`에서 쓴다.
- `Manager(name, base_pay, bonus)`: 관리자. `Employee`를 상속한다. `pay()`는 기본급에 보너스를 더해 돌려준다. **부모의 `pay()`를 `super()`로 불러** 계산한다.
- `PartTimer(name, hourly_wage, hours)`: 시간제. `Employee`를 상속한다. `pay()`는 시급 × 일한 시간이다. 부모의 `__init__`에는 `base_pay`로 0을 넘긴다.

```python
staff = [
    Employee("철수", 3_000_000),
    Manager("영희", 4_000_000, 500_000),
    PartTimer("민수", 12_000, 80),
]
for e in staff:
    print(e)
total = 0
for e in staff:
    total += e.pay()
print(f"총 급여: {total:,}원")
managers = 0
for e in staff:
    if isinstance(e, Manager):
        managers += 1
print(f"관리자 수: {managers}명")
```

```
철수(정규직): 3,000,000원
영희(관리자): 4,500,000원
민수(시간제): 960,000원
총 급여: 8,460,000원
관리자 수: 1명
```

`__str__`은 `Employee`에만 정의했는데 종류와 월급이 직원마다 맞게 나오는 이유를 설명해 보자.

## 5.4 데이터 클래스

지금까지 만든 `Account`는 **동작**(입금, 출금, 이체)과 **규칙**(잔액은 메서드로만 바뀐다)이 중심인 클래스였다. 그런데 프로그램에는 동작보다 **데이터를 묶어 두는 것**이 목적인 값도 많다. 상품(이름, 가격, 분류), 학생(이름, 학번, 점수), 채팅 메시지(역할, 내용), API 응답의 한 항목 같은 것이다. 이 절에서는 이런 "데이터 묶음"을 짧고 안전하게 정의하는 **데이터 클래스**를 배운다.

### 5.4.1 데이터 묶음을 표현하는 세 가지 방법

상품 하나를 표현해 보자. 3장까지 배운 방법은 튜플과 딕셔너리다.

```python
>>> p1 = ("커피", 2500, "음료")
>>> p1[1]
2500
>>> p2 = {"name": "커피", "price": 2500, "category": "음료"}
>>> p2["price"]
2500
```

튜플은 `p1[1]`이 무엇인지 코드만 봐서는 알 수 없다. 딕셔너리는 의미가 드러나지만 5.1.1에서 본 것처럼 키 이름 오타를 막지 못하고 자동 완성도 되지 않는다. 그래서 5.1에서 배운 일반 클래스로 만들어 보자.

```python
class Product:
    def __init__(self, name, price, category):
        self.name = name
        self.price = price
        self.category = category
    def __repr__(self):
        return f"Product(name={self.name!r}, price={self.price!r}, category={self.category!r})"
```

```python
>>> p3 = Product("커피", 2500, "음료")
>>> p3.price
2500
>>> p3
Product(name='커피', price=2500, category='음료')
```

`p3.price`로 읽을 수 있고 자동 완성도 된다. 하지만 속성이 세 개뿐인데 `__init__`에서 이름을 세 번씩(`name`, `self.name`, `= name`) 써야 하고, `__repr__`에서 또 한 번 쓴다. 속성을 하나 추가하면 네 군데를 고쳐야 한다. 게다가 한 가지 문제가 더 있다.

```python
>>> Product("커피", 2500, "음료") == Product("커피", 2500, "음료")
False
```

내용이 똑같은 두 상품을 `==`로 비교했는데 `False`다. 직접 만든 클래스는 `==`를 어떻게 비교해야 할지 모르므로, `object`에게서 물려받은 기본 `__eq__`가 **같은 객체인지**(`is`)를 비교하기 때문이다. 내용이 같으면 같다고 하려면 `__eq__` 메서드도 직접 만들어야 한다. 데이터를 묶어 두기만 하려는데 써야 할 코드가 너무 많다.

### 5.4.2 타입 힌트 — 값의 자료형을 적어 두기

데이터 클래스를 배우기 전에 필요한 표기법을 하나 익히자. 변수 이름 뒤에 콜론과 자료형을 쓰면 "이 이름에는 이런 자료형의 값을 담을 것"이라는 설명을 붙일 수 있다. 이것을 **타입 힌트**(type hint)라고 한다.

```python
>>> name: str = "커피"
>>> price: int = 2500
>>> ratio: float = 0.1
>>> tags: list[str] = ["따뜻함", "인기"]
```

`name: str = "커피"`는 "`name`은 문자열을 담는 이름이고, 지금 `"커피"`를 담는다"라고 읽는다. 함수의 매개변수와 반환값에도 쓸 수 있다.

```python
>>> def total_price(price: int, qty: int = 1) -> int:
...     return price * qty
...
>>> total_price(2500, 3)
7500
```

매개변수 뒤의 `: int`는 그 매개변수의 자료형을, 괄호 뒤의 `-> int`는 **돌려주는 값의 자료형**을 뜻한다. "정수 가격과 정수 수량을 받아 정수를 돌려주는 함수"라고 읽는다.

자주 보는 모양은 다음과 같다.

| 타입 힌트 | 뜻 |
|---|---|
| `x: int`, `x: float`, `x: str`, `x: bool` | 정수 / 실수 / 문자열 / 불리언 |
| `x: list[str]` | 문자열을 담은 리스트 |
| `x: dict[str, int]` | 키가 문자열, 값이 정수인 딕셔너리 |
| `x: tuple[int, int]` | 정수 두 개짜리 튜플 |
| `x: int \| None` | 정수 또는 `None` (`\|`는 "또는") |
| `x: Product` | 직접 만든 `Product` 클래스의 객체 |
| `def f(...) -> None:` | 아무것도 돌려주지 않는 함수 |

**파이썬은 타입 힌트를 검사하지 않는다**

가장 중요한 사실이다. 타입 힌트는 **사람과 도구를 위한 설명**일 뿐, 파이썬은 실행할 때 자료형이 맞는지 확인하지 않는다.

```python
>>> total_price("커피", 3)
'커피커피커피'
```

정수를 받는다고 적었지만 문자열을 넘겨도 오류 없이 실행된다(2장의 문자열 반복이다). 그러면 타입 힌트를 왜 쓸까?

- **읽는 사람에게** 무엇을 넘기고 무엇을 돌려받는지 알려 준다. 독스트링보다 짧고 정확하다.
- **VS Code가** 그 정보를 이용해 자동 완성을 해 주고, 말풍선에 자료형을 보여 주고, 설정에 따라 잘못된 값을 넘기는 코드에 **물결 밑줄로 경고**해 준다. 실행하기 전에 실수를 찾을 수 있다.
- **AI 코딩 도구도** 타입 힌트가 있는 코드를 더 정확하게 이해하고 고친다.
- 일부 라이브러리는 타입 힌트를 **읽어서 동작을 정한다.** 다음에 배울 `@dataclass`와, LLM 응답 모양을 정할 때 쓰는 Pydantic이 그렇다.

이 장에서는 데이터 클래스에 필요한 기본 모양만 쓴다. 타입 힌트를 더 다양하게 쓰는 방법(`typing` 모듈)은 8장에서 조금 더 다룬다. 이미 작성한 코드에 타입 힌트를 모두 붙이려고 애쓸 필요는 없다. 함수의 매개변수와 반환값, 그리고 다음에 배울 데이터 클래스의 필드부터 습관을 들이자.

### 5.4.3 `@dataclass`로 데이터 클래스 만들기

`dataclasses` 모듈의 `dataclass`를 가져와 클래스 위에 붙이면, 5.4.1에서 손으로 쓰던 코드를 파이썬이 **대신 만들어 준다.**

```python
>>> from dataclasses import dataclass
```

```python
@dataclass
class Product:
    name: str
    price: int
    category: str
```

클래스 본문에는 메서드 대신 **`이름: 자료형`** 줄만 늘어놓았다. 이 줄 하나하나를 **필드**(field)라고 한다. `@dataclass`는 5.2.6에서 본 데코레이터 문법으로, 바로 아래 클래스에 기능을 덧붙인다. 필드 목록을 읽어 다음 메서드를 자동으로 만들어 준다.

- `__init__`: 필드를 **적힌 순서대로** 매개변수로 받아 같은 이름의 인스턴스 속성에 저장한다.
- `__repr__`: `Product(name='커피', price=2500, category='음료')` 모양으로 보여 준다.
- `__eq__`: **같은 클래스의 객체이고** 모든 필드의 값이 같으면 `==`가 `True`다. 필드 값이 같아도 클래스가 다르면(예를 들어 실습 5-5의 `Book`과 그 자식 `ReferenceBook`) `False`다.

```python
>>> p = Product("커피", 2500, "음료")
>>> p
Product(name='커피', price=2500, category='음료')
>>> p.name, p.price
('커피', 2500)
>>> p == Product("커피", 2500, "음료")
True
>>> p == Product("커피", 3000, "음료")
False
>>> q = Product(name="삼각김밥", category="식품", price=1500)
>>> q
Product(name='삼각김밥', price=1500, category='식품')
>>> p.price = 2800
>>> p
Product(name='커피', price=2800, category='음료')
```

5.4.1에서 일곱 줄로 쓰던 클래스가 네 줄이 되었고, 그때 없던 `==` 비교까지 생겼다. 만들어진 `__init__`은 평범한 메서드이므로 키워드 인자(4.2.2)도 쓸 수 있고, 인자 개수가 틀리면 4장에서 본 `TypeError`가 난다. 속성은 일반 클래스처럼 바꿀 수 있다.

```python
>>> Product("커피", 2500)
Traceback (most recent call last):
  File "<python-input-12>", line 1, in <module>
    Product("커피", 2500)
    ~~~~~~~^^^^^^^^^^^^^
TypeError: Product.__init__() missing 1 required positional argument: 'category'
>>> Product("커피", 2500, "음료", catgory="음료")
Traceback (most recent call last):
  File "<python-input-13>", line 1, in <module>
    Product("커피", 2500, "음료", catgory="음료")
    ~~~~~~~^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^
TypeError: Product.__init__() got an unexpected keyword argument 'catgory'. Did you mean 'category'?
```

두 번째 오류에 주목하자. 딕셔너리였다면 `{"catgory": "음료"}`처럼 오타가 난 키가 그대로 들어갔을 것이다. 데이터 클래스는 **정해진 필드 말고는 받지 않으므로** 오타를 만든 그 자리에서 알려 주고, 파이썬 3.13부터는 비슷한 필드 이름까지 제안해 준다.

다만 이것은 객체를 **만들 때**의 이야기다. 이미 만든 객체에 할당할 때의 오타는 일반 클래스와 똑같이 오류 없이 새 속성을 만든다(5.1.5).

```python
>>> p.prcie = 1000
>>> vars(p)
{'name': '커피', 'price': 2800, 'category': '음료', 'prcie': 1000}
```

데이터 클래스가 막아 주는 것은 "만들 때 넘기는 인자"까지다. 만든 뒤에는 정해진 필드를 읽고 바꾸는 습관을 지키자.

**기본값이 있는 필드**

필드에 `= 값`을 쓰면 기본값이 된다. 4.2.3에서 기본값이 있는 매개변수를 뒤에 두었던 것처럼, **기본값이 있는 필드는 기본값이 없는 필드보다 뒤에** 써야 한다. 만들어지는 `__init__`의 매개변수 순서가 필드 순서이기 때문이다.

```python
@dataclass
class Product:
    name: str
    price: int
    category: str = "기타"
    stock: int = 0
```

```python
>>> Product("볼펜", 1200)
Product(name='볼펜', price=1200, category='기타', stock=0)
>>> Product("생수", 1000, "음료", stock=30)
Product(name='생수', price=1000, category='음료', stock=30)
```

순서를 어기면 클래스를 **정의하는 순간** 오류가 난다.

```python
@dataclass
class Bad:
    category: str = "기타"
    name: str
```

```
Traceback (most recent call last):
  ...
TypeError: non-default argument 'name' follows default argument 'category'
```

**타입 힌트는 검사되지 않는다 — 데이터 클래스에서도**

`@dataclass`는 타입 힌트를 읽어 "어떤 필드가 있는지"를 알아낼 뿐, 값의 자료형을 검사하지는 않는다.

```python
>>> Product("볼펜", "천이백원")
Product(name='볼펜', price='천이백원', category='기타', stock=0)
```

`price`에 문자열이 들어갔지만 오류가 나지 않는다. VS Code가 경고해 줄 수는 있지만, 실행 중에 자료형을 검사해 주는 것은 아니다. 외부에서 들어온 데이터(사용자 입력, 파일, API 응답)의 자료형까지 확인하려면 직접 검사 코드를 쓰거나(6장), 검사 기능이 있는 라이브러리(Pydantic 등)를 쓴다.

### 5.4.4 데이터 클래스에도 메서드와 프로퍼티를

데이터 클래스도 클래스이므로 메서드, 프로퍼티, `__str__`을 마음대로 추가할 수 있다. 자동으로 만들어지는 것은 `__init__`, `__repr__`, `__eq__`뿐이고, 나머지는 일반 클래스와 같다.

```python
@dataclass
class OrderLine:
    """주문 한 줄: 상품과 수량."""
    product: Product
    qty: int = 1
    @property
    def amount(self) -> int:
        """이 줄의 금액."""
        return self.product.price * self.qty
    def __str__(self):
        return f"{self.product.name} {self.product.price:,}원 x {self.qty} = {self.amount:,}원"
```

```python
>>> coffee = Product("커피", 2500, "음료")
>>> line = OrderLine(coffee, 3)
>>> line.amount
7500
>>> print(line)
커피 2,500원 x 3 = 7,500원
>>> line
OrderLine(product=Product(name='커피', price=2500, category='음료', stock=0), qty=3)
```

`OrderLine`의 `product` 필드에는 **다른 데이터 클래스의 객체**가 들어 있다. 3.4.6에서 딕셔너리 안에 딕셔너리를 넣었던 것처럼 객체 안에 객체를 넣을 수 있고, `line.product.price`처럼 점을 이어서 꺼낸다. LLM 응답을 `response.choices[0].message.content`처럼 꺼내는 것과 같은 모양이다.

`__repr__`은 자동으로 만들어진 것이 쓰이고, `print()`에는 우리가 정의한 `__str__`이 쓰였다. 5.2.4의 규칙 그대로다.

### 5.4.5 가변 객체를 기본값으로 쓰려면 — `field(default_factory=...)`

상품에 태그 목록을 두고, 기본값을 빈 리스트로 하고 싶다. 4.2.5와 5.2.2를 기억한다면 `tags: list[str] = []`가 위험하다는 것을 눈치챘을 것이다. 다행히 데이터 클래스는 이 실수를 **허락하지 않는다.**

```python
@dataclass
class Post:
    title: str
    tags: list[str] = []
```

```
Traceback (most recent call last):
  ...
ValueError: mutable default <class 'list'> for field tags is not allowed: use default_factory
```

"가변 객체 `list`를 기본값으로 쓸 수 없으니 `default_factory`를 쓰라"는 뜻이다. `dataclasses` 모듈의 `field()`에 `default_factory=list`를 넘기면, **객체를 만들 때마다 `list()`를 호출해** 새 빈 리스트를 만들어 준다. `list`에 괄호를 붙이지 않았다는 데 주의하자. 4.4에서 배운 대로 **함수(여기서는 클래스) 자체를 넘기고**, 호출은 데이터 클래스가 필요할 때마다 한다.

```python
>>> from dataclasses import dataclass, field
```

```python
@dataclass
class Post:
    title: str
    tags: list[str] = field(default_factory=list)
```

```python
>>> a = Post("첫 글")
>>> b = Post("둘째 글")
>>> a.tags.append("파이썬")
>>> a.tags, b.tags
(['파이썬'], [])
```

`a`와 `b`가 각자 자기 리스트를 가진다. 빈 딕셔너리가 기본값이면 `field(default_factory=dict)`로 쓴다.

### 5.4.6 바꿀 수 없는 데이터 클래스 — `frozen=True`

좌표, 설정값, 이미 확정된 주문처럼 **한번 만들면 바뀌지 않아야 하는** 데이터가 있다. `@dataclass(frozen=True)`로 쓰면 필드를 바꿀 수 없는 데이터 클래스가 된다.

```python
@dataclass(frozen=True)
class Point:
    x: int
    y: int
```

```python
>>> p = Point(3, 4)
>>> p.x = 10
Traceback (most recent call last):
  File "<python-input-41>", line 1, in <module>
    p.x = 10
    ^^^
  File "<string>", line 16, in __setattr__
dataclasses.FrozenInstanceError: cannot assign to field 'x'
```

3장의 튜플처럼 필드를 바꿀 수 없게 된 것이다. 그리고 튜플처럼 **해시 가능**해져서, 필드가 모두 해시 가능한 값(숫자, 문자열, 튜플 등)이면 집합에 넣거나 딕셔너리의 키로 쓸 수 있다(3.5.6). 일반 데이터 클래스는 가변 객체라서 집합에 넣을 수 없다.

```python
>>> visited = {Point(0, 0), Point(1, 2), Point(0, 0)}
>>> visited
{Point(x=1, y=2), Point(x=0, y=0)}
>>> Point(1, 2) in visited
True
```

(집합은 순서를 보장하지 않으므로 출력 순서는 다를 수 있다.)

**`frozen=True`가 막는 것과 막지 못하는 것**

`frozen=True`가 막는 것은 **필드에 다른 값을 할당하는 것**이다. 필드가 가리키는 객체의 안쪽까지 얼리지는 않는다.

```python
@dataclass(frozen=True)
class Note:
    title: str
    tags: list[str]
```

```python
>>> n = Note("메모", ["파이썬"])
>>> n.tags.append("AI")
>>> n
Note(title='메모', tags=['파이썬', 'AI'])
>>> {n}
Traceback (most recent call last):
  ...
TypeError: unhashable type: 'list'
```

`n.tags = []`는 막히지만 `n.tags.append("AI")`는 리스트를 고치는 것이라서 막히지 않는다. 그리고 해시를 계산할 때 필드 값을 모두 쓰는데 그중 리스트는 해시할 수 없으므로, 집합에 넣으려는 순간 `TypeError`가 난다. 3.5.6에서 리스트가 든 튜플을 집합에 넣을 수 없었던 것과 같다. 정말 바뀌지 않는 데이터를 만들려면 필드를 **안쪽까지 불변인 값**으로 채운다. 문자열과 숫자는 그 자체로 불변이지만, 튜플이나 frozen 데이터 클래스는 그 안에 리스트 같은 가변 객체가 들어 있으면 내용이 바뀔 수 있다. 태그 목록이라면 `tags: tuple[str, ...]`로 두고 요소도 문자열로 채우는 식이다.

값을 "바꾸는" 대신 **새 객체를 만들어 돌려주는** 방식(4.3.6의 `sorted` 방식)으로 메서드를 설계하면 된다. 예를 들어 `def moved(self, dx, dy): return Point(self.x + dx, self.y + dy)`처럼.

### 5.4.7 딕셔너리와 데이터 클래스 오가기

실무에서 데이터는 딕셔너리 모양으로 들어오는 경우가 많다. 3.4.6에서 본 JSON 데이터, 7장에서 읽을 JSON 파일, LLM API의 응답이 그렇다. 딕셔너리와 데이터 클래스를 서로 바꾸는 방법을 알아 두자.

**딕셔너리 → 데이터 클래스: `**`로 풀어 넣기**

4.2.8에서 `f(**d)`처럼 딕셔너리를 `**`로 풀어 키워드 인자로 넘길 수 있다고 배웠다. 데이터 클래스의 `__init__`도 함수이므로 그대로 쓸 수 있다.

```python
@dataclass
class Product:
    name: str
    price: int
    category: str = "기타"
```

```python
>>> data = {"name": "커피", "price": 2500, "category": "음료"}
>>> Product(**data)
Product(name='커피', price=2500, category='음료')
```

`Product(**data)`는 `Product(name="커피", price=2500, category="음료")`와 같다. 딕셔너리의 리스트를 데이터 클래스의 리스트로 바꿀 때도 반복문과 함께 쓴다.

```python
>>> rows = [
...     {"name": "커피", "price": 2500, "category": "음료"},
...     {"name": "삼각김밥", "price": 1500, "category": "식품"},
...     {"name": "볼펜", "price": 1200},
... ]
>>> products = []
>>> for row in rows:
...     products.append(Product(**row))
...
>>> products
[Product(name='커피', price=2500, category='음료'), Product(name='삼각김밥', price=1500, category='식품'), Product(name='볼펜', price=1200, category='기타')]
>>> cheapest = min(products, key=lambda p: p.price)
>>> cheapest.name
'볼펜'
```

딕셔너리에 필드에 없는 키가 있거나 필요한 키가 빠져 있으면 `TypeError`가 난다(5.4.3). 데이터의 모양이 예상과 다르다는 것을 **데이터를 받는 그 자리에서** 알 수 있으므로, 나중에 엉뚱한 곳에서 `KeyError`를 만나는 것보다 훨씬 낫다.

**데이터 클래스 → 딕셔너리: `asdict()`**

반대로 데이터 클래스를 딕셔너리로 바꿀 때는 `dataclasses` 모듈의 `asdict()`를 쓴다. JSON 파일로 저장하거나(7장) API에 보낼 때 필요하다.

```python
>>> from dataclasses import asdict
>>> asdict(products[0])
{'name': '커피', 'price': 2500, 'category': '음료'}
```

### 5.4.8 무엇을 쓸까 — 딕셔너리, 데이터 클래스, 일반 클래스

같은 데이터를 세 가지로 표현할 수 있게 되었다. 다음 표를 기준으로 고르자.

| | 딕셔너리 | 데이터 클래스 | 일반 클래스 |
|---|---|---|---|
| 중심 | 데이터 | 데이터 (+ 간단한 계산) | 동작과 규칙 |
| 키/속성 | 실행 중에 자유롭게 추가 | 만들 때 받는 값은 필드로 정해져 있다. 만든 뒤 새 속성을 할당하는 것은 막지 않는다 | `__init__`에서 정한다. 만든 뒤 새 속성을 할당하는 것은 막지 않는다 |
| 오타 | 그대로 들어가거나 `KeyError` | 만들 때 `TypeError`, 읽을 때 `AttributeError`, 자동 완성. 할당할 때의 오타는 새 속성이 된다 | 만들 때는 `__init__`의 매개변수대로, 그 밖에는 데이터 클래스와 같다 |
| `repr`, `==` | 있음 | 자동으로 만들어진다 | 직접 만들어야 한다 |
| 어울리는 곳 | 키가 그때그때 달라지는 데이터, JSON을 잠깐 다루고 넘길 때 | 모양이 정해진 데이터를 여러 함수가 주고받을 때 | 데이터를 규칙에 맞게만 바뀌도록 지켜야 할 때 |
| 예 | 단어별 개수 `{"사과": 3, ...}`, 설정 파일 내용 | 상품, 학생, 채팅 메시지, 주문 한 줄 | 계좌, 장바구니, 도서관 |

판단이 어려우면 이렇게 생각하자.

- 키가 **미리 정해져 있지 않으면** → 딕셔너리. 단어 빈도처럼 키 자체가 데이터인 경우다.
- 정해진 모양의 데이터를 **여러 함수에 넘기고 받는다면** → 데이터 클래스. 4.1.5에서 "돌려주는 값이 서너 개를 넘어가면 데이터 클래스를 쓰는 것이 좋다"고 한 것이 이 경우다. `return name, price, category, stock` 대신 `return Product(...)`를 돌려주면 받는 쪽에서 순서를 기억할 필요가 없다.
- 바깥에서 데이터를 마음대로 바꾸면 **규칙이 깨지는** 경우 → 일반 클래스에 `_이름`과 프로퍼티, 메서드. 계좌의 잔액이 그런 예다.

> **LLM 코드에서 만나는 데이터 클래스 모양**
> LLM에게 정해진 모양의 답(구조화된 출력)을 받을 때 다음과 같은 코드를 자주 본다.
> ```python
> from pydantic import BaseModel
>
> class MovieReview(BaseModel):
>     title: str
>     rating: int
>     summary: str
> ```
> `@dataclass` 대신 `BaseModel`을 상속했다는 점(5.3)만 다르고, `이름: 자료형`으로 필드를 늘어놓는 모양은 이 절의 데이터 클래스와 같다. Pydantic은 `@dataclass`와 달리 **실행 중에 자료형을 검사**하므로, LLM이 `rating`에 `"다섯 개"`처럼 엉뚱한 값을 돌려주면 그 자리에서 오류를 낸다. Pydantic은 이후 과정에서 다룬다. 지금은 "필드 이름과 자료형으로 데이터의 모양을 정하는 클래스"라고 읽을 수 있으면 충분하다.

**2) `books.py` — 딕셔너리를 데이터 클래스로**

다음 데이터를 `Book` 데이터 클래스의 리스트로 바꾸고, 질문에 답하는 코드를 쓴다.

```python
ROWS = [
    {"title": "파이썬 첫걸음", "author": "김파이", "price": 18000, "year": 2024},
    {"title": "데이터 과학 입문", "author": "이데이", "price": 25000, "year": 2022},
```

- `Book`은 `title: str`, `author: str`, `price: int`, `year: int` 필드를 가진다. 할인율 `discount: float`는 기본값 `0.0`이다.

- `ROWS`를 `Book(**row)`로 바꿔 `books` 리스트를 만든다.
- 2024년 이후에 나온 책에 10% 할인을 적용한다(`book.discount = 0.1`).
- 할인 적용 후 가격이 낮은 순서로 출력한다.
- 마지막으로 가장 비싼 책을 `asdict()`로 딕셔너리로 바꿔 출력한다.

```
「파이썬 첫걸음」 김파이 (2024) 18,000원 → 16,200원
「알고리즘 이야기」 박알고 (2025) 22,000원 → 19,800원
「데이터 과학 입문」 이데이 (2022) 25,000원
「인공지능 개론」 최에이 (2026) 30,000원 → 27,000원
{'title': '인공지능 개론', 'author': '최에이', 'price': 30000, 'year': 2026, 'discount': 0.1}
```

할인율을 바꾸면 `final_price`가 저절로 바뀐다. `final_price`를 필드로 두지 않고 프로퍼티로 만든 이유다(5.2.6).

**3) `chat.py` — 채팅 메시지와 대화**

LLM API에 대화 내용을 보낼 때는 보통 `[{"role": "user", "content": "안녕"}, {"role": "assistant", "content": "안녕하세요!"}]`처럼 **역할과 내용을 담은 딕셔너리의 리스트**를 넘긴다. 이 데이터를 클래스로 다뤄 보자.

- `Message` 데이터 클래스: `role: str`, `content: str` 필드를 가진다. 이미 주고받은 메시지가 바뀌지 않도록 `frozen=True`로 만든다.
- `Conversation` 일반 클래스:
  - `Conversation(system_prompt)`로 만든다. 만들 때 `role`이 `"system"`인 메시지 하나를 `_messages` 리스트에 넣어 둔다.
  - `add_user(content)`, `add_assistant(content)`: 역할에 맞는 `Message`를 추가한다.
  - `messages` 프로퍼티: 메시지들을 튜플로 돌려준다.
  - `to_api()`: 메시지들을 `asdict()`로 바꾼 **딕셔너리의 리스트**로 돌려준다.
  - `count` 프로퍼티: 메시지 수를 돌려준다.

```python
conv = Conversation("너는 친절한 파이썬 강사다.")
conv.add_user("리스트와 튜플의 차이가 뭐야?")
conv.add_assistant("리스트는 바꿀 수 있고, 튜플은 바꿀 수 없습니다.")
conv.add_user("예를 들어 줘.")
print(conv.count)
print(conv.messages[-1])
for m in conv.to_api():
    print(m)
```

```
4
Message(role='user', content='예를 들어 줘.')
{'role': 'system', 'content': '너는 친절한 파이썬 강사다.'}
{'role': 'user', 'content': '리스트와 튜플의 차이가 뭐야?'}
{'role': 'assistant', 'content': '리스트는 바꿀 수 있고, 튜플은 바꿀 수 없습니다.'}
{'role': 'user', 'content': '예를 들어 줘.'}
```

`conv.messages[0].role = "user"`가 오류를 내는지 확인하자. 그다음 `Message`에서 `frozen=True`를 잠시 빼고 다시 실행해 보자. `messages` 프로퍼티가 튜플을 돌려주는데도 무엇이 바뀌는가? 5.2.6의 "튜플이 지켜 주는 범위"로 설명해 보자. `Message`는 데이터 클래스로, `Conversation`은 일반 클래스로 만든 이유도 5.4.8의 표로 설명해 보자. (`role`에 `"user"`, `"assistant"`, `"system"`이 아닌 값이 들어오지 않게 막는 방법은 6장에서 배운다.)

## 실습 5-5. 종합 — 도서 대출 관리 프로그램 (클래스 버전)

4장 실습 4-7의 도서 대출 관리 프로그램을 클래스로 다시 만든다. 기능은 거의 같지만, 데이터와 그 데이터를 다루는 함수를 클래스로 묶으면 코드의 모양이 어떻게 달라지는지 직접 경험하는 것이 목표다. `ch05` 폴더에 `library.py`를 만든다.

4장과 마찬가지로 **클래스와 메서드의 이름, 매개변수, 독스트링이 먼저 주어지고, 우리는 독스트링에 적힌 대로 본문을 채운다.** 4장 버전과 비교하며 읽어 보자.

| 4장 (함수 버전) | 5장 (클래스 버전) |
|---|---|
| `BOOKS` 딕셔너리 `{코드: 제목}` | 바꿀 수 없는 `Book` 데이터 클래스, 대출할 수 없는 `ReferenceBook`(상속) |
| `loans` 딕셔너리 `{코드: {"who": ..., "due": ...}}` | `Loan` 데이터 클래스 |
| `LOAN_DAYS`, `LATE_FEE_PER_DAY` 전역 상수 | `Library`의 클래스 속성 |
| `borrow(loans, ...)`, `return_book(loans, ...)` | `library.borrow(...)`, `library.return_book(...)` |
| `main()`이 `loans`를 들고 모든 함수에 넘긴다 | `main()`은 `library` 객체 하나만 가진다 |

**주어진 코드**

```python
# library.py
from dataclasses import dataclass
from datetime import date, timedelta

WEEKDAYS = ("월", "화", "수", "목", "금", "토", "일")


def format_date(d: date) -> str:
    """날짜를 '2026-11-14(토)' 모양의 문자열로 돌려준다."""


@dataclass(frozen=True)
class Book:
    """도서 한 권. 도서관에 등록된 뒤에는 바뀌지 않는다."""

    code: str
    title: str

    def can_borrow(self) -> bool:
        """관외 대출을 할 수 있으면 True를 돌려준다."""
        return True

    def __str__(self):
        return f"'{self.title}'"


class ReferenceBook(Book):
    """참고 도서(사전 등). 도서관 안에서만 볼 수 있고 대출할 수 없다."""


@dataclass
class Loan:
    """대출 한 건."""

    book: Book
    who: str
    due: date

    def overdue_days(self, today: date) -> int:
        """반납 기한에서 today까지 며칠 지났는지 돌려준다. 기한 당일까지는 0이다."""

    def line(self, today: date) -> str:
        """'B01 파이썬 첫걸음 | 철수 | 기한 2026-11-14(토)' 모양의 한 줄을 돌려준다.

        연체되었으면 끝에 ' | N일 연체'를 붙인다.
        """


class Library:
    """도서관. 소장 도서와 대출 기록을 관리한다."""

    LOAN_DAYS = 14
    LATE_FEE_PER_DAY = 100

    def __init__(self, books: list[Book]):
        """books의 도서를 소장한다. 대출 기록은 비어 있는 상태로 시작한다."""
        self._books = {}  # {도서코드: Book}
        self._loans = {}  # {도서코드: Loan}
        # 여기를 채운다

    @property
    def loan_count(self) -> int:
        """대출 중인 도서 수."""

    def find(self, code: str) -> Book | None:
        """도서 코드(대소문자 구분 없음)로 도서를 찾아 돌려준다. 없으면 None."""

    def late_fee(self, days_over: int) -> int:
        """연체일수 days_over에 따른 연체료(원)를 돌려준다."""

    def borrow(self, code: str, who: str, today: date, days: int | None = None) -> str:
        """도서를 대출하고, 화면에 출력할 결과 메시지를 돌려준다.

        반납 기한은 today로부터 days일 뒤다. days가 None이면 LOAN_DAYS일이다.
        없는 도서, 대출할 수 없는 도서, 이미 대출 중인 도서이면 대출하지 않는다.
        """

    def return_book(self, code: str, today: date) -> str:
        """도서를 반납하고, 화면에 출력할 결과 메시지를 돌려준다.

        연체되었으면 메시지에 연체일수와 연체료를 포함한다.
        """

    def loan_lines(self, today: date, only_overdue: bool = False) -> list[str]:
        """대출 목록을 한 줄에 한 권씩, 문자열의 리스트로 돌려준다.

        기본은 반납 기한이 빠른 순서다(기한이 같으면 도서 코드 순).
        only_overdue가 True이면 연체된 도서만, 연체일수가 긴 순서로 돌려준다.
        """

    def book_lines(self) -> list[str]:
        """소장 도서 전체를 도서 코드 순으로 한 줄씩 돌려준다.

        줄 끝에 '대출 가능', '대출 중', '관내 열람' 중 하나를 붙인다.
        """

    def __repr__(self):
        return f"Library(도서 {len(self._books)}권, 대출 {self.loan_count}권)"


def main():

            Book("B05", "인공지능 개론"),
```

**명령**

**요구 사항**

1. 4장 실습 4-7의 요구 사항 1~5(대소문자 구분 없음, 형식 안내, `날짜 N` 검사, 빈 목록 메시지, `global` 금지)를 그대로 지킨다.
2. 도서 코드의 대소문자 처리는 **`Library`가 한다.** `main()`에서 `code.upper()`를 하지 않아도 `library.borrow("b03", ...)`이 동작해야 한다. 도서관을 쓰는 쪽이 도서관의 내부 규칙을 알 필요가 없게 하는 것이다.
3. `main()`은 `library`의 `_`로 시작하는 속성을 쓰지 않는다. 공개된 메서드와 프로퍼티만 쓴다.
4. `ReferenceBook`은 `Book`을 상속하고 `can_borrow()`만 오버라이딩한다. `Library`의 메서드 안에서 `isinstance(book, ReferenceBook)`로 종류를 검사하지 말고 `book.can_borrow()`를 호출한다.
5. 대출 기간과 연체료는 메서드 안에서 `self.LOAN_DAYS`, `self.LATE_FEE_PER_DAY`로 읽는다.
6. `Book`은 주어진 대로 `frozen=True`로 둔다. `find()`는 도서관이 가진 `Book` 객체를 그대로 돌려주므로, `Book`을 바꿀 수 있으면 바깥 코드가 도서관 내부를 어긋나게 만들 수 있다("확인할 것"에서 직접 확인한다).

**힌트**

- 4장과 마찬가지로 **작은 것부터** 완성하고 확인한다. 순서는 `format_date()` → `Loan` → `ReferenceBook` → `Library`의 `__init__`, `find()` → `borrow()` → 나머지 메서드 → `main()`이 좋다. `format_date()`는 실습 4-7에서 쓴 것을 그대로 가져온다. 모든 것을 클래스로 만들 필요는 없다. 어떤 객체에도 속하지 않는 짧은 계산은 함수로 두어도 된다.
- 클래스를 하나 완성할 때마다 대화형 셸이나 파일 아래쪽에서 시험한다. 예를 들어 `Loan(Book("B01", "파이썬 첫걸음"), "철수", date(2026, 11, 14)).overdue_days(date(2026, 11, 17))`이 `3`인지 확인한다. 데이터 클래스는 `__repr__`이 있으므로 셸에서 결과를 바로 알아볼 수 있다.
- `ReferenceBook`에는 새 필드가 없으므로 `@dataclass`를 다시 붙이지 않아도 된다. `Book`에서 만들어진 `__init__`과 `__repr__`을 물려받고, 필드를 바꿀 수 없다는 성질도 물려받는다. `ReferenceBook("R01", "파이썬 사전")`을 셸에 입력해 `__repr__`이 어떤 클래스 이름을 보여 주는지 확인해 보자.
- `Library.__init__`에서는 받은 `books` 리스트를 그대로 저장하지 말고, 코드로 빨리 찾을 수 있도록 `{도서코드: Book}` 딕셔너리 `self._books`를 만든다(3.6의 "코드로 찾아야 하면 딕셔너리").
- `find()`는 딕셔너리의 `get()`(3.4.2)을 쓰면 한 줄로 쓸 수 있다. `borrow()`와 `return_book()`도 `find()`나 `code.upper()`로 코드를 맞춘 뒤 처리한다.
- `borrow()`는 실습 4-7처럼 조기 반환으로 실패하는 경우를 먼저 처리한다. 실패하는 경우가 하나(대출할 수 없는 도서) 늘었다. 메시지에 제목을 넣을 때는 `Book`의 `__str__`이 `'제목'` 모양을 돌려주므로 f-string에 `{book}`만 쓰면 된다.
- `days`의 기본값을 `days=LOAN_DAYS`가 아니라 `None`으로 둔 이유는 "더 해 보기"의 두 번째 항목에서 알게 된다. 4.2.4의 "기본값은 언제 만들어지는가"를 떠올려 보자.
- `loan_lines()`는 `self._loans.values()`, 즉 `Loan` 객체들을 정렬한다. 4장에서 `item[1]["due"]`처럼 쓰던 키가 `loan.due`, `loan.book.code`가 된다. 한 줄을 만드는 일은 `Loan.line()`에 맡긴다.
- `main()`은 실습 4-7의 `main()`을 옮겨 와 고친다. 모든 함수 호출이 `library.메서드(...)` 모양으로 바뀌고, 인자에서 `loans`가 사라진다. `목록`, `연체`, `도서` 명령은 "줄 목록을 출력하되 비어 있으면 안내 메시지를 출력"하는 일이 같으므로 작은 함수 `print_lines(lines, empty_message)`를 만들어 함께 쓰면 좋다.

**확인할 것**

- 실행 예와 똑같이 입력해 같은 결과가 나오는지 확인한다. (2026년 10월 31일에서 시작한 것처럼 확인하려면 `today = date.today()`를 잠시 `today = date(2026, 10, 31)`로 바꿔 시험한다.)
- 프로그램 맨 아래의 `main()`을 잠시 주석 처리하고, 대화형 셸에서 시험해 보자. VS Code에서 파일을 연 상태로 터미널에 `python -i library.py`를 입력하면 파일을 실행한 뒤 대화형 셸로 들어간다.
  ```python
  >>> lib = Library([Book("B01", "파이썬 첫걸음"), ReferenceBook("R01", "파이썬 사전")])
  >>> lib
  Library(도서 2권, 대출 0권)
  >>> lib.borrow("b01", "철수", date(2026, 10, 31))
  "'파이썬 첫걸음' 대출 완료 - 철수, 반납 기한 2026-11-14(토)"
  >>> lib.loan_count
  1
  >>> lib.find("r01")
  ReferenceBook(code='R01', title='파이썬 사전')
  >>> lib.loan_count = 0
  ```
  마지막 줄에서 어떤 오류가 나는가? 그 오류가 이 클래스를 어떻게 보호하는지 설명해 보자.
- 이어서 셸에서 `lib.find("b01").code = "B99"`를 실행하면 어떻게 되는가? 이번에는 `Book`의 `@dataclass(frozen=True)`를 잠시 `@dataclass`로 바꾸고, 새 `Library`를 만들어 같은 할당을 한 뒤 `B01`을 대출하고 반납해 보자. 대출은 되는데 반납이 실패하는 이유를 `_books`와 `_loans`의 키로 설명하고, 확인한 뒤 `frozen=True`를 되돌린다.
- 4장 버전과 5장 버전의 `main()`을 나란히 놓고 비교해 보자. 각 함수 호출에서 무엇이 사라졌는가? 대출 기록이 딕셔너리라는 사실을 `main()`이 알아야 하는가?
- 디버거로 `library.borrow(...)`를 호출하는 줄에서 `F11`을 눌러 들어간다. 변수 패널에서 `self`를 펼쳐 `_books`와 `_loans`를 확인하고, `Loan` 객체가 추가되는 순간을 확인한다. `Loan` 객체를 펼치면 그 안에 `Book` 객체가 들어 있는 것도 보인다.

**더 해 보기 (선택)**

- **신간 도서**: 대출 기간이 7일인 `NewBook`을 `Book`을 상속해 만든다. `Book`에 "이 도서의 대출 기간"을 알려 주는 메서드를 추가하고(`ReferenceBook`의 `can_borrow()`처럼), `NewBook`에서 오버라이딩한 뒤, `Library.borrow()`가 그 값을 쓰도록 고친다. `days` 인자로 기간을 직접 넘긴 경우에는 그 값이 우선해야 한다.
- **연체료가 다른 도서관**: 연체료가 하루 50원이고 대출 기간이 21일인 `CityLibrary`를 `Library`를 상속해 만든다. **클래스 속성 두 개만 오버라이딩하면** 나머지 메서드는 고칠 필요가 없다는 것을 확인하자. 만약 `borrow()`의 기본값이 `days=LOAN_DAYS`였다면 `CityLibrary`에서도 14일로 대출되었을 것이다. 왜 그런지 4.2.4와 5.2.1로 설명해 보자. (요구 사항 5에서 `Library.LOAN_DAYS`가 아니라 `self.LOAN_DAYS`로 읽게 한 이유도 여기 있다.)
- **대출 현황**: `대출현황 이름` 명령을 추가해 그 사람이 빌린 도서 목록을 보여 준다. `Library`에 메서드를 하나 추가하고, `main()`에는 명령 처리 몇 줄만 추가하면 된다.

## 정리

| 항목 | 핵심 |
|---|---|
| 클래스와 객체 | 클래스는 데이터와 기능의 설계도, 객체(인스턴스)는 그것으로 만든 값. 자료형 = 클래스. `int`, `str`, `list`, `date`도 클래스 |
| 객체 만들기 | `클래스이름(인자)`. 빈 객체를 만들고 `__init__(새 객체, 인자...)`를 호출한 뒤 객체를 돌려준다 |
| 이름 짓기 | 클래스는 `CamelCase`, 변수·함수·메서드·속성은 `snake_case`, 상수는 대문자 |
| 인스턴스 속성 | `__init__`에서 `self.이름 = 값`. 객체마다 따로. 속성은 객체에 붙은 이름표. `vars(객체)`로 확인 |
| 메서드 | 클래스 안의 `def`. 첫 매개변수는 `self`. 4장의 함수 규칙(인자, 기본값, `return`, 범위)이 그대로 적용 |
| `self` | 메서드를 호출한 그 객체. `a.deposit(1000)` = `Account.deposit(a, 1000)`. 정의에서 빠뜨리면 인자 개수 `TypeError` |
| `self.`의 의미 | 메서드 안에서 `self.x = ...`는 객체의 속성(남는다), `x = ...`는 지역 변수(사라진다). 할당하지 않는 이름은 지역 → 전역 → 내장 순으로 찾는다 |
| 클래스 속성 | 클래스 본문의 `이름 = 값`. 모든 객체가 함께 읽는다. 상수, 설정, 객체 수. 바꿀 때는 `클래스이름.속성 = ...` |
| 속성 찾기 순서 | 객체 → 클래스 → 부모 클래스 → ... → `object`. 할당은 언제나 점 앞의 대상에 한다 |
| 가변 클래스 속성 | `items = []`를 클래스 본문에 두면 모든 객체가 공유하는 버그. 객체마다 필요한 리스트는 `__init__`에서 |
| `__str__` | `print()`, `str()`, f-string용. 사용자에게 보여 줄 모습. 출력하지 말고 문자열을 돌려준다 |
| `__repr__` | 셸, 리스트 안의 요소, 디버거, `{x!r}`용. 만드는 코드 모양으로. 거의 항상 정의한다. `__str__`이 없으면 대신 쓰인다 |
| 캡슐화 | 데이터를 정해진 메서드로만 바꾸게 하는 것. 파이썬은 강제하지 않고 `_이름` 관례를 쓴다. 남의 `_` 이름은 쓰지 않는다 |
| `@property` | 메서드를 괄호 없이 속성처럼 읽는다. setter가 없으면 할당 시 `AttributeError`. 계산한 값, 읽기 전용 공개에 쓴다. 내부 리스트는 튜플로 돌려준다 |
| 데코레이터 | 함수·클래스 정의 위의 `@이름`. 아래 정의에 기능을 덧붙인다. 이 과정에서는 붙여 쓰기만 한다 |
| 상속 | `class 자식(부모):`. 부모의 속성과 메서드를 물려받고 필요한 것만 더하거나 바꾼다 |
| 오버라이딩 | 자식에 같은 이름의 메서드를 다시 정의. 부모의 것은 가려진다. `__str__`, `__repr__` 정의도 `object`의 것을 오버라이딩한 것 |
| `super()` | 부모의 메서드 호출. 자식의 `__init__`은 거의 항상 `super().__init__(...)`부터. 부모의 메서드를 부를 때 `self.`가 아니라 `super().` |
| `isinstance()` | "그 클래스의 한 종류인가". 자식 객체는 부모 클래스의 인스턴스이기도 하다. `bool`은 `int`의 자식 |
| 다형성 | 같은 메서드 이름, 객체마다 다른 동작. 종류를 `if`로 따지지 말고 메서드에 맡긴다 |
| 상속 vs 구성 | "자식은 부모의 한 종류다"(is-a)면 상속, "가지고 있다"(has-a)면 속성으로 가진다. 상속은 얕게 |
| 타입 힌트 | `name: str`, `def f(x: int) -> str:`, `list[str]`, `int \| None`. 사람과 도구를 위한 설명. 파이썬은 검사하지 않는다 |
| `@dataclass` | `이름: 자료형` 필드만 쓰면 `__init__`, `__repr__`, `__eq__`를 만들어 준다. 기본값 있는 필드는 뒤에 |
| 가변 기본값 | `field(default_factory=list)`. `[]`를 쓰면 `ValueError`로 막아 준다 |
| `frozen=True` | 필드 재할당을 막는다. 필드가 모두 해시 가능하면 집합의 요소, 딕셔너리의 키로 쓸 수 있다. 필드 안의 리스트까지 얼리지는 않는다 |
| 딕셔너리와 오가기 | `클래스(**딕셔너리)`로 만들고, `asdict(객체)`로 되돌린다. 키가 맞지 않으면 그 자리에서 `TypeError` |
| 무엇을 쓸까 | 키가 정해지지 않은 데이터는 딕셔너리, 모양이 정해진 데이터 묶음은 데이터 클래스, 규칙을 지켜야 하는 상태와 동작은 일반 클래스 |
