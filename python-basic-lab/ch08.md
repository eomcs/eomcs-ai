# 8장. 모듈/패키지

[파이썬 기초](README.md) 과정의 여덟 번째 장이다. 7장을 마친 `library.py`는 500줄이 넘는다. 도서와 대출을 나타내는 클래스, 예외 클래스, 도서관의 규칙을 담은 `Library`, 파일을 읽고 쓰는 함수, 명령을 처리하는 `main()`이 모두 한 파일에 들어 있다. 반납 규칙 하나를 고치려 해도 수백 줄 사이를 오르내려야 하고, `Book` 클래스만 다른 프로그램에서 쓰고 싶어도 파일 전체를 복사해야 한다. 이 장에서는 프로그램을 **여러 파일로 나누고, 나눈 파일을 서로 불러 쓰는** 방법을 배운다.

- **모듈 만들기** — 직접 만든 `.py` 파일을 `import`로 불러온다. 파이썬이 모듈을 어디서 찾는지(**모듈 검색 경로**), `import`할 때 무슨 일이 일어나는지 알아보고, 실행할 때와 불러올 때 다르게 동작하게 하는 `if __name__ == "__main__":`을 배운다.
- **표준 라이브러리 더 보기** — 운영체제와 이야기하는 `os`, 파이썬 실행 환경을 다루는 `sys`, 개수 세기와 그룹 짓기를 한 줄로 끝내는 `collections`의 `Counter`와 `defaultdict`, 그리고 타입 힌트를 더 풍부하게 쓰는 `typing`의 기초를 다룬다. 필요한 모듈을 공식 문서에서 찾는 습관도 이어서 기른다.
- **패키지 구조** — 모듈을 폴더로 묶은 **패키지**를 만든다. `__init__.py`의 역할, 패키지 안의 모듈끼리 불러 쓰는 방법, `python -m`으로 실행하는 방법을 배우고, 작은 프로젝트를 역할별 파일로 나누는 기준을 세운다.

AI 엔지니어가 만나는 코드는 거의 모두 여러 파일과 패키지로 되어 있다. LLM 라이브러리를 쓰는 코드의 첫머리에는 다음과 같은 줄이 흔하다.

```python
import os
import sys
from collections import Counter
from typing import Literal

from openai import OpenAI
from langchain_core.prompts import ChatPromptTemplate

from app.config import settings
from app.services.summarize import summarize
```

`from langchain_core.prompts import ...`는 `langchain_core`라는 **패키지** 안의 `prompts` 모듈에서 이름을 가져온다는 뜻이다. 마지막 두 줄의 `app`은 내 프로젝트 안의 패키지다. API 키는 코드에 적지 않고 `os.environ`으로 **환경 변수**에서 읽는다. 예제 코드의 맨 아래에는 거의 빠짐없이 `if __name__ == "__main__":`이 붙어 있다. 이 장을 마치면 이런 줄이 "어디에 있는 어떤 파일에서 무엇을 가져오는지" 읽을 수 있고, 내 프로그램도 같은 모양으로 정리할 수 있게 된다.

## 학습 목표

이 장을 마치면 다음을 할 수 있다.

- 함수와 상수를 담은 `.py` 파일을 만들어 다른 파일에서 `import`해 쓸 수 있다. 모듈이 객체이고, 모듈 안의 이름이 그 객체의 속성이라는 것을 설명할 수 있다.
- `import`가 모듈 파일을 **처음 한 번 실행**한다는 것을 알고, 모듈의 최상위에는 정의와 상수만 두어야 하는 이유를 설명할 수 있다. `__pycache__` 폴더가 무엇인지 안다.
- `__name__`의 값이 실행 방법에 따라 어떻게 달라지는지 설명하고, `if __name__ == "__main__":`으로 "직접 실행할 때만" 동작하는 코드를 쓸 수 있다.
- 모듈 검색 경로(`sys.path`)의 순서를 알고, `ModuleNotFoundError`와 표준 라이브러리 이름 가리기 문제의 원인을 찾을 수 있다. 파일 경로는 현재 디렉터리를, `import`는 스크립트 위치를 기준으로 한다는 차이를 설명할 수 있다.
- 밑줄로 시작하는 이름이 "모듈 밖에서 쓰지 말라"는 약속이라는 것을 알고, `from 모듈 import 이름`이 이름표를 복사한다는 점을 설명할 수 있다.
- 순환 import가 왜 생기는지 설명하고, 모듈 사이의 **의존 방향**을 한쪽으로 정해 피할 수 있다.
- `os`로 환경 변수를 읽고(`os.environ`, `os.getenv`), `os.path`로 쓴 코드를 `pathlib`과 대응시켜 읽을 수 있다.
- `sys.argv`로 명령행 인자를 받고, `sys.exit()`로 종료 코드를 정하고, 오류 메시지를 `sys.stderr`로 출력할 수 있다.
- `Counter`로 개수를 세고 `most_common()`으로 순위를 매기며, `defaultdict`로 그룹을 모을 수 있다. 3장의 딕셔너리 패턴과 어떻게 대응하는지 설명할 수 있다.
- `Optional`, `Union`, `Any`, `Literal`, `TypedDict` 같은 `typing`의 기본 표기와 `Callable`을 읽을 수 있고, 새 코드에서 어떤 표기를 쓸지 구분할 수 있다.
- 필요한 기능을 표준 라이브러리 문서에서 찾아 셸에서 확인할 수 있다.
- `__init__.py`가 있는 폴더로 패키지를 만들고, 절대 import와 상대 import로 하위 모듈을 불러올 수 있다. `__init__.py`에서 이름을 다시 내보낼 수 있다.
- `python -m`으로 모듈과 패키지를 실행하고, `__main__.py`를 만들 수 있다. 패키지 안의 파일을 직접 실행하면 import가 실패하는 이유를 설명할 수 있다.
- 한 파일짜리 프로그램을 역할별 모듈로 나누고, 모듈 사이의 의존 관계를 그림으로 그려 설명할 수 있다.

코드를 보여 주는 방식은 7장과 같다.

- 앞에 `>>>`가 붙어 있으면 대화형 셸에서 한 줄씩 입력하는 코드다. 절 안에서 이어지는 경우가 많으므로 한 절을 공부하는 동안에는 셸을 끄지 말자.
- 첫 줄이 `def`, `class`로 시작하고 `>>>`가 없는 블록은 셸에 붙여 넣는 코드다.
- 첫 줄에 `# textstats.py` 같은 파일 이름이 있거나 실습의 `# (가)` 같은 표시가 있으면 스크립트 파일 코드다. 이 장에서는 `# textkit/stats.py`처럼 **폴더 이름이 붙은** 파일 이름도 나온다. `ch08` 안에 `textkit` 폴더를 만들고 그 안에 `stats.py`를 만들라는 뜻이다.

이 장에서는 파일 여러 개가 서로를 불러 쓴다. 다음을 지키자.

1. **같은 장의 파일은 모두 `ch08` 폴더 안에 둔다.** 파이썬이 내가 만든 모듈을 찾는 곳이 정해져 있기 때문이다(8.1.6).
2. **스크립트는 터미널에서 `ch08` 폴더로 이동한 뒤 실행한다.** 대화형 셸도 `ch08` 폴더에서 연다. 다른 폴더에서 실행하면 어떻게 되는지는 이 장에서 일부러 실험해 본다.
3. **모듈 파일을 고쳤으면 대화형 셸을 다시 연다.** 셸은 한 번 불러온 모듈을 다시 읽지 않는다. 왜 그런지는 8.1.3에서 본다. 고쳤는데 결과가 그대로라면 셸을 `exit()`로 끝내고 다시 열자.

> **1단계를 마친 사람에게**
> AI에게 "프로젝트 구조를 잡아 줘"라고 하면 `app/`, `services/`, `models/`, `utils/` 같은 폴더와 그 안의 `__init__.py`를 잔뜩 만들어 준다. 그 코드를 VS Code의 ▷ 버튼으로 실행했더니 `ModuleNotFoundError: No module named 'app'`이나 `ImportError: attempted relative import with no known parent package`가 났고, AI가 시키는 대로 `sys.path.append(...)` 같은 줄을 넣어 겨우 돌아가게 만든 경험이 있을지도 모른다. 이 오류들은 **파이썬이 모듈을 어디서 찾는지**와 **프로그램을 어떻게 실행했는지**를 알면 원인이 바로 보인다. `sys.path.append(...)`는 대개 그 원인을 덮어 둘 뿐이다. 이 장을 마치면 AI가 만든 폴더 구조가 왜 그런 모양인지, 어떻게 실행해야 하는지 판단할 수 있을 것이다.

## 8.1 모듈 만들기

4.6에서 `math`, `random`, `datetime` 같은 표준 라이브러리 모듈을 가져다 썼다. 그때 **모듈을 "함수와 변수 등을 모아 둔 파이썬 파일"** 이라고 했다. 이 절에서는 그 파이썬 파일을 직접 만든다. 특별한 문법은 없다. 지금까지 만든 `.py` 파일이 모두 모듈이 될 수 있다.

### 8.1.1 왜 파일을 나누나

한 파일에 모든 코드를 넣어도 프로그램은 돌아간다. 그런데 프로그램이 커지면 다음과 같은 문제가 생긴다.

- **찾기 어렵다.** 7장의 `library.py`에서 연체료를 계산하는 코드를 찾으려면 클래스 열 개와 함수 여덟 개 사이를 훑어야 한다. 파일이 `models.py`, `errors.py`, `core.py`, `storage.py`, `cli.py`로 나뉘어 있다면 "도서관 규칙이니 `core.py`"라고 바로 찾아갈 수 있다.
- **다시 쓰기 어렵다.** 7장의 `format_date()`나 `Book` 클래스를 다른 프로그램에서도 쓰고 싶다면 지금은 복사해서 붙여 넣는 수밖에 없다. 복사한 코드는 한쪽을 고치면 다른 쪽과 달라진다. 모듈로 떼어 두면 두 프로그램이 같은 파일을 `import`해서 쓴다.
- **고친 것의 영향이 어디까지인지 알기 어렵다.** 한 파일 안에서는 어떤 함수든 다른 어떤 함수나 전역 변수든 쓸 수 있다. 파일을 나누고 "이 파일은 저 파일을 쓴다"를 `import` 줄로 드러내면, 어떤 코드가 어떤 코드에 기대고 있는지가 파일 맨 위에 적힌다.
- **여럿이 함께 고치기 어렵다.** 두 사람이 한 파일을 동시에 고치면 서로의 수정이 부딪힌다. 파일이 나뉘어 있으면 각자 다른 파일을 고칠 수 있다.

4장에서 "같은 코드를 여러 번 쓰지 말고 함수로 묶자", 5장에서 "관련된 데이터와 함수를 클래스로 묶자"고 했다. 모듈은 그다음 단계다. **관련된 함수와 클래스를 파일로 묶는다.** 묶는 기준은 7장에서 이미 연습했다. `Library`는 도서관의 규칙만, 모듈 수준의 함수는 파일 읽고 쓰기만, `main()`은 화면과 명령만 맡도록 나눴다. 이렇게 **하는 일(관심사)에 따라 나누는 것**을 관심사 분리라고 한다. 7장에서는 한 파일 안에서 나눴고, 이 장에서는 파일 단위로 나눈다.

### 8.1.2 첫 모듈 만들기

텍스트에서 단어를 나누고 세는 함수를 모듈로 만들어 보자. `ch08` 폴더에 `textstats.py`를 만든다.

```python
# textstats.py
"""텍스트에서 단어를 나누고 세는 함수 모음."""

PUNCTUATION = ".,!?\"'()"


def words(text: str) -> list[str]:
    """text를 단어의 리스트로 나눈다.

    단어 앞뒤의 문장 부호를 지우고, 영문자는 소문자로 바꾼다.
    """
    result = []
    for word in text.split():
        word = word.strip(PUNCTUATION).lower()
        if word:
            result.append(word)
    return result


def word_count(text: str) -> int:
    """text의 단어 수를 돌려준다."""
    return len(words(text))


def top_words(text: str, n: int = 3) -> list[tuple[str, int]]:
    """가장 많이 나온 단어 n개를 (단어, 횟수)의 리스트로 돌려준다."""
    counts = {}
    for word in words(text):
        counts[word] = counts.get(word, 0) + 1
    ranked = sorted(counts.items(), key=lambda item: item[1], reverse=True)
    return ranked[:n]
```

모두 앞 장들에서 배운 코드다. 2.3.5에서는 `strip()`을 인자 없이 써서 앞뒤 공백을 지웠다. 7.1.6의 `rstrip("\n")`처럼 인자로 문자열을 주면 그 문자열에 들어 있는 글자들을 앞뒤에서 지운다. 그래서 `strip(PUNCTUATION)`은 단어 앞뒤의 문장 부호를 모두 지운다. `counts.get(word, 0) + 1`은 3.4.5의 개수 세기 패턴이고, `sorted()`의 `key`는 4.5.5에서 배웠다. 파일 맨 위의 문자열은 **모듈 독스트링**이다. 함수의 독스트링(4.1.7)처럼 이 모듈이 무엇을 하는지 설명한다.

이 파일을 실행하면 아무 일도 일어나지 않는다. 함수를 정의하기만 하고 호출하지 않기 때문이다. 이제 같은 `ch08` 폴더에 이 모듈을 쓰는 `report.py`를 만든다.

```python
# report.py
import textstats

text = "Python is easy. Python is fun! 파이썬은 쉽고, 파이썬은 재미있다."
print("단어 수:", textstats.word_count(text))
print("많이 나온 단어:", textstats.top_words(text, 3))
print("지우는 문장 부호:", textstats.PUNCTUATION)
```

```
python report.py
```

```

많이 나온 단어: [('python', 2), ('is', 2), ('파이썬은', 2)]
지우는 문장 부호: .,!?"'()
```

`import textstats`는 4.6.2의 `import math`와 똑같은 문법이다. 다른 점은 `math`는 파이썬과 함께 설치된 모듈이고, `textstats`는 내가 만든 `textstats.py`라는 것뿐이다. 모듈 이름은 **파일 이름에서 `.py`를 뺀 것**이다. `import textstats.py`라고 쓰지 않는다.

4.6.2에서 "모듈도 객체"라고 했다. `ch08` 폴더에서 대화형 셸을 열어 확인해 보자.

```python
>>> import textstats
>>> textstats
<module 'textstats' from '/Users/본인계정/python-lab/ch08/textstats.py'>
>>> type(textstats)
<class 'module'>
>>> textstats.words("Hello, World!")
['hello', 'world']
>>> dir(textstats)
['PUNCTUATION', '__builtins__', '__cached__', '__doc__', '__file__', '__loader__', '__name__', '__package__', '__spec__', 'top_words', 'word_count', 'words']
>>> help(textstats)
```

`textstats`는 `textstats.py` 파일에서 만든 모듈 객체다. 파일 안에서 최상위에 만든 이름(`PUNCTUATION`, `words`, `word_count`, `top_words`)이 모두 이 객체의 **속성**이 되었다. 그래서 `textstats.words`처럼 점을 찍어 꺼낸다. 4.3.2에서 "파일 최상위에서 만든 이름"을 전역 변수라고 했는데, 정확히 말하면 전역 변수는 **그 모듈의 속성**이다. 파이썬에서 "전역"은 프로그램 전체가 아니라 **모듈 하나**의 범위다. `textstats.py`의 `PUNCTUATION`과 `report.py`에 같은 이름의 변수가 있어도 서로 부딪히지 않는다.

`dir()`의 결과에 섞여 있는 `__name__`, `__file__`, `__doc__` 같은 이름은 파이썬이 모듈을 만들 때 넣어 주는 속성이다. `__file__`은 7.2.4에서 쓴 바로 그 변수로, 모듈 파일의 경로가 들어 있다. `help(textstats)`를 실행하면 모듈 독스트링과 함수들의 독스트링이 정리되어 나온다(`q`를 눌러 빠져나온다). 독스트링을 잘 써 두면 모듈을 쓰는 사람이 파일을 열지 않고도 사용법을 알 수 있다.

`from ... import`와 `as`도 4.6에서 배운 그대로 쓸 수 있다.

```python
>>> from textstats import top_words
>>> top_words("a b a c b a")
[('a', 3), ('b', 2), ('c', 1)]
>>> import textstats as ts
>>> ts.word_count("one two three")
3
```

VS Code에서 `report.py`를 열고 `textstats.` 까지 입력해 보자. 점을 찍는 순간 `words`, `word_count`, `top_words`, `PUNCTUATION`이 자동 완성 목록에 나온다. 함수 이름 위에 마우스를 올리면 타입 힌트와 독스트링이 말풍선으로 보인다. `top_words` 위에서 `F12`(또는 `Ctrl`/`Cmd` + 클릭)를 누르면 `textstats.py`의 그 함수 정의로 바로 이동한다. 파일을 나눠도 길을 잃지 않게 도와주는 기능이니 익혀 두자.

**`from ... import`는 이름표를 복사한다**

3.2에서 변수는 객체에 붙인 이름표라고 배웠다. `from 모듈 import 이름`은 모듈 안의 객체에 **내 파일의 이름표를 하나 더 붙이는** 것이다. 그래서 나중에 모듈 쪽의 이름표가 다른 객체로 옮겨 가도, 내가 붙인 이름표는 원래 객체에 그대로 붙어 있다. `ch08`에 `config.py`를 만들어 확인해 보자.

```python
# config.py
LIMIT = 5
```

```python
>>> import config
>>> from config import LIMIT
>>> config.LIMIT = 10
>>> config.LIMIT
10
>>> LIMIT
5
```

`config.LIMIT = 10`은 `config` 모듈의 `LIMIT` 이름표를 `10`으로 옮겼다. 셸의 `LIMIT`은 가져올 때 붙인 이름표라서 여전히 `5`를 가리킨다. 실제 프로그램에서 다른 모듈의 변수를 바꾸는 일은 피해야 하지만, 혹시 그런 코드를 만나면 `import 모듈` 형태로 가져와 `모듈.이름`으로 써야 바뀐 값을 볼 수 있다는 것을 기억하자. 모듈 이름을 붙여 쓰는 것이 "이 값은 저 모듈의 것"이라는 사실을 드러내 주는 셈이다.

### 8.1.3 `import`는 모듈을 실행한다

`import textstats`를 하면 파이썬은 내부적으로 다음 일을 한다.

1. 이미 불러온 모듈인지 확인한다. 이미 불러왔다면 그 모듈 객체를 그대로 쓰고 끝낸다.
2. 처음이라면 `textstats.py` 파일을 찾는다(어디서 찾는지는 8.1.6).
3. 빈 모듈 객체를 만들고, **파일의 코드를 위에서부터 끝까지 실행**한다. 실행하면서 만든 이름(`def`로 만든 함수, `class`로 만든 클래스, 대입한 변수)이 모듈 객체의 속성이 된다.
4. 실행이 끝나면 내 파일에 `textstats`라는 이름표를 붙인다.

3번이 중요하다. `def`도 실행되는 문장이다. `def words(...):`를 실행하면 함수 객체가 만들어져 `words`라는 이름표가 붙는다(4.4.1). 그러니 모듈을 불러온다는 것은 결국 **그 파일을 한 번 실행하는 것**이다. 파일에 `print()`가 있다면 그것도 실행된다. 확인해 보자.

```python
# noisy.py
print("noisy 모듈의 코드가 실행됩니다")

GREETING = "안녕하세요"


def hello(name):
    return f"{GREETING}, {name}님"


print("noisy 모듈 준비 끝")
```

```python
# use_noisy.py
print("use_noisy 시작")
import noisy
import noisy
from noisy import hello

print(hello("철수"))
print("use_noisy 끝")
```

```
use_noisy 시작
noisy 모듈의 코드가 실행됩니다
noisy 모듈 준비 끝
안녕하세요, 철수님
use_noisy 끝
```

(`import`를 파일 중간에 쓰면 Ruff가 경고를 보여 줄 것이다. 4.6.5에서 말한 대로 `import`는 맨 위에 쓰는 것이 관례다. 여기서는 실행 순서를 보려고 일부러 중간에 썼다.)

세 가지를 확인할 수 있다.

- `import noisy`를 만나는 순간 `noisy.py`의 코드가 실행되었다. 두 `print()`의 출력이 `use_noisy 시작` 바로 다음에 나왔다.
- `import noisy`를 두 번 썼고 `from noisy import hello`까지 세 번 가져왔지만, `noisy.py`는 **한 번만** 실행되었다. 4.6.2에서 "처음 한 번만 실제로 불러온다"고 한 것이 이것이다. 파이썬은 불러온 모듈을 `sys.modules`라는 딕셔너리에 모아 두고, 다음부터는 거기서 꺼내 준다.
- `hello()`는 `noisy.py`의 `GREETING`을 썼다. 함수는 **자기가 정의된 모듈**의 전역 변수를 본다. `use_noisy.py`에는 `GREETING`이 없지만 문제없다.

**모듈의 최상위에는 정의만 둔다**

모듈을 불러오기만 했는데 화면에 무언가 출력되거나, `input()`이 입력을 기다리거나, 파일이 만들어진다면 그 모듈을 쓰는 사람은 당황한다. 그래서 모듈로 쓸 파일의 최상위에는 보통 다음만 둔다.

- 모듈 독스트링
- `import` 문
- 상수(값이 바뀌지 않는 변수, `PUNCTUATION`처럼 대문자 이름)
- 함수와 클래스의 정의

`print()`, `input()`, 파일 쓰기처럼 **무언가를 하는 코드**는 함수 안에 넣고, 쓰는 쪽에서 필요할 때 호출하게 한다. 7장의 `library.py`는 맨 아래에서 `main()`을 호출하므로 이 규칙을 지키지 않는다. 그래서 7장에서는 셸에서 시험하려면 `main()`을 주석 처리해야 했다. 8.1.5에서 이 문제를 해결한다.

**셸은 고친 모듈을 다시 읽지 않는다**

대화형 셸에서 `import textstats`를 한 뒤, VS Code에서 `textstats.py`를 고치고 저장했다고 하자. 셸에서 다시 `import textstats`를 해도 고친 내용이 반영되지 않는다. 이미 `sys.modules`에 있으므로 파일을 다시 읽지 않기 때문이다. 실습 준비에서 "모듈을 고쳤으면 셸을 다시 열라"고 한 이유다.

```python
>>> import sys
>>> "textstats" in sys.modules
True
```

셸을 끄지 않고 다시 읽으려면 `importlib.reload(textstats)`를 쓰는 방법도 있다. 하지만 `from textstats import top_words`로 가져온 이름표는 `reload()`해도 옛 함수를 가리킨다(바로 앞의 "이름표를 복사한다"를 떠올리자). 헷갈리기 쉬우므로 **셸을 다시 여는 것이 가장 확실하다.**

### 8.1.4 `__pycache__` 폴더

`report.py`를 실행한 뒤 VS Code 탐색기를 보면 `ch08` 안에 `__pycache__` 폴더가 생겼을 것이다. 안에는 `textstats.cpython-313.pyc` 같은 파일이 있다.

파이썬은 `.py` 파일을 실행하기 전에 컴퓨터가 처리하기 쉬운 중간 형태(**바이트코드**)로 바꾼다. 모듈을 `import`할 때는 이 결과를 `.pyc` 파일로 `__pycache__`에 저장해 두었다가, 다음에 같은 모듈을 불러올 때 `.py` 파일이 바뀌지 않았으면 다시 바꾸지 않고 `.pyc`를 바로 쓴다. 파일 이름의 `cpython-313`은 "CPython 3.13이 만든 것"이라는 뜻이다.

- `import`된 모듈만 `.pyc`가 생긴다. `python report.py`로 직접 실행한 `report.py`는 생기지 않는다.
- `.py` 파일을 고치면 파이썬이 알아채고 다시 만든다. 직접 관리할 필요가 없다.
- 지워도 된다. 다음에 실행할 때 다시 생긴다. 원본 `.py` 파일이 없어지면 `__pycache__`에 남은 그 모듈의 `.pyc`는 보통의 `import`에서 쓰이지 않는다. 그래서 4.6.6처럼 내 파일의 이름을 바꿨다면 옛 이름의 `.pyc`가 남아 있어도 문제가 되지 않는다.
- 이름을 바꿨는데도 같은 오류가 계속된다면 `__pycache__`보다 **아직 열려 있는 대화형 셸**을 먼저 의심하자. 셸은 이미 불러온 모듈을 `sys.modules`에 들고 있으므로(8.1.3), 파일 이름을 바꿔도 같은 셸에서는 옛 모듈을 계속 쓴다. 셸에서 `모듈.__file__`(예: `json.__file__`)을 출력하면 실제로 불러온 파일이 어디에 있는지 알 수 있다. 내 폴더의 파일 경로가 나온다면 셸을 다시 연다.
- 내 컴퓨터에서 만든 임시 파일이므로 다른 사람과 코드를 주고받을 때는 빼고 보낸다. git을 쓸 때 `.gitignore`에 `__pycache__/`를 넣는 것이 관례다.

### 8.1.5 `__name__`과 `if __name__ == "__main__":`

`textstats.py`의 함수가 제대로 동작하는지 시험하고 싶다. 파일 맨 아래에 시험 코드를 넣으면 될 것 같다.

```python
# textstats.py의 맨 아래에 더한다
sample = "The cat sat. The cat ran!"
print(words(sample))
print(top_words(sample, 2))
```

`python textstats.py`로 실행하면 시험 결과가 나온다. 그런데 이제 `python report.py`를 실행하면, `report.py`의 결과보다 먼저 이 시험 결과가 출력된다. `import textstats`가 `textstats.py`를 처음부터 끝까지 실행하기 때문이다(8.1.3). **직접 실행할 때만** 시험 코드가 돌고, 다른 파일이 불러올 때는 돌지 않게 할 방법이 필요하다.

파이썬은 모든 모듈에 `__name__`이라는 변수를 넣어 준다. 그 값이 무엇인지 확인해 보자. `ch08`에 두 파일을 만든다.

```python
# who_am_i.py
print(f"who_am_i.py의 __name__: {__name__}")
```

```python
# caller.py
import who_am_i

print(f"caller.py의 __name__: {__name__}")
```

**`who_am_i.py`를 직접 실행:**

```zsh
$ python who_am_i.py
who_am_i.py의 __name__: __main__
```

**`caller.py`를 실행:**

```zsh
$ python caller.py
who_am_i.py의 __name__: who_am_i
caller.py의 __name__: __main__
```

같은 `who_am_i.py`인데 `__name__`의 값이 다르다.

| 실행 방법 | `who_am_i.py`의 `__name__` |
|---|---|
| `python who_am_i.py`로 **직접 실행** | `"__main__"` |
| 다른 파일이 `import who_am_i`로 **불러옴** | `"who_am_i"` (모듈 이름) |

파이썬은 `python 파일.py`로 실행한 파일에는 `"__main__"`(주인공)이라는 이름을, `import`로 불러온 파일에는 모듈 이름을 넣어 준다. 그래서 다음 조건문은 **이 파일을 직접 실행했을 때만** 참이 된다.

```python
if __name__ == "__main__":
    ...
```

`textstats.py`의 시험 코드를 이 조건문 안으로 옮기자.

```python
# textstats.py의 맨 아래
if __name__ == "__main__":
    sample = "The cat sat. The cat ran!"
    print(words(sample))
    print(word_count(sample))
    print(top_words(sample, 2))
```

```
python textstats.py
```

```
['the', 'cat', 'sat', 'the', 'cat', 'ran']
6
[('the', 2), ('cat', 2)]
```

이제 `python report.py`를 실행하면 시험 코드는 실행되지 않고 `report.py`의 결과만 나온다. `report.py`가 `textstats`를 불러올 때 `textstats.py`의 `__name__`은 `"textstats"`이므로 조건이 거짓이기 때문이다.

이 모양은 두 가지로 쓰인다.

**1) 모듈에 사용 예나 간단한 시험을 붙인다.** 지금 본 것처럼 모듈을 직접 실행하면 동작을 확인할 수 있고, 불러다 쓸 때는 방해가 되지 않는다.

**2) 프로그램의 시작점을 감싼다.** 4장부터 `main()` 함수를 만들고 파일 맨 아래에서 `main()`을 호출해 왔다. 실무 코드에서는 이 호출을 다음처럼 감싼다.

```python
def main():
    ...


if __name__ == "__main__":
    main()
```

이렇게 해 두면 프로그램을 실행할 때는 전과 똑같이 `main()`이 실행되고, 다른 파일이나 셸에서 `import`할 때는 실행되지 않는다. 7장에서 셸로 `Library`를 시험하려고 `main()`을 주석 처리하던 번거로움이 사라진다. 그냥 `ch07` 폴더에서 셸을 열고 `import library`를 하면 된다. 이 장의 종합 실습부터는 모든 프로그램의 시작점을 이 모양으로 쓴다. 실습 4-7에서 "실무 코드에서는 맨 아래를 `if __name__ == "__main__":`으로 감싼다"고 미뤄 두었던 이야기가 이것이다.

> **`python -i`와 함께 쓸 때**
> `python -i textstats.py`로 실행하면 파일을 **직접 실행**한 것이므로 `__name__`은 `"__main__"`이고, 시험 코드가 실행된 뒤 셸로 들어간다. 시험 코드 없이 모듈의 함수만 셸에서 써 보고 싶다면 `python`으로 셸을 연 뒤 `import textstats`를 하면 된다.

`__name__`을 비롯해 앞뒤에 밑줄이 두 개씩 붙은 이름은 파이썬이 특별한 용도로 쓰는 이름이라고 7.2.4에서 말했다. 밑줄 두 개를 영어로 double underscore라고 하는데, 줄여서 **던더**(dunder)라고 부르기도 한다. `__name__`은 "던더 네임", `__init__`은 "던더 이닛"이라고 읽는다.

### 8.1.6 모듈 검색 경로 — 파이썬은 모듈을 어디서 찾나

`import textstats`라고 쓰면 파이썬은 `textstats.py`를 어디서 찾을까? 파이썬은 **모듈 검색 경로**라는 폴더 목록을 **앞에서부터 차례로** 뒤져서 처음 발견한 것을 쓴다. 이 목록은 `sys.path`라는 리스트에 들어 있다. `sys` 모듈은 8.2.2에서 자세히 배우고, 여기서는 이 리스트만 들여다보자.

```python
# path_demo.py
import sys

for p in sys.path:
    print(p)
```

```
python path_demo.py
```

```
/Users/본인계정/python-lab/ch08
/Library/Frameworks/Python.framework/Versions/3.13/lib/python313.zip
/Library/Frameworks/Python.framework/Versions/3.13/lib/python3.13
/Library/Frameworks/Python.framework/Versions/3.13/lib/python3.13/lib-dynload
/Library/Frameworks/Python.framework/Versions/3.13/lib/python3.13/site-packages
```

(경로는 운영체제와 파이썬을 설치한 방식에 따라 다르다. Windows라면 `C:\Users\본인계정\AppData\Local\Programs\Python\Python313\...` 같은 경로가 보인다.)

목록은 크게 세 부분으로 되어 있다.

1. **실행한 스크립트가 있는 폴더** — 맨 앞이다. 내가 만든 모듈을 찾는 곳이 여기다.
2. **표준 라이브러리 폴더** — `lib/python3.13` 같은 이름이다. `math`, `json`, `csv` 같은 모듈이 여기에 있다.
3. **`site-packages`** — 인터넷에서 내려받아 설치한 외부 패키지가 들어가는 곳이다. 9장에서 다룬다.

이 순서에서 두 가지를 알 수 있다.

**첫째, 4.6.6의 "내 파일 이름을 모듈 이름과 같게 짓지 않는다"의 이유가 이것이다.** 스크립트 폴더가 표준 라이브러리보다 **앞에** 있다. 그래서 `ch08`에 `json.py`가 있으면 `import json`은 표준 라이브러리의 `json`이 아니라 내 `json.py`를 찾아 쓴다. 검색은 처음 발견한 곳에서 멈추므로 진짜 `json`은 찾아보지도 않는다.

**둘째, 기준은 "현재 디렉터리"가 아니라 "스크립트가 있는 폴더"다.** `python-lab` 폴더로 이동한 뒤 `python ch08/report.py`로 실행해 보자.

```
cd ~/python-lab
python ch08/report.py
```

잘 실행된다. `sys.path`의 맨 앞에 들어가는 것은 현재 디렉터리(`python-lab`)가 아니라 `report.py`가 있는 폴더(`ch08`)이므로, 같은 폴더의 `textstats.py`를 찾을 수 있다. VS Code의 ▷ 버튼으로 실행해도 마찬가지다.

### 8.1.7 밑줄로 시작하는 이름 — 모듈 안에서만 쓰는 것

모듈을 만들다 보면 바깥에 보여 줄 함수와, 그 함수를 돕기 위해 모듈 안에서만 쓰는 함수가 생긴다. 5.2.5에서 클래스의 속성 이름 앞에 밑줄을 붙여(`_balance`) "클래스 밖에서 직접 쓰지 말라"는 약속을 표시했다. 모듈에서도 똑같이 한다.

```python
# textstats.py 안에서 쓰는 도우미 함수의 예
def _clean(word: str) -> str:
    """단어 앞뒤의 문장 부호를 지우고 소문자로 바꾼다. 모듈 안에서만 쓴다."""
    return word.strip(PUNCTUATION).lower()
```

밑줄로 시작하는 이름은 **"이 모듈의 내부 사정이니 바깥에서 기대지 말라"**는 뜻이다. 파이썬이 막지는 않는다. `textstats._clean("Hi!")`도 실행된다. 하지만 모듈을 만든 사람은 밑줄 붙은 이름을 언제든 바꾸거나 지울 수 있다고 여기므로, 바깥에서 쓰다가는 모듈이 고쳐질 때 내 코드가 깨진다. VS Code의 자동 완성도 밑줄 붙은 이름을 목록 뒤쪽에 보여 준다.

4.6.3에서 쓰지 말라고 한 `from 모듈 import *`는 밑줄로 시작하는 이름을 가져오지 않는다. 모듈 안에 `__all__`이라는 리스트를 만들어 두면 `*`로 가져갈 이름을 직접 정할 수도 있다.

```python
__all__ = ["words", "word_count", "top_words"]
```

`__all__`은 "이 모듈이 바깥에 공개하는 이름은 이것들"이라는 목록 역할도 한다. 8.3.2에서 패키지의 `__init__.py`에 쓰는 예를 다시 본다.

### 8.1.8 순환 import — 서로가 서로를 부를 때

파일을 나누다 보면 이런 일이 생긴다. 7장의 `library.py`를 나누면서 `Book` 클래스를 `models.py`에, 예외 클래스를 `errors.py`에 넣었다고 하자. `errors.py`의 예외 메시지에서 `Book`을 쓰므로 `errors.py`는 `models.py`를 불러야 한다. 그런데 누군가 `models.py`에서도 예외를 쓰고 싶어서 `errors.py`를 부르게 고쳤다. 간단한 모양으로 재현해 보자. 다른 파일과 섞이지 않게 `ch08` 안에 `circular` 폴더를 만들고 세 파일을 만든다.

```python
# circular/models.py
from errors import LibraryError


class Book:
    pass
```

```python
# circular/errors.py
from models import Book


class LibraryError(Exception):
    pass
```

```python
# circular/app.py
import models
```

```
cd circular
python app.py
```

```
Traceback (most recent call last):
  File "/Users/본인계정/python-lab/ch08/circular/app.py", line 1, in <module>
    import models
  File "/Users/본인계정/python-lab/ch08/circular/models.py", line 1, in <module>
    from errors import LibraryError
  File "/Users/본인계정/python-lab/ch08/circular/errors.py", line 1, in <module>
    from models import Book
ImportError: cannot import name 'Book' from 'models' (consider renaming '/Users/본인계정/python-lab/ch08/circular/models.py' if it has the same name as a library you intended to import)
```

트레이스백을 아래에서 위로 따라가면(4.1.9) 무슨 일이 일어났는지 보인다. 8.1.3에서 배운 `import`의 동작을 대입해 보자.

1. `app.py`가 `import models`를 한다. `models` 모듈 객체가 만들어지고 `models.py`가 **실행되기 시작한다.**
2. `models.py`의 첫 줄 `from errors import LibraryError`에서 `errors.py`가 실행되기 시작한다.
3. `errors.py`의 첫 줄 `from models import Book`에서, `models`는 이미 `sys.modules`에 있으므로 다시 실행하지 않고 그 모듈 객체에서 `Book`을 꺼내려 한다.
4. 그런데 `models.py`는 1번에서 첫 줄을 실행하던 중이었다. 아직 `class Book:`까지 가지 못했으므로 `models` 모듈에는 `Book`이 **없다.** 그래서 `ImportError`가 난다.

이렇게 두 모듈이 서로를 부르는 것을 **순환 import**(circular import)라고 한다. 파이썬 3.13의 메시지는 "이름이 같은 다른 라이브러리를 가져오려던 것이라면 파일 이름을 바꾸라(consider renaming)"는 안내를 붙이는데, 이 경우에는 **맞지 않는 안내**다. 파이썬 3.12에서는 `cannot import name 'Book' from partially initialized module 'models' (most likely due to a circular import)`, 즉 "**덜 만들어진** 모듈에서는 `Book`을 가져올 수 없다. **순환 import** 때문일 가능성이 크다"라고 더 정확하게 알려 준다. 패키지 안의 모듈(8.3)에서는 3.13도 이 정확한 메시지를 보여 준다. `cannot import name`이 나왔는데 이름에 오타가 없다면 순환 import를 의심하자.

**해결 방법: 의존 방향을 한쪽으로 정한다**

모듈 A가 모듈 B를 `import`하면 "A는 B에 **의존**한다"고 말한다. 순환 import는 의존이 원을 그리며 돌아올 때 생긴다. 해결책은 **누가 누구를 부를 수 있는지 방향을 정하는 것**이다.

```
errors ──→ models        errors가 models를 부른다 (O)
models ──→ errors        models가 errors를 부른다 (X, 원이 생긴다)
```

`Book`은 데이터를 나타내는 가장 기본적인 클래스이고, 예외는 그 데이터를 가지고 메시지를 만든다. 그러니 `models`가 더 아래(기본), `errors`가 그 위다. **아래 모듈은 위 모듈을 모른다**는 규칙을 세우면 순환은 생기지 않는다. `models.py`에서 예외가 꼭 필요하다면, 그 예외를 일으키는 코드가 사실은 `models`보다 위층의 일이 아닌지 생각해 보자. 이 장의 종합 실습에서 7장의 `library.py`를 다섯 모듈로 나눌 때 이 방향을 그림으로 정하고 시작한다.

- `memo.py` — 명령을 입력받아 처리하는 `main()`만 둔다. 파일 경로(`Path(__file__).parent / "memo.txt"`)는 이 파일이 정해서 `memo_store`의 함수에 넘긴다. 파일을 직접 열지 않는다.
- 나눈 뒤에도 7장과 똑같이 동작해야 한다.
- 다 했으면 `memo.py`의 `import` 줄을 보자. 이 파일은 무엇에 의존하는가? `memo_store.py`는 `memo.py`를 알아야 하는가? 메모를 파일 대신 다른 곳에 저장하게 바꾼다면 어느 파일만 고치면 되는가?

## 8.2 표준 라이브러리 더 보기

4.6에서 `math`, `random`, `datetime`을, 7장에서 `pathlib`, `csv`, `json`을 썼다. 표준 라이브러리에는 이런 모듈이 200개가 넘는다. 이 절에서는 이후 과정에서 특히 자주 만나는 네 가지, `os`, `sys`, `collections`, `typing`을 배운다. 그리고 4.6.10에서 시작한 "필요한 모듈을 공식 문서에서 찾는 습관"을 한 걸음 더 연습한다.

### 8.2.1 `os` — 운영체제와 이야기하기

`os`는 operating system(운영체제)의 약자다. 파일과 폴더, 환경 변수, 실행 중인 프로그램 같은 **운영체제의 기능**을 파이썬에서 쓸 수 있게 해 준다. macOS든 Windows든 같은 코드로 쓸 수 있게 차이를 감춰 주는 것이 이 모듈의 역할이다.

**파일과 폴더 — `pathlib`과 짝지어 읽기**

7장에서 파일과 폴더는 `pathlib.Path`로 다뤘다. `pathlib`이 생기기 전(파이썬 3.4 이전)에는 같은 일을 `os`와 `os.path`로 했고, 지금도 인터넷의 예제나 오래된 코드, AI가 만든 코드에서 자주 보인다. 새로 쓰는 코드는 `pathlib`으로 쓰되, `os.path` 코드를 만나면 읽을 수 있어야 한다. `ch08` 폴더에서 셸을 열어 확인해 보자.

```python
>>> import os
>>> os.getcwd()
'/Users/본인계정/python-lab/ch08'
>>> os.listdir(".")
['textstats.py', 'report.py', '__pycache__', 'noisy.py', ...]
>>> os.path.join("data", "2026", "report.csv")
'data/2026/report.csv'
>>> os.path.exists("textstats.py"), os.path.isfile("textstats.py"), os.path.isdir("__pycache__")
(True, True, True)
>>> os.path.basename("/Users/me/python-lab/ch08/report.py")
'report.py'
>>> os.path.dirname("/Users/me/python-lab/ch08/report.py")
'/Users/me/python-lab/ch08'
>>> os.path.splitext("report.tar.gz")
('report.tar', '.gz')
```

(`os.listdir()`의 순서는 운영체제마다 다르다. 7.2.3의 `iterdir()`처럼 순서가 정해져 있지 않다. Windows에서 `os.path.join()`의 결과는 `'data\\2026\\report.csv'`다.)

같은 일을 하는 코드를 짝지으면 다음과 같다.

| 하는 일 | `os` / `os.path` | `pathlib` (7장) |
|---|---|---|
| 현재 디렉터리 | `os.getcwd()` | `Path.cwd()` |
| 경로 잇기 | `os.path.join("data", "a.txt")` | `Path("data") / "a.txt"` |
| 있는지, 파일인지, 폴더인지 | `os.path.exists(p)`, `isfile(p)`, `isdir(p)` | `p.exists()`, `p.is_file()`, `p.is_dir()` |
| 파일 이름 / 상위 폴더 | `os.path.basename(p)` / `os.path.dirname(p)` | `p.name` / `p.parent` |
| 확장자 나누기 | `os.path.splitext(p)` | `p.stem`, `p.suffix` |
| 절대 경로 | `os.path.abspath(p)` | `p.absolute()`, `p.resolve()` |
| 폴더 안의 이름 | `os.listdir(p)` (문자열 리스트) | `p.iterdir()` (`Path`를 하나씩) |
| 폴더 만들기 | `os.makedirs(p, exist_ok=True)` | `p.mkdir(parents=True, exist_ok=True)` |
| 파일 크기 | `os.path.getsize(p)` | `p.stat().st_size` |
| 파일 지우기 / 이름 바꾸기 | `os.remove(p)` / `os.rename(a, b)` | `p.unlink()` / `p.rename(b)` |
| 스크립트 폴더 | `os.path.dirname(os.path.abspath(__file__))` | `Path(__file__).parent` |

가장 큰 차이는 `os.path`의 함수는 **문자열**을 받아 **문자열**을 돌려주고, `pathlib`은 `Path` **객체**로 다룬다는 것이다. 마지막 줄을 비교하면 왜 `pathlib`을 권하는지 알 수 있다. 7.1.4에서 파일 크기를 재려고 빌려 쓴 `os.path.getsize()`도 이 표에 있다.

**환경 변수 — 코드 밖에서 값을 받는 방법**

`os`에서 지금 꼭 알아야 할 것은 **환경 변수**(environment variable)다. 환경 변수는 운영체제가 실행하는 프로그램에게 넘겨주는 **이름=값** 쌍이다. 사용자의 홈 폴더가 어디인지, 실행 파일을 어느 폴더들에서 찾을지(`PATH`) 같은 정보가 환경 변수로 전달된다. 파이썬에서는 `os.environ`으로 읽는다.

```python
>>> os.environ["HOME"]
'/Users/본인계정'
>>> os.environ["PATH"]
'/Library/Frameworks/Python.framework/Versions/3.13/bin:/usr/local/bin:/usr/bin:/bin:...'
```

(Windows에서는 홈 폴더가 `HOME`이 아니라 `USERPROFILE`에 들어 있다. `os.environ["USERPROFILE"]`을 입력해 보자.)

`os.environ`은 딕셔너리처럼 쓰는 객체다. 키와 값은 모두 문자열이다. 없는 이름을 대괄호로 꺼내면 딕셔너리처럼 `KeyError`가 나고, `get()`이나 `os.getenv()`로 꺼내면 `None` 또는 지정한 기본값을 돌려준다(3.4.2의 `get()`과 같다).

```python
>>> os.environ["OPENAI_API_KEY"]
Traceback (most recent call last):
  ...
KeyError: 'OPENAI_API_KEY'
>>> print(os.environ.get("OPENAI_API_KEY"))
None
>>> os.getenv("OPENAI_API_KEY", "없음")
'없음'
```

환경 변수는 터미널에서 정한다. `ch08`에 다음 파일을 만든다.

```python
# env_demo.py
import os

user = os.getenv("LAB_USER")
if user is None:
    print("LAB_USER가 정해져 있지 않습니다.")
else:
    print(f"안녕하세요, {user}님")
```

터미널에서 환경 변수를 정한 뒤 실행해 보자.

```bash 
# macOS
$ python env_demo.py
$ export LAB_USER=철수
$ python env_demo.py

# Windows PowerShell
> python env_demo.py
> $env:LAB_USER = "철수"
> python env_demo.py
```

```
LAB_USER가 정해져 있지 않습니다.
안녕하세요, 철수님
```

코드는 그대로인데 **실행하는 환경에 따라** 결과가 달라졌다. 이렇게 정한 환경 변수는 **그 터미널 창에서만**, **그 창을 닫을 때까지만** 유효하다. 새 터미널을 열거나 VS Code의 ▷ 버튼이 새 터미널을 만들면 사라진다. macOS에서는 `LAB_USER=영희 python env_demo.py`처럼 명령 앞에 붙여 그 실행에만 쓸 수도 있다. 프로그램 안에서 `os.environ["LAB_USER"] = "민수"`처럼 바꾸는 것도 가능하지만, 바뀌는 것은 그 프로그램(과 그 프로그램이 실행하는 다른 프로그램)이 보는 값뿐이고 터미널의 값은 그대로다.

AI 엔지니어에게 환경 변수가 중요한 이유는 **API 키** 때문이다. LLM API를 쓰려면 비밀번호와 같은 API 키가 필요하다. 이것을 코드에 `api_key = "sk-..."`처럼 적으면 코드를 공유하거나 GitHub에 올리거나 AI에게 코드를 붙여 넣는 순간 키가 새어 나간다. 남이 내 키로 API를 쓰면 요금은 내가 낸다. 그래서 키는 **코드 밖**에 두고, 코드는 환경 변수에서 읽기만 한다.

```python
api_key = os.environ["OPENAI_API_KEY"]  # 없으면 KeyError로 바로 알 수 있다
```

실제로 많은 LLM 라이브러리는 키를 넘기지 않으면 알아서 정해진 이름의 환경 변수(`OPENAI_API_KEY`, `ANTHROPIC_API_KEY` 등)를 찾아 읽는다. 매번 터미널에서 `export`하기 번거로우므로 실무에서는 `.env`라는 파일에 `이름=값`을 적어 두고 시작할 때 환경 변수로 읽어 들이는 방법을 많이 쓰는데, 외부 패키지(9장)가 필요하므로 이후 과정에서 다룬다. 지금은 **비밀 값은 코드에 쓰지 않고 환경 변수에서 읽는다**는 원칙만 기억하자.

### 8.2.2 `sys` — 파이썬 실행 환경 다루기

`sys`는 system의 약자로, **지금 실행 중인 파이썬**에 관한 정보와 기능을 담고 있다. 8.1에서 `sys.path`(모듈 검색 경로)와 `sys.modules`(불러온 모듈)를 이미 만났다. 여기서는 명령행 인자, 종료 코드, 오류 출력을 배운다.

**`sys.argv` — 명령행 인자**

지금까지 프로그램에 값을 넘길 때는 `input()`으로 물었다. 하지만 터미널에서 쓰는 프로그램은 대개 실행할 때 값을 함께 준다. `cd ch08`의 `ch08`, `python report.py`의 `report.py`처럼 명령 뒤에 붙이는 값을 **명령행 인자**(command-line argument)라고 한다. 파이썬 스크립트에 붙인 인자는 `sys.argv`라는 리스트에 들어온다.

```python
# argv_demo.py
import sys

print(sys.argv)
print(len(sys.argv))
```

```bash
$ python argv_demo.py
$ python argv_demo.py hello.txt 3 "김 철수"
```

```
['argv_demo.py']
1
['argv_demo.py', 'hello.txt', '3', '김 철수']
4
```

- `sys.argv[0]`은 **실행한 스크립트의 경로**다. 실제 인자는 `sys.argv[1]`부터다.
- 인자는 공백으로 나뉜다. 공백이 들어간 값은 따옴표로 감싸면 하나로 들어온다.
- **모든 인자는 문자열**이다. `3`도 `'3'`으로 들어오므로 숫자로 쓰려면 `int()`로 바꿔야 한다. `input()`과 같다.
- 인자를 주지 않으면 리스트에 `sys.argv[0]`만 있다. 확인하지 않고 `sys.argv[1]`을 꺼내면 `IndexError`가 나므로 `len(sys.argv)`부터 검사한다.

인자를 받는 프로그램은 `input()`으로 묻는 프로그램보다 **자동화하기 쉽다.** 같은 일을 파일 100개에 하려면 `input()`에 100번 답해야 하지만, 인자를 받는 프로그램은 다른 프로그램이나 스크립트가 대신 실행해 줄 수 있다. 실습 8-2에서 파일 이름을 인자로 받는 단어 빈도 프로그램을 만든다. (`-n 5`, `--verbose` 같은 옵션까지 받는 본격적인 명령행 프로그램은 표준 라이브러리의 `argparse` 모듈로 만든다. 필요해지면 공식 문서를 찾아보자.)

**`sys.exit()` — 프로그램을 끝내고 종료 코드 남기기**

프로그램이 끝나면 운영체제에 **종료 코드**(exit code)라는 정수를 남긴다. `0`은 "성공", `0`이 아닌 값은 "무언가 실패"라는 약속이다. 지금까지 만든 프로그램은 정상적으로 끝나면 `0`, 처리하지 않은 예외로 트레이스백을 내고 끝나면 `1`을 남겼다. 터미널에서 방금 끝난 프로그램의 종료 코드를 확인할 수 있다.

```
# macOS
$ python argv_demo.py
$ echo $?

# Windows PowerShell
> python argv_demo.py
> $LASTEXITCODE
```

`0`이 나올 것이다. `sys.exit()`를 쓰면 원하는 곳에서 프로그램을 끝내고 종료 코드를 정할 수 있다.

```python
import sys

sys.exit()        # 종료 코드 0
sys.exit(1)       # 종료 코드 1
sys.exit("설정 파일이 없습니다")  # 메시지를 오류 출력에 쓰고 종료 코드 1
```

종료 코드는 사람보다는 **다른 프로그램**을 위한 것이다. 여러 프로그램을 차례로 실행하는 스크립트나, 코드를 올릴 때마다 시험을 돌리는 자동화 도구는 종료 코드를 보고 다음 단계로 갈지 멈출지 정한다. 오류 메시지는 출력했지만 종료 코드가 `0`인 프로그램은 자동화 도구가 보기에 "성공"이다. 그래서 실패로 끝날 때는 `0`이 아닌 코드를 남기는 것이 좋다. 흔히 `1`은 일반적인 실패, `2`는 사용법(인자)이 잘못된 경우에 쓴다.

6.1.5의 예외 계층도에서 `SystemExit`를 보았다. `sys.exit()`는 사실 `SystemExit` 예외를 일으킨다. 아무도 잡지 않으면 파이썬이 그 예외를 받아 프로그램을 조용히 끝낸다(트레이스백을 출력하지 않는다). `SystemExit`는 `Exception`의 자식이 아니므로 `except Exception:`에도 잡히지 않고, `finally`와 `with`의 정리 코드는 그대로 실행된다. 함수 안 깊은 곳에서 `sys.exit()`를 부르면 프로그램이 통째로 끝나므로, 보통은 `main()`처럼 **프로그램의 흐름을 책임지는 곳**에서만 쓴다. 6.2.6에서 "대처할 수 있는 곳에서 잡는다"고 한 것과 같은 생각이다. 아래쪽 함수는 예외를 일으키고, 프로그램을 끝낼지는 `main()`이 정한다.

**`sys.stderr` — 오류는 오류 출력으로**

`print()`는 **표준 출력**(standard output, stdout)에 쓴다. 프로그램에는 출력 통로가 하나 더 있는데, 오류 메시지를 위한 **표준 오류**(standard error, stderr)다. 둘 다 평소에는 화면에 나오므로 차이가 보이지 않는다. 7.1.2에서 `print()`에 `file=`을 주면 파일에 출력했는데, `file=sys.stderr`를 주면 표준 오류에 출력한다.

```python
print("결과입니다")                          # 표준 출력
print("파일이 없습니다", file=sys.stderr)     # 표준 오류
```

차이는 출력을 **파일로 돌릴 때** 드러난다. 터미널에서 명령 뒤에 `> 파일이름`을 붙이면 표준 출력이 화면 대신 그 파일에 저장된다(이것을 **리디렉션**이라고 한다). 이때 표준 오류는 여전히 화면에 나온다. 그래서 결과 파일에는 결과만 남고, 문제가 생기면 사람이 화면에서 바로 알 수 있다. 실습 8-2의 단어 빈도 프로그램에서 확인해 본다. 결과는 `print()`로, 오류 안내와 사용법은 `print(..., file=sys.stderr)`로 쓰는 습관을 들이자. 파이썬의 트레이스백도 표준 오류로 나온다.

**실행 환경 정보**

```python
>>> sys.version
'3.13.2 (main, ...) [Clang ...]'
>>> sys.version_info >= (3, 12)
True
>>> sys.platform
'darwin'
>>> sys.executable
'/Library/Frameworks/Python.framework/Versions/3.13/bin/python3'
```

- `sys.version_info`는 버전을 튜플처럼 비교할 수 있게 해 준다. "3.12 이상에서만 되는 기능"을 쓰기 전에 확인하는 데 쓴다.
- `sys.platform`은 운영체제를 알려 준다. macOS는 `'darwin'`, Windows는 `'win32'`, 리눅스는 `'linux'`다.
- `sys.executable`은 **지금 이 코드를 실행하고 있는 파이썬 프로그램의 경로**다. 컴퓨터에 파이썬이 여러 개 설치되어 있을 때 "설치했는데 import가 안 되는" 문제의 원인을 찾는 열쇠가 된다. 9장에서 중요하게 쓴다.

### 8.2.3 `collections.Counter` — 개수 세기

`collections` 모듈에는 딕셔너리, 리스트, 튜플을 특정한 일에 맞게 다듬은 자료형이 들어 있다. 그중 가장 많이 쓰는 두 가지를 배운다.

3.4.5의 패턴 1에서 메뉴 투표를 셀 때 이렇게 썼다.

```python
counts = {}
for menu in votes:
    counts[menu] = counts.get(menu, 0) + 1
```

그때 "개수 세기는 너무 자주 쓰여서 이 일만 하는 도구가 따로 있다"고 했다. 그것이 `Counter`다.

```python
>>> from collections import Counter
>>> votes = ["짜장", "짬뽕", "짜장", "볶음밥", "짜장", "짬뽕"]
>>> c = Counter(votes)
>>> c
Counter({'짜장': 3, '짬뽕': 2, '볶음밥': 1})
```

리스트를 넘기기만 하면 요소마다 몇 번 나왔는지 세어 준다. 문자열을 넘기면 글자를 센다.

```python
>>> Counter("banana")
Counter({'a': 3, 'n': 2, 'b': 1})
```

`Counter`는 딕셔너리의 자식 클래스다. 그래서 딕셔너리처럼 쓰면서, 개수 세기에 편한 기능이 더 있다.

```python
>>> c["짜장"]
3
>>> c["탕수육"]
0
>>> "탕수육" in c
False
>>> c.most_common(2)
[('짜장', 3), ('짬뽕', 2)]
```

- **없는 키를 꺼내면 `KeyError` 대신 `0`** 을 돌려준다. 그래서 `c[menu] += 1`을 처음 나온 키에도 그냥 쓸 수 있다. 꺼내기만 해서는 키가 추가되지 않는다(`in`으로 확인하면 여전히 `False`다).
- `most_common(n)`은 **많이 나온 순서로 n개**를 `(요소, 개수)` 튜플의 리스트로 돌려준다. `n`을 생략하면 전부다. 개수가 같으면 **먼저 센 것이 앞**에 온다.

개수를 더하는 방법도 여러 가지다.

```python
>>> c["탕수육"] += 1
>>> c.update(["짬뽕", "짬뽕"])
>>> c
Counter({'짬뽕': 4, '짜장': 3, '볶음밥': 1, '탕수육': 1})
>>> c.total()
9
>>> dict(c)
{'짜장': 3, '짬뽕': 4, '볶음밥': 1, '탕수육': 1}
```

`update()`는 리스트를 받아 이어서 센다. `total()`은 개수의 합계다(3.10에 추가되었다). `Counter`끼리 `+`, `-`도 할 수 있는데, `-`는 결과가 0 이하인 것을 빼 버린다.

```python
>>> Counter(a=3, b=1) + Counter(a=1, b=2)
Counter({'a': 4, 'b': 3})
>>> Counter(a=3, b=1) - Counter(a=1, b=2)
Counter({'a': 2})
```

이제 8.1.2의 `textstats.top_words()`를 `Counter`로 바꿔 보자. 일곱 줄이 한 줄이 된다.

```python
# textstats.py
from collections import Counter

...


def top_words(text: str, n: int = 3) -> list[tuple[str, int]]:
    """가장 많이 나온 단어 n개를 (단어, 횟수)의 리스트로 돌려준다."""
    return Counter(words(text)).most_common(n)
```

`python report.py`를 다시 실행해 결과가 같은지 확인하자. `top_words()`를 쓰는 `report.py`는 한 글자도 고치지 않았다. 모듈 안의 구현을 바꿔도 함수의 이름, 매개변수, 돌려주는 값이 같으면 쓰는 쪽은 영향을 받지 않는다. 모듈로 나누는 이점이 이것이다.

`Counter`는 AI 엔지니어의 일에서도 자주 쓴다. 문서에서 많이 나오는 단어를 세거나, 평가용 데이터에 정답 종류(예: `"긍정"`, `"부정"`)가 몇 개씩 있는지 세어 한쪽으로 치우치지 않았는지 확인하거나, LLM이 내놓은 답의 종류별 개수를 셀 때 쓴다. `Counter`는 딕셔너리이므로 `json.dumps()`로 그대로 JSON으로 바꿀 수 있다.

### 8.2.4 `collections.defaultdict` — 기본값이 있는 딕셔너리

3.4.5의 패턴 2(그룹으로 모으기)는 이랬다.

```python
groups = {}
for name, class_name in students:
    if class_name not in groups:
        groups[class_name] = []
    groups[class_name].append(name)
```

"처음 나온 키라면 빈 리스트를 먼저 넣는다"는 두 줄이 매번 필요하다. `defaultdict`는 **없는 키를 꺼내는 순간 기본값을 만들어 넣어 주는** 딕셔너리다.

```python
>>> from collections import defaultdict
>>> students = [("철수", "1반"), ("영희", "2반"), ("민수", "1반"), ("지수", "2반"), ("현우", "3반")]
>>> groups = defaultdict(list)
>>> for name, class_name in students:
...     groups[class_name].append(name)
...
>>> groups
defaultdict(<class 'list'>, {'1반': ['철수', '민수'], '2반': ['영희', '지수'], '3반': ['현우']})
>>> groups["1반"]
['철수', '민수']
```

`defaultdict(list)`의 `list`는 **기본값을 만들 함수**다. 괄호를 붙이지 않았다는 데 주의하자. 4.4에서 배운 대로 함수(여기서는 클래스)를 값으로 넘긴 것이다. 없는 키를 꺼내면 `defaultdict`가 `list()`를 호출해 빈 리스트를 만들고, 그 키에 넣은 뒤 돌려준다. 그래서 `groups[class_name].append(name)`이 처음 나온 반에서도 동작한다. 실수로 `defaultdict([])`처럼 리스트를 넘기면 `TypeError: first argument must be callable or None`(첫 번째 인자는 호출할 수 있는 것이어야 한다)이 난다.

기본값을 만드는 함수는 무엇이든 된다.

```python
>>> int(), list(), str(), set()
(0, [], '', set())
>>> counts = defaultdict(int)
>>> for ch in "banana":
...     counts[ch] += 1
...
>>> counts
defaultdict(<class 'int'>, {'b': 1, 'a': 3, 'n': 2})
```

`defaultdict(int)`로도 개수를 셀 수 있다. 하지만 개수 세기에는 `most_common()`이 있는 `Counter`가 더 알맞다.

**주의: 꺼내기만 해도 키가 생긴다**

`Counter`는 없는 키를 꺼내면 `0`을 돌려주기만 하고 키를 추가하지 않았다. `defaultdict`는 다르다. **꺼내는 것만으로 키가 추가된다.**

```python
>>> groups["4반"]
[]
>>> groups
defaultdict(<class 'list'>, {'1반': ['철수', '민수'], '2반': ['영희', '지수'], '3반': ['현우'], '4반': []})
```

"4반에 누가 있나 보기만" 했는데 빈 4반이 생겼다. 키가 있는지 확인만 하려면 `in`을, 값을 보기만 하려면 `get()`을 쓴다. 둘은 기본값을 만들지 않는다.

```python
>>> "5반" in groups
False
>>> print(groups.get("5반"))
None
```

`defaultdict`는 모으는 동안에 쓰고, 다 모은 뒤 다른 곳에 넘길 때는 `dict(groups)`로 보통 딕셔너리로 바꿔 주면 이런 사고를 막을 수 있다. `defaultdict`도 딕셔너리의 자식 클래스이므로 `json.dumps()`는 그대로 된다.

3장의 딕셔너리 패턴과 `collections`를 짝지으면 다음과 같다.

| 3.4.5의 패턴 | 직접 쓰면 | `collections`로 쓰면 |
|---|---|---|
| 패턴 1. 개수 세기 | `counts[k] = counts.get(k, 0) + 1` | `Counter(items)`, `c[k] += 1`, `most_common()` |
| 패턴 2. 그룹으로 모으기 | `if k not in g: g[k] = []` 다음에 `g[k].append(v)` | `g = defaultdict(list)` 다음에 `g[k].append(v)` |

`collections`는 원리를 바꾸지 않는다. 3장에서 직접 쓴 패턴을 짧고 실수 없이 쓰게 해 줄 뿐이다. 그래서 원리를 먼저 배웠다. 다른 사람의 코드에서 둘 중 어느 모양을 만나도 같은 일을 한다는 것을 알아볼 수 있어야 한다.

### 8.2.5 `typing` 기초 — 타입 힌트 더 읽기

5.4.2에서 타입 힌트의 기본 모양(`name: str`, `list[str]`, `dict[str, int]`, `int | None`, `-> None`)을 배웠고, "타입 힌트를 더 다양하게 쓰는 방법(`typing` 모듈)은 8장에서 조금 더 다룬다"고 했다. 이 절의 목표는 **라이브러리의 코드와 문서에 나오는 타입 힌트를 읽는 것**이다. LLM 라이브러리의 문서는 함수마다 타입 힌트로 무엇을 넘기고 무엇을 돌려받는지 알려 준다.

**옛날 표기 읽기 — `List`, `Dict`, `Optional`, `Union`, `Callable`**

파이썬 3.9 전에는 `list[str]`이라고 쓸 수 없었고, 3.10 전에는 `int | None`이라고 쓸 수 없었다. 그때는 `typing` 모듈의 이름을 가져와 썼다. 오래된 코드와 문서에서 지금도 자주 보이므로 읽을 수 있어야 한다.

| 옛날 표기 (`from typing import ...`) | 지금 표기 | 뜻 |
|---|---|---|
| `List[str]` | `list[str]` | 문자열의 리스트 |
| `Dict[str, int]` | `dict[str, int]` | 키는 문자열, 값은 정수인 딕셔너리 |
| `Tuple[int, int]` | `tuple[int, int]` | 정수 두 개짜리 튜플 |
| `Optional[int]` | `int \| None` | 정수 또는 `None` |
| `Union[int, str]` | `int \| str` | 정수 또는 문자열 |
| `Callable[[int], int]` | `Callable[[int], int]` (`from collections.abc import Callable`) | 정수를 받아 정수를 돌려주는 함수 |

`Optional[int]`는 이름 때문에 "생략할 수 있는 인자"로 오해하기 쉬운데, 뜻은 그냥 **"`int`이거나 `None`"** 이다. 두 표기는 완전히 같다.

```python
>>> from typing import Optional, Union
>>> Optional[int] == (int | None)
True
```

새로 쓰는 코드는 이 교재의 기준인 3.12 이상에서 되는 **지금 표기**로 쓰자.

**지금도 `typing`에서 가져오는 것**

다음은 지금 표기로 대신할 수 없어서 여전히 `typing`에서 가져와 쓴다.

```python
from typing import Any, Literal, TypedDict
```

- **`Any`** — 아무 자료형이나 된다는 뜻이다. `dict[str, Any]`는 "키는 문자열이고 값은 무엇이든 되는 딕셔너리"로, JSON에서 읽은 데이터처럼 값의 자료형이 섞여 있을 때 자주 쓴다. 타입 힌트가 아무것도 알려 주지 않는 것과 같으므로 꼭 필요할 때만 쓴다.
- **`Literal`** — **정해진 값 중 하나**라는 뜻이다. `Literal["system", "user", "assistant"]`는 "문자열인데 이 셋 중 하나"다. 그냥 `str`보다 훨씬 많은 것을 알려 준다.
- **`TypedDict`** — **키가 정해진 딕셔너리**의 모양을 적는다. 5장의 데이터 클래스처럼 쓰지만, 만들어지는 것은 보통 딕셔너리다.

**함수를 나타내는 `Callable`**

함수를 받는다는 뜻의 타입 힌트는 `Callable`이다. `Callable[[int], int]`는 "정수 하나를 받아 정수를 돌려주는 함수"다. 대괄호 안의 첫 번째 리스트가 매개변수의 자료형들, 두 번째가 돌려주는 값의 자료형이다. 4.4.3에서 함수를 인자로 넘기는 방법을 배웠다.

```python
from collections.abc import Callable


def apply(func: Callable[[int], int], x: int) -> int:
    return func(x)
```

새 코드에서는 이처럼 `collections.abc`에서 가져온다. `from typing import Callable`도 같은 뜻으로 동작하지만, 앞의 `List`, `Optional`처럼 지금은 **기존 코드를 읽기 위한 표기**다. 오래된 코드와 라이브러리 문서에서 자주 보이므로 둘 다 알아 두자.

`Literal`과 `TypedDict`는 LLM API에서 바로 만난다. LLM에게 보내는 대화는 보통 `{"role": "user", "content": "안녕"}` 같은 딕셔너리의 리스트다. 이 모양을 타입 힌트로 적으면 다음과 같다.

```python
from typing import Literal, TypedDict

Role = Literal["system", "user", "assistant"]


class Message(TypedDict):
    role: Role
    content: str


messages: list[Message] = [
    {"role": "system", "content": "너는 친절한 도우미야."},
    {"role": "user", "content": "모듈이 뭐야?"},
]
```

`Role = Literal[...]`처럼 긴 타입 힌트에 이름을 붙여 두고 다시 쓸 수 있다. 이것을 **타입 별칭**(type alias)이라고 한다. `class Message(TypedDict):`는 "`role`과 `content`라는 키를 가진 딕셔너리"라는 설명이다. 라이브러리 문서에서 `messages: list[Message]`라는 매개변수를 보면 "이런 딕셔너리의 리스트를 넘기라는 것"이라고 읽으면 된다.

**여전히 검사하지 않는다**

5.4.2에서 강조한 것을 다시 확인하자. 파이썬은 `typing`으로 쓴 타입 힌트도 실행할 때 검사하지 않는다.

```python
>>> bad: Message = {"role": "admin", "content": 1}
>>> bad
{'role': 'admin', 'content': 1}
>>> type(bad)
<class 'dict'>
```

`"admin"`은 정해진 역할이 아니고 `content`는 문자열이 아니지만 오류 없이 만들어진다. 만들어진 것은 그냥 딕셔너리다. 타입 힌트를 검사해 주는 것은 **도구**다. VS Code의 Python 확장(Pylance)은 기본 설정에서는 이런 실수를 거의 알려 주지 않는데, `settings.json`에 다음 한 줄을 더하면 잘못된 값에 빨간 물결 밑줄을 그어 준다.

```json
"python.analysis.typeCheckingMode": "basic"
```

켜 두면 지금까지 작성한 코드에도 밑줄이 몇 개 생길 수 있다. 밑줄에 마우스를 올려 설명을 읽어 보고, 너무 많아서 공부에 방해가 되면 꺼도 된다. 지금 단계에서는 **읽을 수 있는 것**이 목표다.

**어디에 쓸까**

타입 힌트를 모든 변수에 붙일 필요는 없다. `count = 0`에 `: int`를 붙여도 얻는 것이 거의 없다. 다음 세 곳부터 습관을 들이자.

- **함수의 매개변수와 반환값** — 함수를 쓰는 사람이 가장 먼저 보는 곳이다. 특히 모듈로 나눠 다른 파일에서 쓰는 함수는 타입 힌트가 사용 설명서 역할을 한다.
- **데이터 클래스와 `TypedDict`의 필드** — 데이터의 모양을 정하는 곳이다.
- **빈 컬렉션** — `groups: dict[str, list[str]] = {}`처럼, 처음에 비어 있어서 무엇을 담을지 코드만 보고 알 수 없을 때.

### 8.2.6 필요한 모듈을 공식 문서에서 찾는 습관

4.6.10에서 모듈 **안의** 함수를 공식 문서에서 찾는 방법을 배웠다. 이번에는 한 단계 앞, **어떤 모듈을 써야 할지** 모를 때 찾는 방법이다.

표준 라이브러리 문서의 첫 페이지([https://docs.python.org/ko/3/library/](https://docs.python.org/ko/3/library/))는 모듈을 **하는 일에 따라** 장으로 묶어 두었다. "텍스트 처리 서비스", "데이터형", "숫자와 수학 모듈", "파일과 디렉터리 액세스", "데이터 지속성", "파일 형식", "일반 운영 체제 서비스" 같은 식이다. 모듈 이름을 알고 있다면 알파벳순 목록인 **파이썬 모듈 색인**([https://docs.python.org/ko/3/py-modindex.html](https://docs.python.org/ko/3/py-modindex.html))이 빠르다.

**찾는 순서 연습**: "파일 하나를 다른 이름으로 복사하고 싶다"고 하자.

1. **하고 싶은 일을 말로 적는다.** "파일을 복사한다."
2. **어느 장에 있을지 짐작한다.** 파일에 관한 일이니 "파일과 디렉터리 액세스" 장을 연다. `pathlib`, `os.path`, `glob`, `shutil` 등이 있다.
3. **설명을 훑는다.** 7장에서 쓴 `pathlib` 문서를 먼저 찾아본다. 그런데 문서를 내 버전(3.13)으로 맞춰 보면 `Path`에 복사하는 메서드가 없다. 버전을 3.14로 바꿔 보면 `Path.copy()`가 있고 "버전 3.14에 추가"라고 적혀 있다. 내 파이썬에서는 쓸 수 없다. 다음으로 `shutil`의 설명을 보니 파일과 폴더를 복사하고 지우는 고수준 연산을 제공한다고 되어 있다.
4. **함수 정의를 읽는다.** `shutil.copy(src, dst)`가 있다. `src` 파일을 `dst`로 복사한다.
5. **셸에서 확인한다.** `import shutil` 다음에 `shutil.copy("textstats.py", "textstats_backup.py")`를 실행하고 VS Code 탐색기에서 파일이 생겼는지 본다.

이 과정에서 **3번의 버전 확인**을 꼭 기억하자. 인터넷이나 AI가 알려 준 코드가 내 파이썬에서 `AttributeError`를 낸다면, 그 기능이 내 버전보다 나중에 추가된 것일 수 있다.

이름 정도는 알아 두면 좋은 표준 라이브러리 모듈을 모아 보았다. 지금 다 익힐 필요는 없다. "이런 일은 표준 라이브러리에 이미 있다"는 것을 기억해 두었다가, 필요할 때 문서를 찾자.

## 8.3 패키지 구조

모듈이 서너 개일 때는 한 폴더에 나란히 두어도 괜찮다. 하지만 모듈이 늘어나면 `ch08` 폴더처럼 서로 관계없는 파일이 뒤섞인다. 이름이 부딪힐 걱정도 생긴다. 이 장에서 만든 `textstats.py`와 종합 실습의 `models.py`가 한 폴더에 있으면, 어느 것이 어느 프로그램의 것인지 파일 이름만으로는 알 수 없다. 이 절에서는 관련된 모듈을 **폴더로 묶는** 방법을 배운다.

### 8.3.1 패키지 — 모듈을 담은 폴더

**패키지**(package)는 모듈을 담은 폴더다. 폴더 안에 `__init__.py`라는 파일을 두면 파이썬은 그 폴더를 패키지로 다룬다. 8.1의 `textstats.py`를 패키지로 바꿔 보자. `ch08` 안에 `textkit` 폴더를 만들고 다음 세 파일을 만든다.

```
ch08/
├── use_textkit.py
└── textkit/
    ├── __init__.py
    ├── cleaning.py
    └── stats.py
```

`__init__.py`는 일단 **빈 파일**로 만든다. VS Code 탐색기에서 `textkit` 폴더를 선택하고 새 파일 아이콘을 눌러 `__init__.py`를 입력한 뒤, 아무것도 쓰지 않고 저장하면 된다.

```python
# textkit/cleaning.py
"""텍스트를 단어로 나누기 전에 다듬는 함수."""

PUNCTUATION = ".,!?\"'()"


def words(text: str) -> list[str]:
    """text를 단어의 리스트로 나눈다. 문장 부호를 지우고 영문자는 소문자로 바꾼다."""
    result = []
    for word in text.split():
        word = word.strip(PUNCTUATION).lower()
        if word:
            result.append(word)
    return result
```

```python
# textkit/stats.py
"""단어를 세는 함수."""

from collections import Counter

from textkit.cleaning import words


def word_count(text: str) -> int:
    """text의 단어 수를 돌려준다."""
    return len(words(text))


def top_words(text: str, n: int = 3) -> list[tuple[str, int]]:
    """가장 많이 나온 단어 n개를 (단어, 횟수)의 리스트로 돌려준다."""
    return Counter(words(text)).most_common(n)


if __name__ == "__main__":
    print(top_words("the cat and the hat"))
```

`stats.py`는 같은 패키지의 `cleaning.py`에서 `words`를 가져온다. `from textkit.cleaning import words`는 "`textkit` 패키지 안의 `cleaning` 모듈에서 `words`를 가져온다"는 뜻이다. 점(`.`)이 폴더 구분을 나타낸다. `textkit.cleaning`은 `textkit/cleaning.py` 파일이다.

이제 `ch08` 폴더(패키지 폴더의 **바깥**)에 패키지를 쓰는 파일을 만든다.

```python
# use_textkit.py
import textkit.stats
from textkit import cleaning
from textkit.stats import top_words

text = "Python is easy. Python is fun!"
print(cleaning.words(text))
print(textkit.stats.word_count(text))
print(top_words(text, 2))
```

```bash
$ python use_textkit.py
['python', 'is', 'easy', 'python', 'is', 'fun']
6
[('python', 2), ('is', 2)]
```

패키지 안의 모듈을 가져오는 세 가지 모양을 모두 썼다.

| 가져오는 모양 | 쓰는 모양 | 언제 |
|---|---|---|
| `import textkit.stats` | `textkit.stats.word_count(...)` | 어디서 온 것인지 전체 경로를 드러내고 싶을 때. 길다 |
| `from textkit import cleaning` | `cleaning.words(...)` | 모듈 이름만 붙여 쓰고 싶을 때 |
| `from textkit.stats import top_words` | `top_words(...)` | 자주 쓰는 함수나 클래스를 바로 쓰고 싶을 때 |

`import 패키지.모듈` 형태에서 `import` 뒤에는 **패키지나 모듈만** 올 수 있다. `import textkit.stats.top_words`처럼 함수까지 쓸 수는 없다. 함수나 클래스를 가져오려면 `from ... import`를 쓴다.

**패키지도 모듈 객체다**

```python
>>> import textkit
>>> textkit
<module 'textkit' from '/Users/본인계정/python-lab/ch08/textkit/__init__.py'>
>>> textkit.stats
Traceback (most recent call last):
  File "<python-input-2>", line 1, in <module>
    textkit.stats
AttributeError: module 'textkit' has no attribute 'stats'
>>> import textkit.stats
>>> textkit.stats
<module 'textkit.stats' from '/Users/본인계정/python-lab/ch08/textkit/stats.py'>
```

`import textkit`을 하면 패키지의 `__init__.py`가 실행되어 `textkit`이라는 모듈 객체가 만들어진다. 그런데 이것만으로는 **안에 든 모듈을 불러오지 않는다.** 그래서 `textkit.stats`가 없다는 `AttributeError`가 났다. `import textkit.stats`를 하고 나서야 `stats` 모듈이 불러와지고 `textkit`의 속성으로 붙는다. 패키지를 가져오면 그 안의 모든 모듈이 자동으로 따라오리라고 기대하기 쉬운데, 그렇지 않다. 패키지 안의 모듈은 필요한 것을 **하나씩** 가져온다. (8.3.2에서 `__init__.py`가 안의 모듈을 대신 불러 주게 할 수도 있다.)

**표준 라이브러리에도 패키지가 있다**

4.6과 7장에서 쓴 모듈 중에도 패키지가 있다. `json`은 사실 `json/__init__.py`, `json/decoder.py`, `json/encoder.py` 등으로 된 패키지이고, 이 절에서 쓴 `collections`도 패키지다. 웹에서 데이터를 가져오는 `urllib.request`는 `urllib` 패키지 안의 `request` 모듈이다.

```python
>>> import json
>>> json
<module 'json' from '/Library/Frameworks/Python.framework/Versions/3.13/lib/python3.13/json/__init__.py'>
>>> import urllib.request
```

쓰는 사람은 `json`이 모듈 하나인지 패키지인지 신경 쓰지 않고 `json.dumps()`를 썼다. 패키지를 만드는 사람이 안을 어떻게 나눴든 바깥에는 깔끔한 이름만 보이게 할 수 있다는 뜻이다. 그 일을 `__init__.py`가 한다.

### 8.3.2 `__init__.py`가 하는 일

`__init__.py`는 **패키지를 처음 가져올 때 실행되는 모듈**이다. 이름에서 짐작할 수 있듯이 5장의 `__init__` 메서드가 객체를 준비하듯, `__init__.py`는 패키지를 준비한다. `import textkit`을 해도, `import textkit.stats`를 해도, `from textkit.cleaning import words`를 해도 **`__init__.py`가 먼저 한 번** 실행된다. 패키지 안의 모듈을 하나라도 쓰려면 패키지부터 준비해야 하기 때문이다.

**비어 있어도 된다**

지금처럼 빈 파일이어도 된다. 빈 `__init__.py`는 **"이 폴더는 패키지"라는 표시 역할** 만 한다. 처음 만드는 패키지는 빈 `__init__.py`로 충분하다.

> **`__init__.py`가 없으면?**
> 파이썬 3.3부터는 `__init__.py`가 없는 폴더도 패키지처럼 가져올 수 있다(네임스페이스 패키지라는 특별한 용도의 기능이다). 그래서 `__init__.py`를 빼먹어도 대개 돌아간다. 하지만 일부 도구가 패키지로 알아보지 못하는 등 미묘한 차이가 있으므로, **패키지를 만들 때는 언제나 `__init__.py`를 둔다**고 기억하자.

**이름을 다시 내보낸다**

`__init__.py`에서 가장 많이 하는 일은 패키지 안 모듈의 이름을 가져와 **패키지 이름 바로 아래로 다시 내보내는 것**이다. `textkit/__init__.py`를 다음처럼 고쳐 보자.

```python
# textkit/__init__.py
"""텍스트 통계 패키지."""

from textkit.cleaning import words
from textkit.stats import top_words, word_count

__all__ = ["top_words", "word_count", "words"]
```

이제 바깥에서는 패키지 안이 어떻게 나뉘어 있는지 몰라도 된다.

```python
>>> import textkit
>>> textkit.top_words("a b a")
[('a', 2), ('b', 1)]
>>> from textkit import word_count
>>> word_count("x y")
2
```

`__init__.py`가 실행되면서 `words`, `top_words`, `word_count`라는 이름이 `textkit` 모듈 객체의 속성이 되었기 때문이다(8.1.2에서 모듈의 최상위 이름은 모듈의 속성이 된다고 했다). 이 방식에는 두 가지 이점이 있다.

- **쓰는 쪽이 편하다.** `from textkit.stats import top_words` 대신 `from textkit import top_words`라고 쓴다.
- **안을 고쳐도 바깥은 그대로다.** 나중에 `top_words()`를 `stats.py`에서 `ranking.py`로 옮기더라도, `__init__.py`의 한 줄만 고치면 `from textkit import top_words`라고 쓴 바깥 코드는 그대로 동작한다.

라이브러리들이 이렇게 한다. 7장에서 쓴 `json.JSONDecodeError`는 실제로는 `json` 패키지 안의 `decoder` 모듈(`json/decoder.py`)에 정의되어 있다. 클래스의 `__module__` 속성으로 정의된 모듈을 확인할 수 있다.

```python
>>> import json
>>> json.JSONDecodeError.__module__
'json.decoder'
```

`json/__init__.py`가 이 클래스를 가져와 다시 내보내기 때문에 `json.decoder.JSONDecodeError`라고 길게 쓰지 않아도 된다. `from openai import OpenAI`의 `OpenAI`도 패키지 안의 다른 모듈에 정의된 클래스를 `__init__.py`가 다시 내보낸 것이다.

`__all__`은 8.1.7에서 본 대로 `from textkit import *`로 가져갈 이름의 목록이다. 여기서는 또 하나의 역할이 있다. `__init__.py`에서 가져오기만 하고 쓰지 않은 이름에 Ruff가 "가져오고 쓰지 않았다(`F401`)"는 경고를 표시하는데, `__all__`에 적어 두면 **일부러 다시 내보내는 것**이라고 알아듣고 경고하지 않는다.

`__init__.py`에는 이처럼 이름을 다시 내보내는 `import`와 패키지 전체에 쓰는 상수 정도만 둔다. `__init__.py`는 패키지 안의 어떤 모듈을 쓰든 먼저 실행되므로, 여기에 오래 걸리는 일이나 출력하는 코드를 넣으면 패키지의 모든 사용자가 그 비용을 치른다. 8.1.3의 "모듈의 최상위에는 정의만 둔다"가 `__init__.py`에는 더 엄격하게 적용된다.

### 8.3.3 패키지 안에서 서로 부르기 — 절대 import와 상대 import

`stats.py`는 같은 패키지의 `cleaning.py`를 `from textkit.cleaning import words`로 불렀다. 이처럼 **맨 위 패키지 이름부터 전체 경로를 쓰는 것**을 **절대 import**라고 한다. 패키지 안에서는 다른 방법도 있다.

```python
# textkit/stats.py
from .cleaning import words
```

`from .cleaning`의 점 하나는 **"이 모듈이 들어 있는 패키지"** 를 뜻한다. `stats.py`는 `textkit` 패키지 안에 있으므로 `.cleaning`은 `textkit.cleaning`이다. 이렇게 **지금 위치를 기준으로 쓰는 것**을 **상대 import**라고 한다. 7장의 상대 경로가 현재 디렉터리를 기준으로 하듯, 상대 import는 지금 모듈이 속한 패키지를 기준으로 한다.

| 쓰는 모양 | 뜻 (`textkit/stats.py`에서 쓸 때) |
|---|---|
| `from .cleaning import words` | 같은 패키지(`textkit`)의 `cleaning` 모듈에서 `words` |
| `from . import cleaning` | 같은 패키지에서 `cleaning` 모듈 |
| `from ..other import x` | 한 단계 위 패키지의 `other` 모듈에서 `x` (패키지 안에 패키지가 있을 때) |

패키지 안에 패키지를 둘 수도 있다. 예를 들어 `textkit/lang/korean.py`가 있다면 `lang`은 `textkit`의 **하위 패키지**(`textkit/lang/__init__.py`가 필요하다)이고, `korean.py`에서 `cleaning.py`를 부르는 방법은 다음 두 가지다.

```python
# textkit/lang/korean.py
from textkit.cleaning import words   # 절대 import
from ..cleaning import words         # 상대 import: .. 은 lang의 한 단계 위인 textkit
```

두 방법을 비교하면 다음과 같다.

| | 절대 import | 상대 import |
|---|---|---|
| 모양 | `from textkit.cleaning import words` | `from .cleaning import words` |
| 장점 | 어느 파일에서 쓰든 같은 모양이고, 무엇을 가져오는지 한눈에 보인다 | 짧다. 패키지 이름을 바꿔도 고칠 필요가 없다 |
| 단점 | 패키지 이름을 바꾸면 모든 `import`를 고쳐야 한다 | `..`이 겹치면 어디를 가리키는지 헤아려야 한다. **패키지 안에서만** 쓸 수 있다 |

파이썬의 스타일 가이드(PEP 8)는 절대 import를 권하고, 상대 import도 허용한다. 실제로는 둘 다 많이 쓰이므로 **둘 다 읽을 수 있어야** 한다. 이 교재에서는 무엇을 가져오는지 분명히 보이는 **절대 import**를 쓴다. 한 프로젝트 안에서는 한 가지로 통일하는 것이 좋다.

### 8.3.4 패키지 안의 파일을 실행하기 — `python -m`

`stats.py`의 맨 아래에는 시험 코드가 있다. `ch08` 폴더에서 이 파일을 직접 실행해 보자.

```
python textkit/stats.py
```

```
Traceback (most recent call last):
  File "/Users/본인계정/python-lab/ch08/textkit/stats.py", line 5, in <module>
    from textkit.cleaning import words
ModuleNotFoundError: No module named 'textkit'
```

`textkit` 폴더 안에 있는 `stats.py`가 `textkit`을 찾지 못한다. 8.1.6을 떠올리면 이유가 보인다. `python textkit/stats.py`로 실행하면 `sys.path`의 맨 앞에는 **스크립트가 있는 폴더**, 즉 `ch08/textkit`이 들어간다. 파이썬은 `ch08/textkit` 안에서 `textkit`이라는 이름의 모듈이나 폴더를 찾는데, 거기에는 `cleaning.py`, `stats.py`만 있을 뿐 `textkit`은 없다. `textkit` 폴더는 한 단계 위인 `ch08`에 있다.

`stats.py`를 상대 import(`from .cleaning import words`)로 바꿔서 실행하면 다른 오류가 난다.

```
ImportError: attempted relative import with no known parent package
```

"속한 패키지를 모르는데 상대 import를 하려 했다"는 뜻이다. `python textkit/stats.py`로 실행한 파일은 `__name__`이 `"__main__"`인 **그냥 스크립트**다. 파이썬은 이 파일이 `textkit` 패키지의 일부라는 것을 모르므로 `.`이 어디인지 알 수 없다.

두 오류의 원인은 같다. **패키지 안의 파일을 파일 경로로 실행했기 때문**이다. 이 장의 "1단계를 마친 사람에게"에서 말한 AI가 만든 프로젝트의 오류가 바로 이것이다. 해결 방법은 `python -m`이다.

```
python -m textkit.stats
```

```
<frozen runpy>:130: RuntimeWarning: 'textkit.stats' found in sys.modules after import of package 'textkit', but prior to execution of 'textkit.stats'; this may result in unpredictable behaviour
[('the', 2), ('cat', 1), ('and', 1)]
```

(첫 줄의 `RuntimeWarning`은 잠시 뒤에 설명한다. `<frozen runpy>:130`의 줄 번호는 파이썬 버전에 따라 다를 수 있다.)

`-m`은 module의 약자로, **파일 경로 대신 모듈 이름으로** 실행하라는 옵션이다. `python -m textkit.stats`는 다음처럼 동작한다.

1. `sys.path`의 맨 앞에 **현재 디렉터리**(`ch08`)를 넣는다.
2. `import`할 때와 똑같은 방법으로 `textkit.stats`를 찾는다. `ch08` 안에 `textkit` 패키지가 있으므로 찾을 수 있다. 패키지의 `__init__.py`도 먼저 실행된다.
3. 찾은 모듈을 `__name__`을 `"__main__"`으로 해서 실행한다. 그래서 `if __name__ == "__main__":` 아래의 시험 코드가 실행된다.

**`RuntimeWarning`이 나오는 이유**

시험 코드의 결과보다 먼저 나온 경고는 "`textkit` 패키지를 불러온 뒤, `textkit.stats`를 실행하기 **전에** 이미 `sys.modules`에 `textkit.stats`가 있었다. 예측할 수 없는 동작이 생길 수 있다"는 뜻이다. 2번과 3번 사이에 무슨 일이 있었는지 따라가 보자.

- 2번에서 패키지의 `__init__.py`가 먼저 실행된다. 8.3.2에서 `__init__.py`에 `from textkit.stats import top_words, word_count`를 넣었으므로, 이때 `stats.py`가 **보통 모듈**(`__name__`이 `"textkit.stats"`)로 한 번 실행되어 `sys.modules`에 들어간다.
- 3번에서 `-m`은 `stats.py`를 `"__main__"`이라는 이름으로 **한 번 더** 실행한다.

결국 같은 파일이 두 번 실행되어 모듈 객체가 두 개(`textkit.stats`와 `__main__`) 생긴다. 지금의 `stats.py`는 함수만 정의하므로 결과에 문제가 없다. 하지만 모듈에 상태를 담은 변수가 있으면 두 벌이 따로 바뀌고, 클래스가 있으면 이름은 같지만 서로 다른 클래스가 두 개 생긴다. 예를 들어 예외 클래스가 두 벌이면 한쪽의 `except`가 다른 쪽에서 일으킨 예외를 잡지 못한다. 파이썬이 "예측할 수 없다"고 경고하는 이유다.

`__init__.py`를 잠시 비우고 `python -m textkit.stats`를 다시 실행하면 경고가 사라진다. `__init__.py`가 `stats`를 미리 불러오지 않으므로 `stats.py`가 한 번만 실행되기 때문이다. 확인한 뒤에는 `__init__.py`를 되돌린다. 정리하면 다음과 같다.

- **패키지의 `__init__.py`가 가져오는 모듈은 `python -m`으로 실행하지 않는다.**
- 실행할 코드는 `__init__.py`가 가져오지 않는 모듈에 둔다. 패키지 전체를 실행하는 코드는 잠시 뒤의 `__main__.py`에, 시험 코드는 따로 만든 시험용 모듈에 두면 된다.

`python -m`을 쓸 때 주의할 점은 다음과 같다.

- 경로가 아니라 **모듈 이름**을 쓴다. 슬래시(`/`) 대신 점(`.`)을 쓰고, `.py`를 붙이지 않는다. `python -m textkit/stats.py`라고 쓰면 `No module named 'textkit/stats'`와 함께 `.py`를 빼 보라는 안내(`Try using ...`)가 나오는데, 슬래시도 점으로 바꿔야 한다.
- **패키지가 들어 있는 폴더에서** 실행한다. 1번에서 현재 디렉터리를 검색 경로에 넣기 때문이다. `python-lab`에서 `python -m textkit.stats`를 실행하면 `No module named textkit`이 난다. 앞의 표에서 본 것처럼 일반 스크립트는 **스크립트 위치**가 기준이지만, `-m`은 **현재 디렉터리**가 기준이다.

`-m`은 표준 라이브러리의 모듈을 실행할 때도 쓴다. 예를 들어 `json.tool`은 JSON 파일을 보기 좋게 정리해 보여 주는 모듈이다. 7장의 대출 기록 파일을 열어 보자.

```
python -m json.tool --no-ensure-ascii --indent 2 ../ch07/data/loans.json
```

`--no-ensure-ascii`는 7.3.5의 `ensure_ascii=False`와 같은 옵션이다. 이 옵션을 넣었으므로 한글이 `철수`처럼 그대로 나온다. 옵션을 빼고 실행하면 `\ucca0\uc218` 같은 모양으로 나온다. 9장에서는 외부 패키지를 설치할 때 `python -m pip install ...`을 쓰게 되는데, 그것도 `pip`이라는 모듈을 실행하는 것이다.

**`__main__.py` — 패키지 자체를 실행하기**

패키지 폴더에 `__main__.py`라는 파일을 두면 `python -m 패키지이름`으로 **패키지를 통째로 실행**할 수 있다. 이때 실행되는 것이 `__main__.py`다. 파일 이름을 인자로 받아 단어 통계를 보여 주도록 만들어 보자.

```python
# textkit/__main__.py
"""python -m textkit 파일...로 실행하면 파일마다 단어 통계를 보여 준다."""

import sys

from textkit.stats import top_words, word_count

if len(sys.argv) < 2:
    print("사용법: python -m textkit 파일 [파일 ...]", file=sys.stderr)
    sys.exit(2)

failed = False
for name in sys.argv[1:]:
    try:
        with open(name, encoding="utf-8") as f:
            text = f.read()
    except FileNotFoundError:
        print(f"파일이 없습니다: {name}", file=sys.stderr)
        failed = True
        continue
    print(f"{name}: {word_count(text)}단어, 많이 나온 단어 {top_words(text, 3)}")

if failed:
    sys.exit(1)
```

파일 하나가 없어도 나머지 파일은 계속 처리한다. 대신 실패가 하나라도 있었는지 `failed`에 기억해 두었다가, 모든 파일을 처리한 뒤 종료 코드 1로 끝낸다. 오류 메시지만 출력하고 종료 코드 0으로 끝나면, 이 프로그램을 실행한 다른 프로그램은 실패를 알 수 없기 때문이다(8.2.2).

`ch08`에 `cat.txt`를 만들어 시험해 보자.

```
The cat sat on the mat.
The cat ran!
```

```
python -m textkit cat.txt nope.txt
```

```
cat.txt: 9단어, 많이 나온 단어 [('the', 3), ('cat', 2), ('sat', 1)]
파일이 없습니다: nope.txt
```

실행한 뒤 종료 코드를 확인하면 1이다. `python -m textkit cat.txt`처럼 모든 파일을 처리하면 0이다.

`__main__.py`는 `python -m textkit`으로 실행할 때만 쓰이는 파일이므로 `if __name__ == "__main__":`으로 감싸지 않아도 된다. 이 파일을 `import`할 일은 없기 때문이다. 다만 내용이 길어지면 다른 모듈(예: `cli.py`)에 `main()` 함수를 만들고 `__main__.py`에서는 그것을 불러 호출만 하는 경우가 많다. 종합 실습에서 그렇게 한다.

**VS Code의 ▷ 버튼은?**

VS Code의 ▷ 버튼은 지금 열린 파일을 `python 파일경로`로 실행한다. 그래서 패키지 안의 `stats.py`를 열어 놓고 ▷를 누르면 앞에서 본 `ModuleNotFoundError`가 난다. 방법은 두 가지다.

- **패키지 바깥에 짧은 시작 파일을 둔다.** `ch08/main.py`처럼 패키지 바깥에 있는 파일은 ▷로 실행해도 `sys.path`의 맨 앞이 `ch08`이므로 패키지를 찾을 수 있다. 종합 실습에서 이 방법을 쓴다.
- **터미널에서 `python -m`으로 실행한다.** 패키지 안의 모듈을 시험할 때 쓴다.

### 8.3.5 작은 프로젝트의 파일 나누기

이제 파일을 나누는 방법을 모두 배웠다. 남은 것은 **어떻게 나눌지**다. 정답은 없지만, 많은 프로젝트가 따르는 모양과 기준이 있다. 7장의 도서 대출 프로그램 정도의 작은 프로젝트라면 다음과 같은 모양이 흔하다.

```
project/
├── main.py             시작 파일. 패키지의 main()을 불러 호출만 한다
├── data/               데이터 파일
└── app/                프로그램의 패키지
    ├── __init__.py
    ├── models.py       데이터의 모양: 데이터 클래스
    ├── errors.py       예외 클래스
    ├── core.py         규칙과 처리 (services.py, logic.py라고도 한다)
    ├── storage.py      파일이나 데이터베이스 읽고 쓰기 (repository.py라고도 한다)
    └── cli.py          화면과 명령: 입력을 받고 결과를 보여 준다
```

이 모양 뒤에 있는 기준은 다음과 같다.

**1) 하는 일(관심사)로 나눈다.** 8.1.1에서 말한 관심사 분리다. "도서관의 규칙이 바뀌면 `core.py`, 저장 형식이 바뀌면 `storage.py`, 화면에 보이는 문구가 바뀌면 `cli.py`"처럼, **고칠 이유가 같은 코드끼리** 모은다.

**2) 의존 방향을 한쪽으로 정한다.** 8.1.8에서 본 순환 import를 막는 규칙이다. 위 모양의 모듈을 층으로 쌓아 보면 다음과 같다.

```
층  모듈          하는 일            가져오는 것
──  ──────────    ───────────────    ─────────────────────────────
 5  main.py       시작 파일          cli
 4  cli.py        화면과 명령        storage, core, errors, models
 3  storage.py    파일 읽고 쓰기     core, errors, models
 2  core.py       규칙과 처리        errors, models
 1  errors.py     예외               models
 0  models.py     데이터의 모양      (없음)
```

층 번호가 큰 모듈은 **자기보다 아래층의 모듈만** 가져온다.

- 위쪽은 아래쪽을 쓰지만, **아래쪽은 위쪽을 모른다.** `models.py`는 아무것도 가져오지 않고, `core.py`는 `storage.py`나 `cli.py`를 가져오지 않는다.
- 7장에서 정한 "**`Library`는 파일을 모른다**"가 이제 `import` 줄로 드러난다. `core.py`의 맨 위에는 `csv`, `json`, `pathlib`, `storage`를 가져오는 줄이 없다. 규칙이 코드 구조로 바뀐 것이다.
- 아래쪽 모듈일수록 다른 프로그램에서 다시 쓰기 쉽다. 예를 들어 `models.py`와 `core.py`는 나중에 웹 화면을 만들 때도 그대로 쓸 수 있다. `cli.py`만 웹용으로 새로 만들면 된다.

**3) 시작 파일은 짧게 둔다.** `main.py`는 패키지 바깥에서 `from app.cli import main`과 `main()` 호출만 한다. 그래서 ▷ 버튼으로 실행해도, `python main.py`로 실행해도 패키지를 찾을 수 있다(8.3.4).

**4) 경로와 설정은 시작하는 쪽에서 정해 넘긴다.** 7장에서 `load_books(path)`처럼 경로를 매개변수로 받게 했다. `storage.py`는 "어떤 파일이든 주면 읽는다"만 하고, 어느 파일을 읽을지는 `cli.py`가 정한다. 그래야 시험할 때 다른 파일을 넘기거나, 명령행 인자로 데이터 폴더를 바꾸기 쉽다.

`Path(__file__)`을 패키지 안에서 쓸 때는 기준이 한 단계 달라진다는 점에 주의하자. 7장의 `library.py`는 `ch07` 바로 아래에 있었으므로 `Path(__file__).parent`가 `ch07`이었다. 같은 코드를 `app/cli.py`에 두면 `Path(__file__).parent`는 `app` 폴더다. 프로젝트 폴더의 `data`를 가리키려면 `Path(__file__).parent.parent / "data"`처럼 한 단계 더 올라가야 한다.

**5) 너무 잘게 나누지 않는다.** 함수 하나짜리 파일 열 개는 큰 파일 하나만큼이나 찾기 어렵다. "몇 줄이 넘으면 나눈다" 같은 규칙은 없다. 파일 안에서 원하는 코드를 찾기 어렵다고 느낄 때, 또는 한 파일에 서로 다른 이유로 고쳐질 코드가 섞여 있다고 느낄 때 나누면 된다. 그리고 **`utils.py`(잡동사니) 모듈을 조심하자.** "어디 넣을지 모르겠는 것"을 모아 두기 시작하면 금세 아무 관계 없는 함수들의 창고가 된다. 넣기 전에 그 함수가 정말로 어느 역할에 속하는지 한 번 더 생각해 보자.

AI 서비스를 만드는 프로젝트도 크게 다르지 않다. 이후 과정에서는 다음과 같은 구조를 자주 보게 될 것이다.

```
chatbot/
├── main.py
├── prompts/              프롬프트 텍스트 파일
├── data/
└── app/
    ├── __init__.py
    ├── config.py         설정: 환경 변수에서 API 키, 모델 이름 읽기
    ├── models.py         요청과 응답의 모양
    ├── llm.py            LLM API를 부르는 코드
    ├── services/         기능별 처리 (하위 패키지)
    │   ├── __init__.py
    │   ├── summarize.py
    │   └── translate.py
    └── api.py            웹 요청을 받는 곳 (cli.py 자리)
```

`config.py`에서 `os.environ`으로 API 키를 읽고(8.2.1), `llm.py`가 LLM을 부르고, `services`의 모듈들이 `llm.py`를 써서 요약·번역을 하고, 맨 위의 `api.py`가 사용자의 요청을 받아 `services`에 넘긴다. 의존 방향은 여전히 위에서 아래로 한쪽이다.

## 실습 8-4. 종합 — 도서 대출 관리 프로그램 (패키지 버전)

7장 실습 7-4의 도서 대출 관리 프로그램 `library.py`를 **`library` 패키지**로 나눈다. 프로그램이 하는 일은 거의 그대로이고, 코드가 어느 파일에 있느냐가 달라진다. 거기에 이 장에서 배운 표준 라이브러리로 기능 두 가지를 더한다.

| | 7장 | 8장 |
|---|---|---|
| 파일 | `library.py` 한 파일(500줄 이상) | `library` 패키지의 모듈 다섯 개와 시작 파일 |
| "`Library`는 파일을 모른다" | 약속으로 지켰다 | `core.py`가 `csv`, `json`, `pathlib`, `storage`를 가져오지 않는 것으로 드러난다 |
| 시작점 | 맨 아래에서 `main()` 호출 | `if __name__ == "__main__":`. `python main.py`나 `python -m library`로 실행 |
| 데이터 폴더 | `ch07/data`로 고정 | 명령행 인자로 바꿀 수 있다(`sys.argv`) |
| 시작하지 못할 때 | 메시지를 출력하고 `return` | 표준 오류에 출력하고 종료 코드 1(`sys.exit`) |
| 새 명령 | | `대출자`: 대출자별로 빌린 도서를 보여 준다(`defaultdict`) |

이 실습의 목표는 세 가지다. 첫째, 한 파일의 코드를 **역할별 모듈로 나누고 의존 방향을 지킨다.** 둘째, 패키지를 **여러 방법으로 실행**해 보고, 어떤 실행 방법이 왜 되고 왜 안 되는지 설명할 수 있게 된다. 셋째, `sys`와 `collections`를 실제 프로그램에 써 본다.

**준비**

`ch08` 폴더 안에 다음 구조를 만든다. `data/books.csv`는 7장의 것을 복사한다. `loans.json`은 복사하지 않는다(처음 실행하면 프로그램이 만든다).

```
ch08/
├── main.py
├── data/
│   └── books.csv
└── library/
    ├── __init__.py
    ├── __main__.py
    ├── models.py
    ├── errors.py
    ├── core.py
    ├── storage.py
    └── cli.py
```

7장의 `library.py`는 VS Code에서 **열어 두고 보면서** 코드를 옮긴다. `ch08` 폴더에 `library.py`를 복사하지는 말자. 같은 폴더에 `library.py` 파일과 `library` 폴더가 함께 있으면 `import library`가 무엇을 가리키는지 헷갈리게 된다.

**모듈 구성**

8.3.5의 모양을 그대로 쓴다. 각 모듈에 들어갈 것과, 가져올 수 있는 모듈은 다음과 같다.

| 층 | 모듈 | 들어갈 것 (7장의 코드) | 가져올 수 있는 패키지 안 모듈 |
|---|---|---|---|
| 5 | `main.py` (패키지 바깥) | 시작 파일 | `library.cli` |
| 4 | `cli.py` | `DEFAULT_DATA_DIR`, `HELP_TEXT`, `print_lines()`, `parse_days()`, `main()` | `storage`, `core`, `errors`, `models` |
| 3 | `storage.py` | `load_books()`, `load_loans()`, `save_loans()`, `write_report()` | `core`, `errors`, `models` |
| 2 | `core.py` | `Library` | `errors`, `models` |
| 1 | `errors.py` | `LibraryError`과 자식 예외 네 개, `DataFileError` | `models` |
| 0 | `models.py` | `WEEKDAYS`, `format_date()`, `Book`, `ReferenceBook`, `Loan` | 없음 |

`__init__.py`는 바깥에 보여 줄 이름을 다시 내보내고, `__main__.py`는 `python -m library`로 실행할 때 `cli.main()`을 호출한다.

**요구 사항**

1. 실습 7-4의 요구 사항을 그대로 지킨다. 아래에서 바꾸거나 더한 것만 다르다.
2. **모듈 구성과 의존 방향** — 위의 "모듈 구성" 표대로 나눈다. 패키지 안의 모듈은 표의 "가져올 수 있는 패키지 안 모듈"에 있는 것만 가져온다. 특히 `core.py`에는 `csv`, `json`, `pathlib`, `open()`이 없어야 하고, `models.py`, `errors.py`, `core.py`, `storage.py`는 `cli.py`를 가져오지 않는다(`cli.py`를 가져오는 것은 시작 파일인 `main.py`와 `__main__.py`뿐이다).
3. **절대 import** — 패키지 안의 모듈은 `from library.models import Book`처럼 절대 import로 가져온다. 필요한 이름만 가져오고, 가져와 놓고 쓰지 않는 이름이 없게 한다(Ruff의 밑줄로 확인할 수 있다).
4. **모듈의 최상위** — 각 모듈은 모듈 독스트링으로 시작하고, 최상위에는 `import`, 상수, 함수와 클래스의 정의만 둔다. `cli.py`의 `main()`은 `if __name__ == "__main__":` 안에서만 호출한다.
5. **`__init__.py`** — `Library`, `Book`, `ReferenceBook`, `Loan`, 예외 클래스 여섯 개, `load_books`, `load_loans`, `save_loans`, `write_report`를 다시 내보내고, 같은 이름들로 `__all__`을 만든다. `ch08` 폴더에서 연 셸에서 `from library import Library, load_books`가 되어야 한다.
6. **실행 방법** — 다음 네 가지 방법이 모두 같은 `ch08/data`의 파일을 읽고 써야 한다.
   - `ch08` 폴더에서 `python main.py`
   - `python-lab` 폴더에서 `python ch08/main.py`
   - `ch08` 폴더에서 `python -m library`
   - VS Code에서 `main.py`를 열고 ▷ 버튼
7. **데이터 폴더 인자** — `python main.py [데이터 폴더]`처럼 데이터 폴더를 명령행 인자로 줄 수 있다.
   - 인자가 없으면 `DEFAULT_DATA_DIR`을 쓴다.
   - 인자가 하나면 그 폴더를 쓴다. 사용자가 지정한 경로이므로 **현재 디렉터리를 기준**으로 한다(7.2.4). `books.csv`, `loans.json`, `loan_report.csv`는 모두 그 폴더 안의 파일이다.
   - 인자가 둘 이상이면 `사용법: python main.py [데이터 폴더]`를 출력하고 종료 코드 2로 끝낸다.
8. **시작하지 못할 때** — 실습 7-4의 요구 사항 6에서 출력하던 메시지(도서 목록 파일이 없을 때, `books.csv`의 `DataFileError`, `loans.json`의 `DataFileError`와 그 아래의 안내 문장)와 요구 사항 7의 사용법 메시지는 모두 **표준 오류**로 출력하고, 7의 사용법은 종료 코드 2, 나머지는 종료 코드 1로 끝낸다. 프로그램이 정상적으로 시작해 `종료`로 끝나면 종료 코드는 0이다.
9. **`대출자` 명령** — `Library.borrower_lines()`가 만든 줄을 `print_lines()`로 출력한다. 대출 중인 도서가 없으면 `대출 중인 도서가 없습니다.`를 출력한다. `borrower_lines()`는 `defaultdict(list)`로 대출자별 대출 기록을 모은다. `도움`의 명령 목록에도 `대출자`를 더한다.

**힌트**

- 순서는 `models.py` → `errors.py` → `core.py` → `storage.py` → `cli.py` → `main.py`, `__main__.py` → `__init__.py`가 좋다. **아래층부터** 옮기면, 옮긴 모듈을 바로 셸에서 시험할 수 있다. 위층 모듈은 아직 없어도 아래층 모듈은 위층을 가져오지 않기 때문이다.
- **`__init__.py`는 끝날 때까지 비워 둔다.** `import library.models`를 해도 `__init__.py`가 먼저 실행된다(8.3.2). `__init__.py`에 `from library.core import Library`를 미리 써 두면, `core.py`를 아직 옮기지 않은 동안에는 `models`조차 불러올 수 없다.
- 모듈을 하나 옮길 때마다 `ch08` 폴더에서 셸을 열어 확인한다. 셸은 고친 모듈을 다시 읽지 않으므로(8.1.3) 모듈을 고쳤으면 셸을 다시 연다.
  ```python
  >>> from library.models import Book, format_date
  >>> from datetime import date
  >>> format_date(date(2026, 11, 14))
  '2026-11-14(토)'
  >>> from library.errors import NotBorrowableError
  >>> str(NotBorrowableError(Book("R01", "파이썬 사전")))
  "대출할 수 없는 참고 도서입니다: '파이썬 사전'"
  ```
- `import` 줄은 코드를 옮긴 뒤에 쓰면 쉽다. 옮긴 코드에서 다른 모듈에 있는 이름(예: `core.py`의 `Book`, `Loan`, `BookNotFoundError`, `timedelta`)에는 Ruff가 `Undefined name`이라는 밑줄을 긋는다. 밑줄이 그어진 이름을 하나씩 확인하며, 그 이름이 있는 모듈에서 가져온다. 이때 가져오려는 모듈이 표의 "가져올 수 있는" 칸에 있는지 확인하자. 없다면 그 코드가 잘못된 모듈에 들어간 것이다.
- `storage.py`의 함수들은 매개변수의 타입 힌트에 `Library`를 쓰고 `library.import_loans()`를 호출하므로 `core`를 가져와야 한다. 저장(3층)이 규칙(2층)을 쓰는 것은 허용된 방향이다. 반대로 `core.py`가 `storage`를 가져오면 안 된다.
- `cli.py`의 `DEFAULT_DATA_DIR`은 `Path(__file__).parent.parent / "data"`다. 8.3.5에서 말한 대로 `cli.py`는 `library` 폴더 안에 있으므로, `ch08/data`를 가리키려면 `.parent`를 두 번 쓴다. 7장의 `DATA_DIR`, `BOOKS_PATH`, `LOANS_PATH`, `REPORT_PATH` 같은 모듈 상수는 없앤다. 데이터 폴더가 실행할 때 정해지므로, 파일 경로는 `main()` 안에서 만든다.
- `main()`의 시작 부분은 다음 모양이 된다.
  ```python
  if len(sys.argv) > 2:
      print("사용법: python main.py [데이터 폴더]", file=sys.stderr)
      sys.exit(2)
  if len(sys.argv) == 2:
      data_dir = Path(sys.argv[1])
  else:
      data_dir = DEFAULT_DATA_DIR
  books_path = data_dir / "books.csv"
  # loans_path, report_path도 같은 방법으로

  try:
      books = load_books(books_path)
  except FileNotFoundError:
      print(f"도서 목록 파일이 없습니다: {books_path}", file=sys.stderr)
      sys.exit(1)
  ...
  ```
  7장에서는 `return`으로 `main()`을 끝냈다. 이제는 `sys.exit(1)`로 프로그램을 끝내면서 실패했다는 사실을 종료 코드로 남긴다. `python -m library`로 실행할 때 `sys.argv[0]`은 `.../library/__main__.py`이지만, 인자는 똑같이 `sys.argv[1]`부터 들어온다.
- `borrower_lines()`는 `self.loans()`(반납 기한 순)를 차례로 보며 `defaultdict(list)`에 `who`를 키로 `Loan`을 모은다. 기한 순으로 넣었으므로 한 사람의 목록은 저절로 기한 순이 된다. 대출자 이름의 순서는 `sorted(groups, key=lambda who: (-len(groups[who]), who))`로 정한다. 4.5.5에서 튜플을 `key`로 쓰면 앞의 값부터 비교한다고 배웠다. 권수에 `-`를 붙여 많은 순으로 만들었다. 한 줄의 도서 목록은 `", ".join(...)`으로 잇는다.
- 시험할 때는 `cli.py`의 `today = date.today()`를 잠시 `today = date(2026, 10, 31)`로 바꾼다. 7장에서는 `library.py`에서 바꿨지만, 이제는 그 줄이 `cli.py`에 있다. 고칠 곳을 찾을 때 "날짜를 정하는 것은 화면 쪽의 일"이라고 생각하면 바로 찾아갈 수 있다.

**더 해 보기 (선택)**

- **안전하게 저장하기**: 7장 "더 해 보기"의 임시 파일 교체(`tmp.replace(path)`)를 아직 하지 않았다면 지금 해 보자. 이번에는 **`storage.py`의 `save_loans()` 하나만** 고치면 된다는 것을 확인하자. 파일을 나눠 둔 덕분에 다른 모듈은 열어 보지 않아도 된다.
- **환경 변수로 데이터 폴더 정하기**: 명령행 인자가 없을 때 환경 변수 `LIBRARY_DATA_DIR`이 있으면 그 폴더를 쓰고, 그것도 없으면 `DEFAULT_DATA_DIR`을 쓰게 한다. "명령행 인자 → 환경 변수 → 기본값" 순서로 정하는 것은 많은 프로그램이 따르는 관례다. 터미널에서 `export LIBRARY_DATA_DIR=test_data`(Windows PowerShell은 `$env:LIBRARY_DATA_DIR = "test_data"`)를 하고 `python main.py`로 실행해 보자.
- **인기 도서**: 7장 "더 해 보기"의 대출 이력(`history.jsonl`)을 만들었다면, `인기` 명령으로 지금까지 가장 많이 대출된 도서 3권을 보여 준다. 이력의 `action`이 `대출`인 줄만 골라 도서 코드를 `Counter`로 세고 `most_common(3)`을 쓴다. 이력 파일을 읽는 함수는 어느 모듈에, 개수를 세어 줄을 만드는 일은 어느 모듈에 두어야 할까? `Library`는 이력을 알아야 할까?
- **시험용 모듈 만들기**: `library/selftest.py`를 만들고, 파일 없이 `Book` 몇 권으로 `Library`를 만들어 `borrow()`, `return_book()`, `borrower_lines()`를 호출해 결과를 출력하는 시험 코드를 넣는다. `ch08` 폴더에서 `python -m library.selftest`로 실행한다. 시험 코드를 `core.py`의 맨 아래에 두고 `python -m library.core`로 실행하면 어떤 경고가 나오는지도 확인하고, 그 이유를 8.3.4로 설명해 보자. (`python -m library.cli`는 왜 경고가 나지 않는가? `__init__.py`가 무엇을 가져오는지 보자.) 이렇게 손으로 확인하던 것을 자동으로 확인하는 방법(`unittest`, `pytest`)은 이후 과정에서 배운다.

## 정리

| 항목 | 핵심 |
|---|---|
| 모듈 | `.py` 파일 하나. 모듈 이름은 파일 이름에서 `.py`를 뺀 것. 모듈 독스트링으로 시작한다 |
| 모듈 객체 | `import`하면 모듈 객체가 생기고, 최상위 이름이 그 속성이 된다. 전역 변수 = 모듈의 속성. "전역"은 모듈 하나의 범위 |
| 파일을 나누는 이유 | 찾기 쉽고, 다시 쓰기 쉽고, 의존 관계가 `import` 줄로 드러나고, 함께 고치기 쉽다. 관심사(고칠 이유)에 따라 나눈다 |
| `from 모듈 import 이름` | 내 파일에 이름표를 하나 더 붙인다. 모듈 쪽 이름표가 옮겨 가도 내 이름표는 그대로 |
| `import`의 동작 | 처음 한 번만 파일을 위에서부터 **실행**하고 `sys.modules`에 둔다. 다음부터는 꺼내 쓴다 |
| 모듈의 최상위 | 독스트링, `import`, 상수, 함수·클래스 정의만. 출력·입력·파일 쓰기는 함수 안에 |
| 셸과 모듈 | 셸은 고친 모듈을 다시 읽지 않는다. 모듈을 고쳤으면 셸을 다시 연다 |
| `__pycache__` | `import`된 모듈의 바이트코드(`.pyc`) 저장소. 지워도 된다. 원본 `.py`가 없으면 쓰이지 않는다. 공유할 때는 뺀다 |
| `__name__` | 직접 실행한 파일은 `"__main__"`, `import`된 파일은 모듈 이름 |
| `if __name__ == "__main__":` | 직접 실행할 때만 동작하는 코드. 모듈의 시험 코드, 프로그램의 `main()` 호출을 감싼다 |
| 모듈 검색 경로 | `sys.path`를 앞에서부터 찾는다. ① 스크립트 폴더(셸·`-c`·`-m`은 현재 디렉터리) ② 표준 라이브러리 ③ `site-packages` |
| 이름 가리기 | 스크립트 폴더가 표준 라이브러리보다 앞이다. `json.py`, `random.py` 같은 파일 이름은 쓰지 않는다 |
| 파일 경로와 `import` | 상대 파일 경로는 **현재 디렉터리**, `import`는 **스크립트 폴더** 기준 |
| `ModuleNotFoundError` | 파일 위치, 실행 위치, 이름(대소문자)을 확인한다. `sys.path.append()`로 덮지 않는다 |
| `_이름` | 모듈 안에서만 쓰는 이름이라는 약속. `from 모듈 import *`가 가져가지 않는다. `__all__`로 공개 목록을 정한다 |
| 순환 import | 두 모듈이 서로를 부르면 덜 만들어진 모듈에서 이름을 꺼내다 `ImportError`. **의존 방향을 한쪽으로** |
| `os` | 운영체제 기능. `os.path` 코드는 `pathlib`과 짝지어 읽는다. 새 코드는 `pathlib` |
| 환경 변수 | 프로그램 밖에서 주는 이름=값. `os.environ["X"]`(없으면 `KeyError`), `os.getenv("X", 기본값)`. 터미널에서 `export X=값` / `$env:X = "값"`. API 키는 코드에 쓰지 않는다 |
| `sys.argv` | 명령행 인자의 리스트. `[0]`은 스크립트, 인자는 `[1]`부터. 모두 문자열 |
| `sys.exit()` | 프로그램을 끝내고 종료 코드를 남긴다. 0은 성공, 그 밖은 실패(흔히 1: 실패, 2: 사용법 오류). `SystemExit` 예외 |
| `sys.stderr` | 오류 메시지는 `print(..., file=sys.stderr)`. `>`로 표준 출력을 돌려도 화면에 남는다 |
| `sys`의 정보 | `sys.version_info`, `sys.platform`, `sys.executable`(9장), `sys.path`, `sys.modules` |
| `Counter` | 개수 세기. 없는 키는 0(추가되지 않음). `most_common(n)`, `update()`, `total()`, `+`/`-`. 딕셔너리의 자식 |
| `defaultdict` | 없는 키를 꺼내면 기본값을 만들어 넣는다. `defaultdict(list)`로 그룹 모으기. **꺼내기만 해도 키가 생긴다** → 확인은 `in`, `get()` |
| `typing` 옛날 표기 | `List[str]` = `list[str]`, `Optional[int]` = `int \| None`, `Union[int, str]` = `int \| str` |
| `typing` 지금도 쓰는 것 | `Any`(무엇이든), `Literal["a", "b"]`(정해진 값), `TypedDict`(키가 정해진 딕셔너리). 타입 별칭 `Role = Literal[...]` |
| `Callable` | 함수의 타입 힌트 `Callable[[인자들], 반환]`. 새 코드는 `from collections.abc import Callable`, `typing.Callable`은 기존 코드에서 읽는 표기 |
| 타입 검사 | 파이썬은 실행할 때 검사하지 않는다. Pylance의 `typeCheckingMode`로 편집기에서 검사할 수 있다 |
| 문서에서 찾기 | 하고 싶은 일을 말로 → 라이브러리 문서의 장 → 설명과 함수 정의 → **버전 확인** → 셸에서 시험 |
| 패키지 | `__init__.py`가 있는 폴더. `import 패키지.모듈`, `from 패키지 import 모듈`, `from 패키지.모듈 import 이름` |
| 패키지 가져오기 | 패키지만 가져오면 안의 모듈은 따라오지 않는다. 안의 모듈을 하나라도 가져오면 `__init__.py`가 먼저 실행된다 |
| `__init__.py` | 패키지를 준비하는 모듈. 비어 있어도 된다. 이름을 다시 내보내고 `__all__`을 둔다. 무거운 일은 넣지 않는다 |
| 절대 / 상대 import | `from textkit.cleaning import words` / `from .cleaning import words`(`.` 같은 패키지, `..` 한 단계 위). 상대 import는 패키지 안에서만 |
| 패키지 안의 파일 실행 | `python 패키지/모듈.py`는 `No module named ...` 또는 `attempted relative import with no known parent package` |
| `python -m` | 모듈 이름으로 실행(`python -m textkit.stats`). 현재 디렉터리가 검색 경로에 들어간다. 패키지가 있는 폴더에서 실행. `__init__.py`가 가져오는 모듈을 실행하면 두 번 실행되어 `RuntimeWarning` |
| `__main__.py` | `python -m 패키지`로 실행할 때 실행되는 파일 |
| 프로젝트 나누기 | 관심사로 나눈다. 아래층은 위층을 모른다(models ← errors ← core ← storage ← cli). 시작 파일은 짧게, 경로는 시작하는 쪽에서 넘긴다. 너무 잘게, `utils.py`는 조심 |

## 다음 장

[9장. 가상환경](ch09.md)에서는 표준 라이브러리 밖의 패키지를 설치해 쓰는 방법을 배운다. 이 장에서 `sys.path`의 세 번째 부분으로 지나쳤던 `site-packages`가 바로 설치한 패키지가 들어가는 곳이다. 8.2.6의 표에서 "실무에서는 외부 패키지 `requests`를 더 많이 쓴다"고 했던 그 `requests`도 설치해서 써 본다. 그런데 프로젝트마다 필요한 패키지와 버전이 다르고, 한 컴퓨터에 파이썬이 여러 개 설치되어 있기도 하다. 그래서 9장에서는 프로젝트마다 독립된 파이썬 환경을 만드는 **가상환경**(`venv`)을 배우고, `python -m pip install`로 패키지를 설치하고, `requirements.txt`로 같은 환경을 다른 컴퓨터에서 다시 만든다. "분명히 설치했는데 `ModuleNotFoundError`가 난다"는 문제도 다룬다. 이 장에서 본 `sys.executable`과 모듈 검색 경로가 그 문제를 푸는 열쇠다.
