# 10장. 마무리

[파이썬 기초](README.md) 과정의 마지막 장이다. 1장부터 9장까지 문법과 도구를 하나씩 배우면서, 장마다 도서 대출 관리 프로그램을 한 걸음씩 키워 왔다. 5장에서 클래스로 만들고, 6장에서 실패를 예외로 바꾸고, 7장에서 파일에 저장하고, 8장에서 패키지로 나누고, 9장에서 가상환경을 갖춘 프로젝트로 옮겼다. 그런데 그 프로그램의 클래스 이름, 메서드, 모듈을 나누는 방법, 요구 사항은 **모두 교재가 정해 주었다.** 여러분은 정해진 설계대로 코드를 채웠다.

이 장에서는 빈 폴더에서 시작한다. 무엇을 만들지, 입력 파일을 어떤 모양으로 할지, 어떤 실패가 있을 수 있고 각각 어떻게 알릴지, 코드를 어떤 클래스와 함수로 나눌지를 **스스로 정하고** 끝까지 만든다.

- **종합 실습** — 파일에서 데이터를 읽어 가공하고 결과를 저장하는 작은 명령행(CLI) 프로그램(예: 가계부, 할 일 관리, 단어 빈도 분석)을 함수와 클래스로 구조화하여 작성한다.

이 장에는 새 문법이 없다. 대신 **무엇을 어떤 순서로 정하고 만드는가**를 배운다. 10.1에서 설계하는 순서를 익히고, 10.2에서 예제 프로그램 하나(가계부 요약)를 그 순서대로 처음부터 끝까지 함께 만든다. 10.3과 10.4에서는 만든 코드를 남에게 설명하고, 다른 환경에서 똑같이 실행되게 넘겨주는 방법을 다룬다. 마지막 실습 10-4에서 여러분이 고른 주제로 같은 과정을 혼자 해 본다.

종합 실습의 완료 기준은 세 가지다. 이 장의 모든 내용은 이 세 가지를 위한 것이다.

> **종합 실습 완료 기준**
> 1. 정상 파일, 빈 파일, 잘못된 형식의 입력을 각각 처리하고 적절한 메시지를 출력한다.
> 2. 핵심 함수와 클래스가 각각 무슨 일을 하는지, 왜 그렇게 나눴는지 설명할 수 있다.
> 3. 새 가상환경에서 `requirements.txt`로 의존성을 복원하고 동일하게 실행할 수 있다.

> **1단계를 마친 사람에게**
> 1단계에서는 "가계부 프로그램 만들어 줘"라고 말하면 AI가 몇 초 만에 코드를 내놓았다. 실행하면 대개 돌아갔다. 그런데 엑셀에서 저장한 파일을 넣었더니 이상한 오류가 나거나, 금액 칸이 비어 있는 줄 하나 때문에 프로그램이 통째로 멈추거나, 기능을 하나 더해 달라고 했더니 멀쩡하던 다른 기능이 망가진 경험이 있을 것이다. 그때마다 오류 메시지를 AI에게 다시 붙여 넣었다. 문제는 코드를 쓰는 속도가 아니었다. **무엇이 들어올 수 있고, 들어오면 어떻게 할지를 아무도 정하지 않았다는 것**이다. 이 장에서 하는 일이 바로 그것을 먼저 정하는 일이다. 정해 두고 나면 AI에게 맡길 때도 "이 표대로 만들어 줘", "이 경우가 빠졌다"처럼 훨씬 정확하게 말할 수 있고, AI가 만든 코드가 맞는지 스스로 판단할 수 있다.

## 학습 목표

이 장을 마치면 다음을 할 수 있다.

- 만들 프로그램을 한 문단으로 쓰고, **하지 않을 것**을 정해 범위를 좁힐 수 있다.
- 코드를 쓰기 전에 실행 예를 먼저 쓰고, 입력 파일의 형식을 표로 정할 수 있다.
- 정상 파일뿐 아니라 빈 파일, 첫 줄만 있는 파일, 잘못된 형식의 파일을 **시험 파일로 먼저** 만들 수 있다.
- 일어날 수 있는 실패를 표로 정리하고, 각각을 누가 고쳐야 하는지, 어디서 알아차리는지, 어떤 메시지와 종료 코드로 알릴지 정할 수 있다.
- 잘못된 줄을 만났을 때 "첫 오류에서 멈춤", "모두 모아 알리고 멈춤", "건너뛰고 계속" 중 하나를 프로그램의 성격에 맞게 고르고 이유를 말할 수 있다.
- 코드를 데이터(models), 계산(core), 파일(storage), 화면(cli)으로 나누고, 의존 방향을 한쪽으로 정할 수 있다.
- 데이터 클래스, 일반 클래스, 함수 중 무엇으로 만들지 판단할 수 있다.
- 아래층부터 만들고, 한 층을 만들 때마다 셸과 시험 파일로 확인하며 진행할 수 있다.
- 시험 파일을 기대한 결과와 비교하는 작은 확인 스크립트를 만들 수 있다.
- 함수와 클래스가 하는 일을 한 문장으로, 나눈 이유를 "고칠 이유"로 설명하고, 설계 노트(`DESIGN.md`)로 남길 수 있다.
- 프로젝트를 다른 위치에 옮겨 `README.md`만 보고 새 가상환경에 복원해 똑같이 실행되는지 확인할 수 있다.
- AI에게 설계를 주고 모듈 단위로 맡긴 뒤, 결과를 설계와 시험 파일로 검토할 수 있다.

## 실습 준비

1장에서 만든 실습 폴더 안에 `ch10` 폴더를 만든다.

```
cd ~/python-lab
mkdir ch10
cd ch10
pwd
```

```
# macOS
/Users/본인계정/python-lab/ch10

# Windows
C:\Users\본인계정\python-lab\ch10
```

이 장은 앞의 장들과 몇 가지가 다르다.

1. **실습의 단위가 프로젝트다.** 9장 실습 9-4처럼, 실습마다 `ch10` 안에 프로젝트 폴더를 하나씩 만든다(`ledger_app`, 그리고 실습 10-4에서 여러분의 프로젝트). 프로젝트마다 전용 가상환경을 만들고, VS Code 창도 따로 연다(9.2.4).
2. **문서를 쓰는 시간이 길다.** 설계 메모, `README.md`, `DESIGN.md`를 쓴다. 코드를 쓰기 전에 쓰는 문서도 있다. 이것도 프로그램을 만드는 일의 일부다.
3. **실행 결과가 날짜에 따라 바뀌지 않는다.** 예제 프로그램은 오늘 날짜를 쓰지 않고 파일의 내용만 읽는다. 그래서 같은 시험 파일을 넣으면 이 교재와 똑같은 결과가 나와야 한다. 다르다면 무엇이 다른지 찾는 것이 곧 확인이다.
4. **출력의 버전 숫자는 다를 수 있다.** 9장과 마찬가지로 `rich`와 그 의존성의 버전은 여러분의 화면에서 더 높을 수 있다.

코드를 보여 주는 방식은 9장과 같다.

- 앞에 `>>>`가 붙어 있으면 대화형 셸에서 한 줄씩 입력하는 코드다.
- 첫 줄에 `# models.py` 같은 파일 이름이 있으면 스크립트 파일 코드다. 패키지 안의 파일은 `# ledger/models.py`처럼 프로젝트 폴더 기준 경로로 적는다.
- `>>>`도 파일 이름도 없는 블록은 터미널 명령이나 그 출력이다.

## 10.1 처음부터 설계하기

AI에게 "가계부 프로그램 만들어 줘"라고 하면 곧바로 코드가 나온다. 사람도 그렇게 할 수 있다. 빈 파일을 열고 `import csv`부터 쓰기 시작하는 것이다. 작은 스크립트라면 그래도 된다. 하지만 파일을 읽고, 검사하고, 계산하고, 보여 주고, 저장하는 프로그램을 그렇게 만들면 대개 이렇게 된다. 정상 파일로는 잘 돌아가는 코드가 금방 생긴다. 그다음 빈 파일을 넣어 보고, 잘못된 파일을 넣어 보고, 그때마다 `if`와 `try`를 여기저기 끼워 넣는다. 어느새 검사하는 코드와 계산하는 코드와 출력하는 코드가 한 함수 안에 뒤엉킨다.

코드를 쓰기 전에 몇 가지를 먼저 정하면 이 일을 피할 수 있다. 이 절에서는 그 순서를 여섯 단계로 나누어, 이 장의 예제인 **가계부 요약 프로그램**을 설계해 본다. 실제 코드는 10.2에서 쓴다.

| 단계 | 정하는 것 | 남는 것 |
|---|---|---|
| 10.1.1 | 무엇을 만들고, 무엇을 만들지 않을지 | 한 문단 설명, 하지 않을 것 목록 |
| 10.1.2 | 사용자가 무엇을 입력하고 무엇을 보게 될지 | 실행 예 초안 |
| 10.1.3 | 입력 파일의 모양 | 형식 표, 시험 파일 |
| 10.1.4 | 무엇이 잘못될 수 있고 각각 어떻게 할지 | 실패 표 |
| 10.1.5 | 코드를 어떤 모듈, 클래스, 함수로 나눌지 | 모듈 표, 의존 방향 |
| 10.1.6 | 무엇부터 만들지 | 만드는 순서 |

종이에 써도 되고, 프로젝트 폴더에 `notes.md` 같은 파일을 만들어 써도 된다. 어디에 쓰든 **글로 남긴다.** 머릿속으로만 정한 것은 코드를 쓰다 보면 슬그머니 바뀐다. 여기서 쓴 것은 나중에 `README.md`와 `DESIGN.md`(10.3)의 재료가 된다.

### 10.1.1 한 문단으로 쓴다

먼저 만들 프로그램을 한 문단으로 쓴다. **누가, 무엇을 넣어서, 무엇을 얻는지**가 들어가면 된다.

> 엑셀이나 VS Code로 한 달 동안의 수입과 지출을 CSV 파일에 적어 두는 사람이, 그 파일을 명령행 인자로 넘기면 수입·지출·잔액과 지출 분류별 합계를 화면에서 확인하고, 분류별 합계를 엑셀에서 열 수 있는 CSV 파일로 저장해 받는다. 파일에 잘못 적은 줄이 있으면 어느 줄이 왜 잘못되었는지 알려 주고(너무 많으면 앞의 10건과 나머지 건수), 요약은 만들지 않는다.

한 문단으로 쓰기 어렵다면 아직 무엇을 만들지 정하지 못한 것이다. 반대로 한 문단에 "그리고"가 계속 이어진다면 너무 많은 것을 만들려는 것이다.

다음으로 **하지 않을 것**을 적는다. 이것이 한 문단보다 더 중요할 때가 많다.

- 거래를 추가하거나 고치는 기능은 없다. 파일은 엑셀이나 VS Code로 편집한다.
- 여러 달을 비교하지 않는다. 파일 하나에 한 기간의 거래가 있다고 본다.
- 예산, 그래프, 통화 변환은 없다.
- 대화형으로 명령을 입력받지 않는다. 한 번 실행하면 한 가지 일을 하고 끝난다.

만들다 보면 넣고 싶은 기능이 계속 떠오른다. 그때마다 이 목록을 보고 "이번에는 안 한다"고 정리한다. **끝까지 완성한 작은 프로그램이, 반쯤 만든 큰 프로그램보다 낫다.** 하지 않기로 한 것은 버리는 것이 아니라 다음 버전으로 미루는 것이다. 실습 10-4의 주제 C(가계부 넓히기)가 바로 이 목록에서 나온다.

마지막 항목은 프로그램의 모양을 정하는 결정이다. 도서 대출 관리 프로그램은 `> ` 프롬프트를 띄워 놓고 명령을 계속 입력받았다. 대출 기록이 계속 바뀌고, 사용자가 이것저것 확인하며 쓰는 프로그램이기 때문이다. 가계부 요약은 다르다. 파일 하나를 넣으면 결과 하나가 나오면 된다. 8.2.2에서 본 것처럼, 인자를 받아 한 번 실행하고 끝나는 프로그램은 **다른 프로그램이나 스크립트가 대신 실행해 줄 수 있다.** 열두 달 치 파일을 한꺼번에 요약하고 싶어지면, 이 프로그램을 열두 번 실행하는 스크립트를 쓰면 된다.

### 10.1.2 실행 예를 먼저 쓴다

다음은 프로그램이 완성되었을 때 터미널에서 일어날 일을 **코드보다 먼저** 쓴다. 이 교재의 실습마다 있던 "실행 예"를 스스로 쓰는 것이다.

정상 파일을 넣었을 때:

```
python main.py samples/2026-10.csv
```

```
가계부 요약: 2026-10.csv
기간: 2026-10-01 ~ 2026-10-31 (거래 14건)
수입: 2,835,000원
지출: 969,500원
잔액: 1,865,500원
(지출 분류별 합계 표 — 분류, 금액, 비율. 금액이 큰 순. 맨 아래에 합계)
요약을 저장했습니다: samples/2026-10_summary.csv
```

잘못된 줄이 있는 파일을 넣었을 때:

```
python main.py samples/broken.csv
```

```
broken.csv: 형식 오류 9건
  3번째 줄: 날짜가 'YYYY-MM-DD' 모양이 아닙니다: '2026/10/03'
  4번째 줄: 구분은 '수입'이나 '지출'이어야 합니다: '지츨'
  ...
파일을 고친 뒤 다시 실행하세요. 요약 파일은 만들지 않았습니다.
```

실행 예를 쓰다 보면 저절로 많은 것이 정해진다.

- **실행 방법**: `python main.py 파일` 하나다. 인자는 파일 경로 하나뿐이다.
- **보여 줄 것과 그 순서**: 기간과 거래 수, 수입, 지출, 잔액, 그리고 분류별 표.
- **금액의 모양**: 천 단위 쉼표와 `원`(2.3.4의 `:,`).
- **저장할 파일의 이름과 위치**: 입력 파일 옆에 `_summary`를 붙인 이름. 어디에 저장했는지 화면에 알려 준다.
- **오류 메시지의 모양**: 파일 이름과 오류 건수를 먼저, 그다음 줄 번호와 원인을 한 줄씩. 마지막에 사용자가 할 일. 오류가 아주 많으면 화면이 오류로 덮이지 않도록 앞의 10건만 보여 주고 나머지는 건수만 알린다.

그리고 실행 예는 그대로 **완성했는지 확인하는 목록**이 된다. 다 만든 뒤 이 명령을 입력해서 이 화면이 나오면 된 것이다. 숫자(2,835,000원 같은)는 시험 파일을 만든 뒤 계산기로 직접 더해서 채워 넣는다. 프로그램이 낸 숫자를 그대로 옮겨 적으면 확인이 되지 않는다.

실행 예는 초안이다. 만들다가 더 나은 모양이 떠오르면 바꿔도 된다. 다만 바꿀 때는 실행 예부터 고치고 코드를 고친다.

### 10.1.3 입력 형식을 정하고 시험 파일부터 만든다

**입력 형식 정하기**

프로그램이 읽을 파일의 모양을 표로 정한다. CSV라면 열마다 이름, 내용, 허용하는 값을 적는다.

| 열 | 내용 | 허용하는 값 | 예 |
|---|---|---|---|
| `date` | 거래 날짜 | `YYYY-MM-DD` 모양의 실제 날짜 | `2026-10-05` |
| `kind` | 구분 | `수입` 또는 `지출` | `지출` |
| `category` | 분류 | 비어 있지 않은 문자열 | `식비` |
| `memo` | 내용 | 아무 문자열. 비어도 된다 | `점심` |
| `amount` | 금액(원) | 1 이상의 정수. 숫자만 쓰거나 세 자리마다 쉼표를 넣는다. 쉼표를 넣으면 큰따옴표로 감싼다 | `9500`, `"12,000"` |

첫 줄은 열 이름 `date,kind,category,memo,amount`이고, 파일은 UTF-8로 저장한다. 표를 채우면서 정한 것들과 그 이유는 다음과 같다.

- **열 이름은 영어로 했다.** 열 이름은 코드에서 딕셔너리의 키로 쓴다(7.3.2의 `DictReader`). 영어로 하면 코드에서 쓰기 편하고, 도서 목록 `books.csv`와도 같은 방식이다. 한글 열 이름을 쓰기로 해도 문제는 없다. 중요한 것은 **정하고, 적어 두고, 검사하는 것**이다.
- **수입과 지출을 `kind` 열로 나누었다.** 금액에 부호를 붙여 지출은 `-9500`처럼 쓰는 방법도 있다. 하지만 사람이 손으로 적는 파일에서는 `-`를 빠뜨리는 실수가 잦고, 빠뜨려도 티가 나지 않는다. 구분을 글자로 적게 하면 읽기도 쉽고, 오타는 검사에서 걸린다.
- **금액의 쉼표를 허용하되, 위치까지 정했다.** 엑셀에서 천 단위 구분 기호를 켜고 CSV로 저장하면 `"12,000"`처럼 큰따옴표로 감싼 값이 나온다. 이런 값은 받아들인다. 그런데 "쉼표를 허용한다"고만 정하면 `12,00`, `1,,000`, `1,2,3`도 쉼표만 지우고 1200, 1000, 123으로 읽게 된다. 잘못 적은 금액이 **조용히 다른 숫자가 되어** 합계에 들어가는 것이다. 그래서 쉼표는 오른쪽에서 세 자리마다만 올 수 있다고 정한다. 따옴표 없이 쓴 `12,000`은 칸이 하나 더 생기므로 오류로 알린다. 밑줄(`1_000`)이나 `원` 같은 글자, 소수점도 받지 않는다.
- **날짜는 `YYYY-MM-DD`만 받는다.** `2026/10/05`, `10/5` 같은 모양까지 받아들이면 `03/04`가 3월 4일인지 4월 3일인지 알 수 없다. 한 가지 모양만 받고, 다른 모양은 오류로 알려서 고치게 한다.

**시험 파일부터 만들기**

형식을 정했으면 코드를 쓰기 전에 **시험 파일**을 만든다. 정상 파일 하나만 만들면 정상인 경우만 시험하게 된다. 완료 기준 1의 세 가지 입력(정상, 빈, 잘못된 형식)에 맞춰 다음 다섯 개를 만든다.

| 파일 | 내용 | 기대하는 결과 |
|---|---|---|
| `2026-10.csv` | 정상적인 한 달 치 거래 14건 | 요약을 보여 주고 저장한다 |
| `header_only.csv` | 첫 줄(열 이름)만 있다 | 거래가 없다고 알린다 |
| `empty.csv` | 아무것도 없다(0바이트) | 빈 파일이라고 알린다 |
| `broken.csv` | 줄마다 다른 잘못이 하나씩 있다 | 잘못된 줄을 줄 번호와 함께 알린다 |
| `bad_quote.csv` | 큰따옴표의 짝이 맞지 않는 줄이 있다 | CSV 형식이 깨졌다고 알린다 |

"빈 파일"이 두 종류라는 데 주목하자. 0바이트 파일과 첫 줄만 있는 파일은 다르다. 잘못된 형식도 두 종류다. 값이 틀린 줄(`broken.csv`)과 CSV의 문법 자체가 깨진 파일(`bad_quote.csv`)은 처리 방법이 다르다. 두 차이는 10.1.4에서 다룬다.

잘못된 형식의 파일은 **한 줄에 한 가지 잘못만** 넣는다. 한 줄에 잘못이 두 개 있으면, 프로그램이 그중 하나만 알려 줬을 때 다른 하나를 제대로 검사하는지 알 수 없다. 형식 표의 칸마다 "어떻게 틀릴 수 있나"를 생각해서 한 줄씩 만든다.

| 줄 | 잘못 | 기대하는 메시지 |
|---|---|---|
| 2 | (정상인 줄. 잘못된 줄 사이에 정상인 줄이 있어도 되는지 본다) | |
| 3 | 날짜를 `/`로 썼다 | 날짜 모양이 아니다 |
| 4 | 구분에 오타(`지츨`) | 구분은 수입이나 지출이어야 한다 |
| 5 | 금액의 쉼표를 따옴표 없이 썼다 | 칸이 너무 많다 |
| 6 | 분류가 비었다 | 분류가 비어 있다 |
| 7 | 금액에 글자가 있다(`6만2천원`) | 금액이 정수가 아니다 |
| 8 | 금액이 음수다 | 금액은 1 이상이어야 한다 |
| 9 | 칸이 모자란다(내용과 금액이 없다) | 금액이 비어 있다 |
| 10 | 없는 날짜(`2026-02-30`) | 날짜 모양이 아니다 |
| 11 | 쉼표가 세 자리마다가 아니다(`"38,00"`) | 쉼표 위치가 잘못되었다 |

이 표가 곧 검사 코드의 목록이다. 10.2에서 검사 코드를 쓸 때 이 표를 옆에 두고, 줄마다 기대한 메시지가 나오는지 확인한다.

### 10.1.4 실패를 미리 나눈다

이제 무엇이 잘못될 수 있는지를 모두 적는다. 시험 파일로 만든 경우뿐 아니라, 파일이 없거나 인자를 잘못 준 경우처럼 **파일 바깥의 실패**도 적는다. 칸마다 다음을 정한다.

- **누가 고치나** — 실행한 사람, 파일을 편집한 사람, 프로그래머, 실행 환경을 갖추는 사람(9장).
- **어디서 알아차리나** — 어느 모듈, 어느 함수에서 그 문제를 처음 알게 되는가.
- **어떻게 알리나** — 메시지와, 표준 출력인지 표준 오류인지(8.2.2).
- **종료 코드** — 0(성공), 1(실패), 2(사용법이 잘못됨). 8장에서 정한 관례다.

| 상황 | 누가 고치나 | 어디서 알아차리나 | 어떻게 알리나 | 종료 코드 |
|---|---|---|---|---|
| 인자가 없거나 두 개 이상 | 실행한 사람 | `cli` | 사용법 (표준 오류) | 2 |
| 파일이 없다 | 실행한 사람 | `storage`의 `open()` → `cli` | 파일이 없다 (표준 오류) | 1 |
| UTF-8이 아니다 | 파일을 편집한 사람 | `storage` | 인코딩 안내 (표준 오류) | 1 |
| 빈 파일(0바이트) | 파일을 편집한 사람 | `storage` | 빈 파일이다 (표준 오류) | 1 |
| 첫 줄이 다르다 | 파일을 편집한 사람 | `storage` | 첫 줄의 올바른 모양 (표준 오류) | 1 |
| CSV 형식이 깨졌다(큰따옴표의 짝) | 파일을 편집한 사람 | `storage` | 대략의 줄 번호와 함께 (표준 오류) | 1 |
| 값이 잘못된 줄이 있다 | 파일을 편집한 사람 | `storage`, `models` | 줄 번호와 원인. 모두 모으되, 화면에는 앞의 10건과 나머지 건수 (표준 오류) | 1 |
| 첫 줄만 있다 | (고칠 것 없음) | `cli` | 거래가 없다 (표준 출력) | 0 |
| `rich`가 없다 | 실행 환경 | `main.py` | 9장의 안내 (표준 오류) | 1 |
| 빈 목록으로 요약을 부탁했다 | 프로그래머 | `core` | `ValueError` (트레이스백) | 1 |

몇 가지 결정은 따로 설명이 필요하다.

**1) 빈 파일 두 가지**

0바이트 파일과 첫 줄만 있는 파일은 둘 다 거래가 0건이지만 뜻이 다르다. 첫 줄만 있는 파일은 **올바른 형식의 가계부인데 아직 거래가 없는** 것이다. 이번 달 첫날에 실행했다면 당연히 그렇다. 잘못이 아니므로 메시지를 표준 출력으로 보여 주고 종료 코드 0으로 끝낸다. 0바이트 파일은 첫 줄조차 없다. 엉뚱한 파일을 넘겼거나, 저장하다가 내용이 날아간 파일일 가능성이 높다. 이 프로그램이 읽는 형식이 아니므로 오류로 알린다.

어느 쪽으로 정할지는 프로그램마다 다르다. 단어 빈도 분석기라면 0바이트 텍스트 파일도 "단어가 0개인 올바른 텍스트"로 볼 수 있다. 중요한 것은 **두 경우를 구별해서 생각하고, 정한 것을 적어 두는 것**이다.

**2) 잘못된 줄을 만나면**

파일에 잘못된 줄이 있을 때 할 수 있는 일은 세 가지다.

| | 첫 오류에서 멈춤 | 모두 모아 알리고 멈춤 | 건너뛰고 계속 |
|---|---|---|---|
| 동작 | 처음 만난 잘못을 알리고 끝낸다 | 끝까지 검사한 뒤 잘못을 모두 알리고 끝낸다 | 잘못된 줄을 빼고 나머지로 결과를 만든다. 뺀 줄은 경고로 알린다 |
| 좋은 점 | 만들기 가장 쉽다 | 사용자가 한 번에 모두 고칠 수 있다 | 일부라도 결과를 얻는다 |
| 아쉬운 점 | 잘못이 10개면 10번 실행해야 다 찾는다 | 조금 더 복잡하다 | 결과가 **조용히 틀릴** 수 있다 |
| 어울리는 곳 | 프로그램이 스스로 쓰고 읽는 저장 파일 | 사람이 손으로 쓰는 입력 파일 | 일부가 빠져도 되는 대량의 기록(로그 분석 등) |

도서 대출 관리 프로그램은 `loans.json`을 읽다가 문제가 있으면 첫 오류에서 멈췄다(7장). 그 파일은 프로그램이 스스로 저장하는 파일이라 잘못될 일이 드물고, 잘못되었다면 무언가 크게 잘못된 것이기 때문이다. 가계부 파일은 사람이 손으로 쓴다. 오타가 여러 군데 있는 것이 자연스럽다. 그래서 **모두 모아 알리고 멈추기**로 한다.

모두 모으는 것과 모두 **보여 주는** 것은 다른 문제다. 날짜 열을 통째로 잘못 쓴 1,000줄짜리 파일이라면 오류도 1,000건이다. 그것을 모두 화면에 쏟으면 정작 무엇이 문제인지 보이지 않는다. 그래서 문제는 모두 모으되, 화면에는 앞의 10건만 보여 주고 나머지는 "외 990건"처럼 건수만 알리기로 한다. 같은 원인이 반복된 경우가 대부분이므로 10건이면 무엇을 고칠지 알 수 있고, 고치고 다시 실행하면 남은 오류가 보인다. 모으는 일은 파일을 읽는 쪽(`storage`)이, 몇 건을 보여 줄지는 화면 쪽(`cli`)이 정한다.

건너뛰고 계속하는 방법은 왜 고르지 않았을까? 금액 칸이 `6만2천원`인 줄을 건너뛰면 지출 합계가 62,000원 적게 나온다. 경고를 출력해도, 표를 보고 숫자만 확인하는 사람은 놓치기 쉽다. **요약 프로그램에서 틀린 합계는 합계가 없는 것보다 나쁘다.** 반대로 웹 서버의 접속 기록 100만 줄에서 많이 들어온 주소를 세는 프로그램이라면, 깨진 줄 몇 개를 건너뛰는 편이 낫다. 정답은 프로그램의 목적이 정한다.

**3) CSV 문법이 깨지면 그 자리에서 멈춘다**

2)는 **값이 틀린 줄**에 대한 결정이다. CSV에는 그보다 앞선 문제가 있을 수 있다. 큰따옴표로 감싼 칸은 따옴표가 닫힐 때까지 쉼표와 줄바꿈까지 모두 그 칸의 내용으로 읽는다. 그런데 `"12000`처럼 닫는 따옴표를 빠뜨리면, 다음 줄, 그다음 줄이 모두 이 칸에 빨려 들어간다. 어디서부터 칸이 다시 나뉘는지 알 수 없으므로 **그 뒤의 줄은 검사해 봐야 의미가 없다.** 이런 문법 오류는 줄마다 모으지 않고, 처음 만난 곳에서 대략의 위치를 알리고 멈춘다. 2)의 세 가지 방법 중 "첫 오류에서 멈춤"을 이 경우에만 고르는 것이다.

**4) 실패하면 결과 파일을 만들지 않는다**

입력에 문제가 있으면 요약 파일을 쓰지 않는다. 지난번에 제대로 만든 `2026-10_summary.csv`가 있다면 그대로 남는다. 틀린 데이터로 맞는 결과를 덮어쓰지 않는 것이다.

**5) 결과는 표준 출력, 문제는 표준 오류**

8장에서 정한 대로다. 요약은 표준 출력으로, 문제를 알리는 메시지는 표준 오류로 보낸다. `python main.py 파일 > out.txt`로 결과를 파일에 받을 때, 문제가 생기면 메시지는 여전히 화면에 보인다. 첫 줄만 있는 경우의 "거래가 없습니다"는 문제가 아니라 결과이므로 표준 출력이다.

**6) 프로그래머의 실수는 그대로 드러낸다**

표의 마지막 줄은 사용자가 만나는 실패가 아니다. `core`의 요약 함수에 빈 목록을 넘기는 것은 `cli`를 잘못 짠 프로그래머의 실수다(6.2.3). `cli`는 요약을 부탁하기 전에 거래가 있는지 먼저 확인하기로 했으므로, 이 예외가 사용자 앞에 나타난다면 버그다. 버그는 메시지로 감추지 않고 트레이스백으로 드러나게 둔다(6.2.6).

실패 표에 없는 실패도 있을 것이다. 예를 들어 파일 대신 폴더 이름을 넘기면 어떻게 될까? 실습 10-2에서 직접 확인한다. 표는 처음부터 완벽할 필요가 없다. 새로운 실패를 발견할 때마다 **표에 한 줄을 더하고, 시험 파일을 하나 더 만들고, 코드를 고친다.** 이 순서를 지키면 표가 프로그램과 함께 자란다.

### 10.1.5 역할을 나눈다

이제 코드를 어떻게 나눌지 정한다. 8.3.5에서 배운 모양을 출발점으로 삼아, 이 프로그램이 해야 할 일을 하나씩 어디에 둘지 생각한다.

| 해야 할 일 | 성격 | 둘 곳 |
|---|---|---|
| 거래 한 건, 요약 결과의 모양 | 데이터 | `models.py` |
| 구분·분류·금액이 가계부 규칙에 맞는지 검사 | 데이터의 규칙 | `models.py` |
| 거래 목록으로 수입·지출·분류별 합계 계산 | 계산 | `core.py` |
| CSV 파일 읽기, 문자열을 날짜와 정수로 바꾸기 | 파일 | `storage.py` |
| 요약 결과를 CSV 파일로 쓰기 | 파일 | `storage.py` |
| 명령행 인자 받기, 결과 파일 이름 정하기 | 화면과 흐름 | `cli.py` |
| 표와 색으로 보여 주기, 오류 메시지, 종료 코드 | 화면과 흐름 | `cli.py` |
| `rich`가 없을 때 안내 | 시작 | `main.py` |

이것을 층으로 쌓으면 다음과 같다.

```
층  모듈          하는 일              가져오는 것
──  ──────────    ─────────────────    ──────────────────────────
 3  main.py       시작 파일            cli
 2  cli.py        화면과 흐름          core, storage, models, rich
 1  core.py       계산                 models
 1  storage.py    파일 읽고 쓰기       models
 0  models.py     데이터의 모양과 규칙 (없음)
```

`core.py`와 `storage.py`가 **같은 층**에 있다는 점이 도서 대출 관리 프로그램과 다르다. 거기서는 `storage.py`가 `core.py`를 가져왔다. `load_loans()`가 `Library` 객체의 `import_loans()`를 불러야 했기 때문이다. 가계부 요약에서는 `storage`가 파일을 읽어 `Transaction`의 리스트를 돌려주고, `core`는 그 리스트를 받아 계산한다. 둘은 서로를 모른다. 둘을 잇는 것은 `cli`다. 그래서 계산 규칙이 바뀌어도 `storage`는 그대로이고, 파일 형식이 바뀌어도 `core`는 그대로다.

나누면서 내린 결정들은 다음과 같다.

**1) `errors.py`를 따로 두지 않았다**

이 프로그램의 사용자 정의 예외는 "입력 파일의 형식이 맞지 않다"는 `DataFileError` 하나다. 일으키는 곳도 `storage` 하나뿐이다. 그래서 `storage.py` 안에 둔다. 도서 대출 관리 프로그램에서는 예외가 여섯 개였고, `core`와 `storage`가 함께 썼으므로 따로 모았다. 8.3.5의 다섯 번째 기준인 "너무 잘게 나누지 않는다"를 따른 것이다. 나중에 예외가 늘어나고 여러 모듈이 쓰게 되면 그때 `errors.py`로 옮긴다.

**2) 클래스로 할까, 함수로 할까**

도서 대출 관리 프로그램의 `Library`는 일반 클래스였다. 대출 기록이라는 **상태**를 들고 있고, `borrow()`, `return_book()`을 부를 때마다 그 상태가 바뀌고, 바뀔 때마다 규칙("이미 대출 중이면 안 된다")을 지켜야 했기 때문이다. 가계부 요약은 다르다. 거래 목록을 받아서 합계를 한 번 계산하면 끝이다. 계산이 끝난 뒤 바뀌는 것이 없다. 이런 일은 **함수**가 어울린다. 그리고 거래 한 건과 요약 결과는 값을 묶어 두는 **데이터 클래스**로 만든다(5.4).

| 이런 것이면 | 이것으로 | 이 장의 예 |
|---|---|---|
| 값을 묶어 두는 것 | 데이터 클래스 | `Transaction`, `Summary` |
| 상태를 들고 있고, 그 상태가 바뀌며, 바뀔 때 규칙을 지켜야 하는 것 | 일반 클래스 | (없음. 9장까지의 `Library`) |
| 입력을 받아 결과를 돌려주고 끝나는 것 | 함수 | `summarize()`, `load_transactions()` |

"함수와 클래스로 구조화하라"는 말은 클래스를 꼭 많이 만들라는 뜻이 아니다. 각각에 맞는 것을 고르라는 뜻이다. 상태가 없는 계산을 굳이 클래스로 감싸면(`Summarizer().run(transactions)`처럼) 코드만 길어진다.

**3) 검사를 두 곳으로 나누었다**

파일의 한 줄을 거래 한 건으로 만들 때 검사할 것이 두 종류 있다.

- **문자열을 값으로 바꿀 수 있는가** — `'2026-10-05'`가 날짜인가, `'12,000'`이 정수이고 쉼표가 제자리에 있는가, 칸 수가 맞는가. 이것은 파일에 어떻게 적혀 있느냐에 관한 지식이다. 그래서 `storage`가 한다. 앞뒤 공백을 지우는 정리도 여기서 한다.
- **값이 가계부의 규칙에 맞는가** — 날짜가 `date`이고 금액이 정수인가, 구분이 `수입`이나 `지출`인가, 분류가 비어 있지 않은가, 금액이 1 이상인가. 이것은 파일과 관계없는 가계부의 규칙이다. 그래서 `Transaction`의 `__post_init__`이 한다(6.2.3). 타입 힌트는 실행 중에 자료형을 검사하지 않으므로(5.4.3), 자료형도 여기서 직접 검사한다.

나중에 거래를 CSV가 아니라 JSON 파일이나 웹 화면의 입력란에서 받게 되어도, 두 번째 검사는 그대로 쓸 수 있다. `Transaction(...)`으로 만들 때마다 검사가 실행되기 때문이다. 다만 `Transaction`은 값을 **고치지는** 않는다. `' 식비 '`처럼 앞뒤에 공백이 있는 분류는 규칙 위반이 아니므로 그대로 받아들인다. 공백을 지워 `'식비'`로 맞추는 일은 바깥 데이터를 받아들이는 쪽(지금은 `storage`)의 책임이다. 입력 방식이 늘어나면 각 입구에서 같은 정리를 해야 한다는 뜻이다.

**4) 결과 파일의 이름은 `cli`가 정한다**

`storage`의 저장 함수는 경로를 받아서 그 경로에 쓰기만 한다. 입력 파일 옆에 `_summary`를 붙인 이름으로 저장하자는 결정은 `cli`가 한다. 8.3.5의 네 번째 기준 "경로와 설정은 시작하는 쪽에서 정해 넘긴다"이다.

**5) 실행 방법은 하나로 정했다**

`python main.py 파일` 하나다. `__main__.py`를 두어 `python -m ledger`로도 실행되게 할 수 있지만, 실행 방법이 늘면 `README.md`에 적을 것도, 시험할 것도, `rich`가 없을 때의 안내를 넣을 곳도 늘어난다(9장 실습 9-4의 "더 해 보기"). 필요해지면 그때 더한다. 같은 이유로 `__init__.py`에도 다시 내보내는 이름을 두지 않고 독스트링만 둔다(8장 실습 8-4 "확인할 것" 9번).

### 10.1.6 만드는 순서 — 아래층부터, 확인하며

설계가 끝났으면 만드는 순서를 정한다. 원칙은 두 가지다.

**아래층부터 만든다.** `models.py`는 다른 모듈을 가져오지 않으므로, 만들자마자 셸에서 `Transaction`을 만들어 보며 확인할 수 있다. `storage.py`의 읽기 함수는 `models.py`만 있으면 시험 파일로 확인할 수 있다. `core.py`는 셸에서 `Transaction` 몇 개를 만들어 넘겨 보면 된다. 위층부터 만들면 아래층이 없어서 실행해 볼 수가 없다.

**한 층을 만들 때마다 실행해서 확인한다.** 다섯 개 파일을 다 쓴 뒤에 처음 실행하면, 오류가 났을 때 어느 파일의 문제인지 찾기 어렵다. 한 층씩 확인해 두면, 문제가 생겼을 때 방금 만든 층을 보면 된다.

| 순서 | 만드는 것 | 확인하는 방법 |
|---|---|---|
| 0 | 프로젝트 폴더, 가상환경, `rich` 설치, `requirements.txt`, `.gitignore` | `python -m pip freeze` |
| 1 | 시험 파일 다섯 개 | VS Code로 열어 눈으로 확인 |
| 2 | `models.py` | 셸에서 올바른 거래와 규칙에 어긋나는 거래 만들어 보기 |
| 3 | `storage.py`의 읽기 | 셸에서 시험 파일을 차례로 읽어 보기 |
| 4 | `core.py` | 셸에서 거래 몇 개로 요약해 보고 계산기와 비교 |
| 5 | `storage.py`의 쓰기 | 셸에서 요약을 파일로 써 보고 엑셀로 열기 |
| 6 | `cli.py`, `main.py` | 시험 파일로 실행해 실행 예와 비교 |
| 7 | `check_samples.py`, `README.md` | 확인 스크립트 실행, `README.md`대로 따라 하기 |

### 10.1.7 AI와 함께 설계하고 만들기

이 과정을 마친 여러분은 1단계와 다른 방식으로 AI를 쓸 수 있다. 차이는 **설계를 내가 가지고 있다**는 것이다.

**설계를 주고, 한 모듈씩 맡긴다.** "가계부 프로그램 만들어 줘" 대신, 10.1.1~10.1.5에서 쓴 것을 붙여 넣고 한 모듈씩 부탁한다.

```
다음 설계대로 storage.py만 작성해 줘. 다른 모듈은 내가 이미 만들었다.

- 입력 형식: (10.1.3의 형식 표)
- 실패 처리: (10.1.4의 실패 표)
- 모듈 구조와 의존 방향: (10.1.5의 층 표). storage는 models만 가져온다.
- models.py: (지금 코드를 붙여 넣는다)
- 잘못된 줄은 모두 모아 DataFileError(path, problems) 하나로 알린다.
- 표준 라이브러리만 쓴다. 파이썬 3.13 기준. 함수마다 독스트링을 단다.
```

**받은 코드를 설계로 검토한다.** 실행하기 전에 먼저 읽고 확인한다.

- `import` 줄이 의존 방향을 지키는가? `storage.py`가 `core`나 `rich`를 가져오지 않는가?
- 예외를 일으키는 곳과 잡는 곳이 실패 표와 같은가? `storage`에서 `print()`하거나 `sys.exit()`하지 않는가?
- `try` 블록이 너무 넓지 않은가(6.1.7)? `except Exception:`으로 모든 예외를 삼키지 않는가?
- 메시지가 실행 예와 같은가?

**시험 파일로 확인한다.** AI가 만든 코드든 내가 고친 코드든, 바뀔 때마다 시험 파일로 실행해 본다. 10.2.8의 확인 스크립트를 만들어 두면 명령 하나로 된다.

**설계를 검토받는다.** AI는 빠진 경우를 찾는 데 강하다. 실패 표를 주고 "이 프로그램에 들어올 수 있는 입력 중 이 표에서 빠진 경우를 찾아 줘"라고 물어보자. 제안된 경우가 정말 일어날 수 있는지, 일어나면 어떻게 할지는 내가 판단해서 표에 더한다.

**패키지는 확인하고, 필요한지 따진다.** AI는 `pandas`, `click`, `typer`, `pydantic` 같은 패키지를 권하는 경우가 많다. 9.3.1처럼 PyPI에서 이름과 상태를 확인하고, 9.3.4의 기준으로 이 프로그램에 정말 필요한지 따진다. CSV 하나를 읽어 합계를 내는 데 `pandas`가 꼭 필요할까?

**설명은 맡기지 않는다.** 완료 기준 2는 **여러분이** 설명할 수 있어야 한다는 것이다. AI가 쓴 코드라도 줄마다 무슨 일을 하는지, 왜 거기 있는지 말할 수 없다면 아직 내 코드가 아니다. 모르는 줄이 있으면 AI에게 설명을 부탁하되, 들은 설명을 내 말로 `DESIGN.md`에 다시 쓴다(10.3).

### 실습 10-1. 설계 연습

3. **입력 형식 표**: 열마다 허용하는 값을 정한다. 다음을 결정하고 이유를 적는다.
   - 점수의 범위는? 소수점 점수(`87.5`)는 받는가?

5. **실패 표**: 10.1.4의 표를 이 프로그램에 맞게 만든다. 잘못된 줄을 만나면 세 가지 방법 중 무엇을 고를지 정하고 이유를 쓴다.
6. **역할 나누기**: 10.1.5처럼 해야 할 일과 둘 곳을 표로 만들고, 층 그림을 그린다. 데이터 클래스, 일반 클래스, 함수로 각각 무엇을 만들지 정하고 이유를 쓴다.

**생각해 보기**

- 합계가 같은 학생의 순위는 어떻게 매길까? `1, 2, 2, 4`처럼 같은 순위를 주고 다음 순위를 건너뛸까, `1, 2, 2, 3`으로 할까? 이 결정은 어느 모듈의 일인가?
- 과목이 나중에 `science`까지 늘어난다면, 3번에서 정한 형식은 그대로 쓸 수 있는가? 열 이름을 고정해 두는 방식과 첫 줄에 나온 과목을 모두 읽는 방식의 장단점은?
- 다 쓴 설계를 AI에게 보여 주고 "빠진 실패나 애매한 결정을 찾아 줘"라고 부탁해 보자. AI가 찾은 것 중 표에 더할 것과 더하지 않을 것을 고르고, 그렇게 고른 이유를 적는다.

### 10.2.3 `models.py` — 데이터의 모양과 규칙

맨 아래층부터 만든다.

```python
# ledger/models.py
"""가계부의 데이터를 나타내는 클래스.

다른 모듈을 가져오지 않는다. 패키지 안에서 가장 아래에 있는 모듈이다.
"""

from dataclasses import dataclass
from datetime import date

KINDS = ("수입", "지출")


@dataclass(frozen=True)
class Transaction:
    """거래 한 건. 파일에서 읽은 뒤에는 바뀌지 않는다."""

    day: date
    kind: str  # "수입" 또는 "지출"
    category: str
    memo: str
    amount: int  # 원 단위, 1 이상

    def __post_init__(self):
        # 타입 힌트는 실행 중에 검사되지 않으므로(5.4.3) 자료형도 직접 검사한다.
        # 불리언은 정수의 자식 클래스라서 isinstance(True, int)가 True다(4.5.3).
        if not isinstance(self.day, date):
            raise TypeError(f"날짜는 date여야 합니다: {self.day!r}")
        if self.kind not in KINDS:
            raise ValueError(f"구분은 '수입'이나 '지출'이어야 합니다: {self.kind!r}")
        if not isinstance(self.category, str) or not isinstance(self.memo, str):
            raise TypeError("분류와 내용은 문자열이어야 합니다")
        if not self.category.strip():
            raise ValueError("분류가 비어 있습니다")
        if not isinstance(self.amount, int) or isinstance(self.amount, bool):
            raise TypeError(f"금액은 정수여야 합니다: {self.amount!r}")
        if self.amount < 1:
            raise ValueError(f"금액은 1 이상이어야 합니다: {self.amount}")


@dataclass
class Summary:
    """거래 목록을 요약한 결과."""

    count: int
    first_day: date
    last_day: date
    income: int
    expense: int
    expense_by_category: list[tuple[str, int]]  # [(분류, 금액), ...] 금액이 큰 순

    @property
    def balance(self) -> int:
        """수입에서 지출을 뺀 금액. 음수일 수 있다."""
        return self.income - self.expense

    def share(self, amount: int) -> float:
        """지출 합계에서 amount가 차지하는 비율(%). 지출이 0이면 0.0이다."""
        if self.expense == 0:
            return 0.0
        return amount / self.expense * 100
```

- **필드 이름 `day`** — CSV의 열 이름은 `date`인데 필드 이름은 `day`로 했다. `date`라고 하면 `datetime`의 `date` 자료형과 이름이 같아서, 코드를 읽을 때 `date`가 자료형인지 값인지 헷갈린다. 열 이름과 필드 이름을 잇는 일은 `storage`가 한다(10.2.4).
- **`frozen=True`** — 파일에서 읽은 거래는 프로그램 안에서 바뀔 일이 없다. 바꿀 수 없게 해 두면, 실수로 바꾸는 코드를 썼을 때 바로 예외가 난다(5.4.6).
- **`__post_init__`** — 10.1.5의 "값이 가계부의 규칙에 맞는가"를 검사한다(6.2.3). 메시지는 10.1.3의 시험 파일 표에서 정한 그대로다. 타입 힌트는 실행 중에 검사되지 않으므로(5.4.3), 힌트만 믿으면 금액이 `1.5`이거나 날짜가 문자열 `'2026-10-05'`인 `Transaction`도 만들어진다. 그래서 자료형도 `isinstance()`로 직접 검사한다. 금액은 `bool`이 아닌지도 확인한다. 불리언은 정수의 자식 클래스라서 `isinstance(True, int)`가 `True`이기 때문이다(4.5.3). 자료형이 틀린 것은 값의 문제가 아니라 잘못 부른 쪽의 문제이므로 `TypeError`, 값이 규칙에 맞지 않는 것은 `ValueError`로 나누었다(6.2.3). `Transaction(...)`으로 만들 때마다 이 검사가 실행되므로, 규칙에 어긋난 값으로는 `Transaction`을 만들 수 없다. 다만 값을 **고치지는** 않는다. 분류의 앞뒤 공백을 지우는 일은 `storage`가 한다(10.1.5의 3번).
- **`KINDS`** — 구분으로 허용하는 값을 상수로 두었다. 나중에 `이체` 같은 구분을 더한다면 여기를 고친다.
- **`Summary`** — 요약 결과를 묶는 데이터 클래스다. 계산(`core`)이 만들고, 화면(`cli`)과 저장(`storage`)이 읽는다. 세 모듈이 함께 쓰는 데이터의 모양이므로 맨 아래층인 `models`에 둔다.
- **`balance`** — 잔액은 수입과 지출에서 언제나 계산할 수 있으므로 필드로 따로 저장하지 않고 프로퍼티로 만들었다(5.2.6). 필드로 두면 수입이나 지출과 맞지 않는 잔액을 넣을 수 있게 된다.
- **`share()`** — 비율 계산은 화면에서도 저장에서도 쓴다. 두 곳에서 각각 `amount / expense * 100`을 쓰면, 지출이 0일 때의 처리(`ZeroDivisionError`)를 한 곳에서 빠뜨리기 쉽다. **한 곳에 두고 함께 쓴다.** 수입만 있는 달이라면 지출이 0이다. 그런 파일로 시험하는 것은 실습 10-2에서 한다.

### 10.2.4 `storage.py` (1) — 읽고 검사하기

`storage.py`의 앞부분이다. 파일을 읽어 `Transaction`의 리스트로 바꾼다.

```python
# ledger/storage.py
"""가계부 파일을 읽고 요약 파일을 쓰는 함수.

어느 파일을 읽고 쓸지는 정하지 않는다. 경로는 호출하는 쪽(cli)이 넘겨준다.
"""

import csv
from datetime import date
from pathlib import Path

from ledger.models import Summary, Transaction

FIELDNAMES = ["date", "kind", "category", "memo", "amount"]


class DataFileError(Exception):
    """입력 파일의 내용이 형식에 맞지 않는다. problems에 문제 목록을 담는다."""

    def __init__(self, path: Path, problems: list[str]):
        super().__init__(f"{path.name}: 형식 오류 {len(problems)}건")
        self.path = path
        self.problems = problems


def parse_date(text: str) -> date:
    """'2026-10-05' 모양의 문자열을 date로 바꾼다. 아니면 ValueError를 일으킨다."""
    try:
        day = date.fromisoformat(text)
    except ValueError:
        day = None
    if day is None or day.isoformat() != text:
        raise ValueError(f"날짜가 'YYYY-MM-DD' 모양이 아닙니다: {text!r}")
    return day


def parse_amount(text: str) -> int:
    """'12000'이나 '12,000'을 정수로 바꾼다. 형식에 맞지 않으면 ValueError를 일으킨다.

    쉼표는 천 단위 자리에만 올 수 있다. 앞에 '-'가 붙은 음수도 정수로 바꾼다.
    금액이 1 이상인지는 Transaction이 검사한다.
    """
    if not text:
        raise ValueError("금액이 비어 있습니다")
    negative = text.startswith("-")
    body = text[1:] if negative else text
    digits = body.replace(",", "")
    if not digits.isdecimal():
        raise ValueError(f"금액이 정수가 아닙니다: {text!r}")
    amount = int(digits)
    if "," in body and f"{amount:,}" != body:
        raise ValueError(f"금액의 쉼표 위치가 잘못되었습니다: {text!r}")
    return -amount if negative else amount


def parse_row(row: dict) -> Transaction:
    """DictReader가 읽은 한 줄을 Transaction으로 바꾼다.

    값이 형식이나 규칙에 맞지 않으면 ValueError를 일으킨다.
    """
    if None in row:
        raise ValueError("칸이 너무 많습니다")
    values = {}
    for name in FIELDNAMES:
        values[name] = (row[name] or "").strip()
    return Transaction(
        day=parse_date(values["date"]),
        kind=values["kind"],
        category=values["category"],
        memo=values["memo"],
        amount=parse_amount(values["amount"]),
    )


def load_transactions(path: Path) -> list[Transaction]:
    """CSV 파일에서 거래 목록을 읽어 파일에 적힌 순서대로 돌려준다.

    첫 줄만 있고 거래가 없으면 빈 리스트를 돌려준다.
    파일이 없으면 FileNotFoundError를 그대로 보낸다.
    빈 파일, UTF-8이 아닌 파일, 따옴표가 맞지 않는 등 CSV 형식이 깨진 파일,
    첫 줄이 다른 파일이면 DataFileError를 일으킨다.
    값이 맞지 않는 줄이 있으면 문제를 모두 모아 DataFileError 하나로 알린다.
    """
    with open(path, encoding="utf-8-sig", newline="") as f:
        reader = csv.DictReader(f, strict=True)
        try:
            fieldnames = reader.fieldnames
            rows = []
            for row in reader:
                rows.append((reader.line_num, row))
        except UnicodeDecodeError as e:
            raise DataFileError(
                path,
                [
                    "UTF-8로 읽을 수 없습니다. 엑셀에서는 'CSV UTF-8' 형식으로 저장하세요"
                ],
            ) from e
        except csv.Error as e:
            # 오류가 난 레코드는 마지막으로 다 읽은 줄(line_num)의 다음 줄에서 시작한다.
            raise DataFileError(
                path,
                [
                    f"{reader.line_num + 1}번째 줄 근처: CSV 형식이 깨졌습니다. "
                    "큰따옴표의 짝을 확인하세요"
                ],
            ) from e

    if fieldnames is None:
        raise DataFileError(path, ["파일이 비어 있습니다"])
    if fieldnames != FIELDNAMES:
        raise DataFileError(path, [f"첫 줄은 {','.join(FIELDNAMES)}여야 합니다"])

    transactions = []
    problems = []
    for line_no, row in rows:
        try:
            transactions.append(parse_row(row))
        except ValueError as e:
            problems.append(f"{line_no}번째 줄: {e}")
    if problems:
        raise DataFileError(path, problems)
    return transactions
```

함수 네 개와 예외 클래스 하나다. `import` 줄의 `Summary`는 10.2.6의 저장 함수에서 쓴다. 이 부분만 쓰고 저장하면 Ruff가 쓰지 않는 `import`로 보고 `Summary`를 지울 수 있다(1.2.5). 그러면 10.2.6에서 다시 더하면 된다.

아래에서부터 위로 쌓듯이, 작은 함수가 큰 함수의 부품이 된다.

```
load_transactions()   파일 전체: 열기, 첫 줄 검사, 줄마다 parse_row(), 문제 모으기
 └─ parse_row()        한 줄: 칸 수 검사, 공백 정리, Transaction 만들기
     ├─ parse_date()   문자열 → date
     ├─ parse_amount() 문자열 → int
     └─ Transaction()  가계부 규칙 검사 (models)
```

**`DataFileError` — 문제 목록을 담는 예외**

도서 대출 관리 프로그램의 `DataFileError`는 원인(`reason`) 하나를 담았다. 첫 오류에서 멈췄기 때문이다. 가계부 요약은 문제를 모두 모아 알리기로 했으므로(10.1.4), 문제의 **리스트**(`problems`)를 담는다. `str(e)`로 얻는 메시지는 `broken.csv: 형식 오류 9건`처럼 요약만 하고, 자세한 내용은 `e.problems`에서 꺼낸다. 어떻게 보여 줄지는 `cli`가 정한다.

**`parse_date()` — 문자열을 날짜로**

도서 대출 관리 프로그램의 `import_loans()`에서 쓴 방법과 같다(7장 실습 7-4의 힌트). `date.fromisoformat()`은 `'2026-02-30'`처럼 없는 날짜이거나 `'2026/10/03'`처럼 모양이 다르면 `ValueError`를 일으킨다. 그런데 파이썬 3.11부터는 `'20261005'` 같은 다른 ISO 8601 모양도 받아들이므로, 읽은 날짜를 다시 `isoformat()`으로 바꾼 결과가 원래 문자열과 같은지도 비교한다. 어느 경우든 같은 메시지로 바꾼다.

**`parse_amount()` — 문자열을 정수로**

쉼표를 지우고 `int()`에게 맡기면 될 것 같지만, 그러면 10.1.3에서 본 대로 `12,00`이 1200이 된다. 그래서 세 단계로 검사한다.

1. 앞의 `-`를 떼어 둔다. 음수는 여기서 거르지 않는다. `-32000`은 정수로는 올바르고, "1 이상이어야 한다"는 가계부의 규칙이므로 `Transaction`이 검사한다(10.1.5의 3번).
2. 쉼표를 지운 나머지가 숫자로만 되어 있는지 `isdecimal()`로 확인한다. `isdigit()`(2.3.5)과 비슷한 메서드인데, `²` 같은 위 첨자처럼 `int()`가 정수로 바꿀 수 없는 글자를 숫자로 보지 않는다. `int()`에게 바로 맡기지 않는 이유는 `int()`가 생각보다 너그럽기 때문이다. `int('1_000')`은 1000, `int(' 7 ')`은 7이다(파이썬은 숫자 사이의 밑줄과 앞뒤 공백을 허용한다). 숫자만 있다는 것을 먼저 확인했으므로 그다음의 `int()`는 실패하지 않는다. 그래서 `try`/`except`가 필요 없다.
3. 쉼표가 있었다면, 읽은 정수를 `f"{amount:,}"`(2.3.4)로 다시 쉼표를 넣은 모양으로 바꿔 원래 문자열과 비교한다. `12,000`은 `'12,000'`이 되어 같지만, `12,00`은 1200 → `'1,200'`이 되어 다르다. `parse_date()`에서 읽은 날짜를 다시 문자열로 바꿔 비교한 것과 같은 방법이다. **읽은 값을 표준 모양으로 되돌려 원래 글자와 비교하면**, 모양 규칙을 하나하나 검사하는 코드를 쓰지 않아도 된다.

빈 문자열은 맨 처음에 따로 검사해서 "비어 있다"는 더 정확한 메시지를 준다.

```python
>>> from ledger.storage import parse_amount
>>> parse_amount("2,800,000"), parse_amount("-3,000")
(2800000, -3000)
>>> parse_amount("12,00")
Traceback (most recent call last):
  ...
ValueError: 금액의 쉼표 위치가 잘못되었습니다: '12,00'
>>> parse_amount("1_000")
Traceback (most recent call last):
  ...
ValueError: 금액이 정수가 아닙니다: '1_000'
```

- **칸이 많으면** `DictReader`는 남는 값을 키 `None` 아래에 리스트로 모은다(`None: ['000']`). 금액 `45,000`이 쉼표에서 나뉘어 `amount`에는 `'45'`만 들어갔다. 이대로 두면 금액 45원으로 조용히 읽힌다. 그래서 `parse_row()`는 맨 먼저 `None in row`로 칸이 남았는지 검사한다.

마지막으로 `Transaction`을 키워드 인자로 만든다. 필드가 다섯 개나 되므로 위치 인자로 쓰면 순서를 헷갈리기 쉽다(4.2.2). `parse_date()`, `parse_amount()`, `Transaction`의 `__post_init__`이 일으킨 `ValueError`는 잡지 않고 그대로 보낸다. 이 함수는 한 줄만 보므로, 그 줄이 파일의 몇 번째 줄인지 모른다. 줄 번호를 붙이는 일은 파일 전체를 보는 `load_transactions()`의 몫이다.

**`load_transactions()` — 파일 전체**

도서 대출 관리 프로그램의 `load_books()`처럼 두 단계로 나뉜다.

첫 번째 단계는 **읽기만** 한다. 엑셀에서 'CSV UTF-8'로 저장한 파일은 맨 앞에 BOM이 붙으므로 `utf-8-sig`로 연다(7.3.3). `FileNotFoundError`는 잡지 않는다. 파일이 없을 때 이 함수가 할 수 있는 일은 없으므로 `cli`에 맡긴다. 그래서 `open()`은 `try` 바깥에 있다. `reader.line_num`으로 줄 번호를 함께 모아 둔다. 읽는 도중에 날 수 있는 예외는 두 가지이고, 둘 다 `DataFileError`로 바꾼다.

- **`UnicodeDecodeError`** — UTF-8이 아닌 파일이다(7.1.7).
- **`csv.Error`** — CSV의 문법이 깨졌다. 따옴표가 깨진 줄에서 이 예외가 나게 하려면 `DictReader`를 만들 때 `strict=True`를 주어야 한다.

`strict=True`가 없으면 어떻게 될까? `csv` 모듈은 기본 설정에서 문법이 깨진 줄도 최대한 읽어 내려고 한다. `bad_quote.csv`를 기본 설정으로 읽어 보자.

```python
>>> import csv
>>> with open("samples/bad_quote.csv", encoding="utf-8-sig", newline="") as f:
...     for row in csv.DictReader(f):
...         print(row["amount"])
...
2800000
95000
45000
```

`"9500"0`이 `95000`이 되었다. 오류는 나지 않고 금액만 열 배가 되었다. 마지막 줄에 닫는 따옴표를 빠뜨린 `"12000`도 오류 없이 `12000`으로 읽힌다. 10.1.4의 3번에서 정한 대로, 이런 파일은 읽지 말고 알려야 한다. `strict=True`를 주면 같은 파일에서 `csv.Error`가 난다(공식 문서의 `csv` 모듈 중 Dialect의 `strict` 항목).

`csv.Error`는 파일을 여는 순간이 아니라 `for row in reader:`로 줄을 읽어 나가는 도중에 난다. 그래서 `try` 블록이 읽는 반복문 전체를 감싼다. 이 예외가 나면 줄마다 모으지 않고 바로 멈춘다(10.1.4의 3번). 예외가 난 순간의 `reader.line_num`은 **마지막으로 다 읽은 줄**의 번호이고, 문제의 줄은 대개 그다음 줄이다. 그래서 `line_num + 1`을 알린다. 닫는 따옴표를 빠뜨려서 여러 줄이 한 칸으로 빨려 들어간 경우에는 정확한 줄을 짚기 어려우므로 "근처"라고 적었다.

두 번째 단계는 **검사**한다.

- 0바이트 파일이면 `DictReader`가 첫 줄을 읽지 못하므로 `fieldnames`가 `None`이다. 첫 줄만 있는 파일은 `fieldnames`가 올바르고 `rows`가 빈 리스트다. 10.1.4에서 구별하기로 한 두 경우가 여기서 갈린다.
- 첫 줄이 다르면 줄마다 검사할 필요도 없으므로 곧바로 알린다.
- 줄마다 `parse_row()`를 부르고, `ValueError`가 나면 메시지에 줄 번호를 붙여 `problems`에 모은 뒤 **다음 줄로 계속 간다.** `try` 블록에는 `parse_row()` 호출 한 줄만 있다. 넓게 감싸면 내 코드의 버그로 생긴 `ValueError`까지 "파일의 형식 오류"로 둔갑한다(6.1.7).
- 다 검사한 뒤 `problems`가 비어 있지 않으면 `DataFileError` 하나로 알린다. 잘못된 줄이 하나라도 있으면 거래 목록은 돌려주지 않는다. 일부만 돌려주면 그것으로 틀린 요약을 만들 수 있기 때문이다(10.1.4의 2번).

### 10.2.5 `core.py` — 요약 계산

```python
# ledger/core.py
"""거래 목록을 요약하는 계산.

파일도 화면도 모른다. models만 가져온다.
"""

from collections import defaultdict

from ledger.models import Summary, Transaction


def summarize(transactions: list[Transaction]) -> Summary:
    """거래 목록을 요약한 Summary를 돌려준다.

    지출은 분류별로 합쳐 금액이 큰 순(같으면 분류 이름 순)으로 정렬한다.
    거래가 하나도 없으면 ValueError를 일으킨다.
    빈 목록인지는 호출하는 쪽이 먼저 확인한다.
    """
    if not transactions:
        raise ValueError("요약할 거래가 없습니다")

    income = 0
    expense = 0
    by_category = defaultdict(int)  # {분류: 금액}
    for t in transactions:
        if t.kind == "수입":
            income += t.amount
        else:
            expense += t.amount
            by_category[t.category] += t.amount

    ranked = sorted(by_category.items(), key=lambda item: (-item[1], item[0]))
    first = min(transactions, key=lambda t: t.day)
    last = max(transactions, key=lambda t: t.day)
    return Summary(
        count=len(transactions),
        first_day=first.day,
        last_day=last.day,
        income=income,
        expense=expense,
        expense_by_category=ranked,
    )
```

- **`if not transactions:`** — 빈 목록이면 기간(`first_day`, `last_day`)을 정할 수 없다. 이것은 사용자의 실수가 아니라, 거래가 있는지 확인하지 않고 부른 쪽의 실수이므로 `ValueError`로 알린다(10.1.4의 6번). `Summary`의 날짜 필드를 `date | None`으로 해서 빈 목록도 받아들이는 방법도 있다. 하지만 그러면 `Summary`를 쓰는 모든 곳에서 "날짜가 `None`이면?"을 신경 써야 한다. 빈 경우를 입구에서 한 번 거르는 편이 단순하다.
- **`defaultdict(int)`** — 분류별 합계를 모은다. 처음 나온 분류도 `by_category[t.category]`가 0을 만들어 주므로 바로 더할 수 있다(8.2.4).
- **정렬** — `key`가 `(-금액, 분류)` 튜플이므로 금액이 큰 순, 금액이 같으면 분류 이름 순이다(4.5.5). 같은 금액의 분류가 파일 순서에 따라 뒤바뀌지 않게 하려고 두 번째 기준을 넣었다. 결과가 늘 같아야 시험하기 쉽다.
- **`min()`, `max()`의 `key`** — 날짜가 가장 이른 거래와 가장 늦은 거래를 찾는다(4.5.5). 파일이 날짜 순으로 적혀 있지 않아도 기간은 맞게 나온다.
- 이 모듈은 `models`만 가져온다. 파일(`csv`, `pathlib`)도 화면(`rich`)도 모른다. 그래서 셸에서 `Transaction`만 만들어 넘기면 시험할 수 있다.

**셸에서 확인하기**

계산기로 확인하기 쉽게 거래 네 건으로 시험한다. 날짜를 일부러 섞어 넣었다.

### 10.2.6 `storage.py` (2) — 요약 저장하기

`storage.py`의 맨 아래에 저장 함수를 더한다.

```python
# ledger/storage.py (이어서)
def write_summary(summary: Summary, path: Path) -> None:
    """지출 분류별 합계를 엑셀에서 열 수 있는 CSV 파일로 저장한다.

    열은 분류, 금액, 비율(%)이고 금액이 큰 순이다. 마지막 줄은 합계다.
    """
    path.parent.mkdir(parents=True, exist_ok=True)
    with open(path, "w", encoding="utf-8-sig", newline="") as f:
        writer = csv.writer(f)
        writer.writerow(["분류", "금액", "비율(%)"])
        for category, amount in summary.expense_by_category:
            writer.writerow([category, amount, f"{summary.share(amount):.1f}"])
        writer.writerow(
            ["합계", summary.expense, f"{summary.share(summary.expense):.1f}"]
        )
```

- 엑셀에서 한글이 깨지지 않도록 `utf-8-sig`, `csv` 모듈이 줄바꿈을 처리하도록 `newline=""`으로 연다(7.3.3).
- 금액은 쉼표 없는 정수로 쓴다. 쉼표와 `원`은 사람이 읽는 화면을 위한 것이다. 엑셀에서 숫자로 계산하려면 숫자만 있어야 한다. 비율은 `Summary.share()`로 계산하고 소수점 한 자리 문자열로 쓴다.
- 이 함수는 **어느 경로에 저장할지 정하지 않는다.** 받은 경로에 쓸 뿐이다. 폴더가 없으면 만든다(7.2.3). 지금은 입력 파일 옆에 저장하므로 폴더가 늘 있지만, 이 함수는 그것을 모른다. 나중에 `cli`가 `reports` 폴더에 저장하기로 바꿔도 이 함수는 고칠 것이 없다.

셸에서 10.2.5의 `summary`를 파일로 써 보고, 엑셀에서 열어 보자.

### 10.2.7 `cli.py`와 `main.py` — 화면과 흐름

이제 아래층을 모두 이어 프로그램을 완성한다.

```python
# ledger/cli.py
"""명령행에서 가계부 파일을 받아 요약을 보여 주고 저장하는 화면 쪽 코드.

프로그램의 시작점인 main()이 있다. rich를 가져오는 모듈은 이것 하나뿐이다.
"""

import sys
from pathlib import Path

from rich.console import Console
from rich.markup import escape
from rich.table import Table

from ledger.core import summarize
from ledger.models import Summary
from ledger.storage import DataFileError, load_transactions, write_summary

USAGE = "사용법: python main.py 가계부파일.csv"
MAX_PROBLEMS = 10  # 형식 오류를 화면에 몇 건까지 보여 줄지

console = Console()
error_console = Console(stderr=True)


def won(amount: int) -> str:
    """금액을 '1,234원' 모양으로 돌려준다."""
    return f"{amount:,}원"


def summary_path(path: Path) -> Path:
    """입력 파일 옆에 저장할 요약 파일의 경로를 돌려준다.

    samples/2026-10.csv → samples/2026-10_summary.csv
    """
    return path.with_name(f"{path.stem}_summary.csv")


def category_table(summary: Summary) -> Table:
    """지출 분류별 합계 표를 만든다. 출력은 하지 않는다."""
    table = Table(title="지출 분류별 합계")
    table.add_column("분류")
    table.add_column("금액", justify="right")
    table.add_column("비율", justify="right")
    for category, amount in summary.expense_by_category:
        table.add_row(escape(category), won(amount), f"{summary.share(amount):.1f}%")
    table.add_section()
    table.add_row(
        "합계",
        won(summary.expense),
        f"{summary.share(summary.expense):.1f}%",
        style="bold",
    )
    return table


def print_problems(error: DataFileError) -> None:
    """형식 오류를 표준 오류로 출력한다.

    MAX_PROBLEMS건이 넘으면 나머지는 개수만 알린다.
    """
    error_console.print(escape(str(error)), style="bold red")
    for problem in error.problems[:MAX_PROBLEMS]:
        error_console.print(f"  {escape(problem)}", style="red")
    rest = len(error.problems) - MAX_PROBLEMS
    if rest > 0:
        error_console.print(f"  ... 외 {rest}건", style="red")


def main() -> None:
    """명령행 인자로 받은 가계부 파일을 요약해 보여 주고, 요약 파일을 저장한다."""
    if len(sys.argv) != 2:
        print(USAGE, file=sys.stderr)
        sys.exit(2)
    path = Path(sys.argv[1])

    try:
        transactions = load_transactions(path)
    except FileNotFoundError:
        error_console.print(f"파일이 없습니다: {escape(str(path))}", style="red")
        sys.exit(1)
    except DataFileError as e:
        print_problems(e)
        error_console.print(
            "파일을 고친 뒤 다시 실행하세요. 요약 파일은 만들지 않았습니다."
        )
        sys.exit(1)

    if not transactions:
        console.print(f"거래 내역이 없습니다: {escape(str(path))}")
        return

    summary = summarize(transactions)
    console.print(f"가계부 요약: {escape(path.name)}", style="bold")
    console.print(
        f"기간: {summary.first_day} ~ {summary.last_day} (거래 {summary.count}건)"
    )
    console.print(f"수입: {won(summary.income)}")
    console.print(f"지출: {won(summary.expense)}")
    balance_style = "red" if summary.balance < 0 else None
    console.print(f"잔액: {won(summary.balance)}", style=balance_style)
    console.print(category_table(summary))

    out_path = summary_path(path)
    write_summary(summary, out_path)
    console.print(f"요약을 저장했습니다: {escape(str(out_path))}")
```

**모듈 수준의 이름들**

- `USAGE`, `MAX_PROBLEMS` — 바뀔 수 있는 문구와 숫자는 상수로 맨 위에 둔다.
- `console`, `error_console` — 9장처럼 `Console`을 모듈 수준에 만들어 두고 함께 쓴다. `error_console`은 `Console(stderr=True)`로 만들어 **표준 오류**로 출력한다. 9장에서는 `rich`로 표준 출력에만 썼다. 오류 메시지를 표준 오류로 보내면서 색도 입히는 방법을 `rich` 문서의 Console API 부분에서 찾은 것이다(9.3.2). 이처럼 필요한 기능은 문서에서 찾아 쓴다.

**작은 도우미 함수들**

- `won()` — 금액의 모양(`1,234원`)을 한 곳에서 정한다. 화면 여러 곳에서 쓴다.
- `summary_path()` — 결과 파일의 이름을 정한다(10.1.5의 4번). `with_name()`은 경로에서 파일 이름 부분만 바꾼 새 `Path`를 돌려준다. 7.2.2의 `with_suffix()`와 같은 무리의 메서드다. `stem`은 확장자를 뺀 이름이다.
- `category_table()` — 표를 **만들기만** 하고 출력하지 않는다. 9장 `loan_table()`과 같은 생각이다. `add_section()`은 표 안에 가로줄을 긋는다. 합계 줄을 위의 분류들과 나누려고 썼다. 분류 이름은 파일에서 온 데이터이므로 `escape()`로 감싼다(9장). 사용자가 분류를 `[여행]`처럼 적어도 그대로 보인다.
- `print_problems()` — 형식 오류가 많으면 앞의 `MAX_PROBLEMS`건만 보여 주고 나머지는 개수만 알린다. 1,000줄짜리 파일의 날짜 열이 통째로 잘못되었을 때 화면이 1,000줄의 오류로 덮이지 않게 하려는 것이다. 10건을 고치고 다시 실행하면 다음 오류가 보인다.

**`main()` — 흐름**

`main()`은 실패 표(10.1.4)를 코드로 옮긴 것이다. 위에서부터 읽으면 표의 줄이 차례로 나온다.

1. 인자가 하나가 아니면 사용법을 표준 오류로 출력하고 종료 코드 2로 끝낸다. 이 메시지는 색을 입힐 필요가 없어서 8장처럼 `print(..., file=sys.stderr)`를 썼다.
2. 파일을 읽는다. 사용자가 준 경로이므로 현재 디렉터리를 기준으로 한다(7.2.4). 파일이 없거나 형식 오류가 있으면 표준 오류로 알리고 종료 코드 1로 끝낸다. 형식 오류일 때는 **사용자가 할 일**과 **요약 파일을 만들지 않았다는 사실**을 마지막 줄에 알려 준다.
3. 거래가 0건이면 표준 출력으로 알리고 `return`한다. 함수가 끝나면 프로그램이 끝나고, 종료 코드는 0이다. 잘못이 아니므로 `sys.exit(1)`을 쓰지 않는다. `summarize()`를 부르기 전에 이 검사를 하므로, `summarize()`의 `ValueError`는 일어나지 않는다.
4. 요약을 계산해 보여 준다. 잔액이 음수이면 빨간색으로 보여 준다. `style=None`은 "스타일 없음"이다.
5. 요약을 저장하고, 어디에 저장했는지 알려 준다.

`sys.exit()`를 부르는 곳은 이 `main()`뿐이다. 아래층 모듈은 예외만 일으키고, 프로그램을 끝낼지는 흐름을 책임지는 `main()`이 정한다(8장).

**`main.py`**

9장 실습 9-4의 `main.py`와 같은 모양이다. `rich`가 없는 파이썬으로 실행하면 트레이스백 대신 원인과 해결 방법을 알려 준다.

```python

    print(f"실행한 파이썬: {sys.executable}", file=sys.stderr)

```

```python
}


def describe(path: Path) -> list[str]:
    """path를 읽고 요약한 결과를 비교하기 쉬운 문자열의 리스트로 돌려준다."""
    try:
        transactions = load_transactions(path)
    except DataFileError as e:
        return ["형식 오류"] + e.problems
    if not transactions:
        return ["거래 0건"]
    summary = summarize(transactions)
    lines = [
        f"거래 {summary.count}건",
        f"기간 {summary.first_day} ~ {summary.last_day}",
        f"수입 {summary.income}, 지출 {summary.expense}, 잔액 {summary.balance}",
    ]
    for category, amount in summary.expense_by_category:
        lines.append(f"지출 {category} {amount}")
    return lines


def main() -> None:
    failed = 0
    for name, expected in EXPECTED.items():
        actual = describe(SAMPLES_DIR / name)
        if actual == expected:
            print(f"[통과] {name}")
            continue
        failed += 1
        print(f"[실패] {name}")
        for line in expected:
            if line not in actual:
                print(f"  기대했는데 없다: {line}")
        for line in actual:
            if line not in expected:
                print(f"  기대하지 않았는데 있다: {line}")
        if sorted(actual) == sorted(expected):
            print("  줄은 같은데 순서가 다르다")
    print(f"{len(EXPECTED)}개 중 {len(EXPECTED) - failed}개 통과")
    if failed:
        sys.exit(1)


if __name__ == "__main__":
    main()
```

- `describe()`는 파일 하나를 읽고 요약한 결과를 **문자열의 리스트**로 바꾼다. 정상 파일이면 거래 수, 기간, 수입·지출·잔액, 분류별 지출을, 형식 오류가 있는 파일이면 문제마다 줄 번호와 원인을 한 줄씩 담는다. 결과를 이런 모양으로 바꿔 두면 `==` 하나로 비교할 수 있고, 다를 때 어느 줄이 다른지 보여 주기도 쉽다.
- `EXPECTED`에는 시험 파일마다 기대하는 줄들을 적었다. 10.1.3의 "기대하는 결과"와 시험 파일 표를 코드로 옮긴 것이다. 숫자는 10.2.2에서 **계산기로 직접 구한 값**이다. 프로그램이 출력한 숫자를 그대로 옮겨 적으면, 프로그램이 틀렸을 때 기대값도 함께 틀려서 아무것도 확인하지 못한다.
- `describe()`는 화면(`cli`)을 거치지 않고 `storage`와 `core`의 함수를 직접 부른다. 아래층을 따로 쓸 수 있게 나누어 둔 덕분이다. 그 대신 **이 스크립트는 화면 출력과 저장한 요약 파일을 확인하지 않는다.** 확인하는 범위를 독스트링 첫머리에 밝혀 두었다. 화면은 10.2.8의 실행 예와 눈으로 비교하고, 요약 파일은 엑셀로 열어 확인한다.
- 실패하면 기대했는데 없는 줄과 기대하지 않았는데 있는 줄을 보여 준다. 하나라도 실패하면 종료 코드 1로 끝낸다. 다른 프로그램이 이 스크립트를 실행해서 성공인지 실패인지 알 수 있다.

## 10.3 설명할 수 있는 코드

완료 기준 2는 "핵심 함수와 클래스가 각각 무슨 일을 하는지, 왜 그렇게 나눴는지 설명할 수 있다"이다. 돌아가는 코드를 만드는 것과 그 코드를 설명할 수 있는 것은 다른 능력이다. 설명할 수 없는 코드는 고칠 수도 없다. 기능을 하나 더하려고 할 때 어디를 고쳐야 할지, 고치면 무엇이 함께 영향을 받는지 모르기 때문이다. 이 절에서는 설명하는 방법을 세 가지 질문으로 나누어 연습하고, 그 결과를 설계 노트로 남긴다.

### 10.3.1 무슨 일을 하는가 — 한 문장으로

함수와 클래스마다 하는 일을 **한 문장**으로 말해 본다. 함수라면 "무엇을 받아서 무엇을 돌려준다(또는 무엇을 한다)", 클래스라면 "무엇을 나타낸다"의 모양이다.

| 이름 | 한 문장 |
|---|---|
| `Transaction` | 가계부 규칙에 맞는 거래 한 건을 나타낸다. |
| `Summary` | 거래 목록을 요약한 결과(기간, 수입, 지출, 분류별 지출)를 나타낸다. |
| `parse_row()` | CSV의 한 줄(딕셔너리)을 받아 `Transaction`을 돌려준다. |
| `load_transactions()` | CSV 파일 경로를 받아 `Transaction`의 리스트를 돌려준다. |
| `summarize()` | `Transaction`의 리스트를 받아 `Summary`를 돌려준다. |
| `write_summary()` | `Summary`를 받은 경로에 CSV 파일로 저장한다. |
| `category_table()` | `Summary`를 받아 지출 분류별 합계 표(`Table`)를 돌려준다. |

이 문장들은 각 함수의 독스트링 첫 줄과 거의 같다. 독스트링 첫 줄은 원래 이 한 문장을 쓰는 자리다(4.1.7). 그리고 표를 위에서 아래로 읽으면, 파일 하나가 요약이 되기까지의 흐름이 보인다. `load_transactions()`가 리스트를 만들고, `summarize()`가 그것을 `Summary`로 바꾸고, `category_table()`과 `write_summary()`가 그것을 보여 주고 저장한다.

한 문장으로 말하기 어려운 함수는 대개 **너무 많은 일을 하는** 함수다. "이 함수는 파일을 읽고, 그리고 합계를 내고, 그리고 표를 출력한다"처럼 "그리고"가 이어진다면 나눌 때가 된 것이다. 예외는 `main()` 같은 흐름 함수다. `main()`은 "명령행 인자로 받은 파일을 요약해 보여 주고 저장한다"인데, 실제로 하는 일은 다른 함수들을 차례로 부르는 것이다. **일을 직접 하지 않고 순서만 정하는** 함수는 "그리고"가 있어도 괜찮다.

### 10.3.2 왜 그렇게 나눴는가 — 고칠 이유로

"`core`는 계산, `storage`는 파일"이라고 말하는 것은 무엇을 나눴는지일 뿐, 왜 나눴는지는 아니다. 8.3.5에서 관심사를 나누는 기준은 **고칠 이유가 같은 코드끼리 모은다**는 것이었다. 그러니 "왜 나눴나"에는 "이런 변경이 생기면 여기만 고치면 되도록"이라고 답할 수 있어야 한다. 앞으로 생길 만한 변경을 떠올려 보고, 각각 어디를 고쳐야 하는지 표로 만들어 보자.

| 바뀌는 것 | 고칠 곳 | 고치지 않는 곳 |
|---|---|---|
| 금액을 `9500원`처럼 써도 받아들인다 | `storage.parse_amount()` | `models`, `core`, `cli` |
| 요약 파일을 `reports` 폴더에 저장한다 | `cli.summary_path()` | `storage.write_summary()` |
| 표 대신 막대그래프로 보여 준다 | `cli` | `models`, `core`, `storage` |
| 입력 파일로 JSON도 받는다 | `storage`에 읽기 함수를 더하고, `cli`가 확장자를 보고 고른다 | `models`, `core` |
| 같은 기능을 웹 화면으로 만든다 | 웹 화면용 모듈을 새로 만든다 | `models`, `core`, `storage` |
| 수입도 분류별로 보여 준다 | `models.Summary`, `core.summarize()`, `cli`, `storage.write_summary()` | (거의 모두 고친다) |

마지막 줄을 보자. 고칠 곳이 네 군데다. 나누기를 잘못한 것일까? 아니다. 이 변경은 **데이터의 모양**(`Summary`)을 바꾼다. 데이터의 모양이 바뀌면, 그 데이터를 만드는 곳(`core`)과 쓰는 곳(`cli`, `storage`)이 함께 바뀌는 것이 자연스럽다. 그래도 각 파일에서 고칠 곳은 분명하다. `core`에서는 계산만, `cli`에서는 표시만, `storage`에서는 저장만 고친다. 나누는 목적은 변경을 한 파일에 가두는 것이 아니라, **어디를 고쳐야 할지 바로 알 수 있게** 하는 것이다.

이런 표를 만들다 보면 숨어 있던 연결이 드러나기도 한다. 구분에 `이체`를 더한다고 해 보자. 구분으로 허용하는 값은 `models.KINDS`에 있으니 거기만 고치면 될 것 같다. 그런데 `core.summarize()`를 다시 보자.

```python
        if t.kind == "수입":
            income += t.amount
        else:
            expense += t.amount
            by_category[t.category] += t.amount
```

수입이 아니면 **모두 지출로** 센다. `KINDS`에 `이체`만 더하면 이체가 지출 합계에 조용히 들어간다. 오류는 나지 않고 숫자만 틀린다. 구분이 두 개뿐이라는 가정이 `else` 안에 숨어 있었던 것이다. 이런 연결을 찾아내는 것도 "설명할 수 있다"의 일부다. 찾았다면 `DESIGN.md`의 "한계"에 적어 두거나, `elif t.kind == "지출":`로 바꾸고 그 밖의 구분이면 `ValueError`를 일으키게 고쳐 둔다.

### 10.3.3 설계 노트 — `DESIGN.md`

10.1에서 쓴 설계 메모와 10.3.1, 10.3.2의 표를 프로젝트 폴더의 `DESIGN.md`로 정리한다. `README.md`가 **프로그램을 쓰는 사람**을 위한 문서라면, `DESIGN.md`는 **코드를 고칠 사람**을 위한 문서다. 다른 사람일 수도 있고, 석 달 뒤의 나일 수도 있다. 석 달 뒤의 나는 지금의 내가 왜 그렇게 정했는지 기억하지 못한다.

`DESIGN.md`에 꼭 넣을 것은 다음과 같다.

1. **목적과 범위** — 한 문단과 하지 않을 것(10.1.1).
2. **구조** — 모듈과 층, 의존 방향의 규칙(10.1.5).
3. **주요 클래스와 함수** — 한 문장 설명(10.3.1).
4. **실패 처리** — 원칙과 실패 표(10.1.4). `README.md`의 표와 겹치는 내용은 그쪽을 가리키기만 해도 된다.
5. **결정과 이유** — 무엇을 골랐고, 다른 어떤 방법이 있었으며, 왜 이것을 골랐는가.
6. **바뀔 때 고칠 곳** — 10.3.2의 표.
7. **한계** — 알고 있지만 아직 하지 않은 것, 알려진 문제.

가장 중요한 것은 5번이다. 코드를 읽으면 **무엇을** 했는지는 알 수 있다. 하지만 **왜** 그렇게 했는지, 다른 방법은 왜 고르지 않았는지는 코드에 없다. 그래서 적어 둔다. 적어 두지 않으면, 나중에 누군가(나 자신을 포함해서) "잘못된 줄은 그냥 건너뛰면 되지 않나?" 하고 고쳤다가 10.1.4에서 이미 따져 본 문제를 다시 만든다.

가계부 요약의 `DESIGN.md`는 다음과 같다.

````markdown
# 설계 노트 — 가계부 요약

## 목적과 범위

한 달 동안의 수입과 지출을 적은 CSV 파일을 받아 수입·지출·잔액과 지출 분류별 합계를
보여 주고, 분류별 합계를 CSV 파일로 저장한다. 잘못 적은 줄이 있으면 어느 줄이 왜
잘못되었는지 알려 주고 요약은 만들지 않는다.

하지 않는 것: 거래 추가·수정(파일은 엑셀이나 편집기로 고친다), 여러 달 비교, 예산,
그래프, 대화형 명령.

## 구조

| 층 | 모듈 | 하는 일 | 가져오는 것 |
|---|---|---|---|
| 3 | `main.py` | 시작. rich가 없을 때 안내 | cli |
| 2 | `ledger/cli.py` | 명령행 인자, 화면 출력, 결과 파일 이름, 종료 코드 | core, storage, models, rich |
| 1 | `ledger/core.py` | 요약 계산 | models |
| 1 | `ledger/storage.py` | CSV 읽기·검사·쓰기, DataFileError | models |
| 0 | `ledger/models.py` | 데이터의 모양과 가계부 규칙 | (없음) |

규칙
- 아래층은 위층을 가져오지 않는다. core와 storage는 서로를 가져오지 않는다.
- rich는 cli에서만 가져온다. core는 파일(csv, pathlib)과 화면을 모른다.
- sys.exit()는 cli.main()에서만 부른다. 아래층은 예외만 일으킨다.

## 주요 클래스와 함수

| 이름 | 하는 일 |
|---|---|
| `models.Transaction` | 가계부 규칙에 맞는 거래 한 건. 만들 때 자료형과 구분·분류·금액을 검사한다 |
| `models.Summary` | 요약 결과. 잔액(`balance`)과 비율(`share()`)을 계산해 준다 |
| `core.summarize()` | Transaction의 리스트 → Summary. 빈 리스트는 ValueError |
| `storage.load_transactions()` | CSV 경로 → Transaction의 리스트. CSV 문법 오류는 바로, 값 오류는 모두 모아 DataFileError |
| `storage.parse_row()` | CSV 한 줄 → Transaction. 칸 수, 날짜·금액 형식(쉼표 위치 포함)을 검사하고 공백을 정리 |
| `storage.write_summary()` | Summary를 받은 경로에 CSV로 저장 |
| `cli.main()` | 흐름: 인자 확인 → 읽기 → 요약 → 출력 → 저장. 실패하면 종료 코드 1·2 |

## 실패 처리

상황별 메시지와 종료 코드는 README.md의 "입력에 따른 동작" 표에 있다. 원칙은 다음과 같다.
- 결과는 표준 출력, 문제는 표준 오류로 보낸다.
- 값이 잘못된 줄이 있으면 모두 모아 줄 번호와 함께 알리고 멈춘다. 화면에는 앞의 10건
  (cli.MAX_PROBLEMS)과 나머지 건수를 보여 준다. 요약 파일은 쓰지 않는다.
- CSV 문법이 깨졌으면(큰따옴표의 짝) 그 자리에서 대략의 줄 번호와 함께 알리고 멈춘다.
- 프로그래머의 실수(예: summarize()에 빈 리스트)는 트레이스백으로 드러낸다.

## 결정과 이유

1. **수입·지출을 kind 열로 구분한다.** 대안은 지출을 음수로 쓰는 것. 손으로 쓰는
   파일에서는 `-`를 빠뜨리기 쉽고 빠뜨려도 티가 나지 않는다. 글자로 쓰면 오타가 검사에 걸린다.
2. **잘못된 줄은 모두 모아 알리고 멈춘다.** 첫 오류에서 멈추면 잘못이 여러 개일 때 여러 번
   실행해야 한다. 건너뛰면 합계가 조용히 틀린다. 요약에서 틀린 합계는 합계가 없는 것보다 나쁘다.
3. **CSV 문법 오류는 줄마다 모으지 않고 그 자리에서 멈춘다.** DictReader에 strict=True를
   준다. 기본 설정은 `"9500"0`을 95000으로 읽는 등 깨진 줄도 조용히 읽어 낸다. 따옴표가
   깨지면 어디서 칸이 나뉘는지 알 수 없으므로, 그 뒤를 계속 검사해도 믿을 수 없다.
4. **금액의 쉼표는 세 자리마다만 허용한다.** 쉼표만 지우고 int()에 넘기면 `12,00`이
   1200이 된다. 읽은 정수를 다시 쉼표 넣은 모양으로 바꿔 원문과 비교한다.
5. **0바이트 파일은 오류, 첫 줄만 있는 파일은 정상(거래 0건)이다.** 첫 줄만 있는 파일은
   올바른 형식의 빈 가계부이고, 0바이트 파일은 엉뚱한 파일이거나 망가진 파일일 가능성이 높다.
6. **검사를 두 곳에 나눈다.** 문자열 → 값(날짜·정수 형식, 칸 수)과 공백 정리는 파일에 관한
   지식이므로 storage가, 값이 규칙에 맞는지(자료형, 구분, 분류, 금액 ≥ 1)는
   Transaction.__post_init__이 한다. 타입 힌트는 실행 중에 검사되지 않으므로 자료형도 직접
   검사한다. 입력이 CSV가 아니게 되어도 규칙 검사는 그대로 쓸 수 있다. 단, 공백 정리 같은
   값 다듬기는 Transaction이 하지 않으므로 새 입구를 만들면 거기서도 해야 한다.
7. **요약은 함수(summarize)로 만든다.** 상태가 없고 한 번 계산하면 끝나는 일이다. 클래스로
   감쌀 이유가 없다.
8. **errors.py를 두지 않는다.** 예외가 DataFileError 하나이고 storage만 일으킨다.
9. **결과 파일은 입력 파일 옆에 `이름_summary.csv`로 저장하고, 이름은 cli가 정한다.**
   storage.write_summary()는 받은 경로에 쓰기만 한다.
10. **실행 방법은 `python main.py 파일` 하나다.** `python -m ledger`는 필요해지면 더한다.

## 바뀔 때 고칠 곳

| 바뀌는 것 | 고칠 곳 |
|---|---|
| 금액에 `원`을 붙여 써도 받는다 | storage.parse_amount() |
| 요약 파일을 reports 폴더에 저장 | cli.summary_path() |
| 표 대신 그래프 | cli |
| JSON 입력도 받는다 | storage(읽기 함수 추가), cli(고르기) |
| 수입도 분류별로 | models.Summary, core.summarize(), cli, storage.write_summary() |
| 구분에 '이체'를 더한다 | models.KINDS, core.summarize() (아래 한계 1 참고) |

## 한계

1. core.summarize()는 수입이 아니면 모두 지출로 센다. KINDS에 구분을 더할 때는
   summarize()도 함께 고쳐야 한다.
2. 파일 대신 폴더를 넘기면 트레이스백이 난다(macOS IsADirectoryError, Windows PermissionError).
3. 지출이 없는 파일이면 분류별 표에 합계 줄(0원, 0.0%)만 보인다.
4. check_samples.py는 storage와 core의 결과만 비교한다. 화면 출력과 요약 파일은 확인하지 않는다.
````

이 노트는 실습 10-2의 "확인할 것"을 하기 **전**의 상태다. 한계 2, 3은 "확인할 것"에서 다루는 문제이고, 여러분이 결정하고 고쳤다면 한계에서 빼고 "결정과 이유"에 적는다.

> **문서는 짧아도 된다**
> `DESIGN.md`가 길 필요는 없다. 위의 예도 화면 두 장 정도다. 문장을 다듬는 것보다 **결정과 이유를 빠짐없이 적는 것**이 중요하다. 그리고 코드를 고칠 때 함께 고친다. 코드와 맞지 않는 문서는 없는 문서보다 나쁘다. 결정을 바꿀 때는 지난 결정을 지우지 말고 "처음에는 A로 했으나 이런 문제가 있어 B로 바꿨다"처럼 남겨 두면 더 좋다.

### 10.3.4 말로 설명해 보기

글로 정리했으면 이번에는 **말로** 설명해 본다. 동료나 강사 앞에서 5분 동안, 코드를 화면에 띄워 놓고 설명한다. 함께 볼 사람이 없으면 혼자 소리 내어 설명하며 녹음해도 된다. 글로 쓸 때는 넘어갔던 부분이 말로 하면 막힌다. 막힌 곳이 아직 이해하지 못한 곳이다.

1. 이 프로그램은 무엇을 하고, 무엇을 하지 않는가?
2. 파일 하나가 들어와서 요약 파일이 저장되기까지, 어떤 함수가 어떤 순서로 불리는가?
3. `parse_row()`의 검사와 `Transaction.__post_init__`의 검사는 무엇이 다른가? 왜 나눴나?
4. `core.py`에 `import csv`가 없는 이유는 무엇인가? 있으면 무엇이 나빠지는가?
5. `summarize()`를 클래스가 아니라 함수로 만든 이유는?
6. 잘못된 줄을 건너뛰지 않고 멈추는 이유는? 건너뛰는 편이 나은 프로그램의 예를 들어라.
7. 0바이트 파일과 첫 줄만 있는 파일을 다르게 처리하는 이유는?

AI를 면접관으로 쓸 수도 있다. 코드와 `DESIGN.md`를 주고 "이 코드를 쓴 사람이 설계를 이해했는지 확인하는 질문을 하나씩 해 줘. 내 답을 듣고 부족한 점을 짚어 줘"라고 부탁한다. 다만 질문은 AI가 하더라도 **답은 내가 한다.** 답을 AI에게 물어보는 순간 연습이 아니게 된다.

## 10.4 새 환경에서 똑같이 실행하기

완료 기준 3은 "새 가상환경에서 `requirements.txt`로 의존성을 복원하고 동일하게 실행할 수 있다"이다. 9장에서 배운 것을 이번에는 **프로젝트를 넘겨주는 시험**으로 해 본다.

### 10.4.1 "내 컴퓨터에서는 되는데"

내 컴퓨터에서 잘 돌던 프로그램이 다른 컴퓨터에서 돌지 않는 이유는 대개 프로그램이 **적어 두지 않은 무언가에 기대고 있기** 때문이다. 내 컴퓨터에는 그것이 있어서 문제가 드러나지 않는다.

| 기대고 있는 것 | 예 | 막는 방법 |
|---|---|---|
| `requirements.txt`에 없는 패키지 | 가상환경에 나중에 설치하고 `pip freeze`를 다시 하지 않았다 | 설치할 때마다 바로 `freeze`(9.1.7) |
| 코드 안의 절대 경로 | `Path("/Users/jinyoung/python-lab/ch10/...")` | `Path(__file__)` 기준이나 명령행 인자(7.2.4) |
| 프로젝트 밖의 파일 | `../ch08/data/books.csv`를 읽는다 | 필요한 파일은 프로젝트 안에 둔다 |
| 실행 위치 | 프로젝트 폴더에서 실행해야만 시험 파일을 찾는다 | `Path(__file__)` 기준(`check_samples.py`의 `SAMPLES_DIR`) |
| Git에 올리지 않는 파일 | 시험할 때 `data/` 안의 내 가계부를 쓴다 | 시험 파일은 `samples/`에, 올리는 곳에 둔다 |
| 파이썬 버전 | 3.13에서만 되는 기능을 썼는데 받는 사람은 3.10 | `README.md`에 확인한 버전을 적는다(9.1.7) |
| 환경 변수 | API 키를 환경 변수로 읽는다 | `README.md`에 무엇을 설정해야 하는지 적는다(8.2.1) |

이것들은 내 컴퓨터에서 아무리 실행해 봐도 찾을 수 없다. **다른 환경을 만들어 실행해 봐야** 드러난다.

### 10.4.2 복원 시험

두 단계로 시험한다.

**A. 제자리에서 가상환경 다시 만들기**

9.1.7에서 한 것과 같다. 가상환경을 끄고, 지우고, 다시 만들어 `requirements.txt`로 복원한다.

```
# macOS
deactivate
rm -rf .venv
python3 -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements.txt

# Windows
deactivate
Remove-Item -Recurse -Force .venv
python -m venv .venv
.venv\Scripts\Activate.ps1
python -m pip install -r requirements.txt
```

그다음 세 가지를 확인한다.

1. `python -m pip freeze`의 결과가 `requirements.txt`와 같다.
2. `python check_samples.py`가 모두 통과한다.
3. `python main.py samples/2026-10.csv`의 출력이 10.2.8과 같다.

1번을 눈으로 비교하기 어려우면 `python -m pip freeze > after.txt`로 저장한 뒤, VS Code 탐색기에서 `requirements.txt`를 오른쪽 클릭해 "비교를 위해 선택(Select for Compare)"을 고르고, `after.txt`를 오른쪽 클릭해 "선택한 항목과 비교(Compare with Selected)"를 고른다. 두 파일이 나란히 열리고 다른 줄이 색으로 표시된다. 확인했으면 `after.txt`는 지운다.

**B. 다른 위치에 옮겨서 `README.md`만 보고 실행하기**

A는 같은 폴더에서 하므로, 프로젝트 밖의 파일이나 절대 경로에 기대는 문제를 찾지 못한다. 그래서 프로젝트를 **다른 위치에 복사**해서, 처음 받은 사람처럼 `README.md`만 보고 따라 해 본다.

그런데 복사만 해서는 부족하다. 원래 폴더가 그대로 있으면, 복사본의 코드가 `/Users/본인계정/python-lab/ch10/ledger_app/samples`처럼 **원래 폴더를 가리키는 절대 경로**를 쓰고 있어도 그 경로에 파일이 있으니 문제없이 돌아간다. 시험은 통과하는데 다른 컴퓨터에서는 실패하는 것이다. 그래서 시험하는 동안 **원래 폴더의 이름을 잠시 바꿔 둔다.** 원래 경로에 기대는 코드가 있으면 바로 실패한다.

원래 프로젝트를 연 VS Code 창을 닫고, 원래 프로젝트의 가상환경을 끈 뒤 시작한다. (Windows에서는 열려 있는 창이나 터미널이 그 폴더를 쓰고 있으면 이름을 바꿀 수 없다.)

```
# macOS
deactivate
cd ~/python-lab/ch10
mkdir restore_test
cp -R ledger_app restore_test/
mv ledger_app ledger_app_orig
cd restore_test/ledger_app
rm -rf .venv

# Windows
deactivate
cd ~\python-lab\ch10
mkdir restore_test
Copy-Item -Recurse ledger_app restore_test\
Rename-Item ledger_app ledger_app_orig
cd restore_test\ledger_app
Remove-Item -Recurse -Force .venv
```

`cp -R`과 `Copy-Item -Recurse`는 폴더를 안의 내용까지 복사한다. `mv`와 `Rename-Item`은 이름을 바꾼다. 복사된 `.venv`는 원래 위치에 묶여 있으므로(9.1.8) 지운다. 이제 `restore_test/ledger_app`에는 다른 사람에게 넘겨줄 것만 남았고, 원래 폴더는 다른 이름 뒤에 숨었다. 여기서부터는 **`README.md`에 적힌 명령만** 입력한다. 적혀 있지 않은 명령을 입력해야 했다면 그것은 `README.md`에 빠진 내용이다. 복원한 뒤 A의 세 가지를 똑같이 확인한다.

확인이 끝나면 원래 폴더의 이름을 되돌린다.

```
# macOS
cd ~/python-lab/ch10
mv ledger_app_orig ledger_app

# Windows
cd ~\python-lab\ch10
Rename-Item ledger_app_orig ledger_app
```

B가 찾을 수 있는 것에도 한계가 있다. 원래 폴더가 아닌 다른 곳(예: `~/Documents`의 파일)을 가리키는 절대 경로는 이 컴퓨터에서는 여전히 그 파일이 있으므로 드러나지 않는다. 같은 파이썬, 같은 운영체제라는 조건도 그대로다.

더 확실하게 하려면 **다른 사람의 컴퓨터**에서 해 본다. 운영체제가 다르면 더 좋다. macOS에서 만든 프로젝트를 Windows에서 실행해 보면 경로나 명령의 차이로 생기는 문제가 드러난다. 폴더를 압축해서 보낼 때는 `.venv`를 빼고 보낸다. Git을 쓸 줄 안다면 저장소에 올리고 받는 사람이 내려받게 하면, `.gitignore`가 제대로 되어 있는지까지 함께 확인된다(Git은 다음 항목인 "개발 도구"에서 다룬다).

`restore_test` 폴더는 원래 폴더의 이름을 되돌린 뒤에 지운다. 지우기 전에 경로를 두 번 확인하자.

## 실습 10-4. 종합 실습 — 나만의 명령행 프로그램

이제 혼자 해 본다. 주제를 하나 골라 **10.1의 설계부터 10.4의 복원 시험까지** 같은 과정을 거쳐 프로그램을 만든다. 가계부 요약이 정답 모양은 아니다. 주제가 다르면 결정도 달라진다. 중요한 것은 결정을 **스스로 내리고, 이유와 함께 남기는 것**이다.

### 주제 고르기

네 가지 중 하나를 고른다. A와 B는 요구 사항이 정해져 있어 시작하기 쉽고, C는 예제를 넓히는 것이고, D는 주제부터 스스로 정한다.

**A. 할 일 관리** (`todo_app`)

JSON 파일에 저장된 할 일 목록을 명령행 인자로 보고, 더하고, 완료하고, 지운다. 7.3.7의 `todo_store.py`를 프로젝트로 키우는 것이다.

```
python main.py 목록
python main.py 추가 "보고서 쓰기" 2026-11-20
python main.py 추가 "책 반납"
python main.py 완료 2
python main.py 삭제 3
python main.py 내보내기 todos.csv
```

- 저장 파일은 프로젝트의 `data/todos.json`이다(`Path(__file__)` 기준). 환경 변수 `TODO_FILE`이 있으면 그 파일을 쓴다(8.2.1). 시험 파일로 바꿔 가며 실행하기 위해서다.
- 할 일마다 번호, 제목, 기한(없어도 된다), 완료 여부가 있다. 번호는 지워도 다른 할 일의 번호가 바뀌지 않는다. 새 번호는 지금 있는 가장 큰 번호 + 1이다.
- `목록`은 `rich` 표로 보여 준다. 완료하지 않은 일을 먼저, 기한이 빠른 순으로 보여 주고(기한이 없는 일은 뒤로), 기한이 지난 일은 빨간색, 완료한 일은 흐리게(`style="dim"`) 보여 준다.
- `내보내기`는 할 일 목록을 엑셀에서 열 수 있는 CSV 파일로 저장한다.
- 처리할 입력: 저장 파일이 없을 때(첫 실행이므로 빈 목록으로 시작한다), 0바이트 파일, `[]`만 있는 파일, JSON 문법 오류(줄 번호와 함께), 구조 오류(리스트가 아님, 항목에 키가 없음, 기한 모양이 틀림, 완료 여부가 `true`/`false`가 아님, 번호가 겹침 — 몇 번째 항목인지와 함께 모두), 명령행 입력 오류(모르는 명령, 인자 개수, 기한 모양, 정수가 아닌 번호 — 종료 코드 2), 없는 번호(종료 코드 1).
- 저장 파일을 제대로 읽지 못했으면 어떤 명령도 파일을 저장하지 않는다. 0바이트 파일은 저장하다가 망가진 파일일 수 있으므로, 빈 목록으로 보고 덮어쓰면 안 된다.
- 오늘 날짜는 `cli`에서만 `date.today()`로 얻고, 계산하는 함수에는 인자로 넘긴다. 날짜를 바꿔 가며 시험하기 쉽다.

**B. 단어 빈도 분석** (`wordfreq_app`)

텍스트 파일을 읽어 많이 나온 단어를 보여 주고, 단어별 횟수를 CSV 파일로 저장한다. 8장 실습 8-2의 `word_freq.py`를 프로젝트로 키우는 것이다.

```
python main.py samples/speech.txt
python main.py samples/speech.txt 5
```

- 화면에는 파일 이름, 전체 단어 수, 서로 다른 단어 수, 상위 N개(기본 10개)를 `rich` 표(순위, 단어, 횟수, 비율)로 보여 준다.
- 입력 파일 옆에 `파일이름_words.csv`로 모든 단어와 횟수를 저장한다. 횟수가 많은 순, 같으면 단어 순이다.
- 단어는 소문자로 바꾸고, 앞뒤의 문장부호를 지운다(`"Python,"` → `python`). 문장부호를 지우고 아무것도 남지 않으면 단어가 아니다.
- 프로젝트의 `stopwords.txt`에 적힌 단어(불용어. `the`, `is`처럼 너무 흔해서 세지 않을 단어)는 세지 않는다. 한 줄에 단어 하나, `#`으로 시작하는 줄과 빈 줄은 무시한다. 파일이 없으면 불용어 없이 센다.
- 처리할 입력: 0바이트 파일과 공백·문장부호만 있는 파일(단어 0개. 오류로 볼지 정상으로 볼지 정하고 이유를 적는다), UTF-8이 아닌 파일(이미지 파일을 넣어 보는 것도 포함), 없는 파일, 개수가 정수가 아니거나 1보다 작을 때(종료 코드 2), 불용어 파일에 공백이 든 줄이 있을 때(단어가 아니므로 줄 번호와 함께 모두 알린다).
- 큰 파일도 다룰 수 있도록 한 줄씩 읽는다(7.1.6).
- 한국어 문장에서는 `파이썬은`과 `파이썬을`이 다른 단어로 세어진다. 조사를 떼어 내는 일(형태소 분석)은 이 과정의 범위를 넘으므로, 그대로 두고 `DESIGN.md`의 한계에 적는다.

**C. 가계부 넓히기** (`ledger2_app`)

10.1.1에서 "하지 않을 것"으로 미뤄 둔 기능을 더한다. `ledger_app`을 복사해서 시작한다(복사한 뒤 `.venv`는 지우고 새로 만든다).

```
python main.py samples/2026-09.csv samples/2026-10.csv
```

- 파일을 여러 개 받아 파일별(달별) 수입·지출·잔액을 비교하는 표와, 전체 기간의 지출 분류별 합계를 보여 준다.
- 프로젝트의 `budget.csv`(`category,limit`)가 있으면 분류별 한 달 예산 대비 사용률을 보여 주고, 예산을 넘은 분류는 빨간색으로 보여 준다. 없으면 예산 없이 보여 준다.
- 요약은 수입, 지출, 잔액, 분류별 합계, 예산 초과 분류를 모두 담은 JSON 파일로 저장한다. 파일 이름과 위치는 스스로 정한다.
- 처리할 입력: 예제의 모든 경우에 더해, 여러 파일 중 하나만 잘못된 경우(모두 멈출지, 그 파일만 뺄지 정하고 이유를 적는다), 같은 파일을 두 번 넘긴 경우, 예산 파일의 오류(분류가 겹침, 한도가 정수가 아니거나 0 이하), 0바이트 예산 파일.
- `DESIGN.md`에 10.3.3의 예제와 **달라진 결정**을 적는다. `core`, `storage`, `cli`가 각각 어떻게 바뀌었는지, 층 구조는 그대로인지 설명한다.

**D. 자유 주제**

다음 조건을 채우는 주제를 스스로 정한다.

- 파일(CSV, JSON, JSONL, 텍스트 중 하나 이상)에서 데이터를 읽는다.
- 읽은 데이터를 가공해서 화면에 보여 주고, 결과를 파일로 저장한다.
- 사람이 손으로 쓰거나 다른 프로그램이 만든 입력이라서, 잘못된 형식이 들어올 수 있다.

예를 들면 독서 기록 통계(읽은 책 CSV → 월별 권수, 분야별 비율), 운동 기록(날짜별 운동 CSV → 주별 합계, 목표 달성 여부), 대화 기록 통계(7.3.8의 JSONL → 사람별 메시지 수, 시간대별 분포), 프롬프트 만들기(CSV의 줄마다 템플릿 텍스트의 빈칸을 채워 프롬프트 파일을 여러 개 만든다. 이후 LLM 과정에서 자주 하는 일이다) 같은 것이다. 시작하기 전에 10.1의 설계 메모를 강사나 동료에게 보여 주고, 범위가 알맞은지 함께 살펴보자.

### 공통 요구 사항

어느 주제를 고르든 다음을 지킨다.

1. **프로젝트 구조** — `ch10` 안에 프로젝트 폴더를 만들고, 다음을 갖춘다. 모듈 이름은 바꿔도 되지만, 데이터·계산·파일·화면의 역할은 서로 다른 모듈에 있어야 한다.
   ```
   프로젝트폴더/
   ├── .gitignore
   ├── README.md
   ├── DESIGN.md
   ├── requirements.txt
   ├── main.py
   ├── check_samples.py
   ├── samples/
   └── 패키지/
       ├── __init__.py
       ├── models.py
       ├── core.py
       ├── storage.py
       └── cli.py
   ```
2. **함수와 클래스** — 데이터 클래스를 하나 이상, 사용자 정의 예외를 하나 이상 만든다. 일반 클래스는 필요할 때만 만든다(10.1.5의 2번). 모든 함수와 클래스에 독스트링을 단다.
3. **외부 패키지** — PyPI의 패키지를 하나 이상 쓰고 `requirements.txt`로 관리한다. 기본은 `rich`다. 다른 패키지를 쓴다면 왜 그 패키지가 필요한지 `DESIGN.md`에 적는다(9.3.4).
4. **의존 방향** — 층 그림을 그리고 지킨다. 화면을 그리는 외부 패키지는 `cli`에서만 가져온다. `core`는 파일과 화면을 모른다(`csv`, `json`, `pathlib`, `rich`를 가져오지 않는다). `sys.exit()`는 `cli`의 흐름 함수에서만 부른다.
5. **시험 파일** — 정상 파일, 빈 파일(두 종류를 구별한다면 둘 다), 잘못된 형식의 파일을 만든다. 잘못된 형식의 파일에는 한 줄(한 항목)에 한 가지씩, 서로 다른 잘못을 다섯 가지 이상 넣는다. CSV나 JSON이라면 문법 자체가 깨진 파일도 따로 만든다. `check_samples.py`에 시험 파일마다 기대하는 결과를 적고, 모두 통과해야 한다. 기대하는 결과에는 건수만이 아니라 **계산 결과**(합계 등)와 **오류의 위치와 원인**을 넣는다. 기대값은 프로그램의 출력이 아니라 손으로 계산한 값이다. 이 스크립트가 확인하지 않는 것(화면 출력 등)은 독스트링에 밝힌다.
6. **메시지와 종료 코드** — 문제는 무엇이 잘못되었고 사용자가 무엇을 하면 되는지 알려 준다. 문제는 표준 오류로, 결과는 표준 출력으로 보낸다. 종료 코드는 0(성공), 1(실패), 2(사용법)를 쓴다. 상황별 동작을 `README.md`에 표로 적는다.
7. **덮어쓰지 않기** — 입력을 제대로 읽지 못했으면 결과 파일이나 저장 파일을 쓰지 않는다.
8. **문서** — `README.md`에는 프로그램 소개, 확인한 파이썬 버전, 설치(macOS, Windows), 실행 방법, 입력 형식, 입력에 따른 동작을 적는다. `DESIGN.md`는 10.3.3의 일곱 가지 항목으로 쓴다.

다 만들었으면 하나씩 확인한다. 모두 체크되어야 완료다.

**1. 정상 파일, 빈 파일, 잘못된 형식의 입력을 각각 처리하고 적절한 메시지를 출력한다**

- [ ] `samples`에 정상, 빈, 잘못된 형식의 시험 파일이 있고, `python check_samples.py`가 모두 통과한다. 정상 파일의 계산 결과 하나를 일부러 틀리게 바꾸면 `check_samples.py`가 실패한다.
- [ ] 잘못된 형식의 파일로 실행하면 문제가 있는 곳(줄 번호나 항목 번호)과 원인이 나온다. 화면에 일부만 보여 준다면 나머지가 몇 건인지 알려 준다.

- [ ] 사용자가 트레이스백을 보는 경우는 프로그래머의 실수뿐이다(일부러 그렇게 정하고 `DESIGN.md`에 적은 경우는 제외).

**2. 핵심 함수와 클래스가 각각 무슨 일을 하는지, 왜 그렇게 나눴는지 설명할 수 있다**

- [ ] `DESIGN.md`의 "결정과 이유"에 다른 방법과 고르지 않은 이유가 함께 적힌 결정이 다섯 개 이상 있다.

- [ ] 10.3.4와 같은 질문(내 프로그램에 맞게 바꾼 것)에 코드를 보지 않고 답할 수 있다. 동료나 강사 앞에서 5분 동안 설명해 본다.

**3. 새 가상환경에서 `requirements.txt`로 의존성을 복원하고 동일하게 실행할 수 있다**

- [ ] `python -m pip freeze`의 결과가 `requirements.txt`와 같다.
- [ ] 10.4.2의 B대로 다른 위치에 복사해 `.venv`를 지우고, **원래 폴더의 이름을 바꿔 둔 상태에서** `README.md`에 적힌 명령만으로 복원해서 `check_samples.py`가 통과하고 같은 결과가 나온다.
- [ ] `README.md`에 확인한 파이썬 버전이 있다.

### 진행 순서와 힌트

1. **설계 메모부터** — 실습 10-1처럼 한 문단, 하지 않을 것, 실행 예, 형식 표, 시험 파일 표, 실패 표, 역할 표를 쓴다. 이 단계에 전체 시간의 4분의 1을 써도 아깝지 않다.

3. **아래층부터, 셸에서 확인하며** — 10.1.6의 순서대로 만든다. 한 번에 한 층씩.
4. **범위를 지킨다** — 만들다가 떠오른 기능은 `DESIGN.md`의 한계나 "다음에 할 일"에 적어 두고 넘어간다. 필수 요구 사항을 모두 채운 뒤에 더한다.
5. **예제 코드는 참고만** — 도서 대출 관리 프로그램과 가계부 요약의 코드를 참고해도 된다. 하지만 옮겨 붙인 코드는 줄마다 왜 있는지 설명할 수 있어야 한다. 설명할 수 없으면 지우고 다시 쓴다.
6. **AI는 10.1.7처럼** — 설계를 주고 한 모듈씩 맡기거나, 내가 쓴 코드의 검토를 부탁한다. 받은 코드는 설계와 시험 파일로 확인하고, `DESIGN.md`는 내 말로 쓴다. AI가 쓴 부분이 있다면 `DESIGN.md`에 어느 부분인지 적어 두자. 숨길 일이 아니라, 나중에 코드를 볼 사람(나를 포함해)에게 쓸모 있는 정보다.
7. **막히면 시간을 정한다** — 한 문제로 30분 넘게 막혀 있다면 지금까지 시도한 것과 오류 메시지를 정리해서 질문한다. 정리하다가 답이 보이는 경우도 많다.
8. **마지막은 복원 시험** — 다 만들었다고 생각한 뒤에 10.4.2의 B를 한다. 여기서 문제가 나오는 경우가 생각보다 많다.

## 선택 활동 — 1단계 결과물 다시 읽기

1단계 바이브 코딩에서 만든 결과물이 파이썬으로 작성되었다면, 그 코드를 다시 읽고 당시 이해하지 못했던 부분을 정리한다. 이 과정을 마친 지금, 그때와 무엇이 달라졌는지 직접 확인하는 활동이다.

**1) 다시 실행하기**

먼저 9장에서 배운 대로 실행 환경을 갖춘다. 프로젝트를 `ch10/stage1_review` 같은 곳에 복사하고, 전용 가상환경을 만든다. `requirements.txt`가 있으면 그것으로 설치하고, 없으면 `import` 줄을 보고 필요한 패키지를 찾아 설치한 뒤 `requirements.txt`를 만든다. 실행이 되는가? 안 된다면 9.2.6의 순서로 원인을 찾는다. 실행하는 데 성공했다면, 그것만으로도 1단계 때는 못 했을 일을 한 것이다.

**2) 지도 그리기**

코드를 처음부터 한 줄씩 읽지 않는다. 먼저 전체 모양을 본다.

- `README.md`와 `requirements.txt`를 읽고, 어떤 외부 패키지를 쓰는지 본다. 처음 보는 패키지는 PyPI에서 무엇을 하는 패키지인지 확인한다(9.3.1).
- 시작 파일을 찾는다. `if __name__ == "__main__":`이 있는 파일, 또는 `README.md`의 실행 명령에 나오는 파일이다(8.1.5).
- 파일마다 맨 위의 `import` 줄만 읽고, 8.3.5처럼 어느 파일이 어느 파일을 가져오는지 층 그림을 그린다. 의존 방향이 한쪽으로 정해져 있는가? 화면, 계산, 파일 읽기가 나뉘어 있는가, 한 파일에 섞여 있는가?

**3) 흐름 하나 따라가기**

기능 하나를 골라, 사용자가 입력한 순간부터 결과가 나오기까지를 따라간다. 시작 파일에 중단점을 걸고 디버거로 한 줄씩 들어가면 좋다(4.1.8, 6.1.11). 변수 창에서 데이터가 어떤 모양(리스트, 딕셔너리, 객체)으로 바뀌어 가는지 본다.

**4) 모르는 것 정리하기**

읽다가 이해하지 못한 곳을 표로 정리한다. `stage1_review/REVIEW.md`에 쓴다.

| 위치 | 코드 | 그때 몰랐던 것 | 지금 이해한 것 | 관련된 곳 |
|---|---|---|---|---|
| `app.py` 12줄 | `load_dotenv()` | 왜 있는지 몰랐다 | `.env` 파일의 값을 환경 변수로 넣는다. API 키를 코드에 쓰지 않으려고 | 8.2.1, `python-dotenv` 문서 |
| `utils.py` 30줄 | `[x["name"] for x in items]` | 처음 보는 문법 | 아직 모른다 | 이후 과정 |

그리고 "모르는 것"을 세 무리로 나눈다.

- **이 과정에서 배웠는데 그때는 몰랐던 것** — 관련된 장과 절의 번호를 적는다. 이 무리가 가장 길다면 이 과정을 제대로 마친 것이다.
- **아직 배우지 않은 문법** — 예를 들어 `[x for x in items]` 모양의 컴프리헨션, `yield`, `async`/`await`, 데코레이터를 직접 만드는 코드(`def 이름(func):` 안에 함수가 또 있는 모양), `match` 문 같은 것이다. 이름만 적어 두면 파이썬 중급 등 이후 과정에서 만났을 때 "아, 그때 그것"이 된다. 궁금하면 공식 문서에서 찾아보거나 AI에게 설명을 부탁해 보자(4.6.10). 이제는 설명을 듣고 이해할 바탕이 있다.
- **라이브러리나 프레임워크의 사용법** — `streamlit`, `fastapi`, `openai`, `pandas` 같은 패키지의 함수와 클래스다. 문법이 아니라 그 패키지의 약속이다. 문서의 빠른 시작을 읽으면 대부분 풀린다(9.3.2).

**5) 이 과정의 눈으로 점검하기**

마지막으로, 이 과정에서 배운 기준으로 1단계 코드를 점검한다. 찾은 것을 `REVIEW.md`에 적는다. 고칠 수 있는 것은 고쳐 보자.

- API 키나 비밀번호가 코드에 그대로 적혀 있지 않은가(8.2.1)?
- `except:`나 `except Exception: pass`로 모든 예외를 삼키는 곳이 있는가(6.1.7)? 그러면 문제가 생겨도 아무 말 없이 넘어간다.
- 파일 경로가 실행 위치에 기대거나 절대 경로로 적혀 있지 않은가(7.2.4)?
- 파일을 열 때 `encoding`을 지정했는가(7.1.7)?
- `requirements.txt`가 있고, 그것으로 새 가상환경에 복원되는가(9.1.7)?
- 빈 입력, 잘못된 입력을 넣으면 어떻게 되는가? 실패 표를 만든다면 몇 줄이 비어 있는가(10.1.4)?
- 한 함수가 너무 많은 일을 하지 않는가? 한 문장으로 설명할 수 있는가(10.3.1)?

1단계의 결과물이 파이썬이 아니라면, AI에게 "CSV 파일을 읽어 요약하는 파이썬 명령행 프로그램을 만들어 줘"처럼 작은 프로젝트를 하나 만들게 한 뒤, 그 코드로 2)~5)를 해 보자. 남이 쓴 코드를 읽고 평가하는 연습은 앞으로 AI와 함께 일할 때 가장 자주 하게 될 일이다.

| 하지 않을 것 | 범위를 좁힌다. 끝까지 완성한 작은 프로그램이 반쯤 만든 큰 프로그램보다 낫다. 미룬 것은 다음 버전으로 |
| 실행 예 | 코드보다 먼저 쓴다. 실행 방법, 보여 줄 것, 메시지 모양이 정해지고, 그대로 완성 확인 목록이 된다. 숫자는 계산기로 구한다 |
| 입력 형식 | 열마다 허용하는 값을 표로 정한다. 한 가지 모양만 받고 나머지는 오류로 알린다. 쉼표 같은 표기를 허용하면 위치까지 정하고 검사한다 |
| 시험 파일 | 코드보다 먼저 만든다. 정상, 빈 파일(0바이트, 첫 줄만), 잘못된 형식(값이 틀린 줄, 문법이 깨진 파일). 값이 틀린 파일은 한 줄에 한 가지 잘못 |
| 실패 표 | 상황, 누가 고치나, 어디서 알아차리나, 어떻게 알리나, 종료 코드. 새 실패를 찾으면 표 → 시험 파일 → 코드 순으로 더한다 |
| 잘못된 줄 | 첫 오류에서 멈춤 / 모두 모아 알리고 멈춤 / 건너뛰고 계속. 프로그램의 목적이 정한다. 요약에서 틀린 합계는 합계가 없는 것보다 나쁘다. 모두 모으더라도 화면에 몇 건까지 보여 줄지는 따로 정한다 |
| CSV 문법 오류 | `csv` 모듈은 기본 설정에서 깨진 줄도 조용히 읽는다(`"9500"0` → 95000). `strict=True`로 `csv.Error`를 일으키고, 그 뒤는 믿을 수 없으므로 그 자리에서 멈춘다 |
| 덮어쓰지 않기 | 입력에 문제가 있으면 결과 파일이나 저장 파일을 쓰지 않는다 |
| 출력과 종료 코드 | 결과는 표준 출력, 문제는 표준 오류. 0 성공, 1 실패, 2 사용법. `sys.exit()`는 흐름 함수에서만 |
| 역할 나누기 | 데이터(models), 계산(core), 파일(storage), 화면과 흐름(cli), 시작(main.py). 아래층은 위층을 모른다. 같은 층끼리도 서로 모를 수 있다 |
| 클래스와 함수 | 값의 묶음은 데이터 클래스, 바뀌는 상태와 지킬 규칙이 있으면 일반 클래스, 입력을 받아 결과를 돌려주고 끝나면 함수 |
| 검사의 자리 | 문자열 → 값(파일 형식의 지식)과 공백 정리는 storage, 값이 규칙에 맞는지는 데이터 클래스의 `__post_init__`. 타입 힌트는 실행 중에 검사되지 않으므로 자료형도 직접 검사한다 |
| 너무 잘게 나누지 않기 | 예외가 하나이고 한 곳에서만 쓰면 따로 모듈을 만들지 않는다. 실행 방법도 필요한 만큼만 |

| 확인 스크립트 | 시험 파일마다 기대하는 결과를 코드에 적고 비교한다. 건수만이 아니라 계산 결과와 오류의 위치·원인까지. 기대값은 손으로 계산한다. 확인하지 않는 범위를 밝힌다. 실패하면 종료 코드 1 |

23. `check_samples.py`는 무엇을 비교하고, 무엇을 확인하지 않는가? 거래 수만 비교하면 어떤 잘못을 놓치는가? 기대값을 프로그램의 출력에서 옮겨 적으면 안 되는 이유는? 하나라도 실패하면 종료 코드 1로 끝내는 이유는?
24. 함수를 한 문장으로 설명하기 어렵다면 무엇을 의심해야 하는가? "그리고"가 들어가도 괜찮은 함수는 어떤 함수인가?
25. "왜 그렇게 나눴는가"를 설명하는 좋은 방법은? 수입도 분류별로 보여 주려면 네 곳을 고쳐야 하는데, 이것이 나누기를 잘못했다는 뜻이 아닌 이유는?
26. `models.KINDS`에 `이체`만 더하면 어떤 문제가 생기는가? 이 문제를 막으려면 어떻게 고치면 좋은가?
27. `README.md`와 `DESIGN.md`는 각각 누구를 위한 문서인가? `DESIGN.md`에서 가장 중요한 항목은 무엇이고, 왜 그런가?
28. 복원 시험 A만으로는 찾을 수 없는 문제의 예를 들어라. B는 어떻게 하는가? B에서 원래 폴더의 이름을 바꿔 두는 이유는? 그래도 B가 찾지 못하는 문제는? B를 하다가 `README.md`에 적히지 않은 명령을 입력해야 했다면 무엇을 해야 하는가?
29. "내 컴퓨터에서는 되는데 다른 컴퓨터에서는 안 되는" 흔한 원인을 네 가지 들어라.
30. AI에게 프로그램을 맡길 때, 이 과정을 배우기 전과 후의 방식은 어떻게 다른가? AI가 만든 코드를 실행하기 전에 확인할 것을 세 가지 들어라.

## 다음 과정

파이썬 기초 과정을 모두 마쳤다. 1단계에서 AI가 만들어 준 코드를 "대략 따라가던" 여러분은 이제 파이썬 코드를 읽고, 쓰고, 고칠 수 있다. 무엇보다 **무엇이 들어올 수 있고 들어오면 어떻게 할지를 먼저 정하고, 코드를 역할에 따라 나누고, 그 결정을 설명하고, 다른 환경에서 똑같이 실행되게 넘겨줄 수 있다.** 이것은 문법보다 오래 쓰이는 능력이다.

[AI 엔지니어 학습 로드맵](../README.md)의 다음 항목은 **개발 도구**다. 이 과정에서는 꼭 필요한 만큼만 다룬 터미널을 본격적으로 배우고, 코드의 변경 이력을 관리하는 Git을 배운다. 이 장에서 만든 `.gitignore`, `README.md`, `DESIGN.md`, `requirements.txt`가 그대로 쓰인다. 복원 시험 B의 "다른 위치에 복사하기"도 Git 저장소에서 내려받는 것으로 바뀐다.

그 뒤의 과정에서도 이 장에서 한 일이 모양을 바꿔 계속 나온다.

- **파이썬 중급** — 선택 활동에서 "아직 배우지 않은 문법"으로 적어 둔 것들을 만나게 된다. 같은 일을 더 짧고 표현력 있게 쓰는 방법을 배우지만, 무엇을 어디에 둘지 정하는 판단은 그대로다.
- **데이터 처리 기초** — CSV를 읽어 합계를 내는 일을 훨씬 짧은 코드로 하는 도구를 배운다. 그래도 "잘못된 줄을 어떻게 할까", "빈 파일은 오류인가"는 도구가 대신 정해 주지 않는다.
- **웹·API 기초** — 9장의 `requests`에서 이어진다. 10.3.2의 표에서 "같은 기능을 웹 화면으로 만든다"는 줄을 실제로 해 보게 된다. `cli` 자리에 웹 요청을 받는 모듈이 들어서고, 아래층은 그대로 쓴다.
- **LLM API 활용** — API 키는 환경 변수로 읽고(8.2.1), LLM의 응답은 바깥에서 들어온 데이터이므로 입구에서 검사한다(`parse_row()`와 `__post_init__`이 한 일이다). 시간 초과, 요청 한도 초과(429), 형식이 맞지 않는 응답 같은 실패를 표로 정리하고 각각 어떻게 할지 정하는 일이 이 장의 실패 표와 똑같다.

새로운 도구와 라이브러리를 만날 때마다 이 장의 순서를 떠올리자. 한 문단으로 쓰고, 실행 예를 쓰고, 시험할 입력을 먼저 만들고, 실패를 나누고, 역할을 나누고, 아래층부터 확인하며 만든다. 그리고 설명하고, 넘겨준다.
