# 6장. 예외

[파이썬 기초](README.md) 과정의 여섯 번째 장이다. 지금까지 오류는 "프로그램이 멈추는 것"이었다. 1장에서는 트레이스백을 읽고 코드를 고치는 법을 배웠고, 3·4장에서는 `int()`에 숫자가 아닌 문자열이 들어가지 않도록 `isdecimal()`로 **미리 검사**했으며, 5장에서는 출금에 실패하면 `False`를, 없는 도서를 찾으면 `None`을 **돌려주어** 실패를 알렸다. 이 장에서는 오류를 프로그램이 직접 **다룰 수 있는 대상**으로 바꾼다. 오류가 나도 멈추지 않고 대처하는 방법과, 반대로 내가 만든 함수에서 오류를 **일으켜** 호출한 쪽에 알리는 방법을 배운다.

- **예외 처리** — 실행 중에 생기는 오류인 예외를 `try`/`except`로 잡아서 처리한다. `else`와 `finally`로 "성공했을 때 할 일"과 "무슨 일이 있어도 할 일"을 나눈다. 자주 만나는 내장 예외(`ValueError`, `TypeError`, `KeyError`, `IndexError`, `FileNotFoundError`)가 어떤 상황에서 생기는지 알고, 예외가 함수 호출을 거슬러 올라가는 길을 트레이스백에서 읽는다.
- **예외 발생과 정의** — `raise`로 예외를 일으키고, 5장의 상속을 이용해 나만의 예외 클래스를 만든다. 그리고 이 장에서 가장 중요한 판단, **예외를 어디서 잡고 어디서 그대로 둘지**를 연습한다.

AI 엔지니어가 만드는 프로그램은 바깥 세계와 주고받는 일이 많고, 바깥 세계는 자주 실패한다. LLM API를 호출하면 네트워크가 끊기기도 하고, 짧은 시간에 요청을 너무 많이 보내 거절당하기도 하고, 사용 한도를 다 써 버리기도 하고, 응답이 늦어 시간이 초과되기도 한다. 라이브러리는 이런 실패를 **예외**로 알려 준다. 예를 들어 OpenAI 라이브러리를 쓰는 코드에는 다음과 같은 모양이 자주 나온다.

```python
try:
    response = client.chat.completions.create(...)
except openai.RateLimitError:
    ...  # 한도에 걸렸다. 일시적인 속도 제한이면 잠시 뒤 다시 시도하고, 사용 한도를 다 썼으면 알린다
except openai.APIConnectionError:
    ...  # 서버에 연결하지 못했다. 사용자에게 알린다
```

라이브러리가 알려 주지 않는 실패도 있다. LLM에게 JSON으로 답하라고 했는데 형식이 틀린 문자열이 돌아오면, 라이브러리는 그것을 정상 응답으로 돌려준다. 실패는 우리가 그 문자열을 JSON으로 해석하는 순간 `json.JSONDecodeError` 예외로 드러난다. 어느 쪽이든 실패는 결국 **예외**의 모양으로 우리 코드에 도착한다.

이 장을 마치면 이런 코드가 "어떤 실패를 어디서 어떻게 처리하는지" 읽을 수 있고, 라이브러리 문서에서 "이 메서드는 이런 예외를 일으킨다"는 설명을 보고 내 코드에 반영할 수 있게 된다.

## 학습 목표

이 장을 마치면 다음을 할 수 있다.

- 문법 오류와 예외(실행 중에 생기는 오류)를 구분하고, 처리되지 않은 예외가 프로그램을 멈춘다는 것을 설명할 수 있다.
- `try`/`except`로 예외를 잡아 처리하고, `as`로 예외 객체를 받아 메시지를 꺼낼 수 있다.
- `ValueError`, `TypeError`, `KeyError`, `IndexError`, `FileNotFoundError`, `ZeroDivisionError`, `AttributeError`가 각각 어떤 상황에서 생기는지 설명할 수 있다.
- 예외도 클래스이고 상속 관계로 묶여 있다는 것을 알고, 부모 예외 클래스로 여러 예외를 한꺼번에 잡을 수 있다. `except:`나 `except Exception:`을 함부로 쓰면 안 되는 이유를 설명할 수 있다.
- `except` 절 여러 개, `else`, `finally`를 쓰고, 각 블록이 실행되는 순서를 예상할 수 있다.
- 예외가 함수 호출을 거슬러 올라가는 과정을 설명하고, 여러 층의 트레이스백과 연결된 예외(`During handling of ...`, `The above exception was the direct cause of ...`)를 읽을 수 있다.
- "미리 검사하기"와 "일단 해 보고 예외 처리하기" 중 상황에 맞는 쪽을 고를 수 있다.
- `raise`로 예외를 일으키고, 실패를 반환값(`False`, `None`)으로 알릴 때와 예외로 알릴 때의 차이를 설명할 수 있다.
- `Exception`을 상속해 사용자 정의 예외 클래스를 만들고, 필요한 정보를 속성으로 담을 수 있다.
- 예외를 잡아야 할 곳과 그대로 두어야 할 곳을 판단할 수 있다.
- VS Code 디버거가 예외가 난 곳에서 멈추게 하고, 그 순간의 변수를 확인할 수 있다.

이 장에서 배우는 `try` 문은 여러 줄이고, 중간의 `except` 줄에서 들여쓰기를 한 단계 **되돌려야** 한다. 셸에서 직접 입력하면 파이썬 3.13부터의 자동 들여쓰기 때문에 `except` 줄 앞의 공백을 Backspace로 지워야 해서 번거롭다. 그래서 이 장의 `try` 문 예제는 대부분 **스크립트 파일**이나 **셸에 붙여 넣는 함수** 안에 넣어 보여 준다.

이 장의 스크립트 중에는 `input()`으로 입력을 받는 것이 많다. 실행 결과에서 `총 금액: 50000`처럼 프롬프트 뒤에 나오는 값은 **우리가 키보드로 입력한 값**이다. 같은 프로그램을 여러 번 실행해 다른 값을 넣어 보며 결과를 비교하자.

> **1단계를 마친 사람에게**
> AI가 만들어 준 코드에서 `try:`와 `except Exception as e:`로 감싼 블록을 많이 보았을 것이다. 프로그램이 오류 없이 돌아가니 좋은 코드라고 생각했을 수도 있다. 그런데 그렇게 감싼 코드 중에는 **오류를 고친 것이 아니라 숨긴 것**도 적지 않다. 프로그램은 멈추지 않지만 결과가 조용히 틀리고, 무엇이 잘못됐는지 알려 주던 트레이스백도 사라진다. 이 장에서는 `try`/`except`의 문법보다 **어떤 예외를 어디서 잡아야 하는지**를 판단하는 연습에 더 많은 시간을 쓴다. 이 장을 마치고 1단계의 코드를 다시 보면, 고쳐야 할 `except`가 눈에 들어올 것이다.

## 6.1 예외 처리

이 절에서는 실행 중에 생긴 오류를 잡아서 처리하는 방법을 배운다. 먼저 "예외"가 무엇인지부터 정확히 해 두자.

### 6.1.1 예외 — 실행 중에 생기는 오류

1.3.5에서 오류에는 두 종류가 있다고 했다.

- **문법 오류**(`SyntaxError`, `IndentationError`): 실행하려는 파일에 문법 오류가 있으면, 파이썬이 그 파일을 **실행하기 전에** 문법을 검사하다가 발견한다. 그 파일은 한 줄도 실행되지 않으므로 그 안에 쓴 `try`/`except`도 동작할 기회가 없다. 코드를 고치는 수밖에 없다.
- **실행 중의 오류**: 문법은 맞지만 **실행하다가** 그 줄에 도달했을 때 생긴다. 오류가 난 줄 앞까지는 실행된다.

실행 중에 생기는 오류를 **예외**(exception)라고 한다. "정상적인 흐름에서 벗어난 예외적인 상황"이라는 뜻이다. 지금까지 만난 `NameError`, `TypeError`, `ValueError`, `KeyError`, `IndexError`, `AttributeError`, `ZeroDivisionError`가 모두 예외다.

(사실 `SyntaxError`도 예외 클래스의 하나다. 실행 중인 프로그램이 문법 오류가 있는 **다른** 모듈을 `import`하거나, 문자열로 된 코드를 실행하는 `eval()`, `exec()`, `compile()` 같은 함수를 쓰다가 생긴 `SyntaxError`는 다른 예외처럼 잡을 수 있다. 이 장에서 "문법 오류"라고 하면 실행하려는 파일 자체의 문법 오류를 말한다.)

모임 회비를 나누어 내는 프로그램을 만들어 보자. `ch06` 폴더에 `split_bill.py`를 만든다.

```python
# split_bill.py
total = int(input("총 금액: "))
people = int(input("인원 수: "))
print(f"1인당 {total // people:,}원")
print("계산을 마쳤습니다.")
```

올바른 값을 넣으면 잘 동작한다.

```
총 금액: 50000
인원 수: 4
1인당 12,500원
계산을 마쳤습니다.
```

두 경우 모두 오류가 난 줄에서 프로그램이 **그대로 멈췄다.** 마지막 줄의 `계산을 마쳤습니다.`도 출력되지 않았다.

여기서 눈여겨볼 점은 **코드에는 잘못이 없다**는 것이다. 문제는 입력에 있다. 사용자가 무엇을 입력할지는 프로그래머가 정할 수 없다. 앞으로 읽을 파일이 없을 수도 있고(7장), 인터넷 연결이 끊길 수도 있다. 이렇게 **프로그램 바깥에서 오는 문제**는 아무리 코드를 잘 써도 생긴다. 그러니 문제가 생겼을 때 멈추지 말고 **대처하는** 방법이 필요하다.

지금까지는 문제가 생기지 않도록 **미리 검사**했다. 3장 실습 3-7에서 `isdecimal()`로 숫자인지 확인한 뒤에 `int()`를 호출한 것이 그 방법이다. 하지만 미리 검사하는 방법에는 한계가 있다.

- `"-5"`는 `int()`로 바꿀 수 있는 정수인데 `isdecimal()`은 `False`다. 음수를 받아야 하는 프로그램이라면 검사를 따로 만들어야 한다.
- `float()`로 바꿀 문자열은 `"3.14"`, `"-0.5"`, `"1e3"`처럼 모양이 다양해서 검사 코드를 빈틈없이 쓰기 어렵다.
- `"2026-02-30"`처럼 모양은 날짜인데 실제로는 없는 날짜를 미리 걸러 내려면 달마다 마지막 날을 따지는 코드를 써야 한다.

`int()`, `float()`, `date.fromisoformat()`은 이미 이 검사를 모두 하고 있고, 바꿀 수 없으면 예외를 일으켜 알려 준다. 그렇다면 **일단 바꿔 보고, 예외가 나면 그때 대처하는** 편이 간단하다. 이것이 예외 처리다.

먼저 용어를 정리해 두자.

| 용어 | 뜻 |
|---|---|
| 예외가 **발생한다** (raise) | 실행 중에 문제가 생겨 예외가 만들어진다. "예외를 일으킨다", "던진다"라고도 한다 |
| 예외를 **처리한다** (handle) | 발생한 예외를 받아서 대처한다. "예외를 잡는다"(catch)라고도 한다 |
| 처리되지 않은 예외 | 아무도 잡지 않은 예외. 프로그램이 멈추고 트레이스백이 출력된다 |

### 6.1.2 `try`/`except`로 예외 잡기

예외를 잡으려면 예외가 날 수 있는 코드를 `try` 블록에 넣고, 그 아래 `except` 블록에 예외가 났을 때 할 일을 쓴다. `split_bill.py`를 고쳐 `split_bill2.py`로 저장하자.

```python
# split_bill2.py
try:
    total = int(input("총 금액: "))
    people = int(input("인원 수: "))
    print(f"1인당 {total // people:,}원")
except ValueError:
    print("금액과 인원 수는 숫자로 입력하세요.")
print("계산을 마쳤습니다.")
```

```
총 금액: 50000
인원 수: 4
1인당 12,500원
계산을 마쳤습니다.
```

```
총 금액: 만원
금액과 인원 수는 숫자로 입력하세요.
계산을 마쳤습니다.
```

이번에는 트레이스백 대신 안내 메시지가 나왔고, 프로그램이 멈추지 않고 마지막 줄까지 실행되었다.

- `try:` 아래 들여쓴 블록이 **시도할 코드**다.
- `except 예외클래스:` 아래 들여쓴 블록이 **그 예외가 났을 때 실행할 코드**다. 이 블록을 **예외 처리기**(exception handler)라고 한다.
- `if`/`else`처럼 `try`와 `except`는 같은 들여쓰기 수준에 쓴다.

실행 순서를 그림으로 보자.

```
예외가 나지 않으면                       ValueError가 나면 ("만원" 입력)

try:                                     try:
    total = int(...)    ✔ 실행               total = int(...)    ✘ 여기서 예외!
    people = int(...)   ✔ 실행               people = int(...)     (건너뜀)
    print(...)          ✔ 실행               print(...)            (건너뜀)
except ValueError:                       except ValueError:
    print("...숫자로...")  (건너뜀)           print("...숫자로...")  ✔ 실행
print("계산을 마쳤습니다.") ✔ 실행         print("계산을 마쳤습니다.") ✔ 실행
```

핵심은 두 가지다.

1. `try` 블록 안에서 예외가 나면 **그 줄에서 곧바로** `except` 블록으로 건너뛴다. `try` 블록의 나머지 줄은 실행되지 않는다. 그래서 `"만원"`을 입력하면 인원 수를 묻지도 않는다.
2. 예외가 나지 않으면 `except` 블록은 **실행되지 않는다.**

어느 쪽이든 `try` 문이 끝나면 그다음 줄(`print("계산을 마쳤습니다.")`)로 이어진다. `except` 블록이 예외를 처리했으므로, 파이썬은 "문제는 해결되었다"고 보고 프로그램을 계속 실행한다.

**잡지 않은 예외는 그대로 지나간다**

인원 수에 0을 넣어 보자.

```
총 금액: 50000
인원 수: 0
Traceback (most recent call last):
  File "/Users/본인계정/python-lab/ch06/split_bill2.py", line 4, in <module>
    print(f"1인당 {total // people:,}원")
                   ~~~~~~^^~~~~~~
ZeroDivisionError: integer division or modulo by zero
```

`except ValueError:`는 **`ValueError`만** 잡는다. `ZeroDivisionError`는 이 처리기와 관계없으므로 처리되지 않은 예외가 되어 프로그램이 멈췄다. `except` 뒤에 쓴 예외 클래스는 "**이런 종류의 문제라면 내가 대처할 수 있다**"는 선언이다. 대처 방법을 모르는 문제까지 잡지 않는다는 점이 중요하다. 0으로 나누는 경우를 처리하는 방법은 6.1.6에서 본다.

### 6.1.3 예외도 객체다 — `except ... as 이름`

5장 5.3.5의 상자글에서 예외도 클래스라고 했다. 예외가 발생한다는 것은 **예외 클래스의 객체가 만들어진다**는 뜻이다. 예외 객체는 우리가 직접 만들어 볼 수도 있다. 클래스 이름을 호출하면 객체가 만들어지는 것은 다른 클래스와 같다.

```python
>>> e = ValueError("나이는 0 이상이어야 합니다")
>>> e
ValueError('나이는 0 이상이어야 합니다')
>>> type(e)
<class 'ValueError'>
>>> e.args
('나이는 0 이상이어야 합니다',)
>>> str(e)
'나이는 0 이상이어야 합니다'
>>> isinstance(e, Exception)
True
```

(예외 객체를 만들기만 했으므로 아무 일도 일어나지 않는다. 만든 예외를 **일으키는** 방법은 6.2에서 배운다.)

- `args`: 예외를 만들 때 넘긴 인자들을 담은 튜플이다.
- `str(e)`: 예외의 **메시지**다. 트레이스백 마지막 줄의 콜론 뒤에 나오는 바로 그 문장이다.

`except` 블록에서 이 예외 객체를 쓰고 싶으면 `except 예외클래스 as 이름:`으로 이름을 붙인다.

```python
# split_bill3.py
try:
    total = int(input("총 금액: "))
    people = int(input("인원 수: "))
    print(f"1인당 {total // people:,}원")
except ValueError as e:
    print("금액과 인원 수는 숫자로 입력하세요.")
    print(f"({type(e).__name__}: {e})")
print("계산을 마쳤습니다.")
```

```
총 금액: 5만
금액과 인원 수는 숫자로 입력하세요.
(ValueError: invalid literal for int() with base 10: '5만')
계산을 마쳤습니다.
```

`e`에는 `int()`가 일으킨 `ValueError` 객체가 들어 있다. `f"{e}"`는 `str(e)`와 같으므로 메시지가 나오고, `type(e).__name__`은 5.3.2에서 본 대로 클래스 이름 문자열이다.

`as`로 붙인 이름은 **`except` 블록 안에서만** 쓸 수 있다. 블록이 끝나면 파이썬이 이 이름을 지운다. 블록 바깥에서도 예외 정보가 필요하면 블록 안에서 다른 변수에 옮겨 두어야 한다. 이름은 관례적으로 `e`나 `err`, `exc`를 쓴다.

> **메시지는 누구에게 보여 줄까**
> `invalid literal for int() with base 10`은 개발자에게는 유용하지만 프로그램을 쓰는 사람에게는 알아듣기 어려운 문장이다. 사용자에게는 위의 "숫자로 입력하세요"처럼 **무엇을 해야 하는지** 알려 주는 메시지를 보여 주자. 예외의 원래 메시지는 개발 중에 확인하거나 기록(로그)으로 남길 때 쓴다.

**`KeyError`의 메시지는 조금 다르다**

```python
>>> k = KeyError("모카")
>>> str(k)
"'모카'"
>>> k.args
('모카',)
```

다른 예외는 `str()`이 넘긴 문자열을 그대로 돌려주는데, `KeyError`는 **작은따옴표를 붙여** 돌려준다. `KeyError`의 인자는 메시지가 아니라 "찾지 못한 키"이기 때문에, 키가 `""`(빈 문자열)이나 `" "`일 때도 알아볼 수 있게 `repr()` 모양으로 보여 주는 것이다. 그래서 `print(f"오류: {e}")`처럼 `KeyError`를 출력하면 `오류: '모카'`가 된다. 이 점은 6.2에서 나만의 예외를 만들 때 다시 떠올린다.

### 6.1.4 자주 만나는 내장 예외

파이썬에는 수십 가지 예외 클래스가 준비되어 있다. 이것을 **내장 예외**(built-in exceptions)라고 한다. 모두 외울 필요는 없고, 자주 만나는 몇 가지가 **어떤 상황에서 생기는지**만 알면 된다. 셸에서 하나씩 일으켜 보자.

**`ValueError` — 자료형은 맞는데 값이 맞지 않는다**

```python
>>> int("만원")
Traceback (most recent call last):
  File "<python-input-1>", line 1, in <module>
    int("만원")
    ~~~^^^^^^^^
ValueError: invalid literal for int() with base 10: '만원'
>>> from datetime import date
>>> date.fromisoformat("2026-02-30")
Traceback (most recent call last):
  File "<python-input-3>", line 1, in <module>
    date.fromisoformat("2026-02-30")
    ~~~~~~~~~~~~~~~~~~^^^^^^^^^^^^^^
ValueError: day is out of range for month
>>> [1, 2, 3].remove(5)
Traceback (most recent call last):
  File "<python-input-4>", line 1, in <module>
    [1, 2, 3].remove(5)
    ~~~~~~~~~~~~~~~~^^^
ValueError: list.remove(x): x not in list
```

`int()`는 문자열을 받는 함수이므로 `"만원"`은 자료형으로는 맞다. 하지만 그 **값**을 정수로 바꿀 수 없다. 2월 30일, 리스트에 없는 값을 지우라는 요청도 마찬가지다. "받을 수 있는 종류의 값이지만 이 값으로는 할 수 없다"가 `ValueError`다. 사용자 입력을 변환할 때 가장 자주 만난다.

**`TypeError` — 자료형이 맞지 않는다**

```python
>>> "나이: " + 20
Traceback (most recent call last):
  File "<python-input-5>", line 1, in <module>
    "나이: " + 20
    ~~~~~~~~~^~~~
TypeError: can only concatenate str (not "int") to str
>>> len(5)
Traceback (most recent call last):
  File "<python-input-6>", line 1, in <module>
    len(5)
    ~~~^^^
TypeError: object of type 'int' has no len()
```

문자열에 정수를 더하거나 정수의 길이를 묻는 것처럼, **그 종류의 값으로는 애초에 할 수 없는 일**을 시키면 `TypeError`가 난다. 4·5장에서 본 "인자 개수가 맞지 않는다"는 오류도 `TypeError`다. `TypeError`는 대부분 **코드의 실수**에서 생긴다. 그래서 잡아서 처리하기보다는 코드를 고쳐야 하는 경우가 많다(6.2.6).

**`KeyError`와 `IndexError` — 없는 키, 없는 위치**

```python
>>> prices = {"아메리카노": 2500, "라떼": 3000}
>>> prices["모카"]
Traceback (most recent call last):
  File "<python-input-8>", line 1, in <module>
    prices["모카"]
    ~~~~~~^^^^^^^^
KeyError: '모카'
>>> [10, 20, 30][3]
Traceback (most recent call last):
  File "<python-input-9>", line 1, in <module>
    [10, 20, 30][3]
    ~~~~~~~~~~~~^^^
IndexError: list index out of range
```

딕셔너리에 없는 키로 값을 꺼내면 `KeyError`, 리스트나 문자열의 범위를 벗어난 인덱스로 꺼내면 `IndexError`가 난다. 3장에서 이미 여러 번 보았다.

**`FileNotFoundError` — 파일이 없다**

```python
>>> open("memo.txt")
Traceback (most recent call last):
  File "<python-input-10>", line 1, in <module>
    open("memo.txt")
    ~~~~^^^^^^^^^^^^
FileNotFoundError: [Errno 2] No such file or directory: 'memo.txt'
```

`open()`은 파일을 여는 내장 함수다. 사용법은 7장에서 자세히 배우고, 여기서는 **없는 파일을 열려고 하면 `FileNotFoundError`가 난다**는 것만 기억하자. 파일 이름의 오타뿐 아니라, 셸이나 스크립트를 실행한 **현재 위치**(1.1.3)가 생각과 다를 때도 이 예외를 만난다. `[Errno 2]`는 운영체제가 정한 오류 번호다.

**`ZeroDivisionError`와 `AttributeError`**

```python
>>> 10 / 0
Traceback (most recent call last):
  File "<python-input-11>", line 1, in <module>
    10 / 0
    ~~~^~~
ZeroDivisionError: division by zero
>>> name = None
>>> name.upper()
Traceback (most recent call last):
  File "<python-input-13>", line 1, in <module>
    name.upper()
    ^^^^^^^^^^
AttributeError: 'NoneType' object has no attribute 'upper'
```

`AttributeError: 'NoneType' object has no attribute ...`는 실무에서 정말 자주 만나는 오류다. 어떤 함수가 결과 대신 `None`을 돌려주었는데(4.1.6), 그것을 확인하지 않고 메서드를 호출하면 이렇게 된다. 오류가 난 줄이 아니라 **`None`이 들어온 곳**을 찾아 거슬러 올라가야 원인이 보인다. 이 문제는 6.2.2에서 다시 다룬다.

**한눈에 보기**

| 예외 | 언제 생기나 | 대표적인 예 | 주로 어디서 오나 |
|---|---|---|---|
| `ValueError` | 자료형은 맞지만 값이 맞지 않는다 | `int("만원")`, `date(2026, 2, 30)` | 사용자 입력, 바깥 데이터 |
| `TypeError` | 그 자료형으로는 할 수 없는 일 | `"a" + 1`, `len(5)`, 인자 개수 틀림 | 코드의 실수 |
| `KeyError` | 딕셔너리에 없는 키 | `prices["모카"]` | 바깥 데이터, 코드의 실수 |
| `IndexError` | 범위를 벗어난 인덱스 | `[1, 2][5]`, `"".split()[0]` | 바깥 데이터, 코드의 실수 |
| `FileNotFoundError` | 없는 파일 | `open("memo.txt")` | 프로그램 바깥(파일 시스템) |
| `ZeroDivisionError` | 0으로 나눔 | `10 / 0`, `10 % 0` | 사용자 입력, 빈 데이터 |
| `AttributeError` | 없는 속성이나 메서드 | `None.upper()` | 코드의 실수(특히 `None` 확인 누락) |

마지막 열을 눈여겨보자. 같은 예외라도 **바깥에서 들어온 값 때문에** 생긴 것은 처리할 대상이고, **코드의 실수 때문에** 생긴 것은 고칠 대상이다. 이 구분이 6.2.6의 판단 기준이 된다.

공식 문서의 [내장 예외](https://docs.python.org/ko/3/library/exceptions.html) 페이지에 모든 내장 예외가 정리되어 있다. 처음 보는 예외를 만나면 여기서 찾아보자.

### 6.1.5 예외 클래스의 계층 — 부모 클래스로 잡기

예외는 클래스이고, 5장에서 배운 상속 관계로 묶여 있다. `__mro__`로 부모를 따라가 보자(5.3.5).

```python
>>> ZeroDivisionError.__mro__
(<class 'ZeroDivisionError'>, <class 'ArithmeticError'>, <class 'Exception'>, <class 'BaseException'>, <class 'object'>)
>>> KeyError.__mro__
(<class 'KeyError'>, <class 'LookupError'>, <class 'Exception'>, <class 'BaseException'>, <class 'object'>)
>>> FileNotFoundError.__mro__
(<class 'FileNotFoundError'>, <class 'OSError'>, <class 'Exception'>, <class 'BaseException'>, <class 'object'>)
```

자주 만나는 예외의 관계를 그림으로 그리면 다음과 같다(일부만 그렸다).

```
BaseException                  모든 예외의 조상
 ├── KeyboardInterrupt         Ctrl+C를 눌러 프로그램을 멈출 때
 ├── SystemExit                프로그램을 끝내는 함수 sys.exit()를 호출할 때
 └── Exception                 ← 프로그램에서 다루는 거의 모든 예외의 조상
      ├── ArithmeticError      계산 오류
      │    └── ZeroDivisionError
      ├── LookupError          찾기 오류
      │    ├── IndexError
      │    └── KeyError
      ├── OSError              운영체제(파일, 네트워크) 관련 오류
      │    └── FileNotFoundError
      ├── AttributeError
      ├── NameError
      │    └── UnboundLocalError
      ├── TypeError
      └── ValueError
```

**`except`는 `isinstance()`로 판단한다**

`except 예외클래스:`는 "발생한 예외가 **이 클래스의 한 종류이면**(`isinstance(예외, 예외클래스)`가 `True`이면) 잡는다"는 뜻이다. 5.3.5에서 자식 객체는 부모 클래스의 인스턴스이기도 하다고 했다. 그래서 부모 예외 클래스를 쓰면 그 자식 예외를 모두 잡을 수 있다. 다음 함수를 셸에 붙여 넣자.

```python
def show_first_price(prices, menus):
    """menus의 첫 번째 메뉴와 가격을 출력한다."""
    try:
        menu = menus[0]
        print(f"{menu}: {prices[menu]:,}원")
    except LookupError as e:
        print(f"찾을 수 없습니다 - {type(e).__name__}: {e}")
```

```python
>>> prices = {"아메리카노": 2500, "라떼": 3000}
>>> show_first_price(prices, ["라떼", "모카"])
라떼: 3,000원
>>> show_first_price(prices, [])
찾을 수 없습니다 - IndexError: list index out of range
>>> show_first_price(prices, ["모카", "라떼"])
찾을 수 없습니다 - KeyError: '모카'
>>> issubclass(IndexError, LookupError)
True
>>> isinstance(KeyError("모카"), LookupError)
True
```

빈 리스트에서 꺼낼 때의 `IndexError`와 없는 메뉴를 찾을 때의 `KeyError`를 `except LookupError:` 하나로 잡았다. 5장에서 미리 말했던 내용이 이것이다. `type(e).__name__`을 출력해 보면 실제로 잡힌 예외는 여전히 `IndexError`, `KeyError`라는 것을 알 수 있다. 부모 클래스로 잡았다고 예외의 종류가 바뀌는 것은 아니다.

**`except Exception:`과 `except:`**

그렇다면 `except Exception:`이라고 쓰면 거의 모든 예외를 잡을 수 있다. 아예 클래스를 쓰지 않고 `except:`만 쓰면 `BaseException`의 자손, 즉 **모든 예외**를 잡는다. 편해 보이지만 위험하다. 다음 프로그램을 `no_escape.py`로 저장하고 실행해 보자.

```python
# no_escape.py
while True:
    try:
        age = int(input("나이: "))
        break
    except:
        print("숫자로 입력하세요.")
print(f"{age}살이군요.")
```

숫자가 아닌 값을 넣으면 다시 묻는다. 여기까지는 의도대로다. 이제 프로그램을 멈추려고 **Ctrl+C**를 눌러 보자.

```
나이: 스물
숫자로 입력하세요.
나이: ^C숫자로 입력하세요.
나이: ^C숫자로 입력하세요.
나이:
```

멈추지 않는다! Ctrl+C를 누르면 파이썬은 `KeyboardInterrupt` 예외를 일으켜 프로그램을 멈추는데, `except:`가 그것까지 잡아서 "숫자로 입력하세요."로 바꿔 버렸기 때문이다. (터미널을 닫거나, VS Code라면 터미널 패널 오른쪽 위의 휴지통 아이콘을 눌러 터미널을 종료하면 프로그램도 끝난다.)

`except:`를 `except Exception:`으로 바꾸면 `KeyboardInterrupt`는 `Exception`의 자손이 아니므로 Ctrl+C로 멈출 수 있다. 하지만 이것도 근본적인 해결은 아니다. 이 프로그램이 대처할 수 있는 문제는 "숫자가 아닌 입력", 즉 `ValueError` 하나뿐이다. **대처할 수 있는 예외만 잡는다**는 6.1.2의 원칙대로 `except ValueError:`라고 쓰는 것이 맞다.

| 쓰는 모양 | 잡는 범위 | 판단 |
|---|---|---|
| `except ValueError:` | `ValueError`와 그 자식 | 기본. 대처할 수 있는 예외를 이름으로 쓴다 |
| `except LookupError:` | `KeyError`, `IndexError` 등 | 같은 방법으로 대처할 수 있는 형제 예외를 묶을 때 |
| `except Exception:` | 프로그램에서 다루는 거의 모든 예외 | 두 경우에만 쓴다. ① 프로그램의 가장 바깥에서 "무슨 일이 있어도 기록을 남기고 계속 실행해야" 할 때(6.2.6) ② 뒷정리나 되돌리기를 한 뒤 곧바로 `raise`로 같은 예외를 다시 올려 보낼 때(6.2.5) |
| `except:` | Ctrl+C까지 모든 것 | 쓰지 않는다 |

1장에서 설정한 Ruff도 `except:`를 발견하면 `Do not use bare except`(맨 `except`를 쓰지 말라)라고 경고한다.

### 6.1.6 여러 예외를 다르게 처리하기

다시 회비 계산기로 돌아가자. 인원 수에 0을 넣으면 `ZeroDivisionError`가 났다. 숫자가 아닌 입력과는 **대처 방법이 다르므로** 다른 메시지를 보여 주어야 한다. `except` 절은 여러 개 쓸 수 있다.

```python
# split_bill4.py
try:
    total = int(input("총 금액: "))
    people = int(input("인원 수: "))
    print(f"1인당 {total // people:,}원")
except ValueError:
    print("금액과 인원 수는 숫자로 입력하세요.")
except ZeroDivisionError:
    print("인원 수는 1명 이상이어야 합니다.")
print("계산을 마쳤습니다.")
```

```
총 금액: 50000
인원 수: 0
인원 수는 1명 이상이어야 합니다.
계산을 마쳤습니다.
```

예외가 나면 파이썬은 `except` 절을 **위에서부터 차례로** 확인해 처음으로 맞는 **하나만** 실행한다. `if`/`elif` 사슬과 같다. 그래서 순서가 중요하다.

```python
try:
    ...
except LookupError:
    print("찾을 수 없습니다.")
except KeyError:
    print("없는 메뉴입니다.")   # 절대 실행되지 않는다
```

`KeyError`는 `LookupError`의 자식이므로 첫 번째 절에서 이미 잡힌다. 두 번째 절은 영원히 실행되지 않는다. **자식 예외를 먼저, 부모 예외를 나중에** 쓴다.

대처 방법이 같은 예외 여러 개는 **튜플**로 묶어 한 절에 쓸 수 있다.

```python
except (ValueError, ZeroDivisionError):
    print("금액과 인원 수를 다시 확인하세요.")
```

**예외가 나지 않는 잘못된 값도 있다**

`split_bill4.py`에 인원 수 `-4`를 넣어 보자.

```
총 금액: 50000
인원 수: -4
1인당 -12,500원
계산을 마쳤습니다.
```

예외가 나지 않았다. 파이썬에게 `50000 // -4`는 아무 문제 없는 계산이기 때문이다. 예외 처리는 **파이썬이 할 수 없다고 판단한 일**만 잡을 수 있다. "인원 수는 1명 이상"처럼 **우리 프로그램만의 규칙**은 우리가 직접 검사해야 한다. 그 규칙을 어겼을 때 예외를 일으키는 방법은 6.2에서 배운다.

### 6.1.7 `else` — 예외가 나지 않았을 때만 실행할 코드

`try` 블록에는 무엇을 넣어야 할까? 지금까지는 관련된 코드를 모두 넣었다. 그런데 이렇게 하면 문제가 생길 수 있다. 1인당 금액을 실수 나눗셈으로 바꾸다가 실수를 했다고 하자.

```python
# split_bill_bug.py
try:
    total = int(input("총 금액: "))
    people = int(input("인원 수: "))
    print(f"1인당 {total / people:,d}원")
except ValueError:
    print("금액과 인원 수는 숫자로 입력하세요.")
except ZeroDivisionError:
    print("인원 수는 1명 이상이어야 합니다.")
print("계산을 마쳤습니다.")
```

```
총 금액: 50000
인원 수: 4
금액과 인원 수는 숫자로 입력하세요.
계산을 마쳤습니다.
```

숫자를 제대로 입력했는데 숫자로 입력하라고 한다. 원인은 포맷 지정자 `:,d`다. `d`는 정수에만 쓸 수 있는데 `total / people`은 실수(`12500.0`)라서 **`print()` 줄에서 `ValueError`**가 났다. 그런데 이 줄이 `try` 블록 안에 있으니 `except ValueError:`가 이 예외까지 잡아 엉뚱한 메시지로 바꿔 버렸다. 코드의 실수가 사용자의 입력 실수로 둔갑한 것이다. 트레이스백도 나오지 않았으니 원인을 찾기도 어렵다.

해결책은 **`try` 블록에 예외가 날 것으로 예상하는 코드만 넣는** 것이다. 예외가 나지 않았을 때 이어서 할 일은 `else` 블록에 쓴다.

```python
# split_bill5.py
try:
    total = int(input("총 금액: "))
    people = int(input("인원 수: "))
    share = total / people
except ValueError:
    print("금액과 인원 수는 숫자로 입력하세요.")
except ZeroDivisionError:
    print("인원 수는 1명 이상이어야 합니다.")
else:
    print(f"1인당 {share:,d}원")
print("계산을 마쳤습니다.")
```

```
총 금액: 50000
인원 수: 4
Traceback (most recent call last):
  File "/Users/본인계정/python-lab/ch06/split_bill5.py", line 10, in <module>
    print(f"1인당 {share:,d}원")
                  ^^^^^^^^^^
ValueError: Unknown format code 'd' for object of type 'float'
```

이번에는 `else` 블록에서 난 예외이므로 `except`가 잡지 않았고, 트레이스백이 **진짜 원인**을 정확히 가리킨다. `share = total / people`을 `share = total // people`로 고치면 `1인당 12,500원`이 출력된다. 버그는 숨기는 것보다 드러나는 편이 훨씬 낫다.

- `else` 블록은 `try` 블록에서 예외가 **나지 않았을 때만** 실행된다.
- `else` 블록에서 난 예외는 바로 위의 `except` 절들이 잡지 않는다.
- `else`는 모든 `except` 절 **뒤에** 쓴다.

`else`를 쓰지 않고 `try` 문 다음 줄에 이어서 써도 될 것 같지만, 그러면 예외가 났을 때도 그 줄이 실행된다. 예외가 났을 때는 `share`가 만들어지지 않았으므로 `NameError`가 날 것이다. "**성공했을 때만** 이어서 할 일"을 분명히 표시하는 자리가 `else`다.

### 6.1.8 `finally` — 무슨 일이 있어도 실행할 코드

`try` 문의 마지막에는 `finally` 블록을 쓸 수 있다. `finally` 블록은 예외가 나든 나지 않든, 그 예외를 잡았든 잡지 못했든 **언제나** 실행된다. 네 블록을 모두 쓴 함수로 실행 순서를 확인해 보자. 셸에 붙여 넣는다.

```python
def convert(text):
    try:
        print("try 시작")
        number = int(text)
        print("try 끝")
    except ValueError:
        print("except")
    else:
        print("else:", number)
    finally:
        print("finally")
```

```python
>>> convert("42")
try 시작
try 끝
else: 42
finally
>>> convert("사십이")
try 시작
except
finally
```

```
예외가 나지 않으면:  try 전체 → else → finally
except가 잡으면:    try 일부 → except → finally
아무도 잡지 않으면:  try 일부 → finally → (예외가 계속 위로 올라간다)
```

세 번째 경우를 확인해 보자. `except` 없이 `try`와 `finally`만 쓸 수도 있다.

```python
def divide(a, b):
    print("나누기 시작")
    try:
        result = a / b
        return result
    finally:
        print("나누기 끝")
```

```python
>>> divide(10, 4)
나누기 시작
나누기 끝
2.5
>>> divide(10, 0)
나누기 시작
나누기 끝
Traceback (most recent call last):
  File "<python-input-6>", line 1, in <module>
    divide(10, 0)
    ~~~~~~^^^^^^^
  File "<python-input-4>", line 4, in divide
    result = a / b
             ~~^~~
ZeroDivisionError: division by zero
```

`ZeroDivisionError`를 잡지 않았으므로 프로그램은 트레이스백과 함께 멈췄다. 그런데 멈추기 **전에** `나누기 끝`이 출력되었다. 이것이 `finally`의 쓸모다. `try` 블록 안에서 `return`으로 함수를 빠져나가는 경우에도 `finally`는 실행된다.

`finally`에는 **정리 작업**을 쓴다. 열어 둔 파일을 닫기, 네트워크 연결 끊기, 임시로 바꾼 설정 되돌리기처럼 "작업이 성공하든 실패하든 반드시 해야 하는 뒷정리"다. 파일이 열린 채로 남으면 다른 프로그램이 그 파일을 쓰지 못하거나 내용이 저장되지 않을 수 있기 때문이다. 7장에서 배울 `with` 문은 이 뒷정리를 자동으로 해 주는 문법이라서, 실제로 `finally`를 직접 쓸 일은 생각보다 적다. 하지만 `with`가 무엇을 대신해 주는지 이해하려면 `finally`를 알아야 한다.

**정리 — `try` 문의 네 블록**

```python
try:
    ...  # 예외가 날 수 있는 코드 (짧게)
except 예외클래스 as e:
    ...  # 그 예외가 났을 때 대처하는 코드 (여러 개 가능, 자식 예외 먼저)
else:
    ...  # 예외가 나지 않았을 때만 이어서 할 코드 (선택)
finally:
    ...  # 무슨 일이 있어도 마지막에 할 정리 코드 (선택)
```

`try` 다음에는 `except`와 `finally` 중 적어도 하나가 있어야 한다. `else`는 `except`가 있을 때만 쓸 수 있다.

### 6.1.9 예외는 호출한 쪽으로 거슬러 올라간다

지금까지는 예외가 난 바로 그 자리를 `try`로 감쌌다. 그런데 함수 안에서 난 예외는 **함수를 호출한 쪽에서도** 잡을 수 있다. `propagation.py`를 만든다.

```python
# propagation.py
def parse_price(text):
    print("    parse_price 시작:", text)
    price = int(text)
    print("    parse_price 끝")
    return price


def total_price(texts):
    print("  total_price 시작")
    total = 0
    for text in texts:
        total += parse_price(text)
    print("  total_price 끝")
    return total


def main():
    print("main 시작")
    try:
        total = total_price(["1200", "3500", "두 개", "800"])
        print(f"합계: {total:,}원")
    except ValueError as e:
        print(f"가격을 읽을 수 없습니다: {e}")
    print("main 끝")


main()
```

```
main 시작
  total_price 시작
    parse_price 시작: 1200
    parse_price 끝
    parse_price 시작: 3500
    parse_price 끝
    parse_price 시작: 두 개
가격을 읽을 수 없습니다: invalid literal for int() with base 10: '두 개'
main 끝
```

`int("두 개")`에서 난 `ValueError`는 `parse_price()` 안에서 잡히지 않았다. 그러자 파이썬은 `parse_price()`를 **그 자리에서 끝내고**, 예외를 들고 호출한 쪽인 `total_price()`로 돌아갔다. `total_price()`에도 `try`가 없으므로 이 함수도 그 자리에서 끝나고, 다시 호출한 쪽인 `main()`으로 돌아갔다. `main()`에는 `except ValueError:`가 있으므로 여기서 잡혔다.

```
main()           try: ... except ValueError ← ③ 여기서 잡힌다
  └ total_price()     total += parse_price(text)  ← ② 잡는 곳이 없다. 함수를 끝내고 위로
      └ parse_price()     price = int(text)        ← ① 예외 발생. 잡는 곳이 없다. 위로
```

출력에서 `parse_price 끝`, `total_price 끝`, `합계:`가 나오지 않은 것을 확인하자. 예외가 지나간 함수는 **나머지 코드를 실행하지 않고** 끝난다. 반복문의 남은 `"800"`도 처리되지 않았다. 이처럼 예외는 잡아 주는 `try`를 만날 때까지 **호출 스택을 거슬러 올라간다.** 이것을 예외의 **전파**(propagation)라고 한다. 끝까지 아무도 잡지 않으면 프로그램이 멈추고 트레이스백이 출력된다.

**트레이스백은 예외가 지나온 길이다**

`main()`의 `try`를 없앤 `propagation2.py`를 실행해 보자.

```python
# propagation2.py
def parse_price(text):
    return int(text)


def total_price(texts):
    total = 0
    for text in texts:
        total += parse_price(text)
    return total


def main():
    total = total_price(["1200", "3500", "두 개", "800"])
    print(f"합계: {total:,}원")


main()
```

```
    main()
    ~~~~^^

    total = total_price(["1200", "3500", "두 개", "800"])
            ~~~~~~~~~~~^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^
  File "/Users/본인계정/python-lab/ch06/propagation2.py", line 8, in total_price
```

4.1.9에서 여러 층의 트레이스백 읽는 법을 배웠다. 이제 그 의미를 정확히 말할 수 있다. 트레이스백은 **예외가 발생한 곳에서 프로그램 맨 바깥까지, 예외가 거슬러 올라온 길**이다. 위에서 아래로 읽으면 함수가 호출된 순서이고, 아래에서 위로 읽으면 예외가 올라온 순서다. 이 중 어느 층에든 `try`/`except`를 두면 그 층에서 예외가 멈춘다.

| 트레이스백에서 | 읽는 법 |
|---|---|
| 마지막 줄 | 예외 클래스와 메시지. 무슨 일이 일어났나 |
| 마지막 `File` 줄 | 예외가 **발생한** 곳 |
| 그 위의 `File` 줄들 | 그 코드를 **호출한** 곳들. 원인(잘못된 값)이 어디서 왔는지 거슬러 올라가며 찾는다 |
| 첫 번째 `File` 줄 | 프로그램의 시작점(`<module>`) |

그렇다면 예외를 **어느 층에서** 잡아야 할까? 위 예에서 `parse_price()`는 `"두 개"`를 받았을 때 무엇을 해야 할지 모른다. 0원으로 칠지, 건너뛸지, 사용자에게 다시 물을지는 이 함수가 정할 일이 아니다. 반면 `main()`은 프로그램 전체를 알고 있으므로 "사용자에게 알린다"는 결정을 내릴 수 있다. **예외는 대처 방법을 아는 층에서 잡는다.** 이 판단은 6.2.6에서 자세히 다룬다.

### 6.1.10 미리 검사할까, 일단 해 볼까

실패할 수 있는 일을 다루는 방법은 두 가지다.

```python
# 방법 1: 미리 검사한다
if text.isdecimal():
    count = int(text)
else:
    print("숫자로 입력하세요.")

# 방법 2: 일단 해 보고, 실패하면 처리한다
try:
    count = int(text)
except ValueError:
    print("숫자로 입력하세요.")
```

방법 1은 "뛰기 전에 살펴보라(Look Before You Leap)"는 뜻의 **LBYL**, 방법 2는 "허락을 구하는 것보다 용서를 구하는 것이 쉽다(Easier to Ask for Forgiveness than Permission)"는 뜻의 **EAFP**라는 이름으로 부르기도 한다. 파이썬은 두 방법을 모두 쓰지만, 방법 2를 더 파이썬다운 방식으로 여기는 편이다. 두 방법을 비교해 보자.

| | 미리 검사 | 일단 해 보기 |
|---|---|---|
| `"42"` | 통과 | 성공 |
| `"-5"` | **거부**(음수를 받아야 한다면 틀린 결과) | 성공 (`-5`) |
| `" 42 "` | **거부** | 성공 (`int()`는 앞뒤 공백을 무시한다) |
| `"3.14"` | 거부 | `ValueError` |
| 검사 코드 | 바꾸는 규칙을 우리가 다시 써야 한다 | `int()`의 규칙을 그대로 쓴다 |

`int()`는 이미 "정수로 바꿀 수 있는지"를 빈틈없이 검사하고 있다. 미리 검사하는 방법은 그 검사를 우리가 **한 번 더, 그것도 불완전하게** 쓰는 셈이다. 날짜, 실수, JSON 문자열처럼 모양이 복잡할수록 이 차이가 커진다.

그렇다고 언제나 `try`가 나은 것은 아니다. 딕셔너리에 키가 있는지는 `in`이나 `get()`(3.4.2)으로 확인하는 편이 짧고 읽기 쉽다.

```python
# 둘 다 좋다. 이 경우에는 get()이 더 간단하다
price = prices.get(menu)
if price is None:
    print("없는 메뉴입니다.")

try:
    price = prices[menu]
except KeyError:
    print("없는 메뉴입니다.")
```

판단 기준을 정리하면 다음과 같다.

- **검사가 간단하고 정확하다면** 미리 검사해도 좋다. `in`, `get()`, `if not items:`, `if people < 1:` 같은 것이다.
- **검사가 복잡하거나, 변환·처리하는 함수가 이미 검사를 하고 있다면** 일단 해 보고 예외를 처리한다. `int()`, `float()`, `date.fromisoformat()`, 7장의 파일 열기, JSON 해석이 그렇다.
- **검사한 뒤에 상황이 바뀔 수 있다면** 일단 해 본다. 파일이 있는지 확인한 순간과 파일을 여는 순간 사이에 다른 프로그램이 파일을 지울 수도 있다. 프로그램 바깥의 것은 확인한 그대로 있으리라는 보장이 없다.

**잘못 입력하면 다시 묻기**

사용자 입력을 받을 때 가장 자주 쓰는 모양을 익혀 두자. 올바른 값이 들어올 때까지 반복해서 묻는 함수다.

```python
# split_bill6.py
def input_int(prompt, minimum):
    """minimum 이상의 정수를 입력받아 돌려준다. 잘못 입력하면 다시 입력받는다."""
    while True:
        text = input(prompt)
        try:
            number = int(text)
        except ValueError:
            print(f"정수로 입력하세요: {text!r}")
            continue
        if number < minimum:
            print(f"{minimum} 이상으로 입력하세요.")
            continue
        return number


total = input_int("총 금액: ", 0)
people = input_int("인원 수: ", 1)
print(f"1인당 {total // people:,}원")
```

```
총 금액: 5만
정수로 입력하세요: '5만'
총 금액: 50000
인원 수: 0
1 이상으로 입력하세요.
인원 수: -3
1 이상으로 입력하세요.
인원 수: 네 명
정수로 입력하세요: '네 명'
인원 수: 4
1인당 12,500원
```

- "정수인가"는 `int()`에게 맡기고(일단 해 보기), "1 이상인가"는 간단하므로 `if`로 검사했다(미리 검사). 두 방법을 함께 쓴 것이다.
- 인원 수가 1 이상이라는 것이 보장되므로 `total // people`에서 `ZeroDivisionError`가 날 일이 없다. 예외를 잡는 대신 **예외가 날 수 없는 상황을 만든** 것이다.
- 메시지의 `{text!r}`는 5.2.4에서 배운 `repr()` 모양이다. 사용자가 공백만 입력했을 때 `정수로 입력하세요: '  '`처럼 무엇을 입력했는지 보여 준다.

### 6.1.11 디버거로 예외가 난 순간 보기

트레이스백은 예외가 지나온 길을 보여 주지만, 그 순간 **변수에 어떤 값이 들어 있었는지**는 보여 주지 않는다. VS Code 디버거를 쓰면 예외가 난 바로 그 순간에 멈춰서 변수를 확인할 수 있다.

**처리되지 않은 예외에서 멈추기**

1. `propagation2.py`를 열고, **중단점을 찍지 않은 채** `F5`로 디버깅을 시작한다.
2. 프로그램이 `return int(text)` 줄에서 멈추고, 그 줄 아래에 예외 종류와 메시지(`Exception has occurred: ValueError ...`)가 표시된다.
3. 왼쪽 변수 패널에서 `text`가 `'두 개'`인 것을 확인한다.
4. 호출 스택 패널에는 `parse_price`, `total_price`, `main`, `<module>`이 쌓여 있다. 트레이스백과 같은 목록이다. `total_price`를 클릭하면 그 함수의 변수(`texts`, `total`)로 바뀐다. `total`이 `4700`인 것으로, 앞의 두 가격까지는 처리되었다는 것을 알 수 있다.
5. `F5`(계속)를 누르면 프로그램이 트레이스백을 출력하고 끝난다.

디버깅 중에 아무도 잡지 않은 예외가 나면 VS Code는 기본 설정에서 그 자리에 멈춘다. 중단점을 어디에 찍어야 할지 모를 때 특히 유용하다.

**잡힌 예외에서도 멈추기**

`propagation.py`처럼 예외를 잡는 프로그램은 디버깅해도 멈추지 않는다. 예외가 잡혀서 "처리되지 않은 예외"가 아니기 때문이다. 잡힌 예외가 **처음 발생한 곳**을 보고 싶으면 실행 및 디버그 보기(왼쪽 막대의 벌레가 그려진 삼각형 아이콘) 아래쪽의 **중단점**(BREAKPOINTS) 패널에서 **Raised Exceptions**(발생한 예외)에 체크한다. 그러면 예외가 발생하는 모든 순간에 멈춘다. 확인이 끝나면 체크를 해제하자. 켜 둔 채로 두면 라이브러리 안에서 정상적으로 잡고 처리하는 예외에서까지 멈춰 번거롭다. (패널의 항목 이름은 VS Code와 파이썬 확장의 버전에 따라 조금 다를 수 있다.)

## 6.2 예외 발생과 정의

6.1에서는 파이썬이나 라이브러리가 일으킨 예외를 **받는 쪽**이었다. 이 절에서는 내가 만든 함수와 클래스에서 예외를 **일으키는 쪽**이 된다.

### 6.2.1 `raise` — 예외 일으키기

4.1.9의 `average()`를 떠올려 보자. 빈 리스트를 넘기면 `ZeroDivisionError: division by zero`가 났다. 0으로 나누는 코드를 쓴 적이 없는 호출자에게는 알쏭달쏭한 메시지다. 진짜 문제는 "빈 리스트의 평균을 구하려 했다"는 것이다. 이럴 때는 함수가 **직접** 예외를 일으켜 무엇이 잘못되었는지 알려 준다. 다음 함수를 셸에 붙여 넣자.

```python
def average(scores):
    """scores의 평균을 돌려준다. scores가 비어 있으면 ValueError를 일으킨다."""
    if not scores:
        raise ValueError("빈 리스트의 평균은 구할 수 없습니다")
    return sum(scores) / len(scores)
```

```python
>>> average([90, 85, 77])
84.0
>>> average([])
Traceback (most recent call last):
  File "<python-input-3>", line 1, in <module>
    average([])
    ~~~~~~~^^^^
  File "<python-input-1>", line 4, in average
    raise ValueError("빈 리스트의 평균은 구할 수 없습니다")
ValueError: 빈 리스트의 평균은 구할 수 없습니다
```

`raise 예외객체`는 그 자리에서 예외를 일으킨다. 6.1.3에서 만들어 보기만 했던 예외 객체를 이번에는 **던진** 것이다. `raise`가 실행되면 그 아래 줄은 실행되지 않는다. 그다음은 파이썬이 일으킨 예외와 똑같이 6.1의 규칙을 따른다.

- `raise`가 같은 함수 안의 `try` 블록 안에 있고 맞는 `except`가 있으면, 그 `except` 블록으로 건너뛰고 **함수는 계속 실행된다.**
- 같은 함수 안에서 잡히지 않으면, `finally`가 있으면 그것을 실행한 뒤 함수가 그 자리에서 끝나고 예외가 호출한 쪽으로 거슬러 올라간다(6.1.9). 위의 `average([])`가 이 경우다.
- 끝까지 아무도 잡지 않으면 트레이스백이 나온다.

그래서 "`raise`는 `return`처럼 함수를 끝낸다"는 말은 **그 함수 안에서 잡지 않을 때만** 맞다. 같은 함수 안에서 일으키고 잡는 예는 실습 6-2의 (나)와 6.2.6의 `retry_demo.py`에서 볼 수 있다.

`raise ValueError`처럼 괄호 없이 클래스만 써도 되지만, 메시지가 없으면 무엇이 잘못되었는지 알 수 없으므로 거의 언제나 메시지를 넣는다. 그리고 함수가 어떤 경우에 어떤 예외를 일으키는지 **독스트링에 적어 둔다.** 호출하는 쪽은 그것을 보고 무엇을 잡을지 정한다. 파이썬 공식 문서도 같은 방식으로 쓰여 있다. 표준 라이브러리 `statistics` 모듈의 평균 함수 `statistics.mean([])`을 실행해 보면 `StatisticsError: mean requires at least one data point`가 난다. `StatisticsError`는 `ValueError`의 자식이다.

**계좌 규칙을 예외로 지키기**

5장 5.2.7의 `Account`는 금액이 0 이하이거나 잔액이 모자라면 `False`를 돌려주었다. 이번에는 예외를 일으키도록 바꿔 보자. 셸에 붙여 넣는다.

```python
class Account:
    def __init__(self, owner, balance=0):
        if balance < 0:
            raise ValueError(f"초기 잔액은 0원 이상이어야 합니다: {balance}")
        self.owner = owner
        self._balance = balance
    @property
    def balance(self):
        return self._balance
    def deposit(self, amount):
        if amount <= 0:
            raise ValueError(f"입금액은 0보다 커야 합니다: {amount}")
        self._balance += amount
    def withdraw(self, amount):
        if amount <= 0:
            raise ValueError(f"출금액은 0보다 커야 합니다: {amount}")
        if amount > self._balance:
            raise ValueError(f"잔액이 부족합니다 (잔액 {self._balance:,}원, 요청 {amount:,}원)")
        self._balance -= amount
    def __repr__(self):
        return f"Account({self.owner!r}, {self._balance!r})"
```

```python
>>> a = Account("철수", 10000)
>>> a.withdraw(3000)
>>> a
```

검사를 **잔액을 바꾸기 전에** 했으므로, 예외가 나면 잔액은 그대로다. 예외를 일으키는 메서드는 "규칙에 맞으면 끝까지 하고, 맞지 않으면 **아무것도 바꾸지 않고** 예외를 일으킨다"가 원칙이다. **예외는 그 전에 이미 바꾼 것을 되돌려 주지 않는다.** 잔액을 줄인 뒤에 예외가 나면 줄어든 잔액은 그대로 남는다. 그래서 검사를 모두 먼저 하고, 바꾸는 일은 맨 마지막에 한다. 여러 단계를 거치는 작업이라 중간에 실패할 수밖에 없는 경우에 바꾼 것을 직접 되돌리는 방법은 6.2.5에서 본다.

5장에서 "`False`를 돌려줄 수 없는 `__init__` 안의 검사는 6장에서 한다"고 미뤄 둔 것도 이제 할 수 있다.

```python
>>> b = Account("영희", -5000)

    raise ValueError(f"초기 잔액은 0원 이상이어야 합니다: {balance}")
ValueError: 초기 잔액은 0원 이상이어야 합니다: -5000
>>> b
Traceback (most recent call last):

NameError: name 'b' is not defined
```

5.1.4에서 `Account("영희", -5000)`을 실행하면 파이썬이 "1) 빈 객체를 만들고, 2) `__init__`을 호출하고, 3) 그 객체를 돌려준다"고 했다. 객체 자체는 1)에서 이미 만들어졌지만, 2)의 `__init__`에서 예외가 났으므로 3)까지 가지 못한다. 초기화에 실패한 객체는 **호출한 쪽에 돌려지지 않고**, 할당문도 실행되지 않으므로 `b`에 아무것도 대입되지 않는다. 그래서 `b`라는 이름이 생기지 않았다. (`b`가 이미 다른 값을 가리키고 있었다면 그 값이 그대로 남는다.) 아무도 가리키지 않는 반쯤 만든 객체는 파이썬이 알아서 치운다.

결과적으로 **규칙에 맞지 않는 객체는 손에 넣을 수 없게** 만든 것이다. 손에 넣은 객체라면 규칙을 지키고 있다고 믿고 쓸 수 있다.

### 6.2.2 실패를 알리는 두 가지 방법 — 반환값과 예외

함수가 맡은 일을 해낼 수 없을 때 그 사실을 알리는 방법은 두 가지다. 5장까지는 **반환값**(`False`, `None`, 안내 메시지)으로 알렸고, 이 장에서는 **예외**로 알린다. 반환값으로 알리는 방법의 약점을 정리해 보자.

**1) 확인하는 것을 잊으면 실패가 묻힌다**

5.2.7의 `Account`는 잔액이 모자라면 `False`를 돌려주었다.

```python
chulsoo.withdraw(50000)          # False를 돌려주었지만 아무도 보지 않는다
print("5만 원을 출금했습니다.")    # 출금하지 않았는데 출금했다고 안내한다
```

결과를 확인하지 않아도 파이썬은 아무 말도 하지 않는다. 프로그램은 잘못된 안내를 하며 계속 실행된다. 예외는 다르다. 잡지 않으면 프로그램이 멈추므로 **무시할 수 없다.** 실패를 조용히 넘기려면 `except`를 써서 "일부러" 무시해야 한다.

**2) 실패가 엉뚱한 곳에서 드러난다**

5장 실습 5-5의 `find()`는 없는 도서이면 `None`을 돌려주었다. 호출한 쪽이 이를 확인하지 않으면 어떻게 될까?

```python
book = library.find("X99")   # None
...                          # 다른 코드가 한참 실행된 뒤
print(book.title)            # AttributeError: 'NoneType' object has no attribute 'title'
```

6.1.4에서 본 `'NoneType' object has no attribute`다. 오류는 `print()` 줄에서 났지만 원인은 훨씬 앞의 `find()`에 있다. 예외로 알렸다면 `find("X99")`를 호출한 바로 그 줄에서 `BookNotFoundError: 없는 도서 코드입니다: X99`처럼 **원인이 이름 붙은 채로** 멈췄을 것이다.

**3) 왜 실패했는지 알 수 없다**

`withdraw()`가 `False`를 돌려주었을 때, 그것이 금액이 음수라서인지 잔액이 모자라서인지 호출한 쪽은 알 수 없다. 예외는 **종류**(클래스)와 **메시지**, 필요하면 **추가 정보**(6.2.4)까지 담아 전달한다.

**4) 반환값을 쓸 수 없는 곳이 있다**

`__init__`은 아무것도 돌려줄 수 없다. 프로퍼티에 값을 할당하는 코드(6.2.3)도 마찬가지다. 이런 곳에서 실패를 알리는 방법은 예외뿐이다.

**그렇다면 반환값은 언제 쓰나**

파이썬은 두 방법을 모두 쓴다. 문자열에서 위치를 찾는 메서드는 두 가지가 있다. `"hello".find("z")`는 `-1`을 돌려주고, `"hello".index("z")`는 `ValueError`를 일으킨다. 딕셔너리도 `prices.get("모카")`는 `None`을 돌려주고, `prices["모카"]`는 `KeyError`를 일으킨다.

- **"없을 수도 있다"가 정상적인 결과의 하나**이고 호출한 쪽이 당연히 확인할 것이라면 반환값(`None`, `-1`)이 편하다. "이 단어가 문장에 있나?", "이 설정값이 있으면 쓰고 없으면 기본값"이 그렇다.
- **함수가 약속한 일을 해낼 수 없는 것**이라면 예외를 일으킨다. "이 계좌에서 출금하라", "이 도서를 대출하라"는 요청이 규칙에 어긋나면, 그것은 결과가 아니라 실패다.

함수 이름과 독스트링이 이 약속을 드러내야 한다. `find()`라는 이름은 "못 찾을 수도 있다"는 느낌을 주지만, 실습 6-3에서는 독스트링에 "없으면 `BookNotFoundError`를 일으킨다"고 밝혀 약속을 분명히 한다.

### 6.2.3 어떤 예외를 일으킬까

**내장 예외를 먼저 고려한다**

새 예외 클래스를 만들기 전에, 뜻이 맞는 내장 예외가 있으면 그것을 쓴다. 가장 자주 쓰는 두 가지는 다음과 같다.

| 상황 | 일으킬 예외 | 예 |
|---|---|---|
| 인자의 자료형은 맞는데 값이 규칙에 맞지 않는다 | `ValueError` | 음수 금액, 빈 리스트, 범위를 벗어난 점수 |
| 인자의 자료형이 아예 맞지 않는다 | `TypeError` | 정수 자리에 문자열 |

**메시지에는 무엇이 잘못되었는지와 그 값을 쓴다**

`ValueError("잘못된 값")`보다 `ValueError(f"출금액은 0보다 커야 합니다: {amount}")`가 훨씬 낫다. 트레이스백의 마지막 줄만 보고도 **어떤 규칙**을 **어떤 값**이 어겼는지 알 수 있어야 한다. 값이 문자열이면 `{value!r}`로 따옴표까지 보여 주면 빈 문자열이나 공백을 알아보기 쉽다.

**프로퍼티에 할당할 때 검사하기 — setter**

5.2.6의 상자글에서 `@balance.setter`를 붙인 메서드를 만들면 `a.balance = 값`으로 할당할 때 그 메서드가 호출된다고 했다. 이제 `raise`를 배웠으니 할당되는 값을 검사할 수 있다. 예금주 이름은 바꿀 수 있되, 빈 이름은 막아 보자. 셸에 붙여 넣는다.

```python
class Account:
    def __init__(self, owner):
        self.owner = owner
    @property
    def owner(self):
        return self._owner
    @owner.setter
    def owner(self, value):
        value = value.strip()
        if not value:
            raise ValueError("예금주 이름이 비어 있습니다")
        self._owner = value
```

```python
>>> a = Account(" 김철수 ")
>>> a.owner
'김철수'
>>> a.owner = "김영희"
>>> a.owner
'김영희'
>>> a.owner = "   "
Traceback (most recent call last):
  File "<python-input-6>", line 1, in <module>
    a.owner = "   "
    ^^^^^^^
  File "<python-input-1>", line 11, in owner
    raise ValueError("예금주 이름이 비어 있습니다")
ValueError: 예금주 이름이 비어 있습니다
>>> a.owner
'김영희'
>>> Account("")
Traceback (most recent call last):
  File "<python-input-8>", line 1, in <module>
    Account("")
    ~~~~~~~^^^^
  File "<python-input-1>", line 3, in __init__
    self.owner = owner
    ^^^^^^^^^^
  File "<python-input-1>", line 11, in owner
    raise ValueError("예금주 이름이 비어 있습니다")
ValueError: 예금주 이름이 비어 있습니다
```

- `@property`로 읽는 메서드를 만든 뒤, `@프로퍼티이름.setter`를 붙여 **같은 이름**으로 할당하는 메서드를 만든다. 할당되는 값이 `value` 매개변수로 들어온다.
- 실제 값은 `self._owner`에 저장한다. setter 안에서 `self.owner = value`라고 쓰면 setter가 자기 자신을 다시 호출하게 되므로 반드시 밑줄 붙은 이름에 저장한다.
- `__init__`에서도 `self._owner = owner`가 아니라 `self.owner = owner`라고 썼다. 그래서 객체를 만들 때도 setter를 거쳐 같은 검사를 받는다. 트레이스백에서 `__init__` → `owner`(setter) 순으로 호출된 것을 확인할 수 있다. **검사 규칙이 한 곳에만 있으므로** 규칙을 바꿀 때도 한 곳만 고치면 된다.

**데이터 클래스에서 검사하기 — `__post_init__`**

5.4.3에서 데이터 클래스의 타입 힌트는 설명일 뿐, 파이썬이 실행 중에 검사하지 않는다고 했다. 바깥에서 들어온 데이터의 값과 자료형을 확인하고 싶으면 `__post_init__` 메서드를 만든다. `@dataclass`가 만든 `__init__`은 필드에 값을 다 넣은 **뒤에** `__post_init__`이 있으면 호출해 준다(post는 "뒤에"라는 뜻이다).

```python
>>> from dataclasses import dataclass
```

```python
@dataclass
class Product:
    name: str
    price: int
    def __post_init__(self):
        if not isinstance(self.price, int):
            raise TypeError(f"price는 정수여야 합니다: {self.price!r}")
        if self.price < 0:
            raise ValueError(f"price는 0 이상이어야 합니다: {self.price}")
```

```python
>>> Product("커피", 2500)
Product(name='커피', price=2500)
>>> Product("커피", "2500")
Traceback (most recent call last):
  File "<python-input-4>", line 1, in <module>
    Product("커피", "2500")
    ~~~~~~~^^^^^^^^^^^^^^^^
  File "<string>", line 5, in __init__
  File "<python-input-2>", line 7, in __post_init__
    raise TypeError(f"price는 정수여야 합니다: {self.price!r}")
TypeError: price는 정수여야 합니다: '2500'
>>> data = {"name": "커피", "price": -100}
>>> Product(**data)
Traceback (most recent call last):
  File "<python-input-6>", line 1, in <module>
    Product(**data)
    ~~~~~~~^^^^^^^^
  File "<string>", line 5, in __init__
  File "<python-input-2>", line 9, in __post_init__
    raise ValueError(f"price는 0 이상이어야 합니다: {self.price}")
ValueError: price는 0 이상이어야 합니다: -100
```

트레이스백 중간의 `File "<string>", line 5, in __init__`은 `@dataclass`가 자동으로 만든 `__init__`이다. 우리가 쓴 파일이 아니라서 코드 줄이 보이지 않는다. 5.4.7처럼 딕셔너리를 데이터 클래스로 바꾸는 순간 검사가 이루어지므로, JSON이나 API 응답처럼 바깥에서 들어온 데이터를 **프로그램 안으로 들이는 입구**에서 잘못된 값을 걸러 낼 수 있다. 이 일을 훨씬 풍부하게 해 주는 라이브러리가 LLM 응용 개발에서 자주 쓰는 Pydantic이다.

> **모든 함수에서 자료형을 검사해야 할까**
> 아니다. 함수마다 `isinstance()`로 인자의 자료형을 검사하면 코드가 길어지고 읽기 어려워진다. 우리 프로그램 안에서 주고받는 값은 타입 힌트와 VS Code의 도움을 받아 맞게 쓰고, 잘못 쓰면 파이썬이 알아서 `TypeError`를 낸다. 검사는 **바깥에서 들어오는 데이터의 입구**(사용자 입력, 파일, API 응답)와 **객체의 규칙을 지켜야 하는 곳**(`__init__`, setter, 상태를 바꾸는 메서드)에 집중한다.

### 6.2.4 사용자 정의 예외 클래스

6.2.1의 `withdraw()`는 금액이 잘못되었을 때도, 잔액이 모자랄 때도 `ValueError`를 일으켰다. 그런데 ATM 화면을 만든다고 하자. 금액을 잘못 입력했으면 "금액을 확인하세요"라고 하면 되지만, 잔액이 모자라면 "얼마가 모자란지" 알려 주고 싶다. 두 경우가 같은 `ValueError`이니 구별할 방법은 메시지 문자열을 비교하는 것뿐이다.

```python
except ValueError as e:
    if str(e).startswith("잔액이 부족"):   # 메시지 문구를 바꾸면 깨진다
        ...
```

메시지는 사람이 읽으라고 쓴 문장이다. 문구를 다듬는 순간 이 코드는 조용히 동작하지 않게 된다. 실패의 **종류**를 구별해야 한다면 종류마다 **클래스**를 만든다. 예외도 클래스이므로 5장에서 배운 상속으로 만들 수 있다.

```python
class BankError(Exception):
    """은행 업무 규칙에 어긋나는 요청일 때 일으키는 예외의 부모 클래스."""
```

이것으로 완성이다. 본문에는 독스트링만 있으면 된다(독스트링도 문장이므로 `pass`가 없어도 된다). `Exception`을 상속했으므로 메시지를 넣어 만들고, `raise`로 일으키고, `except`로 잡는 모든 기능을 물려받는다.

잔액 부족은 조금 더 신경 써서 만들어 보자. "얼마가 모자란가"를 메시지에서 뽑아내지 않고 **속성으로 꺼낼 수 있게** `__init__`을 만든다. 셸에 차례로 붙여 넣는다.

```python
class InsufficientBalanceError(BankError):
    """잔액이 부족해 출금할 수 없다."""
    def __init__(self, balance, amount):
        super().__init__(f"잔액이 부족합니다 (잔액 {balance:,}원, 요청 {amount:,}원)")
        self.balance = balance
        self.amount = amount
    @property
    def shortage(self):
        """모자라는 금액."""
        return self.amount - self.balance
```

```python
>>> e = InsufficientBalanceError(7000, 50000)
>>> e
InsufficientBalanceError('잔액이 부족합니다 (잔액 7,000원, 요청 50,000원)')
>>> str(e)
'잔액이 부족합니다 (잔액 7,000원, 요청 50,000원)'
>>> e.shortage
43000
>>> isinstance(e, BankError), isinstance(e, Exception), isinstance(e, ValueError)
(True, True, False)
>>> raise e
Traceback (most recent call last):
  File "<python-input-8>", line 1, in <module>
    raise e
InsufficientBalanceError: 잔액이 부족합니다 (잔액 7,000원, 요청 50,000원)
```

- `__init__`에서 메시지를 만들어 **`super().__init__(메시지)`**로 부모(`Exception`)에게 넘긴다. 이것을 빠뜨리면 `str(e)`가 우리가 만든 메시지가 아니라 `(7000, 50000)`처럼 객체를 만들 때 넘긴 인자들을 보여 준다. 자식 클래스에서 `__init__`을 오버라이딩하면 `super().__init__(...)`부터 부른다는 5.3.4의 규칙 그대로다.
- 호출한 쪽이 쓸 정보(`balance`, `amount`)는 속성으로 저장하고, 계산한 값은 프로퍼티(`shortage`)로 제공했다. 예외도 클래스이므로 5장에서 배운 것을 모두 쓸 수 있다.

이제 계좌 클래스와 이것을 쓰는 ATM 함수를 스크립트로 정리하자. `ch06` 폴더에 `bank.py`를 만든다.

```python
# bank.py
class BankError(Exception):
    """은행 업무 규칙에 어긋나는 요청일 때 일으키는 예외의 부모 클래스."""


class InsufficientBalanceError(BankError):
    """잔액이 부족해 출금할 수 없다."""

    def __init__(self, balance, amount):
        super().__init__(f"잔액이 부족합니다 (잔액 {balance:,}원, 요청 {amount:,}원)")
        self.balance = balance
        self.amount = amount

    @property
    def shortage(self):
        """모자라는 금액."""
        return self.amount - self.balance


class Account:
    """은행 계좌."""

    def __init__(self, owner, balance=0):
        if balance < 0:
            raise ValueError(f"초기 잔액은 0원 이상이어야 합니다: {balance}")
        self.owner = owner
        self._balance = balance

    @property
    def balance(self):
        """현재 잔액."""
        return self._balance

    def deposit(self, amount):
        """amount원을 입금한다. 금액이 0 이하이면 ValueError를 일으킨다."""
        if amount <= 0:
            raise ValueError(f"입금액은 0보다 커야 합니다: {amount}")
        self._balance += amount

    def withdraw(self, amount):
        """amount원을 출금한다.

        금액이 0 이하이면 ValueError, 잔액이 모자라면 InsufficientBalanceError를 일으킨다.
        """
        if amount <= 0:
            raise ValueError(f"출금액은 0보다 커야 합니다: {amount}")
        if amount > self._balance:
            raise InsufficientBalanceError(self._balance, amount)
        self._balance -= amount

    def transfer(self, other, amount):
        """other 계좌로 amount원을 이체한다. 출금할 수 없으면 withdraw()의 예외가 그대로 전달된다."""
        self.withdraw(amount)
        other.deposit(amount)

    def __repr__(self):
        return f"Account({self.owner!r}, {self._balance!r})"


def atm_withdraw(account, amount):
    """ATM 화면처럼 출금 결과를 안내한다."""
    try:
        account.withdraw(amount)
    except InsufficientBalanceError as e:
        print(f"출금할 수 없습니다. {e.shortage:,}원이 모자랍니다.")
    except ValueError as e:
        print(f"금액을 확인하세요: {e}")
    else:
        print(f"{amount:,}원을 출금했습니다. 남은 잔액은 {account.balance:,}원입니다.")


chulsoo = Account("철수", 10000)
younghee = Account("영희")
atm_withdraw(chulsoo, 3000)
atm_withdraw(chulsoo, 50000)
atm_withdraw(chulsoo, 0)

try:
    chulsoo.transfer(younghee, 5000)
    chulsoo.transfer(younghee, 5000)
except BankError as e:
    print(f"이체 실패: {e}")
print(chulsoo, younghee)
```

```

출금할 수 없습니다. 43,000원이 모자랍니다.
금액을 확인하세요: 출금액은 0보다 커야 합니다: 0
이체 실패: 잔액이 부족합니다 (잔액 2,000원, 요청 5,000원)
Account('철수', 2000) Account('영희', 5000)
```

눈여겨볼 점이 몇 가지 있다.

- `atm_withdraw()`는 **예외의 종류**로 대처 방법을 나누었다. 메시지 문구를 아무리 바꿔도 이 코드는 그대로 동작한다.
- `transfer()`는 5장에서 `if not self.withdraw(amount): return False`였던 것이 두 줄로 줄었다. 출금에 실패하면 `withdraw()`의 예외가 `transfer()`를 그 자리에서 끝내고 호출한 쪽으로 올라가므로(6.1.9), **입금 줄은 실행되지 않는다.** 실패를 확인하고 전달하는 코드를 직접 쓸 필요가 없다. 그런데 반대로 출금은 성공했는데 **입금에서** 예외가 나면 어떻게 될까? 출금된 돈은 되돌아오지 않는다(6.2.1). 이 `Account`만 쓴다면 출금에 성공한 금액은 0보다 크므로 입금이 실패할 일이 없지만, 계좌가 아닌 값을 넘기거나 입금을 거부하는 계좌가 생기면 이야기가 달라진다. 이 문제는 6.2.5에서 고친다.
- 마지막 부분은 `except BankError:`로 잡았다. 나중에 "거래 정지 계좌", "1일 이체 한도 초과" 같은 은행 업무 오류가 생겨도 `BankError`의 자식으로 만들기만 하면 이 코드는 고칠 필요가 없다. 5.3.5의 다형성이 예외에도 그대로 적용된다.

**사용자 정의 예외를 만드는 관례**

- 이름은 `~Error`로 끝낸다. 내장 예외와 라이브러리의 예외가 모두 그렇다.
- `BaseException`이 아니라 **`Exception`**을 상속한다. `BaseException`의 다른 자식들(`KeyboardInterrupt` 등)은 프로그램을 멈추기 위한 특별한 예외이기 때문이다.
- 프로그램이나 라이브러리마다 **부모 예외 하나**(`BankError`, `LibraryError`)를 두고, 구체적인 예외는 그 자식으로 만든다. 사용하는 쪽은 "이 라이브러리의 오류는 모두" 잡을 수도 있고 하나만 골라 잡을 수도 있다. OpenAI 라이브러리의 예외도 `openai.OpenAIError`라는 부모 아래에 `APIConnectionError`, `RateLimitError` 같은 자식들이 있다.
- 금액이 음수인 것처럼 내장 예외(`ValueError`)로 충분히 뜻이 통하는 경우에는 새 클래스를 만들지 않아도 된다. **호출한 쪽이 구별해서 대처해야 할 실패**에 클래스를 만든다.
- 메시지를 직접 정하는 예외라면 `KeyError`를 상속하지 않는다. 6.1.3에서 본 것처럼 `KeyError`는 메시지에 작은따옴표를 붙여 보여 준다.

### 6.2.5 예외를 바꿔서 다시 일으키기

**잡은 예외를 그대로 다시 일으키기 — `raise`**

`except` 블록 안에서 예외 객체 없이 `raise`만 쓰면 **방금 잡은 예외를 그대로 다시** 일으킨다. 예외가 지나가는 것을 기록만 하고, 대처는 위쪽에 맡길 때 쓴다.

```python
try:
    account.withdraw(amount)
except BankError as e:
    print(f"[기록] {account.owner} 출금 실패: {e}")
    raise
```

이 코드는 실패를 기록한 뒤 예외를 다시 위로 올려 보낸다. 호출한 쪽에서는 이 `try`가 없었던 것처럼 같은 예외를 받는다.

**실패하면 되돌리고 다시 일으키기**

`raise`만 쓰는 모양은 6.2.4에서 미뤄 둔 `transfer()`의 문제를 고칠 때도 쓴다. 지금의 `transfer()`는 출금한 뒤 입금한다. 입금에서 예외가 나면 어떻게 되는지, 터미널에서 `python -i bank.py`로 `bank.py`를 실행한 뒤 셸에서 확인해 보자. 계좌 대신 실수로 `None`을 넘겨 본다.


이체는 실패했는데 민수의 잔액은 3,000원 줄었다. 출금은 이미 끝났고, 입금에서 난 예외가 그것을 되돌려 주지 않기 때문이다(6.2.1). 출금하기 전에 검사해서 막을 수 있으면 가장 좋지만, 상대 계좌가 입금을 받아 줄지는 **입금해 보기 전까지 알 수 없다.** 이런 경우에는 입금에서 예외가 나면 출금을 **직접 되돌린 뒤** 예외를 다시 일으킨다. `bank.py`의 `transfer()`를 다음과 같이 고친다.

```python
    def transfer(self, other, amount):
        """other 계좌로 amount원을 이체한다.

        출금할 수 없으면 withdraw()의 예외가 그대로 전달된다.
        입금에 실패하면 출금을 되돌린 뒤 입금에서 난 예외를 다시 일으킨다.
        """
        self.withdraw(amount)
        try:
            other.deposit(amount)
        except Exception:
            self._balance += amount  # 출금을 되돌린다
            raise
```

`bank.py`를 저장하고 `python -i bank.py`로 다시 실행해 같은 코드를 입력한다.

같은 예외가 나지만, 이번에는 잔액이 그대로다.

- 이 되돌리기에는 **전제가 하나 있다.** 상대 계좌의 `deposit()`이 실패할 때는 자기 잔액을 바꾸지 않고 예외를 일으킨다는 것이다. 지금의 `Account.deposit()`은 검사를 먼저 하고 잔액은 마지막에 바꾸므로(6.2.1) 이 전제를 지킨다. 그런데 어떤 계좌의 `deposit()`이 잔액을 늘린 **뒤에** 예외를 일으킨다면, 송금 계좌는 되돌려지고 상대 계좌에도 돈이 남아 금액이 두 배가 된다. `transfer()`가 되돌릴 수 있는 것은 자기가 바꾼 것(출금)뿐이다. 그래서 "검사를 먼저, 바꾸기는 마지막에"는 한 클래스만의 습관이 아니라, **모든 클래스가 지켜야 서로를 믿고 쓸 수 있는 약속**이다.
- 여기서는 `except Exception:`을 썼다. 6.1.5에서 함부로 쓰지 말라고 했지만, 이 경우는 예외에 **대처하는 것이 아니라** 뒷정리만 하고 `raise`로 그대로 다시 올려 보낸다. 입금이 **어떤 이유로** 실패하든 출금은 되돌려야 하고, 예외를 삼키지도 않으므로 6.2.6의 원칙에 어긋나지 않는다. 6.1.5의 표에서 `except Exception:`을 쓸 수 있다고 한 두 번째 경우가 이것이다.
- 되돌리는 코드는 `self.deposit(amount)`가 아니라 `self._balance += amount`로 썼다. 되돌리기는 새로운 입금이 아니라 "출금을 없던 일로 하기"이기 때문이다. 거래 기록을 남기는 계좌였다면 출금 기록도 함께 지워야 한다.
- 실제 은행이나 쇼핑몰 프로그램은 이런 "모두 성공하거나, 모두 없던 일로 하거나"를 데이터베이스의 **트랜잭션**(transaction) 기능에 맡긴다. 트랜잭션은 위의 전제에 기대지 않고, 작업에 참여한 모든 쪽의 변경을 한꺼번에 확정하거나 한꺼번에 취소해 준다. 그 기능이 무엇을 대신해 주는지는 이 예로 이해할 수 있다.

**다른 예외로 바꿔서 일으키기 — `raise ... from`**

메뉴판에서 가격을 찾는 함수를 만든다고 하자. 메뉴판은 딕셔너리이므로 없는 메뉴를 찾으면 `KeyError`가 난다. 그런데 이 함수를 쓰는 쪽이 "메뉴판이 딕셔너리"라는 사실까지 알아야 할까? 나중에 메뉴판을 데이터베이스에서 읽도록 바꾸면 `KeyError`가 아닌 다른 예외가 날 텐데, 그때마다 호출하는 쪽을 고쳐야 한다. 5.2.5의 캡슐화를 떠올리면, 내부 사정을 드러내는 `KeyError` 대신 **이 함수의 뜻에 맞는 예외**로 바꿔서 알리는 편이 낫다.

```python
# menu_price.py
PRICES = {"아메리카노": 2500, "라떼": 3000}


class MenuNotFoundError(Exception):
    """메뉴판에 없는 메뉴다."""


def get_price(menu):
    """메뉴의 가격을 돌려준다. 메뉴판에 없으면 MenuNotFoundError를 일으킨다."""
    try:
        return PRICES[menu]
    except KeyError:
        raise MenuNotFoundError(f"메뉴판에 없습니다: {menu}")


print(get_price("라떼"))
print(get_price("모카"))
```

1. **맨 마지막 줄**이 최종적으로 프로그램을 멈춘 예외다(`MenuNotFoundError`).
2. 가운데 문장 위쪽이 **먼저 일어난** 예외다(`KeyError`).
3. 위에서 아래로 읽으면 일어난 순서가 된다.

그런데 이 문장은 `except` 블록 안에 **버그가 있을 때**도 똑같이 나온다. 예를 들어 `except` 블록에서 변수 이름을 틀려 `NameError`가 나도 "처리하는 도중에 다른 예외가 발생했다"고 나온다. 위 코드는 일부러 바꾼 것인데, 트레이스백만 보면 실수인지 의도인지 알 수 없다. 의도를 밝히려면 `from`을 쓴다.

```python
    except KeyError as e:
        raise MenuNotFoundError(f"메뉴판에 없습니다: {menu}") from e
```

|---|---|---|
| `During handling of the above exception, another exception occurred:` | `except` 블록 안에서 또 예외가 났다 | `except` 블록에 버그가 없는지 먼저 확인한다 |
| `The above exception was the direct cause of the following exception:` | `raise ... from`으로 일부러 바꿨다 | 위쪽의 원래 예외가 진짜 원인이다 |

이 경우는 사실 6.1.10의 기준대로 `if menu not in PRICES: raise MenuNotFoundError(...)`처럼 미리 검사해도 좋다. `raise ... from`은 라이브러리가 일으킨 예외를 내 프로그램의 예외로 바꿀 때 특히 많이 쓴다. 예를 들어 LLM 응답을 JSON으로 해석하다가 난 `json.JSONDecodeError`(`ValueError`의 자식)를 "LLM이 형식에 맞지 않는 답을 했다"는 뜻의 내 예외로 바꾸는 식이다.

### 6.2.6 예외를 잡을 때와 그대로 둘 때

이 장에서 가장 중요한 절이다. `try`/`except`의 문법은 간단하지만, **어디서** 잡을지 판단하는 데는 연습이 필요하다. 다음 원칙을 기억하자.

**1) 대처할 수 있는 곳에서만 잡는다**

예외를 잡는다는 것은 "이 문제를 내가 해결한다"는 선언이다. 해결이란 다음 중 하나다.

- 사용자에게 다시 입력받는다 (6.1.10의 `input_int()`)
- 다른 방법으로 대신한다 (기본값을 쓴다, 잘못된 항목을 건너뛴다)
- 잠시 뒤에 다시 시도한다 (네트워크, API 호출)
- 사용자가 알아들을 수 있는 메시지로 바꿔 알린다 (`atm_withdraw()`)

이 중 아무것도 할 수 없다면 잡지 말고 **그대로 둔다.** 예외는 위로 올라가서, 대처 방법을 아는 층이 잡을 것이다. 6.1.9의 `parse_price()`가 `ValueError`를 잡지 않은 것, 6.2.4의 `transfer()`가 `withdraw()`의 예외를 잡지 않은 것이 올바른 판단이다.

**2) 좁게 잡는다**

- 대처할 수 있는 예외 클래스만 `except` 뒤에 쓴다. `except:`는 쓰지 않고, `except Exception:`도 꼭 필요한 두 경우, 즉 프로그램의 가장 바깥(아래 5번)과 뒷정리·되돌리기 후 곧바로 `raise`로 다시 올려 보낼 때(6.2.5의 `transfer()`)에만 쓴다(6.1.5).
- `try` 블록에는 예외가 날 것으로 예상하는 줄만 넣고, 나머지는 `else`로 뺀다(6.1.7).

**3) 버그로 생긴 예외는 잡지 말고 고친다**

`TypeError`, `AttributeError`, `NameError`, 그리고 코드의 실수로 생긴 `KeyError`, `IndexError`는 대부분 **코드를 고쳐야** 하는 예외다. 이런 예외를 잡아서 프로그램이 계속 실행되게 만들면 버그가 숨는다. 트레이스백이 나와서 프로그램이 멈추는 것이 오히려 고마운 일이다. 어디를 고쳐야 하는지 정확히 알려 주기 때문이다.

**4) 조용히 삼키지 않는다**

가장 나쁜 코드는 이것이다.

```python
try:
    process(data)
except Exception:
    pass
```

어떤 문제가 생겨도 아무 흔적 없이 넘어간다. 프로그램은 잘 돌아가는 것처럼 보이지만 결과가 틀리고, 왜 틀렸는지 알아낼 단서도 남지 않는다. 1단계에서 AI가 만들어 준 코드에 이런 블록이 있었다면 가장 먼저 의심해 보자. 정말로 무시해도 되는 예외라면, 예외 클래스를 좁게 쓰고 **왜 무시해도 되는지 주석을 남긴다.**

**5) 프로그램의 가장 바깥에서 사용자에게 보여 줄 형태로 바꾼다**

명령을 반복해서 처리하는 프로그램이나 요청을 계속 받는 서버는, 한 요청이 실패했다고 프로그램 전체가 멈추면 곤란하다. 그래서 반복의 가장 바깥에서 예외를 잡아 메시지로 바꾸고 다음 요청을 받는다. 이때도 **업무 규칙에 관한 예외**(`BankError`, `LibraryError`)만 잡아 메시지로 바꾸는 것이 기본이다. 실제 서비스에서는 예상하지 못한 예외까지 `except Exception:`으로 잡는 경우도 있는데, 그때는 반드시 트레이스백을 기록(로그)으로 남겨 개발자가 나중에 원인을 찾을 수 있게 한다. 기록 남기는 방법은 이후 과정에서 배운다.

**판단 연습**

| 상황 | 판단 |
|---|---|
| `input()`으로 받은 문자열을 `int()`로 바꾸다 `ValueError` | 잡는다. 다시 입력받는다 |
| 함수 안에서 인자로 받은 문자열을 `int()`로 바꾸다 `ValueError`, 그런데 이 함수는 사용자와 대화하지 않는다 | 그대로 둔다. 호출한 쪽이 대처한다 (`parse_price()`) |
| 출금 메서드에서 잔액 부족 | 메서드는 예외를 **일으키고**, 화면을 담당하는 쪽이 잡아 안내한다 |
| 내 코드에서 `None.upper()`로 `AttributeError` | 잡지 않는다. `None`이 들어온 곳을 찾아 고친다 |
| 파일 100개 중 하나의 형식이 잘못되어 `ValueError` | 잡는다. 그 파일을 건너뛰고, **건너뛰었다는 사실을 보고한다** |
| LLM API 호출에서 짧은 시간에 요청을 너무 많이 보내 거절당했다는 예외(속도 제한) | 잡는다. 잠시 기다렸다가 다시 시도한다 |
| LLM API 호출에서 사용 한도나 크레딧을 다 썼다는 예외 | 기다려도 풀리지 않으므로 다시 시도하지 않는다. 바깥에서 잡아 "요금제와 사용량을 확인하라"고 알린다 |
| LLM API 호출에서 API 키가 잘못되었다는 예외 | 다시 시도해도 소용없다. 그대로 두거나, 바깥에서 잡아 "설정을 확인하라"고 알리고 끝낸다 |

표의 두 번째 LLM 줄은 주의가 필요하다. OpenAI 라이브러리에서는 속도 제한과 사용 한도 소진이 **같은** `RateLimitError`로 온다(둘 다 HTTP 상태 코드 429다). 예외 클래스만 보고 "기다렸다가 다시 시도"를 정하면, 크레딧이 떨어진 경우에도 소용없는 재시도를 반복하게 된다. 둘을 구별하려면 예외 객체에 담긴 오류 코드와 메시지를 확인해야 한다. 라이브러리 문서에서 **예외 클래스마다 어떤 상황들이 들어 있는지** 확인하는 습관을 들이자.

**재시도 — 일시적인 실패에 대처하기**

판단 표의 속도 제한처럼, AI 엔지니어가 자주 만나는 상황이 "**잠시 뒤에 다시 하면 될 수도 있는** 실패"다. LLM API를 흉내 낸 함수로 재시도하는 코드를 만들어 보자. `retry_demo.py`를 만든다.

```python
# retry_demo.py
import random
import time


class TemporaryServiceError(Exception):
    """잠시 뒤에 다시 시도하면 성공할 수도 있는 오류."""


def call_service(question):
    """LLM API 호출을 흉내 낸다. 60%의 확률로 일시적인 오류가 난다."""
    if random.random() < 0.6:
        raise TemporaryServiceError("서버가 바쁩니다")
    return f"'{question}'에 대한 답변입니다."


def ask_with_retry(question, max_attempts=3):
    """call_service()를 최대 max_attempts번 시도해 답변을 돌려준다.

    모두 실패하면 마지막 TemporaryServiceError를 그대로 일으킨다.
    max_attempts가 1보다 작으면 ValueError를 일으킨다.
    """
    if max_attempts < 1:
        raise ValueError(f"시도 횟수는 1 이상이어야 합니다: {max_attempts}")
    for attempt in range(1, max_attempts + 1):
        try:
            return call_service(question)
        except TemporaryServiceError as e:
            print(f"{attempt}번째 시도 실패: {e}")
            if attempt == max_attempts:
                raise
            time.sleep(1)


def main():
    try:
        answer = ask_with_retry("파이썬이란?")
    except TemporaryServiceError:
        print("지금은 답변할 수 없습니다. 잠시 뒤에 다시 질문해 주세요.")
    else:
        print(answer)


main()
```

여러 번 실행해 보자. 무작위이므로 결과가 매번 다르다.

```
1번째 시도 실패: 서버가 바쁩니다
2번째 시도 실패: 서버가 바쁩니다
'파이썬이란?'에 대한 답변입니다.
```

```
1번째 시도 실패: 서버가 바쁩니다
2번째 시도 실패: 서버가 바쁩니다
3번째 시도 실패: 서버가 바쁩니다
지금은 답변할 수 없습니다. 잠시 뒤에 다시 질문해 주세요.
```

- `random.random()`은 0 이상 1 미만의 실수를 무작위로 돌려준다. 0.6보다 작을 확률이 60%다. `time.sleep(1)`은 프로그램을 1초 동안 멈춘다. 둘 다 표준 라이브러리 함수다.
- `ask_with_retry()`는 `TemporaryServiceError`**만** 잡는다. 이 함수가 대처할 수 있는 것은 "다시 시도하면 되는 실패"뿐이기 때문이다. `call_service()`에 버그가 있어 `TypeError`가 난다면 다시 시도해도 소용없으므로 잡지 않는다.
- 마지막 시도까지 실패하면 `raise`로 잡았던 예외를 **다시 일으켜** 위로 넘긴다. "이제는 내가 대처할 수 없다"는 뜻이다. 그러면 `main()`이 잡아 사용자에게 안내한다. 역할이 나뉜 것을 보자. `ask_with_retry()`는 **다시 시도하는 일**을, `main()`은 **사용자에게 알리는 일**을 맡았다.
- `raise`와 `return`이 모두 `for` 문 안의 `try` 문에 있다는 점도 보자. `call_service()`는 `TemporaryServiceError`를 일으키며 **그 자리에서 끝난다.** 그 예외를 호출한 쪽인 `ask_with_retry()`의 `except`가 잡으므로, **`ask_with_retry()`는 끝나지 않고** 다음 시도로 넘어간다(6.2.1).
- 인자가 올바르고 `call_service()`가 일시적인 오류만 일으킨다면, `ask_with_retry()`가 끝나는 경우는 두 가지다. `return`으로 답변을 돌려줄 때와, 마지막 시도에서 `raise`로 예외를 다시 일으킬 때다. 그 밖에 바로 아래에서 볼 `max_attempts` 검사의 `ValueError`나, `call_service()`의 버그로 생긴 `TypeError`처럼 **이 함수가 잡지 않는 예외**가 나도 `ask_with_retry()`는 그 자리에서 끝나고 예외가 호출한 쪽으로 올라간다.
- 맨 앞에서 `max_attempts`를 검사했다. 이 검사가 없으면 `ask_with_retry("파이썬이란?", max_attempts=0)`은 `range(1, 1)`이 비어 있어 한 번도 시도하지 않고 반복문을 빠져나간다. 그러면 함수 끝까지 내려가 `None`을 돌려주는데(4.1.6), 독스트링이 약속한 "답변을 돌려주거나 예외를 일으킨다" 중 어느 것도 아니다. 호출한 쪽은 `None`을 답변으로 알고 출력하게 된다. 6.2.2의 "실패가 엉뚱한 곳에서 드러난다"를 막으려면, 함수가 약속을 지킬 수 없는 인자는 **들어오는 순간** 거절해야 한다(6.2.3).

실제 LLM 라이브러리에는 이런 재시도 기능이 이미 들어 있는 경우가 많다. 하지만 그 기능을 설정하고, 재시도해도 실패했을 때 무엇을 할지 정하는 것은 여전히 우리 몫이다.

### 실습 6-2. 예외 발생과 정의

**1) 결과 예상하기**

각 코드의 출력을 먼저 예상한 뒤 실행해 확인한다.

```python
# (가)
class AppError(Exception):
    pass


class LoginError(AppError):
    pass


class PaymentError(AppError):
    pass


for error_class in [LoginError, PaymentError, ValueError]:
    try:
        raise error_class("문제 발생")
    except LoginError as e:
        print("로그인:", e)
    except AppError as e:
        print("앱:", type(e).__name__, e)
    except Exception as e:
        print("기타:", repr(e))
```

```python
# (나)
def step(n):
    if n == 2:
        raise ValueError(f"{n}단계 실패")
    print(f"{n}단계 완료")


def run():
    try:
        for n in range(1, 4):
            step(n)
    except ValueError as e:
        print("기록:", e)
        raise
    finally:
        print("정리")


try:
    run()
except ValueError as e:
    print("바깥:", e)
```

```python
# (다)
class TooShortError(ValueError):
    def __init__(self, text, minimum):
        super().__init__(f"{minimum}글자 이상이어야 합니다: {text!r}")
        self.minimum = minimum


def check_password(text):
    if len(text) < 8:
        raise TooShortError(text, 8)
    return True


for pw in ["python3!", "abc"]:
    try:
        print(check_password(pw))
    except ValueError as e:
        print(type(e).__name__, e, getattr(e, "minimum", None))
```

(다)의 `getattr(객체, "이름", 기본값)`은 객체에 그 이름의 속성이 있으면 값을, 없으면 기본값을 돌려주는 내장 함수다. `TooShortError`가 `ValueError`를 상속했으므로 `except ValueError:`로도 잡힌다는 점을 확인하자. `ValueError`를 상속하는 것이 좋은 경우와 `Exception`을 상속하는 것이 좋은 경우를 생각해 보자.

**2) `account3.py` — 예외로 규칙을 지키는 계좌**

6.2.5에서 `transfer()`를 고친 `bank.py`를 `account3.py`로 복사해 다음을 추가한다.

- `MinusAccount(Account)`: 5.3.4의 마이너스 통장이다. `__init__`에서 한도 `limit`(기본값 1,000,000)를 받고, 한도가 음수이면 `ValueError`를 일으킨다. `withdraw()`를 오버라이딩해 잔액이 `-limit`까지 내려갈 수 있게 한다. 한도를 넘으면 `LimitExceededError`를 일으킨다.
- `LimitExceededError(BankError)`: 속성 `limit`(한도)와 `amount`(요청 금액)를 가진다. 메시지는 `한도를 초과합니다 (한도 1,000,000원, 요청 1,500,000원)` 모양으로 만든다.
- `MinusAccount.withdraw()`에서도 금액이 0 이하인지 검사해야 한다. 부모의 검사 코드를 베끼지 않고 재사용하려면 어떻게 해야 할까? (힌트: 금액 검사만 하는 메서드 `_check_amount(amount, kind)`를 `Account`에 만들고 `deposit()`, `withdraw()`, 그리고 자식 클래스의 `withdraw()`가 함께 쓰게 한다. `kind`에는 메시지에 넣을 `"입금"`이나 `"출금"`을 넘긴다. 밑줄로 시작하는 메서드는 5.2.5의 관례대로 "클래스 안에서만 쓰는 메서드"라는 뜻이고, 5.3.2에서 본 것처럼 자식 클래스에서는 써도 된다.)

다음 코드로 시험한다.

```python
accounts = [Account("철수", 10000), MinusAccount("민수", 10000, limit=500000)]
requests = [3000, 20000, -100, 600000]

for acc in accounts:
    for amount in requests:
        try:
            acc.withdraw(amount)
        except BankError as e:
            print(f"{acc.owner} {amount:,}원 실패 - {type(e).__name__}: {e}")
        except ValueError as e:
            print(f"{acc.owner} 금액 오류 - {e}")
        else:
            print(f"{acc.owner} {amount:,}원 출금 - 잔액 {acc.balance:,}원")
```

```
철수 20,000원 실패 - InsufficientBalanceError: 잔액이 부족합니다 (잔액 7,000원, 요청 20,000원)
철수 금액 오류 - 출금액은 0보다 커야 합니다: -100
철수 600,000원 실패 - InsufficientBalanceError: 잔액이 부족합니다 (잔액 7,000원, 요청 600,000원)
민수 3,000원 출금 - 잔액 7,000원
```

**요구 사항**

1. 실습 5-5의 요구 사항(대소문자 처리는 `Library`가 한다, `main()`은 `_` 속성을 쓰지 않는다, `can_borrow()`로 판단한다, `self.LOAN_DAYS`로 읽는다, `Book`은 `frozen=True`)과, 그 안에 포함된 4장 실습 4-7의 요구 사항을 그대로 지킨다. 단, `날짜 N` 검사 방법은 아래 6번으로 바뀐다.
2. `find()`, `borrow()`, `return_book()`은 성공이나 실패를 메시지로 알리지 않는다. 즉 안내 문장을 **출력하지도, 돌려주지도 않는다.** 성공하면 결과 객체(`Book`, `Loan`)를 돌려주고, 실패하면 예외를 일으킨다. (5장 그대로 쓰는 `loan_lines()`, `book_lines()`, `__repr__()`은 목록이나 객체의 모습을 문자열로 돌려주는 메서드이므로 이 요구 사항과 관계없다. 출력하지 않는 것은 마찬가지다.)

4. `borrow()`와 `return_book()`은 `find()`로 도서를 찾는다. `find()`가 일으킨 `BookNotFoundError`는 **잡지 않고** 그대로 호출한 쪽으로 보낸다.

- 순서는 예외 클래스 → `Library.__init__`, `find()` → `borrow()` → `return_book()` → `main()`이 좋다. 예외 클래스는 `Book`과 `Loan` **아래에** 둔다. 예외 클래스의 타입 힌트에서 `Book`과 `Loan`을 쓰기 때문이다.
- 예외 클래스의 `__init__`은 6.2.4의 `InsufficientBalanceError`처럼 메시지를 만들어 `super().__init__(메시지)`로 넘기고, 받은 객체를 속성에 저장한다. 메시지에 도서 제목을 넣을 때는 5장처럼 f-string에 `{book}`만 쓰면 `Book.__str__`이 `'제목'` 모양을 만들어 준다. 날짜는 `format_date()`를 쓴다.
- 주어진 코드의 예외 클래스 `__init__`은 본문이 독스트링뿐이라 실행은 되지만 아무 일도 하지 않는다. 채우지 않은 채로 예외를 일으키면 우리가 정한 메시지 대신 넘긴 객체가 그대로 보이고, `book`이나 `loan` 속성도 없다. 하나씩 채우며 셸에서 `str(NotBorrowableError(Book("R01", "파이썬 사전")))`처럼 확인하자.
- `find()`는 6.1.10의 기준으로 생각해 보자. `in`으로 미리 검사하고 `raise`하는 방법과, `try`/`except KeyError`로 바꿔 일으키는 방법(이때는 6.2.5의 `from`을 쓴다)이 모두 가능하다. 어느 쪽이 더 읽기 쉬운가?
- `borrow()`는 5장의 "실패하는 경우를 먼저 처리하고 조기 반환"하던 모양이 그대로 "실패하는 경우를 먼저 검사하고 `raise`"로 바뀐다. `return f"..."`였던 실패 줄이 `raise ...Error(...)` 줄이 되고, 마지막의 성공 메시지 대신 `Loan` 객체를 돌려준다. 검사는 **대출 기록을 바꾸기 전에** 모두 끝내야 한다(6.2.1).
- `return_book()`은 대출 기록을 지우면서 그 기록을 돌려주어야 한다. 딕셔너리의 `pop()`(3.4)이 바로 그 일을 한다.
- `main()`의 `대출`과 `반납` 처리는 다음 모양이 된다. 연체일수는 돌려받은 `Loan`의 `overdue_days()`로, 연체료는 `library.late_fee()`로 구한다.
  ```python
  try:
      loan = library.borrow(code, who, today)
  except LibraryError as e:
      print(e)
  else:
      print(...)  # 성공 메시지
  ```
- `날짜 N`은 "문자열을 1 이상의 정수로 바꾸고, 그럴 수 없으면 `ValueError`를 일으키는" 작은 함수 `parse_days(text)`를 만들면 `main()`이 깔끔해진다. 1보다 작은 경우에도 `raise ValueError(...)`를 하면, `main()`에서는 `except ValueError:` 하나로 두 경우를 함께 처리할 수 있다.

- 프로그램 맨 아래의 `main()`을 잠시 주석 처리하고 터미널에서 `python -i library.py`로 셸에 들어가 시험한다.

- **연체자 대출 제한**: 연체 중인 도서가 있는 사람은 새로 대출할 수 없게 한다. `OverdueMemberError(LibraryError)`를 만들고, 메시지는 `연체 중인 도서가 있어 대출할 수 없습니다: 철수 ('파이썬 첫걸음' 3일 연체)` 모양으로 한다. `borrow()`에서 이 예외를 일으키도록 고친 뒤, **`main()`을 한 줄도 고치지 않아도** 새 실패가 안내된다는 것을 확인하자. 부모 예외 `LibraryError`로 잡아 둔 덕분이다.
- **1인당 대출 한도**: 한 사람이 동시에 빌릴 수 있는 도서를 클래스 속성 `MAX_LOANS_PER_MEMBER = 3`권으로 제한한다. `BorrowLimitError(LibraryError)`에 속성 `who`와 `limit`을 두고, 메시지는 `대출 한도를 넘었습니다: 민수 (최대 3권)`으로 한다.
- **예외를 확인하는 시험 코드**: "참고 도서를 대출하면 `NotBorrowableError`가 나야 한다"처럼 **예외가 나는 것이 올바른 동작**인 경우도 시험해야 한다. 다음 모양의 함수를 만들어 요구 사항의 실패 경우를 모두 시험해 보자. 이 장에서 배운 `try`/`except`/`else`만으로 만들 수 있다.
  ```python
  def expect_error(error_class, func, *args):
      """func(*args)를 호출해 error_class 예외가 나면 '통과: 클래스이름'을 출력한다.

      예외가 나지 않으면 '실패: 클래스이름 예외가 나지 않았다'를 출력한다.
      """
  ```
  ```python
  lib = Library([Book("B01", "파이썬 첫걸음"), ReferenceBook("R01", "파이썬 사전")])
  today = date(2026, 10, 31)
  expect_error(NotBorrowableError, lib.borrow, "R01", "철수", today)
  expect_error(BookNotFoundError, lib.find, "X99")
  expect_error(NotBorrowedError, lib.return_book, "B01", today)
  expect_error(NotBorrowedError, lib.find, "B01")
  ```
  ```
  통과: NotBorrowableError
  통과: BookNotFoundError
  통과: NotBorrowedError
  실패: NotBorrowedError 예외가 나지 않았다
  ```
  (4.2.6의 `*args`로 인자를 모아 받고, 4.2.8의 `func(*args)`로 풀어서 넘긴다.) 나중에 배울 테스트 도구 `pytest`에는 이 일을 해 주는 `pytest.raises()`가 있다.

## 정리

| 항목 | 핵심 |
|---|---|
| 예외 | 실행 중에 생기는 오류. 문법 오류는 실행 전에, 예외는 그 줄에 도달했을 때 생긴다. 처리되지 않으면 프로그램이 멈추고 트레이스백이 나온다 |
| `try`/`except` | `try` 블록에서 예외가 나면 그 줄에서 곧바로 맞는 `except` 블록으로 건너뛴다. 처리한 뒤에는 `try` 문 다음 줄로 이어진다 |
| `except 클래스 as e` | `e`는 예외 객체. `str(e)`는 메시지, `e.args`는 인자, `type(e).__name__`은 클래스 이름. `as` 이름은 블록 안에서만 쓴다 |
| 주요 내장 예외 | `ValueError`(값이 맞지 않음), `TypeError`(자료형이 맞지 않음), `KeyError`, `IndexError`(없는 키·위치), `FileNotFoundError`(없는 파일), `ZeroDivisionError`, `AttributeError`(없는 속성, 특히 `None`) |
| 예외 계층 | 예외도 클래스. `except 부모:`는 자식 예외도 잡는다(`isinstance`). `LookupError` ⊃ `KeyError`, `IndexError`. 거의 모든 예외는 `Exception`의 자손 |
| `except:` 금지 | Ctrl+C(`KeyboardInterrupt`)까지 잡는다. `except Exception:`은 프로그램의 가장 바깥에서 기록을 남기고 계속 실행할 때와, 뒷정리·되돌리기 후 곧바로 `raise`로 다시 올려 보낼 때만 |
| 여러 `except` | 위에서부터 처음 맞는 하나만 실행. 자식 예외를 먼저. 대처가 같으면 튜플로 묶는다 |
| `else` | 예외가 나지 않았을 때만 실행. `try` 블록을 짧게 유지해 엉뚱한 예외를 잡지 않게 한다 |
| `finally` | 무슨 일이 있어도 마지막에 실행. 뒷정리용. 7장의 `with`가 대신해 주는 경우가 많다 |
| 예외 전파 | 잡지 않은 예외는 함수를 끝내고 호출한 쪽으로 올라간다. 트레이스백은 예외가 지나온 길 |
| 미리 검사 vs 해 보기 | 간단·정확한 검사(`in`, `get()`, 범위)는 미리, 변환·파일·외부 데이터는 해 보고 예외 처리 |
| `raise` | `raise 예외클래스(메시지)`로 일으킨다. 그 아래 줄은 실행되지 않는다. 같은 함수 안의 `except`가 잡으면 함수는 계속 실행되고, 잡지 않으면 `finally`를 실행한 뒤 함수가 끝나고 예외가 호출한 쪽으로 올라간다 |
| 바꾸기 전에 검사 | 예외는 이미 바꾼 것을 되돌려 주지 않는다. 검사를 모두 먼저 하고 바꾸는 일은 마지막에. 중간에 실패할 수 있으면 직접 되돌린 뒤 `raise`로 다시 일으킨다 |
| `__init__`에서 예외 | 객체는 만들어졌지만 초기화에 실패해 호출한 쪽에 돌려지지 않는다. 할당이 일어나지 않으므로 규칙에 맞지 않는 객체는 손에 넣을 수 없다 |
| 반환값 vs 예외 | "없을 수도 있다"가 정상 결과면 반환값(`None`, `-1`), 약속한 일을 못 하면 예외. 반환값은 무시될 수 있고, `__init__`·setter에서는 쓸 수 없다 |
| 검사하는 곳 | `__init__`, `@이름.setter`, 데이터 클래스의 `__post_init__`, 바깥 데이터의 입구 |
| 사용자 정의 예외 | `class 이름Error(Exception):`. 부모 예외 하나 아래에 자식들. 정보는 속성으로, 메시지는 `super().__init__(메시지)` |
| 다시 일으키기 | `except` 안의 `raise`는 같은 예외를 다시. `raise 새예외 from e`는 원인을 밝혀 바꾼다. `from None`은 원래 예외를 숨긴다 |
| 연결된 트레이스백 | `During handling ...`은 `except` 안에서 또 예외(버그일 수 있음), `direct cause`는 `from`으로 일부러 바꾼 것 |
| 잡을 때와 둘 때 | 대처할 수 있는 곳에서, 좁게 잡는다. 버그는 잡지 말고 고친다. 조용히 삼키지 않는다. 사용자에게 보여 줄 메시지는 가장 바깥에서 |
| 재시도 | 일시적인 실패만 잡아 몇 번 다시 시도하고, 끝내 실패하면 `raise`로 위에 넘긴다. 같은 예외 클래스 안에 일시적이지 않은 실패(사용 한도 소진 등)가 섞여 있는지 확인한다. 시도 횟수 같은 인자는 처음에 검사한다 |
| 디버거 | 처리되지 않은 예외에서 자동으로 멈춘다. 잡힌 예외에서도 멈추려면 Raised Exceptions에 체크 |
