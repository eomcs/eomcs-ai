# 9장. 가상환경

[파이썬 기초](README.md) 과정의 아홉 번째 장이다. 8장까지는 파이썬을 설치하면 함께 따라오는 **표준 라이브러리**만 썼다. 그런데 AI 엔지니어가 쓰는 도구는 대부분 표준 라이브러리 밖에 있다. LLM API를 부르는 `openai`, `anthropic`, 데이터를 다루는 `pandas`, 웹 요청을 보내는 `requests`는 모두 인터넷에서 **내려받아 설치하는** 외부 패키지다. 이 장에서는 외부 패키지를 설치해 쓰는 방법과, 그 패키지들을 **프로젝트마다 따로** 관리하는 방법을 배운다.

- **가상환경과 패키지 관리** — `venv`로 프로젝트 전용 파이썬 환경(**가상환경**)을 만들고 켜고 끈다. `python -m pip install`로 패키지를 설치하고, 왜 `pip install`이 아니라 `python -m pip install`로 쓰는지 알아본다. 설치한 패키지 목록을 `requirements.txt`에 적어 두었다가 다른 컴퓨터에서 똑같이 복원한다.
- **실행 환경 확인** — 한 컴퓨터에 파이썬이 여러 개 있을 때 터미널이 어느 파이썬을 찾는지, 지금 실행 중인 파이썬이 무엇인지(`sys.executable`), VS Code가 어느 파이썬을 쓰는지 확인한다. "분명히 설치했는데 `import`가 안 된다"는 문제의 원인을 찾아 해결한다.
- **외부 패키지 사용** — PyPI에서 패키지를 찾고, 믿을 만한지 살피고, 문서를 읽는다. `requests`로 간단한 HTTP 요청을 보내 웹에서 데이터를 가져온다.

AI가 만들어 준 프로젝트의 `README.md`에는 거의 빠짐없이 다음과 같은 줄이 있다.

```
python -m venv .venv
source .venv/bin/activate        # Windows: .venv\Scripts\activate
pip install -r requirements.txt
python main.py
```

그리고 프로젝트 폴더에는 `requirements.txt`가 있다.

```
openai==3.49.0
python-dotenv==1.2.4
requests==2.34.2
```

이 네 줄이 각각 무엇을 하는지, 왜 이 순서로 해야 하는지, 중간에 하나를 빠뜨리면 어떤 오류가 나는지를 이 장에서 모두 다룬다. 이 장을 마치면 남이 만든 파이썬 프로젝트를 받아 내 컴퓨터에서 실행할 수 있고, 내 프로젝트를 남이 실행할 수 있게 넘겨줄 수 있다.

## 학습 목표

이 장을 마치면 다음을 할 수 있다.

- 표준 라이브러리와 외부 패키지의 차이, PyPI와 pip가 각각 무엇인지 설명할 수 있다. 설치한 패키지가 `site-packages`에 들어간다는 것을 안다.
- 모든 패키지를 컴퓨터에 하나뿐인 파이썬에 설치하면 어떤 문제가 생기는지 설명하고, 프로젝트마다 가상환경을 분리하는 이유를 말할 수 있다.
- `python -m venv .venv`로 가상환경을 만들고, macOS와 Windows에서 활성화·비활성화할 수 있다. 활성화가 실제로 무엇을 바꾸는지(`PATH`, 프롬프트) 설명할 수 있다.
- `python -m pip install`, `list`, `show`, `uninstall`로 패키지를 설치하고 확인하고 지울 수 있다. 버전을 지정해 설치할 수 있고, 패키지가 다른 패키지(의존성)를 함께 설치한다는 것을 안다.
- `pip` 대신 `python -m pip`를 쓰는 이유를 "어느 파이썬에 설치되는가"로 설명할 수 있다.
- `pip freeze > requirements.txt`로 패키지 목록을 저장하고, `python -m pip install -r requirements.txt`로 새 가상환경에 복원할 수 있다.
- 가상환경 폴더를 공유하거나 옮기지 않고 **다시 만드는** 것이 원칙이라는 것을 알고, `.gitignore`에 넣을 수 있다.
- 터미널이 찾는 파이썬(`which` / `Get-Command`, `where.exe`)과 실행 중인 파이썬(`sys.executable`)을 확인하고, 가상환경 안에서 실행 중인지 코드로 판단할 수 있다.
- VS Code에서 인터프리터를 선택·확인하고, 터미널의 파이썬과 VS Code가 선택한 파이썬이 다를 때 생기는 문제를 찾아 고칠 수 있다.
- "설치했는데 `import`가 안 되는" 문제를 정해진 순서로 진단할 수 있다. 설치 이름과 `import` 이름이 다른 패키지가 있다는 것을 안다.
- PyPI에서 패키지를 찾아 버전, 지원하는 파이썬, 문서 위치, 관리 상태를 확인하고, 이름이 비슷한 가짜 패키지나 AI가 지어낸 패키지 이름을 조심할 수 있다.
- `requests.get()`으로 HTTP 요청을 보내고, 상태 코드를 확인하고, JSON 응답을 파이썬 데이터로 바꿀 수 있다. `timeout`을 주고 `requests`의 예외를 처리할 수 있다.

## 실습 준비

1장에서 만든 실습 폴더 안에 `ch09` 폴더를 만든다.

```
cd ~/python-lab
mkdir ch09
cd ch09
pwd
```

```
# macOS
/Users/본인계정/python-lab/ch09

# Windows
C:\Users\본인계정\python-lab\ch09
```

이 장은 앞의 장들과 몇 가지가 다르다.

1. **터미널 명령이 많다.** 파이썬 코드보다 터미널에서 입력하는 명령이 더 많이 나온다. 1장에서 배운 대로, 지금 프롬프트가 터미널(`%`, `>`)인지 대화형 셸(`>>>`)인지 늘 확인하자.
2. **macOS와 Windows의 명령이 자주 다르다.** 1장에서 "macOS 사용자는 `python`을 `python3`로 바꿔 읽으라"고 했다. 이 장에서는 그 차이가 중요해지므로, 다른 부분은 두 가지를 모두 적는다. 가상환경을 활성화한 뒤에는 macOS에서도 `python`이 동작한다(9.1.4). 1장에서 약속한 "`python`으로 통일하는 방법"이 바로 이것이다.
3. **인터넷 연결이 필요하다.** 패키지를 내려받고 웹에 요청을 보낸다. 회사나 학교 네트워크에서 설치가 막히면 9.1.5의 상자를 보자.
4. **출력의 버전 숫자는 다를 수 있다.** 패키지는 계속 새 버전이 나온다. 이 교재의 출력에 `requests 2.34.2`라고 나와도 여러분의 화면에는 더 높은 숫자가 보일 수 있다. 숫자가 아니라 **모양**을 비교하자.

코드를 보여 주는 방식은 8장과 같다.

- 앞에 `>>>`가 붙어 있으면 대화형 셸에서 한 줄씩 입력하는 코드다.
- 첫 줄에 `# check_env.py` 같은 파일 이름이 있거나 실습의 `# (가)` 같은 표시가 있으면 스크립트 파일 코드다.
- `>>>`도 파일 이름도 없는 블록은 **터미널 명령**이나 그 출력이다. 이 장에서는 활성화 상태를 보여 주려고 프롬프트를 함께 적은 경우가 있다. `(.venv) ch09 %`나 `(.venv) PS C:\...\ch09>`는 입력하는 것이 아니라 프롬프트이고, 그 뒤가 입력할 명령이다.

> **1단계를 마친 사람에게**
> AI에게 코드를 받아 실행했더니 `ModuleNotFoundError: No module named 'openai'`가 났고, AI가 "`pip install openai`를 실행하세요"라고 해서 그대로 했는데 **같은 오류가 또 난** 경험이 있을지도 모른다. 또는 VS Code의 ▷ 버튼으로는 안 되는데 터미널에서는 되거나, 그 반대였을 수도 있다. AI에게 다시 물으면 `pip3`, `python3 -m pip`, `sudo pip`, `--user`, `conda install`을 차례로 권하고, 이것저것 하다 보면 어느 순간 돌아가지만 왜 돌아가는지는 모른다. 이 문제의 원인은 거의 항상 하나다. **패키지를 설치한 파이썬과 프로그램을 실행한 파이썬이 다르다.** 이 장을 마치면 어느 파이썬에 설치했고 어느 파이썬으로 실행했는지 직접 확인할 수 있고, AI가 권하는 명령 중 무엇이 왜 맞는지 판단할 수 있다.

## 9.1 가상환경과 패키지 관리

### 9.1.1 표준 라이브러리 밖의 패키지 — PyPI와 pip

8.2.6에서 "웹에서 데이터를 가져오는 표준 라이브러리 모듈은 `urllib.request`지만, 실무에서는 외부 패키지 `requests`를 더 많이 쓴다"고 했다. `ch09` 폴더에서 셸을 열고 `requests`를 불러와 보자.

```python
>>> import requests
Traceback (most recent call last):
  File "<python-input-0>", line 1, in <module>
    import requests
ModuleNotFoundError: No module named 'requests'
```

(만약 오류 없이 불러와진다면 예전에 누군가 이 컴퓨터의 파이썬에 `requests`를 설치해 둔 것이다. 그래도 이 장의 실습은 그대로 따라 하면 된다. 9.1.2에서 왜 그것이 문제가 될 수 있는지 이야기한다.)

8.1.6에서 본 모듈 검색 경로(`sys.path`)를 모두 뒤졌지만 `requests`가 없다. 표준 라이브러리가 아니기 때문이다. 이런 모듈은 인터넷에서 내려받아 설치해야 한다. 이때 등장하는 이름이 둘 있다.

- **PyPI**(Python Package Index, "파이 피 아이"로 읽는다) — 파이썬 패키지를 모아 둔 공식 저장소다. [https://pypi.org](https://pypi.org)에 수십만 개의 프로젝트가 올라와 있다. 누구나 패키지를 올릴 수 있다. 이 점은 9.3.1에서 다시 이야기한다.
- **pip**(pip installs packages) — PyPI에서 패키지를 찾아 내려받고 설치하는 프로그램이다. 파이썬을 설치하면 함께 설치된다. pip도 사실은 `site-packages`에 들어 있는 파이썬 패키지다.

설치한 패키지는 8.1.6에서 본 `sys.path`의 세 번째 부분, **`site-packages`** 폴더에 들어간다. 설치는 결국 "패키지 파일을 `site-packages`에 복사해 두는 것"이고, 그러면 `import requests`가 그 폴더에서 `requests`를 찾을 수 있게 된다. 특별한 마법은 없다. 8장에서 `ch08` 폴더에 `textkit` 패키지를 직접 만들어 두고 `import`한 것과 같은 일을, 다른 사람이 만든 패키지를 정해진 폴더에 받아 두는 방식으로 하는 것이다.

> **"패키지"라는 말의 두 가지 뜻**
> 8.3에서 **패키지**는 "`__init__.py`가 있는, 모듈을 담은 폴더"였다. `import`할 때의 패키지다. 그런데 PyPI와 pip에서 말하는 **패키지**는 "내려받아 설치하는 묶음"이다. 설치하는 묶음 하나에는 `import` 패키지가 하나 들어 있는 경우가 많지만, 여러 개가 들어 있을 수도 있고 이름이 다를 수도 있다. 예를 들어 `beautifulsoup4`라는 이름으로 설치한 것은 `import bs4`로 불러온다. 이 차이는 9.2.6에서 "설치했는데 `import`가 안 될 때"의 원인 중 하나로 다시 나온다. 이 장에서 "패키지를 설치한다"고 하면 PyPI 쪽의 뜻이다.

### 9.1.2 한 곳에 모두 설치하면 생기는 문제

가장 단순한 방법은 1장에서 설치한 파이썬에 필요한 패키지를 모두 설치하는 것이다. 이렇게 하면 `site-packages` 폴더 하나에 모든 프로젝트의 패키지가 모인다. 처음에는 편하지만 프로젝트가 늘어나면 문제가 생긴다.

- **버전이 부딪힌다.** 작년에 만든 챗봇 프로젝트 A는 어떤 LLM 라이브러리의 1.x 버전으로 만들었고, 올해 시작한 프로젝트 B는 같은 라이브러리의 2.x 버전이 필요하다고 하자. 라이브러리의 큰 버전이 바뀌면 함수 이름이나 사용법이 바뀌는 경우가 많다. 그런데 `site-packages`에는 같은 이름의 패키지가 **한 버전만** 들어갈 수 있다. B를 위해 2.x를 설치하는 순간 1.x는 지워지고, A는 더 이상 돌아가지 않는다.
- **내 프로젝트에 무엇이 필요한지 알 수 없다.** 1년 동안 이것저것 설치하다 보면 `site-packages`에 패키지가 수십 개 쌓인다. 프로젝트 A를 동료에게 넘기려는데, A가 그중 무엇을 쓰는지 아무도 모른다. 내 컴퓨터에서는 잘 돌던 프로그램이 동료의 컴퓨터에서 `ModuleNotFoundError`를 내는 흔한 이유다.
- **망가뜨렸을 때 되돌리기 어렵다.** 패키지를 잘못 설치하거나 지워서 꼬였을 때, 컴퓨터 전체에서 쓰는 파이썬이라면 다른 프로젝트까지 영향을 받는다. 파이썬을 지우고 다시 설치하는 것 말고는 깨끗하게 되돌릴 방법이 마땅치 않다.
- **운영체제가 쓰는 파이썬을 건드릴 수 있다.** macOS의 Homebrew로 설치한 파이썬이나 리눅스에 미리 깔린 파이썬은 운영체제나 다른 프로그램이 함께 쓴다. 그래서 요즘은 이런 파이썬에 직접 설치하려고 하면 pip가 `error: externally-managed-environment`라는 오류를 내며 **아예 거절한다.** "여기에 설치하지 말고 가상환경을 만들라"는 뜻이다.

해결책은 **프로젝트마다 자기만의 `site-packages`를 갖게 하는 것**이다. 이것이 **가상환경**(virtual environment)이다. 이름에 "가상"이 붙었지만 가상 머신처럼 거창한 것이 아니라, 프로젝트 폴더 안에 만드는 **작은 폴더 하나**다. 그 안에 그 프로젝트 전용의 `site-packages`가 있고, 그 `site-packages`를 쓰는 파이썬 실행 파일이 있다.

```
컴퓨터에 설치한 파이썬 (3.13)
 ├── 표준 라이브러리          ← 모든 가상환경이 함께 쓴다
 └── site-packages           ← 비워 두고 쓰지 않는다

프로젝트 A/.venv/
 └── site-packages           ← 라이브러리 1.x
프로젝트 B/.venv/
 └── site-packages           ← 라이브러리 2.x
```

가상환경은 파이썬 전체를 복사하지 않는다. 파이썬 자체와 표준 라이브러리는 컴퓨터에 설치한 것(**기반 파이썬**, base Python)을 함께 쓰고, `site-packages`만 따로 갖는다. 그래서 만드는 데 몇 초밖에 걸리지 않고, 필요 없어지면 폴더를 지우면 끝이다. 공구를 한 통에 다 넣어 두고 여럿이 쓰는 대신, 작업마다 필요한 공구만 담은 작은 공구함을 따로 두는 것과 같다.

### 9.1.3 가상환경 만들기

파이썬에는 가상환경을 만드는 표준 라이브러리 모듈 `venv`가 들어 있다. 8.3.4에서 배운 `python -m`으로 이 모듈을 실행한다. `ch09` 폴더에서 다음을 입력한다.

```
# macOS
python3 -m venv .venv

# Windows
python -m venv .venv
```

아직 가상환경을 켜기 전이므로 macOS에서는 `python3`를 써야 한다. 아무것도 출력되지 않고 몇 초 뒤 프롬프트가 돌아오면 성공이다.

- `-m venv` — `venv` 모듈을 실행한다.
- `.venv` — 만들 가상환경 폴더의 이름이다. 아무 이름이나 써도 되지만 **`.venv`가 관례**다. VS Code를 비롯한 많은 도구가 프로젝트 폴더의 `.venv`를 자동으로 가상환경으로 알아본다. AI가 만든 프로젝트에서 `venv`나 `env`라는 이름을 볼 수도 있는데, 하는 일은 같다.

이름이 점(`.`)으로 시작하는 폴더는 macOS의 Finder와 `ls`에서 **숨김 폴더**로 취급된다. `ls -a`로 보면 보인다. (Windows의 탐색기와 `ls`에서는 그냥 보인다.)

```
ls -a
```

```
.	..	.venv
```

VS Code 탐색기에서는 숨김 폴더도 보인다. `.venv` 안을 열어 보자.

```
# macOS                          # Windows
.venv/                           .venv\
├── .gitignore                   ├── .gitignore
├── bin/                         ├── Include\
│   ├── activate                 ├── Lib\
│   ├── Activate.ps1             │   └── site-packages\
│   ├── pip                      │       └── pip\ ...
│   ├── pip3                     ├── Scripts\
│   ├── python → python3.13      │   ├── activate
│   ├── python3 → python3.13     │   ├── activate.bat
│   └── python3.13 → (기반 파이썬) │   ├── Activate.ps1
├── include/                     │   ├── pip.exe
├── lib/                         │   └── python.exe
│   └── python3.13/              └── pyvenv.cfg
│       └── site-packages/
│           └── pip/ ...
└── pyvenv.cfg
```

(파일이 더 있을 수 있다. 중요한 것만 적었다.)

- **`bin/`(Windows는 `Scripts\`)** — 이 가상환경의 `python`과 `pip`, 그리고 가상환경을 켜는 `activate` 스크립트가 있다. macOS의 `python`은 기반 파이썬을 가리키는 **바로 가기**(심볼릭 링크)다. 화살표(`→`)가 그 뜻이다. macOS에서도 이 안에는 `python`이라는 이름이 있다는 점을 기억해 두자.
- **`lib/python3.13/site-packages/`(Windows는 `Lib\site-packages\`)** — 이 가상환경 전용의 `site-packages`다. 지금은 pip만 들어 있다. 이 가상환경에서 설치하는 패키지는 모두 여기로 들어간다.
- **`pyvenv.cfg`** — 이 가상환경의 설정 파일이다.
- **`.gitignore`** — 파이썬 3.13부터 만들어 준다. 9.1.8에서 이야기한다.

`pyvenv.cfg`를 열어 보자.

```
home = /Library/Frameworks/Python.framework/Versions/3.13/bin
include-system-site-packages = false
version = 3.13.2
executable = /Library/Frameworks/Python.framework/Versions/3.13/bin/python3.13
command = /Library/Frameworks/Python.framework/Versions/3.13/bin/python3 -m venv /Users/본인계정/python-lab/ch09/.venv
```

`home`은 기반 파이썬이 있는 곳이다. 이 가상환경의 파이썬은 실행될 때 이 파일을 읽고 "나는 저 파이썬을 바탕으로 한 가상환경이구나"를 안다. `include-system-site-packages = false`는 기반 파이썬의 `site-packages`를 **쓰지 않는다**는 뜻이다. 그래서 기반 파이썬에 무엇이 설치되어 있든 이 가상환경은 깨끗한 상태에서 시작한다. 가상환경의 버전은 만들 때 쓴 파이썬의 버전(`version`)으로 정해진다.

### 9.1.4 활성화와 비활성화

가상환경을 만들었다고 바로 쓰이는 것은 아니다. 지금 터미널에서 `python3`(Windows는 `python`)를 입력하면 여전히 컴퓨터에 설치한 파이썬이 실행된다. 이 터미널에서 가상환경의 파이썬을 쓰게 하려면 가상환경을 **활성화**(activate)한다.

```
# macOS
source .venv/bin/activate

# Windows PowerShell
.venv\Scripts\Activate.ps1
```

활성화되면 프롬프트 맨 앞에 가상환경 폴더 이름이 괄호로 붙는다.

```
# macOS
(.venv) ch09 %

# Windows
(.venv) PS C:\Users\본인계정\python-lab\ch09>
```

(프롬프트의 나머지 모양은 터미널 설정에 따라 다르다. **`(.venv)`가 붙었는지**만 보면 된다.)

> **Windows에서 "스크립트를 실행할 수 없으므로"라는 오류가 나면**
> PowerShell에서 활성화할 때 다음과 같은 빨간 오류가 날 수 있다.
> ```
> .venv\Scripts\Activate.ps1 : 이 시스템에서 스크립트를 실행할 수 없으므로 C:\Users\본인계정\python-lab\ch09\.venv\Scripts\Activate.ps1 파일을 로드할 수 없습니다. 자세한 내용은 about_Execution_Policies(https://go.microsoft.com/fwlink/?LinkID=135170)를 참조하십시오.
> ```
> Windows는 기본적으로 PowerShell 스크립트(`.ps1`) 실행을 막아 둔 경우가 있다. `Activate.ps1`도 스크립트이므로 막힌다. 다음 명령을 **한 번만** 실행해 현재 사용자에게 스크립트 실행을 허용한다. 물어보면 `Y`를 입력한다.
> ```
> Set-ExecutionPolicy -ExecutionPolicy RemoteSigned -Scope CurrentUser
> ```
> `RemoteSigned`는 "내 컴퓨터에서 만든 스크립트는 실행하고, 인터넷에서 내려받은 스크립트는 서명된 것만 실행한다"는 설정이다. 그다음 활성화 명령을 다시 입력한다.

이제 macOS에서도 `python`이 동작한다. 어느 파이썬이 실행되는지 확인해 보자. `python -c "코드"`는 8장 실습 8-1에서 쓴, 따옴표 안의 코드를 바로 실행하는 방법이다.

```
python --version
python -c "import sys; print(sys.executable)"
```

```
# macOS
Python 3.13.2
/Users/본인계정/python-lab/ch09/.venv/bin/python

# Windows
Python 3.13.2
C:\Users\본인계정\python-lab\ch09\.venv\Scripts\python.exe
```

8.2.2에서 `sys.executable`은 "지금 이 코드를 실행하고 있는 파이썬 프로그램의 경로"라고 했다. 경로가 `.venv` 안을 가리킨다. `python`이라고만 입력했는데 가상환경의 파이썬이 실행되었다.

**활성화는 무엇을 바꾸나**

활성화가 하는 일은 생각보다 단순하다. 핵심은 **`PATH`라는 환경 변수의 맨 앞에 `.venv/bin`(Windows는 `.venv\Scripts`)을 끼워 넣는 것**이다.

`PATH`는 8.2.1에서 배운 환경 변수 중 하나로, 터미널이 명령을 찾을 폴더의 목록이다. 터미널에 `python`이라고 입력하면 터미널은 `PATH`의 폴더를 **앞에서부터 차례로** 뒤져서 처음 발견한 `python` 프로그램을 실행한다. 8.1.6의 `sys.path`가 "파이썬이 모듈을 찾는 폴더 목록"이었다면, `PATH`는 "터미널이 프로그램을 찾는 폴더 목록"이다. 찾는 방식이 똑같다.

```
python -c "import os; print(os.environ['PATH'])"
```

```
# macOS (보기 좋게 줄을 바꿨다)
/Users/본인계정/python-lab/ch09/.venv/bin:
/Library/Frameworks/Python.framework/Versions/3.13/bin:
/usr/local/bin:/usr/bin:/bin:/usr/sbin:/sbin
```

맨 앞에 `.venv/bin`이 들어갔다. 그래서 `python`, `pip`을 입력하면 가상환경 안의 것이 먼저 발견된다. 활성화 스크립트는 이 밖에 `VIRTUAL_ENV`라는 환경 변수에 가상환경 폴더의 경로를 넣고, 프롬프트에 `(.venv)`를 붙인다. 그것이 전부다. 파이썬 프로그램이나 파일을 바꾸는 것이 아니다.

여기서 두 가지를 알 수 있다.

- **활성화는 그 터미널 창에서만 유효하다.** 8.2.1에서 `export`로 정한 환경 변수가 그 창에서만 유효했던 것과 같다. 새 터미널 창을 열면 활성화되지 않은 상태로 시작한다. 터미널을 새로 열 때마다 `cd`로 프로젝트 폴더에 가서 활성화하는 것이 첫 번째 일이다.
- **활성화하지 않아도 가상환경의 파이썬을 쓸 수 있다.** 가상환경의 `python`을 **경로로 직접** 실행하면 된다. 활성화는 이 경로를 매번 치지 않게 해 주는 편의 기능일 뿐이다.
  ```
  # macOS
  .venv/bin/python -c "import sys; print(sys.executable)"

  # Windows
  .venv\Scripts\python.exe -c "import sys; print(sys.executable)"
  ```
  가상환경의 파이썬은 어떻게 실행되든 자기 옆의 `pyvenv.cfg`를 읽고 자기 `site-packages`를 쓴다. VS Code의 ▷ 버튼이 바로 이 방법을 쓴다(9.2.4).

**비활성화**

가상환경을 끄려면 `deactivate`를 입력한다. macOS와 Windows가 같다.

```
deactivate
```

프롬프트에서 `(.venv)`가 사라지고 `PATH`가 원래대로 돌아온다. macOS에서는 다시 `python`이 없는 상태가 된다(`command not found: python`). 터미널 창을 닫아도 비활성화된다.

> **활성화 상태를 늘 확인하자**
> 이 장의 실습에서 가장 흔한 실수는 **가상환경을 켰다고 생각했는데 꺼져 있는 것**이다. 새 터미널을 열었거나, VS Code를 다시 시작했거나, 다른 폴더의 가상환경을 켰다가 껐을 때 그렇다. 명령을 입력하기 전에 프롬프트에 `(.venv)`가 있는지 보는 습관을 들이자.

`ch09`의 가상환경을 다시 활성화한 뒤 `requests`를 설치한다.

```
python -m pip install requests
```

```
Collecting requests

Collecting charset_normalizer<4,>=2 (from requests)
  Downloading charset_normalizer-3.5.2-cp313-cp313-macosx_10_13_universal2.whl.metadata (46 kB)

```

`python -m pip install 이름`은 "이 `python`의 `pip` 모듈을 실행해서 `이름` 패키지를 설치하라"는 뜻이다. 왜 그냥 `pip install`이 아닌지는 9.1.6에서 본다. 출력을 위에서부터 읽어 보자.

- **`Collecting requests`** — PyPI에서 `requests`를 찾았다. 버전을 지정하지 않았으므로 최신 버전(여기서는 2.34.2)을 고른다.
- **`Collecting charset_normalizer<4,>=2 (from requests)`** — `requests`가 동작하려면 `charset_normalizer`라는 다른 패키지가 필요하다. 괄호 안의 `from requests`가 "requests가 필요로 해서"라는 뜻이다. `<4,>=2`는 "2 이상 4 미만의 버전"이라는 조건이다. 이렇게 어떤 패키지가 동작하는 데 필요한 다른 패키지를 **의존성**(dependency)이라고 한다. pip는 의존성의 의존성까지 모두 찾아서 함께 설치한다.
- **`.whl`** — 휠(wheel)이라고 부르는, 설치할 준비가 끝난 패키지 파일의 형식이다. 내려받은 휠 파일의 내용을 `site-packages`에 풀어 놓는 것이 설치다.
- **`Successfully installed ...`** — 설치한 패키지 다섯 개와 그 버전이다. 하나를 설치하라고 했는데 다섯 개가 설치되었다.

> **설치가 안 될 때**
> - `ERROR: Could not find a version that satisfies the requirement reqeusts (from versions: none)` — PyPI에 그런 이름의 패키지가 없다. 이름의 오타부터 확인한다. 같은 메시지가 **모든 패키지**에서 난다면 인터넷에 연결되지 않은 것일 수 있다.
> - 회사나 학교 네트워크에서 연결 오류나 인증서 오류(`SSL: CERTIFICATE_VERIFY_FAILED`)가 나면, 네트워크가 외부 접속을 막거나 중간에서 검사하는 경우다. 인터넷에서 찾은 "인증서 검사를 끄는" 옵션을 함부로 쓰지 말고 네트워크 관리자에게 프록시 설정을 물어보자.
> - 설치 끝에 `[notice] A new release of pip is available: ... To update, run: python -m pip install --upgrade pip`가 나올 수 있다. 오류가 아니라 pip의 새 버전이 나왔다는 안내다. 지금은 무시해도 되고, 안내대로 실행해 pip를 올려도 된다.

`list`는 이 파이썬에 설치된 패키지를 모두 보여 준다.

```
python -m pip list
```

------------------ ----------

charset-normalizer 3.5.2
idna               3.20
pip                26.2.2
requests           2.34.2
urllib3            2.8.0
```

`show`는 패키지 하나의 정보를 보여 준다.

```
python -m pip show requests
```

```

Version: 2.34.2

Home-page:

```

- **`Location`** — 설치된 곳이다. 가상환경의 `site-packages`다. VS Code 탐색기에서 `.venv/lib/python3.13/site-packages`를 열어 보면 `requests` 폴더가 생겨 있다. 그 안에 `__init__.py`와 여러 `.py` 파일이 있다. 8.3에서 만든 `textkit` 패키지와 생김새가 같다.
- **`Requires`** — `requests`가 필요로 하는 패키지(의존성)다.
- **`Required-by`** — 반대로 `requests`를 필요로 하는 패키지다. 지금은 없다.

이제 셸에서 불러와 보자. **가상환경이 활성화된 터미널**에서 셸을 연다.

```python
>>> import requests
>>> requests.__version__
'2.34.2'
>>> requests.__file__
'/Users/본인계정/python-lab/ch09/.venv/lib/python3.13/site-packages/requests/__init__.py'
```

`__file__`은 7장과 8장에서 쓴 바로 그 속성이다. 모듈 객체에도 있어서, 그 모듈을 어느 파일에서 불러왔는지 알려 준다. 가상환경의 `site-packages`에서 불러왔다. 셸을 끄고 `deactivate`한 뒤 같은 것을 해 보면 9.1.1의 `ModuleNotFoundError`가 다시 난다. 기반 파이썬에는 설치하지 않았기 때문이다.

**버전을 지정해 설치하기**

이름 뒤에 조건을 붙이면 원하는 버전을 설치할 수 있다.

| 쓰는 법 | 뜻 |
|---|---|
| `requests` | 최신 버전 |
| `requests==2.32.3` | 정확히 2.32.3 |
| `"requests>=2.32"` | 2.32 이상 중 최신 |
| `"requests>=2.32,<3"` | 2.32 이상 3 미만 중 최신 |
| `"requests~=2.32.0"` | 2.32.x 중 최신(2.32.0 이상 2.33 미만) |

```
python -m pip install requests==2.32.3
```

```
...
Installing collected packages: requests
  Attempting uninstall: requests
    Found existing installation: requests 2.34.2
    Uninstalling requests-2.34.2:
      Successfully uninstalled requests-2.34.2
Successfully installed requests-2.32.3
```

이미 2.34.2가 설치되어 있었으므로 그것을 **지우고** 2.32.3을 설치했다. 9.1.2에서 말한 "한 `site-packages`에는 한 버전만"이 이것이다.

> **`>`와 `<`가 들어가면 따옴표로 감싼다**
> 8.2.2에서 터미널의 `>`는 출력을 파일로 돌리는 **리디렉션**이라고 했다. `<`도 반대 방향의 리디렉션(파일에서 입력 받기)이다. 그래서 따옴표 없이 `python -m pip install requests>=2.32`라고 입력하면, 셸(터미널 프로그램)에 따라 `>=2.32`를 pip에 넘기지 않고 리디렉션으로 처리하려 한다. 어떻게 처리되는지는 **셸마다 다르다.**
> - **macOS의 기본 셸 zsh** — `zsh: 2.32 not found` 오류가 나고 명령이 아예 실행되지 않는다. zsh는 `=`로 시작하는 낱말을 "그 이름의 명령이 있는 경로"로 바꾸는 기능이 있어서, `=2.32`를 `2.32`라는 명령의 경로로 바꾸려다 실패한 것이다. `requests<3`이라면 `zsh: no such file or directory: 3`(`3`이라는 파일에서 입력을 받으려다 실패)이 난다.
> - **bash**(리눅스, Git Bash, 예전 macOS의 기본 셸) — `python -m pip install requests`가 실행되고, 출력은 `=2.32`라는 파일에 저장된다. 오류 없이 설치는 되지만 버전 조건은 무시되고, 폴더에 `=2.32`라는 이상한 파일이 생긴다.
> - **Windows PowerShell** — PowerShell은 `<`, `>`를 **낱말의 맨 앞에 올 때만** 특별한 문자로 읽는다. 그래서 이 예에서는 `requests>=2.32`가 그대로 pip에 전달되고 버전 조건대로 설치된다. 그래도 다른 셸에서도 같은 명령을 쓸 수 있도록 버전 조건을 따옴표로 감싸는 습관을 들이자.
>
> 셸에 따른 해석 차이를 피하려면 `>`, `<`가 들어간 조건은 `"requests>=2.32"`처럼 **따옴표로 감싸자.** 따옴표 안의 글자는 셸이 건드리지 않고 그대로 pip에 넘긴다. `==`는 리디렉션이 아니므로 감싸지 않아도 된다.

**패키지 올리기와 지우기**

```
python -m pip install --upgrade requests
```

`--upgrade`(짧게 `-U`)는 이미 설치된 패키지를 최신 버전으로 올린다. 다시 2.34.2가 된다.

```
python -m pip uninstall requests
```

```

Uninstalling requests-2.34.2:
  Would remove:
    /Users/본인계정/python-lab/ch09/.venv/lib/python3.13/site-packages/requests-2.34.2.dist-info/*
    /Users/본인계정/python-lab/ch09/.venv/lib/python3.13/site-packages/requests/*
Proceed (Y/n)? y
  Successfully uninstalled requests-2.34.2
```

`uninstall`은 지울 파일을 보여 주고 확인을 받는다. 지운 뒤 `python -m pip list`를 해 보면 `requests`는 없지만 **함께 설치되었던 `certifi`, `idna` 같은 의존성은 그대로 남아 있다.** pip는 의존성을 자동으로 지우지 않는다. 다른 패키지가 그것을 쓰고 있을지도 모르기 때문이다. 이렇게 남은 패키지가 쌓이는 것도 가상환경을 프로젝트마다 나누고, 꼬이면 통째로 다시 만드는 이유 중 하나다(9.1.8). 다음 절을 위해 `requests`를 다시 설치해 두자.

```
python -m pip install requests
```

### 9.1.6 왜 `python -m pip`인가

인터넷의 설명이나 AI는 대부분 `pip install requests`라고 쓴다. 이 교재는 굳이 `python -m pip install requests`라고 쓴다. 차이는 **어느 파이썬에 설치되느냐**를 확실하게 하느냐에 있다.

`pip`도 9.1.4에서 본 `python`처럼 `PATH`에서 찾는 프로그램이다. 그리고 파이썬마다 자기 `pip`이 있다. 기반 파이썬에도, 가상환경에도, 컴퓨터에 따로 설치된 다른 파이썬에도 각자의 `pip`이 있다. 각 `pip`은 **자기를 가진 파이썬의 `site-packages`에** 설치한다. 그러면 다음과 같은 일이 생길 수 있다.

- 터미널이 찾는 `python`과 `pip`이 **서로 다른 파이썬의 것**이다. `PATH`의 순서에 따라 `python`은 A 폴더에서, `pip`은 B 폴더에서 먼저 발견될 수 있다. `pip install`로 B에 설치하고 `python`(A)으로 실행하면 `ModuleNotFoundError`가 난다.
- macOS에서 python.org의 파이썬을 설치하면 `pip`이라는 명령은 없고 `pip3`만 있는 경우가 많다. 반면 다른 경로로 설치한 파이썬의 `pip`이 남아 있을 수도 있다.

`python -m pip`은 "`python`이라고 입력했을 때 실행되는 **바로 그 파이썬**이 자기 `pip` 모듈을 실행하라"는 뜻이다. 8.3.4에서 `python -m textkit.stats`가 그 파이썬의 모듈 검색 경로에서 `textkit.stats`를 찾아 실행했던 것과 같다. 그러면 설치되는 곳은 반드시 그 파이썬의 `site-packages`다. **실행할 때 쓰는 명령(`python`)과 설치할 때 쓰는 명령(`python -m pip`)의 앞부분이 같으므로, 둘이 같은 파이썬이라는 것이 보장된다.**

`pip`이 어느 파이썬의 것인지는 `--version`으로 확인할 수 있다.

```
python -m pip --version
```

```
pip 26.2.2 from /Users/본인계정/python-lab/ch09/.venv/lib/python3.13/site-packages/pip (python 3.13)
```

`from` 뒤가 그 pip이 들어 있는 곳, 괄호 안이 그 pip을 실행한 파이썬의 버전이다. 가상환경 안의 pip이다.

가상환경을 활성화한 상태라면 `PATH`의 맨 앞이 `.venv/bin`이므로 `pip`과 `python`이 모두 가상환경의 것이다. 그래서 `pip install`도 사실 잘 동작한다. 그래도 `python -m pip`을 습관으로 들이자. 활성화를 잊었을 때, 다른 파이썬이 끼어들었을 때도 "실행하는 파이썬에 설치한다"는 원칙이 지켜진다. (Windows에서 pip 자신을 올릴 때는 `pip install --upgrade pip`이 실패하고 `python -m pip install --upgrade pip`만 된다. 실행 중인 `pip.exe`가 자기 자신을 바꿀 수 없기 때문이다.)

> **AI가 권하는 다른 명령들**
> - `pip3 install` — `pip`과 같은 문제가 있다. `pip3`가 어느 파이썬의 것인지 알 수 없다.
> - `python3 -m pip install` — 가상환경을 켜지 않은 macOS라면 `python3`의 pip을 쓰는 올바른 방법이다. 다만 기반 파이썬에 설치하게 되므로, 이 교재에서는 가상환경을 켜고 `python -m pip`을 쓴다.
> - `sudo pip install` — macOS나 리눅스에서 관리자 권한으로 설치한다. 운영체제의 파이썬을 망가뜨릴 수 있으므로 **쓰지 않는다.** 권한 오류가 난다는 것은 대개 가상환경을 켜지 않았다는 신호다.
> - `pip install --user` — 사용자 폴더의 `site-packages`에 설치한다. 9.1.2의 "한 곳에 모두 설치하면 생기는 문제"가 그대로 있다.
> - `pip install --break-system-packages` — `externally-managed-environment` 오류를 억지로 넘기는 옵션이다. 이름 그대로 시스템 패키지를 망가뜨릴 수 있다. 그 오류가 나면 가상환경을 만들자.

### 9.1.7 `requirements.txt` — 패키지 목록을 적어 두고 복원하기

가상환경 폴더는 다른 사람에게 주지 않는다(9.1.8). 대신 **"이 프로젝트에는 어떤 패키지의 어떤 버전이 필요하다"는 목록**을 준다. 받은 사람은 자기 컴퓨터에 가상환경을 새로 만들고, 그 목록대로 설치한다. 이 목록을 적는 파일의 관례적인 이름이 `requirements.txt`다.

**목록 만들기 — `pip freeze`**

`freeze`는 지금 설치된 패키지를 `requirements.txt` 형식으로 출력한다.

```
python -m pip freeze
```

```
certifi==2026.10.23
charset-normalizer==3.5.2
idna==3.20
requests==2.34.2
urllib3==2.8.0
```

`list`와 비슷하지만 `이름==버전` 모양이고, pip 자신은 빠져 있다. 이 출력을 파일에 저장하면 그것이 `requirements.txt`다. 8.2.2에서 배운 리디렉션 `>`를 쓴다.

```
python -m pip freeze > requirements.txt
```

화면에는 아무것도 나오지 않고 `ch09` 폴더에 `requirements.txt`가 생긴다. VS Code에서 열어 보면 위의 다섯 줄이 들어 있다. 이름 그대로 지금 상태를 **얼려서**(freeze) 적어 둔 것이다.

**목록대로 설치하기 — `install -r`**

`-r 파일`은 "이 파일에 적힌 패키지를 모두 설치하라"는 뜻이다.

```
python -m pip install -r requirements.txt
```

이미 모두 설치되어 있으므로 `Requirement already satisfied: ...`만 나온다. 진짜로 복원되는지는 가상환경을 지우고 다시 만들어 확인하자. 가상환경은 폴더이므로 폴더를 지우면 된다. **먼저 `deactivate`로 끄고** 지운다.

```
# macOS
deactivate
rm -rf .venv
python3 -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements.txt

# Windows
deactivate
Remove-Item -Recurse -Force .venv
python -m venv .venv
.venv\Scripts\Activate.ps1
python -m pip install -r requirements.txt
```

`rm -rf`와 `Remove-Item -Recurse -Force`는 폴더를 안의 내용까지 통째로, 묻지 않고 지우는 명령이다. 휴지통을 거치지 않으므로 **지울 폴더 이름을 꼭 두 번 확인하자.** VS Code 탐색기에서 `.venv` 폴더를 오른쪽 클릭해 삭제해도 된다.

```
...
Successfully installed certifi-2026.10.23 charset-normalizer-3.5.2 idna-3.20 requests-2.34.2 urllib3-2.8.0
```

`python -m pip list`로 확인하면 지우기 전과 똑같다. 새 가상환경에 같은 패키지를 같은 버전으로 다시 설치했다. 다른 사람의 컴퓨터에서도, 1년 뒤의 내 컴퓨터에서도 같은 방법으로 복원한다. 이 장의 첫머리에서 본 `README.md`의 네 줄이 바로 이 과정이다.

**`requirements.txt`를 쓰는 두 가지 방식**

`pip freeze`로 만든 파일에는 내가 직접 설치한 `requests`와, 그것 때문에 따라온 의존성 네 개가 **구분 없이** 들어 있다. 그래서 `requirements.txt`를 쓰는 방식이 두 가지로 나뉜다.

| | `pip freeze`로 만들기 | 직접 쓰기 |
|---|---|---|
| 내용 | 설치된 모든 패키지, 정확한 버전(`==`) | 내가 직접 쓰는 패키지만, 필요하면 범위(`>=`) |
| 예 | `certifi==2026.10.23` … `requests==2.34.2` … (다섯 줄) | `requests>=2.32` (한 줄) |
| 좋은 점 | 호환되는 파이썬과 운영체제라면 기록한 **그대로의 버전**으로 복원된다 | 무엇을 왜 쓰는지 한눈에 보인다 |
| 아쉬운 점 | 무엇이 내가 고른 것이고 무엇이 딸려 온 것인지 알 수 없다 | 복원할 때마다 의존성의 버전이 달라질 수 있다 |

이 과정에서는 **프로젝트 전용 가상환경에서 `pip freeze`로 만드는 방식**을 쓴다. "내 컴퓨터에서 돌던 그 버전"으로 복원되는 것이 지금은 더 중요하기 때문이다. 대신 두 가지를 지킨다.

- **가상환경에는 그 프로젝트에 필요한 것만 설치한다.** 연습 삼아 이것저것 설치했다면 그것도 `freeze`에 함께 적힌다. 시험해 볼 패키지는 다른 가상환경에서 시험하자.
- **패키지를 설치하거나 지우거나 올렸으면 `freeze`를 다시 한다.** 파일이 저절로 바뀌지는 않는다.

**`requirements.txt`가 기록하지 않는 것**

`pip freeze`가 기록하는 것은 **설치된 패키지의 이름과 버전**뿐이다. 다음은 기록하지 않는다.

- **파이썬 버전** — 가상환경의 파이썬 버전은 만들 때 쓴 기반 파이썬으로 정해진다(9.1.3). 3.13에서 만든 목록을 3.10의 가상환경에서 복원하면, 그 버전의 패키지가 3.10을 지원하지 않아 설치가 실패할 수 있다. 반대로 아주 새로운 파이썬에서는 오래된 버전의 패키지를 설치할 수 없는 경우도 있다.
- **운영체제** — 패키지 가운데에는 운영체제마다 다른 파일을 설치하거나, 특정 운영체제에서만 필요한 의존성이 있는 것이 있다. 9.1.5의 출력에서 `charset_normalizer`의 파일 이름에 `cp313`(파이썬 3.13용)과 `macosx_..._universal2`(macOS용)가 들어 있던 것이 그 흔적이다. Windows에서는 같은 버전이라도 `win_amd64`가 붙은 다른 파일을 내려받는다. `requests`처럼 파일 이름에 `py3-none-any`가 붙은 것은 어디서나 같은 파일을 쓴다.
- **파이썬 밖의 것** — 패키지가 기대는 운영체제의 프로그램이나 설정, 환경 변수(8.2.1)는 들어 있지 않다.

그래서 `requirements.txt`는 "어디서나 똑같은 환경"을 보장하지 않는다. **호환되는 파이썬과 운영체제에서, 기록한 버전의 패키지를 다시 설치해 준다**는 것이 정확하다. 이 빈칸은 사람이 채운다. 프로젝트의 `README.md`에 **확인한 파이썬 버전**(예: `파이썬 3.13에서 확인함`)과 설치·실행 방법을 적어 두자. 받는 사람은 그 버전의 파이썬으로 가상환경을 만든 뒤 복원하면 된다.

`requirements.txt`에는 `#`으로 시작하는 주석을 쓸 수 있다. 직접 쓰는 방식이라면 "왜 이 패키지가 필요한지"를 주석으로 남겨 두면 좋다. 실무에서는 두 방식의 장점을 함께 얻으려고 "내가 고른 패키지 목록"과 "정확한 버전 목록(잠금 파일, lock file)"을 따로 관리해 주는 도구를 많이 쓴다. 9.1.9에서 이름만 소개한다.

### 9.1.8 프로젝트마다 가상환경을 만든다

지금까지의 내용을 정리하면, 파이썬 프로젝트 폴더는 보통 다음 모양이 된다.

```
my_project/
├── .venv/              ← 가상환경. 내 컴퓨터에서만 쓴다. 공유하지 않는다
├── .gitignore          ← Git에 올리지 않을 것의 목록
├── README.md           ← 확인한 파이썬 버전, 설치·실행 방법
├── requirements.txt    ← 필요한 패키지 목록. 공유한다
├── main.py
└── ...
```

**규칙 1. 가상환경은 프로젝트 폴더 안에, 프로젝트마다 하나 만든다.** 프로젝트 A의 가상환경을 프로젝트 B에서 빌려 쓰지 않는다. 그러면 9.1.2의 문제가 그대로 돌아온다. 가상환경 폴더 안에는 내 코드를 넣지 않는다. 가상환경은 언제든 지우고 다시 만드는 폴더다.

**규칙 2. 가상환경 폴더는 공유하지 않고, 옮기지 않는다.** 가상환경 안에는 **이 컴퓨터의 절대 경로**가 곳곳에 적혀 있다. `pyvenv.cfg`의 `home`도 그렇고, `bin/pip` 같은 프로그램의 첫 줄에도 `/Users/본인계정/python-lab/ch09/.venv/bin/python3` 같은 경로가 적혀 있다. 그래서 가상환경을 다른 컴퓨터에 복사하거나, 프로젝트 폴더를 다른 곳으로 옮기거나 이름을 바꾸면 제대로 동작하지 않는다. 파이썬 공식 문서도 가상환경은 옮기거나 복사하는 것이 아니라 **새 위치에서 다시 만드는 것**이라고 말한다. 프로젝트를 옮겼다면 `.venv`를 지우고, 새 위치에서 만들고, `requirements.txt`로 복원한다. 9.1.7에서 해 본 그 과정이다.

**규칙 3. 가상환경은 Git에 올리지 않는다.** 1단계에서 GitHub에 코드를 올려 보았을 것이다. 가상환경은 수천 개의 파일로 되어 있고(`requests` 하나만 설치해도 그렇다), 다른 컴퓨터에서는 어차피 동작하지 않는다. Git이 무시할 파일과 폴더는 프로젝트 폴더의 `.gitignore`에 적는다. 파이썬 프로젝트라면 적어도 다음을 적어 둔다.

```
# .gitignore
.venv/
__pycache__/
```

`__pycache__`는 8.1.4에서 본, `import`할 때 생기는 바이트코드 폴더다. 이것도 공유하지 않는다. 파이썬 3.13부터는 `venv`가 가상환경 폴더 안에 내용이 `*`인 `.gitignore`를 만들어 두므로(9.1.3) `.venv`는 저절로 무시된다. 그래도 3.12를 쓰는 사람, `venv`가 아닌 도구로 만든 가상환경을 생각해서 프로젝트의 `.gitignore`에 적어 두는 것이 안전하다. 8장에서 이야기한 API 키 같은 비밀 값을 담은 파일(예: `.env`)도 반드시 여기에 적는다.

> **VS Code로 가상환경 만들기**
> VS Code에서도 가상환경을 만들 수 있다. 명령 팔레트(`Cmd + Shift + P` / `Ctrl + Shift + P`)에서 `Python: Create Environment`를 실행하고 **Venv**와 기반 파이썬을 고르면, 열려 있는 폴더에 `.venv`를 만들고 인터프리터로 선택까지 해 준다. 폴더에 `requirements.txt`가 있으면 그대로 설치할지도 물어본다. 편리하지만, 처음에는 터미널에서 직접 해 보자. 무슨 일이 일어나는지 알고 나서 쓰는 단축키여야 문제가 생겼을 때 고칠 수 있다. 또 이 과정처럼 `python-lab` 폴더를 열어 둔 상태에서는 `python-lab` 바로 아래에 `.venv`가 생긴다는 점도 주의하자.

**이 과정에서는**

이 장에서는 `ch09` 폴더에 `.venv`를 하나 만들어 9.1~9.3의 실습에 함께 쓴다. 실습 9-4에서는 도서 대출 관리 프로그램을 하나의 **프로젝트 폴더**로 독립시키고 그 안에 전용 가상환경을 따로 만든다. 10장의 종합 실습도 자기 가상환경을 갖는다. 1~8장의 실습 폴더에는 가상환경이 필요 없다. 표준 라이브러리만 쓰기 때문이다.

### 9.1.9 다른 도구들 — conda, uv, poetry

`venv`와 `pip`은 파이썬에 들어 있는 표준 도구다. 그런데 AI가 만든 프로젝트나 인터넷의 예제에서는 다른 도구를 만날 수 있다.

| 도구 | 보이는 모습 | 특징 |
|---|---|---|
| conda (Anaconda, Miniconda) | `conda create -n myenv python=3.12`, `conda activate myenv`, `environment.yml` | 파이썬 자체와 파이썬이 아닌 프로그램까지 설치·관리한다. 데이터 과학 분야에서 많이 쓴다 |
| uv | `uv venv`, `uv pip install`, `uv add requests`, `uv run main.py`, `pyproject.toml`, `uv.lock` | 매우 빠른 패키지 관리 도구. 최근 빠르게 퍼지고 있다 |
| poetry | `poetry add requests`, `poetry install`, `pyproject.toml`, `poetry.lock` | 패키지 관리와 배포를 함께 한다 |

명령은 달라도 하는 일은 이 절에서 배운 것과 같다. **프로젝트마다 격리된 환경을 만들고, 필요한 패키지 목록을 파일로 남겨 다른 곳에서 복원한다.** `pyproject.toml`은 "내가 고른 패키지 목록", `uv.lock`이나 `poetry.lock`은 "정확한 버전 목록(잠금 파일)"이다. 9.1.7에서 말한 두 방식의 장점을 함께 얻는 방법이다. 이 과정에서는 표준 도구인 `venv`와 `pip`만 쓴다. 기본을 알면 다른 도구는 "같은 일을 다른 명령으로 하는 것"으로 금방 익힐 수 있다. `pyproject.toml`과 패키지 배포는 파이썬 중급에서 다룬다.

### 실습 9-1. 가상환경과 패키지 관리

**1) 결과 예상하기**

macOS를 기준으로 한다(Windows는 `source .venv/bin/activate` 대신 `.venv\Scripts\Activate.ps1`, `python3` 대신 `python`). `ch09/.venv`에는 `requests`가 설치되어 있고, 기반 파이썬에는 설치되어 있지 않다. 새 터미널을 열어 다음을 차례로 입력했다. 표시한 줄마다 결과를 예상하라. 출력되는 경로라면 어느 파이썬의 것인지만 말하면 된다.

```
cd ~/python-lab/ch09
python3 -c "import requests"                          # (가)
source .venv/bin/activate
python -c "import requests; print(requests.__file__)" # (나)
cd ..
python -c "import sys; print(sys.executable)"         # (다)
cd ch08
python -c "import requests"                           # (라)
deactivate
python -c "import requests"                           # (마)
~/python-lab/ch09/.venv/bin/python -c "import requests; print('ok')"  # (바)
```

(다)와 (라)에서는 `ch09` 폴더를 떠났다. 가상환경은 폴더를 떠나면 꺼지는가? (마)에서 macOS와 Windows의 결과는 같은가?

**2) 두 개의 가상환경**

한 컴퓨터에서 같은 패키지의 서로 다른 버전을 동시에 쓸 수 있는지 확인한다.

- `ch09` 안에 `old_app`과 `new_app` 폴더를 만들고, 각 폴더 안에 가상환경 `.venv`를 만든다. `ch09`의 가상환경이 켜져 있다면 먼저 `deactivate`한다.
- `old_app`의 가상환경에는 `requests==2.31.0`을, `new_app`의 가상환경에는 최신 `requests`를 설치한다.
- 각 폴더에 다음 파일을 만들고, 각자의 가상환경을 켠 상태에서 실행한다.
  ```python
  # (가) old_app/show_version.py, new_app/show_version.py (내용이 같다)
  import sys

  import requests

  print("파이썬:", sys.executable)
  print("requests:", requests.__version__)
  ```
- `old_app`의 가상환경을 켠 채로 `python ../new_app/show_version.py`를 실행하면 어떤 버전이 나오는가? 실행하는 **파일**의 위치와 실행하는 **파이썬** 중 무엇이 버전을 정하는가?
- 두 가상환경의 `python -m pip freeze` 결과를 비교해 보자. `requests`의 버전은 다른데, 함께 설치된 `certifi`, `idna` 같은 의존성의 버전은 어떤가? 왜 그렇게 되었을까? (힌트: 9.1.5의 `Collecting charset_normalizer<4,>=2 (from requests)`처럼, `requests`는 의존성의 버전을 하나로 정하지 않고 **범위**로 정한다. pip는 그 범위 안에서 무엇을 고르는가?)

**3) `requirements.txt`로 복원하기**

- `old_app`에서 `python -m pip freeze > requirements.txt`로 목록을 만든다.
- `old_app`의 가상환경을 끄고 `.venv`를 지운 뒤, 다시 만들어 `requirements.txt`로 복원한다. `python show_version.py`의 결과가 지우기 전과 같은지 확인한다.
- `new_app`의 `requirements.txt`는 `pip freeze` 없이 **직접** 써 보자. `requests` 한 줄만 적고(버전 없이) 같은 방법으로 복원한다. 이 방식으로 1년 뒤에 복원하면 어떤 버전이 설치될까? `old_app`의 방식과 비교해 각각 어떤 상황에서 좋은지 말해 보자.
- 다 했으면 `old_app`, `new_app` 폴더를 지운다. 가상환경을 지우는 데 "제거 프로그램"이 필요 없다는 것을 확인하자.

**4) 오류 탐정**

다음 상황에서 각각 무엇이 원인인지, 어떻게 고쳐야 하는지 설명하라.

(가) macOS에서 가상환경을 켜고 `python -m pip install requests<3`을 입력했더니 `zsh: no such file or directory: 3`이 났다. 그래서 `python -m pip install requests>=2.32`로 바꿨더니 이번에는 `zsh: 2.32 not found`가 났다. 같은 명령을 리눅스 서버의 bash에서 입력한 동료는 오류 없이 설치가 되었다고 하는데, 그 폴더에 `=2.32`라는 파일이 생겼고 설치된 버전도 조건과 상관없이 최신이었다. 세 경우 각각 셸이 명령을 어떻게 읽은 것인가? 모든 셸에서 의도대로 동작하게 하려면 어떻게 써야 하는가?

(나) `ch09`에서 잘 쓰던 프로젝트 폴더를 `~/projects/demo`로 옮겼다. 터미널에서 `cd ~/projects/demo` 하고 `source .venv/bin/activate`를 하니 프롬프트에 `(.venv)`가 붙었다. 그런데 `python -c "import requests"`가 `ModuleNotFoundError`를 내고, `python -c "import sys; print(sys.executable)"`은 가상환경이 아닌 경로를 출력했다. `.venv/bin/pip --version`은 `bad interpreter: ... no such file or directory`를 냈다. (힌트: 9.1.4의 `VIRTUAL_ENV`와 9.1.8의 규칙 2. 활성화 스크립트 안에는 가상환경을 만들 때의 경로가 적혀 있다.) 이 상태에서 `python -m pip install requests`를 하면 어디에 설치될까?

(다) Homebrew로 파이썬을 설치한 친구가 가상환경 없이 `python3 -m pip install requests`를 했더니 `error: externally-managed-environment`가 났다. AI는 `--break-system-packages`를 붙이라고 했다. 이 친구에게 무엇을 권하겠는가?

(라) 팀원이 프로젝트를 압축해서 보내 주었다. 안에 `.venv` 폴더까지 들어 있어서 압축 파일이 수백 MB다. 압축을 풀고 `source .venv/bin/activate`를 했지만 프로그램이 실행되지 않는다. 팀원에게 무엇을 다르게 보내 달라고 하면 되는가? 받은 뒤에는 무엇을 하면 되는가?

## 9.2 실행 환경 확인

9.1에서 "패키지를 설치한 파이썬과 프로그램을 실행한 파이썬이 다르면 `ModuleNotFoundError`가 난다"는 것을 여러 번 보았다. 이 절에서는 **지금 어느 파이썬을 쓰고 있는지** 확인하는 방법을 정리한다. 터미널, 실행 중인 프로그램, VS Code 세 곳에서 각각 확인할 수 있어야 한다.

### 9.2.1 파이썬이 여러 개인 컴퓨터

"내 컴퓨터에는 파이썬을 한 번만 설치했는데?"라고 생각할 수 있다. 그런데 실제로는 한 컴퓨터에 파이썬이 여러 개 있는 경우가 흔하다.

| 어디서 왔나 | macOS에서의 위치(예) | Windows에서의 위치(예) |
|---|---|---|
| python.org에서 설치(1장) | `/Library/Frameworks/Python.framework/Versions/3.13/bin/python3` | `C:\Users\본인계정\AppData\Local\Programs\Python\Python313\python.exe` |
| 다른 버전을 또 설치 | `.../Versions/3.12/bin/python3` | `...\Python\Python312\python.exe` |
| 운영체제·개발 도구에 딸려 옴 | `/usr/bin/python3` (Xcode 명령행 도구) | `...\Microsoft\WindowsApps\python.exe` (Microsoft Store로 연결되는 바로 가기) |
| Homebrew, Anaconda 등 | `/opt/homebrew/bin/python3`, `~/anaconda3/bin/python` | `C:\Users\본인계정\anaconda3\python.exe` |
| **가상환경** | `~/python-lab/ch09/.venv/bin/python` | `...\python-lab\ch09\.venv\Scripts\python.exe` |

마지막 줄이 중요하다. 가상환경을 하나 만들 때마다 "파이썬"이 하나 늘어난다. 가상환경의 파이썬은 기반 파이썬과 같은 프로그램이지만, **자기 `site-packages`를 쓰는 별개의 파이썬**으로 생각해야 한다. 프로젝트가 세 개면 기반 파이썬까지 적어도 네 개의 파이썬이 있는 셈이다.

그리고 이 파이썬들은 각자 자기 `site-packages`를 가진다. 그래서 "`requests`가 설치되어 있는가?"라는 질문은 그 자체로는 답할 수 없다. **"어느 파이썬에?"**가 빠졌기 때문이다.

### 9.2.2 터미널이 찾는 파이썬

터미널에 `python`(macOS는 가상환경을 켜기 전에는 `python3`)을 입력했을 때 실행되는 것은 9.1.4에서 본 대로 `PATH`의 폴더를 앞에서부터 뒤져 **처음 발견한** 프로그램이다. 그것이 무엇인지 알려 주는 명령이 있다.

**macOS — `which`**

```
which python3
which python
```

```
# 가상환경을 켜기 전
/Library/Frameworks/Python.framework/Versions/3.13/bin/python3
python not found

# ch09의 가상환경을 켠 뒤
/Users/본인계정/python-lab/ch09/.venv/bin/python3
/Users/본인계정/python-lab/ch09/.venv/bin/python
```

`which`는 "이 이름의 명령을 입력하면 어느 파일이 실행되는가"를 알려 준다. 가상환경을 켜기 전에는 `python`이라는 명령이 없다(`python not found`). 켠 뒤에는 `python`과 `python3`가 모두 가상환경의 것이다. `-a` 옵션을 붙이면 `PATH`에서 발견되는 **모든** 후보를 순서대로 보여 준다. 맨 위가 실제로 실행되는 것이다.

```
which -a python3
```

```
/Users/본인계정/python-lab/ch09/.venv/bin/python3
/Library/Frameworks/Python.framework/Versions/3.13/bin/python3
/usr/local/bin/python3
/usr/bin/python3
```

파이썬이 네 개 보인다. 위의 두 개는 가상환경과 python.org 파이썬이고, `/usr/local/bin/python3`는 python.org 설치 프로그램이 만들어 둔 바로 가기, `/usr/bin/python3`는 Xcode 명령행 도구에 딸린 파이썬이다. (보이는 목록은 컴퓨터마다 다르다.)

**Windows — `Get-Command`, `where.exe`**

PowerShell에서는 `Get-Command`가 실제로 실행될 프로그램을 알려 준다.

```
Get-Command python
```

```
CommandType     Name          Version    Source
-----------     ----          -------    ------
Application     python.exe    3.13.2150… C:\Users\본인계정\python-lab\ch09\.venv\Scripts\python.exe
```

`Source` 칸이 실행될 파일이다. 후보를 모두 보려면 `where.exe`를 쓴다.

```
where.exe python
```

```
C:\Users\본인계정\python-lab\ch09\.venv\Scripts\python.exe
C:\Users\본인계정\AppData\Local\Programs\Python\Python313\python.exe
C:\Users\본인계정\AppData\Local\Microsoft\WindowsApps\python.exe
```

맨 위가 실제로 실행되는 것이다. 마지막 `WindowsApps\python.exe`는 진짜 파이썬이 아니라, 파이썬이 없을 때 Microsoft Store를 열어 주는 바로 가기다(1.2.1). PowerShell에서 `where`라고만 쓰면 다른 명령(`Where-Object`)으로 해석되므로 꼭 `.exe`까지 붙인다.

> **명령이 같아도 파이썬이 다를 수 있다**
> 같은 컴퓨터, 같은 `python` 명령이라도 **어느 터미널 창에서, 가상환경을 켰는지에 따라** 실행되는 파이썬이 다르다. VS Code 안의 터미널과 macOS 터미널 앱, Windows의 PowerShell 창도 각자 따로 활성화 상태를 가진다. "아까는 됐는데"라는 생각이 들면 지금 이 창에서 `which python` / `Get-Command python`을 다시 확인하자.

### 9.2.3 실행 중인 파이썬 — `sys.executable`

`which`는 "앞으로 `python`을 입력하면 무엇이 실행될지"를 알려 준다. 그런데 프로그램은 터미널이 아닌 곳에서도 실행된다. VS Code의 ▷ 버튼, 디버거, 나중에 배울 Jupyter 노트북, 다른 프로그램이 실행하는 파이썬 등이다. 이럴 때는 **프로그램 안에서** 자기가 어느 파이썬으로 실행되고 있는지 물어보는 것이 가장 확실하다. 8.2.2에서 만난 `sys.executable`이다.

환경을 점검하는 작은 스크립트를 만들어 두자. 이 장 내내 쓴다.

```python
# check_env.py
"""지금 실행 중인 파이썬과 가상환경 정보를 보여 준다."""

import platform
import sys


def in_virtualenv() -> bool:
    """가상환경의 파이썬으로 실행 중이면 True를 돌려준다."""
    return sys.prefix != sys.base_prefix


def main():
    print("실행 중인 파이썬:", sys.executable)
    print("버전:", platform.python_version())
    print("가상환경:", in_virtualenv())
    print("sys.prefix:", sys.prefix)
    print("sys.base_prefix:", sys.base_prefix)
    for path in sys.path:
        if path.endswith("site-packages"):
            print("site-packages:", path)


if __name__ == "__main__":
    main()
```

- `platform.python_version()` — 표준 라이브러리 `platform` 모듈의 함수로, `'3.13.2'` 같은 버전 문자열을 돌려준다.
- `sys.prefix`와 `sys.base_prefix` — `sys.prefix`는 지금 파이썬이 쓰는 환경의 폴더, `sys.base_prefix`는 기반 파이썬이 설치된 폴더다. 기반 파이썬으로 실행하면 둘이 같고, 가상환경의 파이썬으로 실행하면 `sys.prefix`가 가상환경 폴더가 되어 서로 달라진다. 그래서 `sys.prefix != sys.base_prefix`가 "가상환경 안인가?"를 알아보는 표준적인 방법이다. 9.1.4의 `VIRTUAL_ENV` 환경 변수로도 알 수 있을 것 같지만, 그것은 **활성화했을 때만** 생긴다. 활성화 없이 가상환경의 파이썬을 경로로 실행하면 `VIRTUAL_ENV`는 없어도 `sys.prefix`는 가상환경을 가리킨다.
- `site-packages` — `sys.path`에서 `site-packages`로 끝나는 것만 골라 출력한다. 이 파이썬이 설치한 패키지를 찾는 곳이다.

가상환경을 켠 상태와 끈 상태에서 각각 실행해 보자.

```
python check_env.py
```

8.1.6에서 본 `sys.path`와 비교해 보자. 가상환경으로 실행하면 표준 라이브러리 폴더는 기반 파이썬의 것을 그대로 쓰고, `site-packages`만 가상환경의 것으로 바뀐다. 9.1.2의 그림 그대로다. 그리고 가상환경으로 실행할 때는 기반 파이썬의 `site-packages`가 **목록에 아예 없다**(9.1.3의 `include-system-site-packages = false`). 그래서 기반 파이썬에 무엇이 설치되어 있든 가상환경 안에서는 보이지 않는다.

같은 정보를 파일을 만들지 않고 한 줄로 확인할 수도 있다. 문제를 찾을 때 자주 쓰므로 기억해 두자.

```
python -c "import sys; print(sys.executable)"
```

**`sys.executable`로 설치하기**

`sys.executable`이 알려 주는 경로는 그대로 명령으로 쓸 수 있다. 어떤 프로그램이 `/Users/본인계정/python-lab/ch09/.venv/bin/python`으로 실행되고 있다면, 그 파이썬에 패키지를 설치하는 가장 확실한 명령은 다음과 같다.

```
/Users/본인계정/python-lab/ch09/.venv/bin/python -m pip install requests
```

`python -m pip`의 `python` 자리에 경로를 넣은 것이다. 9.1.6에서 "실행할 때와 설치할 때 앞부분이 같으면 같은 파이썬"이라고 했다. 실행 중인 파이썬의 경로를 알면 활성화 상태와 상관없이 정확히 그 파이썬에 설치할 수 있다. (Windows에서 경로에 공백이 있으면 `& "C:\경로\python.exe" -m pip install requests`처럼 따옴표로 감싸고 앞에 `&`를 붙인다.)

### 9.2.4 VS Code에서 인터프리터 선택하기

1.2.5에서 VS Code의 오른쪽 아래 상태 표시줄에 보이는 `3.13.2`가 "VS Code가 사용할 파이썬(인터프리터)"이라고 했다. 이제 그 선택을 가상환경으로 바꾼다.

**1) 인터프리터 선택**

1. `ch09` 폴더의 `check_env.py`를 연다.
2. 명령 팔레트(`Cmd + Shift + P` / `Ctrl + Shift + P`)에서 `Python: Select Interpreter`를 실행한다. 상태 표시줄의 파이썬 버전을 클릭해도 된다.
3. 목록에서 `ch09/.venv` 안의 파이썬을 고른다. `Python 3.13.2 ('.venv': venv) ./ch09/.venv/bin/python`과 비슷한 모양이다(Windows는 `.\ch09\.venv\Scripts\python.exe`).
4. **목록에 보이지 않으면** `Enter interpreter path...`(인터프리터 경로 입력)를 고르고 `Find...`(찾기)를 눌러 직접 고른다. macOS는 `python-lab/ch09/.venv/bin/python`, Windows는 `python-lab\ch09\.venv\Scripts\python.exe`다. macOS의 파일 선택 창에서는 `.venv` 같은 숨김 폴더가 보이지 않는데, `Cmd + Shift + .`(마침표)을 누르면 보인다.

선택하면 상태 표시줄에 `.venv`라는 글자가 함께 보인다. 이 선택은 지금 연 폴더(`python-lab`)에 대해 기억된다. 그래서 `ch01`의 파일을 열어도 이 파이썬으로 실행된다. 가상환경에도 표준 라이브러리가 그대로 있으므로 1~8장의 코드는 문제없이 돌아간다.

**2) ▷ 버튼으로 실행해 확인**

`check_env.py`를 ▷ 버튼으로 실행한다. 터미널 패널의 첫 줄을 보자.

```
/Users/본인계정/python-lab/ch09/.venv/bin/python /Users/본인계정/python-lab/ch09/check_env.py
실행 중인 파이썬: /Users/본인계정/python-lab/ch09/.venv/bin/python
가상환경: True
...
```

1.2.5에서 "▷ 버튼도 결국 터미널에서 `python 파일경로`를 실행하는 것"이라고 했다. 그 `python` 자리가 이제 **선택한 인터프리터의 절대 경로**다. 9.1.4에서 말한 "활성화하지 않고 가상환경의 파이썬을 경로로 직접 실행하는" 방법이다. 그래서 ▷ 버튼은 터미널의 활성화 상태와 상관없이 **VS Code에서 선택한 인터프리터**로 실행한다.

**3) VS Code의 터미널**

인터프리터로 가상환경을 고른 뒤 VS Code에서 **새 터미널**을 열면(`` Ctrl + ` ``이 터미널 패널을 열고 닫는다. 패널의 `+` 버튼이 새 터미널), VS Code가 가상환경을 자동으로 활성화해 주는 경우가 많다. 열자마자 `source .../.venv/bin/activate` 같은 명령이 저절로 실행되는 것이 보이거나, 프롬프트에 바로 `(.venv)`가 붙어 있다. 붙어 있지 않다면 9.1.4대로 직접 활성화하면 된다. 이미 열려 있던 터미널은 인터프리터를 바꿔도 그대로이므로, 인터프리터를 바꿨으면 새 터미널을 여는 것이 좋다.

**4) 편집기의 밑줄**

VS Code의 Python 확장(Pylance)은 **선택한 인터프리터의 `site-packages`**를 보고 `import`할 수 있는지 판단한다. 기반 파이썬이 선택된 상태에서 `import requests`를 쓰면 `requests` 아래에 노란 물결 밑줄이 생기고, 마우스를 올리면 다음과 같은 설명이 나온다.

```
Import "requests" could not be resolved from source
```

패키지에 따라 `Import "rich.console" could not be resolved`처럼 나오기도 한다. 어느 쪽이든 "선택한 인터프리터에서 이 패키지를 찾지 못했다"는 뜻이다. 실행하면 `ModuleNotFoundError`가 날 것이라는 **미리 알림**이다. 가상환경을 인터프리터로 고르면 밑줄이 사라진다. 이 밑줄이 보이면 먼저 상태 표시줄의 인터프리터를 확인하자.

> **프로젝트마다 VS Code 창을 따로 연다**
> 이 과정에서는 `python-lab` 폴더 하나를 열어 두고 모든 장을 실습한다. 그런데 인터프리터 선택은 열어 둔 폴더 단위로 하나만 기억된다. 실습 9-4처럼 폴더마다 가상환경이 따로 있으면, 그 폴더의 파일을 실행할 때마다 인터프리터를 바꿔야 한다. 그래서 실무에서는 **프로젝트 폴더를 VS Code 창 하나로 따로 연다.** 프로젝트 폴더 바로 아래에 `.venv`가 있으면 VS Code가 대개 알아서 찾아 선택해 주고, 그 창에서는 늘 그 가상환경을 쓴다. 실습 9-4에서 직접 해 본다.

### 9.2.5 터미널의 파이썬과 VS Code의 파이썬이 다를 때

1.2.5에서 "터미널의 python과 VS Code가 선택한 python이 다를 수 있다"고 미뤄 두었던 이야기를 이제 할 수 있다. VS Code 안에서 파이썬을 실행하는 방법은 두 가지이고, 각각 다른 곳에서 파이썬을 정한다.

| 실행 방법 | 어느 파이썬으로 실행되나 | 확인하는 방법 |
|---|---|---|
| 터미널에 `python check_env.py` 입력 | 그 터미널의 `PATH`에서 처음 찾은 `python` (활성화 상태에 따라 다르다) | 프롬프트의 `(.venv)`, `which python` / `Get-Command python` |
| ▷ 버튼, 디버거(`F5`) | VS Code에서 선택한 인터프리터 | 상태 표시줄, ▷를 눌렀을 때 터미널의 첫 줄 |

`requests`가 `ch09/.venv`에만 설치되어 있다고 하자. 두 가지가 엇갈리면 다음과 같은 일이 생긴다.

| 터미널 | VS Code 인터프리터 | `python app.py` 입력 | ▷ 버튼 |
|---|---|---|---|
| 가상환경 활성화 | 가상환경 | 된다 | 된다 |
| 가상환경 활성화 | 기반 파이썬 | 된다 | `ModuleNotFoundError` |
| 활성화 안 함 | 가상환경 | `ModuleNotFoundError` (macOS는 `python`이 없다) | 된다 |
| 활성화 안 함 | 기반 파이썬 | `ModuleNotFoundError` | `ModuleNotFoundError` |

둘째 줄이 1단계에서 흔히 겪는 상황이다. 터미널에서 `pip install`로 가상환경에 설치하고 터미널에서 실행하면 잘 되는데, ▷ 버튼만 누르면 오류가 난다. VS Code는 아직 기반 파이썬을 쓰고 있기 때문이다. 이때 해결책은 기반 파이썬에도 설치하는 것이 아니라 **VS Code의 인터프리터를 가상환경으로 바꾸는 것**이다.

규칙은 하나다. **터미널과 VS Code가 같은 가상환경을 쓰게 맞춘다.** VS Code에서 인터프리터를 가상환경으로 고르고, VS Code의 새 터미널에 `(.venv)`가 붙어 있는지 확인하면 둘이 맞춰진다.

### 9.2.6 "설치했는데 `import`가 안 된다"

이제 이 장의 첫머리에서 말한 문제를 정식으로 풀 수 있다. `ModuleNotFoundError: No module named '...'`가 났는데 분명히 설치했다면, 다음 순서로 확인한다.

**1단계: 실행한 파이썬을 확인한다.** 오류가 난 **바로 그 방법으로** 확인해야 한다. 터미널에서 실행했다면 그 터미널에서 `python -c "import sys; print(sys.executable)"`을, ▷ 버튼으로 실행했다면 터미널에 나온 첫 줄의 맨 앞 경로를 본다. 확실하지 않으면 오류가 나는 `import` 줄 **위에** 다음 두 줄을 잠시 넣고 같은 방법으로 실행한다.

```python
import sys
print(sys.executable)
```

**2단계: 그 파이썬에 패키지가 있는지 확인한다.** 1단계에서 얻은 경로로 `pip show`를 실행한다.

```
/Library/Frameworks/Python.framework/Versions/3.13/bin/python3 -m pip show requests
```

```
WARNING: Package(s) not found: requests
```

이 파이썬에는 없다. 그렇다면 설치한 곳은 어디였을까? 설치할 때 쓴 터미널에서 `python -m pip --version`을 해 보면 `from` 뒤에 다른 경로가 보일 것이다.

**3단계: 둘을 맞춘다.** 방법은 두 가지다.

- **실행하는 쪽을 바꾼다(권장).** 패키지가 설치된 가상환경으로 실행한다. 터미널이라면 그 가상환경을 활성화하고, VS Code라면 인터프리터를 그 가상환경으로 고른다.
- **설치하는 쪽을 바꾼다.** 1단계에서 확인한 파이썬에 설치한다. 그 파이썬이 이 프로젝트의 가상환경이라면 `그 경로 -m pip install requests`로 설치한다. 기반 파이썬이라면 설치하지 말고 첫 번째 방법을 쓰자.

이 세 단계로 대부분 해결된다. 그래도 안 되면 다음을 확인한다.

| 증상 | 원인 | 해결 |
|---|---|---|
| `pip install beautifulsoup4` 후 `import beautifulsoup4`가 안 된다 | **설치 이름과 `import` 이름이 다르다** | 패키지의 PyPI 페이지나 문서의 첫 예제에서 `import` 줄을 확인한다(아래 표) |
| `AttributeError: module 'requests' has no attribute 'get' (consider renaming '.../ch09/requests.py' ...)` | 내 파일 이름이 패키지 이름과 같아서 내 파일을 불러왔다(8.1.6) | 내 파일의 이름을 바꾸고 `__pycache__`를 지운다. 셸은 다시 연다 |
| 설치 명령의 출력 끝에 `ERROR`가 있다 | 설치가 실패했다 | `Successfully installed`가 나왔는지 확인한다. 오류 메시지를 읽는다 |
| 다른 프로젝트 폴더에서는 된다 | 다른 프로젝트의 가상환경을 켜 놓았거나, 이 프로젝트의 가상환경에는 설치하지 않았다 | 프롬프트의 `(.venv)`가 **어느 폴더의** `.venv`인지 `which python`으로 확인한다 |
| 가상환경 폴더를 옮긴 뒤부터 안 된다 | 가상환경 안의 절대 경로가 맞지 않는다(9.1.8) | 가상환경을 지우고 다시 만든 뒤 `requirements.txt`로 복원한다 |

설치 이름과 `import` 이름이 다른 대표적인 패키지는 다음과 같다. 반대로 `import` 이름으로 설치하려 하면 엉뚱한 패키지가 설치되거나 설치가 거절되는 경우가 있으니 조심하자.

| 설치할 때(`pip install`) | 불러올 때(`import`) | 하는 일 |
|---|---|---|
| `beautifulsoup4` | `bs4` | HTML에서 데이터 뽑기 |
| `Pillow` | `PIL` | 이미지 다루기 |
| `scikit-learn` | `sklearn` | 머신러닝 |
| `PyYAML` | `yaml` | YAML 파일 읽고 쓰기 |
| `python-dotenv` | `dotenv` | `.env` 파일을 환경 변수로 읽기(8.2.1) |
| `opencv-python` | `cv2` | 컴퓨터 비전 |

> **AI에게 물을 때도 "어느 파이썬"을 함께 알려 주자**
> `ModuleNotFoundError`를 AI에게 물을 때 오류 메시지만 붙여 넣으면 AI는 "설치하세요"라는 일반적인 답밖에 할 수 없다. 다음 세 가지를 함께 알려 주면 정확한 답을 받을 수 있다. ① 어떻게 실행했는지(터미널 명령인지 ▷ 버튼인지) ② `sys.executable`의 출력 ③ 설치할 때 쓴 명령과 그 터미널의 `python -m pip --version` 출력. 사실 이 세 가지를 모으다 보면 AI에게 묻기 전에 원인이 보이는 경우가 많다.

## 9.3 외부 패키지 사용

설치하는 방법과 실행 환경을 확인하는 방법을 알았으니, 이제 외부 패키지를 실제로 골라서 써 보자. 이 절에서는 PyPI에서 패키지를 찾고, 믿을 만한지 살피고, 문서를 읽고, `requests`로 웹에서 데이터를 가져온다.

### 9.3.1 PyPI에서 패키지 찾기

[https://pypi.org](https://pypi.org)의 검색 창에 `requests`를 입력하고, 결과에서 `requests`를 누르면 프로젝트 페이지가 열린다. 페이지에서 볼 것은 다음과 같다.

- **맨 위** — 패키지 이름과 최신 버전, 그리고 `pip install requests`라는 설치 명령이 있다. 오른쪽에는 마지막으로 새 버전이 나온 날짜(**Released**)가 있다.
- **왼쪽 메뉴의 Release history** — 지금까지 나온 버전과 날짜의 목록이다. 버전이 꾸준히 나오는지, 마지막 버전이 몇 년 전인지 알 수 있다.
- **Project links** — 문서(Documentation)와 소스 코드(Source, 대개 GitHub) 주소다. 사용법은 여기서 찾는다.
- **Meta** — 라이선스(License)와 **필요한 파이썬 버전(Requires: Python)**이 있다. `requests`는 `>=3.10`, 즉 파이썬 3.10 이상에서 동작한다. 내 파이썬 버전과 맞는지 확인하자.
- **가운데의 Project description** — 패키지를 만든 사람이 쓴 소개다. 대개 설치 방법과 간단한 사용 예가 있다. 여기서 `import` 이름도 확인할 수 있다(9.2.6).

**믿을 만한 패키지인지 살피기**

9.1.1에서 PyPI에는 **누구나** 패키지를 올릴 수 있다고 했다. 그리고 `pip install`로 설치한 패키지의 코드는 `import`하는 순간 **내 컴퓨터에서, 내 권한으로** 실행된다. 내 파일을 읽을 수도, 환경 변수에 있는 API 키를 읽을 수도 있다. 그래서 처음 쓰는 패키지는 설치하기 전에 다음을 살펴보는 습관을 들이자.

| 살펴볼 것 | 어디서 보나 | 좋은 신호 |
|---|---|---|
| 관리되고 있는가 | Release history, 소스 저장소의 최근 변경 | 최근 1~2년 안에 새 버전이 나왔다 |
| 많이 쓰이는가 | 소스 저장소(GitHub)의 별(star) 수, 다른 프로젝트와 문서에서 얼마나 언급되는지 | 공식 문서나 유명한 튜토리얼에서 권한다 |
| 문서가 있는가 | Project links의 Documentation | 설치, 빠른 시작, API 설명이 있다 |
| 이름이 정확한가 | 공식 문서의 설치 명령과 비교 | 한 글자도 다르지 않다 |

마지막 줄이 특히 중요하다. 유명한 패키지와 이름이 한두 글자 다른 **가짜 패키지**를 올려 두고, 철자를 틀린 사람이 설치하기를 기다리는 공격이 실제로 있다(`requests` 대신 `reqeusts`처럼). 또 AI가 그럴듯하지만 **존재하지 않는 패키지 이름**을 알려 주는 경우가 있는데, 누군가 그 이름으로 악성 패키지를 먼저 올려 두는 일도 생긴다. 그래서 다음을 지키자.

- AI가 알려 준 패키지는 설치하기 전에 **PyPI에서 검색해** 실제로 있는지, 위의 표에 비추어 믿을 만한지 확인한다.
- 설치 명령은 가능하면 그 패키지의 **공식 문서에서 복사**한다.
- `pip install` 명령을 입력한 뒤 출력의 `Successfully installed ...`에 **내가 설치하려던 이름**이 있는지 본다.

### 9.3.2 문서 읽기

`requests`의 PyPI 페이지에서 Project links의 **Documentation**을 누르면 공식 문서 [https://requests.readthedocs.io](https://requests.readthedocs.io)가 열린다. 외부 패키지의 문서는 대개 비슷한 차례로 되어 있다.

| 부분 | `requests` 문서에서의 이름 | 언제 읽나 |
|---|---|---|
| 설치 | Installation | 처음 한 번 |
| 빠른 시작 | Quickstart | **가장 먼저 읽는다.** 자주 쓰는 사용법이 예제와 함께 있다 |
| 고급 사용법 | Advanced Usage | 빠른 시작으로 부족할 때 |
| API 설명 | API Reference(Developer Interface) | 함수의 매개변수와 반환값을 정확히 알고 싶을 때. 4.6.10에서 읽은 표준 라이브러리 문서의 함수 정의와 같은 역할이다 |

처음에는 **빠른 시작만** 읽으면 된다. `requests`의 빠른 시작은 "요청 보내기(Make a Request)"로 시작해서 응답 내용 읽기, JSON 응답, 상태 코드, 시간 제한(Timeouts), 오류와 예외(Errors and Exceptions) 등으로 이어진다. 다음 절에서 이 가운데 기본적인 것을 차례로 써 본다.

**문서의 버전과 내가 설치한 버전**

8.2.6에서 표준 라이브러리 문서를 볼 때 "내 파이썬의 버전과 문서의 버전을 맞추라"고 했다. 외부 패키지도 같다. 문서는 대개 최신 버전 기준이고, 화면 구석에서 다른 버전의 문서를 고를 수 있다. 내가 설치한 버전은 세 가지 방법으로 확인할 수 있다.

```
python -m pip show requests
```

```python
>>> import requests
>>> requests.__version__
'2.34.2'
>>> from importlib.metadata import version
>>> version("requests")
'2.34.2'
```

`requests.__version__`처럼 버전을 모듈 속성으로 알려 주는 패키지가 많지만, 모든 패키지가 그런 것은 아니다. 표준 라이브러리의 `importlib.metadata.version()`은 **설치 이름**을 주면 그 패키지의 버전을 돌려준다. 어떤 패키지든 쓸 수 있어서 프로그램 안에서 버전을 확인할 때 편하다. 설치되지 않은 이름을 주면 `importlib.metadata.PackageNotFoundError`가 난다. 9.3.5와 실습 9-4에서 쓴다.

셸의 `help(requests.get)`도 4장에서처럼 그대로 쓸 수 있다. 외부 패키지도 독스트링을 잘 써 두기 때문이다.

### 9.3.3 `requests`로 HTTP 요청 보내기

**HTTP를 아주 짧게**

브라우저에서 주소를 입력하면 브라우저는 그 주소의 컴퓨터(**서버**)에 "이 페이지를 주세요"라는 **요청**(request)을 보내고, 서버는 **응답**(response)을 돌려준다. 이 요청과 응답의 약속이 **HTTP**다. 요청하는 쪽을 **클라이언트**라고 한다. 브라우저도 클라이언트이고, 이제 만들 파이썬 프로그램도 클라이언트다.

- **요청**에는 무엇을 할지(**메서드**. 가져오기는 `GET`)와 어디에 요청하는지(**URL**)가 들어간다.
- **응답**에는 결과를 나타내는 세 자리 숫자인 **상태 코드**, 응답에 대한 정보인 **헤더**, 그리고 실제 내용인 **본문**(body)이 들어 있다.

| 상태 코드 | 뜻 |
|---|---|
| `200` | 성공(OK) |
| `404` | 요청한 것이 없다(Not Found) |
| `401`, `403` | 인증이 필요하거나 권한이 없다. API 키가 틀렸을 때 자주 본다 |
| `429` | 너무 자주 요청했다(Too Many Requests) |
| `500`번대 | 서버 쪽에 문제가 생겼다 |

본문은 웹 페이지라면 HTML이지만, 프로그램끼리 데이터를 주고받는 **API**는 주로 7장에서 배운 **JSON**으로 보낸다.

PyPI는 패키지 정보를 JSON으로 돌려주는 API를 제공한다. 브라우저에서 [https://pypi.org/pypi/requests/json](https://pypi.org/pypi/requests/json)을 열어 보자. 웹 페이지 대신 JSON 데이터가 보인다(브라우저에 따라 보기 좋게 정리해서 보여 준다). 9.3.1에서 프로젝트 페이지로 본 정보가 프로그램이 읽기 좋은 모양으로 들어 있다. 이것을 파이썬으로 가져와 보자.

**요청 보내기와 응답 읽기**

가상환경을 켠 터미널에서 셸을 연다.

```python
>>> import requests
>>> response = requests.get("https://pypi.org/pypi/requests/json", timeout=10)
>>> response
<Response [200]>
>>> response.status_code
200
>>> response.ok
True
```

`requests.get(URL)`은 그 URL에 `GET` 요청을 보내고, 응답이 오면 `Response` 객체를 돌려준다. `timeout=10`은 아래에서 설명한다. `status_code`는 상태 코드이고, `ok`는 상태 코드가 400보다 작으면(성공이면) `True`다.

```python
>>> response.headers["Content-Type"]
'application/json'
>>> response.text[:60]
'{"info":{"author":null,"author_email":"Kenneth Reitz <me@ken'
```

`headers`는 응답 헤더를 담은 딕셔너리 같은 객체다. `Content-Type`이 `application/json`이므로 본문이 JSON이라는 것을 알 수 있다. `text`는 본문을 문자열로 준다. 7장에서 `json.loads()`로 이런 문자열을 파이썬 데이터로 바꿨다. `requests`는 그 일을 하는 메서드를 갖고 있다.

```python
>>> data = response.json()
>>> type(data)
<class 'dict'>
>>> data.keys()
dict_keys(['info', 'last_serial', 'ownership', 'releases', 'urls', 'vulnerabilities'])
>>> info = data["info"]
>>> info["version"]
'2.34.2'
>>> info["requires_python"]
'>=3.10'
>>> info["project_urls"]
{'Documentation': 'https://requests.readthedocs.io', 'Source': 'https://github.com/psf/requests'}
>>> len(data["releases"])
163
```

`response.json()`은 `json.loads(response.text)`와 같다. 결과는 3장의 중첩 딕셔너리다. 여기서부터는 지금까지 배운 딕셔너리와 리스트 다루기 그대로다. PyPI 웹 페이지에서 본 최신 버전, 필요한 파이썬, 문서 주소가 모두 들어 있고, 지금까지 나온 버전은 163개다.

**실패한 응답 — `raise_for_status()`**

없는 패키지를 요청해 보자.

```python
>>> response = requests.get("https://pypi.org/pypi/no-such-package-zzz123/json", timeout=10)
>>> response
<Response [404]>
>>> response.ok
False
>>> response.text
'{"message": "Not Found"}'
```

여기서 중요한 점이 있다. **`requests`는 404나 500 응답을 받아도 예외를 일으키지 않는다.** 요청을 보내고 응답을 받는 데는 성공했기 때문이다. 상태 코드를 확인하지 않고 바로 `response.json()["info"]`를 꺼내면, 실패 응답의 본문(`{"message": "Not Found"}`)에서 `info`를 찾다가 엉뚱한 `KeyError`가 난다. 실패한 응답을 예외로 바꾸고 싶으면 `raise_for_status()`를 호출한다.

```python
>>> response.raise_for_status()
Traceback (most recent call last):
  ...
requests.exceptions.HTTPError: 404 Client Error: Not Found for url: https://pypi.org/pypi/no-such-package-zzz123/json
```

`raise_for_status()`는 성공 응답이면 아무 일도 하지 않고, 실패 응답(상태 코드 400 이상)이면 `HTTPError`를 일으킨다. 그래서 흔히 요청 바로 다음 줄에 둔다. 6.2.2에서 실패를 반환값으로 알리는 방식과 예외로 알리는 방식을 비교했다. `requests`는 상태 코드를 반환값(`Response`)에 담아 주고, 예외로 바꿀지는 호출한 쪽이 고르게 한다.

**시간 제한 — `timeout`**

서버가 응답하지 않으면 어떻게 될까? `requests`는 기본적으로 **응답이 올 때까지 끝없이** 기다린다. 프로그램이 아무 메시지도 없이 멈춘 것처럼 보이게 된다. 그래서 `timeout=초`로 기다릴 시간의 한계를 정한다. `requests`의 문서도 실제 코드에서는 거의 모든 요청에 `timeout`을 주라고 권한다.

이때 `timeout=10`은 "요청 전체를 10초 안에 끝내라"는 뜻이 **아니다.** 다음 두 가지 기다림에 **각각** 10초의 한계를 두는 것이다.

- **연결 대기** — 서버와 연결을 맺을 때까지 기다리는 시간
- **읽기 대기** — 연결된 뒤 서버가 **다음 데이터를 보내 줄 때까지** 기다리는 시간. 데이터가 조금이라도 도착하면 다시 0초부터 센다

그래서 서버가 큰 응답을 몇 초마다 조금씩 계속 보내 주면, 한 번도 10초를 넘겨 기다리지 않았으므로 전체 시간이 10초를 넘어도 예외가 나지 않는다. `timeout`은 "응답이 **멈췄을 때** 끝없이 기다리지 않게" 하는 장치다. 두 한계를 따로 주고 싶으면 `timeout=(3, 10)`처럼 (연결, 읽기) 튜플로 쓴다. 이 장의 예처럼 작은 JSON을 받는 요청이라면 `timeout=10` 하나로 충분하다.

한계를 넘기면 예외가 난다. 아주 짧은 시간을 주어 일부러 일으켜 보자.

```python
>>> requests.get("https://pypi.org/pypi/requests/json", timeout=0.001)
Traceback (most recent call last):
  ...
requests.exceptions.ReadTimeout: HTTPSConnectionPool(host='pypi.org', port=443): Read timed out. (read timeout=0.001)
```

(연결 단계에서 시간이 다 되면 `ConnectTimeout`이 난다.)

**연결 실패 — `ConnectionError`**

인터넷 연결을 잠시 끄고(Wi-Fi 끄기) 요청을 보내 보자.

```python
>>> requests.get("https://pypi.org/pypi/requests/json", timeout=10)
Traceback (most recent call last):
  ...
requests.exceptions.ConnectionError: HTTPSConnectionPool(host='pypi.org', port=443): Max retries exceeded with url: /pypi/requests/json (Caused by NameResolutionError(...: Failed to resolve 'pypi.org' ...))
```

메시지가 길지만 끝부분의 `Failed to resolve 'pypi.org'`가 핵심이다. `pypi.org`라는 이름의 서버를 찾지 못했다. 인터넷에 연결되어 있지 않거나 주소의 철자가 틀렸을 때 난다. 확인했으면 인터넷을 다시 켠다.

**`requests`의 예외 계층**

6.1.5에서 예외 클래스는 계층을 이루고, 부모 예외 하나로 여러 자식 예외를 함께 잡을 수 있다고 했다. 6.2.4에서는 도서관 프로그램의 예외를 직접 그렇게 만들었다. `requests`도 그렇게 되어 있다.

```
OSError
└── requests.RequestException        ← 요청에 관한 모든 실패의 부모
    ├── requests.ConnectionError     ← 서버에 연결하지 못했다
    ├── requests.Timeout             ← 시간 안에 응답이 없었다
    │   ├── requests.ConnectTimeout
    │   └── requests.ReadTimeout
    └── requests.HTTPError           ← raise_for_status()가 일으킨다
```

(실제로는 더 많은 자식이 있고, 일부는 여러 부모를 갖는다. 중요한 것만 적었다.)

"어떤 이유든 요청이 실패하면 안내하고 끝낸다"면 `except requests.RequestException`으로 모두 잡는다. 연결 실패와 시간 초과를 다르게 안내하고 싶다면 자식 예외를 먼저 잡는다. 6.1.6에서 본 대로 `except` 절은 위에서부터 차례로 확인하므로, 부모를 먼저 쓰면 자식 절까지 오지 않는다. 모든 예외가 `requests` 모듈 바로 아래에 있어서 `requests.Timeout`처럼 쓸 수 있다. 트레이스백에 나오는 `requests.exceptions.ReadTimeout`과 같은 것이다.

### 9.3.4 표준 라이브러리와 비교 — 외부 패키지를 쓸 때와 쓰지 않을 때

8.2.6에서 본 표준 라이브러리 `urllib.request`로도 같은 일을 할 수 있다.

```python
>>> import json
>>> import urllib.request
>>> with urllib.request.urlopen("https://pypi.org/pypi/requests/json", timeout=10) as response:
...     data = json.load(response)
...
>>> data["info"]["version"]
'2.34.2'
```

간단한 `GET` 요청은 이 정도로 충분하다. 그런데 요청에 데이터를 실어 보내거나, 헤더에 API 키를 넣거나, 실패를 세밀하게 처리하는 일이 많아지면 `requests`가 훨씬 간결하다. 그래서 `requests`는 "Python HTTP for Humans"(사람을 위한 HTTP)라는 소개 문구 그대로 가장 널리 쓰이는 외부 패키지 중 하나가 되었다. (`urllib`은 404 응답에서 바로 `urllib.error.HTTPError` 예외를 일으킨다는 점도 다르다.)

외부 패키지는 편리하지만 **공짜가 아니다.** 하나를 더할 때마다 설치해야 할 것, 버전을 맞춰야 할 것, 9.3.1에서 말한 보안을 살펴야 할 것이 늘어난다. `requests` 하나에 의존성 네 개가 따라온 것을 보았다. 그래서 다음 순서로 판단하자.

1. 표준 라이브러리로 간단히 할 수 있으면 표준 라이브러리를 쓴다. 7장의 `csv`, `json`, 8장의 `collections`가 그런 예다.
2. 외부 패키지가 확실히 낫고, 널리 쓰이며, 잘 관리되고 있으면 외부 패키지를 쓴다. HTTP의 `requests`, 데이터 분석의 `pandas`, LLM API의 공식 SDK가 그런 예다.
3. 쓰기로 했으면 `requirements.txt`에 적는다.

### 9.3.5 프로그램으로 만들기 — PyPI 패키지 정보 보기

배운 것을 모아, 패키지 이름을 명령행 인자로 받아 PyPI의 최신 정보와 **지금 실행 중인 파이썬에 설치된 버전**을 함께 보여 주는 프로그램을 만든다.

```python
# pypi_info.py
"""PyPI에서 패키지 정보를 가져와 보여 준다.

사용법: python pypi_info.py 패키지이름 [패키지이름 ...]
"""

import sys
from importlib.metadata import PackageNotFoundError, version

import requests


def fetch_info(name: str) -> dict | None:
    """PyPI에서 패키지 정보(info)를 가져온다. 없는 패키지이면 None을 돌려준다."""
    url = f"https://pypi.org/pypi/{name}/json"
    response = requests.get(url, timeout=10)
    if response.status_code == 404:
        return None
    response.raise_for_status()
    return response.json()["info"]


def installed_version(name: str) -> str | None:
    """지금 실행 중인 파이썬에 설치된 버전을 돌려준다. 없으면 None."""
    try:
        return version(name)
    except PackageNotFoundError:
        return None


def main():
    if len(sys.argv) < 2:
        print("사용법: python pypi_info.py 패키지이름 [패키지이름 ...]", file=sys.stderr)
        sys.exit(2)

    for name in sys.argv[1:]:
        try:
            info = fetch_info(name)
        except requests.RequestException as e:
            print(f"PyPI에 요청하지 못했습니다: {e}", file=sys.stderr)
            sys.exit(1)

        if info is None:
            print(f"{name}: PyPI에 없는 패키지입니다.")
            continue
        print(f"{info['name']} {info['version']} - {info['summary']}")
        print(f"  필요한 파이썬: {info['requires_python']}")
        installed = installed_version(name)
        if installed is None:
            print("  설치된 버전: 없음")
        else:
            print(f"  설치된 버전: {installed}")


if __name__ == "__main__":
    main()
```

```
python pypi_info.py requests rich no-such-package-zzz123
```

```
requests 2.34.2 - Python HTTP for Humans.
  필요한 파이썬: >=3.10
  설치된 버전: 2.34.2
rich 15.0.0 - Render rich text, tables, progress bars, syntax highlighting, markdown and more to the terminal
  필요한 파이썬: >=3.9.0
  설치된 버전: 없음
no-such-package-zzz123: PyPI에 없는 패키지입니다.
```

코드에서 볼 점은 다음과 같다.

- **import 줄의 순서** — 표준 라이브러리(`sys`, `importlib.metadata`)를 먼저, 빈 줄을 하나 두고 외부 패키지(`requests`)를 쓴다. 8장에서 내 패키지의 import를 그 아래에 따로 둔 것과 같은 관례다. 1.2.5에서 설정한 Ruff가 저장할 때 이 순서로 정리해 준다.
- **404는 "없다"로, 나머지 실패는 예외로** — `fetch_info()`는 "없는 패키지"를 정상적인 결과 중 하나로 보고 `None`을 돌려준다. 이 프로그램에서 없는 이름을 묻는 것은 흔한 일이기 때문이다. 그 밖의 실패 응답(500 등)은 `raise_for_status()`로 예외가 된다.
- **예외 처리는 `main()`에서** — `fetch_info()`는 네트워크 문제에 대해 할 수 있는 일이 없으므로 예외를 그대로 보낸다. `main()`이 `RequestException`을 잡아 표준 오류로 안내하고 종료 코드 1로 끝낸다. 8장의 도서관 프로그램과 같은 역할 나누기다.
- **설치된 버전은 "실행 중인 파이썬" 기준** — `importlib.metadata.version()`은 지금 이 코드를 실행하는 파이썬의 `site-packages`를 본다. 가상환경을 켜고 실행할 때와 끄고 실행할 때 `requests`의 "설치된 버전"이 어떻게 다른지 확인해 보자. 끄고 실행하면 `import requests`에서 먼저 실패하겠지만.

### 9.3.6 이후 과정과의 연결

이 절에서 한 일은 "URL에 요청을 보내고, JSON 응답을 받아 딕셔너리로 다루는 것"이다. 이후 과정에서 배울 LLM API도 바탕은 같다. LLM API를 부르는 것은 "정해진 URL에, API 키를 헤더에 넣고, 질문을 JSON 본문에 담아 `POST` 요청을 보내고, 답이 담긴 JSON 응답을 받는 것"이다. 모양만 보면 다음과 같다(실제로 동작하는 주소가 아니다).

```python
response = requests.post(
    "https://api.example.com/v1/chat",
    headers={"Authorization": f"Bearer {os.environ['EXAMPLE_API_KEY']}"},
    json={"model": "example-model", "messages": [{"role": "user", "content": "안녕"}]},
    timeout=60,
)
response.raise_for_status()
answer = response.json()
```

`openai`나 `anthropic` 같은 공식 SDK(software development kit)는 이런 HTTP 요청을 대신 만들어 주고, 응답을 다루기 쉬운 객체로 바꿔 주는 외부 패키지다. 그래서 SDK를 쓸 때도 이 절에서 본 것들, 즉 상태 코드(401이면 API 키 문제, 429면 너무 잦은 요청), 시간 제한, 연결 실패 예외가 그대로 나온다. HTTP 메서드, 헤더, 인증은 "웹·API 기초"에서, API 키를 `.env` 파일로 관리하는 방법(`python-dotenv`)과 SDK는 "LLM API 활용"에서 자세히 다룬다.

**3) `pypi_info.py` 고치기**

- 문서 주소가 있으면 `  문서: https://...` 줄을 더한다. `info["project_urls"]`가 `None`이거나 `Documentation` 키가 없는 패키지도 있으므로 안전하게 꺼낸다. 문서 주소가 없으면 그 줄을 출력하지 않는다.
- 시간 초과(`requests.Timeout`)와 연결 실패(`requests.ConnectionError`)를 따로 잡아 각각 `PyPI의 응답이 너무 늦습니다.`, `PyPI에 연결할 수 없습니다. 인터넷 연결을 확인하세요.`를 표준 오류로 출력하고 종료 코드 1로 끝낸다. 그 밖의 `RequestException`은 지금처럼 처리한다. `except`의 순서에 주의하자.
- 인터넷을 끄고 실행해 메시지와 종료 코드를 확인한다. `timeout`을 잠시 `0.001`로 바꿔 시간 초과 메시지도 확인한 뒤 되돌린다.
- 가상환경을 끄고(macOS는 `python3`로) 실행하면 어떻게 되는가? 이 프로그램을 처음 받은 사람이 같은 오류를 만나지 않게 하려면 무엇을 함께 주어야 하는가?

**4) `check_updates.py` — `requirements.txt`의 새 버전 확인하기**

`requirements.txt`를 읽어서 각 패키지의 버전을 PyPI의 최신 버전과 비교하는 프로그램을 만든다.

- 파일 경로를 명령행 인자로 받는다. 인자가 없으면 현재 디렉터리의 `requirements.txt`를 쓴다. 인자가 둘 이상이면 사용법을 표준 오류로 출력하고 종료 코드 2로 끝낸다. 파일이 없으면 표준 오류로 알리고 종료 코드 1로 끝낸다.
- 빈 줄과 `#`으로 시작하는 줄은 건너뛴다. `이름==버전` 모양이 아닌 줄(`==`가 없는 줄)은 `건너뜀(버전이 ==로 고정되지 않음): 그 줄`을 표준 오류로 출력하고 건너뛴다.
- 각 패키지를 PyPI에서 조회해 최신 버전과 같으면 `최신`, 다르면 `새 버전 X`, PyPI에 없으면 `PyPI에 없음`을 출력한다. 마지막 줄에 몇 개 중 몇 개를 올릴 수 있는지 출력한다.
- 함수를 나눈다. 파일을 읽어 `(이름, 버전)` 튜플의 리스트를 돌려주는 `parse_requirements(path)`, PyPI에서 최신 버전을 가져오는 `latest_version(name)`, 그리고 `main()`.

다음 내용의 `req_test.txt`로 시험한 결과의 예다(버전 숫자는 실행하는 때에 따라 다르다).

```

certifi==2026.10.23
charset-normalizer==3.5.2
idna==3.20
urllib3==2.7.0
rich
```

```
python check_updates.py req_test.txt
```

```
건너뜀(버전이 ==로 고정되지 않음): rich
requests 2.32.3: 새 버전 2.34.2
certifi 2026.10.23: 최신
charset-normalizer 3.5.2: 최신
idna 3.20: 최신
urllib3 2.7.0: 새 버전 2.8.0
5개 중 2개를 올릴 수 있습니다.
```

- 같은 일을 pip도 할 수 있다. 가상환경에서 `python -m pip list --outdated`를 실행해 결과를 비교해 보자. pip의 명령은 `requirements.txt`가 아니라 무엇을 기준으로 비교하는가?
- 이 프로그램은 버전이 "다른지"만 본다. `requirements.txt`의 버전이 PyPI의 최신 버전보다 **높으면**(그럴 수 있을까?) 어떻게 출력될까? 버전의 크기를 제대로 비교하려면 2)에서 본 문자열 비교로는 안 된다. 실무에서는 `packaging`이라는 외부 패키지의 `Version`을 쓴다. 궁금하면 문서를 찾아보자.

**`rich` 빠른 시작**

`rich`는 터미널에 색, 표, 진행 막대 같은 것을 출력해 주는 패키지다. pip도 설치 진행 막대를 그릴 때 `rich`를 쓴다. 문서는 [https://rich.readthedocs.io](https://rich.readthedocs.io)에 있다. 코드를 고치기 전에, 이 실습에 필요한 것만 셸에서 먼저 익혀 두자. 위의 "준비"를 마친 `library_app` 창의 터미널에서, **프로젝트의 가상환경이 켜진 상태로** 셸을 연다. `ch09`의 가상환경에는 `rich`를 설치하지 않는다. "확인할 것"에서 `rich`가 없는 가상환경으로 실행해 보는 실험에 그 가상환경을 쓰기 때문이다.

```python
>>> from rich.console import Console
>>> console = Console()
>>> console.print("반납 기한이 지났습니다", style="red")
반납 기한이 지났습니다
```

`Console`은 터미널에 출력하는 객체이고, `console.print()`는 `print()`처럼 쓰되 `style`로 색과 굵기를 줄 수 있다. 화면에서는 글자가 빨간색으로 보인다. (이 교재에는 색이 보이지 않는다.) `style`에는 `"red"`, `"green"`, `"bold"`, `"bold red"` 같은 값을 쓴다.

```python
>>> from rich.table import Table
>>> table = Table(title="대출 중 2권")
>>> table.add_column("코드")
>>> table.add_column("제목")
>>> table.add_column("연체", justify="right")
>>> table.add_row("B01", "파이썬 첫걸음", "3일", style="red")
>>> table.add_row("B02", "데이터 과학 입문", "")
>>> console.print(table)
           대출 중 2권
┏━━━━━━┳━━━━━━━━━━━━━━━━━━┳━━━━━━┓

`Table`에 `add_column()`으로 열을, `add_row()`로 줄을 더하고 `console.print()`로 출력한다. 칸의 너비는 내용에 맞춰 저절로 정해진다. 한글은 영문자보다 두 배 넓게 보이는데, `rich`는 그것까지 계산해서 줄을 맞춘다. `justify="right"`는 그 열을 오른쪽으로 맞추고, `add_row()`의 `style`은 그 줄 전체에 색을 준다.

**대괄호를 조심하자 — `escape()`**

`rich`는 문자열 안의 `[red]...[/red]` 같은 대괄호를 **스타일 표시**(마크업)로 읽는다.

```python
>>> console.print("[bold]굵게[/bold] 보통")
굵게 보통
>>> console.print("철수[/]")
Traceback (most recent call last):
  ...
rich.errors.MarkupError: closing tag '[/]' at position 2 has nothing to close
```

첫 줄에서 `[bold]`와 `[/bold]`는 출력되지 않고 "굵게"가 굵은 글씨로 보인다. 둘째 줄은 아예 예외가 났다. 그런데 도서 제목이나 대출자 이름은 **사용자가 입력하거나 파일에서 읽은 데이터**다. 누군가 이름을 `철수[/]`로 입력하면, 그 이름을 표에 넣는 순간 프로그램이 죽는다. 그래서 데이터에서 온 문자열은 `rich.markup.escape()`로 감싸서 넘긴다. `escape()`는 대괄호 앞에 `\`를 붙여 "이것은 스타일 표시가 아니라 글자 그대로"라는 뜻으로 바꿔 준다. 2.3.6에서 배운 이스케이프 문자와 같은 생각이다.

```python
>>> from rich.markup import escape
>>> escape("철수[/]")
'철수\\[/]'
>>> console.print(escape("철수[/]"))
철수[/]
```

**출력을 파일로 돌리면**

`rich`는 출력하는 곳이 터미널인지 아닌지 스스로 확인한다. `python main.py > out.txt`처럼 출력을 파일로 돌리면(8.2.2) 색을 빼고 글자만 쓴다. 파일에 색을 나타내는 이상한 문자가 섞이지 않는다.

**주어진 코드**

`main.py`는 다음 모양이 된다. `rich`가 없을 때의 안내는 직접 완성한다.

```python
# main.py
"""도서 대출 관리 프로그램의 시작 파일. python main.py로 실행한다."""

import sys

try:
    from library.cli import main
except ModuleNotFoundError as e:
    if e.name != "rich":
        raise
    # 요구 사항 8의 안내를 표준 오류로 출력하고 종료 코드 1로 끝낸다


if __name__ == "__main__":
    main()
```

`from library.cli import main`은 `cli.py`를 실행하고(8.1.3), `cli.py`는 맨 위에서 `rich`를 가져온다. 그래서 `rich`가 설치되지 않은 파이썬으로 실행하면 이 줄에서 `ModuleNotFoundError`가 난다. `import`가 실패하는 것도 예외이므로 6장에서 배운 대로 잡을 수 있다. `ModuleNotFoundError` 객체의 `name` 속성에는 찾지 못한 모듈의 이름이 들어 있다. `rich`가 아닌 모듈을 못 찾은 것은 다른 문제(예: 내 코드의 오타)이므로 `raise`로 그대로 다시 일으킨다(6.2.5).

`core.py`에 더할 메서드는 다음과 같다.

```python
    def overdue_loans(self, today: date) -> list[Loan]:
        """연체된 대출 기록을 연체일수가 긴 순서로 돌려준다(같으면 반납 기한 순)."""
        overdue = []
        for loan in self.loans():
            if loan.overdue_days(today) > 0:
                overdue.append(loan)
        return sorted(overdue, key=lambda loan: -loan.overdue_days(today))
```

`loan_lines(today, only_overdue=True)`와 같은 순서의 대출 기록을, 문자열이 아니라 `Loan` 객체로 돌려준다. 표로 만드는 것은 화면 쪽(`cli.py`)의 일이므로, 규칙 쪽(`core.py`)은 "어떤 대출이 연체인가"라는 데이터만 넘긴다. `sorted()`는 같은 값끼리는 원래 순서를 지키므로, 연체일수가 같으면 `loans()`의 순서(반납 기한 순)가 유지된다.

   - `README.md`에는 프로그램 소개 한 줄, 확인한 파이썬 버전(`python --version`의 결과), 가상환경을 만들고 `requirements.txt`로 설치하는 명령(macOS와 Windows), 실행 방법을 적는다. `requirements.txt`가 기록하지 않는 파이썬 버전을 여기에 남기는 것이다(9.1.7).
   - `.gitignore`에는 `.venv/`, `__pycache__/`, 그리고 실행하면서 생기는 데이터 파일 `data/loans.json`, `data/loan_report.csv`를 적는다. 대출 기록은 이 컴퓨터에서 프로그램을 쓰면서 생기는 데이터이고, 사람 이름이 들어 있기 때문이다. `books.csv`는 프로그램을 실행하는 데 필요하므로 올린다.
3. **모듈 구성과 의존 방향** — 8장의 층 구조를 그대로 지킨다. `rich`를 가져오는 모듈은 `cli.py` **하나뿐**이어야 한다. 화면에 어떻게 보여 줄지는 화면 쪽의 일이다. `models.py`, `errors.py`, `core.py`, `storage.py`에는 `rich`가 나오지 않는다. `core.py`에는 위의 `overdue_loans()`를 더한다.
4. **`목록`과 `연체`는 표로** — `cli.py`에 `loan_table(loans: list[Loan], today: date, title: str) -> Table` 함수를 만들어 대출 기록의 리스트로 표를 만든다.
   - 열은 `코드`, `제목`, `대출자`, `반납 기한`, `연체`이고, `연체` 열은 오른쪽 맞춤이다.
   - `반납 기한`은 `format_date()`로 `2026-11-14(토)` 모양으로 쓴다. `연체`는 연체되었으면 `3일`처럼, 아니면 빈 문자열이다.
   - 연체된 줄은 빨간색이다.
   - 표 제목은 `목록`이면 `대출 중 N권`, `연체`면 `연체 N권`이다.
   - `목록`은 `library.loans()`로, `연체`는 `library.overdue_loans(today)`로 대출 기록을 얻는다. 대출 기록이 없으면 표 대신 8장의 메시지(`대출 중인 도서가 없습니다.`, `연체된 도서가 없습니다.`)를 출력한다.
5. **규칙 위반 메시지는 빨간색** — `대출`, `반납`에서 잡은 `LibraryError`의 메시지는 `print_error(message: str) -> None` 함수로 빨간색으로 출력한다. 그 밖의 메시지(`형식: ...`, `알 수 없는 명령입니다...` 등)와 시작할 때의 메시지는 8장 그대로 둔다.
6. **데이터는 `escape()`로** — 표에 넣는 도서 제목과 대출자 이름, `print_error()`로 출력하는 메시지는 `escape()`로 감싼다. 이름에 `[`, `]`가 들어 있어도 그대로 보여야 한다.
7. **`환경` 명령** — 다음 네 줄을 출력한다. 이 줄들은 `environment_lines() -> list[str]` 함수가 만들고, `print_lines()`로 출력한다. `도움`의 명령 목록에도 `환경`을 더한다.
   ```
   파이썬: (sys.executable)
   버전: (platform.python_version())
   가상환경: (가상환경 안이면 sys.prefix, 아니면 '사용하지 않음')
   rich: (설치된 rich의 버전)
   ```
   `rich`의 버전은 `importlib.metadata.version()`으로 얻는다(9.3.2).
8. **`rich`가 없을 때** — `rich`가 설치되지 않은 파이썬으로 `main.py`를 실행하면 트레이스백 대신 다음 세 줄을 **표준 오류**로 출력하고 종료 코드 1로 끝낸다. 둘째 줄의 경로는 실제로 실행한 파이썬이다.
   ```
   rich 패키지를 찾을 수 없습니다.
   실행한 파이썬: /Library/Frameworks/Python.framework/Versions/3.13/bin/python3
   가상환경을 활성화했는지 확인하고, python -m pip install -r requirements.txt로 설치하세요.
   ```
9. **실행 방법** — 프로젝트의 가상환경을 켠 상태에서 다음 방법이 모두 같은 `library_app/data`의 파일을 읽고 써야 한다.
   - `library_app` 폴더에서 `python main.py`
   - `ch09` 폴더에서 `python library_app/main.py`
   - `library_app` 폴더에서 `python -m library`
   - `library_app` 창의 VS Code에서 `main.py`를 열고 ▷ 버튼 (인터프리터는 이 프로젝트의 `.venv`)
10. **복원** — 가상환경을 지우고 다시 만든 뒤 `requirements.txt`로 복원했을 때 똑같이 실행되어야 한다.

**힌트**

- 순서는 `requirements.txt`, `.gitignore`, `README.md` → `core.py`의 `overdue_loans()` → `cli.py` → `main.py`가 좋다. `requirements.txt`는 `rich`를 설치한 **직후에** 만들어 두자. `cli.py`를 고치기 전에도 `rich`는 이미 이 프로젝트의 의존성이다.
- `cli.py`의 맨 위에 더할 `import`는 다음과 같다. 표준 라이브러리, 외부 패키지, 내 패키지 순서로 무리를 지어 둔다. 저장하면 Ruff가 이 순서로 정리해 준다.
  ```python
  import platform
  import sys
  from datetime import date, timedelta
  from importlib.metadata import version
  from pathlib import Path

  from rich.console import Console
  from rich.markup import escape
  from rich.table import Table

  from library.core import Library
  ...
  ```
  `loan_table()`의 타입 힌트에 쓰는 `Loan`도 `library.models`에서 가져온다.
- `console = Console()`은 `cli.py`의 **모듈 수준**에 한 번만 만들어 두고, 함수들이 함께 쓴다. `DEFAULT_DATA_DIR`처럼 모듈의 상수로 생각하면 된다. 화면에 출력하는 객체이므로, 만드는 것만으로는 아무것도 출력하지 않는다(8.1.3의 "모듈의 최상위에는 정의와 상수만"을 어기지 않는다).
- `loan_table()`은 다음 모양이 된다.
  ```python
  table = Table(title=title)
  table.add_column("코드")
  # 나머지 열
  for loan in loans:
      days_over = loan.overdue_days(today)
      # days_over로 연체 칸의 글자와 줄의 style을 정한다. 연체가 아니면 style은 None
      table.add_row(loan.book.code, escape(loan.book.title), ..., style=style)
  return table
  ```
  출력은 `main()`에서 `console.print(loan_table(...))`로 한다. 표를 만드는 함수와 출력하는 코드를 나누어 두면, 셸에서 `loan_table()`의 결과만 따로 만들어 볼 수 있다.
- `환경` 명령은 `print_lines(environment_lines(), "")`로 출력하면 된다. 줄이 비어 있을 일은 없으므로 두 번째 인자는 쓰이지 않는다.
- `main.py`에서 `rich`를 못 찾았는지 시험하려면 가상환경을 끄면 된다. `e.name`이 실제로 무엇인지 궁금하면 `except` 블록에서 잠시 `print(repr(e), e.name)`을 해 보자.
- 시험할 때는 8장처럼 `cli.py`의 `today = date.today()`를 잠시 `today = date(2026, 10, 31)`로 바꾼다.
- 복원을 시험할 때는 9.1.7처럼 **`deactivate` 한 뒤** `.venv`를 지운다. VS Code가 그 가상환경의 파이썬을 쓰고 있으면 Windows에서는 지우기가 실패할 수 있다. 그럴 때는 VS Code의 터미널을 모두 닫고 다시 시도한다. 다시 만든 뒤에는 `Python: Select Interpreter`로 새 `.venv`를 다시 골라 주어야 할 수도 있다.

- **`escape()`가 하는 일 확인하기**: `loan_table()`에서 대출자 이름의 `escape()`를 잠시 지우고, `대출 B04 철수[/]`로 대출한 뒤 `목록`을 입력해 보자. 어떤 일이 생기는가? 프로그램을 다시 실행해 `목록`을 입력하면 또 어떻게 되는가? 대출 기록이 `loans.json`에 이미 저장되었기 때문이다. `escape()`를 되돌리면 이름이 `철수[/]`로 제대로 보이는지 확인한 뒤 `반납 B04`로 정리한다.
- 출력을 파일로 돌려 보자. `python main.py > out.txt`로 실행하고, 화면에 아무것도 보이지 않아도 `목록`과 `종료`를 차례로 입력한다(8장 실습 8-4의 "확인할 것" 참고). `out.txt`를 VS Code로 열면 표는 어떻게 저장되어 있는가? 색을 나타내는 이상한 문자가 섞여 있는가?
- **새 가상환경에 복원하기**: 가상환경을 끄고 `.venv`를 지운 뒤 다시 만들고 `python -m pip install -r requirements.txt`로 복원한다. 실행 예의 두 번째 부분이 똑같이 나오는지 확인한다. `python -m pip freeze`의 결과가 `requirements.txt`와 같은지도 확인하자. 10장의 종합 실습에서는 이것이 완료 기준 중 하나다.
- `python -m pip show rich`의 `Requires`와 `requirements.txt`를 비교하자. `requirements.txt`의 네 줄 중 이 프로젝트가 **직접** 쓰는 것은 무엇이고, 따라온 것은 무엇인가? 실습 9-3의 2)에서 예상한 것과 같은가?
- 각 모듈의 `import` 줄을 다시 보고, `rich`를 가져오는 모듈이 `cli.py` 하나뿐인지 확인한다. 나중에 `rich` 대신 다른 패키지로 바꾸거나, 화면 대신 웹 페이지로 보여 주게 된다면 어느 파일을 고쳐야 하는가? `core.py`와 `storage.py`는 고쳐야 하는가?
- (Git을 써 본 사람만) `library_app`에서 `git init`을 하고 `git status`를 실행해 보자. `.venv`, `__pycache__`, `data/loans.json`이 목록에 보이지 않아야 한다. Git은 이후 "개발 도구" 항목에서 자세히 다룬다.

**더 해 보기 (선택)**

- **`도서`도 표로**: `도서` 명령도 `코드`, `제목`, `상태` 열의 표로 보여 주자. `대출 중`은 노란색, `관내 열람`은 흐리게(`style="dim"`) 보여 준다. 그런데 지금의 `book_lines()`는 문자열을 돌려주므로 표를 만들 수 없다. `core.py`에 무엇을 돌려주는 메서드를 더해야 할까? `overdue_loans()`를 더한 것과 같은 생각으로 설계해 보자.
- **가상환경 밖에서 실행하면 경고하기**: 프로그램이 시작할 때 가상환경 안이 아니면(`sys.prefix == sys.base_prefix`) `경고: 가상환경이 아닌 파이썬으로 실행 중입니다`를 표준 오류로 출력한다. 그런데 `rich`가 기반 파이썬에 설치되어 있지 않다면 이 경고까지 갈 일이 있을까? 어떤 경우에 이 경고가 쓸모 있을지 생각해 보자.
- **`python -m library`에서도 안내하기**: 확인할 것에서 본 대로 `python -m library`로 실행하면 `main.py`의 안내가 동작하지 않는다. 같은 안내 코드를 `library/__main__.py`에도 복사하면 되지만, 같은 코드가 두 곳에 생긴다. 안내를 출력하고 끝내는 함수를 어디에 두면 두 곳에서 함께 쓸 수 있을까? 그 모듈은 `rich`를 가져오면 안 된다. 왜일까?
- **진행 표시**: `rich`에는 진행 막대(`rich.progress`)와 상태 표시(`console.status()`)도 있다. 실습 9-3의 `check_updates.py`에 `rich`를 써서, PyPI에 요청하는 동안 `PyPI 조회 중...` 같은 표시가 돌아가게 해 보자. 문서의 Progress Display 부분을 찾아 읽는 것부터 시작한다. `check_updates.py`는 `ch09`의 가상환경에서 실행하므로 `rich`를 그 가상환경에도 설치해야 한다. 그러면 "확인할 것"의 "다른 가상환경으로 실행해 보기"는 더 이상 재현되지 않으므로, 그 확인을 모두 마친 뒤에 하자. 설치한 뒤에는 `ch09`의 `requirements.txt`도 새로 만든다.

## 정리

| 항목 | 핵심 |
|---|---|
| 외부 패키지 | 표준 라이브러리 밖의 패키지. 내려받아 설치해야 `import`할 수 있다 |
| PyPI | 파이썬 패키지의 공식 저장소(pypi.org). 누구나 올릴 수 있다 |
| pip | PyPI에서 패키지를 내려받아 설치하는 프로그램. 파이썬마다 자기 pip이 있다 |
| `site-packages` | 설치한 패키지가 들어가는 폴더. `sys.path`의 세 번째 부분. 파이썬마다 따로 있다 |
| 설치 이름과 `import` 이름 | 다를 수 있다. `beautifulsoup4` → `bs4`, `Pillow` → `PIL`, `python-dotenv` → `dotenv` |
| 한 곳에 모두 설치하면 | 버전이 부딪히고, 프로젝트에 무엇이 필요한지 모르고, 되돌리기 어렵다. 시스템 파이썬은 `externally-managed-environment`로 거절한다 |
| 가상환경 | 프로젝트 전용 `site-packages`를 가진 작은 폴더. 파이썬 자체와 표준 라이브러리는 기반 파이썬의 것을 쓴다 |
| 만들기 | `python -m venv .venv`(macOS는 켜기 전이므로 `python3`). 이름은 `.venv`가 관례. 버전은 만든 파이썬의 버전 |
| 활성화 | macOS `source .venv/bin/activate`, Windows `.venv\Scripts\Activate.ps1`. 프롬프트에 `(.venv)`. 그 창에서만 유효 |
| 활성화가 하는 일 | `PATH` 맨 앞에 `.venv/bin`(`Scripts`)을 넣는다. 그래서 `python`, `pip`이 가상환경의 것. macOS에서도 `python`으로 통일 |
| 비활성화 | `deactivate`. 터미널을 닫아도 꺼진다 |
| 활성화 없이 | `.venv/bin/python`(`.venv\Scripts\python.exe`)을 경로로 실행해도 가상환경의 파이썬. ▷ 버튼이 이렇게 한다 |
| PowerShell 실행 정책 | `Activate.ps1`이 막히면 `Set-ExecutionPolicy -ExecutionPolicy RemoteSigned -Scope CurrentUser` |
| 설치 | `python -m pip install 이름`. 의존성도 함께 설치된다. `==`, `>=`, `<`로 버전 지정. `>`, `<`는 따옴표로 감싼다 |
| 확인·삭제 | `list`, `show 이름`(`Location`, `Requires`), `uninstall 이름`(의존성은 남는다), `install --upgrade 이름` |
| `python -m pip` | 실행할 때와 같은 파이썬에 설치한다. `pip`, `pip3`은 어느 파이썬의 것인지 알 수 없다. `python -m pip --version`으로 확인 |
| 쓰지 않을 것 | `sudo pip`, `--break-system-packages`. 권한·관리 오류는 가상환경을 켜라는 신호 |
| `requirements.txt` | `python -m pip freeze > requirements.txt`로 만들고, `python -m pip install -r requirements.txt`로 복원한다 |
| freeze 방식 | 모든 패키지의 정확한 버전. 호환되는 환경에서 그 버전으로 복원된다. 가상환경에는 그 프로젝트에 필요한 것만 설치하고, 바뀌면 다시 freeze |
| 기록되지 않는 것 | 파이썬 버전, 운영체제, 파이썬 밖의 프로그램과 설정. 확인한 파이썬 버전은 `README.md`에 적는다 |
| 프로젝트와 가상환경 | 프로젝트마다 하나. 내 코드는 넣지 않는다. 공유·복사·이동하지 않고 지우고 다시 만든다 |
| `.gitignore` | `.venv/`, `__pycache__/`, 비밀 값 파일, 실행하며 생기는 데이터. 3.13부터 `.venv` 안에 `.gitignore`가 생긴다 |
| 다른 도구 | conda, uv, poetry. 격리된 환경 + 패키지 목록 파일이라는 생각은 같다 |
| 파이썬이 여러 개 | python.org, 운영체제, Homebrew·Anaconda, 그리고 가상환경마다 하나씩. "설치되어 있나?"에는 "어느 파이썬에?"가 따라붙는다 |
| 터미널이 찾는 파이썬 | macOS `which python`, `which -a python3`. Windows `Get-Command python`, `where.exe python`. `PATH`의 앞에서부터 |
| 실행 중인 파이썬 | `sys.executable`. 한 줄로는 `python -c "import sys; print(sys.executable)"` |
| 가상환경 안인가 | `sys.prefix != sys.base_prefix`. `VIRTUAL_ENV`는 활성화했을 때만 있다 |
| VS Code 인터프리터 | `Python: Select Interpreter`. 없으면 `Enter interpreter path...`. ▷와 디버거, 편집기 밑줄이 이것을 따른다 |
| VS Code 터미널 | 새 터미널은 선택한 가상환경을 자동으로 활성화하는 경우가 많다. `(.venv)` 확인 |
| 터미널과 VS Code | 실행하는 곳마다 파이썬을 정하는 곳이 다르다. 같은 가상환경을 쓰게 맞춘다 |
| 설치했는데 `import`가 안 될 때 | ① 실행한 파이썬(`sys.executable`) ② 그 파이썬에 있는지(`경로 -m pip show`) ③ 실행하는 쪽(권장)이나 설치하는 쪽을 맞춘다. 그다음 이름 차이, 이름 가리기 |
| PyPI에서 고르기 | 최근 릴리스, 사용 규모, 문서, 필요한 파이썬, **정확한 이름**. AI가 알려 준 이름은 PyPI에서 확인 |
| 문서 읽기 | 빠른 시작부터. 문서 버전과 설치 버전을 맞춘다. `importlib.metadata.version("이름")` |
| HTTP | 클라이언트가 요청(메서드, URL)을 보내면 서버가 응답(상태 코드, 헤더, 본문)을 돌려준다. API는 주로 JSON |
| `requests.get()` | `requests.get(url, timeout=10)` → `Response`. `status_code`, `ok`, `headers`, `text`, `json()` |
| 실패한 응답 | 404·500에도 예외가 나지 않는다. `raise_for_status()`로 `HTTPError`를 일으키거나 상태 코드를 직접 본다 |
| `timeout` | 주지 않으면 끝없이 기다릴 수 있다. 늘 준다. 연결 대기와 읽기 대기(다음 데이터까지) 각각의 한계이고 요청 전체의 시간 제한은 아니다. 넘으면 `Timeout` |
| `requests`의 예외 | `RequestException` ← `ConnectionError`, `Timeout`, `HTTPError`. 구체적인 것부터 잡는다 |
| 외부 패키지를 쓸지 | 표준 라이브러리로 충분하면 표준 라이브러리. 확실히 낫고 널리 쓰이고 잘 관리되면 외부 패키지. 의존성은 비용이다 |
| `rich` | `Console().print(..., style=)`, `Table`의 `add_column()`/`add_row()`. 대괄호는 마크업이므로 데이터는 `escape()` |
