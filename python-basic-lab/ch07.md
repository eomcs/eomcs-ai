# 7장. 파일 입출력

[파이썬 기초](README.md) 과정의 일곱 번째 장이다. 지금까지 만든 프로그램은 모두 **끝나면 잊어버렸다.** 6장의 도서 대출 프로그램에서 아무리 많은 대출을 처리해도, `종료`를 입력하는 순간 대출 기록은 모두 사라졌다. 변수와 객체는 프로그램이 실행되는 동안에만 메모리에 있기 때문이다. 이 장에서는 데이터를 **파일**에 저장해서 프로그램이 끝난 뒤에도 남게 하고, 다음에 실행할 때 다시 읽어 오는 방법을 배운다.

- **텍스트 파일** — `open()`으로 파일을 열어 읽고 쓰고, `with` 문으로 다 쓴 파일을 자동으로 닫는다. 읽기·쓰기·추가 모드의 차이, 줄 단위로 처리하는 방법, 한글이 깨지지 않게 하는 **인코딩**(UTF-8)을 다룬다.
- **경로 다루기** — `pathlib.Path`로 경로를 조합하고, 파일이 있는지 확인하고, 폴더 안의 파일을 훑는다. 그리고 "분명히 파일이 있는데 `FileNotFoundError`가 나는" 문제의 가장 흔한 원인인 **실행 위치에 따라 상대 경로가 달라지는 문제**를 해결한다.
- **구조화된 파일** — 표 모양의 데이터는 **CSV**로, 겹겹이 쌓인 데이터는 **JSON**으로 저장하고 읽는다. 파일 속의 데이터를 3장의 리스트·딕셔너리, 5장의 데이터 클래스로 바꾸고, 다시 파일로 되돌린다.

AI 엔지니어의 일은 파일과 떨어질 수 없다. 프롬프트가 길어지면 코드에서 떼어 내 텍스트 파일로 관리한다. RAG(검색 증강 생성)를 만들 때 LLM에게 참고하라고 넘겨줄 문서도 결국 파일에서 읽는다. 모델이 얼마나 잘 답하는지 평가할 질문과 정답 목록은 CSV로, LLM에게 "JSON으로 답하라"고 해서 받은 답은 JSON으로 다룬다. 파인튜닝 데이터나 대화 기록은 **JSONL**(한 줄에 JSON 하나)이라는 형식으로 저장하는 경우가 많다. 예를 들어 다음은 이후 과정에서 자주 보게 될 모양이다.

```python
with open("prompts/summary.txt", encoding="utf-8") as f:
    template = f.read()

with open("eval/questions.jsonl", encoding="utf-8") as f:
    for line in f:
        item = json.loads(line)
        answer = ask_llm(template.format(question=item["question"]))
        ...
```

이 장을 마치면 이런 코드가 "어떤 파일을 어떤 형식으로 읽어 어떤 파이썬 자료구조로 바꾸는지" 읽을 수 있고, 내 프로그램의 데이터를 파일에 저장했다가 다시 불러올 수 있게 된다.

## 학습 목표

이 장을 마치면 다음을 할 수 있다.

- `open()`으로 텍스트 파일을 열어 `read()`, `write()`로 읽고 쓸 수 있다.
- 파일을 닫아야 하는 이유를 설명하고, `with` 문으로 파일을 열어 자동으로 닫히게 할 수 있다. `with`가 6장의 `try`/`finally`와 어떤 관계인지 설명할 수 있다.
- 읽기(`"r"`), 쓰기(`"w"`), 추가(`"a"`), 새로 만들기(`"x"`) 모드의 차이를 알고, `"w"` 모드가 기존 내용을 지운다는 것을 기억한다.
- 파일을 줄 단위로 읽고, 줄 끝의 줄바꿈 문자(`\n`)를 처리할 수 있다.
- 문자와 바이트, 인코딩의 관계를 설명하고, 파일을 열 때 항상 `encoding="utf-8"`을 지정하는 이유를 설명할 수 있다. `UnicodeDecodeError`가 났을 때 원인을 짐작할 수 있다.
- `FileNotFoundError`, `FileExistsError`, `IsADirectoryError`, `PermissionError`가 `OSError`의 자식이라는 것을 알고, 파일 작업의 예외를 알맞게 처리할 수 있다.
- `pathlib.Path`로 경로를 조합하고(`/`), 이름·확장자·상위 폴더를 꺼내고, 파일과 폴더가 있는지 확인할 수 있다.
- 폴더를 만들고(`mkdir`), 폴더 안의 파일을 훑을 수 있다(`iterdir`, `glob`, `rglob`).
- 상대 경로가 **현재 디렉터리**를 기준으로 한다는 것과, 그 때문에 실행 위치에 따라 결과가 달라지는 문제를 설명하고, `Path(__file__).parent`로 해결할 수 있다.
- `csv` 모듈로 CSV 파일을 읽고 쓸 수 있다. `newline=""`과 `utf-8-sig`가 필요한 이유를 설명할 수 있다.
- `json` 모듈로 파이썬 자료구조와 JSON 문자열·파일을 서로 바꿀 수 있다(`dumps`/`loads`, `dump`/`load`). JSON으로 바꿀 때 달라지거나 바꿀 수 없는 값을 알고 직접 변환할 수 있다.
- 데이터 클래스의 리스트를 JSON·CSV 파일로 저장하고 다시 데이터 클래스로 읽어 올 수 있다.
- 상황에 따라 텍스트, CSV, JSON, JSONL 중 알맞은 형식을 고를 수 있다.

1. **스크립트는 터미널에서 `ch07` 폴더로 이동한 뒤 실행한다.** `cd ~/python-lab/ch07`로 이동하고 `python 파일이름.py`로 실행한다. 대화형 셸도 `ch07` 폴더에서 연다. VS Code의 ▷ 버튼으로 실행하면 이 장의 앞부분 예제에서 `FileNotFoundError`가 날 수 있다. 왜 그런지, 어떻게 고치는지는 7.2.4에서 정면으로 다룬다. 그 전까지는 터미널에서 실행하자.

실습에 쓸 데이터 파일 중 몇 개는 VS Code에서 직접 만든다. 탐색기에서 `ch07` 폴더를 선택하고 새 파일 아이콘을 눌러 이름을 입력한 뒤, 교재의 내용을 붙여 넣고 저장하면 된다. 1장에서 `settings.json`에 `"files.encoding": "utf8"`을 넣어 두었으므로 VS Code는 파일을 UTF-8로 저장한다. 창 오른쪽 아래 상태 표시줄에 `UTF-8`이 보이는지 확인하자. 이 표시의 의미는 7.1.7에서 배운다.

> **1단계를 마친 사람에게**
> AI가 만들어 준 코드에서 `open("data.txt")`이나 `json.load(open("config.json"))` 같은 줄을 본 적이 있을 것이다. 내 컴퓨터에서는 잘 돌아갔는데, 친구의 Windows 컴퓨터에서는 한글이 깨지거나 `UnicodeDecodeError`가 나고, VS Code의 ▷ 버튼으로 실행하면 `FileNotFoundError`가 나고, AI가 넣어 준 `/Users/someone/project/data.csv` 같은 경로는 애초에 내 컴퓨터에 없다. 모두 이 장에서 다루는 문제다. **인코딩을 지정하지 않은 것, 파일을 닫지 않은 것, 경로를 실행 위치에 맡긴 것**이 원인이다. 이 장을 마치면 AI가 만든 파일 입출력 코드에서 고쳐야 할 줄이 바로 보일 것이다.

## 7.1 텍스트 파일

이 절에서는 글자로 된 파일을 읽고 쓰는 방법을 배운다. 파일 입출력의 모든 것이 이 절의 `open()`과 `with`에서 시작한다.

### 7.1.1 파일 — 프로그램이 끝나도 남는 데이터

변수에 담은 값은 **메모리**에 있다. 메모리는 빠르지만, 프로그램이 끝나면 그 프로그램이 쓰던 메모리는 운영체제에 돌려주고 내용은 사라진다. 프로그램이 끝나도, 컴퓨터를 껐다 켜도 남아 있어야 하는 데이터는 **저장 장치**(SSD, 하드 디스크)에 둔다. 저장 장치에 이름을 붙여 저장한 데이터 덩어리가 **파일**(file)이다.

| | 메모리(변수) | 파일 |
|---|---|---|
| 언제까지 남나 | 프로그램이 끝날 때까지 | 지울 때까지 |
| 무엇으로 찾나 | 변수 이름 | 경로(폴더와 파일 이름) |
| 속도 | 빠르다 | 상대적으로 느리다 |
| 다른 프로그램과 | 나눠 쓸 수 없다 | 나눠 쓸 수 있다(편집기, 엑셀, 다른 파이썬 프로그램) |

그래서 프로그램은 보통 이렇게 일한다. **시작할 때 파일에서 읽어 변수에 담고, 메모리에서 빠르게 처리한 뒤, 남겨야 할 결과를 파일에 쓴다.** 이 장의 마지막 실습에서 도서 대출 프로그램이 정확히 이 순서로 바뀐다.

파일은 내용에 따라 크게 두 가지로 나눈다.

- **텍스트 파일** — 사람이 읽을 수 있는 글자로 이루어진 파일. `.txt`, `.py`, `.md`, `.csv`, `.json`이 모두 텍스트 파일이다. VS Code 같은 편집기로 열어서 읽고 고칠 수 있다.
- **바이너리 파일** — 글자가 아닌 데이터로 이루어진 파일. 사진(`.jpg`, `.png`), 음악, 엑셀 파일(`.xlsx`), 프로그램 실행 파일 등이다. 편집기로 열면 알 수 없는 기호만 보인다.

이 장에서는 텍스트 파일을 다룬다. 바이너리 파일은 보통 그 형식을 다루는 라이브러리(이미지라면 Pillow, 엑셀이라면 openpyxl이나 pandas)를 통해 읽고 쓰기 때문에, 직접 다룰 일은 많지 않다.

텍스트 파일의 내용은 결국 **하나의 긴 문자열**이다. 여러 줄로 보이는 것은 줄이 끝나는 곳마다 **줄바꿈 문자** `\n`(2.3에서 배운 이스케이프 문자)이 들어 있기 때문이다. 다음 두 줄짜리 파일의

```
안녕하세요
파일 입출력을 배웁니다.
```

실제 내용은 `'안녕하세요\n파일 입출력을 배웁니다.\n'`이라는 문자열이다. 이 사실을 기억하면 이 절의 많은 동작이 자연스럽게 이해된다.

### 7.1.2 파일에 쓰기 — `open()`, `write()`, `close()`

파일을 다루는 순서는 세 단계다. **열고**(open), **읽거나 쓰고**(read/write), **닫는다**(close). `ch07` 폴더에서 대화형 셸을 열고 파일을 하나 만들어 보자.

```python
>>> f = open("hello.txt", "w", encoding="utf-8")
>>> f.write("안녕하세요\n")
6
>>> f.write("파일 입출력을 배웁니다.\n")
14
>>> f.close()
```

VS Code 탐색기의 `ch07` 폴더에 `hello.txt`가 생겼을 것이다. 열어 보면 두 줄이 들어 있다.

한 줄씩 살펴보자.

- `open("hello.txt", "w", encoding="utf-8")` — 파일을 연다. 첫 번째 인자는 **파일 경로**, 두 번째 인자는 **모드**다. `"w"`는 쓰기(write) 모드로, 파일이 없으면 새로 만든다. `encoding="utf-8"`은 글자를 어떤 규칙으로 저장할지 정하는 것인데, 7.1.7에서 자세히 배운다. 지금은 **텍스트 파일을 열 때는 언제나 붙인다**고 기억하자.
- `open()`은 열린 파일을 나타내는 **파일 객체**를 돌려준다. 관례적으로 `f`라는 이름에 담는다. 이후의 읽기·쓰기는 모두 이 객체의 메서드로 한다.
- `f.write(문자열)` — 문자열을 파일에 쓴다. 돌려주는 값은 **쓴 글자 수**다. `"안녕하세요\n"`은 다섯 글자에 줄바꿈 문자 하나를 더해 6이다. 셸은 돌려받은 값을 화면에 보여 주므로 `6`, `14`가 나왔다. 스크립트에서는 이 값을 쓸 일이 거의 없다.
- `write()`는 `print()`와 달리 **줄을 바꿔 주지 않는다.** 줄을 바꾸려면 문자열 끝에 `\n`을 직접 넣어야 한다.
- `f.close()` — 파일을 닫는다. 왜 닫아야 하는지는 7.1.4에서 본다.

`print()`에 `file=` 인자를 주면 화면 대신 파일에 출력한다. `print()`처럼 줄도 바꿔 주고, 여러 값을 공백으로 이어 준다.

```python
>>> f = open("hello2.txt", "w", encoding="utf-8")
>>> print("이름:", "철수", file=f)
>>> print("나이:", 20, file=f)
>>> f.close()
```

`hello2.txt`에는 `이름: 철수`와 `나이: 20` 두 줄이 들어간다. `write()`는 문자열만 받으므로 숫자를 쓰려면 `str()`이나 f-string으로 바꿔야 하지만, `print()`는 알아서 바꿔 준다.

### 7.1.3 파일 읽기 — `read()`

이번에는 방금 만든 파일을 읽어 보자. 같은 셸에서 이어서 입력한다.

```python
>>> f = open("hello.txt", encoding="utf-8")
>>> text = f.read()
>>> text
'안녕하세요\n파일 입출력을 배웁니다.\n'
>>> print(text)
안녕하세요
파일 입출력을 배웁니다.

```

- 모드를 생략하면 **읽기 모드**(`"r"`)다. `open("hello.txt", "r", encoding="utf-8")`과 같다.
- `f.read()`는 파일의 **내용 전체를 문자열 하나로** 돌려준다. 7.1.1에서 말한 대로 줄바꿈 문자 `\n`이 그대로 들어 있다.
- `print(text)`의 출력 끝에 빈 줄이 하나 더 보인다. 파일의 마지막 `\n`에서 줄이 바뀌고, `print()`가 한 번 더 줄을 바꾸었기 때문이다.

같은 파일 객체로 `read()`를 한 번 더 호출해 보자.

```python
>>> f.read()
''
>>> f.close()
>>> f.read()
Traceback (most recent call last):
  File "<python-input-14>", line 1, in <module>
    f.read()
    ~~~~~~^^
ValueError: I/O operation on closed file.
```

두 번째 `read()`는 빈 문자열을 돌려주었다. 파일 객체는 **어디까지 읽었는지**를 기억한다. 첫 번째 `read()`가 끝까지 읽었으므로 더 읽을 것이 없다. 처음부터 다시 읽으려면 파일을 다시 열면 된다. 닫은 파일을 읽으려고 하면 `ValueError`가 난다. "파일 객체는 맞는데 닫힌 상태라서 이 일을 할 수 없다"는 뜻이다(6.1.4의 `ValueError` 설명과 같다).

없는 파일을 읽기 모드로 열면 6.1.4에서 본 `FileNotFoundError`가 난다. 쓰기 모드는 파일이 없으면 만들어 주지만, 읽기 모드는 만들어 주지 않는다. 없는 것을 읽을 수는 없기 때문이다.

### 7.1.4 파일을 닫아야 하는 이유와 `with` 문

`close()`를 빼먹으면 어떻게 될까? 같은 셸에서 실험해 보자. 파일 크기(바이트 수)를 알려 주는 `os.path.getsize()`를 함께 쓴다. `os` 모듈은 8장에서 다루고, 여기서는 이 함수 하나만 빌려 쓴다.

```python
>>> f = open("buffer.txt", "w", encoding="utf-8")
>>> f.write("저장될까?")
5
>>> import os
>>> os.path.getsize("buffer.txt")
0
>>> f.close()
>>> os.path.getsize("buffer.txt")
13
```

`write()`로 다섯 글자를 썼다고 했는데, 파일 크기는 **0**이다. 닫은 뒤에야 13바이트가 되었다. (다섯 글자가 왜 13바이트인지는 7.1.7에서 알게 된다.) VS Code에서 `close()` 전에 `buffer.txt`를 열어 보면 비어 있는 것을 확인할 수 있다.

저장 장치에 쓰는 일은 메모리에 쓰는 것보다 훨씬 느리다. 그래서 파이썬은 `write()`할 때마다 곧바로 저장 장치에 쓰지 않고, **버퍼**(buffer)라는 메모리 공간에 모아 두었다가 어느 정도 차거나 파일을 닫을 때 한꺼번에 쓴다. 택배 기사가 물건 하나가 들어올 때마다 배달을 떠나지 않고 트럭에 모아서 출발하는 것과 같다.

그래서 파일을 닫지 않으면 다음 문제가 생긴다.

- **쓴 내용이 저장되지 않을 수 있다.** 버퍼에 남은 내용은 프로그램이 정상적으로 끝날 때 대개 저장되지만, 그 전에 같은 파일을 다른 곳에서 읽으면 비어 있다. 프로그램이 비정상적으로 끝나면 영영 저장되지 않을 수도 있다.
- **운영체제의 자원을 계속 붙잡고 있다.** 한 프로그램이 동시에 열어 둘 수 있는 파일 수에는 한계가 있다. 반복문 안에서 파일을 열기만 하고 닫지 않으면 언젠가 `Too many open files` 오류를 만난다.
- **Windows에서는 열려 있는 파일을 지우거나 이름을 바꿀 수 없다.** 다른 프로그램도 그 파일을 마음대로 다루지 못한다.

그러니 파일은 다 쓰면 반드시 닫아야 한다. 그런데 읽거나 쓰는 도중에 예외가 나면 `close()` 줄까지 가지 못한다. 6.1.8에서 배운 `finally`가 이럴 때 쓰는 것이었다.

```python
f = open("hello.txt", encoding="utf-8")
try:
    text = f.read()
finally:
    f.close()
```

`try` 블록에서 무슨 일이 생기든 `finally`가 파일을 닫는다. 맞는 코드지만, 파일을 열 때마다 이렇게 쓰기는 번거롭다. 그래서 파이썬에는 이 일을 대신해 주는 **`with` 문**이 있다.

```python
>>> with open("hello.txt", encoding="utf-8") as f:
...     text = f.read()
...
>>> f.closed
True
>>> text
'안녕하세요\n파일 입출력을 배웁니다.\n'
```

`with open(...) as f:`는 파일을 열어 `f`에 담고, **들여쓴 블록이 끝나면 파일을 자동으로 닫는다.** 블록이 정상적으로 끝나든, 중간에 예외가 나든, `return`으로 함수를 빠져나가든 마찬가지다. 파일 객체의 `closed` 속성으로 닫혔는지 확인할 수 있다. 블록 안에서 읽은 `text`는 블록이 끝난 뒤에도 그대로 쓸 수 있다. 닫힌 것은 파일이지 변수가 아니다.

예외가 나도 닫히는지 스크립트로 확인해 보자. `hello.txt`의 내용을 정수로 바꾸려고 하면 `ValueError`가 날 것이다.

```python
# with_demo.py
try:
    with open("hello.txt", encoding="utf-8") as f:
        print("파일을 열었다.")
        number = int(f.read())
        print("숫자로 바꿨다.")
except ValueError as e:
    print("오류:", e)
print("닫혔나?", f.closed)
```

```
파일을 열었다.
오류: invalid literal for int() with base 10: '안녕하세요\n파일 입출력을 배웁니다.\n'
닫혔나? True
```

`int()`에서 예외가 나서 `숫자로 바꿨다.`는 출력되지 않았다. 예외는 `with` 블록을 빠져나가 바깥의 `except`가 잡았는데, 그 사이에 `with`가 파일을 닫아 주었다. 6.1.8에서 "`with`가 무엇을 대신해 주는지 이해하려면 `finally`를 알아야 한다"고 했던 것이 바로 이것이다. `with` 문은 **"열었으면 반드시 닫는다"를 `try`/`finally` 없이 보장하는 문법**이다.

앞으로 파일은 **언제나 `with`로 연다.** 이 장의 나머지 코드도 모두 그렇게 쓴다. 파일 두 개를 함께 열 때는 쉼표로 이어 쓸 수 있다.

```python
with open("hello.txt", encoding="utf-8") as src, open("copy.txt", "w", encoding="utf-8") as dst:
    dst.write(src.read())
```

`with`는 파일만을 위한 문법이 아니다. "시작할 때 준비하고, 끝날 때 정리해야 하는" 객체라면 무엇이든 쓸 수 있다. 이런 객체를 **컨텍스트 관리자**(context manager)라고 한다. 이후 과정에서 데이터베이스 연결, 네트워크 세션 같은 것을 `with`로 다루는 코드를 보게 될 것이다. 모양이 같으므로 "블록이 끝나면 정리된다"고 읽으면 된다.

### 7.1.5 파일 모드 — 읽기, 쓰기, 추가, 새로 만들기

`open()`의 두 번째 인자인 모드에 따라 파일을 여는 방식이 달라진다.

| 모드 | 이름 | 파일이 없으면 | 파일이 있으면 | 할 수 있는 일 |
|---|---|---|---|---|
| `"r"` | 읽기(read). 기본값 | `FileNotFoundError` | 처음부터 읽는다 | 읽기 |
| `"w"` | 쓰기(write) | 새로 만든다 | **내용을 모두 지우고** 처음부터 쓴다 | 쓰기 |
| `"a"` | 추가(append) | 새로 만든다 | 기존 내용 **뒤에 이어서** 쓴다 | 쓰기 |
| `"x"` | 새로 만들기(exclusive) | 새로 만든다 | `FileExistsError` | 쓰기 |

셸에서 차례로 확인해 보자.

```python
>>> with open("modes.txt", "w", encoding="utf-8") as f:
...     f.write("첫째 줄\n")
...
5
>>> with open("modes.txt", "a", encoding="utf-8") as f:
...     f.write("둘째 줄\n")
...
5
>>> with open("modes.txt", encoding="utf-8") as f:
...     print(f.read())
...
첫째 줄
둘째 줄

>>> with open("modes.txt", "w", encoding="utf-8") as f:
...     f.write("새 내용\n")
...
5
>>> with open("modes.txt", encoding="utf-8") as f:
...     print(f.read())
...
새 내용

>>> with open("modes.txt", "x", encoding="utf-8") as f:
...     f.write("만들 수 있을까?\n")
...
Traceback (most recent call last):
  File "<python-input-29>", line 1, in <module>
    with open("modes.txt", "x", encoding="utf-8") as f:
         ~~~~^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^
FileExistsError: [Errno 17] File exists: 'modes.txt'
```

(블록 안의 `f.write()`가 돌려준 글자 수 `5`가 셸에 출력되었다. 셸은 블록 안에서 계산된 값도 보여 준다.)

**`"w"` 모드는 파일을 여는 순간 기존 내용을 지운다.** 아무것도 쓰지 않고 닫아도 파일은 이미 비어 있다. 경고도 없고 휴지통에도 들어가지 않는다. 읽으려던 파일을 실수로 `"w"`로 열면 그 내용은 되돌릴 수 없다. 파일 입출력에서 가장 조심해야 할 점이다. 그래서 다음처럼 구분해서 쓴다.

- 매번 **새로 만들어도 되는** 결과물(보고서, 변환 결과, 프로그램이 관리하는 저장 파일) → `"w"`
- 기록을 **계속 쌓아 가는** 파일(로그, 일기, 대화 기록) → `"a"`
- **이미 있으면 덮어쓰면 안 되는** 파일(사용자가 이름을 정해 준 새 파일) → `"x"`. 6장에서 배운 대로 `FileExistsError`를 잡아서 "이미 있는 파일입니다"라고 알려 주면 된다.

추가 모드로 한 줄 일기를 쌓아 가는 프로그램을 만들어 보자. 날짜와 시각은 4.6.9에서 배운 `datetime`으로 붙인다.

```python
# diary.py
from datetime import datetime

text = input("오늘의 한 줄: ")
now = datetime.now().strftime("%Y-%m-%d %H:%M")
with open("diary.txt", "a", encoding="utf-8") as f:
    f.write(f"{now} {text}\n")
print("diary.txt에 저장했습니다.")
```

여러 번 실행해 보고 `diary.txt`를 열어 보자. 실행할 때마다 한 줄씩 늘어난다. `"a"`를 `"w"`로 바꾸면 마지막에 쓴 한 줄만 남는다는 것도 확인해 보자.

모드에는 이 밖에도 `"b"`(바이너리)를 붙인 `"rb"`, `"wb"`나, 읽기와 쓰기를 함께 하는 `"r+"` 같은 것이 있다. `"rb"`는 7.3.3에서 파일의 실제 바이트를 들여다볼 때 한 번 쓴다. 나머지는 이 과정에서 쓸 일이 거의 없다.

### 7.1.6 줄 단위로 처리하기

텍스트 파일은 대부분 **줄 단위**로 의미가 있다. 할 일 목록은 한 줄에 할 일 하나, 로그는 한 줄에 사건 하나다. VS Code에서 `ch07` 폴더에 `todo.txt`를 만들고 다음 내용을 붙여 넣자. 마지막 줄 `방 정리` 뒤에서도 Enter를 눌러, 파일이 줄바꿈으로 끝나게 저장한다.

```
# 이번 주 할 일
장보기
운동하기

파이썬 7장 공부
# 다음 주로 미룬 일
방 정리
```

**`for line in f` — 한 줄씩 읽기**

파일 객체는 `for` 문으로 순회할 수 있다. 한 번 반복할 때마다 **한 줄**씩 꺼내 준다. 셸에서 `repr()`로 각 줄의 실제 모습을 보자.

```python
>>> with open("todo.txt", encoding="utf-8") as f:
...     for line in f:
...         print(repr(line))
...
'# 이번 주 할 일\n'
'장보기\n'
'운동하기\n'
'\n'
'파이썬 7장 공부\n'
'# 다음 주로 미룬 일\n'
'방 정리\n'
```

각 줄의 **끝에 `\n`이 붙어 있다.** 빈 줄은 `'\n'` 하나뿐이다. 이 상태로 `print(line)`을 하면 어떻게 될까?

```python
>>> with open("todo.txt", encoding="utf-8") as f:
...     for line in f:
...         print(line)
...
# 이번 주 할 일

장보기

운동하기



파이썬 7장 공부

# 다음 주로 미룬 일

방 정리

```

줄 사이에 빈 줄이 하나씩 끼어 있다. 줄에 붙은 `\n`에서 한 번, `print()`가 또 한 번 줄을 바꾸기 때문이다. 그래서 줄을 읽으면 먼저 **줄 끝의 `\n`을 떼어 내는** 것이 습관이다.

```python
>>> "장보기\n".strip(), "  운동하기  \n".rstrip("\n")
('장보기', '  운동하기  ')
```

- `strip()`(2.3.5)은 앞뒤의 공백과 줄바꿈을 모두 지운다. 줄 앞뒤의 공백에 의미가 없다면 이것이 가장 간단하다.
- `rstrip("\n")`은 오른쪽 끝의 줄바꿈만 지운다. 들여쓰기처럼 줄 앞의 공백에 의미가 있으면 이것을 쓴다.

**마지막 줄에는 `\n`이 없을 수도 있다.** VS Code에서 마지막 줄 뒤에 Enter를 누르지 않고 저장하면, 마지막 줄은 `'방 정리'`처럼 `\n` 없이 끝난다. 그러니 "마지막 한 글자를 잘라 내면 된다"는 식(`line[:-1]`)으로 처리하면 마지막 줄의 글자가 잘린다. `strip()`이나 `rstrip("\n")`은 `\n`이 있을 때만 지우므로 어느 경우에나 안전하다.

이제 주석 줄(`#`로 시작)과 빈 줄을 건너뛰고 할 일에 번호를 붙여 출력하는 스크립트를 만들자. 2.5.6의 `enumerate()`에 `start=1`을 주면 파일의 몇 번째 줄인지도 함께 알 수 있다.

```python
# todo_list.py
count = 0
with open("todo.txt", encoding="utf-8") as f:
    for line_no, line in enumerate(f, start=1):
        line = line.strip()
        if not line or line.startswith("#"):
            continue
        count += 1
        print(f"{count}. {line}  (todo.txt {line_no}번째 줄)")
print(f"할 일 {count}개")
```

```
1. 장보기  (todo.txt 2번째 줄)
2. 운동하기  (todo.txt 3번째 줄)
3. 파이썬 7장 공부  (todo.txt 5번째 줄)
4. 방 정리  (todo.txt 7번째 줄)
할 일 4개
```

`if not line`은 2.4.5에서 배운 falsy를 이용한 것이다. `strip()`한 빈 줄은 빈 문자열 `''`이므로 거짓이다. 줄 번호를 함께 보여 주는 습관은 나중에 파일에 잘못된 줄이 있을 때 "몇 번째 줄이 잘못되었다"고 알려 줄 수 있어 유용하다. 이 장의 마지막 실습에서 그렇게 쓴다.

**`readlines()`와 `read().splitlines()` — 모든 줄을 리스트로**

줄 전체를 리스트로 받고 싶을 때도 있다. 두 방법이 있다.

```python
>>> with open("todo.txt", encoding="utf-8") as f:
...     lines = f.readlines()
...
>>> lines
['# 이번 주 할 일\n', '장보기\n', '운동하기\n', '\n', '파이썬 7장 공부\n', '# 다음 주로 미룬 일\n', '방 정리\n']
>>> with open("todo.txt", encoding="utf-8") as f:
...     lines = f.read().splitlines()
...
>>> lines
['# 이번 주 할 일', '장보기', '운동하기', '', '파이썬 7장 공부', '# 다음 주로 미룬 일', '방 정리']
```

`readlines()`는 줄 끝의 `\n`을 남겨 두고, 문자열의 `splitlines()` 메서드는 줄바꿈을 기준으로 나누면서 줄바꿈을 지워 준다. 리스트가 필요하면 보통 `read().splitlines()`가 편하다. (`read().split("\n")`과는 다르다. 파일이 `\n`으로 끝나면 `split("\n")`의 결과 끝에는 빈 문자열 `''`이 하나 더 붙는다. 확인 문제에서 다시 묻는다.)

어느 쪽이든 파일 전체를 한꺼번에 메모리에 올린다. 몇 기가바이트짜리 로그 파일이라면 메모리가 부족할 수 있다. `for line in f`는 **한 번에 한 줄씩만** 읽으므로 파일이 아무리 커도 문제가 없다. 처음부터 끝까지 한 번 훑으면 되는 일이라면 `for line in f`를 쓰자.

**여러 줄 쓰기**

리스트의 문자열을 한 줄에 하나씩 쓰는 방법도 정리해 두자.

```python
# write_lines.py
fruits = ["사과", "바나나", "포도"]

with open("fruits.txt", "w", encoding="utf-8") as f:
    for fruit in fruits:
        f.write(fruit + "\n")
```

같은 일을 `f.write("\n".join(fruits) + "\n")`(2.3의 `join`)이나 `print(fruit, file=f)`로도 할 수 있다. 파일 객체에는 `writelines()`라는 메서드도 있는데, 이름과 달리 **줄을 바꿔 주지 않는다.** `f.writelines(fruits)`라고 쓰면 파일에 `사과바나나포도`가 한 줄로 들어간다. `readlines()`가 `\n`을 남겨 두는 것과 짝을 맞춘 것이다.

### 7.1.7 인코딩 — 글자를 바이트로 바꾸는 규칙

7.1.4에서 다섯 글자 `저장될까?`가 13바이트였다. 그 이유를 알아보자.

**문자와 바이트**

저장 장치에는 글자가 아니라 **바이트**(byte, 0~255 사이의 숫자)만 저장할 수 있다. 그래서 글자를 저장하려면 "어떤 글자를 어떤 바이트로 바꿀지" 정한 규칙이 필요하다. 이 규칙을 **인코딩**(encoding)이라고 한다. 반대로 바이트를 글자로 되돌리는 것을 **디코딩**(decoding)이라고 한다.

문자열의 `encode()` 메서드로 글자가 어떤 바이트가 되는지 직접 볼 수 있다.

```python
>>> "A가".encode("utf-8")
b'A\xea\xb0\x80'
>>> len("A가"), len("A가".encode("utf-8"))
(2, 4)
>>> "A가".encode("cp949")
b'A\xb0\xa1'
>>> b"A\xea\xb0\x80".decode("utf-8")
'A가'
```

- `b'...'`는 **바이트열**(bytes)이라는 자료형이다. 문자열과 비슷하게 생겼지만 글자가 아니라 바이트의 나열이다. `\xea`는 16진수로 나타낸 바이트 하나(234)다.
- **UTF-8**에서 영문자 `A`는 1바이트, 한글 `가`는 3바이트다. 그래서 두 글자짜리 문자열이 4바이트가 되었다. `저장될까?`는 한글 네 글자(12바이트)와 물음표(1바이트)라서 13바이트였다.
- **cp949**에서는 같은 `가`가 2바이트이고, 바이트 값도 전혀 다르다.
- `decode()`는 바이트열을 문자열로 되돌린다.

한국어 환경에서 만나는 인코딩은 사실상 두 가지다.

| 인코딩 | 다른 이름 | 특징 |
|---|---|---|
| UTF-8 | | 전 세계의 모든 글자를 다룬다. 웹, macOS, Linux, 파이썬 소스 파일, JSON의 표준. **지금의 표준이다** |
| cp949 | EUC-KR(거의 같은 것), MS949, "ANSI"(한국어 Windows에서) | 한국어 Windows가 오래 써 온 인코딩. 한글과 영문 정도만 다룬다. 오래된 파일, 공공 데이터, 엑셀에서 저장한 CSV에서 아직 자주 만난다 |

**인코딩이 맞지 않으면**

문제는 **쓸 때와 읽을 때의 인코딩이 다를 때** 생긴다. 같은 바이트를 다른 규칙으로 해석하기 때문이다. 오래된 메모장에서 저장한 파일을 흉내 내어, cp949로 저장한 파일을 하나 만들어 보자.

```python
# make_cp949.py
with open("old_memo.txt", "w", encoding="cp949") as f:
    f.write("예전에 메모장으로 저장한 파일\n")
    f.write("한글 인코딩이 cp949이다.\n")
```

이 파일을 UTF-8로 읽어 보자.

```python
# read_memo.py
with open("old_memo.txt", encoding="utf-8") as f:
    print(f.read())
```

`UnicodeDecodeError`는 "이 바이트들은 UTF-8 규칙으로는 글자가 될 수 없다"는 뜻이다. 0번 위치의 바이트 `0xbf`는 UTF-8에서 글자의 첫 바이트로 나올 수 없는 값이다. 트레이스백의 `<frozen codecs>` 줄은 파이썬 내부에서 디코딩하던 곳이므로 신경 쓰지 않아도 된다. 오류가 난 곳이 `open()`이 아니라 `read()`라는 점도 눈여겨보자. 파일을 여는 것은 문제가 없었고, **바이트를 글자로 바꾸는 순간** 실패했다.

파이썬에서도 올바른 인코딩을 알려 주면 된다.

`errors="replace"`를 주면 해석할 수 없는 바이트를 `�`로 바꾸고 예외 없이 계속 읽는다. 내용이 망가지므로 데이터를 처리할 때는 쓰지 말고, "대충 무슨 파일인지 들여다보기"용으로만 쓰자. 반대 방향의 실수, 즉 UTF-8 파일을 cp949로 읽어도 대개 `UnicodeDecodeError`가 나고, 운이 나쁘면 예외 없이 엉뚱한 글자로 읽힌다. 예외가 나는 편이 차라리 낫다.

`UnicodeDecodeError`는 `ValueError`의 자손이다. 6.1.5에서 본 예외 계층을 따라가면 `ValueError` → `UnicodeError`(인코딩 관련 예외의 부모) → `UnicodeDecodeError` 순서다. 그래서 `except ValueError:`로도 잡힌다. "파일이라는 자료형은 맞는데 그 내용(값)이 이 규칙에 맞지 않는다"는 뜻이니 자연스럽다.

**왜 항상 `encoding="utf-8"`을 쓰는가**

`encoding`을 생략하면 파이썬은 **운영체제의 기본 인코딩**을 쓴다. 이것이 문제다.

| 환경 | `encoding`을 생략했을 때 |
|---|---|
| macOS, Linux | UTF-8 |
| 한국어 Windows, 파이썬 3.14 이하 | **cp949** |
| 파이썬 3.15 이상 | 운영체제와 관계없이 UTF-8 |

macOS에서 `encoding` 없이 만든 프로그램은 잘 동작한다. 그런데 같은 프로그램을 한국어 Windows에서 실행하면 UTF-8 파일을 cp949로 읽으려다 `UnicodeDecodeError`가 나거나, 반대로 cp949로 저장해서 macOS에서 읽지 못하는 파일을 만든다. 2026년 10월에 나온 파이썬 3.15부터는 기본값이 어디서나 UTF-8로 바뀌어 이 문제가 줄었지만, 내 코드가 어떤 버전의 파이썬에서 실행될지는 알 수 없다. 이 교재가 기준으로 하는 3.12, 3.13도 아직 많이 쓰인다.

그러니 텍스트 파일을 열 때는 **언제나 `encoding="utf-8"`을 쓴다.** 어느 환경에서나 같은 결과를 내고, 코드를 읽는 사람에게 "이 파일은 UTF-8이다"라고 알려 주는 효과도 있다. cp949 파일을 읽어야 할 때만 `encoding="cp949"`로 바꾼다. (모드가 `"rb"`, `"wb"`처럼 바이너리이면 글자를 다루지 않으므로 `encoding`을 쓰지 않는다.)

> **파일 이름은 인코딩과 관계없다**
> `encoding`은 파일의 **내용**을 읽고 쓰는 규칙이다. `"없는파일.txt"`처럼 파일 **이름**에 한글이 들어가는 것은 운영체제가 알아서 처리하므로 `encoding`과 관계가 없다.

### 7.1.8 파일 작업의 예외 처리

파일은 6장에서 말한 "프로그램 바깥에서 오는 문제"의 대표다. 사용자가 파일 이름을 잘못 입력할 수도 있고, 파일이 지워졌을 수도 있고, 파일 대신 폴더 이름을 줄 수도 있다. 파일 작업에서 만나는 예외를 정리하자.

| 예외 | 언제 | 예 |
|---|---|---|
| `FileNotFoundError` | 없는 파일을 읽으려 할 때, 없는 폴더 안에 파일을 만들려 할 때 | `open("없는파일.txt")`, `open("없는폴더/a.txt", "w")` |
| `FileExistsError` | `"x"` 모드로 이미 있는 파일을 열 때 | `open("modes.txt", "x")` |
| `IsADirectoryError` | 폴더를 파일처럼 열 때 (macOS, Linux) | `open("notes")` |
| `PermissionError` | 권한이 없는 파일을 열 때. **Windows에서는 폴더를 파일처럼 열 때도** | 시스템 파일, 다른 프로그램이 잠근 파일 |
| `UnicodeDecodeError` | 파일의 인코딩이 지정한 것과 다를 때 (`read()` 중에) | 7.1.7 |

앞의 네 가지는 모두 `OSError`의 자식이다. `OSError`는 운영체제(OS)에 무언가를 요청했다가 실패했다는 뜻의 예외로, 파일 말고도 네트워크 같은 운영체제 작업의 실패를 모두 포함한다. `UnicodeDecodeError`는 앞에서 본 대로 `UnicodeError`를 거친 `ValueError`의 자손이다.

```
Exception
 ├── OSError
 │    ├── FileNotFoundError
 │    ├── FileExistsError
 │    ├── IsADirectoryError
 │    └── PermissionError
 └── ValueError
      └── UnicodeError
           └── UnicodeDecodeError
```

`OSError` 계열의 예외 객체에는 `filename` 속성이 있어서, 어떤 파일 때문에 실패했는지 알 수 있다.

**`try`는 `with` 바깥에**

예외를 잡을 때는 보통 `with` 문 전체를 `try`로 감싼다.

```python
# show_file.py
name = input("파일 이름: ")
try:
    with open(name, encoding="utf-8") as f:
        for line_no, line in enumerate(f, start=1):
            print(f"{line_no:>3}: {line.rstrip()}")
except FileNotFoundError as e:
    print(f"파일이 없습니다: {e.filename}")
except UnicodeDecodeError:
    print(f"UTF-8 텍스트 파일이 아닙니다: {name}")
except OSError as e:
    print(f"파일을 열 수 없습니다: {e}")
```

```
파일 이름: todo.text
파일이 없습니다: todo.text
```

```
파일 이름: old_memo.txt
UTF-8 텍스트 파일이 아닙니다: old_memo.txt
```

- `open()`과 `read()`(여기서는 `for line in f`) 양쪽에서 예외가 날 수 있으므로 `with` 문 전체를 감쌌다. 어느 쪽에서 나든 `with`가 파일을 닫은 뒤에 `except`로 온다.
- 6.1.6에서 배운 대로 자식 예외를 먼저 쓴다. `FileNotFoundError`를 `OSError`보다 위에 둔다. `OSError`는 폴더 이름을 입력한 경우(macOS의 `IsADirectoryError`, Windows의 `PermissionError`)처럼 미처 생각하지 못한 파일 문제를 한꺼번에 받는다.
- `{line_no:>3}`은 줄 번호를 세 칸에 맞춰 출력하는 서식이다(2.3.4의 f-string 서식).

**없는 파일이 정상인 경우**

파일이 없는 것이 항상 오류는 아니다. 메모장 프로그램을 **처음 실행하면** 메모 파일이 아직 없다. 이것은 "메모가 하나도 없다"는 정상적인 상태다. 이럴 때는 예외를 잡아서 빈 결과를 돌려준다.

```python
def load_memos(path):
    """메모 파일의 줄을 리스트로 돌려준다. 파일이 없으면 빈 리스트를 돌려준다."""
    try:
        with open(path, encoding="utf-8") as f:
            return f.read().splitlines()
    except FileNotFoundError:
        return []
```

6.2.2에서 배운 기준과 같다. "없을 수도 있다"가 정상적인 결과라면 반환값(여기서는 빈 리스트)으로 알리고, 약속한 일을 할 수 없는 경우라면 예외로 알린다. 같은 `FileNotFoundError`라도 **그 파일이 프로그램에게 어떤 의미인지**에 따라 처리가 달라진다. 사용자가 열어 달라고 이름을 준 파일이 없으면 알려 줘야 하고, 프로그램이 스스로 관리하는 저장 파일이 처음에 없는 것은 정상이고, 프로그램이 돌아가는 데 꼭 필요한 설정 파일이 없으면 시작할 수 없다고 알리고 끝내야 한다. 실습 7-4에서 세 경우를 모두 만난다.

- 처음 실행할 때는 `memo.txt`가 없다. 7.1.8의 `load_memos()`처럼 파일이 없으면 빈 리스트를 돌려주는 함수를 만든다.

- `삭제`는 어떻게 해야 할까? 텍스트 파일에서는 **가운데 한 줄만 지울 수 없다.** 전체를 읽어 리스트에서 지운 뒤, `"w"` 모드로 **전체를 다시 쓴다.**
- `삭제 0`을 입력하면 어떻게 되어야 하는가? 번호에서 1을 빼서 `pop()`(3.1.5)에 넘긴다면, `0`을 입력했을 때 `pop(-1)`이 되어 **마지막 메모가 지워진다.** 예외도 나지 않으니 조용히 틀린다. 번호가 1 이상, 메모 수 이하인지 미리 검사하자(6.1.10).
- 프로그램을 종료하고 다시 실행해 `목록`이 그대로인지, VS Code에서 `memo.txt`의 내용이 화면과 같은지 확인한다.

**4) `to_utf8.py` — 인코딩 바꾸기**

```
변환할 파일: old_memo.txt
저장할 파일: old_memo_utf8.txt

```

```

저장할 파일: old_memo_utf8.txt
이미 있는 파일입니다: old_memo_utf8.txt
```

```
변환할 파일: hello.txt
이미 UTF-8 파일입니다. 변환하지 않습니다.
```

- 파일을 읽어 `(내용, 인코딩)` 튜플을 돌려주는 함수 `read_text(path)`를 만든다. 먼저 UTF-8로 읽어 보고, `UnicodeDecodeError`가 나면 cp949로 다시 읽는다. 6.1.10의 "일단 해 보기"다. cp949로도 읽지 못하면 그 예외는 잡지 않고 호출한 쪽으로 보낸다.
- 저장할 파일은 `"x"` 모드로 열어, 이미 있는 파일을 실수로 덮어쓰지 않게 한다.
- 만든 `old_memo_utf8.txt`를 VS Code에서 열어 한글이 제대로 보이는지 확인한다.
- 생각해 보기: UTF-8로 읽기에 성공했다고 해서 그 파일이 정말 UTF-8로 저장된 파일이라고 확신할 수 있을까? 영문과 숫자로만 된 파일은 UTF-8과 cp949에서 바이트가 똑같다(`"A".encode("utf-8")`과 `"A".encode("cp949")`를 비교해 보자). 이런 파일은 어느 쪽으로 읽어도 결과가 같으므로 문제가 없다.

## 7.2 경로 다루기

7.1에서는 `"hello.txt"`처럼 파일 이름만 썼다. 파일이 `ch07` 폴더에 있고, 프로그램도 `ch07` 폴더에서 실행했기 때문에 그것으로 충분했다. 실제 프로그램은 데이터를 `data` 폴더에 모아 두기도 하고, 폴더 안의 파일을 모두 훑기도 하고, 사용자가 알려 준 다른 폴더의 파일을 읽기도 한다. 이 절에서는 경로를 안전하게 다루는 `pathlib`을 배우고, 실행 위치에 따라 상대 경로가 달라지는 문제를 해결한다.

### 7.2.1 경로 다시 보기 — 상대 경로와 절대 경로

1.1.6에서 배운 내용을 다시 정리하자. **경로**(path)는 파일이나 폴더의 위치를 나타내는 문자열이다.

- **절대 경로** — 맨 꼭대기(macOS는 `/`, Windows는 `C:\` 같은 드라이브)부터 적는다. 어디서 쓰든 같은 곳을 가리킨다.
  - macOS: `/Users/본인계정/python-lab/ch07/hello.txt`
  - Windows: `C:\Users\본인계정\python-lab\ch07\hello.txt`
- **상대 경로** — **현재 디렉터리**를 기준으로 적는다. 현재 디렉터리가 바뀌면 가리키는 곳도 바뀐다.
  - `hello.txt` — 현재 디렉터리에 있는 `hello.txt`
  - `data/scores.csv` — 현재 디렉터리 안의 `data` 폴더 안에 있는 `scores.csv`
  - `../ch06/library.py` — 한 단계 위 폴더(`..`) 안의 `ch06` 폴더 안에 있는 `library.py`

`open("hello.txt")`의 `"hello.txt"`도 상대 경로다. 파이썬은 이 파일을 **프로그램을 실행한 현재 디렉터리**에서 찾는다. 1.1.3에서 "현재 디렉터리가 파일이 있는 곳과 다르면 파일을 찾을 수 없다"고 한 것이 터미널에서 스크립트를 실행할 때만이 아니라 **프로그램 안에서 파일을 열 때도** 똑같이 적용된다. 이 사실이 7.2.4의 출발점이다.

경로를 문자열로 다루면 몇 가지가 불편하다.

- 폴더 구분 기호가 운영체제마다 다르다. macOS와 Linux는 `/`, Windows는 `\`다. `"data" + "/" + "scores.csv"`처럼 문자열을 이어 붙이면 운영체제마다 신경 써야 한다. (사실 Windows의 파이썬은 `/`도 알아듣지만, 화면에 보여 주거나 다른 프로그램에 넘길 때는 `\`가 섞여 혼란스럽다.)
- Windows 경로의 `\`는 2.3.6의 이스케이프 문자와 충돌한다.

```python
>>> print("C:\new\table.txt")
C:
ew	able.txt
```

`\n`은 줄바꿈으로, `\t`는 탭으로 바뀌어 버렸다. 2.3.6에서 본 raw 문자열(`r"C:\new\table.txt"`)로 피할 수 있지만, 매번 신경 쓰기는 번거롭다.

- 파일 이름에서 확장자만 떼어 내기, 상위 폴더 구하기 같은 일을 `split()`과 슬라이싱으로 직접 하면 실수하기 쉽다.

### 7.2.2 `pathlib.Path` — 경로를 객체로 다루기

표준 라이브러리의 `pathlib` 모듈은 경로를 문자열이 아니라 **`Path` 객체**로 다룬다. 경로를 조합하고, 나누고, 파일이 있는지 확인하는 기능이 메서드와 속성으로 들어 있다. 앞의 셸에서 이어서 입력한다.

```python
>>> from pathlib import Path
>>> p = Path("data") / "scores.csv"
>>> p
PosixPath('data/scores.csv')
>>> str(p)
'data/scores.csv'
>>> print(p)
data/scores.csv
```

- `Path("data")`로 경로 객체를 만든다.
- **`/` 연산자로 경로를 이어 붙인다.** 나눗셈 기호를 경로 구분 기호로 다시 정의해 둔 것이다(5장에서 `__str__`을 정의하면 `print()`의 결과가 바뀌었던 것처럼, 클래스는 연산자의 동작도 정할 수 있다). 운영체제에 맞는 구분 기호는 `Path`가 알아서 넣는다.
- macOS와 Linux에서는 `PosixPath`, Windows에서는 `WindowsPath` 객체가 만들어진다. Windows에서 같은 코드를 실행하면 다음과 같다.

```python
>>> p
WindowsPath('data/scores.csv')
>>> str(p)
'data\\scores.csv'
>>> print(p)
data\scores.csv
```

(`repr`에는 `/`로 보이지만 실제 문자열은 `\`로 구분된다. 문자열의 `repr`에서 `\`는 `\\`로 표시된다.)

`Path`와 문자열은 `+`로 이을 수 없다. `/`를 쓰자.

```python
>>> Path("data") + "/scores.csv"
Traceback (most recent call last):
  File "<python-input-12>", line 1, in <module>
    Path("data") + "/scores.csv"
    ~~~~~~~~~~~~~^~~~~~~~~~~~~~~
TypeError: unsupported operand type(s) for +: 'PosixPath' and 'str'
```

**경로의 부분 꺼내기**

```python
>>> p.name
'scores.csv'
>>> p.stem
'scores'
>>> p.suffix
'.csv'
>>> p.parent
PosixPath('data')
>>> p.with_suffix(".json")
PosixPath('data/scores.json')
>>> p.parent / "backup" / p.name
PosixPath('data/backup/scores.csv')
```

| 속성·메서드 | 뜻 | `data/scores.csv`일 때 |
|---|---|---|
| `name` | 마지막 부분(파일 이름) | `'scores.csv'` |
| `stem` | 확장자를 뺀 이름 | `'scores'` |
| `suffix` | 확장자(점 포함) | `'.csv'` |
| `parent` | 상위 폴더 | `Path('data')` |
| `with_suffix(".json")` | 확장자를 바꾼 새 경로 | `Path('data/scores.json')` |

`with_suffix()`는 경로를 바꾸는 것이 아니라 **새 `Path`를 돌려준다.** `Path` 객체는 문자열처럼 불변 객체(3.2.3)다. 경로 객체를 만든다고 해서 그 파일이 생기거나 바뀌는 것도 아니다. `Path`는 "이런 위치"라는 **주소**일 뿐이다.

**현재 디렉터리와 홈 폴더, 절대 경로**

```python
>>> Path.cwd()
PosixPath('/Users/본인계정/python-lab/ch07')
>>> Path.home()
PosixPath('/Users/본인계정')
>>> Path.home() / "python-lab" / "ch07"
PosixPath('/Users/본인계정/python-lab/ch07')
>>> p.is_absolute()
False
>>> p.absolute()
PosixPath('/Users/본인계정/python-lab/ch07/data/scores.csv')
>>> Path("../ch06/library.py").absolute()
PosixPath('/Users/본인계정/python-lab/ch07/../ch06/library.py')
>>> Path("../ch06/library.py").resolve()
PosixPath('/Users/본인계정/python-lab/ch06/library.py')
```

- `Path.cwd()`는 현재 디렉터리(current working directory)를 돌려준다. 터미널의 `pwd`와 같다. 상대 경로는 바로 이 위치를 기준으로 한다.
- `Path.home()`은 홈 폴더를 돌려준다. 사용자마다, 운영체제마다 다른 홈 폴더의 위치를 직접 적지 않아도 된다.
- `absolute()`는 현재 디렉터리를 앞에 붙여 절대 경로로 만든다. `..`은 그대로 남는다. `resolve()`는 `..`까지 정리한 진짜 위치를 돌려준다. 상대 경로가 실제로 어디를 가리키는지 확인하고 싶을 때 `resolve()`를 출력해 보면 좋다.

**파일이 있는지 확인하기**

```python
>>> p.exists()
False
>>> hello = Path("hello.txt")
>>> hello.exists(), hello.is_file(), hello.is_dir()
(True, True, False)
```

`exists()`는 그 경로에 무언가(파일이든 폴더든) 있는지, `is_file()`과 `is_dir()`은 그것이 파일인지 폴더인지 확인한다. 없는 경로이면 셋 다 `False`다.

**`Path`로 파일 읽고 쓰기**

`open()`에는 문자열 대신 `Path` 객체를 그대로 넘길 수 있다. `with open(BASE_DIR / "data.txt", encoding="utf-8") as f:`처럼 쓴다. 파일 전체를 한 번에 읽거나 쓸 때는 `Path`의 메서드가 더 짧다.

```python
>>> hello.read_text(encoding="utf-8")
'안녕하세요\n파일 입출력을 배웁니다.\n'
>>> Path("note.txt").write_text("한 번에 쓰기\n", encoding="utf-8")
8
>>> Path("note.txt").read_text(encoding="utf-8").splitlines()
['한 번에 쓰기']
```

`read_text()`는 파일을 열고, 전부 읽고, 닫는 일을 한 번에 한다. `write_text()`는 `"w"` 모드로 열어 쓰고 닫는다(그러니 기존 내용은 지워진다). 여기서도 `encoding="utf-8"`을 빠뜨리지 말자. 줄 단위로 처리하거나, 추가 모드로 쓰거나, CSV처럼 파일 객체가 필요한 경우에는 `open()`을 쓴다.

> **`os.path`를 쓰는 코드**
> 인터넷이나 AI가 만든 코드에서 `os.path.join("data", "scores.csv")`, `os.path.exists(path)` 같은 코드를 볼 수 있다. `pathlib`이 생기기 전부터 쓰던 방식으로, 경로를 문자열로 다룬다. 같은 일을 하므로 읽을 수 있으면 충분하다. 새로 쓰는 코드에서는 `pathlib`을 쓰자. 대응 관계는 `os.path.join(a, b)` → `Path(a) / b`, `os.path.exists(p)` → `Path(p).exists()`, `os.path.basename(p)` → `Path(p).name`, `os.path.dirname(p)` → `Path(p).parent`다.

### 7.2.3 폴더 만들기와 훑어보기

**`mkdir()` — 폴더 만들기**

같은 셸에서 이어서 입력한다.

```python
>>> notes = Path("notes")
>>> notes.mkdir()
>>> (notes / "monday.txt").write_text("회의\n점심 약속\n", encoding="utf-8")
9
>>> (notes / "tuesday.txt").write_text("운동\n", encoding="utf-8")
3
>>> (notes / "ideas.md").write_text("# 아이디어\n", encoding="utf-8")
7
```

이미 있는 폴더를 다시 만들거나, 중간 폴더가 없는 깊은 폴더를 한 번에 만들려고 하면 예외가 난다.

```python
>>> notes.mkdir()
Traceback (most recent call last):
  File "<python-input-31>", line 1, in <module>
    notes.mkdir()
    ~~~~~~~~~~~^^
  File ".../pathlib/_local.py", line 722, in mkdir
    os.mkdir(self, mode)
    ~~~~~~~~^^^^^^^^^^^^
FileExistsError: [Errno 17] File exists: 'notes'
>>> notes.mkdir(exist_ok=True)
>>> Path("archive/2026/11").mkdir()
Traceback (most recent call last):
  File "<python-input-33>", line 1, in <module>
    Path("archive/2026/11").mkdir()
    ~~~~~~~~~~~~~~~~~~~~~~~~~~~~~^^
  File ".../pathlib/_local.py", line 722, in mkdir
    os.mkdir(self, mode)
    ~~~~~~~~^^^^^^^^^^^^
FileNotFoundError: [Errno 2] No such file or directory: 'archive/2026/11'
>>> Path("archive/2026/11").mkdir(parents=True, exist_ok=True)
>>> (Path("archive/2026/11") / "old.txt").write_text("예전 메모\n", encoding="utf-8")
6
```

(두 번째 `File` 줄은 파이썬이 설치된 위치에 따라 경로가 다르므로 `...`로 줄였다. 표준 라이브러리 안쪽에서 난 예외는 4.1.9에서 배운 대로 **내 코드의 마지막 줄**, 여기서는 `<python-input-...>` 줄을 보면 된다.)

- `exist_ok=True` — 이미 있어도 예외를 내지 않는다. "없으면 만들고, 있으면 그대로 둔다"는 뜻이라 저장할 폴더를 준비할 때 거의 항상 붙인다.
- `parents=True` — 중간 폴더(`archive`, `archive/2026`)가 없으면 함께 만든다.
- 쓰기 모드로 파일을 만들 때 그 **폴더가 없으면** `FileNotFoundError`가 난다. `open()`은 파일은 만들어 주지만 폴더는 만들어 주지 않는다. 저장하기 전에 `path.parent.mkdir(parents=True, exist_ok=True)`로 폴더를 준비하는 것이 흔한 모양이다.

**`iterdir()` — 폴더 안의 항목**

```python
>>> for path in notes.iterdir():
...     print(path)
...
notes/tuesday.txt
notes/ideas.md
notes/monday.txt
>>> for path in sorted(notes.iterdir()):
...     print(path.name, path.is_file(), path.stat().st_size)
...
ideas.md True 15
monday.txt True 21
tuesday.txt True 7
```

- `iterdir()`는 폴더 안의 파일과 폴더를 하나씩 `Path`로 돌려준다. 하위 폴더 속까지 들어가지는 않는다.
- **순서는 정해져 있지 않다.** 운영체제와 파일 시스템에 따라 다르다. 실행할 때마다, 컴퓨터마다 같은 순서가 필요하면 `sorted()`로 정렬한다. `Path`끼리는 경로 문자열 순서로 비교할 수 있다.
- `path.stat().st_size`는 파일 크기(바이트)다. `monday.txt`의 내용 `"회의\n점심 약속\n"`은 한글 다섯 글자(15바이트), 공백 하나, 줄바꿈 둘이라서 21바이트다.

**`glob()`과 `rglob()` — 이름 모양으로 찾기**

```python
>>> for path in sorted(notes.glob("*.txt")):
...     print(path.name)
...
monday.txt
tuesday.txt
>>> for path in sorted(Path("archive").rglob("*")):
...     print(path)
...
archive/2026
archive/2026/11
archive/2026/11/old.txt
```

- `glob("*.txt")`는 이름이 `.txt`로 끝나는 항목만 돌려준다. `*`는 "아무 글자나 몇 개든"을 뜻하는 **와일드카드**다. `"2026-*.csv"`, `"report_??.txt"`(`?`는 아무 글자 하나)처럼 쓸 수 있다.
- `rglob()`은 하위 폴더 속까지 **재귀적으로**(recursive) 찾는다. `Path(".").rglob("*.py")`는 현재 폴더 아래의 모든 파이썬 파일이다.

이것으로 지금까지 만든 실습 파일을 장별로 세어 보자.

```python
# lab_stats.py
from pathlib import Path

lab = Path.home() / "python-lab"
for chapter in sorted(lab.glob("ch*")):
    if not chapter.is_dir():
        continue
    py_files = sorted(chapter.glob("*.py"))
    total_lines = 0
    for py_file in py_files:
        with open(py_file, encoding="utf-8") as f:
            for line in f:
                total_lines += 1
    print(f"{chapter.name}: 파이썬 파일 {len(py_files)}개, {total_lines}줄")
```

실행 결과는 각자 만든 파일에 따라 다르다. 예를 들면 다음과 같다.

```
ch01: 파이썬 파일 7개, 61줄
ch02: 파이썬 파일 15개, 248줄
...
ch07: 파이썬 파일 12개, 187줄
```

`Path.home()`에서 시작했으므로 이 프로그램은 **어느 폴더에서 실행해도** 같은 결과를 낸다. 이 성질이 다음 절의 주제다.

**파일과 폴더 지우기**

```python
>>> (notes / "ideas.md").unlink()
>>> (notes / "ideas.md").exists()
False
>>> notes.rmdir()
Traceback (most recent call last):
  File "<python-input-43>", line 1, in <module>
    notes.rmdir()
    ~~~~~~~~~~~^^
  File ".../pathlib/_local.py", line 755, in rmdir
    os.rmdir(self)
    ~~~~~~~~^^^^^^
OSError: [Errno 66] Directory not empty: 'notes'
```

`unlink()`는 파일을 지우고, `rmdir()`은 **비어 있는** 폴더만 지운다. 안에 파일이 남아 있으면 `OSError`가 난다(오류 번호와 메시지는 운영체제마다 다르다). 프로그램으로 지운 파일은 **휴지통을 거치지 않고 바로 사라진다.** 지우는 코드는 대상 경로를 `print()`로 먼저 확인한 뒤에 실행하는 습관을 들이자. 없는 파일을 `unlink()`하면 `FileNotFoundError`가 나는데, `unlink(missing_ok=True)`로 쓰면 없어도 괜찮다는 뜻이 된다.

이름을 바꾸거나 옮기는 `rename()`은 실습 7-2에서 쓴다.

파이썬은 스크립트 파일은 잘 찾아서 실행했다. 그런데 스크립트 안의 `"greeting.txt"`는 **스크립트가 있는 폴더가 아니라 현재 디렉터리**(`python-lab`)를 기준으로 찾았고, 거기에는 그런 파일이 없다.

**VS Code의 ▷ 버튼으로 실행할 때**

`greeting.py`를 열고 ▷ 버튼을 눌러 보자. VS Code에 새로 열린 터미널이라면 같은 `FileNotFoundError`가 난다. 1.2.5에서 본 대로 ▷ 버튼은 터미널에 `python /Users/본인계정/python-lab/ch07/greeting.py`처럼 **스크립트의 절대 경로**를 입력해 실행한다. 스크립트는 어디서든 찾을 수 있지만, 현재 디렉터리는 **그 터미널이 지금 있는 곳**이다. VS Code의 터미널은 처음 열릴 때 **폴더 열기로 연 폴더**(`python-lab`)에서 시작한다. 그래서 현재 디렉터리가 `python-lab`이 되고 `greeting.txt`를 찾지 못한다.

더 헷갈리는 것은 **될 때도 있다**는 점이다. 그 터미널에서 미리 `cd ch07`을 해 두었다면 ▷ 버튼으로 실행해도 잘 된다. 어제는 되던 프로그램이 오늘은 안 되는 이유가 대부분 이것이다. `F5`로 디버깅할 때도 기본 작업 디렉터리는 열어 둔 폴더(`python-lab`)다.

정리하면, **상대 경로는 "프로그램을 어디서 실행했는가"에 따라 가리키는 곳이 달라진다.**

| 실행 방법 | 현재 디렉터리 | `"greeting.txt"`가 가리키는 곳 | 결과 |
|---|---|---|---|
| `ch07`에서 `python greeting.py` | `python-lab/ch07` | `python-lab/ch07/greeting.txt` | 성공 |
| `python-lab`에서 `python ch07/greeting.py` | `python-lab` | `python-lab/greeting.txt` | 실패 |
| VS Code ▷ (새 터미널) | `python-lab` | `python-lab/greeting.txt` | 실패 |
| VS Code ▷ (미리 `cd ch07`한 터미널) | `python-lab/ch07` | `python-lab/ch07/greeting.txt` | 성공 |

**해결: 스크립트 파일의 위치를 기준으로 하기**

`greeting.txt`는 `greeting.py`와 **한 묶음**이다. 프로그램을 어디서 실행하든 "이 스크립트 옆에 있는 `greeting.txt`"를 찾아야 한다. 그러려면 스크립트 파일이 어디 있는지 알아야 한다.

파이썬은 스크립트를 실행할 때 그 파일의 경로를 **`__file__`**이라는 특별한 변수에 넣어 준다. (앞뒤에 밑줄이 두 개씩 붙은 이름은 파이썬이 특별한 용도로 쓰는 이름이다. 5장의 `__init__`, `__str__`과 같은 규칙이다. 8장에서 비슷한 변수 `__name__`을 배운다.)

```python
# greeting2.py
from pathlib import Path

BASE_DIR = Path(__file__).parent

print("__file__:", __file__)
print("BASE_DIR:", BASE_DIR)
with open(BASE_DIR / "greeting.txt", encoding="utf-8") as f:
    print(f.read(), end="")
```

어디서 실행해도 결과가 같다.

```
cd ~/python-lab
python ch07/greeting2.py
```

```
__file__: /Users/본인계정/python-lab/ch07/greeting2.py
BASE_DIR: /Users/본인계정/python-lab/ch07
반갑습니다!
오늘도 파이썬 공부를 시작해 볼까요?
```

- `__file__`은 실행 중인 스크립트 파일의 경로다. 파이썬 3.9부터는 어떻게 실행하든 절대 경로가 들어 있다.
- `Path(__file__).parent`는 그 스크립트가 **들어 있는 폴더**다. 이것을 기준 폴더로 삼아 `BASE_DIR / "greeting.txt"`처럼 경로를 만들면, 현재 디렉터리와 관계없이 언제나 스크립트 옆의 파일을 가리킨다.
- `BASE_DIR`처럼 대문자로 쓴 것은 "프로그램이 실행되는 동안 바뀌지 않는 값"이라는 관례다(5장의 `LOAN_DAYS`와 같다). 프로그램 맨 위에 한 번 정해 둔다.

`ch07` 폴더에서도, 홈 폴더에서도, VS Code의 ▷ 버튼으로도 실행해 결과가 같은지 확인해 보자.

대화형 셸에는 스크립트 파일이 없으므로 `__file__`도 없다. 셸에서 `__file__`을 입력하면 `NameError`가 난다. `__file__`을 쓰는 코드는 스크립트로 실행하자.

**언제 무엇을 기준으로 할까**

그렇다고 모든 상대 경로를 `__file__` 기준으로 바꿔야 하는 것은 아니다.

| 파일의 성격 | 기준 | 예 |
|---|---|---|
| 프로그램과 **한 묶음**인 파일 | 스크립트 위치(`Path(__file__).parent`) | 프로그램이 쓰는 데이터 파일, 프롬프트 템플릿, 설정 파일, 저장 파일 |
| **사용자가 지정한** 파일 | 현재 디렉터리(상대 경로 그대로) | `input()`으로 받은 파일 이름, 명령줄에서 받은 경로 |

사용자가 터미널에서 `cd ~/Documents`로 이동한 뒤 프로그램에 `report.txt`라고 입력했다면, 사용자는 `~/Documents/report.txt`를 뜻한 것이다. 이때는 상대 경로를 그대로 쓰는 것이 맞다. 7.1.8의 `show_file.py`가 그렇다. 반대로 프로그램이 스스로 읽고 쓰는 파일은 사용자가 어디서 실행할지 모르므로 스크립트 위치를 기준으로 한다.

7.1에서 만든 `todo_list.py`, `memo.py` 같은 프로그램은 모두 프로그램과 한 묶음인 파일을 상대 경로로 열었다. 실습 7-2에서 이것을 고친다. 이 장의 나머지 예제 중 데이터 파일을 다루는 프로그램은 처음부터 `BASE_DIR`을 쓴다.

> **절대 경로를 코드에 적지 말자**
> `open("/Users/jinyoung/python-lab/ch07/greeting.txt")`처럼 절대 경로를 직접 적으면 실행 위치 문제는 없어진다. 하지만 이 코드는 **내 컴퓨터에서만** 동작한다. 다른 사람의 컴퓨터, 다른 운영체제, 나중에 폴더를 옮긴 내 컴퓨터에서는 그 경로가 없다. AI가 만든 코드에 이런 경로가 들어 있다면 `Path(__file__).parent`를 기준으로 한 경로로 바꾸자.

```python
>>> from pathlib import Path
```

`Path("Hello.txt").exists()`의 결과는 운영체제에 따라 다를 수 있다. macOS와 Windows의 기본 설정은 파일 이름의 대소문자를 구분하지 않고, Linux는 구분한다.

**2) `organize.py` — 확장자별로 파일 정리하기**

다운로드 폴더처럼 여러 종류의 파일이 섞인 폴더를 확장자별 하위 폴더로 정리하는 프로그램을 만든다. 실제 다운로드 폴더에 바로 쓰면 위험하므로, 먼저 연습용 폴더를 만드는 스크립트를 실행한다.

```python
# make_samples.py
from pathlib import Path

folder = Path("downloads")
folder.mkdir(exist_ok=True)
names = ["보고서.docx", "회의록.txt", "사진1.jpg", "사진2.JPG", "data.csv", "할일.txt", "README"]
for name in names:
    (folder / name).write_text(f"{name}의 내용\n", encoding="utf-8")
print(f"{folder}에 파일 {len(names)}개를 만들었습니다.")
```

```
정리할 폴더: downloads
README → 기타/
data.csv → csv/
보고서.docx → docx/
사진1.jpg → jpg/
사진2.JPG → jpg/
할일.txt → txt/
회의록.txt → txt/
옮김 7개, 건너뜀 0개
```

- 폴더 이름을 입력받는다. 폴더가 아니면 `폴더가 아닙니다: ...`를 출력하고 끝낸다.
- 폴더 안의 **파일만** 대상으로 한다(이미 만들어진 하위 폴더는 건너뛴다). 처리 순서를 일정하게 하려고 정렬한다.
- 확장자는 소문자로 바꾸고 점을 뗀 것(`"JPG"` → `"jpg"`)을 하위 폴더 이름으로 쓴다. 확장자가 없으면 `기타` 폴더로 보낸다. 문자열의 `lower()`와 `lstrip(".")`를 쓰면 된다.
- 파일을 옮길 때는 `path.rename(새경로)`를 쓴다. 이름을 바꾸는 메서드지만, 새 경로가 다른 폴더이면 그 폴더로 옮겨진다.
- 옮길 곳에 같은 이름의 파일이 이미 있으면 옮기지 않고 `건너뜀: 사진1.jpg (jpg/에 같은 이름의 파일이 있음)`을 출력한다. `rename()`은 같은 이름의 파일이 있을 때 macOS에서는 **조용히 덮어쓰고**, Windows에서는 `FileExistsError`를 낸다. 운영체제마다 다른 동작에 기대지 말고 `exists()`로 미리 검사하자.
- 정리한 뒤 다시 실행하면 `옮김 0개, 건너뜀 0개`가 나와야 한다. `make_samples.py`를 한 번 더 실행해 같은 파일들을 다시 만든 뒤 정리하면 모두 건너뛰어야 한다.

**3) `find_text.py` — 폴더에서 글자 찾기**

폴더 이름과 찾을 단어를 입력받아, 그 폴더와 하위 폴더의 텍스트 파일(`.txt`, `.md`, `.py`, `.csv`, `.json`) 중 그 단어가 들어 있는 줄을 모두 보여 준다.

```
찾을 폴더: .
찾을 단어: 파이썬
greeting.txt:2: 오늘도 파이썬 공부를 시작해 볼까요?
(건너뜀: UTF-8이 아닌 파일 old_memo.txt)
todo.txt:5: 파이썬 7장 공부
2곳에서 찾았습니다.
```

(결과는 폴더에 어떤 파일이 있는지에 따라 다르다.)

- `rglob("*")`으로 모든 항목을 훑고, 파일이면서 확장자가 대상에 들어 있는 것만 처리한다. 대상 확장자는 집합(3.5)으로 두면 `in`으로 검사하기 좋다.
- 출력은 `경로:줄번호: 줄 내용` 모양이다. VS Code의 터미널에서 이 모양의 출력을 `Cmd`/`Ctrl`을 누른 채 클릭하면 그 파일의 그 줄이 열린다.
- UTF-8로 읽을 수 없는 파일은 프로그램을 멈추지 말고 건너뛰되, 건너뛰었다는 사실은 알려 준다. 6.2.6의 "조용히 삼키지 않는다"다. `try` 블록이 어디부터 어디까지여야 하는지 생각해 보자.
- 셸에서 `Path(".").rglob("*")`의 결과에 `.ruff_cache`나 `__pycache__` 같은 폴더 속 파일이 섞여 있다면, 그것도 찾는 대상이 되는가? 확장자 검사가 이 문제를 어떻게 줄여 주는지 확인하자.

## 7.3 구조화된 파일

7.1의 메모장은 한 줄에 메모 하나만 저장했다. 그런데 저장하고 싶은 데이터는 대개 그보다 복잡하다. 학생 한 명에게는 이름과 과목별 점수가 있고, 대출 기록 하나에는 도서 코드, 대출자, 반납 기한이 있다. 이런 데이터를 텍스트 파일에 저장하려면 **어떤 모양으로 적을지** 약속이 필요하다. 이 절에서는 가장 널리 쓰이는 두 가지 약속, CSV와 JSON을 배운다.

### 7.3.1 왜 정해진 형식이 필요한가

3.1.9에서 쉼표로 구분된 문자열을 `split(",")`으로 나눠 성적을 처리했다. 이 방식을 파일에 그대로 쓸 수 있을까? 다음 회원 목록을 생각해 보자. 주소에 쉼표가 들어 있다.

```
이름,주소,메모
철수,서울시 강남구, 테헤란로 1,
```

`split(",")`으로 나누면 주소가 두 칸으로 쪼개져서 메모 자리까지 밀려난다. 그렇다고 구분 기호를 다른 글자로 바꿔도, 언젠가 그 글자가 들어간 데이터를 만난다. 메모에 줄바꿈이 들어 있으면 "한 줄에 한 사람"이라는 규칙마저 깨진다.

이 문제는 모든 프로그램이 겪기 때문에, 이미 표준 형식과 그것을 다루는 모듈이 준비되어 있다.

- **CSV**(Comma-Separated Values) — 표 모양의 데이터. 한 줄이 한 행이고, 쉼표로 칸을 나눈다. 엑셀이나 구글 시트에서 열고 저장할 수 있다. 파이썬에서는 `csv` 모듈로 다룬다.
- **JSON**(JavaScript Object Notation) — 딕셔너리와 리스트가 겹겹이 쌓인 데이터. 웹 API와 LLM API가 주고받는 형식이다. 파이썬에서는 `json` 모듈로 다룬다.

"직접 `split()`하면 되지"라는 생각이 들 때가 바로 이 모듈들을 써야 할 때다. 예외적인 경우(쉼표, 따옴표, 줄바꿈)를 이 모듈들이 이미 다 처리해 두었다.

### 7.3.2 CSV 읽기

VS Code에서 `ch07` 폴더에 `scores.csv`를 만들고 다음 내용을 저장하자. 3.1.9의 성적 데이터에 수학 점수를 더한 것이다.

```
이름,국어,영어,수학
철수,85,90,77
영희,92,88,95
민수,78,85,80
```

**`csv.reader` — 한 행을 리스트로**

```python
>>> import csv
>>> with open("scores.csv", encoding="utf-8", newline="") as f:
...     reader = csv.reader(f)
...     for row in reader:
...         print(row)
...
['이름', '국어', '영어', '수학']
['철수', '85', '90', '77']
['영희', '92', '88', '95']
['민수', '78', '85', '80']
```

- `csv.reader(f)`는 열린 파일 객체를 받아 **CSV 읽기 객체**를 만든다. 이것을 `for`로 순회하면 한 행씩 **문자열의 리스트**로 꺼내 준다. 줄 끝의 `\n`도 알아서 처리한다.
- **값은 모두 문자열이다.** `'85'`는 숫자가 아니라 문자열이다. CSV 파일은 텍스트이고, 그 안의 `85`가 숫자인지 우편번호인지 `csv` 모듈은 알 수 없기 때문이다. 계산하려면 직접 `int()`로 바꿔야 한다.
- CSV 파일을 열 때는 **`newline=""`** 을 준다. 7.3.3에서 이유를 설명한다. 지금은 "CSV 파일은 `encoding="utf-8", newline=""`으로 연다"고 기억하자.

이번에는 쉼표와 줄바꿈이 들어간 데이터를 보자. VS Code에서 `members.csv`를 만든다.

```
이름,주소,메모
철수,"서울시 강남구, 테헤란로 1",
영희,부산시 해운대구,"줄바꿈이
있는 메모"
민수,"인천시 ""송도"" 신도시",VIP
```

CSV의 규칙은 이렇다. 쉼표나 줄바꿈, 큰따옴표가 들어간 값은 **큰따옴표로 감싸고**, 값 안의 큰따옴표는 **두 번 쓴다**(`""`). 이 파일을 `split()`으로 나눈 것과 `csv.reader`로 읽은 것을 비교해 보자.

```python
>>> with open("members.csv", encoding="utf-8") as f:
...     for line in f:
...         print(line.rstrip("\n").split(","))
...
['이름', '주소', '메모']
['철수', '"서울시 강남구', ' 테헤란로 1"', '']
['영희', '부산시 해운대구', '"줄바꿈이']
['있는 메모"']
['민수', '"인천시 ""송도"" 신도시"', 'VIP']
>>> with open("members.csv", encoding="utf-8", newline="") as f:
...     for row in csv.reader(f):
...         print(row)
...
['이름', '주소', '메모']
['철수', '서울시 강남구, 테헤란로 1', '']
['영희', '부산시 해운대구', '줄바꿈이\n있는 메모']
['민수', '인천시 "송도" 신도시', 'VIP']
```

`split()`은 주소를 쪼개고, 영희의 메모를 두 행으로 나누고, 따옴표를 그대로 남겼다. `csv.reader`는 모든 행을 정확히 세 칸으로 읽었다.

**`csv.DictReader` — 한 행을 딕셔너리로**

`row[1]`이 국어 점수라는 것을 기억해야 하는 불편함은 3.1.9에서도 이야기했다. 첫 줄(헤더)에 열 이름이 있다면 `csv.DictReader`를 쓰자.

```python
>>> with open("scores.csv", encoding="utf-8", newline="") as f:
...     reader = csv.DictReader(f)
...     print(reader.fieldnames)
...     for row in reader:
...         print(row)
...
['이름', '국어', '영어', '수학']
{'이름': '철수', '국어': '85', '영어': '90', '수학': '77'}
{'이름': '영희', '국어': '92', '영어': '88', '수학': '95'}
{'이름': '민수', '국어': '78', '영어': '85', '수학': '80'}
>>> row["국어"] + row["영어"]
'7885'
>>> int(row["국어"]) + int(row["영어"])
163
```

- `DictReader`는 첫 줄을 열 이름으로 쓰고, 나머지 각 행을 `{열 이름: 값}` 딕셔너리로 꺼내 준다. 열 이름 목록은 `fieldnames` 속성에 있다.
- `row["국어"]`처럼 **이름으로** 값을 꺼낼 수 있다. 엑셀에서 누군가 열 순서를 바꿔 저장해도 코드는 그대로 동작한다.
- 여기서도 값은 문자열이다. `'78' + '85'`는 덧셈이 아니라 문자열 잇기라서 `'7885'`가 되었다. 오류도 나지 않고 조용히 틀리는 전형적인 실수다. CSV에서 읽은 값을 계산에 쓰기 전에는 꼭 바꾸자.

행이 많지 않다면 `list()`로 모든 행을 리스트로 받아 두고 파일을 닫은 뒤에 처리해도 된다. `students = list(csv.DictReader(f))`처럼 쓴다. 7.3.3의 예제가 그렇게 한다.

### 7.3.3 CSV 쓰기

**`csv.DictWriter` — 딕셔너리를 한 행으로**

`scores.csv`를 읽어 학생별 총점과 평균을 `score_report.csv`에 저장하자.

```python
# score_report.py
import csv

SUBJECTS = ["국어", "영어", "수학"]

with open("scores.csv", encoding="utf-8", newline="") as f:
    students = list(csv.DictReader(f))

with open("score_report.csv", "w", encoding="utf-8", newline="") as f:
    writer = csv.DictWriter(f, fieldnames=["이름", "총점", "평균"])
    writer.writeheader()
    for student in students:
        total = 0
        for subject in SUBJECTS:
            total += int(student[subject])
        writer.writerow(
            {"이름": student["이름"], "총점": total, "평균": round(total / len(SUBJECTS), 1)}
        )

print(f"{len(students)}명의 성적표를 score_report.csv에 저장했습니다.")
```

```
3명의 성적표를 score_report.csv에 저장했습니다.
```

`score_report.csv`의 내용은 다음과 같다.

```
이름,총점,평균
철수,252,84.0
영희,275,91.7
민수,243,81.0
```

- `csv.DictWriter(f, fieldnames=[...])`는 딕셔너리를 한 행으로 쓰는 객체를 만든다. `fieldnames`로 **열 이름과 순서**를 정한다.
- `writeheader()`는 열 이름을 첫 줄에 쓴다.
- `writerow(딕셔너리)`는 한 행을 쓴다. 숫자는 알아서 문자열로 바꿔 준다. 딕셔너리에 `fieldnames`에 없는 키가 있으면 `ValueError`가 난다. 오타를 바로 알 수 있어 좋다.

**`csv.writer` — 리스트를 한 행으로**

헤더 없이 리스트로 쓸 때는 `csv.writer`를 쓴다. 따옴표 처리도 알아서 해 준다.

```python
# members_out.py
import csv

rows = [
    ["이름", "주소", "메모"],
    ["철수", "서울시 강남구, 테헤란로 1", ""],
    ["민수", '인천시 "송도" 신도시', "VIP"],
]
with open("members_out.csv", "w", encoding="utf-8", newline="") as f:
    writer = csv.writer(f)
    writer.writerows(rows)
```

```
이름,주소,메모
철수,"서울시 강남구, 테헤란로 1",
민수,"인천시 ""송도"" 신도시",VIP
```

쉼표가 있는 주소는 큰따옴표로 감싸고, 값 안의 큰따옴표는 두 번 썼다. `writerow(리스트)`는 한 행을, `writerows(리스트의 리스트)`는 여러 행을 한꺼번에 쓴다.

**`newline=""`이 필요한 이유**

`csv` 모듈은 줄바꿈을 **스스로** 처리한다. 쓸 때는 행 끝에 `\r\n`을 넣고(CSV 표준이 정한 줄바꿈이다), 읽을 때는 큰따옴표 안의 줄바꿈과 행을 나누는 줄바꿈을 구별한다. 그런데 텍스트 모드로 연 파일은 읽고 쓸 때 줄바꿈을 운영체제에 맞게 바꾸는 일을 한다. Windows에서는 쓸 때 `\n`을 `\r\n`으로 바꾼다. 두 쪽이 모두 줄바꿈을 손대면 `\r\n`이 `\r\r\n`이 되어, **엑셀에서 열면 행 사이에 빈 행이 끼어 보이는** 문제가 생긴다. `newline=""`은 "파일 쪽에서는 줄바꿈을 손대지 말라"는 뜻이다. 그러면 `csv` 모듈만 줄바꿈을 처리한다. macOS에서는 빼먹어도 겉보기에는 문제가 없지만, 코드는 어디서 실행될지 모르므로 항상 붙이자.

**엑셀과 주고받을 때 — `utf-8-sig`**

`score_report.csv`를 한국어 Windows의 엑셀에서 더블클릭해 열면 한글이 깨져 보인다. 엑셀은 CSV 파일이 UTF-8이라는 표시가 없으면 cp949로 읽기 때문이다. 이 표시를 **BOM**(Byte Order Mark)이라고 한다. 파일 맨 앞에 붙는 세 바이트(`EF BB BF`)로, "이 파일은 UTF-8이다"라는 뜻이다. 인코딩을 `"utf-8-sig"`로 지정하면 파이썬이 BOM을 붙여 준다.

```python
# excel_csv.py
import csv

with open("excel.csv", "w", encoding="utf-8-sig", newline="") as f:
    writer = csv.writer(f)
    writer.writerow(["이름", "점수"])
    writer.writerow(["철수", 90])
```

이 파일은 엑셀에서 한글이 제대로 보인다. 반대로 엑셀에서 **CSV UTF-8** 형식으로 저장한 파일에도 BOM이 붙어 있다. 그런 파일을 `encoding="utf-8"`로 읽으면 무슨 일이 생길까?

```python
>>> with open("excel.csv", encoding="utf-8", newline="") as f:
...     for row in csv.DictReader(f):
...         print(row)
...
{'\ufeff이름': '철수', '점수': '90'}
>>> row["이름"]
Traceback (most recent call last):
  File "<python-input-8>", line 1, in <module>
    row["이름"]
    ~~~^^^^^^^^
KeyError: '이름'
>>> with open("excel.csv", encoding="utf-8-sig", newline="") as f:
...     for row in csv.DictReader(f):
...         print(row)
...
{'이름': '철수', '점수': '90'}
>>> with open("excel.csv", "rb") as f:
...     print(f.read())
...
b'\xef\xbb\xbf\xec\x9d\xb4\xeb\xa6\x84,\xec\xa0\x90\xec\x88\x98\r\n\xec\xb2\xa0\xec\x88\x98,90\r\n'
```

`utf-8`로 읽으면 BOM이 보이지 않는 글자 `'\ufeff'`로 남아 첫 번째 열 이름에 붙는다. 화면에 `print()`하면 `이름`처럼 보이는데 `row["이름"]`은 `KeyError`가 나는, 원인을 찾기 아주 어려운 오류다. `utf-8-sig`로 읽으면 BOM을 떼어 준다. 마지막 줄은 바이너리 모드(`"rb"`)로 파일의 실제 바이트를 본 것이다. 맨 앞의 `\xef\xbb\xbf`가 BOM이고, 행 끝마다 `csv` 모듈이 쓴 `\r\n`이 보인다.

`utf-8-sig`는 BOM이 **없는** UTF-8 파일도 문제없이 읽는다. 그래서 다음과 같이 정해 두면 편하다.

| 상황 | 인코딩 |
|---|---|
| CSV를 **읽을 때** (누가 만들었는지 모른다) | `utf-8-sig` |
| 엑셀에서 열 CSV를 **쓸 때** | `utf-8-sig` |
| 프로그램끼리만 주고받는 CSV를 쓸 때 | `utf-8` |
| 공공데이터포털 등에서 받은 오래된 CSV | `cp949`일 수 있다. `UnicodeDecodeError`가 나면 시도해 보자 |

### 7.3.4 JSON — 파이썬 자료구조를 닮은 형식

3.4.6에서 중첩 딕셔너리가 JSON과 모양이 같다고 했다. JSON 파일은 다음처럼 생겼다.

```json
{
  "title": "파이썬 첫걸음",
  "price": 18000,
  "tags": ["파이썬", "입문"],
  "in_stock": true,
  "discount": null
}
```

파이썬의 딕셔너리 리터럴과 거의 같다. 다른 점은 몇 가지뿐이다.

| JSON | 파이썬 | 차이 |
|---|---|---|
| 객체 `{"키": 값}` | 딕셔너리 `dict` | JSON의 키는 **문자열만** 된다 |
| 배열 `[1, 2]` | 리스트 `list` | |
| 문자열 `"글자"` | 문자열 `str` | JSON은 **큰따옴표만** 쓴다 |
| 숫자 `18000`, `0.92` | `int`, `float` | |
| `true`, `false` | `True`, `False` | 소문자 |
| `null` | `None` | |

JSON에는 튜플, 집합, 날짜 같은 자료형이 없다. 이 여섯 가지만으로 데이터를 표현한다. 그 대신 거의 모든 프로그래밍 언어가 JSON을 읽고 쓸 수 있어서, 서로 다른 프로그램이 데이터를 주고받는 표준 형식이 되었다. 웹 API와 LLM API의 요청과 응답도 JSON이다.

### 7.3.5 문자열과 오가기 — `json.dumps()`, `json.loads()`

`json` 모듈에는 이름이 비슷한 함수가 네 개 있다. 끝에 `s`가 붙은 것은 **문자열**(string)과, 붙지 않은 것은 **파일**과 오간다.

| 함수 | 방향 |
|---|---|
| `json.dumps(데이터)` | 파이썬 데이터 → JSON **문자열** |
| `json.loads(문자열)` | JSON **문자열** → 파이썬 데이터 |
| `json.dump(데이터, f)` | 파이썬 데이터 → JSON **파일** |
| `json.load(f)` | JSON **파일** → 파이썬 데이터 |

먼저 문자열과 오가는 것부터 보자.

```python
>>> import json
>>> book = {"title": "파이썬 첫걸음", "price": 18000, "tags": ["파이썬", "입문"], "in_stock": True, "discount": None}
>>> text = json.dumps(book)
>>> text
'{"title": "\\ud30c\\uc774\\uc36c \\uccab\\uac78\\uc74c", "price": 18000, "tags": ["\\ud30c\\uc774\\uc36c", "\\uc785\\ubb38"], "in_stock": true, "discount": null}'
>>> type(text)
<class 'str'>
>>> print(json.dumps(book, ensure_ascii=False))
{"title": "파이썬 첫걸음", "price": 18000, "tags": ["파이썬", "입문"], "in_stock": true, "discount": null}
>>> print(json.dumps(book, ensure_ascii=False, indent=2))
{
  "title": "파이썬 첫걸음",
  "price": 18000,
  "tags": [
    "파이썬",
    "입문"
  ],
  "in_stock": true,
  "discount": null
}
```

- `json.dumps()`는 딕셔너리를 JSON 모양의 **문자열**로 바꾼다. `True`는 `true`로, `None`은 `null`로 바뀌었다.
- 기본 설정에서는 한글 같은 영문 이외의 글자를 `파` 같은 **유니코드 이스케이프**로 바꾼다. 틀린 것은 아니고 다른 프로그램이 읽으면 원래 글자로 돌아오지만, 사람이 읽을 수 없다. **`ensure_ascii=False`**를 주면 한글을 그대로 쓴다.
- **`indent=2`**를 주면 사람이 읽기 좋게 줄을 바꾸고 들여쓴다. 파일로 저장해 사람이 열어 볼 데이터라면 붙이자.

`str(book)`과 헷갈리지 말자.

```python
>>> str(book)
"{'title': '파이썬 첫걸음', 'price': 18000, 'tags': ['파이썬', '입문'], 'in_stock': True, 'discount': None}"
```

이것은 파이썬의 표현(`repr`)이지 JSON이 아니다. 작은따옴표, `True`, `None`은 JSON 규칙에 맞지 않아서 다른 프로그램은 물론 `json.loads()`로도 읽을 수 없다. 딕셔너리를 파일에 저장하려고 `f.write(str(data))`라고 쓰는 것은 흔한 실수다. JSON으로 저장하려면 반드시 `json` 모듈을 쓰자.

**LLM의 답 해석하기**

반대로 JSON 문자열을 파이썬 데이터로 바꿀 때는 `json.loads()`를 쓴다. LLM에게 "리뷰의 감정을 JSON으로 답하라"고 했더니 다음 문자열이 돌아왔다고 하자.

```python
>>> answer = '{"sentiment": "positive", "score": 0.92, "keywords": ["배송", "친절"]}'
>>> result = json.loads(answer)
>>> result
{'sentiment': 'positive', 'score': 0.92, 'keywords': ['배송', '친절']}
>>> result["keywords"][0]
'배송'
```

문자열이었던 답이 딕셔너리가 되어, 3장에서 배운 대로 키와 인덱스로 값을 꺼낼 수 있다. LLM API의 응답도 결국 이렇게 JSON 문자열로 도착해 딕셔너리로 바뀐다.

그런데 LLM은 언제나 규칙을 지키지는 않는다. 6장 도입부에서 말한 그 실패를 직접 보자.

```python
>>> json.loads("{'sentiment': 'positive'}")
Traceback (most recent call last):
  File "<python-input-23>", line 1, in <module>
    json.loads("{'sentiment': 'positive'}")
    ~~~~~~~~~~^^^^^^^^^^^^^^^^^^^^^^^^^^^^^
  ...(json 모듈 안쪽의 File 줄 생략)...
json.decoder.JSONDecodeError: Expecting property name enclosed in double quotes: line 1 column 2 (char 1)
>>> json.loads('{"sentiment": "positive",}')
Traceback (most recent call last):
  File "<python-input-24>", line 1, in <module>
    json.loads('{"sentiment": "positive",}')
    ~~~~~~~~~~^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^
  ...(json 모듈 안쪽의 File 줄 생략)...
json.decoder.JSONDecodeError: Illegal trailing comma before end of object: line 1 column 25 (char 24)
>>> json.loads('```json\n{"sentiment": "positive"}\n```')
Traceback (most recent call last):
  File "<python-input-25>", line 1, in <module>
    json.loads('```json\n{"sentiment": "positive"}\n```')
    ~~~~~~~~~~^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^
  ...(json 모듈 안쪽의 File 줄 생략)...
json.decoder.JSONDecodeError: Expecting value: line 1 column 1 (char 0)
>>> issubclass(json.JSONDecodeError, ValueError)
True
```

(실제 트레이스백에는 `json` 모듈 안쪽의 `File` 줄이 여러 개 나온다. 내 코드의 줄과 마지막 줄만 남겼다.)

- 작은따옴표를 쓴 경우: 파이썬 딕셔너리처럼 생겼지만 JSON이 아니다. "속성 이름(키)은 큰따옴표로 감싸야 한다"는 메시지다.
- 마지막 값 뒤에 쉼표가 남은 경우: 파이썬은 `[1, 2,]`를 허용하지만 JSON은 허용하지 않는다. `Illegal trailing comma ...`라는 친절한 메시지는 파이썬 3.13부터 나온다. 3.12에서는 같은 입력에 `Expecting property name enclosed in double quotes: line 1 column 26 (char 25)`가 나온다. 메시지는 버전마다 다를 수 있으니, 메시지의 문구보다 **위치**(`line`, `column`)를 보고 그 근처를 살피자.
- 답을 마크다운 코드 블록(` ```json ... ``` `)으로 감싼 경우: LLM이 아주 자주 하는 일이다. 첫 글자부터 JSON이 아니므로 "1번째 줄 1번째 칸에 값이 있어야 한다"는 메시지가 나왔다.

메시지 끝의 `line 1 column 2 (char 1)`은 문자열의 어디에서 문제를 발견했는지 알려 준다. 긴 JSON에서 틀린 곳을 찾을 때 유용하다.

`JSONDecodeError`는 `ValueError`의 자식이다. "문자열이라는 자료형은 맞는데, 그 값이 JSON 규칙에 맞지 않는다"는 뜻이다. LLM의 답을 해석하는 코드는 이 예외를 잡아서 다시 요청하거나 건너뛴다. 실습 7-3에서 이런 함수를 만든다.

### 7.3.6 파일과 오가기 — `json.dump()`, `json.load()`

파일에 저장할 때는 `dump()`와 `load()`를 쓴다. 열린 파일 객체를 함께 넘긴다.

```python
>>> settings = {"user": "철수", "theme": "dark", "font_size": 14, "recent_files": ["memo.txt", "todo.txt"]}
>>> with open("settings.json", "w", encoding="utf-8") as f:
...     json.dump(settings, f, ensure_ascii=False, indent=2)
...
>>> with open("settings.json", encoding="utf-8") as f:
...     loaded = json.load(f)
...
>>> loaded == settings
True
>>> loaded["recent_files"][0]
'memo.txt'
```

`settings.json`을 VS Code에서 열어 보자.

```json
{
  "user": "철수",
  "theme": "dark",
  "font_size": 14,
  "recent_files": [
    "memo.txt",
    "todo.txt"
  ]
}
```

저장했다가 다시 읽은 `loaded`는 원래의 `settings`와 같은 값이다. CSV와 달리 숫자 `14`는 숫자로, 리스트는 리스트로 돌아왔다. JSON은 자료형을 함께 저장하기 때문이다. 이것이 JSON의 큰 장점이다. (`loaded == settings`는 `True`지만 `loaded is settings`는 `False`다. 3.2에서 배운 대로 값이 같은 **다른 객체**다.)

JSON 파일을 열 때도 `encoding="utf-8"`을 쓴다. JSON 표준은 UTF-8을 쓰도록 정해 두었다.

**JSON으로 바꾸면 달라지는 것, 바꿀 수 없는 것**

JSON에는 자료형이 여섯 가지뿐이라서, 저장했다가 다시 읽으면 달라지는 값이 있다.

```python
>>> from datetime import date
>>> json.loads(json.dumps({1: "하나", 2: "둘"}))
{'1': '하나', '2': '둘'}
>>> json.loads(json.dumps({"point": (3, 4)}))
{'point': [3, 4]}
>>> json.dumps({"due": date(2026, 11, 14)})
Traceback (most recent call last):
  File "<python-input-35>", line 1, in <module>
    json.dumps({"due": date(2026, 11, 14)})
    ~~~~~~~~~~^^^^^^^^^^^^^^^^^^^^^^^^^^^^^
  ...(json 모듈 안쪽의 File 줄 생략)...
TypeError: Object of type date is not JSON serializable
```

- 딕셔너리의 **정수 키는 문자열이 된다.** JSON 객체의 키는 문자열만 되기 때문이다. 다시 읽은 딕셔너리에서 `data[1]`로 꺼내면 `KeyError`가 난다.
- **튜플은 리스트가 된다.** JSON에는 튜플이 없다.
- **날짜(`date`), 집합(`set`), 직접 만든 클래스의 객체는 바꿀 수 없다.** `TypeError`가 난다. "JSON으로 바꿀(serialize) 수 없는 자료형"이라는 뜻이다.

날짜는 4.6.9의 `fromisoformat()`과 짝을 이루는 `isoformat()`으로 문자열로 바꿔 저장하고, 읽을 때 다시 날짜로 되돌린다.

```python
>>> date(2026, 11, 14).isoformat()
'2026-11-14'
>>> json.dumps({"due": date(2026, 11, 14).isoformat()})
'{"due": "2026-11-14"}'
>>> date.fromisoformat("2026-11-14")
datetime.date(2026, 11, 14)
```

`2026-11-14` 같은 ISO 8601 모양은 사람이 읽기 쉽고, 문자열 순서로 정렬해도 날짜 순서가 되어 JSON이나 CSV에 날짜를 저장할 때 가장 많이 쓰는 모양이다. 집합은 `sorted()`나 `list()`로 리스트로 바꿔 저장하고 읽을 때 `set()`으로 되돌린다.

정리하면, **파일에 저장할 수 있는 모양으로 바꾸는 일과 다시 되돌리는 일은 프로그래머가 해야 한다.** 이 일을 한곳에 모아 두면 좋은데, 그 방법이 다음 절이다.

### 7.3.7 데이터 클래스와 파일 오가기

5.4.7에서 딕셔너리와 데이터 클래스를 오가는 방법을 배웠다. 데이터 클래스 → `asdict()` → 딕셔너리 → `json.dump()` → 파일, 그리고 그 반대 순서로 이으면 데이터 클래스의 리스트를 파일에 저장하고 읽을 수 있다. 할 일 목록으로 해 보자.

```python
# todo_store.py
import json
from dataclasses import asdict, dataclass
from datetime import date
from pathlib import Path

TODO_PATH = Path(__file__).parent / "todos.json"


@dataclass
class Todo:
    title: str
    due: date
    done: bool = False


def todo_to_dict(todo: Todo) -> dict:
    """Todo를 JSON으로 저장할 수 있는 딕셔너리로 바꾼다."""
    data = asdict(todo)
    data["due"] = todo.due.isoformat()
    return data


def todo_from_dict(data: dict) -> Todo:
    """todo_to_dict()가 만든 딕셔너리를 Todo로 되돌린다."""
    return Todo(data["title"], date.fromisoformat(data["due"]), data["done"])


def save_todos(todos: list[Todo], path: Path) -> None:
    records = []
    for todo in todos:
        records.append(todo_to_dict(todo))
    with open(path, "w", encoding="utf-8") as f:
        json.dump(records, f, ensure_ascii=False, indent=2)


def load_todos(path: Path) -> list[Todo]:
    """파일에서 할 일 목록을 읽는다. 파일이 없으면 빈 리스트를 돌려준다."""
    try:
        with open(path, encoding="utf-8") as f:
            records = json.load(f)
    except FileNotFoundError:
        return []
    todos = []
    for record in records:
        todos.append(todo_from_dict(record))
    return todos


todos = load_todos(TODO_PATH)
print(f"불러온 할 일: {len(todos)}개")
for todo in todos:
    print(" ", todo)

todos.append(Todo("7장 실습 하기", date(2026, 11, 14)))
save_todos(todos, TODO_PATH)
print(f"저장한 할 일: {len(todos)}개")
```

두 번 실행해 보자.

```
불러온 할 일: 0개
저장한 할 일: 1개
```

```
불러온 할 일: 1개
  Todo(title='7장 실습 하기', due=datetime.date(2026, 11, 14), done=False)
저장한 할 일: 2개
```

`todos.json`은 다음과 같다.

```json
[
  {
    "title": "7장 실습 하기",
    "due": "2026-11-14",
    "done": false
  },
  {
    "title": "7장 실습 하기",
    "due": "2026-11-14",
    "done": false
  }
]
```

- 저장 파일의 경로는 7.2.4의 방법대로 스크립트 위치를 기준으로 정했다. 이 파일은 프로그램과 한 묶음이기 때문이다.
- `asdict()`는 날짜를 `date` 객체 그대로 둔다. 그래서 `todo_to_dict()`에서 `due`만 문자열로 바꾸었다. 이것을 빼먹으면 `json.dump()`에서 7.3.6의 `TypeError`가 난다.
- 바꾸는 함수(`todo_to_dict`)와 되돌리는 함수(`todo_from_dict`)를 **짝으로** 만들어 두었다. 파일 형식에 관한 지식이 이 두 함수에만 들어 있으므로, 나중에 필드가 늘어나도 이 두 곳만 고치면 된다. 나머지 코드는 파일이 어떻게 생겼는지 몰라도 `Todo` 객체만 주고받는다.
- 처음 실행할 때는 파일이 없으므로 빈 리스트로 시작한다(7.1.8).

**같은 `Todo`를 CSV로 저장하고 읽기**

같은 일을 CSV로 해 보면 두 형식의 차이가 잘 보인다. `Todo`의 필드는 세 개로 정해져 있으므로 표 한 줄에 담을 수 있다.

```python
# todo_csv.py
import csv
from dataclasses import dataclass
from datetime import date
from pathlib import Path

TODO_CSV_PATH = Path(__file__).parent / "todos.csv"
FIELDNAMES = ["title", "due", "done"]


@dataclass
class Todo:
    title: str
    due: date
    done: bool = False


def todo_to_row(todo: Todo) -> dict:
    """Todo를 CSV 한 행(딕셔너리)으로 바꾼다."""
    return {"title": todo.title, "due": todo.due.isoformat(), "done": todo.done}


def todo_from_row(row: dict) -> Todo:
    """CSV에서 읽은 한 행을 Todo로 되돌린다. 값이 모두 문자열이라는 점에 주의한다."""
    return Todo(row["title"], date.fromisoformat(row["due"]), row["done"] == "True")


def save_todos_csv(todos: list[Todo], path: Path) -> None:
    with open(path, "w", encoding="utf-8", newline="") as f:
        writer = csv.DictWriter(f, fieldnames=FIELDNAMES)
        writer.writeheader()
        for todo in todos:
            writer.writerow(todo_to_row(todo))


def load_todos_csv(path: Path) -> list[Todo]:
    todos = []
    with open(path, encoding="utf-8-sig", newline="") as f:
        for row in csv.DictReader(f):
            todos.append(todo_from_row(row))
    return todos


todos = [
    Todo("7장 실습 하기", date(2026, 11, 14)),
    Todo("우유 사기", date(2026, 11, 11), True),
]
save_todos_csv(todos, TODO_CSV_PATH)
loaded = load_todos_csv(TODO_CSV_PATH)
for todo in loaded:
    print(todo)
print("원래와 같은가?", loaded == todos)
```

```
Todo(title='7장 실습 하기', due=datetime.date(2026, 11, 14), done=False)
Todo(title='우유 사기', due=datetime.date(2026, 11, 11), done=True)
원래와 같은가? True
```

`todos.csv`는 다음과 같다.

```
title,due,done
7장 실습 하기,2026-11-14,False
우유 사기,2026-11-11,True
```

구조는 JSON 버전과 같다. 바꾸는 함수(`todo_to_row`)와 되돌리는 함수(`todo_from_row`)를 짝으로 두고, 저장·읽기 함수는 그것을 부를 뿐이다. 데이터 클래스는 5.4에서 배운 대로 `==`가 필드를 비교하므로, 저장했다가 읽은 `loaded`가 원래의 `todos`와 같은지 바로 확인할 수 있다. 다른 점은 **되돌리는 함수가 하는 일**이다.

| 필드 | JSON에서 읽으면 | CSV에서 읽으면 | 되돌리는 방법 |
|---|---|---|---|
| `title` | `str` | `str` | 그대로 |
| `due` | `"2026-11-14"`(`str`) | `"2026-11-14"`(`str`) | 둘 다 `date.fromisoformat()` |
| `done` | `False`(`bool`) | `"False"`(`str`) | JSON은 그대로, CSV는 `== "True"` |

JSON은 불리언을 불리언으로 저장하지만, CSV는 `DictWriter`가 `str(False)`로 바꾼 글자 `"False"`를 저장한다.

**CSV의 불리언 함정**

`todo_from_row()`에서 `row["done"] == "True"`라고 쓴 이유가 있다. CSV는 모든 값이 문자열이므로 되돌리는 일이 더 많다. `int()`, `float()`로 숫자를 되돌리는 것은 이미 해 보았다. 조심해야 할 것은 **불리언**이다.

```python
>>> bool("False")
True
>>> row = {"name": "커피", "price": "2500", "on_sale": "False"}
>>> int(row["price"]), row["on_sale"] == "True"
(2500, False)
```

2.4.5에서 배운 대로 비어 있지 않은 문자열은 모두 참이다. `"False"`라는 다섯 글자짜리 문자열도 참이라서 `bool("False")`는 `True`다. CSV에서 읽은 `"True"`/`"False"`는 `== "True"`처럼 문자열을 비교해서 되돌려야 한다. 이런 함정이 있으니, 자료형이 여러 가지인 데이터를 저장할 때는 JSON이 더 안전하다.

**잘못된 데이터는 입구에서**

파일은 프로그램 바깥에 있다. 사람이 편집기로 고칠 수도 있고, 다른 프로그램이 잘못 쓸 수도 있고, 저장하는 도중에 컴퓨터가 꺼져서 반만 쓰였을 수도 있다. 그러니 파일에서 읽은 데이터는 사용자 입력과 마찬가지로 6.2.3에서 말한 **바깥에서 들어오는 데이터**이고, 그 입구에서 검사해야 한다.

`todo_from_dict()`에 `"due"` 키가 없는 딕셔너리가 들어오면 `KeyError`가, 날짜 모양이 아니면 `ValueError`가 난다. 이 예외들은 **파일을 읽는 그 자리에서** 나므로, 나중에 엉뚱한 곳에서 이상한 동작으로 드러나는 것보다 훨씬 낫다(5.4.7에서 `Product(**row)`가 `TypeError`를 낸 것과 같은 이유다). 다만 사용자에게는 `KeyError: 'due'`보다 "todos.json의 3번째 기록에 due가 없습니다" 같은 메시지가 필요하다. 6.2.5에서 배운 `raise ... from e`로 예외를 바꿔 다시 일으키면 된다. 실습 7-4에서 그렇게 한다.

### 7.3.8 JSONL — 한 줄에 JSON 하나

JSON 파일은 전체가 하나의 값(보통 리스트나 딕셔너리)이다. 그래서 기록을 하나 **추가**하려면 파일 전체를 읽고, 리스트에 추가하고, 전체를 다시 써야 한다. 기록이 수십만 개라면 부담스럽다. 또 쓰는 도중에 프로그램이 멈추면 닫는 괄호 `]`가 빠진 파일이 남아 **전체를** 읽을 수 없게 된다.

**JSONL**(JSON Lines)은 이 문제를 간단히 해결한다. **한 줄에 JSON 값 하나**를 쓰는 형식이다. 확장자는 `.jsonl`을 쓴다.

```
{"role": "user", "content": "안녕"}
{"role": "assistant", "content": "2글자를 받았습니다."}
```

- 기록을 추가할 때는 `"a"` 모드로 열어 한 줄을 덧붙이면 된다.
- 읽을 때는 7.1.6의 `for line in f`로 한 줄씩 읽어 `json.loads()`로 바꾼다. 파일이 아무리 커도 한 줄씩 처리할 수 있다.
- 한 줄이 망가져도 **그 줄만 건너뛰고** 나머지 줄을 읽을 수 있다. JSON 파일은 괄호 하나만 빠져도 전체를 읽을 수 없지만, JSONL은 줄마다 따로 해석하기 때문이다. 단, 이것은 형식이 그렇게 할 수 있게 해 준다는 뜻이다. 실제로 계속 읽으려면 코드가 **줄마다** 예외를 처리해야 한다. 아래 예제에서 그렇게 한다.

LLM 분야에서 JSONL은 아주 흔하다. 파인튜닝 학습 데이터, 여러 요청을 한꺼번에 보내는 배치 API의 입력 파일, 평가용 질문 목록, 대화 기록이 대부분 JSONL이다. 위의 `{"role": ..., "content": ...}` 모양은 LLM API가 대화를 주고받을 때 쓰는 메시지 모양과 같다.

대화를 JSONL 파일에 쌓아 가는 프로그램을 만들어 보자. 아직 LLM을 호출하지는 않으므로, 답은 받은 글자 수를 알려 주는 것으로 대신한다.

```python
# chat_log.py
import json
from pathlib import Path

LOG_PATH = Path(__file__).parent / "chat_log.jsonl"


def append_message(role: str, content: str) -> None:
    """메시지 하나를 JSONL 파일의 끝에 한 줄로 덧붙인다."""
    record = {"role": role, "content": content}
    with open(LOG_PATH, "a", encoding="utf-8") as f:
        f.write(json.dumps(record, ensure_ascii=False) + "\n")


def load_messages() -> list[dict]:
    """JSONL 파일의 메시지를 모두 읽는다. 파일이 없으면 빈 리스트를 돌려준다.

    빈 줄은 건너뛴다. JSON이 아닌 줄은 알리고 건너뛴다.
    """
    messages = []
    try:
        with open(LOG_PATH, encoding="utf-8") as f:
            for line_no, line in enumerate(f, start=1):
                line = line.strip()
                if not line:
                    continue
                try:
                    messages.append(json.loads(line))
                except json.JSONDecodeError:
                    print(f"(건너뜀: {LOG_PATH.name} {line_no}번째 줄이 JSON이 아님)")
    except FileNotFoundError:
        pass
    return messages


messages = load_messages()
print(f"지난 대화 {len(messages)}개를 불러왔습니다.")
while True:
    text = input("나: ").strip()
    if not text:
        break
    append_message("user", text)
    reply = f"{len(text)}글자를 받았습니다."
    append_message("assistant", reply)
    print("봇:", reply)
```

```
지난 대화 0개를 불러왔습니다.
나: 안녕
봇: 2글자를 받았습니다.
나: 파일 입출력 공부 중이야
봇: 13글자를 받았습니다.
나:
```

다시 실행하면 지난 대화를 불러온다.

```
지난 대화 4개를 불러왔습니다.
나: JSONL 좋다
봇: 8글자를 받았습니다.
나:
```

`chat_log.jsonl`에는 메시지가 한 줄에 하나씩 쌓인다.

```
{"role": "user", "content": "안녕"}
{"role": "assistant", "content": "2글자를 받았습니다."}
{"role": "user", "content": "파일 입출력 공부 중이야"}
{"role": "assistant", "content": "13글자를 받았습니다."}
{"role": "user", "content": "JSONL 좋다"}
{"role": "assistant", "content": "8글자를 받았습니다."}
```

VS Code에서 3번째 줄의 끝부분 `공부 중이야"}`를 지워 저장하고 다시 실행해 보자. 저장 도중에 프로그램이 끊겨 줄이 반만 쓰인 상황을 흉내 낸 것이다.

```
(건너뜀: chat_log.jsonl 3번째 줄이 JSON이 아님)
지난 대화 5개를 불러왔습니다.
나:
```

망가진 한 줄만 빼고 나머지 다섯 메시지를 읽었다.

- 한 줄에 하나씩 써야 하므로 `json.dump()`가 아니라 `json.dumps()`로 문자열을 만든 뒤 `"\n"`을 붙여 썼다. `indent`를 주면 JSON이 여러 줄로 나뉘므로 JSONL에서는 쓰지 않는다.
- `try`/`except json.JSONDecodeError`를 반복문 **안에** 두었다. 그래서 망가진 줄이 있으면 그 줄만 건너뛰고 다음 줄로 넘어간다. 반복문 바깥에서 잡으면 망가진 줄을 만나는 순간 반복이 끝나서 그 뒤의 줄은 읽지 못한다. 건너뛸 때는 몇 번째 줄인지 알려 준다(6.2.6의 "조용히 삼키지 않는다").
- 빈 줄은 오류로 보지 않고 조용히 건너뛰도록 **이 예제에서 정했다.** 편집기로 파일을 열었다가 끝에 빈 줄을 남기는 일이 흔하기 때문이다. JSONL 형식 자체가 빈 줄을 허용하는 것은 아니므로, 다른 프로그램이 만든 JSONL을 읽을 때는 그 프로그램의 규칙을 확인하자.
- `except FileNotFoundError: pass`는 "파일이 없으면 아무것도 하지 않는다"는 뜻이다. `messages`가 빈 리스트인 채로 아래의 `return`에 도착한다.

### 7.3.9 무엇을 쓸까 — 텍스트, CSV, JSON, JSONL

| | 텍스트 | CSV | JSON | JSONL |
|---|---|---|---|---|
| 모양 | 자유로운 글, 한 줄에 하나 | 표(행과 열) | 겹겹이 쌓인 딕셔너리·리스트 | 한 줄에 JSON 하나 |
| 자료형 | 모두 문자열 | 모두 문자열 | 문자열, 숫자, 불리언, `null`, 리스트, 딕셔너리 | JSON과 같다 |
| 추가 | `"a"`로 한 줄 | `"a"`로 한 행 | 전체를 다시 써야 한다 | `"a"`로 한 줄 |
| 엑셀에서 열기 | | 좋다 | 어렵다 | 어렵다 |
| 어울리는 곳 | 메모, 로그, 프롬프트 템플릿, 문서 | 성적표, 가계부, 평가 결과처럼 열이 정해진 표 | 설정 파일, 프로그램의 저장 파일, API 응답, 구조가 깊은 데이터 | 대화 기록, 학습·평가 데이터, 계속 쌓이는 기록 |

판단이 어려우면 이렇게 생각하자.

- **사람이 엑셀에서 열어 볼** 표 데이터 → CSV
- **프로그램이 저장했다가 다시 읽을** 데이터, 특히 안에 리스트나 딕셔너리가 들어 있으면 → JSON
- **계속 쌓이는** 기록, 하나하나가 JSON 모양이면 → JSONL


- 점수는 정수로 바꾸어 저장한다. JSON에서는 `"85"`가 아니라 `85`가 되어야 한다.
- 평균은 소수점 아래 한 자리로 반올림한다(`round()`).

**3) `parse_answers.py` — LLM의 답 검사하기**

LLM에게 리뷰마다 감정을 `{"sentiment": "positive|negative|neutral", "score": 0~1 사이의 숫자}` 모양으로 답하라고 했더니 다음 답들이 돌아왔다. 올바른 답만 받아들이고, 잘못된 답은 **무엇이 잘못되었는지** 보고하는 프로그램을 만든다. 6장 실습 6-1의 `score_report.py`와 같은 구조다.

```python
answers = [
    '{"sentiment": "positive", "score": 0.92}',
    '```json\n{"sentiment": "negative", "score": 0.15}\n```',
    "{'sentiment': 'neutral', 'score': 0.5}",
    '{"sentiment": "positive"}',
    '{"sentiment": "great", "score": 0.99}',
    "죄송합니다. 이 리뷰는 분석할 수 없습니다.",
    '{"sentiment": "negative", "score": "낮음"}',
    '["positive", 0.8]',
]
```

```
1번: positive (0.92)
2번: negative (0.15)
3번 건너뜀: JSON 형식이 아님 (Expecting property name enclosed in double quotes)
4번 건너뜀: score 항목이 없음
5번 건너뜀: sentiment 값이 잘못됨: 'great'
6번 건너뜀: JSON 형식이 아님 (Expecting value)
7번 건너뜀: score가 0~1 사이의 숫자가 아님: '낮음'
8번 건너뜀: JSON 객체가 아님: list
성공 2건, 실패 6건
```

- 답 하나를 `(sentiment, score)` 튜플로 바꾸는 함수 `parse_answer(text)`를 만든다. 형식에 맞지 않으면 무엇이 잘못되었는지 담은 `ValueError`를 일으킨다. 호출하는 반복문은 `except ValueError as e:` 하나로 모든 실패를 처리한다.
- `JSONDecodeError`는 `ValueError`의 자식이므로 그대로 두어도 반복문에서 잡힌다. 하지만 메시지가 `Expecting value: line 1 column 1 (char 0)`처럼 길고 위치 정보까지 있다. 잡아서 `JSON 형식이 아님 (...)`으로 바꿔 다시 일으키자(6.2.5의 `from e`). 위치 정보를 뺀 메시지만 꺼내려면 예외 객체의 `msg` 속성을 쓴다.
- 2번처럼 코드 블록으로 감싼 답은 받아들인다. 앞뒤 공백을 지운 문자열이 ` ``` `으로 시작하면 첫 줄과 마지막 ` ``` ` 줄을 떼어 내는 함수 `strip_code_fence(text)`를 따로 만들자. `splitlines()`와 슬라이싱, `"\n".join()`을 쓰면 된다.
- `json.loads()`의 결과가 딕셔너리가 아닐 수도 있다(8번). 키를 검사하기 전에 `isinstance()`(4.5.3)로 확인한다.
- `score`가 숫자인지 확인할 때 `isinstance(score, (int, float))`를 쓴다. 그런데 `True`도 이 검사를 통과한다. 불리언은 정수의 자식 클래스이기 때문이다(`isinstance(True, int)`를 확인해 보자). `True`를 점수로 받아들이지 않으려면 어떻게 해야 할까?

## 실습 7-4. 종합 — 도서 대출 관리 프로그램 (파일 저장 버전)

6장 실습 6-3의 도서 대출 관리 프로그램이 데이터를 **파일에 저장하고 불러오도록** 고친다. 지금까지는 소장 도서 목록이 `main()` 안에 코드로 적혀 있었고, 대출 기록은 프로그램을 끝내면 사라졌다. 이번에는 다음과 같이 바꾼다.

**요구 사항**

1. 실습 6-3의 요구 사항을 그대로 지킨다.
2. **`Library`는 파일을 모른다.** `Library` 클래스 안에서는 `open()`, `Path`, `csv`, `json`을 쓰지 않는다. `Library`는 `Book`의 리스트를 받아 만들어지고, 대출 기록을 **딕셔너리의 리스트**로 내보내고(`export_loans()`) 받아들인다(`import_loans()`). 파일을 읽고 쓰는 일은 모듈 수준의 함수(`load_books()`, `load_loans()`, `save_loans()`, `write_report()`)가 한다.
3. 데이터 파일의 경로는 주어진 대로 `DATA_DIR`을 기준으로 한다. 어느 폴더에서 실행하든, VS Code의 ▷ 버튼으로 실행하든 같은 파일을 읽고 써야 한다.
4. **`books.csv`** — `load_books()`가 읽는다.
   - 엑셀에서 고쳐 저장한 파일도 읽을 수 있도록 `encoding="utf-8-sig"`로 연다.
   - 첫 줄이 `code,title,kind`가 아니면, 도서 코드나 제목이 비어 있으면, 도서 코드가 겹치면, `kind`가 `일반`/`참고`가 아니면 `DataFileError`를 일으킨다. 헤더 문제가 아니면 메시지에 **파일의** 몇 번째 줄인지 넣는다. 사서가 편집기나 엑셀에서 그 줄을 바로 찾을 수 있어야 하므로, 빈 줄이 끼어 있어도 실제 줄 번호와 맞아야 한다.
   - CP949로 저장한 파일처럼 UTF-8로 읽을 수 없으면 `DataFileError`를 일으킨다. 메시지로 'CSV UTF-8' 형식으로 저장하라고 안내한다.
   - 파일이 없을 때의 `FileNotFoundError`는 잡지 않는다.
5. **`loans.json`** — `load_loans()`가 읽고 `save_loans()`가 쓴다.
   - 파일이 없으면 대출 기록이 없는 상태로 시작한다(처음 실행).
   - UTF-8로 읽을 수 없으면, JSON 형식이 잘못되었으면, 또는 `import_loans()`가 예외를 일으키면 `DataFileError`로 바꿔 일으킨다. 원래 예외는 `from e`로 연결한다(6.2.5).
   - `import_loans()`는 `"code": null`처럼 JSON 문법으로는 맞지만 자료형이 틀린 값, `"20261114"`처럼 날짜이긴 하지만 `YYYY-MM-DD` 모양이 아닌 값도 거절한다. 이 실습의 실행 예와 "확인할 것"에서 다루는 잘못된 파일(`books.csv`가 없는 경우, 인코딩, JSON 형식, 빠진 키, 자료형, 날짜, 없는 도서, 겹치는 도서)은 모두 **트레이스백이 아니라 안내 메시지로** 끝나야 한다. `loans.json`이 없는 것은 잘못된 파일이 아니라 처음 실행한 정상 상태이므로 안내 없이 대출 기록 0건으로 시작한다. (세상의 모든 잘못된 파일을 막는 것은 목표가 아니다. 예를 들어 기본 설정에서 4,300자리를 넘는 정수가 들어 있으면 `json.load()`가 `JSONDecodeError`가 아닌 `ValueError`를 일으키는데, 이런 극단적인 경우까지 하나하나 대비하다 보면 `except`가 끝없이 늘어난다. 6.2.6에서 말한 대로 예상할 수 있는 실패를 좁게 잡고, 예상하지 못한 것은 트레이스백으로 드러나게 두는 편이 낫다.)
   - `import_loans()`는 기록 하나라도 잘못되면 대출 기록을 **하나도 바꾸지 않아야** 한다(6.2.1의 "바꾸기 전에 검사").
   - `save_loans()`는 `ensure_ascii=False, indent=2`로 저장해 사람이 열어 읽을 수 있게 한다.
6. **`main()`의 시작**
   - `books.csv`가 없으면 `도서 목록 파일이 없습니다: (경로)`를 출력하고 끝낸다. 형식 오류이면 `DataFileError`의 메시지를 출력하고 끝낸다.
   - `loans.json`에 문제가 있으면 `DataFileError`의 메시지와 `파일을 고친 뒤 다시 실행하세요. 기록을 지키기 위해 프로그램을 시작하지 않습니다.`를 출력하고 끝낸다. **빈 대출 기록으로 시작하지 않는다.** 왜 그래야 하는지는 "확인할 것"에서 생각해 본다.
   - 준비가 끝나면 `도서 N권, 대출 기록 M건을 불러왔습니다.`를 출력한다.
7. **저장 시점** — 대출과 반납이 **성공할 때마다** 곧바로 `save_loans()`로 저장한다. 실패했을 때는 저장하지 않는다. 6장에서 성공 메시지를 쓰던 `else` 블록이 저장하기에도 알맞은 곳이다. 종료할 때 한꺼번에 저장하지 않는 이유도 "확인할 것"에서 생각해 본다.
8. **`보고서` 명령** — `write_report()`로 `data/loan_report.csv`를 만들고 `대출 N건을 저장했습니다: (경로)`를 출력한다. 엑셀에서 한글이 깨지지 않게 `utf-8-sig`로 쓴다. 대출 기록이 없어도 헤더만 있는 파일을 만든다.

**힌트**

- 순서는 `DataFileError` 확인 → `load_books()` → `Library.loans()`, `export_loans()` → `save_loans()` → `import_loans()` → `load_loans()` → `write_report()` → `main()`이 좋다. 저장(`save_loans`)을 먼저 만들면 올바른 `loans.json`을 프로그램이 만들어 주므로, 그것을 읽는 쪽을 시험하기 쉽다.
- `load_books()`
  - 두 단계로 나누면 깔끔하다. 첫 단계에서는 파일을 **읽기만** 해서 헤더와 `(줄 번호, 행)`의 리스트를 모은다. 두 번째 단계에서 그것을 검사하고 `Book`을 만든다. CP949 파일은 읽는 도중(`for row in reader`)에 `UnicodeDecodeError`가 나므로, 첫 단계만 `try`로 감싸 `except UnicodeDecodeError as e:`에서 `DataFileError`로 바꾸면 된다. 검사 코드까지 `try` 안에 넣지 않는 것이 6.1.7의 "`try` 블록은 짧게"다.
    ```python
    try:
        with open(path, encoding="utf-8-sig", newline="") as f:
            reader = csv.DictReader(f)
            fieldnames = reader.fieldnames
            rows = []
            for row in reader:
                rows.append((reader.line_num, row))
    except UnicodeDecodeError as e:
        raise DataFileError(path, "...") from e
    ```
  - 헤더 검사는 `fieldnames != ["code", "title", "kind"]`로 한다. 빈 파일이면 `fieldnames`가 `None`이므로 이 검사에 함께 걸린다.
  - 줄 번호는 `enumerate(reader, start=2)`로 세면 안 된다. `DictReader`는 **빈 줄을 건너뛰고**, 큰따옴표 안에 줄바꿈이 있는 값(7.3.2의 영희의 메모)은 **여러 줄을 한 레코드로** 읽는다. 그래서 레코드 수와 파일의 줄 번호가 어긋난다. CSV 읽기 객체의 `line_num` 속성은 지금까지 파일에서 읽은 줄 수, 즉 **방금 읽은 레코드의 마지막 줄 번호**다. 레코드를 꺼낸 직후의 `reader.line_num`을 함께 저장해 두자. (값에 줄바꿈이 들어 있는 레코드라면 그 레코드가 시작한 줄이 아니라 끝난 줄을 가리킨다는 점은 알아 두자.)
  - 값이 모자란 줄(예: `B05`만 있는 줄)을 읽으면 `DictReader`는 빈 칸을 `None`으로 채운다. `None`에는 `strip()`을 할 수 없으므로 `(row["title"] or "").strip()`처럼 쓰면 `None`과 빈 문자열을 함께 처리할 수 있다(2.2.5에서 `or`는 왼쪽이 참이면 오른쪽을 보지 않는다고 배웠다. 사실 `or`는 `True`/`False`가 아니라 **마지막으로 확인한 값**을 돌려준다. 그래서 `None or ""`는 `""`이고, `"B05" or ""`는 `"B05"`다).
  - 겹치는 코드는 지금까지 나온 코드를 집합(3.5)에 모아 두고 검사한다. 6장에서는 이 검사를 `Library.__init__`이 `ValueError`로 했다. 그 검사는 그대로 두되, 이제는 도서 목록이 **파일**에서 오므로 `load_books()`가 먼저 줄 번호와 함께 알려 주어야 한다. 왜 이렇게 바뀌었는지는 "확인할 것"에서 다시 생각한다.
- `export_loans()`와 `import_loans()`는 7.3.7의 `todo_to_dict()`, `todo_from_dict()`와 같은 짝이다. 날짜는 `isoformat()`과 `date.fromisoformat()`으로 바꾼다.
- `import_loans()`는 새 딕셔너리 `loans = {}`에 기록을 모두 만들어 넣은 뒤, **모든 검사가 끝나면** 마지막에 `self._loans = loans`로 한 번에 바꾼다. 중간에 예외가 나면 `self._loans`는 손대지 않은 상태로 남는다. 6장 `borrow()`의 검사(`find()`, `can_borrow()`, 이미 대출 중인지)를 다시 쓰되, "이미 대출 중"은 `self._loans`가 아니라 새로 만드는 `loans`에서 검사한다.
- `import_loans()`에서 `record["code"]`를 `find()`에 넘기기 전에 `isinstance()`로 문자열인지 확인한다. JSON에서는 `"code": null`도 올바른 문법이다. 검사하지 않으면 `find()` 안의 `code.upper()`에서 `AttributeError`가 나는데, 이 예외는 `load_loans()`가 잡는 목록에 없으므로 트레이스백으로 끝난다. 그렇다고 `AttributeError`까지 잡으면 내 코드의 오타로 생긴 `AttributeError`도 데이터 파일 오류로 둔갑한다. 바깥 데이터를 **입구에서** 검사해 `TypeError`로 알리는 편이 정확하다.
- 반납 기한은 조금 까다롭다. `date.fromisoformat()`은 날짜가 아니면 `ValueError`를, 문자열이 아니면(예: `20261114`) `TypeError`를 일으킨다. 그런데 파이썬 3.11부터는 `"20261114"`나 `"2026-W46-6"`(2026년 46번째 주의 토요일) 같은 **다른 ISO 8601 모양도 받아들인다.** 셸에서 `date.fromisoformat("20261114")`를 확인해 보자. `YYYY-MM-DD`만 허용하려면 읽은 날짜를 다시 `isoformat()`으로 바꾼 결과가 원문과 같은지 비교한다.
  ```python
  due_text = record["due"]
  try:
      due = date.fromisoformat(due_text)
  except (TypeError, ValueError):
      due = None
  if due is None or due.isoformat() != due_text:
      raise ValueError(f"반납 기한이 'YYYY-MM-DD' 모양이 아닙니다: {due_text!r}")
  ```
  "날짜가 아니다", "문자열이 아니다", "모양이 다르다"는 사용자에게는 모두 "반납 기한이 잘못되었다"는 같은 문제이므로 하나의 메시지로 모았다.
- `load_loans()`는 두 단계로 나눠 `try`를 쓴다.
  ```python
  try:
      with open(path, encoding="utf-8") as f:
          records = json.load(f)
  except FileNotFoundError:
      return  # 처음 실행
  except UnicodeDecodeError as e:
      raise DataFileError(path, "UTF-8로 읽을 수 없습니다") from e
  except json.JSONDecodeError as e:
      raise DataFileError(path, f"JSON 형식이 아닙니다 ({e})") from e

  try:
      library.import_loans(records)
  except ...  # import_loans()가 일으킬 수 있는 예외들을 DataFileError로 바꾼다
  ```
  `UnicodeDecodeError`와 `JSONDecodeError`는 둘 다 `ValueError`의 자손이지만 서로 부모·자식 관계가 아니므로 순서는 상관없다. `KeyError`의 메시지는 `'who'`처럼 키 이름뿐이라서 그대로 보여 주면 무슨 뜻인지 알기 어렵다. `KeyError`만 따로 잡아 `대출 기록에 'who' 항목이 없습니다`로 바꾸자. 나머지(`TypeError`, `ValueError`, `LibraryError`)는 튜플로 묶어 잡고 `str(e)`를 그대로 쓰면 된다. 두 번째 `try` 블록에는 `import_loans()` 호출 **한 줄만** 넣는다. 6.1.7에서 배운 대로, 넓게 감싸면 내 코드의 버그로 생긴 `TypeError`까지 "데이터 파일 오류"로 둔갑한다.
- `save_loans()`와 `write_report()`는 7.2.3에서 본 대로 `path.parent.mkdir(parents=True, exist_ok=True)`로 폴더를 먼저 준비한다.
- `write_report()`는 `csv.writer`로 헤더 한 줄과 대출 한 건당 한 줄을 쓴다. 대출 목록은 `library.loans()`로 얻는다. `main()`과 마찬가지로 `_loans`에 직접 손대지 않는다.
- `main()`의 시작 부분은 다음 모양이 된다.
  ```python
  try:
      books = load_books(BOOKS_PATH)
  except FileNotFoundError:
      print(f"도서 목록 파일이 없습니다: {BOOKS_PATH}")
      return
  except DataFileError as e:
      print(e)
      return

  library = Library(books)
  # load_loans()도 같은 방법으로
  ```
  함수 안의 `return`은 반환값 없이 함수를 끝낸다(4.1.6). `main()`이 끝나면 프로그램도 끝난다.

- 요구 사항 6에서 `loans.json`에 문제가 있으면 **빈 대출 기록으로 시작하지 않고** 프로그램을 끝내도록 했다. 만약 빈 기록으로 시작한 뒤 사용자가 `대출`을 한 번 하면 어떻게 되는가? 요구 사항 7에 따라 `save_loans()`가 실행될 때 `loans.json`에 있던 기록은 어떻게 되는가? `"w"` 모드의 성질(7.1.5)로 설명해 보자.
- 요구 사항 7에서 `종료`할 때 한꺼번에 저장하지 않고 **바뀔 때마다** 저장하도록 했다. 대출을 몇 건 처리하고 **`대출 완료` 메시지가 나온 뒤에**, `종료`를 입력하지 않고 터미널에서 `Ctrl + C`로 프로그램을 멈춰 보자. 다시 실행하면 기록이 남아 있는가? 종료할 때만 저장하는 방식이었다면 어땠을까? 반대로 바뀔 때마다 저장하는 방식의 단점은 무엇일까?
- 즉시 저장이 지켜 주는 것은 **저장이 끝난 기록**까지다. `save_loans()`는 `"w"` 모드로 여는 순간 기존 내용을 지운다. `json.dump()`가 끝나기 전에 프로그램이 끊기거나 쓰기가 실패하면(디스크가 가득 찬 경우 등) `loans.json`은 빈 파일이나 반만 쓰인 파일로 남는다. 일부러 재현해 보자. 이 실험은 **`loans.json`의 내용을 실제로 지운다.** 먼저 VS Code 탐색기에서 `loans.json`을 복사해 `loans_backup.json`으로 저장해 두자. 그다음 `save_loans()`의 `json.dump(...)` 줄 바로 위에 `raise OSError("디스크가 가득 찼다고 치자")`를 잠시 넣고 대출을 한 번 한 뒤, `loans.json`을 열어 보자. 다음 실행에서 어떤 메시지가 나오는가? 이 문제는 아래 "더 해 보기"의 **안전하게 저장하기**가 해결한다. 확인이 끝나면 넣은 줄을 지우고, `loans.json`을 지운 뒤 `loans_backup.json`의 이름을 `loans.json`으로 바꿔 되돌린다.
- 6장에서는 겹치는 도서 코드를 **프로그래머의 실수**로 보고 `ValueError`로 알렸고, `main()`에서 잡지 않았다. 이번에는 같은 문제를 `load_books()`가 `DataFileError`로 알리고 `main()`이 잡아서 메시지로 보여 준다. 무엇이 달라졌기에 판단이 바뀌었는가? 6.2.6의 "대처할 수 있는 곳에서 잡는다"로 설명해 보자. (도서 목록을 고칠 사람이 누구인지 생각해 보자.)
- `Library`가 파일을 모르게 만든 덕분에 무엇을 할 수 있는가? 나중에 대출 기록을 JSON 파일 대신 데이터베이스에 저장하기로 했다면 어느 함수를 고쳐야 하는가? `Library`는 고쳐야 하는가? 셸에서 `lib = Library(load_books(BOOKS_PATH))`를 만든 뒤 `lib.import_loans([{"code": "B01", "who": "철수", "due": "2026-11-14"}])`처럼 **파일 없이도** `Library`를 시험할 수 있다는 것도 확인해 보자(`main()`을 잠시 주석 처리하고 `python -i library.py`로 들어간다).

**더 해 보기 (선택)**

- **안전하게 저장하기**: `save_loans()`가 `loans.json`을 `"w"`로 여는 순간 기존 내용은 지워진다. 그 뒤 `json.dump()` 도중에 문제가 생기면 반만 쓰인 파일이 남는다. 이를 막는 흔한 방법은 **임시 파일에 먼저 다 쓴 뒤, 다 쓰고 나서 이름을 바꾸는** 것이다. `tmp = path.with_suffix(".tmp")`에 저장한 뒤 `tmp.replace(path)`로 바꿔 보자. `Path.replace()`는 같은 이름의 파일이 있으면 덮어쓰면서 이름을 바꾸고, 이 바꾸기는 한 번에 일어나므로 "반쯤 바뀐" 상태가 생기지 않는다.
- **대출 이력 남기기**: 대출과 반납이 일어날 때마다 `data/history.jsonl`에 한 줄씩 기록을 덧붙인다(7.3.8). 기록에는 `{"action": "대출", "code": "B01", "who": "철수", "date": "2026-10-31"}`처럼 무슨 일이 언제 있었는지 담는다. `loans.json`은 "지금 상태", `history.jsonl`은 "지금까지 일어난 일"이다. 그다음 `이력 철수` 명령으로 그 사람의 대출·반납 이력을 보여 주자.
- **도서 추가**: `추가 코드 제목` 명령으로 일반 도서를 추가하고 `books.csv`에 반영한다. 이미 있는 코드이면 거절한다. CSV 끝에 한 행을 덧붙일 것인가(`"a"`), 전체를 다시 쓸 것인가(`"w"`)? VS Code에서 마지막 줄 뒤에 Enter 없이 저장한 `books.csv`라면 `"a"`로 덧붙인 행이 마지막 행 뒤에 그대로 붙어 버린다는 점(7.1.6)도 생각해 보자.

## 정리

| 항목 | 핵심 |
|---|---|
| 파일 | 프로그램이 끝나도 남는 데이터. 시작할 때 읽고, 메모리에서 처리하고, 남길 것을 쓴다 |
| 텍스트 파일 | 내용은 하나의 긴 문자열. 줄마다 끝에 `\n` |
| `open(경로, 모드, encoding="utf-8")` | 파일 객체를 돌려준다. 텍스트 파일은 **언제나** `encoding="utf-8"` |
| `read()`, `write()` | 전체를 문자열 하나로 읽는다. 쓴 글자 수를 돌려주고 줄을 바꿔 주지 않는다. `print(..., file=f)`는 줄을 바꿔 준다 |
| 닫기 | 쓴 내용은 버퍼에 있다가 닫을 때 저장된다. 닫지 않으면 저장 안 됨, 자원 낭비, Windows에서 잠김 |
| `with open(...) as f:` | 블록이 끝나면(예외가 나도) 자동으로 닫는다. `try`/`finally`를 대신한다. 파일은 언제나 `with`로 |
| 모드 | `"r"` 읽기(기본), `"w"` **지우고** 쓰기, `"a"` 뒤에 추가, `"x"` 새로 만들기(있으면 `FileExistsError`) |
| 줄 단위 | `for line in f`(한 줄씩, 큰 파일도 OK), `read().splitlines()`(줄 리스트, `\n` 제거). 줄 끝은 `strip()`/`rstrip("\n")` |
| 인코딩 | 글자 ↔ 바이트 규칙. UTF-8(표준, 한글 3바이트), cp949(옛 한국어 Windows). 맞지 않으면 `UnicodeDecodeError`(`ValueError` → `UnicodeError`의 자식). 생략하면 운영체제마다 달라진다(3.15부터 UTF-8) |
| 파일 예외 | `FileNotFoundError`, `FileExistsError`, `IsADirectoryError`, `PermissionError` ⊂ `OSError`. `with` 전체를 `try`로 감싼다 |
| 없는 파일 | 사용자가 지정한 파일 → 알린다. 프로그램의 저장 파일이 처음에 없음 → 정상(빈 값). 꼭 필요한 파일 → 알리고 끝낸다 |
| `Path` | `from pathlib import Path`. `/`로 잇는다. `name`, `stem`, `suffix`, `parent`, `with_suffix()`. 불변. 주소일 뿐 |
| 위치 | `Path.cwd()`(현재 디렉터리), `Path.home()`, `absolute()`, `resolve()` |
| 확인 | `exists()`, `is_file()`, `is_dir()` |
| 읽고 쓰기 | `open(Path)`도 된다. `read_text()`/`write_text()`는 한 번에(인코딩 지정) |
| 폴더 | `mkdir(parents=True, exist_ok=True)`, `iterdir()`(순서 없음 → `sorted`), `glob("*.txt")`, `rglob()`(하위 폴더까지) |
| 지우기 | `unlink()`(파일), `rmdir()`(빈 폴더). 휴지통을 거치지 않는다 |
| 실행 위치 문제 | 상대 경로는 **현재 디렉터리** 기준. 실행 위치, VS Code 터미널 상태에 따라 달라진다 |
| `Path(__file__).parent` | 스크립트가 있는 폴더. 프로그램과 한 묶음인 파일은 이것을 기준으로. 사용자가 지정한 파일은 상대 경로 그대로 |
| CSV 읽기 | `csv.reader`(행 = 리스트), `csv.DictReader`(행 = 딕셔너리, `fieldnames`). **값은 모두 문자열** |
| CSV 쓰기 | `csv.writer`(`writerow`, `writerows`), `csv.DictWriter(fieldnames=...)`(`writeheader`). 쉼표·따옴표·줄바꿈은 알아서 처리 |
| CSV 옵션 | 항상 `newline=""`. 엑셀용·읽기용은 `utf-8-sig`(BOM). BOM을 `utf-8`로 읽으면 첫 열 이름에 `'\ufeff'` |
| JSON | 객체·배열·문자열·숫자·`true`/`false`·`null`. 키는 문자열만, 큰따옴표만 |
| `dumps`/`loads` | 문자열과. `ensure_ascii=False`(한글 그대로), `indent=2`(보기 좋게). `str(dict)`는 JSON이 아니다 |
| `dump`/`load` | 파일과. 자료형이 함께 저장된다 |
| `JSONDecodeError` | JSON 규칙에 맞지 않음(`ValueError`의 자식). 작은따옴표, 끝의 쉼표, 코드 블록으로 감싼 LLM 답 |
| 달라지는 값 | 정수 키 → 문자열, 튜플 → 리스트. `date`, `set`, 객체는 `TypeError` → `isoformat()`/`fromisoformat()` 등으로 직접 |
| 데이터 클래스 | `to_dict`/`from_dict` 함수를 짝으로. 파일 형식에 관한 지식을 한곳에. CSV의 `"False"`는 참이다 |
| 입구에서 검사 | 파일은 바깥 데이터. 읽는 자리에서 검사하고, 사용자에게는 무엇이 몇 번째에서 잘못되었는지 |
| JSONL | 한 줄에 JSON 하나. `"a"`로 추가, `for line in f` + `json.loads()`. LLM 데이터·대화 기록 |
| 형식 고르기 | 엑셀에서 볼 표 → CSV, 프로그램이 저장·복원할 구조 → JSON, 계속 쌓이는 기록 → JSONL |
