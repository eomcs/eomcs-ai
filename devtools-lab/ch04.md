# 4장. VS Code

[개발 도구](README.md) 과정의 네 번째 장이다. 2·3장에서는 터미널에서 명령을 하나씩 입력하고, 잇고, 읽는 법을 익혔다. 이 장에서는 그 터미널을 품고 있는 **편집기**를 손에 익힌다. 기초 과정에서 VS Code로 파일을 만들고, ▷ 버튼으로 실행하고, 중단점을 하나 찍어 보았다. 이번에는 매일 쓰는 도구답게 **설정을 프로젝트에 담고, 여러 파일에 걸친 코드를 빠르게 읽고 고치고, 디버거로 원인을 찾고, AI가 고친 코드를 검토하는** 데까지 간다.

- **작업 공간** — 폴더 단위로 열기, 화면 구성, 명령 팔레트, 단축키와 단축키 찾는 방법
- **설정과 확장** — 사용자 설정과 작업 공간 설정, 설정 화면과 JSON, 파이썬 확장, 저장할 때 자동 포맷, 권장 확장 알리기, 저장소에 올릴 설정
- **편집 기술** — 줄 단위 편집, 다중 커서, 파일 빠르게 열기, 전체 검색·바꾸기와 정규 표현식, 정의로 이동·참조 찾기·이름 바꾸기
- **디버거 더 쓰기** — `launch.json`으로 실행 설정 저장하기, 조사식과 호출 스택, 조건부 중단점과 로그 지점, 예외에서 멈추기, 모듈로 실행하기
- **통합 터미널** — VS Code 안의 터미널이 바깥 터미널과 다를 수 있는 이유, 인터프리터와 터미널 가상환경 맞추기
- **AI 코딩 도구와 함께 쓰기** — 인라인 제안과 채팅, AI가 고친 파일을 비교 화면으로 검토하기, 프로젝트 규칙을 적어 두는 파일

VS Code의 Git 기능(소스 제어 화면, 병합 편집기)은 이 장에서 다루지 않는다. 1장에서 말한 대로 Git 명령을 배운 뒤 5~8장에서 명령과 나란히 본다.

## 학습 목표

이 장을 마치면 다음을 할 수 있다.

- 터미널에서 `code` 명령으로 프로젝트 폴더를 열고, VS Code가 "폴더"를 작업의 기준으로 삼는다는 것을 설명할 수 있다.
- 화면의 각 부분(액티비티 막대, 사이드바, 편집기, 패널, 상태 표시줄)의 이름과 역할을 말하고, 상태 표시줄에서 인터프리터·인코딩·줄 끝 문자·들여쓰기를 읽을 수 있다.
- 명령 팔레트로 기능을 찾아 실행하고, 모르는 기능의 단축키를 스스로 찾을 수 있다.
- 사용자 설정과 작업 공간 설정(`.vscode/settings.json`)을 구별하고, 설정 화면과 JSON 파일이 같은 설정을 보여 준다는 것을 확인할 수 있다.
- 파이썬 개발에 필요한 확장을 설치하고, 저장할 때 자동 포맷과 권장 확장 목록(`.vscode/extensions.json`)을 프로젝트에 담을 수 있다.
- 저장소에 올릴 설정과 올리지 않을 설정을 구별하고, 처음 받은 폴더를 제한 모드로 열어야 하는 이유를 설명할 수 있다.
- 다중 커서, 줄 이동·복제, 파일 빠르게 열기, 전체 검색·바꾸기(정규 표현식 포함)로 반복 편집을 빠르게 할 수 있다.
- 정의로 이동·참조 찾기·이름 바꾸기(`F2`)로 여러 파일에 걸친 코드를 읽고 안전하게 고칠 수 있다.
- `launch.json`에 명령행 인자·환경 변수·작업 폴더를 정해 디버그 실행 설정을 저장하고, 모듈 실행(`python -m`) 설정을 만들 수 있다.
- 조사식·호출 스택·디버그 콘솔·조건부 중단점·로그 지점·예외 중단점으로 버그의 원인을 찾을 수 있다.
- ▷ 버튼, 디버거, 통합 터미널, 바깥 터미널이 각각 어떤 파이썬과 환경으로 실행되는지 확인하고 맞출 수 있다.
- AI 코딩 도구가 고친 파일을 비교 화면에서 변경 덩어리 단위로 검토하고, 필요한 부분만 받아들인 뒤 검사로 확인할 수 있다.
- 프로젝트 규칙을 적어 두는 AI 지침 파일(`AGENTS.md`, `CLAUDE.md` 등)의 역할과 한계를 설명할 수 있다.

## 실습 환경

2·3장과 같다. macOS는 zsh, Windows는 **PowerShell 7**이다. VS Code의 통합 터미널도 이 셸이어야 한다(1.2.4). 이 장의 단축키는 macOS와 Windows를 `Cmd/Ctrl+Shift+P`처럼 함께 적는다. macOS는 `Cmd`, Windows는 `Ctrl`을 누르라는 뜻이다. 두 운영체제의 단축키가 아예 다르면 `Option+↑`(macOS) / `Alt+↑`(Windows)처럼 따로 적는다. macOS의 `Option` 키는 Windows의 `Alt` 키 자리에 있다.

VS Code의 화면 글자는 영어로 적고, 필요하면 괄호 안에 한국어 UI의 이름을 함께 적는다. 한국어 UI에서도 명령 팔레트에 영어 명령 이름을 입력하면 찾아 준다. VS Code는 거의 매달 새 버전이 나오므로 메뉴의 위치나 이름이 교재와 조금 다를 수 있다. 그럴 때는 명령 팔레트에서 이름으로 찾는다(4.1.3).

실습 폴더는 `~/devtools-lab/ch04`이다.

```
cd ~/devtools-lab
mkdir ch04
cd ch04
```

실습 파일은 이번에도 파이썬 스크립트로 한 번에 만든다. VS Code로 `ch04` 폴더를 열고(`code .`), `make_files.py`를 다음과 같이 만든다. 길지만 대부분은 실습 프로젝트의 소스 코드다. 코드를 그대로 옮겨 적기 어려우면 문자열 부분은 천천히 확인하며 붙여 넣는다.

````python
# make_files.py — 4장 실습 파일을 만든다
import random
from pathlib import Path

random.seed(4)
base = Path("practice")


def write(path, text):
    path.parent.mkdir(parents=True, exist_ok=True)
    path.write_text(text, encoding="utf-8", newline="\n")


# 1. 주문 계산 프로그램 — 여러 파일로 나뉜 작은 프로젝트(디버깅·코드 읽기 실습용)
shop = base / "shop"
write(
    shop / "README.md",
    """# 주문 계산

주문 파일(CSV)을 읽어 결제 금액을 계산한다.

## 실행

```
python main.py orders/small.csv
```

## 할인 규칙

- 묶음 할인: 한 상품을 10개 이상 사면 그 상품 금액의 10%를 깎는다(원 단위 미만 버림).
- 쿠폰 할인: 환경 변수 `SHOP_COUPON_RATE`(예: `0.05`)가 있으면, 묶음 할인을 뺀 금액에
  그 비율을 곱한 만큼 더 깎는다(원 단위 미만 버림).

## 기대하는 결과

쿠폰 할인: -0원

```

## 시험

```
python check_orders.py
```
""",
)
write(
    shop / "main.py",

write(
    shop / "shop" / "models.py",
    '''"""주문 데이터의 모양."""

from dataclasses import dataclass


@dataclass
class OrderLine:
    """주문 한 줄: 상품 이름, 단가, 수량."""

    name: str
    price: int
    qty: int

    def subtotal(self) -> int:
        """할인 전 금액."""
        return self.price * self.qty
''',
)
write(
    shop / "shop" / "loader.py",
    '''"""주문 CSV 파일을 읽는다."""

import csv
from pathlib import Path

from shop.models import OrderLine

HEADER = ["name", "price", "qty"]


def parse_line(row: dict[str, str]) -> OrderLine:
    """CSV 한 줄(딕셔너리)을 OrderLine으로 바꾼다."""
    return OrderLine(
        name=row["name"].strip(),
        price=int(row["price"]),
        qty=int(row["qty"]),
    )


def load_orders(path: Path) -> list[OrderLine]:
    """주문 파일을 읽어 OrderLine 목록을 돌려준다."""
    with path.open(encoding="utf-8", newline="") as f:
        reader = csv.DictReader(f)
        if reader.fieldnames != HEADER:
            raise ValueError(f"머리글이 {HEADER}가 아닙니다: {reader.fieldnames}")
        return [parse_line(row) for row in reader]
''',
)
write(
    shop / "shop" / "pricing.py",
    '''"""할인 규칙."""

import os

from shop.models import OrderLine

BULK_QTY = 10  # 이 수량 이상이면 묶음 할인
BULK_RATE = 0.1  # 묶음 할인율


def coupon_rate() -> float:
    """환경 변수 SHOP_COUPON_RATE에서 쿠폰 할인율을 읽는다. 없으면 0."""
    return float(os.getenv("SHOP_COUPON_RATE", "0"))


def line_discount(line: OrderLine) -> int:
    """주문 한 줄의 묶음 할인 금액."""
    if line.qty > BULK_QTY:
        return int(line.subtotal() * BULK_RATE)
    return 0


def summarize(lines: list[OrderLine]) -> dict[str, int]:
    """상품 금액, 묶음 할인, 쿠폰 할인, 결제 금액을 계산한다."""
    gross = sum(line.subtotal() for line in lines)
    bulk = sum(line_discount(line) for line in lines)
    coupon = int((gross - bulk) * coupon_rate())
    total = gross - bulk - coupon
    return {"gross": gross, "bulk": bulk, "coupon": coupon, "total": total}
''',
)

    shop / "shop" / "cli.py",
    '''"""명령행에서 주문 파일을 받아 결제 금액을 보여 준다."""

import sys
from pathlib import Path

from shop.loader import load_orders
from shop.pricing import summarize

USAGE = "사용법: python main.py 주문파일.csv"


def won(amount: int) -> str:
    """금액을 '1,234원' 모양으로 돌려준다."""
    return f"{amount:,}원"


def main() -> None:
    """명령행 인자로 받은 주문 파일의 결제 금액을 출력한다."""
    if len(sys.argv) != 2:
        print(USAGE, file=sys.stderr)
        sys.exit(2)
    path = Path(sys.argv[1])
    try:
        lines = load_orders(path)
    except FileNotFoundError:
        print(f"파일이 없습니다: {path}", file=sys.stderr)
        sys.exit(1)
    result = summarize(lines)
    print(f"주문 파일: {path.name} (주문 {len(lines)}줄)")
    print(f"상품 금액: {won(result['gross'])}")
    print(f"묶음 할인: -{won(result['bulk'])}")
    print(f"쿠폰 할인: -{won(result['coupon'])}")
    print(f"결제 금액: {won(result['total'])}")
''',
)

print("모두 통과" if failed == 0 else f"{failed}건 실패")

''',
)

## 4.1 작업 공간

### 4.1.1 폴더 단위로 열기 — `code` 명령

기초 과정에서 "VS Code는 폴더 단위로 작업한다. 파일 하나만 열지 말고 폴더 전체를 열자"고 했다. VS Code에서 연 폴더를 **작업 공간**(workspace, 한국어 UI는 "작업 영역")이라고 한다. 작업 공간은 단순히 "왼쪽에 보이는 파일 목록"이 아니라, VS Code의 많은 기능이 기준으로 삼는 **뿌리 폴더**다.

| 기능 | 작업 공간 폴더를 어떻게 쓰나 |
|---|---|
| 검색(`Cmd/Ctrl+Shift+F`) | 이 폴더 아래만 찾는다 |
| 파일 빠르게 열기(`Cmd/Ctrl+P`) | 이 폴더 아래의 파일 이름으로 찾는다 |
| 통합 터미널 | 새 터미널이 이 폴더에서 시작한다 |
| 작업 공간 설정 | 이 폴더의 `.vscode/settings.json`을 읽는다(4.2) |
| 디버거 | `${workspaceFolder}`가 이 폴더이고, 실행할 때의 작업 폴더도 기본으로 이 폴더다(4.4) |
| 인터프리터 선택 | 폴더마다 따로 기억한다. 폴더 바로 아래의 `.venv`를 찾아 준다(4.5) |
| 정의로 이동·이름 바꾸기 | 이 폴더를 프로젝트의 뿌리로 보고 `import`를 해석한다(4.3) |

그래서 **어느 폴더를 여느냐**가 중요하다. 기초 과정 9.2.4에서 "프로젝트 폴더를 VS Code 창 하나로 따로 연다"고 한 것도 이 때문이다. 홈 폴더처럼 너무 위의 폴더를 열면 검색이 느려지고 엉뚱한 파일이 섞이며, 파일 하나만 열면 위의 기능 대부분이 동작하지 않는다.

터미널에서는 `code` 명령으로 연다. 1.2.6에서 설치를 확인했다. macOS에서 `command not found: code`가 나오면 VS Code의 명령 팔레트에서 `Shell Command: Install 'code' command in PATH`를 실행하고 터미널을 새로 연다.

| 명령 | 하는 일 |
|---|---|
| `code .` | 현재 폴더를 연다 |
| `code 폴더` | 그 폴더를 연다 |
| `code 파일` | 파일을 연다. 파일이 없으면 새 파일로 열어 준다(저장해야 만들어진다) |
| `code -n 폴더` | 새 창으로 연다(`--new-window`) |
| `code -r 폴더` | 지금 창에서 연다(`--reuse-window`) |
| `code -g 파일:줄` | 그 파일의 그 줄로 바로 간다(`--goto`) |
| `code --diff 파일1 파일2` | 두 파일을 비교 화면으로 연다(4.6) |
| `code --install-extension 확장ID` | 확장을 설치한다(4.2.3) |
| `code --help` | 모든 옵션을 본다 |

`shop` 프로젝트를 새 창으로 연다. 지금 `practice/shop` 폴더에 있다면 다음과 같다.

```
code .
```

`code -g`는 오류 메시지에서 파일과 줄 번호를 보았을 때 편하다. 3장에서 `grep -rn`이 `shop/pricing.py:18:` 같은 결과를 냈다면 `code -g shop/pricing.py:18`로 그 줄을 바로 연다.

> **처음 여는 폴더 — "이 폴더의 작성자를 신뢰하십니까?"**
> 폴더를 처음 열면 VS Code가 이 폴더의 파일 작성자를 신뢰하는지 묻는 창을 띄울 수 있다. 직접 만든 폴더라면 신뢰한다고 답한다. 인터넷에서 내려받은 저장소처럼 출처를 모르는 폴더라면 신뢰하지 않는다고 답해 **제한 모드**로 연다. 이유는 4.2.7에서 설명한다.

### 4.1.2 화면 구성

VS Code 창은 다섯 부분으로 나뉜다.

```
┌──┬──────────────┬──────────────────────────────────────┐
│  │              │  main.py   pricing.py ×               │ ← 편집기 탭
│액│   사이드바    │                                        │
│티│  (탐색기,     │              편집기                     │
│비│   검색 등)    │                                        │
│티│              ├──────────────────────────────────────┤
│막│              │  문제  출력  디버그 콘솔  터미널          │ ← 패널
│대│              │  $ python main.py orders/small.csv     │
├──┴──────────────┴──────────────────────────────────────┤
│ ⊗0 ⚠0             줄 18, 열 9  공백: 4  UTF-8  LF  Python 3.13.2 ('.venv') │ ← 상태 표시줄
└──────────────────────────────────────────────────────────┘
```

**액티비티 막대**(Activity Bar)는 맨 왼쪽의 아이콘 줄이다. 누르면 사이드바의 내용이 바뀐다. 같은 아이콘을 한 번 더 누르면 사이드바가 접힌다.

| 아이콘 | 이름 | 단축키 | 하는 일 | 이 과정에서 |
|---|---|---|---|---|
| 종이 두 장 | 탐색기(Explorer) | `Cmd/Ctrl+Shift+E` | 파일·폴더 목록, 열린 편집기, 개요(Outline), 타임라인 | 이 장 |
| 돋보기 | 검색(Search) | `Cmd/Ctrl+Shift+F` | 작업 공간 전체 검색·바꾸기 | 4.3.4 |
| 갈래 모양 | 소스 제어(Source Control) | `Ctrl+Shift+G` | Git 변경 보기·커밋 | 5~8장 |
| ▷와 벌레 | 실행 및 디버그(Run and Debug) | `Cmd/Ctrl+Shift+D` | 디버그 실행 설정 고르기, 변수·조사식·호출 스택 | 4.4 |
| 네모 블록 | 확장(Extensions) | `Cmd/Ctrl+Shift+X` | 확장 찾기·설치·관리 | 4.2.3 |

확장을 설치하면 아이콘이 늘어난다. Python 확장을 설치하면 파이썬 환경을 관리하는 아이콘이, 테스트 기능이 있는 확장을 설치하면 시험관 모양의 테스트 아이콘이 생긴다(테스트 탐색기는 중급 과정에서 쓴다). AI 코딩 도구는 창 오른쪽에 **보조 사이드바**(Secondary Side Bar)를 열어 채팅 화면을 보여 주는 경우가 많다(4.6).

**사이드바**(Side Bar)는 `Cmd/Ctrl+B`로 보이고 숨긴다. 편집기를 넓게 쓰고 싶을 때 쓴다.

**편집기**(Editor)는 파일을 여는 곳이다. 탭 하나가 파일 하나다. 탭을 옆으로 끌거나 `Cmd/Ctrl+\`를 누르면 편집기를 **분할**해서 두 파일을 나란히 볼 수 있다. 분할된 각 영역을 편집기 그룹이라고 한다.

> **기울어진 글씨의 탭 — 미리보기 모드**
> 탐색기에서 파일을 **한 번** 클릭하면 탭 제목이 기울어진 글씨(이탤릭)로 열린다. **미리보기 탭**이다. 다른 파일을 한 번 클릭하면 새 탭이 생기지 않고 그 자리의 내용이 바뀐다. 여러 파일을 훑어볼 때 탭이 쌓이지 않게 하려는 기능이다. 계속 열어 두려면 파일을 **두 번** 클릭하거나, 탭 제목을 두 번 클릭하거나, 내용을 고친다. "방금 열어 둔 파일이 사라졌다"면 대개 이것이다. 이 동작이 싫으면 설정 `workbench.editor.enablePreview`를 끈다(설정 바꾸는 법은 4.2).

> **탭의 ● 표시 — 저장했나?**
> 파일을 고치고 저장하지 않으면 탭의 `×` 자리에 `●`가 보인다. 터미널에서 실행하는 `python main.py`는 **디스크에 저장된 파일**을 읽으므로, 저장하지 않은 변경은 반영되지 않는다. "고쳤는데 결과가 그대로"라면 먼저 `●`를 확인한다. 디버거(`F5`)는 시작하기 전에 열린 편집기를 저장하는 것이 기본 설정이다(`debug.saveBeforeStart`). 저장을 잊는 일이 잦으면 설정 `files.autoSave`를 `afterDelay`로 바꾸어 자동 저장을 켤 수 있다. 다만 이렇게 자동으로 저장될 때는 저장할 때 실행되는 포맷(4.2.4)이 동작하지 않고, `Cmd/Ctrl+S`로 직접 저장할 때만 동작한다. 입력하는 도중에 코드 모양이 바뀌지 않게 하려는 것이다.

**패널**(Panel)은 아래쪽 영역이다. 탭이 네 개 있다.

| 탭 | 하는 일 |
|---|---|
| 문제(Problems) | Pylance·Ruff 같은 확장이 찾은 오류와 경고 목록(4.3.7) |
| 출력(Output) | 확장들이 남기는 기록. 오른쪽 목록에서 확장을 고른다. 확장이 이상하게 동작할 때 여기를 본다 |
| 디버그 콘솔(Debug Console) | 디버깅 중에 식을 계산하고, 로그 지점의 출력을 본다(4.4) |
| 터미널(Terminal) | 통합 터미널(4.5) |

`` Ctrl+` ``(macOS와 Windows 모두 `Ctrl`)로 터미널 패널을 열고 닫는다. 패널 전체는 `Cmd/Ctrl+J`로 보이고 숨긴다.

**상태 표시줄**(Status Bar)은 맨 아래 줄이다. 작아서 지나치기 쉽지만 **지금 이 파일과 이 작업 공간의 상태**가 다 모여 있다. 대부분 누르면 바꿀 수 있다.

| 항목 | 예 | 뜻 | 누르면 |
|---|---|---|---|
| 오류·경고 수 | `⊗ 0 ⚠ 2` | 문제 패널의 개수 | 문제 패널이 열린다 |
| 커서 위치 | `줄 18, 열 9` (Ln 18, Col 9) | 커서가 있는 줄과 칸 | 줄 번호로 이동(4.3.3) |
| 들여쓰기 | `공백: 4` (Spaces: 4) | Tab 키가 넣는 것 | 들여쓰기 방식을 바꾼다 |
| 인코딩 | `UTF-8` | 이 파일을 읽고 저장하는 인코딩 | 다른 인코딩으로 다시 열거나 저장한다 |
| 줄 끝 문자 | `LF` 또는 `CRLF` | 줄바꿈 문자(3.6.1의 상자) | LF와 CRLF를 바꾼다 |
| 언어 모드 | `Python` | 이 파일을 어떤 언어로 보는지 | 언어를 바꾼다 |
| 인터프리터 | `3.13.2 ('.venv': venv)` | 이 작업 공간에서 쓸 파이썬(4.5) | 인터프리터를 고른다 |

1장에서 Windows의 PowerShell 5.1이 만든 파일이 UTF-16으로 저장된 일, 3장에서 CRLF로 저장된 셸 스크립트가 macOS에서 실행되지 않은 일을 보았다. 그런 파일을 VS Code로 열면 상태 표시줄에 `UTF-16 LE`, `CRLF`가 보인다. 파일이 이상하게 동작하면 상태 표시줄부터 읽는 습관을 들인다. 5장에서 Git을 쓰기 시작하면 여기에 지금 브랜치의 이름도 나타난다.

### 4.1.3 명령 팔레트

VS Code의 거의 모든 기능은 **명령**(command)이다. 메뉴, 버튼, 단축키는 모두 명령을 실행하는 서로 다른 방법일 뿐이다. 그 명령을 이름으로 찾아 실행하는 곳이 **명령 팔레트**(Command Palette)다.

`Cmd/Ctrl+Shift+P`(또는 `F1`)를 누르면 화면 위쪽에 입력 칸이 열리고 맨 앞에 `>`가 들어 있다. 이름의 일부를 입력하면 맞는 명령이 나온다. 낱말의 순서나 띄어쓰기가 정확하지 않아도 된다.

- `select interpreter` → `Python: Select Interpreter`
- `terminal default` → `Terminal: Select Default Profile`
- `settings json` → `Preferences: Open User Settings (JSON)`
- `zoom` → `View: Zoom In`, `View: Zoom Out`

명령 이름 오른쪽에는 **단축키**가 있으면 함께 보인다. 명령 팔레트로 몇 번 실행하다가 단축키가 눈에 익으면 단축키로 넘어가면 된다. 최근에 실행한 명령은 목록 맨 위에 나온다.

명령 팔레트의 입력 칸은 맨 앞 글자에 따라 하는 일이 달라진다. `Cmd/Ctrl+P`(4.3.3)는 같은 입력 칸을 `>` **없이** 연다.

| 맨 앞 글자 | 하는 일 | 예 |
|---|---|---|
| (없음) | 파일 이름으로 찾아 열기 | `pricing` |
| `>` | 명령 실행 | `>format document` |
| `@` | 지금 파일 안의 함수·클래스로 이동 | `@summarize` |
| `#` | 작업 공간 전체의 함수·클래스로 이동 | `#load_orders` |
| `:` | 줄 번호로 이동 | `:18` |
| `?` | 이 입력 칸에서 쓸 수 있는 글자 목록 | `?` |

"이런 기능이 있을 것 같은데 어디 있지?" 싶을 때는 메뉴를 뒤지기 전에 명령 팔레트에 떠오르는 낱말을 입력해 본다. 예를 들어 줄을 정렬하고 싶으면 `sort`, 대문자로 바꾸고 싶으면 `upper`를 입력한다. 2장에서 터미널 명령을 `--help`로 찾았듯이, VS Code의 기능은 명령 팔레트로 찾는다.

### 4.1.4 자주 쓰는 단축키와 단축키 찾는 방법

단축키를 처음부터 다 외울 필요는 없다. 아래 표의 화면 단축키부터 손에 익히고, 편집 단축키(4.3)와 디버그 단축키(4.4)는 각 절에서 익힌다.

| 하는 일 | macOS | Windows |
|---|---|---|
| 명령 팔레트 | `Cmd+Shift+P` | `Ctrl+Shift+P` |
| 파일 빠르게 열기 | `Cmd+P` | `Ctrl+P` |
| 설정 | `Cmd+,` | `Ctrl+,` |
| 단축키 목록(편집기) | `Cmd+K` 다음 `Cmd+S` | `Ctrl+K` 다음 `Ctrl+S` |
| 사이드바 보이기·숨기기 | `Cmd+B` | `Ctrl+B` |
| 패널 보이기·숨기기 | `Cmd+J` | `Ctrl+J` |
| 터미널 열고 닫기 | `` Ctrl+` `` | `` Ctrl+` `` |
| 새 터미널 | `` Ctrl+Shift+` `` | `` Ctrl+Shift+` `` |
| 편집기 분할 | `Cmd+\` | `Ctrl+\` |
| 탭 닫기 | `Cmd+W` | `Ctrl+W` |
| 닫은 탭 다시 열기 | `Cmd+Shift+T` | `Ctrl+Shift+T` |
| 최근 연 탭 사이 이동 | `Ctrl+Tab` | `Ctrl+Tab` |
| 글자 크게·작게 | `Cmd+=`, `Cmd+-` | `Ctrl+=`, `Ctrl+-` |
| 새 창 | `Cmd+Shift+N` | `Ctrl+Shift+N` |

`Cmd+K` 다음 `Cmd+S`처럼 두 번 누르는 단축키를 **코드**(chord)라고 한다. 첫 키를 누르면 상태 표시줄에 두 번째 키를 기다린다는 표시가 나온다.

**모르는 단축키를 찾는 방법**은 세 가지다.

1. **명령 팔레트에서 본다.** 명령 이름 오른쪽에 단축키가 보인다(4.1.3).
2. **단축키 편집기에서 찾는다.** `Cmd/Ctrl+K` 다음 `Cmd/Ctrl+S`로 연다. 검색 칸에 명령 이름(`rename`)을 입력하면 그 명령의 단축키가, 검색 칸 오른쪽의 키보드 아이콘(Record Keys)을 누르고 키를 누르면 **그 키에 연결된 명령**이 나온다. "실수로 눌렀더니 이상한 일이 생겼다"면 이 방법으로 무슨 명령이었는지 확인한다. 단축키를 바꾸고 싶으면 그 줄을 두 번 클릭해 새 키를 누른다.
3. **단축키 참고표를 본다.** 메뉴의 Help → Keyboard Shortcuts Reference(도움말 → 바로 가기 키 참조)를 누르면 운영체제별 단축키 한 장짜리 PDF가 열린다. 인쇄해 두기 좋다.

> **단축키가 동작하지 않을 때**
> 단축키는 **어디에 초점이 있느냐**에 따라 다르게 동작한다. 단축키 편집기의 "When"(시기) 칸이 그 조건이다. 예를 들어 `Cmd/Ctrl+\`는 편집기에 초점이 있으면 편집기를 분할하지만, 터미널에 초점이 있으면 터미널을 분할한다(Windows의 터미널 분할은 `Ctrl+Shift+5`, 3.5.2). 같은 키를 운영체제나 다른 프로그램이 먼저 가져가는 경우도 있다. macOS에서 입력 소스(한/영) 전환에 `Ctrl+Space`를 쓰거나, Windows에서 그래픽 드라이버가 `Ctrl+Alt+화살표`를 화면 회전에 쓰는 경우다. 이럴 때는 그 프로그램의 단축키를 끄거나, VS Code 쪽 단축키를 바꾼다.

## 4.2 설정과 확장

### 4.2.1 사용자 설정과 작업 공간 설정

기초 과정 1.2.5에서 `settings.json`에 들여쓰기와 Ruff 포맷 설정을 붙여 넣었다. 그때 연 것은 **사용자 설정**이었고, 상자에서 "특정 프로젝트에만 적용하고 싶으면 `.vscode/settings.json`(작업 영역 설정)에 쓴다"고 짧게 소개했다. 이제 두 가지를 함께 쓴다.

VS Code의 설정은 세 층으로 쌓인다. 아래층의 값을 위층이 덮어쓴다.

```
작업 공간 설정   프로젝트/.vscode/settings.json   ← 이 폴더를 열었을 때만. 저장소에 올려 팀이 함께 쓸 수 있다
     ▲ 덮어씀
사용자 설정      내 컴퓨터의 settings.json         ← 내가 여는 모든 폴더에
     ▲ 덮어씀
기본 설정        VS Code와 확장에 들어 있는 값
```

| 층 | 파일 위치 | 여는 명령 |
|---|---|---|
| 기본 설정 | VS Code 안(고칠 수 없다) | `Preferences: Open Default Settings (JSON)` |
| 사용자 설정 | macOS `~/Library/Application Support/Code/User/settings.json`<br>Windows `%APPDATA%\Code\User\settings.json` | `Preferences: Open User Settings (JSON)` |
| 작업 공간 설정 | 프로젝트 폴더의 `.vscode/settings.json` | `Preferences: Open Workspace Settings (JSON)` |

어디에 무엇을 둘지는 "이 설정이 **나**의 취향인가, **이 프로젝트**의 규칙인가"로 정한다.

- **사용자 설정** — 색 테마, 글꼴 크기, 미니맵을 끌지, 자동 저장을 켤지처럼 사람마다 다른 것. 그리고 어느 프로젝트에서나 똑같이 쓰고 싶은 나만의 기본값.
- **작업 공간 설정** — 이 프로젝트의 파이썬 파일을 무엇으로 포맷할지, 탐색기에서 무엇을 숨길지처럼 이 프로젝트에서 일하는 사람이 모두 같아야 하는 것.

작업 공간 설정은 프로젝트 폴더 안의 파일이므로 5장부터 Git으로 함께 관리할 수 있다. 팀원이 저장소를 받아 VS Code로 열면 같은 설정이 적용된다. 기초 과정에서 "들여쓰기와 포맷 설정을 각자 사용자 설정에 붙여 넣으라"고 한 것을, 이제는 프로젝트에 한 번 적어 두면 된다.

> **언어별 설정이 이긴다**
> `"[python]": { ... }`처럼 언어를 지정한 블록(기초 과정 1.2.5)은 층을 따지기 전에 **언어를 지정하지 않은 설정보다 먼저** 적용된다. 그래서 사용자 설정의 `"[python]"` 블록에 `"editor.rulers": [72, 88]`이 있으면, 작업 공간 설정에 `"editor.rulers": [100]`을 적어도 파이썬 파일에서는 72·88 안내선이 그대로 보인다. 작업 공간에서 파이썬 파일의 값을 바꾸려면 작업 공간 설정에도 `"[python]"` 블록을 만들어 그 안에 적는다. 정리하면 "언어별 작업 공간 > 언어별 사용자 > 작업 공간 > 사용자 > 기본" 순서다. 실습 4-2에서 직접 확인한다.

### 4.2.2 설정 화면과 JSON의 관계

설정은 **설정 화면**(Settings editor)에서도 바꿀 수 있다. `Cmd/Ctrl+,`로 연다.

설정 화면 위쪽에 **User**(사용자)와 **Workspace**(작업 영역) 탭이 있다. 어느 탭에서 바꾸느냐에 따라 저장되는 파일이 다르다. User 탭에서 바꾸면 사용자 `settings.json`에, Workspace 탭에서 바꾸면 `.vscode/settings.json`에 적힌다. `.vscode` 폴더와 파일이 없으면 이때 만들어진다. 설정 화면은 JSON 파일을 보기 좋게 보여 주는 **다른 얼굴**일 뿐이다.

설정 화면에서 쓸모 있는 기능은 다음과 같다.

- **검색** — 위쪽 칸에 `rulers`, `format on save`처럼 입력한다. 설정의 ID(`editor.formatOnSave`)로도, 설명의 낱말로도 찾는다.
- **바꾼 설정만 보기** — 검색 칸에 `@modified`를 입력하면 기본값에서 바뀐 설정만 나온다. "내가 무엇을 바꾸어 두었더라?"를 확인할 때 쓴다.
- **확장별로 보기** — `@ext:charliermarsh.ruff`처럼 확장 ID를 넣으면 그 확장의 설정만 나온다. 언어별로는 `@lang:python`이다.
- **바뀐 표시** — 기본값에서 바뀐 설정은 왼쪽에 세로 막대가 보인다. 다른 층에서도 정해져 있으면 "Also modified in: Workspace"(작업 영역에서도 수정됨) 같은 글이 붙는다.
- **톱니바퀴 메뉴** — 설정 이름 옆의 톱니바퀴를 누르면 기본값으로 되돌리기(Reset Setting), 설정 ID 복사(Copy Setting ID), JSON으로 복사(Copy Setting as JSON)를 할 수 있다. 인터넷이나 AI의 답에서 본 설정이 무엇인지 확인하거나, 설정 화면에서 찾은 것을 JSON 파일에 옮길 때 편하다.
- **JSON으로 열기** — 오른쪽 위의 종이 모양 아이콘(Open Settings (JSON))을 누르면 지금 탭(User 또는 Workspace)의 `settings.json`이 열린다.

값이 목록이나 객체인 설정(`files.exclude`, `editor.codeActionsOnSave` 등)은 설정 화면에서 "Edit in settings.json"(settings.json에서 편집)이라는 링크만 보여 주기도 한다. 이럴 때는 JSON 파일에서 고친다. JSON 파일에서 설정 이름 위에 마우스를 올리면 설명이 나오고, 따옴표 안에서 `Ctrl+Space`를 누르면 쓸 수 있는 설정 이름과 값이 자동 완성 목록으로 나온다. 설정 이름을 외울 필요가 없다.

> **VS Code의 JSON 파일에는 주석을 쓸 수 있다**
> 기초 과정 1.2.5에서 `//` 주석이 VS Code의 `settings.json`에서만 허용된다고 했다. 이 장에서 만드는 `.vscode/` 안의 JSON 파일(`settings.json`, `extensions.json`, `launch.json`)은 모두 주석을 허용하는 형식(JSONC)이다. 오른쪽 아래 언어 모드에 `JSON with Comments`라고 보인다. 일반 JSON 파일(예: 웹 API의 응답)에는 주석을 쓸 수 없다.

### 4.2.3 파이썬 개발에 필요한 확장

VS Code 자체는 범용 편집기이고, 파이썬을 이해하는 능력은 **확장**(extension)이 더한다. 기초 과정에서 Python 확장과 Ruff 확장을 설치했다. 이 과정에서 쓰는 확장은 다음과 같다.

| 확장 | ID | 하는 일 | 설치 |
|---|---|---|---|
| Python | `ms-python.python` | 인터프리터 선택, ▷ 실행, 아래 확장들을 묶는다 | 기초 과정 |
| Pylance | `ms-python.vscode-pylance` | 자동 완성, 마우스를 올리면 나오는 설명, 정의로 이동, 이름 바꾸기, `import` 검사 | Python과 함께 |
| Python Debugger | `ms-python.debugpy` | 파이썬 디버거(debugpy). 4.4의 기능 전부 | Python과 함께 |
| Python Environments | `ms-python.vscode-python-envs` | 가상환경 찾기·만들기·고르기, 터미널 자동 활성화(4.5) | Python과 함께(버전에 따라 다르다) |
| Ruff | `charliermarsh.ruff` | 포맷과 린트 | 기초 과정 |
| Jupyter | `ms-toolsai.jupyter` | VS Code에서 노트북 열고 실행하기 | **지금 설치**(9장에서 쓴다) |

Python 확장을 설치하면 Pylance와 Python Debugger가 함께 설치된다. 2025~2026년에 걸쳐 가상환경을 다루는 기능이 Python Environments 확장으로 옮겨 가고 있어서, 설치한 시기에 따라 이 확장이 함께 설치되어 있거나 없을 수 있다. 있으면 액티비티 막대에 파이썬 환경 아이콘이 보인다. 어느 쪽이든 상태 표시줄과 `Python: Select Interpreter`로 인터프리터를 고르는 방법은 같다.

확장은 확장 화면(`Cmd/Ctrl+Shift+X`)에서 이름으로 찾아 설치할 수 있고, **터미널에서도** 설치할 수 있다. 이 과정답게 터미널로 Jupyter 확장을 설치해 본다.

```
code --install-extension ms-toolsai.jupyter
code --list-extensions
```

```
Installing extensions...
Installing extension 'ms-toolsai.jupyter'...
Extension 'ms-toolsai.jupyter' v2026.x.x was successfully installed.
charliermarsh.ruff
ms-python.debugpy
ms-python.python
ms-python.vscode-pylance
ms-python.vscode-python-envs
ms-toolsai.jupyter
ms-toolsai.jupyter-keymap
ms-toolsai.jupyter-renderers
...
```

버전 번호와 목록은 컴퓨터마다 다르다. Jupyter 확장도 몇 가지 확장을 함께 설치한다. `code --list-extensions --show-versions`로 버전까지 볼 수 있다. 명령으로 설치할 수 있으니 `README.md`에 "이 확장들을 설치하라"를 명령으로 적어 둘 수도 있다. 다만 VS Code에는 이 일을 위한 더 좋은 방법이 있다(4.2.5).

확장은 확장 화면에서 오른쪽 클릭 → **Disable (Workspace)**(사용 안 함(작업 영역))로 **이 작업 공간에서만** 끌 수 있다. 이 프로젝트와 맞지 않는 확장이 있을 때 쓴다.

> **확장은 내 권한으로 실행되는 프로그램이다**
> 확장은 편집기의 장식이 아니라 **내 컴퓨터에서 내 권한으로 실행되는 프로그램**이다. 파일을 읽고 쓰고, 명령을 실행하고, 인터넷에 접속할 수 있다. 이름을 비슷하게 지은 가짜 확장이 마켓플레이스에 올라왔다가 내려지는 일도 있다. 3.8에서 처음 보는 패키지를 `pip install`하기 전에 확인했듯이, 확장을 설치하기 전에도 확인한다.
>
> - **게시자**(publisher)를 본다. Microsoft의 공식 확장은 게시자가 `Microsoft`이고 이름 옆에 확인 표시가 있다. ID의 앞부분(`ms-python.`)이 게시자다.
> - 설치 수, 평점, 저장소 링크, 최근 업데이트 날짜를 본다.
> - 교재나 공식 문서에 적힌 **확장 ID**로 찾는다. 이름만으로 찾으면 비슷한 이름의 다른 확장을 설치하기 쉽다.
> - 쓰지 않는 확장은 지운다.

### 4.2.4 저장할 때 자동 포맷

기초 과정 1.2.5에서 사용자 설정에 다음을 넣었다. 파이썬 파일을 저장할 때마다 Ruff가 코드 모양을 정리하게 하는 설정이다.

```jsonc
"[python]": {
  "editor.defaultFormatter": "charliermarsh.ruff",
  "editor.formatOnSave": true,
  "editor.codeActionsOnSave": {
    "source.fixAll.ruff": "explicit",
    "source.organizeImports.ruff": "explicit"
  }
}
```

`defaultFormatter`는 "어느 확장으로 포맷하나", `formatOnSave`는 "저장할 때 포맷하나", `codeActionsOnSave`는 "저장할 때 어떤 자동 수정을 하나"다. 포맷은 저장할 때 말고도 언제든 `Format Document`(문서 서식) 명령으로 할 수 있다. 단축키는 `Shift+Option+F`(macOS) / `Shift+Alt+F`(Windows)다.

**저장했는데 포맷되지 않으면** 다음을 확인한다.

1. **문법 오류가 있는가.** 기초 과정에서 본 대로 포매터는 문법 오류가 있는 코드를 고치지 못한다. 문제 패널(4.3.7)을 본다.
2. **어느 포매터가 정해져 있는가.** 명령 팔레트의 `Format Document With...`(다음으로 문서 서식 지정)를 실행하면 쓸 수 있는 포매터 목록과 지금 기본값이 나온다. 포맷하는 확장이 둘 이상 설치되어 있는데 기본값이 정해져 있지 않으면 VS Code가 어느 것을 쓸지 물어본다.
3. **포매터 확장이 동작하는가.** 출력 패널의 오른쪽 목록에서 `Ruff`를 골라 기록을 본다. 확장이 오류를 남겼다면 여기에 있다.
4. **자동 저장으로 저장되었는가.** 4.1.2의 상자에서 본 대로 `afterDelay` 자동 저장으로 저장될 때는 포맷하지 않는다.

이 설정은 이 프로젝트에서 일하는 사람이 **모두** 같아야 한다. 한 사람은 저장할 때 포맷하고 다른 사람은 하지 않으면, 코드를 조금 고쳤을 뿐인데 파일 전체의 줄바꿈과 따옴표가 바뀐 것처럼 보인다. 5장에서 `git diff`로 변경을 볼 때 진짜 변경이 포맷 변경에 묻혀 버린다. 그래서 이 설정은 **작업 공간 설정**에도 둔다. 실습 4-2에서 `shop`의 `.vscode/settings.json`에 옮긴다.

포맷의 **규칙**(한 줄의 최대 길이, 어떤 린트 규칙을 쓸지 등)은 VS Code 설정이 아니라 Ruff 자체의 설정 파일(`pyproject.toml`)에 적는다. 그래야 VS Code를 쓰지 않는 사람이나 GitHub Actions에서도 같은 규칙이 적용된다. 이것은 중급 과정에서 Ruff를 명령으로 쓰면서 다룬다. 이 장에서는 "VS Code가 저장할 때 Ruff를 부른다"까지만 정해 둔다.

### 4.2.5 팀원에게 권장 확장 알리기 — `.vscode/extensions.json`

작업 공간 설정에 `"editor.defaultFormatter": "charliermarsh.ruff"`를 적어도, 팀원의 VS Code에 Ruff 확장이 없으면 소용이 없다. 이 프로젝트에 필요한 확장을 알려 주는 파일이 `.vscode/extensions.json`이다.

```jsonc
{
  // 이 프로젝트를 열면 VS Code가 설치를 권하는 확장
  "recommendations": [
    "ms-python.python",
    "ms-python.vscode-pylance",
    "ms-python.debugpy",
    "charliermarsh.ruff"
  ]
}
```

이 파일이 있는 폴더를 열었는데 목록의 확장이 설치되어 있지 않으면, VS Code가 오른쪽 아래에 "이 저장소에 권장되는 확장을 설치하시겠습니까?"라는 알림을 띄운다. 확장 화면의 검색 칸에 `@recommended`를 입력하면 권장 확장 목록과 설치 여부가 보인다. **권장일 뿐 자동으로 설치되지는 않는다.** 설치할지는 받는 사람이 정한다(4.2.3의 상자).

파일을 직접 만들어도 되고, 다음 방법도 있다.

- 명령 팔레트의 `Extensions: Configure Recommended Extensions (Workspace Folder)`를 실행하면 이 파일을 만들어 열어 준다.
- 확장 화면에서 확장을 오른쪽 클릭 → **Add to Workspace Recommendations**(작업 영역 권장 사항에 추가)를 누르면 목록에 ID가 들어간다.

목록에는 확장 **ID**를 적는다. 확장 화면에서 확장을 고르면 상세 화면에 ID가 보이고, 오른쪽 클릭 → **Copy Extension ID**로 복사할 수 있다. 권하고 싶지 않은 확장(이 프로젝트와 충돌하는 포매터 등)은 `"unwantedRecommendations"` 목록에 적는다.

### 4.2.6 저장소에 올릴 설정과 올리지 않을 설정

5장부터 프로젝트를 Git 저장소로 만들면 `.vscode` 폴더를 올릴지 정해야 한다. 기준은 세 가지다. **팀 전체에 필요한가, 다른 컴퓨터에서도 맞는가, 비밀이 없는가.**

| 파일·설정 | 올린다 | 이유 |
|---|---|---|
| `.vscode/extensions.json` | 올린다 | 누구에게나 필요한 확장 목록 |
| `.vscode/settings.json`의 포맷 설정, `files.exclude` | 올린다 | 프로젝트의 규칙 |
| `.vscode/launch.json`(4.4) | 올린다 | 디버그 실행 설정을 팀이 함께 쓴다. 비밀 값이 없을 때만 |
| 색 테마, 글꼴 크기, 미니맵 | 올리지 않는다 | 개인 취향. 사용자 설정에 둔다 |
| `/Users/jinyoung/...`, `C:\Users\...` 같은 절대 경로가 든 설정 | 올리지 않는다 | 다른 사람의 컴퓨터에는 그 경로가 없다. `${workspaceFolder}`(4.4.2)처럼 상대적으로 쓰거나 사용자 설정에 둔다 |
| API 키, 비밀번호가 든 설정 | **절대 올리지 않는다** | `.env`에 두고 `.gitignore`에 넣는다(4.4.2, 8장) |

`.vscode` 폴더 전체를 무시하면서 일부 파일만 올리고 싶을 때는 `.gitignore`에 다음과 같이 적는 방법이 흔하다. `!`는 "앞의 규칙에서 빼라(다시 추적하라)"는 뜻이다. `.gitignore`의 패턴 규칙은 5장에서 자세히 다룬다.

```
.vscode/*
!.vscode/settings.json
!.vscode/extensions.json
!.vscode/launch.json
```

> **설정 동기화와 프로필**
> 사용자 설정은 내 컴퓨터에만 있다. 컴퓨터를 여러 대 쓴다면 VS Code의 **설정 동기화**(Settings Sync)를 켜서 GitHub이나 Microsoft 계정으로 사용자 설정, 단축키, 확장 목록을 맞출 수 있다. 계정 아이콘(액티비티 막대 아래쪽) → **Backup and Sync Settings**(설정 백업 및 동기화)에서 켠다. 또, 강의용·업무용처럼 용도별로 설정과 확장을 따로 묶고 싶으면 **프로필**(Profiles)을 만든다. 둘 다 사용자 설정을 다루는 기능이고, 작업 공간 설정(프로젝트의 규칙)을 대신하지는 않는다.

### 4.2.7 믿을 수 있는 폴더만 신뢰하기 — 작업 공간 신뢰

4.2.1에서 작업 공간 설정은 "이 폴더를 열면 적용된다"고 했다. 편리하지만, 거꾸로 말하면 **남이 만든 폴더를 여는 것만으로 그 사람이 정한 설정이 내 VS Code에 적용된다**는 뜻이다. 설정 중에는 실행할 프로그램의 경로를 정하는 것이 있고, `.vscode/tasks.json`에는 폴더를 열 때 명령을 자동으로 실행하게 하는 설정도 있다. `launch.json`은 `F5`를 누르면 정해진 프로그램을 실행한다. 확장들도 작업 공간의 파일을 읽어 프로그램을 실행한다.

그래서 VS Code는 폴더를 처음 열 때 **작업 공간 신뢰**(Workspace Trust)를 묻는다(4.1.1의 상자).

- **신뢰한다** — 모든 기능이 동작한다. 내가 만든 폴더, 내가 내용을 확인한 저장소에만 고른다.
- **신뢰하지 않는다** — **제한 모드**(Restricted Mode)로 열린다. 파일을 읽고 고칠 수는 있지만, 작업(tasks)과 디버깅이 꺼지고, 위험할 수 있는 작업 공간 설정이 무시되며, 신뢰가 필요한 확장(AI 에이전트 확장 다수 포함)이 꺼지거나 기능이 줄어든다. 상태 표시줄 왼쪽에 `제한 모드`(Restricted Mode)가 보인다.

인터넷에서 처음 받은 저장소는 제한 모드로 열어 먼저 읽어 본다. 특히 `.vscode` 폴더 안의 파일과 `README.md`의 설치 명령(3.7)을 확인한 뒤 신뢰로 바꾼다. 제한 모드 표시를 누르거나 명령 팔레트의 `Workspaces: Manage Workspace Trust`(작업 영역: 작업 영역 신뢰 관리)에서 바꾼다. 같은 화면에서 **상위 폴더를 신뢰**해 둘 수도 있다. `~/devtools-lab`을 신뢰해 두면 그 아래에 만드는 실습 폴더마다 묻지 않는다.

이 생각은 4.6에서 AI 도구를 다룰 때 다시 나온다. 남의 저장소에 들어 있는 AI 지침 파일은 그 저장소를 연 내 AI 도구에게 지시를 내린다. 신뢰하지 않는 폴더에서는 AI 에이전트에게 일을 맡기지 않는다.

### 실습 4-2. 설정과 확장

`shop` 창에서 한다. 결과는 `~/devtools-lab/ch04/settings.md`에 적는다.

1. 설정 화면(`Cmd/Ctrl+,`)의 **User** 탭에서 `@modified`로 검색해 바뀐 설정의 목록을 적는다. 오른쪽 위 아이콘으로 사용자 `settings.json`을 열어 목록과 같은지 비교한다. 1.2.4에서 정한 `terminal.integrated.defaultProfile.windows`(Windows)와 기초 과정 1.2.5의 설정이 보이는지 확인한다.
2. `shop` 폴더에서 `python main.py orders/small.csv`(macOS `python3`)를 한 번 실행해 `shop/__pycache__` 폴더가 생긴 것을 탐색기에서 확인한다. 설정 화면의 **Workspace** 탭에서 `files.exclude`를 찾아 `**/__pycache__` 패턴을 추가한다. 탐색기에서 `__pycache__`가 사라지는지, `.vscode/settings.json`이 새로 생겼는지 확인하고 그 내용을 적는다.
3. 4.2.1의 상자를 확인한다. `.vscode/settings.json`에 `"editor.rulers": [100]`을 넣고 저장한 뒤 `pricing.py`와 `README.md`에서 안내선이 어디에 보이는지 각각 적는다. 다음으로 같은 설정을 `"[python]": { "editor.rulers": [100] }` 안으로 옮겨 다시 확인한다. 결과를 4.2.1의 순서로 설명한 뒤, 이 설정은 지운다.
4. 기초 과정에서 사용자 설정에 넣은 포맷 설정 중 `defaultFormatter`와 `formatOnSave`를 `shop`의 `.vscode/settings.json`에도 넣는다. 완성된 파일은 다음과 같다.
   ```jsonc
   {
     "files.exclude": {
       "**/__pycache__": true
     },
     "[python]": {
       "editor.defaultFormatter": "charliermarsh.ruff",
       "editor.formatOnSave": true
     }
   }
   ```
   `where.py`의 `print("파이썬     :", sys.executable)` 줄을 `print( "파이썬     :",sys.executable )`처럼 망가뜨리고 저장해 원래 모양으로 돌아오는지 확인한다.
5. 터미널에서 Jupyter 확장을 설치하고(`code --install-extension ms-toolsai.jupyter`), `code --list-extensions`의 결과를 적는다. 4.2.3의 표에 있는 확장 가운데 설치되지 않은 것이 있으면 적는다.
6. `shop`에 4.2.5의 `.vscode/extensions.json`을 만든다. 확장 화면에서 `@recommended`로 검색해 목록이 어떻게 보이는지 적는다.
7. 다음 설정을 "작업 공간 설정에 둔다 / 사용자 설정에 둔다 / 어디에도 두지 않는다"로 나누고 이유를 한 줄씩 적는다.
   - `"workbench.colorTheme": "Default Light Modern"`
   - `"files.exclude": { "**/__pycache__": true }`
   - `"python.defaultInterpreterPath": "/Users/jinyoung/devtools-lab/ch04/practice/shop/.venv/bin/python"`
   - `"[python]": { "editor.formatOnSave": true }`
   - `"editor.fontSize": 18`
   - `"terminal.integrated.env.osx": { "OPENAI_API_KEY": "sk-..." }`
8. 명령 팔레트에서 `Workspaces: Manage Workspace Trust`를 열어 지금 `shop` 폴더가 신뢰되었는지 확인한다. `~/devtools-lab`을 신뢰하는 폴더로 추가한다.

## 4.3 편집 기술

코드를 쓰는 시간보다 **읽고 고치는** 시간이 훨씬 길다. 특히 AI 도구와 함께 일하면 직접 타이핑하는 양은 줄고, AI가 만든 코드를 읽고 여기저기 조금씩 고치는 일이 늘어난다. 이 절의 기술은 그때 쓰는 것이다. 처음에는 손이 느리더라도 마우스로 하던 일을 하나씩 단축키로 바꾸어 본다.

### 4.3.1 줄 단위 편집

| 하는 일 | macOS | Windows |
|---|---|---|
| 줄을 위·아래로 옮기기 | `Option+↑` / `Option+↓` | `Alt+↑` / `Alt+↓` |
| 줄을 위·아래로 복제 | `Shift+Option+↑` / `↓` | `Shift+Alt+↑` / `↓` |
| 줄 지우기 | `Cmd+Shift+K` | `Ctrl+Shift+K` |
| 줄 잘라내기(선택 없이) | `Cmd+X` | `Ctrl+X` |
| 아래·위에 새 줄 넣기 | `Cmd+Enter` / `Cmd+Shift+Enter` | `Ctrl+Enter` / `Ctrl+Shift+Enter` |
| 줄 주석 전환 | `Cmd+/` | `Ctrl+/` |
| 들여쓰기·내어쓰기 | `Cmd+]` / `Cmd+[` | `Ctrl+]` / `Ctrl+[` |
| 줄 선택(누를수록 늘어난다) | `Cmd+L` | `Ctrl+L` |
| 선택 영역 넓히기 | `Ctrl+Shift+Cmd+→` | `Shift+Alt+→` |
| 줄의 처음·끝으로 | `Cmd+←` / `Cmd+→` | `Home` / `End` |
| 파일의 처음·끝으로 | `Cmd+↑` / `Cmd+↓` | `Ctrl+Home` / `Ctrl+End` |
| 실행 취소·다시 실행 | `Cmd+Z` / `Cmd+Shift+Z` | `Ctrl+Z` / `Ctrl+Y` |

몇 가지는 설명을 붙인다.

- **줄 옮기기**는 잘라 붙이기보다 빠르고 안전하다. 여러 줄을 선택하고 누르면 함께 옮겨지고, 파이썬의 들여쓰기 블록 안팎으로 옮기면 들여쓰기도 맞춰 준다.
- **선택 없이 `Cmd/Ctrl+X`나 `Cmd/Ctrl+C`**를 누르면 커서가 있는 줄 전체가 잘라지거나 복사된다.
- **줄 주석 전환**은 여러 줄을 선택하고 누르면 모두 `#`으로 막고, 다시 누르면 푼다. 디버깅하다 잠깐 실행하지 않을 줄을 막을 때 쓴다.
- **선택 영역 넓히기**는 누를 때마다 낱말 → 따옴표 안 → 괄호 안 → 문장 → 함수 전체처럼 선택이 넓어진다. 괄호 안의 인자 전체를 고를 때 편하다.

이 밖에도 줄 정렬(`Sort Lines Ascending`), 대문자로(`Transform to Uppercase`), 줄 합치기(`Join Lines`) 같은 기능이 있다. 단축키가 없는 것은 명령 팔레트에서 `sort`, `upper`, `join`으로 찾는다(4.1.3).

### 4.3.2 다중 커서

**다중 커서**(multi-cursor)는 커서를 여러 개 놓고 **한 번 입력해서 여러 곳을 똑같이 고치는** 기능이다. 비슷한 줄이 여러 개 있을 때 강력하다.

| 하는 일 | macOS | Windows |
|---|---|---|
| 클릭한 곳에 커서 추가 | `Option+클릭` | `Alt+클릭` |
| 바로 위·아래 줄에 커서 추가 | `Option+Cmd+↑` / `↓` | `Ctrl+Alt+↑` / `↓` |
| 선택한 각 줄의 끝에 커서 | `Shift+Option+I` | `Shift+Alt+I` |
| 다음에 나오는 같은 글자도 선택 | `Cmd+D` | `Ctrl+D` |
| 지금 것은 건너뛰고 다음 것 선택 | `Cmd+K` 다음 `Cmd+D` | `Ctrl+K` 다음 `Ctrl+D` |
| 같은 글자를 모두 선택 | `Cmd+Shift+L` | `Ctrl+Shift+L` |
| 마지막에 추가한 커서 취소 | `Cmd+U` | `Ctrl+U` |
| 사각형으로 선택 | `Shift+Option+드래그` | `Shift+Alt+드래그` |
| 커서를 다시 하나로 | `Esc` | `Esc` |

`practice/edit/names.txt`의 이름 여덟 개를 파이썬 리스트로 바꾸어 보자. `shop` 창의 터미널에서 `code ../edit/names.txt`로 연다. 작업 공간 밖의 파일도 이렇게 열 수 있다.

```
김민준
이서연
...
윤수아
```

1. 첫 줄 맨 앞에 커서를 둔다(`Cmd+↑` / `Ctrl+Home`).
2. `Option+Cmd+↓`(macOS) / `Ctrl+Alt+↓`(Windows)를 일곱 번 눌러 여덟 줄 모두의 맨 앞에 커서를 둔다. 커서 여덟 개가 함께 깜빡인다.
3. `"`를 입력한다. 여덟 줄에 모두 들어간다.
4. 줄 끝으로 간다(`Cmd+→` / `End`). 이름의 길이가 달라도 커서마다 **자기 줄의 끝**으로 간다. `",`를 입력한다.
5. `Esc`로 커서를 하나로 되돌린다.
6. 첫 줄 위에 `MEMBERS = [`를, 마지막 줄 아래에 `]`를 넣고, 이름 줄들을 선택해 `Tab`으로 들여쓴다.

```python
MEMBERS = [
    "김민준",
    "이서연",
    ...
    "윤수아",
]
```

> **다중 커서와 한글 입력**
> 다중 커서로 **한글**을 입력하면 운영체제의 한글 조합(자음과 모음을 모아 글자를 만드는 과정) 때문에 일부 커서에만 들어가거나 글자가 어긋나는 일이 있다. 다중 커서로는 따옴표, 쉼표, 영문처럼 조합이 필요 없는 글자를 입력하고, 한글은 4.3.4의 바꾸기를 쓰는 편이 안전하다.

`Cmd/Ctrl+D`는 **같은 글자가 여러 곳에 있을 때** 쓴다. `practice/edit/visits.csv`를 열고 `강남점`을 더블클릭해 선택한 뒤 `Cmd/Ctrl+D`를 누를 때마다 다음 `강남점`이 선택에 더해진다. `Cmd/Ctrl+Shift+L`은 한 번에 모두 선택한다. 그 상태에서 입력하면 모두 바뀐다.

> **`Cmd/Ctrl+D`로 코드의 이름을 바꾸지 않는다**
> `Cmd/Ctrl+D`는 **글자가 같은 곳**을 고를 뿐 코드의 의미를 모른다. 변수 `line`을 이렇게 바꾸면 `line_discount`나 `lines` 안의 `line`, 주석과 문자열 안의 `line`까지 고르기 쉽다(빈 커서에서 시작하면 낱말 단위로 고르지만, 글자를 직접 선택하고 시작하면 낱말의 일부도 고른다). 코드의 **이름**은 4.3.6의 이름 바꾸기(`F2`)로 바꾼다. 다중 커서는 데이터, 목록, 설정처럼 의미보다 모양이 중요한 글을 고칠 때 쓴다.

### 4.3.3 파일 빠르게 열기와 기호로 이동

탐색기에서 폴더를 펼쳐 가며 파일을 찾는 대신 **이름으로** 연다.

`Cmd/Ctrl+P`를 누르고 파일 이름의 일부를 입력한다. `load`를 입력하면 `shop/loader.py`가 나온다. 글자가 이어져 있지 않아도 순서만 맞으면 찾는다(`ldr` → `loader.py`). 같은 이름의 파일이 여러 폴더에 있으면 경로가 함께 보이므로, 폴더 이름의 일부를 앞에 넣어 좁힌다. 아무것도 입력하지 않으면 최근에 연 파일 목록이 나온다.

- `Enter` — 연다.
- `Cmd/Ctrl+Enter` — 편집기를 분할해 옆에 연다.
- `pricing.py:18`처럼 뒤에 `:줄번호`를 붙이면 그 줄로 바로 간다.

파일 안에서 이동하는 방법도 이름으로 한다.

| 하는 일 | macOS | Windows | 명령 팔레트로 |
|---|---|---|---|
| 파일 안의 함수·클래스로 | `Cmd+Shift+O` | `Ctrl+Shift+O` | `@` |
| 작업 공간 전체의 함수·클래스로 | `Cmd+T` | `Ctrl+T` | `#` |
| 줄 번호로 | `Ctrl+G` | `Ctrl+G` | `:` |

`Cmd/Ctrl+Shift+O` 다음에 `:`를 하나 더 입력하면(`@:`) 함수·클래스·변수를 종류별로 묶어서 보여 준다. 편집기 위쪽의 **이동 경로**(breadcrumbs, `shop > shop > pricing.py > line_discount`)를 눌러도 같은 목록이 나오고, 탐색기 아래쪽의 **개요**(Outline) 보기에는 지금 파일의 구조가 늘 보인다.

### 4.3.4 전체 검색과 바꾸기

3.2에서 `grep -rn`과 `Select-String`으로 여러 파일에서 글자를 찾았다. VS Code에서는 검색 보기(`Cmd/Ctrl+Shift+F`)에서 한다. VS Code의 검색은 3.2.5에서 본 ripgrep으로 동작한다.

```
┌ 검색 ────────────────────────────┐
│ ▸ [qty                ] Aa ab .* │ ← 찾을 글자와 옵션 세 개
│   [바꿀 글자           ] AB      │ ← ▸를 누르면 열린다
│   포함할 파일 [shop/**/*.py    ]  │ ← … 를 누르면 열린다
│   제외할 파일 [orders          ]  │
│ 3개 파일에서 6개 결과              │
│ ▾ loader.py  shop                │
│     HEADER = ["name", "price", "qty"]
│     qty=int(row["qty"]),         │
│ ▾ models.py  shop                │
│ ...                              │
└──────────────────────────────────┘
```

찾을 글자 칸 오른쪽의 옵션 세 개는 다음과 같다. `grep`의 옵션과 비교해 두면 기억하기 쉽다.

| 아이콘 | 이름 | macOS / Windows | 뜻 | `grep`으로는 |
|---|---|---|---|---|
| `Aa` | Match Case | `Option+Cmd+C` / `Alt+C` | 대소문자를 구분한다 | 기본(구분 안 하려면 `-i`) |
| `ab` | Match Whole Word | `Option+Cmd+W` / `Alt+W` | 낱말 전체가 같은 것만 | `-w` |
| `.*` | Use Regular Expression | `Option+Cmd+R` / `Alt+R` | 정규 표현식으로 찾는다(4.3.5) | 기본 |

**VS Code의 검색은 기본으로 대소문자를 구분하지 않는다.** `grep`과 반대이고 PowerShell의 `Select-String`과 같다(3.2.2). `shop`에서 옵션을 모두 끈 채 `qty`를 찾으면 `BULK_QTY`도 나온다. `Aa`와 `ab`를 켜면 `qty`라는 낱말만 나온다.

`…`(Toggle Search Details)를 누르면 **포함할 파일**과 **제외할 파일** 칸이 열린다. 3.2에서 `--include`와 `-not -path`로 하던 일이다. 쉼표로 여러 개를 적는다.

- `*.py` — 이름이 `.py`로 끝나는 파일
- `shop/**/*.py` — `shop` 폴더 아래 어디에 있든 `.py` 파일. `**`는 "몇 단계의 폴더든"이라는 뜻이다
- `orders`, `.venv` — 그 폴더를 통째로

제외할 파일 칸 오른쪽의 아이콘(Use Exclude Settings and Ignore Files)이 켜져 있으면, `files.exclude`·`search.exclude` 설정과 `.gitignore` 같은 무시 파일에 적힌 것도 건너뛴다. 실습 4-2에서 숨긴 `__pycache__`가 검색 결과에 나오지 않는 것도 이 때문이다. 찾아야 할 파일이 결과에 나오지 않으면 이 아이콘을 꺼 본다.

결과는 파일별로 묶여 나오고, 결과를 누르면 그 줄이 열린다. 결과를 오른쪽 클릭하면 결과를 지우거나(Dismiss) 경로를 복사할 수 있다.

**바꾸기**는 찾을 글자 칸 왼쪽의 `▸`를 눌러 바꿀 글자 칸을 연다(`Cmd/Ctrl+Shift+H`로 바로 열 수도 있다). 바꿀 글자를 넣으면 결과마다 지워질 글자와 들어갈 글자가 함께 보인다. 이때 **결과를 누르면 그 파일의 바꾸기 전과 후를 나란히 보여 주는 비교 화면이 열린다.** 실제로 바꾸기 전에 확인하는 미리보기다. 결과 줄에 마우스를 올리면 그 한 곳만 바꾸는 버튼이, 파일 줄에는 그 파일만 바꾸는 버튼이 나온다. 바꿀 글자 칸 오른쪽의 버튼(Replace All)은 모든 결과를 한꺼번에 바꾼다.

여러 파일을 한꺼번에 바꾸는 것은 3.8의 "지우거나 바꾸는 명령"과 같다. **먼저 보기만 한다.** 결과 목록과 미리보기를 확인하고, 바꾸지 말아야 할 결과는 지운(Dismiss) 뒤에 바꾼다. 바꾼 뒤에도 파일마다 `Cmd/Ctrl+Z`로 되돌릴 수 있지만 여러 파일이면 번거롭다. 5장부터는 Git에 커밋해 둔 상태에서 하면 `git diff`로 확인하고 되돌릴 수 있다.

지금 연 파일 하나에서만 찾고 바꿀 때는 `Cmd/Ctrl+F`(찾기)와 `Option+Cmd+F` / `Ctrl+H`(바꾸기)를 쓴다. 옵션 세 개는 같다.

**터미널의 `grep`과 VS Code의 검색은 언제 쓰나?**

| 이럴 때 | 고르는 것 |
|---|---|
| 찾은 곳을 열어서 고치고 싶다 | VS Code 검색 |
| 여러 파일을 미리보기하며 바꾸고 싶다 | VS Code 검색과 바꾸기 |
| 결과를 세고, 정렬하고, 파일로 남기고 싶다 | `grep`·`Select-String`과 파이프(3.2) |
| 스크립트나 AI 도구에게 맡길 명령으로 적고 싶다 | `grep`·`Select-String` |
| 화면이 없는 서버에서 | `grep` |

### 4.3.5 정규 표현식 맛보기

3.2.2에서 `grep`의 패턴이 **정규 표현식**이라고 하고 `^`(줄의 처음)와 `.`(아무 글자 하나)만 써 보았다. 정규 표현식은 그 자체로 책 한 권 분량이지만, 아래 표 정도만 알아도 검색과 바꾸기에서 쓸모가 크다.

| 쓰는 것 | 뜻 | 예 | 맞는 글자 |
|---|---|---|---|
| `.` | 아무 글자 하나 | `a.c` | `abc`, `a-c` |
| `\d` | 숫자 하나 | `\d\d` | `07`, `42` |
| `\w` | 글자·숫자·밑줄 하나 | `\w+` | `load_orders` |
| `\s` | 공백(빈칸·탭) 하나 | `\s+` | 빈칸 여러 개 |
| `+` | 앞의 것이 1번 이상 | `\d+` | `5`, `2026` |
| `*` | 앞의 것이 0번 이상 | `ab*` | `a`, `abbb` |
| `?` | 앞의 것이 있거나 없거나 | `colou?r` | `color`, `colour` |
| `{n}` | 앞의 것이 정확히 n번 | `\d{4}` | `2026` |
| `^`, `$` | 줄의 처음, 줄의 끝 | `^def` | 줄 맨 앞의 `def` |
| `[...]` | 괄호 안의 글자 중 하나 | `[,;]` | `,` 또는 `;` |
| `\` | 다음 글자를 특별한 뜻 없이 | `\.`, `\(` | `.`, `(` 글자 그대로 |
| `(...)` | 묶기. 바꿀 글자에서 `$1`, `$2`로 다시 쓴다 | `(\d{4})/` | `2026/`을 찾고 `2026`을 기억 |

**찾기만 하는 예** — 검색 보기에서 `.*`를 켜고 다음을 찾아 본다.

- `def \w+\(` — 함수를 정의하는 줄. `shop`에서 찾으면 함수 여덟 개(메서드 하나 포함)가 나온다.
- `^\s*print\(` — 줄 맨 앞(들여쓰기 뒤)에서 시작하는 `print(` 호출. 디버깅하려고 넣어 둔 `print`를 찾을 때 쓴다.
- `\s+$` — 줄 끝에 남은 공백.

**바꾸는 예** — `practice/edit/visits.csv`의 날짜는 `2026/11/03`처럼 빗금(`/`)으로 쓰여 있다. 이것을 `2026-11-03`으로 바꾼다. 이 파일을 열고 `Option+Cmd+F` / `Ctrl+H`로 바꾸기를 연 뒤 `.*`를 켠다.

```
찾을 글자: (\d{4})/(\d{2})/(\d{2})
바꿀 글자: $1-$2-$3
```

`(\d{4})`가 연도 네 자리를 찾아 `$1`로, 다음 두 묶음이 월과 일을 찾아 `$2`, `$3`로 기억한다. 바꿀 글자에서 그 사이에 `-`를 넣었다. 찾는 동안 맞는 곳이 노랗게 표시되고 찾기 칸에 `1/8`처럼 개수가 나온다. 여덟 곳이 맞는지 확인하고 모두 바꾸기(`Cmd+Option+Enter` / `Ctrl+Alt+Enter`)를 누른다.

정규 표현식에는 조금씩 다른 **방언**이 있다. VS Code는 JavaScript의 정규 표현식을 쓰고, 묶은 것을 다시 쓸 때 `$1`이라고 쓴다. `grep`은 기본 문법에서 `+`, `?`, `{}`, `()`를 쓰려면 `grep -E`가 필요하고, 파이썬의 `re` 모듈은 다시 쓸 때 `\1`이라고 쓴다. 정규 표현식은 AI에게 만들어 달라고 하기 좋은 일이지만, 받은 식은 **검색 결과의 개수와 미리보기로 먼저 확인**하고 바꾼다.

### 4.3.6 정의로 이동·참조 찾기·이름 바꾸기

여러 파일로 나뉜 프로그램을 읽을 때 가장 많이 하는 일은 "이 함수는 어디에 정의되어 있지?"와 "이 함수를 누가 부르지?"다. Pylance는 `import` 문을 해석해서 이 질문에 답한다. 3.2의 `grep`이 **글자가 같은 곳**을 찾는다면, 이 기능들은 **같은 이름이 가리키는 것**을 찾는다.

| 하는 일 | macOS | Windows |
|---|---|---|
| 정의로 이동 | `F12` 또는 `Cmd+클릭` | `F12` 또는 `Ctrl+클릭` |
| 정의를 그 자리에서 엿보기 | `Option+F12` | `Alt+F12` |
| 참조 찾기(그 자리에 목록) | `Shift+F12` | `Shift+F12` |
| 모든 참조를 사이드바에 | `Shift+Option+F12` | `Shift+Alt+F12` |
| 이름 바꾸기 | `F2` | `F2` |
| 뒤로 가기·앞으로 가기 | `Ctrl+-` / `Ctrl+Shift+-` | `Alt+←` / `Alt+→` |

이름 위에 마우스를 올려 두기만 해도 정의의 첫 줄, 타입, 독스트링이 나온다. 기초 과정 10장에서 함수마다 독스트링을 쓴 보람이 여기서 나타난다.

**코드를 따라 읽기** — `shop`의 `main.py`에서 시작해 `OrderLine`의 정의까지 따라가 보자.

1. `main.py`를 열고 `main()`의 `main`에 커서를 두고 `F12`를 누른다. `shop/cli.py`의 `def main()`으로 간다.
2. `main()` 안의 `load_orders`에서 `F12` → `shop/loader.py`의 `load_orders`로 간다.
3. `parse_line`에서 `F12` → 같은 파일의 `parse_line`으로 간다.
4. `OrderLine`에서 `F12` → `shop/models.py`의 `class OrderLine`으로 간다.
5. 뒤로 가기(`Ctrl+-` / `Alt+←`)를 네 번 누르면 지나온 길을 거꾸로 밟아 `main.py`로 돌아온다.

이번에는 거꾸로 묻는다. `pricing.py`의 `def summarize`에서 `Shift+F12`를 누르면 그 자리에 참조 목록이 펼쳐진다. `cli.py`와 `check_orders.py`가 이 함수를 부른다. **함수를 고치기 전에 누가 부르는지 먼저 본다.** 고친 결과가 그 모든 곳에 영향을 주기 때문이다.

처음 보는 프로젝트를 읽는 순서도 이와 같다. `README.md`에서 실행 명령을 보고, 시작 파일(`main.py`)을 열고, 호출을 `F12`로 따라 들어갔다가 뒤로 가기로 나온다. 한 함수 안에서 길을 잃으면 개요(Outline) 보기나 `Cmd/Ctrl+Shift+O`로 파일의 구조를 다시 본다.

**이름 바꾸기(`F2`)** — `OrderLine`의 `qty`라는 이름이 짧아서 `quantity`로 바꾸고 싶다고 하자. 먼저 검색으로 얼마나 퍼져 있는지 본다. 검색 보기에서 `Aa`와 `ab`를 켜고 `qty`를 찾으면 다음이 나온다.

| 파일 | 줄 | 바꿔야 하나 |
|---|---|---|
| `orders/*.csv` (3개) | `name,price,qty` | **아니다.** 주문 파일의 형식이다 |
| `shop/loader.py` | `HEADER = ["name", "price", "qty"]` | **아니다.** CSV 머리글과 비교하는 문자열이다 |
| `shop/loader.py` | `qty=int(row["qty"]),` | 앞의 `qty=`는 바꾼다. 뒤의 `"qty"`는 CSV 열 이름이므로 그대로 둔다 |
| `shop/models.py` | `qty: int` | 바꾼다. 속성의 정의다 |
| `shop/models.py` | `return self.price * self.qty` | 바꾼다 |
| `shop/pricing.py` | `if line.qty > BULK_QTY:` | `line.qty`는 바꾼다. `BULK_QTY`는 다른 이름이다 |

같은 `qty`라는 글자가 **속성의 이름**으로도, **파일 형식의 일부(문자열)**로도 쓰였다. 전체 바꾸기로 `qty`를 모두 `quantity`로 바꾸면 `HEADER`와 `row["qty"]`까지 바뀐다. 그러면 주문 파일의 머리글과 맞지 않아 프로그램이 오류로 끝나고, CSV 파일까지 바꾸어 맞춘다면 이번에는 **파일 형식이 바뀌어** 이미 다른 사람이 가진 주문 파일을 읽지 못하게 된다.

`F2`는 이름이 가리키는 것을 따라가므로 이 구별을 해 준다.

1. `shop/models.py`에서 `qty: int`의 `qty`에 커서를 두고 `F2`를 누른다. 이름을 입력하는 칸이 뜬다.
2. `quantity`를 입력하고, `Enter` 대신 **`Shift+Enter`**를 누른다. 바로 바꾸지 않고 **리팩터링 미리보기**(Refactor Preview) 패널을 연다.
3. 패널에서 바뀔 곳의 목록을 확인한다. 파일을 누르면 바꾸기 전과 후의 비교 화면이 열린다. `models.py`의 두 곳, `pricing.py`의 `line.qty`가 들어 있고, 문자열 `"qty"`와 `BULK_QTY`, CSV 파일은 들어 있지 않다. `loader.py`의 `qty=`(키워드 인자)가 목록에 있는지 본다. 도구의 버전에 따라 빠질 수도 있다.
4. 위쪽의 **Apply**(적용)를 누른다. 3에서 `qty=`가 빠져 있었다면 `loader.py`에서 직접 `quantity=`로 고친다.
5. 저장하고 실행해서 확인한다.

```
# macOS
python3 check_orders.py

# Windows
python check_orders.py
```

이름을 바꾸기 전과 결과가 같으면(아직 버그가 있으니 "2건 실패") 이름 바꾸기가 프로그램의 동작을 바꾸지 않은 것이다. `TypeError`나 `AttributeError`가 났다면 바꾸지 못한 곳이 남은 것이다. 오류 메시지의 파일과 줄을 보고 고친다.

`F2`는 편리하지만 만능은 아니다. Pylance가 이해하는 범위 안에서만 바꾼다. 문자열 안의 이름, 다른 프로젝트의 코드, `getattr(obj, "qty")`처럼 이름을 글자로 다루는 코드는 따라가지 못한다. 그래서 순서는 언제나 같다. **미리보기로 확인하고, 바꾸고, 실행해서 확인한다.**

확인했으면 같은 방법으로 `quantity`를 다시 `qty`로 되돌린다. 뒤의 절과 실습은 `qty`라는 이름을 쓴다.

> **작업 공간을 잘못 열면 이 기능들이 반쪽이 된다**
> 정의로 이동과 이름 바꾸기는 Pylance가 `from shop.loader import ...`의 `shop`을 찾을 수 있어야 동작한다. Pylance는 **작업 공간 폴더**를 프로젝트의 뿌리로 본다(4.1.1). 프로젝트 폴더(바깥 `shop`)가 아니라 그 위의 `ch04`나 홈 폴더를 열면, `import` 아래에 물결 밑줄이 생기고 `F12`가 "정의를 찾을 수 없다"고 하거나 이름 바꾸기가 일부 파일을 빠뜨릴 수 있다. 선택한 인터프리터가 틀려도(4.5) 설치한 패키지를 찾지 못해 같은 일이 생긴다.

### 4.3.7 문제 패널과 빠른 수정

Pylance와 Ruff는 실행하기 전에 문제가 될 만한 곳에 물결 밑줄을 긋는다(기초 과정 1.2.5). 그 목록을 모아 보는 곳이 **문제 패널**(`Cmd/Ctrl+Shift+M`)이다. 파일별로 묶여 있고, 누르면 그 줄로 간다. `F8`을 누르면 다음 문제로, `Shift+F8`은 이전 문제로 이동한다.

밑줄이 있는 곳에 커서를 두면 왼쪽에 전구 아이콘이 나타날 때가 있다. **빠른 수정**(Quick Fix)이다. `Cmd/Ctrl+.`을 누르면 고치는 방법의 목록이 나온다. 예를 들어 `where.py`에 `Path.cwd()`를 쓰면 `Path`가 정의되지 않았다는 밑줄이 생기고, 빠른 수정 목록에 `from pathlib import Path`를 추가하는 항목이 나온다. 쓰지 않는 `import`를 지우는 항목, 오타가 난 이름을 비슷한 이름으로 고치는 항목도 나온다.

빠른 수정도 4.3.6처럼 **고르기 전에 무엇을 하는지 읽는다.** 비슷한 이름의 다른 모듈에서 가져오는 항목이 섞여 있을 수 있다.

## 4.4 디버거 더 쓰기

### 4.4.1 기초 과정의 디버거 다시 보기

기초 과정 1.2.5에서 중단점을 찍고(줄 번호 왼쪽 클릭), `F5`로 시작하고, `F10`으로 한 줄씩 실행하고, 변수 패널에서 값을 보았다. 디버거의 핵심은 그것이 전부다. 프로그램을 **멈춰 놓고 들여다본다.** 이 절에서는 거기에 몇 가지를 더한다. 먼저 단축키를 정리한다.

| 하는 일 | 단축키 | 디버그 도구 모음 |
|---|---|---|
| 디버그 시작·계속(다음 중단점까지) | `F5` | ▷ |
| 디버그 없이 실행(중단점 무시) | `Ctrl+F5` | |
| 단계 실행(Step Over) — 이 줄을 실행하고 다음 줄에서 멈춤 | `F10` | ↷ |
| 들어가기(Step Into) — 이 줄에서 부르는 함수 안으로 들어가 멈춤 | `F11` | ↓ |
| 나오기(Step Out) — 지금 함수를 끝까지 실행하고 부른 곳으로 돌아가 멈춤 | `Shift+F11` | ↑ |
| 다시 시작 | `Cmd/Ctrl+Shift+F5` | ↻ |
| 중지 | `Shift+F5` | □ |
| 중단점 놓기·지우기 | `F9` | |

`F10`과 `F11`의 차이가 중요하다. `lines = load_orders(path)`에서 `F10`을 누르면 `load_orders()`를 통째로 실행하고 다음 줄로 간다. `F11`을 누르면 `load_orders()`의 첫 줄로 들어간다. 그 함수 안이 궁금하지 않으면 `F10`, 궁금하면 `F11`이다. 들어갔다가 볼 일을 다 보았으면 `Shift+F11`로 나온다.

> **macOS 노트북의 F 키**
> macOS 노트북의 맨 윗줄 키는 기본으로 화면 밝기, 음량 같은 기능을 한다. `F5`를 누르려면 `fn`을 함께 눌러야 한다(`fn+F5`). 디버거를 자주 쓴다면 시스템 설정 → 키보드 → 키보드 단축키 → 기능 키에서 "F1, F2 등의 키를 표준 기능 키로 사용"을 켠다. 그러면 거꾸로 밝기·음량을 바꿀 때 `fn`을 누른다.

디버깅 중의 화면은 다음과 같다. 실행 및 디버그 보기(`Cmd/Ctrl+Shift+D`)가 사이드바에 열린다.

```

│ ▷ [주문 계산: small.csv  ▾] ⚙   │   │
│ ▾ 변수(VARIABLES)              │   │  16  def line_discount(line):
│   ▾ Locals                     │   │  17      """..."""
│     ▸ line: OrderLine(...)     │   │ ●18      if line.qty > BULK_QTY:   ← 멈춘 줄

이제 `shop`의 `main.py`를 열고 `F5`를 눌러 보자. 실행 설정이 아직 없으므로 디버거를 고르라는 목록이 뜬다. **Python Debugger** → **Python File**(Python 파일)을 고른다.

```

프로그램이 사용법만 출력하고 끝났다. `main.py`는 주문 파일 이름을 명령행 인자로 받아야 하는데, `F5`는 인자 없이 실행했기 때문이다. 기초 과정에서는 인자가 필요 없는 프로그램만 디버깅했다. 인자, 환경 변수, 작업 폴더를 정해서 디버깅하려면 **실행 설정**을 파일에 적어 둔다.

### 4.4.2 `launch.json` — 실행 설정 저장하기

**디버그 실행 설정**은 작업 공간의 `.vscode/launch.json`에 적는다. "무엇을, 어떤 인자로, 어떤 환경에서 실행할지"를 이름을 붙여 저장해 두고, 목록에서 골라 `F5`로 실행한다.

실행 및 디버그 보기(`Cmd/Ctrl+Shift+D`)에서 **create a launch.json file**(launch.json 파일 만들기)을 누른다. 디버거로 **Python Debugger**를, 설정 종류로 **Python File**을 고르면 다음 파일이 만들어진다(주석은 생략했다).

```jsonc
{
    "version": "0.2.0",
    "configurations": [
        {
            "name": "Python Debugger: Current File",
            "type": "debugpy",
            "request": "launch",
            "program": "${file}",
            "console": "integratedTerminal"
        }
    ]
}
```

`configurations`는 실행 설정의 **목록**이다. 설정 하나가 `{ }` 하나다. 이 파일을 `shop` 프로젝트에 맞게 다음과 같이 바꾼다.

```jsonc
{
    "version": "0.2.0",
    "configurations": [
        {
            "name": "주문 계산: small.csv",
            "type": "debugpy",
            "request": "launch",
            "program": "${workspaceFolder}/main.py",
            "args": ["orders/small.csv"],
            "console": "integratedTerminal"
        },
        {
            "name": "주문 계산: 쿠폰 5%",
            "type": "debugpy",
            "request": "launch",
            "program": "${workspaceFolder}/main.py",
            "args": ["orders/small.csv"],
            "env": { "SHOP_COUPON_RATE": "0.05" },
            "console": "integratedTerminal"
        },
        {
            "name": "주문 계산: 파일 고르기",
            "type": "debugpy",
            "request": "launch",
            "program": "${workspaceFolder}/main.py",
            "args": "${command:pickArgs}",
            "console": "integratedTerminal"
        },
        {
            "name": "주문 계산: python -m shop",
            "type": "debugpy",
            "request": "launch",
            "module": "shop",
            "args": ["orders/big.csv"],
            "cwd": "${workspaceFolder}",
            "console": "integratedTerminal"
        },
        {
            "name": "현재 파일",
            "type": "debugpy",
            "request": "launch",
            "program": "${file}",
            "console": "integratedTerminal"
        }
    ]
}
```

각 항목의 뜻은 다음과 같다.

| 항목 | 뜻 | 터미널 명령으로 치면 |
|---|---|---|
| `name` | 목록에 보일 이름. 마음대로 짓는다 | |
| `type` | 어느 디버거를 쓸지. 파이썬은 `debugpy` | |
| `request` | `launch`는 프로그램을 새로 실행한다(이미 실행 중인 프로그램에 붙는 `attach`도 있다) | |
| `program` | 실행할 파이썬 파일 | `python main.py` |
| `module` | 모듈로 실행. `program` 대신 쓴다(4.4.6) | `python -m shop` |
| `args` | 명령행 인자 목록. 인자 하나가 문자열 하나다 | `... orders/small.csv` |
| `cwd` | 작업 폴더. 없으면 작업 공간 폴더 | 실행하기 전의 `cd` |
| `env` | 이 실행에만 더할 환경 변수. 값은 모두 문자열 | `SHOP_COUPON_RATE=0.05 python ...`(3.4.1) |
| `envFile` | 환경 변수를 적은 파일(아래 상자) | |
| `console` | 출력을 보일 곳. `integratedTerminal`(통합 터미널, 기본값), `internalConsole`(디버그 콘솔), `externalTerminal`(바깥 터미널) | |
| `python` | 실행할 파이썬. 없으면 VS Code에서 선택한 인터프리터(4.5) | `python`이 어느 파이썬인가 |
| `justMyCode` | `true`(기본값)이면 내 코드에서만 멈추고, 표준 라이브러리·설치한 패키지 안으로는 들어가지 않는다 | |

`${...}`는 VS Code가 실행할 때 채워 넣는 **변수**다.

| 변수 | 값 |
|---|---|
| `${workspaceFolder}` | 작업 공간 폴더의 경로. 예: `/Users/jinyoung/devtools-lab/ch04/practice/shop` |
| `${file}` | 지금 편집기에서 열려 있는 파일의 경로 |
| `${fileDirname}` | 그 파일이 있는 폴더 |
| `${command:pickArgs}` | 실행할 때마다 인자를 입력받는 칸을 띄운다 |

`program`을 `/Users/jinyoung/.../main.py` 같은 절대 경로로 쓰지 않고 `${workspaceFolder}/main.py`로 쓴 것이 중요하다. 이렇게 써야 이 파일을 저장소에 올렸을 때 다른 사람의 컴퓨터에서도 동작한다(4.2.6). Windows에서도 경로를 `/`로 써도 된다.

저장한 뒤 실행 및 디버그 보기 위쪽의 목록에서 설정을 고르고 `F5`를 누른다. 목록의 이름은 `launch.json`의 `name`이다.

- **주문 계산: small.csv** — `python main.py orders/small.csv`를 한 것과 같은 결과가 터미널에 나온다(결제 금액 27,900원).
- **주문 계산: 쿠폰 5%** — 쿠폰 할인 -1,395원, 결제 금액 26,505원이 나온다. `env`의 값은 디버거가 실행하는 프로그램에 주어진다. 작업하던 다른 터미널에서 `echo $SHOP_COUPON_RATE`(Windows `$env:SHOP_COUPON_RATE`)를 해 보면 비어 있다. 다만 디버그 터미널 안에서는 운영체제에 따라 다르다(아래 상자).
- **주문 계산: 파일 고르기** — 화면 위쪽에 인자를 입력하는 칸이 뜬다. `orders/big.csv`를 입력한다. 여러 개면 터미널에서처럼 빈칸으로 나누어 입력한다.

디버그로 실행하면 통합 터미널에 다음과 비슷한 긴 명령이 먼저 보인다.

```
/Users/jinyoung/.../.venv/bin/python /Users/jinyoung/.vscode/extensions/ms-python.debugpy-.../launcher 52731 -- /Users/jinyoung/devtools-lab/ch04/practice/shop/main.py orders/small.csv
```

모양은 버전과 운영체제마다 다르지만 뜻은 같다. 1.2.5에서 "▷ 버튼도 결국 터미널에서 `python 파일경로`를 실행하는 것"이라고 했듯이, 디버거도 **선택한 파이썬으로 디버거 프로그램(debugpy)을 실행하고, 그 프로그램이 `main.py`를 인자와 함께 실행**한다. 맨 앞의 파이썬 경로로 어느 파이썬이 쓰였는지 확인할 수 있다(4.5).

`Ctrl+F5`(디버그 없이 실행)도 같은 설정을 쓴다. 중단점에서 멈추지 않을 뿐이다. 인자와 환경 변수를 정해 둔 설정으로 그냥 실행만 하고 싶을 때 쓴다.

> **디버그 터미널에 남는 환경 변수 — Windows**
> 디버거는 프로그램을 `Python Debug Console`이라는 이름의 통합 터미널에서 실행하고, 다음 디버깅 때도 그 터미널을 다시 쓴다. 이때 `env`의 값을 넘기는 방법이 셸마다 다르다.
> - **macOS(zsh)** — `/usr/bin/env SHOP_COUPON_RATE=0.05 파이썬 ...`처럼 **그 명령에만** 환경 변수를 붙여 실행한다(3.4.1의 "한 명령에만 정하기"). 실행이 끝나면 디버그 터미널에도 남지 않는다.
> - **Windows(PowerShell)** — 먼저 `${env:SHOP_COUPON_RATE}='0.05'; `를 실행해 **그 셸에** 환경 변수를 정한 뒤 프로그램을 실행한다. PowerShell에는 "한 명령에만 정하기" 문법이 없기 때문이다(3.4.1). 그래서 실행이 끝난 뒤에도 그 디버그 터미널에는 값이 **남는다.** 그다음에 `env`가 없는 설정(예: **주문 계산: small.csv**)으로 디버깅하면, 같은 터미널을 다시 쓰므로 남은 값 때문에 쿠폰 할인이 들어간다.
>
> Windows에서 환경 변수가 다른 설정을 번갈아 실행하며 결과를 비교할 때는, 실행할 때마다 터미널 목록에서 `Python Debug Console`을 **휴지통 아이콘으로 닫고**(4.5.5) 실행한다. 디버그 터미널에서 `$env:SHOP_COUPON_RATE`를 입력해 값이 남았는지 확인할 수도 있다.

> **환경 변수 파일 — `envFile`과 `.env`**
> 환경 변수가 여러 개이거나, 사람마다 값이 다르거나, **비밀 값**(API 키)이면 `launch.json`에 직접 적지 않는다. `launch.json`은 저장소에 올리는 파일이기 때문이다(4.2.6). 대신 프로젝트 폴더에 `.env` 파일을 만들어 `이름=값`을 한 줄에 하나씩 적고,
> ```
> SHOP_COUPON_RATE=0.05
> ```
> 설정에서 그 파일을 가리킨다.
> ```jsonc
> "envFile": "${workspaceFolder}/.env"
> ```
> 사실 이 줄을 적지 않아도 디버거는 이 파일을 읽는다. `envFile`을 적지 않으면 Python 확장의 설정 `python.envFile`의 값을 쓰는데, 그 기본값이 `${workspaceFolder}/.env`이기 때문이다. 그래도 적어 두면 "이 설정은 `.env`에 기댄다"는 것이 `launch.json`에 드러난다. 거꾸로 말하면, **프로젝트 폴더에 `.env`가 있으면 모든 디버그 실행에 그 값이 들어간다.** 같은 이름의 값을 `env`에도 적으면 어느 쪽이 쓰이는지 헷갈리므로, 한 변수는 한 곳에서만 정한다. 실험하려고 만든 `.env`는 실험이 끝나면 지운다.
>
> `shop/.gitignore`에는 이미 `.env`가 들어 있다. `.env`는 올리지 않고, 어떤 변수가 필요한지는 값을 비운 `.env.example`을 만들어 알린다(8장). 터미널에서 `python main.py`로 실행할 때는 `.env`가 읽히지 않는다(4.5.4). 프로그램 코드에서 `.env`를 읽는 방법은 "웹·API 기초"에서 배운다.

> **작업 폴더(`cwd`)와 상대 경로**
> `args`의 `orders/small.csv`는 **작업 폴더를 기준으로 한** 상대 경로다(기초 과정 7.2.4). `cwd`를 적지 않으면 작업 공간 폴더가 작업 폴더가 되므로, `shop` 폴더를 작업 공간으로 열어야 이 경로가 맞는다. `ch04` 폴더를 열어 놓고 같은 설정을 쓰면 `${workspaceFolder}/main.py`부터 엉뚱한 곳을 가리킨다. 4.1.1의 "프로젝트 하나 = 창 하나"를 지키면 이런 문제가 생기지 않는다. 작업 폴더를 바꾸고 싶으면 `"cwd": "${workspaceFolder}/orders"`처럼 적고, 인자도 그 폴더를 기준으로 `"small.csv"`로 바꾼다.

설정을 하나 더 만들고 싶을 때는 `launch.json`을 연 상태에서 오른쪽 아래의 **Add Configuration...**(구성 추가) 버튼을 누르면 자주 쓰는 모양의 틀이 목록으로 나온다. 따옴표 안에서 `Ctrl+Space`를 누르면 쓸 수 있는 항목이 자동 완성으로 나오고, 항목 위에 마우스를 올리면 설명이 나온다.

### 4.4.3 변수·조사식·호출 스택·디버그 콘솔

이제 `README.md`와 결과가 다른 이유를 찾는다. 결과에서 **묶음 할인**이 1,800원이어야 하는데 600원이었다. 묶음 할인은 `pricing.py`의 `line_discount()`가 계산한다.

1. `shop/pricing.py`의 18번째 줄(`if line.qty > BULK_QTY:`)에 중단점을 놓는다(`F9`).
2. 목록에서 **주문 계산: small.csv**를 고르고 `F5`를 누른다.
3. 18번째 줄이 노랗게 표시되며 멈춘다.

**변수**(VARIABLES)의 `Locals`에 지금 함수의 지역 변수가, `Globals`에 이 모듈의 전역 이름(`BULK_QTY`, `BULK_RATE` 등)이 보인다. `line`을 펼치면 `name='볼펜'`, `price=1200`, `qty=10`이다. `small.csv`의 첫 줄이다.

**조사식**(WATCH)에는 계속 지켜볼 **식**을 적는다. 조사식 제목 옆의 `+`를 누르고 다음 세 식을 하나씩 넣는다.

```
line.subtotal()
line.qty > BULK_QTY
line.qty >= BULK_QTY
```

```
line.subtotal(): 12000
line.qty > BULK_QTY: False
line.qty >= BULK_QTY: True
```

`F10`을 누르면 19번째 줄(할인 계산)이 아니라 **20번째 줄(`return 0`)**로 간다. 볼펜은 10개를 샀는데 할인을 받지 못했다. `README.md`의 규칙은 "10개 **이상**"인데, 코드는 `>`(초과)로 비교한다. 이것이 버그다. `F5`를 누르면 다음 줄(공책)에서 다시 멈추고, 조사식의 값이 새 `line`으로 바뀐다. 직전과 달라진 값은 강조되어 보인다.

**아직 고치지 않는다.** 4.6에서 AI가 내놓은 수정안을 검토하면서 고친다. 원인을 직접 찾아 두었기 때문에 그 수정안이 맞는지 판단할 수 있다.

**호출 스택**(CALL STACK)은 "지금 이 줄에 어떻게 왔는가"를 보여 준다. 위가 지금 함수이고, 아래로 갈수록 그 함수를 부른 쪽이다.

```
line_discount   pricing.py   18
<genexpr>       pricing.py   26
summarize       pricing.py   26
main            cli.py       28
<module>        main.py       6
```

`main.py`가 `main()`을, `main()`이 `summarize()`를, `summarize()` 안의 `sum(line_discount(line) for line in lines)`가 `line_discount()`를 불렀다. `<genexpr>`는 이 괄호 안의 **제너레이터 식**(generator expression)이 따로 실행되는 단위로 보이는 것이다. 기초 과정에서 트레이스백을 아래에서 위로 읽었던 것(기초 과정 1.3.5)과 순서만 반대이고 내용은 같다.

호출 스택에서 `summarize`를 누르면 편집기가 26번째 줄로 가고, 변수 패널이 **그 함수의** 지역 변수로 바뀐다. `lines`와 `gross`(28500)가 보인다. `main`을 누르면 `path`와 `lines`가 보인다. 이렇게 **부른 쪽의 상태**를 거슬러 올라가 볼 수 있다. 4.4.5에서 이것으로 오류가 난 줄을 찾는다.

**디버그 콘솔**(DEBUG CONSOLE)은 멈춘 순간의 프로그램 안에서 실행되는 파이썬 셸이다. 호출 스택에서 `summarize`를 고른 상태로 패널의 디버그 콘솔 탭에 입력한다.

```
> [l.name for l in lines]
['볼펜', '공책', '지우개', '형광펜']
> sum(l.subtotal() for l in lines if l.qty >= 10)
18000
```

조사식에 넣기엔 한 번만 볼 식, 리스트 전체를 훑는 식은 디버그 콘솔에서 계산한다. 디버그 콘솔에서 변수에 값을 넣을 수도 있고, 변수 패널에서 값을 오른쪽 클릭 → **Set Value**(값 설정)로 바꿀 수도 있다. 예를 들어 `BULK_QTY`를 9로 바꾸고 계속 실행하면 "만약 이 값이 9였다면"을 코드를 고치지 않고 시험할 수 있다. 다만 **실행 중인 프로그램의 상태만 바뀌고 파일은 그대로**라는 점을 잊지 않는다.

확인했으면 `Shift+F5`로 중지하고, 중단점을 다시 `F9`로 지운다.

### 4.4.4 조건부 중단점과 로그 지점

`big.csv`는 300줄이다. 18번째 줄에 중단점을 놓고 실행하면 300번 멈춘다. 그중에 보고 싶은 것은 수량이 정확히 10인 줄뿐이다.

**조건부 중단점** — 18번째 줄 번호 왼쪽을 **오른쪽 클릭**하고 **Add Conditional Breakpoint...**(조건부 중단점 추가)를 고른다. 입력 칸 왼쪽의 목록이 **Expression**(식)인지 확인하고 다음을 입력한 뒤 `Enter`를 누른다.

```
line.qty == 10
```

중단점 아이콘 가운데에 줄(=)이 생긴다. **주문 계산: 파일 고르기**로 `orders/big.csv`를 주고 `F5`를 누르면, 조건이 참인 줄에서만 멈춘다. 처음 멈춘 곳의 `line`은 `OrderLine(name='샤프', price=4400, qty=10)`이다(`big.csv`의 48번째 줄). 조건에는 파이썬 식이면 무엇이든 쓸 수 있다. `line.name == "볼펜"`, `line.subtotal() > 100000`처럼 쓴다.

이미 놓은 중단점에 조건을 붙이려면 빨간 점을 오른쪽 클릭 → **Edit Breakpoint**(중단점 편집)를 고른다.

입력 칸 왼쪽의 목록에서 **Hit Count**(적중 횟수)를 고르면 "몇 번째로 이 줄에 왔을 때 멈출지"를 정한다. `>100`이라고 적으면 101번째부터 멈춘다. 반복이 한참 돈 뒤에 문제가 생길 때 쓴다.

**로그 지점** — 멈추지 않고 **값만 찍어 보고** 싶을 때도 있다. 기초 과정에서는 이럴 때 코드에 `print()`를 넣었다. 그러면 나중에 지우는 것을 잊기 쉽고, 지우는 것을 잊은 `print()`는 3장에서 본 것처럼 표준 출력을 더럽혀 파이프로 잇는 다른 프로그램을 망가뜨린다. **로그 지점**(Logpoint)은 코드를 고치지 않고 `print()`를 넣은 것과 같은 효과를 낸다.

18번째 줄 번호 왼쪽을 오른쪽 클릭하고 **Add Logpoint...**(로그 지점 추가)를 고른다. 메시지를 입력한다. `{ }` 안에는 파이썬 식을 쓴다.

```
{line.name} 수량={line.qty} 할인대상={line.qty > BULK_QTY}
```

아이콘이 마름모(◆)로 바뀐다. `big.csv`로 실행하면 프로그램은 멈추지 않고, **디버그 콘솔**에 300줄이 찍힌다.

```
샤프 수량=2 할인대상=False
풀 수량=3 할인대상=False
...
```

로그 지점도 조건을 함께 줄 수 있다. 로그 지점을 오른쪽 클릭 → Edit Logpoint에서 목록을 Expression으로 바꾸어 `line.qty == 10`을 넣으면, 수량이 10인 줄만 찍힌다. 몇 줄이 찍혔는지 세어 보고, 3장의 방법으로 확인해 보자.

```
# macOS — 셋째 칸이 정확히 10인 줄 세기
cut -d, -f3 orders/big.csv | grep -cx 10

# Windows
(Import-Csv orders/big.csv | Where-Object qty -eq 10).Count
```

```
19
```

`grep -x`는 줄 전체가 패턴과 같은 것만 고른다. 둘 다 19이면 이 19줄은 **모두 할인을 받지 못했다**는 것이다(`할인대상=False`). 버그가 `small.csv`의 볼펜 한 줄의 문제가 아니라는 것을 확인했다.

중단점 목록(BREAKPOINTS)에는 지금까지 놓은 중단점, 조건부 중단점, 로그 지점이 모두 보인다. 체크를 끄면 지우지 않고 잠시 꺼 둘 수 있고, 목록 제목 줄의 버튼으로 모두 끄거나 모두 지울 수 있다. 실습을 마치면 모두 지운다.

중단점 목록(BREAKPOINTS)의 맨 위에 체크 상자가 세 개 있다.

| 항목 | 언제 멈추나 |
|---|---|
| **Raised Exceptions** | 예외가 **일어나는 순간** 언제나. `try`/`except`로 잡히는 예외도 포함 |
| **Uncaught Exceptions** | 아무도 잡지 않아서 프로그램을 끝내게 될 예외. 대개 기본으로 켜져 있다 |
| **User Uncaught Exceptions** | 내 코드에서 일어난 예외가 내 코드에서 잡히지 않고 라이브러리 쪽으로 넘어갈 때 |

**Uncaught Exceptions**가 켜져 있는지 확인하고, **주문 계산: 파일 고르기**로 `orders/broken.csv`를 주어 `F5`를 누른다. 중단점을 하나도 놓지 않았는데도 `loader.py`의 15번째 줄에서 멈추고, 그 줄 아래에 예외의 종류와 메시지가 담긴 상자가 나타난다.

```
Exception has occurred: ValueError
invalid literal for int() with base 10: '12,500'
```

변수 패널을 보면 `row`가 `{'name': '스테이플러', 'price': '12,500', 'qty': '1'}`이다. 문제의 줄을 찾았다. 그런데 이 줄이 파일의 몇째 줄일까? `parse_line()`은 한 줄의 내용만 받으므로 알 수 없다. 파일을 읽는 것은 그것을 부른 `load_orders()`다.

호출 스택을 본다.

```
parse_line      loader.py   15
load_orders     loader.py   26
main            cli.py      24
<module>        main.py      6
```

`load_orders`를 누르면 변수 패널에 `reader`가 보인다. `csv.DictReader`는 지금까지 읽은 줄 수를 `line_num` 속성에 담고 있다. `reader`를 펼치거나 디버그 콘솔에 입력한다.

```
> reader.line_num
214
```

`code -g orders/broken.csv:214`로 열어 보면 그 줄이 `스테이플러,"12,500",1`이다. 가격에 천 단위 쉼표를 넣어 따옴표로 감싼 것이다. 3장의 방법으로도 확인할 수 있다. `grep -n '"' orders/broken.csv`(Windows `Select-String '"' orders/broken.csv`)는 따옴표가 들어간 줄을 줄 번호와 함께 보여 준다.

> **`<listcomp>`가 보이지 않는 이유**
> `load_orders()`의 `[parse_line(row) for row in reader]`는 리스트 컴프리헨션이다. 파이썬 3.11까지는 리스트 컴프리헨션이 따로 실행되는 단위(`<listcomp>`)로 호출 스택에 보였지만, 3.12부터는 그 자리에 바로 펼쳐서 실행하도록 바뀌어 보이지 않는다. 4.4.3의 `<genexpr>`(제너레이터 식)는 3.12 이후에도 따로 보인다. 파이썬 버전에 따라 호출 스택의 모양이 조금 다를 수 있다.

이 프로그램이 형식이 틀린 줄을 만나면 몇째 줄인지 알려 주도록 고치는 것이 근본적인 해결이다. 기초 과정 10장의 가계부 프로그램이 `DataFileError`에 줄 번호를 담아 알려 준 것처럼 말이다. 이 고침은 실습 4-4의 마지막 문제로 남긴다.

**Raised Exceptions**는 잡히는 예외에서도 멈춘다. 체크를 켜고 **주문 계산: 파일 고르기**로 없는 파일 `orders/none.csv`를 주어 실행해 보자. `cli.py`의 `main()`은 `FileNotFoundError`를 잡아서 "파일이 없습니다"를 출력하도록 되어 있다. 그런데도 디버거는 `loader.py`의 `path.open(...)`에서 멈춘다. 예외가 **일어난 곳**에서 멈추는 것이다. `F5`로 계속하면 `main()`의 `except`로 넘어가 메시지가 출력된다.

어딘가의 `try`/`except`가 예외를 삼켜 버려서 "오류는 안 나는데 결과가 이상하다"면 Raised Exceptions를 켜고 실행해 본다. 대신 라이브러리가 안에서 일으켰다가 스스로 잡는 예외에서도 멈출 수 있어서 시끄럽다. 볼 일이 끝나면 끈다.

**User Uncaught Exceptions**는 웹 프레임워크처럼 라이브러리가 모든 예외를 잡아서 처리해 버리는 프로그램에서 쓸모가 있다. 그런 프로그램에서는 내 코드의 예외가 "잡힌 예외"가 되어 Uncaught Exceptions로는 멈추지 않기 때문이다. "웹·API 기초"에서 서버 코드를 디버깅할 때 다시 만난다.

### 4.4.6 모듈로 실행하기 — `python -m`

`shop/cli.py`를 열고 오른쪽 위의 ▷ 버튼을 누르거나, **현재 파일** 설정으로 `F5`를 눌러 보자.

```
Traceback (most recent call last):
  File ".../shop/shop/cli.py", line 6, in <module>
    from shop.loader import load_orders
ModuleNotFoundError: No module named 'shop'
```

`shop` 패키지 안의 파일인데 `shop`을 찾지 못한다. 터미널에서 `python shop/cli.py orders/small.csv`(macOS `python3`)를 실행해도 같다.

파이썬은 `import`할 모듈을 `sys.path`에 있는 폴더들에서 찾는다. **파일 경로로 실행하면, 그 파일이 있는 폴더**가 `sys.path`의 맨 앞에 들어간다. `python main.py`로 실행하면 `main.py`가 있는 프로젝트 폴더가 들어가므로 그 안의 `shop` 폴더(패키지)를 찾는다. `python shop/cli.py`로 실행하면 안쪽 `shop` 폴더가 들어가고, 그 안에는 `shop`이라는 이름의 폴더가 없다.

```
practice/shop/          ← python main.py 로 실행하면 여기가 sys.path[0] → shop 패키지를 찾는다
├── main.py
└── shop/               ← python shop/cli.py 로 실행하면 여기가 sys.path[0] → 이 안에 shop이 없다
    ├── __main__.py
    └── cli.py
```

기초 과정에서는 이 문제를 피하려고 프로젝트 폴더에 시작 파일 `main.py`를 두었다. 다른 방법이 **모듈로 실행하기**다. `-m` 옵션은 파일 경로가 아니라 **모듈 이름**을 받는다.

```
# macOS
python3 -m shop orders/small.csv

# Windows
python -m shop orders/small.csv
```

```
주문 파일: small.csv (주문 4줄)
...
결제 금액: 27,900원
```

`python -m 이름`은 다음과 같이 동작한다.

- **현재 작업 폴더**를 `sys.path`의 맨 앞에 넣는다. 그래서 프로젝트 폴더에서 실행하면 `shop` 패키지를 찾는다.
- 이름이 **패키지**이면 그 안의 `__main__.py`를 실행한다. `shop/__main__.py`가 `main()`을 부르도록 만들어 두었다.
- 이름이 **모듈**이면 그 모듈을 `__name__ == "__main__"`인 상태로 실행한다.

두 가지를 더 확인해 보자.

```
# macOS (Windows는 python)
python3 -m shop.cli orders/small.csv
cd shop
python3 -m shop ../orders/small.csv
cd ..
```

```
No module named shop
```

`python -m shop.cli`는 아무것도 출력하지 않고 끝난다. `cli.py`가 모듈로 실행되기는 했지만, 그 안에는 `if __name__ == "__main__": main()`이 없어서 함수를 정의만 하고 끝났기 때문이다. 안쪽 `shop` 폴더로 들어가서 `-m shop`을 하면 `No module named shop`이 나온다. 작업 폴더가 바뀌어 `sys.path`의 맨 앞에 프로젝트 폴더가 없기 때문이다. **`-m`은 작업 폴더에 따라 결과가 달라진다.**

그래서 `launch.json`의 **주문 계산: python -m shop** 설정은 `program` 대신 `"module": "shop"`을 쓰고, `"cwd": "${workspaceFolder}"`를 적어 작업 폴더를 분명히 했다(적지 않아도 기본값이 같지만, 이 설정이 작업 폴더에 기대고 있다는 것을 드러내려고 적었다). 이 설정으로 실행해 본다.

`-m`은 이미 여러 번 써 왔다. `python -m venv`, `python -m pip`는 모두 "이 파이썬이 찾을 수 있는 `venv`, `pip` 모듈을 실행하라"는 뜻이다(기초 과정 9.1.6). 중급 과정에서 시험 도구를 `python -m pytest`로 실행하고 디버깅할 때도 이 설정이 그대로 쓰인다.

## 4.5 통합 터미널

### 4.5.1 VS Code 안의 터미널도 그냥 터미널이다

2.1에서 터미널(창)과 셸(명령을 해석하는 프로그램)은 다른 프로그램이라고 했다. VS Code의 **통합 터미널**은 VS Code 안에 들어 있는 터미널 창일 뿐이고, 그 안에서 도는 셸은 바깥 터미널 앱과 **같은 zsh, 같은 PowerShell 7**이다. 셸 설정 파일(`~/.zshrc`, `$PROFILE`)도 똑같이 읽는다. 그래서 2·3장에서 배운 명령은 어디서나 똑같이 동작한다.

그런데도 "바깥 터미널에서는 되는데 VS Code 터미널에서는 안 된다"(또는 그 반대)는 일이 생긴다. 다음이 다를 수 있기 때문이다.

| 항목 | 바깥 터미널 앱 | VS Code 통합 터미널 |
|---|---|---|
| 실행되는 셸 | 터미널 앱의 기본 프로필 | VS Code의 기본 프로필(`terminal.integrated.defaultProfile.osx`, `.windows`) |
| 처음 위치 | 대개 홈 폴더 | 작업 공간 폴더 |
| 환경 변수 | 터미널 앱이 시작할 때 받은 것 + 셸 설정 파일 | **VS Code가 시작할 때 받은 것** + 셸 설정 파일 + VS Code와 확장이 더한 것 |
| 가상환경 | 직접 활성화한다 | Python 확장이 자동으로 활성화할 수 있다 |
| 단축키 | 셸이 받는다 | VS Code의 단축키가 먼저 가져갈 수 있다 |

첫째 줄은 1.2.4에서 맞추었다. Windows에서 터미널 패널의 `+` 옆 `∨`를 누르면 **PowerShell**(7)과 **Windows PowerShell**(5.1)이 함께 보인다. 새 터미널이 5.1로 열린다면 기본 프로필이 바뀐 것이다. `$PSVersionTable.PSVersion`으로 확인한다. 나머지 줄을 차례로 본다.

### 4.5.2 VS Code가 시작할 때 받은 환경

3.4.3에서 "환경 변수는 프로그램이 **시작할 때** 부모 프로그램에게서 복사해 받는다"고 했다. VS Code도 프로그램이므로 시작할 때 누군가에게서 환경을 받고, 통합 터미널과 ▷ 버튼, 디버거는 모두 그것을 물려받는다. 그런데 VS Code를 **어떻게 시작했는지**에 따라 그 "누군가"가 다르다.

| VS Code를 시작한 방법 | VS Code가 받는 환경 |
|---|---|
| Dock·시작 메뉴·Finder·탐색기에서 | macOS: VS Code가 시작할 때 로그인 셸을 한 번 실행해 셸 설정 파일의 환경을 읽어 온다<br>Windows: 운영체제에 저장된 사용자·시스템 환경 변수(3.4.3의 상자) |
| 터미널에서 `code .` | **그 터미널의 환경을 그대로** 받는다. 그 터미널에서 활성화한 가상환경, `export`·`$env:`로 정한 값까지 |
| 이미 VS Code가 실행 중일 때 터미널에서 `code .` | 실행 중인 VS Code에 창만 하나 더 열어 달라고 부탁한다. **새 환경은 전해지지 않는다** |

둘째 줄 때문에 생기는 일이 있다. 가상환경을 활성화한 터미널에서 `code .`을 실행하면, VS Code와 그 안의 모든 터미널이 그 가상환경의 `PATH`를 물려받는다. Python 확장이 "활성화된 환경에서 VS Code가 시작되었다"며 그 가상환경을 인터프리터로 고르기도 한다. 편리할 때도 있지만, 다른 프로젝트의 가상환경이 활성화된 터미널에서 `code .`을 하면 엉뚱한 파이썬이 섞인다. 셋째 줄 때문에 "환경 변수를 바꾸고 `code .`을 다시 했는데 반영이 안 된다"는 일도 생긴다.

규칙은 3.4.3과 같다. **`PATH`나 환경 변수를 바꾸었거나 프로그램을 새로 설치했으면 VS Code를 완전히 종료했다가 다시 연다.** 창을 닫는 것만으로는 부족할 수 있다. macOS는 `Cmd+Q`, Windows는 모든 VS Code 창을 닫는다.

### 4.5.3 인터프리터와 터미널 가상환경 맞추기

기초 과정 9.2.5에서 VS Code 안에서 파이썬을 실행하는 방법마다 파이썬을 정하는 곳이 다르다고 했다. 디버거와 바깥 터미널까지 넣어 다시 정리한다.

| 실행 방법 | 어느 파이썬으로 실행되나 | 확인하는 방법 |
|---|---|---|
| ▷ 버튼 | VS Code에서 선택한 인터프리터 | 상태 표시줄, 실행할 때 터미널에 보이는 첫 줄 |
| 디버거(`F5`) | `launch.json`의 `python`. 없으면 선택한 인터프리터 | 디버그 실행 때 터미널에 보이는 첫 줄(4.4.2) |
| 통합 터미널에 `python ...` 입력 | 그 터미널의 `PATH`에서 처음 찾은 `python` | 프롬프트의 `(.venv)`, `which python`·`Get-Command python` |
| 바깥 터미널에 `python ...` 입력 | 그 터미널의 `PATH`에서 처음 찾은 `python` | 위와 같음 |

앞의 둘은 VS Code가 정하고, 뒤의 둘은 터미널이 정한다. 둘을 맞추려면 **VS Code에서 프로젝트의 가상환경을 인터프리터로 고르고, 통합 터미널에서도 그 가상환경이 활성화되어 있게** 한다.

`shop`에 가상환경을 만들어 확인해 보자. `shop` 창의 통합 터미널에서 실행한다.

```
# macOS
python3 -m venv .venv

# Windows
python -m venv .venv
```

가상환경을 만들면 VS Code가 오른쪽 아래에 "새 환경이 만들어졌다. 이 작업 공간에 선택하겠는가?" 같은 알림을 띄울 수 있다. 선택한다. 알림이 없으면 `Python: Select Interpreter`(또는 상태 표시줄의 파이썬 버전)에서 `.venv`를 고른다. 상태 표시줄에 `.venv`가 보이면 된다.

이제 터미널 패널의 휴지통 아이콘으로 지금 터미널을 닫고, 새 터미널을 연다(`` Ctrl+Shift+` ``). 인터프리터를 바꾸어도 **이미 열려 있던 터미널은 그대로**이기 때문이다(기초 과정 9.2.4). 새 터미널에서는 Python 확장이 고른 가상환경을 자동으로 활성화한다. 활성화 방식은 설정에 따라 다르다.

| 방식 | 보이는 모습 |
|---|---|
| 명령 입력(`command`) | 터미널이 열리자마자 `source .../.venv/bin/activate`(Windows `& .../.venv/Scripts/Activate.ps1`)가 저절로 입력되고 실행된다 |
| 셸 시작 시(`shellStartup`) | 활성화 명령이 보이지 않고, 첫 프롬프트부터 `(.venv)`가 붙어 있다 |
| 끔(`off`) | 아무것도 하지 않는다. 직접 활성화한다 |

이 설정은 Python Environments 확장의 `python-envs.terminal.autoActivationType`이다. 2026년 초에 Microsoft는 기본값이 `command`이고 앞으로 `shellStartup`으로 바꿀 예정이라고 발표했으므로, 내 VS Code의 값은 설정 화면에서 직접 확인한다. 예전 설정 이름은 `python.terminal.activateEnvironment`다. 어느 방식이든 확인 방법은 같다. **새 터미널을 열고 프롬프트의 `(.venv)`와 `which python`(Windows `Get-Command python`)을 본다.** 자동 활성화가 늦게 동작해서 첫 명령을 입력하는 도중에 활성화 명령이 끼어드는 일도 있으니, 새 터미널을 열면 잠깐 기다렸다가 입력한다.

**확인 스크립트로 비교하기** — `where.py`는 자기를 실행한 파이썬, 가상환경 여부, 작업 폴더, 환경 변수 `SHOP_COUPON_RATE`를 출력한다. 같은 스크립트를 여러 방법으로 실행해 보면 차이가 한눈에 보인다.

```
# macOS — shop 폴더의 .venv가 활성화된 통합 터미널에서
python where.py
```

```
파이썬     : /Users/jinyoung/devtools-lab/ch04/practice/shop/.venv/bin/python
가상환경   : True
작업 폴더  : /Users/jinyoung/devtools-lab/ch04/practice/shop
쿠폰 할인율: None
```

실습 4-5에서 ▷ 버튼, 디버거, 바깥 터미널로도 실행해 표를 채운다. 결과가 하나라도 다르면 위의 표에서 그 실행 방법이 파이썬을 어디서 정하는지 보고 맞춘다.

> **▷ 버튼의 작업 폴더**
> ▷ 버튼은 통합 터미널 하나에 `파이썬경로 파일경로` 명령을 보내서 실행한다. 이때 `cd`를 하지 않으므로, **그 터미널이 지금 있는 폴더**가 작업 폴더가 된다. 새로 열린 터미널은 작업 공간 폴더에서 시작하니 대개 문제가 없지만, 그 터미널에서 `cd orders`를 해 두었다면 `main.py`의 `orders/small.csv` 같은 상대 경로가 맞지 않게 된다. 작업 폴더가 중요한 프로그램은 `launch.json`에 `cwd`를 적고(4.4.2) 그 설정으로 실행하는 편이 확실하다.

### 4.5.4 터미널과 디버거에 환경 변수 주기

환경 변수를 정하는 곳이 여럿이므로, 어디서 정한 값이 어디에 적용되는지 정리해 둔다.

| 정한 곳 | 통합 터미널에 입력한 명령 | ▷ 버튼 | 디버거(`F5`) |
|---|---|---|---|
| 셸 설정 파일(`~/.zshrc`, `$PROFILE`) | 적용 | 적용(터미널에서 실행되므로) | 적용(디버그용 터미널도 셸이 시작하므로) |
| 터미널에서 직접(`export`, `$env:`) | 그 터미널에만 | 그 터미널에서 실행되면 적용 | 대개 적용되지 않는다(디버거는 따로 터미널을 쓴다) |
| `launch.json`의 `env` | 적용되지 않는다 | 적용되지 않는다 | 적용(Windows는 디버그 터미널에 남는다) |
| 프로젝트의 `.env`(`envFile`, 기본 `python.envFile`) | 적용되지 않는다 | 적용되지 않는다 | 적용(`envFile`을 적지 않아도 기본으로 읽는다) |

디버거는 `Python Debug Console`이라는 이름의 터미널을 따로 열어 실행하고, 다음 디버깅에도 그 터미널을 다시 쓴다. 그래서 작업하던 다른 터미널에서 `export`한 값은 디버거에 전해지지 않는다. 디버깅에 필요한 환경 변수는 `launch.json`이나 `.env`에 적는다(4.4.2).

예외가 하나 있다. Windows에서는 `launch.json`의 `env`를 디버그 터미널의 PowerShell에 `$env:`로 정해 버리므로, 그 값이 디버그 터미널에 **남아서** 다음 디버그 실행에도 적용된다(4.4.2의 상자). 디버그 터미널에 직접 `$env:`를 입력해도 마찬가지다. 결과가 이상하면 `Python Debug Console`을 휴지통 아이콘으로 닫고 다시 실행한다. macOS의 zsh는 환경 변수를 그 명령에만 붙여 실행하므로 남지 않는다.

VS Code에는 통합 터미널에만 환경 변수를 더하는 설정(`terminal.integrated.env.osx`, `terminal.integrated.env.windows`)과, 프로젝트의 `.env` 파일을 새 터미널에 자동으로 넣는 설정(`python.terminal.useEnvFile`, 기본은 꺼짐)도 있다. 후자는 켜지 않는 편이 낫다. `.env`에 API 키가 있다면 그 터미널에서 실행하는 **모든** 프로그램이 키를 받게 되고, AI 코딩 도구가 그 터미널에서 `env`를 실행하면 키가 대화에 들어간다(3.8.3). 키는 그 키가 필요한 프로그램만 읽게 한다.

### 4.5.5 터미널을 편하게 쓰는 기능

**성공·실패 표시** — VS Code의 통합 터미널은 셸과 연결되어(셸 통합, shell integration) 명령 하나하나의 시작과 끝, 종료 코드를 안다. 각 명령의 프롬프트 왼쪽에 작은 동그라미가 붙는데, 종료 코드가 0이면 파란색(또는 회색), 0이 아니면 **빨간색**이다. 3.3에서 `$?`·`$LASTEXITCODE`로 확인하던 것을 눈으로 바로 볼 수 있다. `python check_orders.py`를 실행해 보면 지금은 빨간 동그라미가 붙는다(2건 실패, 종료 코드 1). 동그라미를 누르면 그 명령의 출력을 복사하거나 다시 실행할 수 있다. `Cmd+↑`/`Cmd+↓`(macOS) / `Ctrl+↑`/`Ctrl+↓`(Windows)로 이전·다음 명령의 위치로 화면을 옮긴다.

**파일 경로 링크** — 터미널 출력에 나온 파일 경로를 `Cmd/Ctrl+클릭`하면 VS Code에서 열린다. 트레이스백의 `File ".../shop/loader.py", line 15` 줄을 `Cmd/Ctrl+클릭`하면 그 파일의 15번째 줄이 열린다. `grep -rn`의 `shop/pricing.py:18:` 같은 출력도 마찬가지다.

**여러 터미널** — 패널 오른쪽에 터미널 목록이 보인다. 터미널을 오른쪽 클릭해 이름을 바꿀 수 있다(예: `서버`, `작업`). 3.5.2에서 쓴 터미널 분할도 여기서 한다.

**숨기기와 닫기는 다르다** — `` Ctrl+` ``이나 패널의 `×`는 패널을 **숨길 뿐**이고 터미널 안의 셸과 실행 중인 프로그램은 그대로 돈다. 터미널 목록의 **휴지통 아이콘**(Kill Terminal)이 셸을 끝낸다. 그 셸에서 실행 중이던 서버도 함께 끝난다. 3.5.4에서 "띄워 둔 서버를 잊어서 포트가 사용 중"인 경우를 보았는데, VS Code에서는 패널을 숨겨 놓고 잊는 일이 흔하다.

**단축키가 셸에 가지 않을 때** — 2.3.5의 상자에서 미룬 이야기다. 통합 터미널에 초점이 있어도 일부 단축키는 VS Code가 먼저 가져간다(명령 팔레트를 여는 `Cmd/Ctrl+Shift+P`처럼). 셸의 단축키가 동작하지 않으면 다음을 확인한다.

- 단축키 편집기(4.1.4)에서 그 키를 Record Keys로 눌러 보고, "When" 칸에 `terminalFocus`가 든 VS Code 명령이 있는지 본다. 있으면 그 연결을 지우거나 바꾼다.
- 설정 `terminal.integrated.sendKeybindingsToShell`을 켜면 대부분의 단축키를 VS Code가 가져가지 않고 셸에 보낸다. 대신 터미널에 초점이 있을 때 VS Code의 단축키 일부가 동작하지 않는다.
- macOS에서 `Option+B`, `Option+F` 같은 셸의 줄 편집 키(Option을 Meta 키로 쓰는 키)가 특수 문자를 입력해 버리면 `terminal.integrated.macOptionIsMeta`를 켠다.

   - 두 결과를 4.5.2의 표로 설명한다.
6. 통합 터미널에서 `python check_orders.py`와 `python main.py orders/small.csv`를 차례로 실행하고, 각 명령 옆의 동그라미 색과 `$?`(Windows `$LASTEXITCODE`)의 값을 적는다. 이어서 `python main.py orders/broken.csv`를 실행하고, 트레이스백의 `loader.py` 경로를 `Cmd/Ctrl+클릭`해 몇째 줄이 열리는지 적는다.
7. 숨기기와 닫기를 비교한다. 새 터미널에서 `python -m http.server 8000`을 실행하고, `` Ctrl+` ``로 패널을 숨긴다. 바깥 터미널에서 3.5.4의 방법(macOS `lsof -nP -i :8000`, Windows `Get-NetTCPConnection -LocalPort 8000 -State Listen`)으로 8000번 포트를 쓰는 프로세스가 있는지 확인한다. 다음으로 VS Code에서 그 터미널을 휴지통 아이콘으로 닫고 다시 확인한다.

## 4.6 AI 코딩 도구와 함께 쓰기

### 4.6.1 VS Code 안의 AI 도구

1단계에서 AI 코딩 도구로 결과물을 만들어 보았다. VS Code에서 쓰는 AI 도구는 대개 세 가지 모습으로 일한다.

| 모습 | 하는 일 | 예 |
|---|---|---|
| **인라인 제안** | 입력하는 자리에 다음에 올 코드를 흐린 글씨로 미리 보여 준다 | 함수 이름을 쓰면 본문을 제안 |
| **채팅** | 질문에 답하고, 코드를 설명하고, 수정안을 보여 준다. 사이드바나 편집기 안(인라인 채팅)에 열린다 | "이 함수가 하는 일을 설명해 줘" |
| **에이전트** | 여러 파일을 읽고 고치고, 터미널 명령을 실행하며 작업을 끝까지 진행한다 | "할인 규칙 버그를 찾아 고치고 시험을 돌려 줘" |

VS Code에는 GitHub Copilot의 채팅·에이전트 기능이 들어 있어서 GitHub 계정으로 로그인하면 쓸 수 있고, Claude Code처럼 확장으로 설치하는 도구도 있다(Claude Code는 통합 터미널에서 명령으로 실행할 수도 있다). Cursor처럼 VS Code를 바탕으로 만든 별도의 편집기도 있다. 도구와 요금제, 화면은 몇 달 사이에도 크게 바뀐다. 이 절에서는 특정 도구의 버튼 위치보다 **어느 도구를 쓰든 그대로 통하는 일**에 집중한다.

1. 제안은 **초안**이다. 받아들이기 전에 읽는다(4.6.2).
2. AI가 바꾼 것은 **비교 화면으로** 검토하고, 필요한 부분만 받아들이고, 검사로 확인한다(4.6.3).
3. 프로젝트의 규칙은 **파일에 적어** AI에게 알려 준다(4.6.4).
4. 맡기기 전에 **되돌릴 수 있는 상태**를 만들고, 비밀 값이 새지 않게 한다(4.6.5).

AI 도구의 채팅 화면에 코드를 묻거나 에이전트에게 일을 맡기면, 열어 둔 파일, 선택한 코드, 작업 공간의 파일 내용이 AI 서비스로 보내진다. 회사나 학교의 코드라면 그곳의 규정이 허락하는 도구인지 먼저 확인한다.

> **배우는 동안에는 인라인 제안을 꺼 두는 것도 방법이다**
> 이 과정의 목표는 AI 도구 없이도 스스로 할 수 있게 되는 것이다(README의 학습 목표). 인라인 제안은 손이 먼저 Tab을 누르게 만들어서, 생각하기 전에 코드가 채워진다. 기초 과정의 문제를 다시 풀거나 이 교재의 실습을 할 때는 인라인 제안을 끄고, 실제 작업을 할 때 켜는 식으로 나누어 써 보자. 대부분의 도구는 상태 표시줄의 아이콘이나 설정에서 인라인 제안만 따로 끄고 켤 수 있고, 언어별로도 끌 수 있다.

### 4.6.2 인라인 제안 다루기

인라인 제안은 입력하는 자리 뒤에 **흐린 글씨**(고스트 텍스트)로 나타난다. 무시하고 계속 입력하면 사라진다.

| 하는 일 | 키 |
|---|---|
| 제안을 모두 받아들이기 | `Tab` |
| 제안 버리기 | `Esc` |
| 한 낱말씩 받아들이기 | `Cmd+→`(macOS) / `Ctrl+→`(Windows) |
| 다른 제안 보기 | `Option+]` / `Option+[`(macOS), `Alt+]` / `Alt+[`(Windows) |

제안은 지금 파일과 열어 둔 파일들을 보고 **그럴듯한 다음 코드**를 짐작한 것이다. 프로젝트의 규칙을 아는 것이 아니다. 예를 들어 `pricing.py`에 `def is_bulk(line: OrderLine) -> bool:`을 입력하면 `return line.qty > BULK_QTY`가 제안될 수 있다. 바로 위의 `line_discount()`가 그렇게 쓰고 있으니 그럴듯하지만, `README.md`의 규칙("10개 이상")과는 다르다. **잘못된 코드 옆에서는 잘못된 제안이 나온다.**

인라인 제안을 받아들이기 전에 다음을 본다.

- 이름이 맞는가(있지도 않은 함수나 속성을 부르지 않는가)
- 숫자와 비교 연산자가 맞는가(`>`와 `>=`, `0.1`과 `0.15`)
- 제안이 길면 한 낱말씩 받아들이면서 읽는다

### 4.6.3 AI가 고친 파일 검토하기

AI 에이전트에게 일을 맡기면 결과는 **바뀐 파일**로 돌아온다. 그것을 검토하는 도구가 **비교 화면**(diff editor)이다. 4.3.4의 바꾸기 미리보기와 4.3.6의 리팩터링 미리보기에서 이미 보았다.

```
┌ pricing.py ↔ pricing_from_ai.py ───────────────────────────────┐
│  6                                │  6                          │
│  7  BULK_QTY = 10                 │  7  BULK_QTY = 10           │
│  8− BULK_RATE = 0.1               │  8+ BULK_RATE = 0.15        │ ← 빨강: 지워진 줄, 초록: 들어간 줄
│  9                                │  9                          │
│      ···  (바뀌지 않은 줄은 접혀 있다)  ···                         │
└────────────────────────────────────────────────────────────────┘
    바꾸기 전(원래 파일)                  바꾼 뒤
```

- **왼쪽이 바꾸기 전, 오른쪽이 바꾼 뒤**다. 지워진 줄은 빨간색, 들어간 줄은 초록색이고, 줄 안에서 바뀐 글자는 더 진하게 표시된다.
- 바뀌지 않은 부분은 접혀 있다. 눌러서 펼친다.
- 위쪽 도구 모음의 위·아래 화살표로 다음·이전 **변경 덩어리**(연달아 바뀐 줄의 묶음)로 이동한다.
- 화면이 좁으면 `…` 메뉴에서 **인라인 보기**(Inline View)로 바꾸어 한 열에 위아래로 보여 준다.

AI 도구마다 검토하는 방식이 조금 다르다. 크게 두 가지다.

| | 적용한 뒤에 검토 | 적용하기 전에 검토 |
|---|---|---|
| 예 | VS Code의 Copilot 에이전트 | Claude Code 확장 |
| 파일은 언제 바뀌나 | AI가 고치면 **바로 저장되고**, "검토 대기" 상태로 표시된다 | AI가 바꾸기 전에 비교 화면을 보여 주고 허락을 구한다. 허락해야 저장된다 |
| 검토하는 방법 | 바뀐 곳마다, 파일마다, 전체를 **Keep**(유지)하거나 **Undo**(되돌리기) | 제안을 **수락하거나 거절**한다. 바뀐 곳마다 고를 수 있는 경우도 있고, 비교 화면에서 직접 고친 뒤 수락하거나 "대신 이렇게 하라"고 지시할 수도 있다 |
| 조심할 점 | 검토하기 전에도 파일은 이미 바뀌어 있어서, 그 상태로 실행하거나 시험하면 바뀐 코드가 쓰인다. AI가 **터미널 명령**으로 바꾼 파일은 검토 목록에 나오지 않는다. Keep은 Git에 커밋하는 것이 아니다 | "자동 수락" 같은 모드를 켜면 묻지 않고 저장한다 |

어느 방식이든 VS Code의 같은 비교 화면을 쓰므로 읽는 법은 같다. 그리고 어느 방식이든 **AI가 터미널 명령으로 한 일**(파일 만들기, 지우기, 옮기기, 설치)은 비교 화면에 다 나오지 않는다. 3.8에서 명령을 읽은 것과 5장부터 `git status`로 작업 폴더 전체를 확인하는 것이 함께 필요한 이유다.

**Git이 없을 때의 안전망 — 타임라인과 로컬 기록** — 5장에서 Git을 쓰기 전까지 쓸 수 있는 장치가 있다. VS Code는 편집기에서 파일을 **저장할 때마다** 그 시점의 내용을 따로 보관해 둔다(로컬 기록, Local History). 탐색기 아래쪽의 **타임라인**(Timeline) 보기에 지금 파일의 저장 기록이 시간순으로 보인다.

- 기록을 누르면 그 시점과 지금 파일의 비교 화면이 열린다.
- 기록을 오른쪽 클릭 → **Restore Contents**(내용 복원)로 그 시점의 내용으로 되돌린다.
- 명령 팔레트의 `Local History: Find Entry to Restore`로 파일과 시점을 골라 되돌릴 수도 있다.

로컬 기록은 VS Code 편집기에서 저장한 것만 남는다. 다른 프로그램이나 터미널 명령이 바꾼 내용, VS Code를 거치지 않은 변경은 기록되지 않는다. 컴퓨터가 망가지면 함께 사라진다. 어디까지나 **Git을 배우기 전까지의 임시 안전망**이다.

"저장할 때마다"에도 조건이 있다.

- **짧은 시간 안의 저장은 하나로 합쳐진다.** 같은 방식으로 저장한 기록이 설정 `workbench.localHistory.mergeWindow`의 시간(기본 10초) 안에 이어지면, 새 기록이 직전 기록을 **대신한다.** 저장하고 몇 초 안에 다시 저장하면(AI 도구가 고친 파일을 저장하는 경우도 포함될 수 있다) 앞의 상태가 기록에서 사라질 수 있다.
- **같은 내용을 여러 번 저장해도 매번 새 기록이 생기는 것은 아니다.** 지금 내용이 이미 기록되어 있으면 다시 저장해도 기록이 늘지 않는다. 그래서 `Cmd/Ctrl+S`를 누른 것만으로는 "지금 상태"가 기록에 따로 남았다고 확신할 수 없다.

그래서 "이 상태로 돌아올 수 있어야 한다"는 시점(AI에게 맡기기 직전 등)에는 저장에 기대지 말고 **기록을 직접 만든다.** 파일을 연 상태에서 명령 팔레트의 `Local History: Create Entry`(로컬 기록: 항목 만들기)를 실행하고, 기록의 이름(예: `AI 맡기기 전`)을 입력한다. 이름을 붙여 만든 기록은 보통 저장과 출처가 달라서 합쳐지지 않고, 타임라인에 그 이름으로 보이므로 찾기도 쉽다. 만든 뒤에는 타임라인에서 그 기록이 보이는지 확인한다. 여러 파일을 한꺼번에 맡길 때는 프로젝트 폴더를 통째로 복사해 두는 편이 확실하다(2.4.2).

비교 화면은 AI가 아니어도 언제든 열 수 있다.

| 비교할 것 | 방법 |
|---|---|
| 두 파일 | 터미널에서 `code --diff 파일1 파일2`. 또는 탐색기에서 첫 파일을 오른쪽 클릭 → **Select for Compare**(비교를 위해 선택), 둘째 파일을 오른쪽 클릭 → **Compare with Selected**(선택한 항목과 비교) |
| 저장하지 않은 변경과 저장된 파일 | 명령 팔레트의 `File: Compare Active File with Saved`(`Cmd/Ctrl+K` 다음 `D`) |
| 파일의 지난 저장 시점과 지금 | 타임라인에서 기록을 누른다 |

**검토해 보기** — 4.4.3에서 묶음 할인 버그의 원인을 찾아 두었다. 이 버그를 AI에게 맡겼다고 하자.

> `README.md`의 할인 규칙대로 묶음 할인이 계산되지 않는다. 고쳐 줘.

AI가 고친 `pricing.py`가 `practice/review/pricing_from_ai.py`라고 하자. 지금의 `pricing.py`와 비교한다. `shop` 폴더의 터미널에서 실행한다.

```
code --diff shop/pricing.py ../review/pricing_from_ai.py
```

변경 덩어리가 세 개 보인다. 덩어리마다 받아들일지 판단한다.

| 덩어리 | 바뀐 내용 | 판단 | 이유 |
|---|---|---|---|
| 1 | `BULK_RATE = 0.1` → `0.15` | 버린다 | `README.md`의 규칙은 10%다. 요청하지 않은 변경이다 |
| 2 | `coupon_rate()`의 독스트링을 지우고, `print(f"DEBUG coupon rate = {rate}")`를 넣었다 | 버린다 | 요청과 상관없다. 디버깅 흔적이 남았고, 이 `print`는 **표준 출력**으로 나가서 프로그램의 결과 맨 앞에 끼어든다(3.1) |
| 3 | `if line.qty > BULK_QTY:` → `>=` | **받아들인다** | 4.4.3에서 찾은 원인 그대로다 |
| | `int(...)` → `round(...)` | 버린다 | 규칙은 "원 단위 미만 버림"이다. `round()`는 반올림이다(그것도 `.5`는 짝수 쪽으로 보내는 반올림이다) |

셋째 덩어리를 보자. 이어진 두 줄이 함께 바뀌어서 **한 덩어리 안에 받아들일 것과 버릴 것이 섞여 있다.** 덩어리째 받아들이면 `round()`도 따라 들어온다. AI의 변경은 이렇게 **줄 단위로** 읽어야 한다. 7장에서 `git add -p`로 변경의 일부만 골라 담을 때도 같은 판단을 한다.

받아들일 것은 `>=` 하나다. `shop/pricing.py`의 18번째 줄을 직접 `>=`로 고치고 저장한 뒤 검사한다.

```
# macOS
python3 check_orders.py

# Windows
python check_orders.py
```

```
[통과] small.csv gross: 기대 28500, 결과 28500
[통과] small.csv bulk: 기대 1800, 결과 1800
[통과] small.csv coupon: 기대 0, 결과 0
[통과] small.csv total: 기대 26700, 결과 26700
[통과] broken.csv: ValueError
모두 통과
```

AI의 변경을 **모두** 받아들였다면 어땠을까? 검사는 `BULK_RATE`가 0.15로 바뀐 것을 잡아낸다(묶음 할인이 2,700원이 되어 실패한다). 그런데 `BULK_RATE`만 0.1로 되돌리고 나머지를 받아들이면 검사는 **모두 통과한다.** 시험 파일의 금액으로는 `round()`와 `int()`의 결과가 우연히 같고, `DEBUG` 줄은 검사가 보지 않는 곳에 찍히기 때문이다. **검사를 통과했다고 모든 변경이 맞는 것은 아니다.** 검사는 읽기를 돕는 것이지 대신하지 않는다.

AI가 고친 것을 검토할 때 보는 것을 정리하면 다음과 같다.

1. **범위** — 요청한 것만 바뀌었나? 요청하지 않은 "정리"나 "개선"이 섞이지 않았나?
2. **명세** — `README.md`, 프로젝트의 규칙, 이미 정한 동작과 맞나?
3. **지워진 것** — 독스트링, 검사, 예외 처리, 주석이 사라지지 않았나?
4. **흔적** — 디버깅용 `print`, 주석 처리한 옛 코드, `TODO`가 남지 않았나?
5. **위험** — 비밀 값, 절대 경로, 새 `import`나 새 패키지가 들어오지 않았나?
6. **확인** — 검사 스크립트를 실행했나? 종료 코드가 0인가?
7. **이해** — 읽어도 이해되지 않는 줄이 있으면 받아들이지 않는다. AI에게 설명을 시키고, 정의로 이동(4.3.6)과 디버거(4.4)로 확인한 뒤에 받아들인다.

### 4.6.4 프로젝트 규칙을 적어 두는 파일

검토에서 버린 변경들(할인율을 바꾼 것, `print`를 남긴 것, 반올림으로 바꾼 것)은 AI가 이 프로젝트의 규칙을 몰라서 생긴 것이다. 매번 채팅에 "할인 규칙은 README대로, print는 남기지 말고, 원 단위 미만은 버려"라고 쓰는 대신, 이런 규칙을 **파일에 적어 두면** AI 도구가 작업을 시작할 때 읽는다. 이것이 **AI 도구용 지침 파일**이다.

| 파일 | 읽는 도구 |
|---|---|
| `AGENTS.md` | 여러 AI 코딩 도구가 함께 쓰는 이름(Copilot, OpenAI Codex 등) |
| `CLAUDE.md` | Claude Code |
| `.github/copilot-instructions.md` | GitHub Copilot |
| `.cursor/rules/` 폴더의 파일 | Cursor |

어느 파일을 읽는지, 몇 개를 함께 읽는지는 도구와 버전마다 다르므로 쓰는 도구의 문서를 확인한다. 여러 도구를 쓴다면 내용은 한 파일(예: `AGENTS.md`)에 쓰고, 다른 파일에서는 그 파일을 읽으라고 적는 방법이 흔하다. 대부분 프로젝트 폴더의 맨 위에 둔다. 이 파일은 채팅과 에이전트에 쓰이고, 인라인 제안에는 대개 쓰이지 않는다.

`shop`이라면 다음과 같이 쓸 수 있다.

```markdown
# AGENTS.md — 주문 계산

## 프로젝트
주문 CSV를 읽어 결제 금액을 계산하는 명령행 프로그램이다. 표준 라이브러리만 쓴다.
할인 규칙은 README.md의 "할인 규칙"이 기준이다. 규칙 자체를 바꾸는 변경은 하지 않는다.

## 구조
- main.py: 시작 파일
- shop/cli.py: 화면 출력과 흐름
- shop/loader.py: CSV 읽기
- shop/pricing.py: 할인 계산
- shop/models.py: OrderLine

## 실행과 검사
- 실행: python main.py orders/small.csv
- 검사: python check_orders.py (종료 코드가 0이어야 한다)
- 코드를 고친 뒤에는 검사를 실행하고 결과를 알려 준다.

## 규칙
- 요청받은 범위만 고친다. 관련 없는 정리나 이름 바꾸기는 하지 말고 제안만 한다.
- 금액의 원 단위 미만은 버린다(int). round를 쓰지 않는다.
- 디버깅용 print를 남기지 않는다. 오류와 경고는 표준 오류로 낸다.
- 새 패키지를 설치하지 않는다.
- orders/*.csv의 형식(머리글 name,price,qty)을 바꾸지 않는다.
- .env 파일을 읽거나 출력하지 않는다. 환경 변수 전체를 출력하는 명령(env, printenv, Get-ChildItem Env:)을 실행하지 않는다.
- 사용자에게 보이는 메시지는 한국어로 쓴다.
```

잘 쓴 지침 파일은 **AI가 코드만 보고는 알 수 없는 것**을 담는다. 실행과 검사 명령, 명세가 어디 있는지, 하지 말아야 할 일이다. 코드를 보면 알 수 있는 것(함수 목록, 문법 설명)을 길게 쓰면 오히려 중요한 규칙이 묻힌다. 짧게 쓰고, AI가 같은 실수를 반복하면 한 줄씩 더한다.

지침 파일에는 한계도 있다.

- **지침은 부탁이지 강제가 아니다.** AI가 지침을 어길 수 있다. 검토(4.6.3)는 그대로 한다. 정말 막아야 하는 일(`.env` 읽기, 위험한 명령)은 AI 도구의 권한 설정으로 막는다(3.8.3, 3.8.4).
- **비밀 값을 적지 않는다.** 지침 파일은 저장소에 올리는 파일이다.
- **남의 저장소의 지침 파일은 내 AI에게 내리는 지시다.** 그 저장소를 열고 AI 에이전트를 쓰면, 저장소를 만든 사람이 적어 둔 지시를 내 AI가 따른다. 3.8.1에서 말한 "저장소 안의 문서에 숨겨 둔 악의적인 지시"가 이것이다. 처음 받은 저장소는 제한 모드로 열고(4.2.7), 지침 파일과 `.vscode` 폴더를 먼저 읽는다.

지침 파일을 Git과 함께 관리하고, AI에게 일을 맡기는 흐름에 넣는 방법은 7장에서 다룬다.

### 4.6.5 AI 도구에 맡기기 전에

AI 에이전트에게 일을 맡기기 전에 다음을 확인한다. 3.8의 "AI가 실행하려는 명령 읽기"와 짝을 이루는 목록이다.

| 확인할 것 | 지금(Git 전) | 5장 이후 |
|---|---|---|
| 되돌릴 수 있는가 | 맡길 파일마다 `Local History: Create Entry`로 이름 붙인 기록을 만들어 타임라인에서 확인하거나, 프로젝트 폴더를 복사해 둔다(4.6.3) | 지금까지의 변경을 커밋하고, AI 작업용 브랜치에서 맡긴다(7장) |
| 범위를 좁혔는가 | 고칠 파일, 지켜야 할 명세, 확인할 검사 명령을 지시에 넣는다. "pricing.py만, README 규칙대로, check_orders.py가 통과할 때까지" | 같다 |
| 비밀 값이 새지 않는가 | `.env`를 편집기에 열어 둔 채 채팅하지 않는다. AI 도구가 `.env`를 읽지 못하게 막는 설정이 있으면 쓴다(3.8.3) | 같다. `.env`가 `.gitignore`에 있는지도 확인한다(8장) |
| 명령 허락 범위가 좁은가 | "모든 명령을 계속 허락"을 주지 않는다(3.8.4) | 같다 |
| 믿는 폴더인가 | 신뢰한 작업 공간에서만 에이전트를 쓴다(4.2.7) | 같다 |
| 검토할 준비가 되었나 | 비교 화면과 검사 스크립트(4.6.3) | `git diff`, `git status`, 검사 스크립트 |

### 실습 4-6. AI가 고친 코드 검토하기

`shop` 창에서 한다. 결과를 `~/devtools-lab/ch04/review.md`에 적는다. AI 코딩 도구가 없어도 1~4번은 할 수 있다.

1. 4.6.3을 따라 `code --diff`로 `shop/pricing.py`와 `../review/pricing_from_ai.py`를 비교한다. 변경 덩어리마다 4.6.3의 검토 목록 중 어느 항목에 걸리는지 적는다. 교재의 표를 보기 전에 먼저 스스로 판단해 보고, 교재와 다른 판단이 있으면 이유를 적는다.

3. 타임라인으로 되돌리기를 연습한다.

4. `shop`에 4.6.4의 `AGENTS.md`를 만든다. 쓰는 AI 도구가 `AGENTS.md`가 아닌 다른 이름의 파일을 읽는다면, 그 도구의 문서를 찾아 어느 파일을 읽는지 적고 그 파일도 만든다(내용은 `AGENTS.md`를 읽으라는 한 줄이어도 된다).

     3. **되돌렸는지 확인한다.** `python main.py orders/broken.csv`가 다시 줄 번호 없는 트레이스백을 내는지 본다.

     5. **두 답을 비교한다.** AI의 결과를 검토해 받아들인 뒤, `code --diff ../my_loader.py shop/loader.py`로 내 답(왼쪽)과 AI의 답(오른쪽)을 비교하고, 서로 다른 점과 어느 쪽이 나은지 이유를 적는다.

   - AI가 실행하려 한 터미널 명령과, 허락했는지와 그 이유(3.8)

| 문제·빠른 수정 | 문제 패널 `Cmd/Ctrl+Shift+M`, `F8`, 빠른 수정 `Cmd/Ctrl+.`. 고르기 전에 읽는다 |
| 디버거 | `F5` 시작·계속, `F10` 단계 실행, `F11` 들어가기, `Shift+F11` 나오기, `Shift+F5` 중지, `F9` 중단점, `Ctrl+F5` 디버그 없이. macOS 노트북은 `fn` |

| 멈춘 뒤 보기 | 변수(Locals·Globals), 조사식(식을 계속 지켜본다), 호출 스택(부른 쪽의 상태로 거슬러 올라간다, `<genexpr>`), 디버그 콘솔(멈춘 자리에서 식 계산), Set Value는 파일을 바꾸지 않는다 |
| 조건부·로그 지점 | 조건(Expression), 적중 횟수(Hit Count, `>100`), 로그 지점(`{식}`이 든 메시지, 멈추지 않고 디버그 콘솔에). `print`를 넣었다 지우지 않아도 된다 |
| 예외 중단점 | Uncaught(잡히지 않는 예외), Raised(잡히는 예외도), User Uncaught(라이브러리로 넘어가는 내 예외). 호출 스택으로 부른 쪽의 변수(`reader.line_num`)를 본다 |
| `python -m` | 파일로 실행하면 그 파일의 폴더가, `-m`이면 작업 폴더가 `sys.path[0]`. 패키지면 `__main__.py`를 실행. `launch.json`은 `"module"`과 `cwd` |
| 통합 터미널 | 같은 셸이지만 기본 프로필, 처음 위치, VS Code가 시작할 때 받은 환경, 자동 활성화, 단축키가 다를 수 있다 |
| 시작할 때의 환경 | Dock·시작 메뉴로 열면 로그인 셸·운영체제의 환경, 터미널에서 `code .`이면 그 터미널의 환경(이미 실행 중이면 전해지지 않음). 바꾼 뒤에는 VS Code를 완전히 종료 |
| 인터프리터 맞추기 | ▷·디버거는 선택한 인터프리터, 터미널은 `PATH`. 프로젝트 `.venv`를 고르고, 새 터미널에서 `(.venv)`와 `which python`/`Get-Command python` 확인. 활성화 방식 `command`·`shellStartup`·`off`. ▷는 그 터미널의 현재 폴더에서 실행 |
| 환경 변수 적용 범위 | 셸 설정 파일은 모두에, 터미널에서 정한 값은 그 터미널에만, `launch.json`과 프로젝트의 `.env`는 디버거에만(`Python Debug Console`, Windows는 값이 남는다). 실험용 `.env`는 지운다. `.env`를 터미널에 자동으로 넣지 않는다 |
| 터미널 기능 | 종료 코드 표시(빨간 동그라미), 경로 `Cmd/Ctrl+클릭`, 이름 붙이기, 숨기기(`` Ctrl+` ``)와 닫기(휴지통)는 다르다, `sendKeybindingsToShell`, `macOptionIsMeta` |
| AI 도구 | 인라인 제안·채팅·에이전트. 열어 둔 코드가 AI 서비스로 간다. 배우는 동안 인라인 제안을 끄는 것도 방법 |
| 인라인 제안 | `Tab` 받기, `Esc` 버리기, `Cmd/Ctrl+→` 낱말 단위. 규칙을 모르는 짐작이다 |
| 변경 검토 | 비교 화면(왼쪽 전, 오른쪽 후, 덩어리 단위 이동). 적용한 뒤 검토(Keep/Undo, 이미 저장됨, 터미널로 바꾼 것은 목록에 없음)와 적용하기 전에 검토(수락/거절). 범위·명세·지워진 것·흔적·위험·검사·이해. 검사 통과가 검토를 대신하지 않는다 |
| 로컬 기록 | VS Code에서 저장할 때마다 남는 기록. 타임라인에서 비교·복원. 짧은 시간 안의 저장은 합쳐지고(`mergeWindow`), 같은 내용을 다시 저장해도 기록이 늘지 않으므로 돌아올 시점은 `Local History: Create Entry`로 직접 만든다. 터미널로 바꾼 것은 남지 않는다. Git 전의 임시 안전망 |
| 지침 파일 | `AGENTS.md`, `CLAUDE.md`, `.github/copilot-instructions.md`, `.cursor/rules/`. 코드만 보고 알 수 없는 것(명령, 명세, 금지)을 짧게. 강제가 아니고, 비밀 값을 적지 않고, 남의 저장소의 것은 먼저 읽는다 |
