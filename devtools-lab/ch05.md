# 5장. Git 시작하기

[개발 도구](README.md) 과정의 다섯 번째 장이다. 2·3장에서 터미널을, 4장에서 편집기를 손에 익혔다. 이 장부터 세 장에 걸쳐 **Git**을 명령으로 배운다. 1단계에서 AI 도구에게 "커밋해 줘", "이전 상태로 돌려 줘"라고 부탁했을 때 실제로 실행된 것이 Git 명령이다. 이 장에서는 그중 가장 기본이 되는 일, 즉 **내 컴퓨터에서 프로젝트의 변경을 기록하고, 무엇이 바뀌었는지 확인하고, 기록하지 않은 변경을 되돌리는** 일을 직접 한다.

- **Git이 하는 일** — 버전 관리가 필요한 이유, 내 컴퓨터의 Git 저장소와 GitHub의 관계, 커밋은 그 시점 프로젝트 전체의 스냅숏이라는 것
- **처음 설정** — 사용자 이름·이메일, 기본 브랜치 이름, 기본 편집기를 VS Code로, 한글 파일 이름, Windows의 줄 끝 문자, 설정 확인
- **세 영역** — 작업 폴더·스테이징 영역·저장소, `git init`, `git status`, `git add`, `git commit`, 파일의 상태 변화
- **변경 확인** — `git diff`, `git diff --staged`, `git log`, `git show`, `git blame`
- **좋은 커밋** — 한 커밋에 한 가지 일, 커밋 메시지 쓰는 법, 파일 일부만 골라 커밋하기(`git add -p`)
- **추적하지 않을 것** — `.gitignore` 패턴 규칙, `git check-ignore -v`, 이미 커밋한 파일을 추적에서 빼기, `git mv`와 `git rm`
- **작업 폴더의 변경 되돌리기** — `git restore`와 그 옵션들, 되살릴 수 없는 것, `git clean`

이 장에서는 브랜치를 하나(`main`)만 쓰고, 저장소도 내 컴퓨터에만 둔다. 브랜치는 6장, 이미 한 커밋을 고치거나 되돌리는 일은 7장, GitHub에 올리는 일은 8장에서 다룬다. 1장에서 말한 대로 VS Code의 Git 기능(소스 제어 화면)은 명령을 먼저 배운 뒤 **명령과 나란히** 본다.

## 학습 목표

이 장을 마치면 다음을 할 수 있다.

- 버전 관리가 필요한 이유를 4장의 로컬 기록과 비교해 설명하고, 내 컴퓨터의 Git 저장소와 GitHub 저장소의 관계를 말할 수 있다.
- 커밋이 "바뀐 부분의 기록"이 아니라 그 시점 프로젝트 전체의 스냅숏이라는 것을 설명하고, `git diff`가 두 스냅숏을 비교해 만든 결과라는 것을 안다.
- `git config`로 사용자 이름·이메일, 기본 브랜치 이름, 기본 편집기(VS Code), 한글 파일 이름 표시를 설정하고, `--show-origin`으로 각 설정이 어느 파일에서 왔는지 확인할 수 있다.
- Windows와 macOS의 줄 끝 문자 차이를 설명하고, `core.autocrlf`와 `.gitattributes`가 각각 무엇을 정하는지 구별할 수 있다.
- `git init`으로 저장소를 만들고, 작업 폴더·스테이징 영역·저장소의 세 영역을 그림으로 설명할 수 있다.
- `git status`의 출력(긴 형식과 `-s` 짧은 형식)을 읽고, 파일이 추적 안 됨 → 스테이징됨 → 커밋됨 → 수정됨으로 바뀌는 과정을 따라갈 수 있다.
- `git diff`, `git diff --staged`, `git diff HEAD`가 각각 무엇과 무엇을 비교하는지 말하고, 통합 diff 형식(`@@`, `-`, `+`)을 읽을 수 있다.
- `git log`의 옵션(`--oneline`, `--graph`, `-p`, `--stat`, `-- 경로`, `-S`)과 `git show`, `git blame`으로 이력에서 원하는 정보를 찾을 수 있다.
- 한 가지 일을 하는 커밋을 만들고, 제목과 본문으로 된 커밋 메시지에 "무엇을"보다 "왜"를 쓸 수 있다.
- `git add -p`로 한 파일 안의 변경 일부만 골라 스테이징하고, 커밋하기 전에 `git diff --staged`로 확인하는 습관을 들인다.
- `.gitignore`의 패턴 규칙(`/`, `*`, `**`, `!`)을 읽고 쓰고, `git check-ignore -v`로 무시되는 이유를 확인할 수 있다.
- 이미 커밋한 `.venv`·`__pycache__`를 `git rm --cached`로 추적에서 빼고, 그래도 이력에는 남아 있다는 것을 안다.
- `git mv`, `git rm`으로 파일 이름을 바꾸고 지우며, 대소문자만 바꾸는 이름 변경을 Git에 알릴 수 있다.
- `git restore`가 옵션에 따라 무엇을 무엇으로 되돌리는지 설명하고, 각 명령 전후의 상태를 `git status`·`git diff`·`git diff --staged`로 확인할 수 있다.
- 커밋하지 않은 변경은 버리면 되살릴 수 없다는 것을 알고, `git clean -n`으로 먼저 확인한 뒤 추적하지 않는 파일을 정리할 수 있다.
- VS Code의 소스 제어 화면에서 각 버튼이 어떤 Git 명령에 해당하는지 말할 수 있다.

def write(path, text):
    path.parent.mkdir(parents=True, exist_ok=True)
    path.write_text(text, encoding="utf-8", newline="\n")


AUTHORS = {
    "서연": ("이서연", "seoyeon@example.com"),
    "도윤": ("박도윤", "doyun@example.com"),
}


def git(repo, *args, who="서연", when="2026-11-02T10:00:00+09:00"):
    """실습용 저장소에서 git 명령을 실행한다. 작성자와 시각을 고정한다."""
    name, email = AUTHORS[who]
    env = dict(os.environ)
    env.update(
        GIT_AUTHOR_NAME=name, GIT_AUTHOR_EMAIL=email, GIT_AUTHOR_DATE=when,
        GIT_COMMITTER_NAME=name, GIT_COMMITTER_EMAIL=email, GIT_COMMITTER_DATE=when,
    )
    options = ["-c", "core.autocrlf=false", "-c", "commit.gpgsign=false"]
    subprocess.run(["git", *options, *args], cwd=repo, env=env, check=True,
                   capture_output=True, text=True, encoding="utf-8")


def commit(repo, who, when, *message):
    msg_args = []
    for part in message:
        msg_args += ["-m", part]
    git(repo, "add", "-A", "-f", who=who, when=when)
    git(repo, "commit", "-q", *msg_args, who=who, when=when)

## 5.1 Git이 하는 일

### 5.1.1 버전 관리가 필요한 이유

Git을 쓰기 전에 사람들이 "이전 상태"를 남기던 방법을 떠올려 보자.

```
보고서.docx
보고서_수정.docx
보고서_최종.docx
보고서_최종_진짜최종.docx
보고서_최종_진짜최종_교수님의견반영.docx
```

파일 이름에 버전을 적는 방법이다. 코드라면 프로젝트 폴더를 통째로 복사해 `shop_1102`, `shop_1103_할인추가` 같은 이름을 붙인다. 4.6.5에서 AI에게 여러 파일을 맡기기 전에 "프로젝트 폴더를 통째로 복사해 두라"고 한 것도 같은 방법이다. 4.6.3에서는 VS Code의 **로컬 기록**(타임라인)을 Git 전의 임시 안전망으로 썼다.

이 방법들로는 다음 질문에 답하기 어렵다.

- 어제 잘 돌던 프로그램이 오늘 안 돈다. **그 사이에 무엇이 바뀌었나?**
- 이 줄은 **누가, 언제, 왜** 이렇게 고쳤나?
- 할인 기능을 실험하다 망쳤다. 실험 전 상태로 **프로젝트 전체를** 되돌리고 싶다.
- 두 사람이 같은 프로젝트를 고쳤다. 둘의 변경을 **합치려면?**

**버전 관리 시스템**(version control system)은 이런 질문에 답하려고 만든 프로그램이다. 프로젝트의 상태를 원하는 시점마다 기록해 두고, 기록 사이의 차이를 보여 주고, 원하는 시점으로 되돌리고, 여러 사람의 작업을 합쳐 준다. **Git**은 지금 가장 널리 쓰이는 버전 관리 시스템이다.

4장의 로컬 기록과 비교하면 Git이 무엇을 더 해 주는지 보인다.

| | VS Code 로컬 기록(4.6.3) | Git |
|---|---|---|
| 기록하는 단위 | 파일 하나 | 프로젝트 전체 |
| 언제 기록하나 | VS Code에서 저장할 때(짧은 시간 안의 저장은 합쳐진다) | 내가 "지금 이 상태를 기록한다"고 정할 때(커밋) |
| 무엇이 함께 남나 | 저장한 시각 | 작성자, 시각, **왜 바꿨는지 적은 메시지** |
| 터미널·AI가 바꾼 파일 | 남지 않는다 | `git status`로 모두 보인다 |
| 새로 생긴 파일, 지워진 파일 | 모른다 | 안다 |
| 다른 컴퓨터, 다른 사람과 | 공유할 수 없다 | 저장소를 그대로 복사해 주고받는다(8장) |
| 컴퓨터가 망가지면 | 함께 사라진다 | GitHub 같은 곳에 올려 두었다면 남는다(8장) |

### 5.1.2 내 컴퓨터의 Git 저장소와 GitHub

Git과 GitHub는 이름이 비슷하지만 다른 것이다.

- **Git** — 내 컴퓨터에 설치한 **프로그램**이다(1.2.5). 인터넷 없이도 돌아간다. 이 장에서 하는 일은 모두 인터넷 없이 할 수 있다.
- **Git 저장소**(repository, 줄여서 repo) — Git이 이력을 관리하는 **프로젝트 폴더**다. 겉보기에는 보통 폴더와 같고, 안에 `.git`이라는 숨김 폴더가 하나 더 있다. 그 `.git` 폴더에 지금까지의 모든 기록이 들어 있다.
- **GitHub** — Git 저장소를 인터넷에 올려 두고 다른 사람과 함께 쓰게 해 주는 **서비스**다. 저장소 보관 말고도 이슈, 풀 리퀘스트, 코드 리뷰 같은 협업 기능을 준다(8장). GitLab, Bitbucket 같은 비슷한 서비스도 있다.

```
 내 컴퓨터                                         인터넷
┌───────────────────────────────┐            ┌─────────────────────┐
│ shop/            ← 저장소     │  push(8장) │ GitHub              │
│ ├── .git/        ← 모든 이력  │ ─────────▶ │ github.com/나/shop  │
│ ├── README.md                 │ ◀───────── │ (같은 이력의 복사본)│
│ └── shop/...                  │  pull(8장) │                     │
└───────────────────────────────┘            └─────────────────────┘
   이 장에서 하는 일: 기록(commit)·확인(diff, log)·되돌리기(restore)
```

1단계에서 "GitHub에 올렸다"는 것은 내 컴퓨터의 저장소에 쌓은 기록을 GitHub의 저장소로 보낸(push) 것이다. AI 도구나 VS Code의 버튼이 그 앞의 단계, 즉 내 컴퓨터에 저장소를 만들고 커밋하는 일까지 대신 해 주었을 것이다. 웹 화면에서 파일을 직접 올렸다면 GitHub가 그 자리에서 커밋을 만들어 준 것이다.

중요한 점이 두 가지 있다.

1. **커밋은 내 컴퓨터에서 일어난다.** 커밋했다고 GitHub에 올라가지 않는다. 올리는 것은 따로 하는 일이다(8장). 거꾸로, 아직 GitHub에 올리지 않은 저장소도 완전한 Git 저장소다.
2. **저장소를 복사하면 이력 전체가 함께 온다.** GitHub에서 저장소를 받으면(`git clone`, 8장) 최신 파일만이 아니라 처음부터의 모든 커밋이 내 컴퓨터의 `.git`에 들어온다. 그래서 받은 뒤에는 인터넷 없이도 이력을 보고 되돌릴 수 있다. 이 장의 `practice/shop`도 그런 저장소다. 두 사람이 만든 이력이 통째로 들어 있다.

### 5.1.3 커밋은 스냅숏이다

**커밋**(commit)은 "프로젝트의 지금 상태를 기록하는 일", 또는 그렇게 남긴 기록 하나를 말한다. 흔히 커밋을 "바뀐 부분의 기록"이라고 생각하는데, Git의 커밋은 그렇지 않다. **커밋 하나는 그 시점 프로젝트 전체의 스냅숏**(snapshot, 순간 사진)이다. 커밋에는 다음이 들어 있다.

- 그 시점에 Git이 관리하던 **모든 파일의 내용**과 폴더 구조
- 작성자, 시각, 커밋 메시지
- **부모 커밋**, 즉 바로 앞의 커밋이 무엇인지

```
 커밋 1               커밋 2               커밋 3
 "프로젝트 뼈대"      "주문 CSV 읽기"      "묶음 할인"
┌──────────────┐     ┌──────────────┐     ┌──────────────┐
│ README.md  A │     │ README.md  A │     │ README.md  B │ ← 바뀐 파일은 새 내용
│ main.py    M │ ◀── │ main.py    M │ ◀── │ main.py    M │ ← 안 바뀐 파일은 같은 내용을 가리킨다
│ shop/        │ 부모│ shop/        │ 부모│ shop/        │
│  __init__.py │     │  __init__.py │     │  __init__.py │
│              │     │  loader.py   │     │  loader.py   │
│              │     │  cli.py    C1│     │  cli.py    C2│
│              │     │              │     │  pricing.py  │
└──────────────┘     └──────────────┘     └──────────────┘
```

커밋마다 파일 전체를 새로 복사하면 저장소가 금방 커질 것 같지만, Git은 **내용이 같은 파일은 한 번만 저장**하고 여러 커밋이 그것을 함께 가리키게 한다. 그림에서 `main.py`는 세 커밋이 같은 내용(M)을 가리킨다. 그래서 스냅숏이면서도 저장소가 크지 않다.

그러면 "무엇이 바뀌었나"는 어디서 나올까? **두 스냅숏을 비교해서 그때그때 계산한다.** 5.4에서 배울 `git diff`, `git show`가 보여 주는 "바뀐 줄"은 Git이 저장해 둔 것이 아니라 두 커밋의 파일을 견주어 만든 결과다. 이 차이가 앞으로 여러 번 쓰인다.

- 어떤 커밋으로든 **프로젝트 전체를** 그 시점의 모습으로 꺼낼 수 있다. 앞의 커밋들을 차례로 적용해 재구성하는 것이 아니다.
- 어느 두 커밋이든 바로 비교할 수 있다. 이웃한 커밋이 아니어도 된다(5.4.6).
- Git은 "파일 이름을 바꿨다"를 따로 기록하지 않는다. 앞 스냅숏에 있던 파일이 사라지고 내용이 비슷한 파일이 새 이름으로 생겼으면 "이름이 바뀌었구나"라고 짐작해서 보여 준다(5.6.8).

`practice/shop`의 마지막 커밋을 들여다보자. 아래 명령들은 Git의 속을 보여 주는 명령이라 평소에는 쓰지 않는다. 지금은 스냅숏이 정말 그렇게 생겼는지 확인만 한다.

```
cd ~/devtools-lab/ch05/practice/shop

```

```
tree 4ed1bee35732f9aa7db553a170bb8f2e5928d515
parent 1ed259384f242998491fc8ab4192a29c477346f6
author 박도윤 <doyun@example.com> 1793947500 +0900
committer 박도윤 <doyun@example.com> 1793947500 +0900

금액을 천 단위 쉼표로 표시

README의 기대하는 결과와 출력 모양을 맞춘다.
```

`HEAD`는 "지금 보고 있는 커밋", 여기서는 가장 최근 커밋을 가리키는 이름이다(5.4.5). 커밋에 든 것이 그대로 보인다. `tree`는 이 커밋의 **파일 목록**(스냅숏)을, `parent`는 부모 커밋을 가리키는 번호다. `author`의 `1793947500`은 시각을 1970년부터 센 초로 적은 것이다. 이 커밋이 가리키는 파일 목록을 본다.

```
git ls-tree HEAD
```

```
100644 blob f6a525dbc588fd08b3a85512f7bcb73552645959	.gitattributes
100644 blob de734a413948726408c3ebf586f48a98237b3e87	.gitignore
100644 blob fd05962bde5fbd4d21ce300b91a2c24b685b74d6	README.md
100644 blob bb1918158080ede6b4654885174df0a309646582	check_orders.py
100644 blob 6960ba13b2bb06714edcedaa3733a7f268b34272	main.py
040000 tree ccebba34b8a94ec906a82e3de6f29e7b21af377b	orders
040000 tree 5f4355e9bc8bbe1788c79bf5589c1d0115693661	shop
```

`blob`은 파일 내용, `tree`는 폴더다. 바로 앞 커밋(`HEAD~1`)의 목록과 비교하면 이렇다.

```
git ls-tree HEAD~1
```

```
100644 blob f6a525dbc588fd08b3a85512f7bcb73552645959	.gitattributes
100644 blob de734a413948726408c3ebf586f48a98237b3e87	.gitignore
100644 blob fd05962bde5fbd4d21ce300b91a2c24b685b74d6	README.md
100644 blob bb1918158080ede6b4654885174df0a309646582	check_orders.py
100644 blob 6960ba13b2bb06714edcedaa3733a7f268b34272	main.py
040000 tree ccebba34b8a94ec906a82e3de6f29e7b21af377b	orders
040000 tree 4d3f3151f3a924cf3cceb34f1e06dc5bbcca09d6	shop
```

두 커밋 모두 모든 파일을 가지고 있다. 긴 번호(해시, 5.4.5)는 내용으로 계산한 이름이라서, 내용이 같으면 번호도 같다. `README.md`, `main.py` 등은 번호가 같으므로 **같은 내용을 함께 가리킨다.** 마지막 커밋에서는 `shop/cli.py`만 바뀌었으므로 그것을 담은 `shop` 폴더의 번호만 다르다.

> **커밋 해시는 왜 교재와 같은가**
> 위의 긴 번호들은 파일 내용, 작성자, 시각, 메시지, 부모 커밋을 모두 넣어 계산한 값이다. 하나라도 다르면 완전히 다른 번호가 나온다. `make_files.py`가 작성자와 시각을 고정했으므로 누가 실행해도 같은 번호가 나온다. 이 장의 뒷부분에서 **내가 직접 만드는 커밋**은 작성자와 시각이 사람마다 다르므로 번호도 교재와 다르다.

### 실습 5-1. 스냅숏 들여다보기

`practice/shop`에서 한다. 결과는 `~/devtools-lab/ch05/snapshot.md`에 적는다. 여기서 쓰는 `git log`, `git show`는 5.4에서 자세히 배운다. 지금은 스냅숏을 확인하는 도구로만 쓴다.

1. `git log --oneline`을 실행해 커밋이 몇 개인지, 가장 오래된 커밋과 가장 최근 커밋의 메시지가 무엇인지 적는다. 출력이 화면을 넘으면 `less` 화면이 열린다. `q`로 나온다(2.5.2).
2. 가장 최근 커밋과 가장 오래된 커밋의 **전체 파일 목록**을 비교한다. 가장 오래된 커밋은 `HEAD~6`(지금으로부터 여섯 번 앞)이다. 오래된 커밋에 없는 파일을 모두 적는다.
   ```
   git ls-tree -r --name-only HEAD
   git ls-tree -r --name-only HEAD~6
   ```
3. 네 번 앞 커밋 시점의 `shop/pricing.py`를 꺼내 본다. 파일 이름 앞에 `커밋:`을 붙이면 그 커밋에 들어 있던 내용을 보여 준다. 경로는 Windows에서도 `/`로 쓴다.
   ```
   git show HEAD~4:shop/pricing.py
   ```
   지금 작업 폴더의 `shop/pricing.py`(VS Code에서 연다)와 비교해 달라진 곳을 모두 적는다. 이때 작업 폴더의 파일은 바뀌지 않는다는 것도 확인한다.
4. `git ls-tree HEAD~2`와 `git ls-tree HEAD~1`을 비교한다. 번호가 다른 줄은 무엇인가? 그 커밋에서 어떤 파일이 바뀌었을지 짐작해 적고, `git show --stat HEAD~1`로 확인한다.
5. "커밋은 변경 기록이 아니라 스냅숏이다"를 3번과 4번의 결과를 근거로 두세 문장으로 설명한다.

## 5.2 처음 설정

Git을 설치한 컴퓨터에서 **한 번만** 하면 되는 설정이 있다. 이 절의 설정을 모두 마친 뒤에 5.3에서 첫 저장소를 만든다.

### 5.2.1 `git config`와 설정의 세 범위

Git의 설정은 `git config` 명령으로 보고 바꾼다. 설정은 **세 범위**의 파일에 나뉘어 저장된다.

| 범위 | 옵션 | 파일 위치 | 적용 대상 |
|---|---|---|---|
| 시스템 | `--system` | macOS(Homebrew) `/opt/homebrew/etc/gitconfig`, Windows `C:\Program Files\Git\etc\gitconfig` | 이 컴퓨터의 모든 사용자. Git을 설치할 때 정해진다 |
| 전역(사용자) | `--global` | `~/.gitconfig` | 내 계정의 모든 저장소 |
| 저장소 | `--local`(생략 가능) | 저장소의 `.git/config` | 그 저장소 하나 |

같은 설정이 여러 곳에 있으면 **좁은 범위가 이긴다**(저장소 > 전역 > 시스템). 4.2.1에서 VS Code의 작업 공간 설정이 사용자 설정보다 먼저인 것과 같은 원리다. 이 절에서 정하는 것은 대부분 **전역** 설정이다.

기본 사용법은 다음과 같다.

```
git config --global 이름 값      # 정하기
git config 이름                  # 지금 적용되는 값 보기
git config --global --unset 이름 # 지우기
```

설정 이름은 `user.name`처럼 `구역.이름` 모양이다. 값에 공백이 있으면 따옴표로 감싼다.

### 5.2.2 사용자 이름과 이메일

커밋에는 작성자가 들어간다(5.1.3). Git은 작성자를 `user.name`과 `user.email` 설정에서 가져온다. 이 둘이 없으면 커밋할 때 다음 오류가 난다.

```
Author identity unknown

*** Please tell me who you are.

Run

  git config --global user.email "you@example.com"
  git config --global user.name "Your Name"

to set your account's default identity.
Omit --global to set the identity only in this repository.

fatal: unable to auto-detect email address (got 'jinyoung@MacBook-Pro.(none)')
```

오류가 알려 준 대로 정한다. 이름은 한글로 써도 된다.

```
git config --global user.name "엄진영"
git config --global user.email "jinyoung@example.com"
```

이메일은 **GitHub에 가입한 이메일**과 같게 하는 것이 좋다. GitHub는 커밋의 이메일을 보고 그 커밋이 누구 것인지 알아내서 프로필에 표시한다.

> **이메일은 공개된다**
> 커밋에 적힌 이름과 이메일은 저장소를 받은 사람 누구나 볼 수 있다(`git log`, 5.4.3). 공개 저장소에 올리면 인터넷 전체에 공개된다. 개인 이메일을 드러내고 싶지 않으면 GitHub가 주는 **비공개용 이메일**(`아이디@users.noreply.github.com` 모양)을 쓸 수 있다. 8장에서 GitHub 설정과 함께 다룬다. 지금 아무 이메일로 정해 두어도 나중에 바꿀 수 있다. 다만 이미 만든 커밋의 이메일은 바뀌지 않는다.

회사 저장소에서는 회사 이메일을 써야 하는 경우가 있다. 그럴 때는 그 저장소 안에서 `--global` 없이 정한다. 그 저장소에만 적용되고 다른 저장소는 전역 설정을 그대로 쓴다.

```
# 회사 저장소 폴더 안에서
git config user.email "jinyoung@company.example"
```

### 5.2.3 기본 브랜치 이름

**브랜치**(branch)는 6장에서 배운다. 지금은 "커밋이 쌓이는 줄의 이름"이라고만 알아 두자. 새 저장소를 만들면 첫 브랜치가 하나 생기는데, Git은 지금도 그 이름을 기본으로 `master`라고 짓는다. GitHub를 비롯한 대부분의 서비스와 프로젝트는 몇 년 전부터 `main`을 쓴다. 이름이 다르면 8장에서 GitHub와 연결할 때 헷갈리므로 `main`으로 맞춘다.

```
git config --global init.defaultBranch main
```

이 설정이 없으면 `git init`을 할 때마다 "기본 브랜치 이름이 바뀔 수 있으니 설정하라"는 긴 안내(`hint:`로 시작하는 줄들)가 나온다. 이 설정은 **앞으로 만드는 저장소**에만 적용된다. 이미 `master`로 만든 저장소의 브랜치 이름을 바꾸는 방법은 6장에서 다룬다.

### 5.2.4 기본 편집기를 VS Code로

2.7에서 본 것처럼, `git commit`을 `-m "메시지"` 없이 실행하면 Git은 커밋 메시지를 쓰라고 **편집기**를 연다. 설정하지 않았으면 대개 Vim이 열린다. 이것을 VS Code로 바꾼다.

```
git config --global core.editor "code --wait"
```

`--wait`가 중요하다. `code 파일`은 VS Code에 "이 파일을 열어라"라고 전하고 **바로 끝나는** 명령이다(4.1.1). 그러면 Git은 편집기가 끝났으니 메시지 쓰기도 끝났다고 보고, 아직 비어 있는 메시지를 읽어 "메시지가 비었다"며 커밋을 취소한다. `--wait`를 붙이면 `code` 명령이 **그 탭을 닫을 때까지 기다렸다가** 끝난다. Git은 그때 파일을 읽는다.

`code` 명령이 동작해야 한다. 터미널에서 `code --version`이 실패하면 4.1.1의 방법으로 `code` 명령을 등록한다.

잘 되는지는 **전역 설정 파일을 편집기로 여는** 명령으로 확인한다. 이 명령은 `core.editor`에 정한 편집기를 쓴다.

```
git config --global --edit
```

VS Code에 `.gitconfig` 탭이 열리고, 터미널에는 다음 줄이 나온 채로 멈춰 있다.

```
hint: Waiting for your editor to close the file...
```

VS Code에 지금까지 정한 설정이 보일 것이다.

```
[user]
	name = 엄진영
	email = jinyoung@example.com
[init]
	defaultBranch = main
[core]
	editor = code --wait
```

`git config --global 이름 값`은 결국 이 파일에 한 줄을 적는 일이다. `[core]`가 구역, `editor`가 이름이다. 내용을 바꾸지 말고 **탭을 닫는다**(`Cmd/Ctrl+W`). 터미널의 프롬프트가 돌아오면 성공이다. Vim이 열렸다면 설정이 들어가지 않은 것이다. `:q`로 나와서(2.7.2) 설정 명령을 다시 확인한다.

### 5.2.5 한글 파일 이름

Git은 기본 설정에서 영어가 아닌 파일 이름을 **바이트 번호로 바꾸어** 보여 준다. 예를 들어 `메모.md`라는 파일을 만들고 `git status -s`(5.3.3)를 하면 이렇게 나온다.

```
?? "\353\251\224\353\252\250.md"
```

`메모`를 UTF-8 바이트로 쪼개 8진수로 적은 것이다. 읽을 수 없으니 그대로 보이게 바꾼다.

```
git config --global core.quotepath false
```

```
?? 메모.md
```

이 설정은 화면에 **보이는 모양**만 바꾼다. 파일 이름 자체나 저장소에는 영향이 없다. 그래도 2.6.6에서 정한 규칙대로 **코드 프로젝트의 파일과 폴더 이름은 영어 소문자**로 짓는다. 이 설정은 남이 만든 저장소의 한글 파일이나 문서 폴더를 읽을 때를 위한 것이다.

### 5.2.6 줄 끝 문자 — `core.autocrlf`와 `.gitattributes`

2장 실습 환경의 상자, 3.6.1의 `bash\r` 오류, 4.1.2의 상태 표시줄에서 **줄 끝 문자**를 만났다. 줄이 끝났음을 나타내는 보이지 않는 문자가 운영체제마다 다르다.

| | 줄 끝 문자 | 바이트 |
|---|---|---|
| macOS, 리눅스 | LF | `\n` |
| Windows(전통적으로) | CRLF | `\r\n` |

여러 사람이 여러 운영체제에서 같은 저장소를 쓰면 두 가지 문제가 생긴다.

1. **파일 전체가 바뀐 것처럼 보인다.** Windows의 어떤 편집기가 LF 파일을 CRLF로 저장하면 내용은 한 글자도 안 바뀌었는데 Git은 **모든 줄**이 바뀌었다고 본다. 진짜 변경이 그 속에 묻힌다(4.2.4에서 포맷 설정을 맞추는 이유와 같다).
2. **스크립트가 깨진다.** CRLF로 저장된 셸 스크립트는 macOS·리눅스에서 `bash\r`을 찾다가 실패한다(3.6.1).

Git은 이 문제를 **"저장소 안에는 LF로 보관하고, 작업 폴더에 꺼낼 때 필요하면 바꾼다"**는 방법으로 푼다. 이것을 정하는 곳이 두 군데다.

**`core.autocrlf` — 내 컴퓨터의 설정**

| 값 | 커밋할 때(작업 폴더 → 저장소) | 꺼낼 때(저장소 → 작업 폴더) | 어울리는 곳 |
|---|---|---|---|
| `true` | CRLF를 LF로 바꾼다 | LF를 CRLF로 바꾼다 | Windows |
| `input` | CRLF를 LF로 바꾼다 | 바꾸지 않는다 | macOS, 리눅스 |
| `false` | 바꾸지 않는다 | 바꾸지 않는다 | (아무것도 하지 않는다) |

Windows용 Git은 설치할 때 **시스템** 범위에 `core.autocrlf=true`를 정해 둔다("Checkout Windows-style, commit Unix-style line endings"라는 설치 선택지가 기본값이다). 확인한다.

```
# Windows
git config --show-origin core.autocrlf
```

```
file:C:/Program Files/Git/etc/gitconfig	true
```

`--show-origin`은 값이 **어느 설정 파일에서 왔는지** 함께 보여 준다(5.2.7). Windows는 이대로 둔다. 아무것도 나오지 않으면 직접 정한다(`git config --global core.autocrlf true`).

macOS는 기본값이 `false`다. 실수로 CRLF 파일이 들어와도 커밋할 때 LF로 바뀌도록 `input`으로 정한다.

```
# macOS
git config --global core.autocrlf input
```

**`.gitattributes` — 저장소의 규칙**

`core.autocrlf`는 **각자의 컴퓨터** 설정이라서 팀원이 모두 제대로 해 두었는지 알 수 없다. 그래서 저장소에 `.gitattributes` 파일을 두어 규칙을 정한다. 이 파일은 저장소에 커밋되므로 **그 저장소를 받는 모든 사람에게** 똑같이 적용되고, `core.autocrlf`보다 먼저 적용된다. `practice/shop`의 첫 커밋에 이 파일이 들어 있다.

```
* text=auto eol=lf
*.bat text eol=crlf
*.cmd text eol=crlf
```

한 줄에 "어떤 파일에(패턴), 어떤 속성을" 적는다. 패턴은 `.gitignore`와 거의 같은 문법이다(5.6.2).

- `* text=auto eol=lf` — 모든 파일(`*`)에 대해 텍스트 파일인지 바이너리 파일인지는 Git이 알아서 판단하고(`text=auto`), 텍스트 파일이면 저장소에도 작업 폴더에도 **LF로** 둔다(`eol=lf`). 운영체제에 관계없이 모두 LF가 되므로 `bash\r` 같은 문제가 생기지 않는다.
- `*.bat`, `*.cmd` — Windows의 명령 프롬프트용 배치 파일은 CRLF여야 제대로 돌기 때문에 이것만 예외로 CRLF로 꺼낸다.
- 이미지처럼 텍스트가 아닌 파일은 `text=auto`가 바이너리로 판단하고 손대지 않는다. 확실히 하고 싶으면 `*.png binary`처럼 적는다.

Windows에서도 작업 폴더를 LF로 두어도 괜찮을까? 이 과정에서 쓰는 도구는 모두 LF를 잘 다룬다. VS Code, 파이썬, PowerShell 7, Git이 그렇다. 메모장도 Windows 10(2018년)부터 LF 파일을 제대로 보여 준다. 이 과정에서는 **새 저장소를 만들면 이 세 줄짜리 `.gitattributes`를 함께 커밋한다.**

> **Windows에서 `git add`할 때 나오는 경고**
> `.gitattributes`가 없는 저장소에서 Windows 사용자가 LF로 된 파일을 `git add`하면 다음 경고가 나온다.
> ```
> warning: in the working copy of 'README.md', LF will be replaced by CRLF the next time Git touches it
> ```
> "다음에 Git이 이 파일을 작업 폴더에 꺼낼 때(5.7의 `git restore` 등) CRLF로 바꾸겠다"는 **안내**다. `core.autocrlf=true`이기 때문이다. 커밋은 정상으로 되고, 저장소에는 LF로 들어간다. 반대로 CRLF 파일을 `eol=lf`인 저장소에 넣으면 `CRLF will be replaced by LF`가 나온다. 둘 다 오류가 아니다. 이 장의 실습 파일은 `make_files.py`가 모두 LF로 만들었으므로, `.gitattributes`가 없는 `notes` 폴더(5.3)에서 Windows 사용자는 이 경고를 보게 된다.

파일들의 줄 끝 문자가 지금 어떤 상태인지는 다음 명령으로 본다. `practice/shop`에서 실행한다.

```
cd ~/devtools-lab/ch05/practice/shop
git ls-files --eol
```

```
i/lf    w/lf    attr/text=auto eol=lf 	.gitattributes
i/lf    w/lf    attr/text=auto eol=lf 	.gitignore
i/lf    w/lf    attr/text=auto eol=lf 	README.md
...
```

`i/`는 저장소(정확히는 5.3의 스테이징 영역), `w/`는 작업 폴더, `attr/`은 `.gitattributes`에서 온 속성이다. 둘 다 `lf`이고 속성이 `text=auto eol=lf`면 의도한 대로다.

> **VS Code에서 새 파일의 줄 끝 문자**
> Windows의 VS Code는 새 파일을 기본으로 CRLF로 만든다(상태 표시줄에 `CRLF`). `eol=lf`인 저장소에서는 커밋할 때 LF로 바뀌므로 문제는 없지만, 처음부터 LF로 만들고 싶으면 작업 공간 설정(`.vscode/settings.json`, 4.2.1)에 `"files.eol": "\n"`을 넣는다.

## 5.3 세 영역

이 절에서는 아직 저장소가 아닌 `practice/notes` 폴더를 저장소로 만들고 첫 커밋을 한다. 따라 하면서 명령마다 `git status`가 어떻게 바뀌는지 본다.

### 5.3.1 저장소 만들기 — `git init`

`notes` 폴더로 가서 `git status`를 실행해 본다. `git status`는 "지금 저장소의 상태를 알려 달라"는 명령이다.

```
cd ~/devtools-lab/ch05/practice/notes
git status
```

```
fatal: not a git repository (or any of the parent directories): .git
```

"Git 저장소가 아니다(이 폴더에도, 그 위의 어느 폴더에도 `.git`이 없다)"라는 오류다. Git 명령은 **저장소 안에서** 실행해야 한다(1.3.1). 이 오류를 보면 먼저 `pwd`로 위치를 확인한다. 종료 코드도 확인해 보면 `128`이다. Git은 명령을 아예 실행할 수 없을 때 128을 쓴다.

이 폴더를 저장소로 만든다.

```
git init
```

```
Initialized empty Git repository in /Users/jinyoung/devtools-lab/ch05/practice/notes/.git/
```

"빈 Git 저장소를 만들었다"는 뜻이다. 경로는 내 컴퓨터에 따라 다르다. 폴더를 숨김 파일까지 본다(2.4.5).

```
# macOS
ls -a

# Windows
Get-ChildItem -Force
```

```
.  ..  .git  README.md  git.md
```

`.git` 폴더가 생겼다. 2.4.5에서 예고한 대로 Windows용 Git은 이 폴더에 숨김 속성을 붙이므로, Windows에서는 `-Force`를 붙여야 보이고 `Mode` 칸에 `h`(hidden)가 들어 있다. 안을 들여다보면 이렇다.

```
# macOS
ls .git

# Windows
Get-ChildItem -Force .git
```

```
HEAD  config  description  hooks  info  objects  refs
```

`objects`에 커밋과 파일 내용(5.1.3의 blob, tree)이, `refs`에 브랜치 정보가, `config`에 이 저장소의 설정(5.2.1의 `--local`)이 들어 있다. Git 버전에 따라 목록이 조금 다를 수 있다. 기억할 것은 두 가지다.

- **`.git` 안의 파일은 손으로 고치지 않는다.** 모두 Git 명령으로 다룬다.
- **`.git` 폴더를 지우면 이력이 모두 사라진다.** 작업 폴더의 파일은 남지만, 지금까지의 커밋은 되살릴 수 없다. 폴더를 정리하다 `.git`을 지우지 않도록 조심한다.

Git 명령은 현재 폴더에서 시작해 **위쪽 폴더로 올라가며** `.git`을 찾는다. 그래서 저장소 안의 하위 폴더 어디에서 실행해도 같은 저장소를 다룬다. 지금 어느 저장소 안에 있는지는 다음 명령으로 확인한다.

```
git rev-parse --show-toplevel
```

```
/Users/jinyoung/devtools-lab/ch05/practice/notes
```

> **`git init`은 프로젝트 폴더에서만**
> `git init`을 실수로 홈 폴더(`~`)에서 실행하면 홈 아래의 **모든 폴더**가 그 저장소 안에 들어간다. 그 뒤로는 어느 폴더에서 `git status`를 해도 홈 전체의 파일이 "추적 안 됨"으로 쏟아진다. VS Code도 홈 폴더를 거대한 저장소로 알아보고 느려진다. `git init`을 하기 전에 `pwd`로 위치를 확인하고, `git status`가 처음 보는 파일을 잔뜩 보여 주면 `git rev-parse --show-toplevel`로 저장소의 뿌리가 어디인지 본다. 방금 실수로 만든 저장소라면 그 `.git` 폴더만 지우면 된다. macOS는 `rm -rf ~/.git`, Windows는 `Remove-Item -Recurse -Force ~/.git`이다. **지우기 전에 그 경로가 맞는지 두 번 확인한다.** 커밋이 쌓인 저장소의 `.git`을 지우면 이력이 모두 사라진다.

### 5.3.2 작업 폴더·스테이징 영역·저장소

Git을 이해하는 열쇠는 파일이 머무는 **세 영역**이다.

```
  작업 폴더                 스테이징 영역                저장소(.git)
  (working tree)            (staging area, index)        (repository)
 ┌──────────────┐          ┌──────────────┐            ┌──────────────┐
 │ 내가 편집기로 │ git add  │ 다음 커밋에  │ git commit │ 커밋(스냅숏)  │
 │ 보고 고치는   │ ───────▶ │ 넣을 내용    │ ─────────▶ │ 들이 쌓인다   │
 │ 파일들       │          │ (커밋의 초안) │            │              │
 └──────────────┘          └──────────────┘            └──────────────┘
```

- **작업 폴더** — 탐색기와 VS Code에서 보이는 보통의 파일들이다. 편집기로 고치는 곳이다.
- **스테이징 영역** — **다음 커밋에 들어갈 내용**을 모아 두는 곳이다. 인덱스(index)라고도 한다. `git add`로 작업 폴더의 파일을 여기에 올린다(스테이징한다).
- **저장소** — `git commit`을 하면 스테이징 영역의 내용이 그대로 스냅숏이 되어 저장소에 쌓인다.

왜 한 단계가 더 있을까? 작업 폴더에는 늘 여러 가지가 섞여 있기 때문이다. 기능 하나를 만들다 보면 다른 곳의 오타도 고치고, 실험용 파일도 만들고, 디버깅용 `print()`도 넣는다. 스테이징 영역은 그중에서 **이번 커밋에 넣을 것만 골라 담는 상자**다. 택배에 비유하면 물건을 상자에 담는 것이 `git add`, 상자를 봉하고 송장(커밋 메시지)을 붙여 보내는 것이 `git commit`이다. 5.5에서는 파일 하나 안의 변경 중 일부만 골라 담는 방법도 배운다.

스테이징 영역은 "바뀐 파일 목록"이 아니라 **다음 커밋의 완전한 스냅숏**이라는 점도 알아 두자. 커밋 직후에는 스테이징 영역의 내용이 마지막 커밋과 똑같다. 파일을 고치고 `git add`하면 스테이징 영역의 그 파일만 새 내용으로 바뀐다. 5.4의 `git diff`와 5.7의 `git restore`가 이 사실에 기대어 동작한다.

### 5.3.3 `git status` 읽기

저장소를 만든 직후의 상태를 본다.

```
git status
```

```
On branch main

No commits yet

Untracked files:
  (use "git add <file>..." to include in what will be committed)
	README.md
	git.md

nothing added to commit but untracked files present (use "git add" to track)
```

한 줄씩 읽는다.

- `On branch main` — 지금 `main` 브랜치에 있다(5.2.3에서 정한 이름).
- `No commits yet` — 아직 커밋이 하나도 없다.
- `Untracked files:` — **추적하지 않는 파일**이다. 작업 폴더에 있지만 Git이 한 번도 기록한 적 없는 파일이다. 괄호 안은 "커밋에 넣으려면 `git add <파일>`을 하라"는 안내다.
- 마지막 줄 — "커밋할 것으로 올린 것은 없고, 추적하지 않는 파일만 있다"는 요약이다.

`git status`는 이처럼 **다음에 할 수 있는 명령**을 괄호 안에 알려 준다. 처음에는 이 안내를 읽는 것만으로도 많이 배운다. 상태가 헷갈릴 때마다 `git status`부터 실행한다.

출력이 길게 느껴지면 짧은 형식을 쓴다.

```
git status -s
```

```
?? README.md
?? git.md
```

짧은 형식은 파일마다 **두 글자**로 상태를 보여 준다. **왼쪽 글자는 스테이징 영역**(마지막 커밋과 비교해 스테이징된 변경), **오른쪽 글자는 작업 폴더**(스테이징 영역과 비교해 아직 스테이징하지 않은 변경)의 상태다.

| 표시 | 뜻 |
|---|---|
| `??` | 추적하지 않는 파일 |
| `A ` | 새 파일을 스테이징했다(Added) |
| ` M` | 고쳤지만 스테이징하지 않았다(Modified) |
| `M ` | 고친 것을 스테이징했다 |
| `MM` | 고친 것을 스테이징한 뒤 **또 고쳤다** |
| ` D`, `D ` | 지웠다(Deleted). 스테이징 전·후 |
| `R ` | 이름을 바꿨다(Renamed, 5.6.6) |
| `!!` | 무시하는 파일(`--ignored`를 줄 때만 보인다, 5.6.4) |

`A `과 ` M`처럼 공백의 위치가 뜻을 가진다. 터미널은 대개 왼쪽 글자를 초록, 오른쪽 글자를 빨강으로 칠해 준다. **초록은 다음 커밋에 들어가고, 빨강은 들어가지 않는다**고 읽으면 된다.

### 5.3.4 `git add` — 스테이징하기

`README.md`를 스테이징한다.

```
git add README.md
git status
```

```
On branch main

No commits yet

Changes to be committed:
  (use "git rm --cached <file>..." to unstage)
	new file:   README.md

Untracked files:
  (use "git add <file>..." to include in what will be committed)
	git.md
```

`README.md`가 `Changes to be committed:`(커밋될 변경) 아래로 옮겨 갔다. `new file`은 "새로 추적하기 시작한 파일"이다. 짧은 형식으로는 다음과 같다.

```
A  README.md
?? git.md
```

Windows에서는 `git add`를 할 때 `LF will be replaced by CRLF`라는 경고가 나올 수 있다. 5.2.6의 상자에서 본 안내이며 오류가 아니다. 이 폴더에는 `.gitattributes`가 없기 때문이다.

`git add`에는 파일 여러 개, 폴더, `.`을 줄 수 있다.

| 명령 | 스테이징하는 것 |
|---|---|
| `git add a.py b.py` | 두 파일 |
| `git add shop/` | `shop` 폴더 아래의 바뀐 파일과 새 파일 모두 |
| `git add .` | **현재 폴더 아래의** 바뀐 파일과 새 파일 모두 |
| `git add -A` | 저장소 전체의 바뀐 파일, 새 파일, 지운 파일 모두 |

`git add .`은 편하지만 위험하다. 작업 폴더에 있는 **모든 것**이 올라간다. `.env`에 든 API 키, 실험하다 만든 큰 데이터 파일, 개인 메모까지 함께 들어갈 수 있다. 이 과정에서는 다음 습관을 지킨다.

1. `git add .`이나 `git add -A`를 쓰기 전에 **먼저 `git status`로 무엇이 올라갈지 본다.**
2. 올라가면 안 되는 파일이 보이면 `.gitignore`에 넣는다(5.6).
3. 올린 뒤에도 `git status`로 다시 확인한다.

AI 코딩 도구가 실행하려는 `git add .`도 같은 기준으로 읽는다(3.8). 그 전에 `git status`를 보았는지가 판단 기준이다.

### 5.3.5 `git commit` — 기록하기

스테이징한 것을 커밋한다. `-m` 뒤에 커밋 메시지를 준다.

```
git commit -m "공부 노트 시작"
```

```
[main (root-commit) 76f709e] 공부 노트 시작
 1 file changed, 3 insertions(+)
 create mode 100644 README.md
```

- `[main (root-commit) 76f709e]` — `main` 브랜치에 커밋했다. `root-commit`은 부모가 없는 **첫 커밋**이라는 뜻이다. `76f709e`는 이 커밋의 짧은 번호다. 작성자와 시각이 들어가서 계산되므로(5.1.3의 상자) 내 번호는 교재와 다르다.
- `1 file changed, 3 insertions(+)` — 파일 하나에서 세 줄이 늘었다.
- `create mode 100644 README.md` — 새 파일이 생겼다. `100644`는 "보통 파일"이라는 표시다.

상태를 다시 본다.

```
git status
```

```
On branch main
Untracked files:
  (use "git add <file>..." to include in what will be committed)
	git.md

nothing added to commit but untracked files present (use "git add" to track)
```

`README.md`가 목록에서 사라졌다. 커밋한 뒤 고치지 않은 파일은 `git status`에 나오지 않는다. **`git status`에 보이지 않는 추적 파일은 마지막 커밋과 같다**는 뜻이다.

이번에는 `-m` 없이 커밋해서 5.2.4에서 정한 편집기로 메시지를 써 본다.

```
git add git.md
git commit
```

VS Code에 `COMMIT_EDITMSG` 탭이 열리고 터미널은 `hint: Waiting for your editor to close the file...`에서 기다린다. 탭의 내용은 이렇다.

```

# Please enter the commit message for your changes. Lines starting
# with '#' will be ignored, and an empty message aborts the commit.
#
# On branch main
# Changes to be committed:
#	new file:   git.md
#
```

"커밋 메시지를 입력하라. `#`으로 시작하는 줄은 무시하고, 메시지가 비면 커밋을 취소한다"는 안내와 함께, 이번 커밋에 들어갈 파일이 적혀 있다. 맨 윗줄(빈 줄)에 메시지를 쓴다.

```
Git 노트 추가
```

**저장하고**(`Cmd/Ctrl+S`) **탭을 닫는다**(`Cmd/Ctrl+W`). 터미널에 결과가 나온다.

```
[main fe233c7] Git 노트 추가
 1 file changed, 3 insertions(+)
 create mode 100644 git.md
```

저장하지 않고 닫거나 메시지를 비워 두고 닫으면 다음과 같이 커밋이 취소된다. 스테이징한 내용은 그대로 남아 있으니 다시 `git commit`을 하면 된다.

```
Aborting commit due to empty commit message.
```

`-m`은 한 줄 메시지에, 편집기는 제목과 본문이 있는 긴 메시지(5.5.2)에 쓴다. 지금까지의 커밋을 본다(5.4.3).

```
git log --oneline
```

```
fe233c7 Git 노트 추가
76f709e 공부 노트 시작
```

### 5.3.6 파일의 상태 변화

VS Code에서 `git.md`의 끝에 한 줄을 더하고 저장한다.

```markdown
- 커밋하기 전에 git status를 본다.
```

줄을 입력한 뒤 **`Enter`까지 눌러** 파일이 줄바꿈으로 끝나게 한다. 이 장에서 줄을 더할 때는 모두 그렇게 한다(이유는 5.4.1의 상자에서 본다).

```
git status
```

```
On branch main
Changes not staged for commit:
  (use "git add <file>..." to update what will be committed)
  (use "git restore <file>..." to discard changes in working directory)
	modified:   git.md

no changes added to commit (use "git add" and/or "git commit -a")
```

`Changes not staged for commit:`(스테이징하지 않은 변경) 아래에 `modified`(수정됨)로 나온다. 괄호 안에 두 가지 길이 보인다. `git add`로 스테이징하거나, `git restore`로 변경을 버리는 것이다(5.7). 짧은 형식은 ` M git.md`다. 스테이징한다.

```
git add git.md
git status -s
```

```
M  git.md
```

`M`이 오른쪽에서 왼쪽으로 옮겨 갔다. 이제 **커밋하기 전에** `git.md`에 한 줄을 더 더하고 저장한다.

```markdown
- 세 영역: 작업 폴더, 스테이징 영역, 저장소
```

```
git status
```

```
On branch main
Changes to be committed:
  (use "git restore --staged <file>..." to unstage)
	modified:   git.md

Changes not staged for commit:
  (use "git add <file>..." to update what will be committed)
  (use "git restore <file>..." to discard changes in working directory)
	modified:   git.md
```

같은 파일이 두 곳에 나온다. 짧은 형식은 `MM git.md`다. 이상해 보이지만 5.3.2의 그림으로 보면 당연하다.

- 스테이징 영역에는 `git add`를 한 **그 순간의** `git.md`(첫 번째 줄만 더한 것)가 있다.
- 작업 폴더의 `git.md`는 그 뒤에 한 줄이 더 늘었다.

`git add`는 "이 파일을 지켜봐 달라"는 명령이 아니라 **"지금 이 내용을 다음 커밋에 넣어 달라"**는 명령이다. 이 상태에서 `git commit`을 하면 **첫 번째 줄만** 커밋된다. 둘 다 넣으려면 다시 `git add`한다. 두 영역에 무엇이 들어 있는지는 5.4.1에서 `git diff`로 직접 확인한다. 지금은 둘 다 넣어 커밋한다.

```
git add git.md
git commit -m "Git 노트에 세 영역 정리"
```

```
[main 3dff6ce] Git 노트에 세 영역 정리
 1 file changed, 2 insertions(+)
```

파일이 거치는 상태를 정리하면 다음과 같다.

```
                     git add                       git commit
  추적 안 됨  ──────────────────▶  스테이징됨  ──────────────────▶  커밋됨
 (untracked)                       (staged)                    (unmodified)
                                       ▲                             │
                                       │ git add                     │ 편집기로 고친다
                                       │                             ▼
                                       └────────────────────────  수정됨
                                                                 (modified)
```

| 상태 | `git status`의 제목 | 짧은 형식 |
|---|---|---|
| 추적 안 됨 | `Untracked files` | `??` |
| 스테이징됨 | `Changes to be committed` | `A `, `M `, `D ` |
| 수정됨(스테이징 안 함) | `Changes not staged for commit` | ` M`, ` D` |
| 커밋됨(마지막 커밋과 같음) | 나오지 않는다 | 나오지 않는다 |

> **`git commit -a`**
> `git status`의 안내에 보이는 `git commit -a`는 **이미 추적하는 파일 중 바뀐 것**을 모두 스테이징하고 바로 커밋한다. 추적하지 않는 새 파일은 넣지 않는다. `git add`를 건너뛰니 편하지만, 무엇을 커밋하는지 고르고 확인하는 단계도 함께 건너뛴다. 이 과정에서는 `git add`로 골라 담고 확인한 뒤 커밋한다(5.5.4).

### 5.3.7 VS Code의 소스 제어 화면

여기까지 명령으로 한 일을 VS Code에서도 할 수 있다. `notes` 폴더를 VS Code 창 하나로 연다(4.1.1).

```
code .
```

액티비티 막대의 **소스 제어**(Source Control, 갈라지는 선 모양 아이콘, `Ctrl+Shift+G`)를 누르면 소스 제어 보기가 열린다. 상태 표시줄 왼쪽에는 지금 브랜치 이름(`main`)이 보인다(4.1.2에서 예고한 것이다).

VS Code에서 `git.md`에 한 줄을 더하고 저장한 뒤 화면을 살펴본다.

- 소스 제어 보기의 **Changes**(변경 사항) 아래에 `git.md`가 `M` 표시와 함께 나온다. 이것이 ` M`(스테이징하지 않은 수정)이다.
- 탐색기에서도 파일 이름이 색으로 표시되고 오른쪽에 `M`이 붙는다.
- 편집기 왼쪽 여백(거터)에 바뀐 줄이 색 막대로 표시된다. 초록은 더한 줄, 파랑은 바뀐 줄, 빨간 삼각형은 지운 자리다.

화면의 요소와 명령은 다음과 같이 대응한다.

| VS Code | 명령 |
|---|---|
| 저장소가 아닌 폴더에서 **Initialize Repository**(리포지토리 초기화) 버튼 | `git init` |
| 파일 이름 오른쪽의 표시 `U`, `A`, `M`, `D`, `R` | `git status`의 상태. `U`는 추적 안 됨(Untracked), 나머지는 5.3.3의 표와 같다 |
| **Changes**(변경 사항) 목록 | `Changes not staged for commit` + `Untracked files` |
| **Staged Changes**(스테이징된 변경 사항) 목록 | `Changes to be committed` |
| 파일 오른쪽의 **+**(Stage Changes) | `git add 파일` |
| **Staged Changes**의 파일 오른쪽 **−**(Unstage Changes) | `git restore --staged 파일`(5.7.3) |
| 파일 오른쪽의 **↶**(Discard Changes) | `git restore 파일`. 추적하지 않는 파일이면 **파일을 지운다**(5.7.7) |
| 메시지 칸에 쓰고 **Commit**(커밋) 버튼 | `git commit -m "메시지"` |
| 목록의 파일을 누르면 열리는 비교 화면 | `git diff`(5.4.8) |

`+`를 눌러 `git.md`를 스테이징하면 **Staged Changes**로 옮겨 간다. 터미널에서 `git status -s`를 해 보면 `M  git.md`다. 화면과 명령이 같은 저장소를 보고 있다는 것을 확인할 수 있다. 메시지 칸에 `Git 노트에 표기법 추가`처럼 쓰고 **Commit**을 누르면 커밋된다.

> **"스테이징된 변경 사항이 없습니다. 모두 스테이징하고 커밋할까요?"**
> 아무것도 스테이징하지 않은 채 **Commit**을 누르면 VS Code가 "There are no staged changes to commit. Would you like to stage all your changes and commit them directly?"라고 묻는다. **Yes**나 **Always**를 고르면 추적하지 않는 파일까지 포함해 **모든 변경을** 스테이징하고 커밋한다. 확인 없이 `git add -A`와 `git commit`을 한 것과 같다. 이 과정에서는 고르지 않는다. 대화 상자를 닫고 무엇을 넣을지 골라 스테이징한다. 실수로 **Always**를 골랐다면 설정에서 `git.enableSmartCommit`을 끈다.

## 5.4 변경 확인

커밋하기 전에는 "무엇을 커밋하려는지", 커밋한 뒤에는 "언제 무엇이 왜 바뀌었는지"를 확인할 수 있어야 한다. 4.6.3에서 AI가 고친 파일을 비교 화면으로 검토했다. 이 절에서는 같은 일을 Git으로 한다.

### 5.4.1 `git diff` — 아직 스테이징하지 않은 변경

5.3.6에서 `git.md`가 `MM` 상태였던 순간으로 돌아가 보자. 스테이징 영역에는 첫 번째 줄을 더한 `git.md`가, 작업 폴더에는 두 줄을 더한 `git.md`가 있었다. 그 상태에서 `git diff`를 실행하면 다음이 나온다.

```
git diff
```

```
diff --git a/git.md b/git.md
index ad75c9d..b6b0540 100644
--- a/git.md
+++ b/git.md
@@ -2,3 +2,4 @@
 
 - 커밋은 스냅숏이다.
 - 커밋하기 전에 git status를 본다.
+- 세 영역: 작업 폴더, 스테이징 영역, 저장소
```

옵션 없는 `git diff`는 **작업 폴더를 스테이징 영역과 비교한다.** 그래서 이미 스테이징한 첫 번째 줄은 나오지 않고, 그 뒤에 더한 두 번째 줄만 나온다. 이 형식을 **통합 diff**(unified diff)라고 한다. 4.6.3의 비교 화면이 왼쪽·오른쪽으로 보여 주던 것을 위아래 한 줄씩으로 보여 준다. 읽는 법은 다음과 같다.

| 줄 | 뜻 |
|---|---|
| `diff --git a/git.md b/git.md` | 비교하는 파일. `a/`는 **전**(왼쪽), `b/`는 **후**(오른쪽)다 |
| `index ad75c9d..b6b0540 100644` | 전·후 파일 내용의 번호(5.1.3의 blob)와 파일 종류 |
| `--- a/git.md`, `+++ b/git.md` | 아래에서 `-`는 전 파일의 줄, `+`는 후 파일의 줄이다 |
| `@@ -2,3 +2,4 @@` | **변경 덩어리**(hunk)의 위치. 전 파일의 2번째 줄부터 3줄이, 후 파일에서는 2번째 줄부터 4줄이 되었다 |
| 공백으로 시작하는 줄 | 바뀌지 않은 앞뒤 줄(문맥). 기본으로 위아래 3줄씩 보여 준다 |
| `+`로 시작하는 줄 | 더한 줄 |
| `-`로 시작하는 줄 | 지운 줄 |

한 줄을 **고친** 것은 "옛 줄을 지우고 새 줄을 더했다"로 나타난다. `-` 줄 바로 아래에 `+` 줄이 오면 그 줄이 바뀐 것이다. 터미널은 `-` 줄을 빨강, `+` 줄을 초록으로 칠해 준다. 출력이 화면보다 길면 `less`로 열리므로 `q`로 나온다(2.5.2). 새로 만든 **추적하지 않는 파일**은 `git diff`에 나오지 않는다. Git이 아직 그 파일을 비교할 대상으로 삼지 않기 때문이다.

> **`\ No newline at end of file`**
> diff의 끝에 이 줄이 보이면 그 파일의 마지막 줄 뒤에 줄바꿈 문자가 없다는 뜻이다. 편집기에서 마지막 줄을 입력하고 `Enter`를 누르지 않은 채 저장하면 이렇게 된다. 프로그램은 대개 문제없이 돌지만, 그 뒤에 누가 줄을 더하면 원래 마지막 줄까지 "바뀐 줄"로 나와 diff가 지저분해진다. 텍스트 파일은 줄바꿈으로 끝내는 것이 관례다. VS Code 설정 `files.insertFinalNewline`을 켜면 저장할 때 자동으로 넣어 준다. 4.2의 작업 공간 설정에 넣어 두기 좋은 설정이다.

### 5.4.2 `git diff --staged` — 다음 커밋에 들어갈 변경

같은 순간에 `--staged`를 붙이면 이렇게 나온다.

```
git diff --staged
```

```
diff --git a/git.md b/git.md
index 0888ba6..ad75c9d 100644
--- a/git.md
+++ b/git.md
@@ -1,3 +1,4 @@
 # Git
 
 - 커밋은 스냅숏이다.
+- 커밋하기 전에 git status를 본다.
```

`git diff --staged`는 **스테이징 영역을 마지막 커밋과 비교한다.** 즉 **지금 커밋하면 들어갈 변경**이다. 첫 번째 줄만 보인다. `--cached`도 같은 뜻이다(옛 이름이라 문서와 AI의 답에 자주 나온다). 그리고 `git diff HEAD`는 작업 폴더를 마지막 커밋과 바로 비교하므로 두 줄이 다 보인다.

```
git diff HEAD
```

```
diff --git a/git.md b/git.md
index 0888ba6..b6b0540 100644
--- a/git.md
+++ b/git.md
@@ -1,3 +1,5 @@
 # Git
 
 - 커밋은 스냅숏이다.
+- 커밋하기 전에 git status를 본다.
+- 세 영역: 작업 폴더, 스테이징 영역, 저장소
```

`index` 줄의 번호를 보면 세 명령이 무엇을 비교했는지 드러난다. `0888ba6`이 마지막 커밋의 `git.md`, `ad75c9d`가 스테이징 영역의 `git.md`, `b6b0540`이 작업 폴더의 `git.md`다.

```
  마지막 커밋(HEAD)        스테이징 영역              작업 폴더
     0888ba6                 ad75c9d                  b6b0540
        │                       │                        │
        └── git diff --staged ──┘                        │
                                └────── git diff ────────┘
        └──────────────────── git diff HEAD ─────────────┘
```

가장 흔한 착각이 이것이다. **`git add`한 직후 `git diff`를 하면 아무것도 나오지 않는다.** 변경이 사라진 것이 아니라 스테이징 영역으로 옮겨 가서, 작업 폴더와 스테이징 영역이 같아졌기 때문이다. 그때는 `git diff --staged`로 본다. 커밋하기 직전에 `git diff --staged`를 보는 습관은 5.5.4에서 다시 다룬다.

**가장 최근 커밋부터** 거꾸로 나온다. 커밋마다 번호(해시), 작성자, 시각, 메시지가 보인다. 메시지의 첫 줄이 **제목**, 빈 줄 다음이 **본문**이다(5.5.2). `less` 화면이므로 `Space`로 넘기고 `q`로 나온다.

`git log`는 옵션이 아주 많다. 자주 쓰는 것을 정리한다.

| 명령 | 보여 주는 것 |
|---|---|
| `git log --oneline` | 커밋마다 한 줄(짧은 해시와 제목) |
| `git log -n 3` | 최근 3개만(`-3`도 같다) |
| `git log --stat` | 커밋마다 바뀐 파일과 줄 수 |
| `git log -p` | 커밋마다 바뀐 내용(diff) 전체 |
| `git log --graph` | 커밋의 연결을 선으로 그린다(브랜치를 쓰는 6장에서 쓸모가 커진다) |

| `git log --author=이름` | 작성자 이름이나 이메일에 그 글자가 든 커밋만 |
| `git log --grep=글자` | 커밋 메시지에 그 글자가 든 커밋만 |
| `git log -S 글자` | 바뀐 내용에서 그 글자의 **개수가 달라진** 커밋만(그 글자가 들어오거나 나간 커밋) |

옵션은 섞어 쓸 수 있다. 몇 가지 실행해 본다.

```

```

```

```

이력을 훑어볼 때 가장 많이 쓰는 모양이다. 제목만 읽어도 프로젝트가 어떻게 자랐는지 보인다. 좋은 커밋 메시지가 왜 중요한지가 여기서 드러난다(5.5.2).

```
git log --oneline -- shop/pricing.py
```

```
1ed2593 묶음 할인 기준을 README와 맞춤
2cd870d 쿠폰 할인 추가
356d0e1 묶음 할인 추가
```

`shop/pricing.py`를 바꾼 커밋만 나왔다. `--`는 2.2.2에서 본 대로 "여기서부터는 옵션이 아니라 경로다"라는 표시다.

```
git log --stat -n 2 --oneline
```

```
9666df9 금액을 천 단위 쉼표로 표시
 shop/cli.py | 4 ++--
 1 file changed, 2 insertions(+), 2 deletions(-)
1ed2593 묶음 할인 기준을 README와 맞춤
 shop/pricing.py | 2 +-
 1 file changed, 1 insertion(+), 1 deletion(-)
```

`4 ++--`는 네 줄이 바뀌었는데 두 줄이 더해지고 두 줄이 지워졌다는 뜻이다. 한 줄을 고치면 1줄 지우고 1줄 더한 것으로 센다(5.4.1).

```

```

```

```

`qty >=`라는 글자가 처음 들어온 커밋을 찾았다. "이 코드가 언제 들어왔나"를 찾을 때 쓴다. 메시지가 아니라 **내용**을 찾는다는 점이 `--grep`과 다르다.

```
git log --format="%h %an %ad %s" --date=short
```

```
9666df9 박도윤 2026-11-06 금액을 천 단위 쉼표로 표시
1ed2593 이서연 2026-11-05 묶음 할인 기준을 README와 맞춤
98cad66 이서연 2026-11-05 시험 스크립트 추가
2cd870d 박도윤 2026-11-04 쿠폰 할인 추가
356d0e1 박도윤 2026-11-03 묶음 할인 추가
cb2bb27 이서연 2026-11-02 주문 CSV 읽기 추가
cb8185a 이서연 2026-11-02 프로젝트 뼈대 만들기
```

`--format`으로 원하는 항목만 골라 한 줄로 만든다. `%h` 짧은 해시, `%an` 작성자 이름, `%ad` 작성 시각, `%s` 제목이다. 이런 출력은 3장의 파이프로 이어 세기 좋다. 사람별 커밋 수는 `git shortlog -sn`으로 바로 볼 수도 있다.

> **`git log`가 끝나지 않을 때**
> `git log`를 실행했는데 프롬프트가 돌아오지 않고 화면 아래에 `:`나 `(END)`가 보이면 `less` 화면이다. `q`를 누른다. Windows에서도 같다(2.5.2). 짧은 출력을 `less` 없이 바로 보고 싶으면 `git --no-pager log --oneline`처럼 `git` 바로 뒤에 `--no-pager`를 붙인다.

### 5.4.4 `git show` — 커밋 하나 자세히 보기

`git show`는 커밋 하나의 정보와 **그 커밋이 바꾼 내용**(부모 커밋과의 diff)을 함께 보여 준다. 버그를 고친 커밋을 본다.

```
git show 1ed2593
```

```
commit 1ed259384f242998491fc8ab4192a29c477346f6
Author: 이서연 <seoyeon@example.com>
Date:   Thu Nov 5 10:10:00 2026 +0900

    묶음 할인 기준을 README와 맞춤
    
    README에는 "10개 이상"이라고 적혀 있는데 코드는 qty > 10으로 비교해서
    10개짜리 주문에 할인을 주지 않았다. check_orders.py의 small.csv 시험이
    실패해서 발견했다.

diff --git a/shop/pricing.py b/shop/pricing.py
index 6e68f54..87ab4ff 100644
--- a/shop/pricing.py
+++ b/shop/pricing.py
@@ -15,7 +15,7 @@ def coupon_rate() -> float:
 
 def line_discount(line: OrderLine) -> int:
     """주문 한 줄의 묶음 할인 금액."""
-    if line.qty > BULK_QTY:
+    if line.qty >= BULK_QTY:
         return int(line.subtotal() * BULK_RATE)
     return 0
 
```

4장에서 디버거로 찾은 바로 그 버그다. 메시지의 본문이 **왜** 고쳤는지, **어떻게 발견했는지** 알려 준다. diff만 보면 `>`가 `>=`로 바뀐 것만 알 수 있지만, 본문 덕분에 이것이 실수가 아니라 README의 규칙에 맞춘 의도된 변경이라는 것을 안다. `@@` 줄 끝의 `def coupon_rate() -> float:`는 Git이 덧붙여 준 **이 덩어리 바로 위의 함수 이름**이다. 덩어리가 어느 함수 근처인지 짐작하는 데 도움이 된다(정확히 그 함수 안이라는 뜻은 아니다).

자주 쓰는 모양은 다음과 같다.

| 명령 | 보여 주는 것 |
|---|---|
| `git show` | 마지막 커밋(`HEAD`) |
| `git show --stat 커밋` | 정보와 바뀐 파일 목록만 |
| `git show 커밋 -- 경로` | 그 커밋에서 그 파일의 변경만 |
| `git show 커밋:경로` | 그 커밋 **시점의** 파일 내용 전체(실습 5-1) |

마지막 모양의 차이에 주의한다. `git show 커밋 -- README.md`는 그 커밋이 README를 **어떻게 바꿨는지**(diff)를, `git show 커밋:README.md`는 그 시점 README의 **내용 전체**를 보여 준다. 둘 다 작업 폴더의 파일은 건드리지 않는다.

### 5.4.5 커밋을 가리키는 이름

명령에 커밋을 주는 방법은 여러 가지다.

| 쓰는 법 | 가리키는 커밋 |
|---|---|
| `1ed259384f242998491fc8ab4192a29c477346f6` | 전체 해시(40자리 16진수). 커밋의 진짜 이름이다 |
| `1ed2593`, `1ed25` | 해시의 앞부분. 저장소 안에서 겹치지 않으면 4자리 이상 아무 길이나 된다. 보통 7자리를 쓴다 |
| `HEAD` | 지금 보고 있는 커밋. 보통은 지금 브랜치의 가장 최근 커밋이다(6장에서 자세히) |
| `HEAD~1`, `HEAD~` | `HEAD`의 부모(바로 앞 커밋) |
| `HEAD~3` | `HEAD`에서 세 번 거슬러 올라간 커밋 |
| `1ed2593~1` | 그 커밋의 부모 |

**해시**(hash)는 커밋의 내용(스냅숏, 작성자, 시각, 메시지, 부모)으로 계산한 번호다. 내용이 한 글자만 달라도 완전히 다른 번호가 나온다. 그래서 해시가 같으면 같은 커밋이라고 믿을 수 있다. 커밋을 고치면 번호가 바뀐다는 사실은 7장에서 중요해진다.

`HEAD~1` 대신 `HEAD^`라고 쓴 자료도 많다. 이 장의 범위에서는 같은 뜻이다. 다만 셸에 따라 `^`를 특별하게 해석하는 경우가 있으므로(옛 Windows 명령 프롬프트 등) 이 교재에서는 `~`를 쓴다.

### 5.4.6 두 커밋 비교하기

`git diff`에 커밋 두 개를 주면 **두 스냅숏을 비교**한다(5.1.3). 이웃한 커밋이 아니어도 된다.

```
git diff HEAD~2 HEAD -- shop/
```

```
diff --git a/shop/cli.py b/shop/cli.py
index da85a29..3b70115 100644
--- a/shop/cli.py
+++ b/shop/cli.py
@@ -10,8 +10,8 @@ USAGE = "사용법: python main.py 주문파일.csv"
 
 
 def won(amount: int) -> str:
-    """금액을 '1234원' 모양으로 돌려준다."""
-    return f"{amount}원"
+    """금액을 '1,234원' 모양으로 돌려준다."""
+    return f"{amount:,}원"
 
 
 def main() -> None:
diff --git a/shop/pricing.py b/shop/pricing.py
index 6e68f54..87ab4ff 100644
--- a/shop/pricing.py
+++ b/shop/pricing.py
@@ -15,7 +15,7 @@ def coupon_rate() -> float:
 
 def line_discount(line: OrderLine) -> int:
     """주문 한 줄의 묶음 할인 금액."""
-    if line.qty > BULK_QTY:
+    if line.qty >= BULK_QTY:
         return int(line.subtotal() * BULK_RATE)
     return 0
 
```

두 번 앞 커밋과 지금 사이에 `shop` 폴더에서 바뀐 것, 즉 마지막 두 커밋의 변경이 합쳐져 나왔다. 앞에 오는 커밋이 `a/`(전), 뒤에 오는 커밋이 `b/`(후)다. 순서를 바꾸면 `+`와 `-`가 뒤집힌다.

| 명령 | 비교하는 것 |
|---|---|
| `git diff 커밋A 커밋B` | 커밋 A의 스냅숏과 커밋 B의 스냅숏 |
| `git diff 커밋A 커밋B --stat` | 바뀐 파일과 줄 수만 |
| `git diff 커밋` | 그 커밋과 **지금 작업 폴더** |
| `git diff --word-diff` | 줄 단위가 아니라 낱말 단위로. 한 줄이 긴 문서(README 등)의 변경을 볼 때 좋다 |

> **`git diff`의 비교 대상 정리**
> 옵션 없이 `git diff`는 작업 폴더 ↔ 스테이징 영역, `--staged`는 스테이징 영역 ↔ 마지막 커밋, `HEAD`(또는 커밋 하나)는 작업 폴더 ↔ 그 커밋, 커밋 두 개는 그 둘이다. 헷갈리면 `index` 줄의 번호를 보고 무엇과 무엇을 비교했는지 확인한다.

### 5.4.7 줄별 변경 이력 — `git blame`

"이 줄은 누가 언제 왜 이렇게 썼나?"를 알고 싶을 때 `git blame`을 쓴다. 파일의 **줄마다** 그 줄을 마지막으로 바꾼 커밋을 보여 준다. `-L 시작,끝`으로 줄 범위를 줄 수 있다.

```
git blame -L 16,21 shop/pricing.py
```

```
356d0e14 (박도윤 2026-11-03 11:05:00 +0900 16) def line_discount(line: OrderLine) -> int:
356d0e14 (박도윤 2026-11-03 11:05:00 +0900 17)     """주문 한 줄의 묶음 할인 금액."""
1ed25938 (이서연 2026-11-05 10:10:00 +0900 18)     if line.qty >= BULK_QTY:
356d0e14 (박도윤 2026-11-03 11:05:00 +0900 19)         return int(line.subtotal() * BULK_RATE)
356d0e14 (박도윤 2026-11-03 11:05:00 +0900 20)     return 0
356d0e14 (박도윤 2026-11-03 11:05:00 +0900 21) 
```

줄마다 `커밋 (작성자 시각 줄번호) 내용`이다. 18번째 줄만 이서연이 11월 5일에 바꿨고, 나머지는 박도윤이 11월 3일에 쓴 그대로다. 18번째 줄이 **왜** 바뀌었는지는 그 커밋을 보면 된다. `git show 1ed25938`이다. blame으로 커밋을 찾고, show로 그 커밋의 메시지와 변경을 읽는 것이 한 묶음이다.

이름이 "blame"(탓하다)이지만 누구를 탓하려고 쓰는 명령이 아니다. 코드를 고치기 전에 **그 줄이 왜 그렇게 되어 있는지** 알아보는 명령이다. 이상해 보이는 코드에도 이유가 있는 경우가 많고, 그 이유는 대개 커밋 메시지에 있다(있어야 한다).

> **줄 범위의 이력 전체를 보고 싶으면**
> `git blame`은 각 줄을 **마지막으로** 바꾼 커밋만 보여 준다. 그 전에 어떻게 바뀌어 왔는지 보려면 `git log -L 16,21:shop/pricing.py`를 쓴다. 그 범위를 바꾼 커밋들이 diff와 함께 차례로 나온다.

### 5.4.8 VS Code에서 보기

명령으로 본 것들을 VS Code에서도 볼 수 있다. `practice/shop` 폴더를 VS Code 창으로 연다(`code .`).

**비교 화면** — 소스 제어 보기의 **Changes** 목록에서 파일을 누르면 4.6.3의 비교 화면이 열린다. 왼쪽이 스테이징 영역(스테이징한 것이 없으면 마지막 커밋과 같다), 오른쪽이 작업 폴더다. `git diff`와 같다. **Staged Changes** 목록의 파일을 누르면 왼쪽이 마지막 커밋, 오른쪽이 스테이징 영역이다. `git diff --staged`와 같다. 탭 제목에 `(Working Tree)`, `(Index)`처럼 무엇을 비교하는지 적혀 있다.

**커밋 그래프** — 소스 제어 보기 아래쪽의 **Graph**(그래프. 버전에 따라 Source Control Graph) 영역에 커밋 목록이 `git log --graph`처럼 보인다. 커밋을 누르면 그 커밋에서 바뀐 파일 목록이 펼쳐지고, 파일을 누르면 그 커밋의 변경이 비교 화면으로 열린다. `git show`와 같다.

**타임라인** — 4.6.3에서 로컬 기록을 보던 탐색기 아래쪽 **Timeline**(타임라인)에 이제 **Git 커밋**도 함께 나온다. `shop/pricing.py`를 열고 타임라인을 보면 이 파일을 바꾼 커밋 세 개가 보인다. `git log -- shop/pricing.py`와 같다. 타임라인의 필터 아이콘에서 Git 기록만 보거나 로컬 기록만 볼 수 있다.

**줄별 이력** — 명령 팔레트에 `blame`을 입력하면 편집기에 줄마다 작성자와 커밋을 표시하는 명령(Git Blame 표시 켜기)이 나온다. 켜고 `pricing.py`의 18번째 줄에 커서를 두면 그 줄 끝에 작성자, 시각, 커밋 메시지가 흐리게 보인다. `git blame`과 같다.

## 5.5 좋은 커밋

5.4에서 남의 이력을 읽어 보았다. `git log --oneline`의 제목만으로 프로젝트가 자란 과정이 보였고, 버그를 고친 커밋의 본문이 이유를 알려 주었다. 이 절에서는 **내가** 그런 이력을 남기는 방법을 배운다. 이력을 가장 많이 읽는 사람은 몇 달 뒤의 나 자신이다.

### 5.5.1 한 커밋에 한 가지 일

좋은 커밋의 첫째 조건은 **한 가지 일만 하는 것**이다. 다음 두 이력을 비교해 보자.

```
a1b2c3d README 수정, 할인 버그 고침, 출력 모양 바꿈
```

```
9666df9 금액을 천 단위 쉼표로 표시
1ed2593 묶음 할인 기준을 README와 맞춤
f00ba12 README에 실행 예 추가
```

변경의 총량은 같아도 둘째 이력이 훨씬 다루기 쉽다.

- **읽기 쉽다.** 제목만 보고 각 커밋이 무엇을 했는지 안다. 리뷰하는 사람(8장)도 커밋 하나씩 차례로 확인할 수 있다.
- **하나만 되돌릴 수 있다.** 쉼표 표시가 마음에 들지 않으면 그 커밋만 되돌린다(7장의 `git revert`). 첫째 이력에서는 버그 수정까지 함께 되돌아간다.
- **문제를 일으킨 커밋을 찾기 쉽다.** 7장의 `git bisect`는 커밋 단위로 범위를 좁힌다. 커밋이 작을수록 원인이 좁혀진다.
- **다른 곳에 가져가기 쉽다.** 버그 수정 하나만 다른 브랜치로 옮길 수 있다(7장의 `git cherry-pick`).

"한 가지 일"의 크기를 가늠하는 간단한 시험이 있다. **커밋 메시지의 제목을 "그리고"나 쉼표 없이 쓸 수 있는가?** 쓸 수 없으면 나눈다. 반대로 한 가지 일이 여러 파일에 걸치면 한 커밋에 함께 넣는다. 함수를 고치고 그 함수를 부르는 곳과 문서를 함께 고쳤다면, 그것이 한 가지 일이다. 나누면 중간 커밋에서 프로그램이 돌지 않는다.

그래서 **작게, 자주** 커밋한다. 기능 하나를 다 만들 때까지 기다리지 말고 "돌아갈 수 있는 한 걸음"마다 커밋한다. 커밋은 내 컴퓨터에만 있으므로(5.1.2) 부담 가질 것 없다. 지저분하게 쌓인 커밋을 남에게 보이기 전에 정리하는 방법은 7장에서 배운다.

### 5.5.2 커밋 메시지 쓰는 법

커밋 메시지는 **제목**, **빈 줄**, **본문**으로 쓴다.

```
묶음 할인 기준을 README와 맞춤                                     ← 제목

README에는 "10개 이상"이라고 적혀 있는데 코드는 qty > 10으로 비교해서   ← 본문
10개짜리 주문에 할인을 주지 않았다. check_orders.py의 small.csv 시험이
실패해서 발견했다.
```

**제목**은 이 커밋이 **무엇을** 하는지 짧게 쓴다.

- 한글은 30자 안팎, 영어는 50자 안팎으로 쓴다. `git log --oneline`, GitHub 화면, VS Code의 그래프가 모두 제목만 보여 주는데, 길면 잘린다.
- 끝에 마침표를 찍지 않는다.
- 저장소 안에서 끝맺음을 맞춘다. 이 저장소는 "추가", "맞춤", "표시"처럼 짧게 끝낸다. "~했습니다"와 "~함"이 섞이면 읽기 어렵다.
- "수정", "작업", "업데이트"처럼 **무엇이든 될 수 있는 낱말만** 쓰지 않는다. 무엇을 어떻게 고쳤는지가 드러나야 한다.

**본문**에는 **왜**를 쓴다. 무엇이 바뀌었는지는 diff가 정확히 보여 준다. diff가 보여 주지 못하는 것을 쓴다.

- 이 변경이 왜 필요했나? 어떤 문제가 있었나?
- 어떻게 발견했나? 어떻게 확인했나?
- 다른 방법도 있었다면 왜 이 방법을 골랐나?
- 읽는 사람이 놓치기 쉬운 영향이 있나?

본문은 변경이 작고 이유가 제목으로 충분하면 생략한다. 본문의 한 줄은 72자(한글은 40자) 안팎에서 줄을 바꾼다. 터미널에서 `git log`로 읽을 때 편하다.

나쁜 메시지와 고친 메시지를 비교해 보자.

| 나쁜 메시지 | 무엇이 문제인가 | 고친 메시지 |
|---|---|---|
| `수정` | 무엇을 고쳤는지 모른다 | `묶음 할인 기준을 README와 맞춤` |
| `asdf`, `.`, `ㅇㅇ` | 아무 정보가 없다 | (무엇을 했는지 쓴다) |
| `버그 고침` | 어떤 버그인지 모른다 | `10개짜리 주문에 묶음 할인이 빠지는 문제 고침` |
| `pricing.py 변경` | 파일 이름은 diff에 이미 있다 | `쿠폰 할인율을 환경 변수로 받음` |
| `README 수정, 할인 버그 고침, 출력 모양 바꿈` | 세 가지 일 | 커밋 세 개로 나눈다 |
| `>를 >=로 바꿈` | diff를 말로 옮겼을 뿐, 왜인지 없다 | 제목은 의도로, 본문에 이유를 쓴다 |
| `금요일 작업` | 시각은 커밋에 이미 있다 | (무엇을 했는지 쓴다) |

메시지가 여러 줄이면 편집기로 쓴다(5.3.5). 터미널에서 바로 쓰고 싶으면 `-m`을 두 번 준다. 첫째가 제목, 둘째가 본문이 되고 그 사이에 빈 줄이 들어간다.

```
git commit -m "제목" -m "본문 첫째 줄
본문 둘째 줄"
```

> **팀과 저장소의 규칙을 따른다**
> 많은 프로젝트가 커밋 메시지에 규칙을 둔다. 널리 쓰이는 것이 Conventional Commits라는 규칙으로, 제목 앞에 `feat:`(기능 추가), `fix:`(버그 수정), `docs:`(문서) 같은 종류를 붙인다. 예: `fix: 10개짜리 주문에 묶음 할인 적용`. 영어로만 쓰는 프로젝트도 많다. 남의 저장소에 기여할 때는 먼저 `git log --oneline`으로 그 저장소의 메시지 모양을 보고, `CONTRIBUTING.md`(8장)가 있으면 읽고 그대로 맞춘다. 이 교재의 실습은 한국어로, 위의 규칙대로 쓴다.

### 5.5.3 파일 일부만 골라 커밋하기 — `git add -p`

실제로 해 보자. `practice/shop`에 두 가지 일을 한꺼번에 해 버린 상황을 만든다.

- **일 1: 쿠폰 할인율 검사** — `SHOP_COUPON_RATE`에 `abc`처럼 숫자가 아닌 값을 넣으면 트레이스백이 나고, `1.5`를 넣으면 결제 금액이 음수가 된다. 0 이상 1 미만의 숫자만 받도록 고친다. 4장 실습 4-6의 과제 B와 같다.
- **일 2: README 보강** — 실행 안내에 macOS의 `python3` 이야기를 덧붙인다.

먼저 지금의 동작을 확인해 둔다.

```
# macOS
SHOP_COUPON_RATE=1.5 python3 main.py orders/small.csv

# Windows
$env:SHOP_COUPON_RATE = "1.5"
python main.py orders/small.csv
Remove-Item Env:SHOP_COUPON_RATE
```

```
주문 파일: small.csv (주문 4줄)
상품 금액: 28,500원
묶음 할인: -1,800원
쿠폰 할인: -40,050원
결제 금액: -13,350원
```

결제 금액이 음수다. VS Code에서 세 파일을 고친다. `shop/pricing.py`의 `coupon_rate()`를 다음과 같이 바꾼다.

```python
def coupon_rate() -> float:
    """환경 변수 SHOP_COUPON_RATE에서 쿠폰 할인율을 읽는다. 없으면 0.

    0 이상 1 미만의 숫자가 아니면 ValueError를 낸다.
    """
    text = os.getenv("SHOP_COUPON_RATE", "0")
    try:
        rate = float(text)
    except ValueError:
        raise ValueError(f"쿠폰 할인율이 숫자가 아닙니다: {text}") from None
    if not 0 <= rate < 1:
        raise ValueError(f"쿠폰 할인율은 0 이상 1 미만이어야 합니다: {text}")
    return rate
```

`shop/cli.py`의 `main()`에서 `result = summarize(lines)` 한 줄을 다음과 같이 바꾼다.

```python
    try:
        result = summarize(lines)
    except ValueError as e:
        print(e, file=sys.stderr)

### 5.5.4 커밋하기 전에 확인하는 습관

`git commit`을 누르기 전에 다음 순서를 습관으로 만든다.

1. **`git status`** — 스테이징된 파일 목록에 넣지 않으려던 파일이 있는가? 넣으려던 파일이 빠지지 않았는가? 추적하지 않는 파일 중에 넣어야 할 새 파일은 없는가?
2. **`git diff --staged`** — 이번 커밋에 들어갈 내용을 **한 줄씩** 읽는다. 4.6.3의 검토 목록이 그대로 쓰인다.
   - 디버깅하느라 넣은 `print()`, 주석으로 막아 둔 코드가 남아 있지 않은가?
   - API 키, 비밀번호, 개인 정보가 들어 있지 않은가?
   - 이번 일과 상관없는 변경(포맷만 바뀐 줄, 다른 기능)이 섞이지 않았는가?
3. **검사** — 프로젝트의 검사 스크립트(`check_orders.py`)를 실행한다.
4. **메시지** — 제목을 "그리고" 없이 쓸 수 있는가? 왜를 썼는가?

3번에는 함정이 하나 있다. 검사 스크립트는 **작업 폴더의 파일**로 돈다. `git add -p`로 일부만 스테이징했다면 커밋될 내용(스테이징 영역)과 검사한 내용(작업 폴더)이 다르다. 앞의 예에서 첫 커밋(`python3` 안내)은 README만 바꿨으니 문제가 없었지만, 코드의 일부만 골라 커밋할 때는 "이 커밋만으로 프로그램이 도는가"를 따로 확인해야 한다. 그 방법(`git stash --keep-index`)은 7장에서 배운다.

> **`git commit -v`**
> `git commit -v`(verbose)로 편집기를 열면 메시지 아래에 이번 커밋의 diff가 함께 보인다. diff를 보면서 메시지를 쓸 수 있고, diff 부분은 커밋 메시지에 들어가지 않는다. 늘 이렇게 하고 싶으면 `git config --global commit.verbose true`로 정한다.

### 5.5.5 AI가 쓴 커밋 메시지

VS Code의 소스 제어 보기를 비롯해 많은 AI 도구가 스테이징한 변경을 읽고 **커밋 메시지를 만들어 주는** 기능을 가지고 있다(메시지 칸 옆의 반짝이 모양 버튼 등). 편리하지만 다음을 확인하고 쓴다.

- **스테이징한 변경을 정확히 설명하는가?** 작업 폴더의 다른 변경까지 섞어 설명하거나, 하지 않은 일을 했다고 쓰는 경우가 있다. `git diff --staged`와 대조한다.
- **"왜"가 들어 있는가?** AI는 diff에서 **무엇이** 바뀌었는지는 읽어 내지만, **왜** 바꿨는지는 모른다. 내가 알려 주지 않았다면 본문의 이유는 대개 그럴듯하게 지어낸 것이다. 이유는 내가 쓴다.
- **제목이 한 가지 일인가?** AI가 쓴 제목에 "및", "그리고", 쉼표가 들어 있다면 커밋을 나눌 신호다.
- **저장소의 규칙과 맞는가?** 언어, 끝맺음, 접두어(`feat:` 등)가 기존 이력과 같은지 본다.

AI 코딩 도구가 작업 끝에 **직접 커밋까지 하는** 경우도 있다. 그 커밋이 무엇을 담았는지 `git show`로 확인하는 일, AI에게 맡기기 전에 커밋해 두는 일은 7장에서 다룬다.

## 5.6 추적하지 않을 것

### 5.6.1 저장소에 넣지 않는 것

저장소에는 **다른 사람이 받아서 프로젝트를 다시 만들고 실행하는 데 필요한 것**을 넣는다. 그 밖의 것은 넣지 않는다. 기초 과정 9.1.8과 10장에서 `.gitignore`를 적으며 이야기한 것을 정리하면 다음과 같다.

| 종류 | 예 | 넣지 않는 이유 |
|---|---|---|
| 다시 만들 수 있는 것 | `.venv/`, `__pycache__/`, 프로그램이 만든 결과 파일(`*_summary.csv`) | 크고, 컴퓨터마다 다르고(가상환경에는 절대 경로가 들어 있다), 언제든 다시 만들 수 있다. 다시 만드는 방법(`requirements.txt`, 실행 명령)을 넣는다 |
| 비밀 값 | `.env`, API 키가 든 설정 파일 | 저장소를 받는 모든 사람에게, 공개 저장소라면 인터넷 전체에 공개된다(8장) |
| 개인 데이터 | 내 실제 가계부(`data/`), 고객 정보 | 개인 정보다. 시험용 견본 데이터(`samples/`)만 넣는다 |
| 내 컴퓨터·도구의 흔적 | `.DS_Store`(macOS), `Thumbs.db`(Windows), 편집기의 임시 파일 | 프로젝트와 상관없다 |
| 큰 파일 | 데이터 세트, 학습한 모델, 동영상 | 저장소가 무거워지고, 한 번 커밋하면 이력에 계속 남는다 |

이런 파일을 Git이 **아예 보지 않게** 하는 파일이 `.gitignore`다. 여기에 적힌 이름과 일치하는 파일은 `git status`의 "추적하지 않는 파일"에 나오지 않고, `git add .`을 해도 올라가지 않는다.

### 5.6.2 `.gitignore` 패턴 규칙

`.gitignore`에는 한 줄에 하나씩 **패턴**을 적는다. 3장과 2.6.3의 와일드카드와 비슷하지만, Git만의 규칙이 몇 가지 더 있다.

| 패턴 | 뜻 | 일치하는 예 |
|---|---|---|
| `# 설명` | 주석. 빈 줄도 무시한다 | |
| `.env` | 이름이 `.env`인 파일이나 폴더. **어느 폴더에 있든** | `.env`, `config/.env` |
| `__pycache__/` | 끝에 `/`가 있으면 **폴더만** | `shop/__pycache__/`(폴더). 같은 이름의 파일은 아니다 |
| `/build` | 앞에 `/`가 있으면 **`.gitignore`가 있는 폴더 바로 아래만** | `build`. `docs/build`는 아니다 |
| `*.log` | `*`는 `/`를 뺀 아무 글자 여럿 | `app.log`, `logs/debug.log` |
| `*_summary.csv` | | `2026-10_summary.csv` |
| `*.py[cod]` | `[...]`는 그 안의 글자 하나 | `a.pyc`, `a.pyo`, `a.pyd` |
| `docs/*.pdf` | 가운데 `/`가 있으면 `.gitignore`의 위치를 기준으로 한 경로 | `docs/a.pdf`. `docs/old/a.pdf`는 아니다 |
| `**/temp` | `**`는 폴더 여러 단계 | `temp`, `a/temp`, `a/b/temp` |
| `logs/**` | 그 폴더 안의 모든 것 | `logs/a.txt`, `logs/2026/b.txt` |
| `!keep.log` | 앞의 규칙에 걸렸어도 **다시 추적한다** | |

규칙 몇 가지를 덧붙인다.

- **아래 줄이 위 줄을 이긴다.** `*.log` 다음에 `!keep.log`를 적으면 `keep.log`만 다시 추적한다. 순서를 바꾸면 소용이 없다.
- **폴더를 통째로 무시하면 그 안의 파일은 `!`로 되살릴 수 없다.** Git은 무시한 폴더 안을 아예 들여다보지 않기 때문이다. 4.2.6에서 `.vscode/`가 아니라 `.vscode/*`라고 적은 이유가 이것이다. `.vscode/*`는 "폴더 안의 것들"을 무시하므로 Git이 폴더 안을 들여다보고, 그중 `!`로 적은 파일을 되살린다. 5.6.5에서 직접 확인한다.
- `.gitignore`는 **하위 폴더에도** 둘 수 있다. 그 파일의 패턴은 그 폴더를 기준으로 적용된다. 파이썬 3.13 이상의 `venv`가 `.venv` 안에 내용이 `*` 한 줄인 `.gitignore`를 만들어 두는 것(기초 과정 9.1.3)이 그 예다. "이 폴더 안의 모든 것을 무시하라"는 뜻이다.
- **이미 추적하고 있는 파일에는 적용되지 않는다.** `.gitignore`는 "추적하지 않는 파일 중에서 무엇을 못 본 체할지"를 정할 뿐이다. 이미 커밋한 파일을 나중에 `.gitignore`에 적어도 계속 추적된다. 5.6.7에서 다룬다.

### 5.6.3 파이썬 프로젝트의 `.gitignore`

`practice/shop`의 `.gitignore`는 세 줄이다.

```
.venv/
__pycache__/
.env
```

3.7.1에서 내려받은 `Python.gitignore`는 GitHub가 관리하는 파이썬용 견본으로, 200줄이 넘는다. 여러 도구(테스트 도구, 패키지 빌드 도구, 노트북, 여러 가상환경 관리자)가 만드는 파일을 모두 적어 두었다. GitHub에서 새 저장소를 만들 때 고르는 `.gitignore` 견본도 이것이다(8장).

견본을 그대로 쓰면 빠뜨릴 걱정은 적지만, 무엇이 왜 들어 있는지 모르는 줄이 많아진다. 이 과정에서는 **짧게 직접 쓰고, 새 도구를 쓰기 시작할 때마다 그 도구가 만드는 것을 더한다.** 견본은 무엇을 더할지 찾아보는 자료로 쓴다. 이 과정에서 만날 것들을 미리 적어 두면 다음과 같다.

```
# 가상환경
.venv/

# 파이썬이 만드는 것
__pycache__/
*.py[cod]

# 비밀 값 — .env.example은 올린다(8장)
.env

# 도구가 만드는 것
.pytest_cache/
.ruff_cache/
.ipynb_checkpoints/
```

`.pytest_cache`와 `.ruff_cache`는 중급 과정의 테스트 도구와 포매터가, `.ipynb_checkpoints`는 9장의 Jupyter Notebook이 만드는 폴더다. 프로젝트마다 다른 것(기초 과정 10장의 `data/`, `*_summary.csv`처럼 그 프로그램이 만들거나 읽는 파일)은 그 프로젝트의 `.gitignore`에 더한다.

### 5.6.4 무시되는지 확인하기 — `git check-ignore -v`

`practice/shop`에서 검사 스크립트를 실행하면 파이썬이 `shop/__pycache__` 폴더를 만든다(기초 과정 8.1.4). 이 장의 실습 환경에서 이미 실행했으므로 폴더가 있을 것이다. 다시 실행해 두어도 된다.

```
# macOS
python3 check_orders.py

# Windows
python check_orders.py
```

`shop` 폴더 안에 `__pycache__`가 있지만 `git status`에는 나오지 않는다.

```
git status
```

```
On branch main
Untracked files:
  (use "git add <file>..." to include in what will be committed)
	.vscode/
	AGENTS.md

nothing added to commit but untracked files present (use "git add" to track)
```

**무시하는 파일**까지 보려면 `--ignored`를 붙인다.

```
git status --ignored
```

```
On branch main
Untracked files:
  (use "git add <file>..." to include in what will be committed)
	.vscode/
	AGENTS.md

Ignored files:
  (use "git add -f <file>..." to include in what will be committed)
	.env
	shop/__pycache__/

nothing added to commit but untracked files present (use "git add" to track)
```

`.env`와 `shop/__pycache__/`가 무시되고 있다. **왜** 무시되는지, 어느 파일의 몇째 줄 때문인지는 `git check-ignore -v`로 본다.

```
git check-ignore -v .env shop/__pycache__ main.py
```

```
.gitignore:3:.env	.env
.gitignore:2:__pycache__/	shop/__pycache__
```

한 줄에 `파일:줄번호:패턴` 그리고 탭 뒤에 확인한 경로가 나온다. `.env`는 `.gitignore`의 3번째 줄 `.env` 때문에, `shop/__pycache__`는 2번째 줄 `__pycache__/` 때문에 무시된다. `main.py`는 무시되지 않으므로 아무것도 나오지 않는다. 확인한 경로가 모두 무시되지 않으면 종료 코드가 1이다.

`.gitignore`가 생각대로 동작하지 않을 때 이 명령이 가장 빠른 진단 도구다. 무시되어야 할 파일이 `git status`에 보이면 `git check-ignore -v 파일`이 아무것도 내놓지 않을 것이고(패턴이 틀렸다), 보여야 할 파일이 안 보이면 어느 줄이 가리고 있는지 알려 준다. `.gitignore`가 여러 개이거나 전역 무시 파일(5.6.6)이 있을 때 특히 쓸모 있다.

> **`git add -f`는 무시를 뚫는다**
> `git status --ignored`의 안내에 보이는 `git add -f 파일`(force)은 무시하는 파일도 강제로 스테이징한다. 꼭 필요한 경우가 드물게 있지만, `git add -f .`처럼 쓰면 `.env`와 `.venv`까지 모두 올라간다. AI가 실행하려는 명령에 `-f`가 보이면 무엇을 강제로 넣으려는지 확인한다.

### 5.6.5 팀이 함께 쓸 설정만 올리기

`practice/shop`에 아직 추적하지 않는 `.vscode/`와 `AGENTS.md`가 남아 있다. 4.2.6과 4.6.4에서 정한 기준대로 판단한다.

- `.vscode/settings.json`(포맷 설정, `files.exclude`), `.vscode/extensions.json`(권장 확장)은 팀 전체에 필요하고 비밀이 없으므로 **올린다.**
- 나중에 누군가 `.vscode`에 개인 설정 파일을 만들 수 있으므로, `.vscode` 안에서는 **정해 둔 파일만** 추적하게 한다.
- `AGENTS.md`는 프로젝트의 규칙을 적은 파일이므로 **올린다.**

`.gitignore`의 끝에 4.2.6의 네 줄을 더하고 저장한다. 앞에 빈 줄과 주석을 넣어 무엇을 위한 규칙인지 적어 둔다.

```
.venv/
__pycache__/
.env

# VS Code — 팀이 함께 쓸 설정만 올린다
.vscode/*
!.vscode/settings.json
!.vscode/extensions.json
!.vscode/launch.json
```

`launch.json`은 아직 없지만 4.4.2처럼 만들게 되면 바로 올라가도록 미리 적어 둔다. 상태를 본다. `-u`(정확히는 `--untracked-files=all`)를 붙이면 추적하지 않는 폴더를 `.vscode/`처럼 하나로 접지 않고 안의 파일을 하나씩 보여 준다.

```
git status -s -u
```

```
 M .gitignore
?? .vscode/extensions.json
?? .vscode/settings.json
?? AGENTS.md
```

`!`로 되살린 두 파일이 보인다. `.vscode`에 다른 파일을 만들면 보이지 않을 것이다(실습 5-6에서 확인한다). 만약 `.vscode/*` 대신 `.vscode/`라고 적었다면 Git이 폴더 안을 들여다보지 않으므로 두 파일도 나오지 않는다. `git check-ignore -v .vscode/settings.json`이 `.gitignore:...:.vscode/`를 보여 줄 것이다.

두 가지 일이므로 커밋도 둘로 나눈다(5.5.1). `.gitignore`의 변경은 `.vscode`를 올리기 위한 것이므로 `.vscode`와 함께 커밋한다.

```
git add .gitignore .vscode
git status -s
```

```
M  .gitignore
A  .vscode/extensions.json
A  .vscode/settings.json
?? AGENTS.md
```

```
git commit -m "VS Code 작업 공간 설정 추가"
git add AGENTS.md
git commit -m "AI 도구용 지침 파일 추가"
git status
```

```
On branch main
nothing to commit, working tree clean
```

`working tree clean`은 "작업 폴더가 깨끗하다", 즉 **추적하는 파일은 모두 마지막 커밋과 같고, 무시하지 않은 새 파일도 없다**는 뜻이다. 작업을 시작하기 전과 AI에게 일을 맡기기 전에 바라는 상태가 이것이다(7장).

### 5.6.6 전역 무시 파일

macOS의 Finder는 폴더를 열면 그 폴더에 `.DS_Store`라는 숨김 파일을 만든다. Windows 탐색기도 사진 폴더에 `Thumbs.db`를 만들 때가 있다. 이런 파일은 프로젝트가 아니라 **내 컴퓨터** 때문에 생긴다. 모든 프로젝트의 `.gitignore`에 적는 대신, 내 컴퓨터의 모든 저장소에 적용되는 **전역 무시 파일**에 적는다.

```
git config --global core.excludesFile "~/.gitignore_global"
code $HOME/.gitignore_global
```

따옴표 안의 `~`는 셸이 아니라 Git이 홈 폴더로 바꾼다. `code`에 준 `$HOME`은 두 셸 모두 홈 폴더로 바꾼다(PowerShell은 `code` 같은 외부 프로그램에 주는 `~`를 바꾸지 않을 수 있다). 그래서 두 셸에서 같은 명령을 쓸 수 있다. VS Code에서 다음을 적고 저장한다.

```
# macOS
.DS_Store

# Windows
Thumbs.db
desktop.ini
```

`practice/oops`에는 `.DS_Store`가 있다(5.6.7에서 고친다). 확인해 보면 전역 무시 파일 때문에 무시된다는 것이 보인다.

```
cd ../oops
git check-ignore -v --no-index .DS_Store
```

```
/Users/jinyoung/.gitignore_global:2:.DS_Store	.DS_Store
```

`oops`에서는 `.DS_Store`가 이미 커밋되어 있어서 `--no-index`를 붙여야 결과가 나온다. 이 옵션은 "추적 여부와 상관없이 패턴만 확인하라"는 뜻이다. 추적하는 파일에는 `.gitignore`가 적용되지 않기 때문이다(5.6.2). 바로 다음에 이것을 고친다.

구분하는 기준은 이렇다. **프로젝트 때문에 생기는 것**(`.venv`, `__pycache__`, `.env`)은 프로젝트의 `.gitignore`에 적어 모든 팀원에게 적용하고, **내 컴퓨터나 내가 쓰는 도구 때문에 생기는 것**은 전역 무시 파일에 적는다. 팀원이 어떤 운영체제를 쓸지 모르므로 `.DS_Store`를 프로젝트 `.gitignore`에도 적어 두는 팀도 많다.

### 5.6.7 이미 커밋한 파일을 추적에서 빼기 — `git rm --cached`

`practice/oops`는 `.gitignore` 없이 시작해서 `git add -A`로 모든 것을 커밋해 버린 저장소다. 무엇을 추적하고 있는지 본다. `git ls-files`는 **스테이징 영역에 있는 파일**, 즉 추적하는 파일의 목록을 보여 준다.

```
cd ~/devtools-lab/ch05/practice/oops
git ls-files
```

```
.DS_Store
.venv/lib/python3.13/site-packages/rich/__init__.py
.venv/pyvenv.cfg
README.md
__pycache__/main.cpython-313.pyc
main.py
```

가상환경, 바이트코드, `.DS_Store`가 들어 있다. VS Code로 `.gitignore`를 만들어 다음 두 줄을 적고 저장한다(`code .gitignore`).

```
.venv/
__pycache__/
```

```
git status
```

```
On branch main
Untracked files:
  (use "git add <file>..." to include in what will be committed)
	.gitignore

nothing added to commit but untracked files present (use "git add" to track)
```

`.gitignore`가 새 파일로 보일 뿐, `.venv`와 `__pycache__`는 여전히 추적된다. 5.6.2의 마지막 규칙 때문이다. 추적을 멈추려면 **스테이징 영역에서 빼야** 한다. `git rm --cached`는 파일을 스테이징 영역에서만 지우고 **작업 폴더의 파일은 그대로 둔다.** 폴더는 `-r`을 붙인다.

```
git rm --cached .venv
```

```
fatal: not removing '.venv' recursively without -r
```

```
git rm -r --cached .venv
git rm --cached __pycache__/main.cpython-313.pyc .DS_Store
```

```
rm '.venv/lib/python3.13/site-packages/rich/__init__.py'
rm '.venv/pyvenv.cfg'
rm '__pycache__/main.cpython-313.pyc'
rm '.DS_Store'
```

```
git add .gitignore
git status
```

```
On branch main
Changes to be committed:
  (use "git restore --staged <file>..." to unstage)
	deleted:    .DS_Store
	new file:   .gitignore
	deleted:    .venv/lib/python3.13/site-packages/rich/__init__.py
	deleted:    .venv/pyvenv.cfg
	deleted:    __pycache__/main.cpython-313.pyc
```

`deleted`(지움)로 스테이징되었다. 다음 커밋의 스냅숏에서 이 파일들이 빠진다는 뜻이다. 작업 폴더에는 그대로 있다(`ls -a`로 확인한다). 이제 `.gitignore`와 전역 무시 파일 때문에 이 파일들은 "추적하지 않는 파일"로도 나오지 않는다. 커밋한다.

```
git commit -m "가상환경과 바이트코드를 추적에서 뺌"
git ls-files
```

```
.gitignore
README.md
main.py
```

이제 추적하는 파일은 세 개다. 그런데 **이력에서 사라진 것은 아니다.** 커밋은 스냅숏이므로(5.1.3) 앞의 커밋에는 여전히 들어 있다.

```
git show HEAD~1:.venv/pyvenv.cfg
```

```
home = /Users/doyun/.pyenv/versions/3.13.2/bin
version = 3.13.2
```

박도윤의 컴퓨터 계정 이름까지 그대로 보인다. 저장소를 받은 사람은 누구나 이것을 볼 수 있다. `.venv`나 `__pycache__`라면 저장소가 조금 무거워지는 정도로 넘어갈 수 있다. 하지만 **비밀 값이 든 `.env`를 커밋했다면** `git rm --cached`로는 해결되지 않는다. 키는 이력에 남아 있다. 그때는 **먼저 그 키를 폐기하고 새로 발급받은 뒤** 이력을 정리한다(8장). 그래서 `.gitignore`는 **첫 커밋 전에** 만든다.

> **함께 쓰는 저장소에서 `git rm --cached`를 커밋하면**
> 이 커밋을 다른 팀원이 받으면(8장) 그 사람의 작업 폴더에서는 그 파일들이 **지워진다.** 받는 쪽의 Git에게 이 커밋은 "이 파일을 지웠다"는 스냅숏이기 때문이다. `.venv`라면 다시 만들면 되지만, 설정 파일처럼 각자 가지고 있어야 하는 파일이라면 미리 알려 백업하게 한다.

### 5.6.8 파일 이름 바꾸기와 지우기 — `git mv`, `git rm`

추적하는 파일의 이름을 터미널의 `mv`(2.4.3)로 바꾸면 Git에게는 어떻게 보일까? `practice/notes`에서 해 본다.

```
cd ~/devtools-lab/ch05/practice/notes
mv git.md git-basics.md
git status
```

```
On branch main
Changes not staged for commit:
  (use "git add/rm <file>..." to update what will be committed)
  (use "git restore <file>..." to discard changes in working directory)
	deleted:    git.md

Untracked files:
  (use "git add <file>..." to include in what will be committed)
	git-basics.md
```

Git에게는 "`git.md`가 사라지고 `git-basics.md`라는 모르는 파일이 생긴" 것으로 보인다. 5.1.3에서 말한 대로 Git은 이름 바꾸기를 따로 기록하지 않는다. 두 변경을 모두 스테이징하면 그제야 알아본다.

```
git add -A
git status
```

```
On branch main
Changes to be committed:
  (use "git restore --staged <file>..." to unstage)
	renamed:    git.md -> git-basics.md
```

지운 파일과 새 파일의 내용이 거의 같으므로 "이름을 바꿨구나"라고 짐작해 `renamed`로 보여 준다. 처음부터 `git mv`를 쓰면 이름 바꾸기와 스테이징을 한 번에 한다. 확인을 위해 방금 한 것을 되돌린 뒤(`git restore --staged .`과 `mv git-basics.md git.md`, 5.7) 다시 해 본다.

```
git restore --staged .
mv git-basics.md git.md
git mv git.md git-basics.md
git status
```

```
On branch main
Changes to be committed:
  (use "git restore --staged <file>..." to unstage)
	renamed:    git.md -> git-basics.md
```

```
git commit -m "git.md 이름을 git-basics.md로 바꿈"
```

이름이 바뀐 파일의 이력을 보면 차이가 있다.

```
git log --oneline -- git-basics.md
git log --oneline --follow -- git-basics.md
```

```
21a5b60 git.md 이름을 git-basics.md로 바꿈
```

```
21a5b60 git.md 이름을 git-basics.md로 바꿈
29c8420 Git 노트에 표기법 추가
df6b37f Git 노트에 세 영역 정리
801be7e Git 노트 추가
```

그냥 `git log -- 경로`는 지금 이름으로만 찾으므로 이름을 바꾼 커밋부터 나온다. `--follow`를 붙여야 옛 이름(`git.md`) 시절까지 따라간다. 해시는 교재와 다르고, 커밋의 수도 5.3.7에서 VS Code로 커밋했는지 등에 따라 다를 수 있다.

파일을 지울 때도 마찬가지다.

| 명령 | 작업 폴더의 파일 | 스테이징 영역 |
|---|---|---|
| `rm 파일` | 지운다 | 그대로(` D`로 보인다. `git add`하거나 `git rm`해야 스테이징된다) |
| `git rm 파일` | 지운다 | 지운 것을 스테이징한다(`D `) |
| `git rm --cached 파일` | **남긴다** | 지운 것을 스테이징한다. 추적을 멈춘다(5.6.7) |

`git rm`은 커밋하지 않은 변경이 있는 파일은 지우지 않고 오류를 낸다. 실수로 작업을 날리지 않게 막아 주는 것이다. 커밋해 둔 파일은 지워도 되살릴 수 있다(5.7.4).

**대소문자만 바꾸는 이름 변경** — 2.6.6에서 예고한 문제다. macOS와 Windows는 파일 이름의 대소문자를 구분하지 않으므로(2.6.6) Git도 기본으로 대소문자를 무시하도록 설정되어 있다(`core.ignorecase=true`). 그래서 `mv readme.md README.md`로 바꾸면 **Git이 알아채지 못한다.** `git status`에 아무것도 나오지 않고, 저장소에는 계속 `readme.md`로 남는다. 리눅스 서버나 GitHub Actions에서 `README.md`를 찾는 코드가 있다면 거기서 실패한다. 대소문자만 바꿀 때는 반드시 `git mv`를 쓴다.

```
git mv readme.md README.md
git status
```

```
Changes to be committed:
	renamed:    readme.md -> README.md
```

> **빈 폴더는 추적되지 않는다**
> Git은 파일만 추적한다. 폴더는 그 안에 추적하는 파일이 있을 때만 저장소에 생긴다. 프로그램이 결과를 쓸 `output/` 폴더처럼 빈 폴더가 꼭 있어야 하면, 그 안에 `.gitkeep`이라는 빈 파일을 하나 넣어 커밋하는 관례가 있다. 이름에 특별한 뜻은 없다. 더 좋은 방법은 프로그램이 폴더가 없으면 만들게 하는 것이다(`Path.mkdir(parents=True, exist_ok=True)`).

## 5.7 작업 폴더의 변경 되돌리기

고치다 보면 "방금 한 것은 없던 일로 하고 싶다"는 순간이 온다. 실험이 실패했거나, 엉뚱한 파일을 고쳤거나, AI가 바꾼 것 중 일부를 버리고 싶을 때다. 이 절에서는 **아직 커밋하지 않은 변경**을 되돌리는 방법을 배운다. 이미 한 커밋을 고치거나 되돌리는 일은 7장에서 다룬다.

### 5.7.1 세 영역 사이를 오가는 명령

5.3.2의 세 영역을 다시 그리면, 지금까지 배운 명령은 모두 **왼쪽에서 오른쪽으로** 내용을 옮겼다. 되돌리는 명령은 **오른쪽에서 왼쪽으로** 옮긴다.

```
  작업 폴더                  스테이징 영역                마지막 커밋(HEAD)
 ┌───────────┐  git add     ┌───────────┐  git commit    ┌───────────┐
 │           │ ───────────▶ │           │ ─────────────▶ │           │
 │           │              │           │                │           │
 │           │ ◀─────────── │           │ ◀───────────── │           │
 └───────────┘ git restore  └───────────┘ git restore    └───────────┘
       ▲                                  --staged             │
       └───────────── git restore --staged --worktree ─────────┘
                      (마지막 커밋의 내용으로 둘 다)
```

`git restore`는 **어떤 파일의 한 버전을 가져와 다른 곳에 덮어쓰는** 명령이다. 어디서 가져와 어디에 덮어쓰는지는 옵션이 정한다.

| 명령 | 덮어쓰는 곳 | 가져오는 곳 |
|---|---|---|
| `git restore 파일` | 작업 폴더 | **스테이징 영역** |
| `git restore --staged 파일` | 스테이징 영역 | 마지막 커밋 |
| `git restore --staged --worktree 파일` | 스테이징 영역과 작업 폴더 | 마지막 커밋 |
| `git restore --source=커밋 파일` | 작업 폴더 | 그 커밋 |

첫 줄이 이 절에서 가장 중요하다. 옵션 없는 `git restore`는 작업 폴더를 **마지막 커밋이 아니라 스테이징 영역의 내용으로** 되돌린다. 하나씩 해 보자. `practice/shop`에서 한다. 5.6.5를 마쳤다면 `git status`가 `working tree clean`이어야 한다.

### 5.7.2 `git restore` — 작업 폴더의 변경 버리기

묶음 할인율을 실험 삼아 바꿔 본다. `shop/pricing.py`의 `BULK_RATE = 0.1`을 `0.2`로 고치고 저장한다.

이번에는 스테이징한 뒤에 또 고친 경우를 본다. `README.md`의 끝에 다음 세 줄(앞에 빈 줄 하나)을 더하고 저장한 뒤 스테이징한다.

```markdown

```

```

### 5.7.3 `git restore --staged` — 스테이징 취소

스테이징한 것을 작업 폴더로 돌려보낸다. 변경을 버리는 것이 아니라 **다음 커밋에서 빼기만** 한다. 5.3.4에서 `git status`가 안내하던 명령이다.

```
git restore --staged README.md
git status -s
```

```
 M README.md
```

`M`이 왼쪽에서 오른쪽으로 옮겨 갔다. `git add`의 반대다. README의 끝에는 여전히 "## 문의"와 이서연의 줄이 있다. `git diff`로 보인다. 작업 폴더의 파일은 바뀌지 않았기 때문이다.

> **첫 커밋 전에는**
> 커밋이 하나도 없는 저장소에서는 "마지막 커밋"이 없으므로 `git restore --staged`를 쓸 수 없다. 그래서 5.3.4의 `git status`는 대신 `git rm --cached <file>`을 안내했다. 결과는 같다. 스테이징 영역에서만 빼고 작업 폴더의 파일은 남긴다.

### 5.7.4 마지막 커밋의 상태로, 지난 커밋의 상태로

**스테이징한 것까지 모두 버리고** 마지막 커밋의 상태로 돌아가려면 `--staged`와 `--worktree`를 함께 준다. 줄여서 `-SW`라고 써도 된다. 다시 스테이징한 뒤 해 본다.

```
git add README.md
git restore --staged --worktree README.md
git status
```

```

### 5.7.5 되살릴 수 없는 것

`git restore 파일`과 `git restore --staged --worktree 파일`은 **확인을 묻지 않고** 작업 폴더의 파일을 덮어쓴다. 그 파일에 있던, **한 번도 커밋하지 않은 변경은 사라진다.** Git은 커밋한 것(과 스테이징한 것)만 알고 있으므로, Git에게 맡긴 적이 없는 내용은 되살려 줄 수 없다. 2.4.4의 `rm`과 같다.

그래서 변경을 버리기 전에 다음을 지킨다.

1. **`git diff`로 무엇을 버리는지 먼저 본다.** 3.8.4의 "지우거나 바꾸는 명령은 먼저 보기만 한다"와 같은 원칙이다.
2. **조금이라도 아깝다면 버리지 말고 남긴다.** 커밋하거나(7장에서 나중에 정리할 수 있다), 파일을 복사해 두거나, 7장의 `git stash`로 치워 둔다.
3. 파일 단위로 버린다. `git restore .`은 현재 폴더 아래의 **모든** 변경을 버린다.

이미 버려 버렸다면 마지막 희망은 VS Code의 **로컬 기록**(4.6.3)이다. VS Code에서 저장했던 내용이라면 타임라인에 남아 있을 수 있다. Git의 명령은 VS Code를 거치지 않고 파일을 덮어쓰므로, 덮어쓰기 직전의 저장 기록이 타임라인에 있는지 찾아본다. 보장되는 방법은 아니다.

### 5.7.6 추적하지 않는 파일 정리하기 — `git clean`

`git restore`는 추적하는 파일만 다룬다. 실험하다 만든 **추적하지 않는 파일**은 그대로 남는다. 몇 개 만들어 본다. 메모 파일 하나, 폴더 하나, 프로그램의 출력을 저장한 파일 하나다.

```
# macOS
echo "실험 메모" > notes.txt
mkdir tmp
echo "a,b" > tmp/out.csv
python3 main.py orders/small.csv > result_summary.txt

# Windows
"실험 메모" > notes.txt
mkdir tmp
"a,b" > tmp/out.csv
python main.py orders/small.csv > result_summary.txt
```

```
git status -s
```

```
?? notes.txt
?? result_summary.txt
?? tmp/
```

추적하지 않는 파일을 지우는 명령이 `git clean`이다. 그냥 실행하면 거절한다.

```
git clean
```

```
fatal: clean.requireForce is true and -f not given: refusing to clean
```

"`-f`(force) 없이는 지우지 않겠다"는 뜻이다(Git 버전에 따라 문장이 조금 다르다). 그만큼 위험한 명령이라서 기본으로 막아 두었다. 3.8.4의 표에서 본 대로 **먼저 `-n`(dry run)으로 무엇이 지워질지 본다.**

```
git clean -n
```

```
Would remove notes.txt
Would remove result_summary.txt
```

`tmp/` 폴더는 빠졌다. 폴더까지 지우려면 `-d`를 더한다.

```
git clean -nd
```

```
Would remove notes.txt
Would remove result_summary.txt
Would remove tmp/
```

**무시하는 파일**까지 지우는 `-x`도 있다. 무엇이 지워지는지 보자.

```
git clean -ndx
```

```
Would remove .env
Would remove notes.txt
Would remove result_summary.txt
Would remove shop/__pycache__/
Would remove tmp/
```

`.env`가 들어 있다. `.venv`를 만들어 두었다면 그것도 지워진다. `.env`는 Git에 없으므로 **되살릴 수 없다.** AI 도구나 인터넷의 안내에서 `git clean -fdx`를 보면 특히 조심한다. 확인했으면 `-n`을 `-f`로 바꿔 실행한다.

```
git clean -fd
```

```
Removing notes.txt
Removing result_summary.txt
Removing tmp/
```

| 옵션 | 뜻 |
|---|---|
| `-n` | 지우지 않고 지울 목록만 보여 준다. **항상 먼저 한다** |
| `-f` | 실제로 지운다 |
| `-d` | 추적하지 않는 폴더도 지운다 |
| `-x` | 무시하는 파일(`.env`, `.venv`, `__pycache__`)도 지운다 |
| `-i` | 지울 것을 하나씩 물어본다(interactive) |
| `-- 경로` | 그 경로 아래만 |

`git clean`으로 지운 파일도 휴지통을 거치지 않는다. 지울 파일이 몇 개뿐이라면 `git clean` 대신 `rm`이나 탐색기로 하나씩 지우는 편이 안전하다.

### 5.7.7 옛 명령과 VS Code

`git restore`는 Git 2.23(2019년)에 새로 생긴 명령이다. 그 전에는 같은 일을 `git checkout`과 `git reset`으로 했다. 인터넷의 글, 오래된 책, AI의 답에는 아직 옛 명령이 자주 나오므로 읽을 수는 있어야 한다.

| 옛 명령 | 지금 명령 |
|---|---|
| `git checkout -- 파일` | `git restore 파일` |
| `git reset HEAD 파일`, `git reset 파일` | `git restore --staged 파일` |
| `git checkout HEAD -- 파일` | `git restore --staged --worktree 파일` |
| `git checkout 커밋 -- 파일` | `git restore --source=커밋 --staged --worktree 파일` |

`git checkout`은 파일을 되돌리는 일 말고 브랜치를 옮기는 일(6장)도 하고, `git reset`은 커밋을 되돌리는 일(7장)도 한다. 한 명령이 여러 일을 하다 보니 헷갈리기 쉬워서 일을 나누어 `git restore`(파일 되돌리기)와 `git switch`(브랜치 옮기기, 6장)가 생겼다. 이 교재에서는 새 명령을 쓴다. 옛 명령을 만나면 이 표로 바꿔 읽는다.

VS Code의 소스 제어 보기에서는 다음과 같다.

| VS Code | 명령 |
|---|---|
| **Changes**의 파일 오른쪽 **↶**(Discard Changes) | `git restore 파일` |
| **Changes** 제목 오른쪽 **↶**(Discard All Changes) | 모든 파일에 `git restore`, 그리고 추적하지 않는 파일 **삭제** |
| **Staged Changes**의 파일 오른쪽 **−**(Unstage Changes) | `git restore --staged 파일` |
| 추적하지 않는 파일(`U`)의 **↶** | 그 파일을 **지운다**(`git clean`과 같다) |

VS Code는 버리기 전에 확인 대화 상자를 띄운다. 추적하지 않는 파일을 버리려고 하면 "되돌릴 수 없다(IRREVERSIBLE)"는 경고와 함께 **파일을 지울지** 묻는다. 대화 상자의 문장을 읽고 누른다. 버튼 하나가 명령 하나에 해당한다는 것, 그 명령이 무엇을 되살릴 수 없게 만드는지를 알고 누르는 것이 1장에서 말한 "명령을 먼저 배우는 이유"다.

### 실습 5-7. 되돌리기 연습

`practice/notes`에서 한다. 결과는 `~/devtools-lab/ch05/restore.md`에 적는다. 시작할 때 `git status`가 깨끗한지 확인한다.

1. **예상하고 확인하기** — `git-basics.md`(5.6.8에서 바꾼 이름)의 끝에 줄 A를 더하고 저장해 `git add`한 뒤, 줄 B를 더 더하고 저장한다. 이 상태에서 다음 세 명령을 **각각** 실행했을 때 `git status -s`, `git diff`, `git diff --staged`가 어떻게 나올지 **먼저 표로 예상해 적는다.** 그다음 하나씩 실행해 확인한다. 명령 하나를 확인할 때마다 줄 A를 더해 스테이징하고 줄 B를 더하는 처음 상태로 다시 만든다.
   - `git restore git-basics.md`
   - `git restore --staged git-basics.md`
   - `git restore --staged --worktree git-basics.md`
2. **지운 파일 되살리기** — `README.md`를 터미널에서 지우고 `git status -s`를 적는다. `git restore`로 되살린다. 이번에는 `git rm README.md`로 지우고 `git status -s`를 적는다. 무엇이 다른가? 이 상태에서 되살리려면 어떤 명령이 필요한지 찾아 실행한다.
3. **지난 내용 꺼내기** — `git log --oneline --follow -- git-basics.md`로 이 파일의 첫 커밋을 찾는다. 그 커밋 시점의 내용을 두 방법으로 본다.
   - `git show 커밋:git.md`(그때의 이름으로). 작업 폴더가 바뀌는지 확인한다.
   - `git restore --source=커밋 git-basics.md`를 실행하기 전에, 그 커밋에 `git-basics.md`라는 파일이 있었는지 생각해 보고 무슨 일이 생길지 예상해 적는다. 실행한 뒤 `git status -s`와 `ls`로 확인한다. `--source`의 커밋에 없는 파일을 되돌리면 Git은 그 시점처럼 **파일을 지운다.** 지워진 파일은 `git restore git-basics.md`로 되살린다(스테이징 영역에는 남아 있다).
   - 이번에는 `git restore --source=커밋 git.md`를 실행한다. 어떤 파일이 생겼고 `git status -s`에 어떻게 보이는지 적는다. 확인했으면 그 파일을 지운다.
   - 끝나면 `git status`가 깨끗한지 확인한다.
4. **`git clean`** — `scratch.txt`, `drafts/` 폴더(안에 파일 하나), `secret.env`를 만들고, `.gitignore`를 만들어 `*.env`를 적는다(`.gitignore`는 커밋하지 않는다). 다음 명령의 결과를 차례로 적는다. `git clean -n`, `git clean -nd`, `git clean -ndx`. `.gitignore` 자신은 어느 목록에 나오는가? `secret.env`는 남기고 나머지 셋을 지우는 명령을 찾아 실행한다. 마지막에 `secret.env`도 손으로 지운다.
5. **VS Code** — `git-basics.md`를 고치고 저장한 뒤, 소스 제어 보기에서 **Discard Changes**로 버린다. 확인 대화 상자의 문장을 적는다. 추적하지 않는 파일을 하나 만들어 같은 버튼을 눌러 보고, 대화 상자의 문장이 어떻게 다른지 적는다(이번에는 **취소**를 누른다).
6. **옛 명령 읽기** — 다음은 어떤 사람이 인터넷에서 찾은 명령들이다. 각각 무엇을 하는지 5.7.7의 표로 바꿔 적고, 되살릴 수 없게 되는 것이 있으면 무엇인지 적는다. 실행하지는 않는다.
   - `git checkout -- .`
   - `git reset HEAD README.md`
   - `git checkout HEAD~3 -- shop/pricing.py`
   - `git clean -fdx`

## 정리

| 항목 | 핵심 |
|---|---|
| 버전 관리 | 원하는 시점의 프로젝트 전체를 기록하고, 차이를 보고, 되돌리고, 합친다. 로컬 기록(파일 단위, 저장할 때, 내 컴퓨터만)과 달리 프로젝트 단위, 내가 정할 때, 메시지와 함께 |
| Git과 GitHub | Git은 내 컴퓨터의 프로그램, 저장소는 `.git`이 든 프로젝트 폴더, GitHub는 저장소를 올려 함께 쓰는 서비스. 커밋은 내 컴퓨터에서 일어나고 올리는 것은 따로(8장). 저장소를 받으면 이력 전체가 온다 |
| 커밋 = 스냅숏 | 그 시점 프로젝트 전체 + 작성자·시각·메시지·부모. 같은 내용은 한 번만 저장. "바뀐 줄"은 두 스냅숏을 비교해 그때그때 계산한다. 이름 바꾸기는 기록하지 않고 짐작한다 |
| 설정 범위 | 시스템 < 전역(`--global`, `~/.gitconfig`) < 저장소(`.git/config`). 좁은 범위가 이긴다. `git config --list --show-origin`, `git config --global --edit` |
| 처음 설정 | `user.name`, `user.email`(공개된다), `init.defaultBranch main`, `core.editor "code --wait"`(`--wait`가 없으면 빈 메시지로 취소), `core.quotepath false` |
| 줄 끝 문자 | LF(macOS·리눅스)와 CRLF(Windows). `core.autocrlf`는 내 컴퓨터(Windows `true`는 설치 기본값, macOS `input`), `.gitattributes`는 저장소의 규칙으로 모두에게 적용되고 더 먼저. 이 과정의 기본은 `* text=auto eol=lf` + `*.bat`·`*.cmd`는 CRLF. `LF will be replaced by CRLF`는 안내. `git ls-files --eol` |

| `git commit` | `-m "제목"`(본문은 `-m` 한 번 더), 편집기(저장하고 탭 닫기, 비우면 취소), `-v`로 diff 보며 쓰기. `-a`는 추적 파일만, 확인을 건너뛴다. VS Code의 "모두 스테이징하고 커밋?"은 고르지 않는다 |
| `git diff` | 옵션 없음: 작업 폴더 ↔ 스테이징 영역. `--staged`(`--cached`): 스테이징 영역 ↔ 마지막 커밋(지금 커밋하면 들어갈 것). `HEAD`: 작업 폴더 ↔ 마지막 커밋. 커밋 둘: 두 스냅숏. `add` 직후 `git diff`가 비는 것은 정상. 추적 안 하는 파일은 안 나온다 |
| diff 읽기 | `a/` 전, `b/` 후, `@@ -시작,줄수 +시작,줄수 @@`, `-` 지운 줄, `+` 더한 줄, 고친 줄은 `-`와 `+` 한 쌍. `index` 줄로 무엇을 비교했는지 안다. `\ No newline at end of file` |

| `git show` | 커밋 정보 + 그 커밋의 diff. `--stat`, `커밋 -- 경로`(변경), `커밋:경로`(그 시점 내용 전체, `/`로) |

| 커밋 메시지 | 제목(무엇을, 30자 안팎, 마침표 없음, 끝맺음 통일) + 빈 줄 + 본문(왜, 어떻게 발견, 왜 이 방법). "수정"·파일 이름·diff의 반복은 피한다. 저장소의 규칙(Conventional Commits 등)을 따른다 |

| AI가 쓴 메시지 | 스테이징한 것과 맞는지, 왜가 지어낸 것이 아닌지, 한 가지 일인지, 저장소 규칙과 맞는지 |
| 올리지 않을 것 | 다시 만들 수 있는 것, 비밀 값, 개인 데이터, 내 컴퓨터의 흔적, 큰 파일. 저장소에는 받아서 다시 만드는 데 필요한 것만 |

| `git restore` | 옵션 없음: 스테이징 영역 → 작업 폴더(마지막 커밋이 아니다). `--staged`: 마지막 커밋 → 스테이징 영역(스테이징 취소). `--staged --worktree`(`-SW`): 마지막 커밋 → 둘 다. `--source=커밋`: 그 커밋 → 작업 폴더(그 커밋에 없는 파일은 지운다). 지운 파일 되살리기 |
| 되살릴 수 없는 것 | 커밋(스테이징)한 적 없는 변경. 버리기 전에 `git diff`, 아까우면 커밋·복사·stash(7장). 마지막 희망은 VS Code 로컬 기록 |
| `git clean` | 추적 안 하는 파일 삭제. 기본은 거절. `-n`으로 먼저, `-f` 실행, `-d` 폴더, `-x` 무시하는 파일까지(`.env`, `.venv`가 사라진다), `-i` |

| VS Code | 소스 제어 보기(`Ctrl+Shift+G`): `U`/`A`/`M`/`D`/`R`, Changes·Staged Changes, `+` = add, `−` = restore --staged, `↶` = restore(추적 안 하는 파일은 삭제), Commit 버튼, 비교 화면 = diff, Graph = log, 타임라인 = log -- 파일, Blame 표시, 상태 표시줄의 브랜치 |
