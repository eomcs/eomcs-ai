# 10장. 마무리

[개발 도구](README.md) 과정의 마지막 장이다. 2장부터 9장까지 도구를 하나씩 익혔다. 터미널로 파일을 다루고 명령을 잇고(2·3장), VS Code로 코드를 읽고 디버깅하고(4장), Git으로 변경을 기록하고 갈라지고 합치고 되돌리고(5~7장), GitHub로 나누고 리뷰하고(8장), 노트북으로 데이터를 들여다보았다(9장). 그런데 장마다 실습 재료가 달랐다. `shop`, `notes`, `ledger` 같은 연습용 프로젝트는 `make_files.py`가 만들어 주었고, 그 장에서 배울 도구가 잘 드러나도록 미리 짜여 있었다.

이 장에서는 **내가 만든 프로젝트**로 돌아간다. 기초 과정 10장에서 만든 가계부 요약 프로그램 `ledger_app`이다. 1장에서 이 폴더를 점검하며 "이 과정의 10장에서 Git 저장소가 된다"고 했고, 3장에서는 이 폴더에 `run_all` 스크립트를 만들며 "10장에서 함께 올린다"고 했다. 그 약속을 지킨다.

- **종합 실습** — 기초 과정 10장에서 만든 프로젝트(가계부 요약 또는 직접 만든 CLI 프로그램)를 이 과정의 도구로 다시 다룬다. 저장소로 만들어 GitHub에 올리고, 새 기능 하나를 이슈 → 브랜치 → PR → 리뷰 → 병합 흐름으로 추가하고, 프로그램이 만든 결과를 노트북에서 탐색한다. 마지막으로 기초 과정의 "복원 시험 B"를 Git 저장소에서 내려받는 방식으로 다시 한다.

이 장에는 새 도구가 없다. 대신 지금까지 따로 익힌 도구를 **한 프로젝트의 흐름 안에서 이어 쓰는** 법을 익힌다. 실제 일은 장 단위로 나뉘어 오지 않는다. 기능 하나를 더하는 동안에도 터미널, 편집기, Git, GitHub를 오가고, 중간에 동료의 변경이 끼어들고, 실수한 커밋을 되돌려야 하는 일이 생긴다. 이 장은 그 하루를 처음부터 끝까지 겪어 보는 장이다.

종합 실습의 완료 기준은 아홉 가지다. 이 장의 모든 절은 이 기준을 하나씩 채우기 위한 것이다. 이 장에서는 기준을 번호(①~⑨)로 가리킨다.

> **종합 실습 완료 기준**
> 1. `.venv`, `__pycache__`, 개인 데이터 파일, `.env`가 저장소에 들어가지 않았음을 `git status`, `git check-ignore -v`, GitHub 화면으로 보인다.
> 2. 커밋 하나가 한 가지 일을 하고, 커밋 메시지만 읽어도 무엇을 왜 바꿨는지 알 수 있다.
> 3. 기능 하나를 이슈와 PR로 추가하고, PR에 리뷰 의견을 남기고 반영한 기록이 GitHub에 있다.
> 4. 두 브랜치에서 같은 곳을 고쳐 충돌을 일부러 만들고, 해결해 병합한 이력을 `git log --graph`로 보이고 해결 과정을 설명할 수 있다.
> 5. 잘못 넣은 커밋 하나를 `git revert`로 되돌리고, 첫 완성 시점에 태그(`v1.0.0`)를 단다.
> 6. 명령행 인자를 준 디버그 실행 설정(`launch.json`)과 권장 확장 목록을 저장소에 포함하고, 다른 사람이 받아서 바로 디버깅할 수 있다.
> 7. 프로젝트의 모듈을 import해 결과를 탐색하는 노트북이 출력을 지운 상태로 커밋되어 있고, 새 커널에서 "모두 실행"으로 끝까지 실행된다.
> 8. 다른 폴더(가능하면 다른 운영체제의 컴퓨터)에서 `git clone` 후 `README.md`에 적힌 명령만으로 가상환경을 복원하고 실행·검사 스크립트를 통과한다.
> 9. 프로젝트에서 반복하는 명령(검사 실행 등)을 `&&`로 이은 한 줄 명령이나 스크립트로 정리해 `README.md`에 적는다.

> **1단계를 마친 사람에게**
> 1단계에서는 "GitHub에 올려 줘", "이 기능 추가해 줘", "배포해 줘"라고 말하면 AI 도구가 명령을 실행했다. 화면에는 초록색 체크 표시가 줄줄이 지나갔고, 결과는 대개 돌아갔다. 그런데 무엇이 저장소에 올라갔는지, 왜 어제 되던 기능이 오늘 안 되는지, 두 번 고친 내용 중 어느 것이 남았는지는 알 수 없었다. 이 장의 아홉 가지 기준은 모두 **"그 일을 내가 직접 했고, 무엇이 일어났는지 보여 줄 수 있다"**는 뜻이다. 이 장을 마치면 AI 도구가 같은 일을 대신할 때도 그 결과를 `git log`, `git diff`, PR 화면으로 확인하고, 마음에 들지 않으면 되돌릴 수 있다. 선택 활동 A에서 실제로 그렇게 해 본다.

## 학습 목표

이 장을 마치면 다음을 할 수 있다.

- 이미 있는 프로젝트를 저장소로 만들기 전에 상위 폴더가 저장소가 아닌지, 무엇이 추적되고 무엇이 무시될지를 `git status --ignored`와 `git check-ignore -v`로 확인할 수 있다.
- 처음 커밋할 때도 파일을 성격별로 나누어 커밋하고, 이력 전체에 올리지 않을 파일이 들어간 적이 없는지 `git log --all --name-only`로 확인할 수 있다.
- 디버그 실행 설정, 권장 확장, 작업 공간 설정을 `.gitignore`의 예외 규칙과 함께 저장소에 담고, 절대 경로나 운영체제에 묶인 설정을 빼는 이유를 말할 수 있다.
- `gh`로 비공개 저장소를 만들어 올리고, 올라간 파일 목록을 웹 화면과 `gh api`로 확인할 수 있다.
- 이슈 두 개를 두 사람이 나누어 맡아 브랜치·커밋·PR로 진행하고, 먼저 병합된 변경 때문에 생긴 충돌을 내 브랜치에서 해결할 수 있다.
- 충돌 표시가 없어도 시험이 실패하는 "보이지 않는 충돌"을 찾아 병합 커밋 안에서 고치고, 그 과정을 병합 커밋 메시지에 남길 수 있다.
- 리뷰 의견(제안)을 받아 반영하고 대화를 마무리한 뒤, 병합 방식을 골라 병합하고, `git log --graph`에서 충돌 해결 이력을 찾아 설명할 수 있다.
- 이미 공유한 `main`에 들어간 잘못된 커밋을 `git revert`로 되돌리고, 같은 실수를 막는 습관과 장치를 말할 수 있다.
- 프로젝트 모듈을 import하는 탐색 노트북을 만들고, nbstripout으로 출력을 지워 커밋하고, `jupyter nbconvert --execute`로 새 커널에서 끝까지 실행되는지 검증할 수 있다.
- 실행에 필요한 패키지(`requirements.txt`)와 개발에 필요한 도구(`requirements-dev.txt`)를 나누고, 커밋 전에 실행할 검사를 한 줄 명령으로 `README.md`에 적을 수 있다.
- 첫 완성 시점에 주석 태그를 달아 올리고, 원래 폴더를 숨긴 채 `git clone`으로 받은 저장소를 `README.md`만 보고 복원해 실행·검사·디버깅할 수 있다.
- 완료 기준마다 무엇을 보여 주면 되는지 명령과 화면으로 정리하고, 같은 과정을 내 프로젝트에 적용할 수 있다.

### 시작하기 전에 — 프로젝트 점검

**1. 상위 폴더가 저장소가 아닌지 확인한다.**

저장소 안에 또 저장소를 만들면 바깥 저장소는 안쪽 폴더를 파일로 추적하지 못하고 이상한 상태가 된다. 혹시 `~/python-lab`이나 홈 폴더를 통째로 저장소로 만든 적이 있는지 확인한다.

```
cd ~/python-lab/ch10/ledger_app
git rev-parse --show-toplevel
```

```
fatal: not a git repository (or any of the parent directories): .git
```

이 메시지가 나와야 한다. "이 폴더도, 그 위의 어느 폴더도 저장소가 아니다"라는 뜻이다. 만약 `/Users/본인계정/python-lab`처럼 경로가 출력되면 그 폴더가 이미 저장소다. 그 저장소를 어떻게 할지(지울지, 그대로 둘지) 정하기 전에는 이 장을 시작하지 않는다. 지울 때는 그 폴더의 `.git` 폴더만 지우면 저장소가 아닌 평범한 폴더로 돌아간다. 파일은 그대로 남지만 그 저장소의 이력은 사라지므로, 경로를 두 번 확인한다.

**2. 프로그램이 지금 돌아가는지 확인한다.**

```
# macOS
source .venv/bin/activate

# Windows
.venv\Scripts\Activate.ps1
```

```
python run_all.py
```


`run_all.py`가 없다면 3.6.3을 보고 지금 만든다. 셸 스크립트(`run_all.sh`)나 PowerShell 스크립트(`run_all.ps1`)를 만들었다면 그것도 그대로 둔다. 10.2에서 함께 커밋한다.

**3. 폴더에 무엇이 있는지 본다.**

1.3.5에서 본 파일에 더해 `run_all` 스크립트, 그리고 실습하며 생긴 파일이 있을 것이다. `samples/2026-10_summary.csv`(프로그램이 만든 결과), `__pycache__`, 기초 과정의 실습에서 만든 `out.txt`나 `after.txt`, `samples/test.csv` 같은 파일이다. 지금 지우지 않아도 된다. 10.2에서 Git이 이 파일들을 어떻게 보는지 확인하면서 정리한다.

**4. 백업을 만든다.**

이 장에서는 원래 프로젝트에 직접 저장소를 만들고, 기능을 더하고, 충돌을 만든다. 처음 상태로 돌아갈 수 있도록 사본을 하나 둔다.

```
# macOS
cp -R ~/python-lab/ch10/ledger_app ~/devtools-lab/ch10/ledger_app_backup

# Windows
Copy-Item -Recurse ~\python-lab\ch10\ledger_app ~\devtools-lab\ch10\ledger_app_backup
```

사본에 들어간 `.venv`는 원래 위치에 묶여 있어서 사본에서는 쓸 수 없다(기초 과정 9.1.8). 사본은 되돌릴 때 파일만 다시 가져오는 용도다.

> **기초 과정의 결과가 교재와 다르다면**
> 기초 과정 실습 10-2의 "확인할 것"과 "더 해 보기"에서 프로그램을 고쳤다면 내 `ledger_app`은 교재와 조금 다르다. 특히 **"수입만 있는 달"의 화면을 이미 고쳤다면** 10.5에서 도윤이 맡을 이슈가 이미 해결된 상태다. 두 가지 중 하나를 고른다.
> - **교재와 똑같이 따라 하기** — 교재 저장소의 [`python-basic-lab/ch10/ledger_app`](../python-basic-lab/ch10/ledger_app)에 있는 파일로 `~/python-lab/ch10/ledger_app`을 다시 만든다. 내가 고친 프로젝트는 방금 만든 백업에 남아 있다. 3.6.3의 `run_all.py`를 더하고, 가상환경을 다시 만든다(기초 과정 10.4.2의 A).
> - **내 프로젝트로 하기** — 그대로 진행하되, 10.5에서 고를 두 이슈를 내 프로젝트에 맞게 바꾼다. 두 이슈가 **같은 함수의 같은 부분을 고치게** 고르는 것이 핵심이다.
>
> 기초 과정 실습 10-4에서 만든 **나만의 명령행 프로그램**이 있다면, 이 장의 본문은 `ledger_app`으로 따라 하고, 마지막 실습 10-10에서 같은 과정을 그 프로젝트로 혼자 해 본다.

> **실습을 처음부터 다시 하려면**
> 이 장에서는 세 곳에 흔적이 남는다.
> 1. **GitHub의 `ledger-app` 저장소** — 8.7.2의 상자에 있는 방법으로 지운다. 이슈와 PR 기록도 함께 사라진다.
> 2. **`~/devtools-lab/ch10`의 `doyun`, `restore_test` 폴더** — 통째로 지운다.
> 3. **`~/python-lab/ch10/ledger_app`** — 폴더를 지우고 백업(`ledger_app_backup`)을 같은 이름으로 복사해 온 뒤 가상환경을 다시 만든다. 백업에는 `.git`이 없으므로 저장소가 아닌 처음 상태로 돌아간다.
>
> 지우기 전에는 언제나 `pwd`로 위치를 확인한다(2.4.4).

> **내가 만드는 커밋의 해시**
> 이 장의 모든 커밋은 내가 만든다. 커밋 해시는 작성자, 시각, 내용으로 정해지므로 교재의 해시와 내 화면의 해시는 다르다. 교재의 출력에서 해시를 읽을 때는 내 화면의 해시로 바꿔 읽고, 명령에 해시를 넣을 때는 반드시 내 화면의 것을 쓴다. 이슈와 PR의 번호도 같다. 이 장의 번호는 새 저장소에서 처음부터 따라 했을 때의 번호다.

### 10.1.1 이 장에서 지킬 규칙

이 장에서는 다음 규칙을 정해 두고 일한다. 대부분 이미 배운 것이다. 한 프로젝트에서 모두 함께 지키는 것이 이 장의 연습이다.

1. **`main`은 언제나 실행되는 상태로 둔다**(6.5.1). `main`에 직접 커밋하지 않고, 일마다 브랜치를 만들어 PR로 병합한다. 10.6에서 이 규칙을 일부러 어겨 보고 그 결과를 수습한다.
2. **커밋하기 전에 `git diff --staged`를 본다**(5.5.4). 그리고 `python run_all.py`로 시험을 통과하는지 확인한다.
3. **브랜치 이름에 이슈 번호를 넣는다**(6.5.3). `feature/2-income-table`, `fix/3-no-expense-table`.
4. **PR 설명에 무엇을, 왜, 어떻게 확인했는지 쓴다**(8.5.4). 이슈를 닫는 PR이면 `Closes #번호`를 넣는다.
5. **커밋 메시지는 한국어로, 짧게 끝맺는다**(5.5.2). "추가", "표시", "반영"처럼.
6. **비밀 값과 개인정보는 커밋하지 않는다**(8.3). 이 프로젝트에는 아직 비밀 값이 없지만, 내 실제 가계부는 개인정보다.

## 10.2 저장소로 만들기

5장에서는 `make_files.py`가 만든 빈 폴더에서 저장소를 시작했다. 이번에는 파일이 이미 가득한 폴더, 그것도 실행하며 생긴 결과 파일과 가상환경, 내 가계부가 섞여 있을 수 있는 폴더를 저장소로 만든다. 순서가 중요하다. **무엇을 넣지 않을지 먼저 정하고, 그다음에 넣는다.**

### 10.2.1 `git init` 하고 바로 커밋하지 않는다

```
cd ~/python-lab/ch10/ledger_app
git init
```

```
Initialized empty Git repository in /Users/본인계정/python-lab/ch10/ledger_app/.git/
```

5.2.3에서 `init.defaultBranch`를 `main`으로 정해 두었으므로 브랜치는 `main`이다. 저장소별 설정은 따로 하지 않는다. 이 저장소의 커밋은 5.2.2와 8장의 "커밋에 들어갈 이메일 확인하기"에서 정한 전역 이름과 이메일로 만들어진다. 확인한다.

```
git config user.name
git config user.email
```

```
엄진영
12345678+jinyoung-dev@users.noreply.github.com
```

이제 `git status`를 본다. 아직 `git add .`를 하지 않는다.

```
git status
```

```
On branch main

No commits yet

Untracked files:
  (use "git add <file>..." to include in what will be committed)
	.gitignore
	DESIGN.md
	README.md
	check_samples.py
	ledger/
	main.py
	requirements.txt
	run_all.py
	samples/
```

`.venv`와 `__pycache__`가 목록에 없다. 기초 과정 10.2.1에서 만든 `.gitignore`가 이미 일하고 있다. 무엇이 무시되고 있는지는 `--ignored`를 붙여 본다.

```

```

```

?? DESIGN.md
?? README.md
?? check_samples.py

?? main.py
?? requirements.txt

```

`??`는 추적하지 않는 파일, `!!`는 **무시되는** 파일이다(5.6.4). 결과 파일 `2026-10_summary.csv`가 `*_summary.csv` 규칙으로 무시되고 있다. 내 화면에 `out.txt`, `after.txt`, `samples/test.csv`처럼 `??`로 보이는 연습 파일이 있다면 이 순간이 정리할 때다. 넣을 것인가, 지울 것인가, 무시할 것인가를 파일마다 정한다. 기초 과정에서 연습으로 만든 파일이라면 지운다. 지우기 전에 `git clean -n`으로 무엇이 지워질지 먼저 볼 수 있지만(5.7.6), 지금은 **추적하지 않는 파일이 전부**이므로 `git clean`은 쓰지 않는다. 저장소에 넣을 파일까지 모두 지워 버린다. 파일 이름을 하나씩 확인하며 `rm`(Windows `Remove-Item`)으로 지운다.

### 10.2.2 `.gitignore` 다듬기

기초 과정의 `.gitignore`는 네 줄이었다.

```
.venv/
__pycache__/
data/
*_summary.csv
```

이 과정에서 배운 것으로 보면 빠진 것이 둘 있다.

- **`.env`** — 이 프로그램은 아직 환경 변수를 쓰지 않는다. 하지만 "LLM API 활용"에서 이 프로젝트에 API 키를 더하는 순간 `.env`가 생긴다. 그때 `.gitignore`를 고치는 것을 잊으면 키가 커밋된다(8.3). **비밀 값 파일은 생기기 전에 막아 둔다.**
- **`.vscode`의 개인 파일** — 10.3에서 팀이 함께 쓸 설정만 올린다. 그 밖의 파일은 무시한다(4.2.6).

`.gitignore`를 다음과 같이 고친다. 줄마다 왜 있는지 주석을 단다(5.6.3).

```
# 가상환경
.venv/

# 파이썬이 만드는 것
__pycache__/

# 비밀 값
.env

# 내 가계부(개인 정보)와 프로그램이 만드는 결과
data/
*_summary.csv

# VS Code — 팀이 함께 쓸 설정만 올린다
.vscode/*
!.vscode/settings.json
!.vscode/extensions.json
!.vscode/launch.json
```

규칙이 실제로 동작하는지 확인한다. 아직 없는 파일도 확인할 수 있으므로, **내 실제 가계부가 들어갈 자리**와 `.env`를 함께 확인한다.

```
git check-ignore -v .venv/ ledger/__pycache__ samples/2026-10_summary.csv data/2026-11.csv .env README.md
```

```
.gitignore:2:.venv/	.venv/
.gitignore:5:__pycache__/	ledger/__pycache__
.gitignore:12:*_summary.csv	samples/2026-10_summary.csv
.gitignore:11:data/	data/2026-11.csv
.gitignore:8:.env	.env
```

한 줄에 하나씩 "어느 파일의 몇째 줄, 어떤 규칙에 걸렸는가"가 나온다(5.6.4). 마지막에 넣은 `README.md`는 아무 규칙에도 걸리지 않아서 출력이 없다. 이것도 확인이다. 넣을 파일이 실수로 무시되고 있지 않다는 뜻이다. 완료 기준 ①의 첫 번째 증거다. 이 출력을 `check.md`에 붙여 둔다.

> **`data/` 폴더에 정말로 내 가계부가 있다면**
> 기초 과정에서 내 실제 가계부를 `data/`에 두고 실행해 보았다면 그 파일은 위의 규칙 덕분에 저장소에 들어가지 않는다. 그런데 프로그램은 요약 파일을 **입력 파일 옆에** 저장한다(기초 과정 10.1.4). `data/2026-11.csv`를 요약하면 `data/2026-11_summary.csv`가 생기고, 이것도 `data/` 규칙에 걸린다. 반대로 내 가계부를 `samples/`나 프로젝트 폴더 바로 아래에 두었다면 원본은 무시되지 **않는다.** `git status`에 처음 보는 `.csv` 파일이 `??`로 보이면 넣기 전에 반드시 열어 본다.

### 10.2.3 `.gitattributes` — 줄 끝 문자

macOS와 Windows에서 함께 쓸 저장소이므로 줄 끝 문자를 정해 둔다(5.2.6). 프로젝트 폴더에 `.gitattributes`를 만든다.

```
* text=auto eol=lf
```

저장소에도 작업 폴더에도 텍스트 파일을 LF로 둔다. Windows에서 VS Code로 만든 파일은 CRLF일 수 있다. 그러면 다음 단계의 `git add`에서 다음과 같은 안내가 나온다.

```
warning: in the working copy of 'README.md', CRLF will be replaced by LF the next time Git touches it
```

5.2.6에서 본 대로 오류가 아니라 안내다. 저장소에는 LF로 들어간다. 3.6.1의 상자에서 본 `bash\r` 문제도 이 줄이 막아 준다.

### 10.2.4 성격별로 나누어 첫 커밋하기

이제 넣는다. 이미 완성된 프로젝트를 처음 넣을 때는 `git add .` 한 번에 커밋 하나로 끝내기 쉽다. 그래도 된다. 하지만 완료 기준 ②를 생각하면 **성격이 다른 파일은 나누어 넣는 편이 낫다.** 나중에 `git log`를 읽는 사람(석 달 뒤의 나를 포함해서)이 "이 저장소의 규칙", "프로그램", "문서", "도구"가 각각 언제 어떤 모습으로 들어왔는지 알 수 있다.

**커밋 1 — 저장소 규칙**

```
git add .gitignore .gitattributes
git status --short
```

```
A  .gitattributes
A  .gitignore
?? DESIGN.md
?? README.md
?? check_samples.py
?? ledger/
?? main.py
?? requirements.txt
?? run_all.py
?? samples/
```

```
git commit -m "무시할 파일과 줄 끝 문자 규칙 추가"
```

규칙 파일을 맨 처음에 커밋하는 데는 이유가 있다. 이후의 모든 커밋이 이 규칙 아래에서 만들어진다. 규칙보다 파일이 먼저 들어가면, 무시했어야 할 파일이 이미 커밋된 뒤에 규칙을 더하게 되고 그때는 `git rm --cached`로 빼야 한다(5.6.7).

**커밋 2 — 프로그램**

```
git add main.py ledger samples check_samples.py requirements.txt
git status --short
```

```
A  check_samples.py
A  ledger/__init__.py
A  ledger/cli.py
A  ledger/core.py
A  ledger/models.py
A  ledger/storage.py
A  main.py
A  requirements.txt
A  samples/2026-10.csv
A  samples/bad_quote.csv
A  samples/broken.csv
A  samples/empty.csv
A  samples/header_only.csv
?? DESIGN.md
?? README.md
?? run_all.py
```

`ledger/__pycache__`와 `samples/2026-10_summary.csv`는 폴더째 `git add`했는데도 들어가지 않았다. `git add`는 무시되는 파일을 건너뛴다. 크기가 0인 `empty.csv`도 문제없이 들어갔다. Git은 빈 **파일**은 추적한다(빈 **폴더**는 추적하지 못한다).

Windows에서 기초 과정 10.2.1의 `requirements.txt`를 PowerShell 5.1로 만들었다면 UTF-16일 수 있다. 1.3.5에서 확인하고 다시 만들었는지 한 번 더 본다. 아직 고치지 않았다면 지금 고치고 `git add requirements.txt`를 다시 한다.

```
git diff --staged --stat
```

```
 check_samples.py        | 109 +++++++++++++++++++++
 ledger/__init__.py      |   1 +
 ...
 13 files changed, 520 insertions(+)
```

`requirements.txt` 줄의 숫자가 `Bin`으로 보이면 UTF-16이다(Git이 바이너리로 본다). 숫자 줄 수가 보이면 괜찮다. 숫자는 내 프로젝트에 따라 다르다.

```
git commit -m "가계부 요약 프로그램 첫 버전" -m "기초 과정 10장에서 만든 프로그램을 그대로 옮겼다. 시험 파일 다섯 개와
check_samples.py를 함께 넣었다."
```

본문에 "어디서 온 코드인가"를 적었다. 저장소의 이력이 이 커밋에서 시작하지만 프로그램은 그 전부터 있었다는 것을 남겨 둔다.

**커밋 3 — 문서, 커밋 4 — 도구**

```
git add README.md DESIGN.md
git commit -m "README와 설계 노트 추가"

git add run_all.py
git commit -m "시험과 예제 실행을 묶은 run_all 스크립트 추가"
```

`run_all.sh`나 `run_all.ps1`도 만들었다면 커밋 4에 함께 넣는다.

> **셸 스크립트의 실행 권한**
> macOS에서 `chmod +x run_all.sh`를 해 두었다면(3.6.1) Git은 이 파일을 **실행할 수 있는 파일**로 기록한다. `git ls-files -s run_all.sh`의 맨 앞 숫자가 `100755`이면 실행 권한이 기록된 것이고, `100644`이면 보통 파일이다. Windows에서 만든 `.sh`는 실행 권한이라는 개념이 없어서 `100644`로 들어간다. 그러면 macOS나 리눅스에서 받은 사람이 `./run_all.sh`를 실행할 때 `permission denied`가 난다. Windows에서도 `git update-index --chmod=+x run_all.sh` 후 커밋하면 저장소에 실행 권한을 기록할 수 있다.

```
git status
git log --oneline
```

```
On branch main
nothing to commit, working tree clean
```

```
6f75a08 시험과 예제 실행을 묶은 run_all 스크립트 추가
93a8b1d README와 설계 노트 추가
643136c 가계부 요약 프로그램 첫 버전
f46e106 무시할 파일과 줄 끝 문자 규칙 추가
```

**working tree clean**인데 폴더에는 `.venv`, `__pycache__`, `2026-10_summary.csv`가 그대로 있다. "작업 폴더가 깨끗하다"는 "추적하는 파일 중 바뀐 것이 없고, 추적하지 않는 파일 중 무시되지 않는 것이 없다"는 뜻이다.

### 10.2.5 무엇이 들어갔는지 확인하기

넣지 않을 것이 정말로 빠졌는지 **저장소 쪽에서** 확인한다. `git status`는 작업 폴더를 보여 주고, `git ls-files`는 저장소가 추적하는 파일을 보여 준다.

```
git ls-files
```

```
.gitattributes
.gitignore
DESIGN.md
README.md
check_samples.py
ledger/__init__.py
ledger/cli.py
ledger/core.py
ledger/models.py
ledger/storage.py
main.py
requirements.txt
run_all.py
samples/2026-10.csv
samples/bad_quote.csv
samples/broken.csv
samples/empty.csv
samples/header_only.csv
```

목록이 짧으면 눈으로 보면 되지만, 길어지면 검사를 명령으로 만든다. 3.2.2의 `grep`으로 "들어가면 안 되는 이름"을 찾는다.

```
# macOS
git ls-files | grep -E '(^|/)(\.venv|__pycache__|data)/|\.env$'

# Windows
git ls-files | Select-String -Pattern '(^|/)(\.venv|__pycache__|data)/|\.env$'
```

아무것도 나오지 않아야 한다. macOS에서 `echo $?`를 하면 `1`이다. `grep`은 찾은 것이 없으면 종료 코드 1로 끝난다(3.3). 여기서는 1이 좋은 소식이다.

`git ls-files`는 **지금** 추적하는 파일만 보여 준다. 한 번 커밋했다가 `git rm --cached`로 뺀 파일은 이 목록에는 없지만 **이력에는 남아 있다**(5.6.7, 8.3.5). 이력 전체에서 한 번이라도 들어간 적이 있는 파일을 보려면 다음을 쓴다.

```
git log --all --name-only --format= | sort -u
```

`--name-only`는 커밋마다 바뀐 파일 이름을, `--format=`(빈 형식)은 커밋 정보를 빼고 파일 이름만 출력하게 한다. `sort -u`는 정렬하고 중복을 없앤다(3.2.3. Windows는 `| Sort-Object -Unique`). 지금은 `git ls-files`와 같은 목록이 나온다. 이 장을 마칠 때 한 번 더 실행해서 이 장 내내 들어가면 안 되는 파일이 이력에 들어간 적이 없다는 것을 보인다(10.10).

### 실습 10-2. 저장소로 만들기

1. 10.2.1~10.2.4를 내 `ledger_app`에서 한다. 커밋은 네 개(또는 셸 스크립트를 따로 둔다면 그 이상)로 나눈다.
2. `git status --ignored --short`의 결과와 `git check-ignore -v`의 결과를 `check.md`에 붙인다.
3. 다음 상황에서 어떻게 할지 적고, 가능하면 직접 해 본 뒤 되돌린다.
   - (가) `samples` 폴더에 `my_2026-11.csv`(내 실제 가계부를 복사한 것)를 넣고 `git status`를 본다. 무엇이 보이는가? 이 파일이 실수로 커밋되지 않게 하는 방법 두 가지를 적는다(파일을 옮기기, 규칙 더하기). 어느 쪽이 나은가?
   - (나) `.gitignore`의 `*_summary.csv`를 지우고 `git status`를 본다. 커밋하기 전에 알아챌 수 있는가? 확인했으면 `git restore .gitignore`로 되돌린다.
   - (다) `.env` 파일을 만들어 `X=1`을 적고 `git status`와 `git check-ignore -v .env`를 실행한다. 확인했으면 지운다.
4. `git log --oneline`을 보고, 커밋 메시지만 읽어서 각 커밋이 무엇을 왜 했는지 설명할 수 있는지 적는다. 설명하기 어려운 커밋이 있다면 지금은 아직 푸시 전이므로 `git commit --amend`(마지막 커밋)나 `git rebase -i`(7.5.5)로 메시지를 고칠 수 있다.

### 10.3.1 `launch.json` — 명령행 인자를 준 실행 설정

이 프로그램은 명령행 인자로 파일 이름을 받는다. 그래서 그냥 `F5`를 누르면 인자 없이 실행되어 `사용법: python main.py 가계부파일.csv`가 나오고 끝난다. 인자를 준 설정을 저장해 둔다. 4.4.2처럼 실행 및 디버그 보기에서 **create a launch.json file**을 누르거나, `.vscode/launch.json`을 직접 만든다.

```jsonc
{
    "version": "0.2.0",
    "configurations": [
        {
            "name": "가계부 요약: 2026-10.csv",
            "type": "debugpy",
            "request": "launch",
            "program": "${workspaceFolder}/main.py",
            "args": ["samples/2026-10.csv"],
            "console": "integratedTerminal"
        },
        {
            "name": "가계부 요약: broken.csv",
            "type": "debugpy",
            "request": "launch",
            "program": "${workspaceFolder}/main.py",
            "args": ["samples/broken.csv"],
            "console": "integratedTerminal"
        },
        {
            "name": "가계부 요약: 파일 고르기",
            "type": "debugpy",
            "request": "launch",
            "program": "${workspaceFolder}/main.py",
            "args": "${command:pickArgs}",
            "console": "integratedTerminal"
        },
        {
            "name": "시험: check_samples.py",
            "type": "debugpy",
            "request": "launch",
            "program": "${workspaceFolder}/check_samples.py",
            "console": "integratedTerminal"
        }
    ]
}
```

설정을 고른 기준은 "이 프로젝트를 처음 받은 사람이 가장 먼저 실행해 볼 것"이다.

- **2026-10.csv** — 정상 파일. 프로그램이 하는 일 전체를 따라가 볼 수 있다.
- **broken.csv** — 형식 오류 9건. `parse_row()`에서 오류를 모으는 과정을 중단점으로 따라가 볼 수 있다. 정상 경로만큼 자주 디버깅하게 되는 경로다.
- **파일 고르기** — 그 밖의 파일. 실행할 때마다 인자를 입력받는다(4.4.2).
- **check_samples.py** — 시험이 실패할 때 `describe()` 안에서 멈춰 보려고.

4.4.2에서 강조한 것을 다시 확인한다. `program`은 `${workspaceFolder}/main.py`처럼 **작업 공간 기준**으로 썼고, 인자의 `samples/2026-10.csv`는 작업 폴더 기준의 상대 경로다. `/Users/본인계정/...` 같은 절대 경로가 하나도 없다. 비밀 값(`env`)도 없다. 그래서 이 파일은 저장소에 올려도 된다(4.2.6).

저장한 뒤 목록에서 **가계부 요약: broken.csv**를 고르고, `ledger/storage.py`의 `load_transactions()` 안에서 문제를 모으는 줄에 중단점을 둔 뒤 `F5`를 눌러 본다. 변수 창에 `problems` 리스트가 한 줄씩 늘어나는 것이 보인다(4.4.3).

### 10.3.2 `extensions.json`과 `settings.json`

**권장 확장** — `.vscode/extensions.json`을 만든다(4.2.5).

```jsonc
{
    "recommendations": [
        "ms-python.python",
        "ms-python.vscode-pylance",
        "ms-python.debugpy",
        "charliermarsh.ruff"
    ]
}
```

Jupyter 확장은 10.7에서 노트북을 더할 때 이 목록에 넣는다. 지금 이 프로젝트에는 노트북이 없다. **그 프로젝트에 지금 필요한 것만** 권한다.

**작업 공간 설정** — `.vscode/settings.json`을 만든다(4.2.4). 저장할 때 Ruff로 포맷하는 설정을 작업 공간에도 둔다. 이 프로젝트에서 일하는 사람이 모두 같은 포맷 규칙을 쓰게 하려는 것이다.

```jsonc
{
    "[python]": {
        "editor.defaultFormatter": "charliermarsh.ruff",
        "editor.formatOnSave": true,
        "editor.codeActionsOnSave": {
            "source.fixAll.ruff": "explicit",
            "source.organizeImports.ruff": "explicit"
        }
    },
    "files.exclude": {
        "**/__pycache__": true
    }
}
```

여기에 **넣지 않은 것**도 짚어 둔다.

| 넣고 싶어지는 설정 | 넣지 않는 이유 |
|---|---|
| `"python.defaultInterpreterPath": "${workspaceFolder}/.venv/bin/python"` | Windows에서는 `.venv\Scripts\python.exe`라서 한쪽 운영체제에서만 맞는다. 받은 사람이 `Python: Select Interpreter`로 고른다(4.5.3). VS Code는 작업 공간의 `.venv`를 대개 알아서 찾는다 |
| 색 테마, 글꼴 크기 | 개인 취향(4.2.6) |
| `"python.envFile"` 같은 비밀 값 관련 설정 | 이 프로젝트에는 아직 비밀 값이 없다. 생기면 값은 `.env`에, 파일 이름만 설정에 |

### 10.3.3 무엇이 올라가는지 확인하고 커밋하기

```

```

```

```


GitHub 저장소의 맨 위 폴더에 있는 파일과 폴더의 이름이다. `--jq`는 받은 JSON에서 필요한 부분만 꺼내는 옵션이다(8.7.6). PowerShell에서도 큰따옴표로 감싸면 그대로 동작한다.

### 10.4.3 README에 저장소 주소 반영하기

`README.md`의 설치 방법은 "이미 폴더를 가지고 있는 사람"을 위해 쓴 것이었다. 이제 저장소에서 받는 방법을 맨 앞에 더한다. 이 변경도 브랜치에서 한다.

```
git switch -c docs/readme-clone
```

`README.md`의 `## 설치` 바로 아래에 다음을 더한다.

````markdown
## 설치

```
git clone https://github.com/jinyoung-dev/ledger-app.git
cd ledger-app
```

macOS
...
````

`git clone`으로 받으면 폴더 이름이 저장소 이름(`ledger-app`)이 된다는 것도 이 두 줄에 드러난다.

```
git add README.md
git commit -m "README에 저장소에서 받는 방법 추가"
git push -u origin docs/readme-clone
gh pr create --fill
```

`--fill`은 커밋이 하나일 때 그 커밋의 제목과 본문으로 PR을 채운다(8.7.4). 이 저장소의 첫 PR이므로 번호는 `#1`이다. 바로 병합한다.

```
gh pr merge 1 --merge --delete-branch
```

```
✓ Merged pull request jinyoung-dev/ledger-app#1 (README에 저장소에서 받는 방법 추가)
From https://github.com/jinyoung-dev/ledger-app
 * branch            main       -> FETCH_HEAD
Updating e9ed80b..8a1c3f0
Fast-forward
 README.md | 7 +++++++
 1 file changed, 7 insertions(+)
✓ Deleted local branch docs/readme-clone and switched to branch main
✓ Deleted remote branch docs/readme-clone
```

`--merge`는 병합 커밋을 만드는 방식이다(8.5.6). 이 저장소에서는 **모든 PR을 병합 커밋으로 병합하기로 정한다.** 이유는 10.5.9에서 본다. 혼자 만들고 혼자 병합한 PR이지만, 이 저장소의 모든 변경이 PR을 거친다는 규칙이 GitHub에 기록으로 남는다.

## 10.5 이슈에서 병합까지 — 두 사람이 같은 곳을 고칠 때

이 장의 중심이다. 기능 하나를 이슈 → 브랜치 → PR → 리뷰 → 병합 흐름으로 더한다(완료 기준 ③). 그리고 그사이에 **동료의 변경이 먼저 병합되어** 내 브랜치와 충돌하는 상황을 겪는다(완료 기준 ④). 기준 ④는 "충돌을 일부러 만들고"라고 했다. 일부러 만들되, 실제로 흔히 일어나는 모양으로 만든다. 두 사람이 서로 다른 이슈를 맡았는데, 고쳐야 할 곳이 **같은 함수의 같은 몇 줄**인 경우다.

```python
    income = 0
    expense = 0
    expense_by = defaultdict(int)  # {분류: 금액}
    income_by = defaultdict(int)
    for t in transactions:
        if t.kind == "수입":
            income += t.amount
            income_by[t.category] += t.amount
        else:
            expense += t.amount
            expense_by[t.category] += t.amount

    first = min(transactions, key=lambda t: t.day)
    last = max(transactions, key=lambda t: t.day)
    return Summary(
        count=len(transactions),
        first_day=first.day,
        last_day=last.day,
        income=income,
        expense=expense,
        expense_by_category=_ranked(expense_by),
        income_by_category=_ranked(income_by),
    )


def _ranked(by_category: dict[str, int]) -> list[tuple[str, int]]:
    """{분류: 금액}을 금액이 큰 순(같으면 분류 이름 순)의 리스트로 돌려준다."""
    return sorted(by_category.items(), key=lambda item: (-item[1], item[0]))
```

**커밋 2 — 화면에 수입 분류별 표 표시 (cli)**

`ledger/cli.py`의 `category_table()` 아래에 표를 만드는 함수를 더한다. 지출 표와 달리 비율 열은 넣지 않는다. 이슈의 범위가 "분류, 금액, 합계"였다.

```python
def income_table(summary: Summary) -> Table:
    """수입 분류별 합계 표를 만든다. 출력은 하지 않는다."""
    table = Table(title="수입 분류별 합계")
    table.add_column("분류")
    table.add_column("금액", justify="right")
    for category, amount in summary.income_by_category:
        table.add_row(escape(category), won(amount))
    table.add_section()
    table.add_row("합계", won(summary.income), style="bold")
    return table
```

### 10.5.7 [나] 내 브랜치에서 충돌 해결하기

**Resolve conflicts** 단추를 누르면 웹 편집기에서 해결할 수도 있다. 그러나 여기서는 **내 컴퓨터에서** 해결한다. 이유는 하나다. 웹 편집기에서는 **시험을 돌릴 수 없다.** 충돌을 해결한 결과가 실행되는지, 시험을 통과하는지 확인하지 않고 커밋하게 된다. 곧 보겠지만 이번 충돌에는 표시가 나지 않는 문제가 하나 더 숨어 있다.

충돌은 **내 브랜치에서** 해결한다. `main`은 이미 도윤의 변경으로 앞서 나갔고, 그것을 내 브랜치로 가져와 합치는 것이다. 가져오는 방법은 병합과 리베이스가 있다. 이 브랜치는 이미 푸시해서 PR로 공유했으므로 **병합**한다(7.5.6, 8.6.6).

**[나]**

```
git status
git fetch
git merge origin/main
```

`git pull`이 아니라 `git fetch` 후 `git merge origin/main`을 한 데 주의한다. 내가 지금 있는 브랜치는 `feature/2-income-table`이다. 여기서 `git pull`을 하면 `origin/feature/2-income-table`을 받아 합친다. 가져오고 싶은 것은 **`main`의 새 커밋**이다(8.1.7).

```
Auto-merging DESIGN.md
CONFLICT (content): Merge conflict in DESIGN.md
Auto-merging README.md
Auto-merging check_samples.py
Auto-merging ledger/cli.py
CONFLICT (content): Merge conflict in ledger/cli.py
Automatic merge failed; fix conflicts and then commit the result.
```

GitHub가 말한 두 파일이다. `README.md`와 `check_samples.py`는 두 사람이 모두 고쳤지만 **다른 곳**을 고쳐서 Git이 알아서 합쳤다(Auto-merging).

```
git status
```

```
On branch feature/2-income-table
You have unmerged paths.
  (fix conflicts and run "git commit")
  (use "git merge --abort" to abort the merge)

Changes to be committed:
	modified:   README.md
	modified:   check_samples.py
	new file:   samples/income_only.csv

Unmerged paths:
  (use "git add <file>..." to mark resolution)
	both modified:   DESIGN.md
	both modified:   ledger/cli.py
```

6.4.2에서 읽은 모양이다. **Changes to be committed**는 Git이 이미 합쳐서 스테이징해 둔 것, **Unmerged paths**는 내가 해결해야 할 것이다.

**`ledger/cli.py`**

```python
    console.print(f"잔액: {won(summary.balance)}", style=balance_style)
<<<<<<< HEAD
    if summary.income_by_category:
        console.print(income_table(summary))
    console.print(category_table(summary))
=======
    if summary.expense_by_category:
        console.print(category_table(summary))
    else:
        console.print("지출 내역이 없습니다.")
>>>>>>> origin/main
```

`HEAD` 쪽(위)은 내 브랜치, `origin/main` 쪽(아래)은 도윤의 변경이다(6.4.3). 둘 중 하나를 고르는 문제가 아니다. **둘 다 필요하다.** 수입 표를 보여 주고(내 변경), 지출 표는 지출이 있을 때만 보여 준다(도윤의 변경). 6.4.5처럼 VS Code의 병합 편집기를 열어 두 쪽을 모두 받아들인 뒤 결과 칸에서 다듬어도 되고, 직접 고쳐도 된다. 결과는 다음과 같아야 한다.

```python
    console.print(f"잔액: {won(summary.balance)}", style=balance_style)
    if summary.income_by_category:
        console.print(income_table(summary))
    if summary.expense_by_category:
        console.print(category_table(summary))
    else:
        console.print("지출 내역이 없습니다.")
```

병합 편집기의 **Accept Combination**(조합 수락)을 누르면 두 쪽을 이어 붙여 주지만, 그대로 두면 `console.print(category_table(summary))`가 두 번 들어간다. 이어 붙인 결과를 **반드시 읽고** 고친다. 충돌 해결은 기계적인 선택이 아니라 두 변경의 **의도**를 합치는 일이다.

**`DESIGN.md`**

```markdown

<<<<<<< HEAD

    요약 파일을 엑셀에서 쓰는 사람의 열 구성이 바뀌지 않게 하려고. 필요해지면 이슈로 다룬다.
=======

    (0원, 0.0%)만 있는 표를 보여 주었는데, 계산이 잘못된 것처럼 보였다.
>>>>>>> origin/main
```

두 사람이 모두 결정 11번을 더했다. 둘 다 남긴다. `main`에 먼저 들어간 도윤의 결정을 11번으로 두고, 내 결정을 12번으로 옮긴다.

```markdown

    (0원, 0.0%)만 있는 표를 보여 주었는데, 계산이 잘못된 것처럼 보였다.

    요약 파일을 엑셀에서 쓰는 사람의 열 구성이 바뀌지 않게 하려고. 필요해지면 이슈로 다룬다.
```

충돌 표시가 남아 있지 않은지 확인한다. `git diff --check`는 원래 줄 끝의 공백 같은 문제를 찾는 명령인데, 지우지 않은 충돌 표시도 찾아 준다.


> `check_samples.py`의 수정은 두 브랜치 어디에도 없던 변경이다. 이런 변경을 병합 커밋에 넣지 않고, 병합을 먼저 커밋한 뒤 "수입만 있는 달 시험에 수입 분류 줄 추가"로 따로 커밋하는 방법도 있다. 따로 하면 변경이 눈에 잘 띄지만, **병합 커밋 자체는 시험이 실패하는 상태**로 이력에 남는다. 나중에 `git bisect`(7.7)로 그 커밋에 멈추면 엉뚱한 실패를 만나게 된다. 이 교재는 "모든 커밋에서 시험이 통과한다"를 지키기 위해 병합 커밋 안에서 고치고, 그 사실을 메시지 본문에 적는 쪽을 골랐다. 어느 쪽이든 **메시지에 남기는 것**이 핵심이다.

푸시한다.

```

```

> **병합 대신 리베이스로 맞췄다면**
> PR을 아직 아무도 보지 않았다면 `git rebase origin/main`으로 내 커밋 세 개를 새 `main` 위로 옮겨 심는 방법도 있다(7.5.2). 그러면 충돌을 **커밋마다** 해결하게 된다. 커밋 2(화면)에서 `cli.py`의 충돌을, 커밋 3(문서)에서 `DESIGN.md`의 충돌을 만나고, 커밋 1(계산과 시험)에서는 충돌 없이 시험이 깨진다. 커밋마다 시험을 돌려야 그것을 알아챌 수 있다. 끝나면 이력이 한 줄이 되지만, 이미 푸시한 브랜치를 바꿔 쓰므로 `git push --force-with-lease`가 필요하고(8.1.9), 그 브랜치를 받아 둔 리뷰어의 사본과 어긋난다. 이 장에서는 도윤이 곧 리뷰할 것이므로 병합했다.

- `+     if summary.expense_by_category:` — 첫째 칸이 `+`, 둘째 칸이 빈칸이다. `main`에서 온 줄이다.

`diff --cc`는 변경 덩어리(hunk)마다 결과를 두 부모와 비교해서, 결과가 **어느 한쪽 부모의 내용을 그대로 가져온** 덩어리는 생략한다. 그래서 `README.md`는 나오지 않는다. 병합 결과의 `README.md`는 두 부모와 모두 다르지만(첫 문단은 내 쪽, 표의 새 줄은 도윤 쪽에서 왔다), 덩어리마다 보면 한쪽을 그대로 가져왔기 때문이다. 반대로 두 부모 어느 쪽과도 다른 덩어리, 곧 충돌을 손으로 합친 `cli.py`와 `DESIGN.md`의 덩어리, 병합하면서 새로 더한 `check_samples.py`의 줄은 나온다. 생략되는 기준이 "파일"이 아니라 "덩어리"라는 점, 그리고 생략된 덩어리에도 사람이 고른 결과가 있을 수 있다는 점에 주의한다.

**왜 병합 커밋으로 병합했나**

## 10.6 잘못 올린 커밋 되돌리기

완료 기준 ⑤의 앞부분은 "잘못 넣은 커밋 하나를 `git revert`로 되돌린다"이다. 이번에도 일부러 만들되, 실제로 흔한 모양으로 만든다. **확인용으로 넣은 코드를 지우는 것을 잊고, 그대로 `main`에 커밋하고 푸시하는** 실수다.

### 10.6.1 실수

PR `#4`를 병합한 뒤, 거래 하나가 `Transaction`으로 어떻게 읽히는지 다시 보고 싶어졌다고 하자. `main`에서 `ledger/cli.py`의 `main()`에 한 줄을 넣는다.

**[나]**

```python

    console.print(transactions)  # 확인용
    console.print(f"가계부 요약: {escape(path.name)}", style="bold")
```

실행해서 확인하고, 다른 일을 하다가 이 줄을 잊었다. 한참 뒤 "아까 수입 표를 확인하던 것"을 정리하겠다며 다음을 실행한다.


`git commit -a`는 추적하는 파일의 변경을 **모두** 스테이징하고 바로 커밋한다(5.3.4). `git diff --staged`로 확인할 틈이 없다. 그리고 지금 있는 브랜치는 `main`이다. 이 저장소는 비공개이고 무료 요금제라서 `main`을 지키는 규칙(8.6.4의 상자)을 걸 수 없으므로 푸시는 그대로 받아들여진다. 10.1.1의 규칙 1과 2를 한꺼번에 어겼다.

그사이 도윤이 최신 코드를 받는다.

**[도윤]**


### 10.6.3 reset인가 revert인가

7.2.6의 선택 기준을 다시 꺼낸다.

| 상황 | 고를 것 |
|---|---|
| 아직 푸시하지 않은 내 커밋 | `git reset`(7.1.4)이나 `git commit --amend`(7.1.2)로 이력을 고친다 |
| **이미 푸시해서 남이 받았을 수 있는 커밋** | **`git revert`로 되돌리는 커밋을 새로 만든다**(7.2.2) |

이 커밋은 GitHub에 있고, 도윤이 이미 받았다. 내가 `git reset --hard HEAD~1`로 이 커밋을 지우고 강제 푸시하면, GitHub의 `main`은 되돌아가지만 도윤의 `main`에는 그 커밋이 남는다. 도윤이 다음에 `git pull`을 하면 Git은 도윤의 `main`이 GitHub보다 커밋 하나 **앞서 있다**고 보고, 도윤이 다음에 푸시할 때 그 커밋이 고스란히 되살아난다(8.1.9). 공유한 이력은 고치지 않고 **되돌린다.**

### 10.6.4 `git revert`

**[나]**

```
git revert HEAD
```

5.2.4에서 정한 편집기(VS Code)가 열리고 다음 메시지가 들어 있다.

```
Revert "수입 표 확인"

This reverts commit 3928d8a1b34cc4489ca9d86afb89ff7c0974635c.
```

첫 줄과 둘째 문단은 그대로 두고, **왜 되돌리는지**를 본문에 더한다. 7.2.2에서 본 대로 기본 메시지는 무엇을 되돌렸는지만 알려 준다.

```
Revert "수입 표 확인"

This reverts commit 3928d8a1b34cc4489ca9d86afb89ff7c0974635c.

확인용으로 넣은 console.print(transactions)가 지워지지 않은 채
main에 커밋되었다. 실행할 때마다 거래 목록 전체가 화면에 나온다.
check_samples.py는 화면을 확인하지 않아서 시험은 통과했다.
```

저장하고 편집기 탭을 닫으면 커밋이 만들어진다.

```
git show --stat HEAD
python run_all.py
git push
```

```
commit d564bb5...
Author: 엄진영 <...>

    Revert "수입 표 확인"
    ...

 ledger/cli.py | 1 -
 1 file changed, 1 deletion(-)
```

되돌린 커밋은 앞의 커밋과 **정확히 반대인 diff**를 가진 새 커밋이다. 앞의 커밋은 지워지지 않고 이력에 남는다. 그래서 "언제, 무엇이 잘못 들어왔고, 언제 왜 되돌렸는지"가 모두 기록된다.

**[도윤]**

```
git pull
git log --oneline -3
```

```
d564bb5 (HEAD -> main, origin/main) Revert "수입 표 확인"
3928d8a 수입 표 확인
3117ae2 Merge pull request #4 from jinyoung-dev/feature/2-income-table
```

도윤은 평소처럼 `git pull`만 하면 된다. 이력이 앞으로만 나아갔기 때문이다. `revert`를 고른 이유가 여기 있다.

> **`main`에 직접 커밋하지 않게 하는 장치**
> 이번 실수의 뿌리는 `main`에서 커밋한 것이다. 사람의 습관에만 기대지 않으려면 장치를 둔다.
> - **브랜치 보호**(8.6.4의 상자) — "PR을 거쳐야만 `main`에 들어간다"를 GitHub가 강제한다. 공개 저장소는 무료 요금제에서도 쓸 수 있다.
> - **푸시하기 전에 무엇이 올라가는지 본다** — `git log origin/main..`은 "내가 가졌고 GitHub에는 아직 없는 커밋"이다(8.1.6). `git status`의 `Your branch is ahead of 'origin/main' by 1 commit`이 `main`에서 보이면 멈추고 생각한다.
> - **프롬프트에 브랜치 이름을 보인다** — VS Code의 상태 표시줄 왼쪽 아래에는 지금 브랜치가 늘 보인다(5.3.7). 터미널 프롬프트에 Git 브랜치를 보여 주는 셸 설정도 흔하다.
> - **`git commit -a`를 쓰지 않는다** — 쓰더라도 바로 앞에 `git diff`를 본다.
>
> 이미 `main`에서 커밋했지만 아직 푸시하기 **전**에 알아챘다면, 7장의 방법으로 깨끗하게 옮길 수 있다. `git switch -c fix/xxx`로 지금 커밋을 가진 새 브랜치를 만들고, `git switch main` 후 `git reset --hard origin/main`으로 `main`을 GitHub와 맞춘다. 커밋은 새 브랜치에 남아 있다(7.1.4, 7.3).

### 10.7.1 개발 도구를 따로 적기 — `requirements-dev.txt`

노트북은 이 프로그램을 **실행하는 데는** 필요 없다. 가계부를 요약하려는 사람은 `rich`만 있으면 된다. 노트북 도구는 코드를 고치고 결과를 탐색하는 사람에게만 필요하다. 9.2.6처럼 따로 적는다. 프로젝트 폴더에 `requirements-dev.txt`를 만든다.

9장의 `requirements-dev.txt`와 두 가지가 다르다.

- **`jupyterlab` 대신 `nbconvert`** — 이 프로젝트에서는 노트북을 VS Code에서 쓴다. VS Code에는 `ipykernel`만 있으면 된다(9.2.1). 다만 노트북 검증(9.6.5의 `jupyter nbconvert --execute`)에는 `nbconvert`가 필요하다. 9장에서는 `jupyterlab`이 `nbconvert`를 데려왔다. 이번에는 필요한 것만 직접 적는다. `nbconvert`를 설치하면 `jupyter` 명령도 함께 생긴다.

### 실습 10-7. 노트북과 커밋 전 검사

1. 10.7.1~10.7.7을 한다. 노트북의 마지막 Markdown 셀에 **알게 된 것** 세 가지를 직접 적는다(예: 고정 지출을 빼면 식비의 비중이 얼마인가, 큰 지출 다섯 건 중 몇 건이 식비인가, 요약 파일에 무엇이 빠져 있는가).
2. 노트북에 다음을 하나 더 탐색하는 셀을 더한다. 계산이 길어지면 노트북 안에 함수로 정리한다(9.6.2).
   - (가) 날짜별 지출 합계에서 가장 많이 쓴 날
   - (나) 메모(`memo`)별 지출 합계 — "장보기"에 모두 얼마를 썼는가
   - (다) 수입 대비 지출의 비율(%)
3. 2에서 만든 계산 중 하나를 프로그램에도 넣을 만하다고 판단했다면, 이슈를 만들고 그 계산을 `ledger/core.py`의 함수로 옮기는 PR을 만든다. 노트북은 그 함수를 import해서 쓰도록 바꾼다. 시험(`check_samples.py`)도 더한다. 노트북에 남길 것과 모듈로 옮길 것의 기준을 `check.md`에 적는다.
4. 노트북 맨 아래에 `print(undefined_name)` 셀을 일부러 넣고 저장한 뒤 README의 "커밋하기 전에" 명령을 실행한다. 어디서 멈추는가? 종료 코드는?(macOS `echo $?`, Windows `$LASTEXITCODE`) 확인했으면 셀을 지운다.
5. `nbstripout --install`을 빠뜨린 사람의 상황을 재현한다. `~/devtools-lab/ch10`에 저장소를 새로 받고(`gh repo clone jinyoung-dev/ledger-app nostrip`), 그 폴더에서 가상환경을 만들어 `requirements-dev.txt`로 설치하되 `nbstripout --install`은 **하지 않는다.** VS Code에서 노트북을 열어 Run All을 한 뒤 `git diff explore.ipynb`를 보고, 출력과 실행 번호가 diff에 그대로 나오는 것을 확인한다. 이 상태로 `git add`하면 출력이 커밋된다. 확인했으면 커밋하지 말고 `nostrip` 폴더를 지운다.
   - 도윤의 폴더에서 `git config --unset filter.nbstripout.clean`처럼 필터의 명령만 지워서 흉내 내면 안 된다. `filter.nbstripout.required true`가 남아 있어서, 출력이 보이는 대신 `git diff`와 `git add`가 모두 `fatal: explore.ipynb: clean filter 'nbstripout' failed`로 실패한다. 직접 해 보고 두 상황(설정이 **없을 때**는 조용히 통과, 설정이 **깨졌을 때**는 실패)을 비교해 적는다. 확인했으면 `nbstripout --install --attributes .gitattributes`로 되돌린다.

## 10.9 복원 시험 B — 저장소에서 받아 실행하기

기초 과정 10.4.2의 복원 시험 B는 "프로젝트를 다른 위치에 복사하고, 원래 폴더의 이름을 잠시 바꿔 둔 채, `README.md`만 보고 복원해서 실행한다"였다. 그때 마지막 문단에서 이렇게 말했다. "Git을 쓸 줄 안다면 저장소에 올리고 받는 사람이 내려받게 하면, `.gitignore`가 제대로 되어 있는지까지 함께 확인된다." 이제 그렇게 한다.

복사와 `git clone`은 무엇이 다른가?

| | 폴더 복사(기초 과정) | `git clone`(이 장) |
|---|---|---|
| 받는 것 | 폴더에 있는 모든 것(무시되는 파일까지) | **저장소에 커밋된 것만** |
| `.venv` | 복사된 뒤 지워야 했다 | 처음부터 없다 |
| 결과 파일, 연습 파일, `data/` | 그대로 따라온다 | 없다 |
| 확인되는 것 | 절대 경로, 프로젝트 밖 파일, README의 명령 | 위의 것 **더하기** `.gitignore`가 빼면 안 되는 것을 빼지 않았는지, 커밋을 빠뜨린 파일이 없는지 |

마지막 줄이 중요하다. 내 컴퓨터에서는 잘 돌아가는데 **커밋을 빠뜨린 파일**이 있으면, 복사로는 알 수 없고 클론으로만 드러난다. 예를 들어 새 시험 파일을 만들고 `check_samples.py`의 `EXPECTED`에는 더했지만 `git add`를 잊었다면, 내 폴더에서는 통과하고 클론에서는 실패한다.

### 10.9.1 원래 폴더 숨기기

기초 과정처럼 시험하는 동안 원래 폴더의 이름을 바꿔 둔다. 받은 코드가 원래 폴더의 절대 경로에 기대고 있으면 그 자리에서 실패하게 하려는 것이다. 원래 프로젝트를 연 VS Code 창을 닫고 가상환경을 끈다.

```
# macOS
deactivate
cd ~/python-lab/ch10
mv ledger_app ledger_app_orig

# Windows
deactivate
cd ~\python-lab\ch10
Rename-Item ledger_app ledger_app_orig
```

> **이름을 바꾸는 동안의 nbstripout**
> 원래 폴더의 `.git/config`에는 `.venv` 파이썬의 절대 경로로 필터가 적혀 있다(9.7.3의 상자). 이름을 바꿔 둔 동안 그 폴더에서 노트북을 `git add`하면 `clean filter 'nbstripout' failed`가 난다. 시험이 끝나고 이름을 되돌리면 다시 동작한다. 그래서 이름을 바꿔 둔 동안에는 원래 폴더에서 아무 작업도 하지 않는다.

### 10.9.2 받고, README만 보고 따라 하기

`~/devtools-lab/ch10/restore_test`에 받는다. 이번에는 `gh`가 아니라 **README에 적힌 명령**으로 받는다. README의 첫 명령부터 시험하는 것이다.

```

cd ~/devtools-lab/ch10/restore_test
```

여기서부터는 `README.md`를 브라우저(GitHub 저장소 화면)에 띄워 두고, **적힌 명령만** 차례로 입력한다. 적혀 있지 않은 명령을 입력해야 했다면 그것은 README에 빠진 내용이다. 메모해 두고, 시험이 끝난 뒤 README를 고친다.

```
git clone https://github.com/jinyoung-dev/ledger-app.git
cd ledger-app
git describe --tags
```

```

```

받은 코드가 `v1.0.0`이다. 그 뒤에 커밋이 더 있다면 `v1.0.0-2-g...`처럼 보인다. 시험하려는 것이 정확히 `v1.0.0`이라면 `git switch --detach v1.0.0`으로 그 시점으로 간다(7.6.2). `git clone --branch v1.0.0 주소`로 처음부터 그 태그를 받을 수도 있다. 둘 다 브랜치가 아니라 태그의 커밋에 머무르는 detached HEAD 상태가 된다(6.2.7). 시험만 하고 커밋하지 않을 것이므로 괜찮다.

README의 "설치" 절대로 가상환경을 만든다.

```

source .venv/bin/activate

.venv\Scripts\Activate.ps1

```

```
python -m pip install -r requirements-dev.txt
nbstripout --install --attributes .gitattributes
python run_all.py && jupyter nbconvert --execute --to html explore.ipynb
```

`git clone`으로 받은 폴더, README의 명령만으로 만든 가상환경에서 시험·예제 실행·노트북 검증을 모두 통과했다. 완료 기준 ⑧이다. 기초 과정 10.4.2처럼 `python -m pip freeze`가 `requirements.txt`의 내용을 모두 포함하는지도 확인한다. 이번에는 개발 도구가 함께 설치되었으므로 freeze의 결과가 `requirements.txt`보다 길다. `requirements.txt`의 네 줄이 모두 같은 버전으로 들어 있으면 된다.

### 10.9.3 받아서 바로 디버깅하기

완료 기준 ⑥의 "다른 사람이 받아서 바로 디버깅할 수 있다"를 확인한다.

```

```

1. **권장 확장 알림**이 뜨는지 본다. 이미 모두 설치되어 있으면 뜨지 않는다. 확장 화면에서 `@recommended`를 검색하면 목록이 보인다(4.2.5).
2. 처음 여는 폴더이므로 **작업 공간 신뢰**를 묻는다(4.2.7). 내 저장소이므로 신뢰한다. 남의 저장소였다면 `.vscode` 폴더의 파일부터 읽어 보았을 것이다.

받은 사람이 한 일은 README의 명령 몇 줄과 인터프리터 고르기뿐이다. 실행 설정, 확장 목록, 포맷 설정은 저장소가 가져다주었다.

### 10.9.4 다른 운영체제에서

완료 기준 ⑧은 "가능하면 다른 운영체제의 컴퓨터에서"라고 했다. macOS에서 만든 저장소를 Windows에서, Windows에서 만든 저장소를 macOS에서 받아 보는 것이 가장 확실한 시험이다. 짝이 있다면 서로의 저장소를 받아 본다. 협업자로 초대되어 있어야 비공개 저장소를 받을 수 있다(8.4.3). 이때 자주 드러나는 것은 다음과 같다.

| 증상 | 원인 | 고칠 곳 |
|---|---|---|
| README의 설치 명령이 한쪽 운영체제에만 있다 | 두 운영체제의 명령을 함께 적지 않았다 | README |
| `./run_all.sh: permission denied` | Windows에서 커밋해서 실행 권한이 없다 | `git update-index --chmod=+x`(10.2.4의 상자) |
| `bash\r: No such file or directory` | `.gitattributes`가 없거나, 그것보다 먼저 CRLF로 커밋되었다 | 10.2.3, `git add --renormalize .` |
| 한쪽에서만 `ModuleNotFoundError` | 그쪽에만 설치하고 `requirements.txt`에 적지 않았다 | `requirements.txt` |
| 파일 이름의 대소문자가 다른데 macOS·Windows에서는 되고 리눅스에서는 안 된다 | 코드의 파일 이름과 실제 파일 이름의 대소문자가 다르다 | 2.6.6 |
| 노트북을 실행하니 출력이 커밋된다 | `nbstripout --install`을 하지 않았다 | README의 "개발 환경" |

다른 운영체제의 컴퓨터가 없다면, 8.9의 GitHub Actions가 그 대신이 될 수 있다. GitHub의 리눅스 컴퓨터에서 저장소를 받아 `check_samples.py`를 돌리는 일은 이 저장소에도 그대로 할 수 있다. 실습 10-9의 선택 문제로 남긴다.

   - (가) 새 시험 파일 `samples/restore_missing.csv`를 만들어(내용은 `2026-10.csv`의 앞 다섯 줄 정도) `EXPECTED`에 더하고, `check_samples.py`만 커밋해서 푸시한다(시험 파일은 커밋하지 않는다). 내 폴더와 클론에서 각각 `check_samples.py`의 결과는? 실습 10-5의 4번에서 만든 `expense_only.csv`처럼 이미 저장소에 있는 파일로 하면 클론에도 파일이 있어서 이 실수가 드러나지 않는다. 반드시 처음 만드는 이름을 쓴다.

3. (선택) 8.9를 참고해 이 저장소에 GitHub Actions 워크플로를 더한다. 푸시와 PR마다 리눅스에서 `requirements.txt`를 설치하고 `python check_samples.py`를 실행하게 한다. PR로 더하고, PR 화면에 검사 결과가 표시되는지 확인한다.

## 10.10 완료 기준 점검

마지막으로 아홉 가지 기준을 하나씩 **보여 줄 수 있는지** 점검한다. "했다"가 아니라 "보여 줄 수 있다"가 기준이다. 실습 10-1에서 만든 `check.md`에, 기준마다 아래의 명령을 실행한 결과나 화면 캡처를 붙인다.

| 기준 | 보여 줄 것 | 명령 또는 화면 | 절 |
|---|---|---|---|
| ① 넣지 않을 것 | 무시되는 이유, 저장소와 이력에 없음, GitHub에 없음 | `git status --ignored --short`, `git check-ignore -v .venv/ ledger/__pycache__ data/2026-11.csv .env`, `git log --all --name-only --format= \| sort -u`, `gh api "repos/{owner}/{repo}/contents" --jq ".[].name"`, 저장소 첫 화면 | 10.2, 10.4 |
| ② 좋은 커밋 | 커밋마다 한 가지 일, 메시지로 무엇과 왜 | `git log --oneline`, `git log --format="%h %s%n%b" -10`(제목과 본문) | 전체 |
| ③ 이슈와 PR, 리뷰 | 이슈 `#2` → PR `#4`, 리뷰 의견과 반영 커밋, 해결된 대화 | `gh issue view 2`, `gh pr view 4 --web`(Conversation과 Files changed), `gh api "repos/{owner}/{repo}/pulls/4/comments"` | 10.5 |
| ④ 충돌 해결 | 부모가 둘인 해결 커밋, 무엇을 어떻게 합쳤는지 | `git log --oneline --graph`, `git show --remerge-diff <해결한 병합 커밋>`, 실습 10-5의 3번 답 | 10.5.7, 10.5.9 |
| ⑤ 되돌리기와 태그 | 되돌린 커밋과 이유, `v1.0.0` 주석 태그 | `git show --stat <되돌린 커밋>`, `git tag -n`, `git show v1.0.0`, GitHub의 Tags | 10.6, 10.8 |
| ⑥ 개발 환경 | 저장소의 `.vscode` 세 파일, 받은 폴더에서 `F5`로 멈춤 | `git ls-files .vscode`, 10.9.3의 캡처 | 10.3, 10.9.3 |
| ⑦ 노트북 | 저장소의 노트북에 출력 없음, 새 커널로 끝까지 실행 | `git show HEAD:explore.ipynb \| grep '"execution_count"'`, `jupyter nbconvert --execute --to html explore.ipynb` | 10.7 |
| ⑧ 복원 | 클론한 폴더에서 README의 명령만으로 통과 | 10.9.2의 출력, README에 더한 내용 | 10.9 |
| ⑨ 한 줄 검사 | README의 "커밋하기 전에" 절 | README의 해당 절, 실행 결과 | 10.7.6 |

①의 `git log --all --name-only --format= | sort -u`는 10.2.5에서 한 번 실행했다. 이 장 내내 여러 사람이 커밋하고 병합했지만, 지금 다시 실행해도 `.venv`, `__pycache__`, `data/`, `.env`, `*_summary.csv`, `explore.html`이 하나도 나오지 않아야 한다.

```
# macOS
git log --all --name-only --format= | sort -u | grep -E '(^|/)(\.venv|__pycache__|data)/|\.env$|_summary\.csv$|\.html$'

# Windows
git log --all --name-only --format= | Sort-Object -Unique | Select-String -Pattern '(^|/)(\.venv|__pycache__|data)/|\.env$|_summary\.csv$|\.html$'
```

아무것도 나오지 않으면 이력 전체가 깨끗하다.

②는 명령 하나로 보일 수 없다. `git log --format="%h %s%n%b" -10`은 최근 커밋 열 개의 해시와 제목(`%s`), 본문(`%b`)을 보여 준다. 이것을 읽으며 스스로 묻는다. 메시지만 읽고 무엇을 왜 바꿨는지 알 수 있는가? 한 커밋이 두 가지 일을 하지는 않는가? "수입 표 확인"처럼 정직하지 않은 메시지가 있었다면, 그 커밋이 왜 되돌려졌는지도 함께 설명한다.

### 실습 10-10. 종합 실습 — 내 프로젝트로

`check.md`를 완성한다. 실습 10-1에서 처음 적은 "어떻게 보여 줄지"와 위의 표를 비교하고, 달랐던 것을 적는다.

기초 과정 실습 10-4에서 **나만의 명령행 프로그램**(할 일 관리, 단어 빈도 분석 등)을 만들었다면, 그 프로젝트로 이 장의 과정을 처음부터 혼자 한 번 더 한다. 이번에는 교재의 명령을 옮기지 말고, 무엇을 해야 하는지만 보고 명령을 스스로 고른다.

1. **저장소로 만들기** — 상위 폴더 확인, `.gitignore`(그 프로그램이 만드는 결과 파일과 개인 데이터는 무엇인가?), `.gitattributes`, 성격별로 나눈 첫 커밋.
2. **개발 환경** — 그 프로그램의 명령행 인자에 맞는 `launch.json`, 권장 확장, 작업 공간 설정.
3. **GitHub** — 비공개 저장소, 설명과 주제, 웹에서 확인.
4. **이슈와 PR** — 그 프로그램의 `DESIGN.md`에서 "바뀔 때 고칠 곳"이나 "한계"를 두 개 골라 이슈로. 짝이 있다면 하나씩 나누어 맡고, 없다면 도윤의 폴더를 다시 만든다. **두 이슈가 같은 함수를 고치게** 골라 충돌을 만들고 해결한다. 충돌 뒤에 시험을 돌리는 것을 잊지 않는다.
5. **되돌리기** — `main`에 들어간 커밋 하나를 `git revert`로 되돌린다. 일부러 만든 실수여도 되돌리는 이유를 메시지 본문에 적는다.
6. **노트북** — 그 프로그램의 모듈을 import해서 결과를 탐색하는 노트북. 출력을 지워 커밋하고 `nbconvert --execute`로 검증.
7. **커밋 전 검사** — `&&`로 이은 한 줄을 README에.
8. **태그와 복원 시험** — `v1.0.0`, 원래 폴더를 숨기고 클론해서 README만 보고 복원.
9. **점검** — 아홉 가지 기준을 `check.md`에.

## 선택 활동

### A. AI 코딩 도구에게 기능 하나를 맡기기

이 과정 내내 "AI가 무엇을 바꾸었는지 읽고 검토하고 필요하면 되돌릴 수 있는 능력"을 길렀다. 이제 실제로 맡겨 본다. 7.8과 8.6.9의 흐름을 내 저장소에서 처음부터 끝까지 한다.

1. **이슈를 먼저 쓴다.** 예: "요약 파일에 수입 분류별 합계도 저장하기"(`DESIGN.md`의 바뀔 때 고칠 곳). 범위와 하지 않을 것, 확인 방법(어떤 시험을 통과해야 하는지)을 적는다. 이 이슈가 AI에게 줄 지시의 바탕이 된다.
2. **작업 폴더를 깨끗하게 하고 따로 쓸 공간을 만든다**(7.8.1, 7.8.2). `git status`로 깨끗한지 확인하고, 작업 트리를 나눈다.
   ```
   git worktree add ../ledger_app-ai -b ai/income-in-summary
   ```
   AI 도구는 `../ledger_app-ai` 폴더에서만 일하게 한다. 내 작업 폴더는 그대로다.
3. **지침을 준다.** 이슈 내용과 함께 이 프로젝트의 규칙을 알려 준다. `DESIGN.md`를 읽게 하고, "층의 규칙을 지킬 것", "`python check_samples.py`가 통과해야 한다", "**커밋은 하지 말 것**"처럼. 이 활동에서는 AI가 커밋하지 않게 한다. 변경이 작업 폴더에 남아 있어야 6단계에서 받아들일 부분만 골라 담을 수 있다. 프로젝트의 지침 파일(4.6.4, 7.8.6)을 만들어 저장소에 넣어도 된다.
4. **AI가 실행하려는 명령을 읽는다**(3.8). 패키지 설치, 파일 삭제, `git push`를 하려 하면 멈추고 확인한다.
5. **결과를 검토한다.** `git status`와 `git diff`로 읽는다. 지시와 달리 AI가 커밋해 버렸다면(`git log --oneline main..`에 커밋이 보인다) 먼저 `git log -p main..`으로 읽은 뒤, 7.8.3처럼 커밋을 풀어 변경을 작업 폴더로 돌려놓는다. 리셋 기준은 `main`이 아니라 이 브랜치가 `main`에서 **갈라진 커밋**, 즉 AI가 일을 시작한 커밋이다. AI가 일하는 동안 원래 폴더에서 `main`에 커밋을 더했다면, `main`으로 리셋할 때 그 커밋을 지우는 변경까지 섞여 나온다.
   ```
   # macOS
   git reset --mixed $(git merge-base main HEAD)

   # Windows
   git reset --mixed (git merge-base main HEAD)
   ```
   브랜치만 갈라진 커밋으로 옮겨지고 파일 내용은 그대로이므로 잃는 것은 없다(7.1.6). `DESIGN.md`의 층 규칙을 지켰는가? 시험을 더했는가? 시험의 기대값을 **계산기로 직접 구한 값**과 비교했는가, 아니면 프로그램 출력을 옮겨 적었는가(기초 과정 10.2.8)?
6. **받아들일 것만 골라 PR로 만든다**(7.8.4). 커밋하지 않은 변경에서 받아들일 부분을 `git add -p`로 고른다(새 파일은 `git add 파일`). 나머지는 `git restore`로 버리고, 필요 없는 새 파일은 `git clean -n`으로 확인한 뒤 `git clean -f`로 지운다. 그다음 `python check_samples.py`를 다시 돌린다. 골라 담은 코드가 버린 코드에 기대고 있었다면 여기서 드러난다. 통과하면 그때 내 메시지로 커밋한다. `git add -p`와 `git restore`는 **커밋하지 않은 변경**에만 쓸 수 있다. 이미 커밋된 변경에 쓰면 `No changes.`가 나오고 아무것도 되돌려지지 않는다. 5단계에서 커밋을 풀어 둔 것은 그래서다. PR 설명에 **AI 도구가 만든 변경**이라는 것과, 받아들이지 않은 부분과 그 이유를 적는다.
7. **리뷰하고 병합하고 정리한다**(7.8.5). `git worktree remove ../ledger_app-ai`, 브랜치 정리.

PR 설명의 "받아들이지 않은 부분"이 이 활동의 핵심이다. 아무것도 버리지 않았다면, 정말로 모두 맞았는지 다시 한 번 읽어 본다.

### B. 1단계 결과물 저장소 다시 보기

1단계에서 AI 도구와 함께 만들어 GitHub에 올린 저장소를 다시 연다(8.4.5).

1. `gh repo clone 소유자/저장소`로 받고 `git log --oneline | head -20`을 본다. 커밋 메시지가 무엇을 왜 바꿨는지 알려 주는가?
2. `git ls-files`와 `git log --all --name-only --format= | sort -u`로 들어가면 안 되는 파일(`.venv`, `node_modules`, `__pycache__`, `.env`, 데이터 파일)이 이력에 있는지 본다.
3. 이력에서 비밀 값처럼 보이는 문자열을 찾는다. `git log -p --all | grep -n -i -E "api[_-]?key|secret|token|password"`(Windows는 `Select-String`)로 찾고, 찾았다면 그 커밋을 `git show`로 확인한다. **진짜 키가 있었다면 8.3.5의 순서대로 키부터 폐기한다.** 이력을 고치는 것은 그다음이다.
4. `.gitignore`를 이 과정에서 배운 대로 다시 쓰고, `README.md`에 설치·실행 방법을 명령으로 적는다. 브랜치를 만들어 PR로 병합한다.
5. 그 저장소에서 복원 시험 B를 한다.

### C. 오픈 소스에 작은 PR 보내기

8.8의 흐름을 실제 저장소로 한다.

1. 내가 쓰는 오픈 소스 프로젝트(이 과정에서 설치한 패키지도 좋다) 중 하나를 고른다. 문서에서 오타, 깨진 링크, 예제 코드의 실수를 찾는다.
2. 그 저장소의 `CONTRIBUTING.md`, PR 템플릿, 최근 병합된 PR 몇 개를 읽는다(8.8.4). 작은 문서 수정을 받는지, 이슈를 먼저 열어야 하는지, 커밋 메시지 규칙이 있는지 확인한다.
3. 포크하고 받고, 브랜치를 만들어 고치고, 내 포크에 올리고, PR을 보낸다(8.8.5). 커밋 메시지와 PR 설명은 그 저장소의 언어(대개 영어)와 규칙을 따른다.
4. 리뷰 의견이 오면 반영한다. 받아들여지지 않아도 괜찮다. 이유를 읽고 배운다.

## 정리

| 항목 | 핵심 |
|---|---|
| 시작 전 점검 | 상위 폴더가 저장소가 아닌지(`git rev-parse --show-toplevel`), 프로그램이 돌아가는지, 백업 |
| 넣지 않을 것 먼저 | `git init` 후 바로 `add .` 하지 않는다. `git status --ignored`, `git check-ignore -v`(없는 파일도 확인), 연습 파일 정리 |
| `.gitignore` | 결과 파일·개인 데이터·`.env`(생기기 전에)·`.vscode/*`와 `!` 예외. 줄마다 이유를 주석으로 |
| 첫 커밋 | 규칙 → 프로그램 → 문서 → 도구로 나눈다. 규칙을 맨 먼저 |
| 들어간 것 확인 | `git ls-files`(지금), `git log --all --name-only --format= \| sort -u`(이력 전체), `gh api .../contents`(GitHub) |
| 개발 환경 담기 | `launch.json`(인자, `${workspaceFolder}`, 절대 경로·비밀 값 없음), `extensions.json`(지금 필요한 것만), `settings.json`(포맷). 인터프리터 경로는 넣지 않는다 |
| GitHub | `gh repo create --private --source=. --push`, `gh repo edit --add-topic`, 웹과 API로 확인 |
| 이슈 | 무엇을, 왜, 범위(하지 않을 것까지). 브랜치 이름에 번호 |
| 층을 따라 커밋 | 계산+시험 → 화면 → 문서. 계산이 바뀌면 시험도 같은 커밋에서 |
| 먼저 병합된 PR | 내 PR에 "This branch has conflicts". 웹 편집기보다 내 컴퓨터에서(시험을 돌릴 수 있다) |
| 충돌 해결 | 공유한 브랜치이므로 `git fetch` + `git merge origin/main`. 한쪽을 고르지 말고 두 의도를 합친다. Accept Combination 결과는 반드시 읽는다. 번호를 옮겼으면 가리키는 곳도 |
| 보이지 않는 충돌 | 충돌 표시 없이 합쳐진 파일에서 시험이 실패한다. Git은 줄을 합칠 뿐 뜻을 모른다 → 합친 뒤에는 시험 |
| 병합 커밋 메시지 | 무엇을 어떻게 합쳤는지, 병합하며 새로 고친 것. 모든 커밋에서 시험이 통과하게 |
| 리뷰 | 리뷰어가 직접 실행하고 경계값을 시험. 제안(suggestion). 반영은 내 컴퓨터에서 시험 후 커밋, 어느 커밋에서 반영했는지 답하고 Resolve |
| 병합 방식 | 이 장은 병합 커밋(커밋 단위와 충돌 해결 기록을 남긴다). 지저분한 PR은 스쿼시가 낫다 |
| 이력 읽기 | 아래에서 위로. 부모가 둘인 커밋. `git show <병합>`의 `diff --cc`(두 칸: 첫째 부모, 둘째 부모. 한쪽을 그대로 가져온 덩어리는 생략). 해결 과정은 `git show --remerge-diff <병합>`(자동 병합 결과와 비교 = 사람이 손댄 곳) |
| 잘못 올린 커밋 | 푸시해서 남이 받았으면 `git revert`. 본문에 이유. 이력은 앞으로만 → 남은 `git pull`만 |
| 예방 | `main`에서 커밋하지 않는다, `commit -a` 대신 `diff --staged`, `git log origin/main..`, 브랜치 보호(공개 저장소), 상태 표시줄의 브랜치 |
| 시험의 범위 | 시험이 통과해도 시험이 확인하지 않는 것(화면)은 모른다 |
| `requirements-dev.txt` | `-r requirements.txt` + 개발 도구. VS Code면 `ipykernel`, 검증에 `nbconvert`, 출력 지우기에 `nbstripout` |
| 탐색 노트북 | 프로젝트 폴더 바로 아래(import 때문에). 아래층 함수를 가져다 쓴다. 저장소의 파일(`samples`)만 읽는다. 쓸모 있는 계산은 이슈와 PR로 모듈에 |
| 노트북 검증 | Restart → Run All, `jupyter nbconvert --execute --to html explore.ipynb`. `explore.html`·`.ipynb_checkpoints/`는 무시 |

| 받아서 디버깅 | 권장 확장 알림, 작업 공간 신뢰, 인터프리터, 실행 설정 목록, `F5` |

## 과정을 마치며

이 과정을 시작할 때 1.1.1에서 1단계의 AI 도구가 대신 해 준 일을 적어 보았다. 명령 실행, 커밋, 푸시, 배포. 지금은 그 일을 직접 할 수 있고, 무엇보다 **AI가 한 일을 읽을 수 있다.** AI가 실행하려는 명령을 읽고 허락할지 정할 수 있고(3.8), 바꾼 파일을 diff로 검토할 수 있고(4.6, 5.4), 받아들일 것만 골라 커밋할 수 있고(7.8), PR로 받아 리뷰할 수 있고(8.6), 마음에 들지 않으면 되돌릴 수 있다(5.7, 7.2).

이 장의 `ledger_app` 저장소에는 그 모든 것이 기록되어 있다. 성격별로 나눈 첫 커밋, 이슈와 PR, 리뷰와 반영, 충돌을 해결한 병합 커밋과 그 이유, 되돌린 커밋과 그 이유, 출력을 지운 노트북, 받은 사람이 바로 디버깅할 수 있는 설정, 그리고 `v1.0.0`. 석 달 뒤의 나, 또는 이 저장소를 처음 받은 사람은 `git log`와 GitHub 화면만으로 이 프로그램이 어떻게 지금의 모습이 되었는지 알 수 있다.
