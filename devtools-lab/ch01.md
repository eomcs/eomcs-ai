# 1장. 시작하기

[개발 도구](README.md) 과정의 첫 장이다. 이 장에서는 본격적으로 도구를 배우기 전에 세 가지를 준비한다.

- **개발 도구 과정의 지도** — 1단계에서 AI 도구가 대신 해 준 일을 돌아보고, 그 일들을 이 과정의 어느 장에서 직접 하게 되는지 확인한다. 같은 일을 화면(GUI)과 명령(CLI) 두 가지로 할 수 있을 때 명령부터 배우는 이유를 이해한다.
- **실습 환경** — 패키지 관리자로 Git, GitHub CLI, PowerShell 7(Windows)을 설치하고, 설치한 도구의 버전과 위치를 확인한다.
- **기초 과정 점검** — 파이썬 기초 과정에서 배운 경로, 환경 변수, 가상환경, 종료 코드를 다시 확인하고, 10장에서 만든 프로젝트 폴더가 이 과정에서 쓸 수 있는 상태인지 점검한다.

## 학습 목표

이 장을 마치면 다음을 할 수 있다.

- 1단계에서 AI 도구가 대신 해 준 일을 이 과정의 장과 연결해 말할 수 있다.
- 같은 일을 할 수 있는 화면과 명령 중 명령을 먼저 배우는 이유를 설명할 수 있다.
- 패키지 관리자(macOS Homebrew, Windows `winget`)로 개발 도구를 설치하고, 버전과 설치 위치를 확인할 수 있다.
- (Windows) PowerShell 7과 Windows PowerShell 5.1을 구별하고, 터미널과 VS Code의 기본 셸을 PowerShell 7로 바꿀 수 있다.
- 기초 과정 10장의 프로젝트를 터미널에서 실행하고, 종료 코드와 표준 오류 출력을 확인할 수 있다.

## 실습 환경

이 교재는 기초 과정과 마찬가지로 macOS와 Windows 11을 기준으로 한다. 다만 Windows의 셸이 바뀐다.

- **macOS** — 기본 "터미널" 앱(zsh). 기초 과정과 같다.
- **Windows** — "터미널" 앱의 **PowerShell 7 이상**. 기초 과정에서 쓴 Windows PowerShell 5.1이 아니다. 왜 바꾸는지, 어떻게 바꾸는지는 1.2에서 다룬다.

두 환경에서 명령이 다를 때는 기초 과정처럼 `# macOS`, `# Windows`로 나누어 적는다. 같을 때는 한 번만 적는다.

> **1단계를 마친 사람에게**
> 1단계에서 AI 도구에게 "GitHub에 올려 줘", "이전 상태로 돌려 줘"라고 부탁했을 것이다. 이 과정은 그 부탁을 직접 하는 과정이다. AI 도구는 계속 쓴다. 다만 AI가 실행하려는 명령과 AI가 바꾼 내용을 **읽고 판단하는 사람**이 되는 것이 목표다.

## 1.1 개발 도구 과정의 지도

### 1.1.1 AI 도구가 대신 해 준 일

1단계에서 결과물 하나를 만들어 배포하기까지 한 일을 떠올려 보자. 그중에는 AI 도구가 대신 해 준 일이 꽤 많다.

| 1단계에서 한 일 | 그때의 방식 | 실제로 일어난 일 |
|---|---|---|
| 필요한 프로그램 설치, 개발 서버 실행 | AI 도구가 실행 허락을 구하면 "허용"을 눌렀다 | 터미널에서 명령이 실행되었다 |
| 코드 고치기 | AI 채팅에 부탁하거나 제안을 수락했다 | 파일의 몇 줄이 바뀌었다 |
| 변경 기록(commit), 변경 확인(diff) | 버튼을 누르거나 AI에게 부탁했다 | Git 명령이 실행되었다 |
| 이전 상태로 복원 | AI에게 "되돌려 줘"라고 했다 | Git 명령이 실행되었다(무엇이 실행되었는지 모른다) |
| GitHub에 공유(push), 배포 | 버튼을 누르거나 AI에게 부탁했다 | Git 명령과 GitHub의 기능이 쓰였다 |

오른쪽 열이 이 과정에서 배울 내용이다. AI 도구는 대부분의 일을 **터미널 명령**과 **Git**으로 한다. 그것을 모르면 AI가 "이 명령을 실행해도 될까요?"라고 물을 때 판단할 근거가 없고, 결과가 이상할 때 무엇이 잘못되었는지 알 수 없다. 1단계 포트폴리오에서 "동작하지만 이해 못하는 지점"을 기록했다면, 그중 상당수가 이 과정에서 풀린다.

### 1.1.2 이 과정의 장

| 장 | 다루는 것 | 1단계에서 AI가 대신 한 일 |
|---|---|---|
| 2장. 터미널 기본기 | 셸, 명령의 구조와 도움말, 파일·폴더 다루기 | 명령 실행 |
| 3장. 터미널 활용 | 입출력 연결, 찾기, 종료 코드, 셸 환경, 프로세스, AI가 실행하려는 명령 읽기 | 명령 실행, 개발 서버 실행 |
| 4장. VS Code | 작업 공간, 설정과 확장, 편집 기술, 디버거, AI 도구의 변경 검토 | 코드 고치기 |
| 5장. Git 시작하기 | 저장소, 커밋, 변경 확인, `.gitignore` | 변경 기록, 변경 확인 |
| 6장. 브랜치와 병합 | 브랜치, 병합, 충돌 해결 | (1단계에서는 하지 않았다) |
| 7장. 이력 되돌리기와 고치기 | 되돌리기, 잃어버린 커밋 찾기, stash, 태그, AI 도구와 Git | 이전 상태로 복원 |
| 8장. GitHub로 공유하고 협업하기 | 원격 저장소, 인증, 비밀 값 관리, 이슈와 PR, 코드 리뷰 | GitHub에 공유 |
| 9장. Jupyter Notebook | 노트북, 커널, 노트북과 Git | (1단계에서는 하지 않았다) |
| 10장. 마무리 | 기초 과정 10장의 프로젝트를 이 도구들로 다시 다루기 | 전체 |

장의 순서는 로드맵의 나열 순서(터미널 → VS Code → Git/GitHub → Jupyter)를 따른다. Git은 터미널 명령으로 배우므로 터미널이 먼저다. VS Code는 Git보다 먼저 4장에서 익히지만, VS Code의 Git 기능은 4장에서 다루지 않는다. VS Code의 Git 화면은 버튼 하나가 Git 명령 하나에 해당하는데, 명령을 모르고 버튼을 누르면 1단계와 다를 것이 없기 때문이다. VS Code의 Git 기능은 5~8장에서 명령과 나란히 다룬다.

### 1.1.3 왜 명령부터 배우나

이 과정에서 배우는 일은 대부분 화면(GUI)으로도 할 수 있다. VS Code에는 Git 버튼이 있고, GitHub는 웹 사이트에서 대부분의 작업을 할 수 있다. 그런데도 명령(CLI)부터 배우는 이유는 네 가지다.

**1. 명령은 글자라서 적어 두고 다시 실행할 수 있다.** 기초 과정 10장의 `README.md`에 설치 방법을 "VS Code에서 이것을 누르고, 저것을 고르고"가 아니라 명령으로 적었다. 명령은 복사해서 붙여 넣으면 누구의 컴퓨터에서든 똑같이 실행된다. 오류가 났을 때 AI나 동료에게 보여 주기도 쉽다. 화면 조작은 말로 설명해야 하고, 설명은 쉽게 빠지거나 틀린다.

**2. AI 도구가 실제로 하는 일이 명령이다.** Claude Code나 Cursor는 내 컴퓨터에서 명령을 실행해서 일한다. 실행 허락을 구하는 창에 뜨는 것도 명령이다. 명령을 읽을 수 있어야 허락할지 말지 판단할 수 있다.

**3. 화면이 없는 곳이 많다.** 2단계 후반의 "LLM 서비스 배포"에서 서비스를 올릴 클라우드 서버, Docker 컨테이너, 코드를 올릴 때마다 시험을 돌리는 GitHub Actions에는 마우스로 누를 화면이 없다. 거기서는 명령만 쓸 수 있다.

**4. 버튼은 명령을 대신 실행한다.** VS Code의 "커밋" 버튼은 `git commit`을 실행한다. 버튼을 눌렀을 때 뜨는 오류 메시지도 Git 명령의 오류 메시지 그대로다. 명령을 알면 버튼이 무엇을 하는지, 오류가 무슨 뜻인지 알 수 있다.

명령으로 원리를 이해한 뒤에는 편한 쪽을 쓰면 된다. 변경 내용을 비교할 때는 VS Code의 비교 화면이 터미널보다 보기 좋고, 충돌을 해결할 때는 VS Code의 병합 편집기가 편하다. 이 과정에서도 그런 경우에는 화면을 함께 쓴다.

### 1.1.4 이 과정을 공부하는 방법

**실습 폴더**

이 과정의 실습 파일은 홈 폴더 아래 `devtools-lab` 폴더에 장별로 모은다(`~/devtools-lab/ch01`, `~/devtools-lab/ch02`, …). 기초 과정의 `python-lab` 폴더는 그대로 둔다. 10장에서 기초 과정의 프로젝트를 다시 쓰고, 이 장의 1.3에서도 그 프로젝트를 점검한다.

**명령 표기**

명령과 출력은 따로 적는다. 명령 블록에는 프롬프트(`%`, `PS C:\...>`)를 적지 않는다. 출력 블록의 버전 숫자나 경로는 컴퓨터마다 다르므로 모양만 비교한다.

```
git --version
```

```
git version 2.51.0
```

**명령은 직접 입력한다**

이 과정의 명령은 되도록 복사해서 붙여 넣지 말고 직접 입력한다. 손으로 입력해 보아야 명령의 모양이 눈에 익고, 오타를 냈을 때 나오는 오류 메시지를 만나 볼 수 있다. 그 오류 메시지를 읽는 것도 이 과정에서 배울 기술이다.

**AI 도구는 이렇게 쓴다**

막히면 AI에게 물어도 된다. 다만 두 가지 순서를 지킨다.

1. 오류 메시지를 **먼저 한 번 읽는다**(기초 과정 1.1.7과 같다).
2. AI가 알려 준 명령을 실행하기 **전에**, 그 명령이 무엇을 하는지 한 문장으로 말할 수 있는지 확인한다. 말할 수 없으면 `--help`나 공식 문서로 확인한다(2장). 무엇을 지우거나 덮어쓰는 명령이면 특히 그렇다(3장).

Jupyter는 프로젝트의 가상환경에 설치하는 파이썬 패키지이므로 9장에서 설치한다.

### 1.2.2 패키지 관리자

기초 과정에서 파이썬과 VS Code는 웹 사이트에서 설치 파일을 받아 설치했다. 이 방법은 도구가 몇 개일 때는 괜찮지만, 도구가 늘어나면 불편하다. 도구마다 사이트를 찾아가야 하고, 새 버전이 나왔는지 하나씩 확인해야 하며, 설치 과정을 남에게 설명하기도 어렵다.

**패키지 관리자**(package manager)는 프로그램을 명령으로 설치·갱신·제거하게 해 주는 도구다. 9장에서 쓴 `pip`이 "파이썬 패키지"의 패키지 관리자였다면, Homebrew와 `winget`은 "프로그램"의 패키지 관리자다. 1.1.3의 첫 번째 이유가 여기서도 통한다. 설치 과정이 명령 몇 줄로 남는다.

| 하고 싶은 일 | macOS(Homebrew) | Windows(`winget`) |
|---|---|---|
| 프로그램 찾기 | `brew search 이름` | `winget search 이름` |
| 설치 | `brew install 이름` | `winget install --id 아이디` |
| 설치된 목록 | `brew list` | `winget list` |
| 갱신할 수 있는 것 보기 | `brew outdated` | `winget upgrade` |
| 모두 갱신 | `brew upgrade` | `winget upgrade --all` |

**macOS — Homebrew 설치**

Homebrew는 macOS에 기본으로 들어 있지 않으므로 먼저 설치한다. 설치하기 전에 지원 범위를 확인한다. Homebrew가 공식 지원하는 것은 macOS 15(Sequoia) 이상이다. macOS 11~14에서도 동작할 수는 있지만 지원 대상이 아니므로, 가능하면 macOS를 먼저 업데이트한다. 인텔 맥은 Homebrew가 최소 지원(Tier 3) 대상으로 분류한다. 대부분 동작하지만 문제가 생겼을 때 도움을 받기 어렵다. macOS 버전은 화면 왼쪽 위 Apple 메뉴 → **이 Mac에 관하여**에서, 칩 종류(Apple Silicon인지 인텔인지)도 같은 창에서 확인한다.

공식 사이트(https://brew.sh)의 첫 화면에 있는 설치 명령을 복사해 터미널에 붙여 넣는다. 이 명령은 직접 입력하기에는 길고 틀리기 쉬우므로 예외적으로 복사한다. **반드시 공식 사이트에서 복사한다.** 명령은 다음과 같은 모양이다.

```
/bin/bash -c "$(curl -fsSL https://raw.githubusercontent.com/Homebrew/install/HEAD/install.sh)"
```

이 명령은 인터넷에서 설치 스크립트를 내려받아(`curl`) 곧바로 실행한다(`bash -c`). 이런 형태의 명령은 내려받은 스크립트가 내 컴퓨터에서 무엇이든 할 수 있으므로, **누가 만든 스크립트인지 확인할 수 있을 때만** 실행한다. 이런 명령을 읽는 방법은 3장에서 자세히 다룬다. (명령을 실행하기 꺼려지면 Homebrew의 GitHub 최신 릴리스 페이지(https://github.com/Homebrew/brew/releases/latest)에서 `.pkg` 설치 파일을 받아 설치할 수도 있다. 단, `.pkg` 설치 파일은 **Apple Silicon 맥만** 지원한다. 인텔 맥은 위의 명령으로 설치한다.)

실행하면 맥 로그인 암호를 묻는다. 입력하는 동안 화면에 아무것도 표시되지 않는 것이 정상이다. 입력하고 Enter를 누른다. Xcode 명령행 도구가 없으면 함께 설치하므로 몇 분 걸릴 수 있다.

설치가 끝나면 출력의 마지막 부분에 **Next steps**라는 안내가 나온다. 거기에 적힌 명령(`echo ... >> ~/.zprofile`, `eval ...`로 시작하는 줄)을 그대로 실행한다. 이 명령들은 `brew` 명령이 있는 폴더(Apple Silicon 맥은 `/opt/homebrew/bin`)를 `PATH`에 넣는 설정을 셸 설정 파일에 적는다. 이것을 하지 않으면 다음과 같은 오류가 난다.

```
zsh: command not found: brew
```

기초 과정 9.1.4에서 본 것처럼, 터미널은 `PATH`에 있는 폴더에서만 명령을 찾기 때문이다. 셸 설정 파일은 3장에서 다룬다.

터미널을 닫았다가 새로 열고 확인한다.

```
brew --version
```

### 1.2.3 Windows — PowerShell 7 설치

**왜 PowerShell 7인가**

Windows에는 두 가지 PowerShell이 있다.

| | Windows PowerShell 5.1 | PowerShell 7 |
|---|---|---|
| 실행 파일 | `powershell.exe` | `pwsh.exe` |
| 터미널에 보이는 이름 | Windows PowerShell | PowerShell |
| 설치 | Windows에 들어 있다 | 따로 설치한다 |
| 운영체제 | Windows 전용 | Windows, macOS, 리눅스 |
| 개발 상황 | 더 이상 기능이 추가되지 않는다 | 계속 개발된다 |

기초 과정에서는 Windows에 들어 있는 5.1을 썼다. 기초 과정의 명령에서는 둘의 차이가 거의 드러나지 않았지만, 이 과정에서는 두 가지 차이 때문에 PowerShell 7이 필요하다.

**1. 5.1에는 `&&`와 `||`가 없다.** 3장에서 "앞 명령이 성공했을 때만 다음 명령을 실행하는" `&&`와 "실패했을 때만 실행하는" `||`를 배운다. 이 과정의 10장 완료 기준, AI 도구가 만드는 명령, 여러 프로젝트의 `README.md`에 이 연산자가 자주 나온다. 5.1에서는 다음과 같은 오류가 난다.

```
python --version && git --version
```

```
The token '&&' is not a valid statement separator in this version.
```

(한국어 Windows에서는 같은 뜻의 한국어 메시지가 나온다.)

**2. 5.1에서 `>`로 저장한 파일은 UTF-8이 아니다.** 명령의 출력을 파일에 저장하는 `>`(3장에서 자세히 다룬다)는 기초 과정에서도 썼다. `python -m pip freeze > requirements.txt`다. 5.1에서 `>`로 만든 파일은 **UTF-16**이라는 인코딩으로 저장된다. 기초 과정 7장에서 텍스트 파일은 UTF-8로 다루기로 했는데, 그 약속이 깨지는 것이다. `pip`은 UTF-16 파일도 알아서 읽기 때문에 기초 과정에서는 문제가 드러나지 않았지만, Git은 이런 파일을 텍스트가 아닌 **바이너리 파일**로 취급해서 무엇이 바뀌었는지 보여 주지 못한다. PowerShell 7은 PowerShell이 만든 문자열(예: `"안녕" > hello.txt`)을 `>`로 저장할 때 UTF-8을 쓴다. 두 가지 차이는 실습 1-2에서 직접 확인한다.

> **외부 프로그램의 출력은 프로그램이 인코딩을 정한다**
> PowerShell 7이 `>`를 늘 UTF-8로 저장하는 것은 아니다. `python`, `git` 같은 **외부 프로그램**의 출력을 `>`로 보내면, PowerShell 7.4부터는 프로그램이 내보낸 바이트를 바꾸지 않고 그대로 저장한다. 그러면 파일의 인코딩은 그 프로그램이 정한다. 파이썬은 출력을 화면이 아닌 파일로 보낼 때 운영체제의 기본 인코딩을 쓰는데, 한국어 Windows에서는 UTF-8이 아니라 **cp949**다.
>
> - `pip freeze`처럼 출력이 영문·숫자·기호뿐이면 cp949와 UTF-8의 바이트가 같으므로 결과적으로 UTF-8 파일이 된다.
> - 한글을 출력하는 파이썬 프로그램의 출력은 cp949 파일이 된다. VS Code에서 열면 한글이 깨져 보인다.
> - 파이썬이 UTF-8로 출력하게 하려면 `-X utf8` 옵션을 붙인다. 예: `python -X utf8 main.py samples/2026-10.csv > out.txt`. 이 옵션은 파이썬의 "UTF-8 모드"를 켠다.
>
> macOS는 파이썬의 기본 인코딩이 UTF-8이므로 이 문제가 없다. 리다이렉션은 3장에서 자세히 다룬다.

**설치**

터미널(지금은 Windows PowerShell 5.1)에서 설치한다.

```
winget install --id Microsoft.PowerShell --source winget
```

`--id`는 설치할 프로그램을 정확한 아이디로 지정하는 옵션이다. 이름으로만 찾으면 비슷한 이름의 다른 프로그램이 함께 검색될 수 있다. `--source winget`은 Microsoft Store가 아닌 `winget`의 기본 저장소에서 받으라는 뜻이다. 설치 중에 사용자 계정 컨트롤 창이 뜨면 "예"를 누른다.

PowerShell 7을 설치해도 5.1은 지워지지 않는다. 둘은 나란히 설치되고, 필요하면 언제든 5.1을 쓸 수 있다.

### 1.2.4 Windows — 기본 셸을 PowerShell 7로 바꾸기

설치만 해서는 터미널을 열 때 여전히 5.1이 실행된다. 두 곳의 설정을 바꾼다.

**터미널 앱**

1. 터미널 앱을 닫았다가 다시 연다. 설치한 PowerShell 7이 **PowerShell**이라는 이름의 프로필로 자동으로 추가된다.
2. 탭 오른쪽의 `∨` 단추를 누르고 **설정**을 연다.
3. **시작** → **기본 프로필**에서 **PowerShell**을 고른다. **Windows PowerShell**(5.1)을 고르지 않도록 주의한다.
4. **저장**을 누르고 터미널을 닫았다가 다시 연다.

**VS Code**

VS Code의 통합 터미널은 터미널 앱과 설정이 따로다.

1. VS Code를 **완전히 종료했다가** 다시 연다. VS Code는 시작할 때 설치된 셸을 찾으므로, 실행 중에 설치한 PowerShell 7은 다시 시작해야 보인다.
2. 명령 팔레트(`Ctrl+Shift+P`)에서 `Terminal: Select Default Profile`을 실행한다.
3. 목록에서 **PowerShell**을 고른다. 마찬가지로 **Windows PowerShell**이 아니다.
4. 열려 있는 터미널을 닫고(휴지통 아이콘) 새 터미널을 연다(`` Ctrl+` ``).

이 설정은 VS Code 사용자 설정에 다음과 같이 저장된다. 설정 파일은 4장에서 다룬다.

```json
"terminal.integrated.defaultProfile.windows": "PowerShell"
```

**바꾸었는지 확인하기**

터미널 앱과 VS Code 터미널에서 **각각** 실행한다.

```
$PSVersionTable.PSVersion
```

```
Major  Minor  Patch  PreReleaseLabel BuildLabel
-----  -----  -----  --------------- ----------
7      5      4
```

`Major`가 `7`이면 성공이다. `5`와 `1`이 보이면 아직 5.1이다. `$PSVersionTable`은 PowerShell이 미리 만들어 둔 변수로, 지금 실행 중인 PowerShell의 버전 정보를 담고 있다.

**가상환경 활성화 확인 — 실행 정책**

기초 과정 9.1.4에서 가상환경 활성화 스크립트(`Activate.ps1`)가 막히면 `Set-ExecutionPolicy`로 실행 정책을 바꾸었다. **실행 정책은 5.1과 7이 따로 관리한다.** 5.1에서 바꾼 설정은 7에 적용되지 않는다. PowerShell 7은 설치할 때 컴퓨터 전체 범위(`LocalMachine`)의 정책을 `RemoteSigned`로 정해 두므로 대개 그대로 활성화된다. 하지만 설치 방법이나 컴퓨터의 관리 정책에 따라 다를 수 있으므로, PowerShell 7에서 범위별로 확인한다.

```
Get-ExecutionPolicy -List
```

```
        Scope ExecutionPolicy
        ----- ---------------
MachinePolicy       Undefined
   UserPolicy       Undefined
      Process       Undefined
  CurrentUser       Undefined
 LocalMachine    RemoteSigned
```

실행 정책은 범위(Scope)마다 따로 정할 수 있고, 목록의 **위쪽 범위가 우선한다.** 위에서부터 처음 나오는 `Undefined`가 아닌 값이 실제로 적용되는 정책이다. 모든 범위가 `Undefined`이면 Windows에서는 `Restricted`(스크립트 실행 금지)가 적용된다. 옵션 없이 `Get-ExecutionPolicy`를 실행하면 실제로 적용되는 정책 하나만 보여 준다. 결과에 따라 다음과 같이 한다.

- **적용되는 정책이 `RemoteSigned`나 `Unrestricted`** — 그대로 진행한다.
- **`Restricted`나 `AllSigned`이고, `MachinePolicy`와 `UserPolicy`가 `Undefined`** — 기초 과정 9.1.4의 명령을 PowerShell 7에서 한 번 더 실행한다.
  ```
  Set-ExecutionPolicy -ExecutionPolicy RemoteSigned -Scope CurrentUser
  ```
- **`MachinePolicy`나 `UserPolicy`에 값이 있다** — 회사나 학교의 관리자가 그룹 정책으로 정한 것이다. 이 두 범위는 `CurrentUser`보다 우선하므로 위 명령으로 바꿔도 적용되지 않는다(더 우선하는 범위의 정책 때문에 설정이 무시된다는 메시지가 나온다). 관리자에게 문의한다. 그동안에는 활성화하지 않고 가상환경의 파이썬을 경로로 직접 실행하면 된다(기초 과정 9.1.4, `.venv\Scripts\python.exe main.py ...`).

1.3.3에서 실제로 가상환경을 활성화해 확인한다.

### 1.2.5 Git과 GitHub CLI 설치

**Git**은 5~7장에서 배울 버전 관리 도구다. **GitHub CLI**(`gh`)는 저장소 만들기, 풀 리퀘스트 만들기·병합하기 같은 GitHub 웹 사이트의 기능을 터미널에서 쓰게 해 주는 도구로, 8장에서 쓴다. 둘은 서로 다른 프로그램이다. Git은 GitHub 없이도 쓸 수 있고, GitHub CLI는 Git이 있어야 제대로 동작한다.

```
# macOS
brew install git
brew install gh

# Windows
winget install --id Git.Git --source winget
winget install --id GitHub.cli --source winget
```

Windows에서는 설치가 끝나면 **터미널을 닫았다가 새로 연다.** 설치 프로그램은 `git`과 `gh`가 있는 폴더를 `PATH`에 추가하는데, 이미 열려 있는 터미널은 열릴 때의 `PATH`를 그대로 쓰기 때문이다. VS Code의 통합 터미널도 VS Code가 시작될 때의 `PATH`를 물려받으므로, **VS Code도 완전히 종료했다가 다시 연다.** 설치했는데 `명령을 찾을 수 없다`는 오류가 나는 가장 흔한 이유다.

> **Windows용 Git에 함께 설치되는 것**
> `winget`으로 설치하면 Git for Windows가 기본 설정으로 설치된다. 이때 GitHub 로그인 정보를 안전하게 저장해 주는 **Git Credential Manager**(8장)와, 리눅스식 셸을 흉내 내는 **Git Bash**(1.2.8)가 함께 설치된다. 설치 과정에서 고르는 기본 편집기, 기본 브랜치 이름 같은 설정은 5장에서 명령으로 다시 정한다.

> **macOS에는 이미 Git이 있었다**
> Homebrew를 설치할 때 함께 설치된 Xcode 명령행 도구에도 Git이 들어 있다. 그런데 이 Git은 애플이 관리하므로 버전이 조금 늦다. Homebrew로 설치한 Git을 쓰는 것이 이 과정의 기준이다. 컴퓨터에 Git이 두 개 있으면 어느 것이 실행되는지는 1.2.7에서 확인한다.

### 1.2.6 VS Code의 `code` 명령

VS Code는 기초 과정에서 설치했다. 이 과정에서는 터미널에서 `code` 명령으로 VS Code를 연다. 예를 들어 `code .`은 현재 폴더를 VS Code로 연다(4장). 5장에서는 Git이 커밋 메시지를 입력받을 때 이 명령으로 VS Code를 띄우도록 설정한다.

```
code --version
```

```
1.106.0
...
arm64
```

첫 줄이 버전이다. 

- **macOS**에서 `command not found: code`가 나오면, VS Code에서 명령 팔레트(`Cmd+Shift+P`)를 열고 `Shell Command: Install 'code' command in PATH`를 실행한 뒤 터미널을 새로 연다.
- **Windows**는 VS Code를 설치할 때 기본으로 `PATH`에 추가된다. 그래도 찾을 수 없으면 VS Code 설치 프로그램을 다시 실행해 "PATH에 추가" 항목을 확인한다.

### 1.2.7 설치한 도구 확인하기 — 버전과 위치

설치한 도구마다 두 가지를 확인한다. **버전**과 **위치**다. 버전은 `--version` 옵션으로 확인한다. 위치는 기초 과정 9.2.2에서 "터미널이 찾는 파이썬"을 확인한 명령으로 확인한다.

```
# macOS
which git
which -a git

# Windows
Get-Command git
Get-Command git -All
```

```
# macOS
/opt/homebrew/bin/git

/opt/homebrew/bin/git
/usr/bin/git

# Windows
CommandType     Name       Version    Source
-----------     ----       -------    ------
Application     git.exe    2.51.0.1   C:\Program Files\Git\cmd\git.exe
```

`which -a`(Windows는 `Get-Command -All`)는 처음 찾은 것 하나가 아니라, `PATH`에서 찾을 수 있는 **모든** 같은 이름의 명령을 순서대로 보여 준다. macOS에는 Git이 두 개 있다. Homebrew가 설치한 `/opt/homebrew/bin/git`과 Xcode 명령행 도구에 딸린 `/usr/bin/git`이다. `git`을 입력하면 `PATH`에서 앞에 있는 쪽, 즉 Homebrew의 Git이 실행된다. Homebrew 설치 마지막에 실행한 "Next steps"가 `/opt/homebrew/bin`을 `PATH`의 **앞쪽**에 넣었기 때문이다. 기초 과정에서 가상환경을 활성화하면 `.venv/bin`이 `PATH`의 맨 앞에 들어가서 가상환경의 `python`이 먼저 발견되던 것과 같은 원리다.

(인텔 맥에서는 Homebrew가 `/usr/local/bin`에 설치한다. 위치는 달라도 원리는 같다. 1.2.2에서 말한 대로 인텔 맥은 Homebrew의 최소 지원 대상이다.)

> **"설치했는데 예전 버전이 나온다"**
> 새로 설치한 도구의 `--version`이 예상보다 낮게 나오면, 같은 이름의 다른 프로그램이 `PATH`에서 먼저 발견되고 있는 것이다. `which -a`나 `Get-Command -All`로 모두 찾아보고, 맨 위에 나온 것이 원하는 것인지 확인한다. 기초 과정 9.2.6의 "설치했는데 `import`가 안 된다"와 같은 종류의 문제다.

### 1.2.8 bash, Git Bash, WSL

이 교재는 macOS의 zsh와 Windows의 PowerShell 7을 쓴다. 그런데 앞으로 다른 셸 이름도 자주 만나게 된다.

- **bash** — 리눅스의 표준 셸이다. 이 로드맵의 배포 실습(2단계 "LLM 서비스 배포")에서는 주로 리눅스 클라우드 서버와 리눅스 Docker 컨테이너를 쓰고, 중급 과정에서 맛볼 GitHub Actions도 리눅스 실행 환경을 쓴다. 그때 만나는 셸이 대부분 bash다. (GitHub Actions에는 Windows·macOS 실행 환경도 있지만, 이 로드맵에서는 리눅스를 기본으로 쓴다.) 인터넷의 설치 안내나 AI가 알려 주는 명령도 bash 기준인 경우가 많다. macOS의 zsh는 bash와 같은 계열이라 이 과정에서 배우는 명령은 거의 그대로 통한다. macOS에도 `/bin/bash`가 있지만, 예전 버전이다.
- **Git Bash** — Windows용 Git에 딸려 설치되는 bash 환경이다. Windows에서 bash 명령을 흉내 낼 수 있다. 이 교재에서는 쓰지 않는다. VS Code의 터미널 프로필 목록에 "Git Bash"가 보여도 고르지 않는다.
- **WSL**(Windows Subsystem for Linux) — Windows 안에서 진짜 리눅스를 실행하는 기능이다. 리눅스 서버와 똑같은 환경이 필요할 때 쓴다. 이 과정에서는 쓰지 않으며, 필요해지는 과정에서 다시 소개한다.

PowerShell은 bash와 계열이 다르다. 그래서 같은 일을 하는 명령의 이름이나 옵션이 다를 때가 있다. 2·3장에서는 이런 차이를 표로 정리하며 진행한다. bash 기준 명령을 만났을 때 PowerShell에서 어떻게 할지 찾는 습관도 그때 익힌다.

   VS Code 창이 열리고 탐색기에 `CH01`이 보이면 성공이다. 이 창의 통합 터미널(`` Ctrl+` ``)을 연다. (Windows) 통합 터미널에서 `$PSVersionTable.PSVersion`의 `Major`가 `7`인지 확인한다.
3. VS Code에서 `tools.md` 파일을 만들고, 다음 표를 채운다. 버전은 각 명령의 `--version` 출력에서, 위치는 `which`(Windows는 `Get-Command`)의 출력에서 옮겨 적는다.
   ```markdown
   # 도구 확인

   운영체제: (예: macOS 15 / Windows 11)

   | 도구 | 버전 | 위치 |
   |---|---|---|
   | 패키지 관리자(brew / winget) | | |
   | 셸(zsh / pwsh) | | |
   | git | | |
   | gh | | |
   | code | | |
   | python3 / python | | |
   ```
   셸의 버전은 macOS는 `zsh --version`, Windows는 `$PSVersionTable.PSVersion`으로 확인한다. 셸의 위치는 macOS는 `echo $SHELL`, Windows는 `Get-Command pwsh`로 확인한다. 파이썬은 가상환경을 활성화하지 않은 상태에서 확인한다.
4. (macOS) `which -a git`의 결과를 표 아래에 적고, `git`을 입력하면 둘 중 어느 것이 실행되는지와 그 이유를 한 문장으로 적는다.
5. 표를 채우다가 막힌 칸이 있으면, 그 칸에 받은 오류 메시지를 그대로 적어 두고 1.2의 해당 절을 다시 본다.

이 파일은 이후에 도구를 설치하거나 갱신할 때 비교하는 기준이 된다. 5장에서 이 폴더를 Git 저장소로 만들 때 다시 쓴다.

**Windows — PowerShell 5.1과 7 비교**

PowerShell 7 안에서 `powershell`을 입력하면 5.1이 실행된다. `exit`를 입력하면 5.1이 끝나고 7로 돌아온다. 이것을 이용해 1.2.3의 두 가지 차이를 직접 확인한다. `~/devtools-lab/ch01`에서 한다.

1. 5.1로 들어가서 버전을 확인하고, `&&`를 써 본다.
   ```
   powershell
   $PSVersionTable.PSVersion
   python --version && git --version
   ```
   `Major`가 `5`이고, `&&`에서 오류가 나는 것을 확인한다.
2. 5.1에서 `>`로 파일을 하나 만들고 7로 돌아온다.
   ```
   "안녕" > hello51.txt
   exit
   ```
3. 7에서 같은 일을 한다.
   ```
   $PSVersionTable.PSVersion
   python --version && git --version
   "안녕" > hello7.txt
   ```
   `Major`가 `7`이고, 두 명령이 차례로 실행되는 것을 확인한다.
4. 두 파일의 실제 바이트를 파이썬으로 본다. `'rb'`는 기초 과정 7장에서 다루지 않은 모드로, 파일을 글자로 해석하지 않고 **바이트 그대로** 읽는다.
   ```
   python -c "print(open('hello51.txt', 'rb').read())"
   python -c "print(open('hello7.txt', 'rb').read())"
   ```
   ```
   b'\xff\xfeH\xc5U\xb1\r\x00\n\x00'
   b'\xec\x95\x88\xeb\x85\x95\r\n'
   ```
   두 번째 줄이 UTF-8이다. "안"과 "녕"이 각각 3바이트로 저장되었다. 첫 번째 줄은 UTF-16이다. 맨 앞의 `\xff\xfe`는 "이 파일은 UTF-16이다"라는 표시이고, 글자마다 2바이트를 쓰며, 줄바꿈 문자 뒤에도 `\x00`이 붙어 있다. Git은 파일 안에 `\x00`이 있으면 바이너리 파일로 취급한다.
5. UTF-8로 읽어 본다.
   ```
   python -c "print(open('hello51.txt', encoding='utf-8').read())"
   python -c "print(open('hello7.txt', encoding='utf-8').read())"
   ```
   첫 번째 명령은 기초 과정 7장에서 본 오류를 낸다.
   ```
   UnicodeDecodeError: 'utf-8' codec can't decode byte 0xff in position 0: invalid start byte
   ```
6. 확인했으면 두 파일을 지운다.
   ```
   Remove-Item hello51.txt, hello7.txt
   ```

1. 로그인할 때 실행되는 셸과 버전을 확인한다.


3. `&&`를 써 본다. zsh는 처음부터 이 연산자를 지원한다.

## 1.3 기초 과정 점검

이 과정은 기초 과정에서 배운 몇 가지 개념에 기댄다. 하나씩 다시 확인한다. 막히는 곳이 있으면 괄호 안의 기초 과정 절을 다시 본다. 이번에는 PowerShell 7에서 처음 해 보는 것이므로 Windows 사용자는 결과를 특히 꼼꼼히 확인한다.

### 1.3.1 경로와 현재 위치 (기초 과정 1.1, 7장)

명령은 **현재 디렉터리**를 기준으로 동작한다. 상대 경로는 현재 디렉터리에서 출발하는 경로이고, 절대 경로는 맨 위(macOS `/`, Windows `C:\`)에서 출발하는 경로다. `~`는 홈 폴더, `.`은 현재 폴더, `..`은 한 단계 위의 폴더다.

다음 세 명령은 모두 같은 폴더로 이동한다. 지금 `~/devtools-lab/ch01`에 있다고 하자.

```
# macOS
cd ../../python-lab/ch10
cd ~/python-lab/ch10
cd /Users/본인계정/python-lab/ch10

# Windows
cd ..\..\python-lab\ch10
cd ~\python-lab\ch10
cd C:\Users\본인계정\python-lab\ch10
```

첫 번째 명령은 **지금 있는 곳에 따라** 다른 곳으로 가거나 실패한다. 나머지 두 명령은 어디서 실행해도 같은 곳으로 간다. 기초 과정 7장에서 "실행 위치에 따라 상대 경로가 달라지는 문제"로 만났던 것이다. 이 과정에서 Git 명령은 저장소 폴더 안에서 실행해야 하고, 저장소가 아닌 곳에서 실행하면 `not a git repository`라는 오류가 난다. 명령이 이상하게 동작하면 가장 먼저 `pwd`로 현재 위치를 확인하는 습관을 이어 간다.

(PowerShell 7은 경로 구분자로 `/`도 받아들인다. `cd ~/python-lab/ch10`도 Windows에서 동작한다. 다만 출력에는 `\`로 표시된다.)

### 1.3.2 환경 변수 (기초 과정 8.2.1)

환경 변수는 운영체제가 프로그램에게 넘겨주는 **이름=값** 쌍이다. 터미널에서 정한 환경 변수는 **그 터미널 창에서만, 창을 닫을 때까지만** 유효하다.

```
# macOS
export LAB_USER=영희
python3 -c "import os; print(os.getenv('LAB_USER'))"

# Windows
$env:LAB_USER = "영희"
python -c "import os; print(os.getenv('LAB_USER'))"
```

```
영희
```

새 터미널을 열고 두 번째 줄만 다시 실행하면 `None`이 출력된다. 이 과정에서 환경 변수는 세 군데에서 중요하다. 3장에서는 터미널을 열 때마다 자동으로 정해지게 하는 방법(셸 설정 파일)을 배우고, 8장에서는 API 키를 담은 `.env` 파일을 Git에 올리지 않는 방법을 배우며, 4장에서는 VS Code의 디버그 실행 설정에 환경 변수를 넣는다. 원칙은 기초 과정과 같다. **비밀 값은 코드에 쓰지 않는다.** 이 과정에서 하나 더한다. **비밀 값은 Git에도 올리지 않는다.**

### 1.3.3 가상환경과 터미널이 찾는 파이썬 (기초 과정 9장)

가상환경을 활성화하면 `PATH`의 맨 앞에 가상환경의 폴더(macOS `.venv/bin`, Windows `.venv\Scripts`)가 들어간다. 그래서 `python`을 입력하면 가상환경의 파이썬이 먼저 발견된다. 1.2.7에서 Homebrew의 Git이 먼저 발견된 것과 같은 원리다.

기초 과정 10장의 프로젝트 폴더로 가서 활성화하고 확인한다.

```
# macOS
cd ~/python-lab/ch10/ledger_app
source .venv/bin/activate
which python
python -c "import sys; print(sys.executable)"

# Windows
cd ~\python-lab\ch10\ledger_app
.venv\Scripts\Activate.ps1
Get-Command python
python -c "import sys; print(sys.executable)"
```

```
# macOS
/Users/본인계정/python-lab/ch10/ledger_app/.venv/bin/python
/Users/본인계정/python-lab/ch10/ledger_app/.venv/bin/python

# Windows
CommandType     Name          Version    Source
-----------     ----          -------    ------
Application     python.exe    3.13.2...  C:\Users\본인계정\python-lab\ch10\ledger_app\.venv\Scripts\python.exe
C:\Users\본인계정\python-lab\ch10\ledger_app\.venv\Scripts\python.exe
```

프롬프트 앞에 `(.venv)`가 붙고, 두 결과가 모두 `.venv` 안을 가리키면 된다.

**Windows에서 활성화가 막히면** 1.2.4의 "가상환경 활성화 확인 — 실행 정책"을 본다. 실행 정책은 5.1과 7이 따로 관리하므로, 기초 과정에서 5.1로 해결했더라도 7에서 다시 막힐 수 있다.

VS Code에서 이 프로젝트를 열었을 때 선택된 인터프리터도 이 `.venv`여야 한다(기초 과정 9.2.4). 4장에서 VS Code의 통합 터미널과 선택된 인터프리터를 맞추는 방법을 다시 다룬다.

### 1.3.4 표준 출력·표준 오류·종료 코드 (기초 과정 8.2.2, 10장)

프로그램은 출력을 두 갈래로 보낸다. 정상 결과를 내보내는 **표준 출력**과, 오류나 안내를 내보내는 **표준 오류**다. 화면에서는 둘 다 터미널에 보이므로 구별되지 않는다. 그리고 프로그램은 끝날 때 **종료 코드**를 남긴다. `0`은 성공, 그 밖의 값은 실패다.

가계부 요약 프로그램으로 확인한다. 가상환경이 활성화된 상태로 `ledger_app` 폴더에서 실행한다.

```
python main.py samples/empty.csv
```

```
empty.csv: 형식 오류 1건
  파일이 비어 있습니다
파일을 고친 뒤 다시 실행하세요. 요약 파일은 만들지 않았습니다.
```

종료 코드를 확인한다.

```
# macOS
echo $?

# Windows
$LASTEXITCODE
```

```
1
```

`README.md`의 "입력에 따른 동작" 표에 적은 대로, 빈 파일은 표준 오류로 메시지를 내고 종료 코드 1로 끝난다.

이번에는 출력을 파일로 보내 본다. 기초 과정에서 `pip freeze > requirements.txt`로 쓴 `>`는 **표준 출력만** 파일로 보낸다.

```
python main.py samples/empty.csv > out.txt
```

```
empty.csv: 형식 오류 1건
  파일이 비어 있습니다
파일을 고친 뒤 다시 실행하세요. 요약 파일은 만들지 않았습니다.
```

출력을 파일로 보냈는데도 세 줄이 모두 화면에 나왔다. 기초 과정 10장의 `cli.py`에서 오류 메시지를 `error_console`(표준 오류)로 출력했기 때문에, 이 메시지들은 `>`의 영향을 받지 않는다. `out.txt`를 열어 보면 비어 있다. 반대로 정상 파일로 같은 일을 하면 요약 표가 화면에 나오지 않고 `out.txt`에 들어간다. Windows에서는 1.2.3의 "외부 프로그램의 출력은 프로그램이 인코딩을 정한다"에서 본 대로 이 `out.txt`가 cp949로 저장되어 VS Code에서 한글이 깨져 보인다. `python -X utf8 main.py samples/2026-10.csv > out.txt`로 다시 실행해 비교해 보자. 확인했으면 `out.txt`를 지운다(macOS `rm out.txt`, Windows `Remove-Item out.txt`). 표준 출력과 표준 오류를 따로 파일로 보내거나 합치는 방법은 3장에서 배운다.

> **`$?`는 셸마다 다르다**
> zsh·bash의 `$?`는 종료 코드 숫자다. PowerShell에도 `$?`가 있지만 "앞 명령이 성공했는가"를 `True`/`False`로 알려 준다. PowerShell에서 외부 프로그램의 종료 코드 숫자를 보려면 `$LASTEXITCODE`를 쓴다. 3장에서 다시 다룬다.

종료 코드가 이 과정에서 중요한 이유는 3장에서 배울 `&&` 때문이다. 다음 명령은 시험이 통과했을 때만(종료 코드 0) 요약을 실행한다.

```
python check_samples.py && python main.py samples/2026-10.csv
```

기초 과정에서 `check_samples.py`가 하나라도 실패하면 종료 코드 1로 끝나게 만든 것이 여기서 쓰인다. 7장의 `git bisect run`, 중급 과정의 GitHub Actions도 같은 약속에 기댄다.

### 1.3.5 10장의 프로젝트 폴더

10장에서 만든 `ledger_app` 폴더는 이 과정의 10장에서 Git 저장소가 된다. 지금은 필요한 파일이 모두 있는지만 확인한다.

```
# macOS
ls -a

# Windows
ls
```

```
# macOS
.                 .venv             README.md         ledger            requirements.txt
..                DESIGN.md         check_samples.py  main.py           samples
.gitignore
```

Windows의 `ls`는 `Mode`, `LastWriteTime`, `Length`, `Name` 열이 있는 표로 보여 준다. `Name` 열을 본다.

macOS에서 그냥 `ls`를 하면 `.gitignore`와 `.venv`가 보이지 않는다. macOS와 리눅스에서는 이름이 `.`으로 시작하는 파일과 폴더가 **숨김 파일**이기 때문이다. `-a`(all)를 붙여야 보인다. Finder에서도 기본으로는 보이지 않는다(`Cmd+Shift+.`으로 보이게 할 수 있다). Windows에서는 이름이 `.`으로 시작해도 숨김 파일이 아니라서 그냥 보인다. 2장에서 다시 다룬다. `DESIGN.md`는 기초 과정 10.3.3에서 만든 설계 노트다.

**`requirements.txt`의 인코딩 확인 (Windows)**

기초 과정 10.2.1에서 `python -m pip freeze > requirements.txt`를 Windows PowerShell 5.1에서 실행했다면, 이 파일은 실습 1-2에서 본 UTF-16 파일이다. 파일의 앞부분을 바이트로 확인한다.

```
python -c "print(open('requirements.txt', 'rb').read()[:3])"
```

```
b'mar'
```

`b'mar'`(`markdown-it-py`의 앞 세 글자)이면 UTF-8이다. `b'\xff\xfem'`처럼 `\xff\xfe`로 시작하면 UTF-16이다. 이대로 Git 저장소에 넣으면 Git이 바이너리 파일로 취급해서, 나중에 패키지 버전이 바뀌었을 때 무엇이 바뀌었는지 보여 주지 못한다. 가상환경이 활성화된 상태에서 PowerShell 7로 다시 만든다.

```
python -m pip freeze > requirements.txt
```

`pip freeze`의 출력은 영문·숫자·기호뿐이므로 PowerShell 7에서는 UTF-8과 같은 바이트로 저장된다(1.2.3). 다시 만든 뒤 앞의 명령으로 `b'mar'`가 나오는지 확인한다.

같은 방법으로 `.gitignore`도 확인한다. VS Code에서 만들었다면 UTF-8이다. 5.1에서 `>`로 만든 파일이 있다면 모두 같은 문제가 있다.

macOS는 처음부터 UTF-8이므로 이 확인이 필요 없다.

### 실습 1-3. 기초 과정 점검

`~/python-lab/ch10/ledger_app`에서 다음을 차례로 확인하고, 결과를 `~/devtools-lab/ch01/check.md`에 적는다. 각 항목마다 실행한 명령과 결과(또는 받은 오류 메시지)를 적는다. 기초 과정에서 가계부 요약 대신 실습 10-4의 "나만의 명령행 프로그램"을 주로 다뤘다면 그 프로젝트로 해도 된다.

1. **위치** — 새 터미널을 열고 홈 폴더에서 시작해 `ledger_app` 폴더로 이동한다. 절대 경로 한 번, `~`를 쓴 경로 한 번으로 각각 이동해 보고, 매번 `pwd`로 확인한다.
2. **환경 변수** — 환경 변수 `LAB_USER`를 정하고 파이썬으로 읽는다. 새 터미널 창에서 같은 코드를 실행하면 무엇이 나오는지 적는다.
3. **가상환경** — 가상환경을 활성화하고, `which python`(Windows `Get-Command python`)과 `sys.executable`의 결과를 적는다. 비활성화(`deactivate`)한 뒤 다시 확인하면 어떻게 달라지는지 적는다. 확인했으면 **다시 활성화**하고, `sys.executable`이 다시 `.venv` 안을 가리키는지 확인한다. 4번부터는 가상환경이 켜진 상태에서 실행한다. 꺼진 상태에서 실행하면 `rich`가 없다는 안내가 나오거나, macOS에서는 `python` 명령을 찾지 못한다.
4. **종료 코드** — `README.md`의 "입력에 따른 동작" 표에서 세 가지 경우(정상 파일, 빈 파일, 인자 없음)를 골라 실행하고, 표에 적힌 종료 코드와 실제 종료 코드가 같은지 확인한다.
5. **표준 출력과 표준 오류** — 4번의 세 경우를 `> out.txt`를 붙여 다시 실행하고, 화면에 남는 것과 `out.txt`에 들어가는 것을 나누어 적는다. `README.md` 표에 "(표준 오류)"라고 적힌 경우와 일치하는지 확인한다. 끝나면 `out.txt`를 지운다.
6. **시험** — `python check_samples.py`가 모두 통과하는지, 종료 코드가 0인지 확인한다. 이어서 `python check_samples.py && python main.py samples/2026-10.csv`를 실행해 두 명령이 차례로 실행되는 것을 확인한다.
7. **프로젝트 파일** — `ls -a`(Windows `ls`)로 `.gitignore`, `README.md`, `requirements.txt`, `check_samples.py`가 있는지 확인한다. (Windows) `requirements.txt`가 UTF-8인지 확인하고, 아니면 다시 만든다.
8. **정리** — 점검하다 생긴 파일(`out.txt`, `samples/2026-10_summary.csv`)이 남아 있지 않은지 확인한다. `*_summary.csv`는 `.gitignore`에 적혀 있으므로 남아 있어도 Git에는 올라가지 않지만, 지금은 지워 둔다. 끝나면 `deactivate`로 가상환경을 끈다.

모두 기대한 대로 되었다면 이 과정을 시작할 준비가 되었다. 막힌 항목은 오류 메시지를 `check.md`에 그대로 적고, 1.3의 해당 절과 괄호 안의 기초 과정 절을 다시 본다.

## 정리

| 항목 | 핵심 |
|---|---|
| 이 과정의 목표 | 1단계에서 AI가 대신 한 명령 실행·코드 수정·Git·GitHub 작업을 직접 하고, AI가 한 일을 읽고 판단하고 되돌릴 수 있게 된다 |
| 명령부터 배우는 이유 | 적어 두고 재현할 수 있다, AI 도구가 실제로 하는 일이다, 화면이 없는 곳이 많다, 버튼은 명령을 대신 실행한다 |
| 패키지 관리자 | 프로그램을 명령으로 설치·갱신한다. macOS Homebrew(`brew install`), Windows `winget`(`winget install --id`) |
| PowerShell 7 | Windows의 이 과정 기준 셸(`pwsh`). 5.1에는 `&&`·`||`가 없고 `>`가 UTF-16으로 저장한다. 7의 `>`는 PowerShell 문자열은 UTF-8로, 외부 프로그램의 출력은 바이트 그대로 저장한다(파이썬은 `-X utf8`). 터미널 앱과 VS Code의 기본 프로필을 "PowerShell"로. 실행 정책은 5.1과 따로, `Get-ExecutionPolicy -List`로 범위별 확인 |
| 설치 후 | 새 터미널을 연다(Windows는 VS Code도 다시 시작). `PATH`는 프로그램이 시작할 때의 값을 쓴다 |
| 버전과 위치 | `--version`으로 버전, `which -a` / `Get-Command -All`로 위치. 같은 이름이 여럿이면 `PATH`의 앞쪽이 실행된다 |
| bash | 리눅스 서버의 표준 셸. zsh와 같은 계열. Git Bash와 WSL은 이 과정에서 쓰지 않는다 |
| 종료 코드 | 0은 성공. zsh `echo $?`, PowerShell `$LASTEXITCODE`(PowerShell의 `$?`는 `True`/`False`) |
| `>` | 표준 출력만 파일로 보낸다. 표준 오류는 화면에 남는다 |
| 숨김 파일 | macOS·리눅스에서 `.`으로 시작하는 이름. `ls -a`로 본다 |

## 확인 문제

1. 1단계에서 AI 도구에게 "이전 상태로 되돌려 줘"라고 부탁했을 때 실제로 일어난 일은 무엇인가? 그 내용을 모르면 어떤 문제가 생길 수 있는가?
2. 같은 일을 VS Code의 버튼과 터미널 명령 두 가지로 할 수 있을 때, 이 과정에서 명령부터 배우는 이유를 세 가지 들어라.
3. `brew install`이나 `winget install`로 설치하는 방식이 웹 사이트에서 설치 파일을 받는 방식보다 좋은 점은 무엇인가? 기초 과정에서 쓴 `pip`과는 무엇이 다른가?
4. Homebrew 설치 명령처럼 `curl`로 내려받은 스크립트를 바로 실행하는 명령은 왜 조심해야 하는가? 실행하기 전에 무엇을 확인하는가?
5. Windows에서 `winget`으로 Git을 설치한 직후 같은 터미널에서 `git --version`을 입력했더니 명령을 찾을 수 없다고 나왔다. 왜 그런가? VS Code의 통합 터미널에서도 같은 일이 생긴다면 무엇을 해야 하는가?
6. Windows PowerShell 5.1 대신 PowerShell 7을 쓰는 이유 두 가지는? 지금 쓰는 PowerShell이 어느 것인지 어떻게 확인하는가?
7. Windows PowerShell 5.1에서 `python -m pip freeze > requirements.txt`로 만든 파일을 Git 저장소에 넣으면 어떤 문제가 생기는가? 이 파일이 UTF-16인지 어떻게 확인하는가? 그런데도 기초 과정에서 `pip install -r requirements.txt`가 잘 동작한 이유는?
8. macOS에서 `which -a git`의 결과가 두 줄이었다. `git`을 입력하면 어느 것이 실행되는가? 그 순서는 무엇이 정하는가? 기초 과정의 가상환경 활성화와 어떤 점이 같은가?
9. 기초 과정에서 Windows PowerShell 5.1의 실행 정책을 `RemoteSigned`로 바꾸었는데, PowerShell 7에서 `Activate.ps1`이 막혔다. 왜 그럴 수 있는가? 원인을 확인하는 명령은 무엇인가? `MachinePolicy`에 값이 있다면 `Set-ExecutionPolicy -Scope CurrentUser`로 해결되지 않는 이유는?
10. `python main.py samples/empty.csv > out.txt`를 실행했더니 메시지가 화면에 나오고 `out.txt`는 비어 있었다. 왜 그런가? 정상 파일로 실행하면 어떻게 되는가?
11. `python check_samples.py && python main.py samples/2026-10.csv`에서 두 번째 명령이 실행되는 조건은 무엇인가? `check_samples.py`가 실패를 종료 코드로 알리지 않고 메시지만 출력했다면 어떻게 되는가?
12. macOS 터미널에서 `ls`를 했더니 `.gitignore`가 보이지 않았다. 파일이 없는 것인가? 어떻게 확인하는가?
13. Windows의 PowerShell 7에서 `python main.py samples/2026-10.csv > out.txt`로 만든 파일을 VS Code에서 열었더니 한글이 깨져 보였다. 왜 그런가? 어떻게 하면 UTF-8로 저장되는가? 같은 PowerShell 7에서 `python -m pip freeze > requirements.txt`는 왜 이런 문제가 없는가?
