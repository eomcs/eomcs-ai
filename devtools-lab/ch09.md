# 9장. Jupyter Notebook

[개발 도구](README.md) 과정의 아홉 번째 장이다. 2~8장에서 익힌 도구는 모두 **파일을 만들고, 실행하고, 기록하고, 나누는** 도구였다. 프로그램은 `.py` 파일에 쓰고, 터미널에서 처음부터 끝까지 실행하고, 결과를 보고, 고치고, 다시 처음부터 실행했다. 이 장에서는 일하는 방식이 조금 다른 도구를 배운다. **코드를 조금 쓰고, 바로 실행해 결과를 보고, 그 결과를 보며 다음 코드를 쓰는** 도구, Jupyter Notebook이다.

- **노트북이란** — 코드 셀·Markdown 셀·출력이 한 파일(`.ipynb`)에 담긴다는 것, 커널(코드를 실행하는 파이썬 프로세스), 노트북이 어울리는 일과 스크립트가 어울리는 일
- **설치와 커널 선택** — VS Code에서 쓸 때(`ipykernel`)와 브라우저에서 쓸 때(`jupyterlab`)의 차이, 커널 고르기, "커널의 파이썬"이 터미널의 파이썬과 다를 수 있다는 점
- **셀 다루기** — 실행, 셀 추가·삭제·이동·종류 바꾸기, 마지막 식의 값이 출력되는 규칙, 실행 번호, Markdown 셀
- **숨은 상태의 함정** — 실행한 순서대로 남는 변수, 지운 셀의 변수, 커널 재시작과 "모두 실행", 변수 보기, 인터럽트
- **매직 명령과 셸 명령** — `%pip`와 `!pip`, `!` 셸 명령, `%cd`, 시간 재기, `%%writefile`, `%autoreload`, 노트북의 `await`
- **노트북에서 프로그램으로** — 실험한 코드를 함수로 정리해 `.py` 모듈로 옮기기, `jupyter nbconvert`로 내보내고 새 커널에서 검증하기
- **노트북과 Git** — `.ipynb`의 diff가 읽기 어려운 이유, 출력을 지우고 커밋하기(`nbstripout`), 출력과 소스에 남는 비밀 값, GitHub·VS Code에서 노트북 diff 보기
- **클라우드 노트북 소개** — Google Colab·Kaggle 노트북, 로컬 노트북과의 차이

이 장의 실습 재료는 **가계부**다. 기초 과정 10장에서 가계부 파일을 읽어 요약하는 프로그램을 만들었다. 그때는 무엇을 계산할지 미리 정하고(설계), 그대로 만들었다. 이번에는 거꾸로다. 열 달 치 가계부 파일 하나를 받았는데 **무엇이 들어 있는지, 무엇을 물어야 하는지 아직 모른다.** 열어 보고, 세어 보고, 이상한 값을 만나 고치고, 궁금한 것이 생기면 하나 더 계산해 본다. 이렇게 답을 모르는 채로 데이터를 들여다보는 일을 **탐색**이라고 한다. 노트북은 이 일을 위해 만들어진 도구다. 다음 과정인 "데이터 처리 기초"에서 pandas로 같은 일을 훨씬 짧게 하게 되는데, 그 일도 노트북에서 한다. 이 장에서는 pandas 없이 기초 과정에서 배운 `csv`와 `collections.Counter`만 쓴다. 도구를 익히는 장이므로, 새 라이브러리에 신경 쓰지 않고 노트북 자체에 집중하기 위해서다.

노트북은 편한 만큼 함정도 분명하다. 이 장에서 가장 중요한 것은 **노트북 화면에 보이는 것과 커널 안에 실제로 있는 것이 다를 수 있다**는 사실이다. 셀은 위에서 아래로 놓여 있지만, 실행은 내가 누른 순서대로 일어난다. 지운 셀이 만든 변수도 커널 안에 살아 있다. 그래서 노트북이 "잘 돌아간다"는 말은 **새 커널에서 위에서부터 끝까지 실행해도 같은 결과가 나온다**는 뜻이어야 한다. 이 장의 여러 절이 결국 이 한 가지 습관으로 모인다. 그리고 8장에서 익힌 "비밀 값을 올리지 않기"가 노트북에서 한 번 더 시험받는다. 노트북은 코드뿐 아니라 **실행 결과까지 파일에 저장**하기 때문이다.

## 학습 목표

이 장을 마치면 다음을 할 수 있다.

- 노트북이 코드 셀·Markdown 셀·출력으로 이루어진 JSON 파일(`.ipynb`)이라는 것을 파일을 직접 열어 확인하고, 화면(VS Code나 브라우저)과 커널이 따로 있는 구조를 그림으로 설명할 수 있다.
- 커널이 코드를 실행하는 파이썬 프로세스라는 것을 PID로 확인하고, 커널을 다시 시작하면 무엇이 사라지는지 말할 수 있다.
- 주어진 일이 노트북에 어울리는지 스크립트에 어울리는지 판단하고 그 이유를 말할 수 있다.
- VS Code에서 노트북을 쓸 때는 프로젝트 가상환경에 `ipykernel`만, 브라우저에서 쓸 때는 `jupyterlab`을 설치한다는 차이를 설명하고, 두 방법으로 모두 노트북을 열어 커널을 고를 수 있다.
- 노트북 안에서 `sys.executable`로 커널의 파이썬을 확인하고, 터미널에서는 되는 `import`가 노트북에서 안 될 때 원인을 찾아 고칠 수 있다.
- 명령 모드와 편집 모드를 구별하고, 단축키로 셀을 실행·추가·삭제·이동하고 종류를 바꿀 수 있다.
- 셀의 마지막 식만 자동으로 출력되는 규칙과 실행 번호를 읽고, Markdown 셀에 제목·목록·표·코드·수식을 써서 노트북을 문서로 만들 수 있다.
- 실행 순서 때문에 생기는 숨은 상태의 예를 들고, 커널 재시작 후 "모두 실행"으로 노트북을 검증할 수 있다. 끝나지 않는 셀을 인터럽트로 멈출 수 있다.
- `%pip install`이 `!pip install`보다 안전한 이유를 설명하고, `!` 셸 명령, `%cd`, `%time`·`%timeit`, `%%writefile`, `%autoreload`를 쓸 수 있다. Windows에서 `!` 뒤의 명령이 cmd.exe로 실행된다는 점을 알고 피할 수 있다.
- 노트북에서는 `asyncio.run()` 대신 `await`를 바로 쓴다는 것을 확인할 수 있다.
- 노트북에서 실험한 코드를 함수로 정리해 `.py` 모듈로 옮기고, 노트북에서 import해서 쓸 수 있다. 같은 모듈을 터미널에서 스크립트로도 실행할 수 있다.
- `jupyter nbconvert`로 노트북을 스크립트와 HTML로 내보내고, `--execute`로 새 커널에서 끝까지 실행되는지 검증할 수 있다.
- `.ipynb`의 `git diff`에서 실행 번호·출력·메타데이터의 변경을 구별하고, `nbstripout`으로 출력을 지운 채 커밋되게 설정할 수 있다. 그 설정이 저장소를 받는 사람에게 자동으로 따라가지 않는 이유를 말할 수 있다.
- 노트북의 출력과 소스에 비밀 값과 개인정보가 남는 경로를 들고, 커밋 전에 확인할 수 있다.
- Google Colab·Kaggle 노트북이 로컬 노트북과 파일·패키지·비밀 값을 다루는 방식에서 어떻게 다른지 설명할 수 있다.

VS Code로 `ch09` 폴더를 열고(`code .`), `make_files.py`를 다음과 같이 만든다. 아래쪽의 `notebook()` 함수는 노트북 파일(`.ipynb`)을 JSON으로 직접 써서 만든다. 노트북 파일의 속은 9.1.3에서 들여다본다. 지금은 "노트북 파일도 결국 글자로 된 파일이라 파이썬으로 만들 수 있다"는 것만 기억해 두자.

````python
# make_files.py — 9장 실습 파일을 만든다
import json
import random
import sys
from datetime import date, timedelta
from pathlib import Path

base = Path("practice")
if base.exists():
    sys.exit("practice 폴더가 이미 있다. 다시 만들려면 practice 폴더를 지우고 실행한다.")

random.seed(9)


def write(path, text):
    path.parent.mkdir(parents=True, exist_ok=True)
    path.write_text(text, encoding="utf-8", newline="\n")


# 1. ledger — 가계부 거래 기록을 탐색할 프로젝트
ledger = base / "ledger"

# 형식은 기초 과정 10장의 가계부 파일과 같다: date,kind,category,memo,amount
SPENDING = {
    "식비": (["점심", "저녁", "장보기", "카페", "배달"], 4000, 38000, 26),
    "교통": (["지하철", "버스", "택시"], 1400, 9000, 14),
    "문화": (["영화", "책", "공연"], 9000, 45000, 3),
    "쇼핑": (["생활용품", "옷", "전자제품"], 8000, 120000, 3),
    "의료": (["약국", "병원"], 3000, 25000, 1),
}

rows = []
day = date(2026, 1, 1)
while day <= date(2026, 10, 31):
    if day.day == 25:
        rows.append((day, "수입", "급여", "월급", 3200000))
    if day.day == 1:
        rows.append((day, "지출", "주거", "월세", 650000))
    if day.day == 15:
        rows.append((day, "지출", "통신", "휴대폰 요금", 55000))
    for category, (memos, low, high, per_month) in SPENDING.items():
        # 한 달에 per_month번쯤 나오도록 날마다 확률로 정한다
        if random.random() < per_month / 30:
            amount = random.randrange(low, high, 100)
            rows.append((day, "지출", category, random.choice(memos), amount))
    if random.random() < 0.03:
        rows.append((day, "수입", "부수입", random.choice(["중고 판매", "강의료"]),
                     random.randrange(20000, 300000, 1000)))
    day += timedelta(days=1)

lines = ["date,kind,category,memo,amount"]
for day, kind, category, memo, amount in rows:
    # 엑셀에서 저장한 것처럼 큰 금액 일부는 "12,000" 모양으로 적는다
    if amount >= 10000 and random.random() < 0.3:
        text = f'"{amount:,}"'
    else:
        text = str(amount)
    lines.append(f"{day.isoformat()},{kind},{category},{memo},{text}")
write(ledger / "data" / "2026.csv", "\n".join(lines) + "\n")

write(
    ledger / "README.md",
    """# 가계부 탐색

`data/2026.csv`(2026년 1~10월 가계부)를 노트북에서 탐색한다.

## 입력 파일 형식

기초 과정 10장의 가계부 파일과 같다.

| 열 | 내용 | 예 |
|---|---|---|
| `date` | 거래 날짜(`YYYY-MM-DD`) | `2026-10-05` |
| `kind` | `수입` 또는 `지출` | `지출` |
| `category` | 분류 | `식비` |
| `memo` | 내용 | `점심` |
| `amount` | 금액(원). 세 자리마다 쉼표를 넣었으면 큰따옴표로 감싼다 | `9500`, `"12,000"` |
""",
)
write(
    ledger / ".gitignore",
    """.venv/
__pycache__/
.ipynb_checkpoints/
.env
""",
)


# 2. samples — 미리 만들어 둔 노트북 두 개
def notebook(cells):
    """셀 목록으로 .ipynb의 JSON을 만든다. 셀은 (종류, 소스, 실행 번호, 출력)이다."""
    nb_cells = []
    for kind, source, count, outputs in cells:
        lines = source.splitlines(keepends=True)
        if kind == "markdown":
            nb_cells.append({"cell_type": "markdown", "metadata": {}, "source": lines})
        else:
            nb_cells.append({
                "cell_type": "code",
                "execution_count": count,
                "metadata": {},
                "outputs": outputs,
                "source": lines,
            })
    nb = {
        "cells": nb_cells,
        "metadata": {
            "kernelspec": {"display_name": "Python 3", "language": "python", "name": "python3"},
            "language_info": {"name": "python", "version": "3.13.2"},
        },
        "nbformat": 4,
        "nbformat_minor": 5,
    }
    for i, cell in enumerate(nb["cells"]):
        cell["id"] = f"cell-{i + 1:02d}"
    return json.dumps(nb, ensure_ascii=False, indent=1, sort_keys=True) + "\n"


def stream(text):
    return [{"name": "stdout", "output_type": "stream", "text": text.splitlines(keepends=True)}]


def result(text, count):
    return [{"data": {"text/plain": [text]}, "execution_count": count,
             "metadata": {}, "output_type": "execute_result"}]


# 2-1. 숨은 상태 — 셀을 위에서부터 차례로 실행하지 않은 노트북(9.4)
write(
    base / "samples" / "hidden_state.ipynb",
    notebook([
        ("markdown", "# 할인 계산\n\n할인율을 정하고 할인된 금액을 계산한다.", None, None),
        ("code", "rate = 0.1", 1, []),
        ("code", "price = 20000\nprint(price * (1 - rate))", 5, stream("16000.0\n")),
        ("code", "rate = 0.2", 4, []),
        ("code", "print(won(price))", 6, stream("20,000원\n")),
    ]),
)

# 2-2. 출력에 비밀 값이 남은 노트북(9.7)
write(
    base / "samples" / "leaky.ipynb",
    notebook([
        ("markdown", "# API 연결 시험", None, None),
        ("code", "import os\n\nkey = os.environ[\"LEDGER_API_KEY\"]\nkey", 1,
         result("'lk-demo-7f3a9c2e51b84d06a1c3'", 1)),
        ("code", "print(\"요청 헤더:\", {\"Authorization\": f\"Bearer {key}\"})", 2,
         stream("요청 헤더: {'Authorization': 'Bearer lk-demo-7f3a9c2e51b84d06a1c3'}\n")),
        ("markdown", "키가 제대로 읽히는 것을 확인했다.", None, None),
    ]),
)

print("practice 폴더를 만들었다.")
````

## 9.1 노트북이란

### 9.1.1 코드와 결과와 설명이 한 파일에

지금까지 파이썬을 실행한 방법은 두 가지였다. 하나는 `.py` 파일을 쓰고 `python main.py`로 **처음부터 끝까지** 실행하는 것이고, 다른 하나는 터미널에서 `python`을 입력해 대화형 셸(REPL, 기초 과정 1.2.3)을 열고 **한 줄씩** 실행하는 것이다. 앞의 방법은 코드가 파일로 남지만, 조금 고칠 때마다 처음부터 다시 실행해야 한다. 데이터 파일을 읽는 데 몇 분이 걸린다면 숫자 하나 바꿔 볼 때마다 몇 분을 기다린다. 뒤의 방법은 바로바로 결과를 볼 수 있지만, 셸을 닫으면 입력한 코드도 결과도 사라진다.

노트북은 둘의 좋은 점을 합친다. 노트북은 **셀**(cell)이라는 칸이 위에서 아래로 놓인 문서다.

```
┌─────────────────────────────────────────────────────────┐
│ # 2026년 가계부 탐색                         ← Markdown 셀  │
│ data/2026.csv를 읽어 지출이 어디에 얼마나 쓰였는지 본다.        │
├─────────────────────────────────────────────────────────┤
│ [1] rows = load_rows("data/2026.csv")       ← 코드 셀      │
│     len(rows)                                            │
│ ─────────────────────────────────────────               │
│     533                                     ← 출력        │
├─────────────────────────────────────────────────────────┤
│ [2] spending_by_category(rows).most_common(3)  ← 코드 셀   │
│ ─────────────────────────────────────────               │
│     [('주거', 6500000), ('식비', 5518000), ...]  ← 출력    │
└─────────────────────────────────────────────────────────┘
```

- **코드 셀** — 파이썬 코드를 쓰는 칸이다. 셀 하나를 골라 실행하면 그 셀의 코드만 실행되고, 결과가 셀 바로 아래 **출력** 영역에 나온다. 앞의 셀에서 만든 변수는 다음 셀에서도 쓸 수 있다. 셸에서 한 줄씩 실행하는 것과 같은데, 한 번에 실행하는 단위가 줄이 아니라 셀이다.
- **Markdown 셀** — 설명을 쓰는 칸이다. 8.4.1에서 `README.md`에 쓴 Markdown 문법을 그대로 쓴다. 제목, 목록, 표, 수식을 넣어 "무엇을 왜 계산하는지"를 적는다.
- **출력** — 코드 셀을 실행한 결과다. `print()`로 찍은 글자, 셀의 마지막 식의 값(9.3.3), 오류 메시지, 그리고 나중에 배울 표와 그래프가 여기에 나온다. 출력은 **파일에 함께 저장된다.** 노트북을 다시 열면 코드를 실행하지 않아도 지난번 결과가 보인다.

그래서 노트북 하나에는 **코드와 그 결과와 설명이 함께 담긴다.** 데이터를 탐색하면서 "이 숫자가 왜 이렇지?"를 Markdown으로 적고, 바로 아래 셀에서 확인하는 계산을 하고, 그 결과를 보며 다음 질문을 적는다. 노트북을 받은 사람은 위에서부터 읽기만 해도 무엇을 어떤 순서로 알아냈는지 따라갈 수 있다. 실험 노트에 가까운 도구다. 그래서 이름도 노트북이다.

### 9.1.2 화면과 커널

노트북을 쓸 때 실제로 움직이는 것은 두 가지다.

```
  화면(프런트엔드)                                  커널
┌──────────────────────┐   "이 코드를 실행해"   ┌───────────────────────┐
│ VS Code의 노트북 편집기  │ ───────────────────▶ │ 파이썬 프로세스            │
│ 또는 브라우저의 JupyterLab │ ◀─────────────────── │ (ipykernel)            │
│                      │   "결과는 이것이다"     │                       │
│ 셀, 출력을 보여 주고      │                     │ 변수·함수·import한 모듈이  │
│ .ipynb 파일에 저장한다    │                     │ 메모리에 남아 있다          │
└──────────────────────┘                     └───────────────────────┘
```

- **화면**(프런트엔드) — 셀을 보여 주고, 내가 코드를 쓰고, 실행 단추를 누르는 곳이다. 이 장에서는 VS Code의 노트북 편집기와 브라우저에서 여는 JupyterLab 두 가지를 쓴다. 화면은 노트북 파일(`.ipynb`)을 읽고 저장하지만, **코드를 직접 실행하지는 않는다.**
- **커널**(kernel) — 코드를 실제로 실행하는 **파이썬 프로세스**다. 3.5.1에서 본 "실행 중인 프로그램" 하나다. 화면이 셀의 코드를 보내면 커널이 실행하고 결과를 돌려준다. 커널은 셀을 실행할 때마다 끝나는 것이 아니라 **계속 떠 있으면서** 기다린다. 3.5에서 본 서버 프로그램처럼 스스로 끝나지 않는다. 그래서 앞의 셀에서 만든 변수가 메모리에 남아 있고, 다음 셀에서 쓸 수 있다.

파이썬 노트북의 커널은 `ipykernel`이라는 파이썬 패키지다. 정확히는 **어떤 파이썬이 `ipykernel`을 실행하고 있는 프로세스**가 커널이다. 그래서 가상환경 A의 파이썬으로 커널을 띄우면 그 커널은 가상환경 A에 설치된 패키지만 import할 수 있다. 기초 과정 9.2에서 "터미널이 찾는 파이썬"과 "VS Code가 쓰는 파이썬"이 다를 수 있다고 했다. 노트북에는 하나가 더 있다. **커널의 파이썬**이다. 9.2에서 다룬다.

이 그림에서 기억할 것은 노트북의 정보가 **세 곳**에 나뉘어 있다는 점이다.

| 어디에 | 무엇이 | 언제 사라지나 |
|---|---|---|
| `.ipynb` 파일 | 셀의 코드, Markdown, **마지막으로 실행했을 때의 출력**, 실행 번호 | 파일을 지우거나 고칠 때 |
| 화면 | 지금 보고 있는 셀과 출력(저장하기 전의 변경 포함) | 저장하지 않고 닫을 때 |
| 커널의 메모리 | 변수, 함수, import한 모듈, 읽어 들인 데이터 | **커널을 다시 시작하거나 끌 때** |

변수의 값은 파일에 저장되지 않는다. 커널이 꺼졌다가 새로 시작하면, 노트북의 출력은 그대로 보이지만 변수는 하나도 없다. 화면에 `533`이 찍혀 있어도 `rows`라는 변수는 없다.

노트북을 **닫는 것**과 커널을 **끄는 것**은 같은 일이 아니다. VS Code는 노트북 탭을 닫으면 그 노트북의 커널도 끈다(9.2.4). JupyterLab은 노트북 탭을 닫아도 커널을 끄지 않는다. 다시 열면 떠 있던 커널에 다시 연결되어 변수가 그대로 있다. JupyterLab에서 커널까지 끄려면 메뉴 **File** → **Close and Shut Down Notebook...**을 쓰거나, 왼쪽의 실행 중인 목록(**Running Terminals and Kernels**)에서 끈다. 커널이 아직 떠 있는지 모르겠으면 변수 하나를 실행해 보거나 커널을 다시 시작한다.

반대로 셀을 지워도 그 셀이 만든 변수는 커널에 남는다. 이 어긋남이 9.4의 "숨은 상태"다.

### 9.1.3 `.ipynb` 파일의 속

노트북 파일의 확장자 `.ipynb`는 **IPython Notebook**의 줄임말이다(9.1.5). 속은 JSON이다. 8.9.2에서 YAML로 된 워크플로 파일을 읽었듯이, 노트북 파일도 글자로 된 파일이라 터미널에서 열어 볼 수 있다. 미리 만들어 둔 `samples/hidden_state.ipynb`의 앞부분을 본다.

```
# macOS
head -40 ../samples/hidden_state.ipynb

# Windows
Get-Content ../samples/hidden_state.ipynb -TotalCount 40
```

```json
{
 "cells": [
  {
   "cell_type": "markdown",
   "id": "cell-01",
   "metadata": {},
   "source": [
    "# 할인 계산\n",
    "\n",
    "할인율을 정하고 할인된 금액을 계산한다."
   ]
  },
  {
   "cell_type": "code",
   "execution_count": 1,
   "id": "cell-02",
   "metadata": {},
   "outputs": [],
   "source": [
    "rate = 0.1"
   ]
  },
  {
   "cell_type": "code",
   "execution_count": 5,
   "id": "cell-03",
   "metadata": {},
   "outputs": [
    {
     "name": "stdout",
     "output_type": "stream",
     "text": [
      "16000.0\n"
     ]
    }
   ],
   "source": [
    "price = 20000\n",
    "print(price * (1 - rate))"
   ]
```

맨 바깥은 딕셔너리이고, `"cells"`의 값이 셀의 리스트다. 셀 하나도 딕셔너리다.

| 키 | 뜻 |
|---|---|
| `cell_type` | `"code"` 또는 `"markdown"` |
| `id` | 셀마다 붙는 이름표. 편집기가 셀을 만들 때 정한다 |
| `source` | 셀의 내용. **줄마다 문자열 하나**로 나뉜 리스트다. 줄 끝의 `\n`도 들어 있다 |
| `execution_count` | 코드 셀의 실행 번호(9.3.4). 한 번도 실행하지 않았으면 `null` |
| `outputs` | 코드 셀의 출력 리스트. `print()`의 결과는 `"output_type": "stream"`, 마지막 식의 값은 `"execute_result"`, 오류는 `"error"`로 저장된다 |
| `metadata` | 셀에 붙는 부가 정보. 대개 비어 있다 |

파일의 끝에는 노트북 전체의 정보가 있다.

```
# macOS
tail -15 ../samples/hidden_state.ipynb

# Windows
Get-Content ../samples/hidden_state.ipynb -Tail 15
```

```json
 ],
 "metadata": {
  "kernelspec": {
   "display_name": "Python 3",
   "language": "python",
   "name": "python3"
  },
  "language_info": {
   "name": "python",
   "version": "3.13.2"
  }
 },
 "nbformat": 4,
 "nbformat_minor": 5
}
```

`kernelspec`은 이 노트북을 어떤 커널로 열지, `language_info`는 마지막으로 실행한 파이썬의 버전, `nbformat`은 노트북 파일 형식의 버전이다. 편집기는 이런 정보를 실행할 때마다 고쳐 쓰기도 한다. 9.7에서 이것이 Git에서 왜 성가신지 본다.

이 JSON에서 세 가지를 확인해 두자.

1. **출력이 파일 안에 있다.** `"16000.0\n"`이 그대로 적혀 있다. 출력에 비밀 값이 찍히면 비밀 값도 파일 안에 있게 된다(9.7.4).
2. **변수는 파일 안에 없다.** `rate`가 지금 `0.1`인지 `0.2`인지는 어디에도 적혀 있지 않다. 코드와 그 코드를 실행했을 때의 출력만 있다.
3. **실행 번호가 `1` 다음에 `5`다.** 위에서 두 번째 코드 셀이 다섯 번째로 실행되었다는 뜻이다. 이 노트북이 어떤 순서로 실행되었는지는 9.4.1에서 풀어 본다.

VS Code에서 `.ipynb` 파일을 열면 노트북 편집기가 열린다. JSON 그대로 보고 싶으면 탐색기에서 파일을 오른쪽 클릭 → **Open With...**(연결 프로그램) → **Text Editor**(텍스트 편집기)를 고른다. 이렇게 연 JSON을 손으로 고치는 일은 거의 없다. 쉼표 하나만 틀려도 노트북이 열리지 않는다. 노트북은 노트북 편집기로 고친다.

### 9.1.4 노트북이 어울리는 일, 스크립트가 어울리는 일

노트북은 편하지만 모든 일에 맞지는 않는다. 둘을 비교해 보자.

| | 노트북(`.ipynb`) | 스크립트·모듈(`.py`) |
|---|---|---|
| 실행 단위 | 셀 하나씩, 내가 고른 순서로 | 파일 전체를 위에서 아래로 |
| 결과 | 코드 바로 아래에 남는다(파일에 저장) | 터미널에 나오고 사라진다(저장하려면 따로 쓴다) |
| 상태 | 커널에 남는다. 앞의 결과를 다시 계산하지 않고 이어서 쓴다 | 실행할 때마다 처음부터 |
| 다른 코드에서 쓰기 | 어렵다(노트북은 import하지 않는다) | `import`로 가져다 쓴다 |
| 반복 실행·자동화 | 불편하다 | 터미널, 스케줄러, GitHub Actions에서 실행한다 |
| 시험(테스트) | 어렵다 | 시험 스크립트, 중급 과정의 pytest |
| Git으로 변경 보기 | 어렵다(9.7) | 쉽다 |

**노트북이 어울리는 일**은 답을 모르는 채로 해 보는 일이다.

- **데이터 탐색** — 파일에 무엇이 들어 있는지 보고, 세고, 묶고, 이상한 값을 찾는다. 다음 계산이 앞 계산의 결과에 따라 정해진다. 이 장의 실습이 이것이고, "데이터 처리 기초"의 pandas 실습도 노트북에서 한다.
- **프롬프트 실험** — "LLM API 활용"에서 프롬프트의 문구를 바꿔 가며 응답을 비교한다. 응답을 받는 데 몇 초씩 걸리고 돈이 든다. 노트북이면 앞에서 받은 응답이 출력으로 남아 있어 다시 요청하지 않고 비교할 수 있고, 클라이언트 객체를 만드는 셀은 한 번만 실행해 두면 된다.
- **학습 기록** — 새 라이브러리를 익히면서 해 본 코드와 결과, 알게 된 것을 Markdown으로 함께 남긴다. 나중에 다시 열면 결과까지 보인다.
- **결과 보여 주기** — 계산 과정과 결과를 설명과 함께 남에게 보여 준다. HTML로 내보낼 수도 있다(9.6.5).

**스크립트가 어울리는 일**은 답을 알고 반복하는 일이다.

- **반복 실행** — 매달 가계부 요약을 만드는 일, 매일 밤 데이터를 모으는 일. 같은 코드를 같은 순서로 실행해야 한다.
- **다른 코드에서 가져다 쓰기** — 함수와 클래스는 `.py` 모듈에 두어야 다른 파일과 노트북에서 import할 수 있다.
- **서버와 도구** — 웹 서버, API 서버, MCP 서버, 명령행 프로그램. 노트북으로 만들지 않는다.
- **시험하고 남과 함께 고치기** — 자동 시험, 코드 리뷰, 충돌 해결이 모두 `.py`에서 훨씬 쉽다.

한 문장으로 줄이면 **"답을 찾는 중이면 노트북, 답을 알고 되풀이하면 스크립트"**다. 실제로는 둘을 함께 쓴다. 노트북에서 탐색하다가 쓸 만한 계산이 생기면 함수로 정리해 `.py` 모듈로 옮기고, 노트북은 그 모듈을 import해서 결과를 보고 설명하는 데 쓴다. 이 흐름을 9.6에서 해 본다. 기초 과정 10장에서 만든 가계부 요약 프로그램은 "답을 알고 되풀이하는" 쪽이었다. 이 장의 노트북은 그 앞 단계, 무엇을 요약할지 정하기 전의 일이다.

### 9.1.5 이름 정리

Jupyter 주변에는 비슷한 이름이 많다. 이 장에서 만나는 이름을 한 번에 정리해 둔다.

| 이름 | 무엇인가 |
|---|---|
| **Jupyter**(프로젝트) | 노트북 형식과 관련 도구를 만드는 오픈 소스 프로젝트. 처음 지원한 언어 **Ju**lia, **Py**thon, **R**에서 이름을 따왔다 |
| **노트북**(`.ipynb`) | 이 장에서 다루는 파일 형식. VS Code, JupyterLab, Colab이 모두 같은 형식을 읽고 쓴다 |
| **IPython** | 파이썬 셸을 더 편하게 만든 프로그램. 매직 명령(`%time` 등, 9.5)과 `!` 셸 명령은 파이썬이 아니라 IPython의 기능이다. Jupyter는 IPython Notebook에서 갈라져 나왔고, 그래서 확장자가 `.ipynb`다 |
| **ipykernel** | IPython을 커널로 쓸 수 있게 해 주는 패키지. VS Code에서 노트북을 쓸 때 프로젝트에 설치하는 것은 이것 하나다(9.2) |
| **JupyterLab** | 브라우저에서 노트북을 여는 프로그램. 파일 탐색기, 터미널, 여러 탭을 갖춘 작업 환경이다. 명령은 `jupyter lab` |
| **Jupyter Notebook**(앱) | 브라우저에서 노트북을 여는 또 하나의 프로그램. JupyterLab보다 단순한 화면으로, 노트북 하나를 한 탭에서 연다. 명령은 `jupyter notebook`(`notebook` 패키지). 이 장에서는 쓰지 않는다 |
| **Jupyter Server** | JupyterLab과 Jupyter Notebook의 뒤에서 도는 서버. 브라우저와 커널 사이를 잇는다(9.2.5) |
| **VS Code Jupyter 확장** | VS Code 안에서 노트북을 열고 커널과 이어 주는 확장. JupyterLab 없이도 동작한다 |
| **nbconvert** | 노트북을 스크립트·HTML 등으로 바꾸는 도구. 명령은 `jupyter nbconvert`(9.6.5) |

"Jupyter Notebook"이라는 말은 **파일 형식**(노트북)과 **앱**(Jupyter Notebook 앱)을 함께 가리켜서 헷갈리기 쉽다. 이 교재에서 그냥 "노트북"이라고 하면 파일 형식을 말한다. 노트북을 여는 방법이 여럿이라도 파일은 같다. VS Code에서 만든 노트북을 JupyterLab이나 Colab에서 열 수 있고, 그 반대도 된다.

## 9.2 설치와 커널 선택

### 9.2.1 어디서 쓰느냐에 따라 설치할 것이 다르다

노트북을 쓰려면 화면과 커널(9.1.2)이 모두 있어야 한다. 화면을 무엇으로 하느냐에 따라 설치할 것이 다르다.

| 노트북을 여는 곳 | 화면 | 커널을 위해 설치할 것 | 프로젝트 가상환경에 설치할 패키지 |
|---|---|---|---|
| **VS Code** | Jupyter 확장(4.2.3에서 설치) | `ipykernel` | `ipykernel` 하나 |
| **브라우저**(JupyterLab) | JupyterLab(Jupyter Server 포함) | `ipykernel`(JupyterLab이 함께 설치한다) | `jupyterlab` |
| Google Colab 등(9.8) | 웹 사이트 | 이미 준비되어 있다 | 없음 |

VS Code에서 쓸 때는 **화면이 이미 있으므로 커널만 있으면 된다.** 그래서 프로젝트의 가상환경에 `ipykernel` 하나만 설치한다. JupyterLab은 설치하지 않는다. 인터넷의 설치 안내 중에는 "먼저 `pip install jupyter`를 하라"는 것이 많은데, `jupyter`는 JupyterLab, Jupyter Notebook 앱, 콘솔, nbconvert 등을 한꺼번에 설치하는 묶음 패키지다. VS Code만 쓴다면 필요 없는 것이 대부분이다.

브라우저에서 쓸 때는 화면 역할을 하는 JupyterLab이 있어야 한다. `jupyterlab`을 설치하면 커널(`ipykernel`)과 nbconvert도 함께 설치된다.

이 장에서는 두 가지를 모두 해 본다. 먼저 VS Code로 시작하고(9.2.2~9.2.4), 9.2.5에서 JupyterLab을 더한다. 이 과정에서는 이후로도 주로 VS Code에서 노트북을 쓴다. 편집기·터미널·Git·디버거를 한 창에서 쓸 수 있기 때문이다.

### 9.2.4 커널의 파이썬과 커널 프로세스 확인하기

**커널의 파이썬**

새 셀에 다음을 입력하고 실행한다.

```python
import sys

sys.executable
```

```
# macOS
'/Users/jinyoung/devtools-lab/ch09/practice/ledger/.venv/bin/python'

# Windows
'C:\\Users\\jinyoung\\devtools-lab\\ch09\\practice\\ledger\\.venv\\Scripts\\python.exe'
```

기초 과정 9.2.3의 `sys.executable`, "지금 이 코드를 실행하고 있는 파이썬"이다. 경로가 이 프로젝트의 `.venv` 안이면 커널을 제대로 고른 것이다. `jinyoung` 자리에는 내 사용자 이름이 나온다. Windows의 경로에 `\\`가 두 개씩 나온 것은 셀이 문자열을 따옴표째, 곧 코드에 적는 모양(repr)으로 보여 주기 때문이다. `print(sys.executable)`로 찍으면 하나씩 나온다.

노트북에서 패키지가 import되지 않을 때 가장 먼저 할 일이 이것이다. **노트북 안에서** `sys.executable`을 찍어 커널의 파이썬을 확인하고, 터미널에서 패키지를 설치한 파이썬과 비교한다. 터미널에서는 `python -c "import sys; print(sys.executable)"`로 확인한다. 두 경로가 다르면 다른 파이썬에 설치한 것이다(9.2.7).

**커널 프로세스**

커널이 정말 따로 떠 있는 프로세스인지 확인해 보자. 새 셀에서 커널 프로세스의 PID를 본다.

```python
import os

os.getpid()
```

```
48213
```

숫자는 사람마다 다르다. 통합 터미널에서 이 PID의 프로세스를 찾는다(3.5.1). 숫자는 내 화면의 것으로 바꾼다.

```
# macOS
ps -p 48213 -o pid,command

# Windows
Get-Process -Id 48213 | Select-Object Id, Path
```

```

- **`token=...`** — 이 서버에 들어올 수 있는 열쇠다. 아래 상자에서 다룬다.
- **`Use Control-C to stop this server`** — 이 터미널은 서버가 쓰고 있으므로 다른 명령을 입력할 수 없다. 3.5.2처럼 터미널을 하나 더 열어 쓴다.

> **같은 노트북을 두 곳에서 동시에 열지 않는다**
> VS Code와 JupyterLab에서 같은 노트북을 동시에 열어 두고 양쪽에서 고치면, 나중에 저장하는 쪽이 먼저 저장한 쪽의 변경을 덮어쓴다. JupyterLab은 파일이 밖에서 바뀌었다고 경고를 띄우기도 하지만, 놓치기 쉽다. 이 실습에서는 JupyterLab에서 노트북을 볼 동안 VS Code의 `explore.ipynb` 탭을 닫아 둔다.

JupyterLab을 끄는 방법은 두 가지다.

- 브라우저에서 메뉴 **File** → **Shut Down**(종료)
- `jupyter lab`을 실행한 터미널에서 `Ctrl+C`. macOS에서는 다음과 같이 묻는다.

```

```

```

> **토큰은 비밀번호다**
> JupyterLab의 주소에 붙은 `token=...`은 이 서버에 들어올 수 있는 열쇠다. 노트북 서버에 들어온 사람은 **커널에서 아무 파이썬 코드나 실행할 수 있다.** 파일을 읽고 지우고, 인터넷에 무엇이든 보낼 수 있다. 내 권한으로. 그래서 다음을 지킨다.
>
> - 토큰이 붙은 주소를 채팅이나 이슈, AI 도구에 붙여 넣지 않는다. 화면을 공유할 때 터미널의 이 줄이 보이지 않게 한다. 8.3의 비밀 값과 같게 다룬다.
> - JupyterLab은 기본으로 `localhost`, 곧 **내 컴퓨터 안에서만** 접속을 받는다. 인터넷의 안내에서 `--ip 0.0.0.0`(모든 네트워크에서 접속 받기)이나 `--IdentityProvider.token=''`(토큰 끄기, 예전 이름은 `--NotebookApp.token=''`) 같은 옵션을 보더라도 내 컴퓨터에서는 쓰지 않는다. 같은 네트워크의 누구나 내 컴퓨터에서 코드를 실행할 수 있게 된다.
> - 서버는 쓰고 나면 끈다.

> **JupyterLab 하나로 여러 프로젝트의 가상환경 쓰기**
> 이 장에서는 프로젝트의 가상환경에 JupyterLab까지 설치했다. 가장 단순하고, 커널의 파이썬이 프로젝트의 파이썬과 저절로 같아진다는 장점이 있다. 대신 프로젝트마다 90개 남짓한 패키지를 설치한다. JupyterLab을 한 곳에만 설치해 두고 프로젝트마다 커널만 등록해서 쓰는 방법도 있다. 프로젝트의 가상환경에서 다음을 실행하면, 이 가상환경의 파이썬으로 커널을 띄우는 설정(**kernelspec**)이 내 계정의 Jupyter 설정 폴더에 생긴다.
>
> ```
> python -m ipykernel install --user --name ledger --display-name "Python (ledger)"
> jupyter kernelspec list
> ```
>
> ```
> Installed kernelspec ledger in /Users/jinyoung/Library/Jupyter/kernels/ledger
> Available kernels:
>   python3    /Users/jinyoung/devtools-lab/ch09/practice/ledger/.venv/share/jupyter/kernels/python3
>   ledger     /Users/jinyoung/Library/Jupyter/kernels/ledger
> ```
>
> 이제 어느 JupyterLab에서든 커널 목록에 **Python (ledger)**가 보이고, 고르면 이 프로젝트의 `.venv` 파이썬으로 커널이 뜬다. 등록한 커널은 `jupyter kernelspec remove ledger`로 지운다. 가상환경을 지우거나 옮기면 등록한 커널은 없는 파이썬을 가리키게 되므로 함께 지운다. 이 방법을 쓰면 **JupyterLab의 파이썬과 커널의 파이썬이 다르다.** 그 차이가 9.5.2의 `!pip` 문제를 만든다. (`jupyter kernelspec list`는 `ipykernel`만 설치한 9.2.2의 상태에서도 쓸 수 있다. `jupyter` 명령은 `jupyter_core`에 들어 있기 때문이다.)

### 9.2.6 노트북 도구를 프로젝트에 적어 두기

기초 과정 9.1.7에서는 설치한 패키지를 `python -m pip freeze > requirements.txt`로 적어 두었다. 지금 freeze를 하면 90줄이 넘게 나온다. 그 대부분은 내가 고른 것이 아니라 JupyterLab이 데려온 것이다. 그리고 이 프로젝트에서 노트북 도구는 **탐색할 때만** 필요하다. 9.6에서 만들 `ledger_tools.py`를 터미널에서 실행하는 데는 하나도 필요 없다.

그래서 노트북 도구는 따로 적는다. `practice/ledger`에 `requirements-dev.txt`를 만든다. 이름의 `dev`는 개발(development)할 때만 쓰는 도구라는 뜻이다.

```
# 노트북으로 탐색할 때 쓰는 도구. 프로그램(ledger_tools.py)을 실행하는 데는 필요 없다.
ipykernel==7.4.0
jupyterlab==4.6.6
```

freeze의 출력 전체가 아니라 **내가 직접 설치한 것만** 손으로 적었다. 버전은 `python -m pip show ipykernel`의 `Version:` 줄에서 확인해 내 화면의 숫자로 적는다. 함께 설치되는 나머지는 `pip`가 알아서 맞춰 준다. 복원할 때는 기초 과정과 같은 방법으로 설치한다.

```
python -m pip install -r requirements-dev.txt
```

`#`로 시작하는 줄은 주석이라 `pip`가 건너뛴다. 이 프로젝트처럼 표준 라이브러리만 쓰는 프로그램은 `requirements.txt`가 필요 없다. 프로그램이 외부 패키지를 쓰게 되면 그것은 `requirements.txt`에 적고, `requirements-dev.txt`의 첫 줄에 `-r requirements.txt`를 넣어 "개발 도구를 설치할 때 프로그램의 패키지도 함께 설치하라"고 적는 것이 흔한 방법이다. 실행에 필요한 것과 개발에 필요한 것을 나누는 더 체계적인 방법(`pyproject.toml`)은 중급 과정 8장에서 다룬다. 9.7에서 이 파일을 커밋하고, `README.md`에도 준비 방법을 적는다.

### 9.2.7 커널 문제 해결

노트북을 쓰다 보면 커널 때문에 막히는 일이 자주 생긴다. 증상별로 정리한다.

| 증상 | 확인할 것 | 해결 |
|---|---|---|
| **Select Kernel** 목록에 이 프로젝트의 `.venv`가 없다 | VS Code가 프로젝트 폴더(`ledger`)를 열고 있는가? `.venv`를 만들었는가? | 폴더를 다시 연다. **Python Environments...** 목록 위쪽의 새로 고침 단추를 누른다. 그래도 없으면 `Python: Select Interpreter` → **Enter interpreter path...**로 `.venv/bin/python`(Windows `.venv\Scripts\python.exe`)을 직접 고른다 |
| `requires the ipykernel package` | 창에 적힌 환경 이름이 이 프로젝트의 `.venv`인가? | 맞으면 **Install**. 아니면 커널을 다시 고른다(9.2.3의 상자) |
| 터미널에서는 `import`되는 패키지가 노트북에서 `ModuleNotFoundError` | 노트북의 `sys.executable`과 터미널의 `python -c "import sys; print(sys.executable)"`가 같은가? | 다르면 커널을 바꾸거나, 커널의 파이썬에 설치한다(`%pip install`, 9.5.2) |
| 방금 설치한 패키지가 노트북에서 `import`되지 않는다 | 설치는 맞는 파이썬에 했는가? | 커널을 다시 시작한다. 이미 떠 있는 커널은 새로 설치한 패키지를 못 찾을 때가 있다 |
| 고친 `.py` 모듈의 변경이 노트북에 반영되지 않는다 | | 커널을 다시 시작하거나 `%autoreload`(9.5.7) |
| `The Kernel crashed while executing code in the current cell`(커널이 죽었다) | 큰 데이터를 메모리에 올렸는가? 끝없는 재귀가 있는가? | 커널은 다시 시작된다. 변수는 모두 사라졌으므로 위에서부터 다시 실행한다. 메모리가 원인이면 데이터를 나눠 읽는다 |
| 셀이 끝나지 않는다(`[*]`가 계속 돈다) | 무한 반복인가? 입력(`input()`)을 기다리는가? | 인터럽트, 안 되면 재시작(9.4.6) |

어느 경우든 첫 질문은 같다. **"이 노트북의 커널은 어느 파이썬인가?"** 오른쪽 위의 커널 이름과 `sys.executable`로 확인한다.

## 9.3 셀 다루기

이 절부터는 VS Code에서 `explore.ipynb`로 가계부를 탐색하면서 노트북 조작을 익힌다. JupyterLab에서 해도 되지만, 단축키와 단추 이름은 VS Code를 기준으로 적고 JupyterLab이 다를 때만 함께 적는다.

### 9.3.1 셀 실행하기

셀을 실행하는 방법은 세 가지다. 셋 다 지금 고른 셀을 실행한다는 점은 같고, 실행한 뒤에 어디로 가느냐가 다르다.

| 단축키 | 하는 일 | 쓰는 때 |
|---|---|---|
| `Shift+Enter` | 실행하고 **다음 셀로** 간다. 다음 셀이 없으면 만든다 | 위에서부터 차례로 실행할 때. 가장 많이 쓴다 |
| `Cmd/Ctrl+Enter` | 실행하고 **그 셀에 머문다** | 같은 셀을 고쳐 가며 여러 번 실행할 때 |
| `Option+Enter`(macOS) / `Alt+Enter`(Windows) | 실행하고 **바로 아래에 새 셀을 만든다** | 결과를 보고 다음 코드를 바로 이어 쓸 때 |

셀 왼쪽의 ▷ 단추를 눌러도 실행된다. 도구 막대의 **Run All**(모두 실행)은 노트북의 셀을 위에서부터 끝까지 차례로 실행한다. 셀의 ▷ 옆 메뉴(또는 셀의 **…** 메뉴)에는 **Execute Above Cells**(위의 셀 실행), **Execute Cell and Below**(셀 및 아래 셀 실행)도 있다. 셀을 고쳤을 때 그 셀부터 아래를 다시 계산하는 데 쓴다.

### 9.3.2 명령 모드와 편집 모드

노트북에는 키보드 입력을 받는 상태가 두 가지 있다.

- **편집 모드** — 셀 **안**에 커서가 있는 상태. 입력하는 글자가 셀의 내용이 된다. 셀을 클릭하거나, 셀을 고른 상태에서 `Enter`를 누르면 들어간다.
- **명령 모드** — 셀 **자체**를 고른 상태. 셀 안에 커서가 없다. 이때 누르는 글자 키는 **셀을 다루는 명령**이 된다. 편집 모드에서 `Esc`를 누르면 들어간다.

VS Code에서는 편집 모드일 때 셀의 테두리가 강조되고 셀 안에서 커서가 깜박인다. 명령 모드일 때는 셀 왼쪽에 막대만 표시되고 커서가 없다. JupyterLab도 비슷하다. 명령 모드의 단축키를 익혀 두면 마우스 없이 셀을 빠르게 다룰 수 있다.

| 명령 모드에서 누르는 키 | 하는 일 |
|---|---|
| `Enter` | 편집 모드로 들어간다 |
| `A` / `B` | 위(Above) / 아래(Below)에 새 셀 만들기 |
| `D` `D`(두 번) | 셀 지우기 |
| `M` / `Y` | 셀을 Markdown 셀 / 코드 셀로 바꾸기 |
| `↑` `↓`(또는 `K` `J`) | 위·아래 셀로 옮겨 가기 |
| `Shift+↑` / `Shift+↓` | 여러 셀 고르기 |
| `Option+↑↓`(macOS) / `Alt+↑↓`(Windows) | 셀을 위·아래로 옮기기(VS Code). JupyterLab에서는 셀 왼쪽을 끌어서 옮긴다 |
| `Cmd/Ctrl+Z` | 셀 작업 되돌리기(VS Code). JupyterLab에서는 지운 셀을 `Z`로 되살린다 |
| `L` | 줄 번호 보이기·숨기기(VS Code) |

편집 모드에서 이 키를 누르면 그냥 글자가 입력된다. 셀에 `a`가 써졌다면 편집 모드였던 것이다. `Esc`를 누르고 다시 한다. 반대로 셀에 글자를 입력하려는데 셀이 생기거나 사라진다면 명령 모드였던 것이다. 4.1.4에서 단축키를 찾았듯이 키보드 단축키 화면(`Cmd/Ctrl+K` `Cmd/Ctrl+S`)에서 `notebook`을 검색하면 노트북 단축키를 모두 볼 수 있다.

### 9.3.3 마지막 식의 값이 출력된다

이제 가계부를 읽어 보자. 지금까지 `explore.ipynb`에 만든 셀(`1 + 1`, `sys.executable`, `os.getpid()`)은 명령 모드에서 `D` `D`로 모두 지운다. 그리고 다음 순서로 셀을 만든다.

맨 위 셀을 `M`으로 Markdown 셀로 바꾸고 다음을 입력한 뒤 `Shift+Enter`를 누른다.

```markdown
# 2026년 가계부 탐색

`data/2026.csv`를 읽어 지출이 어디에 얼마나 쓰였는지 본다.
```

Markdown 셀을 실행하면 서식이 적용된 글로 바뀐다. 다시 고치려면 셀을 더블 클릭하거나 명령 모드에서 `Enter`를 누른다. Markdown 문법은 9.3.7에서 더 쓴다.

다음 코드 셀에 파일을 읽는 코드를 쓴다. 기초 과정 7.3.2의 `csv.DictReader`다.

```python
import csv
from pathlib import Path

path = Path("data/2026.csv")
with path.open(encoding="utf-8", newline="") as f:
    rows = list(csv.DictReader(f))

len(rows)
```

```
533
```

경로를 `"data/2026.csv"`처럼 상대 경로로 썼다. 노트북의 커널은 **노트북 파일이 있는 폴더**에서 시작하므로, 이 경로는 `ledger/data/2026.csv`를 가리킨다. 이 규칙은 9.5.4에서 다시 본다.

`print()`를 쓰지 않았는데 `533`이 나왔다. 노트북에는 다음 규칙이 있다.

> 셀의 **마지막 줄이 식**(expression)이면, 그 값이 출력된다.

파이썬 셸(REPL)에서 `len(rows)`라고만 입력해도 값이 나오던 것과 같다. 다만 셸은 줄마다 값을 보여 주고, 노트북은 **셀의 마지막 식 하나만** 보여 준다. 다음 셀로 확인한다.

```python
len(rows)
rows[0]
```

```
{'date': '2026-01-01',
 'kind': '지출',
 'category': '주거',
 'memo': '월세',
 'amount': '650,000'}
```

`len(rows)`의 값은 나오지 않고, 마지막 줄 `rows[0]`의 값만 나왔다. 딕셔너리가 여러 줄로 보기 좋게 나온 것도 눈여겨보자. 노트북은 긴 리스트나 딕셔너리를 자동으로 줄을 나눠 보여 준다(`print()`로 찍으면 한 줄로 나온다).

규칙을 정리하면 다음과 같다.

| 셀의 마지막 줄 | 출력 |
|---|---|
| 식(`len(rows)`, `rows[0]`, `x * 3`, 변수 이름 하나) | 그 값이 나온다 |
| 대입문(`total = len(rows)`), `import`, `def`, `for` 등 문장 | 아무것도 나오지 않는다 |
| 식 뒤에 세미콜론(`x * 3;`) | 나오지 않는다. 값을 보여 주고 싶지 않을 때 쓴다 |
| 값이 `None`인 식(`print(...)`, `rows.append(...)`) | 나오지 않는다(`print()`가 찍은 글자는 나온다) |

`print()`는 셀의 어디에 있든 찍은 글자가 모두 나온다. 셀 중간의 값을 보고 싶으면 `print()`를 쓰거나, 노트북에서 쓸 수 있는 `display()` 함수를 쓴다. `display(len(rows))`는 마지막 줄이 아니어도 `len(rows)`의 값을 셀 출력과 같은 모양으로 보여 준다. `display()`는 IPython이 주는 함수라서 노트북 밖의 `.py` 파일에서는 쓸 수 없다.

여러 값을 한 번에 보고 싶으면 마지막 줄에 튜플을 쓰는 방법도 있다. 9.3.6에서 쓴다.

> **`_`는 바로 앞의 결과**
> 노트북에서 `_`는 마지막으로 출력된 값을 담고 있다. 셸(REPL)과 같다. 실행 번호 `n`인 셀의 결과는 `Out[n]`으로 꺼낼 수도 있다. 편해 보이지만 `_`의 값은 **어느 셀을 마지막으로 실행했느냐**에 따라 달라진다. 9.4의 숨은 상태를 스스로 만드는 셈이므로, 결과를 다시 쓸 일이 있으면 `_` 대신 변수에 담는다.

### 9.3.4 오류도 출력이다

앞의 몇 줄을 보면 금액은 `'650,000'`처럼 문자열이다. `csv` 모듈은 모든 칸을 문자열로 읽는다(기초 과정 7.3). 정수로 바꿔 보자.

```python
amounts = [int(row["amount"]) for row in rows]
```

```
---------------------------------------------------------------------------
ValueError                                Traceback (most recent call last)
Cell In[3], line 1
----> 1 amounts = [int(row["amount"]) for row in rows]

ValueError: invalid literal for int() with base 10: '650,000'
```

오류도 셀의 출력으로 나온다. 읽는 방법은 기초 과정에서 익힌 트레이스백과 같다. 맨 아래 줄이 오류의 종류와 메시지이고, 위쪽이 오류가 난 곳이다. 노트북에서 다른 점은 파일 이름 대신 **`Cell In[3], line 1`**이 나온다는 것이다. "실행 번호 3인 셀의 1번 줄"이라는 뜻이다. 셀의 줄 번호를 보려면 명령 모드에서 `L`을 누른다. `In[3]`의 숫자는 내 화면의 실행 번호와 다를 수 있다. 실행 번호는 다음 절에서 본다.

어떤 값 때문에 났는지도 메시지에 있다. `'650,000'`, 9.1의 실습 파일을 만들 때 넣은 "쉼표가 든 금액"이다. 오류가 났다고 커널이 멈추지는 않는다. 오류가 난 셀만 실패하고, 커널과 앞의 변수(`rows`)는 그대로다. 그래서 다음 셀에서 바로 고친 코드를 시험할 수 있다. 스크립트였다면 프로그램이 멈추고, 고친 뒤 처음부터 다시 실행했을 것이다. 탐색에서 노트북이 편한 이유가 이것이다.

쉼표를 지우고 바꾸는 함수를 만든다.

```python
def to_int(text):
    """"12,000"처럼 쉼표가 든 금액도 정수로 바꾼다."""
    return int(text.replace(",", ""))

to_int("12,000"), to_int("9500")
```

```
(12000, 9500)
```

마지막 줄에 쉼표로 두 식을 이어 써서 튜플 하나로 두 결과를 함께 보았다.

> **탐색용 코드와 프로그램용 코드**
> 기초 과정 10.1.3에서는 쉼표가 **세 자리마다만** 올 수 있다고 정하고 `"12,00"` 같은 값을 오류로 알리게 했다. 위의 `to_int()`는 그런 검사를 하지 않는다. `"12,00"`도 `1200`이 된다. 탐색할 때는 이렇게 일단 빠르게 읽어서 전체 모양을 보는 일이 많다. 다만 탐색에서 쓴 코드를 **그대로 프로그램에 옮기면 안 된다**는 것을 기억해 둔다. 9.6에서 함수를 모듈로 옮길 때 이 점을 독스트링에 적어 둔다.

### 9.3.5 실행 번호 읽기

코드 셀 왼쪽의 `[ ]` 안 숫자가 **실행 번호**(execution count)다. JupyterLab에서는 `[3]:`처럼 보인다.

| 표시 | 뜻 |
|---|---|
| `[ ]` | 실행 번호가 없다. 실행한 적이 없거나, 출력을 지웠거나(9.3.8), 출력 없이 저장된 파일이다(9.7.3) |
| `[*]` 또는 돌아가는 표시 | 지금 실행 중이거나, 앞의 셀이 끝나기를 기다리는 중이다 |
| `[5]` | 이 셀을 **마지막으로 실행했을 때**, 그 커널이 시작된 뒤 다섯 번째로 실행한 셀이었다 |

실행 번호는 셀의 위치가 아니라 **실행한 순서**다. 커널이 시작될 때 1부터 시작해 셀을 하나 실행할 때마다(어느 셀이든) 하나씩 커진다. 같은 셀을 두 번 실행하면 번호가 다시 매겨지고, 커널을 다시 시작하면 1부터 다시 센다. 그래서 실행 번호를 보면 노트북이 어떤 순서로 실행되었는지 거꾸로 알 수 있다.

주의할 것은 실행 번호가 **파일에 저장된 기록**이라는 점이다(9.1.3). 노트북을 다시 열거나 커널을 다시 시작해도 화면의 번호는 지난번 그대로 남는다. 9.4.1의 `hidden_state.ipynb`는 커널을 띄우기 전부터 `[5]`, `[6]`을 보여 준다. 그러니 `[5]`가 보인다고 지금 커널에 그 셀의 결과가 있다는 뜻은 아니다. 번호는 "마지막으로 실행했을 때의 순서"를 알려 줄 뿐, 지금 커널의 상태는 알려 주지 않는다. 의심스러우면 재시작 후 모두 실행(9.4.4)을 한다.

- 위에서부터 `[1] [2] [3] [4]`처럼 차례로 커진다 → 위에서부터 한 번씩 실행했다. 가장 좋은 상태다.
- `[1] [2] [7] [4]` → 세 번째 셀을 나중에 다시 실행했다. 그 사이 `[5]`, `[6]`은 어딘가에서 실행했거나 지운 셀이다.
- `[1] [ ] [3]` → 두 번째 셀은 마지막으로 실행할 때 실행하지 않았거나, 실행한 뒤 그 셀의 출력만 지운 것이다. **번호만으로는 둘을 구별할 수 없다.** 실행하지 않았는데도 세 번째 셀이 성공했다면, 두 번째 셀이 하는 일은 세 번째 셀에 필요 없거나 **다른 곳에서 같은 일이 이미 되어 있다.** 출력만 지운 것이라면 세 번째 셀이 두 번째 셀에 기대고 있을 수 있다. 어느 쪽인지는 재시작 후 모두 실행(9.4.4)으로 확인한다.

실행 번호가 차례대로가 아닌 노트북은 "화면에 보이는 결과가 위에서부터 실행했을 때의 결과와 다를 수 있다"는 경고다. 9.4에서 이것을 직접 겪는다.

### 9.3.6 셀을 이어 가며 탐색하기

### 9.3.7 Markdown 셀로 설명 쓰기

계산만 늘어놓은 노트북은 일주일 뒤의 나도 읽기 어렵다. 알게 된 것을 Markdown 셀로 적는다. 마지막 셀 아래에 Markdown 셀을 만들고(명령 모드에서 `B` → `M`) 다음을 입력한다.

````markdown
## 지금까지 알게 된 것

- 거래 533건(지출 515건, 수입 18건). 금액 일부는 `"650,000"`처럼 쉼표가 들어 있어 `to_int()`로 바꾼다.
- 지출이 큰 분류: **주거 > 식비 > 쇼핑**
- 월 지출은 140만~200만 원. **9월이 가장 많다** → 이유를 찾아볼 것

| 항목 | 금액(원) |
|---|---:|
| 수입 | 33,181,000 |
| 지출 | 16,848,300 |

저축률은 다음과 같이 계산했다. 약 49%다.

$$
\text{저축률} = \frac{\text{수입} - \text{지출}}{\text{수입}}
$$

금액을 정수로 바꾸는 코드:

```python
int(text.replace(",", ""))
```
````

`Shift+Enter`로 실행하면 제목, 목록, 굵은 글씨, 표, 수식, 코드 상자가 서식대로 보인다. 8.4.1에서 정리한 GitHub의 Markdown과 거의 같다. 노트북에서 새로 쓴 것은 **수식**이다.

- `$...$`는 문장 안의 수식(`$a^2 + b^2$`), `$$...$$`는 따로 한 줄을 차지하는 수식이다. 안에는 LaTeX라는 수식 문법을 쓴다. `\frac{위}{아래}`는 분수, `\text{...}`는 수식 안의 글자, `^`는 위첨자, `_`는 아래첨자다. 3단계에서 머신러닝의 식을 적을 때 쓰게 된다. 지금은 이런 것이 된다는 정도만 알아 두자.
- 표의 둘째 줄 `|---|---:|`의 `:`는 정렬이다. 오른쪽에 `:`가 있으면 오른쪽 정렬이다. 금액처럼 숫자를 담는 열에 쓴다.

Markdown 셀에 쓰는 내용의 기준은 다음과 같다.

- **무엇을 왜** — 셀이 무엇을 계산하는지, 왜 궁금했는지. 코드를 읽으면 알 수 있는 "어떻게"는 적지 않는다.
- **알게 된 것** — 결과를 보고 내린 판단. "주거가 가장 크다"처럼. 숫자를 옮겨 적을 때는 그 숫자를 만든 셀이 바로 위에 있게 한다.
- **다음에 할 것** — "9월이 왜 많은지 볼 것"처럼 아직 풀지 않은 질문.

Markdown 셀에 적은 숫자는 코드를 다시 실행해도 저절로 바뀌지 않는다는 점에 주의한다. 데이터가 바뀌면 위의 표는 틀린 말이 된다. 바뀔 수 있는 숫자는 Markdown에 옮겨 적기보다 코드 셀의 출력으로 두는 편이 안전하다.

## 9.4 숨은 상태의 함정

9.1.2에서 노트북의 정보가 파일·화면·커널 세 곳에 나뉘어 있다고 했다. 셋이 어긋날 때 생기는 문제를 **숨은 상태**(hidden state)라고 부른다. 화면에는 보이지 않는데 커널 안에 있어서 결과에 영향을 주는 것들이다. 노트북을 쓰는 사람이 가장 자주 겪는 문제이고, "내 노트북에서는 되는데 남이 열면 안 된다"의 가장 흔한 원인이다.

### 9.4.1 실행한 순서대로 남는다

미리 만들어 둔 `samples/hidden_state.ipynb`를 연다. 통합 터미널(`practice/ledger`)에서 다음을 실행하면 지금 창에서 열린다.

```
code ../samples/hidden_state.ipynb
```

**아직 아무것도 실행하지 않는다.** 화면에는 지난번 출력이 남아 있다.

```
# 할인 계산
할인율을 정하고 할인된 금액을 계산한다.

[1]  rate = 0.1

[5]  price = 20000
     print(price * (1 - rate))
     ─────────────
     16000.0

[4]  rate = 0.2

[6]  print(won(price))
     ─────────────
     20,000원
```

위에서부터 읽어 보자. `rate`가 `0.1`이고 `price`가 `20000`이니 `20000 * 0.9`, 곧 `18000.0`이어야 한다. 그런데 출력은 `16000.0`이다. 그리고 `won()`이라는 함수는 노트북 어디에도 없는데 마지막 셀이 성공했다.

실행 번호로 이 노트북의 역사를 거꾸로 짜 맞춰 보자.

| 순서 | 실행한 셀 | 그때 일어난 일 |
|---|---|---|
| 1 | `rate = 0.1` | `rate`가 0.1 |
| 2, 3 | **지금은 없는 셀** | 둘 중 하나가 `won()`을 정의했을 것이다. 그 뒤에 셀을 지웠다 |
| 4 | `rate = 0.2`(셋째 셀) | `rate`가 0.2로 바뀌었다 |
| 5 | `price = ...`(둘째 셀) | 이때 `rate`는 0.2 → `16000.0` |
| 6 | `print(won(price))` | 지운 셀이 만든 `won()`이 커널에 남아 있었다 → 성공 |

셀은 위에서 아래로 **놓여** 있지만, 커널은 내가 **누른 순서대로** 실행한다. 둘째 셀이 실행될 때 커널의 `rate`는 바로 위의 `0.1`이 아니라 마지막으로 대입된 `0.2`였다. 화면만 보고는 알 수 없다. 화면은 셀의 위치를 보여 주고, 커널은 실행의 순서를 기억한다.

이 노트북을 남에게 보내면 어떻게 될까? 받은 사람은 출력 `16000.0`을 보고 "10% 할인하면 16000원"이라고 읽을 것이다. 위에서부터 실행해 보면 다른 결과가 나온다. 실제로 해 보자. 커널로 `ledger`의 `.venv`를 고른 뒤(9.2.3), 도구 막대의 **Restart**(다시 시작)를 누르고 이어서 **Run All**(모두 실행)을 누른다.

```
[1]  rate = 0.1

[2]  price = 20000
     print(price * (1 - rate))
     ─────────────
     18000.0

[3]  rate = 0.2

[4]  print(won(price))
     ─────────────
     NameError: name 'won' is not defined
```

출력이 바뀌었다. 새 커널에서 위에서부터 실행하니 `18000.0`이 나왔고, `won()`은 정의된 적이 없으니 오류가 났다. 실행 번호도 1부터 차례대로 다시 매겨졌다. **이것이 이 노트북의 진짜 결과다.** 앞의 출력은 다시 만들 수 없는 기록이었다.

> 이 노트북은 숨은 상태를 보여 주려고 만든 것이므로 고치지 않고 닫는다. 닫을 때 저장할지 물으면 저장하지 않는다(**Don't Save**). 실습 9-4에서 다시 연다.

### 9.4.3 같은 셀을 두 번 실행하면

9.3.6에서 `spend = Counter()` 셀과 더하는 셀을 나누어 만들었다. (커널을 다시 시작했다면 위의 셀부터 다시 실행해 둔다. 오류가 나는 `int()` 셀은 건너뛴다.) 더하는 셀만 **한 번 더** 실행해 보자. `Cmd/Ctrl+Enter`로 실행한다.

```python
for row in rows:
    if row["kind"] == "지출":
        spend[row["category"]] += to_int(row["amount"])

spend.most_common()
```

```
[('주거', 13000000),
 ('식비', 11036000),
 ('쇼핑', 5115000),
 ('문화', 1794400),
 ('교통', 1473600),
 ('통신', 1100000),
 ('의료', 177600)]
```

모든 금액이 정확히 두 배가 되었다. `spend`는 앞의 셀에서 한 번 만들어졌고, 이 셀은 거기에 **더하기만** 한다. 두 번 실행하면 두 번 더한다. 오류가 나지 않으니 숫자가 틀렸다는 것을 알아채기 어렵다. 이 상태에서 아래의 저축률 셀을 다시 실행하면 지출이 두 배로 계산된 저축률이 나온다.

고치는 방법은 **처음 값을 정하는 코드와 그 값을 바꾸는 코드를 한 셀에 두는 것**이다. `spend = Counter()` 셀을 지우고, 더하는 셀의 첫 줄에 넣는다.

```python
spend = Counter()
for row in rows:
    if row["kind"] == "지출":
        spend[row["category"]] += to_int(row["amount"])

spend.most_common()
```

이제 이 셀은 몇 번을 실행해도 같은 결과를 낸다. 월별 합계 셀(`monthly = Counter()`가 같은 셀에 있다)이 처음부터 이렇게 되어 있었다. 기준은 다음과 같다.

> 셀은 **여러 번 실행해도 같은 결과**가 나오게 쓴다.

같은 문제를 만드는 코드 모양이 몇 가지 더 있다.

| 코드 | 두 번 실행하면 |
|---|---|
| `total += amount`, `counts[key] += 1` | 두 번 더해진다 |
| `rows.append(...)`, `rows.extend(...)` | 같은 것이 두 번 들어간다 |
| `rows = rows[1:]`(앞을 잘라 내기) | 한 번 더 잘린다. 원래의 `rows`는 다시 읽기 전까지 되찾을 수 없다 |
| `rows.sort()`, `rows.reverse()` | `sort()`는 같지만 `reverse()`는 원래대로 돌아간다 |
| `price = price * 0.9` | 할인이 두 번 들어간다 |

마지막 줄처럼 **변수를 자기 자신으로 덮어쓰는** 코드는 특히 조심한다. `discounted = price * 0.9`처럼 새 이름에 담으면 몇 번을 실행해도 같다.

### 9.4.4 커널 재시작과 "모두 실행"

숨은 상태를 확인하는 방법은 하나뿐이다. **커널을 다시 시작하고 위에서부터 모두 실행해 본다.** 새 커널에는 숨은 것이 없으므로, 그래도 같은 결과가 나오면 노트북이 셀만으로 완결되어 있다는 뜻이다.

- VS Code — 도구 막대의 **Restart**(다시 시작)를 누르고, 이어서 **Run All**(모두 실행)을 누른다.
- JupyterLab — 메뉴 **Kernel** → **Restart Kernel and Run All Cells...**(커널을 다시 시작하고 모든 셀 실행)

`explore.ipynb`에서 해 보자. 실행이 위에서부터 차례로 진행되다가 9.3.4의 `int()` 셀에서 `ValueError`가 나고, **그 아래 셀들은 실행되지 않는다.** "모두 실행"은 오류가 난 셀에서 멈춘다. 아래 셀들의 실행 번호는 `[ ]`로 남거나 지난번 숫자 그대로다.

탐색하면서 일부러 실패시켜 본 셀이 노트북을 끝까지 못 가게 막은 것이다. 실패에서 알게 된 것은 남기고 셀은 지운다. `int()` 셀을 지우고, 바로 아래 `to_int()` 셀 위에 Markdown 셀로 다음과 같이 적는다.

```markdown
금액 일부는 `"650,000"`처럼 쉼표가 들어 있어 `int()`로 바로 바꾸면 `ValueError`가 난다. 쉼표를 지우고 바꾼다.
```

다시 **Restart** → **Run All**을 한다. 이번에는 끝까지 실행되고, 실행 번호가 위에서부터 `[1] [2] [3] ...`으로 빈틈없이 매겨진다. 출력도 9.3.6과 같아야 한다(분류별 합계가 두 배가 아니어야 한다). 이 상태가 되어야 "이 노트북은 돌아간다"고 말할 수 있다.

언제 하는가?

- **커밋하기 전에**, **남에게 보내기 전에** — 받은 사람이 보는 결과가 다시 만들 수 있는 결과여야 한다.
- **결과를 믿고 판단하기 전에** — 보고서에 숫자를 옮기기 전, "식비가 가장 많다"고 결론 내리기 전.
- **이상할 때** — 결과가 이상하면 원인을 찾기 전에 먼저 재시작하고 모두 실행해 본다. 숨은 상태가 원인이었다면 그것만으로 풀린다.
- **하루 일을 마칠 때** — 다음 날 열었을 때 노트북이 그대로 도는지 확인해 둔다.

데이터를 읽는 데 오래 걸리면 재시작이 부담스럽다. 그럴수록 9.6처럼 코드를 함수로 정리해 두면 처음부터 다시 실행하기가 쉬워진다. 9.6.5에서는 화면을 열지 않고 터미널에서 같은 확인을 하는 방법(`jupyter nbconvert --execute`)도 본다.

### 9.4.5 커널에 무엇이 있는지 보기

커널에 지금 어떤 변수가 있는지 보면 숨은 상태를 찾는 데 도움이 된다.

**VS Code** — 노트북 도구 막대의 **Variables**(변수, 또는 **…** 메뉴 안)를 누르면 커널의 변수 목록이 이름·종류·크기·값과 함께 나온다. VS Code의 버전에 따라 아래쪽 패널에 나오기도 하고, 실행 및 디버그 보기의 **VARIABLES**(변수)에 나오기도 한다. 리스트나 딕셔너리는 펼쳐서 안을 볼 수 있다.

### 9.4.6 끝나지 않는 셀 멈추기

셀을 실행했는데 `[*]`가 계속 돌고 끝나지 않을 때가 있다. 무한 반복이거나, 시간이 오래 걸리는 계산이거나, 응답이 오지 않는 네트워크 요청이다. 일부러 만들어 보자.

```python
import time

for i in range(100):
    print(i, end=" ")
    time.sleep(1)
```

1초에 숫자 하나씩 찍힌다. 끝까지 기다리면 100초가 걸린다. 몇 초 뒤 멈춘다.

- VS Code — 도구 막대의 **Interrupt**(인터럽트, ■ 모양) 단추. 실행 중인 셀 왼쪽의 ■ 단추를 눌러도 된다.
- JupyterLab — 도구 막대의 ■ 단추, 또는 명령 모드에서 `I` `I`(두 번), 또는 메뉴 **Kernel** → **Interrupt Kernel**

```
0 1 2 3 ---------------------------------------------------------------------------
KeyboardInterrupt                         Traceback (most recent call last)
Cell In[12], line 5
      1 import time
      2 
      3 for i in range(100):
      4     print(i, end=" ")
----> 5     time.sleep(1)

KeyboardInterrupt:
```

**인터럽트**는 터미널에서 실행 중인 프로그램에 `Ctrl+C`를 누르는 것과 같다(2.3.3). 파이썬에서는 `KeyboardInterrupt` 예외가 나서 실행이 멈춘다. 터미널과 다른 점은 **커널은 살아 있다**는 것이다. 멈춘 셀만 중단되고, 변수는 그대로다. 새 셀에서 `i`를 실행하면 멈춘 순간의 값(`3`)이 나온다. 반쯤 진행된 계산의 결과가 커널에 남는다는 뜻이기도 하다. 9.4.3의 더하는 셀을 중간에 멈췄다면 `spend`에는 일부만 더해진 값이 남는다. 인터럽트한 뒤에는 그 셀이 바꾸던 변수를 믿지 않는다.

인터럽트로 멈추지 않을 때도 있다. 파이썬이 아닌 코드(C로 만든 라이브러리 안의 긴 계산)가 실행 중이면 인터럽트가 그 계산이 끝날 때까지 전달되지 않는다. 그때는 **Restart**(다시 시작)로 커널을 새로 띄운다. 변수는 모두 사라진다.

> **`input()`을 기다리는 셀**
> 셀에서 `input()`을 쓰면 VS Code는 창 위쪽에, JupyterLab은 셀 아래에 입력 칸을 띄우고 기다린다. 입력 칸을 못 보고 지나치면 셀이 끝나지 않는 것처럼 보인다. 노트북에서는 `input()` 대신 값을 변수에 직접 적는 편이 낫다. 다시 실행할 때마다 같은 값을 입력할 필요도 없다.

### 9.4.7 숨은 상태를 줄이는 습관

이 절의 내용을 습관으로 정리한다.

1. **위에서 아래로 쓰고, 위에서 아래로 실행한다.** 위쪽 셀을 고쳤다면 그 셀부터 아래를 다시 실행한다(**Execute Cell and Below**).
2. **셀은 여러 번 실행해도 같은 결과가 나오게 쓴다.** 처음 값을 정하는 코드와 바꾸는 코드를 한 셀에 둔다. 변수를 자기 자신으로 덮어쓰지 않는다.
3. **셀을 지웠으면 재시작한다.** 지운 셀이 만든 변수가 남아 있지 않은지 확인한다.
4. **실패해 본 셀은 지우고, 알게 된 것은 Markdown으로 남긴다.** 오류가 나는 셀은 "모두 실행"을 막는다.
5. **실행 번호가 차례대로가 아니면 의심한다.** 남이 준 노트북이든 내 노트북이든.
6. **커밋 전, 공유 전, 판단 전에 "재시작 후 모두 실행"을 한다.**
7. **노트북이 길어지면 코드를 함수와 모듈로 옮긴다**(9.6). 함수 안의 변수는 커널에 남지 않는다.

## 9.5 매직 명령과 셸 명령

### 9.5.1 매직 명령이란

9.4.5에서 `%whos`를 썼다. `%`로 시작하는 이런 명령을 **매직 명령**(magic command)이라고 한다. 파이썬 문법이 아니라 **IPython**(9.1.5)이 더한 기능이다. 커널이 셀을 파이썬에 넘기기 전에 IPython이 먼저 `%`로 시작하는 줄을 찾아 처리한다. 그래서 노트북에서는 동작하지만, 같은 줄을 `.py` 파일에 쓰면 `SyntaxError`가 난다.

| 모양 | 이름 | 적용 범위 | 예 |
|---|---|---|---|
| `%이름` | 줄 매직(line magic) | 그 줄 | `%whos`, `%time 식`, `%pip install 패키지` |
| `%%이름` | 셀 매직(cell magic) | **셀 전체**. 셀의 첫 줄에 써야 한다 | `%%time`, `%%writefile 파일` |

쓸 수 있는 매직 명령의 목록은 `%lsmagic`으로 본다. 매직 명령이나 함수 뒤에 `?`를 붙여 실행하면 도움말이 나온다. 2.2에서 `--help`로 명령의 사용법을 찾았듯이, 노트북에서는 `?`로 찾는다.

```python
%time?
```

```python
to_int?
```

앞의 것은 `%time`의 설명을, 뒤의 것은 9.3.4에서 만든 `to_int()`의 정의와 독스트링을 보여 준다. VS Code는 이 내용을 셀 출력이나 따로 열리는 창에 보여 준다. `??`를 붙이면 소스 코드까지 보여 준다. 함수에 독스트링을 쓰는 이유가 여기서도 하나 더 생긴다.

이 절에서 다루는 매직 명령은 노트북을 쓰다 보면 반드시 만나는 것들이다. 그 밖의 것은 필요할 때 `%lsmagic`과 `?`로 찾는다.

### 9.5.2 `%pip install`이 `!pip install`보다 안전한 이유

노트북에서 패키지를 설치하는 셀로 인터넷에서 흔히 보는 것은 두 가지다.

```python
!pip install rich
```

```python
%pip install rich
```

생김새는 비슷하지만 **설치되는 곳이 다를 수 있다.**

- **`!pip install`** — `!` 뒤의 글자를 **셸 명령**으로 실행한다(9.5.3). 터미널에 `pip install rich`를 입력한 것과 같다. 어느 `pip`가 실행될지는 셸이 `PATH`에서 찾는 순서에 달려 있다(3.4.2). 커널의 파이썬과 상관이 없다.
- **`%pip install`** — IPython이 **커널을 실행 중인 파이썬**(`sys.executable`)으로 `-m pip install`을 실행한다. 기초 과정 9.1.6에서 `pip` 대신 `python -m pip`를 쓰자고 했던 것과 같은 이유로, 항상 커널의 파이썬에 설치된다.

둘이 달라지는 예를 보자. 9.2.5의 상자처럼 JupyterLab을 한 곳(예를 들어 pipx로 만든 전용 환경)에만 설치해 두고, 이 프로젝트의 `.venv`를 커널로 등록해서 쓴다고 하자. 노트북에서 다음 두 셀을 실행하면 이렇게 나온다.

```python
!pip --version
```

```
pip 26.2.2 from /Users/jinyoung/.local/pipx/venvs/jupyterlab/lib/python3.13/site-packages/pip (python 3.13)
```

```python
%pip --version
```

```
pip 26.2.2 from /Users/jinyoung/devtools-lab/ch09/practice/ledger/.venv/lib/python3.13/site-packages/pip (python 3.13)
Note: you may need to restart the kernel to use updated packages.
```

`!pip`는 JupyterLab이 설치된 환경의 `pip`이고, `%pip`는 커널(`.venv`)의 `pip`이다. 이 상태에서 `!pip install rich`를 하면 설치는 성공했다고 나오지만, 노트북에서 `import rich`를 하면 `ModuleNotFoundError`가 난다. 기초 과정 9.2.6의 "설치했는데 `import`가 안 된다"가 노트북에서 일어나는 것이다. `%pip`로 설치하면 이런 일이 없다. 커널의 파이썬이 곧 `%pip`가 쓰는 파이썬이기 때문이다.

이 장처럼 VS Code에서 프로젝트의 `.venv`를 커널로 쓰면 `!pip`도 대개 `.venv`의 `pip`를 찾는다. VS Code가 커널을 띄울 때 그 환경을 켜 주기 때문이다. 그래도 **노트북에서는 `%pip`를 쓴다**고 정해 두면 환경이 어떻든 걱정할 필요가 없다. 매직 명령이 아닌 방법이 필요하면 `!{sys.executable} -m pip install rich`처럼 커널의 파이썬을 직접 적는다(`{}`는 9.5.3).

`%pip`가 붙이는 마지막 줄 `Note: you may need to restart the kernel to use updated packages.`도 읽어 둔다. 이미 import한 패키지를 새 버전으로 바꿨다면 커널을 다시 시작해야 새 버전이 쓰인다. 처음 설치한 패키지는 대개 바로 import된다.

> **설치 셀을 노트북에 남겨 두지 않는다**
> `%pip install` 셀이 노트북에 남아 있으면 "모두 실행"할 때마다 설치를 시도한다. 그리고 이 노트북에 무엇이 필요한지가 셀 사이에 흩어진다. 노트북에서 설치해 보고 계속 쓰기로 했다면 `requirements.txt`나 `requirements-dev.txt`(9.2.6)에 적고 설치 셀은 지운다. 남이 이 프로젝트를 받으면 노트북을 열기 전에 파일로 한 번에 설치할 수 있다. 9.8의 클라우드 노트북은 예외다. 세션마다 환경이 새로 만들어지므로 설치 셀을 맨 위에 두는 것이 보통이다.

### 9.5.3 `!`로 셸 명령 실행하기

셀에서 `!` 뒤에 쓴 줄은 셸 명령으로 실행되고, 출력이 셀 아래에 나온다. 노트북을 떠나지 않고 터미널 명령을 쓸 수 있다.

```python
!ls data
```

```
2026.csv
```

3.2.4에서 큰 CSV를 열기 전에 줄 수와 앞부분을 보았듯이, 노트북에서도 데이터를 읽기 전에 볼 수 있다.

```python
!wc -l data/2026.csv
!head -3 data/2026.csv
```

```
534 data/2026.csv
date,kind,category,memo,amount
2026-01-01,지출,주거,월세,"650,000"
2026-01-01,지출,식비,장보기,23100
```

`!` 명령의 출력은 파이썬 변수에 담을 수도 있고, 거꾸로 파이썬 변수를 명령에 넣을 수도 있다.

```python
files = !ls data
files
```

```
['2026.csv']
```

```python
name = "2026.csv"
!wc -l data/{name}
```

```
534 data/2026.csv
```

`{name}` 자리에 파이썬 변수 `name`의 값이 들어간다. 출력을 담은 `files`는 줄마다 문자열 하나인 리스트처럼 쓸 수 있다.

> **Windows에서 `!`는 cmd.exe로 실행된다**
> 위의 예는 macOS의 명령이다. Windows에서는 `!` 뒤의 명령이 **PowerShell이 아니라 cmd.exe**(명령 프롬프트)로 실행된다. 1장부터 PowerShell 7을 써 왔지만, 노트북의 `!`는 그 설정을 따르지 않는다. 그래서 `!ls`는 실패한다.
>
> ```
> 'ls'은(는) 내부 또는 외부 명령, 실행할 수 있는 프로그램, 또는
> 배치 파일이 아닙니다.
> ```
>
> cmd.exe의 명령(`!dir data`, `!type data\2026.csv`)은 되지만, PowerShell의 `Get-Content` 같은 cmdlet은 쓸 수 없다. 꼭 PowerShell 명령이 필요하면 `!pwsh -Command "Get-Content data/2026.csv -TotalCount 3"`처럼 PowerShell을 직접 불러야 한다.

macOS와 Windows가 이렇게 다르니, **남에게 줄 노트북이나 두 운영체제에서 같이 쓸 노트북에는 `!` 명령을 쓰지 않는 편이 낫다.** 2.6.5에서 와일드카드 처리를 운영체제에 상관없이 하려고 `pathlib`의 `glob()`을 썼던 것과 같은 판단이다. 파일 목록과 앞부분은 파이썬으로도 쉽게 볼 수 있다.

```python
from pathlib import Path

sorted(Path("data").glob("*.csv"))
```

```
[PosixPath('data/2026.csv')]
```

```python
with open("data/2026.csv", encoding="utf-8") as f:
    for _ in range(3):
        print(f.readline(), end="")
```

Windows에서는 `PosixPath` 대신 `WindowsPath`가 나온다. `!` 명령은 내 컴퓨터에서 잠깐 확인할 때 쓰고, 노트북에 남기는 코드는 파이썬으로 쓴다.

### 9.5.4 작업 폴더 — `!cd`와 `%cd`

9.3.3에서 노트북의 커널은 **노트북 파일이 있는 폴더**에서 시작한다고 했다. 그래서 `explore.ipynb`에서 `"data/2026.csv"`라고 쓸 수 있었다. VS Code는 설정 `jupyter.notebookFileRoot`(기본값 `${fileDirname}`, 곧 노트북 파일의 폴더)로, JupyterLab은 노트북이 있는 폴더로 커널을 시작한다. 터미널에서 프로그램을 실행할 때는 "터미널이 있는 폴더"가 기준이었던 것(기초 과정 7장)과 다르다.

작업 폴더를 바꾸려고 `!cd`를 쓰면 생각대로 되지 않는다.

```python
!cd data
!pwd
```

```
/Users/jinyoung/devtools-lab/ch09/practice/ledger
```

`!` 명령은 **줄마다 새 셸**을 띄워 실행하고 끝낸다. `!cd data`는 그 셸 안에서만 폴더를 옮기고 셸과 함께 사라진다. 커널의 작업 폴더는 그대로다. 3.4.3과 3.5.1에서 본 대로, 셸에서 실행한 프로그램은 자식 프로세스이고 자식은 부모의 상태(작업 폴더, 환경 변수)를 바꾸지 못한다. 여기서는 커널이 부모, `!`가 띄운 셸이 자식이다.

커널의 작업 폴더를 바꾸는 것은 `%cd`다.

```python
%cd data
```

```
/Users/jinyoung/devtools-lab/ch09/practice/ledger/data
```

이번에는 정말 바뀌었다. 그런데 이제 위쪽 셀의 `Path("data/2026.csv")`가 `data/data/2026.csv`를 가리키게 되어 파일을 찾지 못한다. `%cd`는 **커널에 남는 상태**를 하나 더 만든다. 9.4의 숨은 상태다. 셀을 위에서부터 다시 실행하면 `%cd data`를 지나간 뒤의 셀들이 모두 다른 폴더를 기준으로 돈다. 노트북에서는 작업 폴더를 바꾸지 않고, 경로를 제대로 쓰는 편이 안전하다. `%cd ..`로 되돌려 둔다. 지금 커널의 작업 폴더는 `%pwd`나 `Path.cwd()`로 확인한다.

> **노트북을 하위 폴더에 둘 때**
> 노트북이 많아지면 프로젝트 안에 `notebooks/` 폴더를 만들어 모아 두기도 한다. 그러면 커널이 `notebooks/`에서 시작하므로 데이터 경로가 `"../data/2026.csv"`가 된다. 노트북 위치에 따라 경로가 달라지는 것이 번거로우면 맨 위 셀에서 프로젝트 폴더를 변수로 정해 두고(`ROOT = Path.cwd().parent`), 경로는 모두 `ROOT / "data" / "2026.csv"`처럼 쓴다. 9.6에서 모듈을 import할 때도 노트북과 모듈의 위치 관계가 중요해진다. 이 장에서는 노트북을 프로젝트 폴더 바로 아래에 둔다.

### 9.5.5 시간 재기 — `%time`, `%timeit`

코드가 얼마나 걸리는지 재는 매직 명령이다.

**`%time`과 `%%time`** — 한 번 실행하고 걸린 시간을 보여 준다. `%time`은 그 줄만, `%%time`은 셀 전체를 잰다.

```python
%%time
import csv
with open("data/2026.csv", encoding="utf-8", newline="") as f:
    rows = list(csv.DictReader(f))
```

```
CPU times: user 2.04 ms, sys: 0 ns, total: 2.04 ms
Wall time: 1.76 ms
```

`Wall time`은 벽시계로 잰 실제 시간이다. `CPU times`는 CPU가 이 일에 실제로 계산한 시간이다(Windows에서는 `CPU times: total: ...`만 나온다). 파일을 읽거나 네트워크 응답을 기다리는 동안 CPU는 놀고 있으므로, 기다림이 많은 일은 `Wall time`이 `CPU times`보다 훨씬 길다. LLM API를 부르는 셀을 `%%time`으로 재 보면 `Wall time`이 몇 초인데 `CPU times`는 몇 밀리초일 것이다. 중급 과정 7장의 비동기가 이 기다림을 다룬다.

**`%timeit`** — 아주 짧은 코드를 **여러 번** 실행해서 평균을 낸다. 한 번 재면 운에 따라 들쭉날쭉하기 때문이다.

```python
%timeit to_int("650,000")
```

```
86.4 ns ± 4.11 ns per loop (mean ± std. dev. of 7 runs, 10,000,000 loops each)
```

```python
%timeit int("650000")
```

```
41.5 ns ± 3.1 ns per loop (mean ± std. dev. of 7 runs, 10,000,000 loops each)
```

천만 번씩 일곱 묶음을 실행한 평균과 표준 편차다. 쉼표를 지우는 일 때문에 두 배쯤 느리다는 것을 알 수 있다. 숫자는 컴퓨터마다 다르다. 이 숫자를 보고 판단할 것은 "533줄을 바꾸는 데 수십 마이크로초, 걱정할 필요 없다"이다. 빠르게 만들기 전에 정말 느린지부터 재 보는 습관을 들인다.

`%timeit`은 코드를 수백만 번 실행할 수 있으므로 **오래 걸리는 코드나 무언가를 바꾸는 코드에는 쓰지 않는다.** 파일에 쓰거나, API를 부르거나, 9.4.3처럼 변수에 더하는 코드를 `%timeit`하면 그 일이 수백만 번 일어난다. 오래 걸리는 코드는 `%time`으로 한 번만 잰다.

### 9.5.6 셀 내용을 파일로 — `%%writefile`

`%%writefile 파일이름`을 셀의 첫 줄에 쓰면, 셀의 나머지 내용을 실행하지 않고 **그 파일에 쓴다.**

```python
%%writefile hello.py
print("안녕")
```

```
Writing hello.py
```

같은 셀을 다시 실행하면 `Overwriting hello.py`가 나온다. **묻지 않고 덮어쓴다.** 같은 이름의 파일이 이미 있으면 그 내용은 사라진다. `-a` 옵션(`%%writefile -a 파일`)을 주면 덮어쓰지 않고 끝에 덧붙인다.

만든 파일은 `!python hello.py`로 실행할 수도 있고, `%run hello.py`로 실행할 수도 있다. `%run`은 그 파일을 **이 커널 안에서** 실행하므로, 파일이 만든 변수가 커널에 남는다. 편하지만 9.4의 숨은 상태를 만드는 또 하나의 길이다.

`%%writefile`은 노트북 말고는 파일을 만들 방법이 없을 때(9.8의 클라우드 노트북) 쓸모가 있다. 내 컴퓨터에서 `.py` 파일을 만들 때는 VS Code에서 직접 만든다. 편집기의 자동 완성, 포맷, 오류 표시를 쓸 수 있고, 노트북의 셀을 다시 실행해서 고친 파일을 실수로 덮어쓰는 일도 없다. 실습이 끝나면 `hello.py`는 지운다.

### 9.5.7 고친 모듈 다시 불러오기 — `%autoreload`

9.6에서 노트북의 함수를 `.py` 모듈로 옮기고 노트북에서 import해서 쓴다. 그때 만나는 문제를 미리 보자.

파이썬은 같은 모듈을 두 번 import하지 않는다. 처음 import할 때 모듈을 읽어 `sys.modules`에 넣어 두고, 다음부터는 거기 있는 것을 그대로 쓴다. 스크립트는 실행할 때마다 새로 시작하니 문제가 없다. 그런데 노트북의 커널은 계속 떠 있다. 그래서 **모듈 파일을 고친 뒤 노트북에서 import 셀을 다시 실행해도, 고치기 전의 모듈이 그대로 쓰인다.** 해결 방법은 두 가지다.

1. **커널을 다시 시작한다.** 확실하지만, 위의 셀을 모두 다시 실행해야 한다.
2. **`autoreload` 확장을 켠다.** 노트북 맨 위의 셀에 다음 두 줄을 넣는다.

```python
%load_ext autoreload
%autoreload 2
```

`%load_ext autoreload`는 IPython의 `autoreload` 확장을 불러오고, `%autoreload 2`는 "셀을 실행하기 전마다, 바뀐 모듈을 다시 불러오라"는 뜻이다. 이렇게 해 두면 VS Code에서 모듈 파일을 고쳐 저장한 뒤 노트북의 셀을 실행하면 고친 코드가 쓰인다. 9.6.3에서 직접 해 본다.

`autoreload`가 언제나 완벽하지는 않다. 클래스의 구조를 크게 바꾸거나 모듈에서 이름을 지운 경우에는 옛 것이 남아 이상하게 동작할 수 있다. 결과가 이상하면 망설이지 말고 커널을 다시 시작한다(9.4.4).

### 9.5.8 노트북에서는 `await`를 바로 쓴다

중급 과정 7장에서 배울 비동기 코드를 노트북에서 실행할 때 알아 둘 것이 있다. 지금은 문법을 몰라도 된다. "노트북과 스크립트가 다르다"는 점만 본다.

```python
import asyncio

async def hello():
    await asyncio.sleep(0.1)
    return "안녕"

asyncio.run(hello())
```

```
RuntimeError: asyncio.run() cannot be called from a running event loop
```

스크립트에서는 비동기 함수를 `asyncio.run()`으로 실행한다. 그런데 노트북에서는 같은 코드가 오류를 낸다. 메시지는 "이미 돌고 있는 이벤트 루프 안에서는 `asyncio.run()`을 부를 수 없다"는 뜻이다. 커널은 화면과 메시지를 주고받기 위해 **이미 이벤트 루프를 돌리고 있다.** 그래서 노트북에서는 `asyncio.run()` 없이 `await`를 셀에서 바로 쓴다.

```python
await hello()
```

```
'안녕'
```

`.py` 파일에서는 함수 밖에서 `await`를 쓰면 `SyntaxError`다. 노트북에서만 되는 일이다. 그래서 노트북에서 비동기 코드를 실험한 뒤 스크립트로 옮길 때는 `await hello()`를 `asyncio.run(hello())`로 바꿔야 한다. 거꾸로 인터넷의 스크립트 예제를 노트북에 붙여 넣었다가 위의 `RuntimeError`를 만나면, `asyncio.run(...)`을 `await ...`로 바꾼다. "LLM API 활용"에서 비동기 클라이언트로 여러 요청을 동시에 보낼 때 이 차이를 다시 만난다.

### 실습 9-5. 매직 명령과 셸 명령

결과는 `~/devtools-lab/ch09/magic.md`에 적는다. 이 실습의 셀은 `explore.ipynb`가 아니라 새 노트북 `scratch.ipynb`에서 한다(커널은 `.venv`). 실습이 끝나면 `scratch.ipynb`와 `hello.py`는 지운다.

## 9.6 노트북에서 프로그램으로

### 9.6.1 노트북이 너무 길어졌다는 신호

탐색이 길어지면 노트북은 금방 수십 개의 셀로 늘어난다. 다음과 같은 일이 생기면 정리할 때가 된 것이다.

- **같은 코드를 여러 셀에 복사해 쓴다.** 9.3.6의 분류별 합계와 월별 합계는 `if row["kind"] == "지출":`부터 거의 같다. 실습 9-3에서 9월만 따로 계산할 때 또 복사했을 것이다. 한 곳을 고치면 나머지도 찾아 고쳐야 한다.
- **"재시작 후 모두 실행"이 두렵다.** 끝까지 도는지 자신이 없거나, 너무 오래 걸린다.
- **변수 이름이 `rows2`, `spend_new`, `tmp`처럼 늘어난다.** 이름만 봐서는 어느 것이 최신인지 모른다. 9.4.5에서 본 `row`, `total` 같은 반복 변수도 커널에 쌓인다.
- **다른 노트북에서도 같은 계산이 필요하다.** 노트북은 import할 수 없다(9.6.6).
- **같은 계산을 정기적으로 돌려야 한다.** 매달 새 가계부 파일이 생긴다면, 그때마다 노트북을 열어 셀을 누를 것인가?
- **변경을 리뷰하기 어렵다.** 9.7에서 볼 것처럼 노트북의 diff는 읽기 힘들다.

정리의 방향은 정해져 있다. **계산은 함수로 만들어 `.py` 모듈로 옮기고, 노트북에는 그 함수를 불러 결과를 보고 설명하는 셀만 남긴다.** 9.1.4의 "답을 알게 된 것은 스크립트로"를 실행에 옮기는 것이다.

### 9.6.2 셀을 함수로 정리하기

먼저 노트북 안에서 셀을 함수로 바꾼다. 9.4.3에서 고친 분류별 합계 셀을 보자.

```python
spend = Counter()
for row in rows:
    if row["kind"] == "지출":
        spend[row["category"]] += to_int(row["amount"])

spend.most_common()
```

이것을 함수로 바꾼다. 입력(`rows`)은 매개변수로 받고, 결과는 `return`으로 돌려준다.

```python
def spending_by_category(rows):
    """분류별 지출 합계."""
    totals = Counter()
    for row in rows:
        if row["kind"] == "지출":
            totals[row["category"]] += to_int(row["amount"])
    return totals

spend = spending_by_category(rows)
spend.most_common()
```

결과는 같다. 그런데 몇 가지가 좋아졌다.

- **여러 번 실행해도 같다.** `totals`는 함수가 불릴 때마다 새로 만들어진다. 9.4.3의 두 배 문제가 생길 수 없다.
- **반복 변수가 커널에 남지 않는다.** `row`는 함수 안의 지역 변수라서 함수가 끝나면 사라진다. `%whos`로 확인해 보면 `row`가 없다(앞에서 만든 것이 남아 있다면 커널을 다시 시작한다).
- **다른 데이터에 다시 쓸 수 있다.** 9월 거래만 고른 리스트를 넘기면 9월의 분류별 합계가 나온다. 실습 9-3에서 복사했던 코드가 필요 없다.

```python
september = [row for row in rows if row["date"].startswith("2026-09")]
spending_by_category(september).most_common(3)
```

월별 합계와 파일 읽기도 같은 식으로 함수로 만든다. 함수가 노트북 안에 있는 동안은 함수를 고치고 그 셀을 다시 실행하는 것만으로 바로 시험할 수 있다. 함수의 모양이 어느 정도 정해지면 다음 단계로 간다.

### 9.6.3 `.py` 모듈로 옮기고 노트북에서 import하기

VS Code에서 `practice/ledger`에 `ledger_tools.py`를 만들고, 노트북에서 정리한 함수들을 옮긴다. 터미널에서 실행할 때 쓸 `main()`(9.6.4)도 함께 넣었다.

```python
"""가계부 CSV를 탐색할 때 쓰는 함수 모음.

노트북(explore.ipynb)에서 import해서 쓰고, 터미널에서 요약을 볼 때도 쓴다.
    python ledger_tools.py data/2026.csv
"""

import csv
import sys
from collections import Counter
from pathlib import Path


def load_rows(path):
    """가계부 CSV를 읽어 줄마다 딕셔너리 하나로 된 리스트를 돌려준다."""
    with Path(path).open(encoding="utf-8", newline="") as f:
        return list(csv.DictReader(f))


def to_int(text):
    """'12,000'처럼 쉼표가 든 금액도 정수로 바꾼다.

    탐색용이라 쉼표의 위치는 검사하지 않는다(기초 과정 10장의 storage.py와 다르다).
    """
    return int(text.replace(",", ""))


def spending_by_category(rows):
    """분류별 지출 합계."""
    totals = Counter()
    for row in rows:
        if row["kind"] == "지출":
            totals[row["category"]] += to_int(row["amount"])
    return totals


def spending_by_month(rows):
    """월별 지출 합계. 키는 '2026-01' 모양이다."""
    totals = Counter()
    for row in rows:
        if row["kind"] == "지출":
            totals[row["date"][:7]] += to_int(row["amount"])
    return totals


def main():
    if len(sys.argv) != 2:
        sys.exit("사용법: python ledger_tools.py 가계부.csv")
    rows = load_rows(sys.argv[1])
    print(f"거래 {len(rows)}건")
    print("[분류별 지출]")
    for category, total in spending_by_category(rows).most_common():
        print(f"  {category:<4} {total:>12,}원")
    print("[월별 지출]")
    for month, total in sorted(spending_by_month(rows).items()):
        print(f"  {month} {total:>12,}원")


if __name__ == "__main__":
    main()
```

옮기면서 한 일을 짚어 두자.

- **import를 맨 위로 모았다.** 노트북에서는 `import csv`, `from collections import Counter`가 서로 다른 셀에 흩어져 있었다. 모듈에서는 맨 위에 모은다.
- **9.3.4의 상자에서 말한 한계를 독스트링에 적었다.** `to_int()`는 쉼표의 위치를 검사하지 않는다. 노트북에서는 내가 알고 있으면 충분했지만, 모듈은 남이(또는 석 달 뒤의 내가) 가져다 쓴다.
- **노트북에서만 되는 것은 가져오지 않았다.** `display()`, `%whos` 같은 매직 명령, 마지막 줄의 식(`spend.most_common()`)은 `.py` 파일에서 아무 일도 하지 않거나 오류가 난다.

이제 노트북을 정리한다. 맨 위 Markdown 셀 바로 아래에 9.5.7의 `autoreload` 셀을 넣고, 그 아래 셀에서 모듈을 import한다.

**`autoreload`로 모듈 고치기**

모듈에 함수를 하나 더해 보자. 지출 내용(`memo`)별 합계에서 큰 것을 찾는 함수다(실습 9-3의 4번). `ledger_tools.py`의 `spending_by_category()` 위에 다음을 넣고 저장한다.

```python
def top_memos(rows, n=5):
    """지출 내용(memo)별 합계에서 큰 것부터 n개."""
    totals = Counter()
    for row in rows:
        if row["kind"] == "지출":
            totals[row["memo"]] += to_int(row["amount"])
    return totals.most_common(n)
```

`get_ipython()`은 IPython 안에서만 있는 함수라 일반 파이썬에서는 오류가 난다. 매직 명령 줄을 지우고 실행하면 이번에는 오류 없이 끝난다. 그런데 출력은 다음이 전부다.

```
2026-01  1,856,300원
2026-02  1,411,700원
2026-03  1,623,200원
2026-04  1,438,300원
2026-05  1,585,900원
2026-06  1,727,700원
2026-07  1,535,100원
2026-08  1,833,500원
2026-09  2,016,200원
2026-10  1,820,400원
```

`print()`로 찍은 월별 합계만 나왔다. `len(rows)`, `rows[:3]`, `spend.most_common()`, `top_memos(rows)` 같은 마지막 줄의 식은 노트북에서는 출력되었지만(9.3.3), 스크립트에서는 계산만 하고 버려진다. 거래 건수도, 분류별 합계도, 저축률도 보이지 않는다.

그래서 `--to script`로 내보낸 파일은 **프로그램이 아니라 출발점**이다. 노트북의 코드를 한 파일에 모아 보거나, 프로그램으로 옮길 때 복사할 재료로 쓴다. 노트북을 프로그램으로 만드는 것은 9.6.3처럼 함수를 골라 모듈로 옮기는 일이고, 사람이 판단해야 하는 일이다. `explore.py`는 지운다.

**HTML로 내보내기**

```
jupyter nbconvert --to html explore.ipynb
```

`explore.html`이 생긴다. 브라우저로 열면(macOS `open explore.html`, Windows `Invoke-Item explore.html`) 노트북이 코드·설명·출력 그대로 보인다. 파이썬도 Jupyter도 없는 사람에게 결과를 보여 줄 때 쓴다. HTML에는 **출력이 모두 들어 있다**는 점을 잊지 않는다. 출력에 개인정보나 비밀 값이 있으면 그것도 함께 간다(9.7.4).

**새 커널로 처음부터 실행해서 검증하기**

nbconvert의 가장 쓸모 있는 옵션은 `--execute`다. 노트북을 바꾸기 전에 **새 커널을 띄워 위에서부터 모든 셀을 실행**한다. 9.4.4의 "재시작 후 모두 실행"을 화면 없이 터미널에서 하는 것이다.

```
jupyter nbconvert --execute --to html explore.ipynb
```

```
[NbConvertApp] Converting notebook explore.ipynb to html
[NbConvertApp] Writing 287158 bytes to explore.html
```

모든 셀이 성공하면 새로 계산한 출력이 든 HTML이 만들어지고 종료 코드 0으로 끝난다. 어느 셀에서 오류가 나면 그 셀의 코드와 오류를 보여 주고, HTML을 만들지 않고 종료 코드 1로 끝난다. 9.4.4에서 지운 `int()` 셀이 남아 있었다면 다음과 같이 나왔을 것이다(줄임).

```
[NbConvertApp] Converting notebook explore.ipynb to html
Traceback (most recent call last):
...
nbclient.exceptions.CellExecutionError: An error occurred while executing the following cell:
------------------

------------------
...
ValueError: invalid literal for int() with base 10: '650,000'
```

트레이스백이 길지만 3장에서 익힌 대로 **맨 아래부터** 읽는다. 어느 셀에서(`------------------` 사이) 무슨 오류가 났는지가 나와 있다. 종료 코드로 성공과 실패를 알려 주므로 3.3.2의 `&&`와 함께 쓸 수 있다.

```
jupyter nbconvert --execute --to html explore.ipynb && echo "노트북 검증 통과"
```

같은 명령을 8.9의 GitHub Actions 워크플로에 넣으면 푸시할 때마다 노트북이 처음부터 끝까지 도는지 GitHub가 확인해 준다. 내 컴퓨터의 커널에 숨은 상태가 있어도 GitHub의 새 환경은 속지 않는다.

`--execute`는 노트북을 **정말로 실행한다**는 점을 기억한다. 노트북에 파일을 지우거나, API를 부르거나, 메일을 보내는 셀이 있으면 그 일이 일어난다. 남이 준 노트북을 `--execute`로 검증하기 전에는 먼저 읽어 본다.

> **VS Code에서 내보내기**
> 노트북 도구 막대의 **…** → **Export**(내보내기)에서 **Python Script**(Python 스크립트), **HTML**, **PDF**를 고를 수 있다. Python 스크립트는 VS Code가 직접 만들고, HTML과 PDF는 커널의 환경에 설치된 nbconvert를 쓴다. 그래서 `ipykernel`만 있는 환경에서는 HTML 내보내기가 nbconvert를 설치하라는 안내를 띄운다. PDF는 LaTeX라는 별도의 프로그램이 더 필요해서 이 과정에서는 다루지 않는다. 브라우저에서 HTML을 연 뒤 인쇄 기능으로 PDF로 저장하는 편이 쉽다.

### 9.6.6 노트북은 import하지 않는다

`explore.ipynb`에 쓸 만한 함수가 있을 때, 다른 노트북이나 스크립트에서 `import explore`로 가져다 쓸 수는 없다. 파이썬의 `import`는 `.py` 파일을 찾지 `.ipynb`를 읽지 않는다. 노트북을 import하게 해 주는 도구도 있고, `%run explore.ipynb`로 다른 노트북을 통째로 실행할 수도 있지만 권하지 않는다. 노트북 전체가 실행되면서 그 노트북의 출력과 변수가 지금 커널에 쏟아지고(9.4의 숨은 상태), 노트북 하나를 고칠 때 다른 노트북이 깨진다.

규칙은 단순하다. **여러 곳에서 쓸 코드는 `.py`에 둔다.** 노트북은 언제나 import하는 쪽이고, import되는 쪽이 아니다. 이 장의 `explore.ipynb`와 `ledger_tools.py`의 관계가 그 모양이다.

> **AI 코딩 도구와 노트북**
> Copilot·Claude Code 같은 AI 코딩 도구도 노트북의 셀을 쓰고 고친다. VS Code의 노트북에서도 인라인 제안과 채팅을 쓸 수 있다(4.6). 이때 이 절의 내용이 그대로 적용된다.
>
> - **AI가 만든 셀은 재시작 후 모두 실행으로 확인한다.** AI는 커널에 지금 무엇이 있는지 모르고 셀을 쓰거나, 반대로 내 커널에만 있는 변수에 기대어 쓰기도 한다.
> - **계산은 `.py` 모듈에서 고치게 한다.** 노트북의 diff는 읽기 어렵다(9.7). AI에게 `ledger_tools.py`의 함수를 고치게 하면 4.6.3처럼 비교 화면에서 검토하기 쉽고, 7장의 방법으로 받아들일 부분만 고를 수 있다. 노트북은 결과를 확인하는 데 쓴다.
> - **출력도 AI에게 간다.** AI 도구에 노트북을 통째로 보여 주면 셀의 출력, 곧 데이터의 내용도 함께 보낸다. 개인정보가 든 데이터를 탐색한 노트북이라면 출력을 지우고 보여 준다(9.7.3).

| 무엇이 | 왜 성가신가 |
|---|---|
| **JSON이다** | 셀 하나가 딕셔너리이고, 코드는 줄마다 따옴표와 `\n`이 붙은 문자열이다. `"`는 `\"`로 적힌다. 읽기 어렵다 |
| **실행 번호** | 코드가 그대로여도 다시 실행할 때마다 바뀐다 |
| **출력** | 코드가 그대로여도 데이터가 바뀌면 바뀐다. 이후 과정에서 그래프를 그리면 그림이 수십 KB의 글자(base64)로 출력에 들어가서, diff 한 화면이 알아볼 수 없는 글자로 가득 찬다 |
| **메타데이터** | 노트북의 `language_info`에는 마지막으로 실행한 파이썬의 버전이 적힌다. 3.13.2인 사람과 3.13.9인 사람이 번갈아 실행하면 그때마다 바뀐다. 편집기와 확장의 버전에 따라 셀의 `metadata`에 무언가를 적기도 한다 |
| **충돌** | 두 사람이 같은 노트북을 고치면, 둘 다 실행 번호와 출력을 바꿨으므로 코드가 겹치지 않아도 충돌이 나기 쉽다. 충돌 표시(`<<<<<<<`)가 JSON 사이에 끼면 노트북이 열리지 않는다(9.7.6) |

8장에서 PR의 Files changed 화면으로 리뷰하는 법을 익혔다. 그 화면에 이런 diff가 나온다고 생각해 보자. 리뷰어는 무엇이 바뀌었는지 찾느라 시간을 다 쓴다. 이 변경은 커밋하지 않고 되돌린다.

```

```

### 9.7.3 출력을 지우고 커밋하기

해결 방법의 핵심은 **실행 번호와 출력을 저장소에 넣지 않는 것**이다. 그러면 저장소의 노트북에는 코드와 Markdown만 남고, diff에는 정말로 바뀐 셀만 나온다. 방법은 세 가지가 있다.

1. **손으로 지우기** — 커밋하기 전에 도구 막대의 **Clear All Outputs**(모든 출력 지우기)를 누르고 저장한다. 간단하지만 잊기 쉽다. 잊으면 출력이 그대로 커밋된다.
2. **명령으로 지우기** — nbconvert로 출력을 지운다. 손으로 지우는 것과 같고, 역시 잊기 쉽다.

   ```
   jupyter nbconvert --clear-output --inplace explore.ipynb
   ```

3. **Git이 커밋할 때 자동으로 지우게 하기** — `nbstripout`이라는 도구를 Git의 **필터**로 등록한다. `git add`를 할 때마다 Git이 노트북을 nbstripout에 통과시켜 출력과 실행 번호를 뺀 내용을 저장소에 넣는다. **내 작업 폴더의 노트북은 그대로**다. 화면에서는 계속 출력을 보면서, 저장소에는 출력 없는 노트북만 들어간다.

이 과정에서는 3번을 쓴다. 사람이 기억해야 하는 일을 도구에 맡기는 것이다.

**nbstripout 설치와 설정**

가상환경에 설치하고, 노트북 도구이므로 `requirements-dev.txt`에 한 줄 더한다(9.2.6). 버전은 `python -m pip show nbstripout`으로 확인한 내 화면의 숫자로 적는다.

```
python -m pip install nbstripout
```

```
# 노트북으로 탐색할 때 쓰는 도구. 프로그램(ledger_tools.py)을 실행하는 데는 필요 없다.
ipykernel==7.4.0
jupyterlab==4.6.6
nbstripout==0.9.1
```

이 저장소에 필터를 설정한다.

```
nbstripout --install --attributes .gitattributes
```

이 명령은 두 가지를 한다.

**하나, 저장소 폴더에 `.gitattributes` 파일을 만든다.** 5.2.6에서 줄 끝 문자를 정할 때 쓴 그 파일이다. 어떤 파일에 어떤 필터를 쓸지 적는다.

```
# macOS
cat .gitattributes

# Windows
Get-Content .gitattributes
```

```
*.ipynb filter=nbstripout
*.zpln filter=nbstripout
*.ipynb diff=ipynb
```

`*.ipynb filter=nbstripout`은 "`.ipynb` 파일은 `nbstripout`이라는 필터를 거쳐 저장소에 넣는다", `*.ipynb diff=ipynb`는 "`.ipynb` 파일의 diff를 볼 때도 출력을 빼고 비교한다"는 뜻이다. `*.zpln`은 다른 노트북 도구(Zeppelin)의 파일로, 이 과정에서는 쓰지 않는다.

**둘, 이 저장소의 `.git/config`에 필터가 실제로 할 일을 적는다.** `.gitattributes`에는 필터의 **이름**만 있고, 그 이름으로 무엇을 실행할지는 `.git/config`에 있다.

```
git config --get-regexp nbstripout
```

```
filter.nbstripout.clean "/Users/jinyoung/devtools-lab/ch09/practice/ledger/.venv/bin/python" -m nbstripout
filter.nbstripout.smudge cat
filter.nbstripout.required true
diff.ipynb.textconv "/Users/jinyoung/devtools-lab/ch09/practice/ledger/.venv/bin/python" -m nbstripout -t
```

- `clean` — 작업 폴더의 파일을 저장소에 넣을 때(`git add`) 거치는 명령. 가상환경의 파이썬으로 nbstripout을 실행한다. **경로가 절대 경로로 적혀 있다**는 데 주목한다(아래 상자).
- `smudge` — 저장소의 파일을 작업 폴더로 꺼낼 때(`git checkout`, `git restore`) 거치는 명령. `cat`은 아무것도 바꾸지 않고 그대로 내보낸다.
- `required true` — 필터가 실패하면 `git add`도 실패하게 한다. 필터가 조용히 건너뛰어져 출력이 커밋되는 것을 막는다.
- `textconv` — `git diff`로 비교할 때 양쪽을 이 명령에 통과시킨 뒤 비교한다.

설정이 되었는지는 `nbstripout --status`로도 확인할 수 있다.

  diff= "/Users/jinyoung/devtools-lab/ch09/practice/ledger/.venv/bin/python" -m nbstripout -t
  extrakeys=

  *.ipynb: filter: nbstripout

```

**이제 무엇이 달라졌나**

9.7.2를 다시 해 보자. 분류별 합계 셀을 고치지 않고 다시 실행하고 저장한다.

```

```

아무것도 나오지 않는다. 실행 번호와 출력만 바뀐 것은 Git에게 "바뀐 것 없음"이다. 이번에는 `most_common()`을 `most_common(3)`으로 고치고 실행해 저장한다.

```
git diff
```

```diff
diff --git a/explore.ipynb b/explore.ipynb
index d792521..f4266bc 100644
--- a/explore.ipynb
+++ b/explore.ipynb
@@ -60,7 +60,7 @@
    "outputs": [],
    "source": [
     "spend = spending_by_category(rows)\n",
-    "spend.most_common()"
+    "spend.most_common(3)"
    ]
   },
   {
```

내가 고친 한 줄만 나온다. 리뷰할 만한 diff가 되었다. 이 변경은 `git restore explore.ipynb`로 되돌린다.

그런데 되돌린 뒤 VS Code의 노트북을 보면 **출력이 모두 사라져 있다.** `git restore`는 저장소의 노트북, 곧 출력이 없는 노트북으로 작업 폴더의 파일을 덮어쓰기 때문이다(`smudge`는 `cat`이라 출력을 되살리지 못한다). `git switch`로 브랜치를 옮길 때도 노트북이 바뀌면 같은 일이 일어난다. 놀랄 일은 아니다. 노트북을 다시 실행하면 출력이 돌아온다. 출력은 언제든 다시 만들 수 있다는 것, 그래서 저장소에 넣지 않는다는 것이 이 방법의 전제다.

> **nbstripout 설정은 저장소를 따라가지 않는다**
> `.gitattributes`는 커밋되어 저장소를 받는 사람에게 간다. 그런데 필터가 실제로 실행할 명령은 `.git/config`에 있고, `.git/config`는 커밋되지 않는다. 8.1.5에서 본 대로 `git clone`은 `.git/config`를 가져오지 않는다. 그래서 저장소를 받은 사람이 `nbstripout --install`을 하지 않으면, Git은 정의되지 않은 필터를 **조용히 무시하고** 출력이 든 노트북을 그대로 커밋한다. 경고도 나오지 않는다.
>
> 그래서 `README.md`의 준비 방법에 적어 둔다. 이 프로젝트의 `README.md`에 다음 절을 더하고 커밋한다.
>
> ````markdown
> ## 준비
>
> ```
> # macOS
> python3 -m venv .venv
> source .venv/bin/activate
>
> # Windows
> python -m venv .venv
> .venv\Scripts\Activate.ps1
>
> # 공통(가상환경을 켠 뒤)
> python -m pip install -r requirements-dev.txt
> nbstripout --install --attributes .gitattributes
> ```
>
> 노트북(`*.ipynb`)은 출력을 지운 채 커밋된다(nbstripout). 클론한 뒤 위의 마지막 명령을 꼭 실행한다.
> ````

> **가상환경을 옮기거나 다시 만들면**
> `.git/config`의 필터에는 가상환경 파이썬의 **절대 경로**가 적혀 있다. 프로젝트 폴더를 다른 곳으로 옮기거나 `.venv`를 지우고 다시 만들어서 그 경로에 파이썬이 없으면, 노트북을 `git add`할 때 다음과 같이 실패한다(`required true` 때문이다). 문구는 운영체제에 따라 조금 다르다.
>
> ```
> "/Users/jinyoung/.../.venv/bin/python" -m nbstripout: ... No such file or directory
> error: external filter '"/Users/jinyoung/.../.venv/bin/python" -m nbstripout' failed 127
> error: external filter '"/Users/jinyoung/.../.venv/bin/python" -m nbstripout' failed
> fatal: explore.ipynb: clean filter 'nbstripout' failed
> ```
>
> 가상환경을 켜고 `nbstripout --install --attributes .gitattributes`를 다시 실행하면 새 경로로 고쳐 적힌다. 실패해서 다행인 경우다. 필터가 조용히 건너뛰어졌다면 출력이 커밋되었을 것이다.

**출력을 남길까, 지울까**

출력을 지우는 것이 언제나 정답은 아니다. 두 방식을 비교하고 정한다.

| | 출력을 저장소에 넣는다 | 출력을 지우고 넣는다(nbstripout) |
|---|---|---|
| GitHub에서 노트북을 열면 | 결과까지 보인다. 보고서처럼 읽힌다 | 코드와 설명만 보인다. 결과를 보려면 받아서 실행해야 한다 |
| diff·리뷰 | 실행 번호와 출력 때문에 시끄럽다 | 고친 셀만 나온다 |
| 충돌 | 잦다 | 줄어든다 |
| 비밀 값·개인정보 | 출력에 찍힌 것이 저장소에 남는다 | 출력에 찍힌 것은 남지 않는다(소스에 쓴 것은 남는다, 9.7.4) |
| 저장소 크기 | 그래프가 많으면 커진다 | 작다 |
| 결과를 다시 만들 수 있나 | 저장된 결과가 "재시작 후 모두 실행"의 결과라는 보장이 없다 | 언제나 실행해서 만든다 |

이 과정에서는 **지우고 넣는 것을 기본으로 한다.** 결과를 보여 줘야 하면 9.6.5의 `jupyter nbconvert --execute --to html`로 새 커널에서 실행한 HTML을 만들어 따로 전한다. 그 HTML은 숨은 상태가 없는 결과라는 보장도 있다. 교재나 발표 자료처럼 출력이 꼭 저장소에 있어야 하는 노트북이 있다면 nbstripout의 옵션(노트북 메타데이터의 `"keep_output": true`, 명령의 `--keep-output`)으로 그 노트북만 예외로 둘 수 있다. 필요할 때 `nbstripout --help`로 찾아본다.

nbstripout은 검사 도구로도 쓸 수 있다. `nbstripout --verify explore.ipynb`는 파일을 바꾸지 않고, 지울 출력이 있으면 `Dry run: would have stripped explore.ipynb`를 출력하고 종료 코드 1로 끝난다. 8.9의 GitHub Actions에서 "출력이 남은 노트북이 올라오면 실패"하게 만드는 데 쓸 수 있다.

### 9.7.4 출력과 소스에 남는 비밀 값

8.3에서 비밀 값이 새는 길을 세 가지로 정리했다. 파일을 커밋하는 것, 코드에 직접 쓰는 것, 그리고 **출력에 남기는 것**이다. 스크립트에서 출력은 터미널에 잠깐 나왔다 사라지지만, 노트북에서는 **출력이 파일에 저장된다.** 노트북은 세 번째 길이 가장 넓게 열린 도구다.

미리 만들어 둔 `samples/leaky.ipynb`를 VS Code에서 열어 본다(`code ../samples/leaky.ipynb`). **실행하지 않는다.** 누군가 API 키가 잘 읽히는지 확인하려고 만든 노트북이다.

```
# API 연결 시험

[1]  import os

     key = os.environ["LEDGER_API_KEY"]
     key
     ─────────────
     'lk-demo-7f3a9c2e51b84d06a1c3'

[2]  print("요청 헤더:", {"Authorization": f"Bearer {key}"})
     ─────────────
     요청 헤더: {'Authorization': 'Bearer lk-demo-7f3a9c2e51b84d06a1c3'}

키가 제대로 읽히는 것을 확인했다.
```

코드만 보면 잘 쓴 노트북이다. 키를 코드에 직접 적지 않고 환경 변수에서 읽었다(8.3.2). 그런데 셀의 마지막 줄 `key`가 키의 값을 **출력**했고(9.3.3), 둘째 셀도 요청 헤더를 찍으면서 키를 출력했다. 그리고 출력은 파일에 저장되었다. 파일에서 찾아본다.

```
# macOS
grep -n "lk-demo" ../samples/leaky.ipynb

# Windows
Select-String "lk-demo" ../samples/leaky.ipynb
```

```
20:       "'lk-demo-7f3a9c2e51b84d06a1c3'"
45:      "요청 헤더: {'Authorization': 'Bearer lk-demo-7f3a9c2e51b84d06a1c3'}\n"
```

이 노트북을 커밋하고 푸시하면 키가 GitHub에 올라간다. HTML로 내보내 메일로 보내면(9.6.5) 메일에 키가 들어간다. AI 도구에 노트북을 보여 주면 AI에게 키를 보낸 것이다. 8.3.3에서 커밋 전에 쓴 낱말 검사를 이 파일에 해 보자.

```
# macOS
grep -n -i -E "key|token|secret|password" ../samples/leaky.ipynb

# Windows
Select-String -Pattern "key|token|secret|password" ../samples/leaky.ipynb
```

```
31:    "key = os.environ[\"LEDGER_API_KEY\"]\n",
32:    "key"
50:    "print(\"요청 헤더:\", {\"Authorization\": f\"Bearer {key}\"})"
```

걸린 것은 **소스** 줄뿐이다. 정작 키의 값이 든 20번과 45번 줄은 `key`라는 낱말이 없어서 걸리지 않았다. 8.3.3에서 "낱말 검사는 놓치는 것이 있다, 읽는 습관이 핵심"이라고 했던 것이 여기서 그대로 드러난다. 그나마 소스 줄이 걸렸으니 "이 노트북은 키를 다룬다"는 신호로 삼아 출력을 직접 읽어 봐야 한다.

**노트북에서 비밀 값이 남는 길**

| 어디에 | 어떻게 | nbstripout으로 막히나 |
|---|---|---|
| 출력 | 키를 담은 변수를 셀의 마지막 줄에 둔다(`key`) | 막힌다 |
| 출력 | 키가 든 요청 헤더·설정을 `print()`한다 | 막힌다 |
| 출력 | `%env`나 `os.environ`을 그대로 출력한다. **모든 환경 변수**가 찍힌다(9.5.9) | 막힌다 |
| 출력 | API가 돌려준 오류 메시지에 보낸 값의 일부가 들어 있다 | 막힌다 |
| **소스** | 시험 삼아 `key = "lk-..."`처럼 셀에 직접 적는다 | **막히지 않는다** |
| **소스** | `%env LEDGER_API_KEY=lk-...`로 환경 변수를 정한다(9.5.9) | **막히지 않는다** |
| 내보낸 파일 | HTML로 내보낸다. HTML에는 출력이 모두 들어 있다 | **막히지 않는다** |

nbstripout은 **출력**을 지운다. 셀의 **소스**는 커밋해야 할 내용이므로 그대로 둔다. 소스에 적은 비밀 값은 `.py` 파일에 적은 것과 똑같이 커밋된다. 그래서 다음 규칙을 지킨다.

- **비밀 값은 셀에 적지 않는다.** 환경 변수나 `.env` 파일(8.3.2)에서 읽는다. `.env`를 노트북에서 읽는 방법(`python-dotenv`)은 "웹·API 기초"에서 배운다.
- **비밀 값을 출력하지 않는다.** 키가 읽혔는지 확인하고 싶으면 값이 아니라 **있는지**를 출력한다.

  ```python
  import os

  key = os.environ.get("LEDGER_API_KEY")
  print("키가 있나:", key is not None)
  ```

- **`%env`를 인자 없이 실행하지 않는다.** 환경 변수를 보고 싶으면 이름을 골라서 본다.
- **커밋 전에 저장소에 들어갈 내용을 본다.** nbstripout을 설정했다면 `git diff --staged`는 출력을 뺀 내용, 곧 저장소에 들어갈 내용을 보여 준다. 8.3.3의 습관 그대로다.

**개인정보도 출력에 남는다**

비밀 값만이 아니다. 9.3.3에서 `rows[0]`을 실행했을 때 가계부의 한 줄이 출력되었다. 연습용 데이터라 괜찮지만, 실제 고객 명단이나 설문 응답을 탐색한 노트북이라면 출력에 사람의 이름, 연락처, 응답 내용이 남는다. 데이터 파일을 `.gitignore`로 막아 두어도 노트북의 출력으로 일부가 커밋된다. nbstripout은 이 길도 막는다. 출력을 지우고 커밋하는 것이 기본이어야 하는 이유 중 하나다.

**이미 커밋해 버렸다면**

출력에 키가 든 노트북을 이미 커밋했다면, 그 뒤에 nbstripout을 설정해도 **지난 커밋에는 키가 그대로 남아 있다.** 8.3.5의 순서를 그대로 따른다. **키부터 폐기하고 다시 발급받는다.** 그다음에 이력을 정리할지 판단한다. "출력을 지우는 커밋을 하나 더 하면 된다"고 생각하기 쉽지만, 7장에서 본 대로 Git은 지난 커밋을 모두 기억한다. 그 커밋을 받은 사람과 GitHub에는 키가 남아 있다.

nbstripout을 Git 필터가 아니라 **명령으로** 실행하면 파일을 직접 고친다. 되돌리는 기능은 없다. 원본 `leaky.ipynb`는 실습 9-7에서 다시 쓰므로, 복사본을 만들어 그것을 고친다.

```
# macOS
cp ../samples/leaky.ipynb ../samples/leaky_copy.ipynb

# Windows
Copy-Item ../samples/leaky.ipynb ../samples/leaky_copy.ipynb
```

```
nbstripout ../samples/leaky_copy.ipynb
```

복사본에서 `lk-demo`를 찾아보면(macOS `grep -n "lk-demo" ../samples/leaky_copy.ipynb`, Windows `Select-String "lk-demo" ../samples/leaky_copy.ipynb`) 아무것도 나오지 않는다. 원본에는 그대로 남아 있다. 내 노트북에 nbstripout을 명령으로 쓸 때도, 다시 만들 수 없는 출력이 아닌지 먼저 확인한다.

### 9.7.5 VS Code와 GitHub에서 노트북 diff 보기

터미널의 `git diff`는 노트북을 JSON으로 보여 준다. nbstripout으로 많이 나아졌지만, 셀 단위로 보고 싶을 때는 화면 도구를 쓴다.

**VS Code** — 소스 제어 보기(`Ctrl+Shift+G`, 5장)에서 바뀐 `.ipynb` 파일을 누르면 **노트북 diff 편집기**가 열린다. JSON이 아니라 셀이 왼쪽(커밋된 것)과 오른쪽(작업 폴더)에 나란히 놓이고, 바뀐 셀만 색으로 표시된다. 도구 막대에서 메타데이터와 출력의 차이를 보일지 숨길지 고를 수 있다. nbstripout을 설정한 저장소에서는 커밋된 쪽에 출력이 없으므로 출력의 차이가 모든 셀에 나타난다. 출력의 차이를 숨기면 코드의 변경만 남는다.

**GitHub** — 이 저장소를 GitHub에 올려 보자. 8.7.2의 `gh repo create`를 쓴다.

```
gh repo create ledger-notes --private --source=. --remote=origin --push
```

```
✓ Created repository jinyoung-dev/ledger-notes on github.com
  https://github.com/jinyoung-dev/ledger-notes
✓ Added remote https://github.com/jinyoung-dev/ledger-notes.git
✓ Pushed commits to https://github.com/jinyoung-dev/ledger-notes.git
```

`gh repo view --web`으로 저장소를 열고 `explore.ipynb`를 누르면, GitHub가 노트북을 **셀 모양으로 그려서** 보여 준다. Markdown 셀은 서식대로, 코드 셀은 색을 입혀서 보인다. 출력은 보이지 않는다. 저장소에 출력 없이 들어갔기 때문이다(9.7.3의 표). 노트북이 아주 크면 GitHub가 그리지 못하고 원본(JSON)을 보라고 안내하기도 한다. 오른쪽 위의 **Code**(또는 **Raw**)를 누르면 JSON을 볼 수 있다.

풀 리퀘스트의 **Files changed** 화면(8.5.5)에서는 노트북의 변경이 기본으로 JSON diff로 나온다. GitHub가 노트북 diff를 셀 단위로 보여 주는 기능을 기능 미리 보기(Feature preview)로 제공한 적이 있으므로, 프로필 사진 메뉴의 **Feature preview**에 노트북 diff 항목이 보이면 켜 볼 수 있다. 어느 쪽이든 nbstripout을 써서 출력을 지워 두면 PR의 diff가 고친 셀 중심으로 짧아진다. 노트북 리뷰가 잦은 팀은 nbdime(아래 상자) 같은 도구나 노트북 리뷰 전용 서비스를 쓰기도 한다.

> **nbdime — 노트북 전용 diff와 병합 도구**
> nbdime은 Jupyter 프로젝트가 만든 노트북 비교·병합 도구다. `python -m pip install nbdime`으로 설치하면 `nbdiff 옛것.ipynb 새것.ipynb`로 터미널에서 셀 단위 diff를, `nbdiff-web`으로 브라우저에서 그림처럼 보이는 diff를 볼 수 있다. `nbdime config-git --enable`을 하면 `git diff`와 `git merge`가 노트북에 nbdime을 쓰도록 설정된다. 이 과정에서는 nbstripout과 VS Code의 노트북 diff로 충분하므로 설치하지 않는다. 노트북을 많이 다루는 팀에 가면 만날 수 있는 이름이다.

### 9.7.6 노트북 충돌

두 사람이 같은 노트북을 서로 다른 브랜치에서 고치고 병합하면, 6.4에서 본 충돌이 노트북에서도 생긴다. 노트북의 충돌은 `.py`보다 다루기 어렵다.

- 충돌 표시(`<<<<<<<`, `=======`, `>>>>>>>`)가 **JSON 사이에** 들어간다. JSON 문법이 깨지므로 VS Code가 노트북으로 열지 못한다. 텍스트 편집기로 열어 JSON을 직접 고쳐야 한다.
- 출력과 실행 번호를 저장소에 넣는다면, 코드가 겹치지 않아도 실행 번호와 출력이 겹쳐서 충돌이 난다.

그래서 노트북의 충돌은 **해결하기보다 피하는** 편이 낫다.

1. **출력을 지우고 커밋한다**(9.7.3). 충돌의 대부분이 사라진다. 남는 것은 정말로 같은 셀의 코드를 둘이 고친 경우뿐이다.
2. **한 노트북은 한 사람이 고친다.** 노트북은 한 사람의 탐색 기록에 가깝다. 같은 데이터를 둘이 탐색한다면 노트북을 따로 만든다(`explore_jinyoung.ipynb`, `explore_doyun.ipynb`처럼).
3. **함께 고치는 코드는 `.py` 모듈에 둔다**(9.6). `.py`의 충돌은 6.4에서 배운 그대로 해결할 수 있다.

그래도 충돌이 났다면 다음 순서로 해결한다.

1. 6.4.8의 방법으로 **파일 전체를 한쪽 것으로** 고른다. `--ours`와 `--theirs` 중 어느 쪽이 어느 브랜치인지는 병합인지 리베이스인지에 따라 뒤바뀐다(7.5.3).

   ```
   git restore --theirs explore.ipynb    # 또는 --ours
   ```

2. 노트북을 열어, 고르지 않은 쪽에서 고친 셀을 손으로 다시 넣고 저장한다.
3. 재시작 후 모두 실행(9.4.4)으로 끝까지 도는지 확인한다.
4. **마지막으로** 스테이징하고 병합을 마무리한다(리베이스 중이면 `git commit` 대신 `git rebase --continue`, 7.5.3).

   ```
   git add explore.ipynb
   git commit
   ```

`git add`를 1단계 바로 뒤에 하면, 2단계에서 손으로 넣은 변경은 스테이징되지 않은 채 작업 폴더에만 남고 병합 커밋에서 빠진다. 커밋하기 전에 `git status`로 `explore.ipynb`가 스테이징된 쪽에만 있는지 확인한다.

### 실습 9-7. 노트북과 Git

결과는 `~/devtools-lab/ch09/git.md`에 적는다.

1. 9.7.1~9.7.2를 따라 한다. 셀을 다시 실행만 했을 때의 `git diff --stat`과, 코드 한 줄을 고쳤을 때의 `git diff --stat`을 적는다. 두 diff에서 내가 고친 것이 아닌 줄의 종류를 모두 적는다.
2. 9.7.3을 따라 nbstripout을 설정한다. `.gitattributes`의 내용과 `git config --get-regexp nbstripout`의 출력을 적고, 각 줄이 무슨 일을 하는지 한 줄씩 설명한다. `README.md`에 "준비" 절을 더하고 커밋한다.
3. 설정한 뒤 다음을 차례로 해 보고 각 단계의 `git status --short`를 적는다. (가) 셀 하나를 다시 실행만 하고 저장 (나) Markdown 셀의 글자 하나를 고치고 저장 (다) `git restore explore.ipynb`. (다) 뒤에 노트북 화면에서 무엇이 달라졌는지 적고, 그 이유를 `smudge`와 연결해 설명한다.
4. **설정이 따라가지 않는 것을 확인한다.** 다른 폴더에 이 저장소를 클론한다(`cd ~/devtools-lab/ch09/practice && git clone ledger ledger-clone`). 클론한 폴더에서 `git config --get-regexp nbstripout`의 결과를 적는다. VS Code로 클론한 폴더를 열어 `explore.ipynb`의 셀을 하나 실행할 수 있게 커널을 고르고(원래 `ledger`의 `.venv`를 골라도 된다), 실행한 뒤 저장하고 `git status --short`와 `git diff --stat`을 적는다. 출력이 커밋될 상황인지 판단해 적는다. 확인한 뒤 클론한 폴더는 지운다(지우기 전에 경로를 확인한다).
5. `samples/leaky.ipynb`로 9.7.4를 따라 한다. 낱말 검사(`key|token|secret|password`)가 놓친 줄을 적고, 같은 노트북을 "키가 읽혔는지만" 확인하도록 고친 코드를 적는다. 마지막에 원본을 복사한 `leaky_copy.ipynb`에 `nbstripout`을 실행해 출력을 지우고, 복사본에서는 `lk-demo`가 검색되지 않고 원본에서는 여전히 검색되는 것을 확인한다. 원본은 고치지 않는다(다시 실습할 때 쓴다).
6. 9.7.5를 따라 GitHub에 비공개 저장소 `ledger-notes`를 만들어 올리고, GitHub에서 `explore.ipynb`가 어떻게 보이는지 적는다. 브랜치를 하나 만들어 노트북의 셀 하나를 고친 커밋을 올리고 PR을 연 뒤(8.5), Files changed 화면의 diff가 몇 줄인지 적는다. 실습이 끝나면 PR을 닫고 브랜치를 지운다. 저장소를 남길지 지울지는 스스로 정한다(지우는 방법은 8.7.2의 상자).
7. (선택) 이 저장소에서 브랜치 두 개를 만들어 노트북의 **같은 코드 셀**을 서로 다르게 고쳐 커밋하고 병합해 충돌을 만든다. VS Code에서 노트북이 어떻게 열리는지 적고, 9.7.6의 방법으로 해결한다. 출력이 커밋되지 않는 상태(nbstripout 설정 후)에서도 충돌이 나는지, 충돌 표시가 어떤 모양인지 적는다.

## 9.8 클라우드 노트북 소개

### 9.8.1 브라우저만 있으면 되는 노트북

지금까지는 내 컴퓨터에서 커널을 띄웠다. 커널을 **남의 컴퓨터**(클라우드)에 띄우고 브라우저로 쓰는 노트북 서비스도 있다. 9.1.2의 그림에서 커널 상자가 인터넷 너머로 옮겨 간 것이다. 대표적인 것이 두 가지다.

- **Google Colab**(colab.research.google.com) — Google 계정으로 쓰는 노트북 서비스. 노트북은 Google 드라이브에 저장된다. 파이썬과 많이 쓰는 데이터·머신러닝 패키지가 미리 설치되어 있고, 무료 사용 범위 안에서 GPU도 쓸 수 있다.
- **Kaggle 노트북**(kaggle.com) — 데이터 분석 대회 사이트 Kaggle의 노트북. Kaggle에 올라온 데이터셋을 노트북에 바로 붙여 쓸 수 있다. 역시 GPU를 정해진 시간만큼 무료로 쓸 수 있다.

둘 다 설치가 필요 없다. 가상환경도, `ipykernel`도, 커널 선택도 없다. 노트북 파일 형식은 같으므로(9.1.5) 이 장에서 만든 `explore.ipynb`를 Colab에 올려 열 수 있고, Colab에서 만든 노트북을 내려받아 VS Code에서 열 수도 있다. 셀, 실행 번호, 숨은 상태, 매직 명령, `!` 셸 명령도 모두 같다. 커널이 리눅스 컴퓨터에서 돌기 때문에 `!` 명령은 Windows 사용자에게도 리눅스의 bash 명령이다(9.5.3의 상자와 반대다).

### 9.8.2 로컬 노트북과 다른 점

편한 만큼 다른 점도 있다. 다른 점은 모두 "커널이 내 컴퓨터에 있지 않다"에서 나온다.

| | 내 컴퓨터의 노트북 | Colab·Kaggle |
|---|---|---|
| 커널 | 내 컴퓨터의 프로세스 | 서비스가 빌려준 클라우드 컴퓨터의 프로세스. 그 컴퓨터를 **런타임**(Colab) 또는 **세션**(Kaggle)이라고 부른다 |
| 파일 | 내 폴더의 파일을 그대로 읽는다 | 내 컴퓨터의 파일이 보이지 않는다. 올리거나(업로드), 드라이브·데이터셋을 연결해야 한다 |
| 파일이 남나 | 남는다 | 런타임에 만든 파일은 **런타임이 끝나면 사라진다.** 노트북 파일 자체는 드라이브(Colab)나 Kaggle에 저장된다 |
| 패키지 | 내가 가상환경에 설치한 것 | 서비스가 미리 설치한 것. 더 필요하면 **세션마다** `%pip install`(9.5.2의 상자). 버전은 내 `requirements.txt`와 다를 수 있다 |
| 비밀 값 | 환경 변수, `.env`(8.3.2) | 서비스의 비밀 값 보관 기능(아래) |
| 시간 | 내가 끌 때까지 | 한동안 아무것도 안 하거나 최대 사용 시간이 지나면 런타임이 끊긴다. **커널 재시작과 같다.** 변수가 모두 사라진다 |
| GPU | 내 컴퓨터에 있어야 한다 | 무료 범위 안에서 빌려 쓸 수 있다 |

파일을 다루는 방법을 조금 더 보자. Colab에서 커널의 작업 폴더는 `/content`다. 왼쪽의 파일 아이콘을 눌러 파일을 올리면 이 폴더에 들어간다. 런타임이 끊기면 함께 사라지므로 매번 다시 올려야 한다. 계속 쓸 파일은 Google 드라이브에 두고 노트북에서 드라이브를 연결한다.

```python
from google.colab import drive

drive.mount("/content/drive")
```

실행하면 Google 계정 접근을 허락하는 창이 뜨고, 허락하면 내 드라이브가 `/content/drive/MyDrive/` 아래에 보인다. 이 코드는 Colab에서만 동작한다(`google.colab`은 Colab에만 있는 모듈이다). 같은 노트북을 내 컴퓨터에서 열면 `ModuleNotFoundError`가 난다. Kaggle에서는 노트북에 붙인 데이터셋이 `/kaggle/input/` 아래에 보이고, 노트북이 만든 파일은 `/kaggle/working/`에 저장된다.

**비밀 값 다루기**

클라우드 노트북에서는 `.env` 파일을 쓰기 어렵다. 런타임마다 올려야 하고, 올린 파일은 그 런타임의 다른 코드가 모두 읽을 수 있다. 그래서 두 서비스 모두 비밀 값을 **계정에 보관**해 두고 노트북에서 꺼내 쓰는 기능을 준다.

- **Colab** — 왼쪽의 열쇠 모양 아이콘(**Secrets**, 보안 비밀)에서 이름과 값을 등록하고, 이 노트북의 접근을 켠다. 노트북에서는 다음과 같이 꺼낸다.

  ```python
  from google.colab import userdata

  key = userdata.get("LEDGER_API_KEY")
  ```

- **Kaggle** — 노트북 편집 화면의 **Add-ons** → **Secrets**에서 등록하고, 노트북에서는 다음과 같이 꺼낸다.

  ```python
  from kaggle_secrets import UserSecretsClient

  key = UserSecretsClient().get_secret("LEDGER_API_KEY")
  ```

어느 쪽이든 9.7.4의 규칙이 그대로 적용된다. **꺼낸 값을 출력하지 않는다.** 보관 기능은 값이 소스에 적히지 않게 해 줄 뿐, 셀의 마지막 줄에 `key`를 두면 출력에 찍히고 노트북에 저장되는 것은 똑같다.

**공유할 때 출력도 함께 간다**

Colab의 노트북은 드라이브 문서처럼 링크로 공유할 수 있다. 링크를 받은 사람은 노트북의 **출력까지** 본다. Colab에는 메뉴 **Edit**(수정) → **Notebook settings**(노트북 설정)에 저장할 때 코드 셀의 출력을 빼는 설정이 있다. 민감한 데이터를 다루는 노트북이면 켜 둔다. 9.7.3의 nbstripout과 같은 생각이다.

### 9.8.3 Git과 함께 쓰기

Colab은 GitHub와 바로 이어진다. 메뉴 **File**(파일) → **Open notebook**(노트북 열기)의 **GitHub** 탭에서 저장소의 노트북을 열 수 있고, **File** → **Save a copy in GitHub**(GitHub에 사본 저장)로 노트북을 저장소에 커밋할 수도 있다. 다만 이 기능은 Colab이 GitHub에 **직접** 커밋하므로, 9.7.3에서 설정한 nbstripout을 거치지 않는다. 출력이 그대로 커밋되고, `README.md`의 준비 절도 소용이 없다. 9.8.2의 출력 빼기 설정을 켜 두거나, 노트북을 내려받아(**File** → **Download** → **Download .ipynb**) 내 컴퓨터의 저장소에서 평소처럼 커밋하는 편이 안전하다.

VS Code에서 Colab의 런타임을 커널로 쓰는 방법도 있다. Google이 2025년 11월에 내놓은 VS Code용 **Colab** 확장을 설치하면, VS Code에서 연 노트북의 **Select Kernel**(9.2.3) 목록에 Colab이 나타나고, 고르면 그 노트북의 셀이 Colab의 클라우드 컴퓨터에서 실행된다. 편집은 VS Code에서, Git도 VS Code에서 하면서 GPU만 빌려 쓸 수 있다. 이때도 커널은 클라우드에 있으므로 **내 폴더의 파일은 커널에서 보이지 않는다**는 점(9.8.2의 표)은 같다. 노트북 옆의 `data/2026.csv`를 `"data/2026.csv"`로 읽으려 하면 `FileNotFoundError`가 난다. 어떤 커널에 연결되어 있는지 헷갈리면 9.2.4처럼 `sys.executable`과 `os.getcwd()`를 찍어 본다.

### 9.8.4 언제 클라우드 노트북을 쓰나

| 상황 | 고를 곳 |
|---|---|
| 이 과정의 실습, 내 프로젝트의 탐색 | **내 컴퓨터**(VS Code). 파일, 가상환경, Git이 모두 손에 있다 |
| 남이 설치 없이 바로 열어 보게 하고 싶다 | Colab 공유 링크. 출력에 무엇이 있는지 먼저 확인한다 |
| GPU가 필요하다 | Colab·Kaggle |
| Kaggle 데이터셋으로 연습한다 | Kaggle 노트북 |
| 회사나 남의 개인정보가 든 데이터 | **올리기 전에 허락을 받는다.** 클라우드 노트북에 파일을 올리는 것은 그 서비스에 데이터를 맡기는 일이다. 회사에는 쓸 수 있는 서비스를 정한 규칙이 있을 수 있다 |

로드맵의 3단계 "머신러닝·딥러닝"에서 신경망을 학습시킬 때 GPU가 필요해지면 클라우드 노트북을 다시 만난다. 그때 이 장의 내용, 곧 런타임이 끊기면 변수가 사라진다는 것(숨은 상태와 재시작), 패키지는 세션마다 설치한다는 것, 비밀 값은 보관 기능에서 꺼내고 출력하지 않는다는 것, 출력이 공유된다는 것이 그대로 쓰인다.

| 노트북 | 코드 셀·Markdown 셀·출력이 한 파일(`.ipynb`)에. 셀 하나씩 실행하고 결과가 바로 아래에 남는다. 탐색·프롬프트 실험·학습 기록에 |

| 정보의 세 곳 | 파일(코드·Markdown·마지막 출력·실행 번호), 화면(저장 전 변경), 커널(변수·함수·모듈). **변수는 파일에 없다** |

| 노트북 vs 스크립트 | 답을 찾는 중이면 노트북, 답을 알고 되풀이하면 스크립트. import·반복·자동화·시험·리뷰는 `.py` |
| 이름 | Jupyter(프로젝트), 노트북(형식), IPython(매직·`!`), ipykernel(커널), JupyterLab·Jupyter Notebook(브라우저 화면), Jupyter Server, nbconvert |
| 설치 | VS Code: 프로젝트 `.venv`에 `ipykernel`만(29개 남짓). 브라우저: `jupyterlab`(90개 남짓, nbconvert 포함). `pip install jupyter`는 필요 없는 것까지 |
| 커널 고르기 | **Select Kernel** → **Python Environments...** → 이 폴더의 `.venv`. "requires the ipykernel package" 창은 환경 이름을 확인하고 누른다 |
| 커널의 파이썬 | 노트북에서 `sys.executable`. 터미널의 파이썬과 다를 수 있다. 커널은 프로세스(`os.getpid()`), 재시작하면 새 프로세스·변수 모두 사라짐 |
| JupyterLab | 실행한 폴더가 기준. `localhost:8888`, 토큰은 비밀번호. 브라우저 탭을 닫아도 서버는 떠 있다 → `Ctrl+C`(macOS는 `y` 확인), File → Shut Down, `jupyter server list`. `.ipynb_checkpoints/` |
| kernelspec | `python -m ipykernel install --user --name 이름`으로 JupyterLab 하나에서 여러 가상환경 커널. `jupyter kernelspec list/remove` |
| 도구 기록 | `requirements-dev.txt`에 직접 설치한 것만(`ipykernel`, `jupyterlab`, `nbstripout`). 프로그램용은 `requirements.txt` |
| 셀 실행 | `Shift+Enter`(다음으로), `Cmd/Ctrl+Enter`(머문다), `Option/Alt+Enter`(아래에 새 셀). Run All, Execute Above/Cell and Below |
| 두 모드 | 편집(`Enter`)과 명령(`Esc`). 명령 모드: `A`/`B` 추가, `D` `D` 삭제, `M`/`Y` 종류, `Option/Alt+↑↓` 이동, `L` 줄 번호 |
| 출력 규칙 | 셀의 **마지막 식**의 값만 출력. 대입문·`None`·`;`는 안 나옴. `print()`는 모두. `display()`. `_`·`Out[n]`은 숨은 상태를 만든다 |
| 오류 | `Cell In[n], line m`. 오류가 나도 커널과 변수는 그대로 → 바로 다음 셀에서 고쳐 본다 |
| 실행 번호 | 위치가 아니라 **실행한 순서**. `[n]`은 마지막으로 실행했을 때의 순서(파일에 저장된 기록, 지금 커널의 상태가 아니다). `[ ]` 번호 없음(실행 안 함·출력 지움·출력 없이 저장), `[*]` 실행 중. 차례대로가 아니면 의심하고 재시작 후 모두 실행 |
| Markdown 셀 | 제목·목록·표(`---:` 오른쪽 정렬)·코드·수식(`$...$`, `$$...$$`). 무엇을 왜, 알게 된 것, 다음 할 것. 옮겨 적은 숫자는 저절로 안 바뀐다 |
| 숨은 상태 | 실행 순서대로 남는 값, 지운 셀의 변수, 두 번 실행하면 두 번 더해지는 셀, `for`·`with`의 변수 |
| 습관 | 위에서 아래로, 여러 번 실행해도 같게(초기화와 변경을 한 셀에), 실패 셀은 지우고 Markdown으로, **재시작 후 모두 실행**(커밋·공유·판단 전) |
| 변수 보기 | VS Code의 Variables, 어디서나 `%whos`·`%who` |
| 인터럽트 | ■ / JupyterLab `I` `I`. `KeyboardInterrupt`, 커널은 산다(반쯤 바뀐 변수는 믿지 않는다). 안 멈추면 재시작 |
| 매직 명령 | IPython의 기능. `%` 줄, `%%` 셀(첫 줄). `%lsmagic`, `?`, `??`. `.py`에서는 `SyntaxError` |
| `%pip` vs `!pip` | `%pip` = 커널의 파이썬(`sys.executable -m pip`). `!pip` = 셸이 찾는 `pip`. 노트북에서는 `%pip`. 설치 셀은 남기지 않고 requirements에 |
| `!` 셸 명령 | 출력 담기(`x = !ls`), 변수 넣기(`{name}`). **Windows는 cmd.exe**. 남길 코드는 파이썬(`pathlib`)으로 |
| 작업 폴더 | 커널은 노트북 파일의 폴더에서 시작(`jupyter.notebookFileRoot`). `!cd`는 효과 없음, `%cd`는 숨은 상태 → 쓰지 않는다 |
| 시간 재기 | `%time`/`%%time`(한 번, Wall time vs CPU times), `%timeit`(여러 번 평균. 오래 걸리거나 무언가를 바꾸는 코드에는 쓰지 않는다) |
| `%%writefile` | 셀을 파일로(묻지 않고 덮어씀, `-a` 덧붙이기). `%run`은 커널 안에서 실행 |
| `%autoreload` | `%load_ext autoreload` + `%autoreload 2`. 고친 모듈을 셀 실행 전에 다시 불러온다. 이상하면 재시작 |
| `await` | 커널이 이미 이벤트 루프를 돌린다 → `asyncio.run()`은 `RuntimeError`, `await`를 바로. 스크립트로 옮길 때 `asyncio.run()`으로 |
| `%env` | 인자 없이 쓰면 모든 환경 변수 출력. `%env 이름=값`은 소스에 남는다 |
| 노트북 → 프로그램 | 셀을 함수로(여러 번 실행해도 같고, 지역 변수는 남지 않는다) → `.py` 모듈 → 노트북은 import해서 결과를 보고 설명. 모듈은 편집기에서 고친다 |
| `__main__` | 같은 모듈을 `python ledger_tools.py 파일`로도. 노트북은 탐색과 설명, 스크립트는 반복과 자동화 |
| nbconvert | `--to script`(출발점일 뿐, `get_ipython` 오류·식이 버려진다), `--to html`(출력 포함), **`--execute`**(새 커널로 처음부터, 실패하면 종료 코드 1 → `&&`, GitHub Actions). 남의 노트북은 읽고 실행 |
| import | 노트북은 import하지 않는다. 여러 곳에서 쓸 코드는 `.py` |
| 노트북의 diff | JSON, 실행 번호, 출력(그림은 base64), 메타데이터(파이썬 버전) → 다시 실행만 해도 바뀐다. 진짜 변경이 묻힌다. 충돌이 잦다 |
| 출력 지우기 | 손으로(Clear All Outputs), `jupyter nbconvert --clear-output --inplace`, **nbstripout**(Git 필터. 작업 폴더는 그대로, 저장소에는 출력·실행 번호 없이, 셀 `id`도 다시 매김) |
| nbstripout 설정 | `nbstripout --install --attributes .gitattributes` → `.gitattributes`(필터 이름, 커밋됨) + `.git/config`(실행할 명령, 절대 경로, **클론에 안 따라감**) → README 준비 절. 처음 한 번 커밋. `git restore`하면 출력 없는 노트북. `--status`, `--verify`, `--keep-output` |
| 남길까 지울까 | 이 과정은 지우고 커밋. 결과는 `--execute --to html`로 따로 전한다 |
| 비밀 값 | 출력(`key`, `print(헤더)`, `%env`, 오류 메시지)은 nbstripout이 막는다. **소스**(`key = "..."`, `%env 이름=값`)와 **HTML**은 못 막는다. 값이 아니라 있는지를 출력. 낱말 검사는 출력의 값을 놓친다. 커밋했다면 8.3.5(키 폐기부터) |
| 개인정보 | 데이터 파일을 막아도 `rows[0]` 같은 출력으로 커밋된다 |
| diff 보기 | VS Code 노트북 diff 편집기(메타데이터·출력 차이 숨기기), GitHub는 노트북을 셀 모양으로 그린다(출력 없으면 코드만). PR은 JSON diff. nbdime |
| 충돌 | 피한다: 출력 지우기, 한 노트북 한 사람, 함께 고칠 코드는 `.py`. 났다면 `git restore --ours/--theirs` 후 손으로 다시 넣고 재시작 후 모두 실행 |
| 클라우드 노트북 | Colab·Kaggle. 커널이 클라우드에. 내 파일 안 보임(업로드·드라이브·데이터셋), 런타임 끝나면 파일·변수 사라짐, 패키지는 세션마다, 비밀 값은 Secrets(출력하지 않는다), 공유하면 출력도 간다. GitHub 사본 저장은 nbstripout을 거치지 않는다. VS Code Colab 확장. 남의 데이터는 허락받고 올린다 |
