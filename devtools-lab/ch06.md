# 6장. 브랜치와 병합

[개발 도구](README.md) 과정의 여섯 번째 장이다. 5장에서는 `main` 브랜치 하나에 커밋을 한 줄로 쌓았다. 이 장에서는 그 줄을 **여러 갈래로 나누고 다시 합친다.** 새 기능을 만들거나 실험을 할 때 `main`을 건드리지 않고 별도의 갈래에서 작업하고, 다 되면 `main`에 합치고, 실패하면 갈래째 버린다. 두 사람이 각자의 갈래에서 같은 줄을 고쳤다면 Git이 합치지 못하고 멈추는데, 그것을 **충돌**이라고 하고 사람이 직접 해결한다.

- **커밋 그래프와 브랜치** — 커밋 해시와 부모 커밋, 브랜치는 커밋을 가리키는 이름표라는 것, `HEAD`의 의미, `git log --oneline --graph --all`로 그래프 그려 보기
- **브랜치 다루기** — `git branch`, `git switch`, `git switch -c`, 커밋하지 않은 변경이 있을 때 브랜치를 옮기면 생기는 일, 브랜치 이름 바꾸기와 지우기, detached HEAD
- **병합** — `git merge`, 빨리 감기(fast-forward)와 병합 커밋, 병합 후 그래프 읽기
- **충돌 해결** — 충돌 표시 읽기, 직접 고치기와 VS Code 병합 편집기, 해결 후 커밋, `git merge --abort`, 충돌을 줄이는 습관
- **브랜치 전략** — `main`은 언제나 실행되는 상태로, 일마다 브랜치, 브랜치 이름 규칙, 실험이 실패하면 브랜치째 버리기

이 장에서도 저장소는 내 컴퓨터에만 둔다. 브랜치를 GitHub에 올리고 풀 리퀘스트로 병합하는 일은 8장에서 한다. 8장의 협업 흐름(브랜치 → 푸시 → 풀 리퀘스트 → 리뷰 → 병합)은 이 장에서 내 컴퓨터 안에서 하는 일을 GitHub 위로 옮긴 것이므로, 이 장의 내용이 그대로 바탕이 된다. 이미 한 커밋을 고치거나 되돌리는 일(`reset`, `revert`, `rebase`)은 7장에서 다룬다.

## 학습 목표

이 장을 마치면 다음을 할 수 있다.

- 커밋이 부모 커밋을 가리키며 이어진다는 것을 `git log --format="%h %p %s"`로 확인하고, 첫 커밋에는 부모가 없고 병합 커밋에는 부모가 둘이라는 것을 설명할 수 있다.
- 브랜치가 "커밋을 가리키는 이름표"라는 것을 `.git/refs/heads`의 파일로 확인하고, 브랜치를 만드는 일이 왜 빠르고 가벼운지 설명할 수 있다.
- `HEAD`가 보통 브랜치를 가리키고, 그 브랜치가 커밋을 가리킨다는 것을 그림으로 설명하고, 커밋할 때 무엇이 움직이는지 말할 수 있다.
- `git log --oneline --graph --all`의 출력에서 브랜치가 갈라진 곳, 합쳐진 곳, 아직 합쳐지지 않은 브랜치를 찾을 수 있다.
- `git branch`, `git switch`, `git switch -c`로 브랜치를 만들고 옮겨 다니며, 브랜치를 옮길 때 작업 폴더의 파일이 바뀌는 것을 확인할 수 있다.
- 커밋하지 않은 변경이 있을 때 브랜치를 옮기면 변경이 따라오거나 옮기기가 거절된다는 것을 알고, 브랜치를 옮기는 것만으로는 변경이 보존되지 않는다는 것을 설명할 수 있다.
- `git branch -m`으로 브랜치 이름을 바꾸고(`master` → `main` 포함), `-d`와 `-D`의 차이를 알고 브랜치를 지울 수 있다.
- detached HEAD 상태가 무엇인지, 그 상태로 무엇을 할 수 있고 무엇을 조심해야 하는지 알고, 그 상태에서 빠져나오거나 만든 커밋을 브랜치로 살릴 수 있다.
- `git merge`로 브랜치를 합치고, 빨리 감기와 병합 커밋이 각각 언제 생기는지 그래프로 설명할 수 있다.
- 병합 커밋의 첫째 부모와 둘째 부모를 구별하고, `--first-parent`, `main..브랜치`, `--merged`/`--no-merged`로 병합 이력을 읽을 수 있다.
- 충돌이 생기는 경우를 알고, 충돌 표시(`<<<<<<<`, `|||||||`, `=======`, `>>>>>>>`)를 읽어 두 브랜치가 각각 무엇을 바꾸었는지 설명할 수 있다.
- 충돌을 직접 고치거나 VS Code의 병합 편집기로 해결하고, `git diff --check`·검사 스크립트로 확인한 뒤 병합 커밋을 만들 수 있다. "둘 다 받기"가 언제 맞고 언제 틀리는지 판단할 수 있다.
- 병합 도중 `git merge --abort`로 병합 전 상태로 돌아갈 수 있다.
- `main`을 언제나 실행되는 상태로 두는 이유를 설명하고, 일마다 브랜치를 만들어 작업하고 병합하고 정리하는 흐름을 스스로 따를 수 있다.
- VS Code의 브랜치 선택, 병합 명령, 병합 편집기가 각각 어떤 Git 명령에 해당하는지 말할 수 있다.

import os
import subprocess
import sys
from pathlib import Path

base = Path("practice")

    sys.exit("practice 폴더가 이미 있다. 다시 만들려면 practice 폴더를 지우고 실행한다.")


def write(path, text):
    path.parent.mkdir(parents=True, exist_ok=True)
    path.write_text(text, encoding="utf-8", newline="\n")


AUTHORS = {
    "서연": ("이서연", "seoyeon@example.com"),
    "도윤": ("박도윤", "doyun@example.com"),
}


def git(repo, *args, who="서연", when="2026-11-02T10:00:00+09:00"):
    """실습용 저장소에서 git 명령을 실행한다. 작성자와 시각을 고정한다."""
    name, email = AUTHORS[who]
    env = dict(os.environ)
    env.update(
        GIT_AUTHOR_NAME=name, GIT_AUTHOR_EMAIL=email, GIT_AUTHOR_DATE=when,
        GIT_COMMITTER_NAME=name, GIT_COMMITTER_EMAIL=email, GIT_COMMITTER_DATE=when,
    )
    options = ["-c", "core.autocrlf=false", "-c", "commit.gpgsign=false"]
    subprocess.run(["git", *options, *args], cwd=repo, env=env, check=True,
                   capture_output=True, text=True, encoding="utf-8")


def commit(repo, who, when, *message):
    msg_args = []
    for part in message:
        msg_args += ["-m", part]
    git(repo, "add", "-A", "-f", who=who, when=when)
    git(repo, "commit", "-q", *msg_args, who=who, when=when)

LOADER = '''"""주문 CSV 파일을 읽는다."""

import csv
from pathlib import Path

from shop.models import OrderLine

HEADER = ["name", "price", "qty"]


def parse_line(row: dict[str, str]) -> OrderLine:
    """CSV 한 줄(딕셔너리)을 OrderLine으로 바꾼다."""
    return OrderLine(
        name=row["name"].strip(),
        price=int(row["price"]),
        qty=int(row["qty"]),
    )


def load_orders(path: Path) -> list[OrderLine]:
    """주문 파일을 읽어 OrderLine 목록을 돌려준다."""
    with path.open(encoding="utf-8", newline="") as f:
        reader = csv.DictReader(f)
        if reader.fieldnames != HEADER:
            raise ValueError(f"머리글이 {HEADER}가 아닙니다: {reader.fieldnames}")
        return [parse_line(row) for row in reader]

## 6.1 커밋 그래프와 브랜치

### 6.1.1 커밋 해시와 부모 커밋

5.1.3에서 커밋에는 **부모 커밋**, 즉 바로 앞의 커밋이 무엇인지가 들어 있다고 했다. `git log`의 `--format`에서 `%p`는 부모 커밋의 짧은 해시다.

```
git log --format="%h %p %s"
```

```
9666df9 1ed2593 금액을 천 단위 쉼표로 표시
1ed2593 98cad66 묶음 할인 기준을 README와 맞춤
98cad66 2cd870d 시험 스크립트 추가
2cd870d 356d0e1 쿠폰 할인 추가
356d0e1 cb2bb27 묶음 할인 추가
cb2bb27 cb8185a 주문 CSV 읽기 추가
cb8185a  프로젝트 뼈대 만들기
```

첫째 칸이 커밋, 둘째 칸이 그 부모다. `9666df9`의 부모는 `1ed2593`이고, `1ed2593`의 부모는 `98cad66`이다. 맨 아래 `cb8185a`는 둘째 칸이 비어 있다. 저장소의 **첫 커밋에는 부모가 없다.** 부모가 없는 커밋을 **뿌리 커밋**(root commit)이라고 한다.

이것을 그림으로 그리면, 커밋들이 **뒤로**(부모 쪽으로) 화살표를 뻗으며 이어진 사슬이 된다.

```
cb8185a ◀── cb2bb27 ◀── 356d0e1 ◀── 2cd870d ◀── 98cad66 ◀── 1ed2593 ◀── 9666df9
(뿌리)                                                                  (가장 최근)
```

화살표가 왜 뒤를 향하는지가 중요하다.

- **커밋은 자기 부모만 안다.** 커밋을 만들 때 부모는 이미 있으므로 그 해시를 적어 넣을 수 있다. 자식은 아직 없으므로 적을 수 없다. 그래서 Git은 늘 가장 최근 커밋에서 출발해 부모를 따라 거슬러 올라가며 이력을 읽는다. `git log`가 최근 것부터 나오는 이유다.
- **커밋의 해시에는 부모의 해시가 들어간다**(5.4.5). 부모가 하나라도 다르면 해시가 달라진다. 그래서 중간의 커밋 하나를 고치면 그 뒤의 커밋이 모두 새 해시를 가진 새 커밋이 된다. 7장에서 커밋을 고칠 때 이 사실이 중요해진다.
- **한 커밋을 부모로 삼는 자식이 여럿일 수 있다.** 부모 쪽에서는 자식을 모르므로, 같은 커밋에서 출발한 새 커밋을 몇 개든 만들 수 있다. 이것이 이력이 **갈라지는** 원리다.

갈라진 이력을 직접 보자. `--all`을 붙이면 `HEAD`에서 거슬러 올라갈 수 있는 커밋뿐 아니라 저장소의 모든 브랜치에서 출발한 커밋을 보여 준다(6.1.4).

```
git log --all --format="%h %p %s"
```

```
02ac926 9666df9 결과에 총 수량 표시
a8a641b 58e1368 시험에 퍼센트 할인율 검사 추가
58e1368 9666df9 쿠폰 할인율을 퍼센트로도 받기
391a859 8a23623 시험에 쿠폰 할인율 범위 검사 추가
8a23623 9666df9 쿠폰 할인율의 범위 검사
9666df9 1ed2593 금액을 천 단위 쉼표로 표시
1ed2593 98cad66 묶음 할인 기준을 README와 맞춤
...
```

숨어 있던 커밋 다섯 개가 나왔다. `02ac926`, `58e1368`, `8a23623` 세 커밋의 부모가 모두 `9666df9`다. 한 커밋에서 세 갈래가 뻗어 나간 것이다.

```
                                                    ┌── 8a23623 ◀── 391a859
                                                    │
cb8185a ◀── ... ◀── 98cad66 ◀── 1ed2593 ◀── 9666df9 ◀── 58e1368 ◀── a8a641b
                                                    │
                                                    └── 02ac926
```

### 6.1.2 브랜치는 커밋을 가리키는 이름표다

갈래가 셋이면 각 갈래의 끝을 어떻게 찾을까? 해시를 외워 둘 수는 없다. 그래서 갈래의 끝 커밋에 **이름**을 붙여 둔다. 그 이름이 **브랜치**(branch)다.

```
git branch -v
```

```
  feature/coupon-check   391a859 시험에 쿠폰 할인율 범위 검사 추가
  feature/coupon-percent a8a641b 시험에 퍼센트 할인율 검사 추가
  feature/total-qty      02ac926 결과에 총 수량 표시
* main                   9666df9 금액을 천 단위 쉼표로 표시
```

`git branch`는 브랜치 목록을, `-v`는 각 브랜치가 가리키는 커밋까지 보여 준다. 브랜치 이름마다 커밋 하나가 짝지어져 있다. `*`가 붙은 것은 지금 있는 브랜치다(6.1.3).

브랜치가 실제로 무엇인지 `.git` 폴더 안에서 확인한다. 5.3.1에서 `.git`은 손대지 않는다고 했다. 여기서도 **읽기만 한다.**

```
cat .git/refs/heads/main
```

```
9666df9de7862a8b4f799d8365bb271ba58cbb4d
```

`main` 브랜치의 정체는 `.git/refs/heads/main`이라는 **파일 하나**이고, 그 안에는 커밋 해시 40자리가 한 줄 들어 있을 뿐이다. 브랜치는 "이 갈래의 끝은 이 커밋"이라고 적어 둔 **이름표**다. 다른 브랜치도 같다. 이름에 `/`가 든 브랜치는 폴더 안의 파일로 저장된다.

```
ls .git/refs/heads
ls .git/refs/heads/feature
```

```
feature  main
```

```
coupon-check  coupon-percent  total-qty
```

(Windows의 `ls`는 `Get-ChildItem`의 별칭이라 표 모양으로 나온다. 2.1.4.)

이 사실에서 브랜치의 성질 몇 가지가 나온다.

- **브랜치를 만드는 것은 빠르고 가볍다.** 프로젝트 파일을 복사하지 않는다. 41바이트짜리 파일 하나를 쓸 뿐이다. 5.1.1에서 본 "폴더를 통째로 복사해 `shop_실험`이라고 이름 붙이기"와 같은 일을 하면서도 비용은 거의 없다. 그래서 작은 일에도 부담 없이 브랜치를 만든다(6.5.2).
- **브랜치는 커밋을 "담고" 있지 않다.** 커밋은 저장소에 모두 함께 들어 있고, 브랜치는 그중 하나를 가리킬 뿐이다. "`feature/coupon-check` 브랜치의 커밋"이라고 하면 보통 그 브랜치가 가리키는 커밋에서 부모를 따라 거슬러 올라가며 닿는 커밋들을 말한다. 그래서 `9666df9`와 그 앞의 커밋들은 네 브랜치 **모두에** 속한다.
- **브랜치를 지워도 커밋은 바로 사라지지 않는다.** 이름표를 뗄 뿐이다. 다만 이름표가 없는 커밋은 찾기 어려워지고, 오래 지나면 Git이 정리해 버린다(6.2.6, 7장).
- **브랜치는 움직인다.** 브랜치에서 커밋하면 이름표가 새 커밋으로 옮겨 간다(6.2.3). 커밋은 한번 만들면 바뀌지 않지만, 브랜치는 계속 앞으로 나아가는 이름표다.

> **브랜치 파일이 없을 때**
> 저장소를 오래 쓰거나 GitHub에서 받은 저장소(8장)에서는 `.git/refs/heads` 아래에 브랜치 파일이 보이지 않을 수 있다. Git이 정리하면서 여러 브랜치를 `.git/packed-refs`라는 파일 하나에 모아 적어 두기 때문이다. 브랜치가 가리키는 커밋은 `.git` 안을 뒤지지 말고 `git rev-parse main` 또는 `git branch -v`로 확인한다. 이 절에서 파일을 열어 본 것은 브랜치의 정체를 보려는 것이었다.

### 6.1.3 `HEAD` — 지금 어디에 있는가

5장에서 `HEAD`를 "지금 보고 있는 커밋"이라고만 설명했다(5.4.5). 정확히는 `HEAD`는 **지금 있는 브랜치를 가리키는 이름**이다.

```
cat .git/HEAD
```

```
ref: refs/heads/main
```

`HEAD`에는 커밋 해시가 아니라 `ref: refs/heads/main`, 즉 "`main` 브랜치를 보라"고 적혀 있다. 따라서 `HEAD`가 가리키는 커밋을 찾으려면 두 번 따라간다.

```
 HEAD ──▶ main ──▶ 9666df9
(.git/HEAD)  (.git/refs/heads/main)
```

`git log`에 장식(decoration)을 켜면 이 관계가 보인다. 터미널에서 직접 `git log`를 실행하면 장식이 기본으로 켜진다. 출력을 파이프로 넘길 때는 꺼지므로, 확실히 보려면 `--decorate`를 붙인다.

```
git log --oneline --decorate -3
```

```
9666df9 (HEAD -> main) 금액을 천 단위 쉼표로 표시
1ed2593 묶음 할인 기준을 README와 맞춤
98cad66 시험 스크립트 추가
```

`(HEAD -> main)`은 "`HEAD`가 `main`을 가리키고, `main`이 이 커밋을 가리킨다"는 뜻이다. 5장에서 `git log`를 할 때마다 보였던 그 표시다. VS Code 상태 표시줄의 브랜치 이름도 `HEAD`가 가리키는 브랜치다.

`HEAD`가 커밋이 아니라 브랜치를 가리키는 이유는 **커밋할 때** 드러난다. 커밋하면 Git은 다음 일을 한다.

1. 스테이징 영역의 스냅숏으로 새 커밋을 만든다. 부모는 `HEAD`가 가리키는 커밋(`9666df9`)이다.
2. `HEAD`가 가리키는 **브랜치**(`main`)의 이름표를 새 커밋으로 옮긴다.
3. `HEAD`는 여전히 `main`을 가리키므로 저절로 새 커밋을 보게 된다.

```
 커밋 전:   HEAD ──▶ main ──▶ 9666df9

 커밋 후:   HEAD ──▶ main ──▶ (새 커밋) ──부모──▶ 9666df9
```

5장에서 `main`에 커밋할 때마다 일어난 일이 이것이다. 브랜치가 하나뿐이어서 따로 의식할 일이 없었을 뿐이다. 브랜치가 여럿이 되면 "**`HEAD`가 가리키는 브랜치만 앞으로 나아간다**"는 것이 핵심이 된다. 6.2에서 확인한다.

### 6.1.4 그래프 그려 보기 — `git log --oneline --graph --all`

커밋과 부모의 연결을 머릿속으로만 그리기는 어렵다. 5.4.3에서 소개만 한 `--graph`가 그 그림을 그려 준다. 브랜치를 쓸 때 가장 자주 쓰는 모양은 다음 세 옵션의 조합이다.

```
git log --oneline --graph --all
```

```
* 02ac926 (feature/total-qty) 결과에 총 수량 표시
| * a8a641b (feature/coupon-percent) 시험에 퍼센트 할인율 검사 추가
| * 58e1368 쿠폰 할인율을 퍼센트로도 받기
|/  
| * 391a859 (feature/coupon-check) 시험에 쿠폰 할인율 범위 검사 추가
| * 8a23623 쿠폰 할인율의 범위 검사
|/  
* 9666df9 (HEAD -> main) 금액을 천 단위 쉼표로 표시
* 1ed2593 묶음 할인 기준을 README와 맞춤
* 98cad66 시험 스크립트 추가
* 2cd870d 쿠폰 할인 추가
* 356d0e1 묶음 할인 추가
* cb2bb27 주문 CSV 읽기 추가
* cb8185a 프로젝트 뼈대 만들기
```

| 옵션 | 하는 일 |
|---|---|
| `--oneline` | 커밋마다 한 줄 |
| `--graph` | 왼쪽에 커밋의 연결을 선으로 그린다 |
| `--all` | `HEAD`에서 닿는 커밋만이 아니라 **모든 브랜치**의 커밋을 보여 준다 |

그래프를 읽는 규칙은 다음과 같다.

- `*`는 커밋 하나다. 위가 최근, 아래가 과거다.
- `|`는 줄기다. 같은 세로줄의 `*`끼리 부모·자식으로 이어진다.
- `/`와 `\`는 줄기가 갈라지거나 합쳐지는 곳이다. 위 출력의 `|/`는 "오른쪽 줄기가 여기서 왼쪽 줄기로 들어간다", 즉 **오른쪽 갈래가 아래 커밋에서 갈라져 나왔다**는 뜻이다.
- 괄호 안의 이름은 그 커밋을 가리키는 브랜치다. 브랜치 이름은 갈래의 **끝**에만 붙는다.

위 그래프를 말로 읽으면 이렇다. "커밋 일곱 개가 한 줄로 이어져 `9666df9`까지 왔고, 지금 `main`이 거기에 있다(`HEAD -> main`). `9666df9`에서 세 갈래가 뻗어 나갔다. `feature/coupon-check`는 커밋 두 개, `feature/coupon-percent`도 두 개, `feature/total-qty`는 한 개 앞서 있다. 세 갈래 모두 아직 `main`에 합쳐지지 않았다."

`--all`을 빼면 어떻게 될까?

```
git log --oneline --graph
```

```
* 9666df9 (HEAD -> main) 금액을 천 단위 쉼표로 표시
* 1ed2593 묶음 할인 기준을 README와 맞춤
...
```

`HEAD`(`main`)에서 부모를 따라 닿는 커밋만 나온다. 이 절을 시작할 때 `git log`에 커밋이 일곱 개만 보였던 이유가 이것이다. 다른 브랜치의 커밋은 `main`의 조상이 아니므로 보이지 않는다. 특정 브랜치 몇 개만 보고 싶으면 `--all` 대신 이름을 적는다(`git log --oneline --graph main feature/total-qty`).

이번에는 **합쳐진** 이력이 있는 `guide` 저장소의 그래프를 읽는다.

```
cd ../guide
git log --oneline --graph --all
```

```
* 9ff1b6b (exp/docker) Docker 장 실험
*   38ec03f (HEAD -> main) Merge branch 'docs/vscode'
|\  
| * f666954 (docs/vscode) VS Code 장 초안
* | aaf3825 기여 방법 추가
|/  
* 1c3cad7 제목을 학습 안내서로 고침
*   8a529f5 Merge branch 'docs/git'
|\  
| * 456d80c Git 장에 브랜치 절 추가
| * d1acaa0 Git 장 초안
* | 52d26d9 터미널 장에 파이프 절 추가
|/  
* 8ad56d0 터미널 장 초안
* 3215956 가이드 목차 만들기
```

아래에서 위로 읽어 올라가면 이 저장소의 역사가 보인다.

1. `3215956`, `8ad56d0` — 한 줄로 커밋 두 개.
2. `8ad56d0`에서 두 갈래로 나뉜다(`|/`). 오른쪽 갈래(`d1acaa0`, `456d80c`)는 Git 장을 쓰던 `docs/git` 브랜치이고, 왼쪽 갈래(`52d26d9`)는 그동안 `main`에 쌓인 커밋이다.
3. `8a529f5 Merge branch 'docs/git'`에서 두 갈래가 **합쳐진다**(`|\`). 이 커밋이 **병합 커밋**이다. `*` 뒤에 공백이 여럿 있는 것, 바로 아래에 `|\`가 있는 것이 병합 커밋의 표시다. 부모가 둘이다(6.3.3).
4. `1c3cad7` — 갈래 없이 한 줄로 이어진다. 이 커밋은 사실 `fix/typo`라는 브랜치에서 만든 것인데, 병합할 때 **빨리 감기**(6.3.2)가 되어서 그래프에 갈래의 흔적이 남지 않았다.
5. 다시 갈라져(`docs/vscode`와 `main`의 `aaf3825`) `38ec03f`에서 합쳐진다. `docs/vscode` 브랜치는 병합한 뒤에도 지우지 않아서 이름표가 남아 있다.
6. 맨 위 `9ff1b6b`는 `exp/docker` 브랜치의 커밋이다. `main`(`38ec03f`) 바로 위에 이어져 있고 아직 합쳐지지 않았다.

`docs/git` 브랜치와 `fix/typo` 브랜치는 병합한 뒤 지웠으므로 이름이 보이지 않는다. 그래도 그 브랜치에서 만든 커밋은 그대로 남아 있다. 브랜치는 이름표일 뿐이라는 6.1.2의 설명 그대로다. 병합 커밋의 메시지(`Merge branch 'docs/git'`)가 그 브랜치가 있었다는 기록이 된다.

> **자주 쓰는 명령은 Git 별칭으로**
> `git log --oneline --graph --all`은 이 장에서 수십 번 쓴다. 3.4.3에서 셸 설정 파일에 별칭을 만들었듯이 Git에도 별칭(alias)이 있다. 다음처럼 정해 두면 `git graph`로 같은 명령이 실행된다. Git 별칭은 `~/.gitconfig`에 저장되므로 zsh와 PowerShell 어디서나 같게 쓸 수 있다.
> ```
> git config --global alias.graph "log --oneline --graph --all"
> git graph
> ```
> 이 교재에서는 별칭을 정하지 않은 사람도 따라 할 수 있도록 원래 명령을 그대로 적는다.

VS Code에서는 소스 제어 보기 아래쪽의 **Graph**(버전에 따라 Source Control Graph) 영역이 같은 그림을 보여 준다(5.4.8). 기본 설정에서는 지금 브랜치와 관련된 갈래만 보여 주는 경우가 많다. Graph 영역 제목줄의 브랜치 선택 단추(마우스를 올리면 나타난다)에서 보여 줄 브랜치를 고르면 `--all`처럼 여러 브랜치를 함께 볼 수 있다. 단추의 모양과 이름은 버전에 따라 조금 다르다. 그래프의 커밋을 누르면 그 커밋에서 바뀐 파일이 펼쳐진다.

### 실습 6-1. 그래프 읽기

`practice/guide`에서 한다. 결과는 `~/devtools-lab/ch06/graph.md`에 적는다.

1. `git log --all --format="%h %p %s"`를 실행한다. 부모가 둘인 커밋을 모두 찾아 적고, 부모가 없는 커밋도 찾아 적는다.
2. 1번의 출력만 보고 종이에 커밋 그래프를 그린다(화살표는 부모 쪽으로). 다 그렸으면 `git log --oneline --graph --all`과 비교한다.
3. `cat .git/HEAD`와 `git branch -v`를 실행해, 지금 있는 브랜치와 각 브랜치가 가리키는 커밋을 적는다. `.git/refs/heads` 아래에는 어떤 파일과 폴더가 있는가?
4. `git log --oneline --graph`(`--all` 없이)를 실행한다. 3번의 그래프와 비교해 보이지 않게 된 커밋은 무엇이고, 왜 보이지 않는지 적는다.
5. 다음 질문에 그래프를 근거로 답한다.
   - `vscode.md` 파일을 처음 만든 커밋과, 그 파일이 `main`에 들어온 커밋은 각각 무엇인가? `git log --oneline -- vscode.md`에는 커밋이 하나만 나온다. 병합 커밋 `38ec03f`가 결과에 나오지 않는 이유를 생각해 본다(힌트: 병합 커밋은 첫째 부모와 비교하면 `vscode.md`를 더했지만, 둘째 부모와 비교하면 바꾼 것이 없다. 6.3.4).
   - `docker.md`는 지금 `main`에 있는가? `git show main:docker.md`와 `git show exp/docker:docker.md`(5.4.4)로 확인한다.
   - `1c3cad7`은 어떤 브랜치에서 만든 커밋인가? 그래프만 보고 알 수 있는가? 알 수 있다면 어디서, 없다면 왜 없는지 적는다.
6. VS Code로 `guide` 폴더를 열고 소스 제어 보기의 Graph에서 같은 그래프를 찾는다. `exp/docker`의 커밋이 보이지 않으면 브랜치 선택 단추로 보여 줄 브랜치를 바꾼다. 병합 커밋을 눌러 무엇이 보이는지 적는다.

## 6.2 브랜치 다루기

이 절에서는 `practice/shop`에서 브랜치를 직접 만들고, 옮겨 다니고, 지운다. 이 절에서 만드는 브랜치는 모두 연습용이라 절이 끝날 때 지운다. `main`과 세 `feature/` 브랜치는 6.3에서 병합하므로 건드리지 않는다.

```
cd ~/devtools-lab/ch06/practice/shop
git status
```

`On branch main`, `nothing to commit, working tree clean`이 나와야 한다.

### 6.2.1 브랜치 만들기와 목록 — `git branch`

금액을 오른쪽으로 가지런히 맞춰 보는 실험을 하려고 한다. 결과가 마음에 들지 않을 수도 있으니 `main`이 아니라 새 브랜치에서 한다. 브랜치는 `git branch 이름`으로 만든다.

```
git branch exp/align
git branch
```

```
  exp/align
  feature/coupon-check
  feature/coupon-percent
  feature/total-qty
* main
```

`exp/align`이 생겼다. 이름 앞의 `exp/`는 "실험"이라는 뜻으로 붙인 것이다. 브랜치 이름 규칙은 6.5.3에서 다룬다. 목록에서 `*`는 여전히 `main`에 붙어 있다. **`git branch 이름`은 브랜치를 만들기만 하고 옮겨 가지 않는다.**

```
git log --oneline --decorate -1
```

```
9666df9 (HEAD -> main, exp/align) 금액을 천 단위 쉼표로 표시
```

새 브랜치는 **지금 `HEAD`가 가리키는 커밋**을 가리키며 생긴다. `main`과 `exp/align` 두 이름표가 같은 커밋에 붙어 있고, `HEAD`는 아직 `main`을 가리킨다.

```
 HEAD ──▶ main ──────┐
                     ▼
                  9666df9
                     ▲
          exp/align ─┘
```

다른 커밋에서 시작하는 브랜치를 만들려면 이름 뒤에 커밋을 준다. 예를 들어 `git branch fix/old 1ed2593`은 `1ed2593`을 가리키는 `fix/old` 브랜치를 만든다. 커밋 대신 다른 브랜치 이름을 줄 수도 있다.

`git branch`의 자주 쓰는 모양을 정리한다.

| 명령 | 하는 일 |
|---|---|
| `git branch` | 브랜치 목록. `*`가 지금 브랜치 |
| `git branch -v` | 각 브랜치가 가리키는 커밋까지 |
| `git branch 이름` | `HEAD`에서 브랜치 만들기(옮겨 가지 않는다) |
| `git branch 이름 시작점` | 시작점(커밋·브랜치)에서 브랜치 만들기 |
| `git branch -m 옛이름 새이름` | 이름 바꾸기(6.2.6) |
| `git branch -d 이름` | 지우기. 병합되지 않은 브랜치는 거절한다(6.2.6) |
| `git branch -D 이름` | 병합 여부를 따지지 않고 지우기(6.2.6) |

### 6.2.2 브랜치 옮겨 가기 — `git switch`

브랜치를 옮기는 명령은 `git switch`다.

```
git switch exp/align
```

```
Switched to branch 'exp/align'
```

```
cat .git/HEAD
git status
```

```
ref: refs/heads/exp/align
```

```
On branch exp/align
nothing to commit, working tree clean
```

`.git/HEAD`의 내용이 `refs/heads/exp/align`으로 바뀌었다. **브랜치를 옮긴다는 것은 `HEAD`가 가리키는 브랜치를 바꾸는 것이다.** VS Code 상태 표시줄의 브랜치 이름도 `exp/align`으로 바뀐다.

```
git log --oneline --decorate -1
```

```
9666df9 (HEAD -> exp/align, main) 금액을 천 단위 쉼표로 표시
```

두 브랜치가 같은 커밋을 가리키고 있으므로 작업 폴더의 파일은 아무것도 바뀌지 않았다. 바뀐 것은 `HEAD`뿐이다.

```
          main ──────┐
                     ▼
                  9666df9
                     ▲
 HEAD ──▶ exp/align ─┘
```

### 6.2.3 브랜치에 커밋하기

`exp/align`에서 실험을 한다. VS Code에서 `shop/cli.py`의 `won()` 함수를 다음과 같이 고치고 저장한다. 형식 지정의 `>8`은 "8칸에 오른쪽으로 맞춘다"는 뜻이다.

```python
def won(amount: int) -> str:
    """금액을 '1,234원' 모양으로 돌려준다."""
    return f"{amount:>8,}원"
```

```
git diff
```

```
diff --git a/shop/cli.py b/shop/cli.py
index 3b70115..c2d0551 100644
--- a/shop/cli.py
+++ b/shop/cli.py
@@ -11,7 +11,7 @@ USAGE = "사용법: python main.py 주문파일.csv"

실행해 본다. 이 장에서는 macOS의 `python3`로 적는다. Windows에서는 `python`으로 바꿔 실행한다.

출력이 실험 전으로 돌아왔다. VS Code에 열어 둔 `shop/cli.py`도 `return f"{amount:,}원"`으로 바뀌어 있다. 실험이 사라진 것은 아니다. `exp/align` 브랜치의 커밋 `a23e44f`에 그대로 있다.

`git switch`는 `HEAD`를 옮기면서 **작업 폴더와 스테이징 영역을 옮겨 간 브랜치의 커밋 스냅숏으로 바꾼다.** 두 커밋에서 내용이 다른 파일만 바꾸고, 같은 파일은 건드리지 않는다. 한쪽 커밋에만 있는 파일은 옮겨 갈 때 생기거나 사라진다. 그래서 브랜치를 옮길 때마다 VS Code 탐색기의 파일 목록이 달라질 수 있다.

> **`git switch -`**
> `cd -`가 바로 전 폴더로 돌아가듯이(2.6.1), `git switch -`는 **바로 전 브랜치**로 돌아간다. 두 브랜치를 오가며 비교할 때 편하다.

### 6.2.4 만들면서 옮겨 가기 — `git switch -c`

브랜치를 만들고 곧바로 옮겨 가는 일이 가장 흔하므로 한 번에 하는 옵션이 있다. `-c`는 create(만들기)다.

```
git switch -c exp/test
git log --oneline --decorate -1
```

```
Switched to a new branch 'exp/test'
```

```
9666df9 (HEAD -> exp/test, main) 금액을 천 단위 쉼표로 표시
```

`git branch exp/test` 다음에 `git switch exp/test`를 한 것과 같다. 시작점을 줄 수도 있다. `git switch -c fix/old 1ed2593`은 `1ed2593`에서 `fix/old`를 만들고 옮겨 간다. 아무 커밋도 하지 않은 `exp/test`는 바로 지운다. 지우는 방법은 6.2.6에서 자세히 본다.

```
git switch main
git branch -d exp/test
```

```
Switched to branch 'main'
```

```
Deleted branch exp/test (was 9666df9).
```

**새 브랜치는 지금 있는 곳에서 갈라진다**는 점을 기억한다. 기능 브랜치를 만들 때는 보통 `main`에서 시작해야 한다. 다른 기능 브랜치에 있는 채로 `git switch -c`를 하면, 새 브랜치에 그 기능의 커밋까지 딸려 온다. 그래서 새 일을 시작할 때는 먼저 `git switch main`을 하고, `git status`로 깨끗한지 본 뒤 `git switch -c`를 한다(6.5.5).

### 6.2.5 커밋하지 않은 변경이 있을 때 옮기면

커밋하지 않은 변경이 있을 때 브랜치를 옮기면 어떻게 될까? 세 가지 경우를 차례로 해 본다.

**경우 1: 두 브랜치에서 내용이 같은 파일을 고쳤을 때.** `main`에서 `README.md`의 끝에 빈 줄과 `메모: 브랜치 실습 중`이라는 줄을 더하고 저장한다. 새 파일 `todo.txt`도 하나 만든다(내용은 아무것이나).

```
git status -s
```

```
 M README.md
?? todo.txt
```

이 상태로 `exp/align`으로 옮겨 간다.

```
git switch exp/align
```

```
Switched to branch 'exp/align'
M	README.md
```

옮겨 갔다. 둘째 줄의 `M	README.md`는 "`README.md`의 커밋하지 않은 변경을 가지고 왔다"는 안내다.

```
git status -s
```

```
 M README.md
?? todo.txt
```

`main`에서 한 변경이 `exp/align`에서도 그대로 보인다. `README.md`는 `main`과 `exp/align`의 커밋에서 내용이 같으므로, Git은 작업 폴더의 `README.md`를 건드릴 필요가 없었다. 추적하지 않는 `todo.txt`는 애초에 Git이 관리하지 않으므로 그대로 남는다. 다시 `main`으로 돌아가도 마찬가지다.

```
git switch main
```

```
Switched to branch 'main'
M	README.md
```

**경우 2: 두 브랜치에서 내용이 다른 파일을 고쳤을 때.** 이번에는 `main`에서 `shop/cli.py`의 `USAGE`를 `"사용법: python main.py 주문파일.csv (예: orders/small.csv)"`로 고치고 저장한다. `won()` 함수와는 떨어진 줄이다.

```
git switch exp/align
```

```
error: Your local changes to the following files would be overwritten by checkout:
	shop/cli.py
Please commit your changes or stash them before you switch branches.
Aborting
```

**거절되었다.** "로컬 변경이 브랜치를 옮기면 덮어써진다. 브랜치를 옮기기 전에 커밋하거나 stash하라"는 뜻이다. `shop/cli.py`는 `main`과 `exp/align`에서 내용이 다르므로, 옮겨 가려면 작업 폴더의 `shop/cli.py`를 `exp/align`의 것으로 바꿔야 한다. 그러면 내가 고친 `USAGE`가 사라지므로 Git이 멈춘 것이다. 고친 곳이 `won()`과 떨어진 줄이어도 거절된다. Git은 파일 단위로 판단한다. 아무것도 바뀌지 않았다(`Aborting`). `git status -s`를 해 보면 그대로다.

**경우 3: 추적하지 않는 파일이 옮겨 갈 브랜치에 있는 파일과 이름이 같을 때.** 이 저장소에서 해 보기는 어렵지만, 알아 두자. 내가 새로 만든 `notes.md`가 아직 추적되지 않는데 옮겨 갈 브랜치에는 `notes.md`가 커밋되어 있다면, 옮기면 내 파일이 덮어써진다. 이때도 `The following untracked working tree files would be overwritten by checkout`이라며 거절된다.

정리하면 다음과 같다.

| 상황 | `git switch`의 동작 |
|---|---|
| 고친 파일이 두 브랜치에서 같다 | 옮겨 가고, 변경은 **따라온다** |
| 고친 파일이 두 브랜치에서 다르다 | **거절한다**(아무것도 바꾸지 않는다) |
| 추적하지 않는 파일 | 따라온다. 옮겨 갈 브랜치에 같은 이름의 파일이 있으면 거절한다 |

여기서 꼭 기억할 점이 있다. **커밋하지 않은 변경은 어느 브랜치에도 속하지 않는다.** 작업 폴더와 스테이징 영역은 저장소에 하나뿐이고, 브랜치를 옮겨도 그 내용이 브랜치에 보관되지 않는다. 경우 1처럼 변경이 따라오면 "다른 브랜치로 옮겼으니 `main`은 안전하다"고 착각하기 쉽다. 변경은 그대로 내 앞에 있다. 7장에서 AI 코딩 도구에게 일을 맡기기 전에 "브랜치를 만드는 것만으로는 커밋하지 않은 변경이 보존되지 않는다"고 하는 이유가 이것이다.

이 성질이 쓸모 있을 때도 있다. 새 브랜치를 만드는 것을 잊고 `main`에서 고치기 시작했다면, 그 자리에서 `git switch -c feature/새기능`을 한다. 새 브랜치는 지금 커밋에서 갈라지므로 두 브랜치의 파일이 모두 같고, 변경이 그대로 따라온다. 그다음 새 브랜치에서 커밋하면 `main`은 깨끗하게 남는다.

거절되었을 때 할 수 있는 일은 세 가지다.

1. **지금 브랜치에 커밋한다.** 아직 덜 된 작업이라면 메시지에 그렇게 적는다. 커밋을 나중에 다듬는 방법은 7장에서 배운다.
2. **변경을 버린다.** 필요 없는 변경이면 5.7의 `git restore`로 버린다. 되살릴 수 없다는 점을 잊지 않는다.
3. **변경을 잠시 치워 둔다.** `git stash`라는 명령이 있다. 7장에서 배운다.

`git switch`에 `--discard-changes`(또는 `-f`)를 붙이면 거절하지 않고 내 변경을 버리고 옮겨 간다. 되살릴 수 없으므로 이 과정에서는 쓰지 않는다. VS Code에서 브랜치를 바꾸다 같은 상황이 되면 변경을 치워 두고(stash) 옮길지 묻는 대화 상자가 나올 수 있다. 무엇을 하는 버튼인지 아직 모르므로 지금은 취소한다.

실험을 정리한다. 경우 2에서 고친 `shop/cli.py`와 경우 1의 `README.md`를 되돌리고 `todo.txt`를 지운다.

```
git restore README.md shop/cli.py
```

`todo.txt`는 VS Code 탐색기나 터미널(`rm todo.txt`, Windows `Remove-Item todo.txt`)로 지운다. `git status`가 `working tree clean`인지 확인한다.

### 6.2.6 브랜치 이름 바꾸기와 지우기

**이름 바꾸기**는 `git branch -m`이다(move의 m).

```
git branch -m exp/align exp/right-align
git branch
```

```
  exp/right-align
  feature/coupon-check
  feature/coupon-percent
  feature/total-qty
* main
```

지금 있는 브랜치의 이름을 바꿀 때는 옛 이름을 빼고 `git branch -m 새이름`만 쓴다. 이름표의 이름만 바뀔 뿐 가리키는 커밋은 그대로다.

5.2.3에서 예고한 일을 여기서 한다. `practice/old`는 기본 브랜치 이름을 `main`으로 정하기 전에 만든 저장소라 브랜치 이름이 `master`다.

```
cd ../old
git branch
```

```
* master
```

```
git branch -m master main
git branch
```

```
* main
```

내 컴퓨터의 저장소에서는 이것으로 끝이다. GitHub에 이미 올린 저장소라면 GitHub 쪽의 기본 브랜치 이름도 바꿔야 하는데, 그 방법은 8장에서 다룬다. 실습 5-3에서 저장소로 만든 내 폴더들이 `master`로 되어 있다면(5.2.3의 설정을 하기 전에 `git init`했다면) 같은 방법으로 바꾼다.

다시 `shop`으로 돌아가 **브랜치를 지운다.** 지우는 명령은 `git branch -d`다(delete의 d). `exp/right-align`의 실험은 빼기 기호가 떨어져 보기 좋지 않으므로 버리기로 한다.

```
cd ../shop
git branch -d exp/right-align
```

```
error: the branch 'exp/right-align' is not fully merged
hint: If you are sure you want to delete it, run 'git branch -D exp/right-align'
hint: Disable this message with "git config set advice.forceDeleteBranch false"
```

거절되었다. "이 브랜치는 완전히 병합되지 않았다. 정말 지우려면 `-D`를 쓰라"는 뜻이다. `exp/right-align`에는 `main`에 없는 커밋(`a23e44f`)이 있다. 이 브랜치를 지우면 그 커밋을 가리키는 이름표가 하나도 없게 되므로, Git이 실수일지 모른다고 한 번 막아 준 것이다. 병합(6.3)해서 그 커밋이 `main`에도 들어 있다면 `-d`로 바로 지워진다.

실험을 버리기로 한 것이 맞으므로 `-D`로 지운다.

```
git branch -D exp/right-align
```

```
Deleted branch exp/right-align (was a23e44f).
```

`(was a23e44f)`는 지운 브랜치가 가리키던 커밋이다. 이름표를 떼었을 뿐 커밋은 저장소에 한동안 남아 있으므로, 마음이 바뀌면 이 해시로 브랜치를 다시 만들 수 있다(`git branch exp/right-align a23e44f`). 터미널을 닫아 이 해시를 잃어버렸어도 찾는 방법이 있다. 7장의 `git reflog`다.

**지금 있는 브랜치는 지울 수 없다.**

```
git branch -d main
```

```
error: cannot delete branch 'main' used by worktree at '/Users/jinyoung/devtools-lab/ch06/practice/shop'
```

"이 작업 폴더(worktree)에서 쓰고 있는 브랜치는 지울 수 없다"는 뜻이다. 다른 브랜치로 옮긴 뒤에 지운다. (worktree는 7장에서 배운다. 지금은 "지금 작업 폴더"로 읽는다.)

| 명령 | 지우는 조건 |
|---|---|
| `git branch -d 이름` | 그 브랜치의 커밋이 모두 지금 브랜치(또는 그 브랜치가 따라가는 원격 브랜치, 8장)에 병합되어 있을 때만 |
| `git branch -D 이름` | 따지지 않고 지운다. 병합하지 않은 커밋은 이름표를 잃는다 |

평소에는 `-d`를 쓴다. `-d`가 거절하면 지우려는 브랜치에 정말 버려도 되는 것만 있는지 `git log main..이름`(6.3.4)으로 확인한 뒤 `-D`를 쓴다.

### 6.2.7 브랜치가 아닌 커밋으로 가기 — detached HEAD

5장 실습 5-1에서 `git show HEAD~4:shop/pricing.py`로 지난 커밋의 파일을 하나씩 꺼내 보았다. 지난 커밋 시점의 **프로젝트 전체**로 가서 프로그램을 실행해 보고 싶을 때도 있다. "이 버그는 언제부터 있었나", "옛 버전은 어떻게 동작했나"를 확인할 때다.

`git switch`에 커밋 해시를 주면 어떻게 될까? 묶음 할인 버그를 고치기 전 커밋인 `98cad66`(시험 스크립트 추가)으로 가 본다.

```
git switch 98cad66
```

```
fatal: a branch is expected, got commit '98cad66'
hint: If you want to detach HEAD at the commit, try again with the --detach option.
```

"브랜치를 기대했는데 커밋이 왔다. 그 커밋에 `HEAD`를 떼어 붙이려면(detach) `--detach`를 붙여 다시 하라"는 뜻이다. `git switch`는 실수를 막으려고 브랜치가 아닌 곳으로 가는 것을 한 번 확인받는다.

```
git switch --detach 98cad66
```

```
HEAD is now at 98cad66 시험 스크립트 추가
```

```
cat .git/HEAD
git status
```

```
98cad66f74079abd08cea7434d361641d8bbd07d
```

```
HEAD detached at 98cad66
nothing to commit, working tree clean
```

`.git/HEAD`에 브랜치 이름이 아니라 **커밋 해시가 직접** 적혔다. `HEAD`가 브랜치를 거치지 않고 커밋을 바로 가리키는 이 상태를 **detached HEAD**(떨어진 HEAD)라고 한다. 브랜치에서 `HEAD`가 떨어져 나왔다는 뜻이다.

```
 보통:          HEAD ──▶ main ──▶ 9666df9

 detached HEAD: HEAD ──────────▶ 98cad66        main ──▶ 9666df9
```

```
git log --oneline --graph --all
```

```
* 02ac926 (feature/total-qty) 결과에 총 수량 표시
| * a8a641b (feature/coupon-percent) 시험에 퍼센트 할인율 검사 추가
| * 58e1368 쿠폰 할인율을 퍼센트로도 받기
|/  
| * 391a859 (feature/coupon-check) 시험에 쿠폰 할인율 범위 검사 추가
| * 8a23623 쿠폰 할인율의 범위 검사
|/  
* 9666df9 (main) 금액을 천 단위 쉼표로 표시
* 1ed2593 묶음 할인 기준을 README와 맞춤
* 98cad66 (HEAD) 시험 스크립트 추가
* 2cd870d 쿠폰 할인 추가
* 356d0e1 묶음 할인 추가
* cb2bb27 주문 CSV 읽기 추가
* cb8185a 프로젝트 뼈대 만들기
```

`(HEAD)`가 화살표 없이 `98cad66`에 붙어 있다. 작업 폴더는 이 커밋 시점의 모습이다. 시험을 돌려 본다.

```
python3 check_orders.py
```

```
[통과] small.csv gross: 기대 28500, 결과 28500
[실패] small.csv bulk: 기대 1800, 결과 600
[통과] small.csv coupon: 기대 0, 결과 0
[실패] small.csv total: 기대 26700, 결과 27900
[통과] broken.csv: ValueError

```

5장 5.4.4에서 읽은 대로 이 시점에는 묶음 할인 버그(`qty > 10`)가 있어서 시험이 실패한다. 이렇게 지난 시점으로 가서 **실행해 보는 것**이 detached HEAD의 주된 쓰임이다. 7장의 `git bisect`는 이 일을 자동으로 되풀이해 버그가 들어온 커밋을 찾는다.

VS Code 상태 표시줄에는 브랜치 이름 대신 커밋 해시(`98cad66`)가 보인다. `git branch`의 목록에는 `* (HEAD detached at 98cad66)`이 나온다.

**detached HEAD에서 커밋하면** 어떻게 될까? `README.md`의 끝에 빈 줄과 `임시: 이 시점의 시험 결과는 2건 실패`라는 줄을 더하고 커밋한다.

```
git add README.md
git commit -m "임시 메모"
```

```
[detached HEAD 030812d] 임시 메모
 1 file changed, 2 insertions(+)
```

커밋은 된다. 대괄호 안에 브랜치 이름 대신 `detached HEAD`가 나온다. 이때 움직일 브랜치가 없으므로 `HEAD` 자신이 새 커밋으로 옮겨 간다.

```
git log --oneline --graph --all
```

```
* 030812d (HEAD) 임시 메모
| * 02ac926 (feature/total-qty) 결과에 총 수량 표시
| | * a8a641b (feature/coupon-percent) 시험에 퍼센트 할인율 검사 추가
| | * 58e1368 쿠폰 할인율을 퍼센트로도 받기
| |/  
| | * 391a859 (feature/coupon-check) 시험에 쿠폰 할인율 범위 검사 추가
| | * 8a23623 쿠폰 할인율의 범위 검사
| |/  
| * 9666df9 (main) 금액을 천 단위 쉼표로 표시
| * 1ed2593 묶음 할인 기준을 README와 맞춤
|/  
* 98cad66 시험 스크립트 추가
* 2cd870d 쿠폰 할인 추가
* 356d0e1 묶음 할인 추가
* cb2bb27 주문 CSV 읽기 추가
* cb8185a 프로젝트 뼈대 만들기
```

`98cad66`에서 새 갈래가 생겼고, 그 끝 `030812d`에는 `HEAD`만 붙어 있다. **브랜치 이름표가 없는 갈래**다. 이 상태에서 `main`으로 돌아간다.

```
git switch main
```

```
Warning: you are leaving 1 commit behind, not connected to
any of your branches:

  030812d 임시 메모

If you want to keep it by creating a new branch, this may be a good time
to do so with:

 git branch <new-branch-name> 030812d

Switched to branch 'main'
```

"어느 브랜치와도 연결되지 않은 커밋 하나를 두고 떠난다. 남기고 싶다면 지금 `git branch 새이름 030812d`로 브랜치를 만들라"는 경고다. `HEAD`가 떠나면 `030812d`를 가리키는 이름이 하나도 남지 않는다. `git log --all`에도 더는 나오지 않으므로, 해시를 적어 두지 않았다면 찾기 어려워진다(7장의 `git reflog`로는 찾을 수 있다). 이것이 detached HEAD에서 조심할 점이다. **detached HEAD에서는 둘러보기만 하고, 커밋을 남기고 싶으면 브랜치를 만든다.**

이 커밋을 살리고 싶다면 안내대로 한다.

```
git branch rescue/memo 030812d
git log --oneline --graph --all
```

```
* 030812d (rescue/memo) 임시 메모
| * 02ac926 (feature/total-qty) 결과에 총 수량 표시
...
| * 9666df9 (HEAD -> main) 금액을 천 단위 쉼표로 표시
| * 1ed2593 묶음 할인 기준을 README와 맞춤
|/  
* 98cad66 시험 스크립트 추가
...
```

이름표가 붙었으므로 이제 잃어버리지 않는다. detached HEAD 상태에 **있는 동안** 브랜치를 만들려면 `git switch -c 새이름`을 하면 된다. 지금 커밋에서 새 브랜치가 생기고 `HEAD`가 거기에 붙는다.

이 메모는 연습이었으므로 지운다.

```
git branch -D rescue/memo
```

```
Deleted branch rescue/memo (was 030812d).
```

detached HEAD에서 빠져나오는 방법은 간단하다. **브랜치로 `git switch`하면 된다.** 커밋하지 않았다면 경고도 없다. 방금 있던 브랜치로 돌아가려면 `git switch -`도 된다.

> **detached HEAD는 오류가 아니다**
> 처음 보면 놀라지만 detached HEAD는 고장 난 상태가 아니다. 지난 커밋을 둘러보는 정상적인 방법이다. 8장 이후에 GitHub의 풀 리퀘스트를 내려받거나, 7장에서 태그로 지난 버전에 가 볼 때, `git rebase`나 `git bisect`를 하는 동안에도 이 상태가 된다. 상태 표시줄이나 `git status`에서 `HEAD detached`를 보면 "지금은 브랜치 위에 있지 않다. 여기서 한 커밋은 브랜치를 만들지 않으면 잃기 쉽다"고 읽는다.

### 6.2.8 옛 명령 `git checkout`과 VS Code

5.7.7에서 `git checkout`이 파일 되돌리기와 브랜치 옮기기를 모두 하던 명령이라고 했다. `git switch`는 Git 2.23(2019년)에 브랜치 옮기기만 떼어 내 만든 명령이다. 인터넷의 글과 AI의 답에는 `git checkout`이 아직 많이 나온다.

| 옛 명령 | 지금 명령 |
|---|---|
| `git checkout 브랜치` | `git switch 브랜치` |
| `git checkout -b 새브랜치` | `git switch -c 새브랜치` |
| `git checkout -b 새브랜치 시작점` | `git switch -c 새브랜치 시작점` |
| `git checkout 커밋` | `git switch --detach 커밋` |
| `git checkout -` | `git switch -` |
| `git checkout -- 파일` | `git restore 파일`(5.7.7) |

`git checkout 커밋`은 `--detach` 없이도 바로 detached HEAD로 간다. 그 대신 긴 안내를 보여 준다.

```
git checkout 98cad66
```

```
Note: switching to '98cad66'.

You are in 'detached HEAD' state. You can look around, make experimental
changes and commit them, and you can discard any commits you make in this
state without impacting any branches by switching back to a branch.

If you want to create a new branch to retain commits you create, you may
do so (now or later) by using -c with the switch command. Example:

  git switch -c <new-branch-name>

Or undo this operation with:

  git switch -

Turn off this advice by setting config variable advice.detachedHead to false

HEAD is now at 98cad66 시험 스크립트 추가
```

"detached HEAD 상태다. 둘러보고 실험하고 커밋해도 되지만, 브랜치로 돌아가면 그 커밋은 버려진다. 남기려면 `git switch -c`로 브랜치를 만들라. 되돌리려면 `git switch -`"라는 뜻이다. 이 절에서 배운 내용이 그대로 들어 있다. 안내대로 돌아간다.

```
git switch -
```

```
Previous HEAD position was 98cad66 시험 스크립트 추가
Switched to branch 'main'
```

`git checkout 이름`은 그 이름이 브랜치이면 브랜치를 옮기고, 파일이면 파일을 되돌린다. 브랜치와 같은 이름의 파일이 있으면 헷갈리고, 파일 이름을 잘못 적으면 의도치 않게 변경을 버릴 수도 있다. 새 명령을 쓰는 이유다.

VS Code에서는 다음과 같다. 명령 팔레트의 명령 이름은 버전에 따라 조금 다르다.

| VS Code | 명령 |
|---|---|
| 상태 표시줄 왼쪽의 브랜치 이름 | `git branch`(지금 브랜치). 누르면 브랜치 목록이 열린다 |
| 브랜치 목록에서 브랜치 고르기, 명령 팔레트 **Git: Checkout to...** | `git switch 브랜치` |
| 목록의 **+ Create new branch...**, **Git: Create Branch...** | `git switch -c 새브랜치` |
| 목록의 **+ Create new branch from...**, **Git: Create Branch From...** | `git switch -c 새브랜치 시작점` |
| 목록의 **Checkout detached...** | `git switch --detach 커밋` |
| **Git: Rename Branch...** | `git branch -m 새이름` |
| **Git: Delete Branch...** | `git branch -d 이름`. 병합되지 않았으면 강제로 지울지(`-D`) 다시 묻는다 |

### 실습 6-2. 브랜치 다루기

결과는 `~/devtools-lab/ch06/branch.md`에 적는다.

1. **브랜치와 HEAD 관찰** — `practice/guide`에서 한다.
   - `git switch -c fix/heading`을 실행하고 `cat .git/HEAD`, `cat .git/refs/heads/fix/heading`, `git log --oneline --decorate -1`의 결과를 적는다.
   - `README.md`의 첫 줄 `# 개발 도구 학습 안내서`를 `# 개발 도구 학습 안내서 (2026)`로 고쳐 커밋한다. 커밋 결과의 대괄호 안에 무엇이 나오는지 적는다.
   - 커밋 전과 후에 `cat .git/refs/heads/fix/heading`과 `cat .git/refs/heads/main`의 내용이 각각 어떻게 바뀌었는지 비교해 적는다. 어느 쪽이 바뀌었고, 왜인가?

2. **변경을 가지고 옮기기** — 같은 저장소에서 한다.

3. **잊고 `main`에서 시작한 작업** — 같은 저장소의 `main`에서 `vscode.md`의 끝에 `## 단축키` 절(두세 줄)을 더한다. 그다음에야 "브랜치를 만들 걸" 하고 깨달았다고 하자. `main`에 커밋하지 않고 `docs/vscode-keys` 브랜치로 옮겨 커밋하는 명령을 찾아 실행한다. 마지막에 `git log --oneline --graph --all`과 `git status`를 적고, `main`이 바뀌지 않았음을 확인한다.
4. **이름 바꾸기와 지우기**
   - `fix/heading`의 이름을 `fix/title-year`로 바꾼다.
   - `git branch -d fix/title-year`와 `git branch -d docs/vscode-keys`를 실행해 결과를 적는다. 거절되었다면 그 이유를 적는다. (지우지 말고 둔다. 실습 6-3에서 쓴다.)
   - `git branch -d docs/vscode`를 실행한다. 이번에는 지워지는가? 6.1.4의 그래프를 근거로 이유를 적는다.
5. **detached HEAD** — `practice/shop`에서 한다.

6. **내 저장소** — 5장에서 저장소로 만든 `~/devtools-lab/ch04/practice/shop`과 `~/devtools-lab/ch01`에서 `git branch`를 실행한다. 브랜치 이름이 `master`라면 `main`으로 바꾼다. 바꿨다면 VS Code 상태 표시줄도 바뀌었는지 확인한다.

   - `git checkout -b feature/report`
   - `git checkout HEAD~3`
   - `git checkout main`
   - `git checkout -- README.md`

## 6.3 병합

브랜치에서 한 작업이 끝나면 `main`에 합친다. 이것을 **병합**(merge)이라고 한다. 이 절에서는 `practice/shop`의 세 브랜치 중 둘을 `main`에 병합한다. 나머지 하나(`feature/coupon-percent`)는 6.4에서 충돌과 함께 병합한다.

### 6.3.1 `git merge` — 받아들이는 쪽에서 실행한다

`git merge 브랜치`는 **그 브랜치의 변경을 지금 브랜치로 가져온다.** 방향이 중요하다.

- 변경을 **받아들일** 브랜치로 먼저 옮겨 간다. `main`에 합치려면 `git switch main`.
- 그다음 **가져올** 브랜치의 이름을 준다. `git merge feature/coupon-check`.
- 움직이는 것은 지금 브랜치(`main`)뿐이다. 가져온 브랜치는 그대로 남는다.

"`feature/coupon-check`를 `main`에 병합한다"는 말을 명령으로 옮기면 `git switch main` 다음에 `git merge feature/coupon-check`다. 거꾸로 `feature/coupon-check`에 있는 채로 `git merge main`을 하면 `main`의 변경을 기능 브랜치로 가져오는 것이 된다. 이것도 쓸모가 있지만(6.4.9) 지금 하려는 일은 아니다.

병합하기 전에 두 가지를 확인하는 습관을 들인다.

1. **작업 폴더가 깨끗한가.** 커밋하지 않은 변경이 있으면 6.2.5처럼 병합이 거절되거나, 병합 결과와 내 변경이 섞여 무엇이 병합으로 들어왔는지 알기 어려워진다.
2. **무엇이 들어오는가.** 가져올 브랜치에만 있는 커밋과 그 변경을 미리 본다.

```
git switch main
git status
git log --oneline main..feature/coupon-check
```

```
Already on 'main'
```

```
On branch main
nothing to commit, working tree clean
```

```
391a859 시험에 쿠폰 할인율 범위 검사 추가
8a23623 쿠폰 할인율의 범위 검사
```

`main..feature/coupon-check`는 "`feature/coupon-check`에서 닿는 커밋 중 `main`에서는 닿지 않는 것", 즉 **병합하면 `main`에 새로 들어올 커밋**이다(6.3.4). 변경 내용을 파일 단위로 보려면 점을 세 개 쓴다.

```
git diff --stat main...feature/coupon-check
```

```
 README.md       |  2 +-
 check_orders.py | 11 ++++++++++-
 shop/pricing.py | 11 +++++++++--
 3 files changed, 20 insertions(+), 4 deletions(-)
```

`main...feature/coupon-check`(점 셋)는 "두 브랜치가 갈라진 지점부터 `feature/coupon-check`까지 바뀐 것", 즉 **그 브랜치에서 한 일**이다. `--stat`을 빼면 diff 전체를 볼 수 있다. 8장에서 GitHub의 풀 리퀘스트가 "변경된 파일" 화면에 보여 주는 것이 바로 이 diff다.

### 6.3.2 빨리 감기(fast-forward)

병합한다.

```
git merge feature/coupon-check
```

```
Updating 9666df9..391a859
Fast-forward
 README.md       |  2 +-
 check_orders.py | 11 ++++++++++-
 shop/pricing.py | 11 +++++++++--
 3 files changed, 20 insertions(+), 4 deletions(-)
```

`Updating 9666df9..391a859`는 "`main`을 `9666df9`에서 `391a859`로 옮긴다", `Fast-forward`는 "빨리 감기로 병합했다"는 뜻이다. 그래프를 본다.

```
git log --oneline --graph --all
```

```
* 02ac926 (feature/total-qty) 결과에 총 수량 표시
| * a8a641b (feature/coupon-percent) 시험에 퍼센트 할인율 검사 추가
| * 58e1368 쿠폰 할인율을 퍼센트로도 받기
|/  
| * 391a859 (HEAD -> main, feature/coupon-check) 시험에 쿠폰 할인율 범위 검사 추가
| * 8a23623 쿠폰 할인율의 범위 검사
|/  
* 9666df9 금액을 천 단위 쉼표로 표시
* 1ed2593 묶음 할인 기준을 README와 맞춤
...
```

**새 커밋은 생기지 않았다.** `main` 이름표가 `9666df9`에서 `391a859`로 옮겨 가서 `feature/coupon-check`와 같은 커밋에 붙었을 뿐이다.

```
 병합 전:   main
              ▼
           9666df9 ◀── 8a23623 ◀── 391a859
                                      ▲
                       feature/coupon-check

 병합 후:                          main
                                      ▼
           9666df9 ◀── 8a23623 ◀── 391a859
                                      ▲
                       feature/coupon-check
```

이렇게 된 이유는 `main`이 가리키던 `9666df9`가 `feature/coupon-check`의 **조상**이었기 때문이다. 브랜치가 갈라진 뒤 `main`에 아무 커밋도 쌓이지 않았으므로, `feature/coupon-check`의 끝 커밋에는 이미 `main`의 내용이 모두 들어 있다. 합칠 것 없이 `main`을 앞으로 감기만 하면 된다. 그래서 **빨리 감기**(fast-forward)라고 한다. 6.1.4의 `guide`에서 `1c3cad7`이 갈래 없이 한 줄로 보였던 것도 빨리 감기로 병합했기 때문이다.

병합한 뒤에는 반드시 실행해 본다.

```
python3 check_orders.py
```

```
[통과] small.csv gross: 기대 28500, 결과 28500
[통과] small.csv bulk: 기대 1800, 결과 1800
[통과] small.csv coupon: 기대 0, 결과 0
[통과] small.csv total: 기대 26700, 결과 26700
[통과] broken.csv: ValueError
[통과] 쿠폰 할인율 5: ValueError
모두 통과
```

`feature/coupon-check`에서 더한 시험(`쿠폰 할인율 5`)까지 모두 통과한다.

### 6.3.3 병합 커밋 — 갈라진 두 줄 합치기

이번에는 `feature/total-qty`를 병합한다. 그래프를 다시 보면 상황이 다르다. `feature/total-qty`는 `9666df9`에서 갈라졌는데, 그 뒤 `main`은 `391a859`까지 나아갔다. **두 브랜치가 각자 커밋을 쌓아 갈라진** 상태다. `main`을 앞으로 감기만 해서는 `feature/total-qty`의 커밋에 닿을 수 없다.

두 브랜치가 갈라진 지점을 **병합 기준**(merge base)이라고 한다. `git merge-base`로 찾는다.

```
git merge-base main feature/total-qty
```

```
9666df9de7862a8b4f799d8365bb271ba58cbb4d
```

병합한다. 이번에는 **편집기가 열린다.** 5.2.4에서 `core.editor`를 정했으므로 VS Code에 `MERGE_MSG`라는 탭이 열리고 다음 내용이 들어 있다.

```
git merge feature/total-qty
```

```
Merge branch 'feature/total-qty'
# Please enter a commit message to explain why this merge is necessary,
# especially if it merges an updated upstream into a topic branch.
#
# Lines starting with '#' will be ignored, and an empty message aborts
# the commit.
```

Git이 **병합 커밋**을 만들려고 메시지를 물어 온 것이다. 첫 줄 `Merge branch 'feature/total-qty'`는 Git이 미리 채워 둔 메시지다. `#`으로 시작하는 줄은 "이 병합이 왜 필요한지 메시지를 쓰라. `#`으로 시작하는 줄은 무시되고, 메시지를 비우면 커밋이 취소된다"는 안내다. 보통은 이 메시지를 그대로 쓴다. 저장하고 탭을 닫는다(5.3.5). 터미널에 결과가 나온다.

```
Auto-merging README.md
Merge made by the 'ort' strategy.
 README.md   | 1 +
 shop/cli.py | 1 +
 2 files changed, 2 insertions(+)
```

- `Auto-merging README.md` — `README.md`는 **양쪽 브랜치에서 모두 바뀐** 파일이다. `main` 쪽(`feature/coupon-check`에서 온 것)은 쿠폰 규칙 줄을, `feature/total-qty`는 "기대하는 결과"의 출력 예를 고쳤다. 고친 곳이 서로 떨어져 있으므로 Git이 두 변경을 자동으로 합쳤다는 안내다.
- `Merge made by the 'ort' strategy.` — "ort 전략으로 병합했다"는 뜻이다. ort는 Git의 기본 병합 방식의 이름이다. 따로 신경 쓸 것은 없다.
- 아래 줄은 이 병합으로 `main`에 들어온 변경이다.

```
git log --oneline --graph --all
```

```
*   5920ef9 (HEAD -> main) Merge branch 'feature/total-qty'
|\  
| * 02ac926 (feature/total-qty) 결과에 총 수량 표시
* | 391a859 (feature/coupon-check) 시험에 쿠폰 할인율 범위 검사 추가
* | 8a23623 쿠폰 할인율의 범위 검사
|/  
| * a8a641b (feature/coupon-percent) 시험에 퍼센트 할인율 검사 추가
| * 58e1368 쿠폰 할인율을 퍼센트로도 받기
|/  
* 9666df9 금액을 천 단위 쉼표로 표시
* 1ed2593 묶음 할인 기준을 README와 맞춤
...
```

**새 커밋 `5920ef9`가 생겼다.** 이 커밋은 내가 만든 것이므로 해시는 교재와 다르다. `|\`에서 두 줄기가 이 커밋으로 합쳐진다. 커밋 안을 본다.

```
git log -1
```

```
commit 5920ef9a0b543644cdd718e28426f13cb9e6e307
Merge: 391a859 02ac926
Author: 엄진영 <jinyoung@example.com>
Date:   Fri Nov 13 11:10:00 2026 +0900

    Merge branch 'feature/total-qty'
```

`Merge: 391a859 02ac926` 줄이 보통 커밋에는 없던 것이다. **병합 커밋은 부모가 둘이다.** 첫째는 병합할 때 있던 브랜치(`main`)의 커밋 `391a859`, 둘째는 가져온 브랜치의 커밋 `02ac926`이다. `git cat-file -p HEAD`로 보면 `parent` 줄이 두 개 있다.

```
 병합 전:
           9666df9 ◀── 8a23623 ◀── 391a859 ◀── main
               ▲
               └────── 02ac926 ◀── feature/total-qty

 병합 후:
           9666df9 ◀── 8a23623 ◀── 391a859 ◀─(첫째 부모)── 5920ef9 ◀── main
               ▲                                          │
               └────── 02ac926 ◀────────(둘째 부모)───────┘
                          ▲
                   feature/total-qty
```

병합 커밋도 스냅숏이다(5.1.3). Git은 이 스냅숏을 **세 커밋을 비교해서** 만든다. 이것을 **3-way 병합**이라고 한다.

| 비교 | 알 수 있는 것 |
|---|---|
| 병합 기준(`9666df9`) ↔ 지금 브랜치(`391a859`) | `main` 쪽에서 바꾼 것 |
| 병합 기준(`9666df9`) ↔ 가져올 브랜치(`02ac926`) | `feature/total-qty` 쪽에서 바꾼 것 |

- **한쪽만 바꾼 곳**은 바꾼 쪽의 내용을 쓴다. `shop/pricing.py`는 `main` 쪽만, `shop/cli.py`는 `feature/total-qty` 쪽만 바꿨으므로 각각 바꾼 쪽을 가져온다.
- **양쪽 모두 바꿨지만 서로 다른 곳**이면 둘 다 반영한다. `README.md`가 그랬다(`Auto-merging`).
- **양쪽이 같은 곳을 다르게 바꿨으면** Git은 어느 쪽이 맞는지 알 수 없다. 이것이 **충돌**이다(6.4).

병합 기준이 있어야 "누가 바꿨는지"를 알 수 있다는 점이 중요하다. 두 브랜치의 끝만 비교하면 `shop/cli.py`가 다르다는 것만 알 뿐, `main`이 줄을 지운 것인지 `feature/total-qty`가 줄을 더한 것인지 알 수 없다.

실행해 확인한다.

```
python3 main.py orders/small.csv
python3 check_orders.py
```

```
주문 파일: small.csv (주문 4줄)
총 수량: 27개
상품 금액: 28,500원
묶음 할인: -1,800원
쿠폰 할인: -0원
결제 금액: 26,700원
```

```
...
[통과] 쿠폰 할인율 5: ValueError
모두 통과
```

두 브랜치의 기능(총 수량 표시, 쿠폰 할인율 검사)이 모두 들어 있다.

> **병합 커밋 메시지의 `into`**
> `main`이 아닌 브랜치에서 병합하면 Git이 채워 주는 메시지에 받아들인 브랜치 이름이 붙는다. 예를 들어 `feature/total-qty`에 있는 채로 `git merge main`을 하면 `Merge branch 'main' into feature/total-qty`가 된다. `main`(과 `master`)에 병합할 때는 `into main`을 생략한다.

### 6.3.4 병합 후 그래프 읽기

병합 커밋이 생기면 이력이 한 줄이 아니게 된다. 갈라지고 합쳐진 이력을 읽는 도구를 정리한다.

**첫째 부모와 둘째 부모.** 5.4.5에서 `HEAD~1`과 `HEAD^`는 "이 장의 범위에서는 같은 뜻"이라고 했다. 부모가 둘인 병합 커밋에서는 다르다.

| 쓰는 법 | 가리키는 커밋 |
|---|---|
| `HEAD^1`(= `HEAD^`) | 첫째 부모. 병합할 때 있던 브랜치 쪽 |
| `HEAD^2` | 둘째 부모. 가져온 브랜치 쪽 |
| `HEAD~1`(= `HEAD~`) | 첫째 부모 |
| `HEAD~2` | 첫째 부모의 첫째 부모. `~`는 늘 **첫째 부모를 따라** 거슬러 올라간다 |

`~`는 몇 번 거슬러 올라갈지, `^`는 몇째 부모인지를 고른다고 기억하면 된다. 병합 커밋이 아니면 둘째 부모가 없으므로 `^2`는 오류가 난다. `guide`에서 확인한다.

```
cd ../guide
git log --oneline -1 38ec03f^1
git log --oneline -1 38ec03f^2
git log --oneline -1 38ec03f~2
```

```
aaf3825 기여 방법 추가
```

```
f666954 VS Code 장 초안
```

```
1c3cad7 제목을 학습 안내서로 고침
```

`38ec03f`(`Merge branch 'docs/vscode'`)의 첫째 부모는 `main` 쪽의 `aaf3825`, 둘째 부모는 `docs/vscode` 쪽의 `f666954`다. `~2`는 첫째 부모를 두 번 따라가 `1c3cad7`에 닿는다.

> **zsh에서 `^`가 말썽일 때**
> zsh의 `extendedglob` 옵션을 켜 두었다면(셸 설정을 꾸며 주는 도구가 켜기도 한다) `^`를 와일드카드로 해석해 `no matches found: 38ec03f^2` 같은 오류가 날 수 있다. 그럴 때는 따옴표로 감싼다(`git log -1 '38ec03f^2'`). 2.6.4에서 본 "와일드카드를 누가 처리하는가"의 문제다. PowerShell에서는 `^`가 특별하지 않다.

**`main`의 줄기만 보기 — `--first-parent`.** 병합 커밋에서 첫째 부모만 따라가면 `main`이 걸어온 길만 남는다.

```
git log --oneline --first-parent
```

```
38ec03f Merge branch 'docs/vscode'
aaf3825 기여 방법 추가
1c3cad7 제목을 학습 안내서로 고침
8a529f5 Merge branch 'docs/git'
52d26d9 터미널 장에 파이프 절 추가
8ad56d0 터미널 장 초안
3215956 가이드 목차 만들기
```

브랜치 안의 세부 커밋(`d1acaa0`, `456d80c`, `f666954`)이 빠지고 병합 커밋 하나로 요약된다. "`main`에 언제 무엇이 들어왔나"를 볼 때 쓴다. 병합 커밋만 보려면 `git log --oneline --merges`를 쓴다.

**병합 커밋이 가져온 변경.** 병합 커밋을 첫째 부모와 비교하면 그 병합으로 `main`에 **들어온** 변경이 나온다. `shop`으로 돌아가 방금 만든 병합 커밋을 본다.

```
cd ../shop
git diff --stat HEAD^1 HEAD
```

```
 README.md   | 1 +
 shop/cli.py | 1 +
 2 files changed, 2 insertions(+)
```

`feature/total-qty`에서 들어온 변경이다. 둘째 부모와 비교하면 거꾸로 `feature/total-qty`에는 없고 `main`에만 있던 변경(쿠폰 할인율 검사)이 나온다. `git show --stat HEAD`는 첫째 부모와 비교한 결과를 보여 준다.

**병합되었는지 확인 — `--merged`, `--no-merged`.** 브랜치의 커밋이 모두 지금 브랜치에 들어 있는지 알려 준다.

```
git branch --merged
git branch --no-merged
```

```
  feature/coupon-check
  feature/total-qty
* main
```

```
  feature/coupon-percent
```

`--merged`에 나온 브랜치는 `git branch -d`로 바로 지울 수 있는 브랜치다(6.2.6). `feature/coupon-check`와 `feature/total-qty`는 할 일을 마쳤으므로 지운다. 이름표를 떼도 커밋은 `main`의 이력 안에 그대로 남는다.

```
git branch -d feature/coupon-check feature/total-qty
```

```
Deleted branch feature/coupon-check (was 391a859).
Deleted branch feature/total-qty (was 02ac926).
```

**두 브랜치 비교 — 점 둘과 점 셋.** 6.3.1에서 쓴 표기를 정리한다.

| 표기 | `git log`에서 | `git diff`에서 |
|---|---|---|
| `A..B` | B에서 닿지만 A에서는 닿지 않는 커밋. "A에 병합하면 들어올 커밋" | A와 B의 스냅숏 비교(`git diff A B`와 같다) |
| `A...B` | 둘 중 한쪽에서만 닿는 커밋 | 병합 기준과 B의 비교. "B 브랜치에서 한 일" |

`git log`에는 주로 점 둘(`main..브랜치`), `git diff`에는 주로 점 셋(`main...브랜치`)을 쓴다. 헷갈리면 "병합하기 전에 볼 것은 `git log main..브랜치`와 `git diff main...브랜치`"라고 외워 둔다.

### 6.3.5 병합 방식 고르기 — `--no-ff`, `--ff-only`

`git merge`는 빨리 감기가 **가능하면** 빨리 감기를, 불가능하면 병합 커밋을 만든다. 옵션으로 이 동작을 바꿀 수 있다.

| 명령 | 동작 |
|---|---|
| `git merge 브랜치` | 빨리 감기가 가능하면 빨리 감기, 아니면 병합 커밋 |
| `git merge --no-ff 브랜치` | 빨리 감기가 가능해도 **병합 커밋을 만든다** |
| `git merge --ff-only 브랜치` | 빨리 감기만 한다. 불가능하면 **아무것도 하지 않고 멈춘다** |

`--no-ff`(no fast-forward)는 브랜치가 있었다는 흔적을 남기고 싶을 때 쓴다. 빨리 감기로 병합하면 6.1.4의 `1c3cad7`처럼 브랜치의 커밋이 `main`의 줄기에 섞여 들어가, 나중에 그 커밋들이 한 기능으로 묶여 있었다는 것을 알 수 없다. `--no-ff`로 병합하면 브랜치의 커밋이 옆 갈래로 남고 병합 커밋이 "여기서 이 기능이 들어왔다"는 표시가 된다. `--first-parent`로 보면 기능 하나가 커밋 하나로 요약된다. 8장에서 GitHub의 풀 리퀘스트를 기본 방식으로 병합하면 이렇게 늘 병합 커밋이 생긴다.

`--ff-only`는 "갈라지지 않았을 때만 병합하라"는 안전장치다. `shop`에 남은 `feature/coupon-percent`는 `9666df9`에서 갈라졌고 그 뒤 `main`도 나아갔으므로 빨리 감기가 불가능하다. 해 본다.

```
git merge --ff-only feature/coupon-percent
```

```
hint: Diverging branches can't be fast-forwarded, you need to either:
hint:
hint: 	git merge --no-ff
hint:
hint: or:
hint:
hint: 	git rebase
hint:
hint: Disable this message with "git config set advice.diverging false"
fatal: Not possible to fast-forward, aborting.
```

"갈라진 브랜치는 빨리 감기할 수 없다. `git merge --no-ff`로 병합 커밋을 만들거나 `git rebase`를 하라"는 안내다. `aborting`대로 아무것도 바뀌지 않았다. `git status`와 `git log --oneline -1`로 확인한다. `git rebase`는 7장에서 배운다.

어느 방식이 옳다는 정답은 없다. 혼자 쓰는 저장소에서는 기본 동작으로 충분하다. 팀에서는 정해 둔 방식을 따른다. 이 장에서는 기본 동작을 쓴다.

### 6.3.6 충돌이 없어도 확인한다

Git은 **글자**를 합칠 뿐 **프로그램의 뜻**은 모른다. 충돌 없이 병합되었다고 프로그램이 맞게 돈다는 보장은 없다. 예를 들어 보자.

- 브랜치 A에서는 `shop/cli.py`의 `won()` 함수 이름을 `format_won()`으로 바꾸고, 파일 안에서 부르는 곳도 모두 바꿨다. 실행도 검사도 잘 된다.
- 브랜치 B에서는 상품별 금액을 보여 주는 새 파일 `report.py`를 만들었다. 금액 모양을 맞추려고 `from shop.cli import won`으로 `won()`을 가져다 쓴다. 이것도 잘 돈다.

두 브랜치는 서로 다른 파일을 고쳤으므로 충돌 없이 병합된다. `python3 main.py`도, `check_orders.py`도 통과한다. 그런데 `python3 report.py orders/small.csv`를 실행하면 다음 오류로 멈춘다.

```
ImportError: cannot import name 'won' from 'shop.cli'
```

병합 결과에는 이제 없는 함수 `won()`을 가져오려는 줄이 남아 있기 때문이다. 각 브랜치는 혼자서는 옳았지만 합친 결과가 틀렸다. 이런 문제는 Git이 알려 주지 않고, 검사 스크립트가 그 부분을 확인하지 않으면 검사도 통과한다.

그래서 **병합한 뒤에는 충돌이 있었든 없었든 실행해 보고 검사를 돌린다.** 이 장에서 병합할 때마다 `check_orders.py`를 돌린 이유다. 검사가 프로그램의 모든 부분을 확인하는 것은 아니므로, 병합으로 들어온 변경과 관련된 기능은 직접 실행해 본다. 중급 과정에서 테스트를 체계적으로 쓰고 GitHub Actions로 자동 실행하는 이유도 여기에 있다. 이 문제는 실습 6-3에서 직접 만들어 본다.

### 6.3.7 VS Code에서 병합하기

VS Code에서는 명령 팔레트의 **Git: Merge...**(버전에 따라 **Git: Merge Branch...**)로 병합한다. 받아들일 브랜치로 먼저 옮겨 간 뒤(상태 표시줄로 확인) 이 명령을 실행하고, 가져올 브랜치를 고른다. 소스 제어 보기 제목줄의 **⋯**(More Actions) 메뉴의 **Branch** 아래에도 같은 명령이 있다.

| VS Code | 명령 |
|---|---|
| **Git: Merge...** 에서 브랜치 고르기 | `git merge 브랜치` |
| Graph의 병합 커밋(줄기가 합쳐지는 점) | 부모가 둘인 커밋 |

VS Code의 병합은 편집기를 열지 않고 Git이 채워 준 메시지(`Merge branch '...'`)로 바로 병합 커밋을 만든다. 메시지를 직접 쓰고 싶거나 `--no-ff` 같은 옵션을 주고 싶으면 터미널에서 한다.

### 실습 6-3. 병합하기

결과는 `~/devtools-lab/ch06/merge.md`에 적는다.

1. **예상하고 병합하기** — `practice/guide`에서 한다. 실습 6-2를 마쳤다면 `main` 말고 `exp/docker`, `fix/title-year`, `docs/vscode-keys` 브랜치가 있다.
   - `git log --oneline --graph --all`을 적는다.
   - 세 브랜치를 `exp/docker` → `fix/title-year` → `docs/vscode-keys` 차례로 `main`에 병합할 것이다. 각 병합이 빨리 감기가 될지 병합 커밋이 될지 **먼저 예상해** 적고, 그 이유를 그래프로 설명한다. 각 병합 전에 `git log --oneline main..브랜치`로 들어올 커밋을 적는다.
   - 차례로 병합하면서 예상이 맞았는지 확인한다. 병합 커밋이 생기면 편집기에 무엇이 열리는지 적는다.
   - 마지막에 `git log --oneline --graph --all`, `git log --oneline --first-parent`를 적고 비교한다.
2. **`--ff-only`와 `--no-ff`** — 같은 저장소에서 한다.
   - `git switch -c fix/typo2`로 브랜치를 만들어 `terminal.md`의 오타 하나(없으면 문장 하나)를 고쳐 커밋한다. `main`으로 돌아가 `git merge --no-ff fix/typo2`로 병합한다. 빨리 감기가 가능했는데도 그래프가 어떻게 그려지는지 적는다.
   - `git switch -c fix/typo3`로 같은 일을 한 번 더 하되, 이번에는 커밋한 뒤 `main`에서 `README.md`에 한 줄을 더해 커밋한다. 그다음 `git merge --ff-only fix/typo3`를 실행해 결과를 적는다. 왜 멈췄는가? 기본 `git merge`로 병합한다.
3. **부모 읽기** — 같은 저장소에서 한다. 1번에서 만든 마지막 병합 커밋에 대해 `git log --oneline -1 HEAD^1`, `git log --oneline -1 HEAD^2`, `git log --oneline -1 HEAD~2`를 실행해 결과를 적고, 각각 그래프의 어느 커밋인지 표시한다. `git diff --stat HEAD^1 HEAD`와 `git diff --stat HEAD^2 HEAD`의 차이를 설명한다.
4. **정리** — `git branch --merged`의 결과를 적고, `main` 말고 나온 브랜치를 모두 `git branch -d`로 지운다. `git branch --no-merged`에는 무엇이 남는가?
5. **충돌 없는 병합의 함정** — `practice/shop`에서 한다. `main`을 건드리지 않도록 연습용 브랜치 위에서 한다.
   - `git switch -c try/base`로 연습용 기준 브랜치를 만든다.
   - `git switch -c try/rename`을 하고, `shop/cli.py`에서 `won`을 `format_won`으로 모두 바꾼다(4.3.6의 `F2` 이름 바꾸기를 쓴다). `python3 main.py orders/small.csv`와 `python3 check_orders.py`로 확인하고 커밋한다.
   - `git switch try/base`로 돌아가 `git switch -c try/report`를 하고, 6.3.6의 `report.py`를 다음과 같이 만든다. `python3 report.py orders/small.csv`로 확인하고 커밋한다.
     ```python
     """주문 파일의 상품별 금액을 보여 준다. python report.py 주문파일.csv로 실행한다."""

     import sys
     from pathlib import Path

     from shop.cli import won
     from shop.loader import load_orders

     for line in load_orders(Path(sys.argv[1])):
         print(f"{line.name}: {won(line.subtotal())}")
     ```
   - `git switch try/base`로 가서 `try/rename`과 `try/report`를 차례로 병합한다. 각 병합은 빨리 감기였는가, 병합 커밋이었는가? 충돌이 났는가?
   - `python3 main.py orders/small.csv`, `python3 check_orders.py`, `python3 report.py orders/small.csv`를 차례로 실행해 결과를 적는다. 무엇이 잘못되었는지 6.3.6과 견주어 적고, 고치려면 어느 브랜치에서 무엇을 바꿨어야 했는지 적는다.
   - 확인했으면 `git switch main`으로 돌아가 `try/` 브랜치 세 개를 모두 지운다. `main`에서 `-d`로 지우면 어떻게 되는지 보고, 세 브랜치 모두 `-D`가 필요한 이유를 적는다. `git log --oneline --graph --all`로 `main`이 바뀌지 않았는지 확인한다.
6. **VS Code** — `practice/guide`에서 `git switch -c docs/readme-note`로 브랜치를 만들어 `README.md`의 끝에 한 줄을 더해 커밋한다. 그다음 터미널을 쓰지 않고 VS Code만으로 `main`으로 옮겨 가 `docs/readme-note`를 병합한다. 병합 뒤 터미널에서 `git log --oneline --graph -3`을 적고, 빨리 감기였는지 병합 커밋이었는지 확인한다.

## 6.4 충돌 해결

### 6.4.1 충돌이 생기는 경우

6.3.3에서 본 3-way 병합의 셋째 경우, 즉 **두 브랜치가 병합 기준에서 같은 곳을 서로 다르게 바꾼** 경우에 충돌이 생긴다. Git은 어느 쪽이 맞는지 판단하지 않고 멈춰서 사람에게 묻는다.

| 상황 | 충돌인가 |
|---|---|
| 서로 다른 파일을 고쳤다 | 아니다 |
| 같은 파일의 떨어진 곳을 고쳤다 | 아니다(6.3.3의 `README.md`) |
| 양쪽이 **똑같이** 고쳤다 | 아니다. 같은 결과이므로 그대로 쓴다 |
| 같은 줄(또는 바로 붙은 줄)을 서로 다르게 고쳤다 | **충돌**(내용 충돌) |
| 한쪽은 파일을 고치고 다른 쪽은 지웠다 | **충돌**(6.4.8) |
| 양쪽이 같은 이름의 새 파일을 서로 다른 내용으로 만들었다 | **충돌** |

충돌은 잘못이 아니다. 두 사람이 같은 곳을 고쳤다는 사실을 Git이 알려 주는 것이다. 어떻게 합칠지는 코드의 뜻을 아는 사람만 정할 수 있다.

`practice/shop`의 남은 브랜치 `feature/coupon-percent`를 보자. 서연은 쿠폰 할인율을 `5%`처럼 받게 했고, 도윤은(이미 `main`에 병합된 `feature/coupon-check`에서) 할인율의 범위를 검사하게 했다. 둘 다 `coupon_rate()` 함수의 같은 줄을 고쳤다. 들어올 커밋을 확인한다.

```
git log --oneline main..feature/coupon-percent
```

```
a8a641b 시험에 퍼센트 할인율 검사 추가
58e1368 쿠폰 할인율을 퍼센트로도 받기
```

### 6.4.2 충돌 상태 읽기 — `git status`

병합한다. `git status`가 깨끗한지 먼저 확인한다.

```
git merge feature/coupon-percent
```

```
Auto-merging README.md
CONFLICT (content): Merge conflict in README.md
Auto-merging check_orders.py
CONFLICT (content): Merge conflict in check_orders.py
Auto-merging shop/pricing.py
CONFLICT (content): Merge conflict in shop/pricing.py

```

`CONFLICT (content): Merge conflict in ...`는 "이 파일에서 내용 충돌이 났다"는 뜻이다. 세 파일에서 충돌이 났다. 마지막 줄은 "자동 병합에 실패했다. 충돌을 해결하고 결과를 커밋하라"는 안내다. 편집기는 열리지 않았고, **병합 커밋도 아직 만들어지지 않았다.** 병합이 **진행 중인 채로 멈춘** 상태다.

```
git status
```

```
On branch main
You have unmerged paths.
  (fix conflicts and run "git commit")
  (use "git merge --abort" to abort the merge)

Unmerged paths:
  (use "git add <file>..." to mark resolution)
	both modified:   README.md
	both modified:   check_orders.py
	both modified:   shop/pricing.py

no changes added to commit (use "git add" and/or "git commit -a")
```

한 줄씩 읽는다.

- `You have unmerged paths.` — 병합되지 않은 파일이 있다.
- `(fix conflicts and run "git commit")` — 충돌을 고치고 `git commit`을 하라. 이것이 병합을 끝내는 방법이다.
- `(use "git merge --abort" to abort the merge)` — 병합을 그만두려면 `git merge --abort`(6.4.7).
- `Unmerged paths:` 아래의 `both modified` — 양쪽 브랜치가 모두 고친 파일이다. `(use "git add <file>..." to mark resolution)`은 "파일을 고친 뒤 `git add`로 해결했다고 표시하라"는 뜻이다. **충돌 중에는 `git add`가 "해결했다"는 표시**가 된다.

짧은 형식에서는 `UU`로 나온다(unmerged, 양쪽 모두 고침).

```
git status -s
```

```
UU README.md
UU check_orders.py
UU shop/pricing.py
```

충돌이 나지 않은 변경, 예를 들어 이번 병합에서 다른 파일에 있었다면 그 파일의 변경은 이미 스테이징 영역에 들어 있다. 충돌 난 파일만 사람의 손을 기다린다.

Git은 병합이 진행 중이라는 것을 `.git/MERGE_HEAD` 파일로 기억한다. 가져오는 브랜치의 커밋이 적혀 있다.

```
cat .git/MERGE_HEAD
```

```
a8a641bf77bfeb6e895fc0746a4fb18f9714cb7c
```

이 파일이 있는 동안 Git은 "병합 중"이다. 다음 `git commit`은 이 커밋을 둘째 부모로 하는 병합 커밋이 된다. VS Code의 소스 제어 보기에는 **Merge Changes**라는 묶음이 새로 생기고, 그 아래에 충돌 난 파일이 나온다.

- 표시 밖의 줄(함수 첫 줄, 독스트링 첫 줄)은 양쪽이 같아서 그대로 둔 부분이다.

Git 문서와 AI의 답에서는 지금 브랜치 쪽을 **ours**(우리 것), 가져오는 쪽을 **theirs**(그들 것)라고 부른다. VS Code는 각각 **Current**(현재)와 **Incoming**(들어오는)이라고 부른다.

이 표시만으로는 아쉬운 점이 있다. **원래 어땠는지**가 보이지 않는다. 두 쪽이 모두 바뀐 것인지, 한쪽만 바뀐 것인지, 각자 무엇을 바꾸려 했는지를 알려면 병합 기준의 내용이 필요하다. Git에는 병합 기준까지 보여 주는 표시 방식이 있다. 설정하고, 병합을 한 번 취소한 뒤(6.4.7) 다시 병합한다.

```

git merge --abort
git status

### 6.4.4 직접 고치기

충돌을 해결한다는 것은 **충돌 표시가 있는 자리를 원하는 최종 내용으로 바꾸고, 표시 줄(`<<<<<<<`, `|||||||`, `=======`, `>>>>>>>`)을 모두 지우는 것**이다. 어느 한쪽을 고르는 것으로 끝나는 경우도 있지만, 이번처럼 **두 의도를 모두 살린 새 코드**를 써야 하는 경우가 많다. 충돌 표시가 있는 자리마다 다음 순서로 생각한다.

1. 병합 기준과 지금 브랜치를 비교해 **지금 브랜치가 무엇을 하려고 했는지** 말로 적는다.
2. 병합 기준과 가져오는 브랜치를 비교해 **가져오는 브랜치가 무엇을 하려고 했는지** 말로 적는다.
3. 두 의도를 모두 만족하는 코드를 쓴다. 한쪽을 버려야 한다면 그 이유를 병합 커밋 메시지에 남긴다.
4. 표시 줄을 지운다.

커밋 메시지가 의도를 알려 준다. `git log -1 --format=%B 8a23623`과 `git log -1 --format=%B 58e1368`으로 두 브랜치의 커밋 메시지 본문을 다시 읽어 본다(`%B`는 메시지 전체). 도윤은 "퍼센트 숫자를 그대로 넣어 결제 금액이 음수가 되는 것"을 막으려 했고, 서연은 "안내문의 `5%`를 그대로 넣을 수 있게" 하려 했다. 5.5.2에서 메시지 본문에 "왜"를 쓰라고 한 것이 여기서 쓸모를 보인다.

**`shop/pricing.py`** — `%`를 먼저 비율로 바꾸고, 그 결과에 범위 검사를 한다. 충돌 표시가 있던 자리 전체(`<<<<<<< HEAD` 줄부터 `>>>>>>> feature/coupon-percent` 줄까지)를 다음으로 바꾼다. 고친 뒤의 함수 전체는 다음과 같다.

```python
def coupon_rate() -> float:
    """환경 변수 SHOP_COUPON_RATE에서 쿠폰 할인율을 읽는다. 없으면 0.

    "0.05"처럼 비율로 적어도 되고 "5%"처럼 퍼센트로 적어도 된다.
    0 이상 MAX_COUPON_RATE 이하가 아니면 ValueError를 낸다.
    """
    text = os.getenv("SHOP_COUPON_RATE", "0").strip()
    if text.endswith("%"):
        rate = float(text[:-1]) / 100
    else:
        rate = float(text)
    if not 0 <= rate <= MAX_COUPON_RATE:
        raise ValueError(f"쿠폰 할인율은 0 이상 {MAX_COUPON_RATE} 이하여야 합니다: {rate}")
    return rate
```

어느 쪽에도 없던 코드(`rate = float(text[:-1]) / 100`, `else:`)가 생겼다. 양쪽을 그대로 이어 붙이는 것으로는 이 결과가 나오지 않는다(6.4.5).

> **`git add`는 충돌 표시를 검사하지 않는다**
> 충돌 표시가 남은 파일도 `git add`하면 해결된 것으로 표시되고, 그대로 커밋할 수 있다. 그러면 `<<<<<<<`가 든 코드가 `main`에 들어간다. 파이썬 파일이라면 실행할 때 문법 오류로 바로 드러나지만, `README.md`나 설정 파일은 아무도 모른 채 남기 쉽다. `git add` 전에 `git diff --check`로 확인하는 습관을 들인다. VS Code에서는 충돌 표시가 남은 파일을 스테이징하려고 하면 확인 대화 상자가 나온다.

    print(f"[실패] 쿠폰 할인율 5%: 기대 0.05, 결과 {rate}")
    failed += 1
del os.environ["SHOP_COUPON_RATE"]
```

### 6.4.5 VS Code로 해결하기

VS Code는 충돌 표시를 알아보고 해결을 돕는 화면을 준다. 방법은 두 가지다.

**편집기 안의 버튼(CodeLens).** 충돌 난 파일을 열면 충돌 표시 위에 작은 글자 버튼이 나오고, 지금 브랜치 쪽(Current)과 가져오는 쪽(Incoming)이 서로 다른 색으로 칠해진다.

| 버튼 | 결과 |
|---|---|
| **Accept Current Change** | 지금 브랜치 쪽만 남긴다(ours) |
| **Accept Incoming Change** | 가져오는 쪽만 남긴다(theirs) |
| **Accept Both Changes** | 지금 브랜치 쪽 다음에 가져오는 쪽을 **이어 붙인다** |
| **Compare Changes** | 두 쪽을 비교 화면으로 연다 |

버튼을 누르면 표시 줄이 지워지고 고른 내용만 남는다. 저장한 뒤 소스 제어 보기에서 그 파일의 **+**(Stage Changes)를 누르면 `git add`와 같다.

여기서 조심할 것이 **Accept Both Changes**다. 이름만 보면 "둘 다 살린다"이니 이번 경우의 정답 같지만, 실제로는 두 쪽의 줄을 **차례로 이어 붙일 뿐**이다. `shop/pricing.py`에서 누르면 다음과 같이 된다.

```python
def coupon_rate() -> float:
    """환경 변수 SHOP_COUPON_RATE에서 쿠폰 할인율을 읽는다. 없으면 0.

    0 이상 MAX_COUPON_RATE 이하가 아니면 ValueError를 낸다.
    """
    rate = float(os.getenv("SHOP_COUPON_RATE", "0"))
    if not 0 <= rate <= MAX_COUPON_RATE:
        raise ValueError(f"쿠폰 할인율은 0 이상 {MAX_COUPON_RATE} 이하여야 합니다: {rate}")
    return rate
    "0.05"처럼 비율로 적어도 되고 "5%"처럼 퍼센트로 적어도 된다.
    """
    text = os.getenv("SHOP_COUPON_RATE", "0").strip()
    if text.endswith("%"):
        return float(text[:-1]) / 100
    return float(text)
```

독스트링이 닫힌 뒤에 다른 독스트링의 뒷부분이 붙어 문법이 깨진다. 실행하면 `SyntaxError: unterminated triple-quoted string literal`로 멈춘다. 문법이 깨지지 않는 경우가 더 위험하다. `return`이 두 번 나오면 뒤쪽 코드는 실행되지 않는데, 오류 없이 돌아가므로 알아채기 어렵다. **Accept Both는 `check_orders.py`처럼 양쪽이 서로 다른 것을 같은 자리에 "더한" 경우에만 맞다.** 같은 코드를 서로 다르게 "고친" 경우에는 6.4.4처럼 직접 새로 써야 한다.

**병합 편집기.** 충돌 난 파일을 열면 편집기 오른쪽 아래에 **Resolve in Merge Editor** 단추가 나온다. 소스 제어 보기의 **Merge Changes**에서 파일을 오른쪽 클릭해 **Open in Merge Editor**를 골라도 된다. 병합 편집기는 화면을 셋으로 나눈다.

```
┌───────────────────────────┬───────────────────────────┐
│ Incoming                  │ Current                   │
│ feature/coupon-percent    │ main                      │
│ (가져오는 쪽, theirs)      │ (지금 브랜치, ours)        │
│ □ Accept Incoming         │ □ Accept Current          │
├───────────────────────────┴───────────────────────────┤
│ Result                                                │
│ (병합 결과. 직접 고칠 수 있다)                          │
│                                     [Complete Merge]  │
└───────────────────────────────────────────────────────┘
```

- 위의 두 칸은 각 브랜치의 내용이다. 충돌마다 **Accept Incoming**, **Accept Current**, 상황에 따라 **Accept Combination**(둘을 합치기) 같은 선택지가 붙어 있다. 고르면 아래 **Result**에 반영된다.
- **Result**는 실제로 저장될 파일이다. 선택지로 원하는 결과가 나오지 않으면 Result에 **직접 쓴다.** 이번 `coupon_rate()`처럼 새 코드가 필요한 경우가 그렇다.
- 제목줄의 **⋯** 메뉴에서 병합 기준(Base)을 함께 보이게 할 수 있다. 6.4.3의 `zdiff3`처럼 원래 모습을 보며 판단할 수 있다.
- 다 되면 오른쪽 아래의 **Complete Merge**를 누른다. 파일을 저장하고 **스테이징한다**(`git add`). 병합 커밋까지 만드는 것은 아니다. 충돌 난 파일이 더 있으면 하나씩 같은 일을 한다.

모든 파일을 해결했으면 소스 제어 보기의 메시지 칸을 본다. `Merge branch 'feature/coupon-percent'`가 미리 채워져 있다. 메시지를 다듬고 **Commit**을 누르면 병합 커밋이 만들어진다(6.4.6). 병합을 그만두려면 명령 팔레트의 **Git: Abort Merge**를 실행한다(`git merge --abort`와 같다).

| VS Code | 명령 |
|---|---|
| 소스 제어 보기의 **Merge Changes** 목록 | `git status`의 `Unmerged paths` |
| CodeLens **Accept Current/Incoming/Both** | 충돌 자리를 고른 내용으로 바꾸기(직접 고치기와 같다) |
| **Complete Merge**, Merge Changes 파일의 **+** | `git add 파일`(해결했다고 표시) |
| 메시지 칸에 쓰고 **Commit** | `git commit`(병합 커밋) |
| **Git: Abort Merge** | `git merge --abort` |

버전에 따라 편집기 위쪽에 AI로 충돌을 해결하는 단추(예: **Resolve Merge Conflict with AI**)가 보일 수 있다. GitHub Copilot 같은 AI 도구가 두 쪽을 읽고 결과를 제안해 준다. 제안은 4.6.3에서 AI가 고친 파일을 검토하듯이 다룬다. 6.4.4의 순서(양쪽의 의도를 말로 적기)로 제안이 두 의도를 모두 살렸는지 확인하고, `git diff --check`와 검사 스크립트로 확인한 뒤에 받아들인다.

충돌을 해결한 병합 커밋에는 **어떻게 해결했는지**를 적어 두는 것이 좋다. 나중에 이 코드를 읽는 사람(몇 달 뒤의 나를 포함해)은 `coupon_rate()`가 왜 이렇게 생겼는지 궁금할 것이다. 첫 줄 아래에 빈 줄을 두고 본문을 쓴다.

```
Merge branch 'feature/coupon-percent'

README와 check_orders.py에는 두 브랜치의 내용을 모두 남겼다.

```

> **`git commit --no-edit`과 `-m`**
> `git commit --no-edit`을 하면 편집기를 열지 않고 채워진 메시지로 커밋하는데, 이때는 `# Conflicts:` 줄들이 **지워지지 않고 메시지에 그대로 남는다.** `git commit -m "..."`을 하면 Git이 채운 메시지 대신 내가 쓴 메시지만 들어간다. 충돌을 해결한 병합은 편집기로 메시지를 확인하고 쓰는 것이 좋다.

### 6.4.7 병합 취소 — `git merge --abort`

충돌이 너무 많거나, 엉뚱한 브랜치를 병합했거나, 해결하다 꼬였다면 병합을 **처음부터 없던 일로** 돌릴 수 있다. 6.4.3에서 한 번 썼던 명령이다.

```
git merge --abort
```

병합 중에 생긴 모든 것(충돌 표시, 스테이징한 해결 결과, `.git/MERGE_HEAD`)을 버리고 병합을 시작하기 전 상태로 돌아간다. 출력은 없고, `git status`가 `nothing to commit, working tree clean`으로 돌아온다. 마음을 정리하고, 필요하면 상대에게 물어보고, 다시 `git merge`를 하면 된다.

알아 둘 점이 세 가지 있다.

- **병합 중일 때만 쓸 수 있다.** 병합하고 있지 않을 때 실행하면 `fatal: There is no merge to abort (MERGE_HEAD missing).`가 나온다. "병합 중이 아니다(`MERGE_HEAD`가 없다)"는 뜻이다.
- **병합 커밋을 만든 뒤에는 쓸 수 없다.** 이미 끝난 병합을 되돌리는 일은 7장의 `git reset`이나 `git revert`로 한다.
- **병합 전에 커밋하지 않은 변경이 있었다면** 그 변경까지 망가질 수 있다. 6.3.1에서 병합 전에 작업 폴더를 깨끗하게 하라고 한 이유 중 하나다. 깨끗한 상태에서 시작한 병합은 `--abort`로 언제든 안전하게 되돌릴 수 있다.

### 6.4.8 내용 충돌이 아닌 충돌

한쪽은 파일을 고치고 다른 쪽은 파일을 지웠다면, Git은 파일을 남길지 지울지 정할 수 없다. 예를 들어 지금 브랜치에서는 `orders/broken.csv`에 줄을 더했는데, 가져오는 브랜치 `cleanup`에서는 그 파일을 지웠다면 다음과 같이 나온다.

```
CONFLICT (modify/delete): orders/broken.csv deleted in cleanup and modified in HEAD.  Version HEAD of orders/broken.csv left in tree.
Automatic merge failed; fix conflicts and then commit the result.
```

"`orders/broken.csv`가 `cleanup`에서는 지워졌고 `HEAD`에서는 고쳐졌다. `HEAD`의 것을 작업 폴더에 남겨 두었다"는 뜻이다. `git status`에는 `deleted by them: orders/broken.csv`(그쪽에서 지움)로, 짧은 형식에서는 `UD`로 나온다. 파일 안에 충돌 표시는 없다. 해결은 둘 중 하나를 고르는 것이다.

- 파일을 **남기려면** `git add orders/broken.csv`
- 파일을 **지우려면** `git rm orders/broken.csv`

어느 쪽이든 그다음에 `git commit`으로 병합을 끝낸다. `git status`의 안내도 `(use "git add/rm <file>..." as appropriate to mark resolution)`, 즉 "맞는 쪽으로 `git add`나 `git rm`을 하라"고 알려 준다.

내용 충돌에서도 **파일 전체를 한쪽 것으로** 하고 싶을 때가 있다. 그림 파일처럼 줄 단위로 합칠 수 없는 파일이 그렇다. 그럴 때는 `git restore`에 `--ours`나 `--theirs`를 붙인다.

| 명령 | 결과 |
|---|---|
| `git restore --ours 파일` | 작업 폴더의 파일을 지금 브랜치 쪽 내용으로 |
| `git restore --theirs 파일` | 작업 폴더의 파일을 가져오는 쪽 내용으로 |

이 명령은 파일 내용만 바꿀 뿐 해결했다고 표시하지는 않는다. `git status -s`에는 여전히 `UU`로 나오므로, 내용을 확인한 뒤 `git add`를 해야 한다. 옛 자료에는 `git checkout --ours 파일`, `git checkout --theirs 파일`로 나온다.

### 6.4.9 충돌을 줄이는 습관

충돌은 피할 수 없지만 줄이고 작게 만들 수는 있다.

- **작게 자주 병합한다.** 브랜치를 오래 두면 그동안 `main`도 많이 바뀌어 한꺼번에 큰 충돌을 만난다. 기능을 작게 나누어 며칠 안에 병합하면 충돌이 나도 작다.
- **오래 걸리는 브랜치는 `main`을 자주 가져온다.** 기능이 커서 브랜치를 오래 써야 한다면, 그 브랜치에 있는 채로 가끔 `git merge main`을 해서 `main`의 새 변경을 가져온다. 충돌을 마지막에 한꺼번에 만나는 대신 조금씩 나누어 해결하게 된다. (7장의 `git rebase`로도 같은 목적을 이룰 수 있다.)
- **기능 변경과 모양 변경을 섞지 않는다.** 파일 전체의 줄 바꿈, 들여쓰기, 함수 순서를 바꾸는 커밋은 다른 사람의 거의 모든 변경과 충돌한다. 포맷터를 처음 적용하거나 코드를 크게 옮길 때는 따로 브랜치를 만들어 빨리 병합하고, 팀에 알린다. 4.2.4의 "저장할 때 자동 포맷"을 팀 전체가 같은 설정으로 쓰는 이유이기도 하다.
- **줄 끝 문자를 통일한다.** 한 사람의 편집기가 파일 전체를 CRLF로 바꾸면 모든 줄이 바뀐 것이 되어 충돌이 커진다. 5.2.6의 `.gitattributes`가 이것을 막는다.
- **누가 어디를 고치는지 이야기한다.** 같은 함수를 두 사람이 동시에 고치게 될 것 같으면 미리 나누거나 순서를 정한다. 8장의 이슈와 풀 리퀘스트가 이런 소통의 도구다.
- **AI 도구의 큰 변경을 조심한다.** AI 코딩 도구는 부탁한 곳 말고도 파일 여기저기를 고치거나 모양을 바꾸는 경우가 있다. 4.6.3처럼 diff를 검토해 필요 없는 변경을 빼고 커밋하면, 다른 브랜치와의 불필요한 충돌도 줄어든다.

### 실습 6-4. 충돌 해결

결과는 `~/devtools-lab/ch06/conflict.md`에 적는다.

1. **이 장의 충돌을 다시 풀기** — `practice/shop`에서 한다. 6.4를 따라 했다면 `main`에 이미 병합되어 있다. 지운 브랜치의 끝 커밋 해시로 같은 충돌을 연습용 브랜치에서 다시 만든다.
   ```
   git switch -c try/conflict 391a859
   git merge a8a641b
   ```
   - `391a859`는 `feature/coupon-check`의 끝, `a8a641b`는 `feature/coupon-percent`의 끝이었다. 이번에는 `feature/total-qty`가 없는 상태에서의 병합이다. 충돌 난 파일이 6.4.2와 같은지 적는다.
   - `shop/pricing.py`를 VS Code에서 열고 CodeLens의 **Accept Both Changes**를 누른다. 저장한 뒤 `python3 check_orders.py`를 실행해 결과를 적는다. 무엇이 잘못되었는지 설명한다.
   - 편집기에서 `Cmd/Ctrl+Z`로 되돌리거나 `git restore --merge shop/pricing.py`로 다시 충돌 상태를 만든다. `--merge`는 충돌 난 파일을 충돌 표시가 있던 처음 상태로 되돌린다. 이때 표시의 이름은 `ours`, `base`, `theirs`로 나온다. 이번에는 **병합 편집기**를 열어, Base를 보이게 하고 Result에 6.4.4의 코드를 직접 써서 **Complete Merge**를 누른다.
   - `README.md`와 `check_orders.py`는 CodeLens 버튼만으로 해결해 본다. 어느 버튼을 눌렀는지, 그 버튼으로 충분했는지 적는다.
   - 커밋하지 말고 `git merge --abort`로 병합을 취소한다. `git status`와 `git log --oneline -1`로 병합 전 상태로 돌아왔는지 확인한다. `git switch main`으로 돌아가 `try/conflict`를 지운다.
2. **내가 만드는 충돌** — `practice/guide`에서 한다.
   - `main`에서 `git switch -c docs/pwd-a`를 하고, `terminal.md`의 `현재 위치는 pwd로 본다.`를 `현재 위치는 pwd로 보고, 이동은 cd로 한다.`로 고쳐 커밋한다.
   - `main`으로 돌아가 `git switch -c docs/pwd-b`를 하고, 같은 줄을 `현재 위치는 pwd(print working directory)로 본다.`로 고쳐 커밋한다.
   - `main`에서 `docs/pwd-a`를 병합하고, 이어서 `docs/pwd-b`를 병합한다. 첫째 병합과 둘째 병합의 결과가 어떻게 다른지 적는다.
   - 충돌 표시를 그대로 옮겨 적고, 세 부분(지금 브랜치, 병합 기준, 가져오는 쪽)이 각각 어느 커밋의 내용인지 적는다.
   - 두 의도를 모두 살린 문장으로 직접 고치고, `git diff --check`로 확인한 뒤 `git add`하고, 편집기로 병합 커밋 메시지에 해결 방법을 적어 커밋한다.
   - `git show HEAD`의 diff에서 `++`로 시작하는 줄을 찾아 적는다. 왜 `++`인가?
3. **수정/삭제 충돌** — 같은 저장소에서 한다. (실습 6-3에서 `exp/docker`를 병합했다면 `main`에 `docker.md`가 있다.)
   - `git switch -c cleanup`에서 `git rm docker.md`로 지우고 커밋한다.
   - `main`으로 돌아가 `docker.md`에 한 줄을 더해 커밋한다.
   - `main`에서 `cleanup`을 병합한다. 출력과 `git status`, `git status -s`를 적는다.
   - 파일을 남기기로 하고 해결해 병합을 끝낸다. 어떤 명령을 썼는지 적는다.
4. **해결을 그만두기** — 2번과 같은 방법으로 `docs/title-a`, `docs/title-b` 두 브랜치에서 `README.md`의 첫 줄을 서로 다르게 고쳐 커밋한다. `main`에서 `docs/title-a`를 병합하고 이어서 `docs/title-b`를 병합해 충돌을 만든다. 충돌이 난 상태에서 `git status`를 적고, `git merge --abort`를 한 뒤 다시 `git status`와 `git log --oneline -1`을 적는다. 이어서 한 번 더 `git merge --abort`를 실행해 나오는 메시지를 적고 뜻을 설명한다. `docs/title-b`는 5번에서 쓰므로 지우지 않는다.
5. **충돌 표시 방식 비교** — 4번에 이어서 한다. `git config --global merge.conflictStyle merge`로 바꾸고 `git merge docs/title-b`를 해서 충돌 표시를 적은 뒤 `git merge --abort`를 한다. 이번에는 `zdiff3`로 바꾸고 같은 일을 한다. 어느 쪽이 판단하기 쉬운지 이유와 함께 적는다. 끝나면 설정을 `zdiff3`로 두고, `docs/title-b`는 병합하지 않기로 하고 `-D`로 지운다. `git branch --merged`로 지울 수 있는 다른 브랜치(`docs/pwd-a`, `docs/pwd-b`, `cleanup`, `docs/title-a`)도 정리한다.

## 6.5 브랜치 전략

브랜치를 만들고 합치는 방법을 알았으니, **언제 어떤 브랜치를 만들지** 정할 차례다. 팀마다 규칙이 조금씩 다르지만, 이 과정에서는 가장 단순하고 널리 쓰이는 방식을 따른다. `main` 하나를 중심에 두고, 일마다 짧은 브랜치를 만들어 끝나면 `main`에 병합하는 방식이다.

### 6.5.1 `main`은 언제나 실행되는 상태로

가장 중요한 규칙은 **`main`은 언제 꺼내도 실행되고 검사를 통과하는 상태로 둔다**는 것이다.

- `main`은 모두의 출발점이다. 새 브랜치는 `main`에서 갈라지므로(6.2.4), `main`이 망가져 있으면 그 위에서 시작한 모든 작업이 망가진 채로 시작한다.
- `main`은 남에게 보여 주는 얼굴이다. 다른 사람이 저장소를 받아(8장) 처음 실행하는 것도, 마지막 단계에서 서버에 배포하는 것도 보통 `main`이다.
- 몇 주 뒤의 나도 "남"이다. 오랜만에 프로젝트를 열었을 때 `main`이 돌아가지 않으면 무엇부터 고쳐야 할지 알 수 없다.

그래서 **덜 된 작업은 `main`에 커밋하지 않는다.** 브랜치에서 작업하고, 브랜치에서 검사를 통과한 뒤에 병합하고, 병합한 뒤에 `main`에서 다시 검사한다(6.3.6). 6.3과 6.4에서 병합할 때마다 `check_orders.py`를 돌린 것이 이 규칙을 지키는 방법이다. 그래도 `main`이 망가졌다면 다른 일보다 먼저 고친다. 망가뜨린 병합을 되돌리는 방법은 7장의 `git revert`다.

### 6.5.2 일마다 브랜치 하나

**한 가지 일에 브랜치 하나**를 만든다. 5.5.1의 "한 커밋에 한 가지 일"을 브랜치 크기로 넓힌 것이다.

- **기능 하나** — 쿠폰 할인율 검사, 총 수량 표시처럼 사용자에게 보이는 기능 하나
- **버그 수정 하나** — 이슈 하나(8장)
- **실험 하나** — 될지 안 될지 모르는 시도. 실패하면 버린다(6.5.4)
- **문서 작업 하나** — README의 한 절, 장 하나

브랜치는 **짧게** 쓴다. 며칠 안에 병합할 수 있을 만큼 일을 작게 나눈다. 오래 사는 브랜치일수록 `main`과 멀어져 충돌이 커진다(6.4.9). 병합한 브랜치는 바로 지운다(`git branch -d`). 다 쓴 브랜치가 쌓이면 `git branch` 목록이 길어져 지금 진행 중인 일이 무엇인지 알아보기 어렵다.

혼자 쓰는 저장소에서도 브랜치는 쓸모가 있다. 일하는 도중에 **다른 급한 일이 끼어들 때** 특히 그렇다.

> **하던 일을 두고 급한 일부터**
> `feature/report` 브랜치에서 보고서 기능을 반쯤 만들었는데, `main`의 버그를 당장 고쳐야 한다는 연락이 왔다고 하자. 브랜치를 쓰면 다음처럼 한다.
> 1. 반쯤 만든 것을 `feature/report`에 커밋한다. 메시지에 덜 되었다고 적는다(예: `보고서 기능 작업 중: 표 출력까지`). 6.2.5에서 본 대로 커밋하지 않은 변경은 브랜치를 옮길 때 따라오므로, 커밋해서 이 브랜치에 남겨 둔다.
> 2. `git switch main` 후 `git switch -c fix/급한버그`를 만들어 고치고, 검사하고, 커밋한다.
> 3. `git switch main` 후 `git merge fix/급한버그`, 검사, `git branch -d fix/급한버그`.
> 4. `git switch feature/report`로 돌아가 하던 일을 이어서 한다. 고친 버그가 보고서 기능에도 필요하면 `git merge main`으로 가져온다.
>
> 브랜치가 없었다면 반쯤 만든 보고서 코드와 버그 수정이 한 작업 폴더에서 뒤섞였을 것이다. 1번의 "덜 된 커밋"을 깔끔하게 다듬는 방법과 커밋 대신 쓸 수 있는 `git stash`는 7장에서 배운다.

### 6.5.3 브랜치 이름 규칙

브랜치 이름은 **무엇을 하는 브랜치인지** 알 수 있게 짓는다. 이 과정에서는 `종류/설명` 모양을 쓴다.

| 종류 | 쓰임 | 예 |
|---|---|---|
| `feature/` | 새 기능 | `feature/coupon-check`, `feature/total-qty` |
| `fix/` | 버그 수정 | `fix/coupon-error`, `fix/bulk-boundary` |
| `exp/` | 실험(버릴 수도 있다) | `exp/align`, `exp/docker` |
| `docs/` | 문서 | `docs/vscode`, `docs/branch-rules` |
| `refactor/` | 동작은 그대로 두고 코드 구조 바꾸기 | `refactor/format-won` |

설명 부분은 다음을 지킨다.

- **영어 소문자와 숫자, 하이픈(`-`)으로** 짓는다. `feature/coupon-check`처럼 단어를 하이픈으로 잇는다.
- **짧지만 알아볼 수 있게.** `fix/bug`나 `feature/new`는 아무것도 알려 주지 않는다. `feature/add-coupon-rate-validation-and-percent-support-for-readme`는 너무 길다.
- 이슈(8장)가 있으면 번호를 넣는 팀이 많다. `fix/12-coupon-error`.

이렇게 정하는 데는 이유가 있다.

- **공백은 쓸 수 없다.** Git이 거절한다. `..`, `~`, `^`, `:`, `?`, `*`, `[`, `\`도 쓸 수 없고, `/`로 끝나거나 `.lock`으로 끝나는 이름도 안 된다. 이름이 규칙에 맞는지는 `git check-ref-format --branch 이름`으로 확인할 수 있다.
  ```
  git check-ref-format --branch "feature/coupon check"
  git switch -c "feature/coupon check"
  ```
  ```
  fatal: 'feature/coupon check' is not a valid branch name
  ```
  ```
  fatal: 'feature/coupon check' is not a valid branch name
  hint: See `man git check-ref-format`
  hint: Disable this message with "git config set advice.refSyntax false"
  ```
- **한글은 쓸 수는 있지만 피한다.** `git check-ref-format --branch "기능/쿠폰"`은 통과한다. 하지만 입력과 Tab 자동 완성이 불편하고, 8장에서 GitHub 주소에 들어가면 `%EA%B8%B0...`처럼 바뀌어 읽기 어렵다.
- **대문자를 피한다.** 브랜치는 `.git/refs/heads` 아래의 파일이다(6.1.2). macOS와 Windows는 대소문자를 구별하지 않으므로(2.6.6) `Fix/Login`과 `fix/login`을 서로 다른 브랜치로 다루지 못해 이상한 일이 생긴다.
- **`종류` 이름 자체를 브랜치로 만들지 않는다.** `docs/vscode` 브랜치가 있으면 `.git/refs/heads/docs`는 폴더이므로 `docs`라는 브랜치는 만들 수 없다. 거꾸로 `docs` 브랜치가 있으면 `docs/...` 브랜치를 만들 수 없다.
  ```
  git branch docs
  ```
  ```
  fatal: cannot lock ref 'refs/heads/docs': 'refs/heads/docs/vscode' exists; cannot create 'refs/heads/docs'
  ```

팀이나 저장소에 정한 규칙이 있으면 그것을 따른다(5.5.2의 상자와 같다). `CONTRIBUTING.md`(8장)나 `AGENTS.md`(4.6.4)에 브랜치 이름 규칙을 적어 두는 경우가 많다.

### 6.5.4 실험이 실패하면 브랜치째 버리기

6.2에서 금액을 오른쪽으로 맞추는 실험을 `exp/align` 브랜치에서 했고, 결과가 마음에 들지 않아 `git branch -D`로 지웠다. 이것이 실험 브랜치를 쓰는 방법이다.

```
git switch main
git branch -D exp/실험이름
```

`main`은 실험하는 동안 한 번도 바뀌지 않았으므로 되돌릴 것이 없다. 5.1.1에서 본 "폴더를 통째로 복사해 두고 실험하기"와 비교하면 차이가 분명하다. 복사한 폴더는 무엇을 바꿨는지 알 수 없고, 잘된 부분만 원래 폴더로 옮기기도 어렵다. 브랜치는 실험의 모든 단계가 커밋으로 남고, `git diff main...exp/실험이름`으로 무엇을 바꿨는지 언제든 볼 수 있다.

실험이 **반만** 성공했다면 어떻게 할까? 쓸 만한 커밋 하나만 `main`으로 가져오는 `git cherry-pick`을 7장에서 배운다. 지운 실험 브랜치를 다시 살리고 싶을 때는 6.2.6에서 본 `(was 해시)`나 7장의 `git reflog`를 쓴다. 브랜치를 지워도 커밋이 바로 사라지지는 않기 때문에, 실험 브랜치는 부담 없이 만들고 부담 없이 버려도 된다.

8장에서는 4단계가 바뀐다. 내 컴퓨터에서 `git merge`하는 대신 브랜치를 GitHub에 올리고(push), **풀 리퀘스트**를 열어 다른 사람의 리뷰를 받은 뒤 GitHub에서 병합한다. 나머지 단계는 같다. 이렇게 `main` 하나와 짧은 기능 브랜치로 일하는 방식을 GitHub에서는 **GitHub flow**라고 부른다. 정해진 날에 버전을 내는 제품에서는 `develop`, `release/...` 같은 브랜치를 더 두는 Git flow 같은 방식도 쓰이지만, 이 과정에서는 다루지 않는다.

### 6.5.6 AI 코딩 도구와 브랜치

AI 코딩 도구에게 일을 맡길 때도 브랜치는 같은 역할을 한다. AI의 작업은 **실험**처럼 다룬다.

- 맡기기 전에 `main`에서 `git status`가 깨끗한지 보고, AI 작업용 브랜치를 만든다(예: `exp/ai-report`). 커밋하지 않은 내 변경이 있다면 먼저 커밋한다. 6.2.5에서 본 대로 브랜치를 만드는 것만으로는 그 변경이 보호되지 않고, AI의 변경과 섞여 버린다.
- AI가 끝나면 `git diff`, `git diff main...브랜치`로 무엇을 바꿨는지 검토한다. 마음에 들면 커밋하고 검사한 뒤 `main`에 병합한다. 마음에 들지 않으면 브랜치째 버린다(6.5.4).
- AI 도구가 `git switch`, `git merge`, `git branch -D` 같은 명령을 실행하겠다고 허락을 구하면, 3.8에서 배운 대로 읽고 판단한다. 이 장에서 배운 명령들이므로 이제 무엇을 하는지 알 수 있다. 특히 `-D`, `--discard-changes`처럼 되살리기 어려운 옵션에 주의한다.

AI가 바꾼 것 중 일부만 받아들이는 방법(`git add -p`와 `git restore`), 여러 AI 작업을 동시에 맡기는 방법(`git worktree`)은 7장에서 다룬다.

### 실습 6-5. 내 저장소에서 브랜치로 일하기

   - **일 B**(`docs/branch-rules`) — `README.md`의 끝에 "## 작업 규칙" 절을 더하고, 이 저장소에서 쓸 브랜치 이름 규칙(6.5.3)과 작업 흐름(6.5.5)을 서너 줄로 적는다.

   - 병합할 때마다 검사 스크립트를 돌리고, 다 쓴 브랜치를 지운다.
2. **끼어든 급한 일** — 같은 저장소에서 6.5.2의 상자를 직접 해 본다.

   - 급한 일로 `fix/usage` 브랜치를 `main`에서 만들어 `shop/cli.py`의 `USAGE` 문구를 다듬고, `main`에 병합한 뒤 지운다.
   - `feature/report`로 돌아가 `report.py`를 완성해 커밋한다. `git merge main`으로 `fix/usage`의 변경을 가져온다. 병합 커밋의 메시지는 무엇으로 채워졌는가(6.3.3의 상자)?
   - `main`에 `feature/report`를 병합한다. 빨리 감기였는가? 그래프를 보고 이유를 적는다.
3. **이름 짓기** — 다음 일에 맞는 브랜치 이름을 6.5.3의 규칙으로 짓는다. 그다음 아래 다섯 이름을 `git check-ref-format --branch`로 검사해 결과를 적고, 통과하지만 규칙에 맞지 않는 이름은 무엇이 문제인지 적는다.
   - 일: 주문 파일에 머리글이 없을 때 오류 문구 고치기 / 결과를 CSV로 저장하는 기능 / README의 설치 절 다시 쓰기 / 할인 계산 코드를 클래스로 바꿔 보는 시도(잘 될지 모름)

4. **실험 버리기** — 같은 저장소에서 `exp/` 브랜치를 하나 만들어 `shop/pricing.py`에 마음대로 실험을 하고 커밋을 두 개 쌓는다. `git diff main...exp/이름`으로 실험의 전체 변경을 확인한 뒤, 실험을 버리기로 하고 지운다. `-d`와 `-D` 중 무엇을 썼는지, 지울 때 나온 `(was 해시)`로 브랜치를 다시 살렸다가 다시 지워 본다.
5. **(AI 코딩 도구가 있으면)** `exp/ai-` 로 시작하는 브랜치를 만들고, AI에게 작은 기능 하나(예: 주문 줄 수가 0이면 안내 문구 보이기)를 맡긴다. AI가 실행하려고 한 Git 명령이 있었다면 모두 적고 각각 무엇을 하는지 설명한다. `git diff main...브랜치`로 검토한 뒤 받아들일지 버릴지 정하고, 그 이유와 함께 병합하거나 지운다.

## 정리

| 항목 | 핵심 |
|---|---|
| 부모 커밋 | 커밋은 부모를 가리킨다(화살표는 뒤로). 첫 커밋은 부모가 없고(뿌리 커밋), 병합 커밋은 부모가 둘. 자식은 여럿일 수 있다 → 이력이 갈라진다. `git log --format="%h %p %s"` |
| 브랜치 | 커밋을 가리키는 이름표. `.git/refs/heads/이름`에 해시 한 줄(`packed-refs`에 모여 있을 수도). 만드는 비용이 거의 없다. 커밋하면 앞으로 움직인다. 지워도 커밋은 바로 사라지지 않는다 |
| `HEAD` | 지금 있는 브랜치를 가리킨다(`ref: refs/heads/main`). 커밋하면 `HEAD`가 가리키는 브랜치만 움직인다. `(HEAD -> main)` |
| 그래프 | `git log --oneline --graph --all`. `*` 커밋, `|` 줄기, `|/` 갈라짐, `|\` 합쳐짐. 브랜치 이름은 갈래의 끝에. `--all`이 없으면 `HEAD`의 조상만. 별칭 `alias.graph`. VS Code Graph |
| 만들기·목록 | `git branch`, `-v`, `git branch 이름 [시작점]`(옮겨 가지 않는다) |
| 옮기기 | `git switch 브랜치`: `HEAD`를 옮기고 작업 폴더·스테이징 영역을 그 커밋의 스냅숏으로. `git switch -c 새브랜치 [시작점]`, `git switch -`. 새 브랜치는 지금 있는 곳에서 갈라진다 → 보통 `main`에서 시작 |
| 커밋하지 않은 변경 | 어느 브랜치에도 속하지 않는다. 두 브랜치에서 같은 파일이면 따라오고, 다르면 거절(`would be overwritten by checkout`). 거절되면 커밋·버리기·stash(7장). 잊고 `main`에서 시작했으면 `git switch -c` |
| 이름 바꾸기·지우기 | `git branch -m 옛 새`(`master` → `main`), `-d`(병합된 것만), `-D`(강제). `(was 해시)`로 다시 살릴 수 있다. 지금 브랜치는 못 지운다 |
| detached HEAD | `HEAD`가 커밋을 직접 가리키는 상태. `git switch --detach 커밋`. 지난 시점에서 실행해 보기에 쓴다. 여기서 한 커밋은 브랜치를 만들지 않으면 잃기 쉽다(`git switch -c`, `git branch 이름 해시`). 빠져나오기: `git switch 브랜치` |
| 옛 명령 | `git checkout 브랜치` = `switch`, `checkout -b` = `switch -c`, `checkout 커밋` = `switch --detach`(긴 안내) |
| `git merge` | 받아들일 브랜치로 옮겨 가서 `git merge 가져올브랜치`. 지금 브랜치만 움직인다. 전에 `git status`, `git log main..브랜치`, `git diff main...브랜치` |
| 빨리 감기 | 지금 브랜치가 가져올 브랜치의 조상이면 이름표만 앞으로(`Fast-forward`). 새 커밋 없음. 그래프에 갈래가 남지 않는다 |
| 병합 커밋 | 갈라졌으면 병합 기준(`git merge-base`)·양쪽 끝으로 3-way 병합. 한쪽만 바꾼 곳은 그쪽, 양쪽이 다른 곳을 바꿨으면 둘 다(`Auto-merging`), 같은 곳을 다르게 바꿨으면 충돌. 편집기에 `Merge branch '...'`. `Merge: 첫째 둘째` |
| 병합 이력 읽기 | `^1` 첫째 부모(받아들인 쪽), `^2` 둘째 부모(가져온 쪽), `~n`은 첫째 부모를 따라. `--first-parent`, `--merges`, `--merged`/`--no-merged`, `A..B`(log), `A...B`(diff). zsh에서 `^`는 따옴표 |
| 병합 방식 | 기본(가능하면 빨리 감기), `--no-ff`(늘 병합 커밋, 브랜치 흔적), `--ff-only`(갈라졌으면 멈춤) |
| 충돌 없는 병합 | 글자만 합친다. 뜻이 맞는지는 모른다 → 병합 후 늘 실행·검사 |
| 충돌 | 같은 곳을 다르게 고침, 고침/지움, 같은 이름의 새 파일. 양쪽이 똑같이 고친 곳은 충돌 아님. `CONFLICT (content)`, `Unmerged paths`, `both modified`, `UU`, `.git/MERGE_HEAD` |
| 충돌 표시 | `<<<<<<< HEAD`(ours, Current) / `||||||| 기준`(zdiff3) / `=======` / `>>>>>>> 브랜치`(theirs, Incoming). `git config --global merge.conflictStyle zdiff3` |
| 해결 | 양쪽의 의도를 말로 적고(커밋 메시지 참고), 둘 다 만족하는 내용을 쓰고, 표시 줄을 지운다. `git diff --check`, 검사, `git add`(해결 표시, 충돌 표시를 검사하지 않음) → `All conflicts fixed but you are still merging` → `git commit`(편집기, 해결 방법을 본문에) |
| VS Code | Merge Changes 목록, CodeLens(Accept Current/Incoming/Both, Compare), Accept Both는 이어 붙이기일 뿐("더한" 충돌에만), 병합 편집기(Incoming·Current·Result, Base 보기, Complete Merge = `git add`), Commit, Git: Abort Merge, AI 제안은 검토 후 |
| 병합 커밋 보기 | `git show`의 `diff --cc`: 두 칸, `++`는 두 부모 어디에도 없던 줄(직접 쓴 해결) |
| 병합 취소 | `git merge --abort`: 병합 전으로. 병합 중에만. 커밋 후에는 7장. 깨끗한 상태에서 시작해야 안전 |
| 다른 충돌 | 고침/지움(`UD`, `deleted by them`) → `git add`(남기기) 또는 `git rm`(지우기). `git restore --ours/--theirs 파일` 후 `git add` |
| 충돌 줄이기 | 작게 자주 병합, 긴 브랜치는 `git merge main`, 모양 변경 분리, `.gitattributes`, 소통, AI의 불필요한 변경 빼기 |
| 브랜치 전략 | `main`은 언제나 실행되는 상태. 일마다 짧은 브랜치, 병합 후 지우기. 급한 일은 커밋해 두고 새 브랜치로 |
| 이름 규칙 | `종류/설명`(`feature/`, `fix/`, `exp/`, `docs/`, `refactor/`), 영어 소문자·하이픈, 짧고 알아보게. 공백·`..`·`~^:?*[\` 불가(`git check-ref-format --branch`), 한글·대문자 피하기, `docs`와 `docs/x`는 함께 못 쓴다. 팀 규칙 우선 |
| 실험 | `exp/` 브랜치에서, 실패하면 `git branch -D`. `main`은 그대로 |
| 작업 흐름 | `switch main` → `status` → `switch -c` → 커밋(검사) → `switch main` → `merge` → 검사 → `branch -d`. 8장에서는 merge 대신 push와 풀 리퀘스트(GitHub flow) |
| AI와 브랜치 | 내 변경은 먼저 커밋, AI 작업용 브랜치, `git diff main...브랜치`로 검토, 받아들이면 병합·버리면 삭제. AI가 실행하려는 Git 명령을 읽는다 |

## 다음 장

[7장. 이력 되돌리기와 고치기](ch07.md)에서는 이 장까지 쌓은 커밋을 **고치고 되돌린다.** 이 장에서 몇 번 "7장에서"라고 미뤄 둔 것들이다. 방금 한 커밋의 메시지나 빠뜨린 파일을 고치는 `git commit --amend`, 커밋을 취소하는 `git reset`, `main`에 들어간 잘못된 병합을 안전하게 되돌리는 `git revert`, 지운 브랜치와 detached HEAD에서 잃어버린 커밋을 되찾는 `git reflog`, 6.5.2의 "덜 된 커밋" 대신 쓸 수 있는 `git stash`, 실험 브랜치에서 쓸 만한 커밋 하나만 가져오는 `git cherry-pick`, 병합과 다른 방식으로 브랜치를 합치는 `git rebase`를 배운다. 이 장에서 익힌 커밋 그래프와 브랜치 이름표, `HEAD`의 그림이 7장의 모든 명령을 이해하는 바탕이 된다. 각 명령이 그래프에서 무엇을 움직이는지 그려 보며 읽으면 된다.
