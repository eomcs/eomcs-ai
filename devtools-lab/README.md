# 개발 도구

[AI 엔지니어 학습 로드맵](../README.md) 2단계 "LLM 응용 서비스 개발"의 두 번째 항목인 **개발 도구**(Git/GitHub 심화, 터미널(CLI), VS Code, Jupyter Notebook)의 상세 학습 항목이다.

## 학습 목표

[파이썬 기초](../python-basic-lab/README.md)에서는 터미널을 "폴더를 옮겨 다니며 파이썬을 실행하는" 만큼만 썼고, Git은 `.gitignore`를 적어 두기만 했다. 이 과정에서는 **매일 쓰는 도구를 손에 익혀, 코드를 만들고 고치고 되돌리고 나누는 일을 AI 도구 없이도 스스로 할 수 있는** 수준에 도달한다. 1단계에서 AI 도구가 대신 실행해 주던 명령과 GitHub 작업을 직접 하면서, AI가 무슨 명령을 실행하고 무엇을 바꾸었는지 **읽고 검토하고 필요하면 되돌릴 수 있는** 능력을 기른다.

이후 과정과의 연결은 다음과 같다.

- **파이썬 중급** — 모든 실습을 장마다 Git으로 커밋하며 진행한다. VS Code의 Pylance·테스트 탐색기, Git 태그로 버전 표시하기, GitHub Actions로 테스트 자동 실행하기가 이 과정 위에서 이루어진다.
- **데이터 처리 기초** — Jupyter Notebook에서 pandas로 데이터를 탐색한다. 큰 CSV 파일은 열기 전에 터미널에서 먼저 줄 수와 앞부분을 확인한다.
- **웹·API 기초, LLM API 활용** — API 키를 환경 변수와 `.env` 파일로 관리하고 Git에 올리지 않는다. `curl`로 요청을 보내 보고, 노트북에서 프롬프트를 실험한다.
- **에이전트 개발** — MCP 서버 같은 도구가 터미널 명령으로 실행되고 표준 입출력으로 통신하는 모습을 이해한다. AI 코딩 에이전트에게 작업을 맡길 때 브랜치와 작업 트리(worktree)로 변경을 격리한다.
- **LLM 서비스 배포** — 서버 프로세스와 포트, 리눅스 셸(bash), SSH, Docker 명령, GitHub를 통한 배포 자동화가 모두 이 과정의 터미널·Git 사용법 위에 있다.

## 선행 조건

- [파이썬 기초](../python-basic-lab/README.md)를 마쳤거나, 가상환경을 만들고 여러 파일로 나뉜 파이썬 프로그램을 터미널에서 실행할 수 있다.
- 기초 과정 1.1 "터미널 최소 조작"(`pwd`, `cd`, `ls`, `mkdir`, 경로 지정) 정도의 터미널 사용 경험
- 1단계에서 GitHub에 코드를 올려 본 경험이 있으면 좋지만 필요하지는 않다. Git은 5장에서 처음부터 명령으로 다시 다룬다.
- GitHub 계정(1단계에서 만든 것을 그대로 쓴다)

## 학습 항목

장의 순서는 로드맵의 나열 순서(터미널 → VS Code → Git/GitHub → Jupyter Notebook)를 따른다. 터미널을 먼저 익혀야 Git 명령을 편하게 쓸 수 있다. VS Code는 Git보다 먼저 익히지만, VS Code의 Git 화면과 병합 편집기는 Git이 실제로 하는 일을 알고 나서 보아야 무엇을 누르는지 보이므로 4장에서 다루지 않고 5~8장에서 명령과 나란히 다룬다. 터미널(2·3장) → VS Code(4장) → Git(5~7장) → GitHub(8장) → Jupyter Notebook(9장) 순서로 진행하고, 10장에서 기초 과정의 종합 실습 프로젝트를 이 도구들로 다시 다룬다.

### 1장. 시작하기

- **개발 도구 과정의 지도** — 1단계에서 AI 도구가 대신 해 준 일(명령 실행, 커밋, 푸시, 배포)과 이 과정의 장 연결, 같은 작업을 GUI(VS Code·GitHub 웹)와 명령(CLI) 두 가지로 할 수 있을 때 명령을 먼저 배우는 이유
- **실습 환경** — macOS(zsh)와 Windows 11(PowerShell 7 이상) 기준, 패키지 관리자(macOS Homebrew, Windows `winget`)로 도구 설치하기, Windows에서 PowerShell 7 이상이 필요한 이유(기초 과정에서 쓴 Windows PowerShell 5.1에는 `&&`·`||` 연산자가 없고, `>`로 저장한 파일의 기본 인코딩이 UTF-8이 아니다), PowerShell 7 설치(`winget install Microsoft.PowerShell`)와 버전 확인(`$PSVersionTable`), Windows 터미널과 VS Code의 기본 셸을 PowerShell 7로 바꾸기, Git·GitHub CLI(`gh`)·VS Code 설치와 버전 확인, 리눅스 서버에서 쓰는 bash와의 관계(Git Bash와 WSL은 소개만)
- **기초 과정 점검** — 이 과정이 기대는 것 다시 확인: 경로와 현재 위치(1.1), 환경 변수(8.2.1), 가상환경과 "터미널이 찾는 파이썬"(9장), 표준 출력·표준 오류·종료 코드와 10장의 프로젝트 폴더(`.gitignore`, `README.md`, `DESIGN.md`, `requirements.txt`)

### 2장. 터미널 기본기

- **셸과 터미널** — 터미널(창)과 셸(명령을 해석하는 프로그램)의 차이, zsh·bash·PowerShell, 프롬프트 읽기, 셸 종류에 따라 명령이 달라지는 지점과 이 교재의 표기 방법
- **명령의 구조와 도움말** — 명령·옵션·인자, 짧은 옵션과 긴 옵션(`-a`, `--all`), 옵션 합쳐 쓰기, `--help`, `man`, `Get-Help`, 처음 보는 명령의 사용법을 찾는 순서(도움말 → 공식 문서 → AI에게 묻고 도움말로 확인)
- **빠르게 입력하기** — Tab 자동 완성, 명령 기록(↑, `Ctrl+R`, `history`), 실행 중인 명령 멈추기(`Ctrl+C`), 화면 지우기, 줄 편집 단축키
- **파일과 폴더 다루기** — 만들기(`mkdir -p`, `touch` / `New-Item`), 복사·이동·이름 바꾸기(`cp -r`, `mv`), 지우기(`rm`, `rm -r`)는 휴지통을 거치지 않는다는 점, 숨김 파일 보기(`ls -a`, `Get-ChildItem -Force`), 파일 정보(크기·수정 시각)
- **파일 내용 보기** — `cat`, `less`(페이지 넘기기·검색·종료), `head`/`tail`(`Get-Content -TotalCount`/`-Tail`), 계속 늘어나는 로그 파일 지켜보기(`tail -f`, `Get-Content -Wait`)
- **경로와 이름의 함정** — 홈(`~`), `.`과 `..`, 공백·한글이 들어간 경로와 따옴표, 와일드카드(`*`, `?`)를 누가 처리하는지의 차이(zsh·bash는 셸이 파일 이름 목록으로 먼저 펼쳐서 명령에 넘기고, PowerShell은 cmdlet의 매개변수가 와일드카드를 직접 해석하며 외부 프로그램에는 펼치지 않고 그대로 넘긴다), 그래서 `python main.py *.csv`의 `sys.argv`가 macOS에서는 파일 이름 목록이고 Windows에서는 `*.csv`라는 글자 그대로라는 점과 운영체제에 상관없이 처리하는 방법(파이썬에서 `pathlib`의 `glob()`), 대소문자 구분(macOS·Windows와 리눅스의 차이)
- **터미널에서 쓰는 편집기** — `git commit`이 열어 주는 Vim에서 빠져나오기(`:wq`, `:q!`), nano 기본 조작, 기본 편집기를 VS Code로 바꾸는 방법은 5장에서

### 3장. 터미널 활용

- **입출력 연결** — 표준 입력·표준 출력·표준 오류(기초 과정 10장 다시 보기), 리다이렉션(`>`, `>>`, `2>`, `2>&1`), 파이프(`|`)로 명령 잇기, 파이썬 프로그램을 파이프 중간에 넣기(`sys.stdin`으로 읽고 `print()`로 내보내기)
- **찾기와 세기** — 파일 이름으로 찾기(`find`, `Get-ChildItem -Recurse -Filter`), 내용으로 찾기(`grep -rn`, `Select-String`), 줄 수 세기·정렬·중복 세기(`wc -l`, `sort`, `uniq -c` / `Measure-Object -Line`, `Sort-Object`, `Group-Object` — PowerShell에는 `wc`·`uniq`가 없고 `sort`는 `Sort-Object`의 별칭이라 옵션이 다르다), 파일 앞부분 보기(`head`, `Get-Content -TotalCount`), 큰 CSV를 열기 전에 줄 수와 앞부분 확인하기, (선택) ripgrep(`rg`)
- **종료 코드와 명령 연결** — 성공·실패를 알리는 종료 코드(`$?`, `$LASTEXITCODE`), `&&`(앞 명령이 성공했을 때만 다음 명령 실행)와 `||`(앞 명령이 실패했을 때만 다음 명령 실행)로 명령 잇기, 기초 과정의 `check_samples.py`가 종료 코드 1로 끝나게 만든 이유 다시 보기
- **셸 환경** — 환경 변수 보기·정하기(`env`, `export`, `Get-ChildItem Env:`, `$env:`), `PATH`와 명령을 찾는 순서(`which`, `Get-Command` 다시 보기), 셸 설정 파일(`~/.zshrc`, `$PROFILE`)에 영구 설정·별칭(alias) 두기, 설정을 바꾼 뒤 새 터미널을 열어야 하는 이유
- **프로세스와 포트** — 실행 중인 프로그램(프로세스)과 PID, 끝나지 않는 서버 프로그램은 터미널을 하나 더 열어 쓰기(VS Code 터미널 분할), "이미 사용 중인 포트" 오류에서 포트를 쓰는 프로세스 찾기·종료하기(`lsof -i :8000`, `Get-NetTCPConnection`, `kill`, `Stop-Process`), `localhost`와 포트 번호의 의미(웹·API 기초로 연결)
- **반복 작업 묶기** — 자주 쓰는 명령을 셸 스크립트(`.sh`, shebang, `chmod +x`)와 PowerShell 스크립트(`.ps1`, 실행 정책)로 묶기, 두 운영체제에서 똑같이 돌아야 하면 파이썬 스크립트로 쓰는 선택
- **웹에서 내려받기와 설치 명령** — `curl`로 응답 보기와 파일 내려받기(Windows에서는 `curl.exe`), 설치 안내에 흔한 `curl ... | sh` 형태의 명령을 실행하기 전에 확인할 것
- **AI가 실행하려는 명령 읽기** — Claude Code·Cursor 같은 AI 코딩 도구가 실행 허락을 구하는 명령을 읽고 판단하기, 위험 신호(`rm -rf`, 홈·루트 경로, `sudo`, 출처를 모르는 스크립트 실행, 비밀 값을 출력하거나 외부로 보내는 명령), 모르는 명령은 `--help`로 확인하고 허락하는 습관

### 4장. VS Code

- **작업 공간** — 폴더 단위로 열기(`code .`, macOS에서 `code` 명령 등록), 화면 구성(탐색기·검색·소스 제어·실행·확장), 명령 팔레트(`Cmd/Ctrl+Shift+P`), 자주 쓰는 단축키와 단축키 찾는 방법
- **설정과 확장** — 사용자 설정과 작업 공간 설정(`.vscode/settings.json`), 설정 화면과 JSON의 관계, 파이썬 개발에 필요한 확장(Python, Pylance, Jupyter), 저장할 때 자동 포맷(포맷터 자체는 중급 과정의 ruff에서), 팀원에게 권장 확장 알리기(`.vscode/extensions.json`), 저장소에 올릴 설정과 올리지 않을 설정
- **편집 기술** — 다중 커서, 줄 이동·복제, 파일 빠르게 열기(`Cmd/Ctrl+P`), 전체 검색·바꾸기와 정규 표현식 맛보기, 정의로 이동·참조 찾기·이름 바꾸기(`F2`)로 여러 파일에 걸친 코드 읽고 고치기
- **디버거 더 쓰기** — 기초 과정 1.2.5에서 쓴 디버거 다시 보기, 조건부 중단점·로그 지점, 조사식(Watch)과 호출 스택, 예외에서 멈추기, `launch.json`으로 명령행 인자·환경 변수·작업 폴더를 정해 실행 설정 저장하기, 모듈로 실행하기(`python -m`)
- **통합 터미널** — VS Code 안의 터미널과 바깥 터미널이 다를 수 있는 점(기본 셸, 활성화된 가상환경, 환경 변수), 선택한 인터프리터와 터미널 가상환경 맞추기(기초 과정 9장 다시 보기)
- **AI 코딩 도구와 함께 쓰기** — Copilot·Claude Code 등 VS Code 확장의 인라인 제안과 채팅, AI가 고친 파일을 비교 화면(diff)으로 검토하고 받아들이거나 되돌리기, 프로젝트 규칙을 적어 두는 파일(AI 도구용 지침 파일)의 역할 소개(Git과 함께 쓰는 방법은 7장에서)

### 5장. Git 시작하기

- **Git이 하는 일** — 버전 관리가 필요한 이유, 1단계에서 GitHub에 올린 것과 내 컴퓨터의 Git 저장소의 관계, 커밋은 "변경 기록"이 아니라 그 시점 프로젝트 전체의 스냅숏이라는 것
- **처음 설정** — 사용자 이름·이메일(`git config --global`), 기본 브랜치 이름(`init.defaultBranch main`), 기본 편집기를 VS Code로(`core.editor "code --wait"`), Windows의 줄 끝 문자(`core.autocrlf`, `.gitattributes`), 설정 확인(`git config --list --show-origin`)
- **세 영역** — 작업 폴더·스테이징 영역·저장소, `git init`, `git status` 읽기, `git add`, `git commit`, 파일의 상태 변화(추적 안 됨 → 스테이징됨 → 커밋됨 → 수정됨)
- **변경 확인** — `git diff`와 `git diff --staged`, `git log`(`--oneline`, `--graph`, `-p`, `--stat`), `git show`, 파일의 줄별 변경 이력(`git blame`, VS Code 타임라인)
- **좋은 커밋** — 한 커밋에 한 가지 일, 커밋 메시지 쓰는 법(제목 한 줄과 본문, 무엇을보다 왜를), 파일 일부만 골라 커밋하기(`git add -p`), 커밋하기 전에 `git diff --staged`로 확인하는 습관
- **추적하지 않을 것** — `.gitignore` 패턴 규칙(기초 과정 9·10장에서 쓴 것 다시 보기), 무시되는 이유 확인(`git check-ignore -v`), 이미 커밋해 버린 `.venv`·`__pycache__`를 추적에서 빼기(`git rm --cached`), 파일 이름 바꾸기·지우기(`git mv`, `git rm`)
- **작업 폴더의 변경 되돌리기** — 스테이징하지 않은 변경 버리기(`git restore` — 옵션이 없으면 마지막 커밋이 아니라 스테이징 영역의 내용으로 되돌린다), 스테이징 취소(`git restore --staged`), 스테이징한 변경까지 모두 마지막 커밋 상태로 되돌리기(`git restore --staged --worktree`), 각 명령 전후의 상태를 `git status`·`git diff`·`git diff --staged`로 확인하기, 커밋하지 않은 변경은 버리면 되살릴 수 없다는 점, 추적하지 않는 파일 정리(`git clean -n`으로 먼저 확인)

### 6장. 브랜치와 병합

- **커밋 그래프와 브랜치** — 커밋 해시와 부모 커밋, 브랜치는 커밋을 가리키는 이름표라는 것, `HEAD`의 의미, 그래프 그려 보기(`git log --oneline --graph --all`)
- **브랜치 다루기** — 만들기·옮겨 가기·목록·지우기(`git branch`, `git switch`, `git switch -c`), 커밋하지 않은 변경이 있을 때 브랜치를 옮기면 생기는 일, `HEAD`가 브랜치가 아닌 커밋을 가리키는 상태(detached HEAD)와 빠져나오기
- **병합** — `git merge`, 빨리 감기(fast-forward)와 병합 커밋, 병합 후 그래프 읽기
- **충돌 해결** — 충돌이 생기는 경우, 충돌 표시(`<<<<<<<`, `=======`, `>>>>>>>`) 읽기, 직접 고치기와 VS Code 병합 편집기, 해결 후 커밋, 병합 취소(`git merge --abort`), 충돌을 줄이는 습관(작게 자주 병합하기)
- **브랜치 전략** — `main`은 언제나 실행되는 상태로 두기, 기능·실험·버그 수정마다 브랜치 만들기, 브랜치 이름 규칙, 실험이 실패하면 브랜치째 버리기

### 7장. 이력 되돌리기와 고치기

- **마지막 커밋 고치기** — 메시지·빠뜨린 파일 고치기(`git commit --amend`), 커밋 취소하고 변경은 남기기(`git reset --soft`, `--mixed`), 변경까지 버리는 `--hard`가 위험한 이유
- **공개된 이력 되돌리기** — `git revert`로 되돌리는 커밋 만들기, 이미 푸시한 커밋은 고치지 않고 되돌린다는 원칙, `reset`과 `revert`의 선택 기준
- **잃어버린 커밋 찾기** — `git reflog`로 지난 `HEAD`의 위치 보기, 잘못된 `reset`·지운 브랜치 되살리기, "커밋한 것은 거의 잃어버리지 않는다"는 안전망
- **작업 잠시 치워 두기** — `git stash`(`push -m`, `list`, `pop`, `apply`), 기본 stash는 추적하지 않는 새 파일을 보관하지 않는다는 점과 새 파일까지 보관하기(`git stash push -u`, `.gitignore`에 적힌 파일은 그래도 남는다), 보관한 뒤 `git status`로 작업 폴더가 깨끗한지 확인하기, stash 대신 작업용 커밋이나 브랜치를 쓰는 편이 나을 때
- **이력 다듬기** — 다른 브랜치의 커밋 하나 가져오기(`git cherry-pick`), `git rebase`로 브랜치를 최신 `main` 위로 옮기기와 병합과의 차이, 대화형 리베이스(`git rebase -i`)로 푸시 전 커밋 정리하기, 남과 공유한 브랜치에서는 리베이스하지 않는 이유
- **버전 표시** — 태그(`git tag -a v0.1.0`), 태그 목록과 태그 시점으로 가 보기, 태그 푸시(중급 과정 8장의 버전 표시로 연결)
- **(선택) 버그가 들어온 커밋 찾기** — `git bisect`로 이진 탐색하기, 기초 과정의 `check_samples.py`처럼 종료 코드로 성공·실패를 알리는 검사 스크립트와 함께 쓰기(`git bisect run`)
- **AI 코딩 도구와 Git** — AI에게 맡기기 전에 지금까지의 변경을 커밋하거나 `git stash push -u`로 보관하고(새 파일은 `git add`해야 커밋에 들어가고, 기본 `git stash`로는 보관되지 않는다) `git status`로 작업 폴더가 깨끗한지 확인한 뒤 AI 작업용 브랜치를 만들어 진행하기(브랜치를 만들거나 옮기는 것만으로는 커밋하지 않은 변경이 보존되지 않고 새 브랜치로 따라온다), AI가 바꾼 내용을 `git diff`로 검토하고 받아들일 부분만 `git add -p`로 스테이징한 뒤 나머지는 `git restore`로 버리기(5장의 "스테이징 영역 기준" 복원이 여기서 쓰인다), AI가 쓴 커밋 메시지 확인하기, 여러 작업을 동시에 맡길 때 작업 트리를 나누기(`git worktree`)

### 8장. GitHub로 공유하고 협업하기

- **원격 저장소** — 원격(remote)과 `origin`, 내 저장소를 GitHub에 올리기(`git remote add`, `git push -u`), 받아 오기(`git clone`), `fetch`와 `pull`의 차이, 원격 추적 브랜치(`origin/main`)와 "앞서 있음·뒤처짐" 읽기, 푸시가 거절될 때(먼저 받아 와서 합치기)
- **인증** — HTTPS와 SSH, GitHub CLI로 로그인하기(`gh auth login`), 자격 증명 관리자, SSH 키 만들기·등록하기(`ssh-keygen -t ed25519`, `ssh -T git@github.com`), 비밀번호 대신 토큰을 쓰는 이유
- **비밀 값을 올리지 않기** — API 키를 담은 `.env`를 `.gitignore`에 넣고 `.env.example`만 올리기, 커밋하기 전에 비밀 값이 섞였는지 확인하기, GitHub의 비밀 값 검사(push protection), 키를 올려 버렸을 때의 순서(키부터 폐기·재발급, 그다음 이력 정리) — 코드에서 `.env`를 읽는 방법은 "웹·API 기초"에서
- **GitHub 저장소 꾸리기** — `README.md` 렌더링(Markdown 문법 정리), 라이선스, 공개·비공개 저장소, 저장소 설명과 주제(topics), 1단계 결과물 저장소 다시 보기
- **이슈와 풀 리퀘스트** — 이슈로 할 일·버그 기록하기, 브랜치 → 푸시 → 풀 리퀘스트(PR) → 리뷰 → 병합 흐름, PR 설명 쓰기, 커밋 메시지와 PR로 이슈 닫기(`Closes #12`), 병합 방식(병합 커밋·스쿼시·리베이스) 비교, 병합 후 브랜치 정리
- **코드 리뷰** — 변경된 파일 화면에서 줄 단위 의견 달기, 변경 요청과 승인, 리뷰받기 좋은 PR의 크기, 내 PR을 스스로 먼저 리뷰하는 습관, AI가 만든 변경을 PR로 받아 검토하기
- **GitHub CLI** — `gh repo create`, `gh issue`, `gh pr create`·`list`·`checkout`·`merge`, 터미널에서 리뷰 흐름 끝까지 해 보기
- **오픈 소스 기여의 흐름** — 포크(fork)와 `upstream` 원격, 포크를 원본과 맞추기, 기여 안내(`CONTRIBUTING.md`) 읽기, 작은 PR 보내기(4단계 오픈소스 기여로 연결)
- **(선택) GitHub에서 자동으로 실행하기** — GitHub Actions의 개념(푸시하면 정해진 명령이 실행된다), 워크플로 파일 읽어 보기, 실행 결과 확인(직접 작성은 중급 과정 8장에서)

### 9장. Jupyter Notebook

- **노트북이란** — 코드 셀·Markdown 셀·출력이 한 파일(`.ipynb`)에 담긴다는 것, 커널(코드를 실행하는 파이썬 프로세스), 노트북이 어울리는 일(데이터 탐색, 프롬프트 실험, 학습 기록)과 스크립트가 어울리는 일(반복 실행, 다른 코드에서 가져다 쓰기)
- **설치와 커널 선택** — 어디서 노트북을 쓰는지에 따라 설치할 패키지가 다르다는 점(VS Code에서 쓸 때는 프로젝트 가상환경에 `ipykernel`만 설치하고 VS Code에서 노트북을 열어 커널 선택, 브라우저에서 쓸 때는 `jupyterlab`을 설치하고 `jupyter lab`으로 실행), "커널의 파이썬"이 터미널의 파이썬과 다를 수 있다는 점(기초 과정 9장의 `sys.executable`로 확인)
- **셀 다루기** — 실행(`Shift+Enter`), 셀 추가·삭제·이동·종류 바꾸기 단축키, 마지막 식의 값이 자동으로 출력되는 규칙, 실행 번호 읽기, Markdown 셀로 설명 쓰기(제목·목록·표·코드·수식)
- **숨은 상태의 함정** — 위아래가 아니라 실행한 순서대로 변수가 남는다는 것, 지운 셀의 변수가 살아 있는 문제, 커널 재시작과 "모두 실행"(Restart & Run All)으로 확인하는 습관, 변수 보기 창, 무한 반복을 멈추는 인터럽트
- **매직 명령과 셸 명령** — `%pip install`이 `!pip install`보다 안전한 이유(커널의 환경에 설치), `!ls` 같은 셸 명령, 실행 시간 재기(`%time`, `%timeit`), 셀 내용을 파일로 저장(`%%writefile`), 고친 모듈 다시 불러오기(`%autoreload`), 노트북에서는 `await`를 바로 쓸 수 있다는 점(중급 과정 7장으로 연결)
- **노트북에서 프로그램으로** — 노트북에서 실험한 코드를 함수로 정리해 `.py` 모듈로 옮기고 노트북에서 import하기, 스크립트·HTML로 내보내기(`jupyter nbconvert`), 노트북이 너무 길어졌을 때의 신호
- **노트북과 Git** — `.ipynb`가 JSON이라 diff가 읽기 어렵다는 점, 출력·실행 번호 때문에 생기는 불필요한 변경, 출력을 지우고 커밋하기(`nbstripout`), 출력에 API 키·개인정보가 남는 위험, GitHub·VS Code에서 노트북 diff 보기
- **클라우드 노트북 소개** — Google Colab·Kaggle 노트북, 로컬 노트북과의 차이(파일·패키지·비밀 값 다루기), GPU가 필요한 3단계에서 다시 만난다

### 10장. 마무리

- **종합 실습** — 기초 과정 10장에서 만든 프로젝트(가계부 요약 또는 직접 만든 CLI 프로그램)를 이 과정의 도구로 다시 다룬다. 저장소로 만들어 GitHub에 올리고, 새 기능 하나를 이슈 → 브랜치 → PR → 리뷰 → 병합 흐름으로 추가하고, 프로그램이 만든 결과를 노트북에서 탐색한다. 마지막으로 기초 과정의 "복원 시험 B"를 Git 저장소에서 내려받는 방식으로 다시 한다.
   - 완료 기준
     - `.venv`, `__pycache__`, 개인 데이터 파일, `.env`가 저장소에 들어가지 않았음을 `git status`, `git check-ignore -v`, GitHub 화면으로 보인다
     - 커밋 하나가 한 가지 일을 하고, 커밋 메시지만 읽어도 무엇을 왜 바꿨는지 알 수 있다
     - 기능 하나를 이슈와 PR로 추가하고, PR에 리뷰 의견을 남기고 반영한 기록이 GitHub에 있다
     - 두 브랜치에서 같은 곳을 고쳐 충돌을 일부러 만들고, 해결해 병합한 이력을 `git log --graph`로 보이고 해결 과정을 설명할 수 있다
     - 잘못 넣은 커밋 하나를 `git revert`로 되돌리고, 첫 완성 시점에 태그(`v1.0.0`)를 단다
     - 명령행 인자를 준 디버그 실행 설정(`launch.json`)과 권장 확장 목록을 저장소에 포함하고, 다른 사람이 받아서 바로 디버깅할 수 있다
     - 프로젝트의 모듈을 import해 결과를 탐색하는 노트북이 출력을 지운 상태로 커밋되어 있고, 새 커널에서 "모두 실행"으로 끝까지 실행된다
     - 다른 폴더(가능하면 다른 운영체제의 컴퓨터)에서 `git clone` 후 `README.md`에 적힌 명령만으로 가상환경을 복원하고 실행·검사 스크립트를 통과한다
     - 프로젝트에서 반복하는 명령(검사 실행 등)을 `&&`로 이은 한 줄 명령이나 스크립트로 정리해 `README.md`에 적는다
   - 선택 활동
     - AI 코딩 도구에게 기능 하나를 맡기되 별도 브랜치(또는 작업 트리)에서 하게 하고, 결과를 PR로 받아 검토한 뒤 일부만 받아들인다. 받아들이지 않은 부분과 그 이유를 PR에 적는다.
     - 1단계에서 만든 결과물의 저장소를 다시 열어 `.gitignore`와 `README.md`를 보강하고, 이력에 비밀 값이 남아 있지 않은지 확인한다.
     - 관심 있는 오픈 소스 저장소를 포크해 문서의 오타나 깨진 링크를 고치는 작은 PR을 보낸다.
