# 4장. 클로저와 데코레이터

[파이썬 중급](README.md) 과정의 네 번째 장이다. 기초 과정에서 `@property`와 `@dataclass`를 붙여 쓰면서 "데코레이터를 직접 만드는 방법은 파이썬 중급에서 배운다"고 미뤄 두었다(기초 과정 5.2.6). 1장에서는 "`@deco`는 `f = deco(f)`"라고 미리 보았고(1.3.1), 어떤 함수든 감싸서 부르는 `log_call()`을 만들었다(1.3.3). 3장에서는 끝을 정하지 않고 반복하다가 성공하면 `break`하는 재시도 반복을 보았다(3.5.5). 이 장에서 이것들을 하나로 묶는다. 함수 안에서 함수를 만들고, 그 함수가 바깥 변수를 기억하게 하면, **어떤 함수에든 기능을 덧붙이는 도구**를 만들 수 있다.

- **중첩 함수와 클로저** — 함수 안의 함수, 함수를 돌려주는 함수를 만든다. 바깥 함수가 끝난 뒤에도 바깥 변수를 기억하는 클로저와 `nonlocal`, 반복문 안에서 만든 람다가 모두 같은 값을 보는 늦은 바인딩 함정을 익힌다.
- **데코레이터 만들기** — `@deco`가 `f = deco(f)`의 줄임이라는 것을 확인하고, `*args`/`**kwargs`로 어떤 함수든 감싸는 래퍼를 만든다. `functools.wraps`로 이름과 독스트링을 지키고, 데코레이터 여러 개를 겹쳐 붙일 때의 순서를 본다.
- **인자를 받는 데코레이터** — `@retry(times=3)`처럼 괄호가 붙는 데코레이터의 세 겹 구조를 읽는다. 횟수, 대기 시간, 지수 백오프, 다시 시도할 예외를 정하는 재시도 데코레이터를 만들어 LLM API의 시간 초과와 요청 한도 초과(429)에 대비한다.
- **표준 라이브러리의 데코레이터** — `functools.cache`/`lru_cache`로 같은 입력의 결과를 다시 쓰고, `@classmethod`로 대체 생성자 `from_dict()`를, `@staticmethod`로 객체가 필요 없는 메서드를 만든다. 붙여 쓰기만 한 `@property`와 `@dataclass`를 다시 보고, `__eq__`를 만들면 `__hash__`가 사라지는 이유를 확인한다.
- **등록 데코레이터** — 함수를 딕셔너리에 등록하는 데코레이터를 만들어, 웹 프레임워크의 `@app.get("/...")`와 MCP 서버의 `@mcp.tool()`이 하는 일을 흉내 낸다. 함수를 도구 객체로 바꿔 돌려주는 LangChain의 `@tool`과 비교한다.
- **컨텍스트 관리자 만들기** — `with` 문이 실제로 하는 일을 풀어 보고, `__enter__`/`__exit__`로, 그리고 `@contextmanager`와 제너레이터 하나로 컨텍스트 관리자를 만든다. 3장의 `yield`와 이 장의 데코레이터가 만나는 곳이다.

## 학습 목표

이 장을 마치면 다음을 할 수 있다.

- 함수를 돌려주는 함수를 만들고, 돌려받은 함수가 바깥 함수의 변수를 기억하는 모습을 `__closure__`로 확인할 수 있다.
- 바깥 함수의 변수에 다시 할당하려면 `nonlocal`이 필요한 이유를 기초 과정의 `UnboundLocalError`와 연결해 설명할 수 있다.
- 반복문 안에서 만든 람다가 모두 같은 값을 보는 늦은 바인딩 버그를 알아보고, 세 가지 방법으로 고칠 수 있다.
- `@deco`를 `f = deco(f)`로 바꿔 읽고, `*args`/`**kwargs`와 `functools.wraps`를 쓰는 데코레이터를 만들 수 있다.
- 데코레이터 여러 개가 붙은 함수에서 어느 데코레이터가 먼저 적용되고, 호출할 때 어느 래퍼가 먼저 실행되는지 말할 수 있다.
- 인자를 받는 데코레이터의 세 겹 구조를 읽고, 다시 시도할 예외와 대기 시간을 정하는 재시도 데코레이터를 만들 수 있다.
- `functools.cache`/`lru_cache`, `@classmethod`, `@staticmethod`, `@property`, `@dataclass`가 각각 무엇을 받아 무엇을 돌려주는지 설명하고, 알맞은 곳에 쓸 수 있다.
- 함수를 등록하는 데코레이터를 만들고, `@app.get("/...")`, `@mcp.tool()`, `@tool`이 하는 일을 직접 만든 코드와 비교해 설명할 수 있다.
- `__enter__`/`__exit__`로, 그리고 `@contextmanager`로 컨텍스트 관리자를 만들고, `try`/`finally`가 왜 필요한지 설명할 수 있다.

## 4.1 중첩 함수와 클로저

### 4.1.1 함수 안의 함수

`def`는 함수 안에서도 쓸 수 있다. 기초 과정 4.3에서 함수 안에서 만든 변수는 그 함수의 **지역 변수**라고 배웠다. `def`도 "함수 객체를 만들고 이름을 붙이는" 문장이므로(1.3.1), 함수 안에서 `def`로 만든 함수는 그 함수의 지역 이름이 된다.

`ch04/nested.py`

```python
"""함수 안의 함수."""


def format_report(items):
    """(이름, 금액) 목록을 표 모양의 문자열로 만든다."""

    def line(name, amount):
        return f"{name:<6}{amount:>10,}원"

    rows = [line(name, amount) for name, amount in items]
    total = sum(amount for _, amount in items)
    return "\n".join([*rows, "-" * 18, line("합계", total)])


if __name__ == "__main__":
    print(format_report([("식비", 320000), ("교통", 58000), ("구독", 17900)]))
```

```
python ch04/nested.py
```

```
식비       320,000원
교통        58,000원
구독        17,900원
------------------
합계       395,900원
```

`line()`은 `format_report()` 안에서만 쓰는 작은 도우미 함수다. 안에 둔 이유는 두 가지다.

- **쓰는 곳 가까이에 둔다.** `line()`이 어떤 모양의 줄을 만드는지, 그 줄을 어디서 쓰는지가 한눈에 보인다.
- **바깥에서는 보이지 않는다.** 파일 최상위에서 `line("식비", 1000)`을 부르면 `NameError`다. 지역 변수처럼, `format_report()`가 실행되는 동안에만 있는 이름이기 때문이다.

`format_report()`를 부를 때마다 안쪽의 `def line(...)`이 **다시 실행되어** 함수 객체가 새로 만들어진다. 이 사실이 다음 절에서 중요해진다.

> **도우미 함수를 언제 안에 둘까**
> 안쪽 함수는 테스트하기 어렵다. 바깥에서 부를 수 없으므로 6장의 pytest로 `line()`만 따로 검사할 수 없다. 도우미 함수가 몇 줄을 넘거나, 다른 함수에서도 쓸 것 같거나, 따로 검사하고 싶다면 최상위에 `_line()`처럼 밑줄을 붙여 둔다(기초 과정 5.2.5의 `_이름` 관례). 이 장에서 함수를 안에 두는 진짜 이유는 다음 절부터 나온다. **안쪽 함수를 바깥으로 돌려줄 때**다.

### 4.1.2 함수를 돌려주는 함수

함수는 값이므로(1.3.2) `return`으로 돌려줄 수도 있다.

```python
>>> def make_multiplier(factor):
...     def multiply(x):
...         return x * factor
...     return multiply
...
>>> double = make_multiplier(2)
>>> triple = make_multiplier(3)
>>> double
<function make_multiplier.<locals>.multiply at 0x104d03c10>
>>> double(5), triple(5)
(10, 15)
```

`make_multiplier(2)`는 `multiply`를 **호출하지 않고** 함수 객체 자체를 돌려준다. `return multiply`에 괄호가 없다(1.3.2). 돌려받은 함수에 `double`이라는 이름을 붙였다. 출력의 `make_multiplier.<locals>.multiply`는 "`make_multiplier`의 지역 이름 `multiply`로 만들어진 함수"라는 뜻이다.

`make_multiplier()`는 함수를 찍어 내는 틀이다. 인자를 바꿔 부를 때마다 **다른 함수**가 나온다. `double`과 `triple`은 똑같은 코드(`return x * factor`)를 가졌지만, 하나는 2를 곱하고 하나는 3을 곱한다.

LLM 코드에서도 같은 모양을 만난다. 역할(시스템 프롬프트)이 정해진 메시지 목록을 만드는 함수를 찍어 낸다.

```python
>>> def make_prompt(role):
...     def build(question):
...         return [
...             {"role": "system", "content": f"너는 {role}다."},
...             {"role": "user", "content": question},
...         ]
...     return build
...
>>> tutor = make_prompt("친절한 파이썬 강사")
>>> reviewer = make_prompt("깐깐한 코드 리뷰어")
>>> tutor("클로저가 뭐야?")
[{'role': 'system', 'content': '너는 친절한 파이썬 강사다.'}, {'role': 'user', 'content': '클로저가 뭐야?'}]
>>> reviewer("이 코드 어때?")[0]["content"]
'너는 깐깐한 코드 리뷰어다.'
```

### 4.1.3 바깥 변수를 기억하는 클로저

방금 본 코드에는 이상한 점이 있다. `double = make_multiplier(2)`가 끝나는 순간 `make_multiplier()`의 실행은 끝났다. 기초 과정 4.3.1에 따르면 함수가 끝나면 지역 변수는 사라진다. 그런데 `double(5)`를 부를 때 `multiply` 안의 `factor`는 여전히 2다. `factor`는 어디에 남아 있었을까?

```python
>>> double.__code__.co_freevars
('factor',)
>>> double.__closure__
(<cell at 0x104d09510: int object at 0x1064cee68>,)
>>> double.__closure__[0].cell_contents
2
>>> triple.__closure__[0].cell_contents
3
```

- `__code__.co_freevars` — 이 함수가 쓰지만 **자기 지역 변수도 아니고 전역 변수도 아닌** 이름, 즉 바깥 함수에서 빌려 쓰는 이름의 목록이다. `multiply`는 `factor`를 빌려 쓴다.
- `__closure__` — 빌려 쓰는 이름마다 **셀**(cell)이라는 작은 상자가 하나씩 들어 있다. 셀은 바깥 함수의 변수를 담아 두는 상자로, 바깥 함수가 끝나도 안쪽 함수가 붙들고 있는 한 사라지지 않는다.

이렇게 **바깥 함수의 변수를 붙들고 있는 함수**를 **클로저**(closure)라고 부른다. 함수가 만들어질 때의 주변 환경을 "닫아 넣어(close)" 가지고 다닌다는 뜻이다. `double`과 `triple`은 같은 코드를 쓰지만 서로 다른 셀을 가졌다. `make_multiplier()`를 부를 때마다 새 `factor` 변수와 새 `multiply` 함수가 함께 만들어지기 때문이다.

```
make_multiplier(2)를 부른 동안의 지역 이름          (호출이 끝나면 사라진다)
    factor ───▶ [셀] ───▶ 2
                  ▲
                  │ __closure__
double ───▶ multiply 함수 객체 (return x * factor)

make_multiplier(3)를 부른 동안의 지역 이름          (호출이 끝나면 사라진다)
    factor ───▶ [셀] ───▶ 3
                  ▲
                  │ __closure__
triple ───▶ multiply 함수 객체 (return x * factor)
```

함수 호출이 끝나면 지역 이름 `factor`는 사라진다. 그래도 셀은 함수 객체가 `__closure__`로 가리키고 있으므로 남는다. 1.3.1의 "이름표가 하나라도 붙어 있으면 객체는 사라지지 않는다"와 같은 원리다.

이제 파이썬이 이름을 찾는 순서를 정리할 수 있다. 기초 과정 4.3에서는 지역과 전역 두 단계만 보았다. 사이에 한 단계가 더 있다.

| 순서 | 범위 | 무엇인가 | 예 |
|---|---|---|---|
| 1 | 지역(Local) | 지금 실행 중인 함수 안에서 만든 이름 | `multiply`의 `x` |
| 2 | 감싸는 함수(Enclosing) | 바깥 함수의 지역 이름. 클로저가 셀로 붙든다 | `multiply`가 보는 `factor` |
| 3 | 전역(Global) | 파일(모듈) 최상위의 이름 | `make_multiplier`, `import`한 이름 |
| 4 | 내장(Built-in) | 파이썬이 처음부터 준비해 둔 이름 | `print`, `len`, `ValueError` |

머리글자를 따서 **LEGB 규칙**이라고 부른다. 안에서 밖으로 찾아 나가다가 처음 찾은 곳의 이름을 쓴다. 기초 과정에서 함수 안의 지역 `message`가 전역 `message`를 가렸던 것(기초 과정 4.3.3)도 이 규칙이다.

> **안쪽 함수는 바깥 변수의 "값"이 아니라 "변수"를 기억한다**
> 셀은 값을 복사해 둔 것이 아니라 **변수 자체**를 담고 있다. 그래서 바깥 함수가 안쪽 함수를 만든 **뒤에** 그 변수를 바꾸면, 안쪽 함수도 바뀐 값을 본다. 이 사실이 4.1.5의 함정을 만든다.

### 4.1.4 `nonlocal` — 바깥 변수에 다시 할당하기

부를 때마다 1씩 늘어나는 카운터를 클로저로 만들어 보자. 바깥 변수를 **읽기만** 했던 `make_multiplier()`와 달리, 이번에는 바깥 변수를 **바꿔야** 한다.

```python
>>> def make_counter():
...     count = 0
...     def increment():
...         count += 1
...         return count
...     return increment
...
>>> counter = make_counter()
>>> counter()
Traceback (most recent call last):
  ...
UnboundLocalError: cannot access local variable 'count' where it is not associated with a value
```

기초 과정 4.3.3의 방문자 수 세기에서 본 바로 그 오류다. 파이썬은 함수 본문 어디에서든 **할당**되는 이름을 그 함수의 지역 변수로 정한다. `count += 1`도 할당이므로, `increment()` 안의 `count`는 바깥의 `count`가 아니라 `increment()`의 지역 변수가 된다. 그런데 오른쪽의 `count + 1`을 계산할 때 그 지역 변수에는 아직 값이 없다.

기초 과정에서는 `global count`로 "이 이름은 전역 변수다"라고 알려 주었다. 바깥 함수의 변수에는 **`nonlocal`**을 쓴다.

`ch04/counter.py`

```python
"""nonlocal — 클로저가 바깥 변수를 바꾼다."""


def make_counter():
    """부를 때마다 1씩 늘어난 값을 돌려주는 함수를 만든다."""
    count = 0

    def increment():
        nonlocal count
        count += 1
        return count

    return increment


if __name__ == "__main__":
    c1 = make_counter()
    c2 = make_counter()
    print(c1(), c1(), c1(), c2())
```

```
python ch04/counter.py
```

```
1 2 3 1
```

`nonlocal count`는 "`count`는 내 지역 변수가 아니라, 나를 감싸는 함수의 변수다"라는 선언이다. 이제 `count += 1`은 셀 안의 값을 바꾼다. `c1`과 `c2`는 `make_counter()`를 따로 불러 만들었으므로 셀도 따로다. `c1`을 세 번 불러도 `c2`는 영향을 받지 않는다.

기초 과정 4.3.4에서 `global`을 피하라고 한 이유 넷 중 둘, "여러 개를 동시에 다룰 수 없다"와 "어디서 바뀌었는지 추적하기 어렵다"를 클로저는 피한다. 카운터마다 셀이 따로 있고, 그 셀은 `increment()` 말고는 아무도 바꿀 수 없다.

**할당하지 않으면 `nonlocal`이 필요 없다.** 바깥 변수가 리스트나 딕셔너리라면 `append()`나 `d[key] = ...`로 **내용을 바꾸는 것**은 이름에 다시 할당하는 것이 아니다(기초 과정 4.3.5).

```python
>>> def make_recorder():
...     history = []
...     def record(message):
...         history.append(message)   # history라는 이름에 할당하지 않는다
...         return len(history)
...     return record
...
>>> record = make_recorder()
>>> record("안녕"), record("날씨 알려 줘")
(1, 2)
```

`history = history + [message]`라고 썼다면 할당이므로 다시 `UnboundLocalError`다. **이름에 `=`(또는 `+=` 등)가 붙는가**로 판단한다.

| 안쪽 함수에서 하는 일 | 필요한 것 | 예 |
|---|---|---|
| 바깥 변수를 읽기만 한다 | 없음 | `return x * factor` |
| 바깥의 가변 객체의 **내용**을 바꾼다 | 없음 | `history.append(m)` |
| 바깥 변수에 **다시 할당**한다 | `nonlocal 이름` | `count += 1` |
| 전역 변수에 다시 할당한다 | `global 이름` (피한다) | |

### 4.1.5 늦은 바인딩 — 반복문 안에서 만든 람다

모델 이름마다 "그 모델에게 묻는 함수"를 만들어 딕셔너리에 담는다고 하자. 실제 API 대신 어느 모델이 답했는지만 문자열로 돌려준다.

```python
>>> MODELS = ["small", "medium", "large"]
>>> callers = {}
>>> for name in MODELS:
...     callers[name] = lambda question: f"[{name}] {question}"
...
>>> callers["small"]("안녕")
'[large] 안녕'
>>> callers["medium"]("안녕")
'[large] 안녕'
```

`small`에게 물었는데 `large`가 답했다. 세 함수가 **모두** `large`를 쓴다. 오류도 나지 않으므로, 실제 API를 부르는 코드였다면 비싼 모델에게 모든 요청이 가는 것을 청구서를 보고서야 알게 된다.

4.1.3의 상자를 떠올린다. 람다는 `name`의 **값**을 복사해 두지 않았다. `name`이라는 **변수**를 기억했다. 그리고 람다의 본문 `f"[{name}] {question}"`은 람다를 **부를 때** 실행된다. 반복문이 끝난 뒤에 부르면, 그때 `name`이 가리키는 값은 마지막 값 `"large"`다. 셋이 모두 같은 변수를 보고 있으므로 셋 다 `large`다.

이것을 **늦은 바인딩**(late binding)이라고 한다. 변수의 값을 함수를 만들 때가 아니라 **부를 때** 찾는다는 뜻이다. 3.3.4에서 제너레이터 표현식의 `if` 절이 만들 때가 아니라 꺼낼 때 `limit`을 읽은 것과 같은 원리다. 리스트 컴프리헨션으로 만들어도 마찬가지다.

```python
>>> funcs = [lambda: i for i in range(3)]
>>> [f() for f in funcs]
[2, 2, 2]
```

컴프리헨션의 `i`는 밖으로 새지 않지만(2.1.6), 컴프리헨션 안에서는 셋이 같은 `i`를 공유한다. 반복이 끝났을 때 `i`는 2다.

고치는 방법은 세 가지다. 모두 "**함수를 만드는 그 순간의 값**을 붙잡아 둔다"는 생각이다.

**(가) 기본값으로 붙잡기**

```python
>>> for name in MODELS:
...     callers[name] = lambda question, name=name: f"[{name}] {question}"
...
>>> callers["small"]("안녕")
'[small] 안녕'
```

`name=name`은 "매개변수 `name`의 기본값은 지금의 `name` 값"이라는 뜻이다. 기본값은 함수를 **정의할 때** 한 번 계산된다(기초 과정 4.2.4). 그래서 반복마다 그때의 값이 기본값으로 저장된다. 짧아서 자주 보이는 관용구다. 단점은 매개변수가 하나 늘어난다는 것이다. 누군가 `callers["small"]("안녕", "large")`처럼 두 번째 인자를 넘기면 기본값이 덮어써진다.

**(나) 함수를 만드는 함수로 붙잡기**

```python
>>> def make_caller(name):
...     def call(question):
...         return f"[{name}] {question}"
...     return call
...
>>> callers = {name: make_caller(name) for name in MODELS}
>>> callers["small"]("안녕"), callers["large"]("안녕")
('[small] 안녕', '[large] 안녕')
```

4.1.2의 `make_multiplier()`와 같은 모양이다. `make_caller()`를 부를 때마다 **새 `name` 변수**(새 셀)가 생기므로, 함수마다 자기만의 `name`을 갖는다. 가장 분명한 방법이다.

**(다) `functools.partial`로 붙잡기**

```python
>>> from functools import partial
>>> def call_model(name, question):
...     return f"[{name}] {question}"
...
>>> callers = {name: partial(call_model, name) for name in MODELS}
>>> callers["medium"]("안녕")
'[medium] 안녕'
```

`partial(함수, 인자...)`는 **앞쪽 인자를 미리 채워 둔** 새 호출 가능 객체를 만든다. `partial(call_model, "medium")`을 부르면 `call_model("medium", ...)`이 된다. 미리 채울 값은 `partial()`을 부를 때 계산되므로 늦은 바인딩이 생기지 않는다. 이미 있는 함수에 인자 일부만 고정하고 싶을 때 쓴다.

| 방법 | 장점 | 단점 |
|---|---|---|
| (가) 기본값 `name=name` | 한 줄로 고친다 | 매개변수가 늘어 실수로 덮어쓸 수 있다. 처음 보는 사람은 이유를 모른다 |
| (나) 함수를 만드는 함수 | 의도가 가장 분명하다 | 함수 정의가 하나 더 필요하다 |
| (다) `partial` | 이미 있는 함수에 인자만 고정할 때 짧다 | 결과가 함수가 아니라 `partial` 객체라서, 이름(`__name__`)이 없다 |

> **반복문 안에서 `lambda`나 `def`를 보면 의심한다**
> 반복문 안에서 만든 함수가 반복 변수를 쓰고, 그 함수를 **반복이 끝난 뒤에** 부른다면 늦은 바인딩이다. 반복 안에서 바로 부르고 버린다면(`sorted(..., key=lambda x: ...)`처럼) 문제가 없다. AI가 만든 코드에서 "버튼마다 핸들러 만들기", "도구마다 함수 만들기" 같은 반복문을 보면 이 점을 확인한다.

### 4.1.6 클로저와 클래스

`make_counter()`가 하는 일은 기초 과정 5장의 클래스로도 할 수 있다. 1.3.4의 `Counter` 클래스가 바로 그것이었다. 둘 다 **상태(`count`)와 그 상태를 다루는 동작(`increment`)을 한데 묶는다.**

| | 클로저 | 클래스 |
|---|---|---|
| 상태 | 바깥 함수의 지역 변수(셀) | 인스턴스 속성 `self.count` |
| 동작 | 돌려준 함수 하나 | 메서드 여러 개 |
| 바깥에서 상태 보기 | 어렵다(`__closure__`를 뒤져야 한다) | `c.count`로 바로 본다 |
| 어울리는 곳 | 동작이 **하나**이고 상태가 작다. 함수를 받는 곳(`key=`, 콜백, 데코레이터)에 넘긴다 | 동작이 여럿이거나, 상태를 바깥에서 보고 바꿔야 한다 |

동작이 하나뿐인 작은 상태에는 클로저가 짧고 깔끔하다. "현재 값 보기", "초기화하기"가 필요해지면 클래스로 바꾼다. 이 장에서 클로저를 배우는 가장 큰 이유는 다음 절의 데코레이터다. **데코레이터가 돌려주는 래퍼 함수가 바로 클로저**다.

## 4.2 데코레이터 만들기

### 4.2.1 함수를 받아 함수를 돌려주기

1.3.3에서 어떤 함수든 감싸서 부르는 `log_call()`을 만들었다.

```python
def log_call(func, *args, **kwargs):
    print(f"호출: {func.__name__} args={args} kwargs={kwargs}")
    return func(*args, **kwargs)


print(log_call(area, 3, 4, unit="m"))
```

동작은 하지만 불편하다. `area()`를 부르는 곳이 스무 군데라면 스무 군데를 모두 `log_call(area, ...)`으로 고쳐야 한다. 기록을 그만 남기고 싶으면 다시 스무 군데를 고쳐야 한다. 1.3.3에서 예고한 대로, **`area(3, 4, unit="m")`이라고 불러도 기록이 남게** 하고 싶다.

방법은 이렇다. `area`를 받아서, "기록을 남긴 뒤 `area`를 부르는" **새 함수**를 만들어 돌려준다. 그리고 그 새 함수에 `area`라는 이름을 다시 붙인다. 4.1.2에서 함수를 돌려주는 함수를 만들었고, 4.1.3에서 안쪽 함수가 바깥 함수의 변수를 기억하는 것을 보았다. 이번에는 바깥 함수의 매개변수가 **함수**일 뿐이다.

`ch04/logged.py`

```python
"""데코레이터의 시작 — 함수를 받아 함수를 돌려준다."""


def logged(func):
    """호출할 때마다 인자와 결과를 출력하는 함수를 만들어 돌려준다."""

    def wrapper(*args, **kwargs):
        print(f"[호출] {func.__name__} args={args} kwargs={kwargs}")
        result = func(*args, **kwargs)
        print(f"[결과] {func.__name__} → {result!r}")
        return result

    return wrapper


def area(width, height, unit="cm"):
    """사각형의 넓이를 단위와 함께 돌려준다."""
    return f"{width * height}{unit}²"


if __name__ == "__main__":
    area = logged(area)
    print(area(3, 4, unit="m"))
```

```
python ch04/logged.py
```

```
[호출] area args=(3, 4) kwargs={'unit': 'm'}
[결과] area → '12m²'
12m²
```

`area = logged(area)` 한 줄이 하는 일을 따라간다.

1. `logged(area)`가 실행된다. 매개변수 `func`가 원래의 `area` 함수를 가리킨다.
2. `logged()` 안에서 `wrapper` 함수가 만들어진다. `wrapper`는 바깥 변수 `func`를 쓰므로 **클로저**다. `func`를 셀에 붙들고 있다.
3. `logged()`는 `wrapper`를 돌려준다. 그 함수에 `area`라는 이름이 **다시** 붙는다(1.3.1).

이제 `area`라는 이름은 `wrapper`를 가리키고, 원래의 `area` 함수는 `wrapper`의 셀 안에서만 살아 있다. `area(3, 4, unit="m")`을 부르면 실제로는 `wrapper(3, 4, unit="m")`이 실행되고, `wrapper`가 기록을 남긴 뒤 셀 안의 원래 함수를 부른다.

```
area = logged(area) 이전              area = logged(area) 이후

area ──▶ 원래 area 함수               area ──▶ wrapper ──(셀 func)──▶ 원래 area 함수
                                               기록 → 호출 → 기록
```

이렇게 **함수를 받아서, 기능을 덧붙인 함수를 돌려주는 함수**를 **데코레이터**(decorator)라고 부른다. 원래 함수를 고치지 않고 겉을 꾸민다(decorate)는 뜻이다. 덧붙인 기능을 실행하는 안쪽 함수는 원래 함수를 감싼다고 해서 **래퍼**(wrapper)라고 부른다.

### 4.2.2 `@deco`는 `f = deco(f)`의 줄임

`area = logged(area)`를 함수 정의 **아래에** 따로 쓰는 것은 두 가지 면에서 불편하다. 함수 이름을 세 번 써야 하고, 함수 정의만 읽어서는 이 함수가 꾸며진다는 것을 알 수 없다. 그래서 파이썬은 줄임 문법을 준다. `logged.py`에서 `area = logged(area)` 줄을 지우고, `area` 정의 바로 위에 `@logged`를 붙인다.

```python
@logged
def area(width, height, unit="cm"):
    """사각형의 넓이를 단위와 함께 돌려준다."""
    return f"{width * height}{unit}²"


if __name__ == "__main__":
    print(area(3, 4, unit="m"))
```

출력은 똑같다. 다음 두 코드는 **완전히 같다.**

```python
@logged                                def area(width, height, unit="cm"):
def area(width, height, unit="cm"):        ...
    ...                                area = logged(area)
```

기초 과정에서 붙여 쓴 `@property`와 `@dataclass`도 이 규칙대로 읽는다. `@property def balance(self): ...`는 `balance = property(balance)`이고, `@dataclass class Product: ...`는 `Product = dataclass(Product)`다. 4.4에서 이 둘을 다시 본다.

**데코레이터는 함수를 정의할 때 실행된다.** `@logged` 줄은 `def` 문이 끝나는 순간 `logged(area)`를 **한 번** 부른다. 래퍼가 하는 일(기록 남기기)은 함수를 **부를 때마다** 실행된다. 두 때를 구별하기 위해 정의할 때 출력하는 데코레이터를 만들어 본다.

```python
>>> def announce(func):
...     print(f"[꾸미는 중] {func.__name__}")
...     return func
...
>>> print("정의 전")
정의 전
>>> @announce
... def hello():
...     print("안녕")
...
[꾸미는 중] hello
>>> hello()
안녕
>>> hello()
안녕
```

`[꾸미는 중]`은 `hello()`를 한 번도 부르지 않았는데, `def` 문이 끝나자마자 출력되었다. 그 뒤로 `hello()`를 몇 번 불러도 다시 출력되지 않는다. `announce()`는 받은 함수를 **그대로** 돌려주므로 `hello`는 원래 함수 그대로다. 래퍼를 만들지 않는 이런 데코레이터도 쓸모가 있다. 4.5의 등록 데코레이터가 이 모양이다.

파일에 있는 데코레이터라면 그 파일을 실행하거나 **`import`할 때** 실행된다는 뜻이다. 이 사실은 4.5.5에서 중요해진다.

| 때 | 실행되는 것 | `logged`에서 |
|---|---|---|
| 정의할 때 (`def` 문이 끝날 때, 한 번) | 데코레이터 함수의 본문 | `def wrapper(...)`로 래퍼를 만들고 돌려준다 |
| 부를 때 (매번) | 래퍼의 본문 | 기록 → 원래 함수 호출 → 기록 → 결과 돌려주기 |

### 4.2.3 어떤 함수든 감싸기

래퍼의 모양은 거의 정해져 있다. 하나씩 빠뜨려 보면 왜 그런 모양인지 알 수 있다.

**`*args, **kwargs` — 어떤 인자든 받아 그대로 넘긴다.** 래퍼는 감쌀 함수가 어떤 매개변수를 받는지 모른다. `area(width, height, unit)`일 수도 있고 `ask(prompt)`일 수도 있다. 1.3.3의 `log_call()`처럼 받은 것을 모아서 그대로 풀어 넘기면 어떤 함수든 감쌀 수 있다. 래퍼를 `def wrapper(x):`로 만들면 인자가 하나인 함수만 감쌀 수 있다.

**`return result` — 결과를 돌려준다.** 래퍼에서 `return`을 빠뜨리는 것은 데코레이터를 처음 만들 때 가장 흔한 실수다.

```python
>>> def logged_bad(func):
...     def wrapper(*args, **kwargs):
...         print(f"[호출] {func.__name__}")
...         func(*args, **kwargs)
...     return wrapper
...
>>> @logged_bad
... def add(a, b):
...     return a + b
...
>>> add(1, 2)
[호출] add
>>> print(add(1, 2))
[호출] add
None
```

원래 함수는 3을 돌려주었지만, 래퍼가 그 값을 버리고 `None`을 돌려주었다(기초 과정 4.1.6). **오류가 나지 않는다**는 점이 위험하다. 데코레이터를 붙였더니 결과가 `None`이 되었다면 래퍼의 `return`부터 확인한다.

**예외는 래퍼를 지나 그대로 올라간다.** 원래 함수에서 예외가 나면, 래퍼의 `result = func(...)` 줄에서 예외가 난 것과 같다. 래퍼가 잡지 않으면 예외는 래퍼를 부른 쪽으로 올라간다(1.3.5). 그래서 `[결과]` 줄은 출력되지 않는다. 예외가 나도 무언가를 꼭 해야 한다면 `try`/`finally`로 감싼다(4.2.5). 일부러 예외를 잡아서 다시 시도하는 것이 4.3의 재시도 데코레이터다.

래퍼가 할 수 있는 일을 모아 보면, 이 장의 나머지 데코레이터가 모두 이 중 하나다.

| 래퍼가 하는 일 | 예 | 이 장에서 |
|---|---|---|
| 부르기 전·후에 무언가 한다 | 기록 남기기, 시간 재기 | 4.2 `logged`, `timed` |
| 예외를 잡아서 다시 부른다 | 재시도 | 4.3 `retry` |
| 원래 함수를 **부르지 않고** 결과를 돌려준다 | 캐시 | 4.4 `cache` |
| 래퍼를 만들지 않고 함수를 어딘가에 기록해 둔다 | 등록 | 4.5 `command`, `app.get` |
| 함수가 아닌 다른 객체로 바꿔 돌려준다 | 도구 객체, 프로퍼티 | 4.4 `property`, 4.5 `as_tool` |

### 4.2.4 `functools.wraps` — 원래 함수의 이름과 독스트링 지키기

`@logged`를 붙인 `area`를 대화형 셸에서 살펴본다. `ch04` 폴더에서 대화형 셸을 연다.

```python
>>> from logged import area
>>> area
<function logged.<locals>.wrapper at 0x10492bcc0>
>>> area.__name__, area.__doc__
('wrapper', None)
```

`area`라는 이름이 가리키는 것은 래퍼이므로, 함수의 이름은 `wrapper`이고 독스트링은 없다. `help(area)`를 해 봐도 "사각형의 넓이를 단위와 함께 돌려준다"는 설명은 보이지 않는다. 사소해 보이지만 실제로 문제가 된다.

- **함수 이름과 독스트링을 읽는 도구가 망가진다.** 1.1.3 (다)의 LangChain `@tool`은 함수의 이름과 독스트링으로 LLM에게 보여 줄 도구 설명을 만든다. 기록 데코레이터를 함께 붙였더니 모든 도구의 이름이 `wrapper`이고 설명이 비어 있다면, LLM은 어떤 도구를 써야 할지 모른다. 4.5에서 만들 등록 데코레이터도 함수 이름으로 등록한다.
- **기록과 오류 메시지가 헷갈린다.** 데코레이터를 붙인 함수가 열 개라면, 기록에 `wrapper`가 열 번 찍혀도 어느 함수인지 알 수 없다.

표준 라이브러리 `functools`의 `wraps`가 이 문제를 고친다. `logged.py`를 다음과 같이 고친다.

```python
"""데코레이터의 시작 — 함수를 받아 함수를 돌려준다."""

import functools


def logged(func):
    """호출할 때마다 인자와 결과를 출력하는 데코레이터."""

    @functools.wraps(func)
    def wrapper(*args, **kwargs):
        print(f"[호출] {func.__name__} args={args} kwargs={kwargs}")
        result = func(*args, **kwargs)
        print(f"[결과] {func.__name__} → {result!r}")
        return result

    return wrapper
```

대화형 셸을 다시 열어(기초 과정 8.1.3) 확인한다.

```python
>>> from logged import area
>>> area.__name__, area.__doc__
('area', '사각형의 넓이를 단위와 함께 돌려준다.')
>>> area.__wrapped__(1, 2)
'2cm²'
```

`@functools.wraps(func)`는 래퍼 위에 붙인 데코레이터다. 원래 함수 `func`의 이름(`__name__`), 독스트링(`__doc__`), 모듈 이름 등을 **래퍼에 복사**하고, 원래 함수를 `__wrapped__` 속성에 담아 둔다. 그래서 `area.__wrapped__(1, 2)`는 기록 없이 원래 함수를 부른다. 데코레이터가 붙은 라이브러리 함수를 디버깅할 때 쓸 수 있다.

`wraps(func)`처럼 **괄호 안에 인자를 받는 데코레이터**는 4.3에서 직접 만든다. 지금은 모양만 기억한다. **데코레이터를 만들 때는 래퍼에 늘 `@functools.wraps(func)`를 붙인다.** 이 장의 데코레이터는 모두 그렇게 한다.

### 4.2.5 실행 시간 재기 — 예외가 나도 기록하기

두 번째 데코레이터로 실행 시간을 재는 `timed`를 만든다. LLM API 호출이 얼마나 걸리는지 재는 일은 아주 흔하다. `logged.py`의 `logged()` 아래에 더한다.

```python
import time  # 파일 맨 위의 import functools 아래에 더한다


def timed(func):
    """실행 시간을 재서 출력하는 데코레이터. 예외가 나도 시간을 출력한다."""

    @functools.wraps(func)
    def wrapper(*args, **kwargs):
        start = time.perf_counter()
        try:
            return func(*args, **kwargs)
        finally:
            elapsed = time.perf_counter() - start
            print(f"[시간] {func.__name__}: {elapsed:.3f}초")

    return wrapper
```

`time.perf_counter()`는 시간 간격을 잴 때 쓰는 시계다(3.6.2). `logged`와 다른 점은 `try`/`finally`다(기초 과정 6.1.8).

- `return func(*args, **kwargs)` — 원래 함수의 결과를 바로 돌려준다. `return`이 있어도 `finally` 블록은 함수를 빠져나가기 **전에** 반드시 실행된다.
- 원래 함수에서 예외가 나도 `finally` 블록이 실행되어 시간이 출력된다. 그다음 예외는 그대로 올라간다. LLM API 호출은 실패할 때 오래 걸리는 경우가 많다(시간 초과는 정의상 오래 걸린다). **실패한 호출의 시간이야말로 재야 할 시간**이다.

`logged`처럼 `result = func(...)` 다음 줄에서 시간을 출력하게 만들었다면, 예외가 났을 때 그 줄까지 가지 못해 시간이 기록되지 않는다.

### 4.2.6 데코레이터 여러 개를 겹쳐 붙이기

데코레이터는 여러 개를 겹쳐 붙일 수 있다. `logged.py`의 `area` 아래에 두 함수를 더한다.

```python
@timed
@logged
def slow_add(a, b):
    time.sleep(0.2)
    return a + b


@logged
@timed
def slow_mul(a, b):
    time.sleep(0.2)
    return a * b
```

`if __name__ == "__main__":` 아래를 다음으로 바꾸고 실행한다. 실행하기 **전에** 두 함수의 출력 순서를 예측한다.

```python
    print(slow_add(1, 2))
    print("---")
    print(slow_mul(2, 3))
```

```
[호출] slow_add args=(1, 2) kwargs={}
[결과] slow_add → 3
[시간] slow_add: 0.203초
3
---
[호출] slow_mul args=(2, 3) kwargs={}
[시간] slow_mul: 0.200초
[결과] slow_mul → 6
6
```

`@`가 여러 개이면 **함수에 가까운 것(아래)부터** 적용된다. `slow_add`는 다음과 같다.

```python
slow_add = timed(logged(slow_add))
```

`logged`가 먼저 원래 함수를 감싸고, `timed`가 그 결과(로그 래퍼)를 다시 감싼다. 양파 껍질처럼 바깥 껍질이 `timed`, 안쪽 껍질이 `logged`다. **부를 때는 바깥 껍질부터** 들어간다.

```
slow_add(1, 2) 호출
└─ timed의 래퍼: 시계 시작
   └─ logged의 래퍼: [호출] 출력
      └─ 원래 slow_add: 0.2초 자고 3을 돌려준다
   └─ logged의 래퍼: [결과] 출력, 3을 돌려준다
└─ timed의 래퍼: [시간] 출력, 3을 돌려준다
```

`slow_mul`은 순서가 반대라서 `[시간]`이 `[결과]`보다 먼저 나온다. 출력 순서만 다른 것이 아니다. `slow_add`에서 `timed`가 잰 시간에는 `logged`가 출력하는 시간도 들어 있다. 무엇을 바깥에 둘지는 **무엇을 재고 싶은가**로 정한다. 4.3에서 재시도 데코레이터와 함께 쓸 때 이 순서가 결과를 크게 바꾼다. "재시도를 포함한 전체 시간"과 "한 번 시도한 시간"은 다르기 때문이다.

> **정의할 때는 아래부터, 부를 때는 위부터**
> 겹쳐 붙인 데코레이터는 정의할 때 아래(함수 쪽)부터 적용되고, 부를 때는 위(바깥)의 래퍼부터 실행된다. 헷갈리면 `f = 위(아래(f))`로 풀어 쓴다.

### 4.2.7 디버거로 따라가기

데코레이터가 붙은 함수는 디버거로 따라가면 구조가 잘 보인다. `logged.py`의 `print(slow_add(1, 2))` 줄에 중단점을 찍고 `F5`로 디버깅을 시작한다. 멈추면 `F11`(단계 정보, Step Into)을 누른다.

- **원래 `slow_add`가 아니라 `timed`의 `wrapper` 안으로 들어간다.** `slow_add`라는 이름이 가리키는 것이 래퍼이기 때문이다.
- 변수 패널에서 `func`를 찾는다. 래퍼가 클로저로 붙들고 있는 바깥 변수다. 값은 `<function slow_add ...>`로 보이지만, 실제로는 `logged`의 래퍼다. `wraps`가 이름을 복사했기 때문이다. 펼쳐서 `__wrapped__`를 찾으면 그 안에 원래 `slow_add`가 있다.
- `F10`으로 `return func(*args, **kwargs)`까지 간 뒤 다시 `F11`을 누르면 `logged`의 래퍼로, 한 번 더 들어가면 원래 `slow_add`로 들어간다.
- 원래 `slow_add` 안에서 **호출 스택**(Call Stack) 패널을 본다. 아래에서 위로 `<module>` → `wrapper` → `wrapper` → `slow_add`가 쌓여 있다. 래퍼 두 겹을 지나 원래 함수에 왔다는 뜻이다.

`F11`로 들어간 곳이 래퍼라서 당황스러울 수 있다. 라이브러리의 데코레이터가 붙은 함수를 따라갈 때도 마찬가지다. 그럴 때는 래퍼 안에서 `func(...)`를 부르는 줄을 찾아 다시 `F11`로 들어간다.

트레이스백에도 래퍼가 보인다. `slow_add(1, "2")`로 부르면 `TypeError`의 트레이스백에 `wrapper` 줄이 두 번 끼어 있다. 트레이스백을 읽을 때 데코레이터의 래퍼 줄은 "지나가는 길"로 보고, 내 함수의 줄을 찾는다.

### 실습 4-2. 데코레이터 만들기

`ch04/deco_practice.py`에 다음을 만든다. 각 데코레이터에는 `@functools.wraps(func)`를 붙인다.

**1. 호출 횟수 세기**

함수가 몇 번 불렸는지 세는 `count_calls` 데코레이터를 만든다. 횟수는 **래퍼 함수의 속성**에 둔다.

```python
@count_calls
def ask(prompt):
    return f"'{prompt}'의 답"


ask("안녕")
ask("날씨")
print(ask.calls)   # 2
```

(힌트: 함수도 객체이므로 `wrapper.calls = 0`처럼 속성을 붙일 수 있다. 래퍼를 돌려주기 전에 0으로 만들어 두고, 래퍼 안에서 `wrapper.calls += 1`한다.) 래퍼 안에서 `wrapper.calls += 1`을 할 때는 `nonlocal`이 필요 없다. 왜 그런가? 4.1.4의 표로 설명한다.

**2. 버그 찾기**

다음 데코레이터에는 문제가 두 가지 있다. 실행하기 전에 세 `print()`의 출력을 예측하고, 실행해서 확인한 뒤 고친다.

```python
def shout(func):
    def wrapper(text):
        result = func(text)
        result.upper()

    return wrapper


@shout
def greet(text):
    """인사말을 만든다."""
    return f"안녕, {text}"


print(greet("지민"))
print(greet.__name__, greet.__doc__)
print(greet(text="지민", end="!"))
```

마지막 줄은 고친 뒤에도 오류가 난다. 래퍼의 문제가 아니라 `greet()`가 `end`를 받지 않기 때문이다. 래퍼가 `*args, **kwargs`를 받게 고친 경우와 고치지 않은 경우, 오류 메시지가 어떻게 다른지 비교한다. 어느 쪽 메시지가 원인을 더 잘 알려 주는가?

**3. 예외 기록하기**

감싼 함수에서 예외가 나면 `[오류] 함수이름(args, kwargs) → 예외이름: 메시지`를 출력하고, 예외를 **그대로 다시 일으키는** `log_errors` 데코레이터를 만든다. (힌트: `except Exception as e:` 블록 안에서 `raise`만 쓰면 잡은 예외를 그대로 다시 일으킨다. 기초 과정 6.2.5.)

```python
@log_errors
def parse_score(text):
    return int(text)


parse_score("10")
parse_score("열")    # [오류] parse_score(('열',), {}) → ValueError: invalid literal ...
```

`raise` 대신 `return None`으로 예외를 삼키면 무엇이 문제인가? 1.3.5의 마지막 질문과 기초 과정 6.2.6을 떠올리며 `notes.md`에 적는다.

**4. 겹쳐 붙인 순서 예측하기**

다음 코드를 실행하기 **전에** 출력될 모든 줄을 순서대로 예측한다. 정의할 때 출력되는 줄과 부를 때 출력되는 줄을 구별한다.

```python
def deco_a(func):
    print("a: 꾸미는 중", func.__name__)

    @functools.wraps(func)
    def wrapper(*args, **kwargs):
        print("a: 들어감")
        result = func(*args, **kwargs)
        print("a: 나옴")
        return result

    return wrapper


def deco_b(func):
    print("b: 꾸미는 중", func.__name__)

    @functools.wraps(func)
    def wrapper(*args, **kwargs):
        print("b: 들어감")
        result = func(*args, **kwargs)
        print("b: 나옴")
        return result

    return wrapper


@deco_a
@deco_b
def work():
    print("일하는 중")


print("--- 호출")
work()
```

`deco_a`가 꾸밀 때 출력하는 `func.__name__`은 무엇인가? `deco_b`의 래퍼에서 `@functools.wraps(func)`를 지우면 어떻게 달라지는가?

## 4.3 인자를 받는 데코레이터

### 4.3.1 괄호가 붙는 데코레이터 — 세 겹 구조

LLM API는 생각보다 자주 실패한다. 응답이 제한 시간 안에 오지 않기도 하고(시간 초과), 짧은 시간에 요청을 너무 많이 보내 "요청 한도 초과"(HTTP 상태 코드 429)를 받기도 하고, 서버가 바빠서 잠시 거절하기도 한다. 이런 실패는 **잠시 뒤 다시 보내면 대개 성공한다.** 그래서 API를 부르는 함수에는 "실패하면 조금 기다렸다가 다시 시도한다"는 기능이 거의 늘 붙는다. 3.5.5에서 `count(1)`과 `break`로 이 반복을 만들어 보았다. 이것을 API를 부르는 함수마다 붙일 수 있는 데코레이터로 만든다.

그런데 "몇 번까지 다시 시도할까", "얼마나 기다릴까"는 함수마다 다르다. 데코레이터에 설정값을 넘기고 싶다. 그래서 다음과 같이 쓰고 싶다.

```python
@retry(times=3)
def ask(prompt):
    ...
```

4.2.2의 규칙대로 풀면 이렇다.

```python
ask = retry(times=3)(ask)
```

괄호가 두 번 나온다. `retry(times=3)`을 먼저 부르고, 그 **결과**에 `ask`를 넣어 다시 부른다. 그러니 `retry(times=3)`이 돌려주는 것은 "함수를 받아 래퍼를 돌려주는 함수", 즉 **데코레이터**여야 한다. `retry` 자체는 데코레이터가 아니라 **데코레이터를 만드는 함수**다. 그래서 함수가 세 겹이 된다.

```python
def retry(times=3):                  # ① 설정을 받아 데코레이터를 돌려준다
    def decorator(func):             # ② 함수를 받아 래퍼를 돌려준다 — 4.2의 데코레이터
        @functools.wraps(func)
        def wrapper(*args, **kwargs):  # ③ 호출할 때마다 실행된다
            ...  # times와 func를 모두 쓸 수 있다
        return wrapper
    return decorator
```

| 층 | 받는 것 | 돌려주는 것 | 실행되는 때 |
|---|---|---|---|
| ① `retry` | 설정(`times=3`) | `decorator` | 정의할 때, `@retry(times=3)` 줄에서 |
| ② `decorator` | 꾸밀 함수(`func`) | `wrapper` | 정의할 때, `def ask` 문이 끝나자마자 |
| ③ `wrapper` | 원래 함수에 갈 인자(`*args, **kwargs`) | 원래 함수의 결과 | 부를 때마다 |

안쪽 함수는 바깥 함수들의 변수를 모두 볼 수 있으므로(4.1.3) `wrapper`는 ①의 `times`와 ②의 `func`를 함께 쓴다. **세 겹 구조는 바깥에서부터 "설정 → 함수 → 호출"의 순서로 읽는다.** 4.2.4의 `@functools.wraps(func)`도 이 모양이었다. `wraps(func)`가 데코레이터를 돌려주고, 그 데코레이터가 `wrapper`를 꾸민다.

### 4.3.2 재시도 데코레이터 만들기

먼저 실험할 **가짜 API 함수**가 필요하다. 처음 몇 번은 실패하고 그다음부터 성공하는 함수를 만든다. 4.1.4의 `nonlocal` 카운터를 그대로 쓴다.

`ch04/retry.py`

```python
"""재시도 데코레이터."""

import functools
import time


def make_flaky(failures, error=TimeoutError):
    """처음 failures번은 error를 일으키고, 그다음부터는 답하는 가짜 API 함수를 만든다."""
    calls = 0

    def call_api(prompt):
        nonlocal calls
        calls += 1
        if calls <= failures:
            raise error(f"{calls}번째 호출 실패")
        return f"'{prompt}'의 답 ({calls}번째 호출에서 성공)"

    return call_api


def retry(times=3, delay=0.1, backoff=2.0, exceptions=(TimeoutError, ConnectionError)):
    """exceptions에 든 예외가 나면 times번까지 시도하는 데코레이터를 만든다.

    기다리는 시간은 delay초에서 시작해 실패할 때마다 backoff배가 된다.
    """

    def decorator(func):
        @functools.wraps(func)
        def wrapper(*args, **kwargs):
            wait = delay
            for attempt in range(1, times + 1):
                try:
                    return func(*args, **kwargs)
                except exceptions as e:
                    if attempt == times:
                        raise
                    print(f"[재시도] {func.__name__}: {attempt}번째 실패({e}), {wait:.2f}초 뒤 다시")
                    time.sleep(wait)
                    wait *= backoff

        return wrapper

    return decorator


if __name__ == "__main__":
    ask = retry(times=4)(make_flaky(2))
    print(ask("안녕"))

    ask = retry(times=3)(make_flaky(5))
    try:
        print(ask("안녕"))
    except TimeoutError as e:
        print("포기:", repr(e))

    ask = retry()(make_flaky(1, error=KeyError))
    try:
        print(ask("안녕"))
    except KeyError as e:
        print("바로 올라옴:", repr(e))
```

`if __name__ == "__main__":` 아래에서는 `@` 대신 `retry(times=4)(make_flaky(2))`처럼 풀어 쓴 모양을 썼다. 가짜 API 함수를 `make_flaky()`로 **만들어서** 받았기 때문에 그 위에 `@`를 붙일 `def` 문이 없다. `@`는 `def` 바로 위에만 쓸 수 있는 줄임일 뿐, 하는 일은 같다.

```
python ch04/retry.py
```

```
[재시도] call_api: 1번째 실패(1번째 호출 실패), 0.10초 뒤 다시
[재시도] call_api: 2번째 실패(2번째 호출 실패), 0.20초 뒤 다시
'안녕'의 답 (3번째 호출에서 성공)
[재시도] call_api: 1번째 실패(1번째 호출 실패), 0.10초 뒤 다시
[재시도] call_api: 2번째 실패(2번째 호출 실패), 0.20초 뒤 다시
포기: TimeoutError('3번째 호출 실패')
바로 올라옴: KeyError('1번째 호출 실패')
```

세 경우를 하나씩 본다.

- **두 번 실패하고 성공** — 세 번째 시도에서 `return func(...)`이 값을 돌려주면서 반복과 래퍼가 함께 끝난다. 호출한 쪽은 실패가 있었다는 것을 모르고 답만 받는다.
- **끝까지 실패** — 세 번째(마지막) 시도에서도 실패하면 `if attempt == times: raise`가 잡은 예외를 **그대로 다시 일으킨다**(기초 과정 6.2.5). 호출한 쪽은 마지막 실패의 예외를 받는다. 재시도 데코레이터는 실패를 **숨기지 않는다.** 정해진 만큼 해 보고 안 되면 원래대로 알린다.
- **다시 시도할 예외가 아니면 바로 올라감** — `except exceptions as e:`는 `exceptions` 튜플에 든 예외만 잡는다(기초 과정 6.1.6의 `except (A, B):`와 같다). `KeyError`는 튜플에 없으므로 잡히지 않고 첫 시도에서 바로 올라간다.

나머지 부분도 확인한다.

- `for attempt in range(1, times + 1):` — 3.5.5에서는 `for attempt in count(1):`로 끝을 정하지 않고 반복했다. 여기서는 횟수가 정해져 있으므로 `range()`가 더 분명하다. 마지막 시도는 성공하면 `return`, 실패하면 `raise`로 끝나므로 반복문이 끝까지 돌아 빠져나오는 일은 없다.
- `wait *= backoff` — 실패할 때마다 기다리는 시간을 두 배로 늘린다. 다음 절에서 이유를 본다.
- `print(...)` — 실제 프로그램에서는 `print()` 대신 로그를 남긴다. 로그 남기기는 "LLM 서비스 배포"에서 다룬다.

### 4.3.3 지수 백오프와 지터

재시도 사이에 **얼마나 기다릴지**는 생각보다 중요하다.

- **기다리지 않고 바로 다시 보내면** — 서버가 바빠서 거절했는데 곧바로 다시 보내면 또 거절당한다. 요청 한도 초과(429)라면 한도를 더 빨리 소진할 뿐이다.
- **같은 시간만큼 기다리면** — 1초 뒤에도 서버가 바쁘다면 2초 뒤, 3초 뒤에도 바쁠 가능성이 크다.

그래서 실패할 때마다 기다리는 시간을 일정한 배수로 늘린다. 이것을 **지수 백오프**(exponential backoff)라고 한다. `delay=1, backoff=2`라면 1초, 2초, 4초, 8초, …로 늘어난다. 처음 몇 번은 빨리 다시 시도하고, 계속 실패하면 서버에 회복할 시간을 넉넉히 준다.

| 시도 | 실패 뒤 기다리는 시간 (`delay=1`, `backoff=2`) | 기다린 시간 합계 |
|---|---|---|
| 1 | 1초 | 1초 |
| 2 | 2초 | 3초 |
| 3 | 4초 | 7초 |
| 4 | 8초 | 15초 |
| 5 | 16초 | 31초 |
| 10 | 512초 | 1,023초 |

10번째 실패 뒤에는 8분 넘게 기다린다. 지수는 금방 커지므로 보통 **최대 대기 시간**(`max_delay`)을 둔다. `wait = min(wait * backoff, max_delay)`처럼 쓴다.

하나가 더 있다. 서버가 잠깐 멈췄다가 살아나는 상황을 생각해 보자. 그동안 실패한 클라이언트 1,000개가 모두 같은 규칙(1초, 2초, 4초)으로 기다린다면, 1초 뒤에 1,000개가 **동시에** 다시 몰려와 서버가 또 멈춘다. 그래서 기다리는 시간에 약간의 무작위성을 섞어 다시 보내는 때를 흩뜨린다. 이것을 **지터**(jitter)라고 한다.

```python
time.sleep(random.uniform(wait / 2, wait))  # wait의 50~100% 사이에서 무작위로
```

`random.uniform(a, b)`는 `a`와 `b` 사이의 실수를 무작위로 고른다(3.6.2). 실습 4-3에서 `retry()`에 최대 대기 시간과 지터를 더한다.

### 4.3.4 어떤 예외에서 다시 시도할까

재시도 데코레이터를 설계할 때 가장 중요한 것은 **어떤 실패를 다시 시도할 것인가**다. 1.3.5에서 예고한 대로, 이것은 기초 과정 6.2.6의 "예외를 잡을 때와 그대로 둘 때"와 같은 질문이다. 기준은 하나다. **똑같은 요청을 잠시 뒤 다시 보내면 결과가 달라질 수 있는가?**

| 실패 | HTTP 상태 코드 | 다시 시도? | 이유 |
|---|---|---|---|
| 시간 초과, 연결 끊김 | (없음) | 예 | 네트워크가 잠깐 불안정했을 수 있다 |
| 요청 한도 초과 | 429 | 예, 서버가 알려 준 시간만큼 기다린 뒤 | 한도는 시간이 지나면 회복된다 |
| 서버 내부 오류, 과부하 | 500, 502, 503, 529 등 | 예 | 서버 쪽 문제는 잠시 뒤 풀리는 경우가 많다 |
| 잘못된 요청 (프롬프트가 너무 길다, 매개변수가 틀렸다) | 400 | 아니오 | 몇 번을 보내도 같은 요청은 같은 이유로 거절된다 |
| 인증 실패 (API 키가 틀렸다), 권한 없음 | 401, 403 | 아니오 | 키를 고치기 전에는 계속 실패한다 |
| 내 코드의 버그 (`KeyError`, `TypeError` 등) | (없음) | 아니오 | 다시 시도하면 버그를 숨기고 시간만 쓴다 |

다시 시도해도 소용없는 실패를 다시 시도하면, 결과는 같은데 사용자는 7초, 15초를 더 기다린 뒤 오류를 본다. 그래서 `except Exception:`처럼 모든 예외를 다시 시도하면 안 된다. 이것이 `retry()`가 `exceptions` 매개변수로 **다시 시도할 예외를 명시적으로** 받는 이유다.

LLM SDK는 이 구분을 **예외 클래스**로 해 둔다. 예를 들어 Anthropic과 OpenAI의 파이썬 SDK에는 `APITimeoutError`, `RateLimitError`, `InternalServerError`, `BadRequestError`, `AuthenticationError` 같은 예외 클래스가 있고, 모두 공통 부모 클래스(`APIError` 계열)를 물려받는다(기초 과정 6.1.5의 예외 계층). 그래서 재시도 데코레이터에는 다시 시도할 클래스만 골라 넘긴다.

```python
@retry(times=5, exceptions=(anthropic.APITimeoutError, anthropic.RateLimitError, anthropic.InternalServerError))
def ask(prompt):
    ...
```

클래스 이름은 SDK 버전에 따라 조금 다를 수 있다. 실제 이름은 "LLM API 활용"에서 SDK 문서로 확인한다. 실습 4-7에서는 같은 구조의 가짜 예외 클래스를 만들어 쓴다.

요청 한도 초과(429)에는 하나가 더 있다. 서버는 응답의 `Retry-After` 머리글에 "몇 초 뒤에 다시 보내라"를 적어 보내기도 한다. 이 값이 있으면 백오프 계산보다 **서버가 알려 준 시간**을 따르는 것이 맞다. 실습 4-3과 4-7에서 이것을 더한다.

> **다시 보내도 괜찮은 요청인가**
> 재시도는 같은 요청을 **여러 번** 보낸다. LLM에게 요약을 부탁하는 요청은 두 번 보내도 (토큰 비용 말고는) 문제가 없다. 하지만 "결제하기", "메일 보내기" 같은 요청은 다르다. 시간 초과는 "응답을 못 받았다"는 뜻이지 "서버가 처리하지 않았다"는 뜻이 아니다. 서버는 이미 결제를 처리했는데 응답만 늦었을 수 있다. 이것을 다시 보내면 결제가 두 번 된다. 여러 번 실행해도 결과가 한 번 실행한 것과 같은 성질을 **멱등성**(idempotency)이라고 한다. 멱등하지 않은 요청에 재시도를 붙일 때는 "웹·API 기초"에서 다룰 멱등 키 같은 장치가 필요하다.

### 4.3.5 괄호를 빠뜨리면

`retry`는 `@retry(times=3)`처럼 괄호와 함께 써야 한다. 설정값을 모두 기본값으로 쓰고 싶어도 `@retry()`처럼 빈 괄호를 붙여야 한다. 괄호를 빠뜨리면 어떻게 될까?

```python
>>> from retry import retry
>>> @retry
... def ask(prompt):
...     return "답"
...
>>> ask("안녕")
<function retry.<locals>.decorator.<locals>.wrapper at 0x100a26610>
```

**오류가 나지 않는다.** 답 대신 함수 객체가 나왔을 뿐이다. 세 겹 구조로 따라가 본다.

1. `@retry`는 `ask = retry(ask)`다. `retry()`의 첫 매개변수 `times`에 **함수 `ask`가** 들어간다. `retry()`는 `decorator`를 돌려주고, 그것에 `ask`라는 이름이 붙는다.
2. `ask("안녕")`은 `decorator("안녕")`이다. `decorator()`는 `"안녕"`을 꾸밀 함수로 알고 래퍼를 만들어 돌려준다.

괄호 하나를 빠뜨렸을 뿐인데, 함수를 부를 때마다 아무 일도 하지 않고 래퍼 함수를 돌려준다. 이 결과를 다른 함수에 넘기거나 저장하면 한참 뒤의 엉뚱한 곳에서 문제가 드러난다.

그래서 라이브러리는 **괄호가 있어도 없어도** 동작하게 만들기도 한다. `@dataclass`와 `@dataclass(frozen=True)`(기초 과정 5.4.6), pytest의 `@pytest.fixture`와 `@pytest.fixture(scope="module")`(6장)이 그렇다. `dataclass`의 정의를 `F12`로 열어 보면 매개변수가 이렇게 시작한다.

```python
def dataclass(cls=None, /, *, init=True, repr=True, eq=True, order=False, ...):
```

첫 매개변수 `cls`는 기본값이 `None`이고, 나머지 설정은 `*` 뒤에 있어서 **키워드로만** 받는다(기초 과정 4.2.9). 그래서 두 경우를 구별할 수 있다.

- `@dataclass` — 괄호 없이 쓰면 `dataclass(Product)`다. `cls`에 클래스가 들어온다. 바로 꾸며서 돌려준다.
- `@dataclass(frozen=True)` — `dataclass(frozen=True)`다. `cls`는 `None`이다. 데코레이터를 돌려준다.

같은 모양을 `retry`에 적용하면 다음과 같다.

```python
def retry(func=None, *, times=3, delay=0.1, backoff=2.0, exceptions=(TimeoutError, ConnectionError)):
    def decorator(func):
        ...  # 4.3.2와 같다

    if func is None:         # @retry(...) — 설정만 받았다. 데코레이터를 돌려준다
        return decorator
    return decorator(func)   # @retry — 함수를 바로 받았다. 꾸며서 돌려준다
```

설정을 키워드로만 받게 한 것이 중요하다. `@retry(3)`처럼 위치 인자로 쓰면 `func`에 3이 들어가 혼란스러워지므로, 아예 `TypeError`가 나게 막는다. 직접 데코레이터를 만들 때 꼭 이렇게 할 필요는 없다. 다만 라이브러리 코드에서 `def 이름(func=None, *, ...)`이나 `def 이름(cls=None, /, *, ...)`을 보면 "괄호가 있어도 없어도 되는 데코레이터구나" 하고 읽을 수 있으면 된다. 실습 4-3에서 직접 만들어 본다.

### 4.3.6 재시도와 다른 데코레이터의 순서

4.2.6에서 데코레이터를 겹쳐 붙이는 순서에 따라 결과가 달라진다고 했다. 재시도와 시간 재기를 겹쳐 본다. `ch04/order.py`를 만든다.

```python
"""재시도와 시간 재기 — 겹쳐 붙이는 순서."""

from logged import timed
from retry import make_flaky, retry

flaky1 = make_flaky(2)
flaky2 = make_flaky(2)


@timed
@retry(times=3)
def ask1(prompt):
    return flaky1(prompt)


@retry(times=3)
@timed
def ask2(prompt):
    return flaky2(prompt)


print(ask1("안녕"))
print("---")
print(ask2("안녕"))
```

```
python ch04/order.py
```

```
[재시도] ask1: 1번째 실패(1번째 호출 실패), 0.10초 뒤 다시
[재시도] ask1: 2번째 실패(2번째 호출 실패), 0.20초 뒤 다시
[시간] ask1: 0.309초
'안녕'의 답 (3번째 호출에서 성공)
---
[시간] ask2: 0.000초
[재시도] ask2: 1번째 실패(1번째 호출 실패), 0.10초 뒤 다시
[시간] ask2: 0.000초
[재시도] ask2: 2번째 실패(2번째 호출 실패), 0.20초 뒤 다시
[시간] ask2: 0.000초
'안녕'의 답 (3번째 호출에서 성공)
```

- `ask1` — `timed`가 바깥이다. 재시도와 기다린 시간을 **모두 포함한** 시간을 한 번 잰다. 사용자가 실제로 기다린 시간이다.
- `ask2` — `retry`가 바깥이다. `retry`가 시도할 때마다 안쪽의 `timed` 래퍼를 부르므로 **시도마다** 시간이 찍힌다. 기다린 시간은 들어가지 않는다. API 한 번의 응답 시간이다.

둘 다 쓸모 있는 숫자다. 어느 쪽이 맞는 것이 아니라 **무엇을 알고 싶은가**에 따라 순서를 고른다. 서비스의 응답 속도를 관리하려면 `ask1`의 숫자를, API 제공자의 속도를 비교하려면 `ask2`의 숫자를 본다. 실습 4-7에서는 재시도와 캐시를 겹쳐 붙인다. 그때도 순서가 중요하다.

### 4.3.7 실제 라이브러리의 재시도

직접 만든 재시도 데코레이터는 구조를 이해하는 데 아주 좋다. 실제 프로젝트에서는 이미 만들어진 것을 쓰는 경우가 많다. 두 가지를 알아 둔다.

**LLM SDK에 들어 있는 재시도.** Anthropic과 OpenAI의 파이썬 SDK는 연결 오류, 시간 초과, 429, 5xx 같은 실패를 **스스로 몇 번 다시 시도한다.** 클라이언트를 만들 때 횟수를 정할 수 있다.

```python
client = anthropic.Anthropic(max_retries=5)  # 기본값은 2 (SDK 버전에 따라 다를 수 있다)
```

그러니 SDK를 쓰면서 그 위에 재시도 데코레이터를 또 붙일 때는 조심한다. SDK가 3번 시도하는 호출을 데코레이터가 3번 부르면 최대 **9번** 요청이 나가고, 기다리는 시간도 곱절로 늘어난다. 재시도는 한 층에서만 하는 것이 원칙이다.

**재시도 라이브러리.** 파이썬에서 많이 쓰는 재시도 라이브러리로 `tenacity`가 있다. 이 장에서 만든 것과 같은 생각을 더 많은 선택지와 함께 제공한다. 남의 코드에서 만나면 읽을 수 있도록 모양만 본다.

```python
from tenacity import retry, retry_if_exception_type, stop_after_attempt, wait_exponential


@retry(
    stop=stop_after_attempt(3),                        # 3번 시도하고 멈춘다
    wait=wait_exponential(multiplier=1, max=30),       # 지수 백오프, 최대 30초
    retry=retry_if_exception_type(TimeoutError),       # 이 예외일 때만 다시 시도
)
def ask(prompt):
    ...
```

`@retry(...)`가 설정을 받는 세 겹 구조라는 것, `stop`/`wait`/`retry`가 각각 이 장의 `times`/`delay`·`backoff`/`exceptions`에 해당한다는 것을 읽을 수 있다.

### 실습 4-3. 인자를 받는 데코레이터

**1. 느린 호출 경고**

함수가 `seconds`초보다 오래 걸리면 `[느림] 함수이름: 1.23초 (기준 1.00초)`를 출력하는 `warn_if_slow(seconds)` 데코레이터를 `ch04/deco_practice.py`에 더한다. 빨리 끝나면 아무것도 출력하지 않는다.

```python
@warn_if_slow(0.5)
def summarize(text):
    time.sleep(len(text) * 0.1)
    return text[:5]


summarize("짧은 글")         # 출력 없음
summarize("조금 더 긴 글입니다")  # [느림] summarize: 1.10초 (기준 0.50초)
```

다 만들었으면 세 겹 함수의 각 층에 `print("① 설정")`, `print("② 꾸미기")`, `print("③ 호출")`을 넣고, 파일을 실행했을 때 무엇이 몇 번 출력되는지 4.3.1의 표와 비교한다. 확인했으면 `print()`를 지운다.

**2. 최대 대기 시간과 지터**

`retry.py`의 `retry()`에 `max_delay=2.0`과 `jitter=True` 매개변수를 더한다.

- 기다리는 시간은 `max_delay`를 넘지 않는다.
- `jitter`가 참이면 실제로 기다리는 시간은 `random.uniform(wait / 2, wait)`이다. 출력도 실제로 기다린 시간으로 한다.

`retry(times=6, delay=0.5, max_delay=2.0, jitter=False)(make_flaky(5))`를 실행해 기다린 시간이 0.5, 1.0, 2.0, 2.0, 2.0인지 확인한다. `jitter=True`로 바꿔 몇 번 실행하고, 출력되는 시간이 실행할 때마다 다른지 본다.

**3. 서버가 알려 준 시간 따르기**

`retry.py`에 다음 예외 클래스를 더한다.

```python
class RateLimitError(Exception):
    """요청 한도 초과(429). retry_after초 뒤에 다시 보내라는 뜻이다."""

    def __init__(self, message, retry_after=None):
        super().__init__(message)
        self.retry_after = retry_after
```

`make_flaky()`를 고쳐, `error`가 `RateLimitError`일 때는 `error(메시지, retry_after=0.3)`으로 예외를 만들게 한다. 그리고 `retry()`의 래퍼를 고쳐, 잡은 예외에 `retry_after` 속성이 있고 `None`이 아니면 백오프 계산 대신 그 시간을 기다리게 한다. (힌트: `getattr(e, "retry_after", None)`은 속성이 없으면 `None`을 돌려준다. 기초 과정 실습 6-2에서 쓴 `getattr()`이다.) `retry(exceptions=(RateLimitError,))(make_flaky(2, error=RateLimitError))`로 확인한다.

**4. 괄호가 있어도 없어도**

4.3.5처럼 `retry()`를 `retry(func=None, *, times=3, ...)` 모양으로 바꿔, 다음 세 가지가 모두 동작하게 한다. `@retry(3)`은 `TypeError`가 나야 한다. 오류 메시지를 읽고, 이 오류가 4.3.5의 "조용한 실패"보다 나은 이유를 `notes.md`에 적는다.

```python
@retry
def a(): ...

@retry()
def b(): ...

@retry(times=5)
def c(): ...
```

**5. 다시 시도할까**

다음 상황마다 재시도 데코레이터의 `exceptions`에 넣을지 판단하고, 이유를 한 문장으로 `notes.md`에 적는다. 4.3.4의 표와 멱등성 상자를 참고한다.

- (가) 프롬프트에 넣은 문서가 너무 길어 400 오류가 났다.
- (나) 사내 프록시 서버를 거치다 연결이 끊겼다.
- (다) LLM의 답을 `json.loads()`로 읽었는데 `json.JSONDecodeError`가 났다. (힌트: 같은 요청을 다시 보내면 LLM의 답이 달라질 수 있는가? 다시 시도할 곳은 API 호출 함수인가, 답을 읽는 함수까지 포함한 바깥 함수인가?)
- (라) API 키를 환경 변수에서 읽지 못해 401 오류가 났다.
- (마) 결제 API를 불렀는데 시간 초과가 났다.

## 4.4 표준 라이브러리의 데코레이터

### 4.4.1 `functools.cache` — 같은 입력의 결과 다시 쓰기

4.2.3의 표에서 "원래 함수를 **부르지 않고** 결과를 돌려주는" 래퍼를 보았다. 한 번 계산한 결과를 기억해 두었다가, 같은 인자로 다시 부르면 계산하지 않고 기억해 둔 것을 돌려주는 것이다. 이것을 **캐시**(cache)라고 한다. 클로저와 딕셔너리로 직접 만들 수 있다.

```python
def my_cache(func):
    memo = {}  # {인자 튜플: 결과}

    @functools.wraps(func)
    def wrapper(*args):
        if args not in memo:
            memo[args] = func(*args)
        return memo[args]

    return wrapper
```

`memo`는 래퍼가 클로저로 붙들고 있는 딕셔너리다(4.1.4의 표: 내용만 바꾸므로 `nonlocal`이 필요 없다). 인자 튜플 `args`를 키로 쓴다. 처음 보는 인자면 원래 함수를 불러 결과를 저장하고, 본 적 있는 인자면 저장해 둔 결과를 바로 돌려준다.

표준 라이브러리에 이미 있다. `functools.cache`다. 효과를 보기 위해 자기 자신을 두 번씩 부르는 피보나치 함수에 호출 횟수를 세는 줄을 넣는다.

`ch04/cache_demo.py`

```python
"""functools.cache — 같은 입력의 결과를 다시 쓴다."""

import functools

calls = 0


def fib(n):
    """n번째 피보나치 수."""
    global calls
    calls += 1
    if n < 2:
        return n
    return fib(n - 1) + fib(n - 2)


@functools.cache
def fib_cached(n):
    """n번째 피보나치 수. 한 번 구한 값은 기억해 둔다."""
    global calls
    calls += 1
    if n < 2:
        return n
    return fib_cached(n - 1) + fib_cached(n - 2)


if __name__ == "__main__":
    print(fib(25), calls)
    calls = 0
    print(fib_cached(25), calls)
    print(fib_cached(30), calls)
```

`global calls`는 기초 과정 4.3.4에서 피하라고 한 것이다. 여기서는 호출 횟수를 잠깐 확인하려고 썼다.

```
python ch04/cache_demo.py
```

```
75025 242785
75025 26
832040 31
```

캐시가 없는 `fib(25)`는 자기 자신을 24만 번 넘게 불렀다. `fib(23)`, `fib(22)`, …를 셀 수 없이 다시 계산하기 때문이다. `fib_cached(25)`는 `fib_cached(0)`부터 `fib_cached(25)`까지 **한 번씩**, 26번만 불렀다. 이어서 부른 `fib_cached(30)`은 25까지는 기억해 둔 것을 쓰고, 26~30의 5번만 더 계산했다.

**인자는 해시할 수 있어야 한다.** 캐시는 인자를 딕셔너리의 키로 쓰므로, 리스트나 딕셔너리처럼 바꿀 수 있는 객체를 인자로 넘기면 `TypeError: unhashable type: 'list'`다(기초 과정 3.6.4의 해시 가능한 키). 다음 절에서 이 문제를 LLM 메시지 목록으로 다시 만난다.

### 4.4.2 `lru_cache` — 크기를 정한 캐시와 응답 캐시

LLM API 호출은 느리고 돈이 든다. 개발하면서 같은 프롬프트로 프로그램을 몇 번씩 다시 실행한다면, 같은 질문의 답을 기억해 두는 것만으로 시간과 비용을 크게 아낄 수 있다. 1초가 걸리는 가짜 API로 이 아이디어를 확인한다. 이번에는 `functools.lru_cache`를 쓴다. 대화형 셸에서 해 본다.

```python
>>> import functools, time
>>> @functools.lru_cache(maxsize=128)
... def ask(prompt, model="small"):
...     time.sleep(1)  # 느린 API 호출
...     return f"[{model}] '{prompt}'의 답"
...
>>> for p in ["파이썬이란?", "파이썬이란?", "제너레이터란?"]:
...     start = time.perf_counter()
...     answer = ask(p)
...     print(f"{time.perf_counter() - start:.2f}초", answer)
...
1.00초 [small] '파이썬이란?'의 답
0.00초 [small] '파이썬이란?'의 답
1.01초 [small] '제너레이터란?'의 답
>>> ask.cache_info()
CacheInfo(hits=1, misses=2, maxsize=128, currsize=2)
```

같은 질문을 두 번째로 했을 때는 기다리지 않았다. `cache_info()`는 캐시의 상태를 알려 준다. `hits`는 기억해 둔 결과를 돌려준 횟수, `misses`는 원래 함수를 부른 횟수, `currsize`는 지금 기억하고 있는 결과의 수다. 캐시가 효과가 있는지 확인할 때 쓴다.

`lru_cache`는 `cache`와 같은 일을 하되 **기억할 개수에 한도**(`maxsize`)를 둔다. 한도가 차면 **가장 오래 쓰지 않은**(Least Recently Used, LRU) 결과부터 버린다. 크기가 2인 캐시로 확인한다.

```python
>>> @functools.lru_cache(maxsize=2)
... def square(n):
...     print("계산", n)
...     return n * n
...
>>> square(1); square(2); square(1); square(3); square(2)
계산 1
1
계산 2
4
1
계산 3
9
계산 2
4
>>> square.cache_info()
CacheInfo(hits=1, misses=4, maxsize=2, currsize=2)
```

대화형 셸은 세미콜론으로 이은 식의 값도 하나씩 보여 주므로, `계산` 줄과 돌려준 값이 번갈아 나온다. `계산` 줄 없이 나온 세 번째 `1`이 캐시에서 꺼낸 값이다. 세 번째 `square(1)`은 원래 함수를 부르지 않고 기억해 둔 것을 썼다(`hits=1`). 그 순간 1은 "가장 최근에 쓴 것"이 된다. `square(3)`을 계산해 넣을 때 자리가 없으므로 가장 오래 쓰지 않은 2를 버렸다. 그래서 마지막 `square(2)`는 다시 계산했다. `functools.cache`는 사실 `lru_cache(maxsize=None)`, 즉 한도가 없는 캐시다.

`@functools.lru_cache(maxsize=128)`은 괄호가 붙은 데코레이터, 4.3의 세 겹 구조다. `lru_cache`도 4.3.5처럼 괄호 없이 `@functools.lru_cache`로 쓸 수 있다(이때 `maxsize`는 기본값 128).

캐시 래퍼에는 `cache_info()`와 `cache_clear()`(캐시 비우기) 같은 메서드가 붙어 있다. 4.2의 래퍼처럼 평범한 함수가 아니기 때문이다.

```python
>>> type(ask)
<class 'functools._lru_cache_wrapper'>
>>> callable(ask)
True
```

`lru_cache`가 돌려준 것은 **함수처럼 부를 수 있는 객체**다. 실습 4-1의 4번에서 만든 `__call__` 메서드를 가진 클래스의 객체와 같은 종류다. 상태(기억해 둔 결과)와 메서드(`cache_info()`)가 필요하므로 클로저 대신 클래스로 만든 것이다(4.1.6). 4.2.3의 표 마지막 줄처럼, 데코레이터는 함수가 아닌 객체를 돌려줄 수도 있다.

### 4.4.3 캐시를 쓸 때 조심할 것

캐시는 효과가 큰 만큼 잘못 쓰면 찾기 어려운 버그를 만든다. 특히 LLM 응답을 캐시할 때 다음을 확인한다.

**같은 입력이면 같은 답이어야 하는가?** 캐시는 "같은 인자면 결과가 같다"고 가정한다. LLM은 `temperature`가 0보다 크면 같은 질문에도 매번 다른 답을 낸다. 캐시하면 **처음 받은 답 하나로 고정된다.** 개발 중에 비용을 아끼거나, 평가할 때 같은 답으로 비교하려는 것이라면 바라던 바다. 사용자에게 매번 새로운 아이디어를 내놓는 기능이라면 캐시하면 안 된다.

**답에 영향을 주는 것은 모두 인자에 있는가?** 캐시의 키는 **인자**뿐이다. 함수가 전역 설정(`SETTINGS["model"]`)이나 환경 변수를 읽어 모델을 정한다면, 모델을 바꿔도 캐시는 예전 모델의 답을 돌려준다. 모델, 시스템 프롬프트, `temperature`처럼 답을 바꾸는 것은 **모두 인자로** 받게 한다. 같은 이유로, 같은 인자라도 넘기는 **모양이 다르면** 다른 키가 된다.

```python
>>> ask.cache_info()
CacheInfo(hits=1, misses=2, maxsize=128, currsize=2)
>>> ask("파이썬이란?", model="small")
"[small] '파이썬이란?'의 답"
>>> ask.cache_info()
CacheInfo(hits=1, misses=3, maxsize=128, currsize=3)
```

`ask("파이썬이란?")`과 `ask("파이썬이란?", model="small")`은 결과가 같지만 캐시는 둘을 다른 호출로 본다. 1초를 또 기다렸다.

**인자가 리스트나 딕셔너리이면 쓸 수 없다.** LLM에게 보내는 메시지 목록은 딕셔너리의 리스트다.

```python
>>> ask([{"role": "user", "content": "안녕"}])
Traceback (most recent call last):
  ...
TypeError: unhashable type: 'list'
```

메시지 목록을 캐시하려면 튜플이나 JSON 문자열처럼 해시할 수 있는 것으로 바꿔서 키로 쓴다. 실습 4-4에서 해 본다.

**돌려준 결과를 바꾸면 캐시도 바뀐다.** 캐시는 결과의 **복사본이 아니라 그 객체 자체**를 기억한다(1.3.1).

```python
>>> @functools.cache
... def default_messages():
...     return [{"role": "system", "content": "친절하게 답한다."}]
...
>>> msgs = default_messages()
>>> msgs.append({"role": "user", "content": "안녕"})
>>> len(default_messages())
2
```

받은 리스트에 `append()`했더니 캐시 안의 리스트가 바뀌어, 다음 호출부터 모두 사용자 메시지가 하나 들어간 목록을 받는다. 리스트나 딕셔너리를 돌려주는 함수를 캐시한다면, 받은 쪽에서 복사해서 쓰거나 튜플처럼 바꿀 수 없는 객체를 돌려준다.

복사할 때는 **얕은 복사**에 주의한다(기초 과정 3.2.5). `list(...)`나 `{**d}`는 바깥 한 겹만 새로 만든다. 안에 든 딕셔너리는 캐시와 함께 쓴다.

```python
>>> msgs = list(default_messages())
>>> msgs[0]["content"] = "반말로 답한다."
>>> default_messages()[0]["content"]
'반말로 답한다.'
```

새 리스트에 `append()`하는 것은 괜찮지만, 안쪽 딕셔너리를 고치면 캐시도 바뀐다. 이 메시지 목록처럼 딕셔너리를 한 겹 품은 리스트라면 `[dict(m) for m in default_messages()]`로 딕셔너리까지 복사한다. 더 깊이 중첩된 구조라면 `copy.deepcopy()`로 통째로 복사한다.

**오래 실행되는 프로그램에서는 크기를 정한다.** `functools.cache`는 한도가 없다. 웹 서버처럼 며칠씩 실행되는 프로그램에서 사용자 질문마다 결과를 기억하면 메모리가 계속 늘어난다. `lru_cache(maxsize=...)`로 한도를 둔다. 또 이 캐시는 **프로그램 안의 메모리에만** 있다. 프로그램을 다시 시작하면 사라지고, 서버를 여러 대 띄우면 서버마다 따로다. 여러 서버가 함께 쓰는 캐시는 "LLM 서비스 배포"에서 다룬다.

**예외는 기억하지 않는다.** 원래 함수에서 예외가 나면 캐시에 아무것도 저장되지 않고 예외가 그대로 올라간다. 다음에 같은 인자로 부르면 다시 원래 함수를 부른다. 실패한 API 호출이 캐시에 "실패"로 굳어 버리지 않는다는 뜻이다. 실습 4-7에서 재시도와 캐시를 함께 쓸 때 이 성질을 이용한다.

### 4.4.4 `@classmethod` — 대체 생성자

기초 과정 5.4.7에서 딕셔너리를 데이터 클래스로 바꿀 때 `Product(**data)`를 썼다. 그리고 "필드에 없는 키가 있으면 `TypeError`가 난다"고 했다. LLM API의 응답 메시지가 그렇다. 우리가 필요한 것은 `role`과 `content`뿐인데 응답에는 `id`, `model` 같은 키가 더 들어 있다.

```python
>>> data = {"id": "msg_01", "role": "assistant", "content": "안녕하세요", "model": "small"}
>>> ChatMessage(**data)
Traceback (most recent call last):
  ...
TypeError: ChatMessage.__init__() got an unexpected keyword argument 'id'
```

딕셔너리에서 필요한 키만 골라 객체를 만드는 일을 클래스에 맡기고 싶다. `__init__`을 고쳐서 딕셔너리를 받게 할 수도 있지만, 그러면 `ChatMessage("user", "안녕")`처럼 쉽게 만드는 방법이 사라진다. 객체를 만드는 방법을 **하나 더** 두고 싶다. 이때 `@classmethod`를 쓴다.

`ch04/messages.py`

```python
"""대화 메시지 — @classmethod와 @staticmethod."""

from dataclasses import dataclass

ROLES = {"system", "user", "assistant"}


@dataclass
class ChatMessage:
    role: str
    content: str

    def __post_init__(self):
        if not self.is_valid_role(self.role):
            raise ValueError(f"알 수 없는 역할: {self.role!r}")

    @classmethod
    def from_dict(cls, data):
        """API 응답 같은 딕셔너리에서 필요한 키만 골라 메시지를 만든다."""
        return cls(role=data["role"], content=data["content"])

    @classmethod
    def user(cls, content):
        """사용자 메시지를 만든다."""
        return cls("user", content)

    @staticmethod
    def is_valid_role(role):
        """role이 쓸 수 있는 역할인지 돌려준다."""
        return role in ROLES


@dataclass
class TimedMessage(ChatMessage):
    created: str = ""


if __name__ == "__main__":
    data = {"id": "msg_01", "role": "assistant", "content": "안녕하세요", "model": "small"}
    print(ChatMessage.from_dict(data))
    print(ChatMessage.user("날씨 알려 줘"))
    print(ChatMessage.is_valid_role("tool"))
    print(TimedMessage.from_dict(data))
```

```
python ch04/messages.py
```

```
ChatMessage(role='assistant', content='안녕하세요')
ChatMessage(role='user', content='날씨 알려 줘')
False
TimedMessage(role='assistant', content='안녕하세요', created='')
```

`@classmethod`를 붙인 메서드는 첫 번째 매개변수로 **객체(`self`) 대신 클래스**를 받는다. 관례상 이름은 `cls`다. 그리고 객체가 아니라 **클래스로** 부른다. `ChatMessage.from_dict(data)`를 부르면 `cls`에 `ChatMessage`가 들어가고, `cls(role=..., content=...)`는 `ChatMessage(role=..., content=...)`가 된다.

`return ChatMessage(...)`라고 쓰지 않고 `cls(...)`라고 쓴 이유가 마지막 줄에 있다. 자식 클래스 `TimedMessage`로 `from_dict()`를 부르면 `cls`에 `TimedMessage`가 들어가므로, 물려받은 메서드가 **자식 클래스의 객체**를 만든다(기초 과정 5.3). 클래스 이름을 직접 썼다면 자식 클래스로 불러도 `ChatMessage`가 나왔을 것이다.

이렇게 객체를 만드는 또 하나의 방법을 제공하는 클래스 메서드를 **대체 생성자**(alternative constructor)라고 한다. 이름은 보통 `from_무엇`이다. 이미 써 본 것도 있다.

| 대체 생성자 | 하는 일 |
|---|---|
| `dict.fromkeys(["a", "b"], 0)` | 키 목록에서 딕셔너리를 만든다 → `{'a': 0, 'b': 0}` |
| `datetime.fromisoformat("2026-11-14T09:00")` | ISO 형식 문자열에서 날짜·시각을 만든다 |
| `datetime.now()` | 지금 시각으로 만든다 |
| `Path.home()` | 홈 폴더 경로로 만든다 |
| Pydantic의 `Question.model_validate(data)` | 딕셔너리를 검증하고 모델 객체를 만든다 (5장) |

### 4.4.5 `@staticmethod` — 객체도 클래스도 필요 없는 메서드

`is_valid_role()`에는 `@staticmethod`가 붙어 있다. 이 메서드는 `self`도 `cls`도 받지 않는다. 받은 `role`이 쓸 수 있는 역할인지만 본다. 객체의 속성도, 클래스도 쓰지 않는다. 그냥 클래스 안에 들어 있는 함수다.

```python
>>> from messages import ChatMessage
>>> ChatMessage.is_valid_role("user")
True
>>> ChatMessage.user("안녕").is_valid_role("robot")
False
```

클래스로도, 객체로도 부를 수 있다. `__post_init__`에서 `self.is_valid_role(...)`로 불렀다.

정적 메서드는 모듈 최상위의 함수와 하는 일이 같다. `is_valid_role()`을 클래스 밖에 `def is_valid_role(role):`로 두어도 된다. 클래스 안에 두는 이유는 "이 클래스와 관련된 함수"라는 것을 보이기 위해서뿐이다. 파이썬에서는 모듈이 이미 관련된 것을 묶어 주므로, **정적 메서드보다 모듈 함수를 더 자주 쓴다.** 남의 코드에서 `@staticmethod`를 만나면 "`self`를 쓰지 않는 메서드"로 읽으면 된다.

세 가지 메서드를 비교한다.

| | 일반 메서드 | `@classmethod` | `@staticmethod` |
|---|---|---|---|
| 첫 매개변수 | 객체 (`self`) | 클래스 (`cls`) | 없음 |
| 주로 부르는 방법 | `객체.메서드()` | `클래스.메서드()` | `클래스.메서드()` |
| 쓸 수 있는 것 | 객체의 속성, 다른 메서드 | 클래스 (새 객체 만들기, 클래스 속성) | 받은 인자뿐 |
| 주로 쓰는 곳 | 대부분의 메서드 | 대체 생성자 `from_...()` | 클래스와 관련된 도우미 함수 |

### 4.4.6 `@property` 다시 보기

기초 과정 5.2.6에서 `@property`를 붙여 메서드를 속성처럼 읽게 했다. 이제 이것도 4.2.2의 규칙대로 읽을 수 있다. `@property def balance(self): ...`는 `balance = property(balance)`다. `property`는 함수를 받아 **property 객체**를 돌려주는 데코레이터다. 함수가 아닌 객체를 돌려주는 예다(4.2.3 표의 마지막 줄).

기초 과정에서는 읽기만 하는 프로퍼티를 만들었다. **값을 넣을 때 검사하는** 프로퍼티도 만들 수 있다. LLM의 `temperature` 설정은 정해진 범위(예: 0.0~2.0)를 넘으면 API가 오류를 돌려준다. 요청을 보내기 전에 막는다.

`ch04/settings.py`

```python
"""@property와 setter — 값을 넣을 때 검사한다."""


class ModelSettings:
    def __init__(self, model, temperature=1.0):
        self.model = model
        self.temperature = temperature  # 아래의 setter를 거친다

    @property
    def temperature(self):
        """응답의 무작위성. 0.0~2.0."""
        return self._temperature

    @temperature.setter
    def temperature(self, value):
        if not 0.0 <= value <= 2.0:
            raise ValueError(f"temperature는 0.0~2.0이어야 한다: {value}")
        self._temperature = value


if __name__ == "__main__":
    s = ModelSettings("small")
    s.temperature = 0.2
    print(s.temperature)
    try:
        s.temperature = 5
    except ValueError as e:
        print("ValueError:", e)
    try:
        ModelSettings("small", temperature=-1)
    except ValueError as e:
        print("ValueError:", e)
```

```
python ch04/settings.py
```

```
0.2
ValueError: temperature는 0.0~2.0이어야 한다: 5
ValueError: temperature는 0.0~2.0이어야 한다: -1
```

- `@property def temperature(self):` — 읽을 때 부를 함수로 property 객체를 만든다. 이름 `temperature`가 그 객체를 가리킨다.
- `@temperature.setter` — 방금 만든 property 객체의 `setter` 메서드를 데코레이터로 쓴다. `temperature.setter(함수)`는 "값을 넣을 때 부를 함수"를 더한 **새** property 객체를 돌려주고, 같은 이름 `temperature`에 다시 붙는다. 그래서 두 메서드의 이름이 같아야 한다.
- `s.temperature = 5`처럼 값을 넣으면 파이썬이 setter를 부른다. 실제 값은 `_temperature`에 저장한다. setter 안에서 `self.temperature = value`라고 쓰면 setter가 자기 자신을 다시 불러 끝없이 반복된다(`RecursionError`).
- `__init__`의 `self.temperature = temperature`도 setter를 거친다. 그래서 객체를 만들 때 잘못된 값을 넣어도 막힌다.

`@temperature.setter`는 "객체의 메서드를 데코레이터로 쓴다"는 점에서 4.5의 `@app.get("/...")`과 닮았다. `app.get("/...")`도 `app` 객체의 메서드를 불러 데코레이터를 얻는다.

> **`functools.cached_property`**
> 계산이 오래 걸리는 프로퍼티라면 처음 읽을 때 한 번만 계산하고 그 값을 기억해 두는 `@functools.cached_property`를 쓸 수 있다. 문서를 읽어 들인 객체에서 "전체 토큰 수"처럼 한 번 구하면 바뀌지 않는 값에 어울린다. 4.4.3의 캐시와 같은 주의가 필요하다. 바탕이 되는 값이 바뀌어도 기억해 둔 값은 바뀌지 않는다.

### 4.4.7 `@dataclass` 다시 보기 — 클래스 데코레이터

`@dataclass`는 **클래스**를 받는 데코레이터다. `@dataclass class Product: ...`는 `Product = dataclass(Product)`다.

```python
>>> from dataclasses import dataclass
>>> class Product:
...     name: str
...     price: int
...
>>> P = dataclass(Product)
>>> P is Product
True
>>> Product("커피", 2500)
Product(name='커피', price=2500)
```

`dataclass()`는 래퍼를 만들지 않는다. 받은 클래스에 `__init__`, `__repr__`, `__eq__`를 **더해서 같은 클래스를 그대로** 돌려준다. 4.2.2의 `announce`처럼 받은 것을 돌려주되, 그 전에 손을 본 것이다. `@dataclass(frozen=True)`는 4.3.5에서 본 대로 괄호가 있어도 없어도 되는 데코레이터의 괄호 있는 모양이다.

**`__eq__`를 만들면 `__hash__`가 사라진다**

`@dataclass`가 더한 `__eq__` 덕분에 내용이 같은 두 객체는 `==`로 같다. 그런데 이 객체를 집합에 넣으려 하면 오류가 난다.

```python
>>> a = Product("커피", 2500)
>>> b = Product("커피", 2500)
>>> a == b
True
>>> {a, b}
Traceback (most recent call last):
  ...
TypeError: unhashable type: 'Product'
>>> print(Product.__hash__)
None
```

집합과 딕셔너리는 해시로 자리를 찾은 다음, 그 자리에 있는 것과 `==`로 같은지 확인한다(기초 과정 3.6.4). 그래서 **`==`로 같은 두 객체는 해시도 같아야 한다**는 약속이 있다. `object`에게서 물려받은 기본 `__hash__`는 객체의 **정체성**(`id()`)을 바탕으로 계산한다. 기본 `__eq__`가 같은 객체인지(`is`)를 비교하니 둘이 짝이 맞는다. 그런데 `__eq__`만 내용으로 비교하게 바꾸면, 내용이 같아도 서로 다른 두 객체는 `==`로는 같은데 해시는 대개 달라서 약속이 깨진다. 그래서 파이썬은 클래스에 `__eq__`를 정의하면 `__hash__`를 `None`으로 바꿔 해시할 수 없게 한다. `@dataclass`도 마찬가지다.

`@dataclass(frozen=True)`로 바꾸면 `Product`를 집합에 넣을 수 있다. `frozen=True`이면 `@dataclass`가 필드 값을 묶은 튜플로 해시를 계산하는 `__hash__`도 더해 주기 때문이다. 단, 이 해시를 계산할 수 있으려면 **필드가 모두 해시 가능해야** 한다. `Product`의 `str`과 `int`는 해시 가능하므로 문제가 없다. 하지만 `tags: list[str]` 같은 필드가 있으면 `__hash__`가 만들어져도 `hash()`를 부르거나 집합에 넣는 순간 `TypeError: unhashable type: 'list'`가 난다. 기초 과정 5.4.6에서 본 대로 `frozen=True`는 필드에 다른 값을 할당하는 것만 막고, 필드가 가리키는 리스트의 안쪽까지 얼리지는 않기 때문이다. 집합에 넣을 데이터는 필드를 `tuple[str, ...]`처럼 **안쪽까지 불변인 값**으로 채운다.

해시가 바뀌지 않아야 하는 이유도 있다. 해시가 바뀔 수 있는 객체를 집합에 넣으면, 넣은 뒤에 값을 바꾸었을 때 집합이 그 객체를 다시 찾지 못한다.

클래스를 직접 만든다면 두 메서드를 함께 만든다.

```python
>>> class Version:
...     def __init__(self, major, minor):
...         self._major = major
...         self._minor = minor
...     def __eq__(self, other):
...         if not isinstance(other, Version):
...             return NotImplemented
...         return (self._major, self._minor) == (other._major, other._minor)
...     def __hash__(self):
...         return hash((self._major, self._minor))
...
>>> Version(1, 2) == Version(1, 2)
True
>>> Version(1, 2) == "1.2"
False
>>> len({Version(1, 2), Version(1, 2)})
1
```

- `__hash__`는 **`__eq__`가 비교하는 값 중에서만** 골라 계산한다. `__eq__`가 무시하는 값(예를 들어 객체를 만든 시각)을 해시에 넣으면, `==`로 같은 두 객체의 해시가 달라져서 약속이 깨진다. 반대로 비교하는 값의 일부만 써도 약속은 지켜진다. `__hash__`가 `major`만 써도, `==`로 같은 두 객체는 `major`가 같으니 해시도 같다. 다른 객체끼리 해시가 겹치는 것(충돌)은 허용된다. 다만 해시가 자주 겹치면 집합과 딕셔너리가 `==` 비교를 많이 하게 되어 느려진다. 그래서 여기처럼 `__eq__`와 **같은 튜플**로 해시를 계산하는 것이 가장 쉽고 안전하다.
- 속성 이름을 밑줄로 시작하고(기초 과정 5.2.5) 값을 바꾸는 메서드를 두지 않았다. 해시가 바뀌지 않게 하려는 것이다. 값이 바뀌는 객체라면 `__hash__`를 만들지 않는다.
- 비교할 수 없는 상대가 오면 `False`가 아니라 **`NotImplemented`**를 돌려준다. "나는 이 상대와 비교하는 법을 모른다"는 뜻이다. 그러면 파이썬은 상대 쪽의 `__eq__`에게 묻고, 그쪽도 모르면 같은 객체인지(`is`)로 정한다. 그래서 `Version(1, 2) == "1.2"`는 오류 없이 `False`다. 5.5.5에서 `|` 같은 연산자도 같은 방식으로 상대에게 차례를 넘기는 것을 본다.

이런 클래스를 직접 만들 일은 많지 않다. 대부분은 `@dataclass(frozen=True)`가 두 메서드를 맞춰서 만들어 준다.

이로써 기초 과정에서 붙여 쓰기만 한 데코레이터를 모두 읽을 수 있게 되었다.

| 데코레이터 | 받는 것 | 돌려주는 것 |
|---|---|---|
| `@functools.cache`, `@functools.lru_cache(...)` | 함수 | 결과를 기억하는 호출 가능한 객체 |
| `@classmethod`, `@staticmethod` | 함수 | 클래스로 부를 수 있게 바꾼 메서드 객체 |
| `@property`, `@이름.setter` | 함수 | property 객체 |
| `@dataclass`, `@dataclass(...)` | 클래스 | 메서드를 더한 같은 클래스 |
| `@functools.wraps(func)` | 래퍼 함수 | `func`의 이름과 독스트링을 복사한 같은 래퍼 |

## 4.5 등록 데코레이터

### 4.5.1 함수를 딕셔너리에 등록하기

1.3.2에서 함수를 딕셔너리에 담아 이름으로 골라 불렀다.

```python
styles = {"shout": shout, "whisper": whisper}
```

함수를 하나 더 만들 때마다 이 딕셔너리에도 손으로 넣어야 한다. 잊으면 함수는 있는데 쓸 수 없다. 함수를 **정의하는 그 자리에서** 딕셔너리에 들어가게 하면 잊을 일이 없다. 4.2.2에서 데코레이터는 함수를 정의할 때 실행된다고 했다. 받은 함수를 딕셔너리에 넣고 **그대로** 돌려주는 데코레이터를 만든다.

`ch04/commands.py`

```python
"""등록 데코레이터 — 함수를 정의하면 명령 목록에 들어간다."""

COMMANDS = {}


def command(func):
    """func를 COMMANDS에 함수 이름으로 등록하고, func를 그대로 돌려준다."""
    COMMANDS[func.__name__] = func
    return func


@command
def hello(name):
    """인사한다."""
    return f"안녕, {name}!"


@command
def add(a, b):
    """두 수를 더한다."""
    return int(a) + int(b)


@command
def usage():
    """명령 목록을 보여 준다."""
    return "\n".join(f"{name:<6} {func.__doc__}" for name, func in COMMANDS.items())


def run(line):
    """'명령 인자 ...' 모양의 한 줄을 실행한다."""
    name, *args = line.split()
    func = COMMANDS.get(name)
    if func is None:
        return f"모르는 명령: {name}"
    return func(*args)


if __name__ == "__main__":
    print(COMMANDS)
    for line in ["hello 지민", "add 3 4", "usage", "bye"]:
        print(f"> {line}")
        print(run(line))
```

- `command()`는 래퍼를 만들지 않는다. 4.2.2의 `announce`처럼 받은 함수를 그대로 돌려준다. 그래서 `hello`는 원래 함수 그대로이고, `hello("지민")`처럼 직접 불러도 된다. 하는 일은 정의할 때 **딕셔너리에 한 줄 넣는 것**뿐이다.
- `run()`은 2.4.1의 확장 언패킹으로 한 줄을 명령 이름과 인자 목록으로 나누고, 딕셔너리에서 함수를 꺼내 `*args`로 풀어 부른다(1.3.3).
- `usage()`는 등록된 함수의 이름과 독스트링으로 도움말을 만든다. 새 명령을 추가하면 도움말에도 저절로 나타난다. 독스트링이 문서이자 화면에 보이는 설명이 된다.

**함수를 정의하는 것만으로 기능이 추가된다.** 이것이 등록 데코레이터의 핵심이다. 명령을 하나 더 만들고 싶으면 `@command`를 붙인 함수를 하나 더 쓰면 된다. `run()`이나 `usage()`는 고칠 필요가 없다. 웹 프레임워크, 명령행 도구, 테스트 도구, 에이전트 프레임워크가 모두 이 방식을 쓴다. 6장의 pytest는 데코레이터 대신 `test_`로 시작하는 이름으로 함수를 찾지만, "함수를 정의하면 알아서 찾아서 부른다"는 생각은 같다.

### 4.5.2 `@app.get("/...")` — 웹 프레임워크 흉내 내기

1.1.3 (나)의 FastAPI 코드를 다시 본다.

```python
app = FastAPI()


@app.post("/chat")
async def chat(req: ChatRequest) -> ChatResponse:
    ...
```

`@app.post("/chat")`은 세 부분으로 읽는다. `app.post`는 `app` 객체의 메서드이고, `("/chat")`으로 그 메서드를 불러 데코레이터를 얻고, 그 데코레이터가 `chat` 함수를 받는다. 4.3의 세 겹 구조에서 바깥 함수가 **객체의 메서드**인 것이다. 무엇을 하는지 직접 만들어 본다.

`ch04/mini_web.py`

```python
"""작은 웹 프레임워크 흉내 — @app.get("/...")가 하는 일."""


class MiniApp:
    def __init__(self):
        self.routes = {}  # {(메서드, 경로): 처리 함수}

    def route(self, method, path):
        """method와 path의 요청을 처리할 함수로 등록하는 데코레이터를 돌려준다."""

        def decorator(func):
            self.routes[(method, path)] = func
            return func

        return decorator

    def get(self, path):
        return self.route("GET", path)

    def post(self, path):
        return self.route("POST", path)

    def handle(self, method, path, **params):
        """요청을 등록된 함수에 넘기고 (상태 코드, 본문)을 돌려준다."""
        func = self.routes.get((method, path))
        if func is None:
            return 404, {"error": "Not Found"}
        return 200, func(**params)


app = MiniApp()


@app.get("/health")
def health():
    return {"status": "ok"}


@app.post("/chat")
def chat(question):
    return {"answer": f"'{question}'에 대한 답"}


if __name__ == "__main__":
    print(app.routes)
    print(app.handle("GET", "/health"))
    print(app.handle("POST", "/chat", question="안녕"))
    print(app.handle("GET", "/chat"))
```


- `route()`가 세 겹 구조의 바깥 층이다. 설정(`method`, `path`)을 받아 데코레이터를 돌려준다. 데코레이터는 `self.routes`에 함수를 넣는다. `self`도 바깥 변수이므로 안쪽 함수가 쓸 수 있다.
- `get()`과 `post()`는 `route()`에 메서드 이름을 채워 부르는 지름길이다. 4.1.5 (다)의 `partial`과 같은 생각이다.
- 등록 정보를 전역 딕셔너리가 아니라 **객체의 속성**에 두었다. 그래서 `MiniApp` 객체를 여러 개 만들면 각자 따로 경로를 갖는다. FastAPI도 `app = FastAPI()`로 객체를 만들고 그 객체의 메서드로 등록한다.
- `handle()`이 실제 웹 서버가 하는 일을 흉내 낸다. 진짜 서버는 네트워크로 들어온 HTTP 요청에서 메서드와 경로를 읽어 `routes`에서 함수를 찾고, 요청 본문을 함수의 인자로 바꿔 넘기고, 돌려받은 값을 JSON 응답으로 바꿔 보낸다.

실제 FastAPI는 훨씬 많은 일을 한다. 경로 안의 변수(`/users/{user_id}`)를 읽고, 타입 힌트로 요청 본문을 검사하고(5장의 Pydantic), `async def` 함수를 비동기로 실행한다(7장). 하지만 **"데코레이터가 함수를 경로와 짝지어 등록한다"는 뼈대는 같다.** 이제 `@app.post("/chat")`을 "`/chat`으로 오는 POST 요청은 이 함수가 처리한다고 `app`에 등록한다"로 읽을 수 있다.

### 4.5.3 `@mcp.tool()` — 도구 등록하기

에이전트 개발에서는 LLM이 부를 수 있는 **도구**(tool)를 정의한다. LLM에게 "이런 도구들이 있다"고 이름, 설명, 매개변수를 알려 주면, LLM은 필요할 때 "이 도구를 이 인자로 불러 달라"는 응답을 보낸다(2.5.8의 도구 호출 메시지). 그러면 프로그램이 그 함수를 실제로 부르고 결과를 LLM에게 돌려준다.

MCP(Model Context Protocol) 서버를 만드는 파이썬 SDK에서는 도구를 이렇게 정의한다.

```python
from mcp.server.fastmcp import FastMCP

mcp = FastMCP("weather")


@mcp.tool()
def get_weather(city: str, unit: str = "celsius") -> str:
    """도시의 현재 날씨를 알려 준다."""
    ...
```

`@mcp.tool()`은 4.5.2의 `@app.get("/...")`과 같은 모양이다. 다른 점은, 등록하면서 함수의 **이름, 독스트링, 매개변수의 타입 힌트**를 읽어 LLM에게 보여 줄 **도구 설명**을 만든다는 것이다. 기초 과정에서 독스트링과 타입 힌트를 꼬박꼬박 쓴 것이 여기서 LLM이 읽는 문서가 된다. 이것도 직접 만들어 본다.

함수의 매개변수를 읽으려면 표준 라이브러리 `inspect`의 `signature()`를 쓴다.

```python
>>> import inspect
>>> def get_weather(city: str, unit: str = "celsius") -> str:
...     """도시의 현재 날씨를 알려 준다."""
...
>>> sig = inspect.signature(get_weather)
>>> sig
<Signature (city: str, unit: str = 'celsius') -> str>
>>> for p in sig.parameters.values():
...     print(p.name, p.annotation, p.default)
...
city <class 'str'> <class 'inspect._empty'>
unit <class 'str'> celsius
>>> inspect.getdoc(get_weather)
'도시의 현재 날씨를 알려 준다.'
```

`signature()`는 함수의 매개변수 목록을 객체로 돌려준다. 매개변수마다 이름(`name`), 타입 힌트(`annotation`), 기본값(`default`)을 읽을 수 있다. 기본값이 없으면 `inspect.Parameter.empty`라는 특별한 값이다(출력의 `inspect._empty`). 기본값이 없는 매개변수는 LLM이 **반드시** 채워야 하는 인자다. `getdoc()`은 독스트링을 들여쓰기를 정리해서 돌려준다.

`ch04/tools.py`

```python
"""도구 등록 — MCP 서버의 @mcp.tool()이 하는 일."""

import inspect

JSON_TYPES = {str: "string", int: "integer", float: "number", bool: "boolean"}


def describe(func, name=None):
    """함수의 이름, 독스트링, 매개변수로 LLM에게 보여 줄 도구 설명을 만든다."""
    properties = {}
    required = []
    for param in inspect.signature(func).parameters.values():
        properties[param.name] = {"type": JSON_TYPES.get(param.annotation, "string")}
        if param.default is inspect.Parameter.empty:
            required.append(param.name)
    return {
        "name": name or func.__name__,
        "description": inspect.getdoc(func) or "",
        "input_schema": {"type": "object", "properties": properties, "required": required},
    }


class ToolRegistry:
    def __init__(self):
        self.tools = {}  # {도구 이름: 함수}

    def tool(self, name=None):
        """함수를 도구로 등록하는 데코레이터를 돌려준다. name을 주지 않으면 함수 이름을 쓴다."""

        def decorator(func):
            self.tools[name or func.__name__] = func
            return func

        return decorator

    def schemas(self):
        """등록된 도구의 설명 목록. LLM API 요청에 함께 보낸다."""
        return [describe(func, name) for name, func in self.tools.items()]

    def call(self, name, arguments):
        """LLM이 요청한 도구를 인자 딕셔너리로 부른다."""
        return self.tools[name](**arguments)


registry = ToolRegistry()


@registry.tool()
def get_weather(city: str, unit: str = "celsius") -> str:
    """도시의 현재 날씨를 알려 준다."""
    return f"{city}: 맑음, 18도({unit})"


@registry.tool(name="search_docs")
def search(query: str, top_k: int = 3) -> list[str]:
    """사내 문서에서 query와 관련된 문단을 찾는다."""
    return [f"{query} 관련 문단 {i}" for i in range(1, top_k + 1)]


if __name__ == "__main__":
    import json

    print(json.dumps(registry.schemas()[0], ensure_ascii=False, indent=2))
    print([s["name"] for s in registry.schemas()])

    tool_call = {"type": "tool_use", "id": "call_1", "name": "search_docs",
                 "input": {"query": "휴가 규정", "top_k": 2}}
    match tool_call:
        case {"type": "tool_use", "name": str(name), "input": dict(arguments)}:
            print(registry.call(name, arguments))
```

- `describe()` — 함수 하나의 도구 설명을 만든다. 매개변수마다 타입 힌트를 `JSON_TYPES`로 JSON의 타입 이름(`"string"`, `"integer"` 등)으로 바꾸고, 기본값이 없는 매개변수는 `required`에 넣는다. 이 모양을 **JSON 스키마**(JSON Schema)라고 한다. "이 객체에는 이런 이름과 타입의 속성이 있고, 이것들은 꼭 있어야 한다"는 것을 JSON으로 적는 표준 형식이다. LLM API의 도구 정의가 이 형식을 쓴다. Anthropic API는 `input_schema`, OpenAI API는 `parameters`라는 키에 담는 등 바깥 모양은 API마다 조금 다르다.
- `tool(name=None)` — 괄호와 함께 쓰는 등록 데코레이터다. 이름을 주지 않으면 함수 이름을 쓴다. `search`는 `search_docs`라는 이름으로 등록했다. `@mcp.tool()`에 빈 괄호가 붙는 이유도 이처럼 이름, 설명 같은 설정을 받을 수 있기 때문이다.
- `call()` — LLM이 보낸 도구 호출의 `name`과 `input`(인자 딕셔너리)으로 등록된 함수를 찾아 `**`로 풀어 부른다. 마지막 `match` 문은 2.5.8에서 도구 호출 메시지를 분기한 모양 그대로다.

`describe()`는 아주 단순하게 만든 것이다. `list[str]` 같은 타입은 `JSON_TYPES`에 없어서 모두 `"string"`이 되고, 매개변수마다의 설명도 없다. 실제 SDK는 5장의 Pydantic으로 타입 힌트에서 정확한 JSON 스키마를 만든다. 5장에서 `model_json_schema()`로 같은 일을 다시 한다.

### 4.5.4 함수를 바꿔 돌려주는 데코레이터 — LangChain의 `@tool`

1.1.3 (다)의 LangChain 코드도 데코레이터로 도구를 정의했다.

```python
from langchain_core.tools import tool


@tool
def search_docs(query: str, top_k: int = 3) -> list[str]:
    """사내 문서에서 query와 관련된 문단을 찾는다."""
    ...
```

모양은 `@registry.tool()`과 비슷하지만 하는 일이 다르다. LangChain의 `@tool`은 함수를 어딘가에 **등록하지 않는다.** 대신 함수를 **도구 객체로 바꿔서** 돌려준다. 1.3.2에서 "LangChain의 `@tool`은 조금 다르다"고 한 것이 이것이다. 같은 일을 하는 작은 데코레이터를 만들어 본다.

`ch04/as_tool.py`

```python
"""함수를 도구 객체로 바꿔 돌려주는 데코레이터 — LangChain의 @tool이 하는 일."""

import inspect
from dataclasses import dataclass
from typing import Callable


@dataclass
class Tool:
    name: str
    description: str
    func: Callable

    def invoke(self, arguments):
        """인자 딕셔너리로 도구를 실행한다."""
        return self.func(**arguments)


def as_tool(func):
    """함수를 Tool 객체로 바꿔 돌려준다. 원래 함수는 Tool 안에 들어간다."""
    return Tool(func.__name__, inspect.getdoc(func) or "", func)


@as_tool
def search_docs(query: str, top_k: int = 3) -> list[str]:
    """사내 문서에서 query와 관련된 문단을 찾는다."""
    return [f"{query} 관련 문단 {i}" for i in range(1, top_k + 1)]


if __name__ == "__main__":
    print(type(search_docs))
    print(search_docs.name, "/", search_docs.description)
    print(search_docs.invoke({"query": "연차", "top_k": 2}))
    search_docs("연차")
```

`Callable`은 "부를 수 있는 것"을 뜻하는 타입 힌트다. 5장에서 자세히 본다.

`@as_tool`을 붙인 뒤 `search_docs`라는 이름은 **더 이상 함수가 아니다.** `Tool` 객체다. 그래서 함수처럼 부를 수 없고, 객체의 메서드 `invoke()`로 실행한다. LangChain의 도구 객체도 `.invoke()`로 실행하고, 이 객체를 모델이나 에이전트에 **직접 넘겨야** 쓰인다. 어딘가에 저절로 등록되지 않기 때문이다.

| | 등록 데코레이터 (`@app.get`, `@mcp.tool()`, `@command`) | 바꿔 돌려주는 데코레이터 (`@tool`, `@property`) |
|---|---|---|
| 돌려주는 것 | 원래 함수 그대로 | 다른 객체 (도구 객체, property 객체) |
| 정의한 뒤 그 이름으로 | 함수를 그대로 부를 수 있다 | 그 객체의 방식으로 쓴다 (`.invoke()`, 속성 읽기) |
| 함수가 쓰이게 되는 방법 | 등록된 곳(앱, 서버)이 찾아서 부른다 | 객체를 쓸 곳에 직접 넘긴다 (`agent(tools=[search_docs])`) |
| 장점 | 함수를 그대로 테스트할 수 있다 | 전역 상태가 없다. 어떤 도구를 쓸지 넘기는 쪽이 정한다 |

라이브러리의 데코레이터를 처음 만나면 이 둘 중 무엇인지부터 확인한다. 데코레이터를 붙인 이름을 대화형 셸에서 `type()`으로 찍어 보면 바로 알 수 있다.

### 4.5.5 등록은 `import`할 때 일어난다

등록 데코레이터는 함수를 **정의할 때** 등록한다(4.2.2). 파일 안의 함수라면 그 파일이 **실행되거나 `import`될 때**다. 이 사실 때문에 생기는 함정이 있다.

도구가 많아져서 날씨 도구를 `ch04/weather_tools.py`로 옮겼다고 하자.

```python
"""날씨 관련 도구."""

from tools import registry


@registry.tool()
def get_forecast(city: str, days: int = 3) -> str:
    """도시의 며칠 치 일기 예보를 알려 준다."""
    return f"{city}: {days}일 동안 맑음"
```

그리고 다른 파일에서 등록된 도구를 확인한다.

```python
>>> from tools import registry
>>> list(registry.tools)
['get_weather', 'search_docs']
>>> import weather_tools
>>> list(registry.tools)
['get_weather', 'search_docs', 'get_forecast']
```

`get_forecast`는 `weather_tools`를 `import`하기 **전에는** 등록되어 있지 않다. `def get_forecast` 문이 아직 실행되지 않았기 때문이다. 도구 파일을 새로 만들고 `import`하는 것을 잊으면, 오류 없이 **그 도구들만 조용히 빠진다.** LLM은 그런 도구가 있는지도 모른다.

그래서 등록 방식을 쓰는 프로젝트에는 "모든 도구 파일을 `import`하는 곳"이 하나 있다. 프로그램의 시작 파일이나 패키지의 `__init__.py`(기초 과정 8.3.2)에서 `import weather_tools`처럼 쓴다. 이렇게 `import`만 하고 그 이름을 쓰지 않는 줄은 Ruff가 "쓰지 않는 import"라고 밑줄을 긋기도 한다. 등록을 위해 일부러 하는 `import`라면 그 줄에 주석으로 이유를 적어 둔다. FastAPI의 `app.include_router()`처럼 "다른 파일의 등록 정보를 가져와 합치는" 기능을 따로 두는 라이브러리도 있다.

**등록 데코레이터와 다른 데코레이터를 겹쳐 붙일 때도 순서에 주의한다.** 등록되는 것은 **등록 데코레이터가 받은 함수**다.

```python
@app.get("/a")   # timed의 래퍼를 등록한다 → 요청마다 시간이 찍힌다
@timed
def a():
    return "a"


@timed           # 원래 함수를 등록한 뒤에 감싼다 → 등록된 함수에는 시간 재기가 없다
@app.get("/b")
def b():
    return "b"
```

`/b`로 요청이 오면 `app`은 등록해 둔 **원래** `b` 함수를 부르므로 시간이 찍히지 않는다. `timed`의 래퍼는 `b`라는 이름에만 붙어 있어서, 코드에서 `b()`를 직접 부를 때만 동작한다. **등록 데코레이터는 맨 위에 둔다.** 그래야 아래의 데코레이터가 모두 적용된 함수가 등록된다.

### 실습 4-5. 등록 데코레이터

**1. 인자가 틀린 명령**

`commands.py`에서 `run("add 3")`을 실행하면 `TypeError`로 프로그램이 멈춘다. `run()`을 고쳐, 인자의 개수가 맞지 않으면 `사용법: add a b`처럼 그 명령의 매개변수 이름을 보여 주게 한다. (힌트: `inspect.signature(func)`의 `parameters`에서 이름을 꺼낸다. `TypeError`를 잡을 때는 `try` 블록에 `func(*args)` 한 줄만 둔다. 명령 함수 **안에서** 난 `TypeError`까지 "인자가 틀렸다"로 잘못 알리지 않도록, 부르기 전에 `signature(func).bind(*args)`로 인자를 먼저 맞춰 보는 방법도 있다. `help(inspect.Signature.bind)`로 알아본다.)

**2. 별명 붙이기**

`command`를 고쳐 `@command("plus", "더하기")`처럼 별명을 받게 한다. 함수 이름과 별명 모두로 등록한다. 별명이 없으면 `@command()`처럼 빈 괄호로 쓴다. `usage()`에는 함수마다 한 줄만, `add (plus, 더하기)  두 수를 더한다.`처럼 나오게 한다. (힌트: 별명을 함수의 속성 `func.aliases`에 붙여 두면 `usage()`에서 읽을 수 있다.)

**3. 405 Method Not Allowed**

`mini_web.py`의 `handle()`을 고쳐, 경로는 있지만 메서드가 다르면(`app.handle("GET", "/chat")`) 404 대신 `405, {"error": "Method Not Allowed"}`를 돌려주게 한다. 그리고 등록된 경로를 `GET  /health → health`처럼 한 줄씩 출력하는 `print_routes()` 메서드를 더한다.

**4. 도구 호출이 실패하면**

## 4.6 컨텍스트 관리자 만들기

### 4.6.1 `with` 문이 실제로 하는 일

1.3.6에서 `with` 문은 블록을 빠져나갈 때 **반드시** 정리 작업을 한다고 했다. 그리고 1.3.4에서 `with` 블록에 들어갈 때 파이썬이 객체의 `__enter__()`를, 나갈 때 `__exit__()`를 부른다고 했다. 3장에서 `for` 문을 `iter()`와 `next()`로 풀어 썼듯이(3.1.1), `with` 문도 풀어 쓸 수 있다.

```python
with 식 as 이름:
    블록
```

은 대략 다음과 같다.

```python
manager = 식                          # ① with 뒤의 식을 계산한다
이름 = manager.__enter__()            # ② 들어갈 때. 돌려준 값이 as 뒤의 이름에 붙는다
exited = False                        #    __exit__를 이미 불렀는지 표시해 둔다
try:
    블록                              # ③ 블록을 실행한다
except BaseException as e:            # ④ 블록에서 예외가 나면
    exited = True
    if not manager.__exit__(type(e), e, e.__traceback__):
        raise                         #    __exit__가 참을 돌려주지 않으면 예외를 다시 일으킨다
finally:
    if not exited:                    # ⑤ 예외 없이 끝나면 (return, break, continue로 나가도)
        manager.__exit__(None, None, None)
```

⑤를 `try`의 `else:`에 두지 않고 `finally:`에 둔 데 주의한다. `else` 블록은 `try` 블록이 끝까지 실행되었을 때만 실행된다(기초 과정 6.1.7). 블록 안에서 `return`, `break`, `continue`로 빠져나가면 `else`는 건너뛴다. 반면 `finally`는 어떻게 빠져나가든 실행된다(기초 과정 6.1.8). 3.6.5에서 스트림을 `break`로 멈춘 것처럼 `with` 블록을 중간에 빠져나가는 일은 흔하므로, 그때도 정리가 되어야 한다. 예외로 끝난 경우에는 ④에서 이미 `__exit__()`를 불렀으므로, `exited`로 표시해 두고 ⑤에서 다시 부르지 않는다.

- `with` 문을 관리하는 객체, 즉 `__enter__`와 `__exit__`를 가진 객체를 **컨텍스트 관리자**(context manager)라고 부른다. 파일 객체, `httpx.Client`(1.2.6), 3.6.5에서 본 SDK의 스트림이 모두 컨텍스트 관리자다.
- `as` 뒤의 이름에는 `__enter__()`가 **돌려준 값**이 붙는다. `with` 뒤의 객체와 다를 수 있다. 파일 객체는 `__enter__()`가 자기 자신을 돌려주므로 `with open(...) as f:`의 `f`는 파일 객체다.
- `__exit__()`는 블록이 어떻게 끝나든 **반드시** 불린다. 예외로 끝나면 예외의 종류, 예외 객체, 트레이스백 세 가지를 받고, 정상으로 끝나면 셋 다 `None`을 받는다.
- `__exit__()`가 참을 돌려주면 예외가 **사라진다.** 거짓(또는 `None`)을 돌려주면 예외는 그대로 올라간다. 4.6.3에서 다시 본다.

블록이 끝나면 정리하는 이 구조는 4.2의 데코레이터와 닮았다. 데코레이터가 **함수 호출**의 앞뒤에 무언가를 덧붙인다면, 컨텍스트 관리자는 **코드 블록**의 앞뒤에 무언가를 덧붙인다.

### 4.6.2 `__enter__`와 `__exit__`로 만들기

4.2.5에서 함수의 실행 시간을 재는 데코레이터를 만들었다. 함수 전체가 아니라 **코드의 일부**만 재고 싶을 때가 있다. 컨텍스트 관리자로 만든다.

`ch04/timer_class.py`

```python
"""__enter__와 __exit__로 만든 컨텍스트 관리자."""

import time


class Timer:
    """with 블록의 실행 시간을 잰다."""

    def __init__(self, label):
        self.label = label
        self.elapsed = None

    def __enter__(self):
        print(f"[{self.label}] 시작")
        self.start = time.perf_counter()
        return self

    def __exit__(self, exc_type, exc, tb):
        self.elapsed = time.perf_counter() - self.start
        status = "완료" if exc_type is None else f"실패({exc_type.__name__})"
        print(f"[{self.label}] {status}: {self.elapsed:.2f}초")
        return False


if __name__ == "__main__":
    with Timer("요약") as t:
        time.sleep(0.3)
        print("요약하는 중")
    print("잰 시간:", round(t.elapsed, 1))

    try:
        with Timer("번역"):
            time.sleep(0.1)
            raise TimeoutError("응답 없음")
    except TimeoutError as e:
        print("밖에서 잡음:", e)
```

```
[요약] 완료: 0.30초
잰 시간: 0.3
[번역] 시작
[번역] 실패(TimeoutError): 0.10초
밖에서 잡음: 응답 없음
```

- `__enter__`는 시계를 시작하고 **자기 자신**을 돌려준다. 그래서 `as t`의 `t`가 `Timer` 객체이고, 블록이 끝난 뒤 `t.elapsed`로 잰 시간을 읽을 수 있다.
- `__exit__`는 매개변수 세 개를 받는다. 이름은 자유지만 `exc_type, exc, tb`(예외의 종류, 예외 객체, 트레이스백)가 흔하다. `exc_type`이 `None`이면 블록이 정상으로 끝난 것이다.
- `return False` — 예외를 삼키지 않는다. 두 번째 `with` 블록의 `TimeoutError`는 시간을 출력한 뒤 그대로 올라가 바깥 `except`에서 잡혔다. `return`을 아예 쓰지 않아도 `None`(거짓)이므로 결과는 같다. 여기서는 의도를 드러내려고 적었다.

### 4.6.3 예외를 삼키는 `__exit__`

`__exit__()`가 참을 돌려주면 블록에서 난 예외가 사라진다. 일부러 그렇게 만드는 경우도 있다.

```python
>>> class Ignore:
...     def __init__(self, *exc_types):
...         self.exc_types = exc_types
...     def __enter__(self):
...         return self
...     def __exit__(self, exc_type, exc, tb):
...         return exc_type is not None and issubclass(exc_type, self.exc_types)
...
>>> with Ignore(FileNotFoundError):
...     open("없는파일.txt")
...     print("여기는 실행되지 않는다")
...
>>> print("with 다음 줄")
with 다음 줄
```

`open()`에서 `FileNotFoundError`가 나자 블록의 나머지(`print`)는 건너뛰고 `__exit__()`가 불렸다. `issubclass(종류, 튜플)`은 그 종류가 튜플 안의 클래스이거나 그 자식 클래스이면 참이다. 참을 돌려받았으므로 예외는 사라지고 `with` 문 다음 줄부터 계속 실행된다.

표준 라이브러리에 같은 일을 하는 `contextlib.suppress`가 있다. "파일이 있으면 지우고, 없으면 그만"처럼 **일어나도 괜찮은 예외**를 무시할 때 쓴다.

```python
from contextlib import suppress

with suppress(FileNotFoundError):
    os.remove("cache.json")
```

하지만 예외를 삼키는 것은 기초 과정 6.2.6에서 경고한 "모든 예외를 삼키는 `except`"만큼 위험하다. 직접 만든 `__exit__()`에서 실수로 `return True`를 쓰면 블록 안의 **모든** 오류가 소리 없이 사라진다. **`__exit__()`는 특별한 이유가 없으면 거짓을 돌려준다.** 삼킬 예외가 있다면 `Ignore`처럼 종류를 좁힌다.

### 4.6.4 `@contextmanager` — 제너레이터 하나로 만들기

`Timer` 클래스는 메서드가 셋이고, 시작 시각을 `self.start`에 담아 `__enter__`에서 `__exit__`로 넘겨야 했다. 표준 라이브러리 `contextlib`의 `contextmanager` 데코레이터를 쓰면 **제너레이터 함수 하나로** 같은 일을 할 수 있다.

`ch04/timer_cm.py`

```python
"""@contextmanager — 제너레이터 하나로 만드는 컨텍스트 관리자."""

import time
from contextlib import contextmanager


@contextmanager
def timer(label):
    """with 블록의 실행 시간을 출력한다. as로 받은 딕셔너리에 시간을 남긴다."""
    result = {"label": label, "elapsed": None}
    start = time.perf_counter()
    try:
        yield result
    finally:
        result["elapsed"] = time.perf_counter() - start
        print(f"[{label}] {result['elapsed']:.2f}초")


if __name__ == "__main__":
    with timer("요약") as t:
        time.sleep(0.1)
    print(round(t["elapsed"], 1))

    try:
        with timer("번역"):
            raise TimeoutError("응답 없음")
    except TimeoutError:
        print("밖에서 잡음")
```

```

```

```
0.1
[번역] 0.00초
밖에서 잡음
```

`yield`가 하나 있는 제너레이터 함수가 `with` 문의 앞뒤를 나눈다.

```
@contextmanager
def timer(label):
    result = ...            ┐
    start = ...             │ __enter__ — with 블록에 들어갈 때 여기까지 실행하고
    try:                    │
        yield result  ──────┘ yield에서 멈춘다. yield한 값이 as 뒤의 이름(t)에 붙는다
                            ← 여기서 with 블록이 실행된다
    finally:                ┐
        result[...] = ...   │ __exit__ — 블록이 끝나면 yield 다음부터 이어서 실행한다
        print(...)          ┘
```

3.2에서 배운 제너레이터의 성질, "`yield`에서 **멈췄다가** 다음에 **이어서** 실행한다"를 그대로 쓴다. `contextmanager`가 만든 컨텍스트 관리자는 `__enter__()`에서 `next()`로 제너레이터를 `yield`까지 실행하고, `__exit__()`에서 멈춘 자리부터 나머지를 실행한다. 3장의 `yield`와 이 장의 데코레이터가 만나는 곳이다.

`timer()`는 `Timer`와 달리 객체가 없다. 그래서 잰 시간을 돌려줄 곳으로 딕셔너리를 `yield`했다. 블록이 끝난 뒤 `finally`가 그 딕셔너리에 시간을 적으므로, `with` 문 다음 줄에서 `t["elapsed"]`로 읽을 수 있다. 바깥에 아무것도 넘길 필요가 없다면 `yield`만 쓴다. 그러면 `as`로 받는 값은 `None`이다.

**`try`/`finally`가 꼭 필요하다.** 블록에서 예외가 나면, `contextmanager`는 그 예외를 제너레이터가 멈춰 있던 **`yield` 자리에서** 다시 일으킨다. `try`/`finally`가 없으면 `yield` 다음의 정리 코드는 실행되지 않는다. 직접 확인한다. `timer_cm.py`에 다음 함수를 더한다.

```python
@contextmanager
def timer_bad(label):
    start = time.perf_counter()
    yield
    print(f"[{label}] {time.perf_counter() - start:.2f}초")
```

`if __name__ == "__main__":` 아래 끝에 더해 실행한다.

```python
    print("--- try/finally가 없으면")
    with timer_bad("정상"):
        time.sleep(0.1)
    try:
        with timer_bad("실패"):
            raise TimeoutError("응답 없음")
    except TimeoutError:
        print("밖에서 잡음")
```

```
--- try/finally가 없으면
[정상] 0.10초
밖에서 잡음
```

예외가 난 `[실패]`의 시간은 출력되지 않았다. 시간이 출력되지 않는 정도면 다행이지만, 정리 코드가 "연결 닫기"나 "설정 되돌리기"라면 문제가 커진다. **`@contextmanager` 함수의 `yield`는 늘 `try`/`finally`로 감싼다.** 3.6.4의 `fake_event_stream()`에서 첫 `yield`부터 `try` 안에 둔 것과 같은 이유다.

> **예외를 처리하고 싶다면**
> `finally` 대신 `except`를 쓰면 블록에서 난 예외를 컨텍스트 관리자 안에서 잡을 수 있다. 잡은 뒤 다시 `raise`하지 않으면 4.6.3처럼 예외가 사라진다. 기록만 하고 올려보내려면 `except Exception: 기록; raise`로 쓴다.

### 4.6.5 임시 설정 바꾸기

컨텍스트 관리자가 자주 쓰이는 또 하나의 일은 "**블록 안에서만** 설정을 바꾸고, 나가면 원래대로 되돌리기"다. 테스트할 때 특히 많이 쓴다. 테스트 하나에서 바꾼 설정이 다음 테스트에 남아 있으면 안 되기 때문이다.

`ch04/temp_settings.py`

```python
"""임시 설정 변경 — 블록 안에서만 바꾸고, 나가면 되돌린다."""

import os
from contextlib import contextmanager

SETTINGS = {"model": "large", "temperature": 1.0, "max_tokens": 1024}


@contextmanager
def temporary(settings, **changes):
    """settings의 값을 changes로 잠시 바꾼다. 블록을 나가면 원래 값으로 되돌린다."""
    old = {key: settings[key] for key in changes}
    settings.update(changes)
    try:
        yield settings
    finally:
        settings.update(old)


@contextmanager
def temp_env(name, value):
    """환경 변수 name을 잠시 value로 바꾼다. 원래 없던 변수라면 나갈 때 지운다."""
    old = os.environ.get(name)
    os.environ[name] = value
    try:
        yield
    finally:
        if old is None:
            del os.environ[name]
        else:
            os.environ[name] = old


if __name__ == "__main__":
    with temporary(SETTINGS, model="small", temperature=0.0) as s:
        print("블록 안:", s)
    print("블록 밖:", SETTINGS)

    try:
        with temporary(SETTINGS, max_tokens=10):
            raise RuntimeError("테스트 중 실패")
    except RuntimeError:
        pass
    print("예외 뒤:", SETTINGS)

    print(os.environ.get("LLM_MODEL"))
    with temp_env("LLM_MODEL", "fake-model"):
        print(os.environ.get("LLM_MODEL"))
    print(os.environ.get("LLM_MODEL"))
```

```

```

```
블록 밖: {'model': 'large', 'temperature': 1.0, 'max_tokens': 1024}
예외 뒤: {'model': 'large', 'temperature': 1.0, 'max_tokens': 1024}
None
fake-model
None
```

- `temporary()` — 바꿀 키의 원래 값을 딕셔너리 컴프리헨션으로 저장해 두고(2.2.1), `update()`로 바꾼 뒤 `yield`한다. 블록이 예외로 끝나도 `finally`에서 되돌린다. `**changes`로 받았으므로 `temporary(SETTINGS, model="small")`처럼 키워드 인자로 바꿀 값을 넘긴다.
- 원래 값을 저장하는 줄이 `try` **밖에** 있다. `temporary(SETTINGS, modle="small")`처럼 없는 키를 넘기면 그 줄에서 `KeyError`가 나고, 아무것도 바꾸지 않은 채 끝난다. 바꾸기 전에 실패하는 것이므로 되돌릴 것도 없다.
- `temp_env()` — 환경 변수(기초 과정 8.2.1)는 원래 없었을 수 있다. 그때는 되돌린다는 것이 "지운다"는 뜻이다. "원래 없었음"과 "원래 값이 있었음"을 구별해야 하는 것이 `temporary()`보다 까다로운 점이다.

API 키나 모델 이름을 환경 변수에서 읽는 코드를 테스트할 때, 진짜 환경 변수를 건드리지 않고 블록 안에서만 가짜 값을 넣는 데 `temp_env()` 같은 것을 쓴다. 6장의 pytest에는 이 일을 대신 해 주는 `monkeypatch` 픽스처가 있다. 내부에서 하는 일은 이 절의 코드와 같다. 표준 라이브러리에도 작업 폴더를 잠시 바꾸는 `contextlib.chdir()`(3.11에 추가)가 있다.

### 4.6.6 가짜 스트림을 `with`로 — 3장의 숙제

3.6.5에서 스트림을 `break`로 멈춘 뒤 `stream.close()`를 불러 연결을 정리했다. 그리고 `close()`를 잊을 걱정이 없도록 실제 SDK는 스트림을 `with` 문으로 쓰게 한다고 했다. 같은 모양을 만든다. 3장의 `stream_events.py`에서 두 함수를 가져와 `ch04/stream_ctx.py`를 만든다.

```python
"""3장의 가짜 스트림을 with 문으로 쓰기."""

import time
from contextlib import contextmanager


def fake_event_stream(text, piece_size=4, delay=0.03):
    """시작, 텍스트 조각들, 끝 이벤트를 차례로 내놓는다. (3.6.4)"""
    try:
        yield {"type": "message_start", "model": "small-model"}
        for start in range(0, len(text), piece_size):
            time.sleep(delay)
            yield {"type": "text_delta", "text": text[start : start + piece_size]}
        yield {"type": "message_stop", "stop_reason": "end_turn"}
    finally:
        print(" [연결 정리]")


def text_only(events):
    """이벤트 중 텍스트 조각의 글자만 내놓는다. (3.6.4)"""
    for event in events:
        match event:
            case {"type": "text_delta", "text": str(text)}:
                yield text


@contextmanager
def open_stream(text):
    """가짜 스트림을 열어 텍스트 조각의 이터레이터를 내준다. 블록을 나가면 반드시 닫는다."""
    events = fake_event_stream(text)
    try:
        yield text_only(events)
    finally:
        events.close()


if __name__ == "__main__":
    with open_stream("아주 긴 답이 이어지는데 사용자가 중지 버튼을 누른다.") as stream:
        received = []
        for text in stream:
            received.append(text)
            print(text, end="", flush=True)
            if len("".join(received)) >= 10:
                print(" ...(중지)", end="")
                break
    print("받은 것:", "".join(received))
```

```
받은 것: 아주 긴 답이 이어지는
```

3.6.5와 출력은 같다. 다른 점은 `stream.close()`를 **부르지 않았다**는 것이다. `break`로 `for` 문을 빠져나간 뒤 `with` 블록이 끝나면서 `open_stream()`의 `finally`가 `events.close()`를 불렀다. 블록 안에서 예외가 나도 마찬가지다.

- 바깥 `open_stream()` — `@contextmanager`로 만든 제너레이터. `with` 문의 앞뒤를 맡는다.
- 안쪽 `fake_event_stream()` — 3장의 제너레이터. 이벤트를 내놓는다.

제너레이터가 두 가지 역할로 쓰였다. 하나는 값을 하나씩 내놓는 이터레이터(3장)이고, 하나는 `yield`를 경계로 앞뒤를 나누는 컨텍스트 관리자(4장)다. 1.1.3 (가)의 다음 코드가 이제 끝까지 읽힌다.

```python
with client.messages.stream(...) as stream:   # 연결을 열고, 블록이 끝나면 반드시 닫는다 (4장)
    for text in stream.text_stream:           # 도착하는 대로 텍스트 조각을 하나씩 꺼낸다 (3장)
        print(text, end="", flush=True)
```

1.2.6에서 `httpx`의 `Client.stream()` 위에 붙어 있던 `@contextmanager`도 같은 일을 한다. 요청을 보내고 응답을 `yield`한 뒤, 블록이 끝나면 `finally`에서 응답을 닫는다.

### 4.6.7 컨텍스트 관리자를 데코레이터로 쓰기

`@contextmanager`로 만든 컨텍스트 관리자는 **데코레이터로도** 쓸 수 있다. 함수 전체를 `with` 블록으로 감싼 것과 같다. `timer_cm.py`에 더해 본다.

```python
@timer("일괄 처리")
def batch_job(n):
    time.sleep(0.1 * n)
    return n
```

```python

>>> batch_job(1)

1
>>> batch_job(2)
[일괄 처리] 0.20초

```

`batch_job()`을 부를 때마다 `with timer("일괄 처리"):` 안에서 함수 본문을 실행한 것과 같다. 4.2.5의 `timed` 데코레이터와 거의 같은 일을 하는데, 코드는 `timer()` 하나만 만들었다. "코드 블록의 앞뒤"와 "함수 호출의 앞뒤"가 같은 구조라서 가능한 일이다. 남의 코드에서 `@어떤_관리자(...)`를 데코레이터로 쓴 것을 보고, 같은 이름이 다른 곳에서 `with 어떤_관리자(...):`로 쓰인 것을 보더라도 놀라지 않으면 된다.

## 실습 4-7. 종합 — 믿을 만한 LLM 호출

이 장의 내용을 모두 써서 "실패해도 버티는 LLM 호출 함수"를 만든다. 가짜 LLM 클라이언트는 문서마다 정해 둔 순서대로 시간 초과, 요청 한도 초과, 서버 오류, 잘못된 요청을 일으킨 뒤에 답한다. 재시도 데코레이터로 다시 시도할 실패만 다시 시도하고, 캐시로 같은 문서를 두 번 요약하지 않고, 컨텍스트 관리자로 실패한 호출까지 시간을 잰다. 3장 실습 3-7처럼 **함수의 이름과 독스트링이 먼저 주어지고, 본문을 채운다.** 9장의 종합 실습 "문서 일괄 요약기"에서 이 코드를 비동기로 바꿔 다시 쓴다.

`ch04/reliable_llm.py`

```python
"""믿을 만한 LLM 호출 — 4장 종합 실습."""

import functools
import time
from contextlib import contextmanager


class APIError(Exception):
    """가짜 LLM API의 오류. status에 HTTP 상태 코드를 담는다."""

    def __init__(self, message, status=None):
        super().__init__(message)
        self.status = status


class APITimeoutError(APIError):
    """응답이 제한 시간 안에 오지 않았다."""


class RateLimitError(APIError):
    """요청 한도 초과(429). retry_after초 뒤에 다시 보내라는 뜻이다."""

    def __init__(self, message, retry_after=None):
        super().__init__(message, status=429)
        self.retry_after = retry_after


class ServerError(APIError):
    """서버 쪽 문제(500, 503, 529 등). 잠시 뒤에는 될 수 있다."""


class BadRequestError(APIError):
    """요청이 잘못되었다(400). 다시 보내도 같은 결과다."""


RETRYABLE = (APITimeoutError, RateLimitError, ServerError)


class FakeLLM:
    """프롬프트마다 정해 둔 오류를 차례로 일으킨 뒤에 답하는 가짜 LLM 클라이언트."""

    def __init__(self, script):
        self.script = {prompt: list(errors) for prompt, errors in script.items()}
        self.calls = 0

    def complete(self, prompt, *, model="small"):
        self.calls += 1
        errors = self.script.get(prompt, [])
        if errors:
            raise errors.pop(0)
        return f"[{model}] {prompt}의 요약"


def make_script():
    return {
        "문서 A": [],
        "문서 B": [APITimeoutError("응답 시간 초과")],
        "문서 C": [RateLimitError("요청 한도 초과", retry_after=5.0), ServerError("과부하", 529)],
        "문서 D": [BadRequestError("프롬프트가 너무 길다", 400)],
        "문서 E": [ServerError("내부 오류", 500) for _ in range(3)],
    }


def retry(times=3, delay=1.0, backoff=2.0, exceptions=RETRYABLE, sleep=time.sleep):
    """exceptions의 예외가 나면 times번까지 시도하는 데코레이터를 만든다.

    n번째 실패 뒤에는 delay * backoff ** (n - 1)초를 기다린다.
    예외에 retry_after 속성이 있고 None이 아니면 그 시간을 대신 기다린다.
    기다리기 전에 "  [재시도] n번째 실패(예외 이름: 메시지), m초 뒤 다시"를 출력한다.
    """


@contextmanager
def stopwatch(stats, key):
    """with 블록의 실행 시간을 stats[key] 리스트에 더한다. 블록에서 예외가 나도 더한다."""


def make_summarizer(client, *, model="small", sleep=time.sleep):
    """client로 문서를 요약하는 함수를 만들어 돌려준다.

    돌려주는 함수 summarize(doc)는
    - 실패하면 retry()의 규칙대로 다시 시도하고(sleep을 넘긴다),
    - 성공한 결과를 기억해 두었다가 같은 doc이 오면 API를 부르지 않고 돌려준다.
    """


def main():
    waits = []

    def fake_sleep(seconds):
        waits.append(seconds)

    client = FakeLLM(make_script())
    summarize = make_summarizer(client, sleep=fake_sleep)
    stats = {}

    for doc in ["문서 A", "문서 B", "문서 C", "문서 D", "문서 E", "문서 A"]:
        print(f"{doc}:")
        with stopwatch(stats, doc):
            try:
                print(f"  {summarize(doc)}")
            except APIError as e:
                print(f"  실패 — {type(e).__name__}({e.status}): {e}")

    print(f"API 호출 {client.calls}번, 기다린 시간 합계 {sum(waits):.1f}초")
    print(summarize.cache_info())
    print("시간을 잰 문서:", {doc: len(times) for doc, times in stats.items()})


if __name__ == "__main__":
    main()
```

- **예외 클래스** — 4.3.4의 표를 클래스로 옮긴 것이다. 모두 `APIError`를 물려받으므로 `except APIError`로 한꺼번에 잡을 수 있고, 다시 시도할 것만 `RETRYABLE`에 모았다. 실제 SDK의 예외 계층과 같은 구조다. `RateLimitError`는 서버가 알려 준 대기 시간 `retry_after`를 가진다.
- **`FakeLLM`** — 문서마다 일으킬 예외를 목록으로 받아, 부를 때마다 하나씩 꺼내 일으킨다(`pop(0)`). 목록이 비면 답한다. `calls`로 API를 부른 횟수를 센다. 무작위가 없으므로 누가 실행해도 결과가 같다.
- **`sleep` 매개변수** — `retry()`와 `make_summarizer()`는 기다리는 함수를 매개변수로 받는다. 실제로 쓸 때는 기본값 `time.sleep`으로 정말 기다리고, `main()`에서는 기다린 시간을 기록만 하는 `fake_sleep()`을 넘긴다. 그래서 "11초를 기다리는" 프로그램이 즉시 끝난다. 함수가 쓰는 것(여기서는 시계)을 바깥에서 넣어 주는 이 방법을 **의존성 주입**이라고 한다. 6장에서 테스트할 때 정식으로 다룬다.
- `main()`은 이미 채워져 있다. **고치지 않는다.** `main()`이 `summarize.cache_info()`를 부르는 것에 주의한다. `make_summarizer()`가 돌려주는 것은 무엇이어야 할까?

```
시간을 잰 문서: {'문서 A': 2, '문서 B': 1, '문서 C': 1, '문서 D': 1, '문서 E': 1}
```

**힌트**

- `retry()`는 4.3.2의 `retry()`와 거의 같다. 다른 점은 세 가지다. 기다리는 시간을 `wait *= backoff`로 누적하는 대신 `delay * backoff ** (attempt - 1)`로 계산한다. `retry_after`가 있으면 그것을 쓴다. `time.sleep()` 대신 매개변수 `sleep`을 부른다.
- `stopwatch()`는 대여섯 줄이면 된다. `stats.setdefault(key, [])`는 `key`가 없으면 빈 리스트를 넣고, 있든 없든 그 리스트를 돌려준다. 거기에 `append()`한다.
- `make_summarizer()` 안에서 `def summarize(doc):`를 정의하고 데코레이터 두 개를 붙인 뒤 돌려준다. `summarize`는 바깥의 `client`와 `model`을 쓰는 클로저다. 데코레이터에도 바깥의 `sleep`을 넘긴다. `@retry(sleep=sleep)`처럼 데코레이터의 인자로 바깥 함수의 변수를 쓸 수 있다.
- 두 데코레이터의 순서를 정할 때 `main()`이 `summarize.cache_info()`를 부른다는 것을 떠올린다. 바깥에 있는 데코레이터가 돌려준 것에 `summarize`라는 이름이 붙는다.

## 정리

| 항목 | 핵심 |
|---|---|
| 중첩 함수 | 함수 안의 `def`는 그 함수의 지역 이름. 부를 때마다 새 함수 객체가 만들어진다 |
| 함수를 돌려주는 함수 | `return 안쪽함수`(괄호 없이). 인자를 바꿔 부를 때마다 다른 함수가 나온다 |
| 클로저 | 바깥 함수의 변수를 셀(`__closure__`)로 붙들고 있는 함수. 바깥 함수가 끝나도 변수가 남는다. 값이 아니라 **변수**를 기억한다 |
| LEGB | 지역 → 감싸는 함수 → 전역 → 내장 순서로 이름을 찾는다 |
| `nonlocal` | 바깥 함수의 변수에 **다시 할당**할 때. 내용만 바꾸거나(`append`) 읽기만 하면 필요 없다 |
| 늦은 바인딩 | 반복문 안에서 만든 함수는 반복 변수의 **마지막 값**을 본다. 기본값 `x=x`, 함수를 만드는 함수, `partial`로 고친다 |
| 데코레이터 | 함수를 받아 함수(또는 다른 객체)를 돌려주는 함수. `@deco`는 `f = deco(f)`. **정의할 때** 실행된다 |
| 래퍼 | `*args, **kwargs`로 받아 그대로 넘기고, 결과를 `return`한다. 예외는 래퍼를 지나 올라간다 |
| `functools.wraps` | 래퍼에 원래 함수의 이름·독스트링을 복사하고 `__wrapped__`에 원래 함수를 둔다. 늘 붙인다 |
| 겹쳐 붙이기 | `f = 위(아래(f))`. 정의할 때는 아래부터, 부를 때는 위의 래퍼부터 |
| 인자를 받는 데코레이터 | 세 겹: 설정 → 데코레이터 → 래퍼. `@deco(x)`는 `f = deco(x)(f)`. 괄호를 빠뜨리면 조용히 망가진다 |
| 재시도 | 다시 보내면 결과가 달라질 수 있는 실패(시간 초과, 429, 5xx)만. 지수 백오프, 최대 대기, 지터, `Retry-After`. 마지막엔 `raise`. 멱등성 확인. SDK의 재시도와 겹치지 않게 |
| `cache`/`lru_cache` | 인자를 키로 결과를 기억. 인자는 해시 가능해야. 답에 영향을 주는 것은 모두 인자로. 돌려준 객체를 바꾸지 않는다. 예외는 기억하지 않는다 |
| `@classmethod` | 첫 인자가 클래스(`cls`). 대체 생성자 `from_dict()`. `cls(...)`로 만들어야 자식 클래스도 된다 |
| `@staticmethod` | `self`도 `cls`도 없는 메서드. 대개 모듈 함수로 둬도 된다 |
| `@property` | property 객체를 돌려준다. `@이름.setter`로 넣을 때 검사한다 |
| `@dataclass` | 클래스를 받아 메서드를 더한 **같은 클래스**를 돌려준다 |
| `__eq__`와 `__hash__` | `==`로 같으면 해시도 같아야 한다. `__eq__`만 정의하면 `__hash__`는 `None`. `frozen=True`면 해시도 만들어 주지만 필드가 모두 해시 가능해야 쓸 수 있다. `__hash__`는 `__eq__`가 비교하는 값으로만(같은 튜플이 가장 쉽다). 모르는 상대에게는 `NotImplemented` |
| 등록 데코레이터 | 함수를 딕셔너리(또는 객체의 속성)에 넣고 그대로 돌려준다. `@app.get`, `@mcp.tool()`. `import`해야 등록된다. 맨 위에 붙인다 |
| 바꿔 돌려주는 데코레이터 | 함수를 다른 객체로 바꾼다. LangChain `@tool`은 도구 객체(`.invoke()`)를 돌려준다 |
| `with` 문 | `__enter__()`의 반환값이 `as` 뒤에. `__exit__()`는 반드시 불린다. 참을 돌려주면 예외가 사라진다 |
| `@contextmanager` | `yield` 앞이 들어갈 때, 뒤가 나갈 때. `yield`는 늘 `try`/`finally`로 감싼다. 데코레이터로도 쓸 수 있다 |
