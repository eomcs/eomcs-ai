# 7장. 비동기(asyncio)

[파이썬 중급](README.md) 과정의 일곱 번째 장이다. LLM API 호출 한 번에는 몇 초가 걸린다. 그동안 우리 프로그램은 **아무 일도 하지 않고 기다린다.** 질문 스무 개를 차례로 보내면 기다리는 시간이 스무 번 쌓인다. 그런데 첫 번째 답을 기다리는 동안 두 번째, 세 번째 질문을 미리 보내 두면 기다리는 시간이 **겹친다.** 이렇게 기다리는 동안 다른 일을 하도록 짜는 방법이 **비동기**(asynchronous) 프로그래밍이고, 파이썬에서는 `async`/`await` 문법과 표준 라이브러리 **asyncio**로 한다. 1장 1.1.3 (라)의 `summarize_all()`, (나)의 FastAPI `async def chat()`이 이 장의 코드다.

- **왜 비동기인가** — 입출력을 기다리는 시간이 무엇인지 보고, 0.5초 걸리는 가짜 LLM 호출 스무 개를 차례로 할 때와 동시에 할 때를 비교한다. 동시성과 병렬성을 구별하고, CPU를 쓰는 작업은 asyncio로 빨라지지 않는다는 것을 스레드·프로세스와 비교해 확인한다.
- **코루틴과 이벤트 루프** — `async def`로 만든 함수를 부르면 무엇이 돌아오는지, `await`가 무엇을 하는지, `asyncio.run()`이 시작하는 이벤트 루프가 무엇인지 익힌다. `await`를 빠뜨렸을 때의 증상과, `time.sleep()`이 비동기 코드 전체를 멈추는 이유를 본다.
- **동시에 실행하기** — 태스크를 만들어 동시에 실행하고, `asyncio.gather()`와 `asyncio.TaskGroup`으로 여러 작업의 결과를 모은다. 그중 하나가 실패했을 때 두 도구가 어떻게 다르게 동작하는지, `ExceptionGroup`과 `except*`를 어떻게 읽는지 익힌다.
- **시간 제한과 동시 실행 수 제한** — `asyncio.timeout()`으로 오래 걸리는 작업을 포기하고, `asyncio.Semaphore`로 한 번에 보내는 요청 수를 제한한다. 취소가 어떻게 전달되는지 보고, 4장·6장의 재시도 데코레이터를 비동기 함수용으로 바꾼다.
- **비동기 반복과 컨텍스트 관리자** — 3장의 가짜 스트림을 비동기 제너레이터로 바꿔 `async for`로 읽고, 4장의 `open_stream()`을 `async with`로 쓰는 비동기 컨텍스트 관리자로 만든다.
- **비동기 HTTP 요청** — `httpx.AsyncClient`로 여러 요청을 동시에 보내고, `requests`로 차례로 보낼 때와 시간을 비교한다. 비동기 코드 안에 블로킹 코드를 섞으면 무슨 일이 생기는지 보고, `asyncio.to_thread()`로 피한다.
- **비동기 코드 테스트와 읽기** — `pytest-asyncio`로 비동기 함수를 테스트하고, 가짜 `sleep`과 `httpx.MockTransport`로 기다리지 않고 네트워크 없이 테스트한다. FastAPI의 `async def` 엔드포인트와 LLM SDK의 비동기 클라이언트 코드를 읽는다.

## 7.1 왜 비동기인가

### 7.1.1 기다리는 시간

LLM에게 질문을 보내고 답을 받기까지 무슨 일이 일어나는지 생각해 보자.

1. 우리 프로그램이 요청을 만들어 네트워크로 보낸다. 몇 밀리초(ms)면 된다.
2. 요청이 인터넷을 건너 LLM 서버에 도착한다.
3. 서버가 모델을 돌려 답을 만든다. **몇 초**가 걸린다.
4. 답이 인터넷을 건너 돌아온다.
5. 우리 프로그램이 답을 받아 처리한다. 몇 밀리초면 된다.

우리 프로그램의 CPU가 일하는 시간은 1번과 5번뿐이다. 2~4번 동안에는 **바깥 세계가 일하고, 우리는 기다린다.** 파일을 읽을 때 디스크를, 데이터베이스에 질의할 때 데이터베이스 서버를 기다리는 것도 같다. 이렇게 프로그램 바깥과 데이터를 주고받는 일을 **입출력**(input/output, I/O)이라고 하고, 그 결과를 기다리는 것을 **입출력 대기**라고 한다.

기초 과정부터 써 온 코드는 모두 한 번에 한 가지씩 차례로 실행했다. `requests.get()`을 부르면 답이 올 때까지 그 줄에서 멈춰 있다가, 답이 오면 다음 줄로 간다. 이렇게 **끝날 때까지 다음으로 넘어가지 못하게 붙잡아 두는** 호출을 **블로킹**(blocking) 호출이라고 한다. 블로킹 호출 스무 개를 차례로 하면 기다리는 시간이 고스란히 스무 번 더해진다.

식당으로 비유하면 이렇다. 손님 스무 명의 주문을 받는 점원이 한 명 있다. 첫 손님의 주문을 주방에 넣고, **음식이 나올 때까지 주방 앞에 서서 기다렸다가** 음식을 내준 뒤에야 두 번째 손님의 주문을 받는다. 점원은 대부분의 시간을 서 있기만 한다. 실제 점원은 그러지 않는다. 주문을 주방에 넣고 바로 다음 손님에게 가고, 음식이 나왔다는 종이 울리면 그때 가서 내준다. 비동기 프로그래밍이 바로 이것이다.

### 7.1.2 차례로 할 때와 동시에 할 때

0.5초 걸리는 가짜 LLM 호출 스무 개를 두 방법으로 해 본다. 아직 배우지 않은 문법이 섞여 있다. 이 절에서는 **결과의 차이**만 보고, 문법은 7.2와 7.3에서 하나씩 배운다.

`ch07/why_async.py`

```python
"""LLM 호출 20개를 차례로 할 때와 동시에 할 때 — 7장의 첫 비교."""

import asyncio
import time

QUESTIONS = [f"질문 {n}" for n in range(1, 21)]


def ask_sync(question: str) -> str:
    """0.5초 걸리는 가짜 LLM 호출. 기다리는 동안 아무것도 하지 않는다."""
    time.sleep(0.5)
    return f"{question}의 답"


async def ask_async(question: str) -> str:
    """0.5초 걸리는 가짜 LLM 호출. 기다리는 동안 다른 일에 자리를 내준다."""
    await asyncio.sleep(0.5)
    return f"{question}의 답"


async def ask_all(questions: list[str]) -> list[str]:
    return await asyncio.gather(*[ask_async(q) for q in questions])


if __name__ == "__main__":
    start = time.perf_counter()
    answers = [ask_sync(q) for q in QUESTIONS]
    print(f"차례로: {len(answers)}개, {time.perf_counter() - start:.2f}초")

    start = time.perf_counter()
    answers = asyncio.run(ask_all(QUESTIONS))
    print(f"동시에: {len(answers)}개, {time.perf_counter() - start:.2f}초")
    print(answers[:3])
```

```
python ch07/why_async.py
```

```
차례로: 20개, 10.07초
동시에: 20개, 0.50초
['질문 1의 답', '질문 2의 답', '질문 3의 답']
```

같은 일을 했는데 10초와 0.5초다. 차이를 만든 것은 세 군데다.

- `ask_sync()`는 `time.sleep(0.5)`로, `ask_async()`는 `await asyncio.sleep(0.5)`로 기다린다. 앞의 것은 "0.5초 동안 아무것도 하지 마라", 뒤의 것은 "0.5초 뒤에 깨워 주고, 그동안 다른 일을 해라"다. 실제 LLM 호출이라면 `time.sleep()` 자리에 `requests.post()`가, `asyncio.sleep()` 자리에 `await http.post()`가 들어간다.
- `async def`로 만든 함수는 `await`할 수 있는 함수다(7.2).
- `asyncio.gather(*[...])`는 스무 개를 **한꺼번에 시작시키고** 모두 끝나기를 기다린다(7.3). 1장 (라)의 `asyncio.gather(*tasks)`가 이것이다.

스무 개가 모두 0.5초씩 기다렸지만, 기다리는 시간이 **겹쳤으므로** 전체는 0.5초다. 비동기는 일을 빨리 하게 만드는 것이 아니라, **기다리는 시간을 겹치게** 만드는 것이다. 그러니 비동기로 줄일 수 있는 시간은 기다리는 시간뿐이다.

1장에서 "몇 초씩 걸리는 호출 스무 개를 차례로 하면 1분이 넘지만, 동시에 하면 몇 초면 된다"고 한 것이 이것이다. 실제 LLM 호출은 0.5초가 아니라 수 초이므로 차이가 더 크다. 문서 백 개를 요약하는 일이라면 몇 분과 몇 초의 차이다.

### 7.1.3 동시성과 병렬성

`asyncio.gather()`가 스무 개를 "동시에" 실행했다고 했다. 그런데 이 프로그램은 CPU 코어 하나에서, 한 번에 한 줄씩만 실행된다. 정확히 말하면 다음과 같다.

- **동시성**(concurrency) — 여러 일을 **번갈아** 진행해서, 한 일이 끝나기 전에 다른 일이 시작되는 것. 점원 한 명이 여러 손님의 주문을 번갈아 처리하는 것이다. 어느 한 순간에 점원이 하는 일은 하나지만, 손님 스무 명의 주문이 모두 "진행 중"이다.
- **병렬성**(parallelism) — 여러 일을 **정말로 같은 순간에** 실행하는 것. 점원 네 명이 각자 한 손님씩 맡는 것이다. CPU 코어가 여러 개 있어야 한다.

asyncio는 **동시성**을 준다. 스레드 하나에서 여러 작업을 번갈아 실행한다. 한 작업이 `await`로 기다리기 시작하면 그 자리에서 멈추고, 그동안 다른 작업을 실행한다. 기다리던 것이 준비되면 멈춘 자리에서 이어서 실행한다. LLM 호출처럼 **대부분의 시간을 기다리는** 일에는 이것으로 충분하다. 점원 한 명으로 손님 스무 명을 감당할 수 있는 것은, 점원이 하는 일(주문 받기, 음식 내주기)보다 주방에서 기다리는 시간이 훨씬 길기 때문이다.

### 7.1.4 CPU를 쓰는 작업은 빨라지지 않는다

반대로 **CPU가 계속 일해야 하는** 작업이라면 어떨까? 점원이 직접 요리를 해야 한다면, 손님을 번갈아 받아도 요리하는 시간은 줄지 않는다. 소수(prime number)를 일부러 느린 방법으로 세는 함수로 확인한다.

`ch07/cpu_bound.py`

```python
"""CPU를 쓰는 작업은 asyncio로 빨라지지 않는다."""

import asyncio
import time
from concurrent.futures import ProcessPoolExecutor, ThreadPoolExecutor


def count_primes(limit: int) -> int:
    """limit 미만의 소수 개수를 일부러 느린 방법으로 센다."""
    count = 0
    for n in range(2, limit):
        if all(n % d for d in range(2, int(n**0.5) + 1)):
            count += 1
    return count


async def count_primes_async(limit: int) -> int:
    return count_primes(limit)  # await할 곳이 없다


async def main_async(limits: list[int]) -> list[int]:
    return await asyncio.gather(*[count_primes_async(n) for n in limits])


if __name__ == "__main__":
    limits = [300_000] * 4

    start = time.perf_counter()
    print([count_primes(n) for n in limits], end=" ")
    print(f"차례로 {time.perf_counter() - start:.2f}초")

    start = time.perf_counter()
    print(asyncio.run(main_async(limits)), end=" ")
    print(f"asyncio {time.perf_counter() - start:.2f}초")

    start = time.perf_counter()
    with ThreadPoolExecutor() as threads:
        print(list(threads.map(count_primes, limits)), end=" ")
    print(f"스레드 {time.perf_counter() - start:.2f}초")

    start = time.perf_counter()
    with ProcessPoolExecutor() as processes:
        print(list(processes.map(count_primes, limits)), end=" ")
    print(f"프로세스 {time.perf_counter() - start:.2f}초")
```

```

[25997, 25997, 25997, 25997] asyncio 1.56초
[25997, 25997, 25997, 25997] 스레드 1.53초
[25997, 25997, 25997, 25997] 프로세스 0.47초
```

시간은 컴퓨터에 따라 크게 다르다. 비교할 것은 네 줄 사이의 **비율**이다.

- **asyncio** — 빨라지지 않았다. `count_primes_async()` 안에는 `await`가 없다. 기다리는 일이 없으니 자리를 내줄 틈도 없다. 하나가 끝나야 다음 것이 시작된다.
- **스레드**(`ThreadPoolExecutor`) — 운영체제가 여러 실행 흐름(스레드)을 번갈아 실행해 준다. 그런데 이것도 빨라지지 않았다. 파이썬(CPython)에는 **GIL**(Global Interpreter Lock)이라는 장치가 있어서, 한 프로세스 안에서는 한 번에 한 스레드만 파이썬 코드를 실행한다. 스레드를 여러 개 만들어도 파이썬 계산은 차례로 한다. 다만 스레드가 **입출력을 기다리는 동안**에는 GIL을 내려놓으므로, 입출력 대기가 많은 일에는 스레드도 효과가 있다(7.6.5).
- **프로세스**(`ProcessPoolExecutor`) — 파이썬 프로그램 자체를 여러 개 띄워 각자 한 일씩 맡긴다. 프로세스마다 GIL이 따로 있으므로 CPU 코어 여러 개가 정말로 동시에 계산한다. 이것이 **병렬성**이다. 대신 프로세스를 띄우고, 데이터를 주고받는 비용이 든다.

`concurrent.futures`의 두 도구는 모양이 같다. `with` 문으로 만들고, `map(함수, 이터러블)`로 일을 나눠 맡긴다. 결과는 넘긴 순서대로 나온다. 이 과정에서는 스레드와 프로세스를 깊이 다루지 않는다. 언제 무엇을 쓰는지만 알아 둔다.

| | asyncio | 스레드 | 프로세스 |
|---|---|---|---|
| 얻는 것 | 동시성 | 동시성 | 병렬성 |
| 잘 맞는 일 | 입출력 대기가 많은 일. 특히 **아주 많은** 동시 연결(API 호출 수백 개, 웹 서버) | 입출력 대기가 있는데 쓰는 라이브러리가 `async`를 지원하지 않을 때 | CPU를 쓰는 계산(큰 데이터 변환, 이미지 처리) |
| 전환 시점 | 코드에 적힌 `await`에서만 | 운영체제가 아무 때나 | 서로 독립 |
| 주의할 것 | 블로킹 코드를 섞으면 전체가 멈춘다 | 여러 스레드가 같은 데이터를 고치면 꼬인다 | 시작 비용, 데이터를 주고받는 비용 |
| 이 과정에서 | 이 장 | 7.6.5의 `asyncio.to_thread()` | 쓰지 않는다 |

LLM 서비스의 일은 대부분 첫 번째 열이다. 요청을 보내고 기다리고, 데이터베이스를 기다리고, 다른 API를 기다린다. 그래서 LLM SDK와 FastAPI 같은 웹 프레임워크가 비동기를 기본으로 지원한다. 반면 임베딩 모델을 **내 컴퓨터에서** 돌리거나 PDF 수천 개를 파싱하는 일은 CPU를 쓰는 일이다. asyncio로 감싸도 빨라지지 않는다.

> **GIL 없는 파이썬**
> 파이썬 3.13부터 GIL을 끈 "자유 스레드"(free-threaded) 빌드가 따로 배포된다. 이 빌드에서는 스레드도 CPU 코어 여러 개를 동시에 쓸 수 있다. 아직은 일반 빌드가 기본이고 라이브러리 지원이 갖춰지는 중이다. 이 과정의 설명은 일반 빌드를 기준으로 한다. 어느 쪽이든 **입출력 대기에는 asyncio**라는 결론은 같다.

## 7.2 코루틴과 이벤트 루프

### 7.2.1 `async def` — 부르면 코루틴 객체가 나온다

함수 정의 앞에 `async`를 붙이면 **코루틴 함수**(coroutine function)가 된다. 대화형 셸에서 확인한다.

```python
>>> import asyncio
>>> async def greet(name):
...     await asyncio.sleep(1)
...     return f"안녕, {name}"
...
>>> greet("파이썬")
<coroutine object greet at 0x104f2a3e0>
```

함수를 불렀는데 1초를 기다리지도 않았고, `"안녕, 파이썬"`도 돌아오지 않았다. 대신 **코루틴 객체**(coroutine object)가 돌아왔다. 3장에서 제너레이터 함수를 불렀을 때와 같다(3.2.1). 제너레이터 함수를 부르면 본문을 실행하지 않고 제너레이터 객체를 돌려주었다. 코루틴 함수도 부르면 본문을 실행하지 않고, **"이 본문을 실행할 준비가 된 객체"**를 돌려준다. 본문은 누군가 이 객체를 실행해 줄 때 실행된다.

```python
>>> coro = greet("파이썬")
>>> type(coro)
<class 'coroutine'>
>>> asyncio.run(coro)
'안녕, 파이썬'
```

`asyncio.run()`에 코루틴 객체를 넘기면 그제야 본문이 실행된다. 1초를 기다린 뒤 결과가 나온다. 코루틴(coroutine)은 "함께(co) 도는 루틴(routine)"이라는 뜻이다. 실행 도중에 **멈췄다가 이어서 실행할 수 있는** 함수라서, 여러 코루틴이 번갈아 가며 함께 돈다.

> **`<sys>:0: RuntimeWarning: coroutine 'greet' was never awaited`**
> 대화형 셸에서 `greet("파이썬")`만 입력하고 넘어가면, 나중에 셸을 끝낼 때나 그 객체가 정리될 때 이런 경고가 나올 수 있다. "코루틴 객체를 만들고 한 번도 실행하지 않았다"는 뜻이다. 7.2.4에서 이 경고가 무엇을 알려 주는지 자세히 본다.

### 7.2.2 `await` — 기다리는 동안 자리를 내준다

`await`는 코루틴 함수 **안에서만** 쓸 수 있다. `await 코루틴`은 다음과 같은 뜻이다.

> 이 코루틴을 실행해서 결과가 나올 때까지 기다린다. **기다리는 동안 나는 여기서 멈추고, 다른 코루틴이 실행되게 자리를 내준다.** 결과가 나오면 여기서부터 이어서 실행한다.

`await` 뒤에 올 수 있는 것을 **어웨이터블**(awaitable)이라고 한다. 코루틴 객체, 7.3의 태스크, 그리고 라이브러리가 만드는 몇 가지 객체다. `asyncio.sleep(1)`도 코루틴 객체를 돌려주므로 `await asyncio.sleep(1)`이라고 쓴다.

코루틴 함수 두 개를 차례로 `await`하는 프로그램을 만든다.

`ch07/coroutine_basics.py`

```python
"""코루틴 함수, 코루틴 객체, 이벤트 루프."""

import asyncio
import time


async def greet(name: str, seconds: float) -> str:
    print(f"{name}: 시작")
    await asyncio.sleep(seconds)
    print(f"{name}: 끝")
    return f"안녕, {name}"


async def main() -> None:
    start = time.perf_counter()
    first = await greet("하나", 1.0)
    second = await greet("둘", 1.0)
    print(first, second, f"{time.perf_counter() - start:.2f}초")


if __name__ == "__main__":
    asyncio.run(main())
```

```
python ch07/coroutine_basics.py
```

```
하나: 시작
하나: 끝
둘: 시작
둘: 끝
안녕, 하나 안녕, 둘 2.00초
```

2초가 걸렸다. `await greet("하나", 1.0)`는 "하나"가 **끝날 때까지** `main()`을 멈춰 둔다. "하나"가 끝나야 다음 줄의 "둘"이 시작된다. `await`를 썼다고 저절로 동시에 실행되는 것은 아니다. `await`는 "기다리는 동안 **다른 코루틴에게** 자리를 내준다"는 뜻인데, 이 프로그램에는 자리를 내줄 다른 코루틴이 없다. 동시에 실행하려면 기다리기 **전에** 여러 코루틴을 출발시켜 두어야 한다. 7.3에서 한다.

타입 힌트는 일반 함수와 똑같이 쓴다. `async def greet(...) -> str`의 `-> str`은 "`await`했을 때 나오는 값"의 타입이다. `greet()`를 부른 결과 자체는 코루틴 객체이고, mypy는 그것을 `Coroutine[Any, Any, str]`로 본다. 5.3.4에서 제너레이터 함수의 반환 타입에 `Iterator[int]`를 적은 것과 달리, 코루틴 함수에는 **`await`해서 나오는 값의 타입**을 적는다.

### 7.2.3 `asyncio.run()`과 이벤트 루프

`await`가 자리를 내주면, 그 자리를 누가 받아서 다음에 실행할 코루틴을 고를까? **이벤트 루프**(event loop)다. 이벤트 루프는 asyncio의 심장으로, 대략 다음 일을 되풀이하는 반복문이다.

```
while 할 일이 남아 있다:
    지금 실행할 수 있는 코루틴을 하나 꺼낸다
    그 코루틴을 다음 await까지 실행한다          ← 이 동안 다른 코루틴은 실행되지 않는다
    그 코루틴이 무엇을 기다리는지 적어 둔다(타이머, 네트워크 응답 등)
    기다리던 것이 준비된 코루틴들을 "실행할 수 있음"으로 옮긴다
```

식당의 점원이 이벤트 루프이고, 코루틴이 손님의 주문이다. 점원은 주문 하나를 처리하다가 "주방에서 기다려야 함"(`await`)이 되면 그 주문을 적어 두고 다음 주문으로 간다. 종이 울리면(기다리던 것이 준비되면) 그 주문을 다시 이어서 처리한다.

`asyncio.run(코루틴)`은 다음 일을 한다.

1. 새 이벤트 루프를 만든다.
2. 넘겨받은 코루틴을 실행하고, 끝날 때까지 루프를 돌린다.
3. 끝나면 남아 있는 작업을 정리하고 루프를 닫는다.
4. 코루틴의 결과를 돌려준다. 코루틴이 예외를 냈다면 그 예외를 일으킨다.

그래서 비동기 프로그램은 대개 이런 모양이다.

```python
async def main() -> None:
    ...  # 여기서부터는 await를 쓸 수 있다


if __name__ == "__main__":
    asyncio.run(main())
```

**`asyncio.run()`은 프로그램의 입구에서 한 번만** 부른다. 일반 함수 세계에서 비동기 세계로 들어가는 문이다. 일단 `main()` 안으로 들어가면 그 안에서는 `await`로 다른 코루틴을 부른다. 코루틴 안에서 `asyncio.run()`을 또 부르면 오류가 난다.

```
RuntimeError: asyncio.run() cannot be called from a running event loop
```

"이벤트 루프가 이미 돌고 있는데 새 루프를 또 만들 수는 없다"는 뜻이다. 비동기 함수 안에서 다른 비동기 함수를 부를 때는 `asyncio.run()`이 아니라 `await`를 쓴다.

> **코루틴은 제너레이터의 친척이다**
> 코루틴 객체도 3장의 제너레이터처럼 멈췄다가 이어서 실행된다. 실제로 둘은 같은 장치 위에 만들어졌다. 코루틴 객체의 `send(None)`을 직접 불러 보면 제너레이터의 `next()`처럼 다음 멈출 곳까지 실행되고, 끝나면 3.2.3에서 본 `StopIteration`이 일어나며 반환값이 그 안에 들어 있다.
> ```python
> >>> async def answer():
> ...     return 42
> ...
> >>> coro = answer()
> >>> coro.send(None)
> Traceback (most recent call last):
>   ...
> StopIteration: 42
> ```
> 이벤트 루프는 이런 일을 대신해 주는 프로그램이다. 3.4.4에서 "`yield from`은 파이썬에 `async`/`await`가 생기기 전에 비동기 프로그래밍을 하던 방법이었다"고 한 것이 이 관계다. 우리가 `send()`를 직접 부를 일은 없다.

### 7.2.4 `await`를 빠뜨리면

비동기 코드를 처음 쓸 때 가장 흔한 실수는 `await`를 빠뜨리는 것이다. 무슨 일이 생기는지 일부러 해 본다.

`ch07/missing_await.py`

```python
"""await를 빠뜨린 코드. 확인한 뒤 지운다."""

import asyncio


async def fetch_answer(question: str) -> str:
    await asyncio.sleep(0.1)
    return f"{question}의 답"


async def main() -> None:
    answer = fetch_answer("첫 질문")
    print(answer)
    fetch_answer("두 번째 질문")
    print(len(answer))


asyncio.run(main())
```

실행하기 전에 무엇이 출력될지 예측해 본다.


3. **`RuntimeWarning: coroutine '...' was never awaited`** — 결과를 쓰지 않은 14번 줄은 아무 일도 하지 않았다. 질문을 보내지도 않았다. 파이썬은 실행되지 못한 코루틴 객체가 버려질 때 이 경고를 낸다. 경고가 가리키는 줄이 `await`를 빠뜨린 곳이다. 첫 줄의 경고는 14번 줄의 코루틴이, 마지막 줄의 경고는 `answer`에 담겼던 코루틴이 버려질 때 나왔다.

### 7.2.5 `asyncio.sleep()`과 `time.sleep()`

실습 7-1의 1번에서 `ask_async()`의 `await asyncio.sleep(0.5)`를 `time.sleep(0.5)`로 바꿨다면 "동시에"가 10초 걸렸을 것이다. 두 함수의 차이를 시간과 함께 출력해 본다. 아직 배우지 않은 `asyncio.gather()`는 "넘긴 코루틴들을 함께 출발시키고 모두 끝나기를 기다린다"로만 읽는다.

`ch07/blocking_sleep.py`

```python
"""asyncio.sleep()과 time.sleep()의 차이. 확인한 뒤 지운다."""

import asyncio
import time

START = time.perf_counter()


def log(message: str) -> None:
    print(f"{time.perf_counter() - START:4.1f}초  {message}")


async def polite(name: str) -> None:
    for step in range(1, 4):
        await asyncio.sleep(0.5)
        log(f"{name} {step}")


async def rude(name: str) -> None:
    for step in range(1, 4):
        time.sleep(0.5)
        log(f"{name} {step}")


async def main() -> None:
    log("--- asyncio.sleep() 둘")
    await asyncio.gather(polite("가"), polite("나"))
    log("--- time.sleep() 하나와 asyncio.sleep() 하나")
    await asyncio.gather(rude("다"), polite("라"))


asyncio.run(main())
```

- 뒷부분 — "다"가 1.5초 동안 세 단계를 **혼자** 다 했고, 그동안 "라"는 시작도 못 했다. "다"가 끝난 3.0초에야 "라"가 첫 `asyncio.sleep()`을 시작했다. 둘이 합쳐 3.0초다.

`time.sleep(0.5)`는 0.5초 동안 **스레드 전체를 재운다.** 이벤트 루프도 같은 스레드에서 돌고 있으므로 루프까지 잠든다. 루프가 잠들어 있으니 다른 코루틴으로 넘어갈 수 없다. "다"의 코루틴은 반복문을 세 번 도는 동안 `await`를 한 번도 만나지 않았으므로 자리를 내줄 기회도 없었다. 7.1.3의 표에서 asyncio의 전환 시점이 "코드에 적힌 `await`에서만"이라고 한 것이 이 뜻이다.

> **asyncio의 규칙: 루프를 붙잡지 않는다**
> 이벤트 루프는 하나의 스레드에서 모든 코루틴을 번갈아 실행한다. 어느 한 코루틴이 `await` 없이 오래 실행되면 **모든** 코루틴이 그동안 멈춘다. 웹 서버라면 사용자 한 명의 요청 때문에 모든 사용자가 기다린다. 그래서 비동기 코드 안에서는 블로킹 호출(`time.sleep()`, `requests.get()`, 큰 파일을 한꺼번에 읽기 등)을 쓰지 않는다. 피할 수 없을 때의 방법은 7.6.5에서 다룬다.

### 7.2.6 대화형 셸과 Jupyter에서 `await`

`await`는 코루틴 함수 안에서만 쓸 수 있다고 했다. 그런데 일반 대화형 셸에서는 코루틴 함수 밖이므로 `await`를 쓸 수 없다. 짧은 실험을 할 때마다 `asyncio.run()`을 쓰기는 번거롭다. 파이썬에는 **asyncio 대화형 셸**이 따로 있다.

```
python -m asyncio
```

```
asyncio REPL 3.13.2 (main, ...) on darwin
Use "await" directly instead of "asyncio.run()".
Type "help", "copyright", "credits" or "license" for more information.
>>> import asyncio
>>> await asyncio.sleep(1)
>>> async def greet(name):
...     await asyncio.sleep(1)
...     return f"안녕, {name}"
...
>>> await greet("파이썬")
'안녕, 파이썬'
```

안내문 그대로, `asyncio.run()` 대신 `await`를 바로 쓴다. 이 셸은 **이벤트 루프가 이미 돌고 있는 상태**로 시작한다. 그래서 맨 바깥에서 `await`를 쓸 수 있다. 같은 이유로 여기서 `asyncio.run()`을 부르면 7.2.3의 `RuntimeError`가 난다.

**Jupyter 노트북**도 같다. Jupyter의 셀은 이미 돌고 있는 이벤트 루프 안에서 실행되므로, 셀에 `await greet("파이썬")`을 바로 쓸 수 있다. 인터넷에서 찾은 노트북 예제가 `asyncio.run()` 없이 `await`를 바로 쓰는 이유다. 반대로 그 코드를 `.py` 파일로 옮기면 `SyntaxError: 'await' outside function`이 난다. 파일에서는 `async def main()`으로 감싸고 `asyncio.run(main())`으로 실행해야 한다. 거꾸로 `.py` 파일의 `asyncio.run(main())`을 노트북 셀에 붙여 넣으면 `RuntimeError`가 나므로, 노트북에서는 `await main()`이라고 쓴다.

| 실행하는 곳 | 이벤트 루프 | 맨 바깥에서 쓰는 것 |
|---|---|---|
| `.py` 파일 (`python 파일.py`) | 없다. `asyncio.run()`이 만든다 | `asyncio.run(main())` |
| 일반 대화형 셸 (`python`) | 없다 | `asyncio.run(...)` |
| asyncio 대화형 셸 (`python -m asyncio`) | 이미 돌고 있다 | `await ...` |
| Jupyter 노트북 | 이미 돌고 있다 | `await ...` |

## 7.3 동시에 실행하기

### 7.3.1 시간을 찍어 주는 작은 모듈

이 절부터는 "몇 초에 무엇이 일어났는가"를 자주 출력한다. 7.2.5의 `log()`를 여러 파일에서 함께 쓰도록 모듈로 만든다.

`ch07/timeline.py`

```python
"""시작한 뒤 몇 초가 지났는지 붙여서 출력한다 — 7장 예제가 함께 쓴다."""

import time

_start = time.perf_counter()


def reset() -> None:
    """시계를 0초로 되돌린다."""
    global _start
    _start = time.perf_counter()


def log(message: str) -> None:
    print(f"{time.perf_counter() - _start:4.1f}초  {message}")
```

- `_start` — 모듈을 처음 `import`한 시각이다. 이름 앞의 `_`는 "이 모듈 안에서만 쓰는 이름"이라는 관례다.
- `reset()` — 한 파일 안에서 실험을 여러 번 할 때, 실험마다 0초부터 다시 센다. 모듈 수준의 변수에 다시 할당하므로 `global`이 필요하다(기초 과정 4.3.4).

### 7.3.2 태스크 — 기다리기 전에 출발시킨다

7.2.2에서 `await`를 차례로 쓰면 차례로 실행된다는 것을 보았다. 코루틴 객체는 `await`하기 전에는 **출발하지 않는다.** 여러 개를 동시에 진행하려면 기다리기 전에 출발시켜 두어야 한다. 그 일을 하는 것이 **태스크**(task)다.

`ch07/tasks_demo.py`

```python
"""코루틴을 차례로 기다릴 때와 태스크로 만들어 기다릴 때."""

import asyncio

from timeline import log, reset


async def ask(question: str, seconds: float) -> str:
    log(f"{question} 보냄")
    await asyncio.sleep(seconds)
    log(f"{question} 받음")
    return f"{question}의 답"


async def one_by_one() -> None:
    first = await ask("가", 1.0)
    second = await ask("나", 0.5)
    log(f"{first}, {second}")


async def with_tasks() -> None:
    task1 = asyncio.create_task(ask("가", 1.0))
    task2 = asyncio.create_task(ask("나", 0.5))
    log("태스크 두 개를 만들었다")
    first = await task1
    second = await task2
    log(f"{first}, {second}")


if __name__ == "__main__":
    print("--- 코루틴을 차례로 await")
    reset()
    asyncio.run(one_by_one())
    print("--- 태스크로 만든 뒤 await")
    reset()
    asyncio.run(with_tasks())
```

```
python ch07/tasks_demo.py
```

```
--- 코루틴을 차례로 await
 0.0초  가 보냄
 1.0초  가 받음
 1.0초  나 보냄
 1.5초  나 받음
 1.5초  가의 답, 나의 답
--- 태스크로 만든 뒤 await

 0.0초  나 보냄
 0.5초  나 받음
 1.0초  가 받음
 1.0초  가의 답, 나의 답
```

`asyncio.create_task(코루틴)`은 코루틴을 **태스크로 감싸 이벤트 루프에 등록**하고, 태스크 객체를 바로 돌려준다. 등록된 태스크는 루프가 차례가 될 때 실행한다. 출력을 자세히 보면 세 가지를 알 수 있다.

- **태스크는 만들자마자 실행되지 않는다.** "태스크 두 개를 만들었다"가 "가 보냄"보다 먼저 나왔다. `create_task()`는 "실행할 목록에 올려 둔다"일 뿐이다. `with_tasks()`가 `await task1`에서 자리를 내준 **그때** 루프가 두 태스크를 실행하기 시작했다.
- **기다리는 시간이 겹쳤다.** "가"와 "나"를 0.0초에 함께 보냈다. 전체 1.0초로, 가장 오래 걸리는 것만큼이다.
- **`await task`는 결과를 꺼내는 곳이다.** "나"가 0.5초에 먼저 끝났지만 `await task1`이 1.0초까지 기다렸다. 그동안 "나"의 결과는 `task2` 안에 보관되어 있다가 `await task2`에서 바로 나왔다.

> **만든 태스크는 이름으로 붙잡아 둔다**
> `asyncio.create_task(ask("가", 1.0))`의 결과를 변수에 담지 않고 버리면, 드물게 그 태스크가 실행 도중에 사라질 수 있다. 이벤트 루프는 태스크를 **약하게**만 기억하기 때문이다. 아무도 가리키지 않는 객체는 파이썬이 정리해 버린다(기초 과정 3.2). 공식 문서도 "결과를 변수에 저장하라"고 경고한다. 7.3.5의 `TaskGroup`을 쓰면 그룹이 태스크를 붙잡아 두므로 이런 걱정이 없다.

### 7.3.3 `asyncio.gather()` — 여러 개를 한꺼번에

태스크를 하나씩 만들고 하나씩 `await`하는 일은 `asyncio.gather()`가 한 번에 해 준다. 7.1.2에서 이미 썼다.

`ch07/gather_demo.py`

```python
"""gather()는 넘긴 순서대로, as_completed()는 끝난 순서대로."""

import asyncio

from timeline import log, reset

DELAYS = {"가": 1.5, "나": 0.5, "다": 1.0}


async def ask(question: str) -> str:
    await asyncio.sleep(DELAYS[question])
    log(f"{question} 받음")
    return f"{question}의 답"


async def main() -> None:
    answers = await asyncio.gather(*[ask(q) for q in DELAYS])
    log(f"gather 결과: {answers}")

    reset()
    for next_done in asyncio.as_completed([ask(q) for q in DELAYS]):
        answer = await next_done
        log(f"as_completed: {answer}")


if __name__ == "__main__":
    asyncio.run(main())
```

- `asyncio.gather(코루틴1, 코루틴2, ...)` — 넘겨받은 코루틴을 모두 태스크로 만들어 출발시키고, **모두 끝나면** 결과를 리스트로 돌려준다.
- `*[ask(q) for q in DELAYS]` — 컴프리헨션으로 코루틴 객체의 리스트를 만들고(2장), `*`로 풀어서 넘긴다(1.3.3). 1장 (라)의 `asyncio.gather(*tasks)`가 이 모양이다. `gather()`는 리스트 하나가 아니라 코루틴을 **여러 인자로** 받기 때문이다.
- **결과는 넘긴 순서대로다.** "나"가 가장 먼저 끝났지만 결과 리스트에서는 두 번째 자리에 있다. 끝난 순서와 상관없이 `answers[i]`는 `i`번째로 넘긴 질문의 답이다. 질문과 답을 짝지을 때 편하다. `dict(zip(DELAYS, answers))`로 `{"가": "가의 답", ...}`을 만들 수 있다.

**`asyncio.as_completed()` — 끝나는 대로 하나씩.** `gather()`는 가장 느린 것이 끝날 때까지 아무것도 돌려주지 않는다. 요청 백 개 중 먼저 끝난 것부터 화면에 보여 주거나 진행률을 표시하고 싶다면 `as_completed()`를 쓴다. 코루틴 목록을 받아 모두 출발시키고, **끝나는 순서대로** 결과를 꺼낼 수 있는 어웨이터블을 하나씩 내놓는다. `for` 문 안에서 `await next_done`할 때마다 다음으로 끝난 것의 결과가 나온다. 대신 꺼낸 결과가 몇 번째 질문의 것인지는 따로 알 수 있게 해 두어야 한다. 이 예에서는 답 안에 질문이 들어 있어서 알 수 있다.

| | `gather()` | `as_completed()` |
|---|---|---|
| 결과를 받는 때 | 모두 끝난 뒤 한 번에 | 하나 끝날 때마다 |
| 결과의 순서 | 넘긴 순서 | 끝난 순서 |
| 쓰는 곳 | 결과를 모아서 한꺼번에 처리할 때 | 진행률 표시, 먼저 끝난 것부터 처리할 때 |

### 7.3.4 하나가 실패하면 — `gather()`

동시에 보낸 요청 중 하나가 실패하면 어떻게 될까? 실제 LLM API에서는 늘 있는 일이다.

`ch07/gather_errors.py`

```python
"""gather()로 동시에 실행한 것 중 하나가 실패하면."""

import asyncio

from timeline import log, reset


async def ask(question: str, seconds: float, *, fail: bool = False) -> str:
    await asyncio.sleep(seconds)
    if fail:
        log(f"{question} 실패")
        raise ValueError(f"{question}: 형식이 틀린 답")
    log(f"{question} 받음")
    return f"{question}의 답"


async def default_behavior() -> None:
    try:
        answers = await asyncio.gather(
            ask("가", 1.5), ask("나", 0.5, fail=True), ask("다", 1.0)
        )
        log(f"결과: {answers}")
    except ValueError as e:
        log(f"잡은 예외: {e}")
    await asyncio.sleep(1.5)  # 나머지가 어떻게 되는지 지켜본다
    log("끝")


async def collect_exceptions() -> None:
    results = await asyncio.gather(
        ask("가", 1.5),
        ask("나", 0.5, fail=True),
        ask("다", 1.0),
        return_exceptions=True,
    )
    log(f"결과: {results}")
    answers = [r for r in results if isinstance(r, str)]
    errors = [r for r in results if isinstance(r, Exception)]
    log(f"성공 {len(answers)}개, 실패 {len(errors)}개")


if __name__ == "__main__":
    print("--- 기본: 첫 예외가 올라온다")
    asyncio.run(default_behavior())
    print("--- return_exceptions=True")
    reset()
    asyncio.run(collect_exceptions())
```

**기본 동작.** "나"가 0.5초에 실패하자 `await asyncio.gather(...)`가 **바로** 그 예외를 일으켰다. `except`에서 잡았다. 그런데 "가"와 "다"는 그 뒤에도 **계속 실행되어** 1.0초, 1.5초에 끝났다. `gather()`는 첫 예외를 전달할 뿐 나머지를 멈추지 않는다. 그리고 그 결과는 받을 방법이 없다. `answers`에 할당되기 전에 예외가 났기 때문이다. 결과도 못 받을 요청이 계속 돌면서 돈(토큰)을 쓴 셈이다. 이 프로그램에서 1.5초를 더 기다리지 않고 `default_behavior()`가 바로 끝났다면, `asyncio.run()`이 끝나면서 남은 태스크를 취소했을 것이다.

**`return_exceptions=True`.** 예외를 일으키는 대신 **예외 객체를 결과 자리에** 넣는다. 모든 작업이 끝날 때까지 기다리고, 결과 리스트에는 성공한 것의 값과 실패한 것의 예외가 섞여 있다. 문서 백 개를 요약하다 하나가 실패해도 나머지 아흔아홉 개의 결과를 살리고 싶을 때 쓴다. 결과를 꺼낼 때는 `isinstance()`로 나눈다. 5.2.3의 "`isinstance()`로 좁히기"다. mypy는 `return_exceptions=True`일 때 결과의 타입을 `list[str | BaseException]`으로 보므로, `isinstance(r, str)`로 거른 `answers`는 `list[str]`이 된다. 2장의 `match` 문으로 나눌 수도 있다.

```python
for question, result in zip(["가", "나", "다"], results):
    match result:
        case str(answer):
            print(f"{question}: {answer}")
        case Exception() as error:
            print(f"{question}: 실패 — {error}")
```

### 7.3.5 `asyncio.TaskGroup` — 하나가 실패하면 모두 멈춘다

파이썬 3.11에 들어온 `asyncio.TaskGroup`은 태스크를 **묶음**으로 관리한다. `async with` 블록으로 쓴다. `async with`는 7.5에서 자세히 배우고, 지금은 "블록에 들어갈 때 준비하고 나갈 때 정리하는 `with` 문의 비동기 판"으로 읽는다(1.3.6, 4.6).

`ch07/task_group.py`

```python
"""TaskGroup — 하나가 실패하면 나머지를 취소하고 예외를 묶어서 올린다."""

import asyncio

from timeline import log, reset


async def ask(question: str, seconds: float, *, error: Exception | None = None) -> str:
    try:
        await asyncio.sleep(seconds)
    except asyncio.CancelledError:
        log(f"{question} 취소됨")
        raise
    if error is not None:
        log(f"{question} 실패")
        raise error
    log(f"{question} 받음")
    return f"{question}의 답"


async def all_succeed() -> None:
    async with asyncio.TaskGroup() as tg:
        task1 = tg.create_task(ask("가", 1.0))
        task2 = tg.create_task(ask("나", 0.5))
    log(f"결과: {task1.result()}, {task2.result()}")


async def one_fails() -> None:
    try:
        async with asyncio.TaskGroup() as tg:
            tg.create_task(ask("가", 1.5))
            tg.create_task(ask("나", 0.5, error=ValueError("형식이 틀린 답")))
            tg.create_task(ask("다", 1.0))
    except* ValueError as group:
        log(f"잡은 예외: {group!r}")


async def two_kinds() -> None:
    try:
        async with asyncio.TaskGroup() as tg:
            tg.create_task(ask("가", 0.5, error=ValueError("형식이 틀린 답")))
            tg.create_task(ask("나", 0.5, error=TimeoutError("시간 초과")))
            tg.create_task(ask("다", 1.0))
    except* ValueError as group:
        log(f"ValueError {len(group.exceptions)}개: {group.exceptions}")
    except* TimeoutError as group:
        log(f"TimeoutError {len(group.exceptions)}개: {group.exceptions}")


if __name__ == "__main__":
    print("--- 모두 성공")
    asyncio.run(all_succeed())
    print("--- 하나가 실패")
    reset()
    asyncio.run(one_fails())
    print("--- 두 종류가 함께 실패")
    reset()
    asyncio.run(two_kinds())
```

**모두 성공할 때.** `tg.create_task()`로 그룹 안에 태스크를 만든다. `async with` 블록이 끝나는 곳에서 그룹이 **모든 태스크가 끝나기를 기다린다.** 그래서 블록 밖에서는 `task1.result()`로 결과를 바로 꺼낼 수 있다. `await task1`을 따로 쓰지 않아도 된다. 태스크를 잊고 기다리지 않는 실수가 생기지 않는다.

**하나가 실패할 때.** "나"가 0.5초에 실패하자 그룹이 **나머지 태스크("가", "다")를 바로 취소했다.** 취소된 태스크 안에서는 멈춰 있던 `await` 자리에서 `asyncio.CancelledError`가 일어난다. `ask()`가 그것을 잡아 "취소됨"을 출력하고 다시 `raise`했다. 그룹은 모든 태스크가 끝나거나 취소된 뒤, 실패한 태스크들의 예외를 **`ExceptionGroup`이라는 예외 하나로 묶어서** 일으킨다.

`gather()`의 기본 동작과 비교하면, "가"와 "다"가 결과도 못 받을 일을 1.5초까지 계속하지 않고 0.5초에 멈췄다. 요청 하나가 실패하면 전체가 의미 없는 일(예: 한 사용자의 질문 하나에 필요한 자료 세 개를 동시에 모으는데, 하나를 못 모으면 답을 만들 수 없는 경우)이라면 이쪽이 맞다.

> **`CancelledError`를 잡았으면 다시 일으킨다**
> 취소는 "이제 그만하라"는 요청이다. `except asyncio.CancelledError:`에서 정리할 일을 하고 나면 반드시 `raise`로 다시 일으킨다. 삼켜 버리면 취소를 요청한 쪽(여기서는 그룹)은 태스크가 멈췄는지 알 수 없고, 태스크는 아무 일 없었다는 듯 계속 실행된다. `CancelledError`는 `Exception`이 아니라 `BaseException`을 물려받았다. 그래서 `except Exception:`으로는 잡히지 않는다. 일반 오류를 잡는 코드가 실수로 취소까지 삼키지 않게 하려는 설계다. 정리만 할 것이라면 7.4.2처럼 `finally`를 쓰는 편이 더 간단하다.

### 7.3.6 `ExceptionGroup`과 `except*` 읽기

동시에 실행하면 **예외가 여러 개 동시에** 날 수 있다. 위의 `two_kinds()`에서 "가"와 "나"가 같은 0.5초에 서로 다른 예외로 실패했다. 기초 과정 6장에서 배운 예외는 한 번에 하나였다. 여러 예외를 한꺼번에 올리려면 묶음이 필요하다. 그것이 파이썬 3.11에 들어온 **`ExceptionGroup`**이다.

`except*`가 없으면 어떻게 보이는지 확인한다. 대화형 셸이 아니라 짧은 파일로 실행해 본다.

```python
async def main() -> None:
    try:
        async with asyncio.TaskGroup() as tg:
            tg.create_task(ask("가", 1.5))
            tg.create_task(ask("나", 0.5, error=ValueError("형식이 틀린 답")))
    except ValueError:
        print("잡았다")
```

```
 0.5초  나 실패
 0.5초  가 취소됨
  + Exception Group Traceback (most recent call last):
  |   File ".../ch07/eg_demo.py", line 14, in <module>
  |     asyncio.run(main())
  |   ...
  |   File ".../asyncio/taskgroups.py", line 71, in __aexit__
  |     return await self._aexit(et, exc)
  |   ...
  | ExceptionGroup: unhandled errors in a TaskGroup (1 sub-exception)
  +-+---------------- 1 ----------------
    | Traceback (most recent call last):
    |   File ".../ch07/task_group.py", line 16, in ask
    |     raise error
    | ValueError: 형식이 틀린 답
    +------------------------------------
```

`except ValueError:`가 잡지 못했다. 올라온 것은 `ValueError`가 아니라 `ValueError`를 **담은** `ExceptionGroup`이기 때문이다. 오류 메시지도 모양이 다르다.

- 맨 바깥의 `+ Exception Group Traceback` — 묶음 자체가 어디서 올라왔는지다. `TaskGroup`의 `__aexit__`, 즉 `async with` 블록이 끝나는 곳에서 일어났다.
- `ExceptionGroup: unhandled errors in a TaskGroup (1 sub-exception)` — "처리되지 않은 오류가 1개 들어 있다."
- `+-+---- 1 ----` 아래 — 묶음 안의 **첫 번째 예외**의 traceback이다. 예외가 여러 개면 `2`, `3`이 이어진다. 원인을 찾을 때는 이 안쪽을 읽는다. 여기서는 `task_group.py`의 16번 줄 `raise error`에서 `ValueError`가 났다.

묶음 안의 예외를 종류별로 처리하는 문법이 **`except*`**다.

```python
try:
    ...
except* ValueError as group:
    ...  # 묶음 안의 ValueError들만 여기로 온다
except* TimeoutError as group:
    ...  # 묶음 안의 TimeoutError들만 여기로 온다
```

- `except* 종류`는 묶음에서 **그 종류의 예외만 골라낸** 작은 묶음을 받는다. `group`도 `ExceptionGroup`이다. 안의 예외들은 `group.exceptions`(튜플)에 들어 있다.
- 일반 `except`는 처음 맞는 것 **하나만** 실행되지만, `except*`는 맞는 것이 **모두** 실행된다. `two_kinds()`에서 두 블록이 모두 실행되었다.
- 어느 `except*`에도 맞지 않은 예외가 남으면, 남은 것끼리 다시 묶여서 위로 올라간다.
- 한 `try` 문에 `except`와 `except*`를 섞어 쓸 수 없다.

처음에는 `except*`를 직접 쓸 일보다 **읽을 일**이 더 많다. `TaskGroup`을 쓰는 라이브러리 코드와 오류 메시지에서 만난다. 오류 메시지에 `ExceptionGroup`이 보이면 `+-+---- 1 ----` 아래의 안쪽 traceback부터 읽는다.

### 7.3.7 `gather()`와 `TaskGroup` 중 무엇을 쓸까

| | `gather()` | `gather(..., return_exceptions=True)` | `TaskGroup` |
|---|---|---|---|
| 하나가 실패하면 | 첫 예외를 바로 올린다. 나머지는 **계속 실행된다** | 실패를 결과 자리에 담고 **모두 끝까지** 실행한다 | 나머지를 **취소**하고 예외를 묶어서 올린다 |
| 결과 | 넘긴 순서대로의 리스트 | 값과 예외가 섞인 리스트 | 태스크마다 `.result()` |
| 예외의 모양 | 보통의 예외 하나 | 결과 리스트 안의 예외 객체 | `ExceptionGroup` |
| 어울리는 일 | 짧은 실험, 실패가 없다고 확신할 때 | 일부가 실패해도 나머지 결과를 살려야 할 때(일괄 요약) | 하나라도 실패하면 전체가 의미 없을 때. 정리가 확실해야 할 때 |

이 교재에서는 다음 기준을 쓴다.

- **일부 실패를 견뎌야 하는 일괄 작업**은 실패를 **각 작업 안에서** 잡아 결과로 바꾼다. 9장의 문서 일괄 요약기가 그렇다. 조각 하나의 요약이 실패하면 그 조각만 `"error"` 레코드로 남긴다. 각 작업이 예외를 내지 않으므로 `gather()`나 `TaskGroup` 어느 것을 써도 모두 끝까지 실행된다. 실습 7-8에서 이렇게 만든다.
- **모두 성공해야 하는 일**은 `TaskGroup`을 쓴다. 실패하면 나머지를 바로 멈추고 정리한다.
- 남의 코드에서 `gather(*...)`를 만나면 "하나가 실패하면 나머지는 어떻게 되는가?"를 확인한다. 1장 (라)의 `summarize_all()`은 `return_exceptions` 없이 `gather()`를 썼으므로, 문서 하나의 요약이 실패하면 나머지 결과를 모두 잃는다.

## 7.4 시간 제한과 동시 실행 수 제한

LLM API를 동시에 부를 때는 두 가지를 꼭 챙긴다. 하나는 **시간 제한**이다. 답이 영영 오지 않는 요청을 끝없이 기다릴 수는 없다. 다른 하나는 **동시 실행 수 제한**이다. 요청 천 개를 한꺼번에 보내면 API의 요청 한도(429)에 걸리고, 내 컴퓨터의 연결 수도 바닥난다.

### 7.4.1 `asyncio.timeout()` — 정해진 시간 안에 끝나지 않으면

`ch07/timeouts.py`

```python
"""asyncio.timeout() — 정해진 시간 안에 끝나지 않으면 포기한다."""

import asyncio

from timeline import log


async def ask(question: str, seconds: float) -> str:
    try:
        await asyncio.sleep(seconds)
    finally:
        log(f"{question} 정리")
    return f"{question}의 답"


async def ask_with_limit(question: str, seconds: float, limit: float) -> str:
    """limit초 안에 답이 오지 않으면 '(시간 초과)'를 돌려준다."""
    try:
        async with asyncio.timeout(limit):
            return await ask(question, seconds)
    except TimeoutError:
        log(f"{question} 시간 초과")
        return f"{question}: (시간 초과)"


async def main() -> None:
    answers = await asyncio.gather(
        ask_with_limit("가", 0.5, limit=1.0),
        ask_with_limit("나", 3.0, limit=1.0),
        ask_with_limit("다", 0.8, limit=1.0),
    )
    log(f"결과: {answers}")


if __name__ == "__main__":
    asyncio.run(main())
```

```
 1.0초  나 정리
 1.0초  나 시간 초과
 1.0초  결과: ['가의 답', '나: (시간 초과)', '다의 답']
```

- `async with asyncio.timeout(초):` — 블록 안의 일이 그 시간 안에 끝나지 않으면 **블록 안의 일을 취소하고**, 블록을 나갈 때 `TimeoutError`를 일으킨다. 파이썬 3.11에 들어왔다.
- "나"는 3초짜리였지만 1.0초에 멈췄다. 멈출 때 `ask()`의 `finally`가 실행되어 "나 정리"가 출력되었다. 시간 제한은 내부적으로 7.4.2의 **취소**를 쓴다. 그래서 정리 코드가 실행된다.
- `TimeoutError`는 파이썬에 원래 있는 예외다. `except TimeoutError:`로 잡아 "(시간 초과)"라는 결과로 바꿨다. 이렇게 **각 작업이 자기 실패를 결과로 바꾸면** `gather()`가 예외 없이 모든 결과를 모은다(7.3.7).
- 시간 제한을 어디에 거는지에 따라 뜻이 다르다. 위처럼 **요청 하나하나**에 걸 수도 있고, `async with asyncio.timeout(5): await asyncio.gather(...)`처럼 **전체 묶음**에 걸 수도 있다. 앞의 것은 "느린 요청 하나를 포기한다", 뒤의 것은 "5초 안에 끝나지 않으면 전부 포기한다"다.

예전 코드에서는 같은 일을 `asyncio.wait_for()`로 한다.

```python
answer = await asyncio.wait_for(ask("나", 3.0), timeout=1.0)
```

코루틴 하나를 받아 시간 제한을 걸어 실행한다. 3.11 이후로는 시간이 다 되었을 때 `asyncio.timeout()`과 같은 `TimeoutError`를 일으킨다. 남의 코드에서 만나면 읽을 수 있으면 된다. 새로 쓸 때는 여러 줄을 감쌀 수 있는 `asyncio.timeout()`이 편하다.

> **`asyncio.TimeoutError`와 `TimeoutError`**
> 파이썬 3.10 이전에는 asyncio에 따로 `asyncio.TimeoutError`가 있었다. 3.11부터는 내장 `TimeoutError`와 **같은 것**이 되었다(`asyncio.TimeoutError is TimeoutError`가 `True`다). 오래된 예제에서 `except asyncio.TimeoutError:`를 보면 같은 뜻으로 읽는다. HTTP 라이브러리는 자기만의 시간 초과 예외를 쓰기도 한다. httpx는 `httpx.TimeoutException`이다(7.6.4).

### 7.4.2 취소 — 멈춘 자리에서 `CancelledError`가 일어난다

사용자가 "중지" 버튼을 누르면 진행 중인 요청을 멈춰야 한다. 3.6.5에서 제너레이터를 `close()`로 멈추면 멈춘 `yield` 자리에서 `GeneratorExit`가 일어났다. 태스크를 멈추는 방법은 `cancel()`이고, 멈춘 `await` 자리에서 `CancelledError`가 일어난다.

`ch07/cancel_demo.py`

```python
"""태스크 취소 — 멈춘 자리에서 CancelledError가 일어난다."""

import asyncio

from timeline import log


async def long_answer() -> str:
    pieces: list[str] = []
    try:
        for n in range(1, 11):
            await asyncio.sleep(0.3)
            pieces.append(f"조각{n}")
            log(f"조각{n} 받음")
        return " ".join(pieces)
    except asyncio.CancelledError:
        log(f"취소됨 — 받은 것 {len(pieces)}개")
        raise
    finally:
        log("연결 정리")


async def main() -> None:
    task = asyncio.create_task(long_answer())
    await asyncio.sleep(1.0)
    log("중지 버튼")
    task.cancel()
    try:
        await task
    except asyncio.CancelledError:
        log(f"태스크가 취소되었다: cancelled()={task.cancelled()}")


if __name__ == "__main__":
    asyncio.run(main())
```

```

```

```
 0.6초  조각2 받음
 0.9초  조각3 받음
 1.0초  중지 버튼
 1.0초  취소됨 — 받은 것 3개
 1.0초  연결 정리
 1.0초  태스크가 취소되었다: cancelled()=True
```

- `task.cancel()` — 태스크에 "멈춰라"를 **요청**한다. 태스크는 지금 멈춰 있는 `await asyncio.sleep(0.3)` 자리에서 `CancelledError`를 받는다. 이미 실행 중인 코드를 중간에 끊지는 않는다. 다음 `await`에서 멈춘다. 7.2.5에서처럼 `await` 없이 오래 도는 코드는 취소도 할 수 없다.
- `except asyncio.CancelledError:` → `raise` — 받은 조각 수를 기록하고 다시 일으켰다(7.3.5의 상자).
- `finally` — 취소되든, 끝까지 가든, 다른 예외가 나든 실행된다. 연결을 닫는 일처럼 **반드시 해야 하는 정리**는 여기에 둔다. 3장과 4장에서 스트림의 연결을 `finally`에서 정리한 것과 같다.
- `await task` — 취소된 태스크를 `await`하면 `CancelledError`가 다시 올라온다. `task.cancelled()`는 태스크가 취소로 끝났는지를 알려 준다.

취소는 asyncio의 여러 기능이 바탕으로 쓰는 장치다. `asyncio.timeout()`은 시간이 다 되면 블록 안의 일을 취소하고, `TaskGroup`은 하나가 실패하면 나머지를 취소하고, `asyncio.run()`은 끝날 때 남은 태스크를 취소한다. 그래서 **비동기 코드의 정리는 `finally`나 `async with`에 둔다**는 습관이 중요하다. 그렇게 해 두면 어떤 이유로 멈추든 정리된다.

### 7.4.3 `asyncio.Semaphore` — 동시에 몇 개까지

요청 열 개를 동시에 보내되, **한 번에 최대 세 개까지만** 진행되게 하고 싶다. 놀이공원의 놀이기구에 좌석이 세 개뿐이라 네 번째 손님부터는 줄을 서는 것과 같다. 이 "좌석"을 관리하는 것이 **세마포어**(semaphore)다.

`ch07/limit_demo.py`

```python
"""asyncio.Semaphore — 동시에 실행되는 수를 제한한다."""

import asyncio
import time

active = 0  # 지금 요청 중인 수
peak = 0  # 가장 많았을 때의 수


async def ask(question: str) -> str:
    global active, peak
    active += 1
    peak = max(peak, active)
    try:
        await asyncio.sleep(1.0)
        return f"{question}의 답"
    finally:
        active -= 1


async def ask_limited(limit: asyncio.Semaphore, question: str) -> str:
    async with limit:
        return await ask(question)


async def main(max_concurrency: int) -> None:
    global peak
    peak = 0
    limit = asyncio.Semaphore(max_concurrency)
    start = time.perf_counter()
    answers = await asyncio.gather(
        *[ask_limited(limit, f"질문 {n}") for n in range(1, 11)]
    )
    elapsed = time.perf_counter() - start
    print(
        f"동시 {max_concurrency}개까지: {len(answers)}개, {elapsed:.1f}초, 최대 동시 {peak}개"
    )


if __name__ == "__main__":
    for n in (10, 3, 1):
        asyncio.run(main(n))
```

```
동시 1개까지: 10개, 10.0초, 최대 동시 1개
```

- `asyncio.Semaphore(3)` — 좌석이 세 개인 세마포어를 만든다.
- `async with limit:` — 블록에 들어갈 때 좌석을 하나 차지하고, 나갈 때 돌려준다. 빈 좌석이 없으면 **빌 때까지 기다린다**(`await`). 블록 안에서 예외가 나거나 취소되어도 좌석은 반드시 돌려준다. `with` 문이라서다.
- `active`와 `peak` — 정말로 세 개를 넘지 않았는지 확인하려고 센다. `ask()`에 들어올 때 하나 늘리고, `finally`에서 하나 줄인다. 이 숫자로 "최대 동시 3개"를 **테스트로** 확인할 수 있다(실습 7-8).
- 시간 — 동시 3개면 1초짜리 열 개가 3 + 3 + 3 + 1로 네 번에 나뉘어 4초다. 동시 1개면 차례로 하는 것과 같아서 10초다.
- 세마포어는 **같은 것을 함께 써야** 제한이 걸린다. 그래서 `main()`에서 하나를 만들어 모든 `ask_limited()`에 넘겼다. `ask_limited()` 안에서 매번 새로 만들면 좌석이 세 개인 놀이기구가 열 대 생기는 셈이다.

1장 (라)의 `summarize_all()`이 이 모양이었다.

```python
async def summarize_all(docs: list[str]) -> list[str]:
    limit = asyncio.Semaphore(5)  # 동시에 5개까지만
    async with httpx.AsyncClient(timeout=30) as http:
        tasks = [summarize(http, doc, limit) for doc in docs]
        return await asyncio.gather(*tasks)
```

세마포어 하나를 만들어 모든 `summarize()`에 넘겼다. `summarize()` 안에서 `async with limit:`으로 요청을 감쌌을 것이다.

### 7.4.4 동시 실행 수와 요청 한도

세마포어로 제한하는 것은 **동시에 진행 중인** 요청의 수다. LLM API의 요청 한도는 보통 **시간당** 요청 수나 토큰 수(예: "분당 50회", "분당 토큰 4만 개")로 정해진다. 둘은 다르다.

- 동시 5개로 제한해도, 요청 하나가 0.5초 만에 끝나면 1분에 600회를 보낼 수 있다. 분당 50회 한도라면 금방 429를 받는다.
- 반대로 요청 하나가 30초씩 걸린다면, 동시 5개로는 1분에 10회밖에 보내지 못한다. 한도에 한참 못 미친다.

그래서 실제로는 두 가지를 함께 쓴다.

1. **세마포어로 동시 실행 수를 적당히 제한한다.** 내 컴퓨터와 상대 서버가 감당할 만큼으로. 처음에는 5~10 정도에서 시작해 조정한다.
2. **429를 받으면 기다렸다가 다시 시도한다.** 서버가 `retry-after` 헤더로 알려 준 시간만큼 기다린다. 4장 4.3.4와 6.5.2의 `RateLimitError(retry_after=...)` 처리가 바로 이것이다.

시간당 요청 수를 미리 맞춰 보내는 장치(rate limiter)도 만들 수 있지만, 이 과정에서는 다루지 않는다. "LLM API 활용"에서 실제 한도를 보며 다시 생각한다.

### 7.4.5 비동기 함수용 재시도 데코레이터

4장에서 만들고 6장에서 테스트한 `retry()`를 비동기 함수에 그대로 붙이면 어떻게 될까? 4장의 재시도 데코레이터를 줄인 것으로 확인한다.

```python
def retry(times: int = 3) -> Callable[[Callable[..., Any]], Callable[..., Any]]:
    """4장의 재시도 데코레이터를 줄인 것 — 동기 함수용."""

    def decorator(func: Callable[..., Any]) -> Callable[..., Any]:
        @functools.wraps(func)
        def wrapper(*args: Any, **kwargs: Any) -> Any:
            for attempt in range(1, times + 1):
                try:
                    return func(*args, **kwargs)
                except TimeoutError:
                    print(f"  [재시도] {attempt}번째 실패")
                    if attempt == times:
                        raise
            raise AssertionError("여기에 오지 않는다")

        return wrapper

    return decorator


calls = 0


@retry(times=3)
async def flaky_ask(question: str) -> str:
    global calls
    calls += 1
    await asyncio.sleep(0.1)
    if calls < 3:
        raise TimeoutError("시간 초과")
    return f"{question}의 답"


async def main() -> None:
    try:
        print(await flaky_ask("질문"))
    except TimeoutError as e:
        print(f"재시도 없이 실패: {e!r}, 호출 {calls}번")
```

```
재시도 없이 실패: TimeoutError('시간 초과'), 호출 1번
```

세 번까지 다시 시도해야 하는데 **한 번 만에 실패했고, `[재시도]`도 한 번도 출력되지 않았다.** 왜 그럴까? `wrapper()` 안의 `return func(*args, **kwargs)`를 따라가 본다.

1. `func`는 코루틴 함수 `flaky_ask`다. 부르면 본문을 실행하지 않고 **코루틴 객체를 돌려준다**(7.2.1).
2. 코루틴 객체를 돌려받았으니 `try` 블록에서는 아무 예외도 나지 않는다. `wrapper()`는 그 코루틴 객체를 그대로 `return`한다. 재시도 반복문은 **첫 바퀴에서 끝났다.**
3. `main()`의 `await`가 그 코루틴 객체를 실행한다. 예외는 **이때** 난다. 이미 `wrapper()`의 `try` 블록을 한참 벗어난 뒤다.

3장에서 "제너레이터 안의 예외는 함수를 **호출할 때가 아니라 값을 꺼낼 때** 올라온다"고 했다(1.3.5). 코루틴도 같다. 예외는 **`await`할 때** 올라온다. 그러니 비동기 함수를 감싸는 데코레이터는 래퍼도 `async def`로 만들고, 안에서 `await`해야 한다.

더 곤란한 것은 이 실수를 **mypy도 잡지 못한다**는 것이다. 5.3.5처럼 `ParamSpec`으로 타입을 정확히 붙인 `retry()`라도, mypy가 보기에 `flaky_ask`는 "`str`을 받아 `Coroutine[Any, Any, str]`을 돌려주는 함수"일 뿐이다. 동기 데코레이터는 무엇을 돌려주는 함수든 감쌀 수 있으므로 타입은 맞다. **타입은 맞는데 동작이 틀린 코드**, 6장에서 테스트가 찾아야 한다고 한 바로 그런 코드다. 비동기 함수용 재시도 데코레이터를 따로 만들고, 테스트로 확인한다.

`ch07/async_retry.py`

```python
"""비동기 함수용 재시도 데코레이터 — 6장의 retry()를 async로 바꿨다."""

import asyncio
import functools
import random
from collections.abc import Awaitable, Callable, Coroutine
from typing import Any


class APIError(Exception):
    """가짜 LLM API의 오류. status에 HTTP 상태 코드를 담는다."""

    def __init__(self, message: str, status: int | None = None) -> None:
        super().__init__(message)
        self.status = status


class APITimeoutError(APIError):
    """응답이 제한 시간 안에 오지 않았다."""


class RateLimitError(APIError):
    """요청 한도 초과(429). retry_after초 뒤에 다시 보내라는 뜻이다."""

    def __init__(self, message: str, retry_after: float | None = None) -> None:
        super().__init__(message, status=429)
        self.retry_after = retry_after


class ServerError(APIError):
    """서버 쪽 문제(500, 503, 529 등). 잠시 뒤에는 될 수 있다."""


class BadRequestError(APIError):
    """요청이 잘못되었다(400). 다시 보내도 같은 결과다."""


RETRYABLE: tuple[type[Exception], ...] = (APITimeoutError, RateLimitError, ServerError)

type AsyncFunc[**P, R] = Callable[P, Coroutine[Any, Any, R]]


def async_retry[**P, R](
    times: int = 3,
    delay: float = 1.0,
    backoff: float = 2.0,
    jitter: float = 0.0,
    exceptions: tuple[type[Exception], ...] = RETRYABLE,
    sleep: Callable[[float], Awaitable[None]] = asyncio.sleep,
    rand: Callable[[], float] = random.random,
) -> Callable[[AsyncFunc[P, R]], AsyncFunc[P, R]]:
    """exceptions의 예외가 나면 times번까지 시도하는 비동기 데코레이터를 만든다.

    기다리는 규칙은 6장의 retry()와 같다. 기다릴 때는 await sleep(초)를 쓴다.
    times가 1보다 작으면 ValueError를 일으킨다.
    """
    if times < 1:
        raise ValueError(f"times는 1 이상이어야 한다: {times}")

    def decorator(func: AsyncFunc[P, R]) -> AsyncFunc[P, R]:
        @functools.wraps(func)
        async def wrapper(*args: P.args, **kwargs: P.kwargs) -> R:
            for attempt in range(1, times + 1):
                try:
                    return await func(*args, **kwargs)
                except exceptions as e:
                    if attempt == times:
                        raise
                    retry_after = getattr(e, "retry_after", None)
                    if retry_after is not None:
                        wait = retry_after
                    else:
                        wait = delay * backoff ** (attempt - 1) + jitter * rand()
                    print(
                        f"  [재시도] {attempt}번째 실패({type(e).__name__}: {e}), {wait:.1f}초 뒤 다시"
                    )
                    await sleep(wait)
            raise AssertionError("여기에 오지 않는다")

        return wrapper

    return decorator
```

6장의 `ch06/retry.py`를 복사해 와서 고쳤다. 예외 클래스는 그대로다. 6.2.5에서 "장이 달라도 모듈 이름이 겹치지 않게 짓는다"고 했으므로 파일 이름을 `async_retry.py`로 했다. 달라진 곳은 다섯 군데다.

- `async def wrapper(...)` — 래퍼가 코루틴 함수다. 데코레이터를 붙인 함수를 부르면 래퍼의 코루틴 객체가 나오고, 그것을 `await`할 때 재시도 반복문이 돈다.
- `return await func(*args, **kwargs)` — 감싼 함수의 코루틴을 **`await`해서** 실행한다. 예외가 여기서 나므로 `try`가 잡을 수 있다. 이 `await` 하나가 위의 실패와 이 데코레이터의 차이다.
- `await sleep(wait)` — `time.sleep()` 대신 `asyncio.sleep()`으로 기다린다. 재시도를 기다리는 동안에도 다른 요청은 계속 진행된다. 6장 6.5.3의 상자에서 "기다리는 함수를 받으니 7장에서 `asyncio.sleep`으로 바꾸기 쉽다"고 한 곳이다.
- `sleep: Callable[[float], Awaitable[None]] = asyncio.sleep` — "초를 받아서, `await`하면 `None`이 나오는 것을 돌려주는 함수"다. `Awaitable[None]`은 "`await`할 수 있고 결과가 `None`인 것"이다. 기본값은 진짜 `asyncio.sleep`이고, 테스트에서는 가짜를 넘긴다(7.7.2).
- `type AsyncFunc[**P, R] = Callable[P, Coroutine[Any, Any, R]]` — "매개변수가 `P`이고, 부르면 `await`해서 `R`이 나오는 코루틴을 돌려주는 함수"에 이름을 붙였다. 5.4.4의 `type` 별칭 문에 5.3.5의 `ParamSpec`(`**P`)을 함께 쓴 것이다. `Coroutine`의 세 칸 중 앞의 두 칸은 거의 쓰지 않으므로 `Any`로 두고, 마지막 칸이 `await`의 결과다. 이 별칭이 없으면 데코레이터의 반환 타입이 `Callable[[Callable[P, Coroutine[Any, Any, R]]], Callable[P, Coroutine[Any, Any, R]]]`로 길어진다.

> **왜 `Awaitable`이 아니라 `Coroutine`인가**
> 감싼 함수의 타입을 `Callable[P, Awaitable[R]]`로 적어도 `await`는 할 수 있다. 그런데 그러면 데코레이터를 붙인 함수를 `asyncio.create_task()`나 `TaskGroup.create_task()`에 넘길 때 mypy가 오류를 낸다. 두 함수는 **코루틴**만 받기 때문이다(`Awaitable`은 코루틴보다 넓은 약속이다). 5.3.2의 "매개변수는 넓게, 반환값은 구체적으로"를 떠올리면, 데코레이터가 돌려주는 함수의 반환 타입은 구체적인 `Coroutine`이 맞다. 반면 `sleep` 매개변수는 **받는** 쪽이므로 넓은 `Awaitable[None]`으로 두었다.

감싼 함수 여러 개를 동시에 불러 본다.

```python
import asyncio

failures: dict[str, list[Exception]] = {

    "나": [],
    "다": [ServerError("과부하", 529), ServerError("과부하", 529)],

@async_retry(delay=0.5)

        raise failures[question].pop(0)
    log(f"{question} 받음")
    return f"{question}의 답"


async def main() -> None:
    answers = await asyncio.gather(*[ask(q) for q in failures])
    log(f"결과: {answers}")


if __name__ == "__main__":
    asyncio.run(main())
```

### 7.4.6 재시도, 시간 제한, 세마포어를 함께 쓸 때

실제 LLM 호출에는 이 장의 세 장치가 모두 들어간다. 어떤 순서로 감싸느냐에 따라 뜻이 달라진다.

**시간 제한은 시도 하나마다.** 재시도 **안쪽**에 시간 제한을 두면 "한 번 시도에 최대 30초, 넘으면 포기하고 다시 시도"다. 바깥쪽에 두면 "재시도를 다 합쳐 30초"다. 첫 시도가 30초를 다 쓰면 다시 시도할 시간이 남지 않는다. LLM 호출에서는 보통 시도마다 시간 제한을 둔다. 그리고 시간 제한에 걸린 것을 **다시 시도할 예외로 바꿔야** 재시도가 동작한다. `asyncio.timeout()`이 일으키는 `TimeoutError`는 `RETRYABLE`에 없기 때문이다.

```python
@async_retry()
async def ask(prompt: str) -> str:
    try:
        async with asyncio.timeout(30):
            return await client.complete(prompt)
    except TimeoutError as e:
        raise APITimeoutError("30초 안에 답이 없다") from e
```

`raise ... from e`는 "이 예외는 `e` 때문에 생겼다"는 표시다(기초 과정 6.2.5). traceback에 원래의 `TimeoutError`도 함께 나온다.

**세마포어는 무엇을 감싸는가.** 세마포어를 재시도 **바깥**에 두면, 재시도를 기다리는 동안에도 좌석을 차지한다. 429를 받고 5초를 기다리는 요청이 좌석 다섯 개를 모두 차지하면, 그동안 아무 요청도 나가지 않는다. 한도 초과로 기다리는 중이라면 오히려 바람직할 수 있다. 서버가 "천천히 보내라"고 했으니까. 반대로 세마포어를 시도 하나만 감싸게 **안쪽**에 두면, 기다리는 동안 다른 요청이 좌석을 쓴다. 처리량은 늘지만 한도 초과 중에도 새 요청이 계속 나간다. 어느 쪽이 맞는지는 상황에 따라 다르다. 실습 7-8에서는 단순한 바깥쪽을 쓰고, "확인할 것"에서 다시 생각한다.

## 7.5 비동기 반복과 컨텍스트 관리자

3장에서 스트리밍 응답을 `for` 문으로 읽었고, 4장에서 그 스트림을 `with` 문으로 열고 닫았다. 3.6.5의 상자에서 "웹 서버에서 스트리밍 응답을 받아 그대로 사용자에게 흘려보낼 때는 `for` 대신 `async for`를 쓴다"고 했다. 이 절에서 그 두 가지, `async for`와 `async with`를 만든다.

### 7.5.1 비동기 제너레이터와 `async for`

3장의 가짜 스트림은 조각 사이에 `time.sleep()`으로 기다렸다. 7.2.5에서 본 것처럼 비동기 코드에서는 이렇게 기다리면 안 된다. 조각을 기다리는 동안 이벤트 루프가 다른 일을 할 수 있도록 `await asyncio.sleep()`으로 바꿔야 한다. 그런데 일반 제너레이터 안에서는 `await`를 쓸 수 없다. 그래서 **비동기 제너레이터**가 필요하다. `async def` 안에 `yield`가 있으면 비동기 제너레이터 함수가 된다.

`ch07/async_stream.py`

```python
"""비동기 스트림 — 3장과 4장의 가짜 스트림을 async로."""

import asyncio
from collections.abc import AsyncGenerator, AsyncIterator
from contextlib import asynccontextmanager
from typing import Any

from timeline import log, reset


async def fake_event_stream(
    text: str, piece_size: int = 4, delay: float = 0.1
) -> AsyncGenerator[dict[str, Any], None]:
    """시작, 텍스트 조각들, 끝 이벤트를 차례로 내놓는다. (3.6.4의 async 판)"""
    try:
        yield {"type": "message_start", "model": "small-model"}
        for start in range(0, len(text), piece_size):
            await asyncio.sleep(delay)
            yield {"type": "text_delta", "text": text[start : start + piece_size]}
        yield {"type": "message_stop", "stop_reason": "end_turn"}
    finally:
        log("[연결 정리]")


async def text_only(events: AsyncIterator[dict[str, Any]]) -> AsyncIterator[str]:
    """이벤트 중 텍스트 조각의 글자만 내놓는다."""
    async for event in events:
        match event:
            case {"type": "text_delta", "text": str(text)}:
                yield text


@asynccontextmanager
async def open_stream(text: str) -> AsyncIterator[AsyncIterator[str]]:
    """가짜 스트림을 열어 텍스트 조각의 비동기 이터레이터를 내준다. 블록을 나가면 닫는다."""
    log("[연결 열기]")
    events = fake_event_stream(text)
    try:
        yield text_only(events)
    finally:
        await events.aclose()


async def collect(name: str, text: str) -> str:
    """스트림을 열어 조각을 모두 모은 뒤 이어 붙인 전체 답을 돌려준다."""
    async with open_stream(text) as stream:
        pieces = [piece async for piece in stream]
    log(f"{name}: 조각 {len(pieces)}개")
    return "".join(pieces)


async def main() -> None:
    async with open_stream("아주 긴 답이 이어지다가 중지된다.") as stream:
        received: list[str] = []
        async for piece in stream:
            received.append(piece)
            log(f"받음: {piece!r}")
            if len("".join(received)) >= 10:
                log("중지")
                break
    log(f"받은 것: {''.join(received)!r}")

    reset()
    answers = await asyncio.gather(
        collect("가", "첫 번째 답입니다."),
        collect("나", "두 번째 답이에요."),
    )
    log(f"결과: {answers}")


if __name__ == "__main__":
    asyncio.run(main())
```

3장 3.6.4·3.6.5와 4장 4.6.6의 코드와 한 줄씩 비교하며 읽는다. 달라진 곳은 모두 `async`/`await`가 붙은 곳이다.

| 3·4장 (동기) | 7장 (비동기) | 하는 일 |
|---|---|---|
| `def` + `yield` | `async def` + `yield` | 값을 하나씩 내놓는 함수. 안에서 `await`를 쓸 수 있다 |
| `time.sleep(delay)` | `await asyncio.sleep(delay)` | 다음 조각을 기다린다. 기다리는 동안 다른 일을 한다 |
| `for event in events:` | `async for event in events:` | 다음 값을 **`await`해서** 꺼낸다 |
| `[x for x in stream]` | `[x async for x in stream]` | 비동기 컴프리헨션 |
| `events.close()` | `await events.aclose()` | 멈춘 제너레이터를 닫아 `finally`를 실행한다 |
| `@contextmanager` | `@asynccontextmanager` | `yield` 앞이 준비, 뒤가 정리 |
| `with ... as stream:` | `async with ... as stream:` | 들어갈 때와 나갈 때 `await`할 수 있다 |
| `Iterator[str]`, `Generator[...]` | `AsyncIterator[str]`, `AsyncGenerator[...]` | 타입 힌트 |

- **`async for`** — 3.1.1에서 `for` 문이 실제로는 `iter()`로 이터레이터를 얻고 `next()`를 되풀이한다고 했다. `async for`는 `aiter()`로 비동기 이터레이터를 얻고, `await anext()`를 되풀이한다. 다음 값이 아직 준비되지 않았으면 **기다리는 동안 자리를 내준다.** 일반 `for`로 비동기 제너레이터를 돌리면 `TypeError: 'async_generator' object is not iterable`이 난다.
- **비동기 컴프리헨션** — `collect()`의 `[piece async for piece in stream]`처럼, 컴프리헨션 안에서도 `async for`를 쓸 수 있다. 코루틴 함수 안에서만 쓸 수 있다.
- **`aclose()`** — 비동기 제너레이터를 닫는 메서드도 코루틴이다. 그래서 `await events.aclose()`라고 쓴다. 닫히면서 실행되는 `finally` 안에서도 `await`를 쓸 수 있도록 하기 위해서다. 실제 SDK라면 거기서 연결을 비동기로 닫는다.
- **`AsyncGenerator[dict[str, Any], None]`** — `fake_event_stream()`만 `AsyncIterator`가 아니라 `AsyncGenerator`로 적었다. `open_stream()`에서 `aclose()`를 부르기 때문이다. `AsyncIterator`는 "`async for`로 꺼낼 수 있다"만 약속하고 `aclose()`는 약속하지 않으므로, `AsyncIterator`로 적으면 mypy가 `"AsyncIterator[dict[str, Any]]" has no attribute "aclose"`라고 알려 준다. 5.3.4에서 "보통은 `Iterator`, 더 필요할 때 `Generator`"라고 한 것과 같은 판단이다. 비동기 제너레이터는 `return` 값이 없으므로 칸이 두 개(내놓는 값, 받는 값)다.
- **두 스트림이 동시에** — 뒷부분에서 `collect("가", ...)`와 `collect("나", ...)`를 `gather()`로 동시에 돌렸다. 두 연결이 0.0초에 함께 열리고 0.3초에 함께 끝났다. 동기 스트림이었다면 0.6초가 걸렸을 것이다. 웹 서버가 사용자 여러 명의 스트리밍 응답을 동시에 흘려보낼 수 있는 이유다.

1장 1.2.6에서 httpx의 `Response` 클래스 안에서 찾은 `async def aiter_lines(self)`가 바로 이런 비동기 제너레이터 메서드다. 응답 본문을 줄 단위로 하나씩, 도착하는 대로 내놓는다.

> **`__aiter__`와 `__anext__`**
> 3.1.5에서 `__iter__`와 `__next__`로 이터레이터 클래스를 만들었다. 비동기 이터레이터 클래스는 `__aiter__`와 `async def __anext__`를 만들고, 끝나면 `StopIteration` 대신 `StopAsyncIteration`을 일으킨다. 3.2.6에서 "이터러블 클래스를 제너레이터로 간단히" 만든 것처럼, 대부분은 비동기 제너레이터로 충분하다. 라이브러리 코드에서 `__aiter__`를 만나면 "`async for`로 돌릴 수 있는 객체"로 읽는다.

### 7.5.2 `async with` — 비동기 컨텍스트 관리자

`open_stream()`은 4장 4.6.6의 `open_stream()`에서 `@contextmanager`를 `@asynccontextmanager`로, `events.close()`를 `await events.aclose()`로 바꾼 것이다. `main()`의 앞부분을 보면 `break`로 반복을 멈췄는데도 `async with` 블록이 끝나면서 `[연결 정리]`가 출력되었다. 4장과 똑같이, 블록을 어떻게 빠져나가든 반드시 정리된다.

`with` 대신 `async with`가 필요한 이유는 하나다. **들어가고 나가는 일 자체가 기다려야 하는 일**이기 때문이다. 네트워크 연결을 열고 닫는 데는 시간이 걸린다. 그 시간 동안 이벤트 루프를 붙잡지 않으려면 열고 닫는 코드 안에서도 `await`를 써야 한다. 일반 `with` 문이 부르는 `__enter__`와 `__exit__`는 일반 메서드라서 안에서 `await`를 쓸 수 없다. 그래서 `async with`는 **코루틴 메서드** `__aenter__`와 `__aexit__`를 부르고 각각 `await`한다.

4.6.2처럼 클래스로 만들면 다음과 같다.

```python
from types import TracebackType


class FakeConnection:
    async def __aenter__(self) -> "FakeConnection":
        await asyncio.sleep(0.1)  # 연결을 연다
        print("연결 열림")
        return self

    async def __aexit__(
        self,
        exc_type: type[BaseException] | None,
        exc: BaseException | None,
        tb: TracebackType | None,
    ) -> None:
        await asyncio.sleep(0.1)  # 연결을 닫는다
        print("연결 닫힘")


async def main() -> None:
    async with FakeConnection() as conn:
        print("요청 보내기", conn)
```

모양은 4.6.2와 같고, 메서드 이름에 `a`가 붙고 `async def`가 되었을 뿐이다. 4.6.4에서 `@contextmanager`가 이 두 메서드를 제너레이터 하나로 대신 만들어 준 것처럼, `@asynccontextmanager`는 비동기 제너레이터 하나로 대신 만들어 준다.

이 장에서 이미 `async with`를 세 번 썼다.

- `async with asyncio.TaskGroup() as tg:` — 나갈 때 모든 태스크가 끝나기를 **기다린다**(7.3.5).
- `async with asyncio.timeout(1.0):` — 시간이 다 되면 블록 안의 일을 취소한다(7.4.1).
- `async with limit:` — 들어갈 때 빈 좌석이 날 때까지 **기다린다**(7.4.3).

셋 다 들어가거나 나가는 일에 기다림이 있다. 그리고 1장 (라)의 `async with httpx.AsyncClient(timeout=30) as http:`가 다음 절의 주제다.

## 7.6 비동기 HTTP 요청

### 7.6.1 늦게 답하는 가짜 서버

실제 LLM API로 실험하면 돈이 들고, 응답 시간이 매번 달라서 비교하기 어렵다. 공개된 웹 사이트는 응답이 너무 빨라서 차이가 잘 보이지 않는다. 그래서 **정해진 시간만큼 늦게 답하는 가짜 서버**를 직접 띄운다. 표준 라이브러리만 쓴다.

`ch07/slow_server.py`

```python
"""늦게 답하는 가짜 API 서버 — 7.6의 실습용. 다른 터미널에서 실행해 둔다.

http://127.0.0.1:8000/아무경로?delay=초 로 요청하면 delay초(기본 1초) 뒤에 JSON으로 답한다.
"""

import json
import time
from http.server import BaseHTTPRequestHandler, ThreadingHTTPServer
from urllib.parse import parse_qs, urlparse


class SlowHandler(BaseHTTPRequestHandler):
    def do_GET(self) -> None:
        url = urlparse(self.path)
        delay = float(parse_qs(url.query).get("delay", ["1.0"])[0])
        time.sleep(delay)  # 모델이 답을 만드는 시간
        body = json.dumps({"path": url.path, "delay": delay}).encode("utf-8")
        self.send_response(200)
        self.send_header("Content-Type", "application/json")
        self.send_header("Content-Length", str(len(body)))
        self.end_headers()
        self.wfile.write(body)


class SlowServer(ThreadingHTTPServer):
    request_queue_size = 100  # 한꺼번에 들어오는 연결을 받아 둘 수(기본 5)


if __name__ == "__main__":
    server = SlowServer(("127.0.0.1", 8000), SlowHandler)
    print("http://127.0.0.1:8000 에서 기다린다. 끝내려면 Ctrl+C")
    server.serve_forever()
```

이 서버의 코드를 자세히 알 필요는 없다. 무엇을 하는지만 본다.

- `GET` 요청이 오면 `do_GET()`이 불린다. 주소의 `?delay=초`를 읽어 그만큼 `time.sleep()`으로 기다린 뒤, 요청한 경로와 기다린 시간을 JSON으로 돌려준다. LLM 서버가 답을 만드는 시간을 흉내 낸 것이다.
- `ThreadingHTTPServer` — 요청마다 **스레드**를 하나씩 만들어 처리한다. 그래서 요청 열 개가 동시에 와도 각자의 스레드에서 1초씩 기다리고 함께 답한다. 7.1.4의 표에서 "입출력 대기가 있는데 `async`를 쓰지 않을 때"의 스레드다. 서버 쪽에서 `time.sleep()`을 써도 되는 이유이기도 하다. 각자 자기 스레드를 재우기 때문이다.
- `request_queue_size = 100` — 동시에 들어오는 연결을 몇 개까지 줄 세워 둘지다. 기본값 5로 두면 요청 열 개를 한꺼번에 보낼 때 일부 연결이 거절될 수 있다.
- `127.0.0.1`은 "이 컴퓨터 자신"을 뜻하는 주소다. 다른 컴퓨터에서는 접속할 수 없다.

**새 터미널**을 하나 더 연다. VS Code의 터미널 패널에서 `+`를 누르면 된다. 저장소 폴더에서 가상환경을 활성화하고 서버를 실행한다.

### 7.6.2 `requests`로 차례로

기초 과정 9.3.3에서 쓴 `requests`로 요청 열 개를 차례로 보낸다.

`ch07/fetch_sync.py`

```python
"""가짜 API 서버에 요청 10개를 차례로 보낸다 — requests."""

import time

import requests

BASE_URL = "http://127.0.0.1:8000"
PATHS = [f"/ask/{n}" for n in range(1, 11)]


def fetch(session: requests.Session, path: str) -> float:
    """path에 요청하고, 서버가 기다린 시간(delay)을 돌려준다."""
    response = session.get(BASE_URL + path, timeout=10)
    response.raise_for_status()
    delay: float = response.json()["delay"]
    return delay


def main() -> None:
    start = time.perf_counter()
    with requests.Session() as session:
        delays = [fetch(session, path) for path in PATHS]
    elapsed = time.perf_counter() - start
    print(
        f"requests, 차례로: {len(delays)}개, 서버 대기 합 {sum(delays):.1f}초, 걸린 시간 {elapsed:.2f}초"
    )


if __name__ == "__main__":
    main()
```

- `requests.Session()` — 같은 서버에 여러 번 요청할 때 연결을 다시 쓰게 해 주는 객체다. `with` 문으로 쓰면 끝날 때 연결을 닫는다. 기초 과정에서는 `requests.get()`을 바로 불렀는데, 그러면 요청마다 연결을 새로 맺는다.
- `timeout=10` — requests는 **시간 제한의 기본값이 없다.** 지정하지 않으면 서버가 답하지 않을 때 영원히 기다린다. 언제나 지정한다.
- `response.raise_for_status()` — 상태 코드가 400 이상이면 `requests.HTTPError`를 일으킨다(기초 과정 9.3.3).
- `delay: float = response.json()["delay"]` — `response.json()`의 결과는 `Any`다. JSON에 무엇이 들어 있을지 타입 검사기는 모른다. 그대로 돌려주면 `mypy --strict`가 `Returning Any from function declared to return "float"`라고 지적하므로, 변수에 타입을 적어 받는다. 5장에서 본 것처럼 정말 검증하려면 Pydantic 모델을 쓴다.

서버 대기 합이 10초이고 걸린 시간도 10초다. 기다리는 시간이 그대로 쌓였다.

### 7.6.3 `httpx.AsyncClient`로 동시에

같은 일을 `httpx.AsyncClient`로 한다.

`ch07/fetch_async.py`

```python
"""가짜 API 서버에 요청 10개를 동시에 보낸다 — httpx.AsyncClient."""

import asyncio
import time

import httpx
from fetch_sync import BASE_URL, PATHS


async def fetch(client: httpx.AsyncClient, path: str) -> float:
    """path에 요청하고, 서버가 기다린 시간(delay)을 돌려준다."""
    response = await client.get(path)
    response.raise_for_status()
    delay: float = response.json()["delay"]
    return delay


async def main() -> None:
    start = time.perf_counter()
    async with httpx.AsyncClient(base_url=BASE_URL, timeout=10) as client:
        delays = await asyncio.gather(*[fetch(client, path) for path in PATHS])
    elapsed = time.perf_counter() - start
    print(
        f"httpx, 동시에: {len(delays)}개, 서버 대기 합 {sum(delays):.1f}초, 걸린 시간 {elapsed:.2f}초"
    )


if __name__ == "__main__":
    asyncio.run(main())
```

`fetch()` 두 판을 나란히 보면 다른 곳은 세 군데뿐이다.

| `requests` (동기) | `httpx.AsyncClient` (비동기) |
|---|---|
| `def fetch(session: requests.Session, ...)` | `async def fetch(client: httpx.AsyncClient, ...)` |
| `session.get(BASE_URL + path, timeout=10)` | `await client.get(path)` |
| `with requests.Session() as session:` | `async with httpx.AsyncClient(...) as client:` |

httpx는 requests와 거의 같은 모양으로 만들어졌다. `response.raise_for_status()`, `response.json()`, `response.status_code`, `response.text`가 모두 같다. 동기 클라이언트 `httpx.Client`도 있어서, 1장 1.2.6에서 `with httpx.Client() as client:`를 보았다. 같은 라이브러리로 동기와 비동기를 모두 쓸 수 있다는 것이 httpx의 장점이다. Anthropic과 OpenAI의 파이썬 SDK도 안에서 httpx를 쓴다.

### 7.6.4 클라이언트를 쓰는 습관

**클라이언트는 하나를 만들어 함께 쓴다.** `fetch()`가 클라이언트를 만들지 않고 **매개변수로 받는다.** `main()`에서 하나를 만들어 열 번의 요청이 함께 쓴다. 클라이언트는 안에 **연결 풀**(connection pool)을 갖고 있어서, 한 번 맺은 연결을 다음 요청에 다시 쓴다. 연결을 맺는 데도 시간이 걸리므로(특히 HTTPS) 요청마다 클라이언트를 새로 만들면 느려지고 자원도 낭비된다. 6.5.3에서 "의존성 주입"이라고 부른 모양이기도 하다. 클라이언트를 받으니 테스트에서 가짜를 넘길 수 있다(7.7.3).

**`base_url`과 `timeout`을 클라이언트에 정한다.** `base_url=BASE_URL`을 정해 두면 요청할 때는 `client.get("/ask/1")`처럼 경로만 쓴다. `timeout=10`은 이 클라이언트의 모든 요청에 걸리는 시간 제한이다. httpx는 requests와 달리 **기본 시간 제한이 5초**다. LLM API처럼 답이 오래 걸리는 곳에 쓸 때는 넉넉하게 늘린다. 시간이 넘으면 `httpx.TimeoutException`(의 하위 클래스)이 난다.

**동시 연결 수에도 기본 한도가 있다.** `httpx.AsyncClient`는 기본으로 연결을 최대 100개까지 연다. 요청 천 개를 `gather()`로 한꺼번에 보내면 100개만 진행되고 나머지는 클라이언트 안에서 연결이 빌 때까지 기다린다. 기다리는 시간도 시간 제한에 포함될 수 있으므로, 요청이 많을 때는 7.4.3의 세마포어로 **우리 쪽에서** 동시 실행 수를 정해 두는 것이 분명하다. 1장 (라)의 `summarize_all()`이 그렇게 했다.

**오류는 둘로 나뉜다.** 서버가 오류 상태 코드(4xx, 5xx)로 답하면 `raise_for_status()`가 `httpx.HTTPStatusError`를 일으킨다. 응답을 받지도 못했다면(서버가 꺼져 있거나 시간 초과) `httpx.ConnectError`, `httpx.TimeoutException` 같은 **`httpx.TransportError`**의 하위 예외가 난다. 가짜 서버를 끄고(`Ctrl+C`) `fetch_async.py`를 실행하면 `httpx.ConnectError: All connection attempts failed`를 볼 수 있다. 4.3.4의 표처럼 이 예외들을 "다시 시도할 것"과 "다시 시도해도 소용없는 것"으로 나누어 `async_retry()`의 `exceptions`에 넘기면 된다.

### 7.6.5 블로킹 코드를 섞으면 — `asyncio.to_thread()`

비동기 프로그램을 쓰다 보면 `async`를 지원하지 않는 라이브러리를 써야 할 때가 있다. 그 라이브러리의 블로킹 함수를 코루틴 안에서 그냥 부르면 어떻게 될까? 이벤트 루프가 멈췄는지 눈으로 볼 수 있도록 0.3초마다 "♥"를 출력하는 **심장 박동** 코루틴을 함께 돌린다.

`ch07/blocking_mix.py`

```python
"""비동기 코드 안에 블로킹 호출을 섞으면 — 그리고 asyncio.to_thread()."""

import asyncio

import requests
from fetch_sync import BASE_URL
from timeline import log, reset


async def heartbeat() -> None:
    """0.3초마다 살아 있다고 알린다. 이벤트 루프가 멈추면 이 출력도 멈춘다."""
    for _ in range(5):
        log("♥")
        await asyncio.sleep(0.3)


def fetch_blocking(path: str) -> int:
    """requests로 요청한다. 응답이 올 때까지 이 스레드는 아무것도 못 한다."""
    response = requests.get(BASE_URL + path, timeout=10)
    return response.status_code


async def bad() -> None:
    log("요청 보냄")
    status = fetch_blocking("/bad")  # 이벤트 루프를 1초 동안 붙잡는다
    log(f"응답 {status}")


async def good() -> None:
    log("요청 보냄")
    status = await asyncio.to_thread(fetch_blocking, "/good")
    log(f"응답 {status}")


async def main() -> None:
    print("--- async def 안에서 그냥 부르기")
    await asyncio.gather(heartbeat(), bad())
    print("--- asyncio.to_thread()로 부르기")
    reset()
    await asyncio.gather(heartbeat(), good())


if __name__ == "__main__":
    asyncio.run(main())
```

- **그냥 부르기** — 0.0초 다음 "♥"가 1.0초에야 나왔다. `fetch_blocking()`이 응답을 기다린 1초 동안 이벤트 루프 전체가 멈춰서 심장 박동도 멈췄다. 7.2.5의 `time.sleep()`과 같은 일이다. 웹 서버였다면 이 1초 동안 다른 모든 사용자의 요청이 멈춘다.
- **`asyncio.to_thread(함수, 인자...)`** — 블로킹 함수를 **별도의 스레드**에서 실행하고, 그 결과를 `await`할 수 있게 해 준다. 블로킹은 다른 스레드에서 일어나고, 이벤트 루프는 기다리는 동안 다른 코루틴을 계속 실행한다. 심장 박동이 0.3초마다 계속 뛰었다. 함수를 **부르지 않고** 함수와 인자를 따로 넘긴다는 것에 주의한다. `asyncio.to_thread(fetch_blocking("/good"))`이라고 쓰면 `fetch_blocking()`이 지금 이 자리에서 블로킹으로 실행된다.

`asyncio.to_thread()`는 7.1.4 표의 "스레드"를 asyncio와 함께 쓰는 가장 쉬운 방법이다. `async`를 지원하지 않는 라이브러리 호출, 큰 파일 읽기와 쓰기 같은 블로킹 입출력에 쓴다. 다만 CPU를 쓰는 계산은 스레드로 옮겨도 GIL 때문에 빨라지지 않는다(7.1.4). 이벤트 루프가 멈추지 않게 하는 효과만 있다.

**블로킹을 찾는 방법.** 7.2.5에서 ruff가 `time.sleep()`을 찾았다. ruff는 `async def` 안에서 직접 부른 `requests.get()`(ASYNC210)과 `open()`(ASYNC230)도 찾는다. 그런데 이 파일에서는 아무것도 찾지 못한다.

```
ruff check ch07/blocking_mix.py
```

```
All checks passed!
```

`bad()`가 부른 것은 일반 함수 `fetch_blocking()`이고, `requests.get()`은 그 안에 있기 때문이다. 함수를 한 번 거치면 ruff는 따라가지 못한다. 이럴 때는 asyncio의 **디버그 모드**가 도움이 된다. `asyncio.run(main(), debug=True)`로 실행하면, 이벤트 루프를 0.1초 넘게 붙잡은 코루틴을 알려 준다.

```
Executing <Task finished name='Task-3' coro=<bad() done, defined at .../ch07/blocking_mix.py:23> result=None ...> took 1.011 seconds
```

"`bad()` 코루틴이 한 번 실행되는 데 1.011초가 걸렸다." 즉 `await` 없이 1초 동안 루프를 붙잡았다는 뜻이다. 비동기 프로그램이 이유 없이 느리다면 디버그 모드로 한 번 돌려 본다.

| 블로킹 | 비동기 코드에서 쓸 것 |
|---|---|
| `time.sleep(초)` | `await asyncio.sleep(초)` |
| `requests.get(...)` | `await client.get(...)` (`httpx.AsyncClient`) |
| 큰 파일 읽기·쓰기 | `await asyncio.to_thread(함수, ...)` |
| `async`를 지원하지 않는 라이브러리 | `await asyncio.to_thread(함수, ...)` |
| CPU를 오래 쓰는 계산 | 프로세스(`ProcessPoolExecutor`), 또는 작업을 나눈다 |

작은 설정 파일 하나를 읽는 정도는 블로킹이라도 순식간에 끝나므로 신경 쓰지 않아도 된다. 문제는 **오래 걸리는** 블로킹이다. 네트워크는 언제나 오래 걸릴 수 있다고 생각한다.

pytest-asyncio는 이미 설치했다. 그런데도 실패한 이유는, pytest-asyncio가 기본으로 **표시가 붙은 테스트만** 맡기 때문이다. 표시는 6.5.6에서 배운 마커다. 테스트 함수 위에 `@pytest.mark.asyncio`를 붙인다.

```python
"""비동기 함수 테스트의 첫걸음."""

import asyncio

import pytest


async def add(a: int, b: int) -> int:
    await asyncio.sleep(0)
    return a + b


@pytest.mark.asyncio
async def test_add() -> None:
    assert await add(1, 2) == 3
```

`@pytest.mark.asyncio`가 붙은 테스트는 pytest-asyncio가 테스트마다 새 이벤트 루프를 만들어 실행한다. `pytest.ini`에 적은 `function`이 이 "테스트마다"다. 테스트 안에서 하는 일은 `asyncio.run(main())`의 `main()` 안에서 하는 일과 같다. `await`로 코루틴을 부르고, `gather()`로 동시에 실행하고, 결과를 `assert`한다.

**`await`를 빠뜨린 테스트.** 7.2.4의 실수는 테스트에서도 생긴다. 다음 테스트를 더해 본다.

```python
def test_add_without_await() -> None:
    assert add(1, 2) == 3
```

```
E        +  where <coroutine object add at 0x10b08a5a0> = add(1, 2)
```

비동기 함수를 테스트하는데 테스트 함수가 일반 `def`라면 `await`를 쓸 수 없다. `add(1, 2)`는 코루틴 객체이고, 코루틴 객체는 `3`과 같지 않다. 이 경우는 실패해서 다행이지만, `assert add(1, 2)`처럼 "참인지"만 확인했다면 코루틴 객체는 언제나 참으로 취급되어 **통과해 버린다.** mypy로 검사하면 `Non-overlapping equality check`(서로 같을 수 없는 것을 `==`로 비교한다)로 이 줄을 찾는다. 비동기 함수의 테스트는 `async def` + `@pytest.mark.asyncio` + `await`를 한 묶음으로 기억한다. 확인했으면 `test_add_without_await`를 지운다.

> **파일 전체에 마커 붙이기와 auto 모드**
> 6.5.6의 `pytestmark = pytest.mark.live`처럼 `pytestmark = pytest.mark.asyncio`를 파일 맨 위에 두면 파일의 모든 테스트에 마커가 붙는다. 다만 그 파일에 일반 `def` 테스트가 섞여 있으면 "비동기 함수가 아닌데 asyncio 마커가 붙었다"는 경고가 난다. 또 `pytest.ini`에 `asyncio_mode = auto`를 적으면 마커 없이도 **모든** `async def` 테스트를 pytest-asyncio가 맡는다. FastAPI 프로젝트의 예제에서 자주 보는 설정이다. 이 교재에서는 어느 테스트가 비동기인지 눈에 보이도록 마커를 하나씩 붙인다.

### 7.7.2 가짜 `sleep`으로 기다리지 않는 테스트

6.5.2에서 `retry(sleep=waits.append)`로 기다리는 함수를 바꿔 끼워, 3초를 기다리는 재시도를 0.01초 만에 테스트했다. `async_retry()`에도 같은 일을 하려고 하면 문제가 생긴다.

```python
waits: list[float] = []
call = async_retry(sleep=waits.append)(...)
```

```
mypy: error: Argument "sleep" to "async_retry" has incompatible type "Callable[[float], None]"; expected "Callable[[float], Awaitable[None]]"  [arg-type]
실행: TypeError: object NoneType can't be used in 'await' expression
```

`async_retry()`는 `await sleep(wait)`로 기다린다. `waits.append(1.0)`은 `None`을 돌려주므로 `await`할 수 없다. mypy가 실행하기 전에 알려 주고, 실행하면 `TypeError`가 난다. 가짜 `sleep`도 **`await`할 수 있는 것을 돌려주는** 함수, 즉 코루틴 함수여야 한다. 가짜 객체를 모아 두는 모듈을 만든다. 6장의 `fakes.py`와 이름이 겹치지 않게 짓는다(6.2.5).

`ch07/async_fakes.py`

```python
"""7장의 테스트에서 쓰는 가짜 객체들."""

import asyncio


class RecordingSleep:
    """기다리지 않고, 기다리려던 시간만 기록하는 가짜 asyncio.sleep."""

    def __init__(self) -> None:
        self.waits: list[float] = []

    async def __call__(self, seconds: float) -> None:
        self.waits.append(seconds)
        await asyncio.sleep(0)  # 기다리지는 않지만 다른 태스크에 차례를 넘긴다


class AsyncFlaky:
    """정해 둔 예외를 차례로 일으킨 뒤에 "성공"을 돌려주는 비동기 함수 객체."""

    def __init__(self, *errors: Exception) -> None:
        self.errors = list(errors)
        self.calls = 0

    async def __call__(self) -> str:
        self.calls += 1
        await asyncio.sleep(0)
        if self.errors:
            raise self.errors.pop(0)
        return "성공"
```

- `RecordingSleep` — `async def __call__`이 있어서 객체를 `await sleep(1.0)`처럼 부를 수 있다. 부르면 기다리지 않고 시간을 `waits`에 기록한다. 6.5.2의 `waits.append`가 하던 일을 비동기로 한다.
- `await asyncio.sleep(0)` — 0초 기다리기, 즉 **다른 태스크에 한 번 차례를 넘긴다**(실습 7-3의 1번). 진짜 `asyncio.sleep()`은 기다리는 동안 다른 태스크를 실행하게 해 준다. 가짜가 차례를 전혀 넘기지 않으면, 여러 태스크가 동시에 재시도하는 상황에서 진짜와 다르게 동작할 수 있다. 가짜도 진짜의 **중요한 성질**은 지켜야 한다.
- `AsyncFlaky` — 6.5.2의 `Flaky`를 비동기로 바꿨다. `async_retry()`가 감쌀 수 있는 "인자 없는 코루틴 함수"처럼 쓰인다.

`ch07/test_async_retry.py`

- `await call()` — 감싼 함수를 부르면 코루틴이 나오므로 `await`한다.

### 7.7.3 비동기 픽스처와 `httpx.MockTransport`

`fetch_async.py`의 `fetch()`를 테스트하고 싶다. 가짜 서버를 띄워 두고 테스트하면 6.5.1에서 본 문제(느리다, 바깥 상태에 기댄다)가 그대로 생긴다. httpx에는 **네트워크에 나가지 않고** 정해 둔 함수가 응답을 만들어 주는 장치가 있다. `httpx.MockTransport`다.

- `@pytest_asyncio.fixture` + `async def` + `yield` — **비동기 픽스처**다. 6.4.2의 `yield` 픽스처와 같은 모양이고, 준비와 정리에 `async with`를 쓸 수 있다. 클라이언트를 `async with`로 열고, 테스트에 넘기고(`yield`), 테스트가 끝나면 닫는다. 비동기 픽스처에는 `@pytest.fixture`가 아니라 `pytest_asyncio`의 `@pytest_asyncio.fixture`를 붙인다. `@pytest.fixture`를 붙이면 테스트가 `'test_fetch_returns_delay' requested an async fixture 'client', with no plugin or hook that handled it.`라는 오류로 실행되지 못한다. `pytest.ini`의 `asyncio_default_fixture_loop_scope`가 이런 비동기 픽스처가 쓸 이벤트 루프의 범위였다.
- 반환 타입 `AsyncIterator[httpx.AsyncClient]` — 비동기 제너레이터 함수이므로 7.5.1처럼 적는다. 6.4.2의 `Iterator[sqlite3.Connection]`과 같은 생각이다.
- `base_url="http://test"` — 어차피 네트워크에 나가지 않으므로 아무 주소나 된다.

`fetch()`가 클라이언트를 **매개변수로 받았기** 때문에 이런 테스트가 가능했다(7.6.4). `fetch()` 안에서 `httpx.AsyncClient()`를 직접 만들었다면 6.5.4의 `monkeypatch`를 써야 했을 것이다.

### 7.7.4 시간과 동시성을 테스트할 때

비동기 코드를 테스트할 때 "동시에 실행되었는가", "시간 제한이 걸렸는가"를 확인하고 싶어진다. 이때 조심할 것이 있다.

**걸린 시간을 `assert`하지 않는다.** `assert elapsed < 1.1`처럼 실제 시간을 확인하는 테스트는 컴퓨터가 바쁠 때나 느린 CI 서버(8장)에서 가끔 실패한다. 6.6.6에서 본 **들쭉날쭉한 테스트**가 된다. 대신 **세어서 확인한다.** 7.4.3의 `peak`처럼 가짜 객체가 "지금 동시에 몇 개가 진행 중인가"를 세게 하고, 최댓값이 기대한 값인지 `assert`한다. 실습 7-8의 `ScriptedAsyncLLM`이 이렇게 한다.

**시간 제한은 짧게, 지연은 길게.** 시간 제한이 동작하는지 확인할 때는 시간 제한을 `0.05`초처럼 아주 짧게 주고, 가짜가 `10`초처럼 **확실히 넘는** 시간을 기다리게 한다. 시간 제한에 걸리면 10초를 다 기다리지 않고 0.05초 만에 취소되므로 테스트는 빠르다. 경계에 가까운 값(시간 제한 1.0초, 지연 0.99초)은 컴퓨터 상태에 따라 결과가 달라지므로 피한다.

**재시도의 기다림은 가짜로.** 재시도 테스트에서 진짜 `asyncio.sleep`을 쓰면 테스트 하나에 몇 초가 걸린다. 7.7.2처럼 `RecordingSleep`을 주입하고, 기다리려던 시간을 확인한다. 6장 실습 6-7에서 "주입한 `sleep`을 쓰지 않는" 버그를 테스트가 3초 걸린 것으로 찾았던 것을 기억한다.

### 7.7.5 FastAPI의 `async def` 엔드포인트 읽기

1장 (나)의 FastAPI 코드를 다시 읽는다. "LLM 서비스 배포"에서 직접 만들 코드다.

```python
app = FastAPI()


@app.post("/chat")
async def chat(req: ChatRequest) -> ChatResponse:
    answer = await ask_llm(req.question, req.max_tokens)
    return ChatResponse(answer=answer)
```

이제 줄마다 읽을 수 있다. `@app.post("/chat")`은 등록 데코레이터(4.5.2), `ChatRequest`와 `ChatResponse`는 Pydantic 모델(5.6), `async def`와 `await`는 이 장이다. 남은 질문은 **왜 `async def`인가**다.

FastAPI로 만든 웹 서버는 이벤트 루프 **하나**에서 돌아간다. 사용자의 요청이 들어올 때마다 서버는 `chat()` 코루틴을 만들어 태스크처럼 실행한다. 사용자 백 명이 동시에 질문하면 `chat()` 코루틴 백 개가 이벤트 루프에서 함께 돈다. 각 코루틴이 `await ask_llm(...)`에서 LLM의 답을 기다리는 동안 이벤트 루프는 다른 사용자의 요청을 처리한다. 이 장의 `gather()`로 요청 스무 개를 동시에 보낸 것과 같은 일이 서버 쪽에서 일어난다.

그러니 FastAPI의 `async def` 안에서는 **이 장의 규칙이 그대로 적용된다.**

- `async def` 엔드포인트 안에서 `requests.get()`이나 `time.sleep()` 같은 블로킹 호출을 하면, 그동안 **서버 전체**가 멈춘다. 사용자 한 명의 요청 때문에 모든 사용자가 기다린다(7.6.5).
- LLM 호출은 `AsyncAnthropic`, `AsyncOpenAI` 같은 비동기 클라이언트로, HTTP 요청은 `httpx.AsyncClient`로 한다.

FastAPI는 엔드포인트를 일반 `def`로 쓰는 것도 허락한다.

```python
@app.get("/health")
def health() -> dict[str, str]:
    return {"status": "ok"}
```

일반 `def` 엔드포인트는 FastAPI가 **별도의 스레드에서** 실행한다. 7.6.5의 `asyncio.to_thread()`를 FastAPI가 대신 해 주는 셈이다. 그래서 `async`를 지원하지 않는 라이브러리를 꼭 써야 하는 엔드포인트는 일반 `def`로 쓰면 이벤트 루프를 붙잡지 않는다. 정리하면 다음과 같다.

| 엔드포인트 | 실행되는 곳 | 안에서 쓸 것 |
|---|---|---|
| `async def` | 이벤트 루프 | `await`하는 비동기 라이브러리만. 블로킹 호출 금지 |
| `def` | 별도의 스레드 | 블로킹 라이브러리를 써도 된다. `await`는 쓸 수 없다 |

스트리밍 응답도 이 장의 내용으로 읽힌다. FastAPI의 `StreamingResponse`에 7.5.1 같은 **비동기 제너레이터**를 넘기면, 제너레이터가 조각을 내놓을 때마다 사용자에게 흘려보낸다. 3.6.5의 상자에서 "웹 서버에서 스트리밍 응답을 받아 그대로 사용자에게 흘려보낼 때는 `async for`를 쓴다"고 한 것이 이것이다.

### 7.7.6 LLM SDK의 비동기 클라이언트 읽기

Anthropic과 OpenAI의 파이썬 SDK는 모두 동기 클라이언트와 비동기 클라이언트를 함께 제공한다. 실제 호출은 "LLM API 활용"에서 하고, 여기서는 코드의 모양을 읽는다. 3장 3.6.1처럼 모델 이름은 `MODEL`로 둔다.

**Anthropic — `AsyncAnthropic`**

```python
import asyncio

from anthropic import AsyncAnthropic

async def ask(question: str) -> str:
    message = await client.messages.create(
        model=MODEL,
        max_tokens=1024,
        messages=[{"role": "user", "content": question}],
    )
    return message.content[0].text


async def main() -> None:
    answers = await asyncio.gather(*[ask(q) for q in QUESTIONS])


async def stream_answer(question: str) -> None:
    async with client.messages.stream(
        model=MODEL,
        max_tokens=1024,
        messages=[{"role": "user", "content": question}],
    ) as stream:
        async for text in stream.text_stream:
            print(text, end="", flush=True)
```

- `AsyncAnthropic()` — 동기 클라이언트 `Anthropic()`의 비동기 판이다. 클라이언트는 7.6.4처럼 **하나를 만들어 함께 쓴다.** 안에서 `httpx.AsyncClient`를 쓴다.
- `await client.messages.create(...)` — 동기 클라이언트와 인자가 똑같고, 앞에 `await`만 붙는다. `message.content[0].text`는 답의 첫 블록의 글자다. 답에는 텍스트 말고 도구 호출 같은 다른 종류의 블록도 올 수 있으므로, 실제로는 2장의 `match` 문이나 `isinstance()`로 블록의 종류를 확인하고 꺼낸다.
- `asyncio.gather(*[ask(q) for q in QUESTIONS])` — 7.1.2의 `ask_all()`과 같다. 실제로는 7.4.3의 세마포어로 동시 실행 수를 제한한다.
- `async with client.messages.stream(...) as stream:` + `async for text in stream.text_stream:` — 3.6.1과 4.6.6에서 읽은 동기 스트리밍 코드에 `async`가 붙었다. 7.5의 `open_stream()`과 같은 모양이다.

**OpenAI — `AsyncOpenAI`**

```python
from openai import AsyncOpenAI

client = AsyncOpenAI()  # 환경 변수 OPENAI_API_KEY를 읽는다


async def ask(question: str) -> str | None:
    response = await client.chat.completions.create(
        model=MODEL,
        messages=[{"role": "user", "content": question}],
    )
    return response.choices[0].message.content


async def stream_answer(question: str) -> None:
    stream = await client.chat.completions.create(
        model=MODEL,
        messages=[{"role": "user", "content": question}],
        stream=True,
    )
    async for chunk in stream:
        delta = chunk.choices[0].delta.content
        if delta:
            print(delta, end="", flush=True)
```

3.6.1의 OpenAI 스트리밍 코드와 비교하면 `await`와 `async for`가 붙었을 뿐이다. `stream=True`를 주면 `await`한 결과가 **비동기 이터러블**이 되어 `async for`로 조각을 꺼낸다.

| | 동기 | 비동기 |
|---|---|---|
| 클라이언트 | `Anthropic()`, `OpenAI()` | `AsyncAnthropic()`, `AsyncOpenAI()` |
| 요청 | `client.messages.create(...)` | `await client.messages.create(...)` |
| 스트리밍 | `with ... as stream:` / `for` | `async with ... as stream:` / `async for` |
| 쓰는 곳 | 스크립트, 노트북의 간단한 실험 | 여러 요청을 동시에, FastAPI 같은 비동기 서버 |

**SDK와 우리가 만든 장치.** 4.3.7에서 "SDK는 연결 오류, 시간 초과, 429, 5xx를 스스로 몇 번 다시 시도한다. 재시도는 한 층에서만 한다"고 했다. 비동기 클라이언트도 같다. `AsyncAnthropic(max_retries=..., timeout=...)`으로 재시도 횟수와 시간 제한을 정할 수 있다. 그러니 실제 SDK를 쓸 때는 이 장의 `async_retry()`를 그 위에 또 붙이지 않는다. 반면 **동시 실행 수 제한은 SDK가 해 주지 않는다.** `gather()`로 요청 천 개를 보내면 SDK는 천 개를 보내려 한다. 세마포어는 우리가 건다.

이 장의 가짜 클라이언트를 실제 SDK로 바꿔 끼우는 것은 간단하다. 실습 7-8의 `AsyncLLMClient` 프로토콜에 맞춰 SDK를 감싸는 클래스를 만들면 된다. 5.5.4와 6.5.6의 `RealLLM`처럼 비워 둔다.

## 실습 7-8. 종합 — 문서 일괄 요약기, 비동기 판

6장 실습 6-7의 문서 일괄 요약기(`doc_summarizer.py`)는 조각을 **차례로** 요약했다. 조각이 백 개이고 요약 하나에 3초가 걸리면 5분이다. 이 장의 내용을 모두 써서 조각을 **동시에** 요약하는 비동기 판을 만든다. 9장 종합 실습의 중심이 되는 코드다.

3장·4장·5장의 종합 실습에서는 함수의 이름과 독스트링이 주어지고 본문을 채웠다. 6장에서는 거꾸로 코드가 주어지고 테스트를 채웠다. 이번에는 **둘 다 주어진다.** 함수의 이름, 타입 힌트, 독스트링, 그리고 **완성된 테스트**가 주어진다. 본문을 채워 테스트를 모두 통과시킨다. 테스트를 먼저 쓰고 그것을 통과하도록 코드를 쓰는 방식을 **테스트 주도 개발**(test-driven development, TDD)이라고 한다. 6.1.4에서 "새 요구를 먼저 테스트로 적는다"고 한 것을 끝까지 밀고 간 방식이다.

```python
import asyncio
import json

class Summary(BaseModel):
    """LLM이 조각마다 돌려주어야 하는 요약."""

    summary: str = Field(min_length=1, max_length=200, description="200자 이내의 요약")
    keywords: list[str] = Field(
        default_factory=list, max_length=3, description="핵심어 3개 이하"
    )


def split_text(text: str, size: int) -> list[str]:
    """text를 size글자씩 나눈 조각의 리스트를 돌려준다. 빈 글이면 빈 리스트다."""
    if size < 1:
        raise ValueError(f"size는 1 이상이어야 한다: {size}")
    return [text[i : i + size] for i in range(0, len(text), size)]


def build_prompt(piece: str) -> str:
    """조각 하나를 요약해 Summary의 JSON 스키마에 맞는 JSON만 답하라는 프롬프트."""
    schema = json.dumps(Summary.model_json_schema(), ensure_ascii=False)
    return f"다음 글을 요약해 이 JSON 스키마에 맞는 JSON만 답하라.\n{schema}\n\n<글>\n{piece}\n</글>"


def parse_summary(answer: str) -> Summary:
    """응답에서 첫 '{'부터 마지막 '}'까지를 잘라 Summary로 검증한다.

    검증하지 못하면 ValidationError를 일으킨다.
    """
    start, end = answer.find("{"), answer.rfind("}")
    if start != -1 and end != -1:

    return Summary.model_validate_json(answer)
```

- **`AsyncLLMClient`** — 6장의 `LLMClient`에서 `complete()`가 `async def`가 되었다. 프로토콜에서도 `async def`로 적으면 "`await`해서 `str`이 나오는 `complete()`가 있는 것"이라는 약속이 된다. 동기 `complete()`를 가진 6장의 `ScriptedLLM`을 넘기면 mypy가 알려 준다.
- **`Summary`, `build_prompt()`, `parse_summary()`** — 6장 실습 6-7과 같다. **`split_text()`**는 실습 6-7에서 찾은 버그를 고친 판이다. 네 개 모두 이미 채워져 있다.
- **`load_pieces()`, `write_jsonl()`** — 6장의 `summarize_file()`과 `summarize_folder()`가 하던 파일 읽기와 쓰기를 **일반 함수로 따로** 뺐다. 7.6.5의 표대로, 비동기 코드에서는 파일 입출력을 `asyncio.to_thread()`로 부르기 위해서다. 따로 빼니 비동기 없이 테스트하기도 쉽다.
- **`summarize_piece()`** — 조각 **하나**를 맡는다. 6장의 `summarize_file()`이 반복문 안에서 하던 일이다. 시간 제한, 재시도, 응답 검증을 모두 여기서 하고, 어떤 실패든 `"error"` 레코드로 바꿔 **예외를 일으키지 않는다.** 7.3.7의 "실패를 각 작업 안에서 잡아 결과로 바꾼다"다.
- **`summarize_folder()`** — 모든 조각을 동시에 `summarize_piece()`에 맡기되, 동시 실행 수를 `max_concurrency`로 제한한다. 결과는 **끝난 순서가 아니라** 파일 이름과 조각 번호 순으로 저장한다.

```python
OK = '{"summary": "요약", "keywords": ["핵심"]}'


@dataclass
class Slow:
    """seconds초 기다렸다가 answer를 돌려주라는 대본 항목."""

    seconds: float
    answer: str = OK


class ScriptedAsyncLLM:
    """프롬프트에 든 표시 글자마다 정해 둔 응답·예외·지연을 차례로 내놓는 가짜 비동기 클라이언트.

    정해 둔 것이 없거나 다 쓴 조각에는 delay초 기다린 뒤 OK를 돌려준다.
    active는 지금 처리 중인 요청 수, peak는 그 최댓값이다.
    """

    def __init__(
        self,
        script: dict[str, list[str | Exception | Slow]] | None = None,
        *,
        delay: float = 0.0,
    ) -> None:
        self.script = {mark: list(items) for mark, items in (script or {}).items()}
        self.delay = delay
        self.prompts: list[str] = []
        self.active = 0
        self.peak = 0

    async def complete(self, prompt: str, *, max_tokens: int = 1024) -> str:
        self.prompts.append(prompt)
        self.active += 1
        self.peak = max(self.peak, self.active)
        try:
            item = self._next_item(prompt)
            if isinstance(item, Slow):
                await asyncio.sleep(item.seconds)
                return item.answer
            await asyncio.sleep(self.delay)
            if isinstance(item, Exception):
                raise item
            return item
        finally:
            self.active -= 1

    def _next_item(self, prompt: str) -> str | Exception | Slow:
        for mark, items in self.script.items():
            if mark in prompt and items:
                return items.pop(0)
        return OK
```

```python
"""가짜 LLM으로 문서 일괄 요약기를 돌려 보고, 동시 실행 수에 따른 시간을 비교한다."""

import asyncio
import random
import tempfile
import time
from pathlib import Path

from async_retry import RateLimitError
from async_summarizer import summarize_folder


class RandomLLM:
    """0.2~0.6초 걸려 답하고, 가끔 아주 늦거나 요청 한도를 넘는 가짜 클라이언트."""

    def __init__(self, seed: int) -> None:
        self.rand = random.Random(seed)
        self.calls = 0

    async def complete(self, prompt: str, *, max_tokens: int = 1024) -> str:
        self.calls += 1
        roll = self.rand.random()
        if roll < 0.05:
            await asyncio.sleep(10.0)  # 아주 늦는 답 — 시간 제한에 걸린다
        elif roll < 0.10:
            raise RateLimitError("요청 한도 초과", retry_after=0.5)
        await asyncio.sleep(self.rand.uniform(0.2, 0.6))
        return '{"summary": "가짜 요약", "keywords": ["가짜"]}'


def make_docs(folder: Path) -> None:
    """1100글자짜리 문서 다섯 개를 만든다."""
    for n in range(1, 6):
        (folder / f"doc{n}.txt").write_text(
            f"{n}번 문서의 내용. " * 100, encoding="utf-8"
        )


async def main() -> None:
    with tempfile.TemporaryDirectory() as tmp:
        folder = Path(tmp)
        make_docs(folder)
        out_path = folder / "summaries.jsonl"
        for max_concurrency in (1, 5, 25):
            client = RandomLLM(seed=32)
            start = time.perf_counter()
            ok, failed = await summarize_folder(
                client,
                folder,
                out_path,
                size=200,
                max_concurrency=max_concurrency,
                timeout=1.0,
            )
            elapsed = time.perf_counter() - start
            print(
                f"동시 {max_concurrency:2}개: 성공 {ok}, 실패 {failed}, "
                f"호출 {client.calls}번, {elapsed:.1f}초"
            )
        print(out_path.read_text(encoding="utf-8").splitlines()[0])


if __name__ == "__main__":
    asyncio.run(main())
```

- `tempfile.TemporaryDirectory()` — 임시 폴더를 만들고 `with` 블록이 끝나면 지운다. 6.4.4의 `tmp_path`가 테스트에서 해 주던 일을 스크립트에서 한다. 실습 폴더에 시험용 파일이 남지 않는다.

- 가짜 서버(7.6.1)에 요약하는 척하는 경로를 더하고, `httpx.AsyncClient`로 그 서버에 요청하는 `HttpLLM` 클래스를 만들어 `AsyncLLMClient` 대신 넘긴다. 프로토콜만 맞추면 `summarize_folder()`는 고치지 않아도 된다.
- 9장에서는 이 모듈을 명령행 도구와 패키지로 만든다. 지금 `summarize_folder()`를 부르는 `main()`을 만든다면 어떤 매개변수를 명령행 옵션으로 받아야 할지 목록을 `notes.md`에 적어 둔다.

## 정리

| 항목 | 핵심 |
|---|---|
| 입출력 대기 | 네트워크·디스크·데이터베이스를 기다리는 시간. LLM 호출의 대부분이다 |
| 비동기 | 기다리는 시간을 **겹치게** 한다. 일을 빨리 하게 만드는 것이 아니다 |
| 동시성과 병렬성 | 번갈아 진행하기(asyncio, 스레드)와 정말 같은 순간에 실행하기(프로세스). CPU 계산은 asyncio로 빨라지지 않는다 |
| 코루틴 | `async def`로 만든 함수를 부르면 코루틴 객체가 나온다. 본문은 `await`나 `asyncio.run()`이 실행할 때 돈다 |
| `await` | 결과가 나올 때까지 기다리고, 그동안 다른 코루틴에 자리를 내준다. 코루틴 함수 안에서만 쓴다 |
| 이벤트 루프 | 실행할 수 있는 코루틴을 다음 `await`까지 실행하기를 되풀이한다. `asyncio.run()`이 만든다. 프로그램 입구에서 한 번 |
| `await` 빠뜨리기 | 값 대신 코루틴 객체, 엉뚱한 `TypeError`, `was never awaited` 경고. mypy의 `unused-coroutine`이 찾는다 |
| 블로킹 | `time.sleep()`, `requests.get()`은 루프 전체를 멈춘다. ruff의 `ASYNC2xx`, `asyncio.run(..., debug=True)` |
| 대화형 셸과 Jupyter | `python -m asyncio`와 Jupyter는 루프가 이미 돈다. `await`를 바로 쓰고 `asyncio.run()`은 쓰지 않는다 |
| 태스크 | `asyncio.create_task()`로 기다리기 **전에** 출발시킨다. 다음 `await`에서 실행되기 시작한다. 이름으로 붙잡아 둔다 |
| `gather()` | 여러 개를 함께 출발시키고 결과를 **넘긴 순서대로** 모은다. 실패하면 첫 예외를 올리고 나머지는 계속 돈다 |
| `return_exceptions=True` | 예외를 결과 자리에 담는다. 일부 실패를 견뎌야 할 때 |
| `as_completed()` | 끝나는 순서대로 하나씩. 진행률 표시 |
| `TaskGroup` | `async with`로 묶는다. 하나가 실패하면 나머지를 취소하고 `ExceptionGroup`으로 올린다 |
| `ExceptionGroup`, `except*` | 동시에 난 여러 예외의 묶음. `except*`는 종류별로 골라 받고, 맞는 블록이 모두 실행된다 |
| `asyncio.timeout()` | 시간이 다 되면 블록 안의 일을 취소하고 `TimeoutError`. 시도 하나마다 거는지, 전체에 거는지 정한다 |
| 취소 | `task.cancel()` → 멈춘 `await` 자리에서 `CancelledError`. 정리는 `finally`에. 잡았으면 다시 `raise` |
| `Semaphore` | `async with limit:`으로 동시 실행 수를 제한한다. 하나를 만들어 함께 쓴다. 시간당 요청 한도와는 다르다 |
| 비동기 재시도 | 래퍼도 `async def`, 안에서 `await func()`, `await sleep()`. 동기 데코레이터는 비동기 함수를 다시 시도하지 못하고, mypy도 못 찾는다 |
| 비동기 제너레이터 | `async def` + `yield`. `async for`로 꺼내고 `aclose()`로 닫는다. `AsyncIterator`, `AsyncGenerator` |
| `async with` | 들어가고 나가는 일에 기다림이 있을 때. `__aenter__`/`__aexit__`, `@asynccontextmanager` |
| `httpx.AsyncClient` | requests와 같은 모양에 `await`. 하나를 만들어 함께 쓴다. `base_url`, `timeout`(기본 5초) |
| `asyncio.to_thread()` | 블로킹 함수를 별도의 스레드에서 실행하고 결과를 `await`한다. 함수와 인자를 따로 넘긴다 |
| pytest-asyncio | `@pytest.mark.asyncio` + `async def` 테스트. 비동기 픽스처는 `@pytest_asyncio.fixture`. 설정은 `pytest.ini` |
| 가짜 `sleep` | `async def __call__`로 기록만 하는 `RecordingSleep`. `await asyncio.sleep(0)`으로 차례는 넘긴다 |
| `MockTransport` | 네트워크 대신 함수가 응답을 만든다. 클라이언트를 매개변수로 받아야 바꿔 끼울 수 있다 |
| 시간 테스트 | 걸린 시간 대신 센 숫자(`peak`)를 확인한다. 시간 제한은 짧게, 지연은 길게 |
| FastAPI | `async def` 엔드포인트는 이벤트 루프에서, `def` 엔드포인트는 스레드에서. `async def` 안에서 블로킹 금지 |
| 비동기 SDK | `AsyncAnthropic`, `AsyncOpenAI`. `await client.….create(...)`, `async with … stream`, `async for`. 재시도는 SDK가, 동시 실행 수 제한은 우리가 |
