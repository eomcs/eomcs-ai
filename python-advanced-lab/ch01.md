[파이썬 중급](README.md) 과정의 첫 장이다. 이 장에서는 새 문법을 배우기 전에 세 가지를 준비한다.

- **중급 과정의 지도** — 기초 과정 10장의 선택 활동에서 "아직 배우지 않은 문법"으로 적어 둔 것이 이 과정의 어느 장에서 나오는지 확인한다. LLM SDK, FastAPI, LangChain의 예제 코드에서 이 과정의 문법이 어떤 모습으로 등장하는지 미리 본다.
- **실습 환경** — 파이썬 3.12 이상인지 확인하고, 이 과정 전체에서 쓸 실습 폴더·가상환경·Git 저장소를 만든다. VS Code의 Pylance로 정의로 이동하고 타입 정보를 보면서 남이 쓴 라이브러리 코드를 열어 본다.
- **기초 과정 점검** — 이 과정이 기대는 기초 개념 여섯 가지(변수는 객체를 가리키는 이름, 함수도 값, `*args`/`**kwargs`, 클래스와 `self`, 예외의 전파, `with` 문)를 다시 확인한다.

## 1.1 중급 과정의 지도

### 1.1.1 "아직 배우지 않은 문법"

기초 과정 10장의 선택 활동(1단계 결과물 다시 읽기)에서 이해하지 못한 코드를 표로 정리하면서, **아직 배우지 않은 문법**은 이름만 적어 두자고 했다. 그때 예로 든 다섯 가지가 이 과정에서 모두 나온다.

| 코드의 모양 | 이름 | 배우는 장 |
|---|---|---|
| `[t.amount for t in items if t.kind == "지출"]` | 리스트 컴프리헨션 | 2장 |
| `match message:` 다음에 `case {"type": "text"}:` | `match` 문(구조적 패턴 매칭) | 2장 |
| 함수 안에 `return` 대신 `yield`가 있다 | 제너레이터 함수 | 3장 |
| `def 이름(func):` 안에 `def wrapper(*args, **kwargs):`가 또 있다 | 데코레이터 만들기 | 4장 |
| `async def`, `await`, `async with`, `async for` | 코루틴, 비동기 프로그래밍 | 7장 |

이 밖에도 1단계 코드나 라이브러리 문서에서 다음과 같은 줄을 보았을 수 있다. 이것들도 이 과정에서 다룬다.

| 코드의 모양 | 무엇인가 | 배우는 장 |
|---|---|---|
| `first, *rest = items`, `{**defaults, **options}` | 확장 언패킹, 딕셔너리 병합 | 2장 |
| `if (n := len(items)) > 10:` | 할당 표현식(바다코끼리 연산자) | 2장 |
| `@lru_cache`, `@classmethod`, `@tool`, `@app.get("/")` | 데코레이터 사용 | 4장 |
| `def first[T](items: list[T]) -> T:`, `Iterator[str]`, `Protocol` | 타입 힌트 심화 | 5장 |
| `class Question(BaseModel):` | Pydantic 모델 | 5장 |
| `def test_...():`, `@pytest.fixture`, `assert` | pytest 테스트 | 6장 |
| `[project]`, `dependencies = [...]`가 적힌 `pyproject.toml` | 프로젝트 설정 파일 | 8장 |

선택 활동을 해서 `REVIEW.md`가 있다면 지금 열어 본다. "그때 몰랐던 것" 열에 적은 문법 하나하나 옆에 위 표의 장 번호를 적어 둔다. 실습 1-1에서 이 표를 다시 쓴다.

### 1.1.2 같은 일을 더 짧게 — 가계부 요약으로 미리 보기

기초 과정 10장에서 만든 가계부 요약 프로그램의 `ledger/core.py`에는 거래 목록에서 수입과 지출을 합하는 반복문이 있었다(기초 과정 10.2.5).

```python
income = 0
expense = 0
by_category = defaultdict(int)  # {분류: 금액}
for t in transactions:
    if t.kind == "수입":
        income += t.amount
    else:
        expense += t.amount
        by_category[t.category] += t.amount
```

이 과정의 2장과 3장을 마치면 수입과 지출의 합계를 다음처럼 쓸 수 있게 된다.

```python
income = sum(t.amount for t in transactions if t.kind == "수입")
expense = sum(t.amount for t in transactions if t.kind == "지출")
```

괄호 안의 `t.amount for t in transactions if t.kind == "수입"`은 "거래마다, 수입이면, 금액을" 차례로 내놓는 **제너레이터 표현식**이다(3장). 한 줄이 "무엇을 구하는가"를 그대로 말한다.

그렇다고 원래 코드가 틀린 것은 아니다. 원래 반복문은 거래 목록을 **한 번만** 훑으면서 수입, 지출, 분류별 합계를 함께 구한다. 짧게 바꾼 코드는 목록을 두 번 훑고, 분류별 합계는 아직 구하지 못했다. 분류별 합계까지 컴프리헨션으로 억지로 바꾸면 오히려 읽기 어려워진다. 2장의 "컴프리헨션을 쓰지 않을 때"에서 이런 판단을 연습한다. 이 과정에서 배우는 것은 **더 짧게 쓰는 방법**과 함께, **언제 짧게 쓰지 않을지 고르는 기준**이다.

가계부 프로그램에는 이 과정의 다른 장으로 이어지는 곳도 많다. 기초 과정과 개발 도구 과정에서 손으로 하던 일이 이 과정에서 도구로 바뀐다.

| 기초·개발 도구 과정에서 한 일 | 그때의 방식 | 이 과정에서 | 장 |
|---|---|---|---|
| 시험 파일로 결과 확인 | `check_samples.py`를 직접 만들어 기대한 결과와 비교했다 | pytest로 테스트를 쓰고, VS Code 테스트 탐색기로 실행한다 | 6장 |
| 자료형 검사 | `Transaction.__post_init__`에서 `isinstance()`로 하나씩 검사했다. 주석에 "타입 힌트는 실행 중에 검사되지 않으므로"라고 적었다 | 실행 **전에** mypy가 타입 힌트를 검사하고, 실행 **중에는** Pydantic이 검사한다 | 5장 |
| 반복되는 처리 묶기 | 비슷한 `try`/`except`를 함수마다 썼다 | 데코레이터와 컨텍스트 관리자로 한 곳에 모은다 | 4장 |
| 패키지 목록 | `requirements.txt`, `requirements-dev.txt`(개발 도구 10.7.1) | `pyproject.toml` 하나에 의존성과 도구 설정을 모은다 | 8장 |
| 실행 방법 | `python main.py samples/2026-10.csv` | 설치하면 바로 실행되는 명령을 만든다(`ledger samples/2026-10.csv`) | 8장 |
| 저장소에 올릴 때마다 검사 | 커밋하기 전에 손으로 `check_samples.py`를 실행했다 | GitHub Actions가 푸시할 때마다 ruff·mypy·pytest를 실행한다 | 8장(선택) |

이 과정의 9장 선택 활동에서는 가계부 프로그램에 pytest 테스트를 먼저 붙이고, 이 과정에서 배운 문법으로 다시 작성한 뒤 테스트가 그대로 통과하는지 확인한다. 지금은 위 표만 기억해 두면 된다.

### 1.1.3 LLM 코드에서 만나는 모양

이 과정 다음에 배울 "LLM API 활용", "RAG", "에이전트 개발", "LLM 서비스 배포"의 코드에는 이 과정의 문법이 빠짐없이 나온다. 다섯 가지 예를 미리 본다. **지금 이해하지 못해도 된다. 실행하지도 않는다.** 모양을 눈에 익히고, 어느 줄이 어느 장의 내용인지만 확인한다. 이 장의 마지막과 이 과정의 마지막에 다시 보면 같은 코드가 다르게 읽힐 것이다.

코드는 모양을 보여 주려고 줄인 것이다. 라이브러리의 함수 이름과 인자는 버전에 따라 달라질 수 있다.

**(가) LLM의 응답을 조각조각 받아 바로 출력하기 — "LLM API 활용"**

```python
import anthropic

client = anthropic.Anthropic()  # API 키는 환경 변수에서 읽는다

with client.messages.stream(
    model=MODEL,
    max_tokens=1024,
    messages=[{"role": "user", "content": question}],
) as stream:
    for text in stream.text_stream:
        print(text, end="", flush=True)
```

- `with ... as stream:` — 기초 과정에서 파일을 열 때 쓴 `with` 문이다. 이 객체가 `with` 문에서 어떻게 동작하는지는 4장(컨텍스트 관리자 만들기)에서 직접 만들어 본다.
- `for text in stream.text_stream:` — 응답이 다 올 때까지 기다리지 않고 **도착하는 대로** 한 조각씩 받는다. `text_stream`이 이터레이터이기 때문이다. 3장에서 가짜 스트림을 제너레이터로 만들어 똑같이 해 본다.

**(나) 웹 요청을 받아 LLM에게 묻고 답하기 — "웹·API 기초", "LLM 서비스 배포"**

```python
from fastapi import FastAPI
from pydantic import BaseModel

app = FastAPI()


class ChatRequest(BaseModel):
    question: str
    max_tokens: int = 512


class ChatResponse(BaseModel):
    answer: str


@app.post("/chat")
async def chat(req: ChatRequest) -> ChatResponse:
    answer = await ask_llm(req.question, req.max_tokens)
    return ChatResponse(answer=answer)
```

- `class ChatRequest(BaseModel):` — 데이터 클래스처럼 생겼지만, 들어온 값이 타입에 맞는지 **실행 중에 검사**한다. 5장.
- `@app.post("/chat")` — 함수를 "`/chat` 주소로 들어온 요청을 처리할 함수"로 **등록**하는 데코레이터다. 4장에서 등록 데코레이터를 직접 만든다.
- `async def`, `await` — LLM이 답하는 몇 초 동안 다른 요청도 처리할 수 있게 하는 비동기 함수다. 7장.
- `-> ChatResponse` — 타입 힌트다. FastAPI는 이 힌트를 읽어서 응답의 모양을 정한다. 5장.

**(다) LLM이 부를 수 있는 도구 정의하기 — "에이전트 개발"**

```python
from langchain_core.tools import tool


@tool
def search_docs(query: str, top_k: int = 3) -> list[str]:
    """사내 문서에서 query와 관련된 문단을 찾는다."""
    hits = index.search(query)
    return [hit.text for hit in hits[:top_k]]
```

- `@tool` — 이 함수의 이름, 매개변수의 **타입 힌트**, **독스트링**을 읽어서 LLM에게 보여 줄 도구 설명을 만든다. 기초 과정에서 독스트링과 타입 힌트를 꼬박꼬박 쓴 것이 여기서 그대로 쓰인다. 4장과 5장.
- `[hit.text for hit in hits[:top_k]]` — 리스트 컴프리헨션이다. 2장.

**(라) 여러 문서를 동시에 요약하기 — "LLM API 활용", "RAG"**

```python
import asyncio

import httpx


async def summarize_all(docs: list[str]) -> list[str]:
    limit = asyncio.Semaphore(5)  # 동시에 5개까지만
    async with httpx.AsyncClient(timeout=30) as http:
        tasks = [summarize(http, doc, limit) for doc in docs]
        return await asyncio.gather(*tasks)
```

- 문서 100개를 하나씩 요약하면 100번 기다려야 한다. 동시에 보내면 기다리는 시간이 겹친다. 다만 API에는 요청 한도가 있으므로 한 번에 보내는 수를 제한한다(`Semaphore`). 7장.
- `asyncio.gather(*tasks)` — 기초 과정 4.2.8에서 배운 "호출할 때 `*`로 풀어서 넘기기"다.

**(마) 긴 문서를 조각으로 나누고, 그 함수를 테스트하기 — "RAG", "LLM 평가(Evals) 심화"**

```python
from collections.abc import Iterator

import pytest


def chunk(text: str, size: int = 500) -> Iterator[str]:
    for start in range(0, len(text), size):
        yield text[start : start + size]


@pytest.mark.parametrize("size", [1, 3, 500])
def test_chunk_keeps_all_text(size):
    text = "가나다라마바사"
    assert "".join(chunk(text, size)) == text
```

- `yield` — 조각을 한꺼번에 리스트로 만들지 않고 **필요할 때 하나씩** 만든다. 조각을 모두 담은 리스트를 따로 만들지 않으므로 그만큼 메모리를 아낀다. 다만 이 예에서는 원문 `text`가 이미 통째로 메모리에 올라와 있다. 원문까지 조금씩 읽으려면 파일을 줄 단위로 읽는 제너레이터와 연결해야 한다. 3장.
- `-> Iterator[str]` — "문자열을 하나씩 내놓는 것"을 돌려준다는 타입 힌트다. 5장.
- `@pytest.mark.parametrize` — 같은 테스트를 입력만 바꿔 세 번 실행한다. 조각의 크기가 1이든 500이든, 조각을 이어 붙이면 원래 글이 되어야 한다. 6장.

다섯 개의 예를 보면 이 과정의 문법이 **따로따로가 아니라 한데 섞여** 나온다는 것을 알 수 있다. (라)의 세 줄에 비동기, 컴프리헨션, 타입 힌트, 언패킹이 다 있다. 그래서 이 과정의 장은 앞 장의 내용을 계속 다시 쓴다.

### 1.1.4 이 과정의 장

| 장 | 다루는 것 | 기초 과정에서 이어지는 곳 | 이후 과정에서 쓰이는 곳 |

### 1.1.5 이 과정을 공부하는 방법

**실습 저장소 하나, 장마다 커밋**

기초 과정에서는 `~/python-lab`, 개발 도구 과정에서는 `~/devtools-lab`에 장별 폴더를 만들었다. 이 과정에서는 홈 폴더 아래 `python-advanced-lab` 폴더를 만들고, 이 폴더 **전체를 하나의 Git 저장소**로 만든다. 장별 폴더(`ch01`, `ch02`, …)에 실습 파일을 두고, 장을 마칠 때마다 커밋한다. 개발 도구 과정에서 배운 Git을 이 과정 내내 쓰는 것이다. 실습하다가 코드를 망가뜨려도 `git diff`로 무엇을 바꿨는지 보고, `git restore`로 되돌릴 수 있다(개발 도구 5.4, 5.7).

**예측하고, 실행하고, 확인한다**

이 과정의 문법은 "짧은 코드가 많은 일을 하는" 문법이다. 한 줄짜리 컴프리헨션 안에 반복과 조건이 들어 있고, `@` 한 줄이 함수를 통째로 바꾼다. 이런 코드는 눈으로만 읽으면 아는 것 같은 착각이 들기 쉽다. 그래서 이 과정에서는 다음 순서를 습관으로 만든다.

1. 코드를 실행하기 **전에** 결과를 예측한다. 머릿속으로 해도 되지만, 적어 두면 더 좋다.
2. 실행한다. 대화형 셸에서 한 줄씩 해 보는 것이 가장 빠르다.
3. 예측과 다르면 **디버거로 한 줄씩** 따라가며 어디서 생각과 달라졌는지 찾는다.

1.3의 기초 과정 점검과 실습 1-3이 이 순서를 연습하는 자리다.

**AI 도구는 이렇게 쓴다**

AI 코딩 도구는 이 과정의 문법을 아주 좋아한다. 반복문 열 줄을 컴프리헨션 한 줄로 바꿔 주고, 함수마다 데코레이터를 붙여 준다. 이 과정의 목표는 그 코드를 **받아들일지 판단할 수 있게** 되는 것이다. 개발 도구 과정에서 세운 원칙(AI가 실행하려는 명령은 한 문장으로 설명할 수 있을 때만 허락한다, 개발 도구 3.8)을 코드에도 적용한다.

- AI가 쓴 코드를 받아들이기 전에, 그 코드가 무엇을 하는지 **한 문장으로** 말할 수 있는지 확인한다.
- 말할 수 없으면 AI에게 설명을 부탁하되, 설명을 그대로 믿지 말고 대화형 셸이나 디버거로 **직접 확인한다.**
- 6장을 배운 뒤부터는 **테스트로 확인한다.** AI가 고친 코드가 테스트를 통과하는지, 테스트가 정말 그 동작을 검사하는지 본다.

**명령 표기**

이 과정의 명령은 대부분 **가상환경이 활성화된 상태**에서 실행한다. 가상환경 안에서는 macOS에서도 `python`이 동작하므로(기초 과정 9.1.4), 1.2.3에서 가상환경을 만든 뒤로는 두 운영체제 모두 `python`으로 적는다. 가상환경을 만들기 전의 명령만 macOS에서 `python3`로 적는다.

### 실습 1-1. 지도 그리기

1.2에서 실습 폴더를 만든 뒤 `~/python-advanced-lab/ch01/map.md` 파일을 만들어 이 실습의 결과를 적는다. 폴더가 아직 없으므로 지금은 종이나 메모 앱에 적어 두었다가 1.2를 마친 뒤 옮겨도 된다.

### 1.2.1 파이썬 버전 확인

이 과정은 **파이썬 3.12 이상**을 기준으로 한다. 기초 과정도 3.12 이상을 기준으로 했으므로 대부분은 이미 조건을 갖췄다. 그래도 이 과정에서는 버전이 더 중요하다. 이 과정에서 배우는 문법 중 몇 가지는 비교적 최근에 추가되었기 때문이다.

| 추가된 버전 | 기능 | 배우는 장 |
|---|---|---|
| 3.10 | `match` 문, 타입 힌트의 `int \| None` | 2장, 5장 |
| 3.11 | `asyncio.TaskGroup`, `asyncio.timeout()`, `ExceptionGroup`과 `except*` | 7장 |
| 3.12 | 제네릭 문법(`def first[T](...)`), `type` 별칭 문, `itertools.batched()` | 5장, 3장 |

3.11 이하에서 3.12의 문법을 쓰면 `SyntaxError`가 나고, 3.12에서 추가된 함수를 쓰면 `AttributeError`가 난다. 인터넷이나 AI가 알려 준 코드가 내 파이썬에서 안 될 때, 버전 차이가 원인인 경우가 꽤 있다. **공식 문서의 각 기능 설명 끝에 있는 "Added in version 3.12." 같은 표시**를 확인하는 습관을 들이자.

터미널에서 버전을 확인한다.

```
# macOS
python3 --version

# Windows
python --version
```

```
Python 3.13.2
```

3.12 이상이면 된다. 3.11 이하라면 기초 과정 1.2.1처럼 공식 사이트(https://www.python.org/downloads/)에서 최신 버전을 설치한다. 개발 도구 과정에서 배운 패키지 관리자로 설치해도 된다.

```
# macOS
brew install python@3.13

# Windows
winget install --id Python.Python.3.13
```

**파이썬이 여러 개 있어도 괜찮다.** 기존 버전을 지울 필요는 없다. 가상환경을 만들 때 **어느 파이썬으로 만드느냐**가 그 가상환경의 파이썬 버전을 정한다(기초 과정 9.2.1). 여러 버전이 있을 때 특정 버전을 고르는 방법은 다음과 같다.

```
# macOS — 버전 번호가 붙은 명령
python3.13 --version

# Windows — 파이썬 런처(py)
py --list
py -3.13 --version
```

`py --list`는 Windows에 설치된 파이썬 목록을 보여 준다. 공식 사이트의 설치 파일로 파이썬을 설치하면 `py` 런처도 함께 설치된다. 1.2.3에서 가상환경을 만들 때 이 방법으로 버전을 고른다.

### 1.2.3 가상환경

이 과정에서는 저장소 폴더에 **가상환경을 하나** 만들고, 모든 장에서 같이 쓴다. 장이 지날수록 mypy, pydantic, pytest, httpx 같은 패키지가 하나씩 늘어난다. 장마다 가상환경을 따로 만들면 앞 장에서 설치한 도구를 다시 설치해야 한다. 이 과정의 장들은 서로 이어지는 하나의 공부이므로, 기초 과정 9.1.8의 "프로젝트마다 가상환경을 만든다"에서 이 저장소 전체가 하나의 프로젝트인 셈이다. 다만 8장과 9장에서 **배포할 패키지**를 만들 때는 그 패키지를 새 가상환경에 설치해 확인한다. 그때 다시 다룬다.

### 1.2.5 Pylance로 코드 읽기 — 타입 정보 보기

이 과정에서 VS Code의 Pylance는 **남이 쓴 코드를 읽는 도구**로 자주 쓰인다. 라이브러리 함수가 무엇을 받고 무엇을 돌려주는지, AI가 쓴 컴프리헨션의 결과가 어떤 모양인지 실행하지 않고도 알 수 있다.

`ch01` 폴더에 `hover_demo.py`를 만들고 다음을 입력한다.

```python
import json
from pathlib import Path

scores = {"수학": 90, "영어": 85}
names = list(scores)
best = max(scores, key=lambda name: scores[name])
text = json.dumps(scores, ensure_ascii=False)
here = Path(__file__).parent


def average(values: list[int]) -> float:
    return sum(values) / len(values)


result = average([90, 85])
```

**마우스를 올려 타입 보기**

이름 위에 마우스를 올리면 Pylance가 **추론한 타입**이 나온다. 하나씩 올려 보고 다음과 같이 나오는지 확인한다.

| 이름 | 마우스를 올렸을 때 | 읽는 법 |
|---|---|---|
| `scores` | `(variable) scores: dict[str, int]` | 키는 문자열, 값은 정수인 딕셔너리 |
| `names` | `(variable) names: list[str]` | 딕셔너리를 `list()`에 넣으면 **키**의 리스트가 된다 |
| `best` | `(variable) best: str` | `max()`는 키 중 하나를 돌려준다 |
| `text` | `(variable) text: str` | |
| `here` | `(variable) here: Path` | |
| `average` | `(function) def average(values: list[int]) -> float` | 타입 힌트를 쓴 함수는 힌트 그대로 보인다 |
| `json.dumps` | 함수의 전체 매개변수 목록과 독스트링 | |

`names`처럼 코드만 봐서는 헷갈리는 값을 이 방법으로 확인한다. 2장에서 컴프리헨션의 결과가 리스트인지 딕셔너리인지, 3장에서 제너레이터 표현식의 결과가 무엇인지 볼 때 이 방법을 계속 쓴다.

`json.dumps`의 설명을 보면 매개변수 목록 중간에 `*,`가 있다. 기초 과정 4.2.9 "함수 정의 읽기 — `/`와 `*`"에서 본 대로, `*` 뒤의 매개변수(`ensure_ascii`, `indent` 등)는 **키워드로만** 넘길 수 있다. 그래서 `json.dumps(scores, False)`가 아니라 `json.dumps(scores, ensure_ascii=False)`로 쓴다.

**인레이 힌트 — 타입을 코드 사이에 표시하기 (선택)**

마우스를 일일이 올리기 번거롭다면 Pylance가 추론한 타입을 코드 사이에 흐린 글씨로 표시하게 할 수 있다. 이것을 **인레이 힌트**(inlay hint)라고 한다. 사용자 설정(`Preferences: Open User Settings (JSON)`)에 다음을 더한다.

```jsonc
"python.analysis.inlayHints.variableTypes": true,
"python.analysis.inlayHints.functionReturnTypes": true
```

`names = list(scores)`가 `names: list[str] = list(scores)`처럼 보이고, 타입 힌트를 쓰지 않은 함수의 정의 끝에도 Pylance가 추론한 반환 타입이 표시된다. 표시된 힌트는 **진짜 코드가 아니다.** 파일에 저장되지 않고 화면에만 보인다. 화면이 복잡하게 느껴지면 끈다. 이 설정은 개인 취향이므로 작업 공간 설정이 아니라 사용자 설정에 넣는다.

### 1.2.6 Pylance로 코드 읽기 — 라이브러리 안으로 들어가기

개발 도구 4.3.6에서 `F12`(정의로 이동)로 **내 프로젝트** 안의 함수를 따라갔다. 같은 방법으로 **표준 라이브러리와 설치한 패키지**의 코드 안으로도 들어갈 수 있다. 라이브러리의 코드는 이 과정의 문법으로 가득하다. 지금은 다 읽지 못하지만, 어떤 모양인지 한 번 들어가 보자.

| 하는 일 | macOS | Windows |
|---|---|---|
| 정의로 이동 | `F12` 또는 `Cmd+클릭` | `F12` 또는 `Ctrl+클릭` |
| 정의를 그 자리에서 엿보기 | `Option+F12` | `Alt+F12` |
| 뒤로 가기 | `Ctrl+-` | `Alt+←` |
| 파일 안의 기호로 이동 | `Cmd+Shift+O` | `Ctrl+Shift+O` |

**1) 표준 라이브러리 — `json.dumps`**

`hover_demo.py`의 `json.dumps`에서 `F12`를 누른다. 새 탭에 `json/__init__.py`가 열리고 `def dumps(...)`로 이동한다. 탭 위의 경로를 보면 내 파이썬이 설치된 폴더 안이다. 표준 라이브러리도 대부분 **파이썬으로 쓴 파일**이다.

환경에 따라 `.py` 대신 `__init__.pyi`라는 파일이 열리기도 한다. 열어 보면 함수 몸통이 모두 `...`이고 매개변수와 반환값의 타입만 적혀 있다. 이것은 **스텁 파일**(stub file)이라고 하는, 타입 정보만 모아 둔 파일이다. Pylance는 이 정보로 타입을 보여 준다. 실제 코드가 아니므로 동작을 알고 싶을 때는 탭 위의 경로를 확인하고 `.py` 파일을 찾아 연다. 스텁 파일은 5장에서 다시 만난다.

**2) 설치한 패키지 — `httpx`**

7장에서 비동기 HTTP 요청에 쓸 `httpx` 패키지를 미리 설치하고 그 코드를 열어 본다. 가상환경이 활성화된 터미널에서 설치한다.

```
python -m pip install httpx
```

설치한 패키지 목록을 `requirements.txt`에 적는다(기초 과정 9.1.7).

```
python -m pip freeze > requirements.txt
```

`requirements.txt`를 열어 보면 `httpx` 말고도 여러 줄이 있다.

```
anyio==4.16.0
certifi==2026.10.23
h11==0.16.0
httpcore==1.0.9
httpx==0.28.1
idna==3.20
typing_extensions==4.16.0
```

버전 숫자는 설치한 시기에 따라 다르다. `httpx` 하나를 설치했는데 일곱 줄이 된 것은 `httpx`가 기대는 패키지가 함께 설치되었기 때문이다. `pip freeze`는 직접 설치한 것과 함께 설치된 것을 구별하지 않는다. 이 문제는 8장에서 `pyproject.toml`로 해결한다.

`ch01` 폴더에 `read_library.py`를 만든다. **실행하지 않는다.** 코드를 읽기 위한 파일이다.

```python
import httpx

response = httpx.get("https://pypi.org/pypi/httpx/json")
response.raise_for_status()
for line in response.iter_lines():
    print(line)

with httpx.Client() as client:
    with client.stream("GET", "https://pypi.org/simple/") as r:
        pass
```

먼저 `httpx.get`의 `get`에서 `F12`를 누른다. `.venv` 안의 `site-packages/httpx/_api.py`가 열린다. 탐색기에서는 보이지 않던 가상환경의 폴더 안이다. **내가 `pip install`한 패키지는 이렇게 `.venv` 안에 파이썬 파일로 들어 있다.**

```python
def get(
    url: URL | str,
    *,
    params: QueryParamTypes | None = None,
    headers: HeaderTypes | None = None,
    ...
    timeout: TimeoutTypes = DEFAULT_TIMEOUT_CONFIG,
    trust_env: bool = True,
) -> Response:
```

버전에 따라 조금 다르지만 이런 모양이다. 읽을 수 있는 곳을 찾아본다.

- `*,` — 그 뒤의 매개변수는 키워드로만 넘긴다(기초 과정 4.2.9). `httpx.get(url, timeout=10)`처럼 써야 한다.
- `URL | str`, `QueryParamTypes | None = None` — "URL 객체나 문자열", "이 타입이거나 `None`, 기본값은 `None`"이라는 타입 힌트다(기초 과정 8.2.5). 5장에서 정식으로 다룬다.
- `-> Response` — `Response` 객체를 돌려준다.

이번에는 `read_library.py`로 돌아가(`Ctrl+-` / `Alt+←`) `iter_lines`에서 `F12`를 누른다. `httpx/_models.py`의 `Response` 클래스 안으로 간다. 이 파일은 길다. `Cmd/Ctrl+Shift+O`를 누르면 파일 안의 클래스와 메서드 목록이 나오므로, 이름을 입력해 원하는 곳으로 이동할 수 있다. 다음을 찾아서 실습 1-2의 표에 적는다.

| 찾을 것 | 어디서 | 무엇인가 | 배우는 장 |
|---|---|---|---|
| `@property`가 붙은 메서드 | `Response` 클래스 | 기초 과정 5.2.6에서 붙여서 쓰기만 한 데코레이터 | 4장 |
| `def iter_lines(self) -> typing.Iterator[str]:` 안의 `yield` | `Response` 클래스 | 줄을 하나씩 내놓는 제너레이터 | 3장 |
| `async def aiter_lines(self)` 안의 `async for` | `Response` 클래스 | 비동기 제너레이터 | 7장 |
| `def raise_for_status(self) -> Response:` 안의 `raise` | `Response` 클래스 | 상태 코드가 2xx(성공)가 아니면 예외를 일으킨다. 4xx·5xx만 검사하는 기초 과정의 `requests`와 달리 1xx·3xx도 예외다 | 기초 과정 6.2 |

마지막으로 `client.stream`의 `stream`에서 `F12`를 누른다. `httpx/_client.py`의 `Client` 클래스 안으로 간다. `def stream(` 바로 위에 `@contextmanager`가 붙어 있다. 이 데코레이터가 붙은 함수는 `with` 문에 쓸 수 있게 된다. 4장의 "컨텍스트 관리자 만들기"에서 `@contextmanager`로 직접 만든다. 같은 파일에서 `__enter__`와 `__exit__`도 찾아본다. `with httpx.Client() as client:`가 동작하는 이유다(1.3.6).

> **라이브러리 파일은 읽기만 한다**
> `F12`로 연 파일은 편집할 수 있다. 실수로 글자를 지우고 저장하면 **이 가상환경의 httpx가 바뀐다.** 다음에 `import httpx`를 할 때 그 바뀐 코드가 실행된다. 라이브러리 파일의 탭 제목에 수정 표시(●)가 생겼다면 저장하지 말고 닫는다. 이미 저장했다면 다시 설치해서 되돌린다.
>
> ```
> python -m pip install --force-reinstall httpx
> ```
>
> 이 파일들은 `.venv` 안에 있으므로 Git도 바뀐 것을 알려 주지 않는다. 가상환경을 지우고 다시 만드는 방법도 있다(기초 과정 9.1.8).

### 1.2.7 환경 확인 스크립트

마지막으로, 이 과정에 필요한 버전 조건을 **코드로** 확인한다. `ch01` 폴더에 `check_env.py`를 만든다.

```python
"""파이썬 중급 과정의 실습 환경을 확인한다."""

import itertools
import sys


def first[T](items: list[T]) -> T:  # 3.12 문법. 3.11 이하에서는 SyntaxError
    return items[0]


print("버전:", sys.version.split()[0])
print("실행 파일:", sys.executable)
print("가상환경 안인가:", sys.prefix != sys.base_prefix)
print("제네릭 함수:", first(["가", "나", "다"]))
print("batched:", list(itertools.batched("ABCDEFG", 3)))
```

`def first[T](...)`는 5장에서 배울 제네릭 문법이고, `itertools.batched()`는 3장에서 배울 함수다. 지금은 "3.12에서 추가된 것"으로만 쓴다. `sys.prefix != sys.base_prefix`는 기초 과정 9.2.3에서 본 "가상환경 안에서 실행 중인가"를 확인하는 식이다.

터미널에서 실행한다.

```
python ch01/check_env.py
```

```
버전: 3.13.2
실행 파일: /Users/jinyoung/python-advanced-lab/.venv/bin/python
가상환경 안인가: True
제네릭 함수: 가
batched: [('A', 'B', 'C'), ('D', 'E', 'F'), ('G',)]
```

`itertools.batched("ABCDEFG", 3)`는 글자를 3개씩 묶는다. 마지막 묶음은 남은 글자만큼만 들어 있다. 3장에서 API를 일괄 호출할 때 이 함수를 쓴다.

VS Code의 ▷ 버튼으로도 실행해서 같은 결과가 나오는지 확인한다. 특히 "실행 파일"이 `.venv` 안인지 본다. 터미널과 VS Code가 다른 파이썬을 쓰고 있다면 여기서 드러난다(기초 과정 9.2.5).

**3.11 이하의 파이썬으로 실행하면** 다음과 같은 오류가 난다.

```
  File "/Users/jinyoung/python-advanced-lab/ch01/check_env.py", line 7
    def first[T](items: list[T]) -> T:  # 3.12 문법. 3.11 이하에서는 SyntaxError
             ^
SyntaxError: invalid syntax
```

맨 위의 `print()`들도 **하나도 실행되지 않았다.** 파이썬은 파일 전체의 문법을 먼저 확인한 뒤에 실행을 시작하기 때문이다(기초 과정 1.3.5에서 본 `SyntaxError`의 성질). 반대로 문법은 3.11에도 있는데 함수만 없는 경우(`itertools.batched`)는, 그 줄을 실행하는 순간에 `AttributeError`가 난다. 이 차이를 알면 "어느 버전에서 안 되는가"를 오류의 종류로 짐작할 수 있다.

## 1.3 기초 과정 점검

이 과정은 기초 과정의 몇 가지 개념에 크게 기댄다. 이 개념이 흔들리면 이 과정의 문법이 "마법"처럼 보인다. 반대로 이 개념이 단단하면 이 과정의 문법 대부분은 **이미 아는 것을 짧게 쓰는 방법**으로 읽힌다. 하나씩 다시 확인한다. 막히는 곳이 있으면 괄호 안의 기초 과정 절을 다시 본다.

이 절의 예제는 대화형 셸에서 해도 되고, `ch01/review.py` 같은 파일에 써서 실행해도 된다. 대화형 셸은 가상환경이 활성화된 터미널에서 `python`으로 연다.

### 1.3.1 변수는 객체를 가리키는 이름 (기초 과정 3.2)

변수는 값을 담는 상자가 아니라, 객체에 붙인 **이름표**다. `b = a`는 복사가 아니라 같은 객체에 이름표를 하나 더 붙이는 것이다.

```python
>>> a = [1, 2, 3]
>>> b = a
>>> b.append(4)
>>> a
[1, 2, 3, 4]
>>> a is b
True
```

함수도 객체이므로 똑같다.

```python
>>> def greet():
...     print("안녕")
...
>>> hello = greet
>>> greet = None
>>> hello()
안녕
```

`greet`라는 이름을 `None`에 다시 붙여도, 함수 객체는 `hello`라는 이름이 여전히 가리키고 있으므로 사라지지 않는다. `def greet():`는 "함수 객체를 만들고 `greet`라는 이름을 붙인다"는 뜻이었다.

**이 과정에서** — 4장의 데코레이터는 정확히 이 일을 한다. 함수 위에 `@deco`를 붙이는 것은 `greet = deco(greet)`, 즉 **`greet`라는 이름을 다른 객체에 다시 붙이는 것**이다. 3장에서는 두 이름이 같은 이터레이터를 가리킬 때 한쪽에서 꺼내면 다른 쪽에서도 사라지는 것을 보고, 4장에서는 반복문 안에서 만든 람다들이 모두 같은 변수를 가리키는 "늦은 바인딩" 함정을 만난다. 모두 "이름은 객체를 가리킨다"로 설명된다.

### 1.3.2 함수도 값이다 (기초 과정 4.4)

함수는 다른 값처럼 변수에 담고, 자료구조에 넣고, 다른 함수에 인자로 넘길 수 있다.

```python
def shout(text):
    return text.upper() + "!"


def whisper(text):
    return text.lower() + "..."


styles = {"shout": shout, "whisper": whisper}


def speak(text, style):
    func = styles[style]  # 딕셔너리에서 함수를 꺼낸다
    return func(text)  # 꺼낸 함수를 호출한다


print(speak("Hello", "shout"))
print(speak("Hello", "whisper"))
```

```
HELLO!
hello...
```

`styles[style]`은 함수를 **호출하지 않고** 함수 객체 자체를 꺼낸다. 괄호 `()`가 붙어야 호출된다. `styles = {"shout": shout()}`처럼 괄호를 붙이면 딕셔너리를 만드는 순간 함수가 호출되어 버린다(그리고 인자가 없어서 `TypeError`가 난다).

**이 과정에서** — 4장에서는 함수를 **돌려주는** 함수를 만든다. 4장에서 처음 만드는 데코레이터는 "함수를 받아서 함수를 돌려주는 함수"다. 넓게 보면 데코레이터는 받은 것을 무엇으로든 바꿔 돌려줄 수 있다. `@property`는 property 객체를, LangChain의 `@tool`은 LLM이 쓸 수 있는 도구 객체를 돌려준다. 또 위의 `styles` 딕셔너리에 함수를 손으로 넣는 대신, 함수를 정의하는 순간 자동으로 등록되게 하는 **등록 데코레이터**를 만든다. FastAPI의 `@app.get("/...")`, MCP 서버의 `@mcp.tool()`이 하는 일이 바로 이것이다. LangChain의 `@tool`은 조금 다르다. 어딘가에 등록하지 않는다. 돌려준 도구 객체를 모델이나 에이전트에 직접 넘겨야 쓰인다.

### 1.3.3 `*args`와 `**kwargs` (기초 과정 4.2.6~4.2.8)

정의할 때의 `*args`는 남는 위치 인자를 **튜플로 모으고**, `**kwargs`는 남는 키워드 인자를 **딕셔너리로 모은다.** 호출할 때의 `*`와 `**`는 반대로 **풀어서 넘긴다.**

```python
def log_call(func, *args, **kwargs):
    print(f"호출: {func.__name__} args={args} kwargs={kwargs}")
    return func(*args, **kwargs)


def area(width, height, unit="cm"):
    return f"{width * height}{unit}²"


print(log_call(area, 3, 4, unit="m"))
```

```
호출: area args=(3, 4) kwargs={'unit': 'm'}
12m²
```

`func.__name__`은 함수 객체가 가진 이름이다. `log_call`은 `area`가 어떤 매개변수를 받는지 전혀 모른다. 받은 것을 모아(`*args, **kwargs`) 그대로 풀어서(`*args, **kwargs`) 넘겨줄 뿐이다. 그래서 **어떤 함수든** 이 함수로 감쌀 수 있다.

**이 과정에서** — 이 `log_call`이 4장에서 만드는 데코레이터의 핵심 부품인 **래퍼 함수**와 거의 같다. 4장에서는 `log_call(area, 3, 4, unit="m")`이라고 부르는 대신 `area(3, 4, unit="m")`이라고 불러도 기록이 남도록 만든다. 7장의 `asyncio.gather(*tasks)`도 풀어서 넘기기다.

### 1.3.4 클래스와 `self` (기초 과정 5장)

메서드를 `obj.method(인자)`로 부르면 파이썬은 `클래스.method(obj, 인자)`로 바꾸어 실행한다. `self`는 메서드를 부른 **그 객체**다.

```python
>>> class Counter:
...     def __init__(self, start=0):
...         self.value = start
...     def up(self, step=1):
...         self.value += step
...         return self.value
...
>>> c = Counter()
>>> c.up()
1
>>> Counter.up(c, 5)
6
```

그리고 이름이 `__`로 시작하고 끝나는 메서드는 우리가 직접 부르지 않아도 **파이썬이 정해진 순간에 부른다.** 기초 과정에서 `print()`가 `__str__`을 부르는 것을 보았다(5.2.3). 다른 예도 있다.

```python
>>> class Playlist:
...     def __init__(self, songs):
...         self.songs = list(songs)
...     def __len__(self):
...         return len(self.songs)
...     def __repr__(self):
...         return f"Playlist({self.songs!r})"
...
>>> p = Playlist(["봄", "여름"])
>>> len(p)
2
>>> p
Playlist(['봄', '여름'])
```

`len(p)`는 `p.__len__()`을, 대화형 셸에서 `p`를 보여 줄 때는 `p.__repr__()`을 부른다.

**이 과정에서** — 이런 특별한 메서드가 계속 나온다. `for` 문은 `__iter__`와 `__next__`를 부르고(3장), `with` 문은 `__enter__`와 `__exit__`를 부른다(4장, 1.3.6). 이 메서드들을 직접 만들면 **내가 만든 객체를 `for` 문과 `with` 문에 쓸 수 있다.** 4장에서는 기초 과정에서 붙여서 쓰기만 한 `@property`와 `@dataclass`를 다시 보고, `@classmethod`로 `from_dict()` 같은 대체 생성자를 만든다. 5장의 `Protocol`은 "이런 메서드를 가진 객체라면 무엇이든"이라는 약속을 타입으로 적는 방법이다.

### 1.3.5 예외의 전파 (기초 과정 6장)

함수 안에서 난 예외는 그 함수에서 잡지 않으면 **호출한 쪽으로 거슬러 올라간다**(기초 과정 6.1.9). 올라가다가 맞는 `except`를 만나면 거기서 처리되고, 끝까지 아무도 잡지 않으면 프로그램이 트레이스백을 출력하고 끝난다.

```python
def parse(text):
    return int(text)  # 여기서 ValueError가 난다


def load(lines):
    numbers = []
    for line in lines:
        numbers.append(parse(line))
    return numbers


def main():
    try:
        print(load(["1", "2", "셋"]))
    except ValueError as e:
        print("읽기 실패:", e)


main()
```

```
읽기 실패: invalid literal for int() with base 10: '셋'
```

예외는 `parse`에서 났지만 `parse`와 `load`는 잡지 않았다. 예외는 `parse` → `load` → `main`으로 올라와서 `main`의 `except`에서 잡혔다. `load`가 만들던 `numbers` 리스트(`[1, 2]`)는 돌려주지 못하고 버려졌다.

**이 과정에서** — 4장의 재시도 데코레이터는 감싼 함수에서 **올라온 예외를 잡아서** 다시 시도한다. 어떤 예외에서 다시 시도하고 어떤 예외는 그대로 올려보낼지가 설계의 핵심이다(기초 과정 6.2.6 "예외를 잡을 때와 그대로 둘 때"). 6장의 `pytest.raises()`는 "이 코드를 실행하면 이 예외가 올라와야 한다"를 확인한다. 7장에서는 동시에 실행한 작업 여러 개에서 예외가 **한꺼번에** 올라오는 경우를 다룬다. 그리고 3장에서는 조금 놀라운 일을 본다. 제너레이터 안의 예외는 함수를 **호출할 때가 아니라 값을 꺼낼 때** 올라온다.

### 1.3.6 `with` 문 (기초 과정 7.1.4)

`with` 문은 블록을 빠져나갈 때 **반드시** 정리 작업을 한다. 파일이라면 닫는다. 블록 안에서 예외가 나도 마찬가지다.

```python
from pathlib import Path

path = Path("note.txt")

with open(path, "w", encoding="utf-8") as f:
    f.write("첫 줄\n")
    print("블록 안:", f.closed)
print("블록 밖:", f.closed)

try:
    with open(path, encoding="utf-8") as f:
        raise ValueError("읽다가 실패")
except ValueError:
    pass
print("예외 뒤:", f.closed)

path.unlink()  # 확인용 파일을 지운다
```

```
블록 안: False
블록 밖: True
예외 뒤: True
```

두 번째 `with` 블록은 예외 때문에 중간에 빠져나갔지만 파일은 닫혔다. 예외는 닫힌 뒤에 그대로 올라와서 바깥의 `except`에서 잡혔다. `with` 문은 `try`/`finally`(기초 과정 6.1.8)를 짧게 쓴 것과 같다.

**이 과정에서** — `with` 블록에 들어갈 때 파이썬은 객체의 `__enter__()`를, 나갈 때 `__exit__()`를 부른다(1.3.4). 1.2.6에서 `httpx.Client` 안에서 본 그 메서드들이다. 4장에서 이 두 메서드로 컨텍스트 관리자를 직접 만들고, `@contextmanager`로 더 짧게 만든다. 6장의 pytest 픽스처, 7장의 `async with`도 "들어갈 때 준비하고 나갈 때 반드시 정리한다"는 같은 생각이다.

### 실습 1-3. 예측하고 확인하기

1.1.5의 "예측하고, 실행하고, 확인한다"를 연습한다. `ch01/review_quiz.py`를 만들고 아래 코드를 입력한다. **실행하기 전에** `ch01/review.md`에 문제마다 출력될 내용을 예측해서 적는다.

```python
"""1장 기초 과정 점검 — 실행하기 전에 출력을 예측해서 review.md에 적는다."""

from pathlib import Path


def q1():
    """기초 과정 3.2, 4.2.5"""

    def add_item(item, box=[]):
        box.append(item)
        return box

    print(add_item("a"))
    print(add_item("b"))


def q2():
    """기초 과정 3.2.6"""
    grid = [[0] * 2] * 2
    grid[0][0] = 9
    print(grid)


def q3():
    """기초 과정 4.4"""

    def twice(func, value):
        return func(func(value))

    print(twice(lambda x: x * 3, 2))
    print(twice(str.upper, "hi"))


def q4():
    """기초 과정 4.2.6~4.2.8"""

    def show(a, b, *rest, sep="-", **options):
        print(a, b, rest, sep, options)

    args = [1, 2, 3, 4]
    opts = {"sep": "/", "end": "!"}
    show(*args, **opts)


def q5():
    """기초 과정 5장 — 생각해 볼 문제"""

    class Box:
        count = 0

        def __init__(self, items):
            self.items = items
            Box.count += 1

        def __len__(self):
            return len(self.items)

        def __repr__(self):
            return f"Box({len(self)})"

    boxes = [Box([1, 2]), Box([])]
    print(boxes, Box.count)
    print(bool(boxes[1]))


def q6():
    """기초 과정 6장"""

    def step(n):
        print("step", n)
        if n == 2:
            raise KeyError(n)
        return n

    results = []
    try:
        for n in range(1, 4):
            results.append(step(n))
    except KeyError as e:
        print("잡음:", repr(e))
    finally:
        print("끝:", results)


def q7():
    """기초 과정 6.1.8, 7.1.4"""
    path = Path("quiz.txt")
    try:
        with path.open("w", encoding="utf-8") as f:
            f.write("한 줄")
            1 / 0
    except ZeroDivisionError:
        print("나눗셈 실패, 닫혔나?", f.closed)
    print(path.read_text(encoding="utf-8"))
    path.unlink()


if __name__ == "__main__":
    for quiz in [q1, q2, q3, q4, q5, q6, q7]:
        print(f"== {quiz.__name__}")
        quiz()
```

> **밑줄이 생겨도 고치지 않는다**
> Ruff 버전에 따라 q1의 `box=[]`와 q7의 `1 / 0`에 물결 밑줄이 생길 수 있다. 마우스를 올리면 "가변 객체를 기본값으로 쓰지 말라", "아무 데도 쓰지 않는 식이다" 같은 설명이 나온다. 둘 다 이 실습에서 **일부러 넣은 것**이다. 설명을 읽어 보고, 고치지 말고 그대로 둔다. 이 두 규칙은 자동으로 고치면 동작이 바뀔 수 있어서 저장할 때도 Ruff가 바꾸지 않는다. Ruff의 규칙은 6장에서 다룬다.

2. 예측과 실제 출력을 비교해서 맞은 문제와 틀린 문제를 표시한다.
3. 틀린 문제는 디버거로 확인한다. 그 문제의 함수 첫 줄에 중단점을 찍고 `F5`로 시작한 뒤, `F11`(단계 정보, Step Into)로 함수 안에 들어가고 `F10`으로 한 줄씩 진행하면서 변수 패널을 본다. 어느 줄에서 생각과 달라졌는지 찾아 `review.md`에 한두 문장으로 적는다. 관련된 기초 과정의 절(문제의 독스트링)을 다시 읽는다.
4. **q5는 기초 과정에서 직접 다루지 않은 내용**이 섞여 있다. `bool(boxes[1])`의 결과가 예측과 달랐다면, `Box` 클래스에서 `__len__` 메서드를 지우고, `__repr__`의 `len(self)`를 `len(self.items)`로 바꾼 뒤 다시 실행해 본다. `__repr__`도 `len(self)`로 `__len__`을 부르므로, `__len__`만 지우면 `print(boxes, Box.count)`에서 `TypeError`가 먼저 난다. 결과가 어떻게 바뀌는지 보고, 1.3.4의 "파이썬이 정해진 순간에 부르는 메서드"와 연결해서 이유를 추측해 적는다. 공식 문서의 "Truth Value Testing"(참·거짓 판정) 절에서 추측을 확인한다.
5. 맨 아래의 `for quiz in [q1, q2, ...]:`를 다시 본다. 함수 일곱 개를 리스트에 담고, 하나씩 꺼내 이름(`__name__`)을 출력하고 호출했다. 1.3.2의 "함수도 값이다"를 쓴 코드다. 6장의 pytest는 이와 비슷하게 `test_`로 시작하는 함수를 찾아 하나씩 호출한다.

## 정리

| 항목 | 핵심 |
|---|---|
| 이 과정의 목표 | LLM 라이브러리와 웹 프레임워크의 코드를 막힘없이 읽고 같은 방식으로 직접 쓴다. 타입 검사·테스트·패키지 배포로 남이 믿고 쓸 수 있는 코드를 만든다 |
| 아직 배우지 않은 문법 | 컴프리헨션·`match`(2장), `yield`(3장), 데코레이터 만들기(4장), `async`/`await`(7장) |
| 도구로 바뀌는 것 | `check_samples.py` → pytest(6장), `isinstance()` 검사 → mypy·Pydantic(5장), `requirements.txt` → `pyproject.toml`(8장) |
| 장의 순서 | 테스트(6장)를 비동기(7장)보다 먼저. 비동기 코드를 처음부터 테스트와 함께 쓴다 |
| 공부하는 방법 | 예측하고, 실행하고, 다르면 디버거로 확인한다. AI가 쓴 코드는 한 문장으로 설명할 수 있을 때 받아들인다 |
| 파이썬 버전 | 3.12 이상. 버전에 없는 문법은 `SyntaxError`(파일 전체가 실행되지 않는다), 없는 함수는 그 줄에서 `AttributeError` |
| 실습 저장소 | `~/python-advanced-lab` 하나에 장별 폴더, 가상환경 하나. 장을 마칠 때 커밋 |
| Pylance | 마우스를 올려 추론된 타입 보기, `F12`로 표준 라이브러리와 `.venv` 안 패키지의 코드 읽기. `.pyi`는 타입 정보만 담은 스텁 파일. 라이브러리 파일은 고치지 않는다 |
| 이름과 객체 | 변수는 이름표. `def`와 `@`는 이름을 객체에 붙인다 |
| 함수도 값 | 담고, 넘기고, 돌려줄 수 있다. 괄호를 붙여야 호출된다 |
| `*args`/`**kwargs` | 정의할 때는 모으고, 호출할 때는 푼다. 어떤 함수든 감쌀 수 있다 |
| 특별한 메서드 | `__len__`, `__repr__`, `__iter__`, `__enter__`처럼 파이썬이 정해진 순간에 부른다 |
| 예외의 전파 | 잡지 않으면 호출한 쪽으로 올라간다 |
| `with` 문 | 나갈 때 반드시 정리한다. 예외가 나도 마찬가지다 |
