# 6장. 테스트

[파이썬 중급](README.md) 과정의 여섯 번째 장이다. 기초 과정 10장에서 가계부 프로그램을 만들 때 `check_samples.py`를 직접 만들었다. 시험 파일을 읽고 요약한 결과를 **기대한 결과와 비교하는** 스크립트였다. 5장의 mypy는 "타입이 맞는가"를 실행하지 않고 확인했지만, "값이 맞는가"는 확인하지 못한다. `word_count("안녕   파이썬")`이 `2`인지, 재시도 데코레이터가 정말 세 번 시도하는지는 실행해 봐야 안다. 이 장에서는 `check_samples.py`가 하던 일을 **pytest**라는 도구로 제대로 한다. 기대한 결과를 코드로 적어 두고, 코드를 고칠 때마다 명령 하나로 모두 확인한다.

- **자동 테스트가 필요한 이유** — `check_samples.py`를 돌아보고, 고친 곳 때문에 멀쩡하던 곳이 망가지는 **회귀**를 직접 겪는다. 테스트와 타입 검사가 각각 무엇을 확인하는지 나누고, AI가 고친 코드를 테스트로 검토하는 방법을 익힌다.
- **pytest 시작** — pytest를 설치하고 첫 테스트를 쓴다. 테스트 파일과 함수의 이름 규칙, `assert`의 실패 메시지 읽는 법, 자주 쓰는 실행 옵션을 익히고, VS Code 테스트 탐색기로 테스트를 실행하고 디버깅한다.
- **테스트 작성 기술** — 준비·실행·확인(Arrange-Act-Assert)으로 테스트를 짜고, 정상·경계·실패 경우를 나눈다. `pytest.raises()`로 예외를, `pytest.approx()`로 실수를 확인하고, `@pytest.mark.parametrize`로 여러 입력을 한 번에 검사한다.
- **픽스처** — 테스트마다 되풀이되는 준비를 `@pytest.fixture`로 뽑아내고, `yield` 픽스처로 준비와 정리를 함께 쓴다. `conftest.py`로 픽스처를 나눠 쓰고, 내장 픽스처 `tmp_path`, `monkeypatch`, `capsys`를 쓴다.
- **외부 의존을 떼어 내고 테스트하기** — 네트워크와 LLM API를 부르지 않고 LLM을 쓰는 코드를 테스트한다. 의존성 주입, `Protocol`로 만든 가짜 객체, `unittest.mock`을 쓰고, 실제 API를 부르는 테스트는 마커로 표시해 따로 실행한다.
- **코드 품질 도구** — `pytest-cov`로 커버리지를 보고 그 숫자의 함정을 안다. `ruff`로 린트와 포맷을 하고, ruff·mypy·pytest를 한 번에 돌리는 습관을 들인다. LLM의 답처럼 매번 달라지는 결과에서 무엇을 테스트로 단정하고 무엇을 평가(Evals)로 넘길지 정한다.

## 6.1 자동 테스트가 필요한 이유

### 6.1.1 `check_samples.py` 돌아보기

기초 과정 10장에서 가계부 프로그램을 만들 때, 코드를 고칠 때마다 시험 파일 다섯 개로 실행하고 결과를 눈으로 비교하는 일이 금방 귀찮아졌다. 귀찮은 일은 빼먹게 된다. 그래서 **기대한 결과를 코드에 적어 두고 비교하는** `check_samples.py`를 만들었다. 그 생각을 작은 함수 두 개에 똑같이 써 본다.

`ch06/text_tools.py`

```python
"""글을 다루는 작은 도구들 — 6장의 첫 테스트 대상."""


def word_count(text: str) -> int:
    """공백으로 나뉜 낱말의 개수를 돌려준다."""
    return len(text.split())


def truncate(text: str, limit: int, suffix: str = "...") -> str:
    """text가 limit글자를 넘으면 limit글자까지 자르고 끝에 suffix를 붙인다."""
    if len(text) <= limit:
        return text
    return text[:limit] + suffix
```

`ch06/check_text.py`

```python
"""text_tools를 기대한 결과와 비교한다 — check_samples.py 방식."""

import sys

from text_tools import truncate, word_count

CASES = [
    ("word_count 기본", word_count("안녕 파이썬"), 2),
    ("word_count 여러 칸", word_count("안녕   파이썬"), 2),
    ("word_count 빈 글", word_count(""), 0),
    ("truncate 짧은 글", truncate("안녕", 10), "안녕"),
    ("truncate 딱 맞는 글", truncate("안녕하세요", 5), "안녕하세요"),
    ("truncate 긴 글", truncate("안녕하세요 반가워요", 5), "안녕하세요..."),
]

failed = 0
for name, actual, expected in CASES:
    if actual == expected:
        print(f"[통과] {name}")
    else:
        failed += 1
        print(f"[실패] {name}: 기대 {expected!r}, 실제 {actual!r}")
print(f"{len(CASES)}개 중 {len(CASES) - failed}개 통과")
if failed:
    sys.exit(1)
```

```
python ch06/check_text.py
```

```
[통과] word_count 기본
[통과] word_count 여러 칸
[통과] word_count 빈 글
[통과] truncate 짧은 글
[통과] truncate 딱 맞는 글
[통과] truncate 긴 글
6개 중 6개 통과
```

`CASES`의 한 줄이 "이 입력이면 이 결과가 나와야 한다"는 약속 하나다. 이렇게 **코드의 동작을 확인하는 코드**를 **테스트**(test)라고 하고, 사람이 아니라 프로그램이 확인하므로 **자동 테스트**라고 한다. 기초 과정의 `check_samples.py`도 자동 테스트였다.

그런데 이 방식에는 불편한 점이 있다.

- **비교하고 보고하는 코드를 매번 새로 쓴다.** `for` 문, `[통과]`/`[실패]` 출력, 개수 세기, 종료 코드가 테스트의 본론이 아닌데 파일마다 필요하다.
- **하나가 예외를 내면 전체가 멈춘다.** `CASES`를 만드는 도중에 `truncate()`가 예외를 내면 그 뒤의 확인은 하나도 실행되지 않는다. 어디까지 통과했는지도 알 수 없다.
- **실패했을 때 정보가 적다.** 기대한 값과 실제 값은 보이지만, 두 리스트나 딕셔너리가 **어디서** 다른지는 직접 찾아야 한다.
- **일부만 실행할 수 없다.** `truncate`만 확인하고 싶어도 전체를 돌린다.
- **확인하는 방법이 `==` 하나다.** "예외가 나야 한다", "출력이 이래야 한다", "실수가 거의 같아야 한다"를 확인하려면 또 코드를 써야 한다.

pytest는 이 불편을 모두 맡아 준다. 우리는 "이 입력이면 이 결과"만 쓰면 된다. 6.2에서 이 파일을 pytest로 옮긴다.

### 6.1.2 회귀 — 고친 곳 때문에 멀쩡하던 곳이 망가진다

`word_count()`에 새 요구가 들어왔다. "`안녕 , 파이썬 !`처럼 문장 부호만 따로 떨어져 있으면 낱말로 세지 않는다." AI에게 부탁했더니 다음과 같이 고쳐 주었다.

```python
PUNCTUATION = {",", ".", "!", "?"}


def word_count(text: str) -> int:
    """공백으로 나뉜 낱말의 개수를 돌려준다. 문장 부호만 있는 것은 세지 않는다."""
    words = text.split(" ")
    return len([w for w in words if w not in PUNCTUATION])
```

새 요구를 확인하는 줄도 `CASES`에 더한다.

```python
    ("word_count 문장 부호", word_count("안녕 , 파이썬 !"), 2),
```

`ch06/text_tools.py`의 `word_count()`를 이렇게 바꾸고, `check_text.py`의 `"word_count 빈 글"` 줄 아래에 위의 줄을 더한 뒤 실행한다.

```
python ch06/check_text.py
```

```
[통과] word_count 기본
[실패] word_count 여러 칸: 기대 2, 실제 4
[실패] word_count 빈 글: 기대 0, 실제 1
[통과] word_count 문장 부호
[통과] truncate 짧은 글
[통과] truncate 딱 맞는 글
[통과] truncate 긴 글
7개 중 5개 통과
```

새 요구는 통과했다. 그런데 **잘 되던 두 경우가 망가졌다.** AI가 `split()`을 `split(" ")`으로 바꿨기 때문이다. 인자 없는 `split()`은 공백이 몇 칸이든 하나로 보고 빈 문자열을 만들지 않지만, `split(" ")`은 빈칸 하나하나를 구분자로 본다(기초 과정 2.3.5).

```python
>>> "안녕   파이썬".split(" ")
['안녕', '', '', '파이썬']
>>> "".split(" ")
['']
```

이렇게 **고친 곳 때문에 전에 되던 것이 안 되게 되는 일**을 **회귀**(regression)라고 한다. 퇴보한다는 뜻이다. 회귀는 고친 사람이 확인한 곳이 아니라 **확인하지 않은 곳**에서 생긴다. 새 기능만 시험해 본 사람은 알아채지 못한다. 그래서 자동 테스트는 새 기능을 확인하는 것보다 **전에 되던 것이 여전히 되는지** 확인하는 데 더 큰 힘을 발휘한다. 테스트가 쌓일수록 코드를 고칠 때 확인되는 범위가 넓어진다. 이런 쓰임을 강조할 때 **회귀 테스트**라고 부른다.

`split(" ")`을 `split()`으로 되돌리면 일곱 개가 모두 통과한다.

```python
def word_count(text: str) -> int:
    """공백으로 나뉜 낱말의 개수를 돌려준다. 문장 부호만 있는 것은 세지 않는다."""
    return len([w for w in text.split() if w not in PUNCTUATION])
```

> **테스트는 적어 둔 것만 확인한다**
> 고친 `word_count()`에 `"안녕\n파이썬"`을 넣으면 `2`다. 그런데 AI의 `split(" ")` 판에 넣으면 `1`이다. 줄바꿈도 망가졌던 것이다. `CASES`에 줄바꿈 경우가 없었으므로 그 회귀는 드러나지 않았다. 테스트는 **적어 둔 경우만** 확인한다. 테스트가 모두 통과했다는 것은 "적어 둔 경우에 버그가 없다"는 뜻이지 "버그가 없다"는 뜻이 아니다. 어떤 경우를 적어 둘지는 6.3.2에서 다룬다.

### 6.1.3 테스트와 타입 검사

5장의 mypy와 이 장의 테스트는 둘 다 "실행하기 전에 실수를 찾는다"는 같은 목표를 가졌지만, 확인하는 것이 다르다.

| | 타입 검사(mypy) | 테스트(pytest) |
|---|---|---|
| 방법 | 실행하지 않고 코드만 읽는다 | 실제로 실행해서 결과를 비교한다 |
| 확인하는 범위 | **모든** 경로. 부르지 않은 함수도 | 테스트가 **실행한** 경로만 |
| 확인하는 것 | 타입이 맞는가. `str`을 `int` 자리에 넘기지 않았는가 | 값이 맞는가. `word_count("")`가 `0`인가 |
| 찾지 못하는 것 | 타입은 맞는데 값이 틀린 것. 위의 `split(" ")` | 적어 두지 않은 경우의 실수 |

위의 `split(" ")` 회귀는 mypy가 찾지 못한다. `split(" ")`도 `list[str]`을 돌려주므로 타입은 완벽하게 맞다. 반대로 5.1.2의 `shout()`처럼 부르지 않은 함수의 실수는 테스트로는 찾지 못하지만 mypy는 찾는다. 둘은 서로를 대신하지 않고 **보완한다.** 이 장의 끝(6.6.5)에서 둘을 한 번에 돌리는 습관을 들인다.

### 6.1.4 AI가 고친 코드를 테스트로 검토하기

1장에서 "6장을 배운 뒤부터는 테스트로 확인한다"고 했다. 6.1.2의 일이 바로 그 예다. AI가 고친 코드를 읽고 검토하는 것도 중요하지만, 고친 코드 전체를 매번 꼼꼼히 읽기는 어렵다. 테스트가 있으면 "새 요구는 되었는가", "전에 되던 것은 여전히 되는가"를 명령 하나로 확인할 수 있다.

AI와 함께 코드를 고칠 때 테스트를 이렇게 쓴다.

1. **고치기 전에 테스트를 돌린다.** 이미 실패하는 테스트가 있다면 고친 뒤의 실패와 구별할 수 없다.
2. **새 요구를 먼저 테스트로 적는다.** 위의 `"word_count 문장 부호"` 줄이다. 고치기 전에 돌리면 실패해야 한다. 실패하지 않는다면 그 테스트는 새 요구를 확인하지 못하는 것이다.
3. **AI에게 고치게 하고, 테스트를 모두 돌린다.** 새 테스트는 통과하고, 전에 통과하던 테스트도 모두 통과해야 한다.
4. **테스트가 바뀌었는지 확인한다.** AI가 테스트를 통과시키려고 **테스트를 고치는** 일이 있다. 기대값을 실제 값으로 바꾸거나, 실패하는 테스트를 지우거나, 건너뛰게 만든다. `git diff`로 테스트 파일이 바뀌었는지 반드시 본다.

> **기대값은 사람이 정한다**
> 기초 과정 10장의 `check_samples.py`에서 "숫자는 **계산기로 직접 구한 값**이다. 프로그램이 출력한 숫자를 그대로 옮겨 적으면, 프로그램이 틀렸을 때 기대값도 함께 틀려서 아무것도 확인하지 못한다"고 했다. AI에게 테스트를 쓰게 할 때도 같다. AI가 코드를 실행해 본 결과를 기대값으로 적었다면 그 테스트는 "지금 코드가 지금처럼 동작한다"만 확인한다. 기대값이 맞는지는 사람이 직접 따져 본다.

### 실습 6-1. 자동 테스트가 필요한 이유

**1. 회귀 겪어 보기**

6.1.1과 6.1.2를 그대로 따라 한다. `ch06/text_tools.py`와 `ch06/check_text.py`를 만들고, `word_count()`를 AI의 `split(" ")` 판으로 바꿔 회귀를 확인한 뒤 `split()`으로 되돌린다. `ch06/notes.md`에 "새 요구는 통과했는데 무엇이 망가졌는가", "왜 그것을 바로 알 수 있었는가"를 적는다.

**2. 빠진 경우 찾기**

`CASES`에 `word_count("안녕\n파이썬")`과 `word_count("  안녕  ")`을 더한다. 기대값은 실행하기 **전에** 정한다. 지금의 `word_count()`로 통과하는가? `split(" ")` 판으로 잠시 바꾸면 어떻게 되는가? 확인한 뒤 되돌린다.

**3. `truncate()`의 약속 따져 보기**

`truncate("안녕하세요 반가워요", 5)`는 `"안녕하세요..."`로 여덟 글자다. "결과가 `limit`글자를 넘지 않아야 한다"는 요구가 들어왔다고 하자.

- 이 요구를 `CASES`의 줄로 먼저 적는다. 기대값은 무엇인가?
- 기존의 `"truncate 긴 글"` 줄은 어떻게 되어야 하는가? 이것은 회귀인가, 요구가 바뀐 것인가? 둘을 어떻게 구별하는지 `notes.md`에 적는다.
- `truncate("안녕하세요", 2)`처럼 `limit`이 `suffix`보다 짧으면 결과는 무엇이어야 할까? 정답은 없다. 정한 약속을 `truncate()`의 독스트링과 `CASES`에 함께 적는다. (이 실습은 코드를 고치지 않아도 된다. 6.2를 마친 뒤 pytest로 다시 해 본다.)

**4. 타입 검사와 테스트**

`mypy ch06/text_tools.py`를 실행한다. AI의 `split(" ")` 판으로 바꾸고 다시 실행하면 결과가 달라지는가? 6.1.3의 표로 그 이유를 설명한다.

## 6.2 pytest 시작

### 6.2.1 첫 테스트

`check_text.py`의 `CASES`를 pytest 테스트로 옮긴다. 새 파일을 만든다.

`ch06/test_text_tools.py`

```python
"""text_tools의 테스트."""

from text_tools import truncate, word_count


def test_word_count_basic() -> None:
    assert word_count("안녕 파이썬") == 2


def test_word_count_many_spaces() -> None:
    assert word_count("안녕   파이썬") == 2


def test_word_count_empty() -> None:
    assert word_count("") == 0


def test_word_count_skips_punctuation() -> None:
    assert word_count("안녕 , 파이썬 !") == 2


def test_truncate_short_text_is_unchanged() -> None:
    assert truncate("안녕", 10) == "안녕"


def test_truncate_exact_length_is_unchanged() -> None:
    assert truncate("안녕하세요", 5) == "안녕하세요"


def test_truncate_long_text() -> None:
    assert truncate("안녕하세요 반가워요", 5) == "안녕하세요..."
```

`check_text.py`와 비교하면 남은 것은 "이 입력이면 이 결과"뿐이다.

- **테스트 하나가 함수 하나다.** 이름이 `test_`로 시작하는 함수를 pytest가 찾아서 하나씩 부른다. 1장의 퀴즈 함수 일곱 개를 리스트에 담아 하나씩 부른 것(1.3.2), 4장의 등록 데코레이터가 "함수를 정의하면 알아서 찾아서 부른다"(4.5.1)고 한 것과 같은 생각이다.
- **확인은 `assert` 문 하나로 한다.** `assert 조건`은 조건이 참이면 아무 일도 하지 않고, 거짓이면 `AssertionError`를 일으킨다. pytest는 함수가 예외 없이 끝나면 **통과**, `AssertionError`가 나면 **실패**로 본다. 비교하고 출력하고 개수를 세는 코드는 pytest가 맡는다.
- **함수 이름이 설명이다.** 실패했을 때 가장 먼저 보이는 것이 함수 이름이다. `test_1`이 아니라 `test_word_count_many_spaces`처럼 **무엇을 확인하는지** 이름에 적는다. 영어로 쓰는 것이 관례이고, 길어도 괜찮다.
- **테스트 함수에도 `-> None`을 붙인다.** 5.1.6에서 본 것처럼 mypy는 타입 힌트가 하나도 없는 함수의 본문을 검사하지 않는다. `-> None`을 붙여 두면 테스트 코드도 검사받는다. 6.6.5에서 테스트 파일까지 `mypy --strict`로 검사한다.

> **`assert`는 테스트에서 쓰는 것이다**
> 5.2.4에서 "`assert`는 입력 검사에 쓰지 않는다. `python -O`로 실행하면 `assert` 문이 통째로 사라진다"고 했다. 테스트의 `assert`는 이 걱정이 없다. 테스트는 pytest가 실행하고, pytest는 `assert` 문을 직접 읽어서 처리한다(6.2.3). 프로그램 코드의 입력 검사는 여전히 `if`와 `raise`로 쓰고, `assert`는 테스트와 "내 코드의 논리상 이럴 수 없다"는 곳에만 쓴다.

### 6.2.2 pytest가 테스트를 찾는 규칙

pytest는 다음 규칙으로 테스트를 찾는다.

| 대상 | 규칙 | 예 |
|---|---|---|
| 파일 | `test_*.py` 또는 `*_test.py` | `test_text_tools.py` |
| 함수 | 이름이 `test`로 시작 | `test_word_count_basic()` |
| 클래스 | 이름이 `Test`로 시작하고 `__init__`이 없다. 그 안의 `test` 메서드 | `class TestTruncate:`의 `def test_short(self)` |
| 폴더 | 명령에 준 폴더 아래를 모두 뒤진다. `.`으로 시작하는 폴더(`.venv`, `.git`)와 `venv`, `build` 같은 이름은 건너뛴다 | `ch06/` |

그래서 `check_text.py`는 테스트로 수집되지 않는다. 이름이 `test_`로 시작하지 않기 때문이다. `text_tools.py`도 마찬가지다. 반대로 **이름 규칙을 지키지 않은 테스트는 조용히 무시된다.** `def word_count_test():`나 `ch06/tests_text.py`처럼 쓰면 오류도 없이 수집되지 않는다. 테스트를 새로 썼는데 `collected`의 숫자가 늘지 않았다면 이름부터 확인한다.

이 과정에서는 클래스로 묶지 않고 **함수로** 테스트를 쓴다. 관련된 테스트는 같은 파일에 두고, 이름의 앞부분(`test_word_count_...`, `test_truncate_...`)으로 묶는다. 라이브러리 코드에서 `class TestXxx:`로 묶은 테스트를 만나면 "테스트 함수를 묶어 둔 상자"로 읽으면 된다.

`pytest` 뒤에 아무것도 적지 않으면 **현재 폴더** 아래를 모두 뒤진다. 저장소 폴더에서 `pytest`만 실행하면 `ch01`부터 `ch06`까지 모든 테스트를 찾는다. 이 장에서는 `pytest ch06`처럼 폴더를 적어서 실행한다.

### 6.2.3 실패 메시지 읽기

6.2.1의 실패 하나를 다시 본다.

```
_________________________ test_word_count_many_spaces __________________________

    def test_word_count_many_spaces() -> None:
>       assert word_count("안녕   파이썬") == 2
E       AssertionError: assert 4 == 2
E        +  where 4 = word_count('안녕   파이썬')

ch06/test_text_tools.py:11: AssertionError
```

- **밑줄 사이의 이름** — 실패한 테스트 함수다.
- **`>`가 붙은 줄** — 실패한 줄이다. 그 위의 줄들은 테스트 함수의 앞부분이다.
- **`E`가 붙은 줄** — 무엇이 틀렸는지(Error)다. `assert 4 == 2`는 `==`의 왼쪽이 실제로 `4`였다는 뜻이다. 아래 줄의 `where 4 = word_count('안녕   파이썬')`은 그 `4`가 **어디서 왔는지** 알려 준다.
- **마지막 줄** — 파일과 줄 번호, 예외의 종류다. VS Code 터미널에서 `Cmd`(Windows는 `Ctrl`)를 누른 채 클릭하면 그 줄로 이동한다(5.1.3).

그냥 `assert`가 실패하면 파이썬은 `AssertionError`만 낸다. 무엇과 무엇을 비교했는지는 알려 주지 않는다. pytest는 테스트 파일을 불러올 때 `assert` 문을 **고쳐 써서**(assertion rewriting) 비교한 값들을 기록해 둔다. 그래서 `assert 4 == 2`처럼 양쪽의 실제 값이 보인다. `check_text.py`처럼 기대값과 실제 값을 출력하는 코드를 따로 쓸 필요가 없다.

pytest는 비교하는 값의 종류에 따라 다른 점을 더 자세히 보여 준다. 일부러 실패하는 테스트로 확인한다.

```
FAILED ch06/test_failure_demo.py::test_with_message - AssertionError: 토큰이 ...
============================== 4 failed in 0.02s ===============================
```

- **리스트** — `At index 3 diff`. 몇 번째 원소가 다른지 알려 준다.
- **딕셔너리** — 같은 항목은 생략하고(`Omitting 1 identical items`) 다른 항목만 보여 준다(`Differing items`). 키가 수십 개인 LLM 응답 딕셔너리를 비교할 때 특히 고맙다.
- **`in`** — 무엇을 어디서 찾았는지 보여 준다.
- **메시지를 붙인 `assert`** — `assert 조건, 메시지`처럼 쉼표 뒤에 문자열을 주면 실패할 때 그 메시지가 먼저 나온다. 값만 봐서는 뜻을 알기 어려울 때 쓴다. 대부분은 pytest가 보여 주는 값으로 충분하므로 꼭 붙일 필요는 없다.

출력이 길어서 `...`로 줄인 곳은 `-vv`를 붙이면 모두 보인다. 줄 단위의 차이(diff)도 함께 보여 준다.

```
pytest -vv ch06/test_failure_demo.py::test_dict
```

```
E       AssertionError: assert {'role': 'user', 'content': '안녕'} == {'role': 'user', 'content': ' 안녕 '}
E         
E         Common items:
E         {'role': 'user'}
E         Differing items:
E         {'content': '안녕'} != {'content': ' 안녕 '}
E         
E         Full diff: (-: missing in left side, +: extra in left side)
E           {
E               'role': 'user',
E         -     'content': ' 안녕 ',
E         ?                 -  -
E         +     'content': '안녕',
E           }
```

`Full diff`는 `git diff`처럼 읽는다. `-` 줄은 오른쪽(기대값)에만 있고, `+` 줄은 왼쪽(실제 값)에만 있다. `?` 줄은 그 줄 안에서 다른 글자의 위치를 표시한다. 여기서는 앞뒤 공백 두 개다.

> **`==`의 왼쪽에 실제 값, 오른쪽에 기대값**
> `assert word_count("") == 0`처럼 **실제로 계산한 값을 왼쪽**, 기대하는 값을 오른쪽에 쓰는 것이 관례다. pytest의 diff도 왼쪽을 실제 값(left side)으로 보고 표시한다. 순서를 바꿔 써도 테스트는 똑같이 동작하지만, 메시지를 읽을 때 헷갈린다.

`test_failure_demo.py`는 확인한 뒤 지운다.

### 6.2.4 자주 쓰는 실행 옵션

테스트가 많아지면 필요한 것만 골라 실행하고, 필요한 만큼만 보고 싶어진다. 6.2.1의 회귀 판(`split(" ")`)으로 잠시 바꿔 두고 옵션을 하나씩 실행해 본다.

| 옵션 | 하는 일 |
|---|---|
| `-v` | 테스트마다 한 줄씩 이름과 결과(`PASSED`/`FAILED`)를 보여 준다 |
| `-q` | 반대로 짧게 보여 준다. 머리 부분을 생략한다 |
| `-x` | 첫 실패에서 멈춘다. 실패가 쏟아질 때 첫 번째부터 고친다(5.1.3의 "위에서부터 하나씩") |
| `-k 식` | 이름에 그 글자가 들어간 테스트만 실행한다. `and`, `or`, `not`을 쓸 수 있다 |
| `파일::함수` | 테스트 하나만 실행한다 |
| `--lf` | 지난번에 실패한 테스트만 다시 실행한다(last failed) |
| `-s` | 테스트 안의 `print()` 출력을 그대로 보여 준다(6.4.2) |
| `-vv` | 비교한 값을 줄이지 않고 모두 보여 준다(6.2.3) |

```
pytest -v ch06
```

```

ch06/test_text_tools.py::test_word_count_many_spaces FAILED              [ 28%]
```

각 줄의 `ch06/test_text_tools.py::test_word_count_basic`이 그 테스트의 **이름표**(node id)다. 이 이름표를 그대로 명령에 적으면 그 테스트 하나만 실행한다.

```

```

`4 deselected`는 이름이 맞지 않아 **빼놓은** 테스트의 수다. `-k "word_count and not empty"`처럼 조건을 조합할 수도 있다. 식에 빈칸이 있으면 따옴표로 감싼다.

`--lf`는 지난번 실행에서 실패한 테스트만 다시 실행한다.

```

```


코드를 고치고 `--lf`로 실패했던 것만 빠르게 확인한 다음, 마지막에는 **옵션 없이 전체를** 실행한다. 실패했던 것을 고치다가 다른 것을 망가뜨렸을 수 있기 때문이다. 회귀는 언제나 확인하지 않은 곳에서 생긴다.

pytest는 지난번에 무엇이 실패했는지를 저장소 폴더의 `.pytest_cache` 폴더에 기록해 둔다. `--lf`가 이 기록을 쓴다. 5장의 `.mypy_cache`처럼 도구가 만드는 캐시다. 실습 6-8에서 `.gitignore`를 정리할 때 다시 본다.

옵션을 모두 확인했으면 `word_count()`를 `split()`으로 되돌린다.

### 6.2.5 pytest가 모듈을 찾는 방법

`test_text_tools.py`의 첫 줄은 `from text_tools import truncate, word_count`다. 저장소 폴더에서 `pytest ch06`을 실행했는데 어떻게 `ch06` 안의 `text_tools.py`를 찾았을까?

`python ch06/check_text.py`로 실행할 때는 파이썬이 **실행한 파일이 있는 폴더**(`ch06`)를 모듈 검색 경로 `sys.path`의 맨 앞에 넣는다(기초 과정 8.1.6). 그래서 같은 폴더의 `text_tools`를 찾았다. 3장의 `tools_practice.py`가 `from log_pipeline import ...`로 같은 폴더의 파일을 가져온 것도 이 덕분이다.

pytest도 비슷하게 한다. 테스트 파일을 불러오기 전에, 그 파일이 있는 폴더를 `sys.path`의 앞에 넣는다. 그래서 테스트 파일은 같은 폴더의 모듈을 이름만으로 가져올 수 있다. 다만 이 방식에는 한 가지 함정이 있다. **다른 폴더에 이름이 같은 테스트 파일**이 있으면 둘을 구별하지 못한다. 예를 들어 7장에서 `ch07/test_text_tools.py`를 만들고 저장소 폴더에서 `pytest`만 실행하면 수집 단계에서 오류가 난다.

```
==================================== ERRORS ====================================
___________________ ERROR collecting ch07/test_text_tools.py ____________________
import file mismatch:
imported module 'test_text_tools' has this __file__ attribute:
  /Users/.../python-advanced-lab/ch06/test_text_tools.py
which is not the same as the test file we want to collect:
  /Users/.../python-advanced-lab/ch07/test_text_tools.py
HINT: remove __pycache__ / .pyc files and/or use a unique basename for your test file modules
```

모듈 이름은 파일 이름에서 나오므로 두 파일 모두 `test_text_tools`라는 같은 이름의 모듈이 된다. 이 과정에서는 **장이 달라도 테스트 파일 이름이 겹치지 않게** 짓는다. 테스트하지 않는 보통 모듈(`text_tools.py`)의 이름이 겹치는 것도 피한다. 장마다 폴더를 나눈 연습용 저장소라서 생기는 문제다. 8장에서 프로젝트를 패키지 구조(`src` 레이아웃)로 만들면 이 문제가 사라진다.

> **저장하면 `import` 사이의 빈 줄이 없어진다**
> 6.3부터 테스트 파일에 `import pytest`와 `from chunking import chunk`가 함께 나온다. 표준 라이브러리, 외부 패키지, 우리가 만든 모듈을 빈 줄로 나눠 쓰는 것이 파이썬 스타일 가이드(PEP 8)의 관례인데, VS Code에서 저장하면 Ruff가 `import pytest`와 `from chunking import chunk` 사이의 빈 줄을 없앤다. Ruff는 **저장소 폴더 바로 아래**에 있는 모듈만 "우리가 만든 모듈"로 알아본다. `ch06` 안의 `chunking`은 `pytest`와 같은 외부 패키지로 보고 한 무리로 묶는다. 이 장의 코드는 Ruff가 정리한 모양 그대로 싣는다. 8장에서 패키지 구조를 갖추면 다시 나뉜다.

### 6.2.6 VS Code 테스트 탐색기

VS Code에서도 테스트를 찾고 실행할 수 있다. 1장에서 "이 파일은 6장(테스트 탐색기)에서 몇 줄씩 늘어난다"고 한 작업 공간 설정에 세 줄을 더한다(1.2.4).

`.vscode/settings.json`

```jsonc
{
    "[python]": {
        "editor.defaultFormatter": "charliermarsh.ruff",
        "editor.formatOnSave": true,
        "editor.codeActionsOnSave": {
            "source.fixAll.ruff": "explicit",
            "source.organizeImports.ruff": "explicit"
        }
    },
    "files.exclude": {
        "**/__pycache__": true,
        "**/.mypy_cache": true,
        "**/.pytest_cache": true,
        "**/.ruff_cache": true
    },
    "python.analysis.typeCheckingMode": "standard",
    "python.testing.pytestEnabled": true,
    "python.testing.unittestEnabled": false,
    "python.testing.pytestArgs": ["."]
}
```

- `"python.testing.pytestEnabled": true` — 테스트 도구로 pytest를 쓴다.
- `"python.testing.unittestEnabled": false` — 표준 라이브러리의 `unittest`(6.5.5에서 그 일부를 쓴다)를 테스트 도구로 쓰지 않는다. 둘 중 하나만 켠다.
- `"python.testing.pytestArgs": ["."]` — 작업 공간 폴더 전체에서 테스트를 찾는다. 터미널에서 저장소 폴더에서 `pytest`를 실행하는 것과 같다.
- `files.exclude`에 `.pytest_cache`와 `.ruff_cache`(6.6.3)를 더해 탐색기에서 감췄다.

저장하고 왼쪽 활동 막대의 **비커 모양 아이콘**(테스트)을 누르면 테스트 탐색기가 열린다. `python-advanced-lab` → `ch06` → `test_text_tools.py` → 테스트 함수 순서로 나무 모양의 목록이 보인다. 목록이 비어 있으면 명령 팔레트에서 `Test: Refresh Tests`를 실행한다. 그래도 비어 있으면 1.2.4에서 고른 인터프리터가 `.venv`인지, 그 가상환경에 pytest를 설치했는지 확인한다.

- 목록 위의 **▷ 버튼**(Run Tests)은 모두, 각 줄의 ▷는 그 파일이나 그 테스트 하나만 실행한다. 결과는 초록 체크(통과)와 빨간 X(실패)로 보인다.
- 테스트 파일을 열면 **테스트 함수 왼쪽 줄 번호 옆**에도 ▷ 표시가 생긴다. 누르면 그 테스트를 실행하고, 결과에 따라 체크나 X로 바뀐다.
- 실패한 테스트는 실패한 `assert` 줄 아래에 **실패 메시지가 펼쳐진다.** pytest가 터미널에 출력하던 `E` 줄과 같은 내용이다.

**테스트를 디버거로 실행하기**

테스트 탐색기의 진짜 쓸모는 **디버거와 함께 쓸 때**다. 회귀 판(`split(" ")`)으로 잠시 바꾸고 다음을 해 본다.

1. `text_tools.py`의 `return len([w for w in words if w not in PUNCTUATION])` 줄 왼쪽을 눌러 중단점을 건다(기초 과정 4.1.8, 이 과정 4.2.7).
2. 테스트 탐색기에서 `test_word_count_many_spaces`에 마우스를 올리고 **Debug Test** 버튼(벌레가 달린 ▷)을 누른다. 테스트 함수 옆의 ▷를 오른쪽 클릭해 `Debug Test`를 골라도 된다.
3. 중단점에서 멈추면 변수 창에서 `words`를 펼친다. `['안녕', '', '', '파이썬']`이 보인다. 빈 문자열 두 개가 범인이다.

`print()`를 넣고 다시 실행하는 것보다 빠르다. 특히 테스트는 **문제를 일으키는 입력이 이미 적혀 있으므로**, 실패한 테스트를 디버거로 실행하는 것이 버그를 찾는 가장 빠른 길이다. 확인했으면 중단점을 지우고 `split()`으로 되돌린다.

## 6.3 테스트 작성 기술

### 6.3.1 준비·실행·확인

3장에서 제너레이터 파이프라인의 함수들을 두고 "각 함수가 하는 일이 하나라서 따로 시험하기 쉽다. 6장에서 이 함수들에 테스트를 붙인다"고 했다(3.4.2). 그 약속을 지킨다. 먼저 3장의 `chunk()`(3.4.6)부터 시작한다. 5장에서 배운 대로 타입 힌트를 붙여 `ch06`으로 옮긴다. 파이프라인의 나머지 함수는 실습 6-3에서 테스트한다.

`ch06/chunking.py`

```python
"""긴 글을 조각으로 나눈다 — 3장 chunking.py에 타입 힌트를 붙였다."""

from collections.abc import Iterator


def chunk(text: str, size: int, overlap: int = 0) -> Iterator[str]:
    """text를 size글자씩 자른다. 앞 조각의 끝 overlap글자를 다음 조각의 앞에 겹친다."""
    if not 0 <= overlap < size:
        raise ValueError("overlap은 0 이상, size 미만이어야 한다")
    step = size - overlap
    for start in range(0, len(text), step):
        yield text[start : start + size]
        if start + size >= len(text):
            break
```

테스트 하나는 보통 세 부분으로 이루어진다.

```python
def test_chunk_splits_by_size() -> None:
    # 준비
    text = "가나다라마바사아자차"
    # 실행
    pieces = list(chunk(text, 4))
    # 확인
    assert pieces == ["가나다라", "마바사아", "자차"]
```

- **준비**(Arrange) — 테스트할 입력과 필요한 객체를 만든다.
- **실행**(Act) — 테스트할 코드를 **한 번** 부른다.
- **확인**(Assert) — 결과가 기대와 같은지 `assert`로 확인한다.

영어 머리글자를 따서 **AAA 패턴**이라고 한다. 세 부분을 빈 줄로 나눠 두면 무엇을 준비해서 무엇을 부르고 무엇을 확인하는지 한눈에 보인다. 위처럼 주석을 달 필요는 없다. 짧은 테스트는 한두 줄로 합쳐도 된다. 중요한 것은 **실행이 하나**라는 점이다. 한 테스트에서 여러 동작을 차례로 부르고 확인하면, 실패했을 때 어느 동작이 문제인지 알기 어렵다. 동작이 둘이면 테스트를 둘로 나눈다.

`chunk()`가 제너레이터라는 점에 주의한다. `chunk(text, 4)`는 조각을 **만들 준비만** 한 제너레이터 객체다(3.2.1). `list()`로 꺼내야 비교할 수 있다. `assert chunk(text, 4) == [...]`는 제너레이터 객체와 리스트를 비교하므로 언제나 실패한다.

### 6.3.2 정상·경계·실패 경우

무엇을 테스트할지 고를 때 세 가지 경우로 나눠 생각한다.

| 경우 | 뜻 | `chunk()`의 예 |
|---|---|---|
| **정상** | 함수가 원래 하려는 일. 가장 흔한 입력 | 열 글자를 네 글자씩, 겹쳐서 자르기 |
| **경계** | 동작이 바뀌는 지점과 그 바로 옆. 비어 있음, 하나, 딱 맞음, 하나 넘침 | 빈 글, `size`보다 짧은 글, `size`와 같은 글, `size`보다 한 글자 긴 글 |
| **실패** | 받아들이면 안 되는 입력. 정해진 예외가 나야 한다 | `overlap`이 `size`와 같거나 음수 |

버그는 경계에 모인다. `range(0, len(text))`의 끝, `<`와 `<=`, `+ 1`과 `- 1`이 틀리는 곳이 경계다. 2장의 "빈 리스트일 때", 3장의 "마지막 조각"(3.4.6), 5장의 "`None`일 때"(5.2)가 모두 경계였다. 기초 과정 10장에서 시험 파일을 만들 때 "헤더만 있는 파일", "빈 파일"을 따로 둔 것도 같은 생각이다(기초 과정 10.1.3).

세 경우를 나눠 테스트를 쓴다.

### 6.3.3 `pytest.raises()` — 예외가 나야 한다

실패 경우는 "정해진 예외가 나야 통과"다. `with pytest.raises(예외 클래스):` 블록 안에서 그 예외가 나면 통과, 나지 않으면 실패다. 다른 종류의 예외가 나면 그 예외가 그대로 올라와 역시 실패다. 4장에서 만든 컨텍스트 관리자(4.6)를 pytest가 이런 일에 쓴다.

여기에는 제너레이터의 함정이 하나 숨어 있다. 3장에서 "제너레이터 안의 예외는 함수를 **호출할 때가 아니라 값을 꺼낼 때** 올라온다"고 했다(3.2.4). `list()`를 빠뜨리면 어떻게 될까?

```python
def test_forgot_list() -> None:
    with pytest.raises(ValueError):
        chunk("가나다", 3, overlap=3)
```

```
    def test_forgot_list() -> None:
>       with pytest.raises(ValueError):
             ^^^^^^^^^^^^^^^^^^^^^^^^^
E       Failed: DID NOT RAISE ValueError
```

`chunk()`를 부르기만 하고 꺼내지 않았으므로 `if not 0 <= overlap < size:` 줄은 실행되지도 않았다. 이 성질 자체를 테스트로 적어 둘 수도 있다. `test_chunking.py`에 더한다.

```python
def test_chunk_raises_only_when_consumed() -> None:
    pieces = chunk("가나다", 3, overlap=3)
    with pytest.raises(ValueError):
        next(pieces)
```

첫 줄에서는 예외가 나지 않고, `next()`로 처음 꺼낼 때 난다. 3장에서 디버거로 따라가며 본 것을 이제 테스트가 확인한다.

**예외의 메시지와 속성 확인하기**

같은 `ValueError`라도 이유가 여럿일 수 있다. 메시지까지 확인하려면 `match=`를 쓴다. 토큰 수로 요금을 어림하는 함수로 확인한다.

`ch06/cost.py`

```python
"""토큰 수로 요금을 어림한다."""

from collections.abc import Iterable

# 100만 토큰당 요금(달러). 입력과 출력의 요금이 다르다.
PRICES = {
    "small": (0.25, 1.25),
    "large": (3.0, 15.0),
}


def estimate_cost(model: str, input_tokens: int, output_tokens: int) -> float:
    """model로 input_tokens를 보내고 output_tokens를 받을 때의 요금(달러)."""
    if model not in PRICES:
        raise KeyError(f"모르는 모델: {model}")
    if input_tokens < 0 or output_tokens < 0:
        raise ValueError(
            f"토큰 수는 0 이상이어야 한다: {input_tokens}, {output_tokens}"
        )
    input_price, output_price = PRICES[model]
    return (input_tokens * input_price + output_tokens * output_price) / 1_000_000


def total_cost(calls: Iterable[tuple[str, int, int]]) -> float:
    """(모델, 입력 토큰, 출력 토큰) 호출 기록들의 요금 합계."""
    return sum(estimate_cost(model, i, o) for model, i, o in calls)
```

`ch06/test_cost.py`

```python
"""cost의 테스트 — pytest.raises()와 pytest.approx()."""

import pytest
from cost import estimate_cost


def test_estimate_cost_small() -> None:
    assert estimate_cost("small", 1200, 300) == 0.000675


def test_unknown_model() -> None:
    with pytest.raises(KeyError):
        estimate_cost("medium", 100, 100)


def test_negative_tokens() -> None:
    with pytest.raises(ValueError, match="0 이상"):
        estimate_cost("small", -1, 100)


def test_negative_tokens_message() -> None:
    with pytest.raises(ValueError) as excinfo:
        estimate_cost("small", 100, -5)
    assert "-5" in str(excinfo.value)
```

- `match="0 이상"` — 예외 메시지에 이 글자가 **들어 있는지** 확인한다. 정확히는 정규 표현식으로 검색한다. 그래서 `.`, `(`, `?`처럼 정규 표현식에서 뜻이 있는 글자를 쓸 때는 조심한다. 메시지의 특징적인 낱말 몇 개만 적는 것이 안전하다.
- `as excinfo` — 일어난 예외의 정보를 담는다. 블록이 끝난 뒤 `excinfo.value`로 **예외 객체**를 꺼낼 수 있다. 4장의 `RateLimitError`처럼 예외에 속성(`status`, `retry_after`)이 있으면 `excinfo.value.status == 429`처럼 확인한다.

`with pytest.raises(...)` 블록 안에는 **예외가 날 줄 한 줄만** 넣는다. 블록 안에 여러 줄을 넣으면 기대한 줄이 아니라 다른 줄에서 같은 종류의 예외가 나도 통과해 버린다.

### 6.3.4 `pytest.approx()` — 실수는 "거의 같다"로 비교한다

호출 열 번의 요금 합계를 확인한다. 한 번에 `0.000675`달러이므로 열 번이면 `0.00675`달러다.

```python
def test_total_cost_exact() -> None:
    calls = [("small", 1200, 300)] * 10
    assert total_cost(calls) == 0.00675
```

```
    def test_total_cost_exact() -> None:
        calls = [("small", 1200, 300)] * 10
>       assert total_cost(calls) == 0.00675
E       AssertionError: assert 0.006750000000000001 == 0.00675
E        +  where 0.006750000000000001 = total_cost([('small', 1200, 300), ('small', 1200, 300), ('small', 1200, 300), ('small', 1200, 300), ('small', 1200, 300), ('small', 1200, 300), ...])
```

`0.006750000000000001`. 기초 과정에서 본 `0.1 + 0.2 == 0.3`이 `False`가 되는 것과 같은 실수의 오차다(기초 과정 2.1.3, 2.2.4). 기초 과정에서 "실수는 `==`로 비교하지 않는다"고 했다. 실수를 여러 번 더하면 오차가 쌓인다. 코드는 틀리지 않았다. **실수를 `==`로 비교한 테스트가** 틀렸다.

실수는 `pytest.approx()`로 감싸서 "거의 같다"로 비교한다.

```python
def test_total_cost() -> None:
    calls = [("small", 1200, 300)] * 10
    assert total_cost(calls) == pytest.approx(0.00675)
```

`pytest.approx(0.00675)`는 기본으로 기대값의 **백만분의 1**(상대 오차 `1e-6`)까지의 차이를 같다고 본다. 허용 범위를 바꾸려면 `pytest.approx(0.00675, rel=1e-3)`(상대 오차), `pytest.approx(0.0, abs=1e-9)`(절대 오차)처럼 쓴다. 리스트와 딕셔너리에도 쓸 수 있다. `[0.1 + 0.2, 0.3] == pytest.approx([0.3, 0.3])`은 참이다.

`test_estimate_cost_small`은 `==`로 비교하는데 왜 통과했을까? 이번 계산은 우연히 오차 없이 나누어떨어졌을 뿐이다. 실수를 비교할 때는 우연에 기대지 말고 **언제나** `approx()`를 쓴다. `test_estimate_cost_small`도 `pytest.approx(0.000675)`로 바꿔 둔다.

두 테스트를 `test_cost.py`에 더할 때 맨 위의 `import` 줄도 `from cost import estimate_cost, total_cost`로 고친다. `total_cost`를 미리 적어 두지 않은 것은, 쓰지 않는 이름을 `import`해 두면 저장할 때 Ruff가 지우기 때문이다(6.6.3의 `F401`). `test_total_cost_exact`는 확인한 뒤 지우고, `test_total_cost`를 남긴다.

> **돈은 실수로 계산하지 않는다**
> 실제 요금 청구처럼 한 푼도 틀리면 안 되는 계산에는 실수(`float`)를 쓰지 않는다. 표준 라이브러리의 `decimal.Decimal`을 쓰거나, 가계부 프로그램(기초 과정 10장)처럼 **가장 작은 단위의 정수**(원, 센트)로 계산한다. 이 예의 `estimate_cost()`는 "대략 얼마나 드는지" 어림하는 함수라서 실수를 썼다.

### 6.3.5 `@pytest.mark.parametrize` — 여러 입력을 한 번에

1장에서 미리 본 테스트(1.1.3 (마))가 이것이었다.

```python
@pytest.mark.parametrize("size", [1, 3, 500])
def test_chunk_keeps_all_text(size):
    text = "가나다라마바사"
    assert "".join(chunk(text, size)) == text
```

"조각을 이어 붙이면 원래 글이 된다"는 **크기가 얼마든** 성립해야 한다. 크기마다 테스트 함수를 따로 쓰는 대신, 테스트 하나에 입력 목록을 붙인다. `test_chunking.py`에 더한다.

```python
@pytest.mark.parametrize("size", [1, 3, 5, 100])
def test_chunk_keeps_all_text(size: int) -> None:
    text = "가나다라마바사아자차"
    assert "".join(chunk(text, size)) == text
```

- `@pytest.mark.parametrize("size", [1, 3, 5, 100])` — 매개변수 이름과 값의 목록이다. pytest는 값마다 테스트를 한 번씩, 모두 네 번 실행한다.
- `def test_chunk_keeps_all_text(size: int)` — 테스트 함수가 그 이름의 매개변수를 받는다. 4장에서 본 데코레이터(4.3)가 함수에 "이 값들로 불러 달라"는 표시를 붙인 것이다.

매개변수가 여럿이면 이름을 튜플로, 값은 튜플의 리스트로 준다.

```python
@pytest.mark.parametrize(
    ("text", "size", "expected"),
    [
        ("", 5, 0),
        ("가나다", 5, 1),
        ("가나다라마", 5, 1),
        ("가나다라마바", 5, 2),
        ("가" * 12, 5, 3),
    ],
)
def test_chunk_count(text: str, size: int, expected: int) -> None:
    assert len(list(chunk(text, size))) == expected
```

6.3.2에서 경계 경우마다 따로 쓴 테스트를 표 하나로 모은 셈이다. 입력과 기대값이 **표처럼 나란히** 보여서, 빠진 경우를 찾기도 쉽다. `-v`로 실행해 본다.

대괄호 안이 그 실행의 **이름표**(id)다. pytest가 값을 `-`로 이어서 만든다. 그런데 한글이 `\uac00\ub098\ub2e4`처럼 나온다. `가`, `나`, `다`의 유니코드 번호를 `\u` 뒤에 16진수로 적은 표기(유니코드 이스케이프)다. pytest는 운영체제나 터미널에 따라 문제가 생기지 않도록 이름표의 영어가 아닌 글자를 이렇게 바꿔 쓴다. 긴 문자열이나 객체를 값으로 쓰면 이름표가 읽기 어려워진다. 이럴 때는 이름표를 직접 붙인다.

```python
@pytest.mark.parametrize(
    ("text", "size", "expected"),
    [
        ("", 5, 0),
        ("가나다", 5, 1),
        ("가나다라마", 5, 1),
        ("가나다라마바", 5, 2),
        ("가" * 12, 5, 3),
    ],
    ids=["empty", "shorter", "exact", "one-more", "twelve"],
)
def test_chunk_count(text: str, size: int, expected: int) -> None:
    assert len(list(chunk(text, size))) == expected
```

`ids=`에 값의 순서대로 이름표의 목록을 준다. 경우가 많아서 목록 두 개의 순서를 맞추기 어렵다면, 값마다 `pytest.param()`으로 감싸고 `id=`를 붙인다. 실패 경우를 이렇게 모은다.

```python
@pytest.mark.parametrize(

    [
        pytest.param(5, -1, id="negative-overlap"),
        pytest.param(5, 5, id="overlap-equals-size"),
        pytest.param(0, 0, id="zero-size"),
    ],
)
def test_chunk_rejects_bad_arguments(size: int, overlap: int) -> None:
    with pytest.raises(ValueError):
        list(chunk("가나다", size, overlap))
```

### 6.3.6 좋은 테스트의 습관

- **테스트 하나는 동작 하나를 확인한다.** 실패한 테스트의 이름만 보고도 무엇이 망가졌는지 알 수 있어야 한다. `assert`가 여럿이어도 한 동작의 여러 면을 확인하는 것이면 괜찮다(6.5.3의 "결과도 맞고, 호출도 한 번").
- **테스트는 서로 기대지 않는다.** 앞의 테스트가 만든 것을 뒤의 테스트가 쓰면 안 된다. pytest는 파일에 적힌 순서대로 실행하지만, `-k`나 `--lf`로 하나만 실행할 때도 통과해야 한다. 테스트마다 준비를 새로 한다. 되풀이되는 준비는 6.4의 픽스처로 뽑아낸다.
- **기대값을 계산하지 않는다.** `assert estimate_cost("small", 1200, 300) == (1200 * 0.25 + 300 * 1.25) / 1_000_000`처럼 함수와 같은 계산을 테스트에 다시 쓰면, 계산이 틀렸을 때 테스트도 함께 틀린다. 기대값은 손으로 구한 **값**으로 적는다(6.1.4).
- **테스트 안에 `if`와 `for`를 쓰지 않는다.** 조건이나 반복이 필요하면 `parametrize`를 쓴다. 테스트에 논리가 들어가면 테스트도 테스트해야 한다.
- **실패하는 것을 한 번은 본다.** 새 테스트를 썼으면 코드를 일부러 틀리게 바꿔서 그 테스트가 정말 실패하는지 확인한다. 한 번도 실패하는 것을 보지 못한 테스트는 아무것도 확인하지 않는 테스트일 수 있다. 실습 6-2의 2번 `test_d`가 그런 예다.
- **테스트도 코드다.** 읽기 쉽게 쓰고, 이름을 잘 짓고, 커밋한다. 테스트가 읽기 어려우면 실패했을 때 무엇이 문제인지 알기 어렵다.

## 6.4 픽스처

### 6.4.1 되풀이되는 준비 — `@pytest.fixture`

4.4.2에서 같은 프롬프트의 응답을 기억해 두는 캐시를 만들었다. 이번에는 응답을 표준 라이브러리의 **SQLite** 데이터베이스에 저장해서, 프로그램을 다시 실행해도 남아 있게 한다. SQLite는 파일 하나(또는 메모리)에 데이터를 표로 저장하는 작은 데이터베이스다. 파이썬에 `sqlite3` 모듈로 들어 있다. SQL 문장은 읽을 수 있을 정도로만 보면 된다.

`ch06/answer_cache.py`

```python
"""LLM 응답을 SQLite에 저장해 두는 캐시."""

import sqlite3


class AnswerCache:
    """프롬프트를 키로 응답을 저장한다. 4.4.2의 응답 캐시를 파일에 남기는 판이다."""

    def __init__(self, conn: sqlite3.Connection) -> None:
        self.conn = conn
        self.conn.execute(
            "CREATE TABLE IF NOT EXISTS answers (prompt TEXT PRIMARY KEY, answer TEXT)"
        )

    def get(self, prompt: str) -> str | None:
        row = self.conn.execute(
            "SELECT answer FROM answers WHERE prompt = ?", (prompt,)
        ).fetchone()
        return None if row is None else row[0]

    def put(self, prompt: str, answer: str) -> None:
        self.conn.execute(
            "INSERT OR REPLACE INTO answers VALUES (?, ?)", (prompt, answer)
        )
        self.conn.commit()

    def __len__(self) -> int:
        count: int = self.conn.execute("SELECT COUNT(*) FROM answers").fetchone()[0]
        return count
```

- `sqlite3.Connection` — 데이터베이스와의 **연결**이다. `sqlite3.connect("cache.db")`는 파일에, `sqlite3.connect(":memory:")`는 메모리에 데이터베이스를 만든다. 메모리 데이터베이스는 연결을 닫으면 사라진다. 테스트에 알맞다.
- `AnswerCache`는 연결을 **직접 만들지 않고 받는다.** 어느 데이터베이스에 저장할지는 쓰는 쪽이 정한다. 6.5에서 정식으로 다루는 의존성 주입이다.
- `__len__` — `len(cache)`를 쓸 수 있게 한다(1.3.4). `fetchone()`의 결과는 타입이 정해지지 않은 튜플이라 `[0]`이 `Any`다. `count: int`로 받아서 돌려주어야 `mypy --strict`가 통과한다(5.1.6).

테스트를 쓰면 테스트마다 같은 두 줄이 되풀이된다.

```python
def test_new_cache_is_empty() -> None:
    cache = AnswerCache(sqlite3.connect(":memory:"))
    assert len(cache) == 0


def test_put_then_get() -> None:
    cache = AnswerCache(sqlite3.connect(":memory:"))
    cache.put("파이썬이란?", "프로그래밍 언어")
    assert cache.get("파이썬이란?") == "프로그래밍 언어"
```

준비가 한 줄이면 괜찮지만, 준비가 길어지거나 준비하는 방법이 바뀌면(예: 테이블 이름이 바뀐다) 모든 테스트를 고쳐야 한다. 게다가 연결을 닫지 않았다. 이렇게 **테스트에 필요한 준비물**을 만드는 일을 함수로 뽑아낸 것을 **픽스처**(fixture)라고 한다. 원래 실험이나 공장에서 대상을 고정해 두는 받침대를 부르는 말이다.

```python
@pytest.fixture
def cache() -> AnswerCache:
    return AnswerCache(sqlite3.connect(":memory:"))


def test_new_cache_is_empty(cache: AnswerCache) -> None:
    assert len(cache) == 0
```

- `@pytest.fixture` — 이 함수가 픽스처라는 표시다. 픽스처 함수는 테스트가 쓸 준비물을 돌려준다.
- `def test_new_cache_is_empty(cache: AnswerCache)` — 테스트 함수의 **매개변수 이름**이 픽스처 이름과 같으면, pytest가 테스트를 부르기 전에 그 픽스처를 불러서 결과를 넘겨준다. 테스트는 픽스처를 직접 부르지 않는다.
- **테스트마다 새로 만든다.** 테스트 네 개가 `cache`를 쓰면 픽스처 함수가 네 번 불려서 서로 다른 캐시 네 개가 만들어진다. 한 테스트가 넣은 값이 다른 테스트에 남지 않는다. 6.3.6의 "테스트는 서로 기대지 않는다"를 픽스처가 지켜 준다.

매개변수 이름으로 넘겨받는 방식이 처음에는 마법처럼 보인다. 4장의 등록 데코레이터(4.5)가 함수를 딕셔너리에 이름으로 등록해 두었다가 찾아 부른 것처럼, pytest도 `@pytest.fixture`가 붙은 함수를 이름으로 기억해 두었다가 테스트의 매개변수 이름을 보고 찾아 부른다. 이런 방식을 **의존성 주입**(dependency injection)이라고 한다. 테스트는 "`cache`가 필요하다"고 말하기만 하고, 만드는 일은 pytest가 맡는다.

### 6.4.2 `yield` 픽스처 — 준비와 정리

연결을 닫는 일까지 픽스처에 맡기려면 `return` 대신 `yield`를 쓴다. 먼저 순서를 확인한다.

`ch06/test_fixture_order.py`

```python
"""픽스처의 준비와 정리가 언제 일어나는지 본다. 확인한 뒤 지운다."""

from collections.abc import Iterator

import pytest


@pytest.fixture
def resource() -> Iterator[str]:
    print("\n  [준비] 자원을 연다")
    yield "자원"
    print("\n  [정리] 자원을 닫는다")


def test_first(resource: str) -> None:
    print(f"  test_first가 {resource}을 쓴다")


def test_second(resource: str) -> None:
    print(f"  test_second가 {resource}을 쓴다")
    assert resource == "다른 자원"
```

pytest는 테스트 안의 `print()` 출력을 **붙잡아 두고** 보여 주지 않는다. 화면이 지저분해지지 않게 하려는 것이다. 그대로 보려면 `-s`를 붙인다.

- `yield` 앞이 **준비**, `yield`한 값이 테스트에 넘어가는 준비물, `yield` 뒤가 **정리**다.
- 정리는 테스트가 **실패해도** 실행된다. `test_second`가 실패한 뒤에도 `[정리]`가 출력되었다.
- 테스트마다 준비와 정리가 한 번씩 일어난다.

4.6.4의 `@contextmanager`와 똑같은 모양이다. `yield` 앞에서 준비하고, `yield`로 값을 넘기고, 뒤에서 정리한다. 3장의 `yield`가 "값을 내놓고 멈춘다"였으므로, pytest는 테스트를 실행하기 전에 픽스처를 `yield`까지 실행하고, 테스트가 끝나면 나머지를 실행한다. 반환 타입이 `Iterator[str]`인 것도 5.3.4의 "`@contextmanager` 함수는 `Iterator[...]`"와 같다.

```
--------------------------- Captured stdout teardown ---------------------------
```

통과한 테스트의 출력은 보이지 않고, **실패한 테스트의 출력만** 실패 메시지 아래에 단계별로 나온다. `setup`(준비), `call`(테스트 실행), `teardown`(정리)이다. 테스트에 `print()`를 넣어 두면 평소에는 조용하다가 실패할 때만 단서가 된다. 확인했으면 `test_fixture_order.py`를 지운다.

이제 데이터베이스 연결을 `yield` 픽스처로 만든다. 픽스처는 **다른 픽스처를 받을 수 있다.** 연결을 만드는 픽스처와 캐시를 만드는 픽스처를 나눈다.

```python
"""AnswerCache의 테스트 — 픽스처."""

import sqlite3
from collections.abc import Iterator

import pytest
from answer_cache import AnswerCache


@pytest.fixture
def conn() -> Iterator[sqlite3.Connection]:
    connection = sqlite3.connect(":memory:")
    yield connection
    connection.close()


@pytest.fixture
def cache(conn: sqlite3.Connection) -> AnswerCache:
    return AnswerCache(conn)


def test_new_cache_is_empty(cache: AnswerCache) -> None:
    assert len(cache) == 0


def test_get_missing_prompt_returns_none(cache: AnswerCache) -> None:
    assert cache.get("없는 프롬프트") is None


def test_put_then_get(cache: AnswerCache) -> None:
    cache.put("파이썬이란?", "프로그래밍 언어")
    assert cache.get("파이썬이란?") == "프로그래밍 언어"
    assert len(cache) == 1


def test_put_same_prompt_replaces_answer(cache: AnswerCache) -> None:
    cache.put("파이썬이란?", "뱀")
    cache.put("파이썬이란?", "프로그래밍 언어")
    assert cache.get("파이썬이란?") == "프로그래밍 언어"
    assert len(cache) == 1
```

### 6.4.3 `conftest.py`와 픽스처의 범위

`conn` 픽스처를 다른 테스트 파일에서도 쓰고 싶다면 어떻게 할까? 테스트 파일에서 다른 테스트 파일을 `import`하지 않는다. 대신 같은 폴더에 **`conftest.py`**라는 파일을 만들고 그곳에 픽스처를 둔다.

`ch06/conftest.py`

```python
"""ch06의 테스트가 함께 쓰는 픽스처와 설정."""

import sqlite3
from collections.abc import Iterator

import pytest


@pytest.fixture
def conn() -> Iterator[sqlite3.Connection]:
    """메모리 안의 SQLite 데이터베이스. 테스트가 끝나면 닫는다."""
    connection = sqlite3.connect(":memory:")
    yield connection
    connection.close()
```

`test_answer_cache.py`에서는 `conn` 픽스처와 이제 쓰지 않는 `from collections.abc import Iterator`를 지운다. 그래도 테스트는 그대로 통과한다.

- `conftest.py`는 pytest가 **알아서 읽는** 특별한 이름의 파일이다. 테스트 파일에서 `import`하지 않는다.
- `conftest.py`에 둔 픽스처는 **그 폴더와 그 아래 폴더**의 모든 테스트 파일에서 쓸 수 있다. `ch06/conftest.py`의 픽스처는 `ch06`의 테스트만 쓴다.
- 테스트에서 처음 보는 픽스처 이름이 나오면 같은 파일 → 같은 폴더의 `conftest.py` → 위 폴더의 `conftest.py` 순서로 찾아본다. VS Code에서 매개변수 이름에 `F12`를 누르면 픽스처의 정의로 이동한다.
- 6.5에서 이 파일에 가짜 LLM 클라이언트 픽스처와 설정을 더한다.

**픽스처의 범위 — `scope`**

픽스처는 기본으로 테스트마다 새로 만든다. 준비가 오래 걸린다면(큰 파일 읽기, 서버 띄우기) 여러 테스트가 하나를 나눠 쓰게 할 수 있다.

```python
@pytest.fixture(scope="module")
def conn() -> Iterator[sqlite3.Connection]:
    ...
```

| `scope` | 언제 새로 만드는가 |
|---|---|
| `"function"` (기본) | 테스트마다 |
| `"module"` | 테스트 파일마다 한 번 |
| `"session"` | `pytest`를 한 번 실행할 때 한 번 |

`@pytest.fixture(scope="module")`처럼 괄호가 있어도 없어도 되는 데코레이터는 4.3.5에서 보았다. 그런데 범위를 넓히면 **테스트가 서로 기대게 된다.** `conn`을 `scope="module"`로 바꾸고 `test_answer_cache.py`의 `test_new_cache_is_empty`를 파일 **맨 아래로** 옮긴 뒤 실행해 본다.

```
pytest ch06/test_answer_cache.py
```

```
>       assert len(cache) == 0
E       assert 1 == 0
...
FAILED ch06/test_answer_cache.py::test_new_cache_is_empty - assert 1 == 0
```

앞의 테스트들이 같은 데이터베이스에 넣은 값이 남아 있다. 맨 위에 있을 때는 우연히 통과했을 뿐이다. 넓은 범위의 픽스처는 **바뀌지 않는 것**(읽기만 하는 데이터, 설정)에만 쓴다. 테스트가 바꾸는 것은 기본 범위로 둔다. 확인한 뒤 `scope`와 순서를 되돌린다.

### 6.4.4 `tmp_path` — 임시 폴더

pytest에는 미리 만들어 둔 **내장 픽스처**가 있다. 매개변수 이름만 맞게 쓰면 바로 쓸 수 있다. 첫 번째는 파일을 다루는 코드를 위한 `tmp_path`다.

요약 결과를 저장하는 **JSONL** 파일을 다루는 함수를 만든다. JSONL(JSON Lines)은 **한 줄에 JSON 객체 하나**를 쓰는 형식이다. 결과가 나올 때마다 한 줄씩 덧붙이기 쉽고, 큰 파일도 줄 단위로 읽을 수 있어서(3.4) LLM 데이터와 평가 결과를 저장할 때 널리 쓴다. 9장의 종합 실습도 결과를 JSONL로 저장한다.

`ch06/jsonl_store.py`

```python
"""결과를 JSONL 파일로 저장하고 읽는다. 한 줄에 JSON 객체 하나다."""

import json
from collections.abc import Iterable
from pathlib import Path
from typing import Any


def save_jsonl(path: Path, records: Iterable[dict[str, Any]]) -> int:
    """records를 한 줄에 하나씩 path에 저장하고, 저장한 개수를 돌려준다."""
    count = 0
    with open(path, "w", encoding="utf-8") as f:
        for record in records:
            f.write(json.dumps(record, ensure_ascii=False) + "\n")
            count += 1
    return count


def load_jsonl(path: Path) -> list[dict[str, Any]]:
    """path의 줄마다 JSON 객체를 읽어 리스트로 돌려준다. 빈 줄은 건너뛴다."""
    with open(path, encoding="utf-8") as f:
        return [json.loads(line) for line in f if line.strip()]
```

이 함수를 테스트하려면 파일을 실제로 써야 한다. 저장소 폴더에 파일을 쓰면 테스트가 끝난 뒤 지워야 하고, 지우지 못하면 다음 테스트에 남는다. 테스트 두 개가 같은 이름의 파일을 쓰면 서로 덮어쓴다. `tmp_path`는 **테스트마다 새로 만든 빈 임시 폴더**를 `Path` 객체로 준다.

`ch06/test_jsonl_store.py`

```python
"""jsonl_store의 테스트 — tmp_path."""

from pathlib import Path

from jsonl_store import load_jsonl, save_jsonl


def test_save_and_load(tmp_path: Path) -> None:
    path = tmp_path / "results.jsonl"
    records = [
        {"doc": "가.txt", "summary": "요약 1"},
        {"doc": "나.txt", "summary": "요약 2"},
    ]

    count = save_jsonl(path, records)

    assert count == 2
    assert load_jsonl(path) == records


def test_file_has_one_json_per_line(tmp_path: Path) -> None:
    path = tmp_path / "results.jsonl"
    save_jsonl(path, [{"summary": "한글"}, {"summary": "그대로"}])
    assert (
        path.read_text(encoding="utf-8")
        == '{"summary": "한글"}\n{"summary": "그대로"}\n'
    )


def test_load_skips_blank_lines(tmp_path: Path) -> None:
    path = tmp_path / "results.jsonl"
    path.write_text('{"a": 1}\n\n{"a": 2}\n', encoding="utf-8")
    assert load_jsonl(path) == [{"a": 1}, {"a": 2}]


def test_save_from_generator(tmp_path: Path) -> None:
    path = tmp_path / "results.jsonl"
    count = save_jsonl(path, ({"n": n} for n in range(3)))
    assert count == 3


def test_where_is_tmp_path(tmp_path: Path) -> None:
    print(tmp_path)
```

- `test_save_and_load` — 저장한 것을 다시 읽으면 원래와 같아야 한다. 이렇게 **갔다가 돌아오는** 확인(round trip)은 저장과 읽기를 함께 테스트하는 간단한 방법이다.
- `test_file_has_one_json_per_line` — 그것만으로는 파일의 **모양**을 확인하지 못한다. `ensure_ascii=False`를 빠뜨려 한글이 `\ud55c\uae00`처럼 유니코드 이스케이프로 저장되어도, 읽으면 원래대로 돌아오므로 첫 테스트는 통과한다. 파일 내용을 직접 확인하는 테스트를 따로 둔다.
- `test_load_skips_blank_lines` — 테스트 입력 파일을 `tmp_path` 안에 직접 만든다. `write_text()`로 일부러 빈 줄을 넣었다.
- `test_save_from_generator` — `records`의 타입이 `Iterable`이므로 제너레이터도 받아야 한다(5.3.2). 매개변수 타입이 약속한 것을 테스트로 확인한다.

임시 폴더는 어디에 만들어질까? 마지막 테스트를 `-s`로 실행한다.

```

```

```
/private/var/folders/8l/.../T/pytest-of-jinyoung/pytest-1/test_where_is_tmp_path0
```

운영체제의 임시 폴더 아래, 실행할 때마다 번호가 늘어나는 폴더(`pytest-1`, `pytest-2`, ...) 안에 테스트 이름으로 만든다. pytest는 최근 세 번의 실행 폴더만 남기고 오래된 것은 지운다. 테스트가 실패했을 때 그 폴더를 열어 테스트가 만든 파일을 직접 볼 수 있다. 확인했으면 `test_where_is_tmp_path`는 지운다. `assert`가 없어서 아무것도 확인하지 않는 테스트다.

### 6.4.5 `monkeypatch` — 환경 변수와 속성 바꿔 끼우기

LLM 프로그램은 모델 이름이나 API 키 같은 설정을 **환경 변수**에서 읽는 일이 많다(기초 과정 8.2.1의 `os.environ`).

`ch06/settings.py`

```python
"""환경 변수에서 LLM 설정을 읽는다."""

import os
from dataclasses import dataclass


@dataclass(frozen=True)
class Settings:
    model: str
    max_tokens: int


def load_settings() -> Settings:
    """LLM_MODEL(기본 "small")과 LLM_MAX_TOKENS(기본 1024)를 읽는다."""
    model = os.environ.get("LLM_MODEL", "small")
    raw = os.environ.get("LLM_MAX_TOKENS", "1024")
    try:
        max_tokens = int(raw)
    except ValueError:
        raise ValueError(f"LLM_MAX_TOKENS는 정수여야 한다: {raw!r}") from None
    return Settings(model=model, max_tokens=max_tokens)
```

이 함수를 테스트하려면 환경 변수를 바꿔야 한다. 테스트 안에서 `os.environ["LLM_MODEL"] = "large"`라고 쓰면 그 값이 **다음 테스트에도 남는다.** 4.6.5에서 이 문제를 `temp_env()` 컨텍스트 관리자로 풀었다. "블록 안에서만 바꾸고 나가면 되돌린다." pytest에는 같은 일을 하는 내장 픽스처 `monkeypatch`가 있다.

`ch06/test_settings.py`

```python
"""settings의 테스트 — monkeypatch로 환경 변수 바꾸기."""

import pytest
from settings import Settings, load_settings


def test_defaults(monkeypatch: pytest.MonkeyPatch) -> None:
    monkeypatch.delenv("LLM_MODEL", raising=False)
    monkeypatch.delenv("LLM_MAX_TOKENS", raising=False)
    assert load_settings() == Settings(model="small", max_tokens=1024)


def test_reads_environment(monkeypatch: pytest.MonkeyPatch) -> None:
    monkeypatch.setenv("LLM_MODEL", "large")
    monkeypatch.setenv("LLM_MAX_TOKENS", "256")
    assert load_settings() == Settings(model="large", max_tokens=256)


def test_bad_max_tokens(monkeypatch: pytest.MonkeyPatch) -> None:
    monkeypatch.setenv("LLM_MAX_TOKENS", "많이")
    with pytest.raises(ValueError, match="정수여야"):
        load_settings()
```

- `monkeypatch.setenv(이름, 값)` — 환경 변수를 정한다. `delenv(이름)`은 지운다. `raising=False`는 "원래 없어도 오류를 내지 말라"는 뜻이다.
- 테스트가 끝나면 `monkeypatch`가 바꾼 것을 **모두 원래대로 되돌린다.** 테스트가 실패해도 되돌린다. `yield` 픽스처의 정리 단계에서 하는 일이다.
- `pytest.MonkeyPatch`는 이 픽스처의 타입이다. 내장 픽스처의 타입은 `pytest`에서 가져온다.

`test_defaults`가 처음에 `delenv()`를 부르는 이유는 무엇일까? 이 테스트는 "환경 변수가 **없을 때**"를 확인한다. 그런데 테스트를 실행하는 사람의 컴퓨터에 `LLM_MODEL`이 이미 설정되어 있을 수 있다. 그러면 기본값이 아니라 그 값을 읽어서 실패한다. 테스트는 **실행하는 컴퓨터의 상태에 기대지 않아야** 한다. 내 컴퓨터에서는 통과하는데 다른 사람 컴퓨터에서는 실패하는 테스트는, 테스트가 확인하지 않은 바깥 상태에 기대고 있다는 신호다.

`monkeypatch`는 환경 변수 말고도 **모듈의 함수나 객체의 속성**을 잠시 바꿔 끼울 수 있다(`monkeypatch.setattr()`). 기다리는 함수나 현재 시각처럼 테스트에서 통제하고 싶은 것을 바꿔 끼울 때 쓴다. 6.5.4에서 다룬다. "monkey patch"는 실행 중에 남의 코드를 슬쩍 바꿔 끼운다는 뜻의 오래된 은어다.

### 6.4.6 `capsys` — 출력 확인하기

화면에 출력하는 함수는 무엇을 돌려주지 않으므로 `assert`로 확인할 것이 없어 보인다. 요금 영수증을 출력하는 함수로 본다.

`ch06/receipt.py`

```python
"""호출 기록을 영수증처럼 출력한다."""

from collections.abc import Sequence

from cost import estimate_cost, total_cost


def print_receipt(calls: Sequence[tuple[str, int, int]]) -> None:
    for model, input_tokens, output_tokens in calls:
        cost = estimate_cost(model, input_tokens, output_tokens)
        print(
            f"{model:<6} 입력 {input_tokens:>6,} 출력 {output_tokens:>6,}  ${cost:.6f}"
        )
    print(f"합계 {len(calls)}건  ${total_cost(calls):.6f}")
```

`calls`를 두 번 훑으므로(`for` 문과 `total_cost()`) 매개변수 타입을 `Iterable`이 아니라 `Sequence`로 적었다. 제너레이터를 넘기면 두 번째 훑기에서 아무것도 남지 않는다(3.3.5). 타입이 그 실수를 막는다(5.3.2).

6.4.2에서 pytest가 테스트의 출력을 붙잡아 둔다고 했다. 내장 픽스처 `capsys`는 붙잡아 둔 출력을 테스트가 꺼내 볼 수 있게 한다.

`ch06/test_receipt.py`

```python
"""receipt의 테스트 — capsys로 출력 확인하기."""

import pytest
from receipt import print_receipt


def test_print_receipt(capsys: pytest.CaptureFixture[str]) -> None:
    print_receipt([("small", 1200, 300), ("large", 1000, 500)])

    captured = capsys.readouterr()

    assert captured.out.splitlines() == [
        "small  입력  1,200 출력    300  $0.000675",
        "large  입력  1,000 출력    500  $0.010500",
        "합계 2건  $0.011175",
    ]
    assert captured.err == ""


def test_print_receipt_empty(capsys: pytest.CaptureFixture[str]) -> None:
    print_receipt([])
    assert capsys.readouterr().out == "합계 0건  $0.000000\n"
```

- `capsys.readouterr()` — 지금까지 붙잡힌 출력을 꺼낸다. `.out`은 표준 출력(`print()`), `.err`는 표준 오류(`print(..., file=sys.stderr)`)다(기초 과정 8.2.2). 꺼내면 비워진다.
- `splitlines()` — 줄의 리스트로 바꿔 비교하면, 다를 때 pytest가 **몇 번째 줄**이 다른지 알려 준다(6.2.3).
- `pytest.CaptureFixture[str]` — 이 픽스처의 타입이다. 붙잡은 출력이 문자열(`str`)이라는 뜻이다.

출력을 확인하는 테스트는 **깨지기 쉽다.** 빈칸 하나, 소수점 자리 하나만 바뀌어도 실패한다. 출력의 모양이 곧 약속인 경우(명령행 도구의 출력, 보고서)에만 쓰고, 계산 결과는 출력을 거치지 않고 함수의 반환값으로 확인한다. 기초 과정의 `check_samples.py`가 화면 대신 `storage`와 `core`의 결과를 확인한 것도 그 때문이다. `print_receipt()`가 출력과 계산을 함께 하지 않고 계산은 `estimate_cost()`와 `total_cost()`에 맡긴 덕분에, 계산은 6.3의 테스트가 이미 확인하고 있다. 이 테스트는 **모양**만 확인하면 된다.

**3. 깨진 JSONL**

`load_jsonl()`에 JSON이 아닌 줄이 섞인 파일을 넣으면 어떤 예외가 나는가? `tmp_path`로 그런 파일을 만들어 `pytest.raises()`로 확인한다. 몇 번째 줄이 깨졌는지 알려 주도록 `load_jsonl()`을 고치고 싶다면, 먼저 원하는 예외 메시지를 테스트의 `match=`로 적은 뒤 고친다(기초 과정 10장의 `DataFileError`처럼 "3번째 줄: ..." 모양).

**4. 픽스처 만들기**

`tmp_path`를 받아 `docs` 폴더를 만들고, 그 안에 `a.txt`, `b.txt`, `notes.md` 세 파일을 써 넣고 그 폴더를 돌려주는 픽스처 `docs_dir`을 `conftest.py`에 만든다. `ch06/test_docs_dir.py`에서 이 픽스처를 써서 `sorted(docs_dir.glob("*.txt"))`가 `.txt` 파일 두 개만 이름 순으로 찾는지 확인한다. 이 픽스처는 종합 실습(실습 6-7)에서 비슷한 모양으로 다시 나온다. 테스트 두 개가 `docs_dir`을 쓰면 폴더는 몇 번 만들어지는가? `print()`와 `-s`로 확인한다.

## 6.5 외부 의존을 떼어 내고 테스트하기

### 6.5.1 실제 API를 부르는 테스트는 왜 곤란한가

LLM을 쓰는 코드를 테스트하고 싶다. 가장 먼저 떠오르는 방법은 실제 LLM API를 불러 보는 것이다. 그런데 자동 테스트로 실제 API를 부르면 곤란한 일이 많다.

- **느리다.** LLM 호출 한 번에 몇 초가 걸린다. 테스트 백 개면 몇 분이다. 테스트가 느리면 덜 돌리게 되고, 덜 돌리면 회귀를 늦게 발견한다.
- **돈이 든다.** 코드를 고칠 때마다 테스트를 돌리면 호출 수가 금방 쌓인다.
- **결과가 매번 다르다.** 같은 프롬프트에도 다른 답이 온다. `assert summary == "..."`라고 쓸 수 없다.
- **내 코드와 상관없이 실패한다.** 네트워크가 끊기거나, 요청 한도(429)에 걸리거나, 서버가 과부하(529)면 실패한다. 실패했을 때 내 코드가 틀렸는지 바깥이 문제인지 알 수 없다.
- **API 키가 있어야 한다.** 키가 없는 사람, 8장의 GitHub Actions처럼 키를 두지 않은 곳에서는 실행할 수 없다.
- **실패를 일부러 만들 수 없다.** 재시도 데코레이터가 시간 초과를 제대로 처리하는지 확인하고 싶어도, 실제 API가 원하는 때에 시간 초과를 내 주지 않는다.

시계(`time.sleep()`)와 난수(`random.random()`)도 비슷하다. 재시도 테스트가 정말 1초, 2초를 기다리면 느리고, 지터(4.3.3)가 섞이면 기다리는 시간이 매번 다르다.

해결 방법은 하나다. **바깥 세계와 닿는 부분을 테스트에서 바꿔 끼울 수 있게 만든다.** 테스트에서는 정해 둔 대로 답하고, 원하는 때에 원하는 오류를 내고, 기다리지 않고 기다린 척하는 **가짜**를 넣는다. 이렇게 테스트에서 진짜 대신 쓰는 객체를 통틀어 **테스트 대역**(test double)이라고 한다. 영화의 대역 배우처럼 진짜 대신 나선다는 뜻이다.

### 6.5.2 의존성 주입 — 시계와 난수를 바꿔 끼운다

4장 실습 4-7에서 `retry()`와 `make_summarizer()`가 **기다리는 함수를 매개변수로 받게** 만들었다. 실제로 쓸 때는 기본값 `time.sleep`으로 정말 기다리고, `main()`에서는 기다린 시간을 기록만 하는 `fake_sleep()`을 넘겼다. 그리고 "함수가 쓰는 것을 바깥에서 넣어 주는 이 방법을 **의존성 주입**이라고 한다. 6장에서 테스트할 때 정식으로 다룬다"고 했다. 그 `retry()`에 5장의 타입 힌트(5.3.5)를 붙이고, 지터와 지터에 쓸 **난수 함수**도 주입받게 한다.

`ch06/retry.py`

```python
"""다시 시도할 실패만 다시 시도하는 데코레이터 — 4장 실습 4-7에 타입과 지터를 더했다."""

import functools
import random
import time
from collections.abc import Callable


class APIError(Exception):
    """가짜 LLM API의 오류. status에 HTTP 상태 코드를 담는다."""

    def __init__(self, message: str, status: int | None = None) -> None:
        super().__init__(message)
        self.status = status


class APITimeoutError(APIError):
    """응답이 제한 시간 안에 오지 않았다."""


class RateLimitError(APIError):
    """요청 한도 초과(429). retry_after초 뒤에 다시 보내라는 뜻이다."""

    def __init__(self, message: str, retry_after: float | None = None) -> None:
        super().__init__(message, status=429)
        self.retry_after = retry_after


class ServerError(APIError):
    """서버 쪽 문제(500, 503, 529 등). 잠시 뒤에는 될 수 있다."""


class BadRequestError(APIError):
    """요청이 잘못되었다(400). 다시 보내도 같은 결과다."""


RETRYABLE: tuple[type[Exception], ...] = (APITimeoutError, RateLimitError, ServerError)


def retry[**P, R](
    times: int = 3,
    delay: float = 1.0,
    backoff: float = 2.0,
    jitter: float = 0.0,
    exceptions: tuple[type[Exception], ...] = RETRYABLE,
    sleep: Callable[[float], None] = time.sleep,
    rand: Callable[[], float] = random.random,
) -> Callable[[Callable[P, R]], Callable[P, R]]:
    """exceptions의 예외가 나면 times번까지 시도하는 데코레이터를 만든다.

    n번째 실패 뒤에는 delay * backoff ** (n - 1)초에 0~jitter초를 더해 기다린다.
    예외에 retry_after 속성이 있고 None이 아니면 그 시간을 대신 기다린다.
    times가 1보다 작으면 ValueError를 일으킨다.
    """
    if times < 1:
        raise ValueError(f"times는 1 이상이어야 한다: {times}")

    def decorator(func: Callable[P, R]) -> Callable[P, R]:
        @functools.wraps(func)
        def wrapper(*args: P.args, **kwargs: P.kwargs) -> R:
            for attempt in range(1, times + 1):
                try:
                    return func(*args, **kwargs)
                except exceptions as e:
                    if attempt == times:
                        raise
                    retry_after = getattr(e, "retry_after", None)
                    if retry_after is not None:
                        wait = retry_after
                    else:
                        wait = delay * backoff ** (attempt - 1) + jitter * rand()
                    print(
                        f"  [재시도] {attempt}번째 실패({type(e).__name__}: {e}), {wait:.1f}초 뒤 다시"
                    )
                    sleep(wait)
            raise AssertionError("여기에 오지 않는다")

        return wrapper

    return decorator
```

- 예외 클래스는 실습 4-7과 같다. 매개변수에 타입 힌트만 붙였다.
- `sleep: Callable[[float], None] = time.sleep` — "초(실수)를 받아 아무것도 돌려주지 않는 함수"다. 기본값은 진짜 `time.sleep`이다.
- `rand: Callable[[], float] = random.random` — "인자 없이 불러서 실수를 돌려주는 함수"다. 기본값 `random.random`은 `0.0` 이상 `1.0` 미만의 난수를 돌려준다. 지터는 `0`~`jitter`초다.
- `if times < 1:` — 5.3.5에서 mypy가 찾아 준 숨은 경우다. `times`가 0 이하이면 `range(1, times + 1)`이 비어서 반복문을 한 번도 돌지 않고 맨 아래 줄에 닿는다. 그대로 두면 `retry(times=0)`으로 감싼 함수는 원래 함수를 한 번도 부르지 않고 `AssertionError("여기에 오지 않는다")`를 일으킨다. 데코레이터를 **만들 때** 바로 거절하면, 반복문은 언제나 한 번 이상 돌고 마지막 시도에서 반드시 `return`하거나 `raise`한다. 이제 맨 아래 줄은 정말로 닿을 수 없는 줄이 되고, mypy를 위해서만 남는다.
- 기본값이 진짜이므로 **쓰는 쪽은 아무것도 바꾸지 않는다.** `@retry()`로 쓰면 지금까지와 똑같이 정말 기다린다. 테스트만 가짜를 넘긴다.

테스트에는 "정해 둔 예외를 차례로 일으키다가 성공하는 함수"가 필요하다. 실습 4-7의 `FakeLLM`이 하던 일을 작은 클래스로 만든다.

`ch06/test_retry.py`

```python
"""retry의 테스트 — 기다리는 함수와 난수 함수를 주입한다."""

import pytest
from retry import APITimeoutError, BadRequestError, RateLimitError, ServerError, retry


class Flaky:
    """정해 둔 예외를 차례로 일으킨 뒤에 "성공"을 돌려주는 함수 객체."""

    def __init__(self, *errors: Exception) -> None:
        self.errors = list(errors)
        self.calls = 0

    def __call__(self) -> str:
        self.calls += 1
        if self.errors:
            raise self.errors.pop(0)
        return "성공"


def test_retries_until_success() -> None:
    waits: list[float] = []
    flaky = Flaky(APITimeoutError("시간 초과"), ServerError("과부하", 529))
    call = retry(sleep=waits.append)(flaky)

    assert call() == "성공"
    assert flaky.calls == 3
    assert waits == [1.0, 2.0]


def test_uses_retry_after() -> None:
    waits: list[float] = []
    call = retry(sleep=waits.append)(
        Flaky(RateLimitError("한도 초과", retry_after=5.0))
    )
    call()
    assert waits == [5.0]


def test_does_not_retry_bad_request() -> None:
    waits: list[float] = []
    flaky = Flaky(BadRequestError("너무 길다", 400))
    call = retry(sleep=waits.append)(flaky)

    with pytest.raises(BadRequestError):
        call()
    assert flaky.calls == 1
    assert waits == []


def test_gives_up_after_times() -> None:
    waits: list[float] = []
    flaky = Flaky(*[ServerError("내부 오류", 500) for _ in range(3)])
    call = retry(times=3, sleep=waits.append)(flaky)

    with pytest.raises(ServerError):
        call()
    assert flaky.calls == 3
    assert waits == [1.0, 2.0]


@pytest.mark.parametrize("times", [0, -1])
def test_rejects_times_less_than_one(times: int) -> None:
    with pytest.raises(ValueError, match="1 이상"):
        retry(times=times)
```

- `Flaky` — `__call__` 메서드가 있어서 객체를 함수처럼 부를 수 있다(1.3.4). `flaky()`를 부를 때마다 `calls`가 늘고, 정해 둔 예외가 남아 있으면 하나씩 꺼내 일으킨다. "flaky"는 "될 때도 있고 안 될 때도 있는"이라는 뜻이다.
- `retry(sleep=waits.append)(flaky)` — 4.2.2의 "`@deco`는 `f = deco(f)`의 줄임"을 거꾸로 쓴 것이다. 테스트마다 다른 가짜를 넘기려고 `@`를 쓰지 않고 직접 감쌌다.
- `sleep=waits.append` — 이 줄이 주입의 핵심이다. 리스트의 `append` 메서드는 "값 하나를 받아 리스트에 더하고 `None`을 돌려주는" 함수다. `Callable[[float], None]`의 모양과 맞으므로 mypy도 통과한다. 기다리는 대신 **기다리려던 시간을 기록**한다.
- `assert waits == [1.0, 2.0]` — 기다리지 않고도 "첫 실패 뒤 1초, 두 번째 실패 뒤 2초를 기다리려 했다"를 확인한다. 세 번째(마지막) 실패 뒤에는 기다리지 않는다는 것도 `test_gives_up_after_times`가 확인한다.
- `test_rejects_times_less_than_one` — `times`의 경계(6.3.2)다. `1`은 정상, `0`과 음수는 실패 경우다. 감싸기 전, `retry(times=0)`을 부르는 순간 예외가 나야 한다.
- `assert flaky.calls == 1` — `BadRequestError`는 다시 시도하지 않았다. 4.3.4의 표("400은 다시 보내도 같은 결과다")가 테스트로 적혔다.

"3초를 기다리는" 재시도가 0.01초 만에 끝났다. `retry()` 안의 `print()` 출력은 pytest가 붙잡아 두었으므로 보이지 않는다.

**매번 달라지는 결과 테스트하기 — 4장의 질문에 답하기**

실습 4-7에서 "지터를 넣으면 실행 예와 출력이 달라진다. 출력이 매번 달라지는 코드는 어떻게 확인할 수 있을까?"라고 물었다. 두 가지 방법이 있다.

첫째, **달라지는 원인을 주입받아 고정한다.** 난수 함수를 바꿔 끼우면 결과가 정해진다.

```python
def test_jitter_with_fixed_random() -> None:
    waits: list[float] = []
    flaky = Flaky(ServerError("과부하"), ServerError("과부하"))
    call = retry(jitter=1.0, sleep=waits.append, rand=lambda: 0.5)(flaky)
    call()
    assert waits == [1.5, 2.5]
```

`rand=lambda: 0.5`는 "언제나 0.5를 돌려주는 난수 함수"다. 지터는 언제나 `1.0 * 0.5 = 0.5`초이므로 기다리는 시간이 `1.0 + 0.5`, `2.0 + 0.5`로 정해진다.

둘째, **값 대신 언제나 성립하는 성질을 확인한다.** 지터가 얼마든 첫 대기는 `1.0` 이상 `2.0` 미만, 둘째 대기는 `2.0` 이상 `3.0` 미만이어야 한다. 여러 난수로 이 성질을 확인한다.

```python
@pytest.mark.parametrize("seed", range(20))
def test_jitter_stays_in_range(seed: int) -> None:
    waits: list[float] = []
    flaky = Flaky(ServerError("과부하"), ServerError("과부하"))
    call = retry(jitter=1.0, sleep=waits.append, rand=random.Random(seed).random)(flaky)
    call()
    assert 1.0 <= waits[0] < 2.0
    assert 2.0 <= waits[1] < 3.0
```

`random.Random(seed)`는 씨앗(seed)을 고정한 난수 생성기다. 3장에서 실습용 로그 파일을 만들 때 "씨앗이 같으면 언제 실행해도 같은 순서의 난수가 나온다. 6장의 테스트에서도 이 방법을 쓴다"고 했다(3.4.1). 씨앗 스무 개로 스무 번 실행하므로 서로 다른 난수 스무 쌍을 확인하면서도, 실패했을 때 **같은 씨앗으로 다시 실행해 재현할 수 있다.** 그냥 `random.random`을 넘기면 실패한 경우를 다시 만들 수 없다.

두 테스트를 `test_retry.py`에 더하고, 파일 맨 위의 `import pytest` 위에 `import random`과 빈 줄을 더한다. 실행하면 27개가 통과한다(`parametrize`로 20개가 늘었다).

이 두 방법, **원인을 고정하기**와 **성질을 확인하기**는 LLM의 답처럼 매번 달라지는 결과를 다룰 때도 그대로 쓰인다(6.6.6).

### 6.5.3 `Protocol`로 만든 가짜 객체

5.5.4에서 `LLMClient`를 `Protocol`로 정의하고 "개발과 테스트에서는 `FakeLLM`을 넘기고, 실제 서비스에서는 `RealLLM`을 넘긴다. `FakeLLM`은 받은 프롬프트를 기록하므로, 요약 함수가 프롬프트를 제대로 만들었는가를 API를 부르지 않고 확인할 수 있다. 6장에서 바로 이것으로 테스트를 쓴다"고 했다. 이번에는 시계 대신 **LLM 클라이언트 객체**를 주입한다.

`ch06/summarizer.py`

```python
"""LLM으로 글을 요약한다 — 외부 의존을 떼어 내고 테스트하는 대상."""

from typing import Protocol


class LLMClient(Protocol):
    def complete(self, prompt: str, *, max_tokens: int = 1024) -> str: ...


def build_prompt(text: str, max_sentences: int) -> str:
    return f"다음 글을 {max_sentences}문장 이내로 요약하라.\n\n<글>\n{text}\n</글>"


def summarize(client: LLMClient, text: str, *, max_sentences: int = 3) -> str:
    """client로 text를 요약한다. 빈 글이면 API를 부르지 않고 ValueError를 일으킨다."""
    if not text.strip():
        raise ValueError("빈 글은 요약할 수 없다")
    prompt = build_prompt(text, max_sentences)
    answer = client.complete(prompt, max_tokens=100 * max_sentences)
    return answer.strip()
```

`summarize()`가 하는 일은 네 가지다. 빈 글을 거른다, 프롬프트를 만든다, 문장 수에 맞춰 `max_tokens`를 정한다, 답의 앞뒤 공백을 떼어 낸다. 모두 **우리 코드의 일**이고, LLM이 무엇을 답하든 맞아야 한다. 이것들을 가짜 클라이언트로 확인한다.

가짜 클라이언트는 테스트 파일이 아니라 별도의 모듈에 둔다. 여러 테스트 파일과 `conftest.py`에서 함께 쓰기 때문이다.

`ch06/fakes.py`

```python
"""테스트에서 쓰는 가짜 객체들."""


class FakeLLM:
    """정해 둔 답을 돌려주고, 받은 요청을 기록하는 가짜 LLM 클라이언트."""

    def __init__(self, answer: str = "가짜 요약") -> None:
        self.answer = answer
        self.requests: list[tuple[str, int]] = []

    def complete(self, prompt: str, *, max_tokens: int = 1024) -> str:
        self.requests.append((prompt, max_tokens))
        return self.answer
```

5.5.4의 `FakeLLM`은 프롬프트만 `prompts`에 기록했다. 이번에는 `max_tokens`도 확인하려고 `(프롬프트, max_tokens)` 튜플을 `requests`에 기록한다. 가짜는 **확인하고 싶은 것을 기록하도록** 만든다.

`conftest.py`에 픽스처를 더한다. 앞뒤에 공백이 붙은 답을 돌려주게 해서 `strip()`도 확인되게 한다.

`ch06/conftest.py`

```python
"""ch06의 테스트가 함께 쓰는 픽스처와 설정."""

import sqlite3
from collections.abc import Iterator

import pytest
from fakes import FakeLLM


@pytest.fixture
def conn() -> Iterator[sqlite3.Connection]:
    """메모리 안의 SQLite 데이터베이스. 테스트가 끝나면 닫는다."""
    connection = sqlite3.connect(":memory:")
    yield connection
    connection.close()


@pytest.fixture
def fake_llm() -> FakeLLM:
    return FakeLLM(answer="  테스트는 회귀를 막는다.  ")
```

`ch06/test_summarizer.py`

```python
"""summarizer의 테스트 — 가짜 클라이언트로 네트워크 없이."""

import pytest
from fakes import FakeLLM
from summarizer import summarize


def test_returns_stripped_answer(fake_llm: FakeLLM) -> None:
    assert summarize(fake_llm, "긴 글") == "테스트는 회귀를 막는다."


def test_sends_text_in_prompt(fake_llm: FakeLLM) -> None:
    summarize(fake_llm, "자동 테스트는 코드를 고칠 용기를 준다.")
    prompt, _ = fake_llm.requests[0]
    assert "<글>\n자동 테스트는 코드를 고칠 용기를 준다.\n</글>" in prompt


def test_max_sentences_controls_prompt_and_tokens(fake_llm: FakeLLM) -> None:
    summarize(fake_llm, "긴 글", max_sentences=1)
    prompt, max_tokens = fake_llm.requests[0]
    assert "1문장 이내" in prompt
    assert max_tokens == 100


def test_empty_text_does_not_call_api(fake_llm: FakeLLM) -> None:
    with pytest.raises(ValueError):
        summarize(fake_llm, "   \n")
    assert fake_llm.requests == []
```

- **결과 확인** — `test_returns_stripped_answer`는 `summarize()`가 돌려준 값을 확인한다. 가짜가 무엇을 답할지 우리가 정했으므로 기대값을 정확히 쓸 수 있다.
- **요청 확인** — 나머지 테스트는 가짜가 **받은 것**을 확인한다. 프롬프트에 글이 들어갔는가, `max_tokens`가 문장 수에 맞는가, 빈 글이면 **아예 부르지 않았는가**. 실제 API로는 확인하기 어려운 것들이다. 실제 API는 받은 프롬프트를 되돌려 주지 않는다.
- `test_empty_text_does_not_call_api`의 마지막 줄 — "API를 부르지 않는다"는 독스트링의 약속을 확인한다. 돈이 드는 호출을 헛되이 하지 않는다는 것도 중요한 동작이다.

`FakeLLM`은 `LLMClient`를 물려받지 않았지만 `complete()`의 모양이 같으므로 `summarize()`에 넘길 수 있다(5.5.4). 그리고 그 사실을 **mypy가 확인한다.** `FakeLLM.complete()`에서 `max_tokens`를 빠뜨리면, 테스트 파일을 mypy로 검사할 때 `summarize(fake_llm, ...)` 줄에서 오류가 난다. 가짜가 진짜와 모양이 어긋나면 테스트는 통과해도 실제로는 동작하지 않는 코드가 된다. `Protocol`과 mypy가 그 어긋남을 막아 준다.

> **가짜를 위해 코드를 바꾸는 것은 나쁜 일인가**
> `retry()`에 `sleep`과 `rand` 매개변수를 더하고, `summarize()`가 클라이언트를 직접 만들지 않고 받게 한 것은 테스트 때문이다. "테스트를 위해 코드를 바꾸는 것"이 꺼림칙할 수 있다. 그런데 이렇게 바꾼 코드는 테스트 말고도 쓸모가 있다. 클라이언트를 받으니 다른 회사의 LLM으로 바꾸기 쉽고(9장 종합 실습), 기다리는 함수를 받으니 7장에서 `asyncio.sleep`으로 바꾸기 쉽다. **테스트하기 쉬운 코드는 대개 바꾸기 쉬운 코드다.** 테스트를 쓰기 어렵다면 코드의 설계를 다시 볼 신호다.

### 6.5.4 주입할 수 없을 때 — `monkeypatch.setattr()`

남이 쓴 코드나 오래된 코드는 기다리는 함수를 매개변수로 받지 않는다.

`ch06/polling.py`

```python
"""작업이 끝날 때까지 기다린다 — 기다리는 함수를 주입받지 않는 코드."""

from collections.abc import Callable
from time import sleep


def wait_until_done(
    is_done: Callable[[], bool], *, interval: float = 2.0, limit: int = 5
) -> bool:
    """is_done()이 True가 될 때까지 interval초 간격으로 limit번까지 확인한다."""
    for _ in range(limit):
        if is_done():
            return True
        sleep(interval)
    return False
```

LLM API에는 요청을 맡겨 두고 나중에 결과를 가져가는 방식(일괄 처리, batch)이 있다. 이럴 때 "끝났는지" 몇 초 간격으로 물어보는 코드가 이런 모양이다. 이 함수를 그대로 테스트하면 정말 2초씩 기다린다. 6.4.5의 `monkeypatch`는 환경 변수뿐 아니라 **모듈의 이름**도 잠시 바꿔 끼울 수 있다. 먼저 틀리기 쉬운 방법부터 해 본다.

```python
import time


def test_wrong_target(monkeypatch: pytest.MonkeyPatch) -> None:
    waits: list[float] = []
    monkeypatch.setattr(time, "sleep", waits.append)
    answers = iter([False, False, True])

    assert wait_until_done(lambda: next(answers), interval=0.01)
    assert waits == [0.01, 0.01]
```

```
>       assert waits == [0.01, 0.01]
E       assert [] == [0.01, 0.01]
E         
E         Right contains 2 more items, first extra item: 0.01
```

`time` 모듈의 `sleep`을 바꿔 끼웠는데 `waits`가 비어 있다. 실제로 0.01초씩 기다렸다(그래서 `interval`을 작게 주었다). 이유는 `polling.py`의 `from time import sleep`에 있다. 이 줄은 `polling` 모듈 안에 `sleep`이라는 **이름을 새로 만들어** `time.sleep` 함수를 가리키게 한다(1.3.1의 "변수는 객체를 가리키는 이름"). 테스트가 `time` 모듈의 이름 `sleep`을 가짜로 바꿔도, `polling` 모듈의 이름 `sleep`은 여전히 진짜 함수를 가리킨다.

그래서 바꿔 끼울 곳은 **쓰는 곳**이다. `wait_until_done()`이 찾는 이름은 `polling` 모듈의 `sleep`이다.

`ch06/test_polling.py`

```python
"""polling의 테스트 — 주입할 수 없을 때 monkeypatch로 바꿔 끼우기."""

import polling
import pytest
from polling import wait_until_done


def test_done_on_third_check(monkeypatch: pytest.MonkeyPatch) -> None:
    waits: list[float] = []
    monkeypatch.setattr(polling, "sleep", waits.append)
    answers = iter([False, False, True])

    assert wait_until_done(lambda: next(answers))
    assert waits == [2.0, 2.0]


def test_gives_up(monkeypatch: pytest.MonkeyPatch) -> None:
    waits: list[float] = []
    monkeypatch.setattr(polling, "sleep", waits.append)

    assert not wait_until_done(lambda: False, limit=3)
    assert waits == [2.0, 2.0, 2.0]
```

- `monkeypatch.setattr(polling, "sleep", waits.append)` — `polling` 모듈의 이름 `sleep`이 테스트 동안 `waits.append`를 가리키게 한다. 테스트가 끝나면 되돌린다.
- `iter([False, False, True])` — 부를 때마다 다음 값을 내놓는 이터레이터다(3.1). `lambda: next(answers)`는 세 번째에 처음으로 `True`를 돌려주는 가짜 "끝났는가" 함수다.

`polling.py`가 `import time`으로 가져와서 `time.sleep(interval)`로 썼다면 `monkeypatch.setattr(time, "sleep", ...)`이 맞다. 이때는 `polling`이 부를 때마다 `time` 모듈에서 `sleep`을 찾기 때문이다. 어느 쪽이든 원칙은 같다. **코드가 이름을 찾는 곳을 바꾼다.**

`monkeypatch.setattr()`은 편리하지만, 모듈 안의 이름에 기대므로 깨지기 쉽다. 누군가 `polling.py`의 `from time import sleep`을 `import time`으로 바꾸면 테스트가 (느려지면서) 실패한다. 동작은 그대로인데 테스트가 깨지는 것이다. 고칠 수 있는 코드라면 6.5.2처럼 **매개변수로 주입받게 고치는 것이 낫다.** `monkeypatch.setattr()`은 고칠 수 없는 코드에 쓴다.

### 6.5.5 `unittest.mock` 기초

지금까지는 가짜를 직접 만들었다. 표준 라이브러리 `unittest.mock`에는 **무엇이든 흉내 내는 객체** `Mock`이 있다. 라이브러리와 남의 테스트 코드에서 자주 보게 되므로 읽을 수 있을 만큼 익혀 둔다. 대화형 셸에서 해 본다. `ch06` 폴더의 모듈을 가져와야 하므로 `ch06` 폴더에서 `python`을 실행한다.

```python
>>> from unittest.mock import Mock
>>> m = Mock()
>>> m.complete("안녕")
<Mock name='mock.complete()' id='4441459072'>
>>> m.anything.goes(1, 2)
<Mock name='mock.anything.goes()' id='4441460080'>
```

`Mock` 객체는 **어떤 속성이든 있고, 어떻게 불러도 된다.** 부르면 또 다른 `Mock`을 돌려준다. 이것만으로는 쓸모가 없으니 돌려줄 값을 정한다.

```python
>>> from summarizer import summarize
>>> client = Mock()
>>> client.complete.return_value = "  요약  "
>>> summarize(client, "긴 글")
'요약'
>>> client.complete.call_count
1
>>> client.complete.call_args
call('다음 글을 3문장 이내로 요약하라.\n\n<글>\n긴 글\n</글>', max_tokens=300)
>>> client.complete.assert_called_once_with("다른 프롬프트", max_tokens=300)
Traceback (most recent call last):
  ...
AssertionError: expected call not found.
Expected: complete('다른 프롬프트', max_tokens=300)
  Actual: complete('다음 글을 3문장 이내로 요약하라.\n\n<글>\n긴 글\n</글>', max_tokens=300)
```

- `return_value` — 불렀을 때 돌려줄 값이다.
- `call_count`, `call_args` — 몇 번 불렸고 마지막에 무엇을 받았는지 기록한다. `FakeLLM.requests`가 하던 일이다.
- `assert_called_once_with(...)` — "정확히 한 번, 이 인자로 불렸다"를 확인한다. 아니면 `AssertionError`다. `assert_called_once()`, `assert_not_called()`도 있다.

`side_effect`로 부를 때마다 다른 일을 하게 할 수 있다. 리스트를 주면 차례로 돌려주고, 그 안의 **예외는 일으킨다.** 6.5.2의 `Flaky`가 한 줄로 된다.

```python
>>> client = Mock()
>>> client.complete.side_effect = [TimeoutError("시간 초과"), "두 번째 답"]
>>> client.complete("질문")
Traceback (most recent call last):
  ...
TimeoutError: 시간 초과
>>> client.complete("질문")
'두 번째 답'
```

`unittest.mock.patch()`는 6.5.4의 `monkeypatch.setattr()`과 같은 일을 하면서, 바꿔 끼운 자리에 `Mock`을 넣는다. 바꿀 곳을 문자열로 적는데, 이때도 원칙은 **쓰는 곳**이다. `test_polling.py`에 더해 본다.

```python
from unittest.mock import patch

...


def test_with_mock_patch() -> None:
    answers = iter([False, True])
    with patch("polling.sleep") as fake_sleep:
        assert wait_until_done(lambda: next(answers))
    fake_sleep.assert_called_once_with(2.0)
```

`from unittest.mock import patch`는 파일 맨 위의 `import` 자리에 둔다. 표준 라이브러리이므로 `import polling` 위에 빈 줄로 나눠 적는다.

**`Mock`의 위험 — 무엇이든 받아 준다**

`Mock`이 "어떤 속성이든 있고, 어떻게 불러도 된다"는 것은 장점이자 위험이다. `summarize()`에 오타가 있다고 하자.

```python
    answer = client.complete(prompt, max_token=100 * max_sentences)   # max_tokens의 오타
```

실제 클라이언트라면 `TypeError: ... got an unexpected keyword argument 'max_token'`이 난다. 하지만 `Mock`은 받아 준다.

```python
>>> client = Mock()
>>> client.complete.return_value = "답"
>>> client.complete("프롬프트", max_token=300)
'답'
```

`Mock`으로 쓴 테스트는 통과하고, 실제 서비스에서 처음 실패한다. 테스트가 **거짓말을 한** 것이다. 이를 막으려면 흉내 낼 진짜 클래스를 알려 준다.

```python
>>> from unittest.mock import create_autospec
>>> from fakes import FakeLLM
>>> client = create_autospec(FakeLLM, instance=True)
>>> client.complete.return_value = "답"
>>> client.complete("프롬프트", max_token=300)
Traceback (most recent call last):
  ...
TypeError: got an unexpected keyword argument 'max_token'
```

`create_autospec(클래스, instance=True)`는 그 클래스의 객체와 **같은 속성, 같은 매개변수**만 받는 `Mock`을 만든다(실제로는 `FakeLLM`이 아니라 SDK의 클라이언트 클래스를 넘긴다). `Mock(spec=클래스)`는 속성 이름만 확인하고 매개변수는 확인하지 않는다.

이 과정에서는 **직접 만든 가짜**(`FakeLLM`, `Flaky`)를 먼저 쓴다. 가짜가 `Protocol`의 모양을 따르는지 mypy가 확인해 주고, 무엇을 흉내 내는지 코드로 읽을 수 있기 때문이다. `Mock`은 흉내 낼 것이 작고 한 번만 쓸 때, 또는 `patch()`로 남의 코드 안을 바꿔 끼울 때 쓴다.

> **가짜를 너무 많이 쓰면**
> 테스트에서 모든 것을 가짜로 바꾸면, 테스트는 결국 "가짜끼리 정해 둔 대로 주고받는다"만 확인한다. `assert_called_once_with()`로 **어떻게** 불렀는지를 하나하나 확인하는 테스트는, 코드의 동작은 그대로인데 내부 구현만 바꿔도 깨진다. 가짜는 **바깥 세계와 닿는 경계**(네트워크, 시계, 난수, 파일 시스템의 일부)에만 쓰고, 우리 코드끼리는 진짜를 쓴다. 그리고 확인은 가능하면 **결과**(돌려준 값, 저장된 파일)로 한다.

### 6.5.6 실제 API를 부르는 테스트는 마커로 따로

가짜로 우리 코드를 확인하더라도, 실제 API와 **정말로 맞물리는지**는 언젠가 확인해야 한다. SDK가 바뀌었거나, 우리가 응답의 모양을 잘못 알고 있을 수 있다. 이런 테스트는 따로 표시해 두고, 평소에는 건너뛰다가 필요할 때만 실행한다. pytest의 **마커**(mark)가 그 표시다. `@pytest.mark.parametrize`도 마커의 하나였다.

`ch06/test_live.py`

```python
"""실제 LLM API를 부르는 테스트. 평소에는 건너뛴다."""

import os

import pytest
from summarizer import summarize

pytestmark = pytest.mark.live


class RealLLM:
    def complete(self, prompt: str, *, max_tokens: int = 1024) -> str:
        raise NotImplementedError("LLM API 활용에서 채운다")


@pytest.mark.skipif("ANTHROPIC_API_KEY" not in os.environ, reason="API 키가 없다")
def test_real_summary_is_short() -> None:
    answer = summarize(
        RealLLM(),
        "파이썬은 1991년에 처음 공개된 프로그래밍 언어다. " * 20,
        max_sentences=1,
    )
    assert 0 < len(answer) < 300
```

- `pytestmark = pytest.mark.live` — 파일 맨 위에 이 이름의 변수를 두면 파일 안의 **모든 테스트**에 `live`라는 마커가 붙는다. 테스트 하나에만 붙이려면 함수 위에 `@pytest.mark.live`를 쓴다. `live`는 우리가 지은 이름이다.
- `@pytest.mark.skipif(조건, reason=...)` — 조건이 참이면 이 테스트를 **건너뛴다.** API 키가 환경 변수에 없으면 실행하지 않는다.
- `RealLLM`은 5.5.4처럼 아직 비어 있다. "LLM API 활용"에서 SDK 호출로 채운다.
- 확인하는 것은 "요약이 비어 있지 않고 300자보다 짧다"는 **성질**이다. 실제 LLM의 답은 매번 다르므로 내용을 `==`로 비교하지 않는다(6.6.6).

`pytest_configure`는 pytest가 시작할 때 부르는 **약속된 이름의 함수**(hook)다. 4장의 등록 데코레이터처럼 이름으로 찾아서 부른다. 여기서는 `"이름: 설명"` 모양으로 마커를 등록한다. 다시 실행하면 경고가 사라진다. 건너뛴 이유를 보려면 `-rs`(report skipped)를 붙인다.


마커로 테스트를 고를 때는 `-m`을 쓴다.

| 명령 | 실행하는 것 |
|---|---|
| `pytest ch06` | 모두. `live` 테스트는 키가 없으면 건너뛴다 |
| `pytest -m "not live" ch06` | `live`가 아닌 것만. 평소에, 그리고 8장의 GitHub Actions에서 |
| `pytest -m live ch06` | `live`만. 실제 API와 맞물리는지 확인하고 싶을 때, 키를 설정하고 |

`-k`가 **이름**으로 고른다면 `-m`은 **마커**로 고른다. 지금은 `RealLLM`이 비어 있으므로 API 키를 설정하고 `pytest -m live ch06`을 실행하면 `NotImplementedError`로 실패한다. "LLM API 활용"에서 `RealLLM`을 채우면 이 테스트가 살아난다.

> **`skip`과 `skipif`, `xfail`**
> `@pytest.mark.skip(reason="...")`은 조건 없이 건너뛴다. 고치는 중인 테스트를 잠시 꺼 둘 때 쓰는데, 그렇게 꺼 둔 테스트는 잊히기 쉽다. `@pytest.mark.xfail(reason="...")`은 "지금은 실패하는 것이 맞다"는 표시다. 알려진 버그를 테스트로 먼저 적어 둘 때 쓴다. 실행 결과에 `x`로 나오고, 버그가 고쳐져서 통과하면 `X`로 알려 준다. 6.1.4에서 본 것처럼 AI가 실패하는 테스트에 `skip`을 붙여 "통과"시키는 일이 있다. 테스트 파일의 `git diff`에 마커가 새로 생겼다면 이유를 확인한다.

### 6.6.1 커버리지 — 테스트가 실행한 줄

테스트는 **실행한 경로만** 확인한다(6.1.3). 그렇다면 테스트가 코드의 어디를 실행했고 어디를 실행하지 않았는지 알고 싶다. 이것을 재는 것이 **커버리지**(coverage)다. 실습 준비에서 설치한 pytest-cov가 이 일을 한다. `--cov=폴더`로 잴 곳을 정하고, `--cov-report=term-missing`으로 실행하지 않은 줄 번호까지 보여 달라고 한다.

- `retry.py`의 76번 줄은 `raise AssertionError("여기에 오지 않는다")`다. 6.5.2에서 `times`가 1 이상인지 먼저 검증했으므로 이 줄에는 닿을 수 없고, mypy를 위해서만 남아 있다. 실행되지 않는 것이 맞다. 이렇게 **닿을 수 없다는 것을 확인한** 줄은 끝에 `# pragma: no cover` 주석을 달아 커버리지 계산에서 뺄 수 있다. 검증을 넣기 전이었다면 이 줄은 `retry(times=0)`으로 닿을 수 있었다. 그런 줄에 `# pragma: no cover`를 달면 테스트하지 않은 경로를 숨기는 것이 된다. 실행되지 않은 줄을 보면 먼저 "정말 닿을 수 없는가?"를 따지고, 닿을 수 있다면 테스트를 쓰거나 코드를 고친다.
- `test_live.py`는 API 키가 없어서 테스트를 건너뛰었으므로 그 본문이 실행되지 않았다. 테스트 파일이 100%가 아니라면 테스트 파일 안에 **실행되지 않은 문장**이 있다는 뜻이다. 원인은 여러 가지다. 건너뛴 테스트, 이름 규칙(6.2.2)을 어겨 수집되지 않은 테스트, 어느 테스트도 부르지 않는 도우미 함수, 테스트가 모두 실행되었어도 한쪽 분기만 지나간 도우미 함수나 픽스처의 `if`. 목록의 줄 번호를 따라가서 어느 경우인지 확인한다.

pytest-cov는 저장소 폴더에 측정 결과를 담은 `.coverage` 파일을 만든다. `--cov-report=html`을 쓰면 `htmlcov` 폴더에 보고서 웹 페이지를 만든다. `htmlcov/index.html`을 브라우저로 열면 파일마다 실행된 줄은 초록, 실행되지 않은 줄은 빨강으로 칠해 보여 준다. 둘 다 커밋하지 않는다(실습 6-8).

### 6.6.2 커버리지 숫자의 함정

커버리지는 "실행했는가"를 잰다. "**확인했는가**"는 재지 않는다. 작은 함수로 확인한다.

`ch06/tokens.py`

```python
"""요청할 최대 토큰 수를 정한다."""


def max_tokens_for(model: str, requested: int | None = None) -> int:
    """모델의 한도(large 4096, 그 밖 1024)와 requested 중 작은 값. requested가 없으면 한도."""
    limit = 4096 if model == "large" else 1024
    if requested is not None:
        limit = min(limit, requested)
    return limit
```

`ch06/test_tokens.py`

```python
"""tokens의 테스트 — 커버리지의 함정."""

from tokens import max_tokens_for


def test_runs_without_error() -> None:
    max_tokens_for("large", 100)
```

```
pytest --cov=ch06 --cov-report=term-missing ch06/test_tokens.py
```

```

---------------------------------------------------------
...
ch06/tokens.py                  5      0   100%
```

(테스트 파일 하나만 실행해도 `--cov=ch06`이므로 `ch06`의 모든 파일이 목록에 나온다. 다른 파일들은 실행되지 않아 0%에 가깝다. 여기서는 `tokens.py`만 본다.)

`tokens.py`가 100%다. 그런데 이 테스트에는 `assert`가 **없다.** `return limit`을 `return limit + 1`로 바꿔도 통과한다. 줄은 모두 실행했지만 결과는 아무것도 확인하지 않았다.

하나 더 있다. `--cov-branch`를 붙여 **분기 커버리지**를 잰다.

```

```

```
Name                          Stmts   Miss Branch BrPart  Cover   Missing
-------------------------------------------------------------------------
...
ch06/tokens.py                    5      0      2      1    86%   7->9
```

- `Branch` — 갈림길의 수. `if requested is not None:`에서 "참이라서 8번 줄로" 가는 길과 "거짓이라서 9번 줄로 건너뛰는" 길, 두 개다.
- `BrPart` — 한쪽 길만 가 본 갈림길의 수.
- `7->9` — 7번 줄에서 9번 줄로 바로 가는 길(`requested`가 `None`일 때)을 한 번도 가지 않았다.

줄 커버리지는 100%인데 `requested`가 없는 경우는 한 번도 실행되지 않았다. `if`에 `else`가 없으면 "건너뛰는 길"은 줄로 보이지 않기 때문이다. 4096이 맞는지, `"small"`이면 1024인지도 확인하지 않았다(`4096 if model == "large" else 1024`처럼 한 줄 안의 조건 표현식은 분기로도 세지 않는다).

정리하면 이렇다.

- 커버리지가 **낮은** 곳은 확실히 테스트가 부족하다. 실행조차 하지 않은 코드는 확인했을 리 없다. 커버리지 보고서는 **어디에 테스트를 더 써야 하는지** 찾는 데 쓴다.
- 커버리지가 **높다고** 테스트가 충분한 것은 아니다. 숫자는 `assert`의 질을 모른다.
- 그래서 커버리지 숫자를 목표로 삼지 않는다. "90%를 넘겨라"라고 하면 `assert` 없는 테스트가 늘어난다. AI에게 "커버리지를 100%로 올려 달라"고 하면 특히 그렇다.
- 테스트가 정말 무엇을 확인하는지 보려면 6.3.6의 "실패하는 것을 한 번은 본다"를 한다. 코드를 일부러 틀리게 바꿨을 때 실패하는 테스트가 있으면 그 부분은 확인되고 있는 것이다. 이 생각을 자동으로 하는 도구(mutation testing)도 있다.

`test_tokens.py`를 제대로 고치는 것은 실습 6-6의 몫이다.

### 6.6.3 `ruff check` — 린트

1장부터 VS Code의 Ruff 확장이 물결 밑줄로 무언가를 알려 주곤 했다. 1장의 실습에서는 `box=[]`와 `1 / 0`에 밑줄이 생길 수 있다고 하면서 "Ruff의 규칙은 6장에서 다룬다"고 했다. 이렇게 **실행하지 않고 코드를 읽어서 실수나 나쁜 습관을 찾는 일**을 **린트**(lint)라고 한다. 옷에 붙은 보풀을 떼어 낸다는 뜻이다. mypy가 타입만 본다면, 린터는 타입과 상관없는 실수를 본다.

```python
def ask(prompt):
```

문제마다 규칙 코드, 설명, 위치, 해당 줄, 고치는 방법(`help`)을 보여 준다. 한 줄씩 짧게 보려면 `--output-format concise`를 쓴다.

모양은 mypy와 같다. `파일:줄:칸: 규칙 코드 설명`이다. 규칙 코드의 앞 글자는 그 규칙을 처음 만든 도구를 나타낸다. Ruff는 여러 린터의 규칙을 한 프로그램에 모아 다시 만든 도구다.

| 코드 | 뜻 | 왜 문제인가 |
|---|---|---|
| `F401` | 가져오고 쓰지 않는 `import` | 읽는 사람이 "어디서 쓰지?" 하고 찾는다. 프로그램이 시작할 때 쓸데없이 불러온다 |
| `B006` | 가변 객체(`[]`, `{}`)를 기본값으로 썼다 | 기본값은 함수를 정의할 때 **한 번** 만들어진다. `load_history()`를 부를 때마다 같은 리스트에 쌓인다(기초 과정 4.2.5, 1장 실습의 q1) |
| `F841` | 값을 넣고 쓰지 않는 변수 | 쓰려고 했다가 잊었거나, 이름을 잘못 썼다는 신호다 |
| `F541` | `{}`가 없는 f-문자열 | `f`가 필요 없다. 넣으려던 값을 빠뜨렸다는 신호일 수 있다 |
| `E722` | 예외 종류 없는 `except:` | `KeyboardInterrupt`(`Ctrl+C`)까지 삼킨다. 잡을 예외를 적는다(기초 과정 6.2.6) |

`F`는 Pyflakes, `E`는 pycodestyle, `B`는 flake8-bugbear라는 도구에서 온 규칙이다. 규칙의 자세한 설명은 `ruff rule B006`으로 볼 수 있다. 9번 줄의 `path == None`은 5.2에서 "`is None`으로 쓴다"고 한 것인데 지적하지 않았다. 이 규칙(`E711`)은 이 교재의 Ruff 버전에서 **기본으로 켜져 있지 않다.** 어떤 규칙을 켤지는 프로젝트마다 정하고, 8장에서 `pyproject.toml`에 적는다.

`[*]`가 붙은 것은 Ruff가 **안전하게 고칠 수 있는** 것이다.

```
ruff check --fix --output-format concise ch06/lint_demo.py
```

```
ch06/lint_demo.py:7:32: B006 Do not use mutable data structures for argument defaults
ch06/lint_demo.py:11:5: F841 Local variable `count` is assigned to but never used
ch06/lint_demo.py:21:5: E722 Do not use bare `except`
Found 5 errors (2 fixed, 3 remaining).
2 unsafe fixes available with `--fix --unsafe-fixes`.
```

`import os`를 지우고 `f`를 떼어 냈다. 남은 셋은 사람이 판단해야 한다. `B006`과 `F841`에는 "안전하지 않은 고침"(unsafe fix)이 있지만, 동작이 바뀔 수 있어서 저절로 하지 않는다. 예를 들어 `F841`을 고치면 `count = len(data)`가 `len(data)`로 바뀐다. 정말 필요 없는 줄이라면 줄째 지우는 것이 맞고, `count`를 출력하려다 잊은 것이라면 출력을 더하는 것이 맞다. 그 판단은 Ruff가 할 수 없다.

규칙이 틀렸거나 일부러 그렇게 쓴 줄은 끝에 `# noqa: 규칙 코드`를 단다. 4.5.5의 "등록을 위해 일부러 하는 `import`"가 그런 예다.

```python
import weather_tools  # noqa: F401 — @tool 등록을 위해 불러온다
```

5.1.6의 `# type: ignore[코드]`와 같이 **규칙 코드를 꼭 적는다.** AI가 경고를 "고쳤다"며 `# noqa`를 붙였다면, 고친 것인지 숨긴 것인지 확인한다.

Ruff도 실행 결과를 `.ruff_cache` 폴더에 저장해 다음 검사를 빠르게 한다. 6.2.6에서 `files.exclude`에 넣은 그 폴더다. 확인했으면 `lint_demo.py`를 지운다.

### 6.6.4 `ruff format` — 포맷

1장부터 저장할 때 코드의 모양이 저절로 바뀌었다. 따옴표가 `"`로 바뀌고, 쉼표 뒤에 빈칸이 생기고, 긴 줄이 나뉘었다. 이것이 Ruff의 **포매터**다. 터미널에서도 같은 일을 할 수 있다. VS Code의 자동 정리를 거치지 않도록 다른 편집기로(또는 `Save without Formatting`으로) 다음 파일을 만든다.

### 6.6.5 한 번에 돌리는 습관

이제 커밋하기 전에 돌릴 검사가 넷이다.

| 검사 | 명령 | 찾는 것 |
|---|---|---|
| 린트 | `ruff check ch06` | 쓰지 않는 이름, 가변 기본값 같은 실수 |
| 포맷 | `ruff format --check ch06` | 정리되지 않은 코드 모양 |
| 타입 | `mypy --strict ch06` | 타입이 맞지 않는 곳(5장) |
| 테스트 | `pytest -m "not live" ch06` | 값이 틀린 곳, 회귀. 실제 API를 부르는 테스트는 뺀다(6.5.6) |

넷을 매번 따로 입력하면 빼먹는다. 하나로 묶는다. macOS의 터미널이라면 `&&`로 이을 수 있지만, Windows PowerShell의 버전에 따라 `&&`가 동작하지 않는다. 어디서나 동작하도록 파이썬 스크립트로 만든다. 저장소 폴더 바로 아래에 만든다.

`check.py`

```python
"""커밋하기 전에 돌리는 검사 — ruff, mypy, pytest를 차례로 실행한다.

사용법: python check.py ch06
"""

import shlex
import subprocess
import sys

target = sys.argv[1] if len(sys.argv) > 1 else "."
commands = [
    ["ruff", "check", target],
    ["ruff", "format", "--check", target],
    ["mypy", "--strict", target],
    ["pytest", "-q", "-m", "not live", target],
]

for command in commands:
    print(f"$ {shlex.join(command)}", flush=True)
    result = subprocess.run([sys.executable, "-m", *command], check=False)
    if result.returncode != 0:
        sys.exit(f"실패: {shlex.join(command)}")
print("모든 검사를 통과했다")
```

- `subprocess.run([...])` — 다른 프로그램을 실행하고 끝날 때까지 기다린다. 결과의 `returncode`가 그 프로그램의 종료 코드다. 0이 아니면 실패다(6.2.1).
- `[sys.executable, "-m", *command]` — `ruff check ch06` 대신 `python -m ruff check ch06`을 실행한다. `sys.executable`은 지금 이 스크립트를 실행한 파이썬이다(기초 과정 8.2.2). 가상환경의 파이썬으로 실행했다면 가상환경에 설치한 ruff·mypy·pytest를 쓴다. `*command`는 리스트를 풀어서 넣는다(1.3.3).
- `check=False` — `subprocess.run()`에 `check=True`를 주면 실패할 때 예외를 일으킨다. 여기서는 종료 코드를 직접 보므로 `False`다. 이 인자를 빠뜨리면 `ruff check`가 `PLW1510`(`check` 인자를 분명히 적으라)으로 지적한다. 기본값에 기대지 말고 뜻을 적으라는 규칙이다.
- `["pytest", "-q", "-m", "not live", target]` — 실제 API를 부르는 `live` 테스트(6.5.6)를 뺀다. 커밋 전 검사는 빠르고, 공짜이고, 바깥 상태에 기대지 않아야 한다. 마커를 빼먹으면 `ANTHROPIC_API_KEY`가 설정된 컴퓨터에서는 `skipif`의 조건이 거짓이 되어, 아직 비어 있는 `RealLLM`을 부르다 `NotImplementedError`로 실패한다. 같은 검사가 컴퓨터에 따라 결과가 달라지는 것이다(6.4.5). `live` 테스트는 필요할 때 `pytest -m live ch06`으로 따로 고른다.
- `shlex.join(command)` — 명령을 화면에 보여 줄 때 빈칸이 든 인자 `not live`를 따옴표로 감싸서 터미널에 그대로 붙여 넣을 수 있는 모양으로 만든다. `subprocess.run()`에는 리스트를 그대로 넘기므로 따옴표가 필요 없다.
- `sys.exit("메시지")` — 메시지를 표준 오류에 출력하고 종료 코드 1로 끝낸다. 첫 실패에서 멈춘다.

```
python check.py ch06
```

```
$ ruff check ch06
All checks passed!
$ ruff format --check ch06
23 files already formatted
$ mypy --strict ch06
Success: no issues found in 23 source files
$ pytest -q -m 'not live' ch06
........................................................................ [ 90%]
........                                                                 [100%]
80 passed, 1 deselected in 0.04s
모든 검사를 통과했다
```

(파일 수와 테스트 수는 실습에 따라 다르다.) `1 deselected`가 `-m "not live"`로 뺀 `test_live.py`의 테스트다. 6.5.6의 `-k`처럼, 고르지 않은 테스트는 건너뛴(`s`) 것이 아니라 아예 실행 목록에서 빠진다.

`mypy --strict ch06`은 테스트 파일까지 검사한다. 테스트 함수에 `-> None`을, 픽스처를 받는 매개변수에 `tmp_path: Path`, `monkeypatch: pytest.MonkeyPatch`처럼 타입을 붙여 온 것이 이 때문이다. 테스트 코드도 코드다. 픽스처의 타입이 틀리면(예: `fake_llm: FakeLLM` 자리에 다른 것을 넘기면) mypy가 찾아 준다.

이 장에서 일부러 실패하게 쓴 파일(`test_failure_demo.py`, `lint_demo.py` 등)이 남아 있으면 검사가 실패한다. 본문의 지시대로 지웠는지 확인한다.

**언제 돌리는가.** 코드를 고치는 동안에는 `pytest --lf`나 테스트 탐색기로 관련된 테스트만 빠르게 돌리고, **커밋하기 전에** `python check.py ch06`으로 전체를 돌린다. 8장에서는 같은 검사를 GitHub Actions가 푸시할 때마다 대신 돌려준다. 사람은 잊지만 자동화는 잊지 않는다.

> **5장의 일부러 틀린 파일들**
> 5장 폴더에는 mypy 오류를 보려고 일부러 틀리게 쓴 파일이 많다. 그래서 `python check.py`처럼 저장소 전체(`.`)를 검사하면 `ch05`에서 실패한다. 이 과정에서는 장 폴더를 인자로 주어 그 장만 검사한다. 9장의 종합 실습은 처음부터 `check.py`를 통과하게 만든다.

### 6.6.6 매번 달라지는 결과 — 테스트와 평가

LLM을 쓰는 프로그램에는 두 종류의 "맞는가"가 있다.

- **우리 코드가 맞는가.** 프롬프트를 제대로 만드는가, 응답을 제대로 해석하는가, 형식이 틀린 응답을 거르는가, 실패하면 다시 시도하는가, 결과를 제대로 저장하는가.
- **LLM의 답이 좋은가.** 요약이 원문의 뜻을 지키는가, 빠뜨린 내용은 없는가, 어조가 알맞은가, 지어낸 말은 없는가.

첫째는 **테스트**의 일이다. 이 장에서 한 것처럼 LLM을 가짜로 바꾸고, 가짜가 정해 둔 답(정상 답, 형식이 틀린 답, 시간 초과)마다 우리 코드가 정해진 대로 동작하는지 **단정**(assert)한다. 결과가 매번 같으므로 `==`로 비교할 수 있고, 하나라도 틀리면 버그다.

둘째는 **평가**(evaluation, 줄여서 Evals)의 일이다. 같은 질문에도 답이 매번 다르고, "좋은 요약"에는 하나의 정답이 없다. 그래서 평가는 테스트와 모양이 다르다.

| | 테스트 | 평가(Evals) |
|---|---|---|
| 확인하는 것 | 우리 코드의 동작 | LLM이 만든 답의 품질 |
| LLM | 가짜. 결과가 정해져 있다 | 진짜. 결과가 매번 다르다 |
| 판정 | 통과/실패. 하나라도 실패하면 버그 | 점수. 여러 예제의 평균, 비율 |
| 기준 | `==`, `pytest.raises()` | 정답과 비교, 규칙 검사, 사람의 판단, 다른 LLM의 채점 |
| 언제 | 코드를 고칠 때마다. 빠르고 공짜 | 프롬프트나 모델을 바꿀 때. 느리고 돈이 든다 |
| 이 과정에서 | 이 장 | "LLM 평가(Evals) 심화" |

둘 사이에 걸친 것도 있다. 6.5.6의 `test_live.py`처럼 진짜 LLM을 부르면서 **언제나 성립해야 하는 성질**만 단정하는 테스트다. "JSON으로 파싱되고 스키마를 통과한다", "비어 있지 않고 300자보다 짧다", "금지어가 없다". 내용은 매번 달라도 이것들은 매번 지켜져야 한다. 6.5.2의 지터 테스트에서 값 대신 범위를 확인한 것과 같은 생각이다.

LLM의 답을 다루는 코드를 테스트할 때 다음을 기억한다.

- **진짜 답을 모아 가짜의 답으로 쓴다.** 실제 LLM이 돌려준 이상한 답(JSON 앞에 붙은 설명, 빠진 필드, 숫자 대신 글자)을 발견하면, 그 답을 그대로 가짜 클라이언트의 대본에 넣어 테스트를 하나 더한다. 5장 실습 5-7의 `ScriptedLLM`이 그렇게 만든 대본이었다. 한 번 겪은 문제가 다시 생기지 않게 막는 회귀 테스트가 된다.
- **형식은 테스트로, 내용은 평가로.** "답이 `Summary` 모델을 통과하는가"는 Pydantic 검증(5.6)과 테스트로 확인한다. "요약이 좋은가"는 단정하지 않는다. `assert "회귀" in summary`처럼 진짜 LLM의 답 내용을 `assert`하는 테스트는 매번 통과하지도, 매번 실패하지도 않는 **들쭉날쭉한 테스트**(flaky test)가 된다. 들쭉날쭉한 테스트는 실패해도 "또 그거겠지" 하고 무시하게 만들어서, 진짜 실패까지 가린다.
- **평가는 실패해도 막지 않는다.** 평가 점수가 조금 떨어졌다고 커밋을 막지는 않는다. 점수의 변화를 기록하고, 크게 떨어지면 원인을 찾는다. 테스트는 하나라도 실패하면 막는다.

## 실습 6-7. 종합 — 테스트로 버그 찾기: 문서 일괄 요약기

이 장의 내용을 모두 써서 **남이 쓴 코드를 테스트로 검토한다.** 대상은 "폴더의 글 파일을 조각으로 나눠 LLM에게 조각마다 요약을 요청하고, 결과를 JSONL로 저장하는" 모듈이다. 9장 종합 실습 "문서 일괄 요약기"의 동기(sync) 판이다. 이 모듈은 이미 다 만들어져 있고, 실행하면 그럴듯하게 동작한다. 그런데 **숨은 버그가 세 개** 있다.

3장·4장·5장의 종합 실습에서는 함수의 이름과 독스트링이 주어지고 본문을 채웠다. 이번에는 거꾸로다. **코드는 주어지고, 테스트 함수의 이름과 독스트링이 주어진다. 테스트의 본문을 채운다.** 독스트링이 곧 이 모듈의 약속이다. 약속대로 테스트를 쓰면 버그가 드러난다. 버그를 찾으면 모듈을 고친다.

`ch06/doc_summarizer.py`

```python
"""문서 일괄 요약기 — 6장 종합 실습. 이 파일에는 숨은 버그가 세 개 있다."""

import json
import time
from collections.abc import Callable, Iterator
from pathlib import Path
from typing import Any, Protocol

from pydantic import BaseModel, Field
from retry import APIError, retry


class LLMClient(Protocol):
    def complete(self, prompt: str, *, max_tokens: int = 1024) -> str: ...


class Summary(BaseModel):
    """LLM이 조각마다 돌려주어야 하는 요약."""

    summary: str = Field(min_length=1, max_length=200, description="200자 이내의 요약")
    keywords: list[str] = Field(
        default_factory=list, max_length=3, description="핵심어 3개 이하"
    )


def split_text(text: str, size: int) -> list[str]:
    """text를 size글자씩 나눈 조각의 리스트를 돌려준다. 빈 글이면 빈 리스트다."""
    if size < 1:
        raise ValueError(f"size는 1 이상이어야 한다: {size}")
    count = len(text) // size + 1
    return [text[i * size : (i + 1) * size] for i in range(count)]


def build_prompt(piece: str) -> str:
    """조각 하나를 요약해 Summary의 JSON 스키마에 맞는 JSON만 답하라는 프롬프트."""
    schema = json.dumps(Summary.model_json_schema(), ensure_ascii=False)
    return f"다음 글을 요약해 이 JSON 스키마에 맞는 JSON만 답하라.\n{schema}\n\n<글>\n{piece}\n</글>"


def parse_summary(answer: str) -> Summary:
    """응답에서 첫 '{'부터 마지막 '}'까지를 잘라 Summary로 검증한다.

    검증하지 못하면 ValidationError를 일으킨다.
    """
    start, end = answer.find("{"), answer.rfind("}")
    if start != -1 and end != -1:
        answer = answer[start : end + 1]
    return Summary.model_validate_json(answer)


def summarize_file(
    client: LLMClient,
    path: Path,
    *,
    size: int = 500,
    sleep: Callable[[float], None] = time.sleep,
) -> Iterator[dict[str, Any]]:
    """path의 글을 size글자씩 나눠 조각마다 요약을 요청하고, 결과를 하나씩 내놓는다.

    API 오류는 retry()의 규칙대로 다시 시도한다. 기다릴 때는 sleep을 쓴다.
    성공: {"file": 파일 이름, "chunk": 1부터 센 번호, "summary": ..., "keywords": [...]}
    실패: {"file": 파일 이름, "chunk": 번호, "error": "예외 이름: 메시지"}
    한 조각이 실패해도 다음 조각을 계속한다.
    """

    @retry()
    def ask(prompt: str) -> str:
        return client.complete(prompt, max_tokens=300)

    text = path.read_text(encoding="utf-8")
    for number, piece in enumerate(split_text(text, size), start=1):
        try:
            result = parse_summary(ask(build_prompt(piece)))
        except APIError as e:
            yield {
                "file": path.name,
                "chunk": number,
                "error": f"{type(e).__name__}: {e}",
            }
        else:
            yield {"file": path.name, "chunk": number, **result.model_dump()}


def summarize_folder(
    client: LLMClient,
    folder: Path,
    out_path: Path,
    *,
    size: int = 500,
    sleep: Callable[[float], None] = time.sleep,
) -> tuple[int, int]:
    """folder의 .txt 파일을 이름 순으로 요약해 out_path에 JSONL로 저장한다.

    (성공한 조각 수, 실패한 조각 수)를 돌려준다.
    """
    ok = failed = 0
    with open(out_path, "w", encoding="utf-8") as f:
        for path in sorted(folder.glob("*.txt")):
            for record in summarize_file(client, path, size=size, sleep=sleep):
                f.write(json.dumps(record, ensure_ascii=False) + "\n")
                if "error" in record:
                    failed += 1
                else:
                    ok += 1
    return ok, failed
```

- **`Summary`** — 5장 실습 5-7의 `Analysis`처럼, LLM이 지켜야 할 답의 모양이다. 프롬프트에 넣을 스키마를 만들고(`build_prompt()`), 답을 검증한다(`parse_summary()`).
- **`summarize_file()`** — 제너레이터다(3장). 조각마다 결과 레코드를 하나씩 내놓는다. 안쪽 함수 `ask()`에 `@retry()`를 붙여 API 오류를 다시 시도한다(4장, 6.5.2). `try`/`except`/`else`의 `else`는 예외가 나지 않았을 때 실행된다. "`try` 블록에는 예외가 날 것으로 예상하는 코드만 넣는다"(기초 과정 6장)를 지킨 모양이다. `**result.model_dump()`는 모델을 딕셔너리로 바꿔 풀어 넣는다(2.4.3).
- **`summarize_folder()`** — 파일마다 `summarize_file()`을 불러 레코드를 JSONL로 저장하고 성공과 실패를 센다. `sleep`을 `summarize_file()`에 그대로 넘긴다.
- `retry`는 6.5.2의 `ch06/retry.py`를 가져다 쓴다. 그 파일은 이미 테스트로 확인했으므로 **버그가 없다고 믿어도 된다.** 버그는 모두 `doc_summarizer.py` 안에 있다.

이 모듈은 `ruff check`, `ruff format --check`, `mypy --strict`를 모두 통과한다. 타입이 맞고 모양이 깔끔해도 동작은 틀릴 수 있다. 그것을 찾는 것이 테스트의 일이다.

`doc_summarizer`, `retry`, `pydantic`, `json`에서 필요한 이름은 테스트를 쓰면서 파일 맨 위에 더한다. 미리 적어 두면 저장할 때 Ruff가 "쓰지 않는 `import`"로 지운다(6.6.3의 `F401`).

**진행 순서**

1. 테스트 함수를 하나씩 채우고 그때마다 실행한다. `-x`나 `-k`로 지금 쓰는 테스트만 실행하면 편하다.
2. 테스트가 실패하면 **테스트가 틀렸는지, 코드가 틀렸는지** 먼저 따진다. 독스트링(약속)과 비교해서 테스트가 약속대로 썼다면 코드가 틀린 것이다. 실패한 테스트를 디버거로 실행해 본다(6.2.6).
3. 버그를 찾으면 `notes.md`에 "어느 테스트가, 어떤 입력에서, 무엇이 달라서 실패했는가"를 적는다. **아직 고치지 않는다.**
4. 테스트를 모두 채운 뒤 버그 세 개를 고치고, 모든 테스트가 통과하는지 확인한다.

**힌트**

- `ScriptedLLM`의 표시 글자는 **조각의 내용**으로 정한다. 예를 들어 `"가나다라마"`를 `size=3`으로 나누면 `"가나다"`와 `"라마"` 두 조각이므로, `ScriptedLLM({"가나다": [APITimeoutError("시간 초과")]})`는 첫 조각에서만 시간 초과를 낸다. 단, 프롬프트에는 스키마가 들어 있어서 `"요약"`, `"핵심어"` 같은 낱말은 **모든** 프롬프트에 들어 있다. 이런 낱말을 표시 글자로 쓰면 모든 조각에 걸린다.
- `summarize_file()`을 테스트할 때는 글의 길이가 `size`의 배수가 **아니게** 고른다. 그래야 한 테스트에서 두 버그가 섞여 나오지 않는다. 버그 하나를 찾는 테스트는 그 버그에만 실패하는 것이 좋다.
- `summarize_file()`은 제너레이터다. `list()`로 꺼내야 요청이 일어난다. 꺼낸 뒤에 `client.prompts`의 길이로 API를 몇 번 불렀는지 센다.
- 오류 레코드의 `"error"` 값은 `"BadRequestError: 너무 길다"`처럼 예외 이름과 메시지를 이은 것이다. 검증 오류의 메시지는 길고 Pydantic 버전에 따라 다르므로 `startswith("ValidationError")`처럼 앞부분만 확인한다.
- `summarize_folder()`의 결과 파일은 `tmp_path / "out.jsonl"`처럼 `docs` 폴더 **밖에** 둔다. `docs` 안에 `.txt`로 만들면 요약할 파일로 잡힌다.
- 버그 하나는 Ruff가 단서를 준다. 다만 그 규칙은 기본으로 꺼져 있다. 테스트로 버그를 모두 찾은 **뒤에** `ruff check --extend-select ARG ch06/doc_summarizer.py`를 실행해 본다. `ARG`는 "받기만 하고 쓰지 않는 매개변수"를 찾는 규칙이다. 무엇을 가리키는가? 테스트가 찾은 버그 중 어느 것과 같은가?

**확인할 것**

- 버그 세 개를 각각 어느 테스트가 찾았는가? 찾은 테스트와 고친 줄을 `notes.md`에 표로 적는다.
- 처음 실행에서 3초가 걸린 테스트는 무엇 때문이었는가? 그 버그가 실제 서비스에서는 어떤 문제를 일으키는가? (힌트: 테스트에서는 3초였지만 실제로는 정말 기다렸다. 이 버그는 **동작은 맞는데** 주입한 것을 쓰지 않는다.)
- `split_text()`의 버그는 실제 서비스에서 어떤 문제를 일으키는가? LLM에게 무엇을 보내게 되는가? 돈과 결과 파일에 어떤 영향이 있는가?
- 형식이 틀린 답 하나 때문에 생기는 버그는 `summarize_folder()`에서 어떻게 나타나는가? 파일 백 개 중 하나의 조각에서 이 일이 생기면 결과 파일은 어떻게 되는가?
- 버그를 고친 뒤 커버리지가 100%인가? 100%라면 테스트가 충분하다는 뜻인가(6.6.2)? 고친 코드의 한 줄을 일부러 다시 틀리게 바꿨을 때 실패하는 테스트가 있는지 세 곳에서 확인한다.
- `ch06` 폴더에서 이 테스트 파일을 빼고 `pytest`를 돌리면 실패하는 테스트가 있는가? 버그 세 개는 모두 `doc_summarizer.py`만의 것이었는가?

**더 해 보기 (선택)**

- `summarize_file()`이 빈 파일을 만나면 레코드를 하나도 내놓지 않는다. 그 파일이 있었다는 것이 결과에 남지 않는다. 빈 파일은 `{"file": ..., "chunk": 0, "error": "빈 파일"}` 레코드를 남기도록 약속을 바꾸고 싶다면, 테스트를 먼저 쓰고 코드를 고친다.
- `summarize_folder()`에 `on_progress: Callable[[str, int], None] | None = None` 매개변수를 더해, 조각 하나를 처리할 때마다 `on_progress(파일 이름, 조각 번호)`를 부르게 한다. 테스트에서는 `events: list[tuple[str, int]] = []`를 만들고 `on_progress=lambda name, number: events.append((name, number))`처럼 넘겨 부른 순서를 확인한다. `sleep=waits.append`처럼 `append`를 그대로 넘길 수는 없다. `append`는 인자를 하나만 받는데 `on_progress`는 둘을 넘기기 때문이다(mypy도, 실행도 실패한다). 콜백의 약속을 `Callable[[tuple[str, int]], None]`처럼 튜플 하나를 받게 바꾸면 `events.append`를 그대로 넘길 수 있다. 어느 약속이 쓰는 쪽에 더 편한지 생각해 본다. 의존성 주입의 또 다른 쓰임이다.
- 5장 실습 5-7의 `review_analyzer.py`에 테스트를 붙인다. `extract_json()`, `describe_errors()`, `analyze()`, `count_by()`를 각각 테스트하고, `report()`는 `capsys`로 확인한다. 5장의 "실행 예와 똑같이 나오는가?"를 눈 대신 테스트로 확인하는 것이다.
- 기초 과정 10장의 가계부 프로그램에 pytest 테스트를 붙인다. `check_samples.py`의 `EXPECTED`를 `parametrize`로 옮기고, 시험 파일은 `tmp_path`에 만들거나 `samples` 폴더의 것을 쓴다. 9장의 선택 활동("기초 과정 10장에서 만든 프로그램에 먼저 pytest 테스트를 붙인 뒤, 이 과정에서 배운 문법으로 다시 작성하고 테스트가 그대로 통과하는지 확인한다")의 첫 단계다.

## 정리

| 항목 | 핵심 |
|---|---|
| 자동 테스트 | 코드의 동작을 확인하는 코드. "이 입력이면 이 결과"를 적어 두고 명령 하나로 모두 확인한다 |
| 회귀 | 고친 곳 때문에 전에 되던 것이 안 되는 것. 확인하지 않은 곳에서 생긴다. 쌓인 테스트가 막는다 |
| 테스트와 타입 검사 | mypy는 모든 경로의 타입을, 테스트는 실행한 경로의 값을 확인한다. 서로 보완한다 |
| AI와 테스트 | 고치기 전에 돌리고, 새 요구를 먼저 테스트로 적고, 고친 뒤 전부 돌린다. 테스트 파일의 `git diff`를 본다. 기대값은 사람이 정한다 |
| pytest의 규칙 | `test_*.py` 파일의 `test`로 시작하는 함수. 이름 규칙을 어기면 조용히 무시된다 |
| `assert` | pytest가 고쳐 써서 실패할 때 양쪽 값과 차이를 보여 준다. 실제 값은 왼쪽, 기대값은 오른쪽 |
| 실행 옵션 | `-v`, `-q`, `-x`, `-k 식`, `파일::함수`, `--lf`, `-s`, `-vv`, `-m 마커`, `-rs`, `--durations=N` |
| 모듈 찾기 | 테스트 파일의 폴더를 `sys.path`에 넣는다. 다른 폴더에 같은 이름의 테스트 파일을 두지 않는다 |
| 테스트 탐색기 | `python.testing.pytestEnabled`. 실패한 테스트를 **Debug Test**로 실행하는 것이 버그를 찾는 지름길 |
| 준비·실행·확인 | Arrange-Act-Assert. 실행은 하나. 동작이 둘이면 테스트를 나눈다 |
| 정상·경계·실패 | 버그는 경계에 모인다. 비어 있음, 하나, 딱 맞음, 하나 넘침. 경계를 쓰다 보면 약속이 분명해진다 |
| `pytest.raises()` | 블록 안에서 그 예외가 나야 통과. `match=`로 메시지, `as excinfo`로 예외 객체. 제너레이터는 꺼내야 예외가 난다 |
| `pytest.approx()` | 실수는 "거의 같다"로 비교한다. 우연히 `==`가 통과해도 `approx()`를 쓴다 |
| `parametrize` | 같은 확인을 입력만 바꿔 되풀이한다. `ids=`, `pytest.param(..., id=)`으로 읽기 쉬운 이름표 |
| 좋은 테스트 | 동작 하나, 서로 기대지 않기, 기대값을 계산하지 않기, 테스트 안에 `if`/`for` 없이, 실패하는 것을 한 번은 보기 |
| 픽스처 | `@pytest.fixture`. 매개변수 이름으로 주입된다. 테스트마다 새로 만든다. 픽스처는 픽스처를 받을 수 있다 |
| `yield` 픽스처 | `yield` 앞이 준비, 뒤가 정리. 테스트가 실패해도 정리한다. `@contextmanager`와 같은 모양 |
| `conftest.py` | 그 폴더 아래의 테스트가 함께 쓰는 픽스처와 설정. `import`하지 않는다 |
| `scope` | `function`(기본), `module`, `session`. 넓은 범위는 바뀌지 않는 것에만 |
| `tmp_path` | 테스트마다 새 임시 폴더(`Path`). 파일을 읽고 쓰는 코드를 테스트한다 |
| `monkeypatch` | `setenv`/`delenv`, `setattr`. 테스트가 끝나면 되돌린다. 테스트는 실행하는 컴퓨터의 상태에 기대지 않는다 |
| `capsys` | `readouterr().out`/`.err`. 출력 확인은 깨지기 쉽다. 계산은 반환값으로 확인한다 |
| 테스트 대역 | 진짜 대신 쓰는 가짜. 바깥 세계와 닿는 경계(네트워크, 시계, 난수)에만 쓴다 |
| 의존성 주입 | 쓰는 것을 매개변수로 받는다. 기본값은 진짜(`time.sleep`, `random.random`), 테스트는 가짜(`waits.append`) |
| 매번 달라지는 결과 | 원인을 주입받아 고정하거나(`rand=lambda: 0.5`), 언제나 성립하는 성질을 확인한다(씨앗을 고정한 여러 난수) |
| `Protocol` 가짜 | `FakeLLM`이 받은 요청을 기록한다. 결과와 요청을 함께 확인한다. 모양이 어긋나면 mypy가 찾는다 |
| `monkeypatch.setattr()` | 주입할 수 없을 때. **쓰는 곳**의 이름을 바꾼다. `from time import sleep`이면 그 모듈의 `sleep` |
| `unittest.mock` | `Mock`, `return_value`, `side_effect`, `assert_called_once_with`, `patch`. 무엇이든 받아 주므로 `create_autospec`으로 모양을 맞춘다 |
| 마커 | `pytestmark = pytest.mark.live`, `skipif`. `conftest.py`의 `pytest_configure`로 등록. `-m "not live"` |
| 커버리지 | `pytest --cov=ch06 --cov-report=term-missing`. `--cov-branch`로 갈림길까지. 테스트가 부족한 곳을 찾는 데 쓴다 |
| 커버리지의 함정 | 실행했다고 확인한 것은 아니다. `assert` 없는 테스트도 100%. 숫자를 목표로 삼지 않는다 |
| `ruff check` | 린트. `파일:줄:칸: 코드 설명`. `--fix`는 안전한 것만. `# noqa: 코드`는 코드를 꼭 적는다 |
| `ruff format` | 포맷. 동작을 바꾸지 않는다. `--check`는 고칠 곳이 있는지만 본다 |
| 한 번에 | `python check.py ch06` — ruff check, ruff format --check, mypy --strict, `pytest -m "not live"`. 커밋하기 전에 |
| 테스트와 평가 | 우리 코드의 동작은 가짜 LLM으로 테스트한다. LLM 답의 품질은 평가한다. 진짜 답의 내용을 `assert`하면 들쭉날쭉한 테스트가 된다 |

## 다음 장

[7장. 비동기(asyncio)](ch07.md)에서는 LLM API 호출 여러 개를 **동시에** 보낸다. 몇 초씩 걸리는 호출 스무 개를 차례로 하면 1분이 넘지만, 동시에 하면 몇 초면 된다. 그런데 비동기 코드는 실행할 때마다 끝나는 순서가 달라질 수 있어서, 눈으로 출력을 보고 맞는지 판단하기 어렵다. 그래서 테스트를 먼저 배웠다. 이 장의 `Flaky`와 `ScriptedLLM`, `sleep` 주입은 7장에서 그대로 쓰인다. `time.sleep` 자리에 `asyncio.sleep`이 들어가고, 재시도 데코레이터는 비동기 함수용으로 바뀌고, 테스트는 `pytest-asyncio`로 비동기 함수를 부른다. 동시 실행 수 제한과 시간 제한이 의도대로 동작하는지도 테스트로 확인한다.
