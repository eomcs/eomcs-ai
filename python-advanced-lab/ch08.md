# 8장. 패키지 배포

[파이썬 중급](README.md) 과정의 여덟 번째 장이다. 지금까지 만든 코드는 **이 저장소 안에서만** 돌아간다. `ch07/async_summarizer.py`를 다른 프로젝트에서 쓰려면 파일을 복사해야 하고, 그 파일이 기대는 `async_retry.py`도 함께 복사해야 하며, 받는 쪽 가상환경에 Pydantic이 있는지도 알아서 챙겨야 한다. 실행할 때는 `python ch07/run_summarizer.py`처럼 파일의 경로를 알아야 한다. 이 장에서는 코드를 **남이 설치해서 쓸 수 있는 패키지**로 만든다. `pip install 이름` 한 줄로 설치되고, 필요한 패키지가 함께 설치되고, 터미널에서 이름만으로 실행되는 패키지다. 1장 1.1.1의 표에서 "8장"으로 적어 둔 `pyproject.toml`이 그 중심에 있다.

- **`pyproject.toml`** — TOML 파일을 읽는 법을 익히고, 실습 저장소에 흩어진 도구 설정(`pytest.ini`, `conftest.py`의 마커 등록, `check.py`의 `--strict`)을 `pyproject.toml` 한 곳으로 모은다. 프로젝트 정보, 의존성 선언, 빌드 백엔드가 무엇인지 보고, `requirements.txt`와 어떻게 다른지 라이브러리와 애플리케이션으로 나눠 이해한다.
- **프로젝트 구조** — 6장의 `chunk()`와 프롬프트 템플릿을 담은 작은 패키지 `textchunk`를 새 저장소에 `src` 레이아웃으로 만든다. 편집 가능 설치(`pip install -e .`)로 개발하고, 테스트가 왜 **설치된** 패키지를 `import`해야 하는지 확인한다. 패키지 안의 데이터 파일은 `importlib.resources`로 읽는다.
- **명령행 도구 만들기** — 기초 과정의 `sys.argv`에서 한 걸음 더 나아가 `argparse`로 옵션과 도움말이 있는 명령을 만들고, `[project.scripts]`로 설치하면 바로 실행되는 `textchunk` 명령을 만든다.
- **빌드** — `python -m build`로 소스 배포판(sdist)과 휠(wheel)을 만들고, 휠을 열어 무엇이 들어갔는지 확인한다. 새 가상환경에 휠을 설치해 다른 사람의 컴퓨터에서처럼 동작하는지 본다.
- **버전과 의존성 범위** — 유의적 버전(SemVer)으로 버전 번호를 붙이고, 의존성의 범위를 너무 좁지도 넓지도 않게 정한다. 잠금 파일의 역할을 보고, Git 태그로 버전을 표시한다.
- **배포와 설치 확인** — TestPyPI에 계정과 API 토큰을 만들고 `twine`으로 올린 뒤, 새 가상환경에서 설치해 확인한다. 실제 PyPI에 공개하기 전에 확인할 것을 정리한다.
- **uv로 같은 일 하기** — 같은 프로젝트를 uv로 다루며 `uv sync`, `uv add`, `uv run`, `uv.lock`, `uv build`, `uv publish`가 표준 도구의 어느 일에 해당하는지 대응시킨다.
- **(선택) 지속적 통합 맛보기** — GitHub Actions로 푸시할 때마다 ruff, mypy, pytest를 자동으로 실행한다.

## 학습 목표

이 장을 마치면 다음을 할 수 있다.

- TOML 파일을 읽고, `pyproject.toml`의 `[build-system]`, `[project]`, `[dependency-groups]`, `[tool.…]` 표가 각각 누구를 위한 것인지 설명할 수 있다.
- pytest, mypy, ruff의 설정을 `pyproject.toml`에 적고, 설정 파일이 여러 개일 때 어느 것이 쓰이는지 확인할 수 있다.
- 실행에 필요한 의존성과 개발할 때만 쓰는 도구를 나눠 선언하고, `requirements.txt`·잠금 파일과의 차이를 라이브러리와 애플리케이션으로 나눠 설명할 수 있다.
- `src` 레이아웃으로 프로젝트를 만들고, 편집 가능 설치로 개발하며, 설치하지 않은 패키지를 테스트가 실수로 `import`하는 일을 막을 수 있다.
- 패키지 안의 데이터 파일을 `importlib.resources`로 읽고, 그 파일이 휠에 들어갔는지 확인할 수 있다.
- `argparse`로 위치 인자, 옵션, 기본값, 선택지, 도움말이 있는 명령행 도구를 만들고, 종료 코드와 표준 오류를 약속대로 쓸 수 있다.
- `[project.scripts]`로 설치하면 실행되는 명령을 만들고, `main(argv)`에 인자 리스트를 넘겨 명령행 도구를 테스트할 수 있다.
- sdist와 휠을 빌드하고, 휠의 파일 이름과 내용을 읽을 수 있다.
- 유의적 버전(SemVer)으로 버전을 올리고, `>=`, `<`, `~=`, `==`로 의존성 범위를 정하며, 그 범위가 너무 좁거나 넓을 때의 문제를 말할 수 있다.
- TestPyPI에 패키지를 올리고 새 가상환경에서 설치해 확인하며, 실제 PyPI에 공개하기 전에 무엇을 점검할지 말할 수 있다.
- uv의 명령을 표준 도구(`venv`, `pip`, `build`, `twine`)의 명령과 대응시켜 읽고 쓸 수 있다.
- (선택) GitHub Actions 워크플로 파일을 읽고, 푸시할 때마다 검사가 돌게 할 수 있다.

## 8.1 `pyproject.toml`

### 8.1.1 설정이 흩어져 있다

7장까지 실습 저장소에 쌓인 설정을 모아 보면 다음과 같다.

| 무엇을 | 어디에 적었나 | 장 |
|---|---|---|
| 설치할 패키지 목록 | `requirements.txt`(`pip freeze`로 만든 것) | 1장~7장 |
| VS Code의 포매터, 타입 검사 모드, 테스트 탐색기 | `.vscode/settings.json` | 1장, 5장, 6장 |
| mypy를 엄격하게 | `check.py` 안의 `mypy --strict` | 5장, 6장 |
| `live` 마커 등록 | `ch06/conftest.py`의 `pytest_configure()` | 6장 |
| pytest-asyncio의 이벤트 루프 범위 | `pytest.ini` | 7장 |
| ruff의 규칙 | 적은 곳이 없다. 기본 규칙을 썼다 | 6장 |

설정이 다섯 곳에 흩어져 있고, 그 가운데 둘은 문제가 있다.

- **`requirements.txt`는 직접 설치한 것과 함께 설치된 것을 구별하지 못한다.** 1장에서 `httpx` 하나를 설치했는데 일곱 줄이 되었다(1.2.6). 5장에서는 프로그램을 **실행할 때** 필요한 Pydantic과 **개발할 때만** 쓰는 mypy가 한 목록에 섞였다. 이 목록만 보고는 무엇을 지워도 되는지 알 수 없다.
- **같은 종류의 설정이 서로 다른 곳에 있다.** pytest의 설정 하나는 `pytest.ini`에, 다른 하나는 `conftest.py`에 있다. mypy를 엄격하게 검사한다는 약속은 `check.py`에만 있어서, 터미널에서 그냥 `mypy ch07`을 실행하면 엄격하지 않게 검사한다. VS Code가 저장할 때 돌리는 ruff와 `check.py`가 돌리는 ruff가 같은 규칙을 쓴다는 보장도 없다.

파이썬 생태계는 이런 설정을 **`pyproject.toml`** 한 파일에 모으기로 약속했다. 이 파일 하나에 다음이 모두 들어간다.

- 이 프로젝트를 **어떻게 빌드하는가** — `[build-system]`
- 이 프로젝트는 **무엇인가** — 이름, 버전, 설명, 지원하는 파이썬 버전, 실행에 필요한 의존성. `[project]`
- 개발할 때 **무엇이 더 필요한가** — `[dependency-groups]`
- 각 도구를 **어떻게 설정하는가** — `[tool.pytest.ini_options]`, `[tool.mypy]`, `[tool.ruff]` 같은 `[tool.도구이름]`

파이썬 프로젝트를 처음 열었을 때 가장 먼저 읽을 파일이 `pyproject.toml`이다. 1장 1.1.1의 표에서 "`[project]`, `dependencies = [...]`가 적힌 `pyproject.toml`"을 8장으로 적어 둔 것이 이 파일이다. FastAPI, LangChain, Anthropic SDK 같은 라이브러리의 저장소를 열어 보면 맨 위 폴더에 이 파일이 있다.

### 8.1.2 TOML 읽기

`pyproject.toml`은 **TOML**(Tom's Obvious Minimal Language)이라는 형식으로 쓴다. 사람이 읽고 쓰기 쉽게 만든 설정 파일 형식이다. 작은 예로 문법을 익힌다. 실습 저장소의 `ch08`에 만든다.

`ch08/sample.toml`

```toml
# 샵(#) 뒤는 주석이다
title = "TOML 연습"
version = 3
ratio = 0.5
enabled = true

[owner]
name = "홍길동"
emails = ["gildong@example.com", "hong@example.com"]

[model.default]
name = "small"
max_tokens = 1024

[model.large]
name = "large"
max_tokens = 4096
options = { temperature = 0.2, stream = false }
```

| 모양 | 뜻 | 파이썬으로 읽으면 |
|---|---|---|
| `키 = 값` | 이름과 값 한 쌍 | 딕셔너리의 항목 |
| `"…"` | 문자열. 반드시 따옴표로 감싼다 | `str` |
| `3`, `0.5`, `true`/`false` | 정수, 실수, 참/거짓. 참/거짓은 **소문자**다 | `int`, `float`, `bool` |
| `[…, …]` | 배열 | `list` |
| `[이름]` | **표**(table). 다음 표가 나올 때까지의 `키 = 값`이 이 표에 속한다 | 안쪽 딕셔너리 |
| `[이름.이름]` | 점으로 이은 표. `[model.default]`는 `model` 표 안의 `default` 표다 | 두 겹의 딕셔너리 |
| `{ 키 = 값, … }` | 한 줄로 쓰는 표(inline table) | 딕셔너리 |

표준 라이브러리의 `tomllib`(파이썬 3.11부터)로 읽어서 확인한다. 실습 저장소 폴더에서 대화형 셸을 연다.

```python
>>> import tomllib
>>> with open("ch08/sample.toml", "rb") as f:
...     data = tomllib.load(f)
...
>>> data["title"], data["version"], data["enabled"]
('TOML 연습', 3, True)
>>> data["owner"]["emails"]
['gildong@example.com', 'hong@example.com']
>>> data["model"]["large"]["options"]
{'temperature': 0.2, 'stream': False}
>>> list(data["model"])
['default', 'large']
```

- `open(..., "rb")` — `tomllib.load()`는 파일을 **바이트**로 받는다. 글자의 인코딩은 TOML 규칙대로 UTF-8로 정해져 있어서, 텍스트 모드로 열면서 `encoding`을 고를 여지를 두지 않으려는 것이다. 문자열을 읽을 때는 `tomllib.loads(text)`를 쓴다.
- `[model.default]`와 `[model.large]`가 `data["model"]` 안의 두 딕셔너리가 되었다. `pyproject.toml`의 `[tool.mypy]`, `[tool.ruff]`도 같다. 모두 `data["tool"]` 안에 들어가고, 각 도구는 자기 이름의 표만 읽는다.
- `tomllib`은 **읽기만** 한다. TOML 파일을 쓰는 기능은 표준 라이브러리에 없다. 설정 파일은 사람이 쓰고 프로그램이 읽는 것이기 때문이다.

같은 표를 두 번 쓰거나 같은 키를 두 번 쓰면 오류다. 기초 과정의 JSON과 비교하면, TOML은 주석을 쓸 수 있고, 키에 따옴표가 필요 없고, 마지막 항목 뒤의 쉼표를 허락한다. 사람이 손으로 고치는 설정 파일에 맞게 만든 형식이다. 확인했으면 `sample.toml`을 지운다.

### 8.1.3 도구 설정을 한곳에 모으기

실습 저장소 폴더 바로 아래에 `pyproject.toml`을 만든다. 1장의 `README.md`, 6장의 `check.py`와 같은 자리다.

`pyproject.toml`

```toml
# 파이썬 중급 실습 저장소의 도구 설정.
# 이 저장소는 배포할 패키지가 아니므로 [project]와 [build-system]은 두지 않는다.

[tool.pytest.ini_options]
asyncio_default_fixture_loop_scope = "function"
markers = [
    "live: 실제 외부 API를 부르는 테스트",
]

[tool.mypy]
strict = true

[tool.ruff]
target-version = "py312"

[tool.ruff.lint]
extend-select = ["E711", "E712"]
```

**pytest** — `[tool.pytest.ini_options]`에는 `pytest.ini`의 `[pytest]` 아래에 쓰던 것을 그대로 옮긴다. 이름에 `ini_options`가 붙은 것은 pytest가 오래 써 온 `pytest.ini`의 설정을 그대로 받는다는 뜻이다. 다만 TOML이므로 값을 따옴표로 감싸고, 여러 값은 배열로 쓴다.

- `asyncio_default_fixture_loop_scope` — 7장의 `pytest.ini`에 있던 설정이다.
- `markers` — 6.5.6에서 `conftest.py`의 `pytest_configure()`로 등록한 `live` 마커다. 이제 `"이름: 설명"`을 배열에 적기만 하면 된다.

> **`[tool.pytest]`라는 표도 있다**
> pytest 9부터는 `[tool.pytest]` 표에 TOML의 자료형을 그대로 쓰는 새 방식도 받는다. 아직은 대부분의 프로젝트가 `[tool.pytest.ini_options]`를 쓰므로 이 교재도 이것을 쓴다. 남의 프로젝트에서 `[tool.pytest]`를 보면 같은 일을 하는 표로 읽으면 된다.

**mypy** — `strict = true`는 명령행의 `--strict`와 같다. 5.1.6에서 "이 옵션들은 8장에서 `pyproject.toml`에 한 번 적어 두고 `mypy`만 실행하게 바꾼다"고 한 것이 이것이다. 이제 `mypy ch07`만 실행해도 엄격하게 검사한다. mypy는 **실행한 폴더**(현재 작업 폴더)에서 시작해 Git 저장소의 맨 위 폴더까지 올라가며 설정 파일을 찾는다. 검사할 파일이 어디 있느냐가 아니라 **어디서 실행했느냐**가 기준이다. 이 장에서 명령을 어디서 실행하는지 따지는 이유 중 하나다.

**ruff** — 두 가지를 적었다.

- `target-version = "py312"` — 이 코드가 파이썬 3.12 이상에서 돈다는 것을 알린다. ruff는 이것을 보고 "3.12에는 아직 없는 문법"을 쓰라고 권하지 않는다. 8.2에서 만드는 패키지처럼 `[project]` 표에 `requires-python`이 있으면 거기서 알아서 읽으므로 적지 않아도 된다. 이 저장소에는 `[project]`가 없으므로 직접 적는다.
- `extend-select = ["E711", "E712"]` — 기본 규칙에 **더해서** 켤 규칙이다. 6.6.3에서 `path == None`을 지적하지 않았다며 "어떤 규칙을 켤지는 프로젝트마다 정하고, 8장에서 `pyproject.toml`에 적는다"고 했다. `E711`은 `== None`, `E712`는 `== True`처럼 쓴 비교를 찾는다. `select`로 쓰면 기본 규칙을 **바꿔 버리고**, `extend-select`로 쓰면 기본 규칙에 **더한다.** 남의 `pyproject.toml`에서 이 두 키를 볼 때 구별해서 읽는다.

VS Code의 Ruff 확장도 이 파일을 읽는다. 터미널의 `ruff`와 저장할 때 도는 확장이 같은 규칙을 쓰게 되었다.

이제 옮긴 설정의 원래 자리를 정리한다.

1. `pytest.ini`를 지운다.
2. `ch06/conftest.py`에서 `pytest_configure()` 함수를 지운다. 그 함수 때문에 쓰던 `import`가 더 쓰이지 않으면 저장할 때 Ruff가 지운다(6.6.3의 `F401`).
3. `check.py`에서 `"--strict"`를 지운다.

`check.py`

```python

    ["ruff", "format", "--check", target],
    ["mypy", target],
    ["pytest", "-q", "-m", "not live", target],

```

**두 설정 파일이 함께 있으면** — 1번을 하기 전에 무슨 일이 생기는지 보고 지워도 좋다. `pytest.ini`와 `pyproject.toml`이 같은 폴더에 있으면 pytest는 `pytest.ini`를 쓰고 `pyproject.toml`의 설정은 **읽지 않는다.** pytest가 출력의 머리에 어느 파일을 썼는지 알려 준다.

### 8.1.4 프로젝트 정보 — `[project]`

실습 저장소의 `pyproject.toml`에는 `[tool.…]` 표만 있다. 배포할 패키지라면 `[project]` 표가 더 있다. 우리가 써 온 패키지의 정보를 보면 이 표에 무엇을 적는지 알 수 있다.

```
python -m pip show httpx
```

```
Name: httpx
Version: 0.28.1
Summary: The next generation HTTP client.
Home-page: https://github.com/encode/httpx
Author:
Author-email: Tom Christie <tom@tomchristie.com>
License: BSD-3-Clause
Location: /Users/.../python-advanced-lab/.venv/lib/python3.13/site-packages
Requires: anyio, certifi, httpcore, idna
Required-by:
```

이 정보는 httpx의 저장소에 있는 `pyproject.toml`의 `[project]` 표에서 왔다. 대략 다음과 같은 모양이다(줄였다).

```toml
[project]
name = "httpx"
description = "The next generation HTTP client."
license = "BSD-3-Clause"
requires-python = ">=3.8"
authors = [{ name = "Tom Christie", email = "tom@tomchristie.com" }]
dependencies = [
    "certifi",
    "httpcore==1.*",
    "anyio",
    "idna",
]
```

| 키 | 뜻 | `pip show`에서 |
|---|---|---|
| `name` | **배포 이름**. `pip install` 뒤에 쓰는 이름이다 | `Name` |
| `version` | 버전(8.5) | `Version` |
| `description` | 한 줄 설명 | `Summary` |
| `readme` | PyPI 페이지에 보일 긴 설명 파일 | (PyPI 페이지의 본문) |
| `requires-python` | 지원하는 파이썬 버전의 범위 | (맞지 않는 파이썬에는 설치되지 않는다) |
| `license`, `license-files` | 라이선스와 그 전문 파일 | `License` |
| `authors` | 만든 사람. `{ name = ..., email = ... }`의 배열 | `Author-email` |
| `dependencies` | 실행에 필요한 의존성 | `Requires` |

`Requires`에는 `anyio`, `certifi`, `httpcore`, `idna` 네 개만 있다. httpx가 **직접** 쓰는 것만 적었기 때문이다. `httpcore`가 다시 기대는 `h11`은 `httpcore`의 `[project]`에 적혀 있다. pip는 이 목록을 따라 내려가며 필요한 것을 모두 모아 설치한다. 1장에서 httpx 하나를 설치했는데 일곱 개가 된 이유다. `pip freeze`가 이 구별을 잃어버린 결과를 적는다면, `dependencies`는 **사람이 정한 원인**을 적는다.

**배포 이름과 `import` 이름은 다를 수 있다.** httpx는 둘 다 `httpx`지만, 기초 과정과 이 과정에서 이미 이런 예를 보았다.

| `pip install` | `import` |
|---|---|
| `pytest-asyncio` | `pytest_asyncio` |
| `types-requests` | (`requests`의 타입 정보. 직접 `import`하지 않는다) |
| `python-dotenv` | `dotenv` |
| `beautifulsoup4` | `bs4` |

배포 이름은 PyPI에서 쓰는 이름이고, `import` 이름은 휠 안에 든 **폴더**(패키지)의 이름이다. 8.2에서 만드는 패키지도 배포 이름(`textchunk-아이디`)과 `import` 이름(`textchunk`)이 다르다.

### 8.1.5 의존성 선언 — 실행에 필요한 것과 개발할 때 필요한 것

5장에서 "8장에서 `pyproject.toml`로 '실행에 필요한 의존성'과 '개발 도구'를 나눈다"고 했다. 두 곳에 나눠 적는다.

```toml
[project]
dependencies = [
    "pydantic>=2.9,<3",
]

[dependency-groups]
dev = [
    "pytest>=9",
    "pytest-cov>=7",
    "mypy>=2",
    "ruff>=0.17",
]
```

- **`[project]`의 `dependencies`** — 이 패키지를 **쓰는 사람**에게 필요한 것. `pip install 패키지`를 하면 함께 설치된다. 패키지의 정보(메타데이터)에 기록되어 PyPI까지 올라간다.
- **`[dependency-groups]`** — 이 패키지를 **만드는 사람**에게 필요한 것. 테스트 도구, 타입 검사기, 린터다. 패키지의 정보에 들어가지 않으므로, 쓰는 사람은 이것들을 설치하지 않는다. `dev`는 그룹의 이름이고, `test`, `docs`처럼 여러 그룹을 만들 수도 있다.

설치하는 명령도 다르다. `pyproject.toml`이 있는 폴더에서 실행한다.

```
python -m pip install -e .            # 이 패키지와 그 dependencies
python -m pip install --group dev     # dev 그룹
```

`.`은 "지금 폴더의 프로젝트"이고, `-e`는 8.2.3에서 볼 편집 가능 설치다. 두 줄은 `python -m pip install -e . --group dev` 한 줄로 합칠 수 있다.

> **`[project.optional-dependencies]` — 선택 기능**
> 남의 `pyproject.toml`에서 `[project.optional-dependencies]`라는 표도 보게 된다. 이것은 **쓰는 사람이 골라서** 설치하는 의존성이다. `pip install "fastapi[standard]"`처럼 대괄호 안에 이름을 적으면 그 묶음이 함께 설치된다. 패키지의 정보에 기록되어 PyPI까지 올라간다는 점에서 `[dependency-groups]`와 다르다. 예전에는 개발 도구를 `[project.optional-dependencies]`의 `dev`에 넣는 일이 많아서 `pip install -e ".[dev]"`라는 명령을 자주 보게 될 것이다. 개발 도구만을 위한 `[dependency-groups]`는 2024년에 표준이 되었고 pip 25.1부터 `--group`으로 설치할 수 있다.

### 8.1.6 빌드 백엔드 — `[build-system]`

`pip install .`을 하면 pip는 프로젝트 폴더를 그대로 복사하지 않는다. 먼저 **휠**(wheel)이라는 설치용 파일을 만들고(8.4), 그 휠을 설치한다. 휠을 만드는 일을 **빌드**라고 한다. 그런데 pip는 빌드를 직접 하지 않는다. `[build-system]`에 적힌 도구에게 맡긴다.

```toml
[build-system]
requires = ["hatchling>=1.27"]
build-backend = "hatchling.build"
```

- `requires` — 빌드할 때 필요한 패키지. pip는 **임시 가상환경**을 만들어 여기에 적힌 것을 설치하고 그 안에서 빌드한다. 그래서 `hatchling`을 우리 가상환경에 설치할 필요가 없다.
- `build-backend` — 빌드를 맡을 모듈.

빌드를 **시키는** 쪽(pip, build, uv)을 **프런트엔드**, 실제로 휠을 **만드는** 쪽을 **백엔드**라고 한다. 둘 사이의 약속이 표준으로 정해져 있어서 어느 프런트엔드든 어느 백엔드와 짝지을 수 있다.

| 백엔드 | `build-backend` | 남의 프로젝트에서 |
|---|---|---|
| hatchling | `hatchling.build` | 이 교재에서 쓴다. httpx, FastAPI, Pydantic |
| setuptools | `setuptools.build_meta` | 가장 오래된 백엔드. `setup.py`가 함께 있는 오래된 프로젝트가 많다 |
| uv_build | `uv_build` | `uv init`이 기본으로 고른다(8.7) |
| flit-core | `flit_core.buildapi` | 순수 파이썬 패키지를 위한 작은 백엔드 |
| maturin, scikit-build-core | `maturin`, `scikit_build_core.build` | Rust, C++로 쓴 확장 모듈이 든 패키지. Pydantic의 `pydantic-core`가 maturin을 쓴다 |

우리처럼 파이썬 파일만 있는 패키지라면 어느 백엔드를 써도 결과는 거의 같다. 백엔드마다 달라지는 것은 "어떤 파일을 휠에 넣을지"를 정하는 설정(`[tool.hatch.…]`, `[tool.setuptools.…]`)이다. 이 교재는 파이썬 패키징 공식 안내서(Python Packaging User Guide)의 첫 예제가 쓰는 hatchling을 쓴다.

> **`setup.py`를 보면**
> 오래된 프로젝트에는 `pyproject.toml` 대신, 또는 함께 `setup.py`가 있다. `setup(name=..., install_requires=[...])`처럼 **파이썬 코드**로 프로젝트 정보를 적던 방식이다. 설정을 읽으려면 코드를 실행해야 해서, 도구가 정보를 안전하게 읽기 어려웠다. 그래서 정보는 `pyproject.toml`의 `[project]`로 옮겨 가는 중이다. `install_requires`는 `dependencies`, `python_requires`는 `requires-python`과 같은 것으로 읽으면 된다.

### 8.1.7 `requirements.txt`와의 관계 — 라이브러리와 애플리케이션

`dependencies`가 있으면 `requirements.txt`는 필요 없을까? 둘은 하는 일이 다르다. 먼저 만드는 것을 두 종류로 나눈다.

- **라이브러리** — 다른 프로그램이 **가져다 쓰는** 패키지. httpx, Pydantic, 그리고 이 장의 `textchunk`. 쓰는 사람의 가상환경에는 다른 라이브러리도 함께 설치된다.
- **애플리케이션** — 그 자체로 **실행되는** 프로그램. 기초 과정의 가계부 프로그램, "LLM 서비스 배포"에서 서버에 올릴 FastAPI 서비스. 그 가상환경은 이 프로그램 하나만을 위한 것이다.

라이브러리가 `pydantic==2.14.3`처럼 버전을 하나로 못 박으면, 그 라이브러리를 쓰는 사람의 다른 라이브러리가 `pydantic>=2.15`를 원할 때 둘을 함께 설치할 수 없다. 그래서 라이브러리는 **동작하는 범위**를 넓게 적는다(8.5.3). 반대로 애플리케이션은 "어제 서버에서 동작한 그 버전 그대로"를 오늘 다른 서버에서도 설치해야 한다. 그래서 함께 설치된 것까지 **모든 패키지의 정확한 버전**을 적어 둔다. 이렇게 정확한 버전을 모두 적은 파일을 **잠금 파일**(lock file)이라고 한다(8.5.4).

| | 라이브러리 | 애플리케이션 |
|---|---|---|
| 예 | httpx, Pydantic, `textchunk` | 가계부 프로그램, FastAPI 서비스 |
| 직접 쓰는 의존성 | `pyproject.toml`의 `dependencies`에 **범위**로 | `pyproject.toml`의 `dependencies`에 범위로 |
| 함께 설치되는 것까지 정확한 버전으로 | 적지 않는다(배포하지 않는다) | 잠금 파일에. `requirements.txt`(`pip freeze`), `uv.lock`(8.7) |
| 설치하는 사람 | 다른 개발자. 자기 가상환경에 | 우리(서버, 동료의 컴퓨터). 프로그램만을 위한 가상환경에 |

`pip freeze`로 만든 `requirements.txt`는 처음부터 잠금 파일의 역할을 했다. 기초 과정 9.1.7에서 "같은 환경을 다시 만든다"고 한 것이 이 일이다. 문제는 그것 **하나뿐이어서**, 잠금 파일에서 "내가 직접 고른 것"을 읽어 낼 수 없었다는 점이다. 직접 고른 것은 `pyproject.toml`에, 그 결과로 정해진 정확한 버전은 잠금 파일에 나눠 두면 두 가지가 모두 남는다.

실습 저장소는 어느 쪽일까? 배포하지 않고, 이 저장소 하나만을 위한 가상환경에서 돌아가므로 애플리케이션에 가깝다. 그래서 이 저장소는 `requirements.txt`를 지금처럼 **잠금 파일로** 쓴다. 지우지 않는다. 다른 컴퓨터에서 `pip install -r requirements.txt`를 하면 이 교재의 출력을 확인한 그 버전들이 그대로 설치된다.

`ch08/lint_check.py`를 만들어 `if value == None:`과 `if flag == True:`가 든 함수를 하나 쓰고(VS Code에서 `Save without Formatting`으로 저장한다), `ruff check ch08/lint_check.py`를 실행한다. `pyproject.toml`의 `extend-select`를 지우고 다시 실행하면 결과가 어떻게 달라지는가? `extend-select`를 `select`로 바꾸면? 세 결과를 비교해 `notes.md`에 적고, 설정을 되돌리고 파일을 지운다.

**4. 남의 `pyproject.toml` 읽기**

GitHub에서 이 과정에서 써 온 패키지 하나(httpx, pydantic, pytest-asyncio 중 하나)의 저장소를 열어 `pyproject.toml`을 읽는다. 다음을 찾아 `notes.md`에 적는다.

- 빌드 백엔드는 무엇인가?
- `requires-python`은 무엇인가? 우리 파이썬(3.13)이 그 범위에 드는가?
- `dependencies`에 몇 개가 있는가? 그 가운데 범위를 `==`로 못 박은 것이 있는가?
- `[tool.…]` 표가 몇 개 있는가? 그 가운데 이 과정에서 배운 도구는 무엇인가?
- 개발 도구는 `[dependency-groups]`와 `[project.optional-dependencies]` 중 어디에 적었는가?

## 8.2 프로젝트 구조

### 8.2.1 패키지 하나, 저장소 하나

이제 배포할 패키지를 만든다. 이름은 **`textchunk`**, 하는 일은 "긴 글 파일을 LLM에 보낼 조각으로 나눠 JSON으로 출력하는 것"이다. 내용은 새로울 것이 없다. 6장의 `chunk()`와, 조각을 프롬프트로 감쌀 템플릿 두 개, 그리고 8.3에서 만드는 명령행 입구가 전부다. 이 장의 관심은 코드가 아니라 **코드를 담는 그릇**이기 때문이다.

이 패키지는 실습 저장소 안이 아니라 **새 저장소**에 만든다.

- **버전은 저장소의 역사에 붙는다.** 8.5.5에서 `v0.1.0` 같은 Git 태그로 "이 커밋이 0.1.0이다"를 표시한다. 실습 저장소에 붙이면 그 태그가 `ch01`부터 `ch08`까지 모든 폴더를 가리키게 된다.
- **설정 파일은 위로 올라가며 찾는다.** pytest는 인자로 준 경로에서, ruff는 검사하는 파일이 있는 폴더에서, mypy는 실행한 폴더에서 위쪽으로 올라가며 설정 파일을 찾는다. 기준이 도구마다 다르다. 실습 저장소 안에 패키지를 두면 `pyproject.toml`이 두 개가 되어, 같은 파일을 검사해도 도구마다, 실행한 위치마다 다른 설정이 쓰일 수 있다. 8.1.3에서 본 `configfile:` 줄을 매번 확인해야 한다.
- **가상환경도 따로다.** 1장에서 "8장과 9장에서 **배포할 패키지**를 만들 때는 그 패키지를 새 가상환경에 설치해 확인한다"고 했다. 패키지가 실제로 기대는 것이 무엇인지 알려면, 실습 저장소처럼 이것저것 설치된 가상환경이 아니라 그 패키지에 필요한 것만 있는 가상환경에서 개발해야 한다.

실무에서도 대개 **패키지 하나에 저장소 하나**다. httpx, Pydantic, pytest-asyncio가 모두 각자의 저장소를 가진다.

### 8.2.3 `src` 레이아웃

다음 구조를 만든다. 아직 비어 있는 파일은 8.2.6과 8.3에서 채운다.

```

├── .gitignore
├── LICENSE
├── README.md
├── pyproject.toml
├── src/
│   └── textchunk/
│       ├── __init__.py
│       ├── chunking.py
│       ├── prompts.py          ← 8.2.6
│       ├── py.typed
│       └── templates/          ← 8.2.6

└── tests/
    ├── test_chunking.py
    └── test_prompts.py         ← 8.2.6
```

패키지 폴더 `textchunk`가 프로젝트 폴더 바로 아래가 아니라 **`src` 폴더 안에** 있다. 이것을 **`src` 레이아웃**이라고 한다. 프로젝트 폴더 바로 아래에 패키지 폴더를 두는 방식은 **평평한 레이아웃**(flat layout)이라고 한다.

```
src 레이아웃                     평평한 레이아웃
textchunk/                       textchunk/
├── pyproject.toml               ├── pyproject.toml
├── src/                         ├── textchunk/
│   └── textchunk/               │   ├── __init__.py
│       ├── __init__.py          │   └── ...
│       └── ...                  └── tests/
└── tests/
```

평평한 레이아웃이 더 단순해 보이는데 왜 한 겹을 더 두는지는 8.2.5에서 확인한다. 먼저 파일을 채운다.

`src/textchunk/chunking.py`는 6장의 `ch06/chunking.py`를 그대로 복사한다. 첫 줄의 독스트링만 바꾼다.

`src/textchunk/chunking.py`

```python
"""긴 글을 조각으로 나눈다 — 6장 chunking.py를 옮겨 왔다."""

from collections.abc import Iterator


def chunk(text: str, size: int, overlap: int = 0) -> Iterator[str]:
    """text를 size글자씩 자른다. 앞 조각의 끝 overlap글자를 다음 조각의 앞에 겹친다."""
    if not 0 <= overlap < size:
        raise ValueError("overlap은 0 이상, size 미만이어야 한다")
    step = size - overlap
    for start in range(0, len(text), step):
        yield text[start : start + size]
        if start + size >= len(text):
            break
```

`src/textchunk/__init__.py`

```python
"""긴 글을 LLM에 보낼 조각으로 나누는 도구."""

from textchunk.chunking import chunk

__all__ = ["chunk"]
__version__ = "0.1.0"
```

- `from textchunk.chunking import chunk` — 패키지 안의 모듈끼리도 **패키지 이름부터** 쓰는 절대 `import`를 쓴다(기초 과정 8.3.3). 쓰는 사람은 `from textchunk.chunking import chunk` 대신 `from textchunk import chunk`로 짧게 쓸 수 있다.
- `__all__` — 이 패키지가 밖에 **공개하는** 이름의 목록이다. `from textchunk import *`가 가져오는 이름이고, mypy와 Pylance도 이 목록을 공개 이름으로 본다. 목록에 없는 이름은 "안에서만 쓰는 것"으로 읽는다(기초 과정 8.1.7의 밑줄로 시작하는 이름과 같은 생각).
- `__version__` — 패키지의 버전이다. 8.2.4의 `pyproject.toml`이 여기서 버전을 읽어 간다. 버전을 **한 곳에만** 적기 위해서다(8.5.2).

`src/textchunk/py.typed`는 **빈 파일**로 만든다. 이 파일이 있으면 mypy와 Pylance가 "이 패키지는 타입 힌트를 갖추었으니 믿고 검사하라"로 받아들인다. 없으면 다른 사람이 `textchunk`를 설치해 `mypy --strict`로 검사할 때 `module is installed, but missing library stubs or py.typed marker  [import-untyped]` 오류를 받는다. 5.1.6에서 본 `[import-untyped]`와 같은 종류다. 7장에서 `requests`를 검사하려고 `types-requests`를 따로 설치해야 했던 것도 requests가 이 표시 없이 배포되기 때문이다.

`tests/test_chunking.py`는 6장의 `ch06/test_chunking.py`를 옮기면서 `parametrize`로 줄였다.

`tests/test_chunking.py`

```python
"""chunking의 테스트 — 6장 test_chunking.py를 옮겨 왔다."""

import pytest

from textchunk.chunking import chunk


def test_chunk_splits_by_size() -> None:
    assert list(chunk("가나다라마바사아자차", 4)) == ["가나다라", "마바사아", "자차"]


def test_chunk_with_overlap() -> None:
    pieces = list(chunk("가나다라마바사아자차", 5, overlap=2))
    assert pieces == ["가나다라마", "라마바사아", "사아자차"]


@pytest.mark.parametrize(
    ("text", "expected"),
    [
        ("", []),
        ("가나다", ["가나다"]),
        ("가나다라마", ["가나다라마"]),
        ("가나다라마바", ["가나다라마", "바"]),
    ],
)
def test_chunk_boundaries(text: str, expected: list[str]) -> None:
    assert list(chunk(text, 5)) == expected


@pytest.mark.parametrize("overlap", [-1, 3])
def test_chunk_rejects_bad_overlap(overlap: int) -> None:
    with pytest.raises(ValueError, match="overlap"):
        list(chunk("가나다", 3, overlap=overlap))
```

`import pytest`와 `from textchunk.chunking import chunk` 사이에 **빈 줄이 있다.** 6.2.5의 상자에서 "Ruff는 `ch06` 안의 `chunking`을 외부 패키지로 보고 `pytest`와 한 무리로 묶는다. 8장에서 패키지 구조를 갖추면 다시 나뉜다"고 했다. Ruff는 프로젝트 폴더와 그 아래의 `src` 폴더에서 찾은 패키지를 "우리가 만든 것"(first-party)으로 알아본다. 이제 `textchunk`가 그렇다. 저장하면 표준 라이브러리, 외부 패키지, 우리 패키지가 빈 줄로 나뉜다.

### 8.2.4 패키지의 `pyproject.toml`

이제 이 프로젝트의 `pyproject.toml`을 쓴다. 8.1에서 본 표들이 모두 모인다.

**먼저 배포 이름을 정한다.** PyPI와 TestPyPI에서 이름은 **먼저 올린 사람의 것**이다. `textchunk`라는 이름은 누군가 이미 쓰고 있을 수 있고, 이 교재를 따라 하는 모든 사람이 같은 이름을 쓸 수도 없다. 그래서 배포 이름은 `textchunk-` 뒤에 **자기 GitHub 아이디**를 붙여 만든다. 이 교재에서는 `textchunk-gildong`으로 쓴다. `gildong`이 나오는 곳은 모두 자기 아이디로 바꾼다. `import` 이름은 그대로 `textchunk`다(8.1.4).

`pyproject.toml`

```toml
[build-system]
requires = ["hatchling>=1.27"]
build-backend = "hatchling.build"

[project]
name = "textchunk-gildong"
dynamic = ["version"]
description = "긴 글을 LLM에 보낼 조각으로 나누는 명령행 도구"
readme = "README.md"
requires-python = ">=3.12"
license = "MIT"
license-files = ["LICENSE"]
authors = [{ name = "홍길동", email = "gildong@example.com" }]
classifiers = [
    "Programming Language :: Python :: 3",
    "Operating System :: OS Independent",
]
dependencies = [
    "pydantic>=2.9,<3",
]

[dependency-groups]
dev = [
    "pytest>=9",
    "pytest-cov>=7",
    "mypy>=2",
    "ruff>=0.17",
]

[tool.hatch.version]
path = "src/textchunk/__init__.py"

[tool.hatch.build.targets.wheel]
packages = ["src/textchunk"]

[tool.pytest.ini_options]
testpaths = ["tests"]
addopts = ["--import-mode=importlib"]

[tool.mypy]
strict = true
files = ["src", "tests"]

[tool.ruff.lint]
extend-select = ["E711", "E712", "I", "UP"]
```

8.1에서 보지 못한 것만 설명한다.

- `dynamic = ["version"]` — 버전을 여기에 직접 적지 않고 **빌드할 때 알아내겠다**는 뜻이다. 어디서 알아낼지는 `[tool.hatch.version]`의 `path`가 정한다. hatchling은 그 파일에서 `__version__ = "…"`를 찾아 읽는다. 버전을 `__init__.py` 한 곳에만 적어 두면 코드에서 `textchunk.__version__`으로 쓸 수 있고, 패키지 정보에도 같은 값이 들어간다.
- `license = "MIT"`, `license-files = ["LICENSE"]` — 라이선스를 정해진 이름(SPDX 식별자)으로 적고, 전문 파일을 패키지에 함께 넣는다.
- `classifiers` — PyPI에서 검색과 분류에 쓰는 정해진 문구다. PyPI 사이트의 "Classifiers" 페이지에 목록이 있다. 없어도 올라가지만 적어 두는 것이 관례다.
- `dependencies` — 이 패키지는 8.3에서 출력의 한 줄을 Pydantic 모델로 만든다. 그래서 Pydantic 2.9 이상, 3 미만이 필요하다. 범위를 이렇게 정한 이유는 8.5.3에서 본다.
- `[tool.hatch.build.targets.wheel]`의 `packages` — 휠에 넣을 패키지 폴더다. hatchling은 배포 이름과 같은 이름의 폴더를 알아서 찾는데, 배포 이름(`textchunk-gildong`)과 폴더 이름(`textchunk`)이 다르면 찾지 못한다. 그래서 직접 알려 준다. 빼먹으면 어떻게 되는지는 8.4.4에서 본다.
- `[tool.pytest.ini_options]` — `testpaths`는 `pytest`를 인자 없이 실행했을 때 테스트를 찾을 폴더다. `--import-mode=importlib`는 8.2.5에서 설명한다.
- `[tool.mypy]`의 `files` — `mypy`를 인자 없이 실행했을 때 검사할 폴더다. 이제 `mypy` 한 단어로 패키지와 테스트를 모두 `--strict`로 검사한다.
- `[tool.ruff.lint]` — 실습 저장소보다 규칙을 둘 더 켰다. `I`는 `import` 정렬(VS Code가 저장할 때 하던 일을 명령행 검사에도 넣는다), `UP`는 `requires-python`보다 오래된 파이썬을 위한 옛 문법(예: `Optional[int]` 대신 `int | None`)을 찾는다. 새로 시작하는 프로젝트는 처음부터 규칙을 엄격하게 켜기 쉽다. 실습 저장소처럼 코드가 쌓인 뒤에 켜면 고칠 곳이 한꺼번에 쏟아진다.

- `dependencies`에 Pydantic을 적는 것을 잊었다. 개발하는 가상환경에는 이미 있으니 테스트는 통과하고, 새 가상환경에 설치한 사람만 `ModuleNotFoundError`를 받는다.

`src` 레이아웃은 "설치하지 않으면 `import`할 수 없게" 만들어서, 테스트가 언제나 **설치 과정을 거친 패키지**를 시험하게 한다. 다만 편집 가능 설치는 그 설치 과정을 거치되 파일은 복사하지 않는 절충이라, 위의 두 실수를 모두 잡지는 못한다. 템플릿은 여전히 `src` 폴더에서 읽히고, 빠뜨린 의존성은 개발하던 가상환경에 이미 설치되어 있기 때문이다. 둘 다 8.4.5에서 **진짜 휠을 새 가상환경에 설치**해야 확인된다. `src` 레이아웃은 그 확인을 할 수 있는 바탕이다. 다시 설치하고 넘어간다.


**`--import-mode=importlib`** — 6.2.5에서 장이 다른 두 폴더에 같은 이름의 테스트 파일이 있으면 pytest가 오류를 낸다고 했다. pytest의 기본 방식(`prepend`)은 테스트 파일이 있는 폴더를 모듈 검색 경로의 맨 앞에 넣고 파일 이름을 모듈 이름으로 쓰기 때문이다. 실습 저장소의 `ch06` 테스트가 `from chunking import chunk`로 같은 폴더의 모듈을 가져올 수 있었던 것도 그 덕분이다. `importlib` 방식은 검색 경로를 건드리지 않고 테스트 파일을 직접 불러온다. 그래서 같은 이름의 테스트 파일이 있어도 괜찮고, 테스트가 `tests` 폴더의 파일을 **우연히** `import`하는 일도 없다. 테스트는 오직 설치된 `textchunk`만 `import`한다. pytest의 문서도 새 프로젝트에는 이 방식을 권한다. 실습 저장소에서 이 방식으로 바꾸지 않은 것은, 장마다 테스트가 같은 폴더의 모듈을 `import`하는 방식에 기대고 있기 때문이다.

### 8.2.6 패키지 안의 데이터 파일 — `importlib.resources`

LLM 프로그램에는 코드가 아닌 파일이 함께 다니는 일이 많다. 프롬프트 템플릿, 기본 설정, 작은 사전 같은 것이다. `textchunk`에 프롬프트 템플릿 두 개를 넣는다.

`src/textchunk/templates/summarize.txt`

```
다음 글을 세 문장 이내로 요약하라.

<글>
$text
</글>
```

`src/textchunk/templates/keywords.txt`

```
다음 글에서 핵심어를 다섯 개 이하로 뽑아 쉼표로 구분해 답하라.

<글>
$text
</글>
```

`$text`는 조각이 들어갈 자리다. 표준 라이브러리의 `string.Template`이 `$이름`을 값으로 바꾼다. f-문자열이나 `str.format()`의 `{}`를 쓰지 않는 것은, 템플릿이 JSON 예시처럼 `{`와 `}`를 담는 일이 많기 때문이다(6장 실습 6-7의 `build_prompt()`가 프롬프트에 JSON 스키마를 넣었다).

이 파일을 어떻게 읽을까? 먼저 떠오르는 방법은 `open("templates/summarize.txt")`인데, 이것은 **현재 폴더**를 기준으로 찾는다. `textchunk`를 설치한 사람이 어느 폴더에서 실행할지 모르므로 틀린 방법이다. `Path(__file__).parent / "templates"`처럼 모듈 파일의 위치를 기준으로 찾는 방법은 대부분 동작한다. 그러나 패키지가 늘 폴더에 펼쳐진 파일로 설치된다는 가정에 기댄다. 파이썬은 zip 파일 안에 든 패키지도 `import`할 수 있고, 그때는 `__file__`이 실제 파일을 가리키지 않는다.

표준 라이브러리의 **`importlib.resources`**는 "**패키지 안의** 파일"을, 패키지가 어떤 모양으로 설치되었든 같은 방법으로 읽게 해 준다.

`src/textchunk/prompts.py`

```python
"""패키지에 함께 담은 프롬프트 템플릿을 읽는다."""

from importlib.resources import files
from string import Template

TEMPLATES = files("textchunk") / "templates"


def available_templates() -> list[str]:
    """쓸 수 있는 템플릿의 이름(.txt를 뺀 것)을 이름 순으로 돌려준다."""
    return sorted(
        item.name.removesuffix(".txt")
        for item in TEMPLATES.iterdir()
        if item.name.endswith(".txt")
    )


def render(name: str, text: str) -> str:
    """템플릿 name의 $text 자리에 text를 넣은 프롬프트를 돌려준다. 없는 이름이면 ValueError."""
    names = available_templates()
    if name not in names:
        raise ValueError(f"없는 템플릿: {name} (쓸 수 있는 것: {', '.join(names)})")
    template = Template((TEMPLATES / f"{name}.txt").read_text(encoding="utf-8"))
    return template.substitute(text=text)
```

- `files("textchunk")` — **패키지 이름**을 받아, 그 패키지의 자리를 가리키는 객체(`Traversable`)를 돌려준다. `pathlib.Path`와 모양이 비슷하다. `/`로 하위 경로를 잇고, `iterdir()`로 안의 항목을 훑고, `.name`으로 이름을 보고, `read_text()`로 읽는다.
- `available_templates()` — `templates` 폴더의 `.txt` 파일 이름에서 확장자를 뗀 목록이다. 3장의 제너레이터 표현식을 `sorted()`에 바로 넘겼다. 템플릿 파일을 하나 더 넣으면 코드를 고치지 않아도 목록에 나타난다.
- `render()` — 없는 이름이면 쓸 수 있는 이름을 알려 주는 `ValueError`를 일으킨다. `Template.substitute()`는 템플릿 안의 `$text`만 바꾸므로, **넣는 글**에 `$`가 있어도 괜찮다.

`__init__.py`에서 두 함수를 공개한다.

## 8.3 명령행 도구 만들기

### 8.3.1 `sys.argv`에서 한 걸음 더

기초 과정 8.2.2에서 `sys.argv`로 명령행 인자를 받았고, 10장의 가계부 프로그램은 `python main.py samples/2026-10.csv`처럼 파일 이름 하나를 받았다. 같은 방법으로 "파일과 조각 크기"를 받는 프로그램을 만들어 본다. 이 절의 연습 파일은 **실습 저장소**의 `ch08`에 만든다. 실습 저장소의 VS Code 창과 가상환경으로 돌아간다.

`ch08/argv_chunk.py`

```python
"""sys.argv로 인자를 받는 조각 내기 — 기초 과정 10장의 방식."""

import sys
from pathlib import Path

USAGE = "사용법: python ch08/argv_chunk.py 파일 [크기]"


def main() -> None:
    if not 2 <= len(sys.argv) <= 3:
        print(USAGE, file=sys.stderr)
        sys.exit(2)
    path = Path(sys.argv[1])
    size = int(sys.argv[2]) if len(sys.argv) == 3 else 500
    text = path.read_text(encoding="utf-8")
    for start in range(0, len(text), size):
        print(text[start : start + size])


if __name__ == "__main__":
    main()
```

`ch08/memo.txt`에 `가나다라마바사`를 넣고 실행한다.

```
python ch08/argv_chunk.py ch08/memo.txt 3
```

```
가나다
라마바
사
```

동작은 한다. 그런데 이 프로그램을 남에게 건넨다고 생각해 보자.

- `python ch08/argv_chunk.py ch08/memo.txt 셋`처럼 숫자가 아닌 크기를 주면 `ValueError`의 트레이스백이 그대로 쏟아진다.
- 사용하는 사람은 `--size 3`처럼 **이름을 붙여** 주고 싶어 한다. 그렇게 주면 인자가 셋이 되어 사용법만 출력된다. 인자의 순서도 바꿀 수 없다.
- `--help`를 주면 도움말 대신 `--help`라는 파일을 읽으려 한다.
- 옵션을 하나 더할 때마다 `len(sys.argv)`를 세는 `if`가 늘어난다. 겹침(`--overlap`), 출력 파일(`--output`)까지 더하면 인자를 해석하는 코드가 일하는 코드보다 길어진다.

인자를 해석하는 일은 어느 프로그램에서나 같다. 그래서 표준 라이브러리에 **`argparse`**가 있다. "이런 인자를 받는다"를 적어 두면, 해석, 타입 변환, 오류 메시지, 도움말을 모두 알아서 한다.

### 8.3.2 `argparse` 기초

`ch08/args_demo.py`

```python
"""argparse 연습 — 명령행 인자를 어떻게 읽는지 출력만 한다."""

import argparse

parser = argparse.ArgumentParser(
    prog="demo", description="argparse가 명령행 인자를 읽는 모습을 본다."
)
parser.add_argument("path", help="읽을 파일")
parser.add_argument(
    "-s", "--size", type=int, default=500, help="조각의 크기 (기본값: %(default)s)"
)
parser.add_argument("-v", "--verbose", action="store_true", help="자세히 출력한다")
parser.add_argument(
    "--model", choices=["small", "large"], default="small", help="쓸 모델"
)

args = parser.parse_args()
print(args)
print(args.path, args.size, args.verbose, args.model)
```

순서는 세 단계다. `ArgumentParser`를 만들고, `add_argument()`로 받을 인자를 하나씩 적고, `parse_args()`로 `sys.argv`를 해석한다. 여러 모양으로 실행해 본다.

```
python ch08/args_demo.py ch08/memo.txt
python ch08/args_demo.py ch08/memo.txt --size 3 -v --model large
python ch08/args_demo.py -s3 --model=large ch08/memo.txt
```

```
Namespace(path='ch08/memo.txt', size=500, verbose=False, model='small')
ch08/memo.txt 500 False small
Namespace(path='ch08/memo.txt', size=3, verbose=True, model='large')
ch08/memo.txt 3 True large
Namespace(path='ch08/memo.txt', size=3, verbose=False, model='large')
ch08/memo.txt 3 False large
```

- `parse_args()`는 **`Namespace`** 객체를 돌려준다. 인자 하나가 속성 하나다. 속성 이름은 `--size`에서 `-`를 뗀 `size`다. `--max-tokens`처럼 중간에 `-`가 있으면 `max_tokens`가 된다.
- `size=3` — 명령행의 글자 `"3"`이 `type=int` 덕분에 정수 `3`이 되었다.
- `verbose=False` — `action="store_true"`는 값을 받지 않는 **스위치**다. 주면 `True`, 안 주면 `False`다.
- 세 번째 줄처럼 `-s3`, `--model=large`로 붙여 써도 되고, 위치 인자를 옵션 뒤에 두어도 된다. 사람들이 명령행 도구에 기대하는 쓰임새를 `argparse`가 모두 받아 준다.

`-h`(또는 `--help`)를 주면 도움말이 나온다. 우리는 도움말을 쓰지 않았다. `add_argument()`의 `help`를 모아 `argparse`가 만들었다.

```
python ch08/args_demo.py -h
```

```
usage: demo [-h] [-s SIZE] [-v] [--model {small,large}] path

argparse가 명령행 인자를 읽는 모습을 본다.

positional arguments:
  path                  읽을 파일

options:
  -h, --help            show this help message and exit
  -s, --size SIZE       조각의 크기 (기본값: 500)
  -v, --verbose         자세히 출력한다
  --model {small,large}
                        쓸 모델
```

- 첫 줄 `usage:`는 사용법의 요약이다. 대괄호 `[...]`는 **주지 않아도 되는** 것이다. `path`에는 대괄호가 없다. 꼭 주어야 한다.
- `positional arguments`는 **위치 인자**, `options`는 **옵션**이다. 이름이 `-`로 시작하면 옵션, 아니면 위치 인자다.
- `(기본값: 500)` — `help` 안의 `%(default)s`가 기본값으로 바뀌었다. 기본값을 바꾸면 도움말도 저절로 바뀐다. `%`가 특별한 뜻을 가지므로, 도움말에 `%` 글자를 그대로 쓰려면 `%%`로 쓴다.
- `-h`와 `show this help message and exit`는 `argparse`가 넣는 것이라 영어다.

트레이스백 대신 **사용법과 무엇이 틀렸는지** 한 줄이 나온다. 모두 표준 오류로 출력되고, 종료 코드는 **2**다. 기초 과정 10장의 가계부 프로그램이 인자가 틀렸을 때 `sys.exit(2)`를 쓴 것과 같은 약속이다(기초 과정 10.2.7). `--help`는 종료 코드 0으로 끝난다.

> **줄여 쓴 옵션**
> `--verbose`를 `--verb`처럼 앞부분만 주어도 다른 옵션과 헷갈리지 않으면 받아들인다. 편하지만, 나중에 `--verbatim` 같은 옵션이 생기면 `--verb`가 갑자기 오류가 된다. 스크립트나 문서에는 **언제나 옵션의 전체 이름**을 쓴다. 이 기능을 끄려면 `ArgumentParser(allow_abbrev=False)`로 만든다.

`add_argument()`에 자주 쓰는 인자를 정리한다.

| 인자 | 하는 일 | 예 |
|---|---|---|
| `"이름"` | 위치 인자 | `"path"` |
| `"-짧은", "--긴"` | 옵션. 짧은 이름은 한 글자 | `"-s", "--size"` |
| `type=` | 글자를 바꿀 함수. 바꾸지 못하면(`ValueError`) 오류 메시지 | `int`, `float`, `Path` |
| `default=` | 주지 않았을 때의 값. 없으면 `None` | `500` |
| `choices=` | 고를 수 있는 값 | `["small", "large"]` |
| `action="store_true"` | 값 없는 스위치 | `--verbose` |
| `nargs=` | 값의 개수. `"+"`는 하나 이상, `"*"`는 0개 이상, `"?"`는 0개나 1개 | `nargs="+"` |
| `required=True` | 옵션인데 꼭 주어야 할 때 | |
| `metavar=` | 도움말에서 값 자리에 보일 이름 | `metavar="FILE"` |
| `help=` | 도움말 | `"읽을 파일"` |

`type=Path`가 눈에 띈다. `type`에는 **글자 하나를 받아 값을 돌려주는 함수라면 무엇이든** 넘길 수 있다. 4.4에서 본 "함수도 값"이다. `int`, `float`, `Path`가 모두 그런 함수(클래스)다. 5.5.3의 `Model`(`StrEnum`)도 된다. `type=Model`로 주면 `"small"`이 `Model.SMALL`이 되고, `choices=list(Model)`을 함께 주면 도움말에 쓸 수 있는 모델이 나온다. 5.5.3에서 "명령행 도구의 도움말에 '쓸 수 있는 모델: small, large'를 보여 주기도 쉽다(8장)"고 한 것이 이것이다.

확인했으면 `args_demo.py`와 `argv_chunk.py`, `memo.txt`는 남겨 둔다. 실습 8-3에서 다시 쓴다.

### 8.3.3 `textchunk`의 명령

이제 **패키지 저장소**로 돌아간다. `textchunk`의 명령은 다음처럼 쓰게 만든다.

```
textchunk 파일... [-s 크기] [--overlap 겹침] [-t 템플릿] [-o 출력 파일]
```

글 파일을 하나 이상 받아 조각으로 나누고, 조각마다 `{"file": 파일 이름, "chunk": 번호, "text": 조각}`을 한 줄의 JSON으로 출력한다. 6장부터 써 온 JSONL이다(6.4.4). `-t`를 주면 조각을 템플릿의 프롬프트로 감싼다. 결과를 그대로 다음 프로그램(9장의 요약기 같은)의 입력으로 쓸 수 있다.

`src/textchunk/cli.py`

```python
"""textchunk 명령 — 글 파일을 조각으로 나눠 한 줄에 하나씩 JSON으로 출력한다."""

import argparse
import sys
from collections.abc import Sequence
from pathlib import Path

from pydantic import BaseModel

from textchunk import __version__
from textchunk.chunking import chunk
from textchunk.prompts import available_templates, render


class Record(BaseModel):
    """출력의 한 줄."""

    file: str
    chunk: int
    text: str


def build_parser() -> argparse.ArgumentParser:
    parser = argparse.ArgumentParser(
        prog="textchunk",
        description="글 파일을 LLM에 보낼 조각으로 나눠 한 줄에 하나씩 JSON으로 출력한다.",
    )
    parser.add_argument(
        "files", nargs="+", type=Path, metavar="FILE", help="나눌 글 파일(UTF-8)"
    )
    parser.add_argument(
        "-s",
        "--size",
        type=int,
        default=500,
        help="조각 하나의 최대 글자 수 (기본값: %(default)s)",
    )
    parser.add_argument(
        "--overlap",
        type=int,
        default=0,
        help="앞 조각과 겹칠 글자 수 (기본값: %(default)s)",
    )
    parser.add_argument(
        "-t",
        "--template",
        choices=available_templates(),
        help="조각을 이 템플릿의 프롬프트로 감싼다",
    )
    parser.add_argument(
        "-o", "--output", type=Path, help="결과를 저장할 파일. 없으면 화면에 출력한다"
    )
    parser.add_argument(
        "--version", action="version", version=f"%(prog)s {__version__}"
    )
    return parser


def main(argv: Sequence[str] | None = None) -> int:
    parser = build_parser()
    args = parser.parse_args(argv)
    if not 0 <= args.overlap < args.size:
        parser.error("--overlap은 0 이상, --size 미만이어야 한다")

    lines: list[str] = []
    for path in args.files:
        try:
            text = path.read_text(encoding="utf-8")
        except OSError as e:
            print(f"textchunk: {path}: 읽을 수 없다 ({e.strerror})", file=sys.stderr)
            return 1
        for number, piece in enumerate(chunk(text, args.size, args.overlap), start=1):
            if args.template:
                piece = render(args.template, piece)
            record = Record(file=path.name, chunk=number, text=piece)
            lines.append(record.model_dump_json())

    output = "".join(f"{line}\n" for line in lines)
    if args.output:
        args.output.write_text(output, encoding="utf-8")
        print(f"조각 {len(lines)}개를 {args.output}에 저장했다", file=sys.stderr)
    else:
        sys.stdout.write(output)
    return 0
```

**`build_parser()`를 따로 둔다.** 인자를 **정의하는** 일과 **해석해서 일하는** 일을 나눴다. 파서만 따로 만들 수 있으면 테스트에서 파서만 시험하거나, 도움말을 문서로 뽑는 일이 쉬워진다. 기초 과정 10.1.5의 "역할을 나눈다"다.

**`choices=available_templates()`** — 8.2.6에서 만든 함수로 고를 수 있는 템플릿을 정한다. 템플릿 파일을 더하면 명령의 선택지와 도움말이 함께 늘어난다.

**`action="version"`** — `--version`을 주면 `version=`의 글자를 출력하고 종료 코드 0으로 끝난다. `%(prog)s`는 프로그램 이름(`textchunk`)으로 바뀐다. 버전은 `__init__.py`의 `__version__`에서 가져온다. 8.2.4에서 버전을 한 곳에만 적은 덕분이다.

**`main(argv: Sequence[str] | None = None) -> int`** — 두 가지 약속이 들어 있다.

- `argv`를 받는다. `parse_args(None)`은 `sys.argv[1:]`을 해석하고, `parse_args(["a.txt", "-s", "4"])`처럼 리스트를 주면 그 리스트를 해석한다. 그래서 테스트에서는 터미널 없이 `main(["a.txt", "-s", "4"])`로 명령을 흉내 낼 수 있다(8.3.5). 6.5.2에서 시계와 난수를 매개변수로 받은 의존성 주입과 같은 생각이다.
- **종료 코드를 돌려준다.** `main()` 안에서 `sys.exit()`를 부르지 않고 `0`이나 `1`을 `return`한다. 프로그램을 끝내는 일은 `main()`을 부른 쪽(8.3.4)이 한다. 함수가 프로그램을 끝내 버리면 테스트에서 다루기 어렵다.

**`parser.error()`** — `argparse`가 스스로 검사할 수 없는 규칙(`--overlap`은 `--size`보다 작아야 한다)은 `parse_args()` 뒤에 검사하고, 틀리면 `parser.error("메시지")`를 부른다. 8.3.2에서 본 것과 같은 모양(사용법과 `textchunk: error: 메시지`)으로 출력하고 종료 코드 2로 끝낸다. `chunk()`가 `ValueError`를 일으키게 두지 않는 이유는, 사용하는 사람에게 트레이스백이 아니라 **어느 옵션을 고치면 되는지**를 보여 주기 위해서다.

**표준 출력과 표준 오류를 나눈다** — 결과(JSONL)는 표준 출력으로, 안내와 오류("조각 몇 개를 저장했다", "읽을 수 없다")는 표준 오류로 보낸다(기초 과정 8.2.2). `textchunk a.txt > out.jsonl`처럼 결과를 파일로 돌려도 안내 문구가 결과에 섞이지 않는다. 다른 프로그램이 결과를 읽어 갈 수 있는 명령행 도구의 기본 예의다.

**종료 코드** — 이 명령이 쓰는 종료 코드를 정리한다. 6.6.5의 `check.py`가 그랬듯, 다른 프로그램은 이 숫자로 성공과 실패를 가린다.

| 코드 | 뜻 | 누가 |
|---|---|---|
| 0 | 성공. `--help`, `--version`도 0 | `return 0`, `argparse` |
| 1 | 실행 중의 실패. 파일을 읽을 수 없다 | `return 1` |
| 2 | 사용법이 틀렸다 | `argparse`, `parser.error()` |

**`Record`와 `model_dump_json()`** — 출력의 한 줄을 Pydantic 모델로 정했다. 한 줄의 모양이 코드의 한 곳에 적혀 있고, 이 출력을 읽는 쪽(9장)은 같은 모델의 `model_validate_json()`으로 검증할 수 있다(5.6). `model_dump_json()`은 한글을 `가`처럼 바꾸지 않고 그대로 쓰며, 빈칸 없이 촘촘하게 출력한다. 이 모델 때문에 `pyproject.toml`의 `dependencies`에 Pydantic을 적었다.

> **Windows에서 결과를 파일로 돌릴 때**
> Windows의 PowerShell에서 `textchunk a.txt > out.jsonl`로 결과를 파일로 돌리면, 환경에 따라 한글이 UTF-8이 아닌 인코딩으로 저장될 수 있다. `-o out.jsonl` 옵션은 `write_text(..., encoding="utf-8")`로 쓰므로 어느 운영체제에서나 UTF-8이다. 결과를 파일로 저장할 때는 `-o`를 쓴다.

### 8.3.4 `[project.scripts]` — 설치하면 실행되는 명령

`main()`을 터미널의 명령으로 만든다. `pyproject.toml`의 `[project]` 표 바로 아래에 더한다.


`sys.exit(main())` — `main()`이 돌려준 종료 코드로 프로그램을 끝낸다. 8.3.3에서 "프로그램을 끝내는 일은 `main()`을 부른 쪽이 한다"고 한 그 쪽이 여기다. 첫 줄은 **이 가상환경의 파이썬**을 가리킨다. 그래서 가상환경을 활성화하지 않아도 이 파일의 경로로 직접 실행하면 그 가상환경에서 돈다. (Windows에서는 `textchunk.exe`라는 작은 실행 파일이 같은 일을 한다.)

```
  -s, --size SIZE       조각 하나의 최대 글자 수 (기본값: 500)
  --overlap OVERLAP     앞 조각과 겹칠 글자 수 (기본값: 0)
  -t, --template {keywords,summarize}
                        조각을 이 템플릿의 프롬프트로 감싼다
  -o, --output OUTPUT   결과를 저장할 파일. 없으면 화면에 출력한다
  --version             show program's version number and exit
```

- `FILE [FILE ...]` — `nargs="+"`이므로 하나 이상이다. `metavar="FILE"`이 도움말과 사용법의 이름을 정했다. `metavar`가 없으면 `files`로 보인다.
- `-t {keywords,summarize}` — 템플릿 폴더에서 읽은 선택지가 도움말에 그대로 보인다.

틀리게 써 본다.

```
textchunk a.txt -s 4 --overlap 9
textchunk 없는파일.txt
```

```
usage: textchunk [-h] [-s SIZE] [--overlap OVERLAP] [-t {keywords,summarize}]
                 [-o OUTPUT] [--version]
                 FILE [FILE ...]
textchunk: error: --overlap은 0 이상, --size 미만이어야 한다
textchunk: 없는파일.txt: 읽을 수 없다 (No such file or directory)
```

종료 코드는 각각 2와 1이다. macOS에서는 명령 바로 뒤에 `echo $?`, PowerShell에서는 `$LASTEXITCODE`로 확인한다.

**`python -m textchunk`로도 실행하기** — 기초 과정 8.3.4에서 `python -m 패키지.모듈`로 패키지 안의 모듈을 실행했다. 패키지 이름만 주어 `python -m textchunk`로 실행하면 파이썬은 그 패키지의 **`__main__.py`**를 찾아 실행한다. 이 파일을 만들어 둔다.

`src/textchunk/__main__.py`

```python
"""python -m textchunk로 실행할 때의 입구."""

import sys

from textchunk.cli import main

if __name__ == "__main__":
    sys.exit(main())
```

```
python -m textchunk a.txt -s 4
```

결과는 `textchunk a.txt -s 4`와 같다. `python -m pip`, `python -m pytest`, `python -m mypy`가 모두 이렇게 동작한다. 기초 과정 9.1.6에서 `pip` 대신 `python -m pip`을 쓰라고 한 이유와 같이, `python -m textchunk`는 "**지금 이 파이썬**에 설치된 `textchunk`"를 확실히 실행한다. 6.6.5의 `check.py`가 `[sys.executable, "-m", *command]`로 도구를 실행한 것도 이 때문이다. 확인했으면 `a.txt`를 지운다.

### 8.3.5 명령행 도구를 테스트하기

`main()`이 인자 리스트를 받고 종료 코드를 돌려주므로, 테스트는 터미널 없이 함수를 부르기만 하면 된다.

`tests/test_cli.py`

```python
"""cli의 테스트 — main()에 인자 리스트를 넘겨 명령을 흉내 낸다."""

import json
from pathlib import Path

import pytest

from textchunk import __version__
from textchunk.cli import main


@pytest.fixture
def doc(tmp_path: Path) -> Path:
    path = tmp_path / "a.txt"
    path.write_text("가나다라마바", encoding="utf-8")
    return path


def test_prints_jsonl(doc: Path, capsys: pytest.CaptureFixture[str]) -> None:
    assert main([str(doc), "--size", "4"]) == 0
    lines = capsys.readouterr().out.splitlines()
    assert [json.loads(line) for line in lines] == [
        {"file": "a.txt", "chunk": 1, "text": "가나다라"},
        {"file": "a.txt", "chunk": 2, "text": "마바"},
    ]


def test_wraps_with_template(doc: Path, capsys: pytest.CaptureFixture[str]) -> None:
    assert main([str(doc), "-s", "10", "-t", "summarize"]) == 0
    record = json.loads(capsys.readouterr().out)
    assert "<글>\n가나다라마바\n</글>" in record["text"]


def test_writes_output_file(
    doc: Path, tmp_path: Path, capsys: pytest.CaptureFixture[str]
) -> None:
    out = tmp_path / "out.jsonl"
    assert main([str(doc), "-s", "4", "-o", str(out)]) == 0
    assert len(out.read_text(encoding="utf-8").splitlines()) == 2
    assert capsys.readouterr().err == f"조각 2개를 {out}에 저장했다\n"


def test_rejects_bad_overlap(doc: Path, capsys: pytest.CaptureFixture[str]) -> None:
    with pytest.raises(SystemExit) as exc_info:
        main([str(doc), "--size", "4", "--overlap", "4"])
    assert exc_info.value.code == 2
    assert "--overlap은 0 이상" in capsys.readouterr().err


def test_missing_file(tmp_path: Path, capsys: pytest.CaptureFixture[str]) -> None:
    assert main([str(tmp_path / "없음.txt")]) == 1
    assert "읽을 수 없다" in capsys.readouterr().err


def test_version(capsys: pytest.CaptureFixture[str]) -> None:
    with pytest.raises(SystemExit) as exc_info:
        main(["--version"])
    assert exc_info.value.code == 0
    assert capsys.readouterr().out == f"textchunk {__version__}\n"
```

- **`doc` 픽스처** — 6.4.4의 `tmp_path`에 시험 파일을 만든다. 출력의 `"file"`이 `"a.txt"`인 것은 `cli.py`가 경로 전체가 아니라 `path.name`을 쓰기 때문이다. 임시 폴더의 긴 경로가 결과에 들어가지 않는다.
- **`capsys`** — 6.4.6에서 본 출력 확인 픽스처다. `readouterr()`의 `.out`이 표준 출력, `.err`가 표준 오류다. 결과와 안내가 **각자의 자리로** 나가는지 확인한다.
- **`json.loads()`로 비교한다** — 출력 글자를 그대로 비교하지 않고 JSON으로 읽어서 딕셔너리로 비교한다. `model_dump_json()`의 빈칸 넣는 방식이 바뀌어도 테스트가 깨지지 않는다. 테스트는 "무엇이 중요한가"를 확인해야지 "우연히 그렇게 된 것"을 확인하지 않는다(6.3.6).
- **`pytest.raises(SystemExit)`** — `argparse`는 사용법이 틀리거나 `--version`을 받으면 `sys.exit()`를 부른다. `sys.exit()`는 사실 `SystemExit` 예외를 일으키는 함수다. 테스트에서 이 예외를 잡지 않으면 pytest가 실패로 처리한다. 잡은 예외의 `.code`가 종료 코드다. `exc_info.value`는 6.3.3에서 본 대로 잡은 예외 객체다.

```
pytest
```

```
...
collected 18 items

tests/test_chunking.py ........                                          [ 44%]
tests/test_cli.py ......                                                 [ 77%]
tests/test_prompts.py ....                                               [100%]

```

`ruff check .`, `ruff format --check .`, `mypy`도 통과하는지 확인한다.

> **`argparse` 말고 다른 것**
> 남의 코드에서 명령행 도구를 만드는 라이브러리로 **Click**이나 **Typer**를 자주 보게 된다. Click은 데코레이터로 옵션을 붙이고(`@click.option("--size", default=500)`), Typer는 **타입 힌트**를 읽어 옵션을 만든다(`def main(size: int = 500):`). 4장의 데코레이터, 5장의 타입 힌트가 여기서도 쓰인다. FastAPI를 만든 사람이 만든 Typer는 FastAPI와 생각이 같다. 하는 일은 `argparse`와 같으므로, `argparse`를 알면 어느 것이든 읽을 수 있다. 이 교재가 `argparse`를 쓰는 것은 표준 라이브러리라서 의존성이 늘지 않기 때문이다.

### 8.4.1 `python -m build`

지금까지는 편집 가능 설치로 **이 폴더에서** 패키지를 썼다. 다른 사람이 설치할 수 있게 하려면 패키지를 **파일 하나로** 만들어야 한다. 이 일을 빌드라고 했다(8.1.6). 패키지 저장소에서, 빌드 도구 **build**와 8.6에서 쓸 **twine**을 설치한다.

| | 소스 배포판(sdist) | 휠(wheel) |
|---|---|---|
| 파일 | `.tar.gz` | `.whl`(실은 zip 파일) |
| 들어 있는 것 | 프로젝트의 소스. `pyproject.toml`, 테스트까지 | 설치될 파일 그대로. 패키지 폴더와 정보 폴더 |
| 설치할 때 | 받은 컴퓨터에서 **빌드한 뒤** 설치한다 | 압축을 풀어 **복사만** 한다 |
| 쓰임 | 휠이 없는 환경에서 빌드하기, 리눅스 배포판처럼 소스에서 다시 만드는 곳 | 보통의 설치. 빠르고 빌드 도구가 필요 없다 |

pip는 휠이 있으면 휠을 고른다. 우리 패키지처럼 파이썬 파일만 있으면 둘의 차이가 작지만, C나 Rust로 만든 확장 모듈이 든 패키지(Pydantic의 `pydantic-core`)는 소스 배포판을 설치하려면 그 언어의 컴파일러가 있어야 한다. 그래서 그런 패키지는 운영체제와 파이썬 버전마다 휠을 따로 빌드해 올린다.

`[project.scripts]`가 여기에 기록되었다. pip는 휠을 설치할 때 이 파일을 읽고 8.3.4에서 본 실행 파일을 만든다. `RECORD`에는 휠 안의 파일마다 해시가 적혀 있어서, 설치할 때 파일이 바뀌지 않았는지 확인하고, 지울 때(`pip uninstall`) 무엇을 지울지 안다.

**휠의 파일 이름** — `textchunk_gildong-0.1.0-py3-none-any.whl`의 이름에도 정보가 들어 있다.

| 부분 | 뜻 |
|---|---|
| `textchunk_gildong` | 배포 이름. `-`가 `_`로 바뀌었다(아래 상자) |
| `0.1.0` | 버전 |
| `py3` | 파이썬 3이면 된다 |
| `none` | 특정 파이썬 구현의 바이너리 규약(ABI)에 기대지 않는다 |
| `any` | 운영체제와 CPU를 가리지 않는다 |

`py3-none-any`는 "파이썬 3이 있는 어디서든"이라는 뜻이다. 파이썬 파일만 든 패키지는 이렇게 휠 하나로 모든 곳을 감당한다. `pydantic-core`의 휠 이름에는 `cp313-cp313-macosx_11_0_arm64`처럼 파이썬 버전과 운영체제, CPU가 들어 있다. pip는 이 이름을 보고 내 컴퓨터에 맞는 휠을 고른다.

> **이름의 정규화**
> PyPI는 배포 이름을 비교할 때 대소문자를 가리지 않고, `-`, `_`, `.`을 같은 것으로 본다. `textchunk-gildong`, `textchunk_gildong`, `TextChunk.Gildong`은 모두 같은 패키지다. 그래서 `pip install textchunk_gildong`으로도 설치된다. 파일 이름에는 `-`가 이름과 버전을 가르는 구분자로 쓰이므로, 이름 안의 `-`는 `_`로 바꿔 적는다.

`.vscode`는 해롭지는 않지만 받는 사람에게 쓸모가 없다. 소스 배포판에서 빼려면 `pyproject.toml`에 다음 표를 더한다.

```toml
[tool.hatch.build.targets.sdist]
exclude = [".vscode"]
```

다시 빌드해서 목록에서 `.vscode`가 사라졌는지 확인한다. 이 교재의 이후 출력은 이 표를 더한 것을 기준으로 한다.

## 8.5 버전과 의존성 범위

### 8.5.1 유의적 버전

`textchunk`의 버전은 `0.1.0`이다. 점으로 나눈 세 숫자에는 약속된 뜻이 있다. 개발 도구 7.6.3에서 Git 태그의 이름을 붙이며 본 **유의적 버전**(Semantic Versioning, SemVer, 시맨틱 버저닝이라고도 한다)이다. 그때 "중급 과정 8장에서 파이썬 패키지의 버전과 태그를 맞추는 방법을 다룬다"고 했다. 여기서는 패키지를 **쓰는 사람의 눈**으로 다시 본다.

```
MAJOR.MINOR.PATCH
  1  .  4  .  2
```

| 올리는 숫자 | 언제 | 예 |
|---|---|---|
| **PATCH** | 동작은 그대로, 버그만 고쳤다 | `--size 0`의 오류 메시지를 고쳤다 |
| **MINOR** | 기능을 **더했다**. 예전 방식으로 쓰던 코드는 그대로 동작한다 | `--by-paragraph` 옵션을 더했다 |
| **MAJOR** | 예전 방식으로 쓰던 코드가 **깨질 수 있는** 변경 | `chunk()`의 매개변수 이름을 바꿨다, 출력의 `"text"` 키를 `"content"`로 바꿨다 |

앞자리를 올리면 뒷자리는 0으로 되돌린다. `1.4.2`에서 기능을 더하면 `1.5.0`, 그다음 깨지는 변경을 하면 `2.0.0`이다. 이 약속 덕분에 쓰는 사람은 버전 번호만 보고 "올려도 안전한가"를 짐작할 수 있다. Pydantic 1에서 2로 넘어갈 때 많은 코드를 고쳐야 했던 것이 MAJOR의 예다. 5.6에서 쓴 `model_validate()`, `model_dump_json()`은 Pydantic 2에서 새로 생긴 이름이고, Pydantic 1에서는 `parse_obj()`, `json()`이었다.

**`0.`으로 시작하는 버전**은 "아직 만드는 중"이라는 뜻이다. SemVer는 `0.y.z`에서는 무엇이든 바뀔 수 있다고 정한다. 그래서 `0.x`의 라이브러리는 관례상 MINOR를 올리면서 깨지는 변경을 하기도 한다. httpx가 아직 `0.28`이고, 0.27에서 0.28로 올라가며 몇몇 옛 인자를 지웠다. 공개한 기능을 오래 지키겠다고 약속할 수 있을 때 `1.0.0`을 낸다. `textchunk`는 `0.1.0`에서 시작한다.

**정식 버전이 나오기 전의 버전**도 있다. 파이썬의 버전 규칙(PEP 440)은 다음 표기를 쓴다.

| 표기 | 뜻 | 순서 |
|---|---|---|
| `1.0.0a1` | 알파(alpha). 기능이 아직 다 들어가지 않았다 | 가장 먼저 |
| `1.0.0b1` | 베타(beta). 기능은 다 있고 시험하는 중 | |
| `1.0.0rc1` | 출시 후보(release candidate) | |
| `1.0.0` | 정식 | |
| `1.0.0.post1` | 정식 뒤의 작은 수정(문서 등) | 가장 나중 |

`pip install pydantic`은 이런 앞선 버전을 고르지 않는다. 정식 버전만 고른다. 앞선 버전을 시험하려면 `pip install --pre pydantic`이나 `pip install pydantic==3.0.0b1`처럼 분명히 요청해야 한다.

> **모든 패키지가 SemVer를 따르지는 않는다**
> `pip 26.3`은 "2026년의 세 번째 릴리스"이고, `certifi 2026.10.23`은 날짜다. 이런 방식을 **달력 버저닝**(CalVer)이라고 한다. 버전 번호만 보고 깨지는 변경인지 알 수 없으므로, 이런 패키지는 **변경 기록**(changelog, release notes)을 읽어야 한다. 어떤 방식을 쓰든 패키지의 저장소나 문서에 변경 기록이 있다. 의존성을 올리기 전에 읽는 습관을 들인다.

### 8.5.2 버전을 한 곳에

버전 번호는 여러 곳에서 쓰인다. 패키지의 정보(`METADATA`), `textchunk --version`의 출력, 휠의 파일 이름, 8.5.5의 Git 태그. 이것들이 서로 다르면 곤란하다. 그래서 8.2.4에서 버전을 `src/textchunk/__init__.py`의 `__version__` **한 곳에만** 적고, `pyproject.toml`은 `dynamic = ["version"]`으로 그것을 읽게 했다. 버전을 올릴 때는 이 한 줄만 고친다.

다른 방법도 흔하다. `pyproject.toml`의 `[project]`에 `version = "0.1.0"`을 직접 적고, 코드에서는 **설치된 패키지의 정보**를 읽는 것이다.

```python
>>> from importlib.metadata import version
>>> version("pydantic")
'2.14.3'
>>> version("textchunk-gildong")
'0.1.0'
```

`importlib.metadata.version()`은 **배포 이름**을 받아 `.dist-info`(8.2.5)에 기록된 버전을 돌려준다. 다른 패키지의 버전을 코드에서 확인할 때도 쓴다. 이 방법에서는 버전을 `pyproject.toml`에만 적는다. 대신 코드에 배포 이름(`"textchunk-gildong"`)을 적어야 하고, 설치하지 않은 상태에서는 동작하지 않는다. 8.7의 `uv init`이 만드는 프로젝트는 이 방식이다. 남의 코드에서 둘 중 어느 쪽을 보든 "버전은 한 곳에"라는 생각은 같다.

### 8.5.3 의존성 범위 지정

`textchunk`의 의존성은 `"pydantic>=2.9,<3"`이다. 범위를 적는 연산자를 정리한다.

| 표기 | 뜻 | `pydantic`의 예에서 받아들이는 버전 |
|---|---|---|
| `>=2.9` | 2.9 이상 | 2.9.0, 2.14.3, 3.0.0, … |
| `<3` | 3 미만 | …, 2.14.3 |
| `>=2.9,<3` | 쉼표는 "그리고" | 2.9.0 ~ 2.x |
| `~=2.9` | **호환 버전**. `>=2.9,==2.*`와 같다 | 2.9.0 ~ 2.x |
| `~=2.9.0` | `>=2.9.0,==2.9.*`와 같다 | 2.9.0 ~ 2.9.x |
| `==2.14.3` | 정확히 그 버전 | 2.14.3만 |
| `==2.*` | 2로 시작하는 모든 버전 | 2.0.0 ~ 2.x |
| `!=2.10.0` | 그 버전만 빼고 | |

`~=`는 처음 보면 헷갈린다. **마지막 자리만 올라갈 수 있다**고 읽는다. `~=2.9`는 `9`가 마지막 자리이므로 `2.9`, `2.10`, `2.14`…는 되고 `3.0`은 안 된다. `~=2.9.0`은 마지막 자리가 `0`이므로 `2.9.x`만 된다. 확실하지 않으면 계산해 본다. pip가 쓰는 **packaging** 라이브러리가 개발 가상환경에 이미 있다(pytest가 기대는 패키지다).

```python
>>> from packaging.specifiers import SpecifierSet
>>> versions = ["2.6.4", "2.9.0", "2.9.2", "2.14.3", "3.0.0", "3.0.0b1"]
>>> for spec in ["~=2.9", "~=2.9.0", ">=2.9,<3", "==2.*"]:
...     print(spec, [v for v in versions if v in SpecifierSet(spec)])
...
~=2.9 ['2.9.0', '2.9.2', '2.14.3']
~=2.9.0 ['2.9.0', '2.9.2']
>=2.9,<3 ['2.9.0', '2.9.2', '2.14.3']
==2.* ['2.6.4', '2.9.0', '2.9.2', '2.14.3']
```

`3.0.0b1`은 어디에도 들지 않았다. 8.5.1의 앞선 버전은 따로 요청하지 않는 한 고르지 않는다.

**너무 좁으면** — `textchunk`가 `pydantic==2.14.3`으로 못 박았다고 하자. 어떤 사람의 프로젝트가 `textchunk`와 함께, `pydantic>=2.15`가 필요한 다른 라이브러리를 쓴다. 두 약속을 동시에 지킬 수 없으므로 pip는 설치를 거부한다.

```
ERROR: Cannot install other-lib==1.0 and textchunk-gildong==0.1.0 because these package versions have conflicting dependencies.

The conflict is caused by:
    textchunk-gildong 0.1.0 depends on pydantic==2.14.3
    other-lib 1.0 depends on pydantic>=2.15
```

`textchunk`는 Pydantic 2.15에서도 잘 돌아갈 텐데, 범위를 좁게 적은 탓에 쓰는 사람이 둘 중 하나를 포기해야 한다. 라이브러리가 `==`를 쓰지 않는 이유다(8.1.7). 쓰는 사람의 가상환경에는 다른 라이브러리도 함께 살고 있다.

**너무 넓으면** — `"pydantic"`처럼 범위 없이 적으면 어떨까?

- **아래쪽이 열려 있으면** Pydantic 1이 설치된 가상환경에도 설치된다. `cli.py`의 `model_dump_json()`은 Pydantic 2에서 생긴 메서드이므로, 설치는 되는데 실행하면 `AttributeError`가 난다. 설치할 때가 아니라 **쓸 때** 터지는 것이 더 나쁘다.
- **위쪽이 열려 있으면** 언젠가 Pydantic 3이 나왔을 때, 깨지는 변경(8.5.1)에 우리 코드가 맞는지 확인하지 않은 채 설치된다.

그래서 범위는 다음 기준으로 정한다.

- **아래쪽은 실제로 시험해 본 가장 낮은 버전.** `textchunk`는 Pydantic 2.9로 테스트가 통과하는 것을 확인했다(실습 8-5에서 직접 확인한다). 쓰는 기능이 생긴 버전보다 낮게 적으면 안 된다.
- **위쪽은 다음 MAJOR 미만.** SemVer를 따르는 패키지라면 MAJOR가 바뀔 때 깨질 수 있다. 다만 위쪽 경계는 의견이 갈린다. 경계를 두면 새 MAJOR가 나왔을 때 쓰는 사람이 우리의 새 버전을 기다려야 한다. 그래서 위쪽을 열어 두는 라이브러리도 많다(8.1.4의 httpx는 `anyio`의 위쪽을 열어 두었다). 이 교재는 Pydantic이 1에서 2로 넘어갈 때 크게 바뀐 일을 보았으므로 경계를 둔다.
- **`==`는 쓰지 않는다.** 정확한 버전은 잠금 파일의 몫이다.

`requires-python = ">=3.12"`도 같은 생각이다. 3.12에서 생긴 기능(5장의 `def first[T]` 같은 제네릭 문법)을 쓰면 아래쪽을 3.12로 적어야 한다. 위쪽은 대개 열어 둔다.

### 8.5.4 잠금 파일

범위로 적은 의존성은 **설치할 때마다 다른 버전**이 될 수 있다. 오늘 설치하면 Pydantic 2.14.3이 오고, 다음 달에 설치하면 2.15.0이 올 수 있다. 라이브러리에는 그것이 맞다. 그러나 애플리케이션과 **개발 환경**에는 곤란하다. "어제까지 통과하던 테스트가 오늘 새로 만든 가상환경에서 실패한다"는 일이 생긴다. 코드는 그대로인데 함께 설치된 무언가의 버전이 바뀐 것이다.

**잠금 파일**은 "이 범위들을 풀었더니 이 버전들이 나왔다"를 **모든 패키지에 대해** 적어 둔 파일이다(8.1.7). 잠금 파일대로 설치하면 언제 어디서든 같은 버전이 설치된다.

| 잠금 파일 | 만드는 명령 | 설치하는 명령 |
|---|---|---|
| `requirements.txt` | `python -m pip freeze > requirements.txt` | `python -m pip install -r requirements.txt` |
| `uv.lock` | `uv lock`(`uv add`, `uv sync`가 알아서 갱신한다) | `uv sync` |

실습 저장소의 `requirements.txt`가 지금까지 이 일을 했다. 다만 `pip freeze`는 **지금 가상환경에 있는 것**을 적는다. 실험하느라 설치했다가 지우지 않은 패키지가 섞여 들어가고, 운영체제마다 다른 패키지가 필요한 경우를 담지 못한다. `uv.lock`은 가상환경이 아니라 `pyproject.toml`에서 출발해서 의존성을 풀고, 운영체제와 파이썬 버전마다 필요한 것을 모두 적는다(8.7.4).

라이브러리인 `textchunk`에도 잠금 파일이 쓸모가 있다. **개발 환경**을 맞추는 데다. 같이 개발하는 사람과 GitHub Actions(8.8)가 같은 버전의 pytest, mypy, ruff로 검사해야 "내 컴퓨터에서는 통과하는데"가 없다. 이때 잠금 파일은 저장소에 커밋하지만 **휠에는 들어가지 않는다.** 쓰는 사람은 여전히 `dependencies`의 범위만 받는다.

### 8.5.5 Git 태그로 버전 표시하기

PyPI에 `0.1.0`을 올렸다면, 나중에 "0.1.0의 코드는 무엇이었나"를 다시 찾을 수 있어야 한다. 버그 신고가 "0.1.0에서 이런 문제가 있다"로 오기 때문이다. 개발 도구 7.6에서 배운 Git의 **태그**(tag)로 커밋 하나에 버전 이름을 붙인다. 브랜치와 달리 움직이지 않는다.

패키지 저장소에서 지금까지의 변경을 커밋한다. 실습 8-3의 첫 커밋 뒤에 8.4.3의 `[tool.hatch.build.targets.sdist]`를 더했다.

```
git status --short
git add pyproject.toml
git commit -m "sdist에서 .vscode 빼기"
```

이 커밋이 0.1.0이다. 태그를 붙인다.

```
git tag -a v0.1.0 -m "textchunk 0.1.0"
git tag
git log --oneline --decorate -3
```

```
v0.1.0
c4e1f20 (HEAD -> main, tag: v0.1.0) sdist에서 .vscode 빼기
8b3d9a1 textchunk: src 레이아웃, 템플릿, textchunk 명령
```

- `-a` — 만든 사람, 날짜, 메시지를 함께 기록하는 **주석 태그**(annotated tag)를 만든다(개발 도구 7.6.1). 릴리스에는 주석 태그를 쓴다.
- `v0.1.0` — 태그 이름은 버전 앞에 `v`를 붙이는 것이 관례다. 태그의 `0.1.0`과 `__version__`의 `0.1.0`이 **같아야** 한다.
- `git show v0.1.0`으로 태그의 정보와 그 커밋의 변경을 볼 수 있고, `git switch --detach v0.1.0`으로 그때의 코드로 돌아가 볼 수 있다(개발 도구 6.2.7, 7.6.2). 돌아온 뒤에는 `git switch main`.

태그는 `git push`만으로는 GitHub에 올라가지 않는다. 따로 올린다(개발 도구 8.1.4).

```
git push origin v0.1.0
```

(GitHub에 올리는 것은 8.8의 선택 활동에서 한다. 저장소가 아직 GitHub에 없다면 이 명령은 건너뛴다.)

**태그는 빌드한 코드와 같아야 한다.** 순서는 언제나 "버전을 올리고 → 커밋하고 → 태그를 붙이고 → 그 커밋에서 빌드해 올린다"이다. 커밋하지 않은 변경이 있는 상태에서 빌드하면, PyPI에 올라간 0.1.0과 태그 `v0.1.0`의 코드가 달라진다. `git status`가 깨끗한지 확인하고 빌드한다. 태그를 붙인 뒤 `dist`를 지우고 다시 빌드해 둔다.

```
# macOS
rm -rf dist
python -m build

# Windows
Remove-Item -Recurse -Force dist
python -m build
```

> **Git 태그에서 버전을 읽는 방법도 있다**
> `hatch-vcs`, `setuptools-scm` 같은 도구를 쓰면 버전을 파일에 적지 않고 **Git 태그에서** 읽는다. `v0.2.0` 태그를 붙이고 빌드하면 버전이 0.2.0이 된다. 버전을 정말로 한 곳(태그)에만 두는 방법이라 큰 프로젝트에서 많이 쓴다. `pyproject.toml`에 `dynamic = ["version"]`과 `[tool.hatch.version] source = "vcs"`가 있으면 이 방식이다.

### 실습 8-5. 버전과 의존성 범위

**1. 다음 버전은?**

`textchunk 0.1.0`에서 시작해 다음 변경을 차례로 한다고 하자. 변경마다 버전이 무엇이 되어야 하는지 `~/python-advanced-lab/ch08/notes.md`에 적고 이유를 한 줄씩 붙인다. (지금은 `0.x`이지만 `1.0.0` 이후의 SemVer 규칙대로 답한다.)

- `httpx>=0.28`

`~=0.28`이 `0.29.0`을 받아들이는 것이 `0.x` 라이브러리에는 왜 위험할 수 있는가? 8.5.1의 "`0.`으로 시작하는 버전"과 연결해 설명한다.

```

```

테스트가 통과하는가? 같은 방법으로 `pydantic==2.0.3`을 시도해 본다. 설치되는가? (파이썬 3.13이 나오기 전의 버전이라 휠이 없어서, Rust 컴파일러가 없으면 설치에 실패할 수 있다. 실패했다면 그 메시지의 마지막 부분을 `notes.md`에 옮긴다.) 이 실험이 "아래쪽 경계를 낮게 잡을수록 좋은가"라는 질문에 무엇을 알려 주는가? 마지막 줄로 Pydantic을 최신으로 되돌리는 것을 잊지 않는다.

## 8.6 배포와 설치 확인

### 8.6.1 PyPI와 TestPyPI

`pip install httpx`를 하면 pip는 **PyPI**(Python Package Index, `pypi.org`)에서 httpx를 찾는다(기초 과정 9.1.1). 누구나 계정을 만들어 패키지를 올릴 수 있는 공개 저장소다. 그런데 PyPI에 올린 것은 **되돌리기 어렵다.**

- 한 번 쓴 이름은 지워도 다른 사람이 함부로 다시 쓸 수 없고, 한 번 올린 **파일 이름**(이름과 버전)은 지워도 다시 올릴 수 없다(8.6.5).
- 올리는 즉시 전 세계에서 내려받을 수 있다. 미러 서버와 캐시에 복사된 것은 지워도 남는다.

그래서 연습과 시험을 위한 별도의 저장소 **TestPyPI**(`test.pypi.org`)가 있다. 계정도 따로이고, 올라간 것은 가끔 정리된다. 이 장에서는 **TestPyPI에만** 올린다. 실제 PyPI에 공개하는 것은 8.6.6을 모두 확인한 뒤, 정말 남이 쓸 만한 것을 만들었을 때의 일이다. 연습용 패키지를 실제 PyPI에 올리는 것은 공용 이름 공간을 어지럽히는 일이므로 하지 않는다.

### 8.6.2 계정과 API 토큰

1. **계정을 만든다.** `https://test.pypi.org/account/register/`에서 가입하고, 받은 메일로 주소를 확인한다.
2. **2단계 인증을 켠다.** PyPI와 TestPyPI는 2단계 인증을 켜지 않은 계정의 업로드를 받지 않는다. 계정 설정(Account settings)에서 인증 앱(TOTP)을 등록한다. GitHub의 2단계 인증과 같은 방식이다(개발 도구 8.2). 함께 보여 주는 **복구 코드**는 안전한 곳에 보관한다.
3. **API 토큰을 만든다.** 계정 설정의 "API tokens"에서 "Add API token"을 누른다. 이름은 `textchunk-upload`처럼 쓰임새를 적는다. **범위**(scope)는 "Entire account"를 고른다. 프로젝트가 아직 없어서 그 프로젝트만으로 범위를 좁힐 수 없기 때문이다.
4. 만들어진 토큰(`pypi-`로 시작하는 긴 문자열)은 **이 화면에서 한 번만** 보인다. 바로 복사해 둔다.

토큰은 비밀번호와 같다. 이 토큰이 있으면 누구든 내 이름으로 패키지를 올릴 수 있다. 개발 도구 8.2.4의 GitHub 개인용 액세스 토큰, 8.3의 비밀 값과 같이 다룬다.

- **저장소에 넣지 않는다.** 코드, `pyproject.toml`, `README.md`, 커밋 메시지 어디에도 적지 않는다. AI에게 오류를 물을 때 붙여 넣는 터미널 출력에 섞이지 않았는지도 확인한다.
- **처음 올린 뒤에는 범위를 좁힌다.** 8.6.3에서 처음 올리고 나면 `textchunk-gildong` 프로젝트가 생긴다. 그때 "Entire account" 토큰을 지우고, 이 프로젝트에만 쓸 수 있는 토큰을 새로 만든다. 새어 나가도 피해가 이 프로젝트에 그친다.
- **잃어버리면 지우고 새로 만든다.** 토큰은 다시 볼 수 없다. 새로 만들면 된다.

> **`.pypirc`**
> 남의 안내문에서 홈 폴더의 `.pypirc` 파일에 토큰을 적어 두라는 방법을 보게 된다. `[testpypi]` 아래에 `username = __token__`, `password = pypi-...`를 적으면 twine이 매번 묻지 않는다. 편하지만 토큰이 평문 파일로 남는다. 이 장에서는 올릴 때마다 붙여 넣는다. 자동화할 때는 8.6.6의 "신뢰할 수 있는 게시"를 쓴다.

패키지 저장소에서 가상환경을 활성화하고, 8.5.5에서 다시 빌드한 `dist`의 두 파일을 먼저 **검사한다.**

`README.md`

````markdown

긴 글을 LLM에 보낼 조각으로 나누는 명령행 도구.

```

```

```
textchunk notes.txt --size 500 --overlap 50
textchunk notes.txt -t summarize -o prompts.jsonl
```

조각마다 `{"file": ..., "chunk": ..., "text": ...}`를 한 줄의 JSON으로 출력한다.
`textchunk --help`로 모든 옵션을 볼 수 있다.
````

```
python -m build
```

`File already exists` — **한 번 올린 파일 이름은 다시 쓸 수 없다.** 내용이 달라도, 앞의 것을 지웠어도 마찬가지다. `textchunk-gildong 0.1.0`을 이미 설치한 사람이 있는데 같은 이름의 다른 파일이 나타나면, "0.1.0"이라는 이름이 더는 하나의 코드를 가리키지 않게 되기 때문이다. 8.5.5에서 "0.1.0의 코드는 무엇이었나를 다시 찾을 수 있어야 한다"고 한 것을 PyPI가 강제로 지켜 준다.

그러니 버전을 올린다. 코드는 그대로이고 문서만 고쳤으므로 PATCH를 올려 `0.1.1`이다.

1. `src/textchunk/__init__.py`의 `__version__`을 `"0.1.1"`로 고친다.
2. 커밋하고 태그를 붙인다.
   ```
   git add README.md src/textchunk/__init__.py
   git commit -m "README에 사용 예, 0.1.1"
   git tag -a v0.1.1 -m "textchunk 0.1.1"
   ```
3. `dist`를 지우고 빌드한 뒤 검사하고 올린다.
   ```
   python -m build
   twine check dist/*
   twine upload --repository testpypi dist/*
   ```

`dist`를 먼저 지우는 이유는 `dist/*`에 0.1.0의 파일이 남아 있으면 그것까지 다시 올리려다 같은 오류를 만나기 때문이다(`twine upload --skip-existing`으로 이미 있는 것을 건너뛸 수도 있다). TestPyPI의 페이지에서 "Release history"에 0.1.0과 0.1.1이 함께 있고, 0.1.1의 본문에 사용 예가 보이는지 확인한다.

> **잘못 올렸다면 — 지우기보다 얀크**
> 실제 PyPI에서 버그가 있는 버전을 올렸다면 지우기보다 **얀크**(yank)를 쓴다. 프로젝트 관리 화면에서 그 버전을 "yank"하면 `pip install 이름`이 그 버전을 고르지 않는다. 하지만 `이름==그 버전`처럼 정확히 요청한 사람(잠금 파일로 설치하는 사람)은 여전히 받을 수 있어서, 그 버전에 기대던 프로그램이 갑자기 설치되지 않는 일이 없다. 그리고 고친 버전을 새 번호로 올린다.

### 8.6.6 실제 PyPI에 공개하기 전에

언젠가 정말로 남이 쓸 만한 패키지를 만들어 PyPI에 공개한다면, 다음을 확인한다.

| 확인할 것 | 무엇을 | 이 장에서 |
|---|---|---|
| **이름** | `https://pypi.org/project/이름/`이 비어 있는가. 유명한 패키지와 헷갈리는 이름이 아닌가(`reqeusts` 같은 이름은 악성 패키지가 쓰는 수법이라 PyPI가 막기도 한다). 배포 이름과 `import` 이름이 너무 다르지 않은가 | 8.2.4 |
| **라이선스** | 남이 써도 되는지, 어떤 조건으로 써도 되는지를 정한다. 라이선스가 없으면 남은 **볼 수만 있고 쓸 수 없다**(개발 도구 8.4.2). MIT, Apache-2.0, BSD-3-Clause가 흔하다. 회사에서 만든 코드라면 회사의 규칙을 먼저 확인한다 | 8.2.3 |
| **README** | 무엇을 하는가, 어떻게 설치하는가, 가장 짧은 사용 예. PyPI 페이지의 첫인상이다. `twine check`가 통과해도 **읽어 보고** 판단한다 | 8.6.5 |
| **프로젝트 정보** | `description`, `requires-python`, `classifiers`, 저장소 주소(`[project.urls]`) | 8.2.4 |
| **의존성 범위** | 아래쪽은 시험한 버전, `==`는 없다 | 8.5.3 |
| **들어간 파일** | 휠과 소스 배포판의 목록. 비밀 값이 없는가 | 8.4.2, 8.4.3 |
| **새 가상환경 설치** | TestPyPI에서 설치해 명령이 동작하는가 | 8.6.4 |
| **버전과 태그** | 버전이 맞고, 그 커밋에 태그가 있는가 | 8.5.5 |
| **변경 기록** | 무엇이 바뀌었는지 `CHANGELOG.md`나 GitHub의 릴리스 노트에 적는다 | 8.5.1의 상자 |

`[project.urls]`는 PyPI 페이지 왼쪽에 링크로 나타난다. 저장소를 GitHub에 올렸다면 더해 둔다.

```toml
[project.urls]
Repository = "https://github.com/gildong/textchunk"
Issues = "https://github.com/gildong/textchunk/issues"
```

> **신뢰할 수 있는 게시**(trusted publishing)
> API 토큰은 오래 살아 있는 비밀 값이라, 새어 나가면 위험하다. 그래서 PyPI는 **GitHub Actions가 직접 올리게** 하는 방법을 권한다. PyPI의 프로젝트 설정에 "이 GitHub 저장소의 이 워크플로가 올릴 수 있다"고 등록해 두면, 워크플로가 실행될 때마다 짧은 시간만 유효한 토큰을 받아 올린다. 사람의 컴퓨터에는 토큰이 남지 않는다. 8.8의 GitHub Actions를 익힌 뒤 "태그를 푸시하면 빌드해서 PyPI에 올린다"를 자동화할 때 쓴다. 공식 안내서(Python Packaging User Guide)에 "Publishing package distribution releases using GitHub Actions"라는 안내가 있다.

### 실습 8-6. 배포와 설치 확인

**1. TestPyPI에 올리기**

8.6.2~8.6.3을 따라 TestPyPI 계정과 토큰을 만들고 `textchunk-gildong 0.1.0`을 올린다. 이름이 이미 있다는 오류가 나면 이름을 조금 바꾼다(`textchunk-gildong2`처럼). 이름을 바꾸면 `pyproject.toml`의 `name`만 고치면 된다. `import` 이름(`textchunk`)과 명령 이름(`textchunk`)은 그대로다. 왜 그런지 8.1.4와 8.3.4로 설명한다.

## 8.7 uv로 같은 일 하기

### 8.7.1 uv

지금까지 패키지를 만들고 내보내는 데 도구 넷을 썼다. 가상환경은 `venv`, 설치는 `pip`, 빌드는 `build`, 올리기는 `twine`. 기초 과정 9.1.9에서 이름만 소개한 **uv**는 이 일을 하나의 프로그램으로 한다. Ruff를 만든 회사가 Rust로 만들어서 매우 빠르고, 최근에 시작하는 프로젝트와 LLM 라이브러리의 문서에서 `uv add`, `uv run` 같은 명령을 자주 보게 된다. "LLM 서비스 배포"에서 서비스를 컨테이너로 만들 때도 쓰인다.

uv는 새로운 규칙을 만들지 않는다. **같은 `pyproject.toml`**을 읽고, **같은 휠**을 만들고, **같은 PyPI**에 올린다. 그래서 이 절은 새로 배우기보다 **대응시키기**다. 8.6까지 한 일을 uv로 다시 하면서, 각 명령이 표준 도구의 무엇에 해당하는지 본다.

uv는 파이썬 패키지가 아니라 독립된 프로그램이므로 가상환경 밖, 운영체제에 설치한다.

```
# macOS
curl -LsSf https://astral.sh/uv/install.sh | sh

# Windows
powershell -ExecutionPolicy ByPass -c "irm https://astral.sh/uv/install.ps1 | iex"
```

macOS에서 Homebrew를 쓴다면 `brew install uv`, Windows에서 winget을 쓴다면 `winget install --id=astral-sh.uv -e`로도 설치할 수 있다. 설치한 뒤 **새 터미널**을 열어 확인한다.

```
uv --version
```

```
uv 0.13.8
```

> **인터넷에서 받은 스크립트를 바로 실행하는 명령**
> `curl ... | sh`와 `irm ... | iex`는 인터넷에서 받은 스크립트를 **읽지 않고 바로 실행**한다. 개발 도구 과정에서 본 대로, 이런 명령은 주소가 공식 문서의 것인지 확인하고 실행한다. 위 주소는 uv 공식 문서(`docs.astral.sh/uv`)의 설치 안내에 있는 것이다. 걱정된다면 주소를 브라우저로 열어 스크립트를 먼저 읽어 보거나, Homebrew·winget처럼 이미 믿고 쓰는 설치 도구를 쓴다.

### 8.7.2 `uv init` — 프로젝트 시작하기

uv가 새 프로젝트를 어떻게 만드는지 먼저 본다. 홈 폴더에서, 어느 가상환경도 활성화하지 않은 상태로 실행한다.

```
cd ~
uv init --package uvdemo
cd uvdemo
```

```
Initialized project `uvdemo` at `/Users/.../uvdemo`
```

```
uvdemo/
├── .gitignore
├── .python-version
├── README.md
├── pyproject.toml
└── src/
    └── uvdemo/
        └── __init__.py
```

`--package`는 "배포할 패키지를 만든다"는 뜻이다. **`src` 레이아웃**이고, `.gitignore`가 있고, `git init`까지 해 두었다. 8.2에서 손으로 한 일을 한 번에 했다. `.python-version`에는 이 프로젝트에서 쓸 파이썬 버전(`3.13`)이 적혀 있다.

`pyproject.toml`

```toml
[project]
name = "uvdemo"
version = "0.1.0"
description = "Add your description here"
readme = "README.md"
authors = [
    { name = "홍길동", email = "gildong@example.com" }
]
requires-python = ">=3.13"
dependencies = []

[project.scripts]
uvdemo = "uvdemo:main"

[build-system]

build-backend = "uv_build"
```

8.1과 8.2에서 본 표들이다. 다른 점만 짚는다.

- `version = "0.1.0"` — 버전을 `pyproject.toml`에 직접 적었다. 8.5.2에서 본 "다른 방법"이다.
- `authors` — Git 설정(`user.name`, `user.email`)에서 읽어 채웠다.
- `[project.scripts]`의 `uvdemo = "uvdemo:main"` — `src/uvdemo/__init__.py`에 `main()`이 들어 있다. 8.3.4와 같은 진입점이다.
- 빌드 백엔드는 uv가 만든 `uv_build`다(8.1.6). 빌드 백엔드의 버전 범위를 위아래 모두 막았다(`>=0.13.8,<0.14.0`). 백엔드는 패키지를 **만드는** 도구라서 바뀌면 결과물이 달라질 수 있으므로 좁게 잡은 것이다. 8.5.3의 "라이브러리는 넓게"와 대상이 다르다.

`uv run`이 번거로우면 지금까지처럼 `.venv`를 활성화하고 `pytest`, `mypy`를 그대로 써도 된다. uv가 만든 `.venv`도 보통의 가상환경이다. 다만 한 가지가 다르다. **uv가 만든 가상환경에는 pip가 없다.** 패키지는 `uv add`(8.7.4)나 `uv sync`로 관리한다. 꼭 pip처럼 설치해야 할 때는 `uv pip install 패키지`를 쓴다. 이 장의 나머지 실습(실습 8-9)은 pip로 만든 가상환경과 uv로 만든 가상환경 어느 쪽에서도 할 수 있게 두 명령을 함께 적는다.

> **활성화된 다른 가상환경이 있으면**
> 실습 저장소의 가상환경을 활성화한 채로 `~/textchunk`에서 `uv run`을 하면 "`VIRTUAL_ENV=...` does not match the project environment path `.venv` and will be ignored"라는 경고가 나온다. uv는 활성화된 가상환경이 아니라 **프로젝트의 `.venv`**를 쓴다는 뜻이다. 헷갈리지 않게 `deactivate`로 끄고 쓴다.

### 8.7.4 `uv add`와 `uv remove` — 의존성 고치기

pip를 쓸 때 의존성을 더하는 일은 두 단계였다. `pyproject.toml`의 `dependencies`를 고치고, `pip install -e .`로 다시 설치한다. uv는 한 명령으로 한다. 시험 삼아 httpx를 더해 본다.

```
uv add httpx
```

```

 + certifi==2026.10.23
 + h11==0.16.0
 + httpcore==1.0.9
```

`pyproject.toml`

```toml
dependencies = [
    "httpx>=0.28.1",
    "pydantic>=2.9,<3",

```

`dependencies`에 `"httpx>=0.28.1"`이 더해졌고, 설치되었고, `uv.lock`도 갱신되었다. uv는 **아래쪽 경계만** 지금 설치한 버전으로 적는다. 8.5.3의 기준대로라면 위쪽을 어떻게 할지는 우리가 정해야 한다. 처음부터 정하려면 범위를 함께 준다.

```
uv add "httpx>=0.28,<1"
```

개발 도구는 `--dev`를 붙인다. `[dependency-groups]`의 `dev`에 들어간다.

```

```

```toml
dev = [
    "pytest>=9",
```

```
uv remove httpx
uv remove --dev pytest-asyncio
```

`git diff pyproject.toml`이 비어 있는지 확인한다.

### 8.7.5 `uv.lock` — 잠금 파일

`uv.lock`을 VS Code로 열어 본다. TOML 형식이다(8.1.2). 패키지마다 `[[package]]` 표가 하나씩 있다. `[[이름]]`처럼 대괄호를 두 겹으로 쓰면 **같은 이름의 표를 여러 개** 이어 쓰는 "표의 배열"이다.

`uv.lock`(일부)

```toml
version = 1
revision = 5
requires-python = ">=3.12"

[[package]]
name = "pydantic"
version = "2.14.3"
source = { registry = "https://pypi.org/simple" }
dependencies = [
    { name = "annotated-types" },
    { name = "pydantic-core" },
    { name = "typing-extensions" },
    { name = "typing-inspection" },
]
sdist = { url = "https://files.pythonhosted.org/.../pydantic-2.14.3.tar.gz", hash = "sha256:1054f2...", ... }
wheels = [
    ...
]

[[package]]
name = "textchunk-gildong"
source = { editable = "." }
dependencies = [
    { name = "pydantic" },
]

[package.dev-dependencies]
dev = [
    { name = "mypy" },
    { name = "pytest" },
    { name = "pytest-cov" },
    { name = "ruff" },
]

[package.metadata]
requires-dist = [{ name = "pydantic", specifier = ">=2.9,<3" }]
...
```

- **정확한 버전** — `pydantic`은 `2.14.3`이다. `pyproject.toml`의 범위(`>=2.9,<3`)를 풀어서 나온 답이다.
- **어디서 받는가와 해시** — 받을 파일의 주소와 `sha256` 해시가 적혀 있다. 다음에 설치할 때 받은 파일의 해시가 다르면 설치를 거부한다. 누군가 파일을 바꿔치기해도 알아챌 수 있다.
- **우리 프로젝트도 있다** — `textchunk-gildong`은 `editable = "."`, 즉 이 폴더를 편집 가능 설치한다. 그 아래 `requires-dist`에는 `pyproject.toml`의 범위가 그대로 적혀 있다. 범위와 그 답이 한 파일에 함께 있다.

8.5.4의 표에서 `requirements.txt`와 비교한 차이가 여기서 보인다. 무엇이 무엇에 기대는지가 남는다. 사람이 읽기 좋은 모양으로 보려면 `uv tree`를 쓴다.

```
uv tree --no-dev
```

```
Resolved 20 packages in 4ms
textchunk-gildong
└── pydantic v2.14.3
    ├── annotated-types v0.8.0
    ├── pydantic-core v2.50.4
    │   └── typing-extensions v4.16.0
    ├── typing-extensions v4.16.0
    └── typing-inspection v0.4.5
        └── typing-extensions v4.16.0
```

1장에서 "`pip freeze`는 직접 설치한 것과 함께 설치된 것을 구별하지 않는다. 이 문제는 8장에서 `pyproject.toml`로 해결한다"고 했다. 직접 고른 것은 `pyproject.toml`에, 그 결과와 관계는 `uv.lock`에 있다.

`uv.lock`은 **사람이 고치지 않는다.** `uv add`, `uv remove`, `uv sync`가 고친다. 새 버전으로 올리고 싶으면 `uv lock --upgrade`(전부)나 `uv lock --upgrade-package pydantic`(하나)을 쓴다. 그리고 **커밋한다.** 같이 개발하는 사람과 GitHub Actions가 `uv sync`로 같은 버전을 설치하게 하기 위해서다(8.5.4). 휠에는 들어가지 않으므로 쓰는 사람에게는 영향이 없다.

### 8.7.6 `uv build`와 `uv publish`

빌드한다. 8.4.1의 `python -m build`에 해당한다.

```
uv build
```

```
Building source distribution...
Building wheel from source distribution...
Successfully built dist/textchunk_gildong-0.1.1.tar.gz
Successfully built dist/textchunk_gildong-0.1.1-py3-none-any.whl
```

`[build-system]`이 hatchling이므로 uv도 hatchling에게 빌드를 맡긴다(8.1.6의 프런트엔드와 백엔드). 같은 휠이 나온다. 8.4.2처럼 열어 보면 확인할 수 있다.

올리기는 `uv publish`다. 8.6.3의 `twine upload`에 해당한다. TestPyPI에 올리려면 어디에 올릴지를 알려 줘야 한다. 매번 주소를 적지 않도록 `pyproject.toml`에 저장소를 등록해 둔다.

```toml
[[tool.uv.index]]
name = "testpypi"
url = "https://test.pypi.org/simple/"
publish-url = "https://test.pypi.org/legacy/"
explicit = true
```

- `url`은 **설치할 때** 찾는 주소, `publish-url`은 **올릴 때** 쓰는 주소다. 8.6.3의 `Uploading distributions to https://test.pypi.org/legacy/`와 8.6.4의 `--index-url https://test.pypi.org/simple/`가 이 둘이다.
- `explicit = true` — "의존성을 찾을 때 이 저장소를 함부로 쓰지 말라"는 뜻이다. 8.6.4의 상자에서 본 `--extra-index-url`의 함정을 피한다.

```
uv publish --index testpypi
```

uv가 이름과 비밀번호를 물으면 이름은 `__token__`, 비밀번호는 토큰을 넣는다. 토큰을 명령에 직접 적는 `--token` 옵션도 있지만, 그러면 토큰이 터미널의 명령 기록에 남는다. 이 장에서는 쓰지 않는다. 지금 `dist`에 있는 0.1.1은 이미 올렸으므로, 실제로 올리는 것은 실습 8-9에서 0.2.0을 만든 뒤에 한다.

### 8.7.7 대응표

| 하는 일 | 표준 도구 | uv |
|---|---|---|
| 프로젝트 시작 | 손으로 폴더와 `pyproject.toml`을 만든다 | `uv init --package 이름` |
| 가상환경 만들기 | `python -m venv .venv` | `uv venv`(보통은 `uv sync`가 알아서) |
| 프로젝트와 개발 도구 설치 | `python -m pip install -e . --group dev` | `uv sync` |
| 쓰는 사람용만 설치 | `python -m pip install -e .` | `uv sync --no-dev` |
| 의존성 더하기 | `pyproject.toml`을 고치고 다시 `pip install -e .` | `uv add 패키지`, `uv add --dev 패키지` |
| 의존성 빼기 | `pyproject.toml`을 고치고 `pip uninstall 패키지` | `uv remove 패키지` |
| 잠금 파일 | `python -m pip freeze > requirements.txt` | `uv lock`(`uv add`, `uv sync`가 알아서) |
| 잠금 파일대로 설치 | `python -m pip install -r requirements.txt` | `uv sync --locked` |
| 명령 실행 | 가상환경을 활성화하고 `pytest` | `uv run pytest` |
| 의존성 나무 보기 | (`pip show`로 하나씩) | `uv tree` |
| 빌드 | `python -m build` | `uv build` |
| 올리기 | `twine upload --repository testpypi dist/*` | `uv publish --index testpypi` |
| pip처럼 설치 | `python -m pip install 패키지` | `uv pip install 패키지` |
| 파이썬 설치 | 공식 설치 파일, Homebrew, winget(1.2.1) | `uv python install 3.13` |

`uv sync --locked`는 "`uv.lock`이 `pyproject.toml`과 맞지 않으면 고치지 말고 **실패하라**"는 뜻이다. 8.8의 GitHub Actions처럼 잠금 파일을 그대로 믿고 설치해야 하는 곳에서 쓴다. 마지막 줄의 `uv python install`은 파이썬 자체를 내려받아 설치한다. 1.2.1에서 3.12 이상의 파이썬을 설치하느라 고생했다면 다음부터는 이것으로 충분하다.

**어느 쪽을 쓸까?** 결과물(`pyproject.toml`, 휠)이 같으므로 프로젝트마다 정하면 된다. 남의 프로젝트에 `uv.lock`이 있으면 uv를 쓰고, 없으면 그 프로젝트의 `README.md`가 안내하는 방법을 따른다. 이 과정의 실습 저장소는 지금처럼 `venv`와 pip를 그대로 쓴다. 표준 도구로 먼저 익혀 두면 uv가 무엇을 대신해 주는지 알고 쓸 수 있다.

### 실습 8-7. uv로 같은 일 하기

**1. uv 설치와 `uv init`**

8.7.1~8.7.2를 따라 uv를 설치하고 `uvdemo`를 만들어 실행한다. `uvdemo`의 `pyproject.toml`과 `textchunk`의 `pyproject.toml`을 나란히 놓고, 다른 점을 세 가지 이상 `~/python-advanced-lab/ch08/notes.md`에 적는다. 각 차이가 이 장의 어느 절과 관계있는지 함께 적는다. 확인한 뒤 `uvdemo`를 지운다.

**2. `textchunk`를 uv로**

8.7.3~8.7.5를 따라 `.venv`를 uv로 다시 만들고, `uv run`으로 검사를 모두 돌린다. `uv add`와 `uv remove`를 해 본 뒤 `git diff pyproject.toml`이 비어 있는지 확인한다. `uv.lock`을 커밋한다.

```
git add uv.lock
git commit -m "uv.lock 추가"
```

**3. 대응시키기**

다음은 어느 LLM 라이브러리의 `README.md`에 있을 법한 "개발하기" 안내다. 각 줄을 uv를 쓰지 않는 표준 도구의 명령으로 바꿔 `notes.md`에 적는다.

```
uv sync
uv run pytest -m "not live"
uv add "anthropic>=0.80"
uv build
```

**4. 잠금 파일의 쓸모 (선택)**

`uv lock --upgrade-package pydantic --dry-run`(이미 최신이면 바뀌는 것이 없다)과 `uv tree --outdated`를 실행해 보고, 각각 무엇을 알려 주는지 적는다.

## 8.8 (선택) 지속적 통합 맛보기

### 8.8.1 푸시할 때마다 검사하기

6.6.5에서 "8장에서는 같은 검사를 GitHub Actions가 푸시할 때마다 대신 돌려준다. 사람은 잊지만 자동화는 잊지 않는다"고 했다. 개발 도구 8.9에서는 GitHub Actions의 워크플로 파일을 **읽고** 결과를 확인했다. 그때 "직접 작성은 중급 과정 8장에서"라고 했다. 이제 `textchunk`를 위한 워크플로를 쓴다. 이렇게 코드가 바뀔 때마다 자동으로 빌드하고 검사하는 것을 **지속적 통합**(continuous integration, CI)이라고 한다.

이 절은 GitHub 계정과 GitHub CLI(`gh`)가 필요하다. 없으면 워크플로 파일만 만들어 읽고 넘어가도 된다.

### 8.8.2 워크플로 파일

패키지 저장소에 `.github/workflows` 폴더를 만들고 그 안에 파일을 만든다. 폴더 이름과 위치가 정해져 있다. GitHub는 이 폴더의 `.yml` 파일만 워크플로로 읽는다.

`.github/workflows/check.yml`

```yaml
# 푸시와 풀 리퀘스트마다 ruff, mypy, pytest를 실행한다.
name: check

on:
  push:
    branches: [main]
  pull_request:

jobs:
  check:
    runs-on: ubuntu-latest
    strategy:
      matrix:
        python-version: ["3.12", "3.13"]
    steps:
      - uses: actions/checkout@v7
      - uses: actions/setup-python@v7
        with:
          python-version: ${{ matrix.python-version }}
      - run: python -m pip install --upgrade pip
      - run: python -m pip install -e . --group dev
      - run: ruff check .
      - run: ruff format --check .
      - run: mypy
      - run: pytest
```

개발 도구 8.9.2에서 읽은 워크플로와 모양이 같다. 새로 나온 것만 설명한다.

- **`strategy:` / `matrix:`** — 같은 잡을 **값을 바꿔 가며 여러 번** 실행한다. `python-version`이 `"3.12"`일 때 한 번, `"3.13"`일 때 한 번, 두 잡이 동시에 돈다. `${{ matrix.python-version }}`이 그 값으로 바뀐다. 6.3.5의 `@pytest.mark.parametrize`를 잡에 한 것이다. `requires-python = ">=3.12"`라고 약속했으니, 가장 낮은 3.12에서도 정말 도는지 확인한다. 우리 컴퓨터에는 3.13만 있어서 직접 확인하기 어려운 일이다.
- **`python -m pip install --upgrade pip`** — 러너에 설치된 파이썬의 pip가 `--group`(pip 25.1)을 모르는 오래된 것일 수 있어서 먼저 올린다.
- **`python -m pip install -e . --group dev`** — 8.2.5와 같다. 러너는 빈 컴퓨터라서 매번 설치부터 한다.
- **검사 넷** — 6.6.5의 `check.py`가 하던 일이다. 설정이 `pyproject.toml`에 있으므로(8.2.4) 인자가 거의 필요 없다. 하나라도 종료 코드가 0이 아니면 그 자리에서 잡이 실패한다.
- **`ANTHROPIC_API_KEY` 같은 비밀 값은 없다.** 이 검사들은 네트워크도 API 키도 필요 없게 만들었다(6.5). 그래서 아무 데서나 돌릴 수 있다.

`@v7`은 액션의 버전이다. 개발 도구 8.9.2에서 본 대로, 나중에 읽을 때는 더 큰 숫자가 있을 수 있다.

> **uv를 쓴다면**
> uv를 쓰는 프로젝트의 워크플로에서는 `actions/setup-python` 대신 `astral-sh/setup-uv` 액션을 쓰고, 설치는 `uv sync --locked`, 검사는 `uv run pytest`처럼 쓴다. `--locked` 덕분에 개발자의 컴퓨터와 같은 버전의 도구로 검사한다(8.7.7).

`tests/test_paragraphs.py`

```python
"""paragraphs, chunk_paragraphs의 테스트 — 실습 8-9. 이 파일은 고치지 않는다."""

from textchunk.chunking import chunk_paragraphs, paragraphs


def test_paragraphs_joins_lines_and_splits_on_blank_lines() -> None:
    lines = ["첫 줄\n", "  둘째 줄\n", "\n", "\n", "새 문단\n", "   \n"]
    assert list(paragraphs(lines)) == ["첫 줄 둘째 줄", "새 문단"]


def test_paragraphs_empty() -> None:
    assert list(paragraphs([])) == []
    assert list(paragraphs(["\n", "  \n"])) == []


def test_chunk_paragraphs_packs_until_limit() -> None:
    paras = ["가나", "다라", "마바사아"]
    assert list(chunk_paragraphs(paras, 5)) == ["가나 다라", "마바사아"]


def test_chunk_paragraphs_splits_long_paragraph() -> None:
    assert list(chunk_paragraphs(["가나다라마바사"], 3)) == ["가나다", "라마바", "사"]


def test_chunk_paragraphs_empty() -> None:
    assert list(chunk_paragraphs([], 5)) == []
```

**2. 옵션 더하기**

`cli.py`에 `--by-paragraph` 스위치를 더한다. 주면 `chunk(text, size, overlap)` 대신 `chunk_paragraphs(paragraphs(text.splitlines()), size)`로 조각을 만든다. 문단 단위로 모을 때는 겹침을 지원하지 않으므로, `--by-paragraph`와 0이 아닌 `--overlap`을 함께 주면 사용법 오류(종료 코드 2)로 끝낸다. `tests/test_cli.py`의 끝에 다음 테스트를 더하고 통과시킨다.

```python
def test_by_paragraph(tmp_path: Path, capsys: pytest.CaptureFixture[str]) -> None:

    memo.write_text("첫 문단입니다.\n\n둘째 문단입니다.", encoding="utf-8")

    lines = capsys.readouterr().out.splitlines()
    assert [json.loads(line)["text"] for line in lines] == [

def test_by_paragraph_rejects_overlap(
    doc: Path, capsys: pytest.CaptureFixture[str]
) -> None:

    assert exc_info.value.code == 2
    assert "함께 쓸 수 없다" in capsys.readouterr().err
```

## 정리

| 항목 | 핵심 |
|---|---|
| `pyproject.toml` | 프로젝트를 처음 열면 가장 먼저 읽는 파일. `[build-system]`(어떻게 빌드), `[project]`(무엇인가), `[dependency-groups]`(개발에 더 필요한 것), `[tool.…]`(도구 설정) |
| TOML | `키 = 값`, `[표]`, `[표.표]`, `[[표의 배열]]`, 주석 `#`, 참/거짓은 소문자. `tomllib`로 읽기만 한다 |
| 도구 설정 | `[tool.pytest.ini_options]`, `[tool.mypy]`, `[tool.ruff]`. pytest의 `configfile:` 줄로 어느 설정이 쓰였는지 확인. mypy는 현재 폴더에서 찾는다 |
| `select`와 `extend-select` | 기본 규칙을 바꾸기와 기본 규칙에 더하기 |
| 배포 이름과 `import` 이름 | `pip install textchunk-gildong`, `import textchunk`. 이름은 대소문자와 `-`, `_`, `.`을 가리지 않는다 |
| `dependencies` | 쓰는 사람에게 필요한 것. 범위로 적는다. 메타데이터에 들어간다 |
| `[dependency-groups]` | 만드는 사람에게 필요한 것. `pip install --group dev`(pip 25.1 이상). 메타데이터에 들어가지 않는다 |
| `[project.optional-dependencies]` | 쓰는 사람이 골라 설치하는 기능. `pip install "패키지[이름]"` |
| 빌드 프런트엔드와 백엔드 | pip, build, uv가 시키고 hatchling, setuptools, uv_build가 만든다. 빌드는 임시 가상환경에서 |
| 라이브러리와 애플리케이션 | 라이브러리는 범위만, 애플리케이션은 잠금 파일까지. 실습 저장소의 `requirements.txt`는 잠금 파일 |
| `src` 레이아웃 | 설치하지 않으면 `import`할 수 없게 해서, 테스트가 설치 과정을 거친 패키지를 시험하게 한다 |
| 편집 가능 설치 | `pip install -e .`. `.pth`가 `src`를 가리킨다. 코드는 바로 반영, `pyproject.toml`을 고치면 다시 설치 |
| `--import-mode=importlib` | 테스트 파일 이름이 겹쳐도 되고, 테스트가 설치된 패키지만 `import`한다 |
| `__init__.py` | 공개할 이름을 가져오고 `__all__`에 적는다. `__version__`을 한 곳에 |
| `py.typed` | "이 패키지는 타입 힌트를 갖추었다"는 표시. 쓰는 사람의 mypy가 검사한다 |
| `importlib.resources` | `files("패키지") / "폴더" / "파일"`. 현재 폴더나 `__file__`이 아니라 패키지를 기준으로 데이터 파일을 읽는다 |
| `argparse` | `ArgumentParser` → `add_argument()` → `parse_args()`. `type`, `default`, `choices`, `nargs`, `action`, `help`, `%(default)s`. 도움말과 오류 메시지를 만들어 준다 |
| `parser.error()` | `argparse`가 못 하는 검사. 사용법과 함께 출력하고 종료 코드 2 |
| `main(argv) -> int` | 인자 리스트를 받고 종료 코드를 돌려준다. `sys.exit()`는 부른 쪽이. 테스트에서는 `main([...])`, `capsys`, `pytest.raises(SystemExit)` |
| 표준 출력과 표준 오류 | 결과는 표준 출력, 안내와 오류는 표준 오류. 종료 코드 0 성공, 1 실행 실패, 2 사용법 오류 |
| `[project.scripts]` | `명령 = "패키지.모듈:함수"`. 설치하면 가상환경의 `bin`(`Scripts`)에 실행 파일이 생긴다 |
| `__main__.py` | `python -m 패키지`의 입구 |
| sdist와 휠 | 소스(`tar.gz`, 테스트까지)와 설치할 모양 그대로(`.whl`, zip). 빌드는 sdist를 거쳐 휠로 |
| 휠 열어 보기 | `python -m zipfile -l`. 데이터 파일과 `.dist-info`(`METADATA`, `entry_points.txt`, `RECORD`)를 확인. `.gitignore`에 걸린 것은 빠지고, 걸리지 않은 것은 들어간다 |
| 휠 이름 | `이름-버전-py3-none-any.whl`. 파이썬, ABI, 플랫폼 |
| 새 가상환경 설치 | 다른 사람의 컴퓨터를 흉내 낸다. 빠진 파일과 빠진 의존성은 여기서 드러난다 |
| 유의적 버전 | PATCH 고침, MINOR 기능 더하기, MAJOR 깨지는 변경. `0.x`는 아직 만드는 중. `a`, `b`, `rc`는 기본으로 설치되지 않는다 |
| 의존성 범위 | 아래쪽은 시험한 버전, 위쪽은 다음 MAJOR 미만(의견이 갈린다), `==`는 쓰지 않는다. `~=`는 마지막 자리만 올라간다 |
| 잠금 파일 | 모든 패키지의 정확한 버전. 애플리케이션과 개발 환경을 맞춘다. 휠에는 들어가지 않는다 |
| Git 태그 | `git tag -a v0.1.0`. 버전을 올리고 → 커밋하고 → 태그 → 그 커밋에서 빌드. 태그는 따로 푸시 |
| TestPyPI | 연습용 저장소. 2단계 인증, API 토큰(`__token__`), 처음 뒤에는 프로젝트 범위로 |
| `twine` | `twine check dist/*`, `twine upload --repository testpypi dist/*` |
| 같은 버전 | 한 번 올린 파일 이름은 다시 쓸 수 없다. 버전을 올린다. 실제 PyPI에서 잘못 올렸다면 얀크 |
| `--extra-index-url` | 저장소를 동등하게 보고 높은 버전을 고른다. 의존성 혼동에 주의 |
| 공개 전 확인 | 이름, 라이선스, README, 프로젝트 정보, 범위, 들어간 파일, 새 가상환경 설치, 태그, 변경 기록. 자동화는 신뢰할 수 있는 게시로 |
| uv | 같은 `pyproject.toml`, 같은 휠, 같은 PyPI. `uv sync`, `uv run`, `uv add`, `uv.lock`, `uv build`, `uv publish`. uv의 가상환경에는 pip가 없다 |
| GitHub Actions | `.github/workflows/*.yml`. `matrix`로 여러 파이썬에서, 설치 → ruff → mypy → pytest. 종료 코드로 성공과 실패 |
