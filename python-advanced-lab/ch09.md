# 9장. 마무리

[파이썬 중급](README.md) 과정의 마지막 장이다. 2장부터 8장까지 문법과 도구를 하나씩 배웠다. 그런데 실제 코드에서 그것들은 따로 나오지 않는다. 1장 1.1.3의 (라)에서 본 세 줄짜리 코드에 비동기, 컴프리헨션, 타입 힌트, 언패킹이 한꺼번에 들어 있었던 것처럼, 한 프로그램 안에서 서로 맞물려 쓰인다. 이 장에서는 7장 실습 7-8에서 만든 비동기 문서 일괄 요약기를 **남이 설치해서 쓰는 명령행 도구**로 완성하면서, 이 과정에서 배운 것을 모두 한 프로그램에 모은다.

- **설계부터** — 기초 과정 10장의 순서대로 한 문단, 실행 예, 실패 표를 먼저 쓴다. 7장 판에서 무엇을 바꿔야 도구가 되는지 정리하고, 모듈을 층으로 나눈다.
- **패키지로 옮기기** — 8장의 `textchunk`처럼 새 저장소에 `src` 레이아웃으로 만든다. 아래층(데이터와 규칙)부터 위층(명령)까지 차례로 쓰고, 층마다 확인한다.
- **테스트로 보이기** — 정상 응답, 형식이 맞지 않는 응답, 시간 초과, 요청 한도 초과, 동시 실행 수 제한을 각각 테스트로 보이고, 네트워크 없이 모든 테스트를 통과시킨다. `ruff`와 `mypy`도 경고 없이 통과시킨다.
- **재서 비교하기** — 같은 문서를 차례로(동시 1개) 요약할 때와 동시에 요약할 때의 시간을 재고, 그 차이를 설명한다.
- **(선택) 실제 LLM으로 바꿔 끼우기** — API 키가 있다면 같은 `Protocol`을 따르는 Anthropic 클라이언트를 만들어 가짜 대신 끼운다. 다른 코드는 한 줄도 고치지 않는다.
- **내보내기** — `README.md`와 설계 노트를 쓰고, 휠을 빌드해 새 가상환경에 설치한 뒤 설치된 명령으로 실행한다.
- **돌아보기** — 컴프리헨션, 제너레이터, 데코레이터, `Protocol`, Pydantic, 비동기, 테스트를 **어디에, 왜** 썼는지 설명한다. 1장 실습 1-1의 `ch01/map.md`를 마지막으로 다시 연다.

## 학습 목표

이 장을 마치면 다음을 할 수 있다.

- 기존 모듈을 명령행 도구로 만들기 전에 한 문단, 실행 예, 실패 표, 층 그림으로 설계를 글로 남길 수 있다.
- 조각 하나의 실패(시간 초과, 요청 한도 초과, 형식이 틀린 답)와 프로그램 전체를 멈춰야 하는 실패(입력 폴더가 없다, API 키가 없다)를 나누고, 각각을 다르게 처리할 수 있다.
- 라이브러리 코드에서 `print()`를 빼고, 알릴 일을 콜백으로 넘겨 화면 출력은 명령행 쪽에서 하도록 나눌 수 있다.
- 같은 `Protocol`을 따르는 가짜 클라이언트와 실제 클라이언트를 바꿔 끼우고, 바꿔 끼우는 지점을 한 곳으로 모을 수 있다.
- 비동기 코드의 시간 제한, 재시도, 동시 실행 수 제한이 의도대로 동작함을 걸린 시간이 아니라 **센 값**으로 테스트할 수 있다.
- 동시 실행 수에 따라 걸린 시간을 재고, 가장 오래 걸린 조각 하나로 그 결과를 설명할 수 있다.
- 선택 의존성(`[project.optional-dependencies]`)으로 무거운 패키지를 필요한 사람만 설치하게 하고, 설치되지 않았을 때 한 줄의 안내로 끝낼 수 있다.
- 완성한 패키지를 빌드해 새 가상환경에 설치하고, 설치된 명령으로 실행해 확인할 수 있다.
- 이 과정의 문법과 도구를 각각 프로그램의 어디에 썼고 왜 그 자리였는지, 그리고 왜 다른 자리에는 쓰지 않았는지 설명할 수 있다.

## 9.1 설계 — 7장의 모듈을 도구로

7장의 `async_summarizer.py`는 동작한다. 테스트 16개가 통과하고, `run_summarizer.py`로 실행하면 동시 실행 수에 따라 시간이 줄어드는 것도 보았다. 그런데 이것은 아직 **도구**가 아니다. `run_summarizer.py`는 임시 폴더에 문서를 만들어 요약하고 지운다. 내 폴더를 요약하려면 코드를 고쳐야 한다. 재시도 메시지는 `print()`로 화면에 섞여 나오고, 실패해도 종료 코드는 0이다. 다른 사람이 쓰려면 파일 세 개를 복사해야 한다.

바로 코드를 고치고 싶겠지만, 기초 과정 10.1의 순서를 따른다. **한 문단 → 실행 예 → 실패 표 → 역할 나누기 → 만드는 순서.** 코드를 고치는 것보다 글을 고치는 것이 훨씬 싸다.

### 9.1.1 한 문단으로

> `summarize-docs`는 폴더 안의 `.txt` 파일을 문단 단위로 묶어 조각으로 나누고, 조각마다 LLM에게 요약을 요청해 결과를 한 줄에 하나씩 JSON(JSONL)으로 저장하는 명령행 도구다. 요청은 정해 둔 수만큼 동시에 보내고, 시간 초과·요청 한도 초과·서버 오류는 다시 시도하며, 끝내 실패한 조각은 오류를 기록하고 나머지를 계속한다. 결과는 끝난 순서가 아니라 파일 이름 순, 조각 번호 순이다. API 키 없이도 시험할 수 있도록 무작위로 늦거나 실패하는 가짜 클라이언트를 기본으로 쓰고, 키가 있으면 Anthropic API를 쓸 수 있다.

**하지 않을 것**도 적는다(기초 과정 10.1.1).

- `.txt`가 아닌 파일(PDF, 워드, 마크다운)은 읽지 않는다.
- 요약의 **품질**은 판단하지 않는다. 형식(JSON 스키마)만 검사한다. 품질은 평가(Evals)의 일이다(6.6.6).
- 조각마다의 요약을 다시 모아 문서 전체의 요약을 만들지 않는다. 그것은 다음 버전의 일이다.
- 중간에 멈췄을 때 이어서 하기(이미 요약한 조각 건너뛰기)는 하지 않는다.

### 9.1.2 실행 예부터

코드보다 먼저, 사용하는 사람이 보게 될 화면을 쓴다. 8장 `textchunk`의 약속(결과는 표준 출력, 안내와 오류는 표준 오류, 종료 코드 0·1·2)을 그대로 따른다.

```
summarize-docs samples -s 200 -c 5 --timeout 2 --seed 32 -o summaries.jsonl
```

```
  [재시도] doc1.txt 1번 조각: 1번째 실패(RateLimitError: 요청 한도 초과), 0.5초 뒤 다시
  [재시도] doc2.txt 2번 조각: 1번째 실패(APITimeoutError: 2.0초 안에 답이 없다), 1.0초 뒤 다시
  ...
조각 30개: 성공 30, 실패 0, 9.7초 (동시 5개)
```

`summaries.jsonl`의 한 줄은 다음과 같다. 성공한 조각과 실패한 조각은 모양이 다르다.

```
{"file":"doc1.txt","chunk":1,"summary":"1번 문서에서 컴프리헨션에 관한 문단이다. 1번 문서에서 컴프리헨션에 …","keywords":["1번","문서에서","컴프리헨션에"]}
{"file":"doc3.txt","chunk":1,"error":"APITimeoutError: 2.0초 안에 답이 없다"}
```

명령의 옵션은 7장 실습 7-8의 "더 해 보기"에서 `notes.md`에 적어 둔 목록이 출발점이다. `summarize_folder()`의 매개변수가 거의 그대로 옵션이 된다.

| 옵션 | 기본값 | 7장의 매개변수 |
|---|---|---|
| `FOLDER` | (꼭 준다) | `folder` |
| `-o`, `--output` | 없으면 표준 출력 | `out_path` |
| `-s`, `--size` | 500 | `size` |
| `-c`, `--concurrency` | 5 | `max_concurrency` |
| `--timeout` | 30.0 | `timeout` |
| `--retries` | 3 | (7장에서는 `async_retry()`의 기본값 3에 묶여 있었다) |
| `--client` | `fake` | (7장에서는 코드에서 넘겼다) |
| `--model` | `claude-opus-5-5` | (없었다) |
| `--seed` | 없음 | (`RandomLLM(seed=32)`로 코드에 있었다) |

`--client`의 기본값을 `fake`로 한 것은 결정이다. 이 도구의 진짜 목적은 LLM으로 요약하는 것이지만, 이 과정을 따라 하는 사람 모두에게 API 키가 있지는 않다. 키 없이 설치하자마자 실행해 볼 수 있고, 실수로 돈을 쓰지 않는 쪽을 기본으로 했다. 이 결정과 이유는 9.8.1의 설계 노트에 남긴다.

### 9.1.3 실패를 나눈다

기초 과정 10.1.4의 실패 표를 만든다. 이 도구에서 새로 생긴 칸이 있다. **결과 파일**이다. 어떤 실패는 결과 파일에 한 줄로 남기고 계속하고, 어떤 실패는 결과 파일을 쓰지 않고 멈춘다.

| 상황 | 어디서 알아차리나 | 어떻게 하나 | 결과 파일 | 종료 코드 |
|---|---|---|---|---|
| 옵션이 틀렸다(`-c 0`, `--client openai`) | `argparse`, `parser.error()` | 사용법과 한 줄 오류 | 쓰지 않는다 | 2 |
| 입력 폴더가 없다 | `load_pieces()` | 한 줄 오류 | 쓰지 않는다 | 1 |
| `.txt` 파일이 하나도 없다 | `main()` | 한 줄 오류 | 쓰지 않는다 | 1 |
| 글 파일이 UTF-8이 아니거나 읽을 수 없다 | `read_pieces()` | 어느 파일인지와 한 줄 오류 | 쓰지 않는다 | 1 |
| 결과를 저장할 폴더가 없다 | `main()`, **요약을 시작하기 전에** | 한 줄 오류 | 쓰지 않는다 | 1 |
| 조각 하나가 시간 초과, 요청 한도 초과, 서버 오류 | `summarize_piece()` | 다시 시도. 끝내 실패하면 그 조각에 `error` | 쓴다 | 1 |
| 조각 하나의 요청이 잘못되었다(400) | `summarize_piece()` | 다시 시도하지 않고 그 조각에 `error` | 쓴다 | 1 |
| 조각 하나의 답이 JSON 스키마에 맞지 않는다 | `parse_summary()` | 그 조각에 `error` | 쓴다 | 1 |
| API 키가 없거나 틀렸다 | 클라이언트 | **전체를 멈추고** 한 줄 오류 | 쓰지 않는다 | 1 |
| anthropic 패키지가 설치되지 않았다 | `main()` | 설치 방법을 한 줄로 | 쓰지 않는다 | 1 |
| 결과 파일을 쓸 수 없다 | `main()` | 한 줄 오류 | (쓰지 못했다) | 1 |

세 가지 결정이 들어 있다.

- **조각의 실패는 기록하고 계속한다.** 문서 백 개 중 조각 하나가 시간 초과로 실패했다고 나머지를 버리면, 이미 쓴 시간과 돈이 아깝다. 실패한 조각은 결과 파일에 `error`로 남으므로, 나중에 그 조각만 다시 요약할 수 있다. 기초 과정 10장 가계부는 반대로 "잘못된 줄이 있으면 멈춘다"였다. 틀린 합계는 합계가 없는 것보다 나쁘기 때문이었다. 요약은 조각마다 독립적이므로 일부가 빠져도 나머지의 가치가 그대로다. **프로그램의 목적이 정한다**(기초 과정 10.1.4).
- **그래도 종료 코드는 1이다.** 결과 파일은 썼지만, 실패한 조각이 하나라도 있으면 1로 끝낸다. 이 명령을 다른 스크립트나 GitHub Actions에서 부른다면, 종료 코드만 보고도 "다시 확인할 것이 있다"를 알 수 있어야 한다. 성공과 실패의 수는 표준 오류의 마지막 줄에 나온다.
- **모든 조각이 똑같이 실패할 오류는 전체를 멈춘다.** API 키가 없으면 조각 서른 개가 모두 같은 이유로 실패한다. 결과 파일에 같은 오류를 서른 줄 쓰는 것은 기록이 아니라 소음이다. 이런 오류는 조각의 실패와 **다른 예외 클래스**로 만들어 맨 위까지 올려보낸다(9.7.3).

"결과를 저장할 폴더가 없다"를 **요약을 시작하기 전에** 확인하는 것에도 이유가 있다. 실제 API로 조각 백 개를 요약하고 나서 마지막에 "저장할 수 없다"로 끝나면, 시간과 돈을 모두 버린다. **돈을 쓰기 전에 확인할 수 있는 것은 먼저 확인한다.**

### 9.1.4 7장 판에서 바뀌는 것

7장의 코드에서 출발해 무엇을 바꿔야 하는지 정리한다. 바꾸는 이유는 모두 "도구가 되기 위해서"다.

| 7장 실습 7-8 | 9장 | 이유 |
|---|---|---|
| 파일 세 개(`async_summarizer.py`, `async_retry.py`, `async_fakes.py`) | 패키지 `docsum`의 모듈 | 설치해서 쓰도록(8장) |
| `async_retry()`가 `print()`로 재시도를 알린다 | `on_retry` 콜백으로 알리고, 출력은 `cli`가 한다 | 라이브러리가 화면을 차지하지 않도록(9.2.4) |
| 레코드는 `dict[str, Any]` | `Record` 모델(Pydantic) | 한 줄의 모양을 코드 한 곳에 적고, 읽는 쪽이 검증할 수 있도록 |
| 조각은 `tuple[str, int, str]` | `Piece` 데이터 클래스 | `piece[2]` 대신 `piece.text`로 읽도록 |
| `split_text()` — 글자 수로만 자른다 | `paragraphs()` + `chunk_paragraphs()` | 문단을 지키도록(3.4.6, 8장 실습 8-9) |
| `summarize_folder()`가 파일 읽기·요약·쓰기를 모두 한다 | `load_pieces()`, `summarize_all()`, `to_jsonl()`로 나누고 `cli`가 잇는다 | 비동기 부분을 작게, 파일 입출력은 이벤트 루프 밖으로(9.3.3) |
| `timeout` 매개변수 | `attempt_timeout` | 시도 한 번의 제한이라는 뜻을 이름에(9.3.3) |
| 시도 횟수는 3으로 고정 | `retries` 매개변수, `--retries` 옵션 | 사용하는 사람이 정하도록 |
| 실패해도 종료 코드 0 | 실패한 조각이 있으면 1 | 부르는 쪽이 알 수 있도록 |
| 설정 오류라는 개념이 없다 | `ClientSetupError` | 모두 똑같이 실패할 오류는 전체를 멈추도록(9.7.3) |
| 실제 클라이언트는 `NotImplementedError`(7.7.6) | `AnthropicLLM`, 선택 의존성 | 키가 있는 사람만 설치해서 쓰도록(9.7) |

### 9.1.5 역할을 나눈다

기초 과정 10.1.5처럼 층으로 나눈다. 모듈은 **자기보다 아래층의 모듈만** `import`한다. 아래층은 위층을 모른다.

```
3층  cli                                     명령 — 옵션, 클라이언트 고르기, 출력, 종료 코드
      │
2층  core · storage · anthropic_client       흐름 · 파일 · 실제 클라이언트(선택)
      │
1층  clients · retry · prompts · chunking    클라이언트의 약속과 가짜 · 재시도 · 프롬프트 · 조각
      │
0층  models · errors                         데이터의 모양 · 오류의 종류

(옆) testing                                 테스트용 가짜. 아무것도 import하지 않는다
```

| 모듈 | 하는 일 | 쓰는 모듈 |
|---|---|---|
| `errors` | 오류의 종류와 "다시 시도할 오류"의 목록 | 없음 |
| `models` | `Piece`, `Summary`, `Record` | 없음 |
| `chunking` | 줄 → 문단 → 조각 | 없음 |
| `prompts` | 프롬프트 만들기, 답을 `Summary`로 검증하기 | `models` |
| `retry` | 비동기 재시도 데코레이터 | `errors` |
| `clients` | `AsyncLLMClient` 프로토콜, 가짜 클라이언트 `RandomLLM` | `errors`, `models` |
| `storage` | 폴더의 글 파일 → 조각, 레코드 → JSONL | `chunking`, `models` |
| `core` | 조각 하나 요약하기, 여러 조각을 동시에 요약하기 | `clients`, `errors`, `models`, `prompts`, `retry` |
| `cli` | 명령 | `core`, `storage`, `clients`, `errors`, `models` |
| `anthropic_client` | Anthropic API를 쓰는 실제 클라이언트(선택) | `clients`, `errors`, 그리고 `anthropic` |
| `testing` | 테스트용 가짜(`ScriptedLLM`, `Slow`, `RecordingSleep`) | 없음 |

`core`는 파일을 모른다. 조각의 리스트를 받아 레코드의 리스트를 돌려줄 뿐이다. `storage`는 LLM을 모른다. 그래서 `core`는 파일 없이, `storage`는 비동기 없이 테스트할 수 있다. `anthropic_client`만이 `anthropic` 패키지를 `import`한다. 이 패키지를 설치하지 않은 사람도 나머지는 모두 쓸 수 있다(9.7.1).

**만드는 순서**는 아래층부터다(기초 과정 10.1.6). `errors`, `models` → `chunking`, `prompts` → `retry` → `clients`, `storage` → `core` → `cli`. 한 층을 만들 때마다 대화형 셸이나 테스트로 확인한다.

`src/docsum/errors.py`

```python
"""LLM 클라이언트가 일으키는 오류 — 7장 async_retry.py에서 옮기고 ClientSetupError를 더했다."""


class APIError(Exception):
    """LLM API의 오류. status에 HTTP 상태 코드를 담는다."""

    def __init__(self, message: str, status: int | None = None) -> None:
        super().__init__(message)
        self.status = status


class APITimeoutError(APIError):
    """응답이 제한 시간 안에 오지 않았다."""


class RateLimitError(APIError):
    """요청 한도 초과(429). retry_after초 뒤에 다시 보내라는 뜻이다."""

    def __init__(self, message: str, retry_after: float | None = None) -> None:
        super().__init__(message, status=429)
        self.retry_after = retry_after


class ServerError(APIError):
    """서버 쪽 문제(500, 503, 529 등). 잠시 뒤에는 될 수 있다."""


class BadRequestError(APIError):
    """요청이 잘못되었다(400). 다시 보내도 같은 결과다."""


class ClientSetupError(Exception):
    """클라이언트의 설정(API 키 등)이 잘못되어 어떤 요청도 성공할 수 없다.

    APIError가 아니므로 조각 하나의 실패로 기록되지 않고 전체를 멈춘다.
    """


RETRYABLE: tuple[type[Exception], ...] = (APITimeoutError, RateLimitError, ServerError)
```

7장의 `async_retry.py` 윗부분을 그대로 옮기고, 재시도 데코레이터와 따로 떼어 냈다. 오류의 종류는 `retry`, `clients`, `core`, `anthropic_client`가 모두 쓰므로 누구에게도 기대지 않는 맨 아래에 둔다.

새로 더한 것은 `ClientSetupError` 하나다. **`APIError`를 물려받지 않은 것이 핵심이다.** `summarize_piece()`는 `except (APIError, ValidationError)`로 조각의 실패를 잡아 `error` 레코드로 바꾼다. `ClientSetupError`는 이 그물에 걸리지 않고 빠져나가 맨 위의 `cli`까지 올라간다. 9.1.3의 "모든 조각이 똑같이 실패할 오류는 전체를 멈춘다"를 **예외 클래스의 계층**으로 표현한 것이다. 어디서 잡힐지가 클래스를 어디에 두느냐로 정해진다(기초 과정 6장).

`src/docsum/models.py`

```python
"""데이터의 모양 — 요약할 조각, LLM이 돌려줄 요약, 결과 파일의 한 줄."""

from dataclasses import dataclass

from pydantic import BaseModel, Field


@dataclass(frozen=True)
class Piece:
    """요약할 조각 하나. chunk는 파일 안에서 1부터 센 번호다."""

    file: str
    chunk: int
    text: str


class Summary(BaseModel):
    """LLM이 조각마다 돌려주어야 하는 요약."""

    summary: str = Field(min_length=1, max_length=200, description="200자 이내의 요약")
    keywords: list[str] = Field(
        default_factory=list, max_length=3, description="핵심어 3개 이하"
    )


class Record(BaseModel):
    """결과 파일의 한 줄. 성공하면 summary와 keywords가, 실패하면 error가 있다."""

    file: str
    chunk: int
    summary: str | None = None
    keywords: list[str] | None = None
    error: str | None = None

    @property
    def ok(self) -> bool:
        return self.error is None
```

모양이 셋인데 만드는 방법이 둘이다. 5.6.8의 선택 기준을 그대로 적용했다.

- **`Piece`는 데이터 클래스다.** 우리 코드가 우리 코드에 넘기는 값이다. 바깥에서 들어오지 않으므로 실행 중에 검증할 필요가 없다. `frozen=True`로 만든 뒤에 바꿀 수 없게 했다. 조각은 동시에 여러 코루틴이 들고 다니는데, 누가 중간에 `piece.text`를 바꾸면 찾기 어려운 버그가 된다.
- **`Summary`는 Pydantic 모델이다.** LLM의 답, 즉 **바깥에서 들어오는** 값을 검증한다. 7장과 같다.
- **`Record`도 Pydantic 모델이다.** 우리가 만드는 값이지만 파일로 **나가서** 다른 프로그램이 읽는다. `model_dump_json()`으로 한 줄의 JSON을 쓰고, 읽는 쪽은 `Record.model_validate_json(줄)`로 검증한다. 8장 `textchunk`의 `Record`와 같은 생각이다(8.3.3). 성공과 실패가 한 클래스이고 `error`가 있느냐로 구별한다. `ok` 프로퍼티(기초 과정 5.2.6)는 그 판단을 이름 붙여 한 곳에 둔 것이다.

> **성공과 실패를 클래스 둘로 나누면?**
> `Success(file, chunk, summary, keywords)`와 `Failure(file, chunk, error)`로 나누고 `type Record = Success | Failure`로 쓸 수도 있다. 그러면 "성공했는데 `error`도 있는" 이상한 레코드를 아예 만들 수 없다. 대신 결과 파일을 읽는 쪽이 어느 클래스로 검증할지 먼저 알아야 하고, 2장의 `match` 문이나 Pydantic의 판별 공용체(discriminated union)를 써야 한다. 이 도구에서는 단순한 쪽을 골랐다. 이런 결정이 9.8.1의 설계 노트에 들어갈 거리다.

### 9.2.3 `chunking.py`와 `prompts.py`

`src/docsum/chunking.py`

```python
"""글을 문단 단위로 묶어 조각을 만든다 — 3장 chunking.py를 옮겨 왔다."""

from collections.abc import Iterable, Iterator


def paragraphs(lines: Iterable[str]) -> Iterator[str]:
    """빈 줄로 나뉜 문단을 하나씩 내놓는다. 문단 안의 줄은 공백 하나로 잇는다."""
    buffer: list[str] = []
    for line in lines:
        line = line.strip()
        if line:
            buffer.append(line)
        elif buffer:
            yield " ".join(buffer)
            buffer = []
    if buffer:
        yield " ".join(buffer)


def split(text: str, size: int) -> Iterator[str]:
    """text를 size글자씩 자른다."""
    for start in range(0, len(text), size):
        yield text[start : start + size]


def chunk_paragraphs(paras: Iterable[str], max_chars: int) -> Iterator[str]:
    """문단을 이어 붙여 max_chars를 넘지 않는 조각을 만든다. 긴 문단은 잘라서 넣는다.

    max_chars가 1보다 작으면 ValueError를 일으킨다.
    """
    if max_chars < 1:
        raise ValueError(f"max_chars는 1 이상이어야 한다: {max_chars}")
    current = ""
    for para in paras:
        for piece in split(para, max_chars):
            if current and len(current) + 1 + len(piece) > max_chars:
                yield current
                current = ""
            current = f"{current} {piece}" if current else piece
    if current:
        yield current
```

3.4.6의 `paragraphs()`와 `chunk_paragraphs()`에 타입 힌트를 붙였다. 8장 실습 8-9에서 `textchunk`에 옮긴 것과 같다. 3장의 `chunk()`는 겹침(`overlap`)까지 다뤘는데, 여기서는 겹침이 필요 없어서 더 단순한 `split()`으로 바꿨다.

세 함수 모두 **제너레이터**다. 9.3.2에서 `paragraphs(f)`에 열린 파일 객체를 넘긴다. 파일 객체는 줄을 하나씩 내놓는 이터레이터이므로(3.1.4), 파일 → 줄 → 문단 → 조각이 3.4.2의 파이프라인처럼 이어진다.

`chunk_paragraphs()`의 `max_chars` 검사에는 함정이 하나 있다. 제너레이터 함수는 부를 때가 아니라 **처음 값을 꺼낼 때** 본문을 실행한다(3.2.3). 그래서 `chunk_paragraphs(paras, 0)`을 불러도 바로 `ValueError`가 나지 않고, `list()`나 `for`로 꺼낼 때 난다. 테스트에서 `list(chunk_paragraphs(["가나다"], 0))`처럼 꺼내야 하는 이유다(9.5.1).

> **`textchunk`를 의존성으로 쓰지 않은 이유**
> 8장에서 같은 함수를 `textchunk` 패키지에 넣었다. `dependencies`에 `textchunk-gildong`을 적으면 복사하지 않아도 된다. 그런데 `textchunk-gildong`은 TestPyPI에만 있다. 실제 PyPI에 없는 패키지에 기대면 이 도구를 설치하는 사람 누구도 설치할 수 없다. 의존성은 **쓰는 사람이 받을 수 있는 곳에 있어야** 한다. 함수 세 개는 복사하는 편이 낫다고 판단했다. 이 결정도 설계 노트에 남긴다.

`src/docsum/prompts.py`

```python
"""프롬프트를 만들고 LLM의 답을 검증한다."""

import json
from functools import cache

from docsum.models import Summary


@cache
def schema_text() -> str:
    """Summary의 JSON 스키마를 글자로 만든다. 처음 한 번만 만들고 그 뒤로는 재사용한다."""
    return json.dumps(Summary.model_json_schema(), ensure_ascii=False)


def build_prompt(text: str) -> str:
    """조각 하나를 요약해 Summary의 JSON 스키마에 맞는 JSON만 답하라는 프롬프트."""
    return (
        "다음 글을 요약해 이 JSON 스키마에 맞는 JSON만 답하라.\n"
        f"{schema_text()}\n\n<글>\n{text}\n</글>"
    )


def parse_summary(answer: str) -> Summary:
    """응답에서 첫 '{'부터 마지막 '}'까지를 잘라 Summary로 검증한다.

    검증하지 못하면 ValidationError를 일으킨다.
    """
    start, end = answer.find("{"), answer.rfind("}")
    if start != -1 and end != -1:
        answer = answer[start : end + 1]
    return Summary.model_validate_json(answer)
```

7장의 `build_prompt()`는 조각마다 `Summary.model_json_schema()`를 부르고 `json.dumps()`로 글자를 만들었다. 조각이 천 개면 같은 글자를 천 번 만든다. 스키마는 프로그램이 도는 동안 바뀌지 않으므로 4.4.1의 **`functools.cache`**로 한 번만 만든다. 매개변수가 없는 함수에 `@cache`를 붙이면 "처음 부를 때 계산하고, 그 뒤로는 기억해 둔 값을 돌려주는" 함수가 된다. 4.4.3의 주의, "결과가 입력만으로 정해지는 함수에만 쓴다"를 만족한다.

그런데 이 캐시가 정말 필요할까? 스키마 하나를 만드는 데는 1밀리초도 걸리지 않고, LLM 호출 하나는 몇 초가 걸린다. 솔직히 말하면 **속도 때문은 아니다.** 프롬프트에 들어갈 스키마 글자가 프로그램 전체에서 **한 번 정해진 같은 값**이라는 것을 코드로 드러내기 위해서다. 테스트로도 확인한다(`schema_text() is schema_text()`, 9.5.1). 이렇게 "왜 썼는가"를 정직하게 말할 수 있는지가 9.9에서 돌아볼 거리다.

### 9.2.4 `retry.py` — `print()`를 `on_retry`로

`src/docsum/retry.py`

```python
"""비동기 함수용 재시도 데코레이터 — 7장 async_retry.py에서 옮기고 print()를 on_retry로 바꿨다."""

import asyncio
import functools
import random
from collections.abc import Awaitable, Callable, Coroutine
from typing import Any

from docsum.errors import RETRYABLE

type AsyncFunc[**P, R] = Callable[P, Coroutine[Any, Any, R]]
type OnRetry = Callable[[int, Exception, float], None]


def async_retry[**P, R](
    times: int = 3,
    delay: float = 1.0,
    backoff: float = 2.0,
    jitter: float = 0.0,
    exceptions: tuple[type[Exception], ...] = RETRYABLE,
    sleep: Callable[[float], Awaitable[None]] = asyncio.sleep,
    rand: Callable[[], float] = random.random,
    on_retry: OnRetry | None = None,
) -> Callable[[AsyncFunc[P, R]], AsyncFunc[P, R]]:
    """exceptions의 예외가 나면 times번까지 시도하는 비동기 데코레이터를 만든다.

    다시 시도하기 전에 on_retry(몇 번째 실패, 예외, 기다릴 초)를 부르고 await sleep(초)로 기다린다.
    times가 1보다 작으면 ValueError를 일으킨다.
    """
    if times < 1:
        raise ValueError(f"times는 1 이상이어야 한다: {times}")

    def decorator(func: AsyncFunc[P, R]) -> AsyncFunc[P, R]:
        @functools.wraps(func)
        async def wrapper(*args: P.args, **kwargs: P.kwargs) -> R:
            for attempt in range(1, times + 1):
                try:
                    return await func(*args, **kwargs)
                except exceptions as e:
                    if attempt == times:
                        raise
                    retry_after = getattr(e, "retry_after", None)
                    if retry_after is not None:
                        wait = retry_after
                    else:
                        wait = delay * backoff ** (attempt - 1) + jitter * rand()
                    if on_retry is not None:
                        on_retry(attempt, e, wait)
                    await sleep(wait)
            raise AssertionError("여기에 오지 않는다")

        return wrapper

    return decorator
```

7.4.5의 `async_retry()`에서 바뀐 곳은 두 군데다.

- 매개변수 `on_retry: OnRetry | None = None`이 생겼다. `OnRetry`는 "몇 번째 실패인지(`int`), 예외(`Exception`), 기다릴 초(`float`)를 받고 아무것도 돌려주지 않는 함수"다. 5.4.4의 `type` 별칭 문으로 이름을 붙였다.
- `print(f"  [재시도] ...")`가 `if on_retry is not None: on_retry(attempt, e, wait)`로 바뀌었다.

**왜 `print()`를 뺐는가.** 이 데코레이터는 이제 **라이브러리**의 일부다. `from docsum import summarize_all`로 쓰는 사람의 프로그램이 웹 서버라면, 재시도할 때마다 서버의 표준 출력에 글자가 찍힌다. 그 사람은 끌 방법도 없다. 결과를 표준 출력으로 내보내는 명령행 도구라면 더 나쁘다. `textchunk`에서 "결과는 표준 출력, 안내는 표준 오류"를 지켰는데(8.3.3), 7장의 `print()`는 표준 **출력**에 찍혔다. `summarize-docs docs > out.jsonl`로 결과를 파일로 돌리면 재시도 메시지가 JSONL 사이에 섞인다.

그래서 **무엇을 알릴지는 라이브러리가, 어디에 어떻게 보여 줄지는 쓰는 쪽이** 정하게 나눴다. 알릴 일이 생기면 받은 함수를 부를 뿐이다. 이런 함수를 **콜백**(callback)이라고 한다. 우리 명령은 9.4.1에서 표준 오류에 출력하는 함수를 넘기고, 테스트는 리스트에 기록하는 함수를 넘기고, 아무것도 넘기지 않으면 조용하다. 6.5.2의 의존성 주입, 7.7.2의 `sleep` 주입과 같은 생각을 **알림**에 적용한 것이다.

> **더 큰 프로그램에서는 `logging`**
> 라이브러리가 "무슨 일이 있었는지" 남기는 표준 방법은 표준 라이브러리의 **`logging`** 모듈이다(기초 과정 8장의 표준 라이브러리 표). 라이브러리는 `logger = logging.getLogger(__name__)`을 만들고 `logger.warning("...")`로 기록만 하고, 그 기록을 화면에 보일지, 파일에 남길지, 버릴지는 프로그램 쪽에서 설정한다. anthropic, httpx 같은 SDK도 이렇게 한다. 이 도구에서는 이 과정에서 배운 콜백으로 같은 나눔을 했다. 알릴 일이 많아지고 단계(디버그, 정보, 경고)를 나눌 필요가 생기면 `logging`으로 옮겨 간다.

### 9.3.1 `clients.py` — 약속과 가짜

`src/docsum/clients.py`

```python
"""LLM 클라이언트의 약속과, API 키 없이 시험하는 가짜 클라이언트."""

import asyncio
import random
from typing import Protocol

from docsum.errors import RateLimitError
from docsum.models import Summary

DEFAULT_MODEL = "claude-opus-5-5"


class AsyncLLMClient(Protocol):
    async def complete(self, prompt: str, *, max_tokens: int = 1024) -> str: ...


def fake_answer(prompt: str) -> str:
    """프롬프트의 <글> 부분에서 앞 40글자를 요약으로, 두 글자 이상인 낱말 셋을 핵심어로 삼은 JSON."""
    text = prompt.rpartition("<글>\n")[2].removesuffix("\n</글>")
    summary = text if len(text) <= 40 else text[:39] + "…"
    keywords = list(dict.fromkeys(word for word in text.split() if len(word) >= 2))
    return Summary(summary=summary, keywords=keywords[:3]).model_dump_json()


class RandomLLM:
    """무작위로 늦게 답하고 가끔 실패하는 가짜 클라이언트.

    호출마다 slow_rate의 확률로 10초를 기다리고(시간 제한에 걸린다),
    rate_limit_rate의 확률로 RateLimitError를 일으키고,
    bad_answer_rate의 확률로 JSON이 아닌 답을 돌려준다.
    나머지는 delay 범위의 초만큼 기다린 뒤 fake_answer()를 돌려준다.
    """

    def __init__(
        self,
        seed: int | None = None,
        *,
        delay: tuple[float, float] = (0.2, 0.6),
        slow_rate: float = 0.05,
        rate_limit_rate: float = 0.05,
        bad_answer_rate: float = 0.02,
    ) -> None:
        self.rand = random.Random(seed)
        self.delay = delay
        self.slow_rate = slow_rate
        self.rate_limit_rate = rate_limit_rate
        self.bad_answer_rate = bad_answer_rate
        self.calls = 0

    async def complete(self, prompt: str, *, max_tokens: int = 1024) -> str:
        self.calls += 1
        roll = self.rand.random()
        if roll < self.slow_rate:
            await asyncio.sleep(10.0)
        elif roll < self.slow_rate + self.rate_limit_rate:
            raise RateLimitError("요청 한도 초과", retry_after=0.5)
        await asyncio.sleep(self.rand.uniform(*self.delay))
        if roll >= 1 - self.bad_answer_rate:
            return "죄송합니다. 이 글은 요약할 수 없습니다."
        return fake_answer(prompt)
```

- **`AsyncLLMClient`** — 7장 실습 7-8의 프로토콜 그대로다. 이 패키지의 모든 코드는 실제 클라이언트가 아니라 이 **약속**에 기대어 쓴다(5.5.4). 9.7의 `AnthropicLLM`도, 테스트의 `ScriptedLLM`도 이 클래스를 물려받지 않는다. `complete()`의 모양만 같으면 된다.
- **`DEFAULT_MODEL`** — 실제 클라이언트가 쓸 모델 이름이다. `anthropic_client.py`가 아니라 여기 둔 것은, `cli`가 `--model`의 기본값을 도움말에 보여 줄 때 anthropic 패키지 없이도 읽을 수 있어야 하기 때문이다.
- **`RandomLLM`** — 7장 `run_summarizer.py`의 가짜를 **제품의 일부**로 승격했다. `--client fake`가 이것을 쓴다. 그래서 7장 것보다 조금 더 갖췄다. 지연과 실패 확률을 매개변수로 받아 테스트에서 `delay=(0.0, 0.0)`처럼 기다림 없이 쓸 수 있고(9.5.1), 2%의 확률로 JSON이 아닌 답도 돌려준다. 9.1.3의 실패 표에 있는 실패를 모두 일으킬 수 있는 가짜다.
- **`fake_answer()`** — 7장의 가짜는 늘 `"가짜 요약"`을 돌려줬다. 이번에는 프롬프트의 `<글>` 부분을 꺼내 앞 40글자를 요약이라고 돌려준다. 결과 파일을 열었을 때 어느 조각의 답인지 눈으로 알 수 있다. 가짜도 **쓸모 있는 가짜**가 낫다.
- **`dict.fromkeys(...)`** — 중복을 없애면서 **처음 나온 순서는 지키는** 관용구다. 집합(`set`)은 중복을 없애지만 순서를 지키지 않는다(2.2.4). 딕셔너리의 키는 중복될 수 없고 넣은 순서를 지키므로, 키만 꺼내면 순서가 지켜진 "중복 없는 목록"이 된다. 안에 들어간 것은 3.3.2의 괄호를 생략한 제너레이터 표현식이다.

### 9.3.2 `storage.py` — 폴더에서 조각까지

`src/docsum/storage.py`

```python
"""파일을 다룬다 — 폴더의 글 파일을 조각으로 읽기, 결과를 JSONL로 만들기."""

from collections.abc import Iterable
from pathlib import Path

from docsum.chunking import chunk_paragraphs, paragraphs
from docsum.models import Piece, Record


class InputError(Exception):
    """입력 폴더나 파일을 읽을 수 없다. 메시지는 사용하는 사람에게 그대로 보여 준다."""


def read_pieces(path: Path, max_chars: int) -> list[Piece]:
    """파일 하나를 문단 단위로 묶은 조각의 리스트로 만든다. 조각 번호는 1부터 센다."""
    try:
        with path.open(encoding="utf-8") as f:
            texts = list(chunk_paragraphs(paragraphs(f), max_chars))
    except UnicodeDecodeError as e:
        raise InputError(f"{path.name}: UTF-8로 읽을 수 없다") from e
    except OSError as e:
        raise InputError(f"{path.name}: 읽을 수 없다 ({e.strerror})") from e
    return [
        Piece(path.name, number, text) for number, text in enumerate(texts, start=1)
    ]


def load_pieces(folder: Path, max_chars: int) -> list[Piece]:
    """folder의 .txt 파일을 이름 순으로 읽어, 모든 파일의 조각을 차례로 담은 리스트를 돌려준다."""
    if not folder.is_dir():
        raise InputError(f"{folder}: 폴더가 아니다")
    return [
        piece
        for path in sorted(folder.glob("*.txt"))
        for piece in read_pieces(path, max_chars)
    ]


def to_jsonl(records: Iterable[Record]) -> str:
    """레코드를 한 줄에 하나씩 JSON으로 만든다. 값이 None인 필드는 쓰지 않는다."""
    return "".join(f"{r.model_dump_json(exclude_none=True)}\n" for r in records)
```

**`read_pieces()`** — `with path.open(...) as f:` 안에서 `paragraphs(f)`에 파일 객체를 그대로 넘긴다. 파일 → 줄 → 문단 → 조각이 제너레이터로 이어지고, 맨 끝의 `list()`가 그 사슬을 끝까지 당긴다. `list()`를 `with` 블록 **안에서** 부르는 것이 중요하다. 제너레이터는 값을 꺼낼 때 비로소 파일을 읽으므로(3.2.5), `with` 블록을 벗어나 파일이 닫힌 뒤에 꺼내면 `ValueError: I/O operation on closed file`이 난다. 3.4.8의 "파이프라인을 쓸 때 주의할 것"이다.

같은 이유로 `UnicodeDecodeError`도 `open()`이 아니라 **`list()`가 줄을 읽는 순간에** 난다. `try` 블록이 `with` 문 전체를 감싸야 하는 이유다. 오류는 8.3.3의 `textchunk`처럼 셋으로 나눴는데, 여기서는 메시지를 `print()`하지 않고 **`InputError`로 바꿔 올려보낸다.** `storage`는 화면을 모른다. 메시지를 보여 줄지, 종료 코드를 몇으로 할지는 `cli`가 정한다. `raise ... from e`로 원래 예외를 이어 두었으므로(기초 과정 6.2.5), 디버깅할 때는 원인까지 볼 수 있다.

**`load_pieces()`** — 7장 실습 7-8의 힌트에서 "바깥 반복문 두 개를 컴프리헨션 하나로 합친다"고 한 그 함수다. 2.1.5의 중첩 컴프리헨션을 읽는 순서대로, 앞의 `for`가 바깥 반복이다. "정렬한 `.txt` 파일마다, 그 파일의 조각마다, 조각을 담는다." 두 겹이지만 각 `for`가 한 가지 일만 하므로 2.3.2의 "두 겹 이상의 중첩은 반복문으로 되돌린다"에 걸리지 않는다고 판단했다. 파일 하나를 조각으로 만드는 복잡한 일은 `read_pieces()`라는 이름 뒤에 숨겼기 때문이다. 판단이 다르다면 반복문으로 써도 된다.

조각 번호를 붙이는 `enumerate(texts, start=1)`가 `load_pieces()`가 아니라 `read_pieces()`에 있다. 번호는 **파일마다** 1부터 다시 센다. 7장에서는 이 일을 컴프리헨션 한 줄에 넣었는데, 이름 붙은 함수로 떼어 내니 파일마다 다시 센다는 것이 더 잘 드러난다.

**`to_jsonl()`** — 7장의 `write_jsonl()`은 파일에 직접 썼다. 이번에는 **글자만 만들고** 쓰는 일은 `cli`에 맡겼다. 결과를 파일에 쓸지 표준 출력에 쓸지는 `-o` 옵션, 즉 명령의 일이기 때문이다. `exclude_none=True`는 값이 `None`인 필드를 빼라는 뜻이다. 그래서 성공한 줄에는 `error`가, 실패한 줄에는 `summary`와 `keywords`가 나오지 않는다(9.1.2의 실행 예). `json.dumps(..., ensure_ascii=False)`를 따로 챙길 필요도 없다. `model_dump_json()`은 처음부터 한글을 그대로 쓴다(8.3.3).

### 9.3.3 `core.py` — 조각 하나, 그리고 여럿을 동시에

`src/docsum/core.py`

```python
"""요약의 흐름 — 조각 하나를 요약하기, 여러 조각을 동시에 요약하기."""

import asyncio
from collections.abc import Awaitable, Callable, Sequence

from pydantic import ValidationError

from docsum.clients import AsyncLLMClient
from docsum.errors import APIError, APITimeoutError
from docsum.models import Piece, Record
from docsum.prompts import build_prompt, parse_summary
from docsum.retry import async_retry

type Sleep = Callable[[float], Awaitable[None]]
type OnPieceRetry = Callable[[Piece, int, Exception, float], None]


async def summarize_piece(
    client: AsyncLLMClient,
    piece: Piece,
    *,
    attempt_timeout: float = 30.0,
    retries: int = 3,
    sleep: Sleep = asyncio.sleep,
    on_retry: OnPieceRetry | None = None,
) -> Record:
    """조각 하나의 요약을 요청해 Record를 돌려준다. 예외를 일으키지 않는다.

    한 번의 요청은 attempt_timeout초까지 기다리고, 넘으면 APITimeoutError로 바꾼다.
    다시 시도할 수 있는 API 오류는 retries번까지 시도한다. 기다릴 때는 sleep을 쓰고,
    다시 시도하기 전에 on_retry(조각, 몇 번째 실패, 예외, 기다릴 초)를 부른다.
    끝내 API 오류가 나거나 답의 형식이 틀리면 error가 있는 Record다.
    """

    def report(attempt: int, error: Exception, wait: float) -> None:
        if on_retry is not None:
            on_retry(piece, attempt, error, wait)

    @async_retry(times=retries, sleep=sleep, on_retry=report)
    async def ask(prompt: str) -> str:
        try:
            async with asyncio.timeout(attempt_timeout):
                return await client.complete(prompt)
        except TimeoutError as e:
            raise APITimeoutError(f"{attempt_timeout}초 안에 답이 없다") from e

    try:
        summary = parse_summary(await ask(build_prompt(piece.text)))
    except (APIError, ValidationError) as e:
        return Record(
            file=piece.file, chunk=piece.chunk, error=f"{type(e).__name__}: {e}"
        )
    return Record(
        file=piece.file,
        chunk=piece.chunk,
        summary=summary.summary,
        keywords=summary.keywords,
    )


async def summarize_all(
    client: AsyncLLMClient,
    pieces: Sequence[Piece],
    *,
    max_concurrency: int = 5,
    attempt_timeout: float = 30.0,
    retries: int = 3,
    sleep: Sleep = asyncio.sleep,
    on_retry: OnPieceRetry | None = None,
) -> list[Record]:
    """pieces를 최대 max_concurrency개까지 동시에 요약해 pieces와 같은 순서의 Record 리스트를 돌려준다.

    max_concurrency가 1보다 작으면 ValueError를 일으킨다.
    """
    if max_concurrency < 1:
        raise ValueError(f"max_concurrency는 1 이상이어야 한다: {max_concurrency}")
    limit = asyncio.Semaphore(max_concurrency)

    async def limited(piece: Piece) -> Record:
        async with limit:
            return await summarize_piece(
                client,
                piece,
                attempt_timeout=attempt_timeout,
                retries=retries,
                sleep=sleep,
                on_retry=on_retry,
            )

    return await asyncio.gather(*(limited(piece) for piece in pieces))
```

7장 실습 7-8의 `summarize_piece()`와 `summarize_folder()`를 채운 모양과 거의 같다. 다른 곳만 본다.

**클로저 둘, 데코레이터 하나.** `summarize_piece()` 안에 함수가 둘 있다.

- `report()` — 재시도 데코레이터는 `on_retry(몇 번째, 예외, 초)`를 부르는데, 명령의 화면에는 **어느 조각**이 실패했는지도 보여 주고 싶다. 데코레이터는 조각을 모른다. 그래서 바깥의 `piece`와 `on_retry`를 기억하는 클로저(4.1.3)를 만들어, 받은 세 값 앞에 `piece`를 붙여 넘긴다. 인자의 모양이 다른 두 함수 사이를 이어 주는 **어댑터**다.
- `ask()` — 4장의 데코레이터, 7장의 시간 제한, 바깥의 `client`와 `attempt_timeout`을 기억하는 클로저가 한 함수에 모였다. `ask()`를 `summarize_piece()` 안에 만드는 이유는, `async_retry(...)`에 넘길 `retries`, `sleep`, `report`가 **부를 때마다** 달라질 수 있기 때문이다. 모듈 맨 위에서 `@async_retry()`로 한 번 감싸 두면 그 값들을 바꿀 수 없다.

시간 제한은 `ask()` **안에서**, 즉 재시도의 안쪽에서 건다. 7.4.6의 "시간 제한은 시도 하나마다"다.

**`timeout`이 아니라 `attempt_timeout`.** 7장에서는 매개변수 이름이 `timeout`이었다. 그 이름 그대로 옮기고 `ruff check .`을 실행하면 이렇게 나온다.

```
ASYNC109 Async function definition with a `timeout` parameter
  --> src/docsum/core.py:22:5
   |
22 |     timeout: float = 30.0,
   |     ^^^^^^^^^^^^^^^^^^^^^
   |
help: Use `asyncio.timeout` instead
```

`ASYNC109`는 "비동기 함수가 `timeout` 매개변수를 받지 말고, 부르는 쪽이 `async with asyncio.timeout(...)`으로 감싸게 하라"는 규칙이다. 비동기에서는 어떤 코루틴이든 바깥에서 시간 제한을 걸 수 있으므로(7.4.1), 함수마다 `timeout`을 따로 받으면 바깥의 제한과 안의 제한이 겹쳐 헷갈리기 때문이다.

그런데 이 함수의 시간 제한은 바깥에서 걸 수 **없다.** 바깥에서 `async with asyncio.timeout(30):`으로 `summarize_piece()`를 감싸면 "재시도를 다 합쳐 30초"가 된다(7.4.6). 우리가 원하는 것은 "시도 한 번에 30초"다. 그래서 규칙의 권고는 따르지 않되, 규칙이 걱정하는 **헷갈림**은 없앤다. 이름을 `attempt_timeout`으로 바꿔 "전체가 아니라 시도 한 번의 제한"이라는 뜻을 이름에 담았다. 규칙도 더 이상 지적하지 않는다. 린트의 경고는 "고쳐라"가 아니라 **"이유가 있는지 생각해 보라"**다(6.6.3). 이유가 있으면 이름이나 주석으로 남기고, `# noqa`는 이름으로도 설명할 수 없을 때 쓴다.

**파일 입출력이 사라졌다.** 7장의 `summarize_folder()`는 `asyncio.to_thread()`로 `load_pieces()`와 `write_jsonl()`을 불렀다. 비동기 함수 안에서 파일을 읽으면 이벤트 루프를 붙잡기 때문이었다(7.6.5). `summarize_all()`은 이미 만든 조각의 리스트를 받아 레코드의 리스트를 돌려줄 뿐이다. 파일은 `cli`가 **이벤트 루프를 시작하기 전에** 읽고, **끝난 뒤에** 쓴다(9.4.1). 이벤트 루프 밖에서 하는 일은 이벤트 루프를 붙잡을 수 없으므로 `to_thread()`가 필요 없다. **비동기로 만드는 부분을 작게** 하면 신경 쓸 것도 줄어든다.

**`gather()`인가, `TaskGroup`인가.** `summarize_piece()`는 조각의 실패를 모두 `Record`로 바꾸므로, 7.3.7의 표대로 `gather()`로 충분하다. 결과의 순서도 `gather()`가 지켜 준다. 그런데 이제 `summarize_piece()`가 잡지 않는 예외가 하나 있다. `ClientSetupError`다(9.2.2). 조각 하나에서 이 예외가 나면 `gather()`는 그 예외를 바로 올려보내고, `summarize_all()`을 부른 `asyncio.run()`은 아직 끝나지 않은 나머지 태스크를 모두 취소한 뒤 끝난다(7.2.3). `TaskGroup`이었다면 예외가 `ExceptionGroup`에 싸여 올라오므로 `cli`가 `except*`로 잡아야 한다(7.3.6). 이 차이는 실습 9-3에서 직접 확인한다.

이제 `__init__.py`의 주석을 푼다. `python -c "import docsum; print(docsum.__all__)"`이 다섯 이름을 출력하면 된다.

### 9.3.4 `testing.py` — 테스트용 가짜를 패키지에

7장에서는 테스트용 가짜를 `test_async_summarizer.py`(`ScriptedAsyncLLM`, `Slow`)와 `async_fakes.py`(`RecordingSleep`)에 두었다. 테스트 파일에서 `from async_fakes import RecordingSleep`으로 가져왔다. 같은 일을 `tests/fakes.py`를 만들어 하려고 하면 막힌다.

```
ImportError while importing test module '.../docsum/tests/test_core.py'.
E   ModuleNotFoundError: No module named 'fakes'
```

`--import-mode=importlib`(8.2.5) 때문이다. 이 방식에서 pytest는 테스트 파일을 모듈 검색 경로에 넣지 않고 불러온다. 그래서 테스트 파일이 같은 폴더의 다른 파일을 이름으로 `import`할 수 없다. 테스트가 **설치된 패키지만** `import`하게 하려고 고른 설정이 여기서도 효과를 낸다.

방법은 몇 가지다. 픽스처라면 `conftest.py`에 두면 된다. pytest가 `conftest.py`를 알아서 찾아 읽기 때문이다(6.4.3). 하지만 클래스를 `conftest.py`에 두고 테스트 파일에서 `import`할 수는 없다. 이 도구에서는 가짜를 **패키지 안의 `testing` 모듈**로 옮겼다.

`src/docsum/testing.py`

```python
"""테스트에서 쓰는 가짜 객체 — 이 패키지로 만든 코드를 테스트할 때도 쓸 수 있다."""

import asyncio
from dataclasses import dataclass

OK = '{"summary": "요약", "keywords": ["핵심"]}'


@dataclass
class Slow:
    """seconds초 기다렸다가 answer를 돌려주라는 대본 항목."""

    seconds: float
    answer: str = OK


class ScriptedLLM:
    """프롬프트에 든 표시 글자마다 정해 둔 응답·예외·지연을 차례로 내놓는 가짜 비동기 클라이언트.

    정해 둔 것이 없거나 다 쓴 조각에는 delay초 기다린 뒤 OK를 돌려준다.
    active는 지금 처리 중인 요청 수, peak는 그 최댓값이다.
    """

    def __init__(
        self,
        script: dict[str, list[str | Exception | Slow]] | None = None,
        *,
        delay: float = 0.0,
    ) -> None:
        self.script = {mark: list(items) for mark, items in (script or {}).items()}
        self.delay = delay
        self.prompts: list[str] = []
        self.active = 0
        self.peak = 0

    async def complete(self, prompt: str, *, max_tokens: int = 1024) -> str:
        self.prompts.append(prompt)
        self.active += 1
        self.peak = max(self.peak, self.active)
        try:
            item = self._next_item(prompt)
            if isinstance(item, Slow):
                await asyncio.sleep(item.seconds)
                return item.answer
            await asyncio.sleep(self.delay)
            if isinstance(item, Exception):
                raise item
            return item
        finally:
            self.active -= 1

    def _next_item(self, prompt: str) -> str | Exception | Slow:
        for mark, items in self.script.items():
            if mark in prompt and items:
                return items.pop(0)
        return OK


class RecordingSleep:
    """기다리지 않고, 기다리려던 시간만 기록하는 가짜 asyncio.sleep."""

    def __init__(self) -> None:
        self.waits: list[float] = []

    async def __call__(self, seconds: float) -> None:
        self.waits.append(seconds)
        await asyncio.sleep(0)
```

7장의 코드를 그대로 옮겼다. 이름만 `ScriptedAsyncLLM`에서 `ScriptedLLM`으로 줄였다. 이 패키지에는 동기 클라이언트가 없으므로 "비동기"를 이름에 붙일 이유가 없다.

가짜를 패키지에 넣으면 **휠에도 들어간다.** 설치한 사람도 `from docsum.testing import ScriptedLLM`으로 쓸 수 있다는 뜻이다. 이것을 장점으로 본다. `docsum`의 `summarize_all()`을 자기 프로그램에서 쓰는 사람은, 자기 코드를 테스트할 때 실제 LLM 대신 끼울 가짜가 필요하다. 7.7.3의 `httpx.MockTransport`가 바로 그렇게, 라이브러리가 **테스트용 도구를 함께 내놓는** 예였다. 다만 공개한 것은 쉽게 바꿀 수 없다(8.5.1). `testing` 모듈의 이름과 클래스도 이제 이 패키지의 약속이다.

> **`tests` 폴더의 파일끼리 `import`하고 싶다면**
> `[tool.pytest.ini_options]`에 `pythonpath = ["tests"]`를 더하면 pytest가 `tests` 폴더를 모듈 검색 경로에 넣는다. 그러면 `tests/fakes.py`를 `from fakes import ...`로 가져올 수 있다. 가짜를 배포하고 싶지 않다면 이 방법을 쓴다. 남의 프로젝트에서 이 설정을 보면 "테스트 도우미 모듈이 `tests` 안에 있구나"로 읽는다.

## 9.4 위층 — 명령

### 9.4.1 `cli.py`

`src/docsum/cli.py`

```python
"""summarize-docs 명령 — 폴더의 글 파일을 동시에 요약해 한 줄에 하나씩 JSON으로 출력한다."""

import argparse
import asyncio
import sys
import time
from collections.abc import Sequence
from pathlib import Path

from docsum import __version__
from docsum.clients import DEFAULT_MODEL, AsyncLLMClient, RandomLLM
from docsum.core import summarize_all
from docsum.errors import ClientSetupError
from docsum.models import Piece
from docsum.storage import InputError, load_pieces, to_jsonl


def build_parser() -> argparse.ArgumentParser:
    parser = argparse.ArgumentParser(
        prog="summarize-docs",
        description="폴더의 .txt 파일을 조각으로 나눠 LLM에게 동시에 요약을 요청하고, "
        "결과를 한 줄에 하나씩 JSON으로 출력한다.",
    )
    parser.add_argument(
        "folder", type=Path, metavar="FOLDER", help="요약할 .txt 파일이 든 폴더(UTF-8)"
    )
    parser.add_argument(
        "-o", "--output", type=Path, help="결과를 저장할 파일. 없으면 화면에 출력한다"
    )
    parser.add_argument(
        "-s",
        "--size",
        type=int,
        default=500,
        help="조각 하나의 최대 글자 수 (기본값: %(default)s)",
    )
    parser.add_argument(
        "-c",
        "--concurrency",
        type=int,
        default=5,
        help="동시에 보낼 요청 수 (기본값: %(default)s)",
    )
    parser.add_argument(
        "--timeout",
        type=float,
        default=30.0,
        help="요청 한 번을 기다릴 초 (기본값: %(default)s)",
    )
    parser.add_argument(
        "--retries",
        type=int,
        default=3,
        help="조각 하나에 요청을 보낼 최대 횟수 (기본값: %(default)s)",
    )
    parser.add_argument(
        "--client",
        choices=["fake", "anthropic"],
        default="fake",
        help="요약을 맡길 클라이언트. fake는 API 키 없이 시험하는 가짜 (기본값: %(default)s)",
    )
    parser.add_argument(
        "--model",
        default=DEFAULT_MODEL,
        help="--client anthropic일 때 쓸 모델 (기본값: %(default)s)",
    )
    parser.add_argument("--seed", type=int, help="가짜 클라이언트의 난수 씨앗")
    parser.add_argument(
        "--version", action="version", version=f"%(prog)s {__version__}"
    )
    return parser


def fail(message: str) -> int:
    """오류 메시지를 표준 오류에 출력하고 종료 코드 1을 돌려준다."""
    print(f"summarize-docs: {message}", file=sys.stderr)
    return 1


def report_retry(piece: Piece, attempt: int, error: Exception, wait: float) -> None:
    print(
        f"  [재시도] {piece.file} {piece.chunk}번 조각: {attempt}번째 실패"
        f"({type(error).__name__}: {error}), {wait:.1f}초 뒤 다시",
        file=sys.stderr,
    )


def main(argv: Sequence[str] | None = None) -> int:
    parser = build_parser()
    args = parser.parse_args(argv)
    if args.size < 1:
        parser.error("--size는 1 이상이어야 한다")
    if args.concurrency < 1:
        parser.error("--concurrency는 1 이상이어야 한다")
    if args.timeout <= 0:
        parser.error("--timeout은 0보다 커야 한다")
    if args.retries < 1:
        parser.error("--retries는 1 이상이어야 한다")

    try:
        pieces = load_pieces(args.folder, args.size)
    except InputError as e:
        return fail(str(e))
    if not pieces:
        return fail(f"{args.folder}: 요약할 .txt 파일이 없다")
    if args.output and not args.output.parent.is_dir():
        return fail(f"{args.output}: 결과를 저장할 폴더가 없다")

    client: AsyncLLMClient
    if args.client == "anthropic":
        try:
            from docsum.anthropic_client import AnthropicLLM
        except ModuleNotFoundError:
            return fail(
                'anthropic 패키지가 없다. pip install "docsum-gildong[anthropic]"으로 설치한다'
            )
        client = AnthropicLLM(args.model)
    else:
        client = RandomLLM(args.seed)

    start = time.perf_counter()
    try:
        records = asyncio.run(
            summarize_all(
                client,
                pieces,
                max_concurrency=args.concurrency,
                attempt_timeout=args.timeout,
                retries=args.retries,
                on_retry=report_retry,
            )
        )
    except ClientSetupError as e:
        return fail(str(e))
    elapsed = time.perf_counter() - start

    output = to_jsonl(records)
    if args.output:
        try:
            args.output.write_text(output, encoding="utf-8")
        except OSError as e:
            return fail(f"{args.output}: 쓸 수 없다 ({e.strerror})")
    else:
        sys.stdout.write(output)

    failed = sum(1 for record in records if not record.ok)
    print(
        f"조각 {len(records)}개: 성공 {len(records) - failed}, 실패 {failed}, "
        f"{elapsed:.1f}초 (동시 {args.concurrency}개)",
        file=sys.stderr,
    )
    return 1 if failed else 0
```

8.3.3의 `textchunk`와 뼈대가 같다. `build_parser()`로 인자의 정의를 따로 두고, `main(argv) -> int`가 인자 리스트를 받아 종료 코드를 돌려준다. 결과는 표준 출력, 안내와 오류는 표준 오류다. 새로 본 것만 짚는다.

**`main()`은 9.1.3의 실패 표를 위에서 아래로 따라간다.** 옵션 검사(종료 코드 2) → 입력 읽기 → 결과를 저장할 폴더 확인 → 클라이언트 만들기 → 요약 → 저장 → 성공과 실패의 수. 표의 한 줄이 코드의 한 덩어리다. 표를 먼저 써 두면 `main()`은 표를 옮겨 적는 일이 된다.

**비동기는 `asyncio.run()` 한 줄뿐이다.** `main()`은 일반 함수다. 파일을 읽고(`load_pieces()`), 이벤트 루프를 한 번 돌려 요약하고(`asyncio.run(summarize_all(...))`), 끝나면 파일을 쓴다(`write_text()`). 9.3.3에서 말한 "파일 입출력은 이벤트 루프 밖에서"가 이 모양이다. `[project.scripts]`의 진입점은 일반 함수여야 하므로(8.3.4), 이 모양은 명령행 도구에 잘 맞는다.

**클라이언트를 고르는 곳은 여기 한 곳이다.** 프로그램 전체에서 `AsyncLLMClient`의 **구체적인 클래스 이름**이 나오는 곳은 `main()`의 이 `if` 문뿐이다. 나머지 코드는 모두 약속(`AsyncLLMClient`)만 안다. 새 클라이언트(예: OpenAI)를 더하려면 `choices`에 이름 하나와 이 `if`에 갈래 하나를 더하면 된다. 이런 곳을 흔히 **조립하는 곳**(composition root)이라고 부른다. 의존성 주입(6.5.2)은 "주입한다"에서 끝나지 않고, **어디서 주입할지 한 곳으로 모으는 것**까지가 설계다.

**`import`를 함수 안에서 한다.** `from docsum.anthropic_client import AnthropicLLM`은 `--client anthropic`을 골랐을 때만 실행된다. 맨 위에 두면 anthropic을 설치하지 않은 사람은 `--client fake`로도 명령을 실행할 수 없다. 모듈을 가져오다 `ModuleNotFoundError`가 나기 때문이다. 이렇게 필요할 때 가져오는 것을 **지연 `import`**(lazy import)라고 한다. 쓰는 곳은 이렇게 **선택 의존성**을 다룰 때로 한정한다. 아무 데서나 함수 안에 `import`를 두면 그 모듈이 무엇에 기대는지 맨 위만 보고는 알 수 없게 된다.

`client: AsyncLLMClient` — 변수의 타입을 먼저 적어 두었다. 이 줄이 없으면 mypy는 첫 대입(`AnthropicLLM(...)`)을 보고 `client`의 타입을 `AnthropicLLM`으로 정하고, `else`의 `RandomLLM(...)` 대입을 오류로 본다. 두 갈래가 모두 **약속**을 만족한다는 것을 타입으로 먼저 말해 두는 것이다(5.2).

**`ClientSetupError`만 잡는다.** `asyncio.run()`을 감싼 `try`는 `ClientSetupError`만 잡는다. `except Exception`으로 모두 잡으면 우리 코드의 버그(`KeyError` 같은)까지 "한 줄 오류"로 숨어 버린다. 버그는 트레이스백으로 보여야 고칠 수 있다(8.3.3).

**`time.perf_counter()`로 잰다.** 마지막 줄에 걸린 시간과 동시 실행 수를 함께 출력한다. 9.6에서 동시 실행 수를 바꿔 가며 비교할 때 이 줄을 읽는다. 4.6.4의 `timer()` 컨텍스트 관리자를 써도 되지만, 잰 값을 다른 출력과 한 줄로 합쳐야 해서 두 줄로 직접 쟀다.

요약할 글이 필요하다. 시험용 글 파일을 만드는 작은 스크립트를 프로젝트 폴더 바로 아래에 둔다. 패키지(`src/docsum`) 밖에 있으므로 휠에는 들어가지 않는다.

`make_samples.py`

```python
"""시험용 글 파일 다섯 개를 samples 폴더에 만든다."""

from pathlib import Path

TOPICS = ["컴프리헨션", "제너레이터", "데코레이터", "타입 힌트", "테스트", "비동기"]


def make_samples(folder: Path) -> None:
    folder.mkdir(exist_ok=True)
    for n in range(1, 6):
        paras = [f"{n}번 문서에서 {topic}에 관한 문단이다. " * 6 for topic in TOPICS]
        text = "\n\n".join(paras) + "\n"
        (folder / f"doc{n}.txt").write_text(text, encoding="utf-8")


if __name__ == "__main__":
    make_samples(Path(__file__).parent / "samples")
```

```
python make_samples.py
summarize-docs samples -s 200 --timeout 2 --seed 32
```

문서마다 문단이 여섯 개이고, 문단 하나는 150글자쯤이다. `-s 200`으로 나누면 문단 둘을 합치면 200글자를 넘으므로 문단 하나가 조각 하나가 된다. 문서 다섯 개에서 조각 30개다.

`--timeout 2`는 시험을 빠르게 하려고 준 것이다. 가짜 클라이언트는 아주 늦을 때 10초를 기다리는데, 기본값 30초로는 시간 제한에 걸리지 않고 10초를 다 기다린다. 시간 제한이 동작하는 모습을 보려면 10초보다 짧게 준다. `--seed 32`는 7장의 `run_summarizer.py`와 같은 씨앗이다.

### 실습 9-4. 명령 만들기

1. `cli.py`, `__main__.py`, `make_samples.py`를 만들고 9.4.3의 명령을 모두 실행해 교재와 비교한다. 재시도 메시지의 순서와 시간은 컴퓨터에 따라 조금 다를 수 있다.
2. `summarize-docs samples -s 200 --timeout 2 --seed 32 > out.jsonl`로 결과를 파일로 돌린다. 터미널에 남은 것은 무엇이고 `out.jsonl`에 들어간 것은 무엇인가? 7장의 `print()`였다면 어떻게 되었을지 9.2.4와 연결해 설명한다. (Windows에서는 8.3.3의 상자처럼 `-o`를 쓰는 것이 안전하다.)
3. `--seed 32`를 주고 같은 명령을 두 번 실행한다. 재시도 메시지와 결과가 같은가? `-c 1`로 두 번 실행하면? 7장 실습 7-8의 "확인할 것"에서 생각한 "난수가 어느 조각의 호출에 쓰이는지는 무엇이 정하는가"로 설명한다.
4. `samples` 폴더에 빈 파일 `empty.txt`와 CP949로 저장한 파일을 하나씩 만들어(8.3.5처럼 `write_bytes("가나다".encode("cp949"))`) 실행한다. 각각 어떻게 되는가? 빈 파일이 결과에 아무 흔적도 남기지 않는 것이 문제라면, 9.1.3의 실패 표에 어떻게 적고 어디를 고칠지 `notes.md`에 적는다. 확인한 뒤 두 파일을 지운다.
5. `main()` 맨 위의 옵션 검사 네 개를 보고, `argparse`만으로 할 수 있는 것과 없는 것을 나눈다. 힌트: `type=`에 "1 이상의 정수로 바꾸고, 아니면 `argparse.ArgumentTypeError`를 일으키는 함수"를 넘길 수 있다. 바꿔 볼지 그대로 둘지 정하고 이유를 적는다.

## 9.5 테스트로 보이기

README의 완료 기준에는 "동시 실행 수 제한·시간 제한·재시도가 의도대로 동작함을 테스트로 보인다", "정상 응답, 형식이 맞지 않는 응답, 시간 초과, 요청 한도 초과를 각각 테스트하고, 네트워크 없이 모든 테스트가 통과한다"가 있다. 이 절의 테스트가 그 증거다. 대부분 7장 실습 7-8의 테스트를 옮긴 것이고, 이번에 새로 생긴 것(콜백, 설정 오류, 명령)의 테스트를 더했다.

실제로는 층을 하나 만들 때마다 그 층의 테스트를 함께 쓴다(기초 과정 10.1.6의 "확인하며"). 교재에서는 한곳에 모아 보여 준다.

### 9.5.1 픽스처와 아래층의 테스트

`tests/conftest.py`

```python
"""여러 테스트 파일이 함께 쓰는 픽스처."""

from pathlib import Path

import pytest

from docsum.testing import RecordingSleep


@pytest.fixture
def sleep() -> RecordingSleep:
    return RecordingSleep()


@pytest.fixture
def docs(tmp_path: Path) -> Path:
    """a.txt(문단 둘), b.txt(문단 하나), memo.md가 든 폴더."""
    folder = tmp_path / "docs"
    folder.mkdir()
    (folder / "b.txt").write_text("나나나\n", encoding="utf-8")
    (folder / "a.txt").write_text("가가가가\n가가\n\n다다다다\n", encoding="utf-8")
    (folder / "memo.md").write_text("요약하지 않는다\n", encoding="utf-8")
    return folder
```

7장에서는 `sleep`과 `docs` 픽스처가 테스트 파일 안에 있었다. 이번에는 여러 테스트 파일이 함께 쓰므로 `conftest.py`에 둔다(6.4.3). `docs`의 `a.txt`는 이제 **문단**이 둘이다. 첫 문단은 두 줄(`가가가가`, `가가`)이 공백 하나로 이어져 7글자가 된다. `b.txt`를 먼저 만드는 것은 7장과 같은 이유다. 만든 순서가 아니라 이름 순으로 읽는지 확인하려는 것이다.

import pytest

from docsum.chunking import chunk_paragraphs, paragraphs


def test_paragraphs_joins_lines_and_splits_on_blank_lines() -> None:

    assert list(paragraphs([])) == []
    assert list(paragraphs(["\n", "  \n"])) == []


def test_chunk_paragraphs_packs_until_limit() -> None:
    paras = ["가나", "다라", "마바사아"]
    assert list(chunk_paragraphs(paras, 5)) == ["가나 다라", "마바사아"]


def test_chunk_paragraphs_splits_long_paragraph() -> None:
    assert list(chunk_paragraphs(["가나다라마바사"], 3)) == ["가나다", "라마바", "사"]


def test_chunk_paragraphs_empty() -> None:
    assert list(chunk_paragraphs([], 5)) == []

마지막 테스트의 `list()`가 9.2.3에서 말한 "제너레이터의 검사는 꺼낼 때 일어난다"를 확인한다. `list()`를 빼면 이 테스트는 실패한다. 예외가 나지 않기 때문이다.

```python
"""prompts의 테스트."""

import pytest
from pydantic import ValidationError

from docsum.models import Summary
from docsum.prompts import build_prompt, parse_summary, schema_text


def test_build_prompt_contains_text_and_schema() -> None:
    prompt = build_prompt("가나다")
    assert "<글>\n가나다\n</글>" in prompt
    assert '"summary"' in prompt


def test_schema_text_is_made_once() -> None:
    assert schema_text() is schema_text()


@pytest.mark.parametrize(
    "answer",
    [
        '{"summary": "요약", "keywords": ["핵심"]}',
        '요약입니다.\n```json\n{"summary": "요약", "keywords": ["핵심"]}\n```',
    ],
)
def test_parse_summary(answer: str) -> None:
    assert parse_summary(answer) == Summary(summary="요약", keywords=["핵심"])


@pytest.mark.parametrize(
    "answer",
    [
        "요약할 수 없습니다.",
        '{"summary": ""}',
        '{"summary": "요약", "keywords": ["가", "나", "다", "라"]}',
    ],
)
def test_parse_summary_rejects(answer: str) -> None:
    with pytest.raises(ValidationError):
        parse_summary(answer)
```

**형식이 맞지 않는 응답**의 테스트가 여기 있다. JSON이 아닌 답, 빈 요약(`min_length=1`), 핵심어가 넷인 답(`max_length=3`). 두 번째 `test_parse_summary`의 입력은 실제 LLM이 자주 하는 답의 모양이다. JSON 앞에 설명을 붙이고 코드 블록(```` ``` ````)으로 감싼다. 6.6.6에서 "진짜 답을 모아 가짜의 답으로 쓴다"고 한 그런 입력이다.

`schema_text() is schema_text()`는 `==`가 아니라 `is`로 비교한다. 같은 내용의 글자가 아니라 **같은 객체**인지, 즉 두 번째 부를 때 새로 만들지 않고 기억해 둔 것을 돌려줬는지 확인한다(기초 과정 3.2의 "같은 객체"). `@cache`를 지우면 실패한다.

`tests/test_retry.py`

```python
"""retry의 테스트 — 7장 test_async_retry.py에서 on_retry를 더했다."""

import pytest

from docsum.errors import BadRequestError, RateLimitError, ServerError
from docsum.retry import async_retry
from docsum.testing import RecordingSleep


class Flaky:
    """정해 둔 예외를 차례로 일으킨 뒤에 "성공"을 돌려주는 비동기 함수 객체."""

    def __init__(self, *errors: Exception) -> None:
        self.errors = list(errors)
        self.calls = 0

    async def __call__(self) -> str:
        self.calls += 1
        if self.errors:
            raise self.errors.pop(0)
        return "성공"


@pytest.mark.asyncio
async def test_retries_and_reports(sleep: RecordingSleep) -> None:
    events: list[tuple[int, str, float]] = []
    flaky = Flaky(ServerError("과부하", 529), RateLimitError("한도", retry_after=3.0))
    call = async_retry(
        sleep=sleep, on_retry=lambda n, e, wait: events.append((n, str(e), wait))
    )(flaky)
    assert await call() == "성공"
    assert flaky.calls == 3
    assert sleep.waits == [1.0, 3.0]
    assert events == [(1, "과부하", 1.0), (2, "한도", 3.0)]


@pytest.mark.asyncio
async def test_gives_up_after_times(sleep: RecordingSleep) -> None:
    flaky = Flaky(*[ServerError("과부하", 529)] * 3)
    with pytest.raises(ServerError):
        await async_retry(times=3, sleep=sleep)(flaky)()
    assert flaky.calls == 3
    assert sleep.waits == [1.0, 2.0]


@pytest.mark.asyncio
async def test_does_not_retry_bad_request(sleep: RecordingSleep) -> None:
    flaky = Flaky(BadRequestError("너무 길다", 400))
    with pytest.raises(BadRequestError):
        await async_retry(sleep=sleep)(flaky)()
    assert flaky.calls == 1


def test_rejects_bad_times() -> None:
    with pytest.raises(ValueError, match="1 이상"):
        async_retry(times=0)
```

- `Flaky`는 7.7.2의 `AsyncFlaky`에서 `await asyncio.sleep(0)`을 뺀 것이다. 테스트 파일 안에서만 쓰므로 `testing`에 넣지 않았다.
- `on_retry=lambda n, e, wait: events.append((n, str(e), wait))` — 콜백이 받은 세 값을 튜플로 묶어 리스트에 넣는다. 6장 실습 6-7의 "더 해 보기"에서 `on_progress`에 `events.append`를 바로 넘길 수 없어 람다로 감쌌던 것과 같다. `on_retry`는 값 셋을 넘기는데 `append`는 하나만 받기 때문이다.
- `sleep.waits == [1.0, 3.0]` — 첫 번째는 지수 백오프의 1초(`delay * backoff ** 0`), 두 번째는 `RateLimitError`의 `retry_after` 3초다. 서버가 "3초 뒤에"라고 말하면 우리의 규칙보다 서버의 말을 따른다(4.3.4).
- `async_retry(...)(flaky)` — 데코레이터를 `@` 없이 부르는 모양이다. `@deco`는 `f = deco(f)`의 줄임이라는 것(4.2.2)을 거꾸로 쓴 것이다.

`Piece`가 데이터 클래스라서 `==`로 바로 비교할 수 있다(기초 과정 5.4.3). 7장에서는 튜플로 비교했는데, 이제 테스트를 읽기만 해도 무엇이 파일 이름이고 무엇이 조각인지 보인다. 마지막 테스트는 `json.loads()`로 읽어 비교한다. 8.3.5처럼 출력 글자의 빈칸 모양이 아니라 **내용**을 확인한다. 그 위의 `"가.txt" in lines[0]`만은 글자를 확인한다. 한글이 `가`으로 바뀌지 않았는지는 글자를 봐야 알 수 있기 때문이다.

```python
"""clients의 테스트 — 가짜 클라이언트도 약속대로 동작해야 한다."""

import pytest

from docsum.clients import RandomLLM, fake_answer
from docsum.errors import RateLimitError
from docsum.prompts import build_prompt, parse_summary

NO_DELAY = (0.0, 0.0)


def test_fake_answer_is_valid_summary() -> None:
    summary = parse_summary(
        fake_answer(build_prompt("파이썬 제너레이터는 값을 하나씩 내놓는다."))
    )
    assert summary.summary == "파이썬 제너레이터는 값을 하나씩 내놓는다."
    assert summary.keywords == ["파이썬", "제너레이터는", "값을"]


def test_fake_answer_shortens_long_text() -> None:
    summary = parse_summary(fake_answer(build_prompt("가" * 100)))
    assert len(summary.summary) == 40
    assert summary.summary.endswith("…")


@pytest.mark.asyncio
async def test_random_llm_answers() -> None:
    client = RandomLLM(
        delay=NO_DELAY, slow_rate=0, rate_limit_rate=0, bad_answer_rate=0
    )
    answer = await client.complete(build_prompt("가나다"))
    assert parse_summary(answer).summary == "가나다"
    assert client.calls == 1


@pytest.mark.asyncio
async def test_random_llm_rate_limit() -> None:
    client = RandomLLM(delay=NO_DELAY, slow_rate=0, rate_limit_rate=1)
    with pytest.raises(RateLimitError):
        await client.complete(build_prompt("가나다"))


@pytest.mark.asyncio
async def test_random_llm_bad_answer() -> None:
    client = RandomLLM(
        delay=NO_DELAY, slow_rate=0, rate_limit_rate=0, bad_answer_rate=1
    )
    assert "{" not in await client.complete(build_prompt("가나다"))


@pytest.mark.asyncio
async def test_random_llm_same_seed_same_answers() -> None:
    async def run(seed: int) -> list[str]:
        client = RandomLLM(seed, delay=NO_DELAY, slow_rate=0, rate_limit_rate=0)
        return [await client.complete(build_prompt(f"글{n}")) for n in range(50)]

    assert await run(7) == await run(7)
```

**가짜도 테스트한다.** `RandomLLM`은 `--client fake`로 사용하는 사람이 직접 쓰는 제품의 일부다. 가짜가 늘 형식이 틀린 답만 낸다면, 이 도구를 시험해 본 사람은 "요약기가 고장 났다"고 생각할 것이다. 확률을 0이나 1로 주면 무작위인 가짜도 정해진 대로 동작하게 할 수 있다. 6.5.2에서 "난수를 매개변수로 받으면 테스트할 수 있다"고 한 것과 같은 생각이다.

마지막 테스트의 `[await client.complete(...) for n in range(50)]`는 컴프리헨션 안에 `await`가 있다. `async def` 안에서는 이렇게 쓸 수 있다. 다만 이것은 50개를 **차례로** 기다린다. 동시에 실행하려면 `gather()`로 넘겨야 한다(7.3.3). 이 테스트는 같은 씨앗이면 같은 순서로 같은 답이 나오는지를 보려는 것이므로 차례로 기다리는 것이 맞다.

7장 실습 7-8의 테스트에서 바뀐 곳은 셋이다.

- **조각이 파일이 아니라 `Piece`다.** `summarize_all()`은 파일을 모르므로 `docs` 폴더가 필요 없다. `PIECES`처럼 조각의 리스트를 코드에서 바로 만든다. 테스트가 짧아졌다. 9.3.3에서 파일 입출력을 뺀 덕분이다.
- **`max_concurrency`가 조각 수보다 큰 경우를 더했다.** `[1, 3, 7, 10]` 중 10은 조각이 7개뿐이므로 `peak`가 7이어야 한다. 7장의 테스트는 `client.peak == max_concurrency`였는데, 그대로 두면 10일 때 실패한다. 기대값을 `min(max_concurrency, len(PIECES))`로 고쳤다. 경계를 하나 더 시험하니 테스트의 **기대값 자체**를 다시 생각하게 되었다(6.3.2).
- **새로 생긴 약속의 테스트** — `on_retry`가 조각과 함께 불리는지(`test_summarize_piece_retries_and_reports`), 설정 오류는 잡지 않고 올려보내는지(`test_summarize_all_stops_on_setup_error`).

**`main()`은 클라이언트를 받지 않는다.** `main(argv)`는 명령행 인자만 받는다. `RandomLLM`을 만드는 일은 `main()` 안에서 일어나므로, 6.5.2처럼 매개변수로 가짜를 넣을 수 없다. 이럴 때 쓰는 것이 6.5.4의 `monkeypatch.setattr()`이다. `"docsum.cli.RandomLLM"`, 즉 **`cli` 모듈 안의 `RandomLLM`이라는 이름**을 "씨앗을 받아 `scripted`를 돌려주는 람다"로 잠시 바꿔 끼운다. `docsum.clients.RandomLLM`이 아니라 `docsum.cli.RandomLLM`을 바꾸는 이유는, `cli`가 `from docsum.clients import RandomLLM`으로 이름을 **자기 모듈에 가져와서** 쓰기 때문이다(6.5.4의 "쓰는 곳의 이름을 바꾼다"). 테스트가 끝나면 `monkeypatch`가 원래대로 돌려놓는다.

`main()`에 클라이언트를 받는 매개변수를 더하는 방법도 있다. `main(argv, client_factory=...)`처럼. 그러면 `monkeypatch` 없이 테스트할 수 있지만, 진입점의 모양이 테스트 때문에 복잡해진다. 조립하는 곳(9.4.1)만은 `monkeypatch`로 시험하는 것이 흔한 타협이다.

- `test_writes_records`는 결과 파일의 줄을 **`Record.model_validate_json()`으로** 읽는다. 9.2.2에서 "읽는 쪽은 같은 모델로 검증할 수 있다"고 한 것을 테스트가 직접 해 본다. 결과 파일의 모양이 모델과 어긋나면 여기서 `ValidationError`로 실패한다.
- `test_output_folder_missing_is_checked_first`의 `assert client.prompts == []` — "결과를 저장할 폴더가 없으면 **요약을 시작하기 전에** 멈춘다"(9.1.3)를 확인한다. 메시지가 맞는지만 보면, 서른 개를 다 요약하고 나서 같은 메시지로 끝나도 통과한다. **요청을 하나도 보내지 않았는지**를 세어야 약속을 확인한 것이다.
- `test_setup_error_exits_1_without_output`의 `assert not out.exists()` — 설정 오류는 결과 파일을 쓰지 않는다(9.1.3의 실패 표).

## 9.6 차례로와 동시에 — 재서 비교하기

테스트는 동시 실행 수가 **지켜지는지**를 보였다. 그래서 얼마나 빨라지는지는 테스트가 아니라 **측정**으로 본다. 7.7.4에서 "걸린 시간을 `assert`하지 않는다"고 했다. 시간은 컴퓨터의 상태에 따라 달라지므로 통과/실패로 판정할 것이 아니라, 재서 기록하고 설명할 것이다.

같은 문서, 같은 씨앗으로 동시 실행 수만 바꿔 세 번 실행한다. `-c 1`이 "차례로"다. 세마포어의 좌석이 하나이면 한 번에 요청 하나만 나간다.

```
summarize-docs samples -s 200 --timeout 2 --seed 32 -c 1 -o out1.jsonl
summarize-docs samples -s 200 --timeout 2 --seed 32 -c 5 -o out5.jsonl
summarize-docs samples -s 200 --timeout 2 --seed 32 -c 30 -o out30.jsonl
```

각 실행의 마지막 줄만 모으면 이렇다.

```
조각 30개: 성공 29, 실패 1, 31.4초 (동시 1개)
조각 30개: 성공 30, 실패 0, 9.7초 (동시 5개)
조각 30개: 성공 30, 실패 0, 7.4초 (동시 30개)
```

| 동시 실행 수 | 걸린 시간 | 차례로에 비해 | 성공 / 실패 | 종료 코드 |
|---|---|---|---|---|
| 1 | 31.4초 | 1배 | 29 / 1 | 1 |
| 5 | 9.7초 | 3.2배 빠르다 | 30 / 0 | 0 |
| 30 | 7.4초 | 4.2배 빠르다 | 30 / 0 | 0 |

**동시 1개는 모든 기다림의 합이다.** 동시 1개의 재시도 메시지를 세어 보면 시간 초과가 6번, 요청 한도 초과가 3번이다. 정상 응답 30번은 평균 0.4초씩 약 12초, 시간 초과 6번은 2초씩 12초, 재시도 전에 쉰 시간이 약 7.5초(시간 초과 뒤 1초, 1초, 1초, 2초, 1초와 한도 초과 뒤 0.5초 세 번)다. 더하면 약 31.5초로, 잰 값과 맞는다. 차례로 하면 **모든 기다림이 한 줄로 이어진다.**

**동시 30개는 가장 오래 걸린 조각 하나의 시간이다.** 조각 30개가 한꺼번에 출발하므로, 전체 시간은 가장 늦게 끝난 조각이 정한다. 동시 30개의 메시지에서 `doc2.txt 4번 조각`이 시간 초과를 두 번 겪었다. 2.0초(첫 시도) + 1.0초(쉼) + 2.0초(둘째 시도) + 2.0초(쉼) + 0.4초쯤(셋째 시도) = 약 7.4초. 잰 값과 같다. 동시 실행 수를 아무리 늘려도 이 조각 하나보다 빨라질 수는 없다. 7장 실습 7-8의 "확인할 것"에서 동시 25개가 동시 5개보다 크게 빨라지지 않은 이유와 같다.

**동시 5개는 그 사이다.** 다섯 줄로 나눠 서 있는 셈이다. 정상 응답만 있다면 30개 ÷ 5줄 × 0.4초 = 약 2.4초겠지만, 시간 초과와 재시도로 쉬는 조각이 좌석을 차지한 채 기다린다(7.4.6의 "세마포어는 재시도를 기다리는 시간까지 감싼다"). 그동안 다른 조각이 그 좌석을 쓰지 못한다.

**실패가 동시 1개에서만 났다.** 같은 씨앗인데도 그렇다. 씨앗이 정하는 것은 **난수의 순서**다. 동시 1개에서는 조각이 차례로 요청하므로 `doc3.txt 1번 조각`이 연달아 세 번의 "아주 늦은 답"을 뽑았다. 동시 5개에서는 같은 순서의 난수를 **여러 조각이 번갈아** 가져가므로, 어느 조각이 어느 난수를 뽑는지가 달라진다. 무작위인 가짜로는 "동시 1개일 때 실패가 있다"를 재현할 수는 있어도(같은 명령은 같은 결과다), "이 조각은 늘 실패한다"를 약속할 수는 없다. 그래서 특정 조각의 실패는 `ScriptedLLM`의 대본으로 테스트했다(9.5).

> **진짜 LLM에서는 무엇이 다른가**
> 가짜의 기다림은 `asyncio.sleep()`이라서 동시에 몇 개를 기다리든 비용이 없다. 진짜 API는 다르다. 동시에 너무 많이 보내면 서버가 요청 한도 초과(429)를 더 자주 돌려주고, 그만큼 재시도로 기다린다. 동시 실행 수를 30으로 올렸다가 오히려 느려지는 일이 생긴다. 계정마다 분당 요청 수와 토큰 수의 한도가 정해져 있으므로(7.4.4), 진짜 API에서는 작은 수에서 시작해 늘려 가며 재 보고, 429가 늘기 시작하는 곳의 조금 아래를 기본값으로 정한다. 우리 도구의 기본값 5는 그렇게 정한 숫자가 아니라 출발점이다. 설계 노트의 "한계"에 적는다.

## 9.7 (선택) 실제 LLM으로 바꿔 끼우기

이 절은 **API 키가 있을 때** 한다. 키가 없다면 9.7.1~9.7.3을 읽고 코드와 테스트(네트워크 없이 도는 것)까지만 만든다. 실제 호출은 "LLM API 활용"에서 해도 된다. 키를 만들고 다루는 방법도 그 과정에서 자세히 다룬다.

> **요금에 주의한다**
> 실제 API는 호출할 때마다 요금이 나간다. 이 절의 명령은 작은 입력(`samples`, 조각 30개)으로만 실행한다. 큰 폴더를 요약하기 전에는 조각 수(`--size`로 조절)와 모델의 가격을 먼저 확인한다. API 키는 코드나 커밋에 넣지 않고 환경 변수로 넘긴다(1장의 `.gitignore`에 `.env`를 넣은 이유다).

### 9.7.1 선택 의존성

9.2.1의 `pyproject.toml`에 이미 적었다.

```toml
[project.optional-dependencies]
anthropic = ["anthropic>=2.8,<3"]
```

이 패키지를 쓰는 사람은 두 가지로 설치할 수 있다.

| 설치 명령 | 설치되는 것 | 쓸 수 있는 클라이언트 |
|---|---|---|
| `pip install docsum-gildong` | docsum, pydantic(과 그 의존성) | `fake` |
| `pip install "docsum-gildong[anthropic]"` | 위에 더해 anthropic(과 그 의존성) | `fake`, `anthropic` |

anthropic SDK는 HTTP 라이브러리를 비롯해 여러 패키지를 함께 끌고 온다. 가짜로 시험만 해 볼 사람, 또는 `from docsum import summarize_all`에 자기 클라이언트를 넘겨 쓸 사람에게는 필요 없다. 그래서 **필요한 사람만** 설치하게 했다. 대괄호의 이름(`anthropic`)을 **엑스트라**(extra)라고 한다. 휠의 `METADATA`에는 이렇게 들어간다(9.8.2).

```
Requires-Dist: pydantic<3,>=2.9
Provides-Extra: anthropic
Requires-Dist: anthropic<3,>=2.8; extra == 'anthropic'
```

`; extra == 'anthropic'`은 "엑스트라 `anthropic`을 골랐을 때만 필요하다"는 조건이다. 셸에서 대괄호는 특별한 뜻이 있으므로(zsh에서는 파일 이름 패턴), 설치 명령에서는 따옴표로 감싼다.

개발하는 우리는 `dev` 그룹에 anthropic을 넣었으므로 이미 설치되어 있다. 9.4.1의 지연 `import`와 이 선택 의존성이 짝을 이룬다. 선택 의존성으로 선언했으면, 코드도 그 패키지 없이 `import`될 수 있어야 한다.

### 9.7.2 `anthropic_client.py`

`src/docsum/anthropic_client.py`

```python
"""Anthropic API로 요약하는 실제 클라이언트. pip install "docsum-gildong[anthropic]"이 필요하다."""

import anthropic

from docsum.clients import DEFAULT_MODEL
from docsum.errors import (
    APIError,
    APITimeoutError,
    BadRequestError,
    ClientSetupError,
    RateLimitError,
    ServerError,
)


def convert_status_error(e: anthropic.APIStatusError) -> Exception:
    """SDK의 상태 코드 오류를 이 패키지의 오류로 바꾼다."""
    match e.status_code:
        case 401 | 403:
            return ClientSetupError(f"API 키를 확인한다 ({e.status_code}: {e.message})")
        case 429:
            retry_after = e.response.headers.get("retry-after")
            return RateLimitError(
                e.message, retry_after=float(retry_after) if retry_after else None
            )
        case 400:
            return BadRequestError(e.message, 400)
        case status if status >= 500:
            return ServerError(e.message, status)
        case status:
            return APIError(e.message, status)


class AnthropicLLM:
    """AsyncLLMClient 약속을 따르는 Anthropic 클라이언트.

    재시도는 docsum의 async_retry()가 하므로 SDK의 재시도는 끈다(max_retries=0).
    """

    def __init__(self, model: str = DEFAULT_MODEL) -> None:
        self.client = anthropic.AsyncAnthropic(max_retries=0)
        self.model = model

    async def complete(self, prompt: str, *, max_tokens: int = 1024) -> str:
        try:
            message = await self.client.beta.messages.create(
                model=self.model,
                max_tokens=max_tokens,
                output_config={"effort": "low"},
                betas=["server-side-fallback-2026-07-01"],
                fallbacks="default",
                messages=[{"role": "user", "content": prompt}],
            )
        except TypeError as e:
            # API 키를 찾지 못하면 SDK는 요청을 만들 때 TypeError를 일으킨다.
            raise ClientSetupError(
                "API 키가 없다. ANTHROPIC_API_KEY 환경 변수를 설정한다"
            ) from e
        except anthropic.APITimeoutError as e:
            raise APITimeoutError("Anthropic API가 제한 시간 안에 답하지 않았다") from e
        except anthropic.APIConnectionError as e:
            raise ServerError(f"Anthropic API에 연결할 수 없다: {e}") from e
        except anthropic.APIStatusError as e:
            raise convert_status_error(e) from e
        if message.stop_reason == "refusal":
            raise APIError("모델이 요약을 거절했다")
        return "".join(block.text for block in message.content if block.type == "text")
```

**이 클래스가 하는 일은 "번역"이다.** 바깥(SDK)의 말을 안(우리 패키지)의 말로 바꾼다.

- **요청** — 우리의 `complete(prompt)`를 SDK의 `messages.create(...)`로 바꾼다. 7.7.6에서 읽은 `AsyncAnthropic`의 모양 그대로다.
- **답** — SDK의 답(`message`)은 여러 종류의 **블록**으로 이루어진다. 글자 블록(`type == "text"`) 말고도 생각 블록 같은 것이 섞일 수 있다(7.7.6). 글자 블록의 `text`만 골라 이어 붙인다. 제너레이터 표현식에 조건을 붙인 모양이다(3.3.2). mypy는 `if block.type == "text"`를 보고 그 뒤의 `block`을 글자 블록으로 좁혀 `block.text`를 허락한다(5.2.3의 타입 좁히기).
- **오류** — SDK의 예외를 우리 예외로 바꾼다. 이 번역 덕분에 `core`와 `retry`는 SDK를 전혀 모른 채 그대로 동작한다. 시간 초과는 `APITimeoutError`로(다시 시도한다), 연결 실패는 `ServerError`로(다시 시도한다), 상태 코드 오류는 `convert_status_error()`로 나눈다.

`except`의 **순서**에 이유가 있다. SDK에서 `APITimeoutError`는 `APIConnectionError`의 하위 클래스다. 연결 오류를 먼저 잡으면 시간 초과도 거기서 잡혀 버린다. 기초 과정 6장의 "구체적인 예외부터 잡는다"다. `APIStatusError`와 `APIConnectionError`는 형제라서 둘의 순서는 상관없다.

**`convert_status_error()`의 `match` 문.** 2.5에서 배운 패턴이 셋 들어 있다.

- `case 401 | 403:` — **또는 패턴**. 둘 중 하나와 같으면 맞는다. 인증 실패(401)와 권한 없음(403)은 모든 조각이 똑같이 실패할 오류이므로 `ClientSetupError`로 바꾼다.
- `case status if status >= 500:` — **캡처 패턴에 가드**를 붙였다(2.5.5). 어떤 값이든 `status`라는 이름에 담고, 그 값이 500 이상일 때만 맞는다.
- `case status:` — 가드 없는 캡처 패턴은 무엇에나 맞는다. `case _:`(2.5.1)와 같지만 값을 이름으로 받아 쓸 수 있다. 맨 끝에 두어 나머지(404 등)를 모두 받는다.

같은 일을 `if`/`elif`로도 쓸 수 있다. 2.5.7의 기준대로라면 "값 하나를 여러 경우로 나누고, 경우마다 모양이 다른" 이런 곳이 `match`가 잘 읽히는 자리다. `429`의 `Retry-After` 헤더(서버가 "몇 초 뒤에 다시"라고 알려 주는 값)를 꺼내 `retry_after`로 넘기는 것도 여기서 한다. 그러면 `async_retry()`가 우리 규칙 대신 서버의 말을 따른다(9.5.1).

**`max_retries=0` — 재시도는 한 층에서만.** SDK는 기본으로 시간 초과, 429, 5xx를 두 번까지 스스로 다시 시도한다. 그 위에 우리 `async_retry()`가 세 번을 시도하면, 최악의 경우 요청이 3 × 3 = 9번 나간다. 4.3.7과 7.7.6에서 "재시도는 한 층에서만 한다"고 했다. 이 도구에서는 재시도의 규칙(횟수, 기다림, 알림)을 우리가 정하고 테스트했으므로, **SDK의 재시도를 끄고** 우리 층에서만 한다. 반대로 SDK의 재시도를 쓰고 우리 것을 끄는 선택도 있다. 그러면 `[재시도]` 메시지는 볼 수 없다.

시간 제한도 마찬가지다. SDK에도 `timeout` 설정이 있지만(기본 10분), 우리는 `summarize_piece()`의 `asyncio.timeout()`으로 시도마다 제한을 건다. 우리 제한이 먼저 걸리면 SDK의 요청은 취소된다(7.4.2).

**모델과 요청의 설정.**

- `model` — 기본값은 `clients.py`의 `DEFAULT_MODEL`(`claude-opus-5-5`)이다. `--model`로 바꿀 수 있다. 모델의 이름과 가격은 자주 바뀌므로, 사용할 때 공식 문서에서 확인한다.
- `output_config={"effort": "low"}` — 이 모델은 답하기 전에 생각하는 양을 `effort`로 조절한다. 문단 하나의 요약은 깊이 생각할 일이 아니므로 낮게 두어 시간과 요금을 줄인다.
- `betas=[...]`, `fallbacks="default"` — 모델이 안전 기준 때문에 요청을 거절하면, 서버가 그 자리에서 다른 모델로 다시 처리하게 하는 기능이다. 아직 베타 기능이라 `client.beta.messages`로 부르고 `betas`에 기능의 이름을 적는다. 요약할 글 중에 보안이나 의학처럼 민감한 주제가 섞여 있어도 결과를 받을 가능성이 높아진다.
- 그래도 끝내 거절하면 답의 `stop_reason`이 `"refusal"`이다. 이때는 `APIError`를 일으킨다. `RETRYABLE`에 없으므로 다시 시도하지 않고, 그 조각만 `error` 레코드가 된다. 같은 글은 다시 보내도 거절될 것이기 때문이다.

SDK의 함수 이름과 매개변수는 버전에 따라 달라질 수 있다. 이 코드는 anthropic 2.8로 확인했다. 다른 버전에서 mypy가 오류를 내면, 1.2.6처럼 `F12`로 SDK의 코드에 들어가 지금의 이름을 확인한다.

### 9.7.3 키가 없을 때 — `ClientSetupError`가 생긴 이유

처음 이 클래스를 만들 때는 `except TypeError`가 없었다. API 키를 설정하지 않은 채 `summarize-docs samples --client anthropic`을 실행하면 이렇게 끝났다.

```
Traceback (most recent call last):
  ...
TypeError: "Could not resolve authentication method. Expected one of api_key, auth_token, or credentials to be set. Or for the `Authorization` header to be explicitly omitted"
```

SDK는 키를 찾지 못하면 클라이언트를 만들 때가 아니라 **요청을 만들 때** `TypeError`를 일으킨다. `TypeError`는 `APIError`도 `ValidationError`도 아니므로 `summarize_piece()`가 잡지 않고, `gather()`를 지나 `asyncio.run()`을 뚫고 트레이스백으로 끝났다. 사용하는 사람에게는 무엇을 하라는 것인지 알 수 없는 메시지다.

고치는 방법을 생각해 본다.

- **`summarize_piece()`가 `TypeError`도 잡게 한다** — 그러면 조각 서른 개에 같은 오류가 서른 줄 기록되고, 종료 코드 1로 끝난다. 9.1.3에서 "소음"이라고 한 바로 그 모습이다. 게다가 우리 코드의 진짜 버그(`TypeError`는 흔한 버그다)까지 조각의 실패로 숨어 버린다.
- **`AnthropicLLM`이 번역하고, 전체를 멈추는 예외로 올려보낸다** — 고른 방법이다. SDK의 `TypeError`를 SDK와 가장 가까운 곳(`complete()`)에서 우리 말(`ClientSetupError`)로 바꾸고, `ClientSetupError`는 `APIError`가 아니므로(9.2.2) `summarize_piece()`를 빠져나가 `cli`의 `except ClientSetupError`에서 한 줄로 끝난다.

```
summarize-docs: API 키가 없다. ANTHROPIC_API_KEY 환경 변수를 설정한다
```

`except TypeError`는 넓은 그물이다. 그래서 `try` 블록 안에 SDK 호출 **하나만** 두었다. 이 블록 안에서 `TypeError`를 일으킬 수 있는 우리 코드는 인자를 넘기는 것뿐이고, 그 인자의 타입은 mypy가 검사한다. 8.3.3에서 말한 "예외의 종류를 짐작으로 고르지 말고, 일부러 실패시켜서 **확인하고** 잡는다"를 그대로 한 것이다. 키 없이 실행해 보지 않았다면 이 경우는 실패 표에 없었을 것이다.

같은 생각으로 401(키가 틀렸다)과 403(권한이 없다)도 `ClientSetupError`로 바꾼다. 키가 틀렸으면 서른 번 보내도 서른 번 틀린다.

**네트워크 없이 테스트하기.** 이 번역들을 실제 API 없이 테스트한다.

`tests/test_anthropic_client.py`

```python
"""anthropic_client의 테스트. 실제 API를 부르는 것은 live 테스트 하나뿐이다."""

import os

import anthropic
import httpx2
import pytest

from docsum.anthropic_client import AnthropicLLM, convert_status_error
from docsum.core import summarize_piece
from docsum.errors import (
    APIError,
    BadRequestError,
    ClientSetupError,
    RateLimitError,
    ServerError,
)
from docsum.models import Piece


def status_error(
    status: int, headers: dict[str, str] | None = None
) -> anthropic.APIStatusError:
    """SDK가 일으키는 것과 같은 상태 코드 오류를 네트워크 없이 만든다."""
    request = httpx2.Request("POST", "https://api.anthropic.com/v1/messages")
    response = httpx2.Response(status, headers=headers, request=request)
    return anthropic.APIStatusError("오류", response=response, body=None)


@pytest.mark.parametrize(
    ("status", "expected"),
    [
        (400, BadRequestError),
        (401, ClientSetupError),
        (404, APIError),
        (429, RateLimitError),
        (529, ServerError),
    ],
)
def test_convert_status_error(status: int, expected: type[Exception]) -> None:
    assert type(convert_status_error(status_error(status))) is expected


def test_convert_rate_limit_reads_retry_after() -> None:
    error = convert_status_error(status_error(429, {"retry-after": "7"}))
    assert isinstance(error, RateLimitError)
    assert error.retry_after == 7.0


@pytest.mark.asyncio
async def test_missing_key_is_setup_error(monkeypatch: pytest.MonkeyPatch) -> None:
    """API 키를 찾지 못하면 SDK가 일으키는 TypeError를 ClientSetupError로 바꾼다."""

    async def no_key(**kwargs: object) -> None:
        raise TypeError("Could not resolve authentication method.")

    llm = AnthropicLLM()
    monkeypatch.setattr(llm.client.beta.messages, "create", no_key)
    with pytest.raises(ClientSetupError, match="API 키가 없다"):
        await llm.complete("안녕")


@pytest.mark.live
@pytest.mark.asyncio
@pytest.mark.skipif("ANTHROPIC_API_KEY" not in os.environ, reason="API 키가 없다")
async def test_real_summary() -> None:
    piece = Piece(
        "live.txt", 1, "파이썬은 1991년에 처음 공개된 프로그래밍 언어다. " * 10
    )
    record = await summarize_piece(AnthropicLLM(), piece, attempt_timeout=60)
    assert record.ok, record.error
    assert 0 < len(record.summary or "") <= 200
```

- **`status_error()`** — SDK가 서버의 오류 응답을 받았을 때 만드는 것과 같은 예외를 손으로 만든다. 예외에는 HTTP 응답 객체가 필요하므로 `httpx2`(anthropic SDK가 쓰는 HTTP 라이브러리. 7장의 `httpx`와 쓰는 법이 거의 같은 다음 판이다)로 요청과 응답을 만든다. 네트워크에는 아무것도 보내지 않는다. 6.6.6의 "진짜 답을 모아 가짜로 쓴다"처럼, 진짜 SDK의 예외 **객체**로 우리의 번역을 시험한다.
- **`type(...) is expected`** — `isinstance()`가 아니라 `type() is`로 비교한다. `BadRequestError`도 `APIError`이므로 `isinstance(error, APIError)`는 400에서도 참이 된다. 정확히 **그 클래스인지**를 확인해야 번역이 맞는지 알 수 있다.
- **`test_missing_key_is_setup_error`** — 9.7.3의 이야기를 테스트로 남긴다. 키가 없는 상황을 진짜로 만들기는 어렵다(컴퓨터에 따라 환경 변수나 설정 파일에 키가 있을 수 있다). 그래서 `monkeypatch.setattr()`로 SDK의 `create`를 "늘 `TypeError`를 일으키는 함수"로 잠시 바꿔 끼운다. 6.5.4의 방법이다.
- **`test_real_summary`** — 실제 API를 부르는 테스트는 이 하나다. 6.5.6처럼 `live` 마커를 붙이고, 키가 없으면 건너뛴다. 요약의 **내용**은 확인하지 않는다. "성공했고, 200자 이내다"라는 늘 성립해야 하는 **성질**만 확인한다(6.6.6).

### 9.7.4 실제로 실행하기

키를 환경 변수로 설정한다. 키를 명령에 직접 적으면 터미널의 기록에 남으므로, 아래처럼 하거나 1장에서 막아 둔 `.env` 파일에 넣고 불러온다.

```
# macOS
export ANTHROPIC_API_KEY="여기에 키"

# Windows
$env:ANTHROPIC_API_KEY = "여기에 키"
```

`live` 테스트만 실행한다. 명령행의 `-m live`가 `addopts`의 `-m "not live"`보다 나중에 읽혀서 이긴다.

```
pytest -m live -rs
```

키가 없으면 이렇게 나온다. 건너뛴 이유가 `-rs`로 보인다.

```
SKIPPED [1] tests/test_anthropic_client.py:63: API 키가 없다
====================== 1 skipped, 64 deselected in 0.59s =======================
```

키가 있으면 몇 초 걸려 `1 passed`가 된다. 같은 테스트를 세 번 실행해 매번 통과하는지, 몇 초 걸리는지(`--durations=1`) 본다.

이제 명령으로 실행한다. 다른 코드는 하나도 고치지 않았다. **바꾼 것은 `--client` 옵션 하나다.**

```
summarize-docs samples -s 200 --client anthropic -c 3 -o real.jsonl
```

`real.jsonl`을 열어 가짜의 결과와 비교한다. 진짜 요약은 "1번 문서에서 컴프리헨션에 관한 문단이다…"의 앞 40글자가 아니라, 같은 문장이 되풀이된 문단을 한 문장으로 줄인 글일 것이다. 핵심어도 "1번", "문서에서" 같은 낱말 대신 "컴프리헨션" 같은 것이 나올 것이다. 결과는 실행할 때마다 다르다.

### 실습 9-7. (선택) 실제 LLM으로 바꿔 끼우기

1. `anthropic_client.py`와 `test_anthropic_client.py`를 만들고 `mypy`, `pytest`를 통과시킨다. 이것까지는 키가 없어도 된다.
2. `anthropic_client.py`에서 `except TypeError` 블록을 지우고, 키를 설정하지 **않은** 터미널에서 `summarize-docs samples --client anthropic`을 실행해 9.7.3의 트레이스백을 직접 본다. 어느 테스트가 실패하는지도 확인한 뒤 되돌린다.
3. `except anthropic.APIConnectionError`와 `except anthropic.APITimeoutError`의 순서를 바꾸면 무엇이 달라지는가? 그 차이를 잡아내는 테스트를 `status_error()`처럼 예외 객체를 만들어 써 본다. 힌트: `anthropic.APITimeoutError(request=httpx2.Request(...))`.
4. (키가 있다면) `pytest -m live`와 9.7.4의 명령을 실행하고, `-c 1`과 `-c 3`의 시간을 9.6의 표에 더한다. 진짜 LLM에서 동시 실행의 효과는 가짜와 비슷한가?
5. (키가 있다면) `real.jsonl`의 요약 몇 개를 원문과 비교해 "좋은 요약인가"를 판단해 본다. 그 판단을 테스트로 쓸 수 있는가? 6.6.6의 표에서 어느 쪽 일인가? 판단 기준을 세 가지 적어 `notes.md`에 남긴다. "LLM 평가(Evals) 심화"의 출발점이 된다.

# docsum

폴더의 `.txt` 파일을 문단 단위로 나눠 LLM에게 동시에 요약을 요청하고,

## 설치

```
pip install docsum-gildong                # 가짜 클라이언트로 시험만 할 때
pip install "docsum-gildong[anthropic]"   # Anthropic API로 요약할 때
```

파이썬 3.12 이상이 필요하다.

## 사용

```
summarize-docs docs -o summaries.jsonl
summarize-docs docs -c 10 --timeout 60 --client anthropic -o summaries.jsonl
```

- `--client`의 기본값은 `fake`다. API 키 없이, 무작위로 늦거나 실패하는 가짜 LLM으로 동작을 시험한다.
- `--client anthropic`은 환경 변수 `ANTHROPIC_API_KEY`의 키를 쓴다. 호출마다 요금이 나간다.
- 모든 옵션은 `summarize-docs --help`로 본다.

결과 파일의 한 줄은 성공하면 `summary`와 `keywords`가, 실패하면 `error`가 있다.

```
{"file":"a.txt","chunk":1,"summary":"...","keywords":["...","..."]}
{"file":"a.txt","chunk":2,"error":"APITimeoutError: 30.0초 안에 답이 없다"}
```

| 종료 코드 | 뜻 |
|---|---|
| 0 | 모든 조각을 요약했다 |
| 1 | 실패한 조각이 있다(결과 파일은 쓴다), 또는 실행할 수 없었다(입력 폴더, API 키 등) |
| 2 | 사용법이 틀렸다 |

`DESIGN.md`

```markdown
# 설계 노트 — docsum

## 목적과 범위
폴더의 .txt 파일을 조각으로 나눠 LLM에게 동시에 요약시키고 JSONL로 저장한다.
하지 않는 것: .txt가 아닌 파일, 요약의 품질 판단(형식만 검사), 문서 전체의 요약, 중단 후 이어 하기.

## 구조
0층 models, errors / 1층 clients, retry, prompts, chunking / 2층 core, storage, anthropic_client / 3층 cli.
모듈은 자기보다 아래층만 import한다. testing은 옆에 있고 아무것도 import하지 않는다.
core는 파일을 모르고, storage는 LLM을 모른다. 비동기는 core에만 있다.

## 주요 함수
- load_pieces(folder, max_chars) -> list[Piece]: 폴더 → 조각. 파일마다 번호는 1부터.
- summarize_piece(client, piece, ...) -> Record: 조각 하나. 예외를 일으키지 않는다(ClientSetupError만 예외).
- summarize_all(client, pieces, ...) -> list[Record]: 세마포어로 동시 실행 수를 제한한다. 결과는 pieces의 순서.
- cli.main(argv) -> int: 실패 표를 위에서 아래로 따라간다. 클라이언트를 고르는 곳은 여기 한 곳.

## 실패 처리
- 조각의 실패(시간 초과, 429, 5xx, 400, 형식이 틀린 답, 거절)는 error 레코드로 남기고 계속한다. 종료 코드 1.
- 모두 똑같이 실패할 오류(API 키 없음, 401/403)는 ClientSetupError로 전체를 멈춘다. 결과 파일을 쓰지 않는다.
- 입력과 출력 위치의 오류는 요약을 시작하기 전에 확인한다. 돈을 쓰기 전에 실패한다.

## 결정과 이유
- --client 기본값 fake: 키 없이 설치하자마자 실행해 볼 수 있고, 실수로 요금이 나가지 않는다.
  대안: anthropic을 기본으로. 실제 도구로는 자연스럽지만 처음 쓰는 사람이 바로 막힌다.
- 재시도 알림은 on_retry 콜백: 라이브러리가 표준 출력을 차지하지 않게. 알릴 일이 늘면 logging으로.
- 재시도는 한 층에서만: AnthropicLLM은 SDK의 재시도를 끈다(max_retries=0).
- 시간 제한은 시도마다(attempt_timeout): 재시도 전체가 아니라 시도 하나를 제한한다.
- 세마포어는 재시도를 기다리는 시간까지 감싼다: 429로 기다리는 동안 새 요청을 보내지 않는다.
  대안: 시도 하나만 감싸기. 처리량은 늘지만 한도 초과 중에도 요청이 나간다.
- 파일 입출력은 이벤트 루프 밖(cli)에서: to_thread가 필요 없고 core를 파일 없이 테스트할 수 있다.
- Record는 성공과 실패를 한 클래스로: 읽는 쪽이 모델 하나로 검증한다. 대안: Success | Failure.
- chunking은 textchunk에서 복사: textchunk-gildong은 TestPyPI에만 있어 의존성으로 쓸 수 없다.
- 테스트용 가짜(testing)를 패키지에 넣어 공개: 이 패키지를 쓰는 사람도 자기 코드를 테스트할 수 있게.

## 바뀔 때 고칠 곳
- 새 LLM 클라이언트: clients 또는 새 모듈에 complete()가 있는 클래스, cli의 choices와 if 한 갈래, 선택 의존성.
- 결과에 필드 추가(예: 조각의 글자 수): models.Record, core.summarize_piece. 읽는 쪽이 있으면 버전의 MINOR.
- .md도 읽기: storage.load_pieces의 glob, 실패 표.

## 한계
- 모든 결과를 메모리에 모았다가 끝에 한 번에 쓴다. 중간에 멈추면 결과가 하나도 남지 않는다.
- 빈 .txt 파일은 조각이 없어 결과에 흔적이 남지 않는다.
- 형식이 틀린 답은 다시 시도하지 않는다.
- 동시 실행 수의 기본값 5는 측정해서 정한 값이 아니다. 실제 API의 요청 한도에 맞춰 재서 정한다.
```

`DESIGN.md`에서 가장 중요한 절은 **결정과 이유**다(기초 과정 10.3.3). 거의 모든 줄에 **대안**이 함께 적혀 있다. 6개월 뒤의 나, 또는 이 코드를 고칠 AI가 "왜 SDK의 재시도를 껐지? 켜는 게 낫지 않나?"라고 물을 때, 대답이 여기 있어야 한다. 대답이 없으면 그 결정은 이유를 모른 채 뒤집힌다.

여기서부터는 선택이다.

- **TestPyPI에 올리기** — 8.6을 따라 `twine check dist/*`와 `twine upload --repository testpypi dist/*`(또는 uv로 `uvx twine check dist/*`, `uv publish --index testpypi`)로 올리고, 9.8.3의 새 가상환경에서 `--index-url`과 `--extra-index-url`(8.6.4)로 설치해 실행한다. 프로젝트 범위의 API 토큰은 8.6.2에서 `textchunk-gildong`용으로 만들었으므로, 이 프로젝트는 처음 올릴 때 계정 범위의 토큰이 필요하다.

- **uv로 다루기** — 8.7처럼 `uv sync`, `uv run pytest`, `uv build`로 같은 일을 할 수 있다. `uv sync`는 `dev` 그룹을 기본으로 설치한다.

## 9.9 돌아보기

### 9.9.1 어디에 무엇을 썼는가

README의 완료 기준 첫 줄은 "컴프리헨션·제너레이터·데코레이터·`Protocol`·Pydantic을 각각 어디에 썼는지, **왜 그 자리에** 썼는지 설명할 수 있다"이다. 위치를 찾는 것은 쉽다. 이유를 말하는 것이 이 과정의 목표다.

| 배운 것 | 어디에 | 왜 그 자리에 |
|---|---|---|
| 리스트 컴프리헨션(2장) | `load_pieces()`의 두 겹, `read_pieces()`의 `enumerate()`, 테스트의 `PIECES` | **리스트를 만드는 것이 목적인** 반복이다. 부수 효과가 없다(2.3.1) |
| 제너레이터 표현식(3.3) | `to_jsonl()`의 `"".join(...)`, `fake_answer()`의 `dict.fromkeys(...)`, `gather(*(...))`, `AnthropicLLM`의 글자 블록 잇기, `cli`의 `sum(1 for ...)` | 결과를 한 번 훑어 **바로 다른 함수에 넘긴다.** 중간 리스트가 필요 없다(3.3.4) |
| 딕셔너리 컴프리헨션(2.2) | `ScriptedLLM.__init__`의 대본 복사 | 받은 딕셔너리의 리스트를 **복사해 두어** 바깥의 리스트를 건드리지 않는다 |
| `match` 문(2.5) | `convert_status_error()` | 값 하나(상태 코드)를 여러 경우로 나누고, 경우마다 모양이 다르다. 또는 패턴과 가드가 그대로 읽힌다(2.5.7) |
| 제너레이터 함수(3.2) | `paragraphs()`, `split()`, `chunk_paragraphs()` | 파일 → 줄 → 문단 → 조각을 **파이프라인**으로 잇는다. 단계마다 한 가지 일만 한다(3.4.2) |
| 클로저(4.1) | `report()`, `ask()`, `limited()` | 바깥의 값(`piece`, `client`, `limit`)을 기억하는 작은 함수가 필요했다. 클래스를 만들 만큼은 아니다(4.1.6) |
| 데코레이터 만들기(4.2, 4.3) | `async_retry()` | "다시 시도하기"는 **어떤 비동기 함수에든** 붙일 수 있는 일이다. 요약의 흐름과 섞지 않는다 |
| 표준 데코레이터(4.4) | `@cache`(`schema_text()`), `@dataclass`(`Piece`, `Slow`), `@property`(`Record.ok`) | 한 번 정해지는 값, 값의 묶음, 이름 붙은 판단 |
| 콜백·의존성 주입(6.5) | `on_retry`, `sleep`, `client` | **무엇을 할지**는 이쪽이, **어떻게 할지**는 부르는 쪽이 정한다. 테스트에서 바꿔 끼운다 |
| 타입 힌트(5장) | 모든 함수. `type` 별칭(`AsyncFunc`, `OnRetry`, `Sleep`, `OnPieceRetry`), `ParamSpec`(`async_retry`), `client: AsyncLLMClient` | 함수끼리의 약속을 mypy가 검사한다. 긴 타입에는 이름을 붙인다 |
| `Protocol`(5.5.4) | `AsyncLLMClient` | 가짜·실제·SDK 클라이언트가 **우리 클래스를 물려받지 않고도** 같은 자리에 들어간다 |
| Pydantic(5.6) | `Summary`(LLM의 답 검증), `Record`(결과의 한 줄) | **바깥과 주고받는** 값이다. 들어오는 것은 검증하고, 나가는 것은 읽는 쪽이 검증할 수 있게 |
| 데이터 클래스 | `Piece` | **안에서만** 오가는 값이다. 검증이 필요 없고 바뀌면 안 된다(`frozen=True`, 5.6.8) |
| pytest(6장) | 테스트 64개. `parametrize`, 픽스처(`conftest.py`), `tmp_path`, `capsys`, `monkeypatch`, 마커 | 약속을 코드로 적고, 고칠 때마다 확인한다 |
| asyncio(7장) | `summarize_all()`의 `Semaphore`와 `gather()`, `summarize_piece()`의 `timeout()`, `cli`의 `asyncio.run()` 한 줄 | 기다리는 시간이 대부분인 일을 **겹쳐서** 기다린다. 비동기는 필요한 곳(`core`)에만 |
| 패키지(8장) | `src` 레이아웃, `pyproject.toml`, `[project.scripts]`, 엑스트라, `py.typed`, 휠 | 다른 사람이 설치해서 이름만으로 실행한다 |

### 9.9.2 쓰지 않은 것

**배운 것을 모두 쓰는 것이 목표가 아니다.** 이 도구에 쓰지 않은 것도 이유와 함께 적는다. AI가 만든 코드에 "배운 것이 다 들어 있는" 경우가 많은데, 그것이 좋은 코드라는 뜻은 아니다.

| 쓰지 않은 것 | 이유 |
|---|---|
| `TaskGroup`(7.3.5) | 조각의 실패를 모두 결과로 바꾸므로 `gather()`로 충분하다. 설정 오류 하나만 올라오는데, `ExceptionGroup`으로 싸면 `cli`가 `except*`를 써야 한다 |
| `as_completed()` | 결과를 **입력의 순서로** 써야 한다. 끝나는 대로 받을 이유가 없다 |
| `itertools.batched()`(3.5.3) | 조각을 다섯 개씩 묶어 보내면 묶음마다 **가장 느린 조각**을 기다린다. 세마포어는 좌석이 비는 대로 다음 조각을 보낸다 |
| `asyncio.to_thread()`(7.6.5) | 파일 입출력을 이벤트 루프 밖으로 옮겨서 필요가 없어졌다 |
| 비동기 제너레이터와 스트리밍(7.5) | 요약은 짧은 JSON이고, **다 받아야** 검증할 수 있다. 조각조각 받아 화면에 보일 이유가 없다 |
| 컨텍스트 관리자 만들기(4.6) | 열고 닫을 자원을 우리가 만들지 않았다. `open()`, `asyncio.timeout()`, 세마포어의 것을 쓰기만 했다 |
| 등록 데코레이터(4.5) | 클라이언트가 둘뿐이라 `if` 한 줄이 더 읽기 쉽다. 다섯 개를 넘으면 `@register("openai")`로 바꿀 만하다 |
| 응답 캐시(`lru_cache`, 4.4.2) | 같은 조각을 두 번 요약하는 일이 거의 없다. 이어 하기를 만든다면 파일에 남긴 결과가 캐시 노릇을 한다 |
| `TypedDict`, `Enum`, `Literal`(5.5) | 레코드는 Pydantic 모델로, 클라이언트의 선택지는 `argparse`의 `choices`로 충분했다 |
| `cast()`(5.2.5) | 한 번도 필요하지 않았다. 필요했다면 설계를 먼저 의심했을 것이다 |
| `:=`(2.4.5) | 쓸 자리가 없었다. 억지로 넣으면 읽기만 어려워진다 |

이 표의 결정도 바뀔 수 있다. "클라이언트가 다섯 개가 되면", "이어 하기를 만들면" 같은 **조건**을 함께 적어 두면, 그 조건이 왔을 때 다시 꺼내 볼 수 있다.

### 9.9.3 지도를 다시 연다

1장 실습 1-1에서 1.1.3의 (가)~(마)를 한 줄씩 읽으며 "읽을 수 있다 / 모양만 안다 / 모른다"로 표시했다. 2장부터 장이 끝날 때마다 몇 줄씩 표시를 고쳐 왔다. 이제 마지막으로 `ch01/map.md`를 연다.

1.1.3의 다섯 예를 **지금** 다시 읽는다. 이번에는 줄마다 "무엇을 하는가"뿐 아니라 이 장의 `docsum`에서 같은 모양을 찾아 **짝을 지어** 본다.

| 1.1.3 | 줄 | `docsum`에서 같은 모양 |
|---|---|---|
| (가) | `for text in stream.text_stream:` | `paragraphs(f)`가 파일 객체를 `for`로 훑는다 — 둘 다 이터레이터 |
| (나) | `class ChatRequest(BaseModel):` | `Summary`, `Record` |
| (나) | `@app.post("/chat")` | (쓰지 않았다. 9.9.2의 등록 데코레이터) |
| (나) | `async def chat(...)`, `await ask_llm(...)` | `summarize_piece()`, `await client.complete(...)` |
| (다) | `@tool` | `@async_retry(...)` — 함수를 받아 다른 것으로 바꿔 돌려준다 |
| (라) | `asyncio.Semaphore(5)`, `asyncio.gather(*tasks)` | `summarize_all()` |
| (마) | `yield`, `-> Iterator[str]`, `@pytest.mark.parametrize` | `chunking.py`, `test_summarize_all_limits_concurrency` |

그리고 다음을 적는다.

1. "모양만 안다"와 "모른다"가 몇 줄 남았는가? 1장에서 몇 줄이었는가?
2. 남은 줄이 있다면, 그것은 이 과정에서 배운 **문법**인데 아직 낯선 것인가, 아니면 라이브러리(FastAPI, LangChain, anthropic)의 **사용법**인가? 기초 과정 10장 선택 활동의 구분이다. 사용법이라면 어느 과정에서 만나는지 로드맵에서 찾아 적는다.
3. 맨 아래에 적었던 "이 과정을 마치면 하고 싶은 것"을 읽는다. 할 수 있게 되었는가? 아직이라면 무엇이 더 필요한가?

### 9.9.4 AI와 함께 고칠 때

이 패키지를 AI 코딩 도구와 함께 고친다고 해 보자. 예를 들어 "중간에 멈춰도 이미 요약한 조각은 건너뛰게 해 줘"라고 맡긴다. 이 과정에서 배운 것으로 AI의 결과를 **받아들일지 판단하는 방법**이 생겼다(1.1.5).

- **설계를 먼저 준다.** `DESIGN.md`를 함께 읽게 한다. "모듈은 아래층만 `import`한다", "`core`는 파일을 모른다" 같은 규칙이 적혀 있지 않으면, AI는 `core.py`에서 파일을 읽는 가장 짧은 길을 고를 것이다.
- **테스트를 먼저 쓴다.** 새 기능의 약속을 테스트로 적고 AI에게 그 테스트를 통과시키게 한다(7장 실습 7-8의 테스트 주도 개발). 그리고 `git diff tests/`로 AI가 **기존 테스트를 고치지 않았는지** 확인한다(6.1.4).
- **검사를 돌린다.** `ruff`, `mypy`, `pytest`가 모두 통과하는지. 실패를 "고쳐 줘"라고만 맡기지 말고, 실패 메시지를 먼저 읽고 무엇이 틀렸는지 내 말로 말해 본다.
- **설명하게 하고, 확인한다.** "왜 이 줄을 여기에 넣었는가"를 묻고, 그 설명을 대화형 셸이나 디버거로 확인한다. 9.9.1의 표처럼 "왜 그 자리에"를 말할 수 없는 코드는 아직 받아들일 때가 아니다.
- **결정은 `DESIGN.md`에.** AI와 함께 내린 결정도 결정이다. 이유와 대안을 남긴다.

기초 과정 10장에서 만든 가계부 요약 프로그램(또는 실습 10-4에서 고른 주제의 프로그램)을 이 과정에서 배운 것으로 다시 쓴다. 6장 실습 6-7의 "더 해 보기"에서 첫 단계(pytest 테스트 붙이기)를 했다면 거기서 이어 간다.

- 모든 함수에 타입 힌트를 붙이고 `mypy --strict`를 통과시키기(5장)
- 명령 인자를 `sys.argv`에서 `argparse`로(8.3)

**3) 비교한다.** 다시 쓴 코드와 원래 코드를 나란히 놓고 `REVIEW.md`(또는 `notes.md`)에 적는다. 짧아진 곳, 오히려 길어진 곳, 읽기 쉬워진 곳, 어려워진 곳. 바꾸지 않기로 한 곳과 그 이유. 테스트가 처음부터 끝까지 **고치지 않고** 통과했는가? 테스트를 고쳐야 했다면, 그것은 동작이 바뀌었다는 뜻인가, 테스트가 구현에 너무 기대고 있었다는 뜻인가(6.3.6)?

## 정리

**이 장의 핵심**

| 항목 | 핵심 |
|---|---|
| 설계 순서 | 한 문단 → 하지 않을 것 → 실행 예 → 실패 표 → 층 나누기 → 아래층부터. 기존 코드를 도구로 만들 때도 같다 |
| 실패 표의 새 칸 | 결과 파일을 쓰는가. 조각의 실패는 기록하고 계속, 모두 똑같이 실패할 오류는 전체를 멈춘다 |
| 돈을 쓰기 전에 | 입력과 출력 위치처럼 미리 확인할 수 있는 것은 요약을 시작하기 전에 확인한다 |
| 예외 계층으로 흐름 정하기 | `ClientSetupError`는 `APIError`가 아니어서 `summarize_piece()`의 그물을 빠져나가 `cli`까지 간다 |
| 라이브러리와 화면 | 라이브러리는 `print()`하지 않는다. 알릴 일은 콜백(`on_retry`)으로 넘기고, 보여 주는 것은 `cli`가 한다. 더 크면 `logging` |
| 비동기는 작게 | 파일 입출력은 이벤트 루프 밖(`cli`)에서. `asyncio.run()` 한 줄. `to_thread()`가 필요 없어진다 |
| 린트 경고와 이름 | `ASYNC109` → `attempt_timeout`. 경고는 "이유가 있는가"를 묻는다. 이유가 있으면 이름이나 주석으로 남긴다 |
| 조립하는 곳 | 구체적인 클라이언트 클래스가 나오는 곳은 `cli.main()`의 `if` 하나. 나머지는 `Protocol`만 안다 |
| 지연 `import` | 선택 의존성은 고른 갈래에서만 `import`한다. 없으면 설치 방법을 한 줄로 |
| 엑스트라 | `[project.optional-dependencies]`, `pip install "패키지[이름]"`, `METADATA`의 `extra == '이름'` |
| 테스트용 가짜의 자리 | `--import-mode=importlib`에서는 테스트끼리 `import`할 수 없다. 픽스처는 `conftest.py`, 클래스는 패키지의 `testing` 모듈(공개) 또는 `pythonpath` 설정 |
| `monkeypatch`로 조립하는 곳 시험 | `main()`이 직접 만드는 객체는 `monkeypatch.setattr("docsum.cli.RandomLLM", ...)`처럼 **쓰는 곳의 이름**을 바꾼다 |
| 센 값으로 확인 | 동시 실행은 `peak`, 재시도는 호출 수와 `sleep.waits`, 설정 오류는 "요청을 하나도 보내지 않았다" |
| 시간은 측정 | 동시 1개는 모든 기다림의 합, 동시 N개는 가장 늦은 조각 하나가 정한다. 진짜 API에서는 429가 늘기 직전이 한계 |
| SDK를 감쌀 때 | 요청·답·오류를 번역한다. `except`는 구체적인 것부터. 재시도는 한 층에서만(`max_retries=0`) |
| `live` 테스트 | `addopts`에 `-m "not live"`, 필요할 때 `pytest -m live`. 내용이 아니라 성질만 단정 |
| 문서 둘 | `README.md`는 쓰는 사람, `DESIGN.md`는 고칠 사람. 결정에는 이유와 대안 |
| 쓰지 않은 것 | 배운 것을 모두 쓰는 것이 목표가 아니다. 쓰지 않은 이유와 쓰게 될 조건을 적는다 |

## 다음 과정

파이썬 중급 과정을 모두 마쳤다. 1장에서 "모양만 안다"고 표시했던 줄들, 대괄호 안의 `for`, 함수 위의 `@`, `yield`, `async def`와 `await`, `class ...(BaseModel)`, `pyproject.toml`은 이제 **읽을 수 있고, 같은 방식으로 쓸 수 있는** 코드가 되었다. 무엇보다 그것들을 **어디에 쓰고 어디에 쓰지 않을지** 판단하고, 그 판단을 테스트로 확인하고, 다른 사람이 설치해서 쓸 수 있게 내보낼 수 있다.

[AI 엔지니어 학습 로드맵](../README.md)의 다음 항목은 **자료구조·알고리즘**이다. 코딩 테스트를 대비하면서 배열, 해시, 스택과 큐, 트리, 그래프를 다루고 시간 복잡도를 따진다. 이 과정에서 무심코 써 온 것들이 거기서 이름을 얻는다. `dict.fromkeys()`가 순서를 지키며 중복을 없애는 데 걸리는 시간, `in`으로 리스트와 집합을 찾을 때의 차이, `deque`가 큐에 좋은 이유. 그리고 테스트는 거기서도 쓴다. 알고리즘 문제의 예제 입력을 `parametrize`로 옮겨 두면, 풀이를 고칠 때마다 확인할 수 있다.

그 뒤의 과정에서도 `docsum`의 부품이 모양을 바꿔 계속 나온다.

- **데이터 처리 기초** — JSONL과 CSV를 pandas로 읽는다. `Record.model_validate_json()`으로 한 줄씩 검증하던 결과 파일을 표로 불러와 실패한 조각만 거르고, 파일별로 센다.
- **웹·API 기초** — `httpx`로 실제 웹 API를 부른다. `AnthropicLLM`이 한 "번역"(바깥의 오류를 우리 오류로)을 다른 API에도 하게 된다. 9.1.5의 층 그림에서 `cli` 자리에 웹 요청을 받는 모듈이 들어서는 것도 이때 해 볼 수 있다.
- **프롬프트 엔지니어링, LLM API 활용** — `build_prompt()`의 프롬프트를 고치고, `parse_summary()`처럼 답을 잘라 검증하는 대신 API의 **구조화 출력**으로 스키마에 맞는 답을 받는다. 9.7의 `AnthropicLLM`을 스트리밍, 도구 호출로 넓힌다. 실습 9-7에서 적어 둔 "좋은 요약의 기준"이 작은 평가셋의 출발점이 된다.
- **RAG** — `chunk_paragraphs()`가 문서 청킹의 첫 판이다. 조각마다 요약 대신 임베딩을 구하고, 세마포어로 동시 요청 수를 제한하는 구조는 그대로다.
- **에이전트 개발** — 4.5에서 흉내 낸 `@tool`, `@mcp.tool()`이 실물로 나온다. 도구 호출이 실패할 때 무엇을 다시 시도하고 무엇을 멈출지, 9.1.3의 실패 표가 다시 필요하다.
- **LLM 평가(Evals) 심화** — 6.6.6에서 나눈 테스트와 평가 중 평가를 본격적으로 한다. `live` 테스트가 단정한 "성질"을 넘어, 요약의 **품질**을 여러 예제로 점수 매긴다.
- **LLM 서비스 배포** — `docsum`의 `core`를 FastAPI의 `async def` 엔드포인트 뒤에 두고, Docker로 묶고, API 키를 환경 변수로 관리하고, `on_retry` 대신 `logging`으로 기록을 남긴다. `pyproject.toml`과 GitHub Actions는 그대로 쓴다.

새 라이브러리나 프레임워크를 만날 때마다 이 과정의 순서를 떠올리자. 예제 코드의 낯선 줄을 이 과정의 문법으로 읽고, 쓰기 전에 실패를 나누고, 약속을 테스트로 적고, 바깥(SDK, 네트워크, 시간)은 바꿔 끼울 수 있게 떼어 내고, 결정은 이유와 함께 남긴다.
