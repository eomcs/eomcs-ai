# 2장. 컴프리헨션과 표현력 있는 문법

[파이썬 중급](README.md) 과정의 두 번째 장이다. 1장에서 "아직 배우지 않은 문법"으로 이름만 확인한 것 중 두 가지, **컴프리헨션**과 **`match` 문**을 이 장에서 배운다. 그 사이에 코드를 짧고 분명하게 만드는 작은 문법 몇 가지도 함께 익힌다.

- **리스트 컴프리헨션** — `for`와 `append()`로 새 리스트를 만들던 반복을 한 줄로 쓴다. `map()`/`filter()`를 컴프리헨션으로 바꾸고, 조건으로 거르고, 조건 표현식과 함께 쓰고, 중첩된 컴프리헨션을 읽는 순서를 익힌다.
- **딕셔너리·집합 컴프리헨션** — 같은 생각으로 딕셔너리와 집합을 만든다. 키와 값을 뒤집고, JSON 형태의 데이터에서 필요한 필드만 뽑고, 중복 없는 값을 모은다.
- **컴프리헨션을 쓰지 않을 때** — 짧게 쓸 수 있다고 늘 짧게 쓰는 것은 아니다. 반복문으로 되돌리는 판단 기준을 세운다.
- **더 표현력 있는 문법** — 확장 언패킹, 딕셔너리 병합, `any()`/`all()`, 할당 표현식(`:=`).
- **`match` 문** — 값의 **모양**에 따라 분기하고, 그 안의 값을 한 번에 꺼낸다. LLM 응답 메시지를 종류(텍스트/도구 호출/오류)에 따라 처리하는 예로 마무리한다.

- `any()`/`all()`의 단락 평가와 빈 묶음에서의 결과를 설명하고, `:=`를 써도 되는 곳과 쓰지 말아야 할 곳을 구별할 수 있다.
- `match` 문의 값·시퀀스·매핑·클래스 패턴과 가드를 써서, 딕셔너리의 모양에 따라 분기하는 함수를 만들 수 있다.

## 2.1 리스트 컴프리헨션

### 2.1.1 `for`+`append()`를 한 줄로

기초 과정에서 "새 리스트를 만드는 반복"을 여러 번 썼다. 빈 리스트를 만들고, 반복하면서 하나씩 `append()`하는 모양이다(기초 과정 2.5.2의 누적 패턴).

```python
>>> words = ["apple", "kiwi", "banana"]
>>> lengths = []
>>> for w in words:
...     lengths.append(len(w))
...
>>> lengths
[5, 4, 6]
```

같은 일을 **리스트 컴프리헨션**(list comprehension)으로 쓰면 한 줄이 된다. 기초 과정 4.5.6의 상자에서 "리스트 내포"라는 이름으로 잠깐 소개한 문법이다.

```python
>>> [len(w) for w in words]
[5, 4, 6]
```

반복문에서 컴프리헨션으로 옮겨 가는 과정을 나누어 보면 이렇다.

```
lengths = []                     ① 빈 리스트 만들기와 append()가 사라진다
for w in words:                  ② for 줄은 그대로 대괄호 안으로 들어간다
    lengths.append(len(w))       ③ append()의 괄호 안에 있던 식이 맨 앞으로 나간다

lengths = [len(w) for w in words]
           ───③──  ─────②──────
```

모양은 다음과 같다.

```
[식 for 변수 in 묶음]
```

"묶음의 각 요소를 변수에 담아, 식을 계산한 결과를 모은 **새 리스트**"다. 소리 내어 읽을 때는 **`for`부터** 읽는다. "`words`의 각 `w`에 대해, `len(w)`를 모은 리스트." 맨 앞의 식은 마지막에 읽는다. 반복문에서 `append()` 안에 있던 것, 즉 "무엇을 모으는가"이기 때문이다.

식 자리에는 값이 되는 것이면 무엇이든 올 수 있다.

```python
>>> [w.upper() for w in words]
['APPLE', 'KIWI', 'BANANA']
>>> [f"{w}({len(w)})" for w in words]
['apple(5)', 'kiwi(4)', 'banana(6)']
>>> [(w, len(w)) for w in words]
[('apple', 5), ('kiwi', 4), ('banana', 6)]
>>> [w[0] for w in words]
['a', 'k', 'b']
```

세 번째처럼 식이 튜플이면 **괄호를 꼭 쓴다.** `[w, len(w) for w in words]`는 `SyntaxError`다. 파이썬도 오류 메시지에서 "컴프리헨션의 식을 괄호로 감싸는 것을 잊지 않았느냐"(`did you forget parentheses around the comprehension target?`)고 알려 준다.

묶음 자리에도 반복할 수 있는 것이면 무엇이든 온다. 문자열, `range()`, 딕셔너리, `enumerate()`, `zip()`, 파일 객체도 된다.

```python
>>> [c * 2 for c in "abc"]
['aa', 'bb', 'cc']
>>> [n * n for n in range(5)]
[0, 1, 4, 9, 16]
>>> [f"{i}. {w}" for i, w in enumerate(words, start=1)]
['1. apple', '2. kiwi', '3. banana']
```

마지막 예처럼 `for` 뒤에서 언패킹(기초 과정 3.3.4)도 그대로 할 수 있다.

> **새 리스트를 만든다**
> 컴프리헨션은 언제나 **새 리스트**를 만든다. 원래의 `words`는 바뀌지 않는다. 기초 과정 4.3.6의 "원본을 바꾸는 함수, 새 객체를 돌려주는 함수"로 보면 컴프리헨션은 언제나 뒤쪽이다. 원본을 고쳐야 한다면 `words[:] = [w.upper() for w in words]`처럼 슬라이스에 할당하거나, 새 리스트를 원래 이름에 다시 붙인다(`words = [...]`). 두 방법의 차이는 1.3.1의 "이름표"로 설명된다. 앞의 것은 같은 리스트 객체의 내용을 바꾸고, 뒤의 것은 새 리스트 객체에 이름표를 옮겨 붙인다.

### 2.1.2 조건으로 거르기

반복문 안에 `if`가 있어서 **조건에 맞는 것만** 모으는 경우도 많다.

```python
>>> scores = [85, 42, 97, 60, 73]
>>> passed = []
>>> for s in scores:
...     if s >= 70:
...         passed.append(s)
...
>>> passed
[85, 97, 73]
```

컴프리헨션에서는 `for` 절 **뒤에** `if` 절을 붙인다.

```python
>>> [s for s in scores if s >= 70]
[85, 97, 73]
```

```
[식 for 변수 in 묶음 if 조건]
```

읽는 순서는 반복문과 같다. **`for` → `if` → 식.** "`scores`의 각 `s`에 대해, `s >= 70`이면, `s`를 모은다." 걸러진 요소는 식을 계산하지도 않는다.

거르기와 바꾸기를 함께 할 수 있다.

```python
>>> [s + 5 for s in scores if s < 70]
[47, 65]
>>> names = ["  철수 ", "", "영희", "   ", " 민수"]
>>> [n.strip() for n in names if n.strip()]
['철수', '영희', '민수']
```

두 번째 예는 빈 문자열과 공백만 있는 문자열을 거르고 앞뒤 공백을 지운다. `if n.strip()`은 공백을 지운 결과가 빈 문자열이면 거짓이 되는 성질(기초 과정 2.4.5)을 쓴 것이다. 그런데 `n.strip()`을 두 번 계산한다. 2.4.5에서 이 중복을 없애는 방법을 본다.

`if` 절을 여러 개 이어 붙일 수도 있다. `[x for x in xs if a if b]`는 `[x for x in xs if a and b]`와 같다. 그러나 `and`로 쓰는 쪽이 훨씬 읽기 쉽다. 이어 붙인 `if`는 남의 코드에서 만나면 알아보기만 하자.

### 2.1.3 `map()`/`filter()`를 컴프리헨션으로

기초 과정 4.5.6에서 `map()`과 `filter()`를 배웠다. "각각에 적용"과 "조건에 맞는 것만"이다. 이 둘은 각각 컴프리헨션의 **식**과 **`if` 절**에 대응한다.

```python
>>> nums = [1, 2, 3, 4, 5]
>>> list(map(lambda x: x * 10, nums))
[10, 20, 30, 40, 50]
>>> [x * 10 for x in nums]
[10, 20, 30, 40, 50]
>>> list(filter(lambda x: x % 2 == 0, nums))
[2, 4]
>>> [x for x in nums if x % 2 == 0]
[2, 4]
```

둘을 겹쳐 쓰면 차이가 더 드러난다.

```python
>>> list(map(lambda x: x * 10, filter(lambda x: x % 2 == 0, nums)))
[20, 40]
>>> [x * 10 for x in nums if x % 2 == 0]
[20, 40]
```

`map`/`filter` 쪽은 안쪽(`filter`)부터 바깥쪽(`map`)으로 거꾸로 읽어야 하고, `lambda x:`가 두 번 나온다. 컴프리헨션은 왼쪽에서 오른쪽으로 읽힌다. 파이썬 코드에서 `map()`/`filter()`보다 컴프리헨션을 훨씬 많이 보게 되는 이유다.

그렇다고 `map()`을 쓰지 말라는 것은 아니다. **이미 이름이 있는 함수**를 그대로 적용할 때는 `map()`도 충분히 짧다.

```python
>>> list(map(int, "85 92 78".split()))
[85, 92, 78]
>>> [int(t) for t in "85 92 78".split()]
[85, 92, 78]
```

둘 다 좋다. 람다를 새로 만들어야 한다면 컴프리헨션을 고르자.

> **결과가 만들어지는 때가 다르다**
> 기초 과정 4.5.6에서 `map()`의 결과를 그대로 출력하면 `<map object ...>`만 보였다. `map()`과 `filter()`는 결과를 미리 다 만들지 않고 **꺼낼 때마다 하나씩** 계산한다. 리스트 컴프리헨션은 그 자리에서 **결과 전체를 리스트로** 만든다. 그래서 `map()`의 결과는 한 번 꺼내면 끝이지만, 컴프리헨션의 결과는 리스트이므로 몇 번이든 다시 쓸 수 있다. "꺼낼 때마다 하나씩" 계산하는 방식은 3장의 주제다.

### 2.1.4 조건 표현식과 함께 쓰기

기초 과정 2.4.6의 **조건 표현식**(`A if 조건 else B`)은 두 값 중 하나를 고르는 **식**이다. 식이므로 컴프리헨션의 맨 앞에 쓸 수 있다.

```python
>>> scores = [85, 42, 97, 60, 73]
>>> ["합격" if s >= 70 else "불합격" for s in scores]
['합격', '불합격', '합격', '불합격', '합격']
```

이제 컴프리헨션 안에 `if`가 들어가는 자리가 두 곳이 되었다. 둘은 하는 일이 전혀 다르다.

| 위치 | 모양 | 하는 일 | 결과의 길이 |
|---|---|---|---|
| 맨 앞(식 자리) | `[A if 조건 else B for x in xs]` | 요소마다 **값을 고른다** | 원래와 같다 |
| `for` 뒤(`if` 절) | `[x for x in xs if 조건]` | 조건에 맞는 요소만 **남긴다** | 같거나 짧다 |

자리를 바꾸어 쓰면 문법 오류가 난다.

```python
>>> [s if s >= 70 for s in scores]
  File "<python-input-2>", line 1
    [s if s >= 70 for s in scores]
     ^^^^^^^^^^^^
SyntaxError: expected 'else' after 'if' expression
>>> [s for s in scores if s >= 70 else 0]
  File "<python-input-3>", line 1
    [s for s in scores if s >= 70 else 0]
                                  ^^^^
SyntaxError: invalid syntax
```

첫 번째는 맨 앞의 식 자리에 `else` 없는 `if`를 썼다. 식 자리의 `if`는 조건 표현식이므로 `else`가 꼭 있어야 한다. 두 번째는 거르는 `if` 절에 `else`를 붙였다. 거르는 `if`에는 "거짓일 때의 값"이라는 것이 없다. (파이썬 버전에 따라 첫 번째도 `invalid syntax`로만 나올 수 있다.)

두 자리를 함께 쓸 수도 있다. 이때도 `for` → `if` 절 → 식 순서로 읽는다.

```python
>>> raw = ["85", "결석", "", "97", "abc"]
>>> [int(t) if t.isdecimal() else 0 for t in raw if t]
[85, 0, 97, 0]
```

"`raw`의 각 `t`에 대해, 빈 문자열이 아니면, 숫자이면 정수로, 아니면 0으로." 이 정도가 한 줄로 읽을 수 있는 한계에 가깝다. 이보다 조건이 늘어나면 2.3의 기준으로 반복문을 다시 고려한다.

### 2.1.5 중첩 컴프리헨션을 읽는 순서

**`for`가 두 개인 컴프리헨션**

중첩 리스트(기초 과정 3.1.9)를 한 줄로 펴는 반복문이다.

```python
>>> matrix = [[1, 2, 3], [4, 5, 6]]
>>> flat = []
>>> for row in matrix:
...     for n in row:
...         flat.append(n)
...
>>> flat
[1, 2, 3, 4, 5, 6]
```

컴프리헨션으로는 `for` 절을 **반복문에 쓴 순서 그대로** 이어 쓴다.

```python
>>> [n for row in matrix for n in row]
[1, 2, 3, 4, 5, 6]
```

```
for row in matrix:          →  [n  for row in matrix  for n in row]
    for n in row:                   ─────바깥 for────  ──안쪽 for──
        flat.append(n)
```

바깥 반복이 먼저, 안쪽 반복이 나중이다. 반복문을 위에서 아래로 읽던 순서를 왼쪽에서 오른쪽으로 옮긴 것이다. 이 순서를 거꾸로 쓰는 실수가 아주 흔하다.

같은 셸에서 위의 반복문을 실행했다면 반복문의 변수 `row`가 아직 남아 있다. 반복문의 변수는 반복이 끝난 뒤에도 남기 때문이다(2.1.6). 먼저 `del row`로 지운 뒤 순서를 거꾸로 쓴 컴프리헨션을 실행한다.

```python
>>> del row
>>> [n for n in row for row in matrix]
Traceback (most recent call last):
  File "<python-input-6>", line 1, in <module>
    [n for n in row for row in matrix]
                ^^^
NameError: name 'row' is not defined. Did you mean: 'pow'?
```

첫 번째 `for n in row`를 실행하는 시점에 `row`는 아직 없다. 그런데 `del row`를 하지 않았다면 어떻게 될까? 앞의 반복문이 남긴 값을 다시 넣어 확인한다.

```python
>>> row = [4, 5, 6]  # 앞의 반복문이 마지막으로 남긴 값
>>> [n for n in row for row in matrix]
[4, 4, 5, 5, 6, 6]
```

오류도 나지 않고 **엉뚱한 결과**가 나왔다. 첫 번째 `for`는 바깥에 남아 있던 `row`(`[4, 5, 6]`)를 훑고, 두 번째 `for row in matrix`는 `matrix`의 행 수(2)만큼 `n`을 되풀이했다. 이렇게 조용히 틀리는 것보다 오류가 나는 편이 차라리 낫다.

`if` 절은 어느 `for` 뒤에든 붙일 수 있고, 그 자리의 반복문 안에 `if`가 있는 것과 같다.

```python
>>> [n for row in matrix for n in row if n % 2 == 0]
[2, 4, 6]
```

`for`가 두 개인 컴프리헨션은 LLM 코드에서도 자주 보인다. 문서 여러 개를 조각(청크)으로 나눈 결과를 한 리스트로 모을 때다.

```python
>>> docs = [
...     {"title": "안내서", "chunks": ["설치", "실행"]},
...     {"title": "FAQ", "chunks": ["요금", "환불", "탈퇴"]},
... ]
>>> [chunk for doc in docs for chunk in doc["chunks"]]
['설치', '실행', '요금', '환불', '탈퇴']
```

**컴프리헨션 안의 컴프리헨션**

모양이 비슷하지만 전혀 다른 것이 있다. 식 자리에 **또 하나의 컴프리헨션**이 들어간 경우다.

```python
>>> [[n * 10 for n in row] for row in matrix]
[[10, 20, 30], [40, 50, 60]]
```

결과가 펴지지 않고 **중첩 리스트 그대로** 남았다. 바깥 컴프리헨션이 `row`마다 "안쪽 컴프리헨션이 만든 리스트 하나"를 모으기 때문이다. 읽을 때는 바깥부터 읽는다. "`matrix`의 각 `row`에 대해, `[n * 10 for n in row]`를 모은다." 안쪽 대괄호는 그다음에 따로 읽는다.

| 모양 | 결과 | 반복문으로 쓰면 |
|---|---|---|
| `[n for row in m for n in row]` | 펼친 리스트 | `append()`가 안쪽 `for` 안에 하나 |
| `[[n for n in row] for row in m]` | 중첩 리스트 | 바깥 반복마다 새 리스트를 만들어 `append()` |

행과 열을 바꾸는(전치) 예도 같은 방법으로 읽는다.

```python
>>> [[row[i] for row in matrix] for i in range(3)]
[[1, 4], [2, 5], [3, 6]]
```

"0, 1, 2의 각 `i`에 대해, 모든 행의 `i`번째 값을 모은 리스트를 모은다."

> **1장 실습 1-3의 q2 다시 보기**
> `grid = [[0] * 2] * 2`는 **같은 리스트 하나**를 두 번 가리키는 바깥 리스트를 만들었다(기초 과정 3.2.6). 그래서 `grid[0][0] = 9`가 두 행을 모두 바꾸었다. 컴프리헨션으로 만들면 반복할 때마다 `[0] * 2`가 **새로** 계산되므로 행마다 다른 리스트가 된다.
>
> ```python
> >>> grid = [[0] * 2 for _ in range(2)]
> >>> grid[0][0] = 9
> >>> grid
> [[9, 0], [0, 0]]
> ```
>
> 반복 변수를 쓰지 않을 때는 관례대로 `_`라고 이름 붙인다(기초 과정 3.3.3).

### 2.1.6 컴프리헨션의 변수는 밖으로 새지 않는다

`for` 반복문의 변수는 반복이 끝난 뒤에도 남는다. 컴프리헨션의 변수는 그렇지 않다.

```python
>>> x = "바깥"
>>> squares = [x * x for x in range(3)]
>>> x
'바깥'
>>> for x in range(3):
...     pass
...
>>> x
2
```

컴프리헨션의 `x`는 컴프리헨션 안에서만 쓰이는 이름이다. 바깥의 `x`를 덮어쓰지 않는다. 반대로 반복문의 `x`는 바깥의 `x`를 덮어써서 마지막 값 `2`가 남았다. 컴프리헨션을 쓰면 이름이 의도치 않게 남아서 생기는 실수(2.1.5의 `row` 같은)가 줄어든다.

**긴 컴프리헨션은 여러 줄로**

컴프리헨션은 대괄호 안이므로 줄을 나누어도 된다(기초 과정 3.1.1). 한 줄에 다 들어가지 않으면 `for` 절과 `if` 절마다 줄을 나눈다.

```python
active_names = [
    user["name"].strip()
    for user in users
    if user["active"]
]
```

1장에서 설정한 대로 저장할 때 Ruff가 서식을 정리하므로, 줄이 너무 길면 Ruff가 이렇게 나누어 준다. 이렇게 나누어도 읽기 어렵다면 2.3에서 볼 "반복문으로 되돌리기"를 고려할 때다.

## 2.2 딕셔너리·집합 컴프리헨션

### 2.2.1 딕셔너리 컴프리헨션

중괄호 안에 `키: 값`을 쓰면 **딕셔너리 컴프리헨션**이 된다.

```
{키_식: 값_식 for 변수 in 묶음 if 조건}
```

```python
>>> words = ["apple", "kiwi", "banana"]
>>> {w: len(w) for w in words}
{'apple': 5, 'kiwi': 4, 'banana': 6}
```

반복문으로는 이렇다.

```python
result = {}
for w in words:
    result[w] = len(w)
```

딕셔너리를 순회할 때는 `items()`로 키와 값을 함께 꺼내는 경우가 대부분이다(기초 과정 3.4.4).

```python
>>> prices = {"커피": 4500, "라떼": 5000, "케이크": 6500}
>>> {name: price for name, price in prices.items() if price <= 5000}
{'커피': 4500, '라떼': 5000}
>>> {name: int(price * 0.9) for name, price in prices.items()}
{'커피': 4050, '라떼': 4500, '케이크': 5850}
```

첫 번째는 값으로 거르고, 두 번째는 값을 바꾸었다. 둘 다 원래의 `prices`는 바뀌지 않는다.

같은 키가 여러 번 나오면 **나중 것이 남는다.** 딕셔너리에 같은 키로 여러 번 할당한 것과 같다(기초 과정 3.4.3). 이 성질이 다음 절에서 문제를 일으킨다.

> **두 리스트로 딕셔너리 만들기**
> 키 리스트와 값 리스트가 따로 있으면 `{k: v for k, v in zip(keys, values)}`로 만들 수 있다. 하지만 `dict(zip(keys, values))`가 더 짧다. 키나 값을 **바꾸거나 거를 일이 없다면** 컴프리헨션이 필요 없다. 리스트도 마찬가지다. `[x for x in items]`는 아무것도 바꾸지 않으므로 `list(items)`로 충분하다.

### 2.2.2 키와 값 뒤집기

국가 코드로 이름을 찾는 딕셔너리가 있는데, 이름으로 코드를 찾고 싶다. 키와 값의 자리를 바꾸면 된다.

```python
>>> code_to_name = {"KR": "한국", "JP": "일본", "US": "미국"}
>>> name_to_code = {name: code for code, name in code_to_name.items()}
>>> name_to_code
{'한국': 'KR', '일본': 'JP', '미국': 'US'}
>>> name_to_code["일본"]
'JP'
```

`for code, name in ...`으로 받아서 `name: code`로 쓰는 것이 핵심이다. 그런데 **값이 겹치면** 조용히 문제가 생긴다.

```python
>>> grades = {"철수": "A", "영희": "B", "민수": "A"}
>>> {g: n for n, g in grades.items()}
{'A': '민수', 'B': '영희'}
```

`"A"` 키가 두 번 만들어졌고 나중 것(`'민수'`)이 남았다. `'철수'`는 오류도 없이 사라졌다. 뒤집기 전에 값이 겹치지 않는다는 것을 확신할 수 없다면, 뒤집은 결과의 길이를 확인한다.

```python
>>> len(grades), len({g: n for n, g in grades.items()})
(3, 2)
```

길이가 다르면 값이 겹친 것이다. 겹치는 값마다 **여러 개를 모아야** 한다면(예: 성적별 학생 목록) 컴프리헨션이 아니라 반복문과 `defaultdict`(기초 과정 8.2.4)를 쓴다. 이것을 컴프리헨션으로 억지로 쓰는 모습은 2.3에서 본다.

### 2.2.3 JSON 형태 데이터에서 필요한 필드만 뽑기

JSON을 파이썬으로 읽으면 JSON 객체(`{...}`)는 딕셔너리로, 배열(`[...]`)은 리스트로 바뀐다(기초 과정 3.4.6). 이 절의 사용자 목록 API는 사용자 객체의 배열을 돌려주므로 **딕셔너리의 리스트**가 된다. 웹 API와 LLM API의 응답에는 대개 **필요한 것보다 많은 필드**가 들어 있다. 컴프리헨션은 여기서 필요한 것만 뽑는 데 가장 많이 쓰인다.

`ch02/users_api.py`를 만들고 사용자 목록 API의 응답을 흉내 낸 데이터를 넣는다.

```python
users = [
    {
        "id": 101,
        "name": "김철수",
        "email": "cs@example.com",
        "active": True,
        "profile": {"city": "서울", "age": 31},
    },
    {
        "id": 102,
        "name": "이영희",
        "email": "yh@example.com",
        "active": False,
        "profile": {"city": "부산", "age": 27},
    },
    {
        "id": 103,
        "name": "박민수",
        "email": "ms@example.com",
        "active": True,
        "profile": {"city": "서울"},
    },
]
```

같은 폴더에서 대화형 셸을 열고 `from users_api import users`로 가져와도 되고(기초 과정 8장), 파일 아래쪽에 `print()`로 하나씩 확인해도 된다.

**1) 필드 몇 개만 남기기**

```python
>>> [{"id": u["id"], "name": u["name"]} for u in users if u["active"]]
[{'id': 101, 'name': '김철수'}, {'id': 103, 'name': '박민수'}]
```

식 자리에 딕셔너리를 만드는 식을 썼다. 남길 필드가 많다면 필드 이름을 리스트로 두고, 식 자리에 **딕셔너리 컴프리헨션**을 쓴다.

```python
>>> fields = ["id", "email"]
>>> [{k: u[k] for k in fields} for u in users]
[{'id': 101, 'email': 'cs@example.com'}, {'id': 102, 'email': 'yh@example.com'}, {'id': 103, 'email': 'ms@example.com'}]
```

2.1.5의 "컴프리헨션 안의 컴프리헨션"이다. 바깥부터 읽는다. "`users`의 각 `u`에 대해, `{k: u[k] for k in fields}`를 모은다." 안쪽은 "`fields`의 각 `k`에 대해 `k: u[k]`"다.

**2) 없을 수도 있는 필드**

```python
>>> [u["profile"]["age"] for u in users]
Traceback (most recent call last):
  ...
KeyError: 'age'
>>> [u["profile"].get("age") for u in users]
[31, 27, None]
```

박민수의 `profile`에는 `age`가 없다. API 응답에서 선택 항목은 빠져 있기 일쑤다. 그런 필드는 `get()`으로 꺼낸다(기초 과정 3.4.2). 어느 필드가 **반드시** 있고 어느 필드가 **없을 수도** 있는지는 API 문서를 보고 정한다. 5장의 Pydantic은 이 구분을 코드로 적고 자동으로 검사하는 도구다.

**3) id로 찾을 수 있게 만들기**

리스트에서 특정 사용자를 찾으려면 처음부터 훑어야 한다. 자주 찾는다면 **id를 키로 하는 딕셔너리**로 바꾼다.

```python
>>> by_id = {u["id"]: u for u in users}
>>> by_id[102]["name"]
'이영희'
>>> 104 in by_id
False
```

기초 과정 3.6.2 "고르는 질문"에서 본 "자주 찾는다면 딕셔너리"를 한 줄로 만든 것이다. 값으로 들어간 것은 원래 리스트의 **딕셔너리 객체 그 자체**다(복사가 아니다). `by_id[102]["active"] = True`라고 쓰면 `users[1]`도 바뀐다(1.3.1).

**4) LLM 대화 기록에서**

기초 과정 3.4.6의 대화 기록에서도 같은 일을 한다.

```python
>>> messages = [
...     {"role": "system", "content": "당신은 친절한 파이썬 강사입니다."},
...     {"role": "user", "content": "리스트가 뭐예요?"},
...     {"role": "assistant", "content": "여러 값을 순서대로 모은 것입니다."},
...     {"role": "user", "content": "튜플과 차이는요?"},
... ]
>>> [m["content"] for m in messages if m["role"] == "user"]
['리스트가 뭐예요?', '튜플과 차이는요?']
>>> [m for m in messages if m["role"] != "system"]
```

두 번째 줄은 시스템 메시지를 뺀 대화 기록을 만든다. 일부 LLM API는 시스템 프롬프트를 대화 기록과 **따로** 넘기도록 되어 있어서, 이런 줄을 실제로 자주 쓴다.

### 2.2.4 집합 컴프리헨션 — 중복 없는 값 모으기

중괄호 안에 `키: 값`이 아니라 식 하나만 쓰면 **집합 컴프리헨션**이다. 결과는 집합(기초 과정 3.5)이므로 **중복이 없다.**

```python
>>> {u["profile"]["city"] for u in users}
{'서울', '부산'}
```

세 사용자 중 두 명이 서울이지만 `'서울'`은 한 번만 들어 있다. 집합에는 순서가 없으므로, 출력하는 순서는 실행할 때마다 다를 수 있다. 정해진 순서로 보여 주어야 한다면 `sorted()`로 감싼다. 결과는 리스트가 된다.

```python
>>> sorted({u["profile"]["city"] for u in users})
['부산', '서울']
```

`for`가 두 개인 모양과 함께 쓰면 "모든 글에 붙은 태그를 중복 없이" 같은 일을 한 줄로 한다.

```python
>>> posts = [
...     {"title": "파이썬 시작", "tags": ["python", "입문"]},
...     {"title": "컴프리헨션", "tags": ["python", "문법"]},
...     {"title": "RAG 소개", "tags": ["llm", "입문"]},
... ]
>>> sorted({tag for post in posts for tag in post["tags"]})
['llm', 'python', '문법', '입문']
```

대소문자만 다른 단어를 하나로 보고 싶다면 식 자리에서 바꾼 뒤 모은다. `{w.lower() for w in words}`.

> **빈 중괄호는 집합이 아니다**
> `{}`는 빈 **딕셔너리**다. 빈 집합은 `set()`으로 만든다(기초 과정 3.5.1). 컴프리헨션도 같은 규칙을 따른다. 중괄호 안에 콜론(`:`)이 있으면 딕셔너리, 없으면 집합이다.

### 2.2.5 괄호에 따라 달라지는 결과

컴프리헨션의 괄호 종류에 따라 결과가 달라진다.

| 모양 | 결과 |
|---|---|
| `[x for x in xs]` | 리스트 |
| `{x for x in xs}` | 집합 |
| `{k: v for k, v in pairs}` | 딕셔너리 |
| `(x for x in xs)` | **튜플이 아니다** — 제너레이터(3장) |

마지막 줄을 셸에서 확인한다.

```python
>>> (n * 2 for n in range(3))
<generator object <genexpr> at 0x102840660>
```

소괄호로 감싼 것은 튜플이 아니라 **제너레이터 표현식**이다. 2.1.3의 `map()`처럼 꺼낼 때마다 하나씩 계산하는 객체를 만든다. 3장에서 자세히 배운다. 튜플이 필요하면 `tuple(n * 2 for n in range(3))`처럼 `tuple()`에 넘긴다.

### 실습 2-2. 딕셔너리·집합 컴프리헨션

`ch02/products.py`를 만들고 상품 검색 API의 응답을 흉내 낸 다음 데이터를 넣는다. 아래의 일을 **각각 컴프리헨션 한 개**로 하고 결과를 출력한다. (필요하면 `sorted()`, `len()` 같은 함수로 감싸도 된다.)

```python
response = {
    "query": "키보드",
    "total": 4,
    "items": [
        {"id": "p1", "title": "기계식 키보드", "price": 89000, "tags": ["게이밍", "유선"], "stock": 3},
        {"id": "p2", "title": "무선 키보드", "price": 39000, "tags": ["무선", "사무용"], "stock": 0},
        {"id": "p3", "title": "접이식 키보드", "price": 45000, "tags": ["무선", "휴대용"]},
        {"id": "p4", "title": "저소음 키보드", "price": 39000, "tags": ["사무용", "유선"], "stock": 12},
    ],
}
```

1. 재고가 있는 상품의 이름 리스트. `stock` 필드가 없는 상품은 재고 0으로 본다.
2. `{상품 id: 가격}` 딕셔너리.
3. 2의 결과를 뒤집은 `{가격: 상품 id}` 딕셔너리. 길이를 2와 비교하고, 무엇이 사라졌는지 적는다.
4. 모든 상품의 태그를 중복 없이, 가나다순 리스트로.
5. 상품마다 `id`와 `price`만 남긴 딕셔너리의 리스트.
6. 10% 할인한 가격의 `{상품 이름: 할인 가격}` 딕셔너리. 할인 가격은 정수로 만든다(2.2.1처럼 `int(price * 0.9)`, 또는 정수 나눗셈 `price * 9 // 10`).
7. `"무선"` 태그가 붙은 상품의 `{id: 이름}` 딕셔너리.

## 2.3 컴프리헨션을 쓰지 않을 때

컴프리헨션을 익히고 나면 모든 반복을 컴프리헨션으로 쓰고 싶어진다. AI 코딩 도구도 반복문을 컴프리헨션으로 바꾸는 것을 좋아한다. 그러나 1장 1.1.2에서 본 것처럼 짧게 쓴 코드가 늘 나은 것은 아니다. 이 절에서는 반복문이 **더 나은** 경우를 네 가지로 나누어 본다.

### 2.3.1 부수 효과가 목적인 반복

컴프리헨션은 **새 컬렉션을 만드는** 문법이다. 출력하기, 파일에 쓰기, 다른 리스트에 추가하기처럼 반복의 목적이 **무언가를 하는 것**(부수 효과)이라면 컴프리헨션을 쓰지 않는다.

```python
>>> [print(name) for name in ["철수", "영희"]]
철수
영희
[None, None]
```

출력은 되었지만, 쓸모없는 리스트 `[None, None]`이 만들어졌다. `print()`가 돌려주는 값이 `None`이기 때문이다(기초 과정 4.1.6). 변수에 담아 마우스를 올리면 Pylance도 `list[None]`이라고 알려 준다. 파일 쓰기도 마찬가지다.

```python
# 이렇게 쓰지 않는다
[f.write(line + "\n") for line in lines]   # 쓴 글자 수의 리스트가 만들어진다
[result.append(x * 2) for x in xs]          # None의 리스트가 만들어진다

# 이렇게 쓴다
for line in lines:
    f.write(line + "\n")
result.extend(x * 2 for x in xs)            # 또는 result += [x * 2 for x in xs]
```

메모리 낭비보다 더 큰 문제는 **의도가 흐려진다**는 것이다. 대괄호를 보면 읽는 사람은 "새 리스트를 만드는구나" 하고 그 리스트가 어디에 쓰이는지 찾게 된다. 반복의 목적이 행동이라면 `for` 문이 그 의도를 그대로 말한다.

### 2.3.2 두 겹 이상의 중첩

`for` 두 개까지는 읽을 만하다. 셋이 되고 `if`가 여러 개 끼면 반복문보다 읽기 어려워진다. 다음은 스프레드시트를 흉내 낸 데이터에서 비어 있지 않은 칸을 모으는 코드다.

```python
cells = [cell.strip() for sheet in workbook for row in sheet["rows"] if row for cell in row if cell and cell.strip()]
```

같은 일을 반복문으로 쓰면 다음과 같다.

```python
cells = []
for sheet in workbook:
    for row in sheet["rows"]:
        if not row:
            continue
        for cell in row:
            if cell and cell.strip():
                cells.append(cell.strip())
```

줄은 길어졌지만, 들여쓰기가 반복의 깊이를 **눈으로** 보여 준다. 중단점을 찍을 자리도 생긴다. 또 다른 방법은 **안쪽을 함수로 빼는 것**이다.

```python
def cells_of(sheet):
    """시트 하나에서 비어 있지 않은 칸을 모은다."""
    return [cell.strip() for row in sheet["rows"] for cell in row if cell and cell.strip()]


cells = [cell for sheet in workbook for cell in cells_of(sheet)]
```

함수 이름이 "이 부분이 무엇을 하는가"를 설명해 주므로 각 컴프리헨션이 다시 읽을 만한 길이가 되었다. (`if row`는 빼도 결과가 같다. 빈 행이면 안쪽 `for`가 한 번도 돌지 않기 때문이다.)

### 2.3.3 디버깅하기 어려운 긴 식

컴프리헨션은 **한 줄 안에서** 반복·거르기·변환이 모두 일어난다. 그래서 결과가 이상할 때 어느 단계에서 생각과 달라졌는지 짚기 어렵다. 디버거는 "줄" 단위로 움직이고, 컴프리헨션 안에는 `print()`를 끼워 넣을 자리도 마땅치 않다.

더 결정적인 차이는 **컴프리헨션 안에서는 예외를 잡을 수 없다**는 것이다. 거래 기록의 금액을 정수로 바꾸는 예를 보자.

```python
records = [
    {"date": "2026-11-01", "amount": "4500"},
    {"date": "2026-11-02", "amount": "12,000"},
    {"date": "2026-11-03", "amount": "8000"},
    {"date": "2026-11-04", "amount": "만 원"},
]
amounts = [int(r["amount"]) for r in records]
```

```
ValueError: invalid literal for int() with base 10: '12,000'
```

첫 번째 잘못된 값에서 멈췄다. 잘못된 값이 몇 개인지, 어느 날짜의 기록인지는 알 수 없다. 컴프리헨션 안에는 `try`/`except`를 쓸 수 없다. 기록이 천 건이라면, 하나를 고치고 다시 실행하고, 또 하나를 고치고 다시 실행해야 한다. 반복문이라면 기록마다 예외를 잡아서 **모든** 잘못을 한 번에 모을 수 있다.

```python
amounts = []
errors = []
for r in records:
    try:
        amounts.append(int(r["amount"]))
    except ValueError:
        errors.append(f"{r['date']}: 금액 {r['amount']!r}")

print(amounts)
print(errors)
```

```
[4500, 8000]
["2026-11-02: 금액 '12,000'", "2026-11-04: 금액 '만 원'"]
```

기초 과정 10장의 가계부 프로그램에서 파일을 읽을 때 잘못된 줄을 모두 모아 알린 것(기초 과정 10.1.4)도 이 방식이었다. 여기서도 2.3.2처럼 **예외 처리를 함수로 빼는** 방법이 있다. `parse_amount(text)`가 잘못된 값이면 `None`을 돌려주게 만들면 `[parse_amount(r["amount"]) for r in records]`는 다시 짧은 컴프리헨션이 된다. 다만 어떤 값이 왜 실패했는지는 그 함수 안에서 따로 기록해야 한다.

### 2.3.4 한 번 훑어서 여러 결과를 만들 때

1장 1.1.2에서 본 가계부 요약이 이 경우다.

```python
income = 0
expense = 0
by_category = defaultdict(int)
for t in transactions:
    if t.kind == "수입":
        income += t.amount
    else:
        expense += t.amount
        by_category[t.category] += t.amount
```

반복문 하나가 **세 가지 결과**를 함께 만든다. 컴프리헨션은 결과를 **하나** 만드는 문법이다. 세 결과를 컴프리헨션으로 만들면 목록을 세 번 훑어야 하고, 분류별 합계는 이렇게 된다.

```python
by_category = {
    c: sum([t.amount for t in transactions if t.kind == "지출" and t.category == c])
    for c in {t.category for t in transactions if t.kind == "지출"}
}
```

컴프리헨션이 세 개 겹쳤다. 분류마다 전체 목록을 다시 훑으므로 분류가 많아질수록 느려지기도 한다. 2.2.2에서 "겹치는 값마다 여러 개를 모으는" 일을 반복문과 `defaultdict`로 하라고 한 이유가 이것이다.

**앞의 결과에 기대는 반복**도 같은 경우다. 누적 합계를 리스트로 만드는 일이다.

```python
running = []
total = 0
for x in [1, 2, 3]:
    total += x
    running.append(total)
# running == [1, 3, 6]
```

반복할 때마다 `total`이라는 **상태**가 바뀐다. 컴프리헨션은 요소 하나하나를 서로 독립적으로 바꾸는 데 알맞다. 앞 요소의 결과를 기억해야 하는 반복은 반복문이 자연스럽다. (2.4.5에서 이것을 억지로 컴프리헨션으로 쓰는 모습을 보고, 3장에서 이 일을 하는 `itertools.accumulate()`를 만난다.)

### 2.3.5 판단 기준

다음 질문에 모두 "예"라면 컴프리헨션을 쓴다. 하나라도 "아니요"라면 반복문(또는 함수로 빼기)을 먼저 고려한다.

| 질문 | "아니요"라면 |
|---|---|
| 반복의 목적이 **새 컬렉션 하나**를 만드는 것인가? | 출력·쓰기·추가 같은 부수 효과는 `for` 문. 결과가 여러 개면 반복문 하나로 한 번에 |
| "○○의 각 ○에 대해, ~이면, ~을 모은다"처럼 **한 문장**으로 읽히는가? | 반복문으로 쓰거나, 안쪽을 이름 있는 함수로 뺀다 |
| `for` 절은 두 개 이하, `if` 절은 하나(조건이 짧은 것) 이하인가? | 반복문으로 쓰거나, 안쪽을 함수로 뺀다 |
| 요소마다 **예외 처리**나 기록(로그)이 필요 없는가? | 반복문 안에서 `try`/`except` |
| 요소를 **서로 독립적으로** 바꾸는가? (앞 요소의 결과에 기대지 않는가?) | 반복문 |

**반복문으로 되돌리는 것은 실패가 아니다.** 컴프리헨션으로 썼다가 조건이 늘어나서 다시 반복문으로 바꾸는 일은 실무에서 흔하다. 반대로 반복문으로 시작했다가 조건이 단순해져서 컴프리헨션으로 바꾸기도 한다. 기준은 늘 "다음에 이 코드를 읽을 사람(몇 달 뒤의 나 포함)이 한 번에 읽을 수 있는가"다.

> **AI가 컴프리헨션으로 바꿔 주었을 때**
> AI 코딩 도구에 "더 파이썬답게 바꿔 줘"라고 하면 반복문이 컴프리헨션으로 바뀌어 돌아오는 경우가 많다. 받아들이기 전에 1장 1.1.5의 원칙대로, 바뀐 컴프리헨션을 **한 문장으로** 읽어 본다. 그리고 위 표의 질문을 확인한다. 특히 원래 반복문에 있던 `try`/`except`나 `print()`가 **조용히 사라지지** 않았는지 본다. 동작이 바뀌었을 수 있다.

### 실습 2-3. 바꿀까, 둘까

아래 다섯 코드를 각각 판단해서 `ch02/notes.md`에 적는다. "컴프리헨션으로 바꾼다", "반복문으로 둔다(또는 되돌린다)", "함수로 뺀다" 중 하나를 고르고, 2.3.5 표의 어느 질문 때문인지 한 줄로 적는다. 바꾸기로 한 것은 실제로 바꾼 코드도 적는다.

```python
# (1)
for m in messages:
    log_file.write(f"[{m['role']}] {m['content']}\n")

# (2)
valid = []
for r in rows:
    if r["score"] >= 0:
        valid.append(r)

# (3)
lowest = highest = rows[0]["score"]
total = 0
for r in rows:

# (4)
settings = [line.strip().split("=") for line in lines if line.strip() and not line.strip().startswith("#")]
```

## 2.4 더 표현력 있는 문법

### 2.4.1 확장 언패킹 — `first, *rest = items`

기초 과정 3.3.3에서 별표(`*`)로 "나머지"를 모으는 언패킹을 배웠다. 여기서는 그 규칙을 정리하고, 쓰임새를 넓힌다.

```python
>>> first, *rest = [10, 20, 30, 40]
>>> first, rest
(10, [20, 30, 40])
>>> *init, last = [10, 20, 30, 40]
>>> init, last
([10, 20, 30], 40)
>>> head, *middle, tail = "가나다라"
>>> head, middle, tail
('가', ['나', '다'], '라')
```

규칙은 네 가지다.

1. 별표 붙은 이름은 앞뒤의 이름들이 **자리를 먼저 차지하고 남은 것**을 모은다. 가운데에도 올 수 있다.
2. 별표 붙은 이름은 오른쪽이 튜플이든 문자열이든 **언제나 리스트**가 된다. 위의 `middle`도 리스트다.
3. 남은 것이 없으면 **빈 리스트**가 된다. 별표 없는 이름의 개수만큼은 꼭 있어야 한다.
4. 별표는 **하나만** 쓸 수 있다.

```python
>>> first, *rest = [1]
>>> rest
[]
>>> first, *rest = []
Traceback (most recent call last):
  File "<python-input-4>", line 1, in <module>
    first, *rest = []
    ^^^^^^^^^^^^
ValueError: not enough values to unpack (expected at least 1, got 0)
>>> *a, *b = [1, 2, 3]
  File "<python-input-5>", line 1
SyntaxError: multiple starred expressions in assignment
```

`*a, *b`는 어디까지가 `a`이고 어디부터가 `b`인지 정할 수 없으므로 문법 오류다.

**쓰임새**

```python
# 첫 줄은 머리글, 나머지는 데이터
header, *rows = lines

# 명령과 인자 나누기 (기초 과정 3.3.3, 4장 실습 4-7)
command, *args = "add 커피 4500".split()

# 처음과 끝만 필요하다 — 가운데는 버린다
first_turn, *_, last_turn = conversation["turns"]

# 반복문에서: 이름 뒤의 점수 개수가 행마다 다를 때
for name, *scores in [["철수", 90, 85], ["영희", 70], ["민수"]]:
    print(name, scores)
```

마지막 반복문은 `철수 [90, 85]`, `영희 [70]`, `민수 []`를 출력한다. 행마다 길이가 달라도 언패킹이 실패하지 않는다. 쓰지 않을 나머지는 `*_`로 받는다.

### 2.4.2 언패킹으로 리스트·딕셔너리 조립하기

별표는 **값을 만드는 쪽**에서도 쓴다. 리스트·튜플·집합을 만드는 괄호 안에서 `*묶음`은 "이 묶음의 요소들을 여기에 풀어 넣는다"는 뜻이다. 1장 1.3.3에서 본, 함수를 호출할 때 `*`로 풀어서 넘기는 것과 같은 생각이다.

```python
>>> a = [1, 2]
>>> b = (3, 4)
>>> [*a, *b]
[1, 2, 3, 4]
>>> [0, *a, 99]
[0, 1, 2, 99]
>>> [*"ab", *range(2)]
['a', 'b', 0, 1]
>>> {*a, *b, 1}
{1, 2, 3, 4}
```

`a + b`는 리스트와 튜플이라 `TypeError`가 나지만, `[*a, *b]`는 반복할 수 있는 것이면 종류가 달라도 된다. 결과의 종류는 바깥 괄호가 정한다.

LLM API에 보낼 대화 기록을 조립할 때 이 모양이 자주 나온다.

```python
system = {"role": "system", "content": "당신은 친절한 파이썬 강사입니다."}
history = [
    {"role": "user", "content": "리스트가 뭐예요?"},
    {"role": "assistant", "content": "여러 값을 순서대로 모은 것입니다."},
]
question = {"role": "user", "content": "튜플과 차이는요?"}

messages = [system, *history, question]
```

`history`를 바꾸지 않고 새 리스트를 만든다. `history.append(question)`과 달리 원래 기록은 그대로다.

딕셔너리는 별표 **두 개**(`**`)로 푼다. 1장 1.3.3의 `**kwargs`와 같은 기호다.

```python
>>> {**{"a": 1}, "a": 9, "b": 2}
{'a': 9, 'b': 2}
```

같은 키가 여러 번 나오면 **나중 것이 이긴다.** 다음 절에서 이 성질을 쓴다.

### 2.4.3 딕셔너리 병합 — `|`, `{**a, **b}`

LLM API를 부를 때는 기본 설정에 요청마다 몇 가지만 바꾸어 넘기는 일이 많다.

```python
>>> defaults = {"model": "small-model", "temperature": 0.7, "max_tokens": 512}
>>> options = {"temperature": 0.2}
>>> {**defaults, **options}
{'model': 'small-model', 'temperature': 0.2, 'max_tokens': 512}
>>> defaults | options
{'model': 'small-model', 'temperature': 0.2, 'max_tokens': 512}
>>> defaults
{'model': 'small-model', 'temperature': 0.7, 'max_tokens': 512}
```

두 방법 모두 **새 딕셔너리**를 만들고, 겹치는 키는 **오른쪽 것이** 이긴다. 원래의 `defaults`는 바뀌지 않았다. 키의 순서는 처음 나온 순서를 따른다. `temperature`는 `defaults`에서 처음 나왔으므로 두 번째 자리에 있고, 값만 바뀌었다.

`|`는 파이썬 3.9에 추가된 **딕셔너리 병합 연산자**다. 집합의 합집합(기초 과정 3.5.4)과 같은 기호다. `|=`는 왼쪽 딕셔너리를 **그 자리에서** 바꾼다. 기초 과정의 `update()`와 같다.

```python
>>> settings = dict(defaults)       # 복사본을 만든다
>>> settings |= {"stream": True}
>>> settings
{'model': 'small-model', 'temperature': 0.7, 'max_tokens': 512, 'stream': True}
```

`|`와 `{**a, **b}` 중 무엇을 쓸까? 딕셔너리 두세 개를 합칠 때는 `|`가 읽기 쉽다. 병합하면서 키를 더하거나(`{**defaults, "stream": True}`), `|`를 쓸 수 없는 것이 섞여 있을 때는 `{**a, **b}`를 쓴다. `|`는 양쪽이 모두 딕셔너리여야 한다.

```python
>>> {"a": 1} | [("b", 2)]
Traceback (most recent call last):
  ...
TypeError: unsupported operand type(s) for |: 'dict' and 'list'
```

**얕은 병합의 함정**

병합은 **맨 바깥 키만** 합친다. 값이 딕셔너리여도 안쪽까지 합치지 않고, 오른쪽 값으로 **통째로 바꾼다.**

```python
>>> base = {"model": "small", "extra": {"top_p": 0.9, "seed": 1}}
>>> override = {"extra": {"seed": 42}}
>>> base | override
{'model': 'small', 'extra': {'seed': 42}}
```

`seed`만 바꾸려 했는데 `top_p`가 사라졌다. 안쪽까지 합치려면 안쪽도 병합한다.

```python
>>> base | {"extra": base["extra"] | override["extra"]}
{'model': 'small', 'extra': {'top_p': 0.9, 'seed': 42}}
```

또 하나, 병합으로 만든 새 딕셔너리는 얕은 복사(기초 과정 3.2.5)라서 **안쪽 딕셔너리는 원래 것과 같은 객체**다.

```python
>>> merged = base | {"temperature": 0.2}
>>> merged["extra"]["seed"] = 7
>>> base
{'model': 'small', 'extra': {'top_p': 0.9, 'seed': 7}}
```

`merged`를 고쳤는데 `base`가 바뀌었다. 1장 1.3.1의 "이름표" 그림을 떠올리면, `merged["extra"]`와 `base["extra"]`는 같은 딕셔너리에 붙은 두 이름표다. 설정을 겹겹이 병합해서 쓰는 코드에서 이런 일이 생기면 원인을 찾기 아주 어렵다. 중첩된 설정을 병합한 뒤 고쳐야 한다면 `copy.deepcopy()`로 깊은 복사를 먼저 한다.

### 2.4.4 `any()`와 `all()`

기초 과정 실습 4-5에서 한 번씩 호출만 해 본 함수다. `any()`는 **하나라도** 참이면 `True`, `all()`은 **모두** 참이면 `True`를 돌려준다. 컴프리헨션과 함께 쓸 때 진가가 드러난다.

```python
>>> scores = [85, 42, 97]
>>> any(s < 50 for s in scores)
True
>>> all(s >= 50 for s in scores)
False
```

괄호 안이 대괄호 없는 컴프리헨션 모양이다. 2.2.5의 표에서 본 **제너레이터 표현식**이다. 함수의 인자가 이것 하나뿐일 때는 소괄호를 겹쳐 쓰지 않고 이렇게 쓸 수 있다. `sum(t.amount for t in ...)`(1.1.2)도 같은 모양이다. 지금은 "대괄호를 뺀 리스트 컴프리헨션"으로 읽으면 된다.

이 두 함수는 기초 과정에서 썼던 "깃발 변수" 반복을 한 줄로 바꾼다.

```python
# 반복문
has_system = False
for m in messages:
    if m["role"] == "system":
        has_system = True
        break

# any()
has_system = any(m["role"] == "system" for m in messages)
```

**단락 평가 — 답이 정해지면 멈춘다**

`any()`는 참인 것을 하나 찾으면, `all()`은 거짓인 것을 하나 찾으면 **나머지를 보지 않고** 멈춘다. `and`/`or`의 단락 평가(기초 과정 2.2.5)와 같다. 확인해 본다.

```python
>>> def check(n):
...     print("검사:", n)
...     return n > 50
...
>>> any(check(n) for n in [10, 60, 70])
검사: 10
검사: 60
True
>>> any([check(n) for n in [10, 60, 70]])
검사: 10
검사: 60
검사: 70
True
```

대괄호 없이 쓰면 60에서 멈췄다. 대괄호를 쓰면 리스트를 **먼저 다 만든 뒤에** `any()`가 받으므로 70까지 모두 검사했다. 검사가 비싼 일(파일 열기, API 호출)이라면 차이가 크다. `any()`와 `all()`에는 **대괄호 없이** 넘기자.

**빈 묶음의 함정**

```python
>>> any([])
False
>>> all([])
True
```

`all([])`가 `True`다. "모든 요소가 조건을 만족한다"에 반대되는 요소가 하나도 없기 때문이다. 수학에서 공허하게 참(vacuous truth)이라고 부르는 성질이다. 문제는 이것이 실제 코드에서 거짓말을 할 수 있다는 것이다.

```python
results = []  # 요청을 하나도 보내지 못했다
if all(r["ok"] for r in results):
    print("모든 요청 성공")   # 출력된다!
```

요청이 0개일 때도 "모두 성공"이 된다. 비어 있을 수 있는 묶음에 `all()`을 쓸 때는 비어 있는 경우를 먼저 따로 확인한다(`if results and all(...)`).

### 2.4.5 할당 표현식 `:=`

기초 과정 2.2.3에서 `if x = 5:`라고 잘못 쓰면 파이썬이 "`==`나 `:=`를 쓰려던 것 아니냐"고 물었다. 그때 "다루지 않는다"고 미뤄 둔 `:=`가 **할당 표현식**이다. 생김새 때문에 **바다코끼리 연산자**(walrus operator)라고도 부른다.

`=`는 **문장**이라서 값이 되지 않는다. `:=`는 이름에 값을 붙이고, **그 값이 되는 식**이다. 그래서 식이 들어가는 자리(조건, 컴프리헨션 안)에서 할당할 수 있다.

**쓸 만한 곳 1 — 같은 계산의 중복 없애기**

2.1.2에서 `n.strip()`을 두 번 계산했다.

```python
>>> names = ["  철수 ", "", "영희", "   ", " 민수"]
>>> [n.strip() for n in names if n.strip()]
['철수', '영희', '민수']
>>> [s for n in names if (s := n.strip())]
['철수', '영희', '민수']
```

`if (s := n.strip())`는 "`n.strip()`의 결과를 `s`라고 부르고, 그 값이 참이면"이다. 2.1.2에서 본 읽는 순서대로 `if` 절이 식보다 **먼저** 실행되므로, 맨 앞의 `s`는 이미 값이 붙어 있다. `strip()` 정도라면 두 번 계산해도 괜찮지만, 계산이 비싸거나(정규화, 파싱, 함수 호출) 식이 길다면 이 방법이 중복을 없앤다.

**쓸 만한 곳 2 — 값을 얻고 바로 검사하기**

```python
user = by_id.get(user_id)
if user is not None:
    print(user["name"])

# :=로
if (user := by_id.get(user_id)) is not None:
    print(user["name"])
```

```python
items = list(range(15))
if (n := len(items)) > 10:
    print(f"너무 많다: {n}개 (최대 10개)")
```

**쓸 만한 곳 3 — "읽고, 검사하고, 처리하는" `while` 반복**

```python
# 반복문 앞과 끝에서 같은 줄을 두 번 쓴다
line = input("> ")
while line != "quit":
    print("입력:", line)
    line = input("> ")

# :=로 한 번만
while (line := input("> ")) != "quit":
    print("입력:", line)
```

`input()`을 부르는 곳이 한 곳으로 줄었다. 3장에서 파일을 일정한 크기씩 읽을 때도 이 모양(`while chunk := f.read(1024):`)을 만난다.

**괄호를 빼먹으면**

`:=`는 연산자 중 우선순위가 가장 낮다. 괄호 없이 쓰면 생각과 다르게 묶인다.

```python
>>> items = list(range(15))
>>> if n := len(items) > 10:
...     print(n)
...
True
```

`n`에 개수 15가 아니라 `len(items) > 10`의 결과인 `True`가 붙었다. 오류 없이 잘못된 값이 들어가므로 찾기 어렵다. **`:=`는 언제나 괄호로 감싸서** 쓰는 습관을 들이자. 한편 문장 맨 앞에 혼자 쓰는 것은 문법이 막는다.

```python
>>> n := 5
  File "<python-input-9>", line 1
    n := 5
      ^^
SyntaxError: invalid syntax
```

보통의 할당은 `=`로 하라는 뜻이다.

**남용을 피하는 기준**

`:=`는 쓸 수 있는 곳이 많지만 써서 좋은 곳은 적다. 다음은 동작은 하지만 쓰지 말아야 할 코드다.

```python
>>> total = 0
>>> [total := total + x for x in [1, 2, 3]]
[1, 3, 6]
>>> total
6
```

2.3.4의 누적 합계를 컴프리헨션으로 쓴 것이다. 그런데 컴프리헨션 **바깥의** `total`이 바뀌었다. 2.1.6에서 컴프리헨션의 반복 변수는 밖으로 새지 않는다고 했지만, `:=`로 붙인 이름은 **바깥에 만들어진다.** 2.1.2의 `s`도 컴프리헨션이 끝난 뒤 바깥에 마지막 값(`'민수'`)으로 남아 있다. 컴프리헨션 안에서 바깥 상태를 바꾸는 것은 2.3.1의 부수 효과와 같은 문제다.

| 쓴다 | 쓰지 않는다 |
|---|---|
| 같은 계산을 두 번 하는 것을 없앨 때 | 보통의 할당(`=`로 충분한 곳) |
| "얻고 → 검사하고 → 쓰는" 세 단계가 한 줄에 자연스럽게 읽힐 때 | 한 줄에 `:=`가 두 개 이상 |
| `while`에서 읽기 → 검사를 한 곳으로 모을 때 | 컴프리헨션 안에서 바깥 상태를 바꿀 때 |
| | 읽는 사람이 "어느 것이 먼저 실행되지?" 하고 멈춰야 할 때 |

마지막 줄이 가장 중요하다. 두 줄로 나누어 쓴 코드를 읽기 어려워하는 사람은 없다.

2. `merge()`가 `retry`를 안쪽까지 병합하지 않으면 출력이 어떻게 달라지는가? 일부러 바꿔서 확인한다.
3. `merge()`가 돌려준 결과의 `["retry"]["times"]`를 `99`로 바꾼 뒤 `DEFAULTS["retry"]`를 출력한다. 바뀌었다면 왜 바뀌었는가? 안쪽까지 병합하는 코드를 이미 썼다면 바뀌지 않았을 것이다. 왜 그런지 설명한다.
4. `REQUIRED`가 빈 리스트라면 `all(k in settings for k in REQUIRED)`는 무엇을 돌려주는가? 이것이 문제가 될 상황을 하나 적는다.
5. `temperature`가 문자열 `'0.2'`로 남았다. 실제 API에 넘기기 전에 숫자로 바꾸어야 한다. 이 "모양과 타입의 검사"는 5장의 Pydantic이 대신해 준다. 지금은 문제를 알아차린 것으로 충분하다.

## 2.5 `match` 문

`match` 문은 파이썬 3.10에 추가된 **구조적 패턴 매칭**(structural pattern matching)이다. 값이 **어떤 모양인지**에 따라 분기하고, 맞는 모양이면 그 안의 값을 이름에 바로 붙여 준다. 이름만 보면 다른 언어의 `switch` 문과 비슷해 보이지만 할 수 있는 일이 훨씬 많다.

```python
match 대상:
    case 패턴1:
        ...
    case 패턴2:
        ...
    case _:
        ...
```

위에서부터 차례로 패턴과 맞춰 보고, **처음 맞는 `case` 하나만** 실행한 뒤 `match` 문을 빠져나간다. 다른 언어의 `switch`처럼 아래 `case`로 넘어가는(fall-through) 일은 없고, `break`도 쓰지 않는다.

`match`와 `case`는 이 자리에서만 특별한 뜻을 가지는 **소프트 키워드**다. 그래서 `match = re.match(...)`처럼 변수 이름으로 써도 된다. 오래된 코드를 깨뜨리지 않으려고 이렇게 정했다.

### 2.5.1 값 패턴과 `case _`

가장 단순한 패턴은 **값**이다. HTTP 상태 코드를 설명으로 바꾸는 함수를 `ch02/status.py`에 만든다.

```python
def status_text(status: int) -> str:
    match status:
        case 200:
            return "성공"
        case 400 | 422:
            return "요청 형식 오류"
        case 401 | 403:
            return "권한 없음"
        case 429:
            return "요청 한도 초과"
        case 500 | 502 | 503:
            return "서버 오류"
        case _:
            return f"알 수 없는 상태: {status}"


for code in [200, 422, 429, 503, 418]:
    print(code, status_text(code))
```

```
200 성공
422 요청 형식 오류
429 요청 한도 초과
503 서버 오류
418 알 수 없는 상태: 418
```

- `case 200:` — 값이 `200`과 같으면(`==`) 맞는다.
- `case 400 | 422:` — `|`로 여러 패턴 중 **하나라도** 맞으면 맞는다(OR 패턴). 2.4.3의 딕셔너리 병합 `|`와는 다른 뜻이다. `case` 뒤의 `|`는 언제나 "또는"이다.
- `case _:` — **무엇이든** 맞는다(와일드카드). 앞의 어떤 `case`에도 맞지 않은 값이 여기로 온다. `if`/`elif` 사슬의 마지막 `else`에 해당한다.

429(요청 한도 초과)와 5xx(서버 오류)는 4장의 재시도 데코레이터에서 "다시 시도할 오류"로 다시 만난다.

**함정: 이름은 값이 아니라 "붙잡기"다**

상태 코드를 상수로 두고 `case`에 쓰고 싶어질 수 있다.

```python
OK = 200
TOO_MANY = 429

match status:
    case OK:
        print("성공")
    case TOO_MANY:
        print("한도 초과")
```

```
SyntaxError: name capture 'OK' makes remaining patterns unreachable
```

`case` 뒤에 **점이 없는 이름**을 쓰면 "이 값과 같은가"가 아니라 "**무엇이든** 맞고, 그 값을 이 이름에 붙인다"는 뜻이다(**캡처 패턴**). `case OK:`는 `status`가 무엇이든 맞아서 `OK = status`를 하므로, 그 아래 `case`는 영영 실행될 수 없다. 파이썬이 이것을 알아차리고 문법 오류를 냈다. `case`가 하나뿐이었다면 오류도 없이 모든 값이 첫 `case`로 가고, 상수 `OK`의 값까지 바뀌었을 것이다.

상수와 비교하려면 **점이 들어간 이름**을 쓴다. 점이 있으면 값 패턴으로 본다.

```python
from http import HTTPStatus

match status:
    case HTTPStatus.OK:
        print("성공")
    case HTTPStatus.TOO_MANY_REQUESTS:
        print("한도 초과")
```

`http.HTTPStatus`는 상태 코드에 이름을 붙여 둔 표준 라이브러리의 열거형(Enum, 5장)이다. `HTTPStatus.TOO_MANY_REQUESTS == 429`가 참이므로 정수 상태 코드와 비교할 수 있다. 내가 만든 상수라면 모듈이나 클래스 안에 두고 `config.OK`, `Status.OK`처럼 점을 붙여 쓴다.

### 2.5.2 시퀀스 패턴

대괄호(또는 소괄호) 안에 패턴을 나열하면 **시퀀스 패턴**이다. 리스트나 튜플의 **길이와 각 자리의 값**을 함께 맞춰 본다. 기초 과정 4장 실습 4-7에서 `command, *args = words`로 명령을 나누고 `if`/`elif`로 인자 개수를 확인한 일이 이것 하나로 된다.

`ch02/command.py`

```python
def run(command: str) -> str:
    match command.split():
        case []:
            return "명령을 입력하세요"
        case ["help"]:
            return "명령: add 분류 금액, del 번호..., list"
        case ["add", category, amount]:
            return f"추가: {category} {int(amount):,}원"
        case ["del", first, *others]:
            return f"삭제: {[first, *others]}"
        case ["list" | "ls"]:
            return "목록 출력"
        case _:
            return f"알 수 없는 명령: {command!r}"


for cmd in ["", "help", "add 커피 4500", "add 커피", "del 3", "del 1 4 7", "del", "ls", "list all"]:
    print(f"{cmd!r} -> {run(cmd)}")
```

```
'' -> 명령을 입력하세요
'help' -> 명령: add 분류 금액, del 번호..., list
'add 커피 4500' -> 추가: 커피 4,500원
'add 커피' -> 알 수 없는 명령: 'add 커피'
'del 3' -> 삭제: ['3']
'del 1 4 7' -> 삭제: ['1', '4', '7']
'del' -> 알 수 없는 명령: 'del'
'ls' -> 목록 출력
'list all' -> 알 수 없는 명령: 'list all'
```

패턴을 하나씩 읽는다.

- `case []:` — 길이가 0인 시퀀스. 빈 줄을 입력하면 `split()`의 결과가 `[]`다.
- `case ["add", category, amount]:` — 길이가 **정확히 3**이고, 첫 자리가 `"add"`이면 맞는다. 둘째·셋째 자리는 캡처 패턴이므로 무엇이든 맞고, 그 값이 `category`와 `amount`에 붙는다. `"add 커피"`는 길이가 2라서 맞지 않았다.
- `case ["del", first, *others]:` — 2.4.1의 확장 언패킹과 같은 규칙이다. `first` 자리 때문에 번호가 **하나 이상** 있어야 맞는다. `"del"`만 입력하면 맞지 않는다.
- `case ["list" | "ls"]:` — 자리 하나 안에 OR 패턴을 썼다. 길이 1이고 그 값이 `"list"`나 `"ls"`이면 맞는다.

시퀀스 패턴은 언패킹과 닮았지만 결정적인 차이가 있다. 언패킹은 길이가 맞지 않으면 `ValueError`가 나지만, 패턴은 길이가 맞지 않으면 **다음 `case`로 넘어갈 뿐**이다. 그래서 "인자 개수가 맞는가"를 따로 검사할 필요가 없다.

> **문자열은 시퀀스 패턴에 맞지 않는다**
> 문자열도 시퀀스지만, `case [a, b]:`는 `"ab"`에 맞지 않는다. 문자열을 글자 단위로 쪼개 맞추는 일은 거의 언제나 실수이기 때문에 일부러 막아 두었다. 리스트와 튜플은 모두 맞는다. `case [a, b]:`와 `case (a, b):`는 같은 패턴이다.

### 2.5.3 매핑 패턴

중괄호 안에 `키: 패턴`을 쓰면 **매핑 패턴**이다. 딕셔너리에 그 키가 **있고**, 그 값이 패턴에 맞으면 맞는다. JSON에서 온 데이터를 다룰 때 가장 많이 쓰는 패턴이다.

```python
def describe(event: dict) -> str:
    match event:
        case {"type": "click", "x": x, "y": y}:
            return f"클릭 ({x}, {y})"
        case {"type": "key", "key": "Enter"}:
            return "엔터"
        case {"type": "key", "key": key}:
            return f"키 {key}"
        case {"type": kind}:
            return f"처리하지 않는 이벤트: {kind}"
        case _:
            return "이벤트가 아니다"
```

```python
>>> describe({"type": "click", "x": 10, "y": 20, "button": "left"})
'클릭 (10, 20)'
>>> describe({"type": "key", "key": "Enter"})
'엔터'
>>> describe({"type": "key", "key": "a"})
'키 a'
>>> describe({"type": "scroll", "dy": -3})
'처리하지 않는 이벤트: scroll'
>>> describe({"x": 1})
'이벤트가 아니다'
```

- **패턴에 없는 키는 무시한다.** 첫 번째 예의 `"button"` 키는 패턴에 없지만 맞았다. 시퀀스 패턴이 길이까지 정확히 맞춰 보는 것과 다르다. API 응답에 필드가 나중에 추가되어도 코드가 깨지지 않는다.
- **패턴에 있는 키가 없으면 맞지 않는다.** `{"x": 1}`에는 `"type"` 키가 없어서 마지막 `case _`까지 내려왔다. `KeyError`가 나지 않는다.
- 값 자리에는 다시 **어떤 패턴이든** 쓸 수 있다. `"Enter"` 같은 값 패턴, `key` 같은 캡처 패턴, 그리고 다음 절의 패턴들을 겹쳐 쓸 수 있다.
- 순서가 중요하다. `{"type": "key", "key": "Enter"}`가 `{"type": "key", "key": key}`보다 **위에** 있어야 한다. 반대로 두면 엔터도 `"키 Enter"`가 된다. **구체적인 패턴을 위에, 일반적인 패턴을 아래에** 둔다.

중첩된 딕셔너리도 그대로 맞춰 본다.

```python
match response:
    case {"error": {"type": "rate_limit_error", "message": msg}}:
        print("한도 초과:", msg)
    case {"data": {"items": [first, *_]}}:
        print("첫 항목:", first)
    case {"data": {"items": []}}:
        print("결과 없음")
```

두 번째 `case`는 "`data` 안의 `items`가 항목이 **하나 이상인** 리스트이면, 첫 항목을 `first`에 붙인다"다. `if`/`elif`로 쓰면 `"data" in response and "items" in response["data"] and len(...) > 0` 같은 검사를 줄줄이 써야 한다.

나머지 키를 모두 받고 싶으면 `**rest`를 쓴다. `case {"type": "click", **rest}:`는 `type`을 뺀 나머지 키를 딕셔너리 `rest`로 받는다.

### 2.5.4 클래스 패턴

`클래스이름(...)` 모양은 **클래스 패턴**이다. `isinstance()`(기초 과정 4.5.3)로 타입을 확인하고, 맞으면 속성을 꺼낸다.

**내장 타입 확인하기**

```python
def kind_of(value) -> str:
    match value:
        case bool():
            return "불리언"
        case int() | float():
            return "숫자"
        case str(text) if text.strip():
            return f"문자열 {text!r}"
        case str():
            return "빈 문자열"
        case list() | tuple():
            return "시퀀스"
        case None:
            return "없음"
        case _:
            return type(value).__name__
```

- `case int():` — `isinstance(value, int)`가 참이면 맞는다. **괄호를 꼭 쓴다.** `case int:`라고 쓰면 2.5.1의 캡처 패턴이 되어 무엇이든 맞고, `int`라는 이름에 그 값이 붙어 버린다.
- `case str(text):` — `str`, `int`, `float`, `list`, `dict` 같은 내장 타입은 괄호 안에 이름을 하나 쓰면 **값 전체**가 그 이름에 붙는다. "문자열이면 `text`라고 부른다."
- `bool()`이 `int()`보다 **위에** 있다. 기초 과정 10장의 `Transaction.__post_init__`에서 본 대로 불리언은 정수의 자식 클래스라서 `isinstance(True, int)`가 참이다. 순서를 바꾸면 `True`가 `"숫자"`가 된다.
- `case None:` — `None`, `True`, `False`는 이름이지만 값 패턴으로 다룬다. `is`로 비교한다.

**데이터 클래스**

기초 과정 5.4.3의 데이터 클래스는 클래스 패턴과 잘 어울린다.

```python
from dataclasses import dataclass


@dataclass
class Point:
    x: int
    y: int


def where(p: Point) -> str:
    match p:
        case Point(x=0, y=0):
            return "원점"
        case Point(x=0, y=y):
            return f"y축 위, y={y}"
        case Point(x, 0):
            return f"x축 위, x={x}"
        case Point():
            return "그 밖의 점"
        case _:
            return "점이 아니다"
```

```python
>>> [where(p) for p in [Point(0, 0), Point(0, 5), Point(3, 0), Point(2, 2)]]
['원점', 'y축 위, y=5', 'x축 위, x=3', '그 밖의 점']
```

- `Point(x=0, y=0)` — `Point`의 인스턴스이고, `p.x == 0`이고 `p.y == 0`이면 맞는다. 객체를 **만드는** 코드처럼 생겼지만 객체를 만들지 않는다. "이런 모양의 `Point`인가"를 묻는다.
- `Point(x=0, y=y)` — `x`는 0이어야 하고, `y`는 무엇이든 받아서 이름 `y`에 붙인다.
- `Point(x, 0)` — 키워드 없이 자리로 쓸 수도 있다. 데이터 클래스는 필드 순서(`x`, `y`)를 `__match_args__`라는 특별한 속성에 자동으로 적어 두고, 파이썬은 이것을 보고 첫 자리가 `x`, 둘째 자리가 `y`라고 안다. 직접 만든 일반 클래스에서 자리로 쓰려면 `__match_args__ = ("x", "y")`를 직접 적어야 한다. 헷갈리면 키워드로 쓰는 것이 안전하다.

### 2.5.5 가드 — `case 패턴 if 조건`

패턴만으로 표현할 수 없는 조건은 `case` 뒤에 `if`를 붙인다. 이것을 **가드**(guard)라고 한다.

```python
match command.split():
    case ["add", category, amount] if amount.isdecimal() and int(amount) > 0:
        return f"추가: {category} {int(amount):,}원"
    case ["add", _, amount]:
        return f"금액은 1 이상의 정수로: {amount!r}"
    case ["add", *_]:
        return "형식: add 분류 금액"
```

1. 먼저 패턴을 맞춰 본다. 맞으면 이름(`category`, `amount`)이 붙는다.
2. 그다음 가드를 계산한다. 가드에서는 방금 붙은 이름을 쓸 수 있다.
3. 가드가 거짓이면 이 `case`는 맞지 않은 것으로 보고 **다음 `case`로 넘어간다.**

위 코드는 2.5.2의 `run()`에서 `add` 명령을 세 경우로 나눈 것이다. 금액이 올바르면 첫째 `case`, 형식은 맞는데 금액이 이상하면 둘째 `case`, 인자 개수가 틀리면 셋째 `case`로 간다. `case ["add", _, amount]`의 `_`는 "무엇이든 맞지만 이름은 붙이지 않는다"이다.

가드는 범위 비교처럼 **값의 크기**를 따질 때 특히 필요하다. 패턴에는 "50보다 크다"를 쓸 방법이 없다.

### 2.5.6 아무 `case`에도 맞지 않으면

`match` 문의 어떤 `case`에도 맞지 않으면 **아무 일도 일어나지 않는다.** 오류도 나지 않는다. 함수가 `match` 문으로 끝난다면 `None`을 돌려주게 된다(기초 과정 4.1.6). 예상하지 못한 값이 조용히 지나가는 것이다.

처리할 수 없는 값이라면 `case _:`에서 **예외를 일으키는** 것이 좋다. 기초 과정 6.2.6 "예외를 잡을 때와 그대로 둘 때"에서 본 대로, 문제가 생긴 곳에서 바로 알리는 편이 나중에 엉뚱한 곳에서 터지는 것보다 낫다.

```python
match message:
    case {"type": "text", "text": text}:
        ...
    case {"type": "tool_use"}:
        ...
    case _:
        raise ValueError(f"처리할 수 없는 메시지: {message!r}")
```

(`case {"type": "tool_use"}:`는 `id`, `name` 같은 다른 키가 있어도 맞는다. 매핑 패턴은 패턴에 없는 키를 무시한다(2.5.3). 다른 키가 있다는 뜻으로 패턴 안에 `...`을 쓰면 `SyntaxError`가 난다.)

"모르는 종류는 건너뛴다"가 맞는 상황도 있다. 그럴 때도 `case _: pass`처럼 **건너뛴다는 결정을 코드에 적어 두면** 읽는 사람이 "빠뜨린 것"과 "일부러 뺀 것"을 구별할 수 있다.

### 2.5.7 `if`/`elif` 사슬과의 선택 기준

`match` 문으로 할 수 있는 일은 모두 `if`/`elif`로도 할 수 있다. 2.5.3의 매핑 패턴 하나를 `if`로 쓰면 다음과 같다.

```python
# match
match block:
    case {"type": "tool_use", "name": str(name), "input": dict(args)}:
        call_tool(name, args)

# if
if (
    isinstance(block, dict)
    and block.get("type") == "tool_use"
    and isinstance(block.get("name"), str)
    and isinstance(block.get("input"), dict)
):
    name = block["name"]
    args = block["input"]
    call_tool(name, args)
```

`if` 쪽은 "모양 검사"와 "값 꺼내기"를 따로 써야 하고, 키 이름이 두 번씩 나온다. 반대로 `match`가 어울리지 않는 경우도 있다.

| 상황 | 고를 것 | 이유 |
|---|---|---|
| 데이터의 **모양**(키가 있는가, 길이가 얼마인가, 어떤 타입인가)에 따라 나누고, 그 안의 값을 꺼내야 한다 | `match` | 검사와 꺼내기를 한 번에 한다 |
| 명령어, 메시지 종류처럼 **경우가 여럿**이고 각각 모양이 다르다 | `match` | 경우마다 `case` 하나로 나란히 읽힌다 |
| `score >= 90`처럼 **범위나 크기**로 나눈다 | `if`/`elif` | `match`로 하면 `case`마다 가드를 붙여야 한다 |
| 조건이 하나나 둘뿐이다 | `if` | `match`는 들여쓰기가 한 단계 더 깊다 |
| 값 하나를 상수 몇 개와 비교해 **값 하나를 고른다** | 딕셔너리 | `STATUS_TEXT.get(code, "알 수 없음")` 한 줄이면 된다(기초 과정 4.4.2) |

마지막 줄에 주의한다. 2.5.1의 `status_text()`는 사실 딕셔너리 하나로 충분하다. `400 | 422`처럼 여러 값을 묶는 것도 딕셔너리에 키를 두 번 넣으면 된다. 2.5.1은 값 패턴을 보여 주려고 고른 예다. `match`가 정말 빛나는 곳은 다음 절처럼 **모양이 다른 데이터가 섞여 들어올 때**다.

### 2.5.8 LLM 응답 메시지를 종류에 따라 처리하기

LLM API의 응답에는 여러 종류의 조각이 섞여 들어온다. 모델이 글로 답하기도 하고, 도구(함수)를 불러 달라고 요청하기도 하고, 요청 한도 초과 같은 오류가 오기도 한다. 종류마다 딕셔너리의 모양이 다르다. 이 절에서는 실제 SDK의 응답을 단순하게 줄인 다음 세 모양을 다룬다.

```python
# 텍스트 — 모델이 쓴 답
{"type": "text", "text": "서울의 날씨를 확인해 볼게요."}

# 도구 호출 — 모델이 "이 도구를 이 인자로 불러 달라"고 요청한다
{"type": "tool_use", "id": "call_1", "name": "get_weather", "input": {"city": "서울"}}

# 오류
{"type": "error", "error": {"type": "rate_limit_error", "message": "Too many requests"}}
```

Anthropic API의 응답 내용(content) 블록이 이와 비슷한 모양이고, OpenAI API는 도구 호출을 `tool_calls`라는 다른 필드에 담는다. SDK와 버전마다 필드 이름이 조금씩 다르지만, **"`type` 필드로 종류를 나누고 종류마다 다른 필드를 꺼낸다"**는 구조는 같다. "LLM API 활용"에서 실제 응답을 받을 때 이 함수의 `case`만 실제 모양에 맞게 고치면 된다.

`ch02/llm_messages.py`

```python
"""LLM 응답 메시지를 종류에 따라 처리한다."""


def get_weather(city: str) -> str:
    return f"{city}: 맑음, 18도"


TOOLS = {"get_weather": get_weather}


def handle(message: dict) -> str:
    match message:
        case {"type": "text", "text": str(text)} if text.strip():
            return f"[답변] {text}"
        case {"type": "text"}:
            return "[답변] (빈 텍스트)"
        case {"type": "tool_use", "name": str(name), "input": dict(args)}:
            if name not in TOOLS:
                return f"[도구 호출] 등록되지 않은 도구: {name}"
            result = TOOLS[name](**args)
            return f"[도구 호출] {name}({args}) -> {result}"
        case {"type": "error", "error": {"type": "rate_limit_error"}}:
            return "[오류] 요청 한도 초과 — 잠시 뒤 다시 시도한다"
        case {"type": "error", "error": {"message": str(msg)}}:
            return f"[오류] {msg}"
        case {"type": str(kind)}:
            return f"[건너뜀] 처리하지 않는 종류: {kind}"
        case _:
            raise ValueError(f"메시지 형식이 아니다: {message!r}")


if __name__ == "__main__":
    messages = [
        {"type": "text", "text": "서울의 날씨를 확인해 볼게요."},
        {"type": "tool_use", "id": "call_1", "name": "get_weather", "input": {"city": "서울"}},
        {"type": "text", "text": "   "},
        {"type": "error", "error": {"type": "rate_limit_error", "message": "Too many requests"}},
        {"type": "error", "error": {"type": "overloaded_error", "message": "서버가 바쁩니다"}},
        {"type": "thinking", "thinking": "..."},
    ]
    for message in messages:
        print(handle(message))
    try:
        handle({"text": "type 키가 없다"})
    except ValueError as e:
        print("ValueError:", e)
```

```
[도구 호출] get_weather({'city': '서울'}) -> 서울: 맑음, 18도
[답변] (빈 텍스트)
[오류] 요청 한도 초과 — 잠시 뒤 다시 시도한다
[오류] 서버가 바쁩니다
[건너뜀] 처리하지 않는 종류: thinking

```

이 장에서 배운 패턴이 모두 들어 있다. 위에서부터 읽는다.

1. **매핑 + 클래스 패턴 + 가드** — `type`이 `"text"`이고, `text`가 문자열이고, 공백만 있는 것이 아니면 답변이다. `str(text)`는 "문자열이면 `text`라고 부른다"(2.5.4)이다.
2. 1에 맞지 않은 텍스트(빈 텍스트, 또는 `text`가 문자열이 아닌 것)는 여기로 온다. 가드가 거짓이면 다음 `case`로 넘어간다는 성질(2.5.5)을 썼다.
3. **도구 호출** — `name`은 문자열, `input`은 딕셔너리여야 한다. `dict(args)`는 "딕셔너리이면 `args`라고 부른다"이다. `id` 키는 패턴에 없지만 매핑 패턴은 없는 키를 무시하므로 상관없다. 도구는 `TOOLS` 딕셔너리에서 이름으로 찾아(1장 1.3.2 "함수도 값이다") `**args`로 풀어서 호출한다(1.3.3). 4장에서는 이 `TOOLS`에 함수를 손으로 넣는 대신, 함수 위에 데코레이터를 붙이면 자동으로 등록되게 만든다. MCP 서버의 `@mcp.tool()`이 하는 일이다.
4. **중첩 매핑** — 오류 중에서도 요청 한도 초과는 따로 처리한다. 4장의 재시도, 7장의 동시 실행 수 제한으로 이어지는 오류다. 일반 오류(5)보다 **위에** 있어야 한다.
5. 그 밖의 오류는 메시지를 꺼내 보여 준다.
6. `type`은 있지만 처리하지 않는 종류(새로 추가된 종류 등)는 **일부러 건너뛴다**고 적어 두었다(2.5.6).
7. `type`조차 없으면 형식이 잘못된 것이므로 예외를 일으킨다.

`case`의 순서를 바꿔 가며 실행해 보면 "구체적인 것을 위에"라는 규칙이 왜 필요한지 바로 보인다.

### 실습 2-5. `match` 문

1. **명령 처리기 고치기** — `ch02/command.py`의 `run()`에 2.5.5의 가드를 넣어 `add` 명령을 세 경우로 나눈다. `del` 명령도 번호가 모두 숫자인지 가드로 확인해서(`all(n.isdecimal() for n in [first, *others])`), 숫자가 아닌 번호가 있으면 `"번호는 숫자로: ..."`를 돌려준다. 아래 입력으로 확인한다.
   ```python
   ["add 커피 4500", "add 커피 0", "add 커피 사천", "add", "del 1 2", "del 1 둘"]
   ```
2. **순서 실험** — `ch02/llm_messages.py`에서 4번 `case`(요청 한도 초과)와 5번 `case`(일반 오류)의 순서를 바꿔 실행한다. 출력이 어떻게 달라지는가? 1번과 2번 `case`의 순서를 바꾸면 어떻게 되는가? 결과를 `notes.md`에 적고 원래대로 되돌린다.
3. **새 종류 더하기** — 도구 실행 결과를 담는 `{"type": "tool_result", "tool_use_id": "call_1", "content": "서울: 맑음, 18도"}`를 처리하는 `case`를 더한다. 출력은 `[도구 결과] call_1: 서울: 맑음, 18도`처럼 만든다. 어느 자리에 넣어야 하는가? 6번 `case`보다 아래에 넣으면 어떻게 되는가?
4. **`if`/`elif`로 다시 쓰기** — `handle()`과 똑같이 동작하는 `handle_if()`를 `if`/`elif`로 써 본다. `isinstance()`와 `get()`을 써야 한다. 다 쓴 뒤 두 함수에 2.5.8의 메시지와 아래의 이상한 메시지들을 넣어 결과가 모두 같은지 확인한다.
   ```python
   [{"type": "text", "text": 123}, {"type": "tool_use", "name": "get_weather"}, {"type": "error", "error": "문자열"}, {}]
   ```
   두 함수의 줄 수를 비교하고, 어느 쪽이 "어떤 모양의 메시지를 처리하는가"를 더 잘 보여 주는지 `notes.md`에 적는다.

## 실습 2-6. 종합 — 대화 기록 보고서

이 장의 문법을 모두 써서, LLM 서비스의 대화 기록을 읽고 보고서를 출력하는 프로그램을 만든다. 기초 과정 4장 실습 4-7처럼 **함수의 이름과 독스트링이 먼저 주어지고, 본문을 채운다.** 각 함수의 본문은 짧다. 대부분 한두 줄이면 된다. 짧게 쓰는 것이 목표가 아니라, 2.3.5의 기준에 맞는 문법을 고르는 것이 목표다.

## 정리

| 항목 | 핵심 |
|---|---|
| 리스트 컴프리헨션 | `[식 for 변수 in 묶음 if 조건]`. `for` → `if` → 식 순서로 읽는다. 언제나 새 리스트를 만든다 |
| `map`/`filter`와 비교 | 식 자리가 `map`, `if` 절이 `filter`. 람다가 필요하면 컴프리헨션이 읽기 쉽다. 이름 있는 함수면 `map(int, ...)`도 좋다 |
| 두 자리의 `if` | 맨 앞의 `A if 조건 else B`는 값을 고른다(길이 유지). 뒤의 `if` 절은 거른다(길이 줄어듦) |
| `for` 두 개 | 반복문에 쓴 순서 그대로 왼쪽에서 오른쪽으로. 결과는 펼쳐진다 |
| 컴프리헨션 안의 컴프리헨션 | 식 자리에 들어간 컴프리헨션. 결과는 중첩된다. 바깥부터 읽는다 |
| 변수의 범위 | 컴프리헨션의 반복 변수는 밖으로 새지 않는다. `:=`로 붙인 이름은 바깥에 남는다 |
| 딕셔너리·집합 컴프리헨션 | `{k: v for ...}`, `{x for ...}`. 뒤집을 때 값이 겹치면 조용히 사라진다. `{}`는 빈 딕셔너리 |
| JSON 다루기 | 필요한 필드만 뽑기, 없을 수 있는 필드는 `get()`, 자주 찾으면 `{u["id"]: u for u in users}` |
| `( ... for ...)` | 튜플이 아니라 제너레이터 표현식(3장) |
| 쓰지 않을 때 | 부수 효과가 목적, `for` 셋 이상이나 긴 조건, 요소마다 예외 처리, 결과 여러 개를 한 번에, 앞 요소에 기대는 반복. 반복문으로 되돌리거나 함수로 뺀다 |
| 확장 언패킹 | `first, *rest`, `*init, last`, `head, *_, tail`. 별표 이름은 언제나 리스트. 별표는 하나만 |
| 언패킹으로 조립 | `[system, *history, question]`, `{**defaults, "stream": True}` |
| 딕셔너리 병합 | `a \| b`(새 딕셔너리), `a \|= b`(그 자리에서). 오른쪽이 이긴다. 얕은 병합 — 안쪽 딕셔너리는 통째로 바뀌고 객체를 공유한다 |
| `any()`/`all()` | 대괄호 없이 넘겨 단락 평가를 살린다. `all([])`는 `True` |
| `:=` | 식 안에서 할당한다. 언제나 괄호로 감싼다. 중복 계산 제거, "얻고-검사하고-쓰기", `while` 읽기에만 쓴다 |
| `match` 문 | 처음 맞는 `case` 하나만 실행. 맞는 것이 없으면 아무 일도 없다 — `case _`에서 예외를 일으키거나 건너뛰는 결정을 적는다 |
| 패턴 | 값(`200`, `"add"`, `HTTPStatus.OK`), OR(`400 \| 422`), 캡처(`name`), 와일드카드(`_`), 시퀀스(`["add", x, *rest]`), 매핑(`{"type": "text", "text": t}`), 클래스(`str(s)`, `Point(x=0)`) |
| 패턴의 함정 | 점 없는 이름은 캡처(`case OK:`는 무엇이든 맞는다). 클래스 패턴은 괄호 필수. 구체적인 `case`를 위에. `bool()`은 `int()`보다 위에 |
| 가드 | `case 패턴 if 조건:`. 거짓이면 다음 `case`로 |
| `match` vs `if` | 모양에 따라 나누고 값을 꺼낼 때 `match`. 범위 비교, 조건 한두 개는 `if`. 값 하나 고르기는 딕셔너리 |
