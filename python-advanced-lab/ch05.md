# 5장. 타입 힌트

[파이썬 중급](README.md) 과정의 다섯 번째 장이다. 기초 과정에서 타입 힌트를 처음 배울 때(기초 과정 5.4.2) 가장 강조한 것은 "**파이썬은 타입 힌트를 검사하지 않는다**"였다. `total_price("커피", 3)`은 오류 없이 `'커피커피커피'`를 돌려주었다. 8.2.5에서 `Literal`과 `TypedDict`로 메시지의 모양을 적었지만, `{"role": "admin", "content": 1}`도 아무 문제 없이 만들어졌다. 1장에서는 가계부 프로그램의 `Transaction.__post_init__`이 `isinstance()`로 자료형을 하나씩 검사하던 일을 "실행 **전에는** mypy가, 실행 **중에는** Pydantic이 맡는다"고 미리 보았다(1.1.2). 이 장에서 그 두 도구를 쓴다. 타입 힌트는 이제 **읽는 설명**에서 **검사받는 약속**이 된다.

- **정적 타입 검사** — mypy를 설치해 실행하고 검사 오류를 읽는다. `reveal_type()`으로 검사기가 본 타입을 확인하고, VS Code(Pylance)의 타입 검사 모드를 켠다. 타입 힌트가 없는 기존 코드에 검사를 조금씩 도입하는 방법을 익힌다.
- **타입 좁히기** — `int | None`을 받았을 때 `None`을 먼저 처리하는 습관을 들인다. `isinstance()`, `match` 문, `assert`로 타입을 좁히고, `cast()`를 최후의 수단으로 두는 이유를 본다.
- **컬렉션과 함수의 타입** — 매개변수는 넓게(`Iterable`, `Sequence`, `Mapping`), 반환값은 구체적으로 적는다. 함수를 받는 매개변수(`Callable`), 제너레이터의 반환 타입(`Iterator`, `Generator`), 4장에서 만든 데코레이터의 타입(`ParamSpec`)을 읽는다.
- **제네릭** — `def first[T](items: list[T]) -> T`처럼 타입 매개변수로 "받은 것과 같은 타입을 돌려준다"를 적는다. 제네릭 클래스와 `type` 별칭 문을 쓰고, 옛 표기(`TypeVar`, `Generic`)를 읽는다.
- **설계에 쓰는 타입** — `Literal`, `TypedDict`, `Enum`으로 "정해진 값"과 "정해진 모양"을 적는다. `Protocol`로 LLM 클라이언트의 약속을 정의하고, 실제 클라이언트와 가짜 클라이언트를 바꿔 끼운다. 지금까지 만난 특별한 메서드를 "어떤 문법이 어떤 메서드를 부르는가"로 한 표에 모으고, `|`가 부르는 `__or__`로 LangChain의 `prompt | model | parser`를 읽는다.
- **실행 중 검증과 Pydantic** — `BaseModel`과 `Field`로 데이터의 모양과 규칙을 정하고, 딕셔너리와 JSON을 검증해 모델로 만든다. 검증 오류를 읽고, `model_json_schema()`로 JSON 스키마를 만들어 LLM 구조화 출력·도구 정의·FastAPI 요청 본문과 연결한다.

## 학습 목표

이 장을 마치면 다음을 할 수 있다.

- mypy로 파일과 폴더를 검사하고, 검사 오류의 위치·내용·오류 코드를 읽어 고칠 수 있다.
- `reveal_type()`으로 검사기가 추론한 타입을 확인하고, 타입 힌트가 없는 함수는 기본 설정에서 검사되지 않는다는 것을 설명할 수 있다.
- `X | None`을 받은 코드에서 `None` 처리, `isinstance()`, `match` 문, `assert`로 타입을 좁히고, `cast()`가 실행 중에는 아무것도 하지 않는다는 것을 설명할 수 있다.
- 매개변수에는 `Iterable`/`Sequence`/`Mapping`을, 반환값에는 `list`/`dict`를 고르는 이유를 설명하고, `list[int]`를 `list[float]` 매개변수에 넘길 수 없는 이유를 말할 수 있다.
- `Callable`, `Iterator`, `Generator`로 함수와 제너레이터의 타입을 적고, `ParamSpec`을 쓴 데코레이터의 타입을 읽을 수 있다.
- 타입 매개변수를 쓰는 제네릭 함수·클래스와 `type` 별칭을 만들고, `TypeVar`/`Generic`으로 쓴 옛 코드를 읽을 수 있다.
- `Literal`, `TypedDict`, `Enum`, `Protocol` 중 상황에 맞는 것을 골라 데이터와 객체의 약속을 타입으로 적을 수 있다.
- `len()`, `in`, `[]`, `if x:`, `|` 같은 문법이 부르는 특별한 메서드를 말하고, 직접 만들어 내 객체를 그 문법에 쓸 수 있다. 모르는 특별한 메서드는 공식 문서의 "Data model"에서 찾을 수 있다.
- Pydantic 모델로 딕셔너리와 JSON을 검증하고, 검증 오류를 읽고, JSON 스키마를 만들 수 있다.
- 데이터 클래스, `TypedDict`, Pydantic 모델 중 무엇을 쓸지 "데이터가 어디서 오는가"를 기준으로 고를 수 있다.

## 5.1 정적 타입 검사

### 5.1.1 "읽기"에서 "검사받기"로

기초 과정에서 타입 힌트를 쓴 이유는 네 가지였다(기초 과정 5.4.2). 읽는 사람에게 알려 주고, VS Code가 자동 완성과 경고를 해 주고, AI 도구가 코드를 더 잘 이해하고, 일부 라이브러리가 타입 힌트를 읽어 동작을 정한다. 이 중 두 번째, "실행하기 **전에** 실수를 찾는다"를 제대로 하는 도구가 **정적 타입 검사기**(static type checker)다.

- **정적**(static) — 프로그램을 **실행하지 않고** 코드만 읽어서 검사한다는 뜻이다. 반대말은 실행 중에 검사하는 **동적**(dynamic) 검사다. 파이썬이 `"3" + 1`에서 `TypeError`를 내는 것은 실행 중의 검사다.
- **타입 검사기** — 타입 힌트를 보고, 값이 흘러가는 길(할당, 인자 전달, 반환, 속성 접근)마다 타입이 맞는지 따져 본다.

대표적인 검사기는 두 가지다.

| 검사기 | 만든 곳 | 쓰는 곳 |
|---|---|---|
| **mypy** | 파이썬 커뮤니티(파이썬 타입 힌트를 처음 설계한 사람들이 시작했다) | 터미널에서 실행한다. 8장의 GitHub Actions처럼 자동 검사에 넣는다 |
| **Pyright** | Microsoft | VS Code의 Pylance 안에 들어 있다. 코드를 쓰는 동안 물결 밑줄로 보여 준다 |

두 검사기는 대부분 같은 판단을 하지만, 메시지의 표현과 일부 규칙이 다르다. 이 장에서는 **mypy를 기준**으로 삼고, Pylance는 쓰는 동안 바로바로 보는 보조 도구로 쓴다. 터미널에서 실행하는 mypy는 누가 어느 편집기를 쓰든 같은 결과를 내므로, 6장 이후 테스트·린트와 함께 "커밋하기 전에 돌리는 검사"가 된다.

검사기가 하는 일과 하지 않는 일을 먼저 분명히 해 둔다.

- 검사기는 프로그램을 **바꾸지 않는다.** mypy가 오류를 백 개 찾아도 `python`으로 실행하는 데는 아무 영향이 없다. 타입 힌트는 여전히 실행 중에 검사되지 않는다.
- 검사기는 **코드에 적힌 것만** 안다. 파일에서 읽은 JSON, 사용자가 입력한 문자열, LLM이 돌려준 답은 실행해 봐야 내용을 안다. 이런 값은 5.6의 Pydantic이 실행 중에 검사한다.

### 5.1.2 mypy로 첫 검사

### 5.1.3 검사 오류 읽기

mypy의 오류는 늘 같은 모양이다.

```
ch05/first_check.py : 18 : error : Argument 1 to "total_price" has incompatible type "str"; expected "int"  [arg-type]
       ① 파일         ② 줄   ③ 종류                             ④ 내용                                    ⑤ 오류 코드
```

(읽기 쉽게 콜론 앞뒤를 띄웠다. 실제 출력에는 빈칸이 없다.)

- **파일과 줄** — VS Code의 터미널에서는 `ch05/first_check.py:18`을 `Cmd`(Windows는 `Ctrl`)를 누른 채 클릭하면 그 줄로 이동한다.
- **종류** — `error`는 고쳐야 할 것, `note`는 앞의 오류를 설명하는 덧붙임이다. `note`는 혼자 나오기도 한다(5.1.4의 `reveal_type()`).
- **내용** — 대부분 "**무엇이** 어떤 타입인데(got), **어디서는** 어떤 타입을 기대한다(expected)"는 모양이다. 따옴표 안이 타입이다.
- **오류 코드** — 대괄호 안의 이름이다. 오류의 종류를 나타낸다. 검색할 때와, 5.1.6에서 특정 오류만 끄거나 무시할 때 쓴다.

자주 보는 오류 코드를 정리한다.

| 오류 코드 | 뜻 | 위의 예 |
|---|---|---|
| `arg-type` | 인자의 타입이 매개변수의 타입과 맞지 않는다 | `total_price("커피", 3)` |
| `return-value` | 돌려주는 값이 반환 타입과 맞지 않는다 | `return None`, `return text.upper` |
| `assignment` | 변수에 선언한 타입과 다른 값을 넣는다 | `count: int = "3"` |
| `attr-defined` | 그 타입에 없는 속성이나 메서드를 쓴다 | `.round()` |
| `union-attr` | `str \| None` 같은 타입의 **일부**에 없는 속성을 쓴다 | 5.2 |
| `call-arg` | 인자의 개수나 이름이 틀렸다 | `ask("안녕", max_token=10)` |
| `index` | 인덱스나 키의 타입이 틀렸거나, 인덱싱할 수 없는 것에 `[]`를 쓴다 | 5.3 |
| `var-annotated` | 빈 컬렉션처럼 타입을 추론할 수 없어 힌트가 필요하다 | `items = []` |

두 번째 오류는 4장의 "래퍼에서 `return`을 빠뜨리는 실수"(4.2.3)처럼 **오류 없이 조용히 틀리는** 종류다. `text.upper`에 괄호가 없어서 메서드를 부르지 않고 메서드 객체를 돌려준다. mypy는 그 타입을 `Callable[[], str]`, 즉 "인자 없이 불러서 문자열을 돌려주는 것"이라고 적었다. `Callable`은 5.3.3에서 읽는다.

**`--pretty`로 보기 좋게**

오류가 어느 부분을 가리키는지 한눈에 보고 싶으면 `--pretty`를 붙인다.

```
mypy --pretty ch05/first_check.py
```

```
ch05/first_check.py:10: error: Incompatible return value type (got "None",
expected "float")  [return-value]
            return None
                   ^~~~
ch05/first_check.py:15: error: Incompatible return value type (got
"Callable[[], str]", expected "str")  [return-value]
        return text.upper
               ^~~~~~~~~~
...
```

오류 메시지 아래에 해당 줄을 보여 주고, 문제가 된 부분에 `^~~~`로 표시한다.

> **오류는 위에서부터 하나씩 고친다**
> 앞의 오류가 뒤의 오류를 낳는 일이 많다. 함수의 반환 타입이 틀리면 그 함수를 부르는 모든 곳에서 오류가 날 수 있다. 오류가 스무 개라고 겁먹지 말고, 첫 오류를 고치고 다시 검사한다. AI에게 오류를 고쳐 달라고 할 때도 오류 메시지 **전체**를 붙여 넣는다. 파일·줄·오류 코드가 다 들어 있어야 정확히 고친다.

### 5.1.4 `reveal_type()` — 검사기가 본 타입 확인하기

1장에서 Pylance에 마우스를 올려 추론한 타입을 보았다(1.2.5). mypy에게는 `reveal_type()`으로 묻는다.

`ch05/reveal_demo.py`

```python
"""reveal_type() — mypy가 추론한 타입을 보여 달라고 한다."""

import json

scores = {"수학": 90, "영어": 85}
reveal_type(scores)
best = max(scores, key=lambda name: scores[name])
reveal_type(best)
reveal_type(scores.get("과학"))
data = json.loads('{"model": "small"}')
reveal_type(data)
squares = (n * n for n in range(5))
reveal_type(squares)
items = []
```

```
mypy ch05/reveal_demo.py
```

```
ch05/reveal_demo.py:6: note: Revealed type is "dict[str, int]"
ch05/reveal_demo.py:8: note: Revealed type is "str"
ch05/reveal_demo.py:9: note: Revealed type is "int | None"
ch05/reveal_demo.py:11: note: Revealed type is "Any"
ch05/reveal_demo.py:13: note: Revealed type is "typing.Generator[int, None, None]"
ch05/reveal_demo.py:14: error: Need type annotation for "items" (hint: "items: list[<type>] = ...")  [var-annotated]
Found 1 error in 1 file (checked 1 source file)
```

- `scores.get("과학")`은 `int | None`이다. 키가 없으면 `None`을 돌려주기 때문이다(기초 과정 3.4.2). 이 `None`이 5.2의 주제다.
- `json.loads()`는 `Any`다. JSON 문자열의 내용은 실행해 봐야 알기 때문이다. `Any`는 "검사하지 않는다"는 뜻이다(5.1.6). 5.6에서 Pydantic으로 이 구멍을 막는다.
- 제너레이터 표현식은 `Generator[int, None, None]`이다. 3.3.1에서 Pylance로 본 것과 같다. 5.3.4에서 세 칸을 읽는다.
- `items = []`는 오류다. 빈 리스트만 보고는 무엇을 담을지 알 수 없다. 기초 과정 8.2.5의 "빈 컬렉션에는 타입 힌트를 붙인다"가 이것이다. 오류 메시지의 `hint`대로 `items: list[str] = []`처럼 고친다.

`reveal_type()`은 **검사기에게 하는 질문**이다. 이대로 `python`으로 실행하면 어떻게 될까?

```
python ch05/reveal_demo.py
```

```
Traceback (most recent call last):
  File "/Users/.../python-advanced-lab/ch05/reveal_demo.py", line 6, in <module>
    reveal_type(scores)
    ^^^^^^^^^^^
NameError: name 'reveal_type' is not defined
```

mypy는 `reveal_type`을 특별한 이름으로 알아보지만, 파이썬에게는 정의되지 않은 이름이다. 실행도 하고 싶다면 `from typing import reveal_type`으로 가져온다. 그러면 실행할 때는 **실제 값의 타입**을 출력하고 값을 그대로 돌려준다.

```python
>>> from typing import reveal_type
>>> reveal_type({"수학": 90})
Runtime type is 'dict'
{'수학': 90}
```

mypy는 `dict[str, int]`라고 하고, 실행 중에는 `dict`라고 한다. 실행 중의 객체는 "키와 값이 어떤 타입인지"를 따로 기록하지 않는다. `reveal_type()`은 확인이 끝나면 지운다. 검사기에게 물어보는 디버깅용 코드다.

### 5.1.5 VS Code(Pylance)의 타입 검사 모드

기초 과정 8.2.5에서 `"python.analysis.typeCheckingMode": "basic"`으로 Pylance의 검사를 켜 보았다. 이 설정은 네 단계다.

| 값 | 검사하는 것 |
|---|---|
| `"off"` | 타입 오류를 보여 주지 않는다. 정의되지 않은 이름, 잘못된 `import` 정도만 알린다. Pylance의 기본값이다 |
| `"basic"` | 분명한 타입 오류를 보여 준다 |
| `"standard"` | `basic`보다 조금 더 엄격하다. mypy의 기본 설정과 비슷한 수준이다 |
| `"strict"` | 타입 힌트가 빠진 곳, `Any`가 섞인 곳까지 모두 지적한다 |

이 과정에서는 `"standard"`를 쓴다. 1장에서 만든 작업 공간 설정 `.vscode/settings.json`에 한 줄을 더한다(1.2.4). 저장소를 받은 사람 모두가 같은 기준으로 검사받도록 사용자 설정이 아니라 **작업 공간 설정**에 넣는다.

`.vscode/settings.json`

```jsonc
{
    "[python]": {
        "editor.defaultFormatter": "charliermarsh.ruff",
        "editor.formatOnSave": true,
        "editor.codeActionsOnSave": {
            "source.fixAll.ruff": "explicit",
            "source.organizeImports.ruff": "explicit"
        }
    },
    "files.exclude": {
        "**/__pycache__": true,
        "**/.mypy_cache": true
    },
    "python.analysis.typeCheckingMode": "standard"
}
```

`files.exclude`에 `.mypy_cache`도 더해 탐색기에서 감췄다. 저장하고 `ch05/first_check.py`를 열면 mypy가 찾은 다섯 곳에 빨간 물결 밑줄이 생긴다. 18번 줄의 `"커피"`에 마우스를 올리면 다음과 같은 설명이 나온다.

```

  "Literal['커피']"은 "int"에 할당할 수 없습니다. Pylance(reportArgumentType)
```

VS Code의 표시 언어가 영어라면 `Argument of type "Literal['커피']" cannot be assigned to parameter "price" ...`처럼 영어로 나온다. 같은 실수를 mypy는 `"str"`이라고 했는데, Pylance는 `Literal['커피']`라고 더 자세히 말한다. 검사기마다 표현은 다르지만 가리키는 실수는 같다. 끝의 `reportArgumentType`이 Pylance의 오류 코드다. mypy의 `arg-type`에 해당한다.

`Ctrl+Shift+M`(macOS는 `Cmd+Shift+M`)으로 **문제** 패널을 열면 열려 있는 파일의 오류가 모두 목록으로 보인다.

> **Pylance와 mypy가 다르게 말할 때**
> 두 검사기는 따로 만든 프로그램이라 드물게 판단이 다르다. 한쪽에서만 오류가 난다면 먼저 **설정의 엄격함**이 같은지 본다. mypy의 기본 설정은 타입 힌트가 없는 함수 안을 검사하지 않지만(5.1.6), Pylance는 추론한 타입으로 검사한다. 이 과정에서는 **mypy가 통과하는 것**을 기준으로 삼는다. 9장의 완료 기준도 "`mypy` 검사를 경고 없이 통과한다"이다.

### 5.1.6 기존 코드에 점진적으로 도입하기

1~4장에서 만든 코드에는 타입 힌트가 거의 없다. 실무에서 만나는 코드도 대개 그렇다. 수천 줄짜리 코드에 타입 힌트를 한꺼번에 붙일 수는 없다. 그래서 파이썬의 타입 검사는 처음부터 **점진적 타이핑**(gradual typing)으로 설계되었다. 타입 힌트가 있는 곳은 검사하고, 없는 곳은 내버려 둔다. 그 차이를 확인한다.

`ch05/gradual.py`

```python
"""타입 힌트가 있는 함수와 없는 함수."""


def word_count(text):
    return len(text.split()) + "개"


def char_count(text: str) -> int:
    return len(text) + "개"


def main():
    print(word_count("타입 힌트를 검사받는다"))
    print(char_count(42))


main()
```

세 군데가 틀렸다. 정수에 문자열을 더하는 곳이 두 곳(5번, 9번 줄), 문자열을 받는 함수에 정수를 넘기는 곳이 한 곳(14번 줄)이다.

```
mypy ch05/gradual.py
```

```
ch05/gradual.py:9: error: Unsupported operand types for + ("int" and "str")  [operator]
Found 1 error in 1 file (checked 1 source file)
```

하나만 찾았다. mypy의 기본 규칙은 이렇다.

- **타입 힌트가 하나도 없는 함수는 본문을 검사하지 않는다.** `word_count()`와 `main()`은 매개변수에도 반환값에도 힌트가 없다. mypy는 "아직 타입을 붙이지 않은 코드"로 보고 건너뛴다. 그래서 5번 줄과, `main()` 안의 14번 줄을 지나쳤다.
- **힌트가 없는 매개변수와 반환값은 `Any`로 본다.** `word_count(text)`의 `text`는 `Any`, 반환값도 `Any`다.

**`Any` — 검사를 끄는 타입**

`Any`는 "어떤 타입이든 된다"는 뜻이 아니라, 더 정확히는 "**이 값은 검사하지 않는다**"는 뜻이다. `Any`인 값에는 무엇을 해도 오류가 나지 않고, `Any`인 값은 어디에 넘겨도 오류가 나지 않는다. `json.loads()`의 결과가 `Any`였다(5.1.4). 그 결과에 `data["model"].nonexistent()`처럼 써도 mypy는 아무 말도 하지 않는다.

`Any`와 비슷해 보이는 것으로 `object`가 있다. 모든 값은 `object`이지만, `object`에는 모든 객체가 가진 연산만 할 수 있다.

```python
def show(value: object) -> None:
    print(value.upper())   # error: "object" has no attribute "upper"  [attr-defined]
```

| | `Any` | `object` |
|---|---|---|
| 무엇이든 받는가 | 받는다 | 받는다 |
| 받은 값으로 무엇이든 할 수 있는가 | 할 수 있다. **검사하지 않는다** | 할 수 없다. `isinstance()`로 좁혀야 쓸 수 있다(5.2) |
| 쓰는 곳 | 정말 알 수 없을 때, 타입 힌트를 붙이는 중간 단계 | "무엇이든 받지만 함부로 쓰지 않는다"를 적을 때 |

2.5.8의 `handle(message: dict)`처럼 `dict`나 `list`를 대괄호 없이 쓰면 `dict[Any, Any]`, `list[Any]`가 된다. 키와 값을 검사하지 않겠다는 뜻이다.

**검사를 넓혀 가는 옵션**

| 옵션 | 하는 일 |
|---|---|
| (없음) | 힌트가 있는 함수만 검사한다. 처음 도입할 때 |
| `--check-untyped-defs` | 힌트가 없는 함수의 **본문도** 검사한다. 매개변수는 여전히 `Any` |
| `--disallow-untyped-defs` | 힌트가 빠진 함수를 오류로 본다 |
| `--strict` | 위의 것을 포함해 엄격한 옵션을 모두 켠다. 새로 쓰는 코드의 목표 |

```
mypy --check-untyped-defs ch05/gradual.py
```

```
ch05/gradual.py:5: error: Unsupported operand types for + ("int" and "str")  [operator]
ch05/gradual.py:9: error: Unsupported operand types for + ("int" and "str")  [operator]
ch05/gradual.py:14: error: Argument 1 to "char_count" has incompatible type "int"; expected "str"  [arg-type]
Found 3 errors in 1 file (checked 1 source file)
```

```
mypy --strict ch05/gradual.py
```

```
ch05/gradual.py:4: error: Function is missing a type annotation  [no-untyped-def]
ch05/gradual.py:5: error: Unsupported operand types for + ("int" and "str")  [operator]
ch05/gradual.py:9: error: Unsupported operand types for + ("int" and "str")  [operator]
ch05/gradual.py:12: error: Function is missing a return type annotation  [no-untyped-def]
ch05/gradual.py:12: note: Use "-> None" if function does not return a value
ch05/gradual.py:13: error: Call to untyped function "word_count" in typed context  [no-untyped-call]
ch05/gradual.py:14: error: Argument 1 to "char_count" has incompatible type "int"; expected "str"  [arg-type]
ch05/gradual.py:17: error: Call to untyped function "main" in typed context  [no-untyped-call]
Found 7 errors in 1 file (checked 1 source file)
```

`--strict`는 타입 힌트가 빠진 것 자체를 오류로 본다. `main()`처럼 아무것도 돌려주지 않는 함수에도 `-> None`을 붙이라고 한다(note). 반환 타입을 적지 않으면 "검사하지 않는 함수"와 구별할 수 없기 때문이다.

**기존 코드에 도입하는 순서**

1. 옵션 없이 `mypy`를 돌려, 이미 힌트가 있는 곳의 오류부터 없앤다.
2. 다른 파일에서 `import`해 쓰는 함수, 즉 모듈의 **경계**에 있는 함수부터 힌트를 붙인다. 여러 곳에서 부르는 함수일수록 검사의 효과가 크다.
3. `--check-untyped-defs`를 켜서 힌트가 없는 본문도 검사한다.
4. 새로 쓰는 파일은 처음부터 `--strict`를 통과하게 쓴다. 이 장의 종합 실습(실습 5-7)이 그렇다.

이 옵션들은 8장에서 `pyproject.toml`에 한 번 적어 두고 `mypy`만 실행하게 바꾼다. 지금은 명령행에 붙인다.

**`# type: ignore` — 한 줄만 무시하기**

검사기가 틀렸거나, 지금 당장 고칠 수 없는 줄이 있다. 그 줄 끝에 주석을 단다.

```python
count: int = "3"  # type: ignore[assignment]
```

대괄호 안에 **오류 코드를 꼭 적는다.** 코드 없이 `# type: ignore`만 쓰면 그 줄의 다른 오류까지 모두 숨긴다. `--strict`에는 더 이상 필요 없어진 `# type: ignore`를 알려 주는 옵션(`--warn-unused-ignores`)도 들어 있다. AI가 오류를 "고쳤다"며 `# type: ignore`를 붙였다면, 진짜로 고친 것인지 숨긴 것인지 확인한다.

**타입 정보가 없는 라이브러리**

`import`한 라이브러리에 타입 정보가 없으면 mypy는 이렇게 알린다. YAML 파일을 읽는 `pyyaml` 패키지를 예로 들면 다음과 같다.

```
error: Library stubs not installed for "yaml"  [import-untyped]
note: Hint: "python3 -m pip install types-PyYAML"
```

요즘 라이브러리는 대부분 코드 안에 타입 힌트를 넣어 배포한다. 1장에서 본 `httpx`, 이 장의 `pydantic`, LLM SDK가 모두 그렇다. 타입 힌트가 없는 오래된 라이브러리는 1.2.6에서 본 **스텁 파일**(`.pyi`)을 따로 배포하기도 한다. 이름이 `types-`로 시작하는 패키지가 그것이다. 힌트대로 설치하면 오류가 사라진다. 스텁 패키지조차 없다면 그 라이브러리에서 가져온 것은 모두 `Any`가 된다.

### 실습 5-1. 정적 타입 검사

**1. 예측하고 검사하기**

`ch05/check_quiz.py`를 만들고 아래 코드를 입력한다. 검사하기 **전에** `ch05/notes.md`에 mypy가 오류를 낼 줄 번호와 오류 코드를 예측해서 적는다. 실행하면 어디서 멈출지도 적는다.

```python
"""실습 5-1 — 검사하기 전에 예측한다."""


def make_greeting(name: str, times: int = 1) -> str:
    return ("안녕, " + name + "! ") * times


def word_lengths(words: list[str]) -> dict[str, int]:
    return {w: len(w) for w in words}


greeting = make_greeting("파이썬", "두 번")
lengths = word_lengths("타입 힌트")
print(lengths["타입"] + 1)
total: float = sum(word_lengths(["a", "bb"]).values())
print(make_greeting("mypy").uppercase())
```

`mypy ch05/check_quiz.py`로 확인하고, 예측과 다른 것이 있으면 이유를 적는다. 특히 13번 줄의 `word_lengths("타입 힌트")`는 실행하면 오류 없이 무엇을 돌려주는가? 문자열도 반복할 수 있으므로 컴프리헨션이 동작한다(2장). 이런 실수를 실행으로는 찾기 어려운 이유를 적는다.

**2. `reveal_type()`으로 묻기**

앞 장에서 만든 파일 두 개를 골라 `reveal_type()`을 몇 줄 넣고 mypy로 검사한다. 예를 들어 3장의 제너레이터 함수를 부른 결과, 4장의 `make_multiplier(2)`의 결과가 어떤 타입으로 보이는지 확인한다. 타입 힌트가 없는 함수의 결과는 무엇으로 나오는가? 확인했으면 `reveal_type()` 줄을 지운다.

**3. 점진적 도입**

## 5.2 타입 좁히기

### 5.2.1 `None`일 수도 있는 값

`dict.get()`, `os.environ.get()`, `re.match()`처럼 "**찾지 못하면 `None`**"을 돌려주는 함수가 많다. LLM 응답에도 "있을 수도 있고 없을 수도 있는" 필드가 많다. 이런 값의 타입은 `X | None`이다. mypy는 `None`일 수 있는 값을 `None`이 아닌 것처럼 쓰면 지적한다.

`ch05/narrowing.py`

```python
"""타입 좁히기 — None일 수도 있는 값."""

import os


def greet(name: str | None) -> str:
    return "안녕하세요, " + name.strip() + "님"


def get_model() -> str:
    model = os.environ.get("LLM_MODEL")
    return model


def next_age(ages: dict[str, int], name: str) -> int:
    age = ages.get(name)
    return age + 1
```

```
mypy ch05/narrowing.py
```

```
ch05/narrowing.py:7: error: Item "None" of "str | None" has no attribute "strip"  [union-attr]
ch05/narrowing.py:12: error: Incompatible return value type (got "str | None", expected "str")  [return-value]
ch05/narrowing.py:17: error: Unsupported operand types for + ("None" and "int")  [operator]
ch05/narrowing.py:17: note: Left operand is of type "int | None"
Found 3 errors in 1 file (checked 1 source file)
```

세 오류 모두 "`None`일 때를 생각하지 않았다"는 뜻이다. 실행해 보면 `None`이 들어오는 경우에만 `AttributeError: 'NoneType' object has no attribute 'strip'` 같은 오류가 난다. 환경 변수가 설정된 개발자 컴퓨터에서는 잘 되다가, 설정이 빠진 서버에서 터지는 종류의 버그다.

첫 오류의 `union-attr`는 "**합집합 타입**(union type)의 일부에 없는 속성"이라는 뜻이다. `str | None`은 `str`과 `None`의 합집합이다. `strip()`은 `str`에는 있지만 `None`에는 없다.

이 오류를 고치는 방법은 "`None`이 아니라는 것을 **확인한 뒤에** 쓰는 것"이다. 검사기는 `if` 문 같은 확인 코드를 읽고, 그 아래에서는 타입을 더 좁게 본다. 이것을 **타입 좁히기**(type narrowing)라고 한다.

### 5.2.2 `None`을 먼저 처리하기

`greet()`를 고친다.

```python
def greet(name: str | None) -> str:
    if name is None:
        return "안녕하세요"
    reveal_type(name)  # Revealed type is "str"
    return "안녕하세요, " + name.strip() + "님"
```

`if name is None:` 안에서 `return`했으므로, 그 아래로 내려왔다면 `name`은 `None`이 아니다. mypy는 이 흐름을 따라가서 아래에서는 `name`을 `str`로 본다. **함수의 첫머리에서 `None`인 경우를 처리하고 빠져나가는** 이 모양을 **이른 반환**(early return)이라고 한다. 본문이 `if`/`else`로 깊어지지 않아서 읽기도 쉽다.

`None`일 때 계속할 수 없다면 예외를 일으킨다.

```python
def get_model() -> str:
    model = os.environ.get("LLM_MODEL")
    if model is None:
        raise RuntimeError("LLM_MODEL 환경 변수가 없다")
    return model
```

`raise`도 `return`처럼 그 아래로 내려가지 않으므로 좁히기가 된다. 기본값이 있다면 아예 `None`이 나오지 않게 한다.

```python
model = os.environ.get("LLM_MODEL", "small")      # str
age = ages.get(name, 0)                           # int
```

`get()`에 기본값을 넘기면 mypy도 결과를 `str`, `int`로 본다. **`None`이 생기지 않게 하는 것이 가장 좋은 처리**다.

> **`if name:`과 `if name is not None:`은 다르다**
> `if name:`으로도 좁혀진다. 하지만 빈 문자열 `""`도 거짓이므로 함께 걸러진다. 정수라면 0이 걸러진다.
> ```python
> def max_tokens(value: int | None) -> int:
>     if value:
>         return value
>     reveal_type(value)  # Revealed type is "Literal[0] | None"
>     return 1024
> ```
> mypy는 `if value:`를 지나지 못한 `value`를 `Literal[0] | None`, 즉 "0 또는 `None`"이라고 정확히 알려 준다. `max_tokens(0)`이 1024가 되는 것이 의도한 것인가? `temperature=0.0`처럼 0이 뜻있는 값인 설정에서 흔한 버그다. "없음"을 확인하려면 `is None`으로 쓴다.

### 5.2.3 `isinstance()`로 좁히기

LLM API의 메시지 `content`는 **문자열이기도 하고 블록의 리스트이기도 하다.** 짧은 질문은 `"안녕"`처럼 문자열로, 이미지나 도구 결과가 섞인 메시지는 `[{"type": "text", "text": "..."}, ...]`처럼 블록의 리스트로 보낸다. 두 모양을 모두 받아 글자만 뽑는 함수를 만든다.

`ch05/content.py`

```python
"""isinstance()로 좁히기 — 문자열이거나 블록 리스트인 content."""

type Block = dict[str, str]


def text_of(content: str | list[Block]) -> str:
    """content에서 글자만 뽑는다. 블록 리스트라면 text 블록만 이어 붙인다."""
    if isinstance(content, str):
        reveal_type(content)
        return content
    reveal_type(content)
    return "".join(block["text"] for block in content if block["type"] == "text")


if __name__ == "__main__":
    print(text_of("안녕"))
    print(text_of([{"type": "text", "text": "사진 속 "}, {"type": "image", "url": "a.png"},
                   {"type": "text", "text": "고양이"}]))
```

`type Block = ...`은 타입에 이름을 붙이는 **타입 별칭** 문이다(5.4.4). 지금은 "`Block`은 `dict[str, str]`의 다른 이름"으로 읽는다.

```
mypy ch05/content.py
```

```
ch05/content.py:9: note: Revealed type is "str"
ch05/content.py:11: note: Revealed type is "list[dict[str, str]]"
Success: no issues found in 1 source file
```

`note`만 있고 `error`가 없으므로 검사는 통과다. `isinstance(content, str)`가 참인 쪽에서 `content`는 `str`이다. 그 아래, 즉 `str`이 아닌 쪽에서는 합집합에서 `str`을 뺀 나머지 `list[Block]`이다. 검사기는 "**남은 것**"까지 계산한다. 확인했으면 `reveal_type()` 두 줄을 지우고 실행한다.

```
python ch05/content.py
```

```
안녕
사진 속 고양이
```

`isinstance()`의 두 번째 인자에는 **실행 중에 확인할 수 있는 클래스**만 쓸 수 있다. `isinstance(x, list)`는 되지만 `isinstance(x, list[str])`은 `TypeError`다. 실행 중의 리스트는 무엇을 담았는지 기록하지 않기 때문이다(5.1.4의 `Runtime type is 'dict'`).

**`match` 문도 좁힌다**

2.5.4의 클래스 패턴은 `isinstance()`와 같은 확인을 한다. 그래서 `case` 안에서도 타입이 좁혀진다.

```python
def text_of(content: str | list[Block]) -> str:
    match content:
        case str():
            return content
        case list():
            return "".join(b["text"] for b in content if b["type"] == "text")
```

`case str():` 안에서 `content`는 `str`, `case list():` 안에서는 `list[Block]`이다. 두 `case`가 가능한 경우를 모두 다루므로 mypy는 "`return`이 빠졌다"고 하지 않는다. 가능한 경우를 모두 다뤘는지 검사기에게 확인받는 방법은 5.5.1에서 본다.

### 5.2.4 `assert`로 좁히기

"여기서는 절대 `None`이 아니다"라고 확신하는 곳에서는 `assert`를 쓸 수 있다.

```python
def first_line(text: str | None) -> str:
    assert text is not None, "text가 없다"
    return text.splitlines()[0]
```

`assert 조건, 메시지`는 조건이 거짓이면 `AssertionError`를 일으킨다. mypy는 `assert` 아래에서 조건이 참이라고 보고 타입을 좁힌다. 검사기에게 "여기서는 이렇다"고 알려 주면서, 실행 중에 그 믿음이 틀리면 **그 자리에서** 멈추게 한다. 틀린 값이 멀리 흘러가서 엉뚱한 곳에서 터지는 것보다 낫다.

다만 `assert`는 **입력 검사에 쓰지 않는다.** `python -O`로 최적화 모드로 실행하면 `assert` 문은 통째로 사라진다. 사용자나 API에서 들어온 값의 검사는 5.2.2처럼 `if`와 `raise`로 쓴다. `assert`는 "내 코드의 논리상 이럴 수 없다"를 확인하는 곳에 쓴다. 6장에서 테스트의 `assert`를 만나는데, 그것은 pytest가 따로 처리하므로 이 걱정이 없다.

### 5.2.5 `cast()` — 최후의 수단

`typing.cast(타입, 값)`은 검사기에게 "이 값은 이 타입**이라고 쳐라**"라고 말한다.

```python
>>> from typing import cast, reveal_type
>>> x = cast(int, "삼")
>>> reveal_type(x)
Runtime type is 'str'
'삼'
>>> x + 1
Traceback (most recent call last):
  ...
TypeError: can only concatenate str (not "int") to str
```

mypy는 `x`를 `int`로 믿지만, 실행 중의 `x`는 여전히 문자열이다. `cast()`는 **실행 중에 아무것도 하지 않는다.** 변환도 검사도 하지 않고 값을 그대로 돌려준다. 검사기의 입을 막을 뿐이다.

| 방법 | 검사기에게 | 실행 중에 | 쓰는 곳 |
|---|---|---|---|
| `if x is None: return/raise` | 좁혀진다 | 처리한다 | 가장 먼저 고려한다 |
| `isinstance()`, `match` | 좁혀진다 | 확인한다 | 여러 타입 중 하나일 때 |
| `assert` | 좁혀진다 | 확인한다(`-O`에서는 빠진다) | 논리상 그럴 수 없는 경우 |
| `cast()` | 믿게 한다 | **아무것도 하지 않는다** | 검사기가 알 수 없고, 확인할 방법도 없을 때 |
| `# type: ignore[코드]` | 그 줄의 오류를 숨긴다 | 아무것도 하지 않는다 | 검사기가 틀렸을 때 |

`cast()`는 틀려도 아무도 알려 주지 않는다. 그래서 위에서부터 차례로 고려하고, `cast()`는 마지막에 둔다. AI가 만든 코드에 `cast()`가 많다면 타입 오류를 "해결"한 것이 아니라 "숨긴" 것일 수 있다.

## 5.3 컬렉션과 함수의 타입

### 5.3.1 `list[int]`는 `list[float]`가 아니다

점수의 합계를 구하는 함수에 `list[float]`라고 힌트를 붙였다. 정수 점수의 리스트를 넘겨 본다.

`ch05/stats.py`

```python
"""매개변수는 넓게, 반환값은 구체적으로."""

from collections.abc import Collection, Iterable, Mapping


def total_list(values: list[float]) -> float:
    return sum(values)


def total(values: Iterable[float]) -> float:
    return sum(values)


def mean(values: Collection[float]) -> float:
    return sum(values) / len(values)


def price_lines(prices: Mapping[str, int]) -> list[str]:
    return [f"{name}: {price:,}원" for name, price in prices.items()]


scores = [90, 85, 77]
total_list(scores)
total(scores)
total((90, 85))
total(n * 10 for n in range(3))
mean(scores)
mean((1.5, 2.5))
mean(n for n in range(3))
print(price_lines({"커피": 2500, "케이크": 6000}))
```

```
mypy ch05/stats.py
```

```
ch05/stats.py:23: error: Argument 1 to "total_list" has incompatible type "list[int]"; expected "list[float]"  [arg-type]
ch05/stats.py:23: note: "list" is invariant -- see https://mypy.readthedocs.io/en/stable/common_issues.html#variance
ch05/stats.py:23: note: Consider using "Sequence" instead, which is covariant
ch05/stats.py:29: error: Argument 1 to "mean" has incompatible type "Generator[int, None, None]"; expected "Collection[float]"  [arg-type]
ch05/stats.py:29: note: "Generator" is missing following "Collection" protocol members:
ch05/stats.py:29: note:     __contains__, __len__
Found 2 errors in 1 file (checked 1 source file)
```

23번 줄이 이상하다. 정수는 실수 자리에 넘길 수 있다. `def area(w: float, h: float)`에 `area(2, 3)`을 넘기는 것은 오류가 아니다. 그런데 `list[int]`는 `list[float]` 자리에 넘길 수 없다고 한다.

이유는 리스트가 **바꿀 수 있는** 컬렉션이기 때문이다. 다음 함수를 보자.

```python
def add_missing(values: list[float | None]) -> None:
    values.append(None)   # list[float | None]에 None을 넣는 것은 정당하다
```

`scores`(`list[int]`)를 이 함수에 넘길 수 있다면, 함수가 돌아온 뒤 `scores`에는 `None`이 들어 있다. 그런데 바깥에서는 여전히 `scores`를 "정수만 든 리스트"로 믿고 `sum(scores)`를 한다. 실행 중에 `TypeError`가 난다. 그래서 검사기는 "원소의 타입이 조금이라도 다른 리스트"를 서로 넘기지 못하게 한다. 이 성질을 **불변**(invariant)이라고 한다. note의 "`list` is invariant"가 이것이다. `dict`와 `set`도 마찬가지다.

note의 둘째 줄이 해결책을 알려 준다. "`Sequence`를 쓰라, 그것은 **공변**(covariant)이다." `Sequence`는 "읽기만 하는 순서 있는 컬렉션"이다. `append()`가 없으므로 `None`을 넣을 걱정이 없다. 그래서 `Sequence[float]` 자리에는 `list[int]`도, `tuple[float, ...]`도 넘길 수 있다. 24번 줄의 `Iterable[float]`도 같은 이유로 통과했다.

> **용어는 몰라도 된다, 판단만 기억한다**
> "불변", "공변"은 외울 필요가 없다. "**함수가 받은 컬렉션을 바꾸지 않는다면, 매개변수 타입에 `list`/`dict` 대신 읽기 전용 타입(`Sequence`/`Mapping`/`Iterable`)을 쓴다**"만 기억하면 된다. mypy도 오류가 나면 이렇게 하라고 알려 준다.

### 5.3.2 매개변수는 넓게, 반환값은 구체적으로

`collections.abc`에는 "이런 일을 할 수 있는 것"을 뜻하는 타입이 모여 있다. 3장에서 본 이터러블과 이터레이터(3.1.2)도 여기에 있다.

| 타입 | 할 수 있는 일 | 넘길 수 있는 것 |
|---|---|---|
| `Iterable[T]` | `for`로 한 번 훑는다 | 리스트, 튜플, 집합, 딕셔너리(키), 문자열, 파일, 제너레이터 |
| `Iterator[T]` | `next()`로 하나씩 꺼낸다 | 제너레이터, 파일, `zip`·`map`의 결과 |
| `Collection[T]` | `for`, `len()`, `in` | 리스트, 튜플, 집합, 딕셔너리 |
| `Sequence[T]` | 위의 것 + 인덱스 `[i]`, 슬라이스, 여러 번 훑기 | 리스트, 튜플, 문자열, `range` |
| `Mapping[K, V]` | 키로 읽기, `keys()`/`values()`/`items()`, `get()` | 딕셔너리 |
| `MutableSequence[T]`, `MutableMapping[K, V]` | 위의 것 + 바꾸기 | 리스트 / 딕셔너리 |

**매개변수는 넓게** — 함수가 **실제로 쓰는 일만큼만** 요구한다.

- `total()`은 한 번 훑기만 하므로 `Iterable`로 충분하다. 그래서 제너레이터 표현식도 받았다(26번 줄). 3.4의 파이프라인 단계가 `Iterable`을 받는 이유다.
- `mean()`은 `sum()`으로 한 번 훑고 `len()`으로 개수를 센다. 인덱스(`values[0]`)는 쓰지 않는다. 그래서 `len()`까지 되는 `Collection`이면 충분하다. 리스트와 튜플은 물론 집합도 넘길 수 있다. 제너레이터는 `__len__`이 없어서 `len()`을 쓸 수 없다. 29번 줄의 제너레이터는 거절당했고, note가 `Collection`에 필요한 `__len__`(과 `in`에 쓰는 `__contains__`)이 없다고 이유를 알려 준다. 검사 없이 실행했다면 `TypeError: object of type 'generator' has no len()`이 났을 것이다. `Sequence`로 적어도 동작하지만, 쓰지도 않는 인덱스를 요구해서 집합을 받지 못하게 된다.
- `price_lines()`는 딕셔너리를 읽기만 하므로 `Mapping`을 받는다. `Mapping`에는 `prices["커피"] = 0` 같은 대입이 없다. 함수 안에서 실수로 바꾸려 하면 `Unsupported target for indexed assignment ("Mapping[str, int]")  [index]` 오류가 난다. 타입 힌트만 보고도 "이 함수는 내 딕셔너리를 바꾸지 않는다"는 약속을 알 수 있다.

**반환값은 구체적으로** — 받는 쪽이 할 수 있는 일을 줄이지 않는다.

`price_lines()`는 `list[str]`을 돌려준다. `Iterable[str]`이라고 적을 수도 있지만, 그러면 받는 쪽은 `lines[0]`도 `len(lines)`도 `lines.append(...)`도 할 수 없다. 실제로 리스트를 돌려준다면 `list[str]`이라고 적어서 리스트로 할 수 있는 일을 모두 허락한다. 반대로 제너레이터를 돌려준다면 `list`라고 적을 수 없으므로 `Iterator[str]`이라고 적는다(5.3.4).

**튜플은 두 가지로 적는다**

| 타입 힌트 | 뜻 | 예 |
|---|---|---|
| `tuple[str, int]` | 정확히 두 개. 첫째는 문자열, 둘째는 정수 | `("커피", 2500)` |
| `tuple[int, ...]` | 정수가 몇 개든. 말줄임표 `...`는 "같은 타입이 더 있다" | `(1, 2, 3)`, `()` |

리스트는 `list[int]`처럼 원소의 타입을 하나만 적는다. 튜플은 **자리마다** 타입을 적는다. 기초 과정에서 "튜플은 자리마다 뜻이 정해진 묶음"이라고 한 것이 타입에도 그대로 드러난다.

### 5.3.3 `Callable` — 함수를 받는 매개변수

기초 과정 8.2.5에서 `Callable[[int], int]`를 읽었다. "정수 하나를 받아 정수를 돌려주는 함수"다. 함수를 받는 함수, 함수를 돌려주는 함수에 타입을 붙여 본다.

`ch05/callables.py`

```python
"""Callable — 함수의 타입."""

import time

def apply_all(texts: list[str], func: Callable[[str], str]) -> list[str]:
    return [func(t) for t in texts]


def make_multiplier(factor: int) -> Callable[[int], int]:
    def multiply(x: int) -> int:
        return x * factor

    return multiply


def wait_and_call(func: Callable[[], str], sleep: Callable[[float], None] = time.sleep) -> str:
    sleep(0.1)
    return func()


apply_all(["a", "b"], str.upper)
apply_all(["a", "b"], lambda t: t * 2)
apply_all(["a", "b"], len)
double = make_multiplier(2)
reveal_type(double)
wait_and_call(lambda: "답", sleep=lambda seconds: None)
```

- `Callable[[인자 타입, ...], 반환 타입]` — 대괄호 안의 리스트가 매개변수들의 타입, 그 뒤가 반환 타입이다. 인자가 없으면 `Callable[[], str]`이다. 5.1.2에서 mypy가 `text.upper`를 `Callable[[], str]`이라고 한 것이 이것이다.

- 람다는 넘겨질 자리의 타입으로 매개변수 타입이 정해진다. `lambda t: t * 2`의 `t`는 `str`로 추론된다.
- `wait_and_call()`의 `sleep` 매개변수는 4장 실습 4-7의 **의존성 주입**이다. `Callable[[float], None]`이라고 적어 두면, 실수로 인자를 받지 않는 함수나 두 개 받는 함수를 넘기는 것을 검사기가 막는다.

4.5.4의 `as_tool.py`에서는 `from typing import Callable`이라고 썼다. 기초 과정 8.2.5에서 본 대로 지금은 `collections.abc`에서 가져온다. 둘은 같은 것이다.

**인자를 따지지 않을 때 — `Callable[..., T]`**

대괄호 자리에 말줄임표를 쓰면 "인자는 무엇이든"이라는 뜻이다. `Callable[..., str]`은 "어떤 인자든 받아 문자열을 돌려주는 함수"다. 4장의 `ToolRegistry`처럼 매개변수가 제각각인 함수를 모아 두는 곳에서 쓴다.

```python
tools: dict[str, Callable[..., object]] = {}
```

다만 이렇게 적으면 그 함수를 부를 때 인자를 검사하지 않는다. 인자까지 지키고 싶으면 5.3.5의 `ParamSpec`이나 5.5.4의 `Protocol`을 쓴다.

### 5.3.4 제너레이터의 타입 — `Iterator`와 `Generator`

제너레이터 함수는 부르면 제너레이터 객체를 돌려준다(3.2.1). 반환 타입에는 `yield`하는 값이 아니라 **제너레이터 객체의 타입**을 적는다.

`ch05/gen_types.py`

```python
"""제너레이터와 컨텍스트 관리자의 타입."""

import time
from collections.abc import Generator, Iterator
from contextlib import contextmanager


def count_up(limit: int) -> Iterator[int]:
    n = 0
    while n < limit:
        yield n
        n += 1


def count_up_with_result(limit: int) -> Generator[int, None, str]:
    n = 0
    while n < limit:
        yield n
        n += 1
    return "끝"


def bad_count(limit: int) -> list[int]:
    for n in range(limit):
        yield n


@contextmanager
def timer(label: str) -> Iterator[None]:
    start = time.perf_counter()
    try:
        yield
    finally:
        print(f"[{label}] {time.perf_counter() - start:.2f}초")


reveal_type(count_up(3))
reveal_type(n * n for n in range(3))
```

- **`Iterator[int]`** — "정수를 하나씩 내놓는 것"이다. 1장 (마)의 `chunk()`와 3장 실습 3-7의 함수들이 이렇게 적었다. 제너레이터 함수에는 대부분 이것으로 충분하다.
- **`Generator[Y, S, R]`** — 세 칸을 모두 적는 정식 이름이다. `Y`는 `yield`하는 값의 타입, `S`는 `send()`로 받는 값의 타입, `R`은 `return`하는 값의 타입이다. 3.3.1에서 Pylance가 보여 준 `Generator[int, None, None]`은 "정수를 내놓고, 아무것도 받지 않고, 아무것도 돌려주지 않는다"는 뜻이다. `send()`는 이 과정에서 쓰지 않고, 제너레이터의 `return` 값은 거의 쓰지 않는다(3.2.3). 그래서 뒤의 두 칸이 `None`이 아닐 때만 `Generator`라고 적는다.
- **`bad_count()`** — 본문에 `yield`가 있으면 리스트가 아니라 제너레이터를 돌려준다. 3.2.4에서 "리스트를 돌려주는 함수"와 "제너레이터 함수"를 비교했다. 함수를 제너레이터로 고치면서 반환 타입을 그대로 둔 실수를 검사기가 찾았다.
- **`@contextmanager` 함수** — 이것도 제너레이터 함수다(4.6.4). `yield`가 값 없이 쓰였으므로 `Iterator[None]`이다. 4.6.4의 `timer()`처럼 `yield`로 딕셔너리를 내놓는다면 `Iterator[dict[str, float]]`이다. `with ... as 이름:`의 `이름`에는 `Iterator[...]`가 아니라 **`yield`한 값**이 붙으므로, `이름`의 타입은 대괄호 안의 타입이다. `Iterator[None]`이면 `None`이고(그래서 `as`를 쓰지 않는다), `Iterator[dict[str, float]]`이면 `dict[str, float]`이다.

### 5.3.5 데코레이터의 타입 — `ParamSpec`

4장에서 만든 `logged`에 타입 힌트를 붙여 본다. 먼저 생각나는 대로 `Callable[..., Any]`로 적는다.

`ch05/typed_deco.py`

```python
"""타입 힌트를 붙인 데코레이터."""

import functools
import time
from collections.abc import Callable
from typing import Any


def logged_any(func: Callable[..., Any]) -> Callable[..., Any]:
    @functools.wraps(func)
    def wrapper(*args: Any, **kwargs: Any) -> Any:
        print(f"[호출] {func.__name__}")
        return func(*args, **kwargs)

    return wrapper


def logged[**P, R](func: Callable[P, R]) -> Callable[P, R]:
    @functools.wraps(func)
    def wrapper(*args: P.args, **kwargs: P.kwargs) -> R:
        print(f"[호출] {func.__name__}")
        return func(*args, **kwargs)

    return wrapper


@logged_any
def area_any(width: float, height: float) -> float:
    return width * height


@logged
def area(width: float, height: float) -> float:
    return width * height


reveal_type(area_any)
reveal_type(area)
area_any("2", 3)
area("2", 3)
```

`@logged_any`를 붙인 `area_any`는 "아무 인자나 받아 `Any`를 돌려주는 함수"가 되었다. 원래 함수가 무엇을 받고 무엇을 돌려주는지 **잊어버렸다.** 그래서 `area_any("2", 3)`을 지적하지 못한다. 데코레이터 하나 때문에 그 함수를 쓰는 모든 곳의 검사가 꺼진 셈이다. 4.2.4의 `functools.wraps`가 이름과 독스트링을 지켰듯이, 타입도 지켜야 한다.

`@logged`는 원래 함수의 타입을 그대로 지켰다. 이 모양을 읽어 본다.

```python
def logged[**P, R](func: Callable[P, R]) -> Callable[P, R]:
```

- `[**P, R]` — 이 함수의 **타입 매개변수**다(5.4에서 정식으로 다룬다). 함수를 부를 때마다 `P`와 `R`이 실제 타입으로 정해진다. `R`은 보통의 타입 매개변수로, 여기서는 원래 함수의 반환 타입이다.
- `**P` — 별 두 개가 붙은 것은 **`ParamSpec`**(parameter specification)이다. 타입 **하나**가 아니라 **매개변수 목록 전체**를 담는다. `area`에 붙이면 `P`는 `(width: float, height: float)`, `R`은 `float`가 된다.
- `Callable[P, R]` — "`P`라는 매개변수 목록을 받아 `R`을 돌려주는 함수"다. 받은 것과 돌려주는 것이 같은 `Callable[P, R]`이므로 "**원래 함수와 같은 모양의 함수를 돌려준다**"는 뜻이다.
- `*args: P.args, **kwargs: P.kwargs` — 래퍼가 받는 인자가 원래 함수의 인자와 같다는 표시다. 4.2.3의 `*args, **kwargs`가 "어떤 인자든"이었다면, 이제는 "원래 함수와 같은 인자"다.

인자를 받는 데코레이터는 한 겹이 더 있을 뿐이다. 4.3.2의 `retry()`에 타입을 붙이면 다음과 같다. `ch05/typed_deco.py`의 맨 아래 호출 부분 앞에 더한다.

```python
def retry[**P, R](
    times: int = 3,
    delay: float = 0.1,
    backoff: float = 2.0,
    exceptions: tuple[type[Exception], ...] = (TimeoutError, ConnectionError),
) -> Callable[[Callable[P, R]], Callable[P, R]]:
    """exceptions에 든 예외가 나면 times번까지 시도하는 데코레이터를 만든다."""

    def decorator(func: Callable[P, R]) -> Callable[P, R]:
        @functools.wraps(func)
        def wrapper(*args: P.args, **kwargs: P.kwargs) -> R:
            wait = delay
            for attempt in range(1, times + 1):
                try:
                    return func(*args, **kwargs)
                except exceptions as e:
                    if attempt == times:
                        raise
                    print(f"[재시도] {func.__name__}: {attempt}번째 실패({e}), {wait:.2f}초 뒤 다시")
                    time.sleep(wait)
                    wait *= backoff
            raise AssertionError("여기에 오지 않는다")

        return wrapper

    return decorator
```

- `exceptions: tuple[type[Exception], ...]` — `type[Exception]`은 "예외 **객체**"가 아니라 "예외 **클래스**"라는 뜻이다. `TimeoutError()`가 아니라 `TimeoutError`를 넘긴다. 그런 클래스를 몇 개든 담은 튜플이다.
- 반환 타입 `Callable[[Callable[P, R]], Callable[P, R]]` — "함수를 받아 같은 모양의 함수를 돌려주는 것", 즉 **데코레이터**의 타입이다. 4.3.1에서 "`retry(times=3)`은 데코레이터를 돌려준다"고 한 것을 타입으로 적은 것이다. 겹겹이 보여도 바깥에서부터 한 겹씩 읽으면 된다.
- `raise AssertionError("여기에 오지 않는다")` — `for` 문은 마지막 시도에서 `return`하거나 `raise`하므로 실제로는 반복문 아래에 오지 않는다. 하지만 mypy는 `range(1, times + 1)`이 비어 있을 수도 있다(`times=0`)고 보고, 이 줄이 없으면 `Missing return statement  [return]` 오류를 낸다. 검사기가 4.3.2의 숨은 경우 하나(`times=0`이면 `None`을 돌려준다)를 찾아 준 것이다.

> **데코레이터의 타입은 "읽을 수 있으면" 된다**
> 데코레이터의 타입을 처음부터 혼자 쓸 일은 많지 않다. 대신 FastAPI, LangChain, MCP SDK 같은 라이브러리의 코드를 `F12`로 열면(1.2.6) 이런 모양을 자주 만난다. `Callable[P, R]`이 보이면 "원래 함수의 모양을 지키는 데코레이터"로, `Callable[..., Any]`가 보이면 "모양을 지키지 않는다"로 읽는다. 옛 코드에서는 `P = ParamSpec("P")`처럼 따로 만든 이름을 쓴다(5.4.5).

### 실습 5-3. 컬렉션과 함수의 타입

**1. 매개변수를 넓히기**

다음 함수들에 타입 힌트를 붙인다. 매개변수는 함수가 실제로 하는 일에 맞는 가장 넓은 타입으로, 반환값은 구체적으로 적는다. `ch05/widen.py`에 만들고 `mypy --strict`를 통과시킨다. 각 함수 아래에 리스트, 튜플, 제너레이터 표현식을 넘기는 호출을 하나씩 넣어, 어느 것이 통과하고 어느 것이 거절되는지 확인한다.

```python
def longest(words):
    """가장 긴 단어를 돌려준다."""
    return max(words, key=len)


def last_two(items):
    """마지막 두 원소를 리스트로 돌려준다."""
    return list(items[-2:])


def invert(d):
    """키와 값을 뒤집은 새 딕셔너리를 돌려준다."""
    return {v: k for k, v in d.items()}
```

`invert()`의 키와 값은 우선 `str`과 `int`로 적는다. 아무 타입이나 받게 하는 방법은 5.4에서 배운다.

**3. 콜백의 타입**

## 5.4 제네릭

### 5.4.1 타입 매개변수 — 받은 것과 같은 타입을 돌려준다

리스트의 첫 원소를 돌려주는 함수에 타입 힌트를 붙이려고 한다. 어떤 리스트든 받아야 한다. 무엇을 돌려준다고 적어야 할까?

```python
def first_any(items: Sequence[object]) -> object:
    return items[0]
```

`object`라고 적으면 어떤 리스트든 받을 수는 있지만(5.3.1의 이유로 `list[object]`가 아니라 `Sequence[object]`로 적었다), 돌려받은 값으로 할 수 있는 일이 없다. `first_any(["a", "b"]).upper()`는 `"object" has no attribute "upper"` 오류다. 넣은 것이 문자열이었다는 정보를 잃었다.

필요한 것은 "**넣은 원소와 같은 타입**을 돌려준다"는 약속이다. 이것을 **타입 매개변수**(type parameter)로 적는다.

`ch05/generic_funcs.py`

```python
"""제네릭 함수 — 타입 매개변수."""

from collections.abc import Hashable, Iterable, Sequence


def first[T](items: Sequence[T]) -> T:
    """첫 원소를 돌려준다."""
    return items[0]


reveal_type(first([1, 2, 3]))
reveal_type(first("abc"))
reveal_type(first([{"role": "user", "content": "안녕"}]))
first([1, 2]).upper()
```

`def first[T](...)`의 함수 이름 뒤 대괄호가 **타입 매개변수 목록**이다. 파이썬 3.12에서 생긴 문법이다(1.2.1). 함수의 매개변수 `items`가 부를 때마다 다른 **값**을 받듯이, 타입 매개변수 `T`는 부를 때마다 다른 **타입**을 받는다. `first([1, 2, 3])`에서 `T`는 `int`가 되고, 반환 타입 `T`도 `int`가 된다. 이렇게 타입 매개변수를 가진 함수나 클래스를 **제네릭**(generic)이라고 한다.

`list[int]`, `dict[str, int]`의 대괄호도 같은 생각이다. `list`는 원소의 타입을 매개변수로 받는 제네릭 클래스다. 우리는 지금까지 제네릭을 **써 왔고**, 이제 **만든다.**

README의 학습 항목에는 `def first[T](items: list[T]) -> T`라고 적혀 있다. 이 장에서는 5.3.1의 이유로 `Sequence[T]`를 받게 했다. `list[T]`로 적어도 `first([1, 2, 3])`은 잘 동작한다. 튜플이나 문자열까지 받고 싶을 때 `Sequence[T]`로 넓힌다.

### 5.4.2 타입 매개변수에 조건 붙이기

`T`에는 아무 타입이나 들어갈 수 있다. 그래서 함수 안에서 `T`인 값으로는 `object`에 할 수 있는 일만 할 수 있다. 특정한 일을 해야 한다면 조건을 붙인다. `generic_funcs.py`의 아래에 더한다.

```python
def dedupe[T: Hashable](items: Iterable[T]) -> list[T]:
    """순서를 지키면서 중복을 없앤다."""
    seen: set[T] = set()
    result: list[T] = []
    for item in items:
        if item not in seen:
            seen.add(item)
            result.append(item)
    return result


def longer[S: (str, bytes)](a: S, b: S) -> S:
    """둘 중 긴 것을 돌려준다. 둘은 같은 타입이어야 한다."""
    return a if len(a) >= len(b) else b


reveal_type(dedupe(["a", "b", "a"]))
dedupe([[1], [2]])
reveal_type(longer("ab", "c"))
longer("ab", b"c")
```

- **`[T: Hashable]` — 상한**(upper bound). "`T`는 `Hashable`이거나 그 하위 타입이어야 한다." 집합에 넣으려면 해시할 수 있어야 한다(4.4.3의 `unhashable type: 'list'`). 리스트의 리스트는 거절된다.
- **`[S: (str, bytes)]` — 제약**(constraints). "`S`는 `str`이거나 `bytes`, 둘 중 **하나로 정해진다**." `longer("ab", b"c")`처럼 섞으면 거절된다. 문자열과 바이트를 섞어서 비교하는 실수를 막는다.

조건을 붙인 타입 매개변수는 자주 쓰지는 않는다. 라이브러리 코드에서 만나면 "`T`에는 이런 것만 들어갈 수 있다"로 읽는다.

### 5.4.3 제네릭 클래스

LLM API나 웹 API는 결과가 많으면 한 번에 다 주지 않고 **페이지**로 나눠 준다. 문서 목록, 메시지 목록, 파일 목록 등 무엇을 담든 "항목의 리스트 + 다음 페이지를 가리키는 값"이라는 모양은 같다. 담는 것의 타입만 다르다.

`ch05/page.py`

```python
"""제네릭 클래스 — 무엇을 담든 같은 모양의 페이지."""

from dataclasses import dataclass


@dataclass
class Page[T]:
    items: list[T]
    next_cursor: str | None = None

    def first(self) -> T | None:
        return self.items[0] if self.items else None

    def has_more(self) -> bool:
        return self.next_cursor is not None


docs = Page(items=["휴가 규정.md", "출장 규정.md"], next_cursor="c_02")
reveal_type(docs)
reveal_type(docs.first())

scores: Page[int] = Page(items=[])
scores.items.append("만점")
```

### 5.4.4 `type` 별칭 문

기초 과정 8.2.5에서 `Role = Literal["system", "user", "assistant"]`처럼 긴 타입에 이름을 붙였다. 파이썬 3.12부터는 `type` 문으로 별칭을 만든다. 5.2.3의 `type Block = dict[str, str]`이 그것이다.

`ch05/aliases.py`

```python
def swap[T](pair: Pair[T]) -> Pair[T]:
    return pair[1], pair[0]


reveal_type(swap((1, 2)))
```


- `type Pair[T] = tuple[T, T]` — 별칭도 타입 매개변수를 가질 수 있다. `Pair[int]`는 `tuple[int, int]`다.
- `type JSON = ... JSON ...` — 별칭이 **자기 자신을 가리킬** 수 있다. "JSON 값은 문자열을 키로 하고 JSON 값을 값으로 하는 딕셔너리이거나, JSON 값의 리스트이거나, 문자열·숫자·불리언·`None`이다." 얼마나 깊이 중첩되든 JSON으로 바꿀 수 있는 값이면 통과하고, 집합처럼 JSON에 없는 것은 거절된다. 오류 메시지에 `bool`이 빠진 것은 `bool`이 `int`의 하위 타입이라 하나로 합쳐 보여 주기 때문이다.

`json.loads()`의 결과는 `Any`였다(5.1.4). 그것을 `JSON` 타입의 변수에 담으면 적어도 "JSON에 있을 수 있는 값"이라는 것은 알 수 있다. 하지만 "`model` 키가 있고 그 값은 문자열"이라는 것까지는 모른다. 그것은 5.5.2의 `TypedDict`나 5.6의 Pydantic이 할 일이다.

**`=`로 만든 별칭과 `type` 문의 차이**

| | `Role = Literal[...]` | `type Role = Literal[...]` |
|---|---|---|
| 무엇인가 | 그냥 변수 할당. 검사기가 "타입처럼 쓰이는 변수"로 짐작한다 | 타입 별칭이라는 것이 **분명한** 문장 |
| 자기 자신 가리키기 | 따옴표로 감싸야 한다(`"JSON"`) | 그대로 쓴다 |
| 타입 매개변수 | `TypeVar`를 따로 만들어야 한다 | `type Pair[T] = ...` |
| 옛 코드에서 | `Role: TypeAlias = Literal[...]`로 별칭임을 표시하기도 한다 | 3.12 이상 |

새 코드에서는 `type` 문을 쓴다. 라이브러리 코드에서 `X: TypeAlias = ...`나 그냥 `X = ...`로 만든 별칭을 만나면 같은 뜻으로 읽는다.

### 5.4.5 옛 표기 읽기 — `TypeVar`, `Generic`, `ParamSpec`

3.12의 `[T]` 문법 전에는 타입 매개변수를 **변수로 먼저 만들어** 썼다. 지금도 라이브러리 코드와 문서, AI가 만든 코드에서 자주 보인다. 읽을 수 있어야 한다.

```python
from collections.abc import Callable, Hashable, Sequence
from typing import Generic, ParamSpec, TypeVar

T = TypeVar("T")
H = TypeVar("H", bound=Hashable)
S = TypeVar("S", str, bytes)
P = ParamSpec("P")
R = TypeVar("R")


def first(items: Sequence[T]) -> T:
    return items[0]


class Box(Generic[T]):
    def __init__(self, value: T) -> None:
        self.value = value


def logged(func: Callable[P, R]) -> Callable[P, R]: ...
```

| 옛 표기 | 지금 표기 (3.12 이상) |
|---|---|
| `T = TypeVar("T")` + `def first(items: Sequence[T]) -> T` | `def first[T](items: Sequence[T]) -> T` |
| `TypeVar("H", bound=Hashable)` | `[H: Hashable]` |
| `TypeVar("S", str, bytes)` | `[S: (str, bytes)]` |
| `class Box(Generic[T]):` | `class Box[T]:` |
| `P = ParamSpec("P")` | `[**P]` |
| `Pair: TypeAlias = tuple[T, T]` | `type Pair[T] = tuple[T, T]` |

옛 표기에서 `TypeVar("T")`의 문자열 `"T"`는 변수 이름과 같아야 한다. 같은 `T`를 여러 함수가 함께 쓰지만, 함수마다 따로 정해진다. 새 표기는 타입 매개변수가 **그 함수나 클래스에만** 속한다는 것이 문법으로 드러나서 헷갈릴 일이 적다.

### 실습 5-4. 제네릭

**1. 제네릭 함수 만들기**

`ch05/generic_quiz.py`에 다음 함수를 제네릭으로 만들고 `mypy --strict`를 통과시킨다. 각 함수를 두 가지 타입으로 불러 `reveal_type()`으로 결과 타입을 확인한다.

- `last[T](items)` — 마지막 원소를 돌려준다. 비어 있으면 `None`을 돌려준다. 반환 타입은 무엇인가?
- `invert[K, V](d)` — 실습 5-3의 `invert()`를 어떤 키·값 타입이든 받도록 바꾼다. 값이 키가 되므로 `V`에는 어떤 조건이 필요한가?
- `chunked[T](items, size)` — `Sequence[T]`를 `size`개씩 잘라 `list[list[T]]`로 돌려준다. 3장의 `batched()`와 결과가 어떻게 다른가?

**2. 제네릭 클래스**

`ch05/page.py`의 `Page[T]`에 메서드 `map(self, func)`을 더한다. 각 항목에 `func`를 적용한 **새 `Page`**를 돌려주고, `next_cursor`는 그대로 둔다. `Page[str]`에 `len`을 적용하면 `Page[int]`가 되어야 한다. `map`의 타입 힌트에는 `T` 말고 타입 매개변수가 하나 더 필요하다. 메서드에도 `def map[U](self, func: ...) -> ...:`처럼 타입 매개변수를 붙일 수 있다.

**3. 옛 표기 옮기기**

다음 코드를 3.12의 새 표기로 바꾸고, 바꾸기 전과 후의 mypy 결과가 같은지 확인한다.

```python
from typing import Generic, TypeVar

K = TypeVar("K")
V = TypeVar("V")


class LRU(Generic[K, V]):
    def __init__(self, maxsize: int) -> None:
        self.maxsize = maxsize
        self.data: dict[K, V] = {}

    def get(self, key: K) -> V | None:
        return self.data.get(key)
```

## 5.5 설계에 쓰는 타입

지금까지는 "이 값은 문자열이다", "이것은 정수의 리스트다"처럼 **값의 종류**를 적었다. 이 절에서는 타입으로 **설계의 약속**을 적는다. "역할은 이 셋 중 하나다", "이 딕셔너리에는 이 키들이 있다", "LLM 클라이언트라면 이런 메서드가 있어야 한다." 약속을 타입으로 적어 두면 검사기가 그 약속을 지키는지 확인한다.

### 5.5.1 `Literal` — 정해진 값 중 하나

기초 과정 8.2.5에서 `Literal["system", "user", "assistant"]`를 읽었다. 이제 검사기가 이것을 어떻게 쓰는지 본다.

`ch05/roles.py`

```python
"""Literal — 정해진 값 중 하나."""

from typing import Literal, assert_never

type Role = Literal["system", "user", "assistant"]
type StopReason = Literal["end_turn", "max_tokens", "tool_use"]


def make_message(role: Role, content: str) -> dict[str, str]:
    return {"role": role, "content": content}


def explain(reason: StopReason) -> str:
    match reason:
        case "end_turn":
            return "답을 마쳤다"
        case "max_tokens":
            return "길이 제한에 걸려 잘렸다"
        case _:
            assert_never(reason)


make_message("user", "안녕")
make_message("admin", "안녕")
role = "user"
make_message(role, "안녕")
```

**26번 줄** — `role = "user"`로 만든 변수를 넘겼는데 거절되었다. mypy는 `role = "user"`의 `role`을 `str`로 추론한다. 변수이므로 나중에 다른 문자열이 들어갈 수도 있기 때문이다. `role: Role = "user"`처럼 변수에 타입을 적어 주면 통과한다. 직접 `"user"`를 넘긴 23번 줄은 처음부터 `Literal['user']`로 보므로 문제가 없다.

**20번 줄 — `assert_never()`로 빠뜨린 경우 찾기**

`explain()`의 `match` 문은 `"end_turn"`과 `"max_tokens"`만 처리했다. 마지막 `case _:`에 다다른 `reason`은 무엇일까? mypy는 5.2.3처럼 "남은 것"을 계산한다. 셋 중 둘을 처리했으므로 남은 것은 `Literal['tool_use']`다.

`assert_never(x)`는 "**여기에는 아무 값도 올 수 없다**"는 선언이다. 매개변수 타입이 `Never`, 즉 "어떤 값도 아닌 타입"이다. 모든 경우를 처리했다면 `case _:`에 남은 타입이 없으므로(`Never`) 통과한다. 하나라도 빠뜨리면 남은 타입이 `Never`가 아니므로 오류가 나고, **무엇을 빠뜨렸는지**(`'tool_use'`)까지 알려 준다.

`case "tool_use": return "도구를 불러 달라고 한다"`를 더하면 오류가 사라진다. 나중에 누군가 `StopReason`에 `"refusal"`을 더하면, 이 `match` 문이 다시 오류를 내서 처리할 곳을 알려 준다. 2.5.6에서 "아무 `case`에도 맞지 않으면" 어떻게 할지 고민했는데, 가능한 값이 `Literal`로 정해져 있다면 검사기에게 맡길 수 있다.

실행 중에 `assert_never()`에 정말 값이 오면 `AssertionError: Expected code to be unreachable, but got: 'tool_use'`가 난다. 타입 힌트를 무시하고 들어온 값도 조용히 지나가지 않는다.

### 5.5.2 `TypedDict` — 키가 정해진 딕셔너리

LLM API에 보내는 메시지, 받는 응답, 도구 호출 인자는 모두 딕셔너리다. 2장부터 `message["role"]`, `response.get("usage")`처럼 다뤘다. `TypedDict`는 이 딕셔너리의 **키와 값의 타입**을 적는다(기초 과정 8.2.5).

`ch05/messages.py`

```python
"""TypedDict — 키가 정해진 딕셔너리."""

import json
from typing import Literal, NotRequired, TypedDict

type Role = Literal["system", "user", "assistant"]


class Message(TypedDict):
    role: Role
    content: str
    name: NotRequired[str]


ok: Message = {"role": "user", "content": "안녕", "name": "민수"}
no_name: Message = {"role": "user", "content": "안녕"}
missing: Message = {"role": "user"}
extra: Message = {"role": "user", "content": "안녕", "id": "msg_01"}
wrong: Message = {"role": "user", "content": 1}

reveal_type(ok["content"])
reveal_type(ok.get("name"))
from_api: Message = json.loads('{"role": "admin", "content": 1}')
print(from_api)
```

그러면 `TypedDict`는 언제 쓸까? **내 코드가 만들어 바깥으로 보내는 딕셔너리**, 그리고 SDK가 딕셔너리로 받는 매개변수다. LLM SDK의 코드를 열어 보면 `messages: Iterable[MessageParam]`의 `MessageParam`이 `TypedDict`로 정의되어 있는 경우가 많다. 그래서 우리가 `{"role": "user", "content": "안녕"}`처럼 딕셔너리를 그대로 넘겨도, 키 이름을 틀리면 Pylance가 밑줄을 긋는다.

### 5.5.3 `Enum` — 이름 붙은 상수의 모음

모델 이름처럼 정해진 값 중 하나를 쓰는 또 다른 방법이 **열거형**(`Enum`)이다. 2.5.1에서 `http.HTTPStatus`를 열거형이라고 소개했다. 직접 만들어 본다.

`ch05/models.py`

```python
"""Enum — 이름 붙은 상수의 모음."""

from enum import StrEnum


class Model(StrEnum):
    SMALL = "small"
    LARGE = "large"


PRICE_PER_MTOK = {Model.SMALL: 0.25, Model.LARGE: 3.0}


def price_of(model: Model, tokens: int) -> float:
    """토큰 수에 따른 요금(달러)."""
    if model is Model.SMALL:
        return tokens / 1_000_000 * PRICE_PER_MTOK[model]
    reveal_type(model)
    return tokens / 1_000_000 * PRICE_PER_MTOK[model]


if __name__ == "__main__":
    print(price_of(Model.SMALL, 1000))
    print(price_of("small", 1000))
```

- `class Model(StrEnum):` — 클래스 안의 이름 하나하나가 **멤버**다. `Model.SMALL`은 값이 `"small"`인 `Model` 멤버다.
- `StrEnum`(3.11 이상)의 멤버는 **문자열이기도 하다.** 그래서 문자열과 비교되고, `json.dumps()`도 그대로 문자열로 쓴다. 정수 상태 코드를 담은 `HTTPStatus`는 같은 생각의 `IntEnum`이다. 그냥 `Enum`을 물려받으면 멤버는 문자열도 정수도 아니다.
- `if model is Model.SMALL:` 아래에서 남은 것은 `Literal[Model.LARGE]`다. 열거형 멤버도 `Literal`처럼 좁혀지고, `assert_never()`로 빠뜨린 멤버를 찾을 수도 있다.
- 24번 줄 — `Model` 자리에 문자열 `"small"`은 넘길 수 없다. 반드시 `Model.SMALL`을 쓴다.

확인했으면 `reveal_type(model)` 줄과 24번 줄을 지운다. 대화형 셸에서 열거형이 하는 일을 본다(`ch05` 폴더에서 연다).

```python
>>> from models import Model
>>> Model.SMALL

>>> Model.SMALL == "small", Model.SMALL.value
(True, 'small')
>>> list(Model)
[<Model.SMALL: 'small'>, <Model.LARGE: 'large'>]
>>> Model("small")
<Model.SMALL: 'small'>
>>> Model("medium")

  ...
ValueError: 'medium' is not a valid Model
```

`Model("small")`은 문자열에서 멤버를 찾는다. 설정 파일이나 명령행 인자로 받은 문자열을 바꿀 때 쓴다. 없는 값이면 **실행 중에** `ValueError`가 난다. `list(Model)`로 가능한 값을 모두 꺼낼 수 있어서, 명령행 도구의 도움말에 "쓸 수 있는 모델: small, large"를 보여 주기도 쉽다(8장).

**`Literal`과 `Enum` 중 무엇을 쓸까**

| | `Literal["small", "large"]` | `class Model(StrEnum)` |
|---|---|---|
| 실행 중의 값 | 그냥 문자열 | 열거형 멤버(`StrEnum`이면 문자열이기도 하다) |
| 쓰는 모양 | `"small"` | `Model.SMALL` |
| 가능한 값 모두 꺼내기 | `typing.get_args()`로 꺼낼 수는 있지만 번거롭다 | `list(Model)` |
| 값에 딸린 것 | 없다 | 메서드, 속성을 더할 수 있다 |
| 실행 중 검사 | 없다 | `Model("medium")`이 `ValueError` |
| 어울리는 곳 | JSON·API의 필드처럼 **문자열 그대로** 주고받는 값 | 프로그램 안에서 여러 곳이 함께 쓰는 **선택지 목록** |

LLM API의 `role`, `stop_reason`처럼 JSON에 문자열로 오가는 값은 `Literal`이 간편하다. 지원하는 모델 목록, 작업 상태처럼 코드 여러 곳에서 쓰고 목록을 꺼낼 일이 있는 값은 `Enum`이 낫다.

### 5.5.4 `Protocol` — "이런 메서드가 있으면 된다"

4장 실습 4-7에서 `FakeLLM` 클래스를 만들었다. `complete(prompt, *, model=...)` 메서드가 있는 가짜 클라이언트다. 요약 함수는 진짜 클라이언트든 가짜 클라이언트든 `complete()`만 부를 수 있으면 된다. 이 "**`complete()`를 부를 수 있는 것**"을 타입으로 어떻게 적을까?

상속으로 적을 수도 있다. `class LLMClient:`를 만들고 진짜와 가짜가 모두 물려받게 한다(기초 과정 5.3). 그런데 진짜 클라이언트가 **남이 만든 SDK의 클래스**라면 우리 클래스를 물려받게 할 수 없다. 테스트용 가짜를 만들 때마다 부모 클래스를 `import`해야 하는 것도 번거롭다.

파이썬은 원래 "**오리처럼 걷고 오리처럼 꽥꽥거리면 오리다**"라는 생각으로 동작한다. 이것을 **덕 타이핑**(duck typing)이라고 한다. `for` 문은 객체가 리스트를 물려받았는지 묻지 않고 `__iter__`가 있는지를 본다(3.1.5). `Protocol`은 이 덕 타이핑을 타입으로 적는다.

`ch05/llm_client.py`

```python
"""Protocol — 이런 메서드가 있으면 LLM 클라이언트다."""

from typing import Protocol


class LLMClient(Protocol):
    def complete(self, prompt: str, *, max_tokens: int = 1024) -> str: ...


class FakeLLM:
    """정해 둔 답을 돌려주고, 받은 프롬프트를 기록하는 가짜 클라이언트."""

    def __init__(self, answer: str = "가짜 요약") -> None:
        self.answer = answer
        self.prompts: list[str] = []

    def complete(self, prompt: str, *, max_tokens: int = 1024) -> str:
        self.prompts.append(prompt)
        return self.answer[:max_tokens]


class RealLLM:
    """실제 LLM API를 부르는 클라이언트. 본문은 "LLM API 활용"에서 SDK 호출로 채운다."""

    def __init__(self, model: str) -> None:
        self.model = model

    def complete(self, prompt: str, *, max_tokens: int = 1024) -> str:
        raise NotImplementedError("LLM API 활용에서 채운다")


class OldLLM:
    def complete(self, prompt: str) -> str:
        return prompt


class Chatbot:
    def ask(self, prompt: str) -> str:
        return prompt


def summarize(client: LLMClient, text: str) -> str:
    return client.complete(f"다음 글을 한 문장으로 요약하라.\n\n{text}", max_tokens=200)


if __name__ == "__main__":
    fake = FakeLLM()
    print(summarize(fake, "타입 힌트는 검사기를 위한 약속이다."))
    print(fake.prompts)
    summarize(OldLLM(), "글")
    summarize(Chatbot(), "글")
```

- `class LLMClient(Protocol):` — 메서드의 **모양만** 적는다. 본문은 `...`이다. 1.2.6의 스텁 파일처럼 "이런 이름, 이런 매개변수, 이런 반환 타입의 메서드"라는 약속이다.
- `FakeLLM`과 `RealLLM`은 `LLMClient`를 **물려받지 않았다.** 그래도 `complete()`의 모양이 같으므로 `LLMClient` 자리에 넘길 수 있다. 이것을 **구조적 타이핑**(structural typing)이라고 한다. 상속 관계가 아니라 **구조**(가진 메서드)로 판단한다.
- `OldLLM`은 `complete()`가 있지만 `max_tokens`를 받지 않는다. 메시지가 무엇이 기대되었고(Expected) 무엇이 왔는지(Got) 나란히 보여 준다. `summarize()`가 `max_tokens=200`을 넘기므로 실행 중에 `TypeError: OldLLM.complete() got an unexpected keyword argument 'max_tokens'`가 난다. 실제로 `python ch05/llm_client.py`로 실행하면 `FakeLLM`으로 부른 두 줄을 출력한 뒤 이 오류로 멈춘다. mypy는 실행하기 전에 알려 주었다.
- `Chatbot`은 메서드 이름부터 다르다.

`summarize()`는 이제 **어떤 클라이언트가 올지 모른 채** 쓸 수 있다. 개발과 테스트에서는 `FakeLLM`을 넘기고, 실제 서비스에서는 `RealLLM`을 넘긴다. 실습 4-7에서 `sleep`을 바꿔 끼운 의존성 주입을 객체 단위로 하는 것이다. `FakeLLM`은 받은 프롬프트를 `prompts`에 기록하므로, "요약 함수가 프롬프트를 제대로 만들었는가"를 API를 부르지 않고 확인할 수 있다. 6장에서 바로 이것으로 테스트를 쓴다. 9장의 종합 실습은 "가짜 클라이언트를 같은 `Protocol`을 따르는 실제 클라이언트로 바꿔 끼운다"로 마무리한다.

| | 상속(`class Fake(LLMClient)`) | `Protocol` |
|---|---|---|
| 판단 기준 | 부모 클래스를 물려받았는가 (이름으로) | 필요한 메서드가 있는가 (구조로) |
| 남이 만든 클래스 | 물려받게 할 수 없다 | 메서드 모양만 맞으면 된다 |
| 공통 코드 물려주기 | 된다 | 하지 않는다. 약속만 적는다 |
| 어울리는 곳 | 공통 동작을 나눠 쓰는 클래스 계층 | "이것을 부를 수 있으면 된다"는 매개변수 |

`Iterable`, `Sized`, `Hashable`도 사실 `Protocol`이다. `__iter__`가 있으면 `Iterable`, `__len__`이 있으면 `Sized`다. 3.1.5에서 만든 이터레이터 클래스가 `list`를 물려받지 않고도 `for` 문에 쓰였던 것과 같은 원리다.

> **`isinstance()`로 `Protocol`을 확인하려면**
> `Protocol`은 검사기를 위한 것이라 기본적으로 `isinstance(x, LLMClient)`를 쓸 수 없다(`TypeError`). 클래스 위에 `@typing.runtime_checkable`을 붙이면 쓸 수 있지만, 실행 중에는 **메서드 이름이 있는지만** 확인한다. `OldLLM`도 `complete`라는 이름은 있으므로 `True`가 된다. 매개변수까지 확인하는 것은 검사기의 몫이다.

### 5.5.5 특별한 메서드 한눈에 보기 — 파이썬 데이터 모델

`Protocol`은 "어떤 클래스든 이 메서드가 있으면 된다"는 약속이다. 파이썬 문법도 같은 약속 위에서 동작한다. `for` 문은 `__iter__`를 찾고(3.1.5), `with` 문은 `__enter__`와 `__exit__`가 있는지만 본다(4.6.2). 1.3.4에서 "이런 특별한 메서드가 이 과정에서 계속 나온다"고 했는데, 지금까지 만난 것을 표 하나로 모아 보자. 파이썬 공식 문서는 "어떤 문법이 어떤 메서드를 부르는가"를 정한 이 약속 전체를 **데이터 모델**(data model)이라고 부른다.

| 이렇게 쓰면 | 파이썬이 부르는 메서드 | 만난 곳 | 대응하는 타입 |
|---|---|---|---|
| `Account(...)` (객체 만들기) | `__init__` | 기초 과정 5.1.4 | |
| `print(x)`, `str(x)`, `f"{x!s}"` | `__str__` | 기초 과정 5.2.3 | |
| 대화형 셸의 `x`, `repr(x)`, `f"{x!r}"` | `__repr__` | 기초 과정 5.2.4 | |
| `f"{x}"`, `f"{x:형식}"`, `format(x, 형식)` | `__format__`. 형식이 비어 있으면 기본 구현이 `__str__`을 부른다 | 3.4.1의 `f"{t:%Y-%m-%d...}"` | |
| `a == b` | `__eq__` | 기초 과정 5.4.1, 4.4.7 | |
| `hash(x)`, 집합의 요소, 딕셔너리의 키 | `__hash__` | 4.4.7 | `Hashable` |
| `len(x)` | `__len__` | 1.3.4 | `Sized` |
| `for v in x`, `iter(x)` | `__iter__`, 없으면 `__getitem__`(예전 방식) | 3.1.5, 이 절 | `Iterable` |
| `next(it)` | `__next__` | 3.1.5 | `Iterator` |
| `v in x` | `__contains__` → `__iter__` → `__getitem__` 순서 | 이 절 | `Container` |
| `x[i]`, `x[key]` | `__getitem__` | 이 절 | `Sequence`, `Mapping`의 일부 |
| `if x:`, `bool(x)` | `__bool__`, 없으면 `__len__` | 이 절 | |
| `x(...)` | `__call__` | 실습 4-1, 4.4.2 | `Callable` |
| `with x as v:` | `__enter__`, `__exit__` | 4.6.2 | `contextlib.AbstractContextManager` |
| `a \| b` | `__or__` | 2.4.3, 이 절 | |

"대응하는 타입"은 `AbstractContextManager`(`contextlib`에 있다)만 빼면 모두 `collections.abc`에 있는 이름이다. 5.3에서 쓴 `Iterable`, `Collection`, `Sequence`, `Callable`이 여기서 왔다. 이 이름들이 모두 같은 방식으로 판단하지는 않는다.

- **메서드가 있는지로 판단하는 것** — `Hashable`, `Sized`, `Iterable`, `Iterator`, `Container`, `Collection`, `Callable`, `AbstractContextManager`. `Protocol`처럼 물려받지 않아도 메서드만 있으면 mypy가 그 자리에 넘기는 것을 허락하고, `isinstance()`도 `True`다.
- **물려받아야 인정되는 것** — `Sequence`, `Mapping`. `__getitem__`과 `__len__`을 만들어도 물려받지 않으면 mypy는 거절하고 `isinstance()`는 `False`다. 두 메서드는 딕셔너리에도 있으므로, 메서드 이름만으로는 정수 인덱스로 읽는 시퀀스인지 키로 읽는 매핑인지 구별할 수 없기 때문이다. 내 클래스를 `Sequence`로 쓰려면 `class Pages(Sequence[str]):`처럼 물려받는다. 그러면 `__getitem__`과 `__len__`만 만들어도 `__iter__`, `__contains__`, `index()`, `count()`를 물려받는다. (`Sequence.register(Pages)`로 `isinstance()`만 `True`로 만드는 방법도 있지만 mypy는 이것을 보지 않는다.)

7장에서 `async for`(`__aiter__`, `__anext__`)와 `async with`(`__aenter__`, `__aexit__`) 두 줄이 이 표에 더해진다.

표에서 "이 절"로 적은 메서드를 직접 만들어 보자. 대화 기록을 담는 클래스를 리스트처럼 쓸 수 있게 한다.

`ch05/history.py`

```python
"""특별한 메서드 — 대화 기록을 리스트처럼 쓰기."""

from collections.abc import Collection, Iterator

type Message = dict[str, str]


class History:
    def __init__(self) -> None:
        self._messages: list[Message] = []

    def add(self, role: str, content: str) -> None:
        self._messages.append({"role": role, "content": content})

    def __len__(self) -> int:
        return len(self._messages)

    def __getitem__(self, index: int) -> Message:
        return self._messages[index]

    def __iter__(self) -> Iterator[Message]:
        return iter(self._messages)

    def __contains__(self, text: object) -> bool:
        return any(m["content"] == text for m in self._messages)

    def __repr__(self) -> str:
        return f"History({len(self)}개)"


def count_roles(messages: Collection[Message]) -> dict[str, int]:
    counts: dict[str, int] = {}
    for m in messages:
        counts[m["role"]] = counts.get(m["role"], 0) + 1
    return counts


if __name__ == "__main__":
    h = History()
    print(h, bool(h))
    h.add("user", "안녕")
    h.add("assistant", "안녕하세요")
    print(h, bool(h), len(h))
    print(h[-1])
    print("안녕" in h, "잘 가" in h)
    print([m["role"] for m in h])
    print(count_roles(h))
```

- **`bool(h)`** — `History`에는 `__bool__`이 없다. 그러면 파이썬은 `__len__`을 불러 0이면 거짓으로 본다. 빈 기록은 거짓이고, 메시지가 하나라도 있으면 참이다. `__bool__`도 `__len__`도 없는 객체는 언제나 참이다. 1장 실습 1-3의 q5에서 `bool(boxes[1])`이 예측과 달랐다면 이것이 이유다. 5.2.2에서 "없음"은 `if x:`가 아니라 `is None`으로 확인하라고 한 까닭도 여기 있다. `history: History | None`을 받아 `if history:`로 확인하면 `None`일 때뿐 아니라 **비어 있을 때도** 걸러진다.
- **`h[-1]`** — `__getitem__`은 받은 인덱스를 안쪽 리스트에 그대로 넘기므로 음수 인덱스도 된다. 매개변수를 `index: int`로 적었으므로 `h[1:]` 같은 슬라이스는 mypy가 거절한다. 슬라이스까지 받으려면 `slice` 객체도 따로 처리해야 한다.
- **`"안녕" in h`** — `in`이 무엇을 뜻할지는 `__contains__`를 만드는 사람이 정한다. 여기서는 "이 내용의 메시지가 있는가"로 정했다. `__contains__`가 없으면 파이썬은 `__iter__`로 요소를 하나씩 꺼내 `==`로 비교한다. 그러면 메시지 딕셔너리와 문자열 `"안녕"`을 비교하게 되어 언제나 `False`다.
- **`for m in h`** — `__iter__`는 안쪽 리스트의 이터레이터를 돌려준다. 3.1.5에서 이터러블과 이터레이터를 나눴는데, 여기서는 이터레이터 쪽을 리스트에 맡겼다. 부를 때마다 새 이터레이터가 나오므로 몇 번이든 반복할 수 있다.
- **`count_roles(h)`** — `History`는 아무 클래스도 물려받지 않았지만 `__len__`, `__iter__`, `__contains__`를 모두 가졌으므로 `Collection`이다. 5.3.2에서 "`len()`까지 되는 `Collection`이면 충분하다"고 한 그 자리에 그대로 넘길 수 있다. 5.5.4의 `FakeLLM`이 `LLMClient` 자리에 넘겨진 것과 같은 원리다.

> **`__iter__`가 없어도 `for`가 도는 경우**
> `__iter__`가 없고 `__getitem__`만 있으면, 파이썬은 `x[0]`, `x[1]`, `x[2]`, ...를 차례로 꺼내다가 `IndexError`가 나면 멈춘다. `in`도 `__contains__`와 `__iter__`가 모두 없으면 이 방식으로 하나씩 꺼내 비교한다. `__iter__`가 생기기 전부터 있던 예전 방식이다. 실행은 되지만 mypy는 `has no attribute "__iter__" (not iterable)`라고 거절하고, `isinstance(x, Iterable)`도 `False`다. 반복할 수 있는 객체를 만들 때는 `__iter__`를 만든다. `History`에 `__getitem__`이 있는데도 `__iter__`를 따로 만든 이유다.
>
> f-string도 비슷하게 한 단계를 거친다. `f"{x}"`는 `__str__`을 바로 부르지 않고 `__format__`을 부르며, 기본 `__format__`이 형식이 비어 있으면 `__str__`에 맡긴다. 그래서 보통은 `str(x)`와 결과가 같다. 날짜처럼 `__format__`을 따로 만든 객체는 `f"{t:%Y-%m-%d}"`처럼 형식을 받을 수 있다(3.4.1).

**연산자도 메서드다**

`a | b`라고 쓰면 파이썬은 `a.__or__(b)`를 부른다. 그래서 같은 `|`라도 왼쪽 객체에 따라 뜻이 다르다. 딕셔너리에서는 병합(2.4.3), 집합에서는 합집합(기초 과정 3.5.4), 타입에서는 `int | None` 같은 합집합 타입(5.2.1)이다. LLM 라이브러리에서는 LangChain이 이 메서드로 처리 단계를 잇는다.

```python
chain = prompt | model | parser
answer = chain.invoke({"question": "..."})
```

같은 구조를 작게 만들어 보자.

`ch05/pipe.py`

```python
"""연산자도 메서드다 — |로 단계를 잇는다."""

from collections.abc import Callable


class Step:
    def __init__(self, func: Callable[[str], str]) -> None:
        self.func = func

    def __or__(self, other: "Step") -> "Step":
        return Step(lambda text: other.func(self.func(text)))

    def __call__(self, text: str) -> str:
        return self.func(text)


strip = Step(str.strip)
upper = Step(str.upper)
exclaim = Step(lambda s: s + "!")

if __name__ == "__main__":
    chain = strip | upper | exclaim
    print(chain("  hello "))
    print(type(chain).__name__)
```

```
python ch05/pipe.py
```

```
HELLO!
Step
```

- `strip | upper`는 `strip.__or__(upper)`다. 두 단계를 차례로 실행하는 **새 `Step`**을 돌려준다. 결과도 `Step`이므로 다시 `| exclaim`을 이을 수 있다.
- 체인을 만드는 동안에는 아무것도 실행되지 않는다. `chain("  hello ")`로 부를 때(`__call__`) 비로소 세 단계가 차례로 실행된다. 3.4의 제너레이터 파이프라인이 연결만 해 두었다가 값을 꺼낼 때 실행된 것과 닮았다.
- LangChain의 `prompt | model | parser`도 같다. 각 단계 객체의 `__or__`가 단계를 이은 새 객체를 돌려주고, `invoke()`를 부를 때 실행된다. LangChain 코드에서는 `{"context": retriever, "question": ...} | prompt`처럼 왼쪽이 딕셔너리인 것도 보게 된다. 딕셔너리의 `__or__`는 상대가 딕셔너리가 아니면 `NotImplemented`("나는 이 상대를 모른다")를 돌려주고, 그러면 파이썬은 오른쪽 객체의 `__ror__`를 부른다. LangChain의 단계 객체에는 `__ror__`가 있어서 이것이 된다. 2.4.3의 `{"a": 1} | [("b", 2)]`가 `TypeError`였던 것은 리스트에 `__ror__`가 없기 때문이다. 4.4.7에서 `__eq__`가 `NotImplemented`를 돌려준 것과 같은 구조다.

**모르는 특별한 메서드를 만났을 때**

- 라이브러리 코드를 읽다가 표에 없는 `__이름__`을 만나면 공식 문서 The Python Language Reference의 **"Data model"** 장(https://docs.python.org/3/reference/datamodel.html)에서 이름을 찾는다. 그 메서드를 어떤 문법이 부르는지 적혀 있다. `__add__`(`+`), `__lt__`(`<`, `sorted()`), `__getattr__`(없는 속성을 읽을 때) 같은 메서드도 모두 여기에 있다.
- 특별한 메서드는 **직접 부르지 않는다.** `h.__len__()`이 아니라 `len(h)`로 쓴다. 내장 함수와 문법은 `__bool__`이 없을 때 `__len__`을 쓰는 것처럼 메서드 하나를 부르는 것보다 많은 일을 한다.
- 쓸 문법에 해당하는 메서드만 만든다. `History`에 `__add__`를 만들어 `h1 + h2`가 되게 할 수도 있지만, `h1.extend(h2)`처럼 이름 있는 메서드가 더 잘 읽힌다면 그쪽을 쓴다. 연산자는 그 뜻이 누구에게나 뻔할 때만 만든다.

## 5.6 실행 중 검증과 Pydantic

### 5.6.1 검사기가 볼 수 없는 값

5.5.2의 23번 줄에서 본 것처럼, 정적 검사기는 **바깥에서 들어오는 데이터**를 확인하지 못한다. LLM 서비스를 만들면 이런 데이터가 사방에서 들어온다.

- 사용자가 웹으로 보낸 요청 본문(JSON)
- LLM이 돌려준 답. "JSON으로 답하라"고 해도 필드를 빠뜨리거나, 숫자를 문자열로 쓰거나, 앞뒤에 설명을 붙인다
- 설정 파일, 환경 변수, 다른 API의 응답

이런 값은 **실행 중에** 확인해야 한다. 기초 과정의 가계부는 `__post_init__`에서 `isinstance()`로 필드를 하나씩 검사했다(1.1.2). 필드가 열 개이고 중첩된 리스트까지 있다면 검사 코드가 본 코드보다 길어진다. **Pydantic**은 타입 힌트를 읽어서 이 검사를 대신 해 주는 라이브러리다. 타입 힌트를 한 번 적으면, 검사기는 그것으로 코드를 검사하고 Pydantic은 그것으로 데이터를 검사한다.

| | 정적 검사(mypy) | 실행 중 검증(Pydantic) |
|---|---|---|
| 언제 | 실행하기 **전에** | 실행하는 **중에**, 데이터가 들어올 때 |
| 무엇을 | 코드에 적힌 값의 흐름 | 바깥에서 들어온 실제 데이터 |
| 틀리면 | 검사 오류(프로그램은 그대로) | `ValidationError` 예외 |
| 비용 | 없다(실행에 영향 없음) | 데이터마다 검사하는 시간 |

### 5.6.2 첫 모델 — `BaseModel`

`ch05/question.py`

```python
"""Pydantic 모델 — 타입 힌트로 데이터를 검증한다."""

from pydantic import BaseModel


class Question(BaseModel):
    text: str
    max_tokens: int = 512
    tags: list[str] = []


if __name__ == "__main__":
    q = Question(text="타입 힌트가 뭐야?")
    print(q)
    print(repr(q))
    print(q.text, q.max_tokens, q.tags)
    print(Question(text="질문", max_tokens="256"))
```

```
python ch05/question.py
```

```
타입 힌트가 뭐야? 512 []

```

- `class Question(BaseModel):` — `BaseModel`을 물려받고, 필드를 **데이터 클래스처럼** 타입 힌트로 적는다(기초 과정 5.4.3). 기본값도 같은 방법으로 준다. `@dataclass`를 붙이지 않는다.
- `tags: list[str] = []` — 데이터 클래스에서는 리스트를 기본값으로 쓰면 안 되고 `field(default_factory=list)`를 써야 했다(기초 과정 5.4.5). Pydantic은 객체를 만들 때마다 기본값을 **복사**하므로 `[]`를 그대로 써도 된다.
- `max_tokens="256"` — 문자열 `"256"`이 정수 `256`으로 **바뀌었다.** Pydantic은 기본적으로 "뜻이 분명하면 바꿔 준다." 웹 요청이나 환경 변수에서는 숫자도 문자열로 오는 일이 많기 때문이다. 2장 실습 2-4에서 `temperature`가 문자열 `'0.2'`로 남았던 문제를 Pydantic이 해결한다. 다만 이것은 **바깥에서 온 데이터**를 위한 너그러움이다. 코드에 직접 `max_tokens="256"`이라고 쓴 17번 줄은 mypy가 `Argument "max_tokens" to "Question" has incompatible type "str"; expected "int"`라고 지적한다(5.6.6).

뜻이 분명하지 않은 값은 바꾸지 않고 거절한다. 대화형 셸에서 확인한다(`ch05` 폴더에서 연다).

`"많이"`는 정수로 읽을 수 없고, `3.5`를 정수로 바꾸면 값이 달라진다. Pydantic은 이런 값을 몰래 고치지 않고 `ValidationError`를 일으킨다. 그리고 **틀린 곳을 모두** 한꺼번에 알려 준다. 두 번째 예에서는 `text`가 빠진 것과 `max_tokens`가 틀린 것을 함께 보고했다. 오류 메시지 읽는 법은 5.6.5에서 정리한다.

### 5.6.3 `Field` — 검증 규칙과 설명

타입만으로는 부족한 규칙이 있다. "검색어는 빈 문자열이면 안 된다", "`top_k`는 1에서 10 사이", "`temperature`는 0 이상 2 이하." 이런 규칙은 `Field()`로 적는다.

`ch05/tool_input.py`

```python
"""Field — 검증 규칙과 설명."""

from pydantic import BaseModel, ConfigDict, Field


class SearchInput(BaseModel):
    """사내 문서 검색 도구의 입력."""

    model_config = ConfigDict(extra="forbid")

    query: str = Field(min_length=1, description="검색어")
    top_k: int = Field(default=3, ge=1, le=10, description="돌려줄 문단 수")
```

| `Field()`의 인자 | 뜻 | 쓰는 타입 |
|---|---|---|
| `default=값` | 기본값. 없으면 꼭 있어야 하는 필드 | 모두 |
| `default_factory=함수` | 객체를 만들 때마다 함수를 불러 기본값을 만든다 | 리스트, 딕셔너리, 시각 등 |
| `ge`, `gt`, `le`, `lt` | 이상(≥), 초과(>), 이하(≤), 미만(<) | 숫자 |
| `min_length`, `max_length` | 길이의 최소·최대 | 문자열, 리스트 |
| `pattern=r"..."` | 정규 표현식에 맞아야 한다 | 문자열 |
| `description="..."` | 사람과 LLM이 읽을 설명. 검증에는 쓰이지 않는다 | 모두 |

`model_config = ConfigDict(extra="forbid")`는 모델 전체의 설정이다. Pydantic은 기본적으로 **모르는 필드를 조용히 버린다.** API 응답처럼 우리가 쓰지 않는 필드가 섞여 오는 데이터를 받을 때 편하다. 반대로 LLM이 도구를 부를 때 보낸 인자처럼 **모르는 필드가 오면 실수**인 경우에는 `extra="forbid"`로 거절하게 한다.

### 5.6.4 딕셔너리와 JSON에서 모델 만들기

바깥에서 들어온 데이터는 딕셔너리나 JSON 문자열이다. 두 가지 클래스 메서드로 모델을 만든다. 4.4.4에서 만든 대체 생성자 `from_dict()`와 같은 역할이다.

```python
>>> from question import Question
>>> data = {"id": "q_01", "text": "제네릭이 뭐야?", "max_tokens": 100}
>>> Question.model_validate(data)
Question(text='제네릭이 뭐야?', max_tokens=100, tags=[])
>>> raw = '{"text": "Protocol은?", "tags": ["5장", "타입"]}'
>>> Question.model_validate_json(raw)
Question(text='Protocol은?', max_tokens=512, tags=['5장', '타입'])
```

- **`model_validate(딕셔너리)`** — 딕셔너리를 검증해서 모델을 만든다. 4.4.4의 `ChatMessage.from_dict()`처럼 모르는 키(`id`)는 버린다. `Question(**data)`로 만들어도 되지만, 데이터를 검증한다는 뜻이 이름에 드러나는 `model_validate()`를 쓴다.
- **`model_validate_json(문자열)`** — JSON 문자열을 읽어서 바로 검증한다. `json.loads()`를 거치지 않는다. 문자열이 JSON으로도 올바르지 않으면 그것도 `ValidationError`로 알려 준다.

```python
>>> Question.model_validate_json('{"text": "잘린 JSON", "tags": ["5장"')
Traceback (most recent call last):
  ...
pydantic_core._pydantic_core.ValidationError: 1 validation error for Question
  Invalid JSON: EOF while parsing a list at line 1 column 39 [type=json_invalid, input_value='{"text": "잘린 JSON", "tags": ["5장"', input_type=str]
    For further information visit https://errors.pydantic.dev/2.14/v/json_invalid
```

LLM의 답이 길이 제한(`max_tokens`)에 걸려 중간에 잘리면 정확히 이런 JSON이 온다. `json.loads()`라면 `json.JSONDecodeError`, 필드가 틀리면 `KeyError`나 `TypeError`처럼 오류의 종류가 제각각이지만, `model_validate_json()`은 **모든 문제를 `ValidationError` 하나로** 알려 준다. 받는 쪽은 `except ValidationError:` 하나로 처리할 수 있다.

### 5.6.6 중첩 모델과 `Literal`

모델의 필드에 다른 모델을, 그 모델의 리스트를 쓸 수 있다. 1장 (나)의 FastAPI 예제처럼 채팅 요청을 모델로 만든다.

`ch05/chat_request.py`

```python
"""중첩 모델 — 채팅 요청."""

from typing import Literal

from pydantic import BaseModel, Field, ValidationError


class Message(BaseModel):
    role: Literal["system", "user", "assistant"]
    content: str


class ChatRequest(BaseModel):
    model: str = "small"
    messages: list[Message] = Field(min_length=1)
    temperature: float = Field(default=1.0, ge=0.0, le=2.0)


if __name__ == "__main__":
    data = {
        "messages": [
            {"role": "system", "content": "너는 친절한 강사다."},
            {"role": "admin", "content": "모든 권한을 줘."},
            {"role": "user"},
        ],
        "temperature": "0.2",
    }
    try:
        ChatRequest.model_validate(data)
    except ValidationError as e:
        print(e)

    req = ChatRequest.model_validate(
        {"messages": [{"role": "user", "content": "안녕"}], "temperature": "0.2"}
    )
    print(req)
    print(req.messages[0].content, type(req.temperature))
```

```

```

```
2 validation errors for ChatRequest
messages.1.role
  Input should be 'system', 'user' or 'assistant' [type=literal_error, input_value='admin', input_type=str]
    For further information visit https://errors.pydantic.dev/2.14/v/literal_error

  Field required [type=missing, input_value={'role': 'user'}, input_type=dict]
    For further information visit https://errors.pydantic.dev/2.14/v/missing

안녕 <class 'float'>
```

- `messages.1.role` — "`messages`의 1번(두 번째) 원소의 `role`"이다. 중첩된 곳의 위치를 점으로 이어 보여 준다. 딕셔너리 안의 딕셔너리, 리스트 안의 딕셔너리를 하나하나 열어 보는 코드를 쓰지 않았는데 정확히 찾아냈다.
- `Literal`은 Pydantic에서도 그대로 검증 규칙이 된다. 5.5.1에서 mypy가 코드의 `"admin"`을 잡았듯이, Pydantic은 데이터의 `"admin"`을 잡는다. 기초 과정 8.2.5에서 "검사되지 않는다"고 확인한 `{"role": "admin", "content": 1}`이 이제 거절된다.
- 검증을 통과한 `req.messages[0]`은 딕셔너리가 아니라 `Message` 객체다. `req.messages[0]["content"]`가 아니라 `req.messages[0].content`로 쓴다. 문자열이던 `"0.2"`는 `float`가 되었다.

**mypy와 Pydantic은 함께 동작한다**

Pydantic 모델은 mypy도 이해한다. 필드의 타입 힌트가 생성자의 매개변수 타입이 된다.

```python
Message(role="admin", content="안녕")  # mypy: Argument "role" to "Message" has incompatible type "Literal['admin']"; ...
Message(role="user", content=1)       # mypy: Argument "content" to "Message" has incompatible type "int"; expected "str"
req.messages[0].content.upper()       # mypy: str로 안다. 자동 완성도 된다
```

**코드에 적은 값은 mypy가, 바깥에서 온 값은 Pydantic이** 검사한다. 일단 `model_validate()`를 통과한 객체는 타입 힌트대로라는 것이 보장되므로, 그 뒤의 코드는 mypy의 검사를 믿고 쓸 수 있다. `json.loads()`로 받은 `Any`가 프로그램 곳곳으로 퍼지는 것을 **입구에서** 막는 셈이다.

> **필드에 다시 넣는 값은 검증하지 않는다**
> Pydantic은 기본적으로 **객체를 만들 때만** 검증한다. `req.temperature = 5`처럼 나중에 필드에 넣는 값은 검증하지 않으므로 `le=2.0` 규칙을 어긴 객체가 생긴다. 넣을 때도 검증하려면 `model_config = ConfigDict(validate_assignment=True)`를 준다. 또는 `ConfigDict(frozen=True)`로 아예 바꿀 수 없게 만든다. 기초 과정 5.4.6의 `frozen=True` 데이터 클래스와 같은 생각이다.

### 5.6.7 JSON 스키마 만들기 — `model_json_schema()`

4.5.3에서 `describe()`로 함수의 타입 힌트를 읽어 JSON 스키마를 손으로 만들었다. `list[str]`은 표현하지 못했고, 매개변수마다의 설명도 없었다. Pydantic 모델은 자기 자신의 JSON 스키마를 만들 수 있다.

```python
>>> import json
>>> from tool_input import SearchInput
>>> print(json.dumps(SearchInput.model_json_schema(), ensure_ascii=False, indent=2))
{
  "additionalProperties": false,
  "description": "사내 문서 검색 도구의 입력.",
  "properties": {
    "query": {
      "description": "검색어",
      "minLength": 1,
      "title": "Query",
      "type": "string"
    },
    "top_k": {
      "default": 3,
      "description": "돌려줄 문단 수",
      "maximum": 10,
      "minimum": 1,
      "title": "Top K",
      "type": "integer"
    }
  },
  "required": [
    "query"
  ],
  "title": "SearchInput",
  "type": "object"
}
```

`describe()`가 만든 것과 비교한다.

- 필드마다 `description`이 들어갔다. 클래스의 독스트링은 모델 전체의 `description`이 되었다.
- `ge=1, le=10`은 `minimum`, `maximum`으로, `min_length=1`은 `minLength`로 바뀌었다. **같은 규칙이 Pydantic에게는 검증 규칙이, LLM에게는 설명이 된다.**
- 기본값이 없는 `query`만 `required`에 들어갔다. `describe()`가 `inspect.Parameter.empty`로 하던 일이다.
- `extra="forbid"`는 `"additionalProperties": false`가 되었다. "이 밖의 속성은 안 된다."

**LLM과 연결하기**

이 스키마는 이 과정 뒤의 세 곳에서 쓰인다.

1. **도구 정의** — 4.5.3의 도구 설명에서 `input_schema`에 이 스키마를 넣는다. LLM이 도구를 부르며 보낸 인자는 `SearchInput.model_validate(tool_call["input"])`로 검증한다. 스키마를 만드는 것과 인자를 검증하는 것이 **같은 모델 하나**에서 나오므로 둘이 어긋날 일이 없다.

   ```python
   tool = {
       "name": "search_docs",
       "description": "사내 문서에서 관련 문단을 찾는다.",
       "input_schema": SearchInput.model_json_schema(),
   }
   ```

   MCP 서버의 `@mcp.tool()`과 LangChain의 `@tool`은 함수의 타입 힌트로 Pydantic 모델을 **자동으로** 만들고, 그 모델로 스키마를 만든다. 4.5.3에서 "실제 SDK는 Pydantic으로 정확한 JSON 스키마를 만든다"고 한 것이 이것이다.

2. **구조화 출력** — LLM에게 "이 스키마에 맞는 JSON으로만 답하라"고 요청하고, 받은 답을 `model_validate_json()`으로 검증한다. 요즘 LLM API는 스키마를 요청에 함께 보내면 그 모양을 지키도록 답을 만들어 주는 기능이 있고, SDK에 Pydantic 모델 클래스를 그대로 넘기면 검증된 모델 객체를 돌려주는 메서드도 있다. 이름과 사용법은 SDK와 버전마다 다르므로 "LLM API 활용"에서 실제 SDK로 본다. 어느 쪽이든 원리는 같다. **모델 → 스키마 → LLM → JSON → 모델.** 실습 5-7에서 이 흐름을 가짜 클라이언트로 만든다.

3. **FastAPI 요청 본문** — 1장 (나)의 `async def chat(req: ChatRequest) -> ChatResponse:`를 다시 읽는다. FastAPI는 매개변수의 타입 힌트 `ChatRequest`가 Pydantic 모델인 것을 보고, 들어온 요청 본문을 `model_validate_json()`처럼 검증해서 넘겨준다. 검증에 실패하면 함수를 부르지도 않고 **422 오류**와 함께 5.6.5의 `errors()`와 같은 모양의 오류 목록을 돌려준다. 반환 타입 `-> ChatResponse`로는 응답의 모양을 검증하고, 두 모델의 스키마로 API 문서를 자동으로 만든다. 타입 힌트 두 개가 검증, 변환, 문서를 모두 해 주는 것이다. "LLM 서비스 배포"에서 직접 만든다.

### 5.6.8 데이터 클래스, `TypedDict`, Pydantic 중 무엇을 쓸까

세 가지 모두 "필드의 이름과 타입이 정해진 데이터"를 적는다. 고르는 기준은 **데이터가 어디서 오는가**다.

| | 데이터 클래스 | `TypedDict` | Pydantic 모델 |
|---|---|---|---|
| 실행 중의 모양 | 객체(`m.role`) | 딕셔너리(`m["role"]`) | 객체(`m.role`) |
| 실행 중 검증 | 없다(`__post_init__`에 직접 쓴다) | 없다 | **있다**. 형 변환도 한다 |
| 정적 검사 | 된다 | 된다 | 된다 |
| JSON 오가기 | `asdict()` + `json` | 이미 딕셔너리 | `model_validate_json()`, `model_dump_json()` |
| JSON 스키마 | 없다 | 없다 | `model_json_schema()` |
| 설치 | 표준 라이브러리 | 표준 라이브러리 | 외부 패키지 |
| 속도 | 빠르다 | 가장 빠르다(그냥 딕셔너리) | 검증하는 만큼 느리다 |
| 어울리는 곳 | **프로그램 안에서** 만들고 쓰는 데이터 | 딕셔너리를 주고받는 라이브러리 API, 내가 만들어 **보내는** JSON | **바깥에서 들어오는** 데이터: 요청 본문, LLM 출력, 설정 파일, 도구 인자 |

하나의 프로그램에서 셋을 모두 쓰는 것이 자연스럽다. 바깥에서 들어오는 **입구**에서 Pydantic으로 검증하고, 안에서는 검증된 객체나 데이터 클래스를 쓰고, SDK에 넘길 때는 `TypedDict` 모양의 딕셔너리를 만든다. 경계마다 한 번씩만 검증하고, 안에서는 mypy의 검사를 믿는다.

> **모든 곳에 Pydantic을 쓰지 않는다**
> Pydantic 모델은 만들 때마다 검증하므로, 이미 검증된 데이터를 함수 사이에서 주고받을 때마다 모델을 새로 만들면 같은 검사를 반복하게 된다. 문서 조각 수십만 개를 처리하는 3장의 파이프라인 같은 곳에서는 차이가 커진다. "**경계에서 한 번**"을 기억한다.

## 실습 5-7. 종합 — 타입으로 지키는 리뷰 분석기

이 장의 내용을 모두 써서 "LLM에게 리뷰 분석을 시키고, 답을 검증하고, 틀리면 다시 시키는" 프로그램을 만든다. LLM의 답은 Pydantic 모델로 검증하고, 검증에 실패하면 **오류 내용을 프롬프트에 넣어** 다시 요청한다. LLM 클라이언트는 `Protocol`로 정의하고, 정해 둔 답을 차례로 돌려주는 가짜 클라이언트를 쓴다. 가짜 클라이언트는 실제 LLM이 자주 저지르는 실수를 흉내 낸다. 정해진 값이 아닌 감정(`"부정"`), 숫자 대신 글자(`"보통"`), 너무 긴 목록, JSON 앞뒤에 붙인 설명과 코드 블록, 아예 JSON이 아닌 답이다.

3장·4장의 종합 실습처럼 **함수의 이름, 타입 힌트, 독스트링이 먼저 주어지고, 본문을 채운다.** 이번 실습의 완료 기준에는 실행 결과와 함께 **`mypy --strict` 통과**가 들어간다.

`ch05/review_analyzer.py`

```python
"""타입으로 지키는 리뷰 분석기 — 5장 종합 실습."""

import json
from collections.abc import Callable, Hashable, Iterable, Mapping, Sequence
from typing import Literal, Protocol

from pydantic import BaseModel, Field, ValidationError

type Sentiment = Literal["positive", "negative", "neutral"]


class Analysis(BaseModel):
    """LLM이 돌려주어야 하는 리뷰 분석 결과."""

    sentiment: Sentiment
    score: int = Field(ge=1, le=5, description="1(매우 나쁨)부터 5(매우 좋음)까지")
    keywords: list[str] = Field(default_factory=list, max_length=3, description="핵심어 3개 이하")


class LLMClient(Protocol):
    def complete(self, prompt: str) -> str: ...


class ScriptedLLM:
    """리뷰마다 정해 둔 응답을 차례로 돌려주는 가짜 LLM 클라이언트."""

    def __init__(self, script: Mapping[str, Sequence[str]]) -> None:
        self.script = {review: list(answers) for review, answers in script.items()}
        self.calls = 0

    def complete(self, prompt: str) -> str:
        self.calls += 1
        for review, answers in self.script.items():
            if review in prompt and answers:
                return answers.pop(0)
        return "죄송합니다. 무슨 말씀인지 모르겠어요."


def make_script() -> dict[str, list[str]]:
    return {
        "배송이 빨라서 좋아요": [
            '{"sentiment": "positive", "score": 5, "keywords": ["배송", "속도"]}',
        ],
        "포장이 엉망이고 제품도 깨져서 왔어요": [
            '{"sentiment": "부정", "score": 1, "keywords": ["포장", "파손"]}',
            '{"sentiment": "negative", "score": 1, "keywords": ["포장", "파손"]}',
        ],
        "가격 대비 괜찮아요. 다시 살게요": [
            '분석 결과입니다.\n```json\n{"sentiment": "positive", "score": 4, "keywords": ["가격"]}\n```',
        ],
        "그냥 그래요": [
            '{"sentiment": "neutral", "score": "보통"}',
            '{"sentiment": "neutral", "score": 3, "keywords": ["보통", "무난", "평범", "그럭저럭"]}',
        ],
        "환불은 어떻게 하나요?": [],
    }


def build_prompt(review: str, error: str | None = None) -> str:
    """리뷰를 분석해 Analysis의 JSON 스키마에 맞는 JSON만 답하라는 프롬프트를 만든다.

    error가 주어지면 "직전 응답의 문제: {error}"라는 줄을 끝에 더한다.
    """


def extract_json(text: str) -> str:
    """응답에서 첫 '{'부터 마지막 '}'까지를 잘라 돌려준다. 중괄호가 없으면 text를 그대로 돌려준다."""


def describe_errors(error: ValidationError) -> str:
    """검증 오류를 "위치(종류), 위치(종류)" 모양의 한 줄로 만든다.

    위치는 loc의 원소를 점으로 이은 것이다. loc가 비어 있으면 "(전체)"라고 쓴다.
    """


def analyze(client: LLMClient, review: str, *, retries: int = 1) -> Analysis | None:
    """client에게 리뷰 분석을 요청하고 검증된 Analysis를 돌려준다.

    응답이 검증을 통과하지 못하면 오류를 프롬프트에 넣어 retries번까지 다시 요청한다.
    다시 요청할 때마다 "  [다시 요청] 오류: {오류 설명}"을, 끝내 실패하면
    "  [포기] 오류: {오류 설명}"을 출력하고 None을 돌려준다.
    """


def count_by[T, K: Hashable](items: Iterable[T], key: Callable[[T], K]) -> dict[K, int]:
    """items를 key(item)의 값마다 세어 {값: 개수} 딕셔너리로 돌려준다."""


def report(results: Mapping[str, Analysis | None]) -> None:
    """감정별 개수, 평균 점수, 실패한 리뷰를 출력한다.

    성공한 리뷰가 없으면 평균 점수 자리에 "-"를 출력한다.
    """


def main() -> None:
    client = ScriptedLLM(make_script())
    results: dict[str, Analysis | None] = {}
    for review in make_script():
        print(f"리뷰: {review}")
        result = analyze(client, review)
        if result is not None:
            print(f"  → {result.sentiment}, {result.score}점, 핵심어: {', '.join(result.keywords)}")
        results[review] = result
    report(results)
    print(f"LLM 호출 {client.calls}번")


if __name__ == "__main__":
    main()
```

- **`Analysis`** — LLM이 지켜야 할 답의 모양이다. 이 모델 하나가 세 가지 일을 한다. 프롬프트에 넣을 **JSON 스키마**를 만들고(5.6.7), LLM의 답을 **검증**하고(5.6.4), 검증된 뒤에는 mypy가 `result.score`가 정수라는 것을 **안다**(5.6.6).
- **`LLMClient`와 `ScriptedLLM`** — `ScriptedLLM`은 `LLMClient`를 물려받지 않았지만 `complete()`의 모양이 같으므로 `analyze()`에 넘길 수 있다(5.5.4). 프롬프트에 들어 있는 리뷰를 찾아 그 리뷰에 정해 둔 답을 하나씩 꺼낸다. 정해 둔 답이 없거나 다 쓰면 엉뚱한 말을 한다. `calls`로 호출 횟수를 센다. 4장 실습 4-7의 `FakeLLM`과 같은 생각이다.
- `main()`은 이미 채워져 있다. **고치지 않는다.** `analyze()`가 `Analysis | None`을 돌려주므로 `main()`이 `if result is not None:`으로 좁힌 뒤에 `result.sentiment`를 쓰는 것에 주의한다(5.2.2).

**쓸 것**

| 함수 | 이 장에서 쓸 것 |
|---|---|
| `build_prompt()` | `Analysis.model_json_schema()`(5.6.7), `json.dumps(..., ensure_ascii=False)`, `None` 확인(5.2.2) |
| `extract_json()` | `str.find()`, `str.rfind()`, 슬라이스. 없으면 `-1`을 돌려준다는 것 |
| `describe_errors()` | `error.errors()`와 `err["loc"]`, `err["type"]`(5.6.5), `str.join()` |
| `analyze()` | `model_validate_json()`(5.6.4), `except ValidationError`, 4.3.2의 재시도 반복 |
| `count_by()` | 타입 매개변수와 상한(5.4.1, 5.4.2), `Callable`(5.3.3), `dict.get(키, 0)` |
| `report()` | 컴프리헨션과 `is not None`으로 좁히기(5.2.2), `count_by()` |

**힌트**

- `build_prompt()`는 리뷰 문장을 **그대로** 프롬프트에 넣어야 한다. `ScriptedLLM`이 프롬프트에서 리뷰를 찾아 답을 고르기 때문이다. 실제 LLM에게도 "무엇을 분석할지"와 "어떤 모양으로 답할지"(스키마), 그리고 다시 요청할 때는 "무엇이 틀렸는지"를 함께 알려 준다.
- `extract_json()`은 "분석 결과입니다.\n```json\n{...}\n```"처럼 JSON 앞뒤에 붙은 말을 떼어 낸다. 실제 LLM도 자주 이렇게 답한다. 중괄호가 없는 답은 그대로 돌려주면 `model_validate_json()`이 `json_invalid`로 알려 준다.
- `describe_errors()` — JSON 자체가 틀린 오류(`json_invalid`)는 어느 필드의 문제도 아니므로 `loc`가 빈 튜플이다. 그래서 "(전체)"가 필요하다. `loc`의 원소에는 리스트 번호(정수)도 있을 수 있으므로 `str()`로 바꿔서 잇는다.
- `analyze()`는 `for attempt in range(retries + 1):`로 반복한다. 반복문 안에서 `return Analysis.model_validate_json(...)`을 `try`로 감싸면, 성공하면 바로 돌아가고 실패하면 `except`로 간다. 마지막 시도인지에 따라 출력이 다르다. 반복문을 빠져나왔다면 모두 실패한 것이다.
- `analyze()`에서 오류 설명을 담을 변수는 처음에 `None`이다. 첫 요청에는 오류가 없기 때문이다. mypy가 그 변수의 타입을 `None`으로만 추론하지 않도록 `error: str | None = None`처럼 적는다.
- `count_by()`의 본문에는 타입 힌트가 필요한 빈 딕셔너리가 하나 있다(5.1.4의 `var-annotated`). 함수 안에서도 `T`와 `K`를 쓸 수 있다. `K`에 `Hashable` 상한을 붙인 이유는 `K`가 딕셔너리의 키가 되기 때문이다. 상한이 없어도 mypy는 통과하지만, `count_by(items, lambda a: a.keywords)`처럼 리스트를 키로 쓰는 호출이 검사를 통과한 뒤 실행 중에 `unhashable type` 오류를 낸다. 상한을 붙이면 이 호출을 검사 단계에서 잡는다(5.4.2의 `dedupe()`와 같다).
- `report()`에서 `[a for a in results.values() if a is not None]`의 타입은 무엇인가? `reveal_type()`으로 확인한다. 컴프리헨션의 `if`도 타입을 좁힌다.

## 정리

| 항목 | 핵심 |
|---|---|
| 정적 타입 검사 | 실행하지 않고 코드만 읽어 타입 힌트를 검사한다. 프로그램을 바꾸지 않고, 바깥에서 들어온 데이터는 모른다 |
| mypy | `mypy 파일` / `mypy 폴더`. `파일:줄: error: 내용 [오류 코드]`. 위에서부터 하나씩 고친다 |
| `reveal_type()` | 검사기가 추론한 타입을 묻는다. 실행하려면 `from typing import reveal_type`. 확인 뒤 지운다 |
| Pylance | `"python.analysis.typeCheckingMode": "standard"`를 작업 공간 설정에. 이 과정의 기준은 mypy |
| 점진적 타이핑 | 힌트가 없는 함수는 검사하지 않는다. `--check-untyped-defs` → `--strict`로 넓힌다. 새 코드는 `--strict` |
| `Any`와 `object` | `Any`는 검사를 끈다. `object`는 무엇이든 받지만 좁혀야 쓸 수 있다. `json.loads()`는 `Any` |
| `# type: ignore[코드]` | 그 줄의 그 오류만 숨긴다. 코드를 꼭 적는다 |
| 타입 좁히기 | `if x is None: return/raise`, `isinstance()`, `match`, `assert`. 검사기는 "남은 것"까지 계산한다 |
| `if x:`와 `is None` | `if x:`는 `0`, `""`도 거른다. "없음"은 `is None`으로 |
| `cast()` | 실행 중에 아무것도 하지 않는다. 검사기를 믿게 할 뿐. 최후의 수단 |
| 불변성 | `list[int]`는 `list[float]`가 아니다. 바꾸지 않을 컬렉션은 `Sequence`/`Mapping`/`Iterable`로 받는다 |
| 넓게 받고 구체적으로 돌려준다 | 매개변수는 하는 일만큼(`Iterable` < `Collection` < `Sequence`), 반환값은 실제 타입(`list`, `dict`) |
| `Callable` | `Callable[[인자...], 반환]`. `Callable[..., T]`는 인자를 검사하지 않는다. `collections.abc`에서 가져온다 |
| 제너레이터의 타입 | 보통 `Iterator[Y]`. `Generator[Y, S, R]`은 `send`·`return` 값까지. `@contextmanager` 함수는 `Iterator[...]` |
| `ParamSpec` | `def deco[**P, R](func: Callable[P, R]) -> Callable[P, R]`. 원래 함수의 모양을 지키는 데코레이터 |
| 제네릭 | `def first[T](items: Sequence[T]) -> T`, `class Page[T]:`. `[T: 상한]`, `[T: (A, B)]` |
| `type` 별칭 | `type JSON = dict[str, JSON] \| ...`. 매개변수, 자기 참조 가능. 옛 표기는 `X = ...`, `X: TypeAlias = ...` |
| 옛 표기 | `TypeVar("T")`, `Generic[T]`, `ParamSpec("P")` → `[T]`, `class C[T]`, `[**P]` |
| `Literal` | 정해진 값 중 하나. `assert_never()`로 빠뜨린 경우를 찾는다. 변수에 담으면 `str`로 추론되니 타입을 적는다 |
| `TypedDict` | 키가 정해진 딕셔너리. `NotRequired`. 실행 중에는 그냥 딕셔너리이고 검증하지 않는다 |
| `Enum` | 이름 붙은 상수. `StrEnum`은 문자열이기도 하다. `list(Model)`, `Model("small")` |
| `Protocol` | 메서드의 모양만 적는다. 물려받지 않아도 모양이 맞으면 된다(구조적 타이핑). 가짜 객체를 바꿔 끼운다 |
| 특별한 메서드 | 문법이 부르는 메서드(데이터 모델). `if x:`는 `__bool__`, 없으면 `__len__`. `in`은 `__contains__` → `__iter__` → `__getitem__`. `for`는 `__iter__`, 없으면 `__getitem__`(mypy는 인정하지 않는다). f-string은 `__format__`. 직접 부르지 않는다 |
| `collections.abc`의 타입 | `Iterable`, `Sized`, `Collection` 등은 메서드가 있으면 된다. `Sequence`, `Mapping`은 물려받아야 한다. `AbstractContextManager`는 `contextlib`에 있다 |
| 연산자 메서드 | `a \| b`는 `a.__or__(b)`. 모르는 상대면 `NotImplemented` → 오른쪽의 `__ror__`. LangChain의 `prompt \| model \| parser` |
| Pydantic `BaseModel` | 타입 힌트로 실행 중에 검증한다. 뜻이 분명하면 형 변환, 아니면 `ValidationError`. 틀린 곳을 모두 알려 준다 |
| `Field` | `ge`/`le`, `min_length`/`max_length`, `default_factory`, `description`. `ConfigDict(extra="forbid")` |
| 만들기와 내보내기 | `model_validate(dict)`, `model_validate_json(str)`, `model_dump()`, `model_dump_json()` |
| 검증 오류 | 위치(`loc`, 점으로 이음)·내용(`msg`)·종류(`type`)·입력값. `e.errors()`로 꺼낸다 |
| `model_json_schema()` | 같은 모델이 검증 규칙(Pydantic)이자 설명(LLM)이 된다. 도구 정의, 구조화 출력, FastAPI |
| 무엇을 쓸까 | 안에서 쓰는 데이터는 데이터 클래스, 주고받는 딕셔너리는 `TypedDict`, **바깥에서 오는 데이터는 Pydantic**. 경계에서 한 번 검증한다 |
