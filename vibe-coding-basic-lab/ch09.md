# 9장. 최종 프로젝트 개발

> 이 장에서는 지금까지 배운 것을 모두 모아 나만의 프로젝트를 만든다. 아이디어를 한 장짜리 기획서로 정리하고, 범위를 알맞게 줄이고, AI와 함께 기능 하나씩 단계적으로 구현한다.

## 이 장에서 배울 것

- 아이디어 중 첫 프로젝트로 알맞은 것을 고르고, **범위를 줄이는** 방법을 익힌다.
- 한 장짜리 기획서를 작성하고, Claude Code와 함께 다듬는다.
- **계획 → 구현 → 확인 → 커밋**의 개발 흐름을 처음부터 끝까지 혼자 진행한다.
- 긴 작업을 여러 대화에 걸쳐 이어 가는 방법(진행 상황 기록, 대화 요약, 지난 대화 이어 하기)을 익힌다.

## 1. 아이디어에서 프로젝트로

### 1-1. 좋은 첫 프로젝트의 조건

| 조건 | 이유 |
|---|---|
| **내 문제**를 해결한다 | 필요한 사람이 나이므로 무엇을 만들지 분명하고, 끝까지 만들 동기가 생긴다. |
| **작다** | 정해진 시간 안에 "동작하는 것"을 손에 쥘 수 있다. |
| **배운 것으로** 만들 수 있다 | 파일 저장(4장), 엑셀(6장), API(7장), 웹 앱(8장)을 조합한다. |
| **결과가 눈에 보인다** | 화면이 있으면 발표하고 다른 사람에게 보여 주기 좋다. |

> 💡 10장에서는 프로젝트를 인터넷에 배포한다. 8장에서 배운 **Streamlit 웹 앱**으로 만들면 배포까지 자연스럽게 이어진다.

### 1-2. 범위 줄이기

비전공자 프로젝트가 실패하는 가장 흔한 원인은 **범위가 너무 큰 것**이다. 처음부터 완벽한 앱을 만들려 하지 말고, **핵심 기능 하나가 동작하는 가장 작은 버전**을 먼저 만든다. 이런 버전을 **MVP**(Minimum Viable Product, 최소 기능 제품)라고 한다.

| 처음 생각한 버전 | 줄인 버전 (MVP) |
|---|---|
| 회원 가입해서 친구들과 맛집을 공유하고, 지도에 표시하고, 별점과 사진을 올리고, 추천도 받는 앱 | 맛집 이름·주소·한 줄 평을 기록하고 목록으로 보는 웹 앱 |
| 은행 계좌와 연결해서 자동으로 지출을 모으고 AI가 소비 습관을 분석해 주는 가계부 | 카드 내역 엑셀을 올리면 카테고리별 지출 차트를 보여 주는 웹 앱 |
| 동아리 회원 관리, 회비, 일정, 출석, 공지를 모두 하는 앱 | 출석을 체크하고 회원별 출석률을 보여 주는 웹 앱 |

줄인 버전이 완성되면 그다음에 기능을 하나씩 더하면 된다. **동작하는 작은 것**이 **동작하지 않는 큰 것**보다 언제나 낫다.

### 1-3. 범위를 키우는 위험 신호

아이디어에 다음 기능이 들어 있으면 범위가 커질 가능성이 크다. 처음 버전에서는 빼거나 단순하게 바꾼다.

| 위험 신호 | 단순하게 바꾸기 |
|---|---|
| 회원 가입, 로그인 | 나 혼자 쓰는 앱으로 시작한다. |
| 여러 사람이 동시에 쓰고 데이터 공유 | 내 컴퓨터의 파일에 저장한다(4장). |
| 결제, 은행·카드사 연동 | 엑셀 파일을 내려받아 올리는 방식으로 바꾼다(6장). |
| 스마트폰 앱 | 스마트폰 브라우저에서도 열리는 웹 앱으로 만든다(8장). |
| 실시간 알림, 자동 실행 | 실행하면 결과를 보여 주는 방식으로 바꾼다. |
| 구하기 어려운 데이터 | 가짜 데이터로 먼저 만든다(6장). |

### 1-4. 세 아이디어 중 하나 고르기

8장 과제로 생각해 온 아이디어 3개를 다음 기준으로 비교한다. 항목마다 1~3점을 매기고 합계가 가장 높은 것을 고른다.

| 기준 | 질문 | 아이디어 A | 아이디어 B | 아이디어 C |
|---|---|:---:|:---:|:---:|
| 필요성 | 내가 정말 쓸 것인가? | | | |
| 크기 | 3시간 안에 핵심 기능이 동작할 수 있는가? | | | |
| 기술 | 배운 것으로 만들 수 있는가? | | | |
| 데이터 | 필요한 데이터를 구할 수 있는가? (가짜 데이터 포함) | | | |
| **합계** | | | | |

## 2. 한 장 기획서 작성

### 2-1. 기획서 양식

```markdown
# 프로젝트 이름
## 누구의 어떤 문제를 해결하나요?
## 핵심 기능 (꼭 필요한 것 3개 이하)
## 있으면 좋은 기능 (시간이 남으면)
## 사용하는 데이터 / 외부 서비스
## 완성 기준 (무엇이 되면 "완성"인가?)
```

- **핵심 기능**은 이것이 없으면 프로젝트가 의미 없는 기능이다. 3개 이하로, 가능하면 하나로 줄인다.
- **있으면 좋은 기능**은 핵심 기능을 다 만든 뒤에 시간이 남으면 한다. 생각난 기능을 버리지 않고 여기에 적어 두면 마음이 편하다.
- **완성 기준**은 "무엇을 하면 무엇이 보인다"처럼 **직접 확인할 수 있게** 쓴다. "잘 동작한다"는 기준이 아니다.

### 2-2. 작성 예시: 가계부 분석기

```markdown
# 가계부 분석기

## 누구의 어떤 문제를 해결하나요?
매달 카드 내역을 보면서 어디에 돈을 많이 썼는지 손으로 계산하는 나.
카드사 앱의 분류가 내 기준과 달라서 매번 엑셀로 다시 정리하느라 30분씩 걸린다.

## 핵심 기능 (꼭 필요한 것 3개 이하)
1. 카드 내역 엑셀 파일을 올리면 표로 보여 준다.
2. 가맹점 이름으로 카테고리(식비, 카페, 교통, 쇼핑, 기타)를 자동 분류한다.
3. 카테고리별 지출 합계를 막대 차트로 보여 준다.

## 있으면 좋은 기능 (시간이 남으면)
- 월별 지출 비교 차트
- 화면에서 분류 규칙(가맹점 → 카테고리) 추가하기
- 카테고리별 예산을 넘으면 경고

## 사용하는 데이터 / 외부 서비스
- 가짜 카드 내역 엑셀 (날짜, 가맹점, 금액) 100건
- 실제 카드 내역은 Claude Code에게 읽히지 않고, 완성 후 내 컴퓨터에서만 실행한다.
- Streamlit, pandas

## 완성 기준 (무엇이 되면 "완성"인가?)
- 가짜 카드 내역 100건을 올리면 카테고리별 합계 표와 막대 차트가 나온다.
- 카테고리별 합계를 모두 더한 값이 전체 지출 합계와 같다.
- "기타"로 분류된 내역이 전체의 20% 이하다.
```

> 💡 완성 기준의 두 번째 줄은 6장에서 배운 **전체 합계 비교** 검증이다. 검증 방법을 미리 완성 기준에 넣어 두면 "다 만들었다"를 확실하게 판단할 수 있다.

### 2-3. Claude Code와 기획서 다듬기

기획서 초안을 쓴 뒤 Claude Code에게 검토를 요청한다.

```
아래는 내 최종 프로젝트 기획서야. 코딩 초보자가 Claude Code와 함께 3시간 안에 핵심 기능을 완성할 수 있는 크기인지 평가해 줘. 너무 크다면 무엇을 빼거나 줄이면 좋을지, 완성 기준이 직접 확인할 수 있게 쓰였는지도 알려 줘. 코드는 아직 만들지 마.

(기획서 붙여 넣기)
```

아이디어가 아직 막연하다면 AI에게 **질문을 받는** 방식도 좋다.

```
가계부 앱을 만들고 싶은데 아직 생각이 정리되지 않았어. 한 장 기획서를 쓸 수 있도록 나에게 질문을 하나씩 해 줘. 내 대답을 다 듣고 나서 기획서 초안을 만들어 줘.
```

> ⚠️ AI가 제안하는 기능을 모두 받아들이면 범위가 다시 커진다. AI의 의견은 참고하되, **무엇을 만들지는 내가 정한다.**

## 3. AI와 함께 개발하는 흐름

### 3-1. 개발 사이클

지금까지 장마다 조금씩 연습한 방법을 하나의 흐름으로 정리하면 다음과 같다.

```
  ┌─────────────────────────────────────────────────┐
  │                                                 │
  ▼                                                 │
① 계획 ──→ ② 구현 ──→ ③ 확인 ──→ ④ 커밋 ──→ 다음 기능
(Plan 모드)  (기능 하나)  (실행·검증)  (세이브 포인트)
   3장         2장         6장         5장
```

| 단계 | 하는 일 | 핵심 요청 |
|---|---|---|
| ① 계획 | 이번 기능을 어떻게 만들지 계획을 보고 승인한다. | Plan 모드에서 "○○ 기능을 만들 계획을 세워 줘" |
| ② 구현 | 기능 **하나만** 만든다. | "계획대로 만들어 줘" |
| ③ 확인 | 직접 실행해서 동작을 확인하고, 숫자가 있다면 검증한다. | (두 번째 터미널에서 실행) |
| ④ 커밋 | 동작하면 바로 커밋한다. | "잘 동작해. 커밋해 줘." |

이 사이클을 **핵심 기능 개수만큼** 반복한다. 한 바퀴가 짧을수록 문제가 생겼을 때 원인을 찾기 쉽다.

### 3-2. 핵심 기능을 단계로 쪼개기

핵심 기능 하나도 한 번에 요청하기에는 클 수 있다. 2장에서 배운 대로 **실행해서 확인할 수 있는 단위**로 쪼갠다.

| 핵심 기능 | 쪼갠 단계 |
|---|---|
| 카드 내역을 올리면 표로 보여 준다 | ① 가짜 카드 내역 엑셀 만들기 → ② 파일 올리기 화면 → ③ 올린 파일을 표로 보여 주기 |
| 카테고리 자동 분류 | ① 분류 규칙(가맹점 키워드 → 카테고리) 만들기 → ② 표에 카테고리 열 추가 → ③ "기타" 비율 확인 |
| 카테고리별 지출 차트 | ① 카테고리별 합계 표 → ② 합계 검증 → ③ 막대 차트 |

### 3-3. 막혔을 때 대처법

| 상황 | 대처법 | 배운 장 |
|---|---|---|
| 오류가 난다 | 오류 메시지 전체를 붙여 넣고 "먼저 설명하고 고쳐 줘" | 3장 |
| AI가 같은 실수를 반복한다 | `/rewind`로 되돌리고 다르게 설명한다. 또는 대화를 비우고 처음부터 요청한다. | 3장 |
| 고칠수록 더 엉망이 된다 | "마지막 커밋 상태로 되돌려 줘"로 세이브 포인트로 돌아간다. | 5장 |
| 결과 숫자가 이상하다 | 직접 계산·전체 합계·개수로 검증하고, 계산 기준을 설명하게 한다. | 6장 |
| 화면이 마음에 들지 않는다 | 스크린샷을 붙여 넣고 한두 가지씩 고친다. | 8장 |
| 기능이 너무 어렵다 | "더 쉬운 방법이 있는지 알려 줘"라고 묻거나, 기능을 "있으면 좋은 기능"으로 미룬다. | 9장 |
| 모르는 기술이 나온다 | "이게 무엇인지 쉽게 설명해 줘", 문서 주소를 주고 읽힌다. | 3장, 7장 |

> 💡 30분 넘게 같은 문제에서 맴돌고 있다면 **범위를 줄일 때**라는 신호다. 막힌 기능을 "있으면 좋은 기능"으로 옮기고 다음 핵심 기능으로 넘어간다.

## 4. Claude Code 기능 익히기: 긴 작업 이어 가기

### 4-1. PLAN.md로 진행 상황 기록하기

프로젝트는 하루에 끝나지 않는다. 다음에 이어서 작업할 때 Claude Code가 지금까지의 상황을 알 수 있도록, 기획서를 프로젝트 폴더에 **`PLAN.md`** 로 저장하고 진행 상황을 체크리스트로 기록한다.

```markdown
## 진행 상황
- [x] 가짜 카드 내역 엑셀 만들기
- [x] 파일 올리기와 표 보기
- [ ] 카테고리 자동 분류   ← 지금 하는 중
- [ ] 카테고리별 합계와 검증
- [ ] 카테고리별 막대 차트
```

CLAUDE.md에 다음 규칙을 넣어 두면 Claude Code가 알아서 PLAN.md를 참고하고 갱신한다.

```markdown
- 작업을 시작할 때 PLAN.md를 먼저 읽어.
- 기능을 완성하고 커밋하면 PLAN.md의 진행 상황 체크리스트를 갱신해.
```

### 4-2. 대화 비우기와 대화 요약하기

대화가 길어지면 Claude Code의 응답이 느려지고, 앞의 내용을 헷갈리기도 한다.

| 명령 | 하는 일 | 언제 쓰나 |
|---|---|---|
| `/clear` | 대화를 모두 비운다. | 기능 하나를 완성하고 커밋한 뒤 다음 기능을 시작할 때 |
| `/compact` | 지금까지의 대화를 짧게 요약해서 남기고 나머지는 비운다. | 한 기능을 만드는 중인데 대화가 너무 길어졌을 때 |

> 💡 **기능 하나 = 대화 하나**를 기본으로 한다. 기능을 완성하고 커밋한 뒤 `/clear`로 대화를 비워도, CLAUDE.md와 PLAN.md 덕분에 Claude Code는 프로젝트의 상황을 다시 파악할 수 있다.

### 4-3. 지난 대화 이어 하기

Claude Code를 종료했다가 다시 시작할 때, 지난 대화를 이어서 할 수 있다.

| 명령 | 하는 일 |
|---|---|
| `claude --continue` | 이 폴더에서 **가장 최근에** 나눈 대화를 이어서 시작한다. |
| `claude --resume` | 지난 대화 목록을 보여 주고, **골라서** 이어서 시작한다. |

새 대화로 시작해도 괜찮다. 이때는 이렇게 요청하면 된다.

```
PLAN.md를 읽고 지금까지 어디까지 했는지, 다음에 할 일이 무엇인지 알려 줘.
```

### 4-4. 터미널(CLI)과 VS Code 확장의 사용법 비교

| 기능 | 터미널(CLI) | VS Code 확장 |
|---|---|---|
| 대화 비우기 | `/clear` | **새 대화** 버튼 |
| 대화 요약 | `/compact` | `/compact` 입력. 동작하지 않으면 새 대화로 시작하고 PLAN.md를 읽게 한다. |
| 가장 최근 대화 이어 하기 | `claude --continue` | 패널의 이전 대화 기록에서 선택 |
| 대화 골라서 이어 하기 | `claude --resume` | 패널의 이전 대화 기록에서 선택 |

## 5. 실습: 최종 프로젝트 개발

이 장의 실습은 정해진 예제가 아니라 **내 프로젝트**로 진행한다. 아래의 요청 예시는 가계부 분석기를 기준으로 썼으니, 내 프로젝트에 맞게 바꿔 쓴다.

### 5-1. 아이디어 발표와 범위 조정 (30분)

1. 1-4의 표로 8장 과제의 아이디어 3개 중 하나를 고른다.
2. 고른 아이디어를 **1분** 안에 발표한다: 누구의 어떤 문제인지, 핵심 기능이 무엇인지.
3. 듣는 사람은 다음 질문 중 하나 이상을 해 준다.
   - "3시간 안에 핵심 기능이 동작할 수 있을까?"
   - "핵심 기능 중 하나만 남긴다면 무엇인가?"
   - "데이터는 어디서 구하는가?"
   - "1-3의 위험 신호에 해당하는 기능이 있는가?"
4. 받은 질문과 의견을 바탕으로 범위를 줄인다.

### 5-2. 한 장 기획서 작성 (20분)

2-1의 양식으로 기획서를 쓰고, 2-3의 방법으로 Claude Code에게 검토를 받는다. 검토 결과를 반영해 기획서를 확정한다.

### 5-3. 프로젝트 준비

```bash
cd ~/vibe-coding
mkdir 프로젝트폴더이름     # 예: budget
cd 프로젝트폴더이름
code .
```

> 💡 폴더 이름은 영어 소문자와 `-`로 짓는다(예: `budget`, `book-log`). 10장에서 GitHub 저장소 이름과 배포 주소에도 쓰인다.

Claude Code를 시작하고 프로젝트를 준비한다.

```
uv init --no-package로 이 폴더를 uv 프로젝트로 만들고, streamlit과 pandas 패키지를 설치해 줘. 그리고 아래 기획서를 PLAN.md로 저장하고, 맨 아래에 핵심 기능을 단계로 쪼갠 "진행 상황" 체크리스트를 만들어 줘.

(확정한 기획서 붙여 넣기)
```

`/init`으로 CLAUDE.md를 만들고 규칙을 추가한다. 지금까지 장마다 쓴 규칙을 모으면 다음과 같다. 내 프로젝트에 필요 없는 것은 빼고, 필요한 것은 더한다.

```
CLAUDE.md에 아래 규칙을 추가해 줘.
- 나는 코딩 초보자야. 설명은 쉬운 한국어로 해 줘.
- 코드에는 한국어 주석을 달아 줘.
- 파이썬 실행은 uv run을, 패키지 설치는 uv add를 사용해.
- 새 패키지를 설치하기 전에 왜 필요한지 먼저 알려 줘.
- 사용자 입력을 받는 프로그램과 Streamlit 앱은 네가 실행하지 말고, 내가 실행할 명령만 알려 줘.
- API 키 같은 비밀 정보는 코드에 쓰지 말고 .env에서 읽어 와. .env 내용은 읽지 마.
- 작업을 시작할 때 PLAN.md를 먼저 읽어.
- 기능을 완성하고 커밋하면 PLAN.md의 진행 상황 체크리스트를 갱신해.
- 커밋 메시지는 한국어로 써 줘.
```

`.gitignore`를 점검하고 첫 커밋을 만든다.

```
.gitignore에 .env가 없으면 추가해 줘. 그다음 지금 상태를 "프로젝트 준비: uv, CLAUDE.md, PLAN.md"로 커밋해 줘.
```

### 5-4. 개발: 기능마다 사이클 돌리기 (110분)

PLAN.md의 진행 상황 체크리스트를 위에서부터 하나씩 3-1의 사이클로 진행한다.

**① 계획** — Plan 모드로 전환하고 요청한다.

```
PLAN.md의 진행 상황에서 다음 할 일을 만들 계획을 세워 줘.
```

계획을 읽고, 이해되지 않는 부분은 질문하고, 범위가 커 보이면 줄여 달라고 한 뒤 승인한다.

**② 구현** — 계획을 승인하면 Claude Code가 만든다. 한 번에 다음 기능까지 만들려고 하면 멈추고 "이번 단계만 만들어 줘"라고 말한다.

**③ 확인** — 두 번째 터미널에서 직접 실행해서 확인한다. 숫자가 나오는 기능이라면 6장의 방법으로 검증한다.

```
(가계부 예시) 카테고리별 합계를 모두 더한 값과 전체 지출 합계가 같은지 확인해 줘. "기타"로 분류된 내역이 몇 건인지도 알려 줘.
```

**④ 커밋** — 동작하면 커밋하고, 대화를 비운다.

```
잘 동작해. 커밋하고 PLAN.md 진행 상황을 갱신해 줘.
```

그다음 `/clear`(VS Code 확장은 **새 대화**)로 대화를 비우고 ①로 돌아간다.

> 💡 핵심 기능을 모두 완성하기 전에는 "있으면 좋은 기능"에 손대지 않는다. 화면 꾸미기도 핵심 기능이 다 동작한 뒤에 한다.

### 5-5. 중간 점검 (20분)

개발 시간 중간에 손을 멈추고, 다음 세 가지를 짧게 공유한다.

| 항목 | 예 |
|---|---|
| 된 것 | 카드 내역 올리기, 카테고리 자동 분류까지 커밋했다. |
| 막힌 것 | "기타"로 분류되는 내역이 35%나 된다. |
| 다음 할 일 | 분류 규칙에 가맹점 키워드를 더 추가하고, 카테고리별 차트를 만든다. |

다른 사람의 막힌 점에 대해 3-3의 대처법 중 도움이 될 만한 것을 함께 찾아본다. 남은 시간 안에 핵심 기능을 모두 끝내기 어려워 보이면 **지금 범위를 줄인다.**

### 5-6. 마무리

개발 시간이 끝나면 다음을 정리한다.

```
지금까지 한 작업을 커밋하고 PLAN.md 진행 상황을 갱신해 줘. 그리고 GitHub에 공개 저장소로 올려 줘. 올리기 전에 어떤 파일이 올라가는지 목록을 먼저 보여 줘.
```

- GitHub 저장소에 `.env`나 개인 데이터 파일이 올라가지 않았는지 확인한다.
- PLAN.md에 남은 할 일이 정리되어 있는지 확인한다. 다음 작업은 여기서부터 시작한다.

## 6. 문제가 생겼을 때

| 증상 | 해결 방법 |
|---|---|
| 기획서를 쓰다 보니 기능이 자꾸 늘어난다 | 늘어난 기능은 모두 "있으면 좋은 기능"에 적는다. 핵심 기능은 3개를 넘기지 않는다. |
| 무엇부터 만들어야 할지 모르겠다 | "PLAN.md의 핵심 기능을 실행해서 확인할 수 있는 작은 단계로 쪼개 줘"라고 요청한다. |
| Claude Code가 한 번에 너무 많이 만든다 | 작업을 중단하고 "이번 단계만 만들어 줘"라고 요청한다. CLAUDE.md에 "한 번에 한 단계씩만 만들어 줘" 규칙을 추가한다. |
| 다음 날 다시 시작했더니 AI가 상황을 모른다 | "PLAN.md를 읽고 어디까지 했는지 알려 줘"라고 요청하거나, `claude --continue`로 지난 대화를 이어 간다. |
| 대화가 길어져 응답이 느리고 엉뚱하다 | 지금까지의 작업을 커밋하고 `/clear`로 비운다. 작업 중이라면 `/compact`로 요약한다. |
| 실제 데이터가 있어야 테스트할 수 있다 | 실제 데이터의 열 이름과 형식만 알려 주고 가짜 데이터를 만들어 달라고 한다(6장). |
| 필요한 API가 유료이거나 승인이 오래 걸린다 | 처음에는 가짜 데이터로 화면과 기능을 완성하고, API 연결은 "있으면 좋은 기능"으로 미룬다. |
| 시간 안에 끝나지 않을 것 같다 | 핵심 기능을 하나로 줄이고, 그 하나를 확실하게 완성한다. 동작하는 작은 것이 낫다. |

## 7. 정리

### 핵심 요약

1. 좋은 첫 프로젝트는 **내 문제를 해결하고, 작고, 배운 것으로 만들 수 있고, 결과가 눈에 보이는** 프로젝트다.
2. 처음에는 핵심 기능 하나가 동작하는 **가장 작은 버전(MVP)** 을 만든다. 생각난 기능은 "있으면 좋은 기능"에 적어 둔다.
3. 한 장 기획서의 **완성 기준**은 직접 확인할 수 있게 쓰고, 검증 방법을 포함한다.
4. **계획 → 구현 → 확인 → 커밋** 사이클을 기능마다 짧게 반복한다.
5. 긴 작업은 **PLAN.md**에 진행 상황을 기록하고, **기능 하나 = 대화 하나**로 관리한다.

### 요청문 템플릿

**기획서 검토**
```
아래 기획서가 코딩 초보자가 3시간 안에 핵심 기능을 완성할 수 있는 크기인지 평가해 줘. 너무 크다면 무엇을 줄이면 좋을지 알려 줘. 코드는 아직 만들지 마.
(기획서)
```

**다음 단계 계획 (Plan 모드)**
```
PLAN.md의 진행 상황에서 다음 할 일을 만들 계획을 세워 줘.
```

**완성 후 정리**
```
잘 동작해. 커밋하고 PLAN.md 진행 상황을 갱신해 줘.
```

**작업 재개**
```
PLAN.md를 읽고 지금까지 어디까지 했는지, 다음에 할 일이 무엇인지 알려 줘.
```

### 용어 사전

| 용어 | 뜻 |
|---|---|
| 범위 | 프로젝트에서 만들기로 정한 기능의 크기와 양 |
| MVP | 핵심 기능 하나가 동작하는 가장 작은 버전 (최소 기능 제품) |
| 한 장 기획서 | 문제, 핵심 기능, 데이터, 완성 기준을 한 장에 정리한 문서 |
| 완성 기준 | 프로젝트가 완성되었는지 직접 확인할 수 있는 조건 |
| 개발 사이클 | 계획 → 구현 → 확인 → 커밋을 반복하는 흐름 |
| PLAN.md | 기획서와 진행 상황 체크리스트를 담아 프로젝트 폴더에 두는 파일 |
| `/compact` | 지금까지의 대화를 요약해 남기고 나머지를 비우는 명령 |

### 스스로 점검하기

- [ ] 1-4의 기준으로 아이디어를 비교해 하나를 골랐다.
- [ ] 아이디어에서 위험 신호를 찾아 범위를 줄였다.
- [ ] 직접 확인할 수 있는 완성 기준이 들어간 한 장 기획서를 썼다.
- [ ] 기획서를 Claude Code에게 검토받고 반영했다.
- [ ] PLAN.md와 CLAUDE.md를 만들고 첫 커밋을 했다.
- [ ] 기능마다 계획 → 구현 → 확인 → 커밋 사이클을 돌렸다.
- [ ] 기능을 완성할 때마다 대화를 비우고 다음 기능을 시작했다.

## 8. 과제

최종 프로젝트의 **핵심 기능을 완성**하고 GitHub에 커밋한다.

### 진행 방법

1. PLAN.md의 진행 상황에서 남은 핵심 기능을 5-4의 사이클로 완성한다.
2. 기획서의 **완성 기준**을 하나씩 직접 확인한다.
3. 모든 작업을 커밋하고 GitHub에 올린다.
4. 10장 발표를 위해 다음 내용을 메모해 둔다.
   - 어떤 문제를 해결하려 했나?
   - 가장 어려웠던 점과 어떻게 해결했나?
   - AI와 일하며 배운 점은 무엇인가?

### 제출할 것

1. GitHub 저장소 주소 (PLAN.md의 핵심 기능이 모두 체크되어 있어야 한다)
2. 완성 기준을 확인한 결과 (기준마다 확인 방법과 결과를 한 줄씩)

> 💡 10장에서는 이 프로젝트를 인터넷에 배포한다. Streamlit 웹 앱이라면 `uv run streamlit run app.py`로 문제없이 실행되는지 미리 확인해 둔다. 터미널 프로그램이라면 발표 때 내 컴퓨터에서 시연할 순서를 정리해 둔다.
