## 1. 버전 관리와 Git

### 1-1. 왜 버전 관리가 필요한가

문서 작업을 하다 보면 이런 파일들이 생기곤 한다.

```
보고서.docx
보고서_수정.docx
보고서_최종.docx
보고서_최종_진짜최종.docx
보고서_최종_진짜최종_팀장님검토반영.docx
```

어느 파일이 최신인지, 각 파일에서 무엇이 바뀌었는지 알기 어렵다. 프로그램도 마찬가지다. 잘 동작하던 코드를 고쳤다가 망가지면 **잘 동작하던 때로 돌아가고 싶어진다.**

**버전 관리**는 파일의 변경 이력을 기록해서, 언제 무엇이 바뀌었는지 확인하고 원하는 시점으로 되돌릴 수 있게 하는 것이다. **Git**은 가장 널리 쓰이는 버전 관리 도구다.

### 1-2. Git은 게임의 세이브 포인트다

어려운 게임을 할 때는 보스를 만나기 전에 저장해 둔다. 지더라도 저장한 지점에서 다시 시작하면 된다. Git도 같다.

- 프로그램이 **잘 동작할 때마다 세이브 포인트(커밋)를 만든다.**
- 코드를 고치다 망가지면 **마지막 세이브 포인트로 돌아간다.**
- 세이브 포인트 목록을 보면 **프로그램이 어떻게 발전해 왔는지** 한눈에 보인다.

세이브 포인트가 있으면 실수를 두려워하지 않고 새로운 시도를 할 수 있다. 이 장의 제목이 "실수해도 괜찮은 환경"인 이유다.

### 1-3. 핵심 용어

| 용어 | 뜻 | 게임 비유 |
|---|---|---|
| **저장소**(repository) | Git이 변경 이력을 기록하는 프로젝트 폴더 | 세이브 파일이 있는 게임 |
| **커밋**(commit) | 특정 시점의 파일 상태를 저장한 것 | 세이브 포인트 |
| **커밋 메시지** | 커밋마다 붙이는 설명 | 세이브 슬롯 이름 ("보스 직전") |
| **커밋 기록**(log) | 지금까지의 커밋 목록 | 세이브 슬롯 목록 |
| **변경 사항**(diff) | 마지막 커밋 이후 바뀐 내용 | 저장 이후 진행한 내용 |

> 💡 Git 명령을 외울 필요는 없다. Claude Code에게 말로 요청하면 알맞은 명령을 실행해 준다. 이 장에서는 **무엇을 요청할지**와 **결과를 어떻게 확인할지**를 익힌다.

### 1-4. `/rewind`와 Git은 무엇이 다른가

3장에서 배운 `/rewind`도 되돌리는 기능이다. 둘의 차이는 다음과 같다.

| 구분 | `/rewind` | Git 커밋 |
|---|---|---|
| 되돌릴 수 있는 것 | Claude Code가 고친 파일만 | 내가 직접 고친 것을 포함한 모든 파일 |
| 저장 기간 | 대화 중 임시 저장 | 지우지 않는 한 영구 저장 |
| 저장 시점 | 요청할 때마다 자동 | 내가 원할 때 직접 만든다 |
| 다른 컴퓨터와 공유 | 불가능 | GitHub에 올려 공유 가능 |
| 비유 | 문서 편집기의 실행 취소(`Ctrl+Z`) | 문서를 날짜별로 따로 보관 |

`/rewind`는 방금 한 요청을 빠르게 취소할 때, Git은 **잘 동작하는 상태를 확실하게 보관**할 때 쓴다.

### 1-5. `.gitignore`: 저장소에 넣지 않을 파일

모든 파일을 저장소에 넣으면 안 된다. `.gitignore` 파일에 적힌 파일과 폴더는 Git이 무시한다.

| 넣지 않을 파일 | 이유 |
|---|---|
| `.venv/` | 가상환경은 `uv sync`로 언제든 다시 만들 수 있고 용량이 크다. |
| `__pycache__/` | 파이썬이 실행할 때 자동으로 만드는 임시 파일이다. |
| `todos.json` 같은 개인 데이터 | 내 개인 정보가 인터넷에 공개될 수 있다. |
| `.env` 같은 비밀 정보 파일 | 비밀번호·API 키가 노출된다(7장에서 배운다). |

4장에서 `uv init`이 만든 `.gitignore`에는 이미 `.venv`와 `__pycache__/`가 들어 있다.

## 2. GitHub

### 2-1. Git과 GitHub의 차이

| 구분 | Git | GitHub |
|---|---|---|
| 정체 | 내 컴퓨터에서 동작하는 프로그램 | 인터넷 서비스(웹사이트) |
| 하는 일 | 변경 이력을 기록하고 되돌린다 | Git 저장소를 인터넷에 보관하고 공유한다 |
| 비유 | 내 공책 | 공책을 보관하는 클라우드 서비스 |

내 컴퓨터의 저장소를 GitHub에 올려 두면 다음과 같은 장점이 있다.

- 컴퓨터가 고장 나도 코드가 **안전하게 보관**된다.
- 다른 컴퓨터에서 **같은 코드를 내려받아** 작업할 수 있다.
- 다른 사람에게 **링크 하나로 내 작품을 보여 줄** 수 있다.
- 10장에서 웹 앱을 **인터넷에 배포**할 때 GitHub 저장소를 사용한다.

GitHub에 있는 저장소를 **원격 저장소**, 내 컴퓨터에 있는 저장소를 **로컬 저장소**라고 한다. 로컬 저장소의 커밋을 원격 저장소로 올리는 것을 **푸시**(push)라고 한다.

### 2-2. 공개 저장소와 비공개 저장소

| 구분 | 공개(public) | 비공개(private) |
|---|---|---|
| 볼 수 있는 사람 | 인터넷의 누구나 | 나와 내가 초대한 사람 |
| 쓰임 | 포트폴리오, 작품 공유 | 개인 작업, 회사 업무 |

> ⚠️ 공개 저장소에 올린 파일은 누구나 볼 수 있고, 지워도 이미 다른 사람이 복사했을 수 있다. 올리기 전에 **개인 정보와 비밀 정보가 없는지** 반드시 확인한다.

## 3. 환경 설정

### 3-1. Git 설치 확인

터미널에 다음 명령을 입력한다.

```bash
git --version
```

`git version 2.xx.x`처럼 버전이 나오면 이미 설치된 것이다. 나오지 않으면 운영체제에 맞게 설치한다.

- **macOS**: `git --version`을 입력했을 때 "명령어 라인 개발자 도구를 설치하겠습니까?" 창이 뜨면 **설치**를 누른다.
- **Windows**: https://git-scm.com 에서 Git for Windows를 내려받아 설치한다. 설치 중 선택 화면은 기본값을 그대로 둔다. 1장에서 Claude Code를 설치할 때 이미 설치했을 수 있다.

### 3-2. GitHub 가입

1. https://github.com 에 접속해 **Sign up**으로 가입한다.
2. 아이디(username)는 저장소 주소에 들어가므로(`github.com/아이디/저장소`) 신중하게 정한다.
3. 가입한 이메일로 온 인증 메일을 확인한다.

### 3-3. Git 사용자 정보 설정

Git은 커밋마다 **누가 만들었는지**(이름과 이메일)를 기록한다. 처음 한 번만 설정하면 된다.

```bash
git config --global user.name "홍길동"
git config --global user.email "내-이메일"
```

> ⚠️ 커밋에 기록된 이메일은 공개 저장소에서 누구나 볼 수 있다. 개인 이메일을 공개하고 싶지 않다면 GitHub에서 **Settings → Emails → Keep my email addresses private**을 켜고, 화면에 나오는 `숫자+아이디@users.noreply.github.com` 형태의 주소를 대신 사용한다.

### 3-4. GitHub CLI(`gh`) 설치와 로그인

**GitHub CLI**(`gh`)는 터미널에서 GitHub를 다루는 도구다. Claude Code가 GitHub에 저장소를 만들고 코드를 올릴 때 사용한다.

**설치**

- **macOS**: Homebrew가 있다면 `brew install gh`, 없다면 https://cli.github.com 에서 내려받아 설치한다.
- **Windows (PowerShell)**: `winget install --id GitHub.cli`

설치가 끝나면 터미널을 새로 열고 `gh --version`으로 확인한다.

**로그인**

로그인은 질문에 하나씩 답하며 진행하는 명령이라, Claude Code에게 맡기지 않고 **두 번째 터미널에서 직접** 실행한다.

```bash
gh auth login
```

질문마다 다음과 같이 선택한다(화살표 키로 고르고 `Enter`).

| 질문 | 선택 |
|---|---|
| Where do you use GitHub? | GitHub.com |
| What is your preferred protocol for Git operations? | HTTPS |
| Authenticate Git with your GitHub credentials? | Yes |
| How would you like to authenticate GitHub CLI? | Login with a web browser |

화면에 나온 **일회용 코드**(예: `ABCD-1234`)를 복사한 뒤 `Enter`를 누르면 브라우저가 열린다. 코드를 붙여 넣고 승인하면 로그인이 끝난다. 다음 명령으로 확인한다.

```bash
gh auth status
```

`Logged in to github.com account (내 아이디)`가 보이면 성공이다.

## 4. Claude Code와 Git 함께 쓰기

### 4-1. Git 작업은 말로 요청한다

| 하고 싶은 일 | 요청 예시 | Claude Code가 실행하는 명령 |
|---|---|---|
| 상태 확인 | `지금 바뀐 파일이 뭐가 있는지 알려 줘.` | `git status` |
| 변경 내용 확인 | `마지막 커밋 이후 무엇이 바뀌었는지 쉽게 설명해 줘.` | `git diff` |
| 커밋 | `지금 상태를 커밋해 줘.` | `git add`, `git commit` |
| 기록 보기 | `커밋 기록을 보여 주고 각 커밋에서 무엇이 바뀌었는지 설명해 줘.` | `git log` |
| 커밋 전으로 되돌리기 | `main.py를 마지막 커밋 상태로 되돌려 줘.` | `git restore` |
| 커밋 취소하기 | `"검색 기능 추가" 커밋을 취소해 줘.` | `git revert` |
| GitHub에 올리기 | `GitHub에 올려 줘.` | `git push` |

Claude Code가 명령을 실행하기 전에 허락을 구하면, 명령이 무엇을 하는지 읽어 보고 승인한다. 모르겠다면 "이 명령이 무슨 일을 하는지 먼저 설명해 줘"라고 묻는다.

### 4-2. 좋은 커밋 메시지

커밋 메시지는 나중에 커밋 기록을 볼 때 **어느 시점으로 돌아갈지 고르는 단서**가 된다.

| 나쁜 예 | 좋은 예 |
|---|---|
| 수정 | 할 일 검색 기능 추가 |
| 오류 고침 | 없는 번호를 입력하면 멈추는 문제 수정 |
| asdf | README에 실행 방법 추가 |

Claude Code는 바뀐 내용을 보고 커밋 메시지를 알아서 써 준다. 한국어로 쓰게 하려면 CLAUDE.md에 규칙으로 적어 둔다(실습 4단계).

> 💡 Claude Code가 만든 커밋 메시지 끝에는 Claude가 함께 작업했다는 표시(`Co-Authored-By: Claude ...`)가 붙을 수 있다. 문제가 되는 것은 아니다.

### 4-3. VS Code에서 변경 사항 눈으로 보기

VS Code 왼쪽의 **소스 제어** 아이콘(갈라지는 선 모양)을 누르면 마지막 커밋 이후 바뀐 파일 목록이 보인다.

| 표시 | 뜻 |
|---|---|
| `M` (Modified) | 내용이 바뀐 파일 |
| `U` (Untracked) | 새로 생겨서 아직 Git이 관리하지 않는 파일 |
| `D` (Deleted) | 지워진 파일 |

파일 이름을 클릭하면 바뀌기 전과 후가 나란히 표시된다. **빨간색**은 지워진 줄, **초록색**은 추가된 줄이다. 커밋하기 전에 여기서 무엇이 바뀌었는지 훑어보는 습관을 들인다.

### 4-4. 되돌리기 전에 꼭 알아 둘 것

> ⚠️ **커밋하지 않은 변경 사항을 "마지막 커밋 상태로 되돌리면" 그 변경 사항은 영원히 사라진다.** 되돌리기 전에 정말 버려도 되는 내용인지 확인한다. 그래서 **잘 동작하면 바로 커밋**하는 습관이 중요하다.

| 상황 | 요청 | 결과 |
|---|---|---|
| 커밋 후에 고친 내용을 버리고 싶다 | `마지막 커밋 상태로 되돌려 줘.` | 커밋하지 않은 변경이 사라진다. |
| 이미 커밋한 기능을 취소하고 싶다 | `"○○" 커밋을 취소해 줘.` | 그 커밋을 거꾸로 적용한 **새 커밋**이 생긴다. 기록은 지워지지 않는다. |

### 4-5. 터미널(CLI)과 VS Code 확장의 사용법 비교

Git 작업은 Claude Code에게 말로 요청하므로 터미널(CLI)과 VS Code 확장의 사용법이 같다.

| 기능 | 터미널(CLI) | VS Code 확장 |
|---|---|---|
| Git 작업 요청 | 입력창에 요청 | 입력창에 요청 |
| 변경 사항 확인 | VS Code 소스 제어 화면 또는 Claude Code에게 요청 | VS Code 소스 제어 화면 또는 Claude Code에게 요청 |
| `gh auth login` | 두 번째 터미널에서 직접 실행 | VS Code 터미널에서 직접 실행 |

## 5. 실습: 할 일 관리 프로그램을 GitHub에 올리기

### 5-1. 시작 준비

4장에서 만든 `todo` 프로젝트에서 시작한다.

```bash
cd ~/vibe-coding/todo
code .
```

VS Code에서 **터미널 → 새 터미널**을 열고 `claude`를 입력한다(VS Code 확장을 쓴다면 Claude Code 패널을 연다). 이 장 3절의 환경 설정(Git 설치, GitHub 가입, 사용자 정보 설정, `gh` 로그인)을 먼저 마친다.

### 5-2. 1단계: 저장소 확인하기

```
이 폴더가 Git 저장소인지 확인해 줘. 저장소가 아니면 Git 저장소로 만들어 줘.
```

4장에서 `uv init`을 실행했다면 이미 Git 저장소이고 아직 커밋은 없다는 답이 나올 것이다. VS Code의 소스 제어 화면을 열면 모든 파일이 `U`(새 파일)로 표시된다.

### 5-3. 2단계: `.gitignore` 점검하기

```
.gitignore 파일에 무엇이 들어 있는지 하나씩 설명해 줘. 그리고 todos.json에는 내 개인적인 할 일이 들어 있으니 .gitignore에 추가해 줘.
```

추가가 끝나면 소스 제어 화면에서 `todos.json`이 목록에서 사라졌는지 확인한다. Git이 이 파일을 무시하기 시작한 것이다.

> 💡 `todos.json`이 저장소에 없어도 문제없다. 4장에서 "파일이 없으면 빈 목록으로 시작"하도록 만들었기 때문이다.

### 5-4. 3단계: 첫 번째 커밋 만들기

```
지금 상태를 첫 번째 커밋으로 저장해 줘. 커밋 메시지는 "할 일 관리 프로그램 첫 버전"으로 해 줘.
```

커밋이 끝나면 소스 제어 화면의 파일 목록이 비어 있다. 마지막 커밋 이후 바뀐 것이 없다는 뜻이다. 첫 번째 세이브 포인트가 만들어졌다.

```
커밋 기록을 보여 줘.
```

### 5-5. 4단계: CLAUDE.md에 커밋 규칙 추가하기

```
CLAUDE.md에 아래 규칙을 추가해 줘.
- 커밋 메시지는 한국어로, 무엇을 했는지 한 줄로 써 줘.
- 기능이 완성되고 동작을 확인하면 커밋할지 나에게 물어봐 줘.
```

규칙을 추가하면 `CLAUDE.md`가 바뀌므로 소스 제어 화면에 `M`으로 표시된다. 이 변경도 커밋한다.

```
방금 바꾼 CLAUDE.md를 커밋해 줘.
```

### 5-6. 5단계: 기능 추가하고 커밋하기

```
메뉴에 "6. 검색"을 추가해 줘. 검색어를 입력하면 제목에 그 검색어가 들어간 할 일만 보여 줘.
```

기능이 만들어지면 커밋하기 전에 다음을 확인한다.

1. VS Code 소스 제어 화면에서 `main.py`를 클릭해 무엇이 바뀌었는지 훑어본다.
2. 두 번째 터미널에서 `uv run main.py`로 실행해 검색 기능이 동작하는지 확인한다.

동작을 확인했으면 커밋한다. CLAUDE.md 규칙에 따라 Claude Code가 먼저 커밋할지 물어볼 수도 있다.

```
검색 기능이 잘 동작해. 커밋해 줘.
```

### 5-7. 6단계: 망가뜨리고 되돌리기

이번에는 **내가 직접** VS Code에서 `main.py`를 망가뜨린다. `save_todos` 함수 전체를 지우고 저장한다.

두 번째 터미널에서 실행하고 할 일을 추가해 보면 오류가 난다.

```
NameError: name 'save_todos' is not defined. Did you mean: 'show_todos'?
```

3장에서 배웠듯이 내가 직접 고친 내용은 `/rewind`로 되돌릴 수 없다. 하지만 Git으로는 되돌릴 수 있다.

```
main.py를 마지막 커밋 상태로 되돌려 줘.
```

다시 실행해서 프로그램이 정상으로 돌아왔는지 확인한다. 마지막 세이브 포인트로 돌아간 것이다.

### 5-8. 7단계: 이미 커밋한 기능 취소하기

검색 기능을 빼기로 했다고 가정한다.

```
"할 일 검색 기능 추가" 커밋을 취소해 줘. 기록은 지우지 말고 취소하는 커밋을 새로 만들어 줘.
```

```
커밋 기록을 보여 줘.
```

기록은 대략 다음과 같다.

```
db0d3eb Revert "할 일 검색 기능 추가"
7b2e8d4 할 일 검색 기능 추가
5c1a0f9 CLAUDE.md에 커밋 규칙 추가
67dfec5 할 일 관리 프로그램 첫 버전
```

검색 기능 커밋은 기록에 그대로 남아 있고, 그 위에 취소 커밋이 새로 쌓였다. 실행해서 메뉴에서 검색이 사라졌는지 확인한다. 마음이 바뀌면 다시 살릴 수도 있다.

```
방금 취소한 검색 기능을 다시 살려 줘.
```

다시 살리면 `Reapply "할 일 검색 기능 추가"` 커밋이 하나 더 쌓인다. 취소도, 되살리기도 모두 기록으로 남는다.

### 5-9. 8단계: GitHub에 올리기

```
GitHub에 vibe-todo라는 공개 저장소를 만들어서 올려 줘. 올리기 전에 어떤 파일이 올라가는지 목록을 먼저 보여 줘.
```

Claude Code가 보여 주는 파일 목록에 `todos.json`이나 `.venv`가 없는지 확인한 뒤 승인한다. Claude Code는 대략 다음 명령을 실행한다.

```bash
gh repo create vibe-todo --public --source=. --push
```

올리기가 끝나면 브라우저에서 `https://github.com/(내 아이디)/vibe-todo`에 접속해 확인한다.

- 파일 목록에 `main.py`, `pyproject.toml`, `CLAUDE.md` 등이 있는가?
- `todos.json`과 `.venv`는 없는가?
- 커밋 기록(**Commits**)에 내가 만든 커밋들이 보이는가?

### 5-10. 9단계: 수정하고 다시 올리기

GitHub 저장소 첫 화면에는 `README.md` 내용이 표시되는데, 지금은 비어 있다. 프로그램 설명을 채운다.

```
README.md에 이 프로그램이 무엇인지, 어떤 기능이 있는지, uv로 설치하고 실행하는 방법을 써 줘. 다 쓰면 커밋하고 GitHub에 올려 줘.
```

브라우저에서 저장소 페이지를 새로 고쳐 README가 표시되는지 확인한다. 이제부터는 **고치기 → 확인 → 커밋 → 올리기**를 반복하면 된다.

## 6. 문제가 생겼을 때

| 증상 | 해결 방법 |
|---|---|
| `git: command not found` 또는 "인식할 수 없는 명령" | 3-1의 방법으로 Git을 설치하고 터미널을 새로 연다. |
| `Author identity unknown` 또는 `Please tell me who you are` | Git 사용자 정보가 없는 것이다. 3-3의 `git config` 명령을 실행한다. |
| `gh: command not found` | 3-4의 방법으로 GitHub CLI를 설치하고 터미널을 새로 연다. |
| GitHub에 올릴 때 로그인 오류가 난다 | 두 번째 터미널에서 `gh auth status`로 확인하고, 로그인되어 있지 않으면 `gh auth login`을 다시 실행한다. |
| 같은 이름의 저장소가 이미 있다는 오류가 난다 | 다른 이름(예: `vibe-todo-2`)으로 만들어 달라고 요청한다. |
| 올리면 안 되는 파일을 GitHub에 올렸다 | 개인 정보라면 GitHub 저장소를 지우고, `.gitignore`에 추가한 뒤 새로 만드는 것이 가장 확실하다. 비밀번호·API 키라면 즉시 해당 키를 폐기하고 새로 발급받는다(7장). 파일을 지우고 다시 올려도 커밋 기록에는 남는다. |
| 되돌렸더니 작업한 내용이 사라졌다 | 커밋하지 않은 변경은 되돌리면 복구할 수 없다. 앞으로는 잘 동작할 때마다 커밋한다. |
| GitHub에 올릴 때 `rejected` 오류가 난다 | GitHub 웹사이트에서 파일을 직접 고친 경우 생긴다. "GitHub의 변경 사항을 먼저 내려받고 다시 올려 줘"라고 요청한다. |
| 커밋 메시지가 영어로 만들어진다 | CLAUDE.md에 "커밋 메시지는 한국어로" 규칙을 추가하고 대화를 새로 시작한다. |

## 7. 정리

### 핵심 요약

1. **Git**은 파일의 변경 이력을 기록하는 도구이고, **커밋**은 게임의 세이브 포인트다.
2. 잘 동작할 때마다 커밋하면, 망가뜨려도 언제든 마지막 커밋으로 돌아갈 수 있다. **"작동하면 커밋"** 을 습관으로 만든다.
3. `/rewind`는 대화 중 임시 되돌리기이고, Git은 내가 직접 고친 것까지 포함해 영구적으로 보관한다.
4. **GitHub**는 Git 저장소를 인터넷에 보관하고 공유하는 서비스다. 로컬의 커밋을 GitHub로 올리는 것을 **푸시**라고 한다.
5. 개인 정보와 비밀 정보는 `.gitignore`에 넣어 저장소에 들어가지 않게 한다. 공개 저장소에 올리기 전에 반드시 확인한다.

### 요청문 템플릿

**작동하면 커밋**
```
[기능]이 잘 동작하는 것을 확인했어. 커밋해 줘.
```

**변경 확인**
```
마지막 커밋 이후 무엇이 바뀌었는지 쉽게 설명해 줘.
```

**되돌리기**
```
[파일 이름]을 마지막 커밋 상태로 되돌려 줘.
```

**GitHub에 올리기**
```
GitHub에 [저장소 이름]이라는 [공개/비공개] 저장소를 만들어서 올려 줘. 올리기 전에 어떤 파일이 올라가는지 목록을 먼저 보여 줘.
```

### 용어 사전

| 용어 | 뜻 |
|---|---|
| 버전 관리 | 파일의 변경 이력을 기록하고 원하는 시점으로 되돌릴 수 있게 하는 것 |
| Git | 가장 널리 쓰이는 버전 관리 도구 |
| 저장소(repository) | Git이 변경 이력을 기록하는 프로젝트 폴더 |
| 커밋(commit) | 특정 시점의 파일 상태를 저장한 것 |
| 커밋 메시지 | 커밋마다 붙이는, 무엇을 했는지에 대한 설명 |
| 변경 사항(diff) | 마지막 커밋 이후 바뀐 내용 |
| `.gitignore` | Git이 무시할 파일과 폴더를 적어 두는 파일 |
| GitHub | Git 저장소를 인터넷에 보관하고 공유하는 서비스 |
| 원격 저장소 | GitHub처럼 인터넷에 있는 저장소 |
| 로컬 저장소 | 내 컴퓨터에 있는 저장소 |
| 푸시(push) | 로컬 저장소의 커밋을 원격 저장소로 올리는 것 |
| GitHub CLI(`gh`) | 터미널에서 GitHub를 다루는 도구 |

### 스스로 점검하기

- [ ] 버전 관리가 왜 필요한지 설명할 수 있다.
- [ ] 저장소, 커밋, 원격 저장소의 뜻을 말할 수 있다.
- [ ] `/rewind`와 Git의 차이를 설명할 수 있다.
- [ ] Claude Code에게 요청해서 커밋하고, 커밋 기록을 확인했다.
- [ ] VS Code 소스 제어 화면에서 변경 사항을 확인했다.
- [ ] 직접 망가뜨린 파일을 마지막 커밋 상태로 되돌렸다.
- [ ] `.gitignore`에 개인 데이터 파일을 추가했다.
- [ ] 프로젝트를 GitHub에 올리고, 브라우저에서 확인했다.

## 8. 과제

1~3장에서 만든 프로그램들을 하나의 저장소로 모아 GitHub에 올린다.

### 진행 방법

1. `vibe-coding` 폴더 안에 `basics` 폴더를 만들고, Claude Code에게 요청해서 `hello.py`, `game.py`, `quiz.py`를 그 안으로 옮긴다.
2. `basics` 폴더에서 Claude Code를 시작하고, Git 저장소로 만들어 첫 커밋을 만든다.
3. `README.md`에 각 프로그램이 무엇인지, 어떻게 실행하는지 써 달라고 요청하고 커밋한다.
4. GitHub에 `vibe-basics`라는 공개 저장소를 만들어 올린다.
5. 4장 과제(마감일, 오늘 할 일 보기)도 `todo` 프로젝트에 커밋하고 GitHub에 올린다.

### 제출할 것

1. `vibe-basics` 저장소 주소
2. `vibe-todo` 저장소 주소 (4장 과제가 반영된 커밋이 보여야 한다)

> 💡 다음 장부터는 기능 하나가 완성될 때마다 **"잘 동작해. 커밋해 줘."** 를 요청하는 것을 습관으로 만든다. 세이브 포인트가 많을수록 마음 놓고 새로운 시도를 할 수 있다.
