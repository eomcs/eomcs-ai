# 10장. 배포와 발표

> 이 장에서는 내 컴퓨터에서만 동작하던 웹 앱을 인터넷에 배포해 누구나 쓸 수 있게 만들고, 최종 프로젝트와 바이브 코딩 경험을 발표한다. 과정의 마지막 장이다.

- **Streamlit Community Cloud**에 GitHub 저장소를 연결해 웹 앱을 배포한다.
- 배포 오류를 로그로 확인하고 Claude Code와 함께 해결한다.
- 프로젝트를 README로 소개하고, 5분 동안 발표한다.

## 1. 배포란?

### 1-1. 내 컴퓨터와 서버

8장에서 앱을 실행하면 `http://localhost:8501`이라는 주소가 나왔다. `localhost`는 "내 컴퓨터"라는 뜻이다. 이 주소는 **내 컴퓨터에서만** 열린다. 친구에게 알려 줘도 친구의 컴퓨터에는 내 앱이 없으므로 열리지 않는다. 내 노트북을 끄면 앱도 꺼진다.

**배포**는 앱을 **24시간 켜져 있는 인터넷의 컴퓨터(서버)** 에 올려서, 누구나 주소로 접속해 쓸 수 있게 하는 것이다.

| 구분 | 내 컴퓨터에서 실행 | 배포 |
|---|---|---|
| 주소 | `http://localhost:8501` | `https://○○.streamlit.app` |
| 쓸 수 있는 사람 | 나만 | 주소를 아는 누구나 |
| 켜져 있는 시간 | 내가 켜 둔 동안만 | 언제나 |
| 비유 | 집에서 요리해 먹기 | 식당을 열어 손님 받기 |

### 1-2. Streamlit Community Cloud

웹 앱을 배포하는 방법은 여러 가지가 있지만, 서버를 직접 빌리고 설정하는 것은 초보자에게 어렵다. **Streamlit Community Cloud**는 Streamlit 앱을 **무료로** 배포해 주는 서비스다.

- GitHub 저장소를 연결하기만 하면 서버 설정을 알아서 해 준다.
- GitHub에 새 커밋을 올리면 배포된 앱도 **자동으로 갱신**된다.
- `○○.streamlit.app` 형태의 주소를 무료로 준다.

5장에서 GitHub에 코드를 올리는 법을 배운 이유가 여기에 있다.

### 1-3. 배포 전에 알아 둘 것

서버는 내 컴퓨터와 다른 **새 컴퓨터**다. 내 컴퓨터에만 있는 것은 서버에 없다.

| 내 컴퓨터에만 있는 것 | 서버에서 생기는 문제 | 해결 방법 |
|---|---|---|
| `uv add`로 설치한 패키지 | 패키지가 없어 `ModuleNotFoundError` | 의존성 목록 파일을 저장소에 넣는다 (2-1) |
| `.env`의 API 키 | `.env`는 GitHub에 올리지 않았으므로 키가 없다 | 배포 서비스의 **Secrets**에 키를 넣는다 (2-2) |
| 앱이 저장한 파일 | 서버가 다시 시작되면 **사라진다** | 저장이 필요한 앱은 배포에 맞게 바꾼다 (2-3) |
| GitHub에 올리지 않은 데이터 파일 | `FileNotFoundError` | 필요한 예시 데이터는 저장소에 넣는다 (2-4) |

## 2. 배포 준비하기

### 2-1. 의존성 목록: `requirements.txt`

서버는 저장소의 **의존성 목록 파일**을 읽고 필요한 패키지를 설치한다. 4장에서 배운 `pyproject.toml`과 `uv.lock`에도 패키지 목록이 있지만, 가장 널리 쓰이는 형식인 **`requirements.txt`** 를 만들어 두면 확실하다. uv로 다음과 같이 만든다.

```bash
uv export --format requirements.txt --no-hashes --no-dev -o requirements.txt
```

만들어진 `requirements.txt`에는 설치된 패키지와 버전이 한 줄에 하나씩 적혀 있다.

```
# This file was autogenerated by uv via the following command:
#    uv export --format requirements.txt --no-hashes --no-dev -o requirements.txt
altair==6.3.0
    # via streamlit
...
openpyxl==3.1.5
pandas==3.1.1
...
streamlit==1.67.0
```

> ⚠️ 나중에 `uv add`로 패키지를 추가하면 `requirements.txt`도 **다시 만들어야** 한다. CLAUDE.md에 "패키지를 추가하면 requirements.txt도 다시 만들어 줘" 규칙을 넣어 두면 잊지 않는다.

### 2-2. 비밀 정보: Secrets

7장에서 API 키를 `.env`에 저장하고 GitHub에는 올리지 않았다. 그래서 서버에는 키가 없다. Streamlit Community Cloud에서는 앱 설정의 **Secrets** 칸에 키를 입력한다.

```toml
OPENWEATHER_API_KEY = "발급받은키"
```

- `.env`와 비슷하지만 **TOML 형식**이다. 값을 큰따옴표(`"`)로 감싸고, `=` 앞뒤에 빈칸이 있어도 된다.
- Secrets 칸에 맨 위 단계로 적은 값은 **환경 변수**로도 등록된다. 그래서 7장처럼 `os.getenv("OPENWEATHER_API_KEY")`로 키를 읽는 코드를 **고치지 않고** 그대로 쓸 수 있다.
- Secrets에 넣은 값은 앱 주인만 볼 수 있고, GitHub에는 올라가지 않는다.

### 2-3. 앱이 저장한 파일은 사라진다

4장의 할 일 관리 프로그램처럼 앱이 파일(`todos.json`)에 데이터를 저장하는 경우, Streamlit Community Cloud에서는 **서버가 다시 시작될 때 저장한 파일이 사라진다.** 서버는 앱을 갱신하거나, 오래 쓰지 않아 잠들었다 깨어날 때 다시 시작된다.

| 앱의 종류 | 배포해도 괜찮은가 |
|---|---|
| 사용자가 올린 파일을 분석해 보여 주는 앱 (8장 대시보드, 가계부 분석기) | 괜찮다. 저장할 것이 없다. |
| API에서 받아 온 정보를 보여 주는 앱 (7장 알리미) | 괜찮다. 매번 새로 받아 온다. |
| 사용자가 입력한 데이터를 파일에 계속 쌓는 앱 (할 일 관리, 맛집 기록장) | 데이터가 사라질 수 있다. |

데이터를 쌓는 앱이라면 다음 중 하나를 고른다.

- 발표용 시연이 목적이라면 **사라져도 괜찮다**는 점을 알고 배포한다.
- 데이터를 **내려받기·올리기** 버튼으로 사용자가 직접 보관하게 바꾼다. "저장된 데이터를 CSV로 내려받는 버튼과, 내려받은 CSV를 다시 올려 불러오는 기능을 만들어 줘"라고 요청한다.
- 영구 저장이 꼭 필요하면 Claude Code에게 방법을 물어본다. 외부 데이터베이스나 구글 스프레드시트를 연결하는 방법이 있지만, 이 과정의 범위를 넘는다.

### 2-4. 데이터 파일과 경로

- 앱이 읽는 예시 데이터 파일(예: `data/sales_2026.xlsx`)이 있다면 **가짜 데이터인지 확인한 뒤** 저장소에 넣는다.
- 파일 경로는 `C:\Users\gildong\...`나 `/Users/gildong/...`처럼 내 컴퓨터의 전체 경로가 아니라, `data/sales_2026.xlsx`처럼 **프로젝트 폴더 기준 경로**로 써야 서버에서도 찾을 수 있다.

### 2-5. 배포하면 공개된다

> ⚠️ 배포한 앱은 **주소를 아는 누구나** 쓸 수 있다. 다른 사람이 내 앱에 파일을 올리면 그 파일은 서버로 전송된다. 가계부 분석기처럼 개인 정보가 담긴 파일을 다루는 앱이라면, 배포한 앱에는 **가짜 데이터로 시연**하고 실제 내 카드 내역은 **내 컴퓨터에서 실행한 앱**에 올린다.

API 키를 쓰는 앱을 공개하면 다른 사람이 앱을 쓸 때마다 **내 키의 사용량**이 줄어든다. 무료 사용 한도를 넘지 않는지 확인한다.

## 3. Claude Code 기능 익히기: 배포 오류 해결과 README 작성

### 3-1. 배포 로그 읽기

배포하다 오류가 나면 Streamlit Community Cloud 화면에 오류 메시지가 나타난다. 앱 화면 오른쪽 아래의 **Manage app**을 누르면 서버에서 일어난 일이 시간 순서대로 기록된 **로그**가 보인다.

로그를 읽는 방법은 3장의 오류 메시지 읽는 법과 같다. **마지막 부분부터** 읽는다. 로그 전체를 복사해서 Claude Code에게 붙여 넣으면 원인을 함께 찾을 수 있다.

```
Streamlit Community Cloud에 배포했더니 아래 오류가 났어. 내 컴퓨터에서는 잘 동작해. 무엇이 문제인지 먼저 설명해 주고, 고쳐 줘.
(로그 붙여 넣기)
```

> ⚠️ 로그를 붙여 넣기 전에 API 키 같은 비밀 정보가 들어 있지 않은지 확인한다. 있다면 `***`로 가린다(7장).

### 3-2. "내 컴퓨터에선 되는데…"

배포 오류의 대부분은 **내 컴퓨터에는 있고 서버에는 없는 것** 때문에 생긴다. Claude Code에게 배포 전 점검을 요청하면 미리 찾아낼 수 있다.

```
이 앱을 Streamlit Community Cloud에 배포하려고 해. 배포하면 문제가 될 만한 것이 있는지 점검해 줘. 의존성 목록, 비밀 정보, 파일 경로, 앱이 저장하는 파일, 저장소에 없는 데이터 파일을 확인해 줘. 아직 고치지는 마.
```

### 3-3. README 작성하기

README는 저장소의 **얼굴**이다. GitHub 저장소 첫 화면에 표시되어, 처음 보는 사람에게 프로젝트를 소개한다. Claude Code에게 초안을 요청하고 **직접 다듬는다.**

```
README.md를 다시 써 줘. 아래 순서로, 처음 보는 사람도 이해할 수 있게 써 줘.
1. 프로젝트 이름과 한 줄 소개
2. 배포 주소 (https://○○.streamlit.app)
3. 어떤 문제를 해결하는지
4. 주요 기능
5. 사용 방법 (화면에서 무엇을 하면 되는지)
6. 내 컴퓨터에서 실행하는 방법 (uv 사용)
7. 사용한 기술
8. 만든 사람
```

초안을 받은 뒤 다음을 직접 고친다.

- **문제 설명**은 내 말로 쓴다. 왜 이 프로젝트를 만들었는지는 나만 알고 있다.
- AI가 지어낸 기능이 없는지 확인한다. 실제로 동작하는 기능만 남긴다.
- 앱 화면의 **스크린샷**을 넣으면 한눈에 무엇인지 알 수 있다. 스크린샷 파일을 `images` 폴더에 넣고 "README에 images/screenshot.png를 넣어 줘"라고 요청한다.

### 3-4. 터미널(CLI)과 VS Code 확장의 사용법 비교

배포 준비와 오류 해결은 요청으로 진행하므로 터미널(CLI)과 VS Code 확장의 사용법이 같다. 배포 설정은 Streamlit Community Cloud 웹사이트에서 한다.

| 기능 | 터미널(CLI) | VS Code 확장 |
|---|---|---|
| 배포 전 점검, 오류 해결, README 작성 | 입력창에 요청 | 입력창에 요청 |
| 로그 전달 | 로그를 복사해 붙여 넣기 | 같음 |
| 배포 설정, Secrets 입력 | Streamlit Community Cloud 웹사이트 | 같음 |

## 4. 실습: Streamlit Community Cloud에 배포하기

9장에서 만든 최종 프로젝트를 배포한다. 최종 프로젝트가 Streamlit 웹 앱이 아니라면, 8장에서 만든 **`vibe-dashboard`** 를 배포하며 과정을 익히고, 최종 프로젝트는 발표 때 내 컴퓨터에서 시연한다.

### 4-1. 1단계: 배포 전 점검

프로젝트 폴더에서 Claude Code를 시작하고 3-2의 점검을 요청한다.

```
이 앱을 Streamlit Community Cloud에 배포하려고 해. 배포하면 문제가 될 만한 것이 있는지 점검해 줘. 의존성 목록, 비밀 정보, 파일 경로, 앱이 저장하는 파일, 저장소에 없는 데이터 파일을 확인해 줘. 아직 고치지는 마.
```

점검 결과를 읽고, 고칠 것이 있으면 하나씩 고쳐 달라고 요청한다. 그다음 `requirements.txt`를 만든다.

```
uv export로 requirements.txt를 만들어 줘. 그리고 CLAUDE.md에 "패키지를 추가하면 requirements.txt도 다시 만들어 줘" 규칙을 추가해 줘.
```

### 4-2. 2단계: 내 컴퓨터에서 마지막 확인

두 번째 터미널에서 앱을 실행해 모든 기능이 동작하는지 확인한다.

```bash
uv run streamlit run app.py
```

> 💡 앱의 시작 파일 이름을 확인해 둔다(예: `app.py`, `main.py`). 배포 설정에서 입력해야 한다.

모든 변경을 커밋하고 GitHub에 올린다.

```
배포 준비를 마쳤어. 커밋하고 GitHub에 올려 줘. 올리기 전에 어떤 파일이 올라가는지 목록을 보여 주고, .env가 없는지 확인해 줘.
```

### 4-3. 3단계: Streamlit Community Cloud 가입

1. https://share.streamlit.io 에 접속한다.
2. **Continue with GitHub**를 눌러 GitHub 계정으로 가입한다.
3. Streamlit이 GitHub 저장소에 접근하도록 허락하는 화면이 나오면 승인한다.

### 4-4. 4단계: 앱 배포하기

1. **Create app**(또는 **New app**)을 누르고, GitHub 저장소에서 배포하는 방식을 고른다.
2. 다음 항목을 채운다.

| 항목 | 입력할 내용 |
|---|---|
| Repository | 내 저장소 (예: `내아이디/vibe-dashboard`) |
| Branch | `main` |
| Main file path | 앱의 시작 파일 (예: `app.py`) |
| App URL | 원하는 주소 이름. 영어 소문자와 `-`만 쓴다 (예: `gildong-dashboard`) |

3. **Advanced settings**를 열어 다음을 설정한다.
   - **Python version**: 프로젝트의 `.python-version` 파일에 적힌 버전과 같은 버전을 고른다.
   - **Secrets**: API 키가 필요한 앱이라면 2-2의 형식으로 입력한다. 필요 없으면 비워 둔다.
4. **Deploy**를 누른다.

처음 배포할 때는 서버가 패키지를 설치하느라 몇 분 걸린다. 화면 오른쪽에 설치 과정이 표시된다. 설치가 끝나면 내 앱이 나타난다.

### 4-5. 5단계: 배포된 앱 확인하기

- 브라우저 주소창의 `https://○○.streamlit.app` 주소를 복사한다.
- **스마트폰**으로 그 주소에 접속해 본다. 내 컴퓨터가 아닌 곳에서도 앱이 열린다.
- 모든 기능을 하나씩 써 본다. 특히 파일 올리기, 필터, API 정보가 내 컴퓨터에서와 똑같이 동작하는지 확인한다.
- 숫자가 나오는 앱이라면 6장처럼 검증해 둔 값과 비교한다. 8장 대시보드라면 서울·1월 필터에서 **27건, 11,880,000원**이 나와야 한다.

### 4-6. 6단계: 고치고 다시 배포하기

배포된 앱을 고치려면 내 컴퓨터에서 고친 뒤 **커밋하고 GitHub에 올리기만** 하면 된다. Streamlit Community Cloud가 바뀐 것을 알아채고 앱을 자동으로 갱신한다.

```
앱 제목 옆에 "(배포 버전)"이라고 붙여 줘. 확인하면 커밋하고 GitHub에 올려 줘.
```

GitHub에 올리고 1~2분 뒤 배포된 앱을 새로 고쳐 바뀌었는지 확인한다. 확인했으면 "(배포 버전)"은 다시 빼 달라고 요청한다.

### 4-7. 7단계: README 다듬기

3-3의 요청으로 README를 다시 쓰고, 배포 주소와 스크린샷을 넣는다. 직접 다듬은 뒤 커밋하고 GitHub에 올린다. GitHub 저장소 페이지에서 README가 잘 보이는지, 배포 주소를 누르면 앱이 열리는지 확인한다.

> 💡 GitHub 저장소 오른쪽의 **About** 옆 톱니바퀴를 누르면 저장소 설명과 웹사이트 주소를 넣을 수 있다. 배포 주소를 넣어 두면 저장소에서 바로 앱으로 갈 수 있다.

## 5. 발표하기

### 5-1. 5분 발표 구성

| 순서 | 시간 | 내용 |
|---|---|---|
| ① 문제 | 1분 | 누구의 어떤 문제를 해결하려 했나? 왜 이 프로젝트를 골랐나? |
| ② 시연 | 2분 | 배포된 앱을 직접 써 보이며 핵심 기능을 보여 준다. |
| ③ 어려웠던 점 | 1분 | 가장 어려웠던 순간은 언제였고, 어떻게 해결했나? |
| ④ 배운 점 | 1분 | AI와 함께 일하며 배운 점, 다음에 더 해 보고 싶은 것 |

> 💡 9장 과제에서 메모해 둔 내용(해결하려 한 문제, 어려웠던 점, 배운 점)이 발표의 뼈대가 된다.

### 5-2. 발표 자료 만들기

발표 자료는 길 필요가 없다. 3~5장이면 충분하다. 슬라이드 없이 README와 앱만으로 발표해도 된다.

Claude Code에게 발표 원고 초안을 요청할 수도 있다.

```
PLAN.md와 README.md, 커밋 기록을 읽고, 아래 순서로 5분 발표 원고 초안을 써 줘. 각 부분에 걸리는 시간도 적어 줘.
1. 문제 (1분)  2. 시연 순서 (2분)  3. 어려웠던 점 (1분)  4. 배운 점 (1분)
어려웠던 점과 배운 점은 내가 직접 채울 수 있게 빈칸으로 남겨 둬.
```

> ⚠️ 어려웠던 점과 배운 점은 **내 경험**이다. AI가 지어낸 그럴듯한 이야기보다, 짧더라도 내가 실제로 겪은 일이 훨씬 설득력 있다.

### 5-3. 시연 팁

- 발표 전에 배포된 앱을 **미리 열어** 둔다. 오래 쓰지 않은 앱은 잠들어 있어서 깨어나는 데 시간이 걸린다.
- 시연에 쓸 **예시 파일**을 바탕화면 같은 찾기 쉬운 곳에 준비해 둔다.
- 시연 순서를 정해 두고 한 번 연습한다. 2분은 생각보다 짧다.
- 인터넷 연결이나 서버 문제에 대비해 **앱 화면 스크린샷**을 준비해 둔다. 앱이 열리지 않으면 스크린샷으로 설명한다.

### 5-4. 동료 발표 피드백

### 6-4. 잊지 말아야 할 것

- **무엇을 만들지는 내가 정한다.** AI는 유능한 동료이지만, 문제를 정의하고 결과를 판단하는 것은 나의 몫이다.

## 7. 문제가 생겼을 때

| 증상 | 해결 방법 |
|---|---|
| 배포 중 `ModuleNotFoundError` | `requirements.txt`가 저장소에 있는지, 필요한 패키지가 들어 있는지 확인한다. `uv export`로 다시 만들고 커밋해서 올린다. |
| 저장소 목록에 내 저장소가 보이지 않는다 | Streamlit이 GitHub 저장소에 접근하도록 허락했는지 확인한다. 저장소를 GitHub에 올렸는지도 확인한다. |
| `FileNotFoundError` | 앱이 읽는 데이터 파일이 저장소에 있는지, 경로가 프로젝트 폴더 기준(`data/...`)인지 확인한다. |
| API 정보가 나오지 않는다 / `401` 오류 | 앱 설정(**Settings → Secrets**)에 키를 넣었는지, 이름이 코드와 같은지, 값을 큰따옴표로 감쌌는지 확인한다. |
| 패키지 설치 단계에서 오류가 난다 | Advanced settings의 Python 버전이 `.python-version`과 같은지 확인한다. 로그를 Claude Code에게 보여 준다. |
| 코드를 고쳤는데 배포된 앱이 그대로다 | 커밋하고 GitHub에 올렸는지 확인한다. 1~2분 기다린 뒤 새로 고친다. 그래도 그대로면 **Manage app**에서 **Reboot app**을 누른다. |
| 앱 주소에 들어가니 잠들어 있다는 화면이 나온다 | 오래 쓰지 않아 앱이 잠든 것이다. 깨우는 버튼을 누르고 잠시 기다린다. |
| 저장한 데이터가 사라졌다 | 2-3의 내용대로 서버가 다시 시작되면 파일이 사라진다. 내려받기·올리기 방식으로 바꾸는 것을 고려한다. |
| 원하는 App URL을 쓸 수 없다 | 이미 다른 사람이 쓰는 이름이다. 내 이름이나 아이디를 붙여 다른 이름으로 정한다. |

## 8. 정리

### 핵심 요약

1. **배포**는 앱을 24시간 켜져 있는 서버에 올려 누구나 주소로 쓸 수 있게 하는 것이다.
2. 서버는 새 컴퓨터다. **의존성 목록**(`requirements.txt`)을 저장소에 넣고, **비밀 정보**는 Secrets에 넣는다. 앱이 저장한 파일은 사라질 수 있다.
3. Streamlit Community Cloud는 GitHub 저장소를 연결해 배포하고, 새 커밋을 올리면 **자동으로 갱신**한다.
4. 배포 오류는 **로그의 마지막 부분**부터 읽고, 로그를 Claude Code에게 보여 주며 해결한다.
5. README와 발표에는 **내가 해결한 문제와 내 경험**을 내 말로 담는다.

### 요청문 템플릿

**배포 전 점검**
```
이 앱을 Streamlit Community Cloud에 배포하려고 해. 배포하면 문제가 될 만한 것이 있는지 점검해 줘. 의존성 목록, 비밀 정보, 파일 경로, 앱이 저장하는 파일, 저장소에 없는 데이터 파일을 확인해 줘. 아직 고치지는 마.
```

**배포 오류 해결**
```
Streamlit Community Cloud에 배포했더니 아래 오류가 났어. 내 컴퓨터에서는 잘 동작해. 무엇이 문제인지 먼저 설명해 주고, 고쳐 줘.
(로그 붙여 넣기)
```

**README 작성**
```
README.md를 처음 보는 사람도 이해할 수 있게 다시 써 줘. 프로젝트 소개, 배포 주소, 해결하는 문제, 주요 기능, 사용 방법, 내 컴퓨터에서 실행하는 방법, 사용한 기술 순서로 써 줘.
```

### 용어 사전

| 용어 | 뜻 |
|---|---|
| 배포 | 앱을 서버에 올려 다른 사람도 인터넷 주소로 쓸 수 있게 하는 것 |
| 서버 | 24시간 켜져 있으면서 요청에 응답하는 인터넷의 컴퓨터 |
| Streamlit Community Cloud | Streamlit 앱을 무료로 배포해 주는 서비스 |
| `requirements.txt` | 프로젝트에 필요한 패키지와 버전을 적은 의존성 목록 파일 |
| Secrets | 배포 서비스에 비밀 정보를 저장하는 설정 칸 |
| 로그 | 서버에서 일어난 일을 시간 순서대로 기록한 것 |
| 자동 갱신 | GitHub에 새 커밋을 올리면 배포된 앱도 바뀌는 것 |
| README | 저장소 첫 화면에 표시되는 프로젝트 소개 문서 |

## 9. 과제 (선택)

주변 사람 **3명**에게 배포한 앱을 써 보게 하고, 받은 피드백으로 앱을 개선한다.

### 진행 방법

1. 앱 주소를 보내기 전에, 무엇을 하는 앱인지 한두 문장으로 소개한다.
2. 앱을 쓰는 모습을 옆에서 지켜볼 수 있다면 **도와주지 말고** 지켜본다. 사용자가 어디서 머뭇거리는지가 가장 좋은 피드백이다.
3. 다음 질문으로 의견을 받는다.
   - 무엇을 하는 앱인지 바로 알 수 있었나?
   - 쓰다가 헷갈리거나 막힌 곳이 있었나?
   - 하나만 바꿀 수 있다면 무엇을 바꾸고 싶나?
4. 받은 의견 중 가장 많이 나온 것 하나를 골라 고치고, 커밋해서 배포한다.
